STM32 DMA 应用实战

前面那篇《DMA 与总线矩阵》回答的是 「DMA 是什么、它为什么能省 CPU」：总线矩阵怎么交叉、请求线怎么接到通道、 一次传输的握手长什么样、突发和 FIFO 为什么能摊薄开销、四个标志位分别代表什么。 那些是机制层的东西，换到任何一颗 STM32 上都成立。

这一篇换一个视角：把 DMA 用进一条真正的数据通道里。 我们只做一个项目——1kHz 采样、连续采 10 分钟、通过串口实时上传到上位机的数据采集器—— 然后把这件小事里所有的工程问题一个个挖出来：缓冲区的两半怎么分工、正在写的那一半为什么绝对不能读、 不定长的帧怎么保证一个字节都不丢、四路 DMA 同时跑的时候谁先走、你到底能不能证明DMA 省了 CPU、 出错之后怎么自己爬起来、丢进 RTOS 里又该怎么接、换一颗芯片要改哪些地方。

机制不重讲：凡是「请求线怎么映射到通道」「突发为什么快」「 CCR 每一位是什么」这类问题，本文只用一句话带过并给出回链， 这里只讲那些只有真的把数据采上一天、真的被上位机投诉过的人才会遇到的问题。 全文的代码都是在 STM32F103C8T6（72MHz、20KB SRAM、64KB Flash）上编译验证过的写法， 换型号的地方会单独标出来。

为什么需要它

先把这个项目说清楚。硬件：STM32F103C8T6 最小系统板（8MHz 晶振经 PLL 9 倍频到 72MHz）， 一路模拟传感器接到 PA0（ADC1_IN0），USB-TTL 模块接 PA9/PA10（USART1）， 上位机用串口助手或自己写的 Python 脚本收数。需求：以 1kHz 的固定节拍采样， 连续采 10 分钟，数据实时上传，上位机画波形。听起来是个大作业里最普通的一题，很多同学第一版两小时就能跑起来。

问题都出在「跑起来之后」。下面这四个现场，是我见过的、也是这一篇要逐个解决的。 如果你正在做类似的项目，大概会在其中至少一个里卡住。

现场一：波形看着挺好，一数点数少了 4 万个

第一版用的是老办法：TIM2 定时中断里做一次 ADC 单次转换，转完在中断里把结果拼成 ASCII 字符串、 用 printf 发出去。跑 10 秒看着完美，跑 10 分钟一统计：应该是 60 万个点， 实际只收到 56 万个左右，而且丢的地方很有规律——每次上位机点「清空显示」或者你手碰一下板子，就丢一小段。 根因：采样节拍由中断的「准点」保证，但中断里干了太多活。 printf 走的是阻塞发送，一个数 6~7 个字节、115200 下发要 0.6ms， 这段时间里 TIM2 的下一次中断来不了（同级不能抢占），节拍就被拉长了。

现场二：改成 DMA 之后，数据出现了「整段的旧值」

第二版学乖了：ADC 连续转换 + DMA 循环模式，缓冲区 1024 个半字，在传输完成中断里把整块打包发走。 波形大体对了，但每隔一段时间会看到一整段数值是上一个时刻的、像是"卡了一下又追上"。 根因：DMA 是循环走的，你在中断里处理整块的同时，它已经开始覆盖缓冲区的开头了。 1024 个点在 1kHz 下只够它走 1.024 秒，而你要打包 + 发送 + 等上位机应答，一旦超过这个时间， 你读到的就是「一半新数据、一半正在被覆盖的数据」。这不是 DMA 的 bug，是你没有给它划出"不许碰"的区域。

现场三：上位机永远拼不出一帧完整的命令

采集器要能被上位机控制（开始、停止、改采样率），所以还得收。上位机发的命令帧长度不固定 （帧头 2 字节 + 长度 + 若干参数字节 + 校验 + 帧尾），长度随命令而变。用「接收中断每来一个字节进一次」的写法， 1 个字节一次中断，在 115200 下每秒 1.15 万次中断；而且帧一旦被拆成两半（上位机分两次发）， 中断里的状态机就会把第二半当成新帧的帧头，从此永久错位——除非你手动拔插一次串口。 根因：逐字节中断的框架没有「帧边界」的概念，也没有「超时重同步」。

现场四：「用了 DMA，CPU 占用很低」——你怎么知道？

这一条不是故障，是大部分人的知识盲区。老师问「你这个方案 CPU 占用多少」，答案通常是「很低」「几乎不占」。 但「很低」是多少？是 0.1% 还是 8%？如果四路 DMA 同时在跑，总线被占掉 10%，会不会让主循环变慢？ 这些问题的答案不能靠感觉，得靠量——而量它需要 DWT 周期计数器或示波器， 以及一套「怎么量才不会被测量本身干扰」的方法。

四个现场看下来，规律很清楚：DMA 本身从来不是难点，难点是"DMA 与 CPU 共享同一块内存"这件事带来的一整套约定—— 谁在什么时候可以读写哪一块、边界由谁定义、处理不过来了怎么办、出错了谁知道。 这些约定没有人会在教程的第一页告诉你，因为它们不属于「DMA 的用法」，而属于数据通道的架构。

核心概念

这一节有七个子节，正好对应一个数据通道从「采」到「传」要过的七道关：

1

缓冲区的两半怎么分工（2.1）

DMA 一直在写，CPU 想读，怎么办？答案是「错开」——用半传输中断把缓冲区切成两半，两边各管一半。这一节给出三者的约束不等式。

2

怎么知道 DMA 现在写到哪了（2.2）

NDTR 反推写指针是个好技巧，但它在三种场合下会骗你。搞清楚哪三种，这个技巧才好用。

3

收进来的字节怎么切成「帧」（2.3）

IDLE 中断 + DMA 给出天然的帧边界，但中断里只该记账，不该解析。这一节给出三层结构、帧格式设计和超时重同步。

4

四路 DMA 同时跑，谁先走（2.4）

通道仲裁和总线仲裁是两层，优先级只能在其中一层起作用。这一节给出带宽预算的算法和「哪一路该最高」的判据。

5

怎么证明 DMA 真省了 CPU（2.5）

DWT 周期计数器和 GPIO 翻转 + 示波器，两种办法各有各的坑，也各有各的适用场合。

6

出错了怎么知道、怎么爬起来（2.6）

TE 会自己把通道关掉，FE 和 DME 不会但数据已经错了。这一节讲三种错误的发生条件和重启姿势。

7

丢进 RTOS、换一颗芯片（2.7、2.8）

回调里只能发消息不能干活；F1 的通道、F4 的数据流 + 仲裁器、H7 的 DMAMUX 是三套不同的模型，M7 还多一个 cache 要照顾。

环形缓冲：把「正在写的那一半」隔开

任何一个采集系统都可以拆成三个角色：生产者（ADC，以 1kHz 的固定节奏吐出数据）、 缓冲（SRAM 里的一块数组）、消费者（主循环：打包、发串口、必要时存 Flash）。 生产者不管消费者在不在，消费者也追不上生产者的节奏，两者唯一的接口就是那块缓冲。设计数据通道，本质上就是设计这块缓冲的「交接规则」。

ADC + DMA 的循环模式给了我们一个非常廉价的实现：让 DMA 把这块数组当作一个圈，写到末尾就自动回到开头。 代码只需要 HAL_ADC_Start_DMA(&hadc1, (uint32_t*)adc_buf, ADC_BUF_LEN)， 加上 hdma_adc1.Init.Mode = DMA_CIRCULAR，硬件就会一直转下去，CPU 一个周期都不用花。

那麻烦在哪？麻烦在于「圈」是没有起点也没有终点的。 如果你在主循环里随便找个时刻去读 adc_buf，你怎么知道读到的那一段是完整的？ 万一你读 adc_buf[500] 的同一瞬间，DMA 正好写到 adc_buf[500] 呢？ 结果是：这个数可能是上一次的数据，也可能是这一次的，甚至可能是半个旧的半字 + 半个新的半字（16 位数据被撕裂成两半，得到一个谁也不是的值）。

解决办法不是加锁，而是错开。 把缓冲区当作两个相等的半区，让 DMA 和 CPU 永远处于「不同的半区」： 

  缓冲区 adc_buf[1024]，每个元素 1 个半字（16 位）。DMA 循环模式，从索引 0 一直走到 1023 再回 0。

  时间轴 →（一个完整的循环 = 1024 个采样点 = 1.024 s @1kHz）

  ① 刚启动，NDTR = 1024 ────────────────────────────────────────────────────
     ┌───────────────────────────┬───────────────────────────┐
     │        前半区 [0..511]     │       后半区 [512..1023]   │
     │   DMA 正在写 →→→→→→→→→→→   │         CPU 不能读          │
     └───────────────────────────┴───────────────────────────┘
       ↑ 从头开始写                     （此时两个半区都还没有有效数据）

  ② 前半区写满的那个瞬间，硬件置 HT 标志 ─────────────────────────────────
     ┌───────────────────────────┬───────────────────────────┐
     │   前半区【已满，归 CPU】    │   DMA 正在写 →→→→→→→→→→   │
     │   ★ 在这里处理这里的数据 ★  │                           │
     └───────────────────────────┴───────────────────────────┘
       ↑ HT 中断：处理 buf[0..511]     ↑ 此时绝不能碰 buf[512..1023]

  ③ 后半区也写满，NDTR 归零并自动重装，硬件置 TC 标志 ──────────────────────
     ┌───────────────────────────┬───────────────────────────┐
     │   DMA 又绕回来写这里 →→→→  │   后半区【已满，归 CPU】    │
     │                           │   ★ 在这里处理这里的数据 ★  │
     └───────────────────────────┴───────────────────────────┘
       ↑ 此时绝不能碰 buf[0..511]      ↑ TC 中断：处理 buf[512..1023]

  ④ 又回到 ② 的状态，如此往复。

  ── 一句话记忆：HT 到了处理前半区，TC 到了处理后半区，永远处理"刚满的那一半"。
  ── 为什么能这样？因为 DMA 是顺序推进的：它写后半区时，前半区不会被它碰到。

现在把这段图里的规则写成三条铁律。这三条听起来像废话，但九成的「数据偶尔错一块」都是违反了其中一条：

1

HT 中断里只碰前半区，TC 中断里只碰后半区

不要在 HT 中断里「顺便把整块都处理了」，也不要在 TC 中断里从 buf[0] 开始处理。这不是风格问题：你多碰的那一半正在被 DMA 写。

2

一半缓冲的所有权，在中断到来的那一刻从 DMA 移交给 CPU

移交给 CPU 的时间有多长？就是半个半区的采集时间 T_half = (N/2) / f_s。超过这个时间还没处理完，DMA 就会绕回来覆盖它——这一条直接给出了「主循环最长允许阻塞多少毫秒」的答案。

3

缓冲区必须 volatile，且必须是全局或静态数组

不加 volatile，编译器在 -O2 下可能把「主循环里反复读同一个位置」优化成只读一次；写成函数内的局部数组，函数一返回栈就被别人复用，而 DMA 还在往里写。这两条在第 30 篇里讲过，这里只强调一次：它们是"偶尔才出错"的典型来源，比逻辑错误难查十倍。

为什么必须是"两半"，不是"三段""四段"？ 因为硬件只提供两个边界：半传输（HT）和传输完成（TC）。 CNDTR 从 N 减到 N/2 时置 HT，减到 0 时置 TC 并自动重装——这是 DMA 控制器给的、唯一两个「确定的时间锚点」。 你当然可以在软件上把每个半区再切成四份，但那样切出来的边界没有任何硬件保证， 本质上是「用时间戳去猜」，一旦某个时刻被打断就全乱了。硬件的两个锚点，正好对应两个半区，这就是这个结构被普遍使用的原因。

接下来是最容易被忽略、也最重要的一件事：处理不过来了，怎么知道？ 前面说「处理时间必须小于 T_half」，但你不能指望主循环永远守规矩—— 某一个时刻它可能在写 Flash（页擦除 20~100ms）、在响应用户按键、或者在等一个 I2C 传感器应答。 这些时候，HT/TC 中断照来不误，而你手上那半区还没处理完。如果没有溢出检测，你就只是"丢了数据"，而且不知道丢了多少。

最省事的检测办法是一个计数器和两条规则：

volatile uint8_t  half_ready = 0;    /* 有几个半区在等着被处理 */
volatile uint32_t half_lost  = 0;    /* 因为处理不及时而被覆盖的半区数 */
volatile uint32_t half_seq   = 0;    /* 半区序号：每来一个半区 +1，可用于时间对齐 */

/* ---- HT 中断：前半区就绪（这段代码在主循环里读，中断里只加） ---- */
void HAL_ADC_ConvHalfCpltCallback(ADC_HandleTypeDef *hadc)
{
    (void)hadc;
    if (half_ready >= 1) {          /* 上一次的半区还没被取走 */
        half_lost++;                /* 记一笔：这一段数据不完整 */
    }
    half_ready++;
    half_seq++;
}

/* ---- TC 中断：后半区就绪，规则与 HT 完全一样 ---- */
void HAL_ADC_ConvCpltCallback(ADC_HandleTypeDef *hadc)
{
    (void)hadc;
    if (half_ready >= 1) {
        half_lost++;
    }
    half_ready++;
    half_seq++;
}

主循环每处理完一个半区就把 half_ready--。 这样 half_lost 就是「这次 10 分钟采集里，有多少个 256ms 的数据段是不可信的」。 把它随数据一起上传（或者放在每帧的头部一个字节里），上位机就能在波形上把丢数据的时间段标出来—— 对测量系统来说，「知道哪段数据不可信」比「假装数据都在」重要得多。

丢数据时，丢新还是丢旧？

上面这种写法是丢新保旧：最新的半区因为没地方放而被丢掉，主循环继续处理手上那半区。 另一种策略是丢旧保新：主循环发现 half_ready ≥ 2 时，直接把手上的丢掉，去取最新的。

怎么选取决于你要什么。做实时监控、要看到"现在"的值 → 丢旧保新；做离线记录、要有连续的时间序列 → 丢新保旧， 因为丢新只是缺一段（时间轴上一段空白，可以打标记），丢旧则是把已经排好序的数据挖掉一块，前后拼接处会产生看不出来的时间跳变—— 你的上位机画出来的波形会突然"压缩"一下，而没人知道那里少了一段。 本文的采集器选丢新保旧，并且把 half_lost 上报。

最后把这一节的约束关系写成不等式，这是第 3 节例 2 要算的东西：

半区大小、采样率、主循环最长阻塞时间，三者的约束

T_half = (N_buf / 2) / (f_s × B_sample)

其中 N_buf 是缓冲区的字节数，f_s 是采样率（点/秒）， B_sample 是每个采样点的字节数（12 位 ADC 放 uint16_t 就是 2）。 要求 T_block_max < T_half / K，K 是安全系数，工程上取 3~5。

用 NDTR 反推写指针：正用与五个陷阱

上一节我们用 HT/TC 两个中断来划分所有权，这是"事件驱动"的思路。 但很多时候你不需要精确的边界，只想知道「DMA 现在大概写到哪了」—— 比如主循环想让 LED 跟着数据量闪烁、想在上位机界面上显示进度、想确认「DMA 到底还在不在动」。 这时候读 CNDTR 比等中断方便得多。

先把这个寄存器的语义钉死，因为一半的错误都来自理解偏差： CNDTR 里装的是「还剩多少个数据要搬」， 不是「已经搬了多少个」。它从你设定的初值往下减，减到 0 时——循环模式下自动装回初值，单次模式下停住并把 EN 清零。 所以在循环模式下： 

  设缓冲区有 N 个元素（N = ADC_BUF_LEN），DMA 配置为循环模式，CMAR 指向 buf[0]。

  DMA 刚启动：  CNDTR = N            → 已写 0 个      → 下一个要写的位置 = buf[0]
  搬了 1 个：   CNDTR = N - 1        → 已写 1 个      → 下一个要写的位置 = buf[1]
  搬了 512 个： CNDTR = N - 512      → 已写 512 个    → 下一个要写的位置 = buf[512]（此刻置 HT）
  搬了 N 个：   CNDTR = 0 → 重装为 N → 已写 N 个      → 下一个要写的位置 = buf[0]（此刻置 TC）

  于是：

      已写元素个数 = N - CNDTR
      下一个要写的位置（写指针）= N - CNDTR     ← 注意：两者数值相同，含义不同

  加个边界：刚重装完的那一瞬间，CNDTR = N，算出来写指针 = 0，这是对的。
  但如果 CNDTR 恰好为 0（还没重装，硬件上有一两个周期的窗口），算出来写指针 = N，
  已经越界了 —— 所以任何用 NDTR 算出来的下标，都必须再取模一次： idx = (N - CNDTR) % N。

正用一：IDLE 中断里算「这一帧收到了多少字节」。 这是 NDTR 反推最经典、也是最无可替代的用途。 串口接收用 DMA 循环模式搬到 rx_ring[RX_RING]，当总线上出现一个字节时间的空闲时， USART 置 IDLE 标志并进中断——此刻线上已经没有数据在传输了，DMA 也不会再收到新的接收请求， CNDTR 停在一个稳定的值上。于是这一帧的长度就是 len = RX_RING - CNDTR - last_wr（要减去上一帧已经处理掉的部分，还要处理回绕）。 这是硬件给的、准确到字节的帧长度，比任何软件计时都可靠。

正用二：健康检查。 主循环里每隔 100ms 读一次 CNDTR 存进一个静态变量，两次一样 → DMA 没在动， 可以在界面上报「采集通道无数据」，而不是让用户对着一条直线猜是不是传感器坏了。 这个用途对精度要求极低，随便读都行。

正用三：单次模式下的「实际收到多少」。 单次模式搬完就停、EN 清零，NDTR 稳定不变， 此时 已收 = 初值 - CNDTR 是准的。用它可以在「发一条命令、读固定长度应答」的场景里 知道对端到底回了几字节（比如 SPI Flash 的 JEDEC ID 应该回 3 字节，回少了就是通信有问题）。

接下来是五个陷阱。它们的共同点是：代码能跑，结果偶尔错，而错的时候往往正是你最需要正确数据的时候。

陷阱为什么错正确做法
① 把它当成字节数 CNDTR 的单位是数据个数，不是字节。宽度配成半字（DMA_PDATAALIGN_HALFWORD）时，512 表示 512 个半字 = 1024 字节 一律按「元素个数」思考；要字节数就乘上 B_sample。缓冲数组的下标本来也是元素单位，直接用最省事
② 忘了 ±1~2 的不确定 一次传输是「读源 → 写目的 → 计数减一」三步。你读到 CNDTR 的那一刻，可能有一个数据已经写进内存但计数还没减 用 NDTR 推算位置时留 2 个元素的余量，不要拿它当作「精确边界」。要精确边界就用 HT/TC 中断
③ 循环模式下它绕圈了 N - CNDTR 只能告诉你「当前在这一圈里的哪个位置」，它不告诉你转了第几圈。转了两圈半，算出来和转了半圈一模一样 圈数必须由软件自己数（HT/TC 中断各加一次）；需要绝对位置时用 圈数 × N + (N - CNDTR)
④ 缓冲区不是从数组开头启动 这个公式默认 CMAR 指向数组首地址。如果你从 buf[100] 处启动，或者中途改过 CMAR，基准就错了 永远从数组首地址启动；确实要从中间开始时，把「起始偏移」也记下来一起加
⑤ 读 NDTR 和读缓冲区不是原子的 你读到 CNDTR = 700，于是去读 buf[300]；但你算完到真去读之间，DMA 可能已经走到 buf[310]——你读的也许正是它刚写的那一格 这就是 2.1 节存在的理由：定位用 NDTR，取数用半区。两者别混用
一个真实踩过的坑：DMA 单次模式 + 循环缓冲区

有个同学用 DMA 单次模式收串口，缓冲区 256 字节，在 TC 中断里处理完、重启 DMA。 但他同时在主循环里用 256 - CNDTR 显示「已收字节数」。 结果是：每次 TC 中断重启 DMA 之后，显示的数字会从 255 突然跳回 0， 上位机看到的进度条一直在闪。

原因很简单：重启之后 CNDTR 被装回 256，反推出来的值就归零了。 「已收字节数」这个概念在循环/重装的架构里是没有全局意义的—— 有意义的是「自某个起点以来收了多少」。想要后者，就得用一个只增不减的软件计数器， 在每次 TC 中断里把这一轮的量加进去，而不是去问硬件。

不定长帧接收：IDLE 只记账，解析交给主循环

采集器要能被上位机控制，所以接收路径必须做。命令帧的特点是长度不固定： 「开始采集」只有 4 个字节，「设置采样率 + 通道号 + 触发阈值 + 上传周期」可能有十几个字节。 你不可能用「收固定 N 个字节」的方式去接。

先看逐字节中断的问题有多大。 115200 波特率、8N1 每字节 10 位，就是 11520 字节/秒。每字节一次中断， 按第 30 篇实测的 108 个周期计算（进栈 12 + 现场处理 80 + 出栈 12，含 HAL 层的标志清除和回调）： 11520 × 108 = 1 244 160 周期/秒，占 72MHz 的 1.73%。 单看不算多，但如果你把波特率提到 1Mbps（100 000 字节/秒），立刻变成 100000 × 108 = 10 800 000，15% 的 CPU 全花在"每个字节进一次中断"上。 这还没算 HAL 层 HAL_UART_Receive_IT() 的额外开销，实测会到 20% 以上。

IDLE 中断解决的是「边界」问题，不只是「省中断」问题。 USART 的 IDLE 标志在接收线上连续出现一个完整字节时间的空闲之后置位。 串口发一帧时，字节和字节之间最多只有一个停止位的时间，而一帧发完之后，线会一直空着—— 所以 IDLE 中断恰好就是硬件送给你的「一帧发完了」的信号。 这个信号配合 DMA 的 CNDTR，就能算出这一帧精确有多少字节（见 2.2 节正用一）。

为什么强调"不要在 IDLE 中断里解析大帧"？ 因为帧长是不定的，而中断里花的时间会跟着帧长一起长。我们来算一笔账： 一帧 1KB 的固件升级包，在中断里跑状态机 + 逐字节 CRC16（每个字节约 40 个周期） 大约是 1024 × 40 + 状态机开销 ≈ 50 000 个周期，也就是 0.7ms。 这 0.7ms 里会发生什么？

1

ADC 的半区中断被推迟

你的 1kHz 采集正在跑，半区边界是硬时间点。中断被压后 0.7ms 不会丢数据（还有 256ms 的余量），但如果这个帧解析发生在 SPI 高速传输的中间，就可能丢 SPI 数据——SPI 的接收缓冲只有 1~2 层，等 0.7ms 早就溢出（ORE）了。

2

帧会排队，然后溢出

上位机如果以 10ms 的间隔连发大帧，中断里的处理时间（0.7ms）虽然小于间隔，但只要有一次挤在一起（比如同时来了 ADC 半区 + 串口 IDLE），中断就叠起来了。中断叠中断，最坏情况下的延迟是所有中断处理时间之和，这是实时系统里最典型的"偶尔卡一下"。

3

优先级立刻变得无法收拾

你给 IDLE 中断设高优先级（因为怕丢帧），它就会压住别人；设低优先级，它又会被别人压住导致下一帧的 IDLE 标志来不及清而丢帧。把重活放进中断，就等于把自己逼进这个两难。而"中断只记账、解析在主循环"的结构里，这个问题根本不存在。

所以接收路径的正确分层是三层： 第一层是 DMA（纯硬件，把字节搬进内存，零 CPU）；第二层是 IDLE/HT/TC 中断（只记账：算长度、登记、清标志， 时间常数化）；第三层是主循环或 RTOS 任务（解析状态机 + CRC + 执行命令，可以被抢占、可以慢慢来）。 这三层的分界线是「时间是否可预测」，不是「活儿是否相关」。

现在说第二层和第三层之间怎么交接。有两种主流架构，各有各的适用场合：

架构怎么工作优点代价 / 什么时候不能用
A · 双缓冲提交
（最稳妥）		 DMA 单次模式，交替写入 rx_seg[0] / rx_seg[1]；IDLE 中断里把刚写满那一段的指针和长度压进队列，随即把 DMA 重启到另一段 数据一定有完整的落点；解析慢了也不会被覆盖（队列满了就丢帧并计数，行为明确）；天然适合交给 RTOS 任务或队列 需要两倍缓冲内存；每次重启 DMA 有几十个周期的开销；一段缓冲区的大小必须 ≥ 最长帧
B · 零拷贝环形缓冲
（最省 CPU）		 DMA 循环模式往一个大环里写；IDLE 中断里只更新「写到哪了」（last_wr）；解析器在主循环里从 last_parsed 追到 last_wr，读一个推进一个 零拷贝、零重启，中断里只有几条指令；内存占用小；连续高速数据流（比如透传）特别合适 没有背压：解析速度必须持续大于接收速度，否则 DMA 会绕一圈把没解析的数据覆盖掉。必须自己做「解析落后多少」的检测

两种架构本文都给出代码（例程二里 A 是主推，B 作为对照）。 选哪个的判断标准很朴素：你的解析速度是否稳定地快于接收速度？ 命令帧（几十字节、偶尔来一次）用哪个都行；固件升级包（每秒几十 KB、连续来）如果解析里还有 Flash 写入，就必须用 A， 因为写 Flash 一定会慢到让 B 溢出。

帧格式的设计，直接决定了接收框架的健壮性。 下面这个格式是为采集器设计的，你可以直接抄（字节序统一小端）： 

  偏移  字段      长度    取值/说明                              设计理由

  ── 为什么既有 CRC 又有帧尾？CRC 是"内容对不对"，帧尾是"结束位对不对"。
     两者都过才认为这是一帧，可以把误判率压到几乎为零。
  ── 为什么 LEN 只放净荷长度、不含头部？这样头部结构固定，状态机在还没读全之前就能定出剩余长度。
  ── 为什么 LEN 上限是 250？因为它是 1 字节（最大 255），而缓冲区至少要能装下 LEN+9 = 259 字节，
     留一点余量取 256 或 512 的段大小。上限是"防御性设计"的一部分，不是随便定的。

最后是这套框架里最容易被省略、但一旦省略就一定会出问题的一环：超时重同步。 考虑这个场景：上位机发了一帧，但在第 5 个字节时被你拔了 USB 线（或者串口上电时序导致丢了几个字节）。 状态机现在停在「等净荷第 3 个字节」，它不知道剩下的字节永远不会来了。 下一个上电周期，上位机发来一帧新的，状态机把新帧的 0xAA 当成净荷吃了进去—— 从此永久错位，除非复位单片机。

解决办法就是给状态机配一个「死线」：记录最后一次收到字节的时刻， 每收到一个字节就刷新，如果在解析过程中超过 T_resync 没有再收到任何字节，就无条件把状态机复位到"找帧头"， 丢掉半截帧并计数。T_resync 的选取原则是： 要大于「一帧最长发送时间」的两倍（防止把正常的慢速发送误判成超时）， 同时要小于「上位机的重发间隔」（保证下一帧来之前状态机已经干净了）。 115200 下 259 字节的帧需要 2590 / 115200 ≈ 22.5ms， 所以 T_resync 取 100ms 是安全的（4 倍余量）， 而万一波特率配错（比如上位机其实发的是 9600），这个超时也能在 100ms 内把状态机拉回干净状态。

重同步的粒度：丢一帧，还是丢一个字节？

超时是把整帧丢掉（状态机整体复位）；而在「找帧头」状态里遇到不等于 0xAA 的字节， 是只丢这一个字节继续找。两者的粒度不同，别搞混： 帧内出错就丢整帧（因为长度字段可能已经不可信了），找帧头时出错只丢一个字节 （这样才能从 AA AA 55 这种"帧头前面多了一个 AA"的情况里恢复出来）。 这个细节处理好了，你的接收框架才算真的健壮。

四路并发：两级仲裁，只有一级听你的

到这一步，采集器已经不是"一路 DMA"了。一个真实的数据采集器通常同时跑着四路 DMA： ADC1（通道 1，外设 → 内存，采数据）、SPI1_RX（通道 2，外设 → 内存，读外部 Flash 里存的配置或历史数据）、 USART1_TX（通道 4，内存 → 外设，上传）、USART1_RX（通道 5，外设 → 内存，收命令）。 四路请求同时到达是常态，问题就来了：谁先走？谁等多久？等太久会怎样？

要回答这个，先得知道这里有两次仲裁，而不是一次。 第 30 篇讲过总线矩阵是个交叉开关，主设备之间有仲裁；但如果你只记得那一层，就会得出「优先级是总线矩阵决定的」这个错误结论。 实际上第一道关在 DMA 控制器内部：

                                      │  只有一路能在这一个瞬间占用控制器
                                      ↓
  【第二级 · 总线仲裁】发生在总线矩阵里，DMA 与 CPU 争同一个从设备

        CPU(ICode) ──┐                                ┌── Flash（取指）
        CPU(DCode) ──┤                                │
        DMA1 ────────┼──→ ┌───────────────────────┐ ──┼── SRAM（数据）
        DMA2 ────────┘    │  总线矩阵 / 交叉开关    │   │
                          │  主设备之间【轮询】仲裁  │ ──┼── AHB 外设 / APB 桥
                          │  软件无法干预            │   │
                          └───────────────────────┘ ──┴── FSMC…
                                      ↑
                          ← 这一层你只能"少用带宽"，不能"改优先级"

  ── 结论：软件优先级只在第一级生效。第二级永远是轮询，四路都设 VeryHigh 也换不来更多总线时间。
  ── 真正决定"谁等多久"的，是你的总带宽需求有多接近上限（见例 3）。

这里有个 F1 特有的细节值得注意：通道号小的优先这条规则。 ADC1 恰好固定在通道 1，所以只要四路的软件优先级相同，ADC 就永远排在最前面。 这既是个"免费好处"，也是个陷阱——很多人在 CubeMX 里给每个 DMA 请求都填 Medium（默认值）， 以为"大家都一样就是公平"，其实是按通道号排了一个固定的次序， 而你的外设恰好分布在通道 1、2、4、5 上时，公平是不存在的。

那怎么给优先级？不要凭感觉，按三条判据排。 这三条判据回答的是同一个问题：「这一路要是晚几十微秒被服务，会付出什么代价？」

判据它在问什么怎么查
① 外设侧能顶住多久 缓冲深度有几层？从请求发出到数据被取走，最多能容忍多少时间？ 查参考手册的外设章节：USART 接收只有 1 个字节的 DR；SPI 是 1 个 DR + 1 个移位寄存器；ADC 有 DR，但连续模式下下一次转换完成会覆盖它
② 超时的后果可不可恢复 晚一步是丢一个字节、丢一个点，还是整个数据块作废？ USART 接收溢出（ORE）→ 丢掉的那个字节永远回不来，整帧 CRC 必然不过，整帧作废；ADC 晚一步 → 丢一个采样点，波形上一个毛刺
③ 服务延迟会不会自己累积 这一路是"来了就搬"，还是"搬不完就有连锁反应"？ TX 方向一般不紧急：TXE 会一直保持置位等你来写，USART 不会因为你慢就自己发垃圾字节。RX 方向会累积：一个字节没取走，下一个字节来了就溢出

把四路按这三条过一遍，结论有点反直觉：

  紧急度   通道          外设缓冲深度      超时后果            请求频率（典型）
  ──────  ────────────  ───────────────  ──────────────────  ──────────────────────
  最高    USART1_RX     1 字节           丢字节→整帧作废      11 520 次/秒 @115200
  高      SPI1_RX       1~2 字节         读出的数据错位       1 125 000 次/秒 @9MHz（8 位）
  中      ADC1          1 个 DR（会被覆盖）丢一个采样点        1 000 次/秒 @1kHz
  低      USART1_TX     1 字节（TXE 等着） 只是发送晚一点      11 520 次/秒 @115200

  ── 于是配置通常是：
       USART1_RX → DMA_PRIORITY_VERY_HIGH
       SPI1_RX   → DMA_PRIORITY_HIGH
       ADC1      → DMA_PRIORITY_MEDIUM
       USART1_TX → DMA_PRIORITY_LOW

  ── 注意 SPI1_RX 的请求频率比 USART1_RX 高了 97.7 倍，但"最高"给了串口。
     理由是"超时后果"：SPI 是同步总线，DMA 慢一点，SPI 的时钟也会跟着慢（主机模式由软件/硬件控制节奏），
     数据不会凭空消失；而 USART 是异步的，对端不等你，字节来了就是来了。

  ── 反过来说：如果 ADC 的采样率提到 200kHz（做振动分析），它的紧急度立刻升到最高。
     优先级不是"一次配好就永远对"的东西，它跟着采样率走。
把优先级设高不是免费的：它会把别人的延迟顶上去

PL 是一个"抢"的机制，不是"快"的机制。你把 SPI1_RX 设成 VERY_HIGH， 它的每一次请求都会插到 ADC 前面；如果 SPI 以 9MHz 持续读 Flash（每 0.89µs 就有一个字节的请求）， ADC 的请求就要在这个洪水里排队——ADC 单次请求最多等多久？最坏情况等于 SPI 的一次传输时间乘以等待中排在你前面的请求数。 在 F1 上，一次 DMA 传输大约 4~6 个 AHB 周期（0.06~0.08µs），看起来很小； 但总线矩阵那一层的轮询仲裁会让 DMA 和 CPU 交替访问 SRAM， 实际每次传输的等效等待可能是十几个周期。

正确的思路是：先用带宽预算（例 3）确认总量安全，再用优先级处理"相对紧急度"。 总量不安全的时候，调优先级是没用的——那叫"把堵车从一个车道挪到另一个车道"。

带宽预算怎么算？分四步，任何一路 DMA 都能套：

1

算出每一路的字节率 R（字节/秒）

ADC：采样率 × 每点字节数；串口：波特率 ÷ 10（8N1 每字节 10 位）；SPI：时钟频率 ÷ 8（8 位一帧）。这一步一定要用真实配置，不要用"应该差不多"的数字。

2

估算每个字节要占多少 AHB 周期 C

一次 DMA 传输是「读源 + 写目的」，每次访问含 1 个地址相位 + 1 个数据相位 = 2 周期，合计 4 周期；如果有一端挂在 APB 桥上，还要加上桥的同步等待，保守取 C = 6。这个系数是"按典型值估算"，追求精确就得用第 30 篇的方法算突发和 FIFO 的摊薄效果。

3

求和再除时钟：占用率 = Σ(R × C) ÷ f_HCLK

F103 的 HCLK = 72MHz，AHB 与内核同频。算出来的百分比是"AHB 总线上被 DMA 交易占用的时间比例"，不是 CPU 的减速比例——两者的关系在例 3 里解释。

4

把"冲突点"单独拎出来看

DMA 的天量数据流通常来自一个固定的从设备（比如 SPI1 走 APB2 桥、ADC 走 APB2 桥），而 SRAM 是所有路的共同终点。占用率 6% 平均分布和 6% 全压在 APB2 桥上，是完全不同的两件事——后者会让挂在 APB2 上的每一个外设都被拖慢。

具体的数字和第 30 篇算过的 288MB/s 上限，放在第 3 节例 3 里完整走一遍。 这里只留一个结论：在 1kHz 采集 + 115200 上传 + 9MHz SPI 这个典型配置下，四路 DMA 的总线占用在 10% 以内， 优先级怎么排都不会出问题；真正需要紧张的是 SPI 的时钟提到 18MHz 以上、或者加了第二路 SPI 屏刷新之后。

怎么证明 DMA 真的省了 CPU：两种测量法

这一节的标题里有两个动词值得强调：证明和测量。 我们不需要"相信"DMA 省 CPU——它在原理上必然省（第 30 篇已经算过：中断搬 1024 字节 110 592 周期 vs DMA 大约 1µs 的一次性配置）。 我们需要的是在自己这块板子上、自己这份代码里，把它量出来， 因为"省"的幅度完全取决于你的中断里干了多少活、你的半区有多大。 量出来之后你才能回答那些真正有用的工程问题：要不要上 DMA？半区该加大还是减小？四路并发有没有让主循环变慢？

第一种办法是DWT 周期计数器。Cortex-M3/M4/M7 的内核里都有一个数据观察点与跟踪单元（DWT）， 其中 CYCCNT 是一个自由运行的 32 位周期计数器，每个内核时钟加一。 它不需要外接任何仪器，读起来就是一条 LDR：

#include "stm32f1xx.h"

/* ---- 初始化：只需在 main 开头调用一次 ---- */
void DWT_Init(void)
{
    CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;  /* 打开跟踪与调试模块的总开关 */
    DWT->CYCCNT = 0;                                  /* 计数器清零 */
    DWT->CTRL |= DWT_CTRL_CYCCNTENA_Msk;              /* 使能周期计数 */
}
/* 注意：CYCCNT 是 32 位，72MHz 下 2^32 / 72e6 = 59.65 秒 会绕回一圈。
 * 单次测量只要不超过 59 秒就没问题；无符号减法的环绕特性让差值天然正确。 */

/* ---- 测法 A：测一段代码（比如"主循环处理一个半区"）花了多少周期 ---- */
static uint32_t t_proc_max = 0, t_proc_sum = 0, t_proc_cnt = 0;

static inline void measure_half_processing(void)
{
    uint32_t t0 = DWT->CYCCNT;
    process_half_buffer();                  /* 被打量的那段代码 */
    uint32_t dt = DWT->CYCCNT - t0;         /* 无符号减法，自动处理环绕 */

    t_proc_sum += dt;
    t_proc_cnt++;
    if (dt > t_proc_max) t_proc_max = dt;   /* 最大值往往比平均值更能说明问题 */
}

/* ---- 测法 B：测"中断里花了多少"——在 ISR 入口和出口各读一次 ----
 * 这是最有用的一种：它直接告诉你"中断搬数据"和"DMA 搬数据"的差别。
 * 累加变量必须是 volatile，因为它在中断和主循环之间共享。 */
volatile uint32_t isr_cycles_total = 0;
volatile uint32_t isr_count        = 0;

void EXTI0_IRQHandler(void)                 /* 以任意一个 ISR 为例 */
{
    uint32_t t0 = DWT->CYCCNT;
    /* ... 中断服务内容 ... */
    isr_cycles_total += DWT->CYCCNT - t0;
    isr_count++;
}

/* ---- 测法 C：测"CPU 占用率"——用一个固定的时间窗做分母 ----
 * 占用率 = 窗口内所有忙时间之和 / 窗口长度。
 * 这里用 SysTick 每 1ms 取一次样，连续取 1000 次即 1 秒的窗口。 */
volatile uint32_t busy_cycles_1s = 0;
volatile uint32_t cpu_load_ppm  = 0;       /* 用百万分之一表示，避免浮点 */

void SysTick_Handler(void)
{
    static uint32_t acc = 0, ticks = 0;
    acc += isr_cycles_total;               /* 把这一毫秒里中断花的周期累起来 */
    isr_cycles_total = 0;
    if (++ticks >= 1000) {                 /* 1 秒的窗口到了 */
        busy_cycles_1s = acc;
        cpu_load_ppm   = (uint32_t)((uint64_t)acc * 1000000ull / 72000000ull);
        acc = 0; ticks = 0;
    }
}

DWT 的优点是精确到周期、不需要任何仪器、可以在产品里长期保留（占几十字节）。 但它有四个必须知道的坑：

坑现象处理
① M0 / M0+ 没有 DWT 编译报 DWT 未定义；或者寄存器存在但计数不动 F0、G0、L0 这些 Cortex-M0+ 的型号只能用 GPIO + 示波器，或者用定时器计数
② 测量本身有开销 读 CYCCNT 是私有外设访问，M3 上约 1~2 周期，M7 上因为有总线桥可能到 10 个周期以上 测几十个周期的代码时，把测量开销也考虑进去；或者在测法里连读两次取差，把固定开销减掉
③ 测出来的是"墙钟时间"，包含被打断的部分 测一段代码得到 5000 周期，但其中 3000 周期是在等一个中断 这正是你想要的（真实占用），但要知道它的含义：它是"这段代码从进到出用了多久"，不是"CPU 执行了多少条指令"
④ 调试器会影响它 挂上调试器单步、或者在 CYCCNT 上设了观察点，数字会失真 要拿"可以写进报告的数字"时，拔掉调试器、让程序自己通过串口把结果打出来

第二种办法是GPIO 翻转 + 示波器。 做法简单到不像话：在要测量的区间开始时把某根引脚拉高，结束时拉低， 示波器上看高电平的宽度就是这段时间，看高电平占空比就是 CPU 占用率。 

/* 用 PA1 当"忙"指示脚。BSRR 的写法只要 1 条 STR 指令：
 *   低 16 位写 1 → 置位；高 16 位写 1 → 复位。不用读-改-写，不会与其他引脚冲突。 */
#define PROF_HIGH()  (GPIOA->BSRR = GPIO_BSRR_BS1)                  /* PA1 = 1 */
#define PROF_LOW()   (GPIOA->BSRR = GPIO_BSRR_BR1)                  /* PA1 = 0 */

/* 反面教材：HAL_GPIO_WritePin(GPIOA, GPIO_PIN_1, GPIO_PIN_SET);
 * 它要经过函数调用、参数检查、可能的断言，实测比直接写 BSRR 慢 10~20 个周期。
 * 测 1.5µs（108 周期）的中断时，这就已经是 10% 以上的误差了。 */

void process_half_buffer_profiled(void)
{
    PROF_HIGH();
    process_half_buffer();
    PROF_LOW();
}

/* 用示波器看：周期 = 512ms（半区时间），高电平宽 = 实测的耗时。
 * 占空比 = 高电平宽 / 512ms，就是"处理半区"这件事的 CPU 占用率。
 * 例如测得 1.2ms → 1.2 / 512 = 0.23%。 */

两种办法不是二选一，而是配着用：示波器负责给出"眼见为实"的总览（抖动、是否有偶发的长阻塞、多路信号之间的时序关系）， DWT 负责给出可以写进报告的精确数字（每个半区平均多少周期、最大值多少周期、中断总共占了多少）。

你要回答的问题用哪种为什么

看「1.73% → 0.011%」这个对比，很容易得出「DMA 省了 150 倍 CPU」的结论。 这个结论在 115200 下是对的，但没有意义——因为 1.73% 的占用本来就不影响你干任何事。

DMA 的真正价值不在平均数，而在最坏情况。 逐字节中断的最坏情况是：中断正在处理时又来一个字节请求， 如果被更高优先级的中断压住超过 86.8µs（115200 下一个字节的时间），这个字节就丢了。 1Mbps 下这个窗口只剩 10µs——任何一段关中断时间超过 10µs 的代码都会导致丢字节， 而在中断里搬数据的方案里，你的"关中断时间"就是你的 ISR 时间。 表里 108 周期的 ISR 是 1.5µs，看起来安全；但只要有任何一个地方关了 200µs 的中断（比如 Flash 页擦除的等待循环没放开中断）， 立刻丢字节。

换句话说：中断搬数据是「平均很便宜、最坏很贵」，DMA 搬数据是「平均很便宜、最坏也很便宜」。 这才是要证明的东西。

错误与恢复：TE 会自己刹车，FE 和 DME 不会

DMA 的错误有一个很讨厌的特点：大部分错误不会让程序崩溃，只会让它"安静地做错事"。 没有 HardFault、没有断言、主循环照常跑，只是数据不更新了，或者数据偶尔错一段。 如果不主动去读错误标志，你可能要等到用户投诉才发现。

三类错误的分工必须先说清楚，因为其中只有一类在 F1 上存在—— 很多同学从 F4 的例程里抄了 HAL_DMA_ERROR_FE 的判断，跑在 F103 上永远进不去这个分支， 于是以为"我的代码没有 FIFO 错误"，其实是"我的芯片没有 FIFO"。

TE 在真实项目里最常见的三个成因，按出现频率排：

1

外设时钟没开就启动 DMA

DMA 去读一个时钟没开的外设寄存器，总线返回错误。典型场景：在 HAL_ADC_MspInit() 里忘了 __HAL_RCC_ADC1_CLK_ENABLE()，或者在低功耗唤醒后没有重新使能外设时钟。这是"配好了就是不动"的头号原因。

2

宽度没对齐

传输宽度配成半字（16 位），但地址是奇数字节（比如一个 uint8_t 数组的第二个元素）。半字访问要求地址是 2 的倍数。这类错误在"缓冲区类型改了但 DMA 配置没改"时特别容易发生。

3

指针已经越界/失效

最常见的是把 DMA 的目标地址设成了函数内的局部数组——函数返回后栈被复用，那个地址可能落在栈的保护区或者干脆是别的数据。DMA 往那里写，第一次可能没事，第二次就撞上不该碰的地址。

知道了错误的种类，接下来的问题是怎么优雅地重启一次传输。 「优雅」这两个字包含三层意思：不能死等、不能反复重启、不能让上位机以为数据是好的。 下面是六个步骤，顺序不能换： 

volatile uint32_t dma_err_te = 0, dma_err_fe = 0, dma_err_dme = 0;
volatile uint32_t dma_restart_cnt = 0;
#define DMA_RESTART_MAX  5      /* 连续错这么多次就别再重启了，说明根因没除 */

void HAL_ADC_ErrorCallback(ADC_HandleTypeDef *hadc)
{
    /* ── 第 1 步：识别错误类型，只记账，绝不在这里 printf ──
     * HAL 已经把 ISR/CCR 的信息整理进 hadc->DMA_Handle->ErrorCode，
     * 可以直接用；手写寄存器时读 DMA1->ISR。 */
    uint32_t ec = hadc->DMA_Handle->ErrorCode;
    if (ec & HAL_DMA_ERROR_TE)       dma_err_te++;
    else if (ec & HAL_DMA_ERROR_FE)  dma_err_fe++;      /* F1 上永远不会进这里 */
    else if (ec & HAL_DMA_ERROR_DME) dma_err_dme++;
    else                             dma_err_te++;       /* 未知错误也按 TE 记一笔 */
    dma_restart_cnt++;

    /* ── 第 2 步：先停外设侧的 DMA 请求，防止重启期间有杂散请求进来 ──
     * 顺序很重要：先断来源，再动 DMA。 */
    CLEAR_BIT(hadc->Instance->CR2, ADC_CR2_DMA);
    CLEAR_BIT(hadc->Instance->CR2, ADC_CR2_DDS);   /* 连续请求模式也要关 */

    /* ── 第 3 步：确认通道真的停了（TE 的情况下硬件已经帮你停了） ── */
    HAL_DMA_Abort_IT(hadc->DMA_Handle);            /* 不是 TE 时用这句主动停 */

    /* ── 第 4 步：把这一路的所有标志清干净（IFCR 一次写清） ──
     * HAL_DMA_Abort_IT 内部会清一部分，但显式清一遍更稳，
     * 否则残留的 TEIF 会让你下一次进中断时立刻又报同一笔错。 */
    DMA1->IFCR = DMA_IFCR_CGIF1;                   /* 通道 1 的全局标志清位 */

    /* ── 第 5 步：重启次数保护 ──
     * 如果根因是"时钟没开""地址越界"这类硬伤，重启多少次都会立刻再错。
     * 限制次数，超过就停下并进入安全状态，让上位机看到明确的错误码。 */
    if (dma_restart_cnt > DMA_RESTART_MAX) {
        g_daq_state = DAQ_STATE_FATAL;             /* 主循环见到这个状态就停止上传并报警 */
        return;
    }

    /* ── 第 6 步：重新启动 ──
     * 注意 hadc 的启动要先把 ADC 停下再启（HAL_ADC_Stop_DMA 会做清理），
     * 这里是简化后的写法；同时把"数据不可信"这件事记进统计里。 */
    g_half_lost += 2;                               /* 至少丢了两个半区，宁可多报 */
    if (HAL_ADC_Start_DMA(&hadc1, (uint32_t *)adc_buf, ADC_BUF_LEN) != HAL_OK) {
        g_daq_state = DAQ_STATE_FATAL;
    }
}
两个"优雅"的细节，写错就白重启了

第一，别在错误回调里死等。有些人为了"确认 DMA 停了"，在回调里写 while (DMA1_Channel1->CCR & DMA_CCR_EN) { }。 这个循环在某些情况下永远不会退出（比如时钟被关了、EN 位因为某种原因一直读回 1）， 于是整个系统卡死在一个高优先级中断里，连看门狗都可能喂不上。 要等就等带超时的实现（HAL 的 HAL_DMA_Abort() 内部有超时计数），或者干脆不等。

第二，重启前一定要清外设自己的错误标志。 串口是最典型的例子：接收溢出（ORE）置位后，如果不按"先读 SR 再读 DR"的顺序清掉它， 接收侧的状态会一直不正常——现象是"重启了 DMA 但还是收不到数据"。 所以错误恢复的最后一步，应该包括一句外设级的清理（串口清 ORE/NE/FE/PE，ADC 清 EOC/OVR，SPI 清 OVR）。 这一条在不同系列上的具体行为不完全一样，但"清干净再重启"这个习惯永远是对的。

最后是每个做过 DMA 项目的人都会遇到的那个问题：DMA 卡住不动了，怎么查？ 不要一上来就怀疑代码，按这个三步决策树走，通常两分钟就能定位： 

  第 0 步（先做）：在调试器里打开 DMA1 的寄存器窗口，把 ISR / CCR / CNDTR / CPAR / CMAR 五个值看一眼。

  ┌─ 第 1 步：CNDTR 在变吗？（连续两次 halt，看它有没有减小）
  │
  ├── 在变 ──→ DMA 在搬，问题不在 DMA
  │              → 去查数据内容：缓冲区里是旧值？地址对不对？宽度对不对？
  │              → 去查外设：ADC 采的是不是你以为的那个通道？
  │
  └── 不变 ──→ 继续往下
        │
        ┌─ 第 2 步：CCR 的 EN 位还是 1 吗？
        │
        ├── EN = 0 ──→ 有人把通道关了。三种可能：
        │               ① 发生了 TE（读 ISR 的 TEIF 确认）→ 查时钟/地址/对齐
        │               ② 单次模式搬完了（NDTR = 0）→ 那它本来该停，是没重启
        │               ③ 软件调用了 HAL_DMA_Abort() 忘了重启
        │
        └── EN = 1 ──→ 通道开着但没收到请求。继续：
              │
              ┌─ 第 3 步：外设侧的 DMA 请求使能位开了吗？外设自己在产生请求吗？
              │
              ├── 外设的 DMA 位 = 0 ──→ 就是它。ADC 看 CR2.DMA、USART 看 CR3.DMAR/DMAT、SPI 看 CR2.RXDMAEN/TXDMAEN
              │
              ├── DMA 位 = 1，但外设的状态标志不动 ──→ 问题在外设本身，不在 DMA：
              │        ADC 没启动（ADON/SWSTART）？串口波特率/引脚配错？SPI 没使能（SPE）？
              │
              └── 外设明明在工作（ADC 的 EOC 在置位、串口 RXNE 在置位） ──→ 只有一种可能：
                      请求线根本没接到这个通道上 —— 查请求映射（F1 硬件固定），
                      或者通道被另一个外设共用了（USART1_RX 和 TIM2_CH1 都在通道 5）。
                      第 30 篇那张映射表就是为这一步准备的。

注意这三步里没有一步是"改代码"，全是"看寄存器"。这就是为什么我一直建议： 做 DMA 项目时，把 DMA1 的寄存器窗口常驻在调试器的 Watch 里，出问题时先看数，再改代码。 例程四给了一个 dma_snapshot() 函数， 把这一路的所有关键寄存器和标志一次格式化输出（不打 printf，写进一个结构体由主循环上报）， 在没有调试器的现场也能量到这些数。

DMA 与 RTOS 的对接：回调只发消息，不搬东西

把采集器从裸机搬到 FreeRTOS 上，结构会变得很清楚： DMA 是硬件层，中断是"驱动层"，任务是"应用层"。 三层之间的两条通道是队列（传"哪个缓冲满了"）和信号量（传"缓冲可以复用了"）。 这套结构不只在 FreeRTOS 上成立，RT-Thread、裸机的前后台架构都是同一个道理。

先立一条铁律，它是这一节所有内容的前提： DMA 完成回调里只能做三件事——置标志、发队列、给信号量，然后按需触发一次任务切换。 任何"拷贝、打包、校验、打印"都属于任务该干的活。理由有四条，一条比一条严重：

理由具体说明
① 回调的优先级高于所有任务 中断上下文里花的时间，是所有任务的最坏延迟的一部分。你在回调里拷 2KB（约 2000+ 周期 ≈ 28µs），就等于给系统里的每个任务都加上了 28µs 的抖动预算
② 它会挤掉同一时刻的其他中断 比它优先级低的中断（ADC 半区、串口 IDLE、SysTick）全部排队等候。四路 DMA 都这么干，最坏延迟是所有回调耗时之和
③ FreeRTOS 的大部分 API 不能在中断里调用 只有带 FromISR 后缀的版本可以；malloc、printf、vTaskDelay、xQueueSend（不带后缀）在中断里调用是未定义行为
④ 最要紧的：它让"处理不过来"变得不可观测 如果拷贝发生在回调里并且同步，那么"任务来不及处理"永远不会表现为队列堆积，而是表现为"中断变长了"——你失去了队列长度这个最好的背压指标（见第 3 节例 6）

队列、信号量、任务通知这三种机制该用哪个？很多人上来就用队列传数据，结果把一个 512 字节的缓冲塞进队列项里， 每次拷贝两遍。正确的分工是：

机制传什么典型用法注意
队列
xQueueSendFromISR		 值或指针（固定大小的小数据） 把「哪个缓冲满了」这个描述符（指针 + 长度 + 序号，约 12 字节）发给任务 队列项是拷贝的，所以别放 512 字节的缓冲；默认深度要够，满了要处理 errQUEUE_FULL
二值信号量
xSemaphoreGiveFromISR		 一个事件（就绪 / 未就绪） 「有一个半区就绪了」；任务里 xSemaphoreTake(sem, portMAX_DELAY) 阻塞等待 只能记住"至少有一次"，连续两次 Give 只算一次。双缓冲场景会丢事件，要用计数信号量
计数信号量
xSemaphoreCreateCounting		 资源的数量 「现在有 N 个缓冲可以处理」；最大计数值 = 缓冲池的大小 双缓冲 + 交替提交的标准选择；也可以反过来用作「空闲缓冲池」的配额

最容易漏的一句：portYIELD_FROM_ISR

这是初学者最常犯的一个"看起来能用、实际慢得离谱"的错误： 在回调里调用了 xQueueSendFromISR()，但忘了处理它的第三个参数 pxHigherPriorityTaskWoken。

后果是：任务确实被唤醒了（进入了就绪态），但要等到下一个 SysTick 才会被调度。 FreeRTOS 默认的 tick 是 1ms——你的 1kHz 采集任务因此凭空多了最多 1ms 的延迟。 对采集器来说，这意味着半区处理的实际节奏变成"每 512ms 里可能晚 1ms"，听起来不多， 但如果你后面还挂了"实时显示"任务，这 1ms 就是肉眼可见的卡顿。

写法是固定的三行： BaseType_t woken = pdFALSE; → xQueueSendFromISR(q, &item, &woken); → portYIELD_FROM_ISR(woken); （放在回调的最后一行）。

现在给出双缓冲交替提交给任务的标准写法。这段代码是整个第 4 节例程二的 RTOS 版骨架， 关键在于「缓冲的所有权」用两个队列/信号量明确地传来传去： 

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"
#include "semphr.h"

/* ── 数据结构的定义：一个"缓冲描述符"就是一次交接的全部内容 ── */
typedef struct {
    uint16_t *buf;      /* 这一半数据的首地址 */
    uint16_t  len;      /* 有多少个采样点 */
    uint32_t  seq;      /* 半区序号，用来对齐时间轴、发现丢帧 */
} half_desc_t;

static QueueHandle_t     q_half_ready;   /* 中断 → 任务：有半区就绪 */
static SemaphoreHandle_t sem_half_free;  /* 任务 → 中断：半区已用完，可以再填 */

/* ── 中断侧：只做"登记 + 唤醒"，一共三条语句 ── */
void HAL_ADC_ConvHalfCpltCallback(ADC_HandleTypeDef *hadc)
{
    BaseType_t woken = pdFALSE;
    half_desc_t dsc = { &adc_buf[0], ADC_BUF_LEN / 2, half_seq++ };

    /* 队列满说明任务严重落后：丢这一半，并计数（这就是"可观测的背压"） */
    if (xQueueSendFromISR(q_half_ready, &dsc, &woken) != pdPASS) {
        half_lost++;
    }
    portYIELD_FROM_ISR(woken);          /* ← 少了这一句，任务要等到下一个 tick */
}

void HAL_ADC_ConvCpltCallback(ADC_HandleTypeDef *hadc)
{
    BaseType_t woken = pdFALSE;
    half_desc_t dsc = { &adc_buf[ADC_BUF_LEN / 2], ADC_BUF_LEN / 2, half_seq++ };
    if (xQueueSendFromISR(q_half_ready, &dsc, &woken) != pdPASS) {
        half_lost++;
    }
    portYIELD_FROM_ISR(woken);
}

/* ── 任务侧：阻塞等描述符 → 处理 → 归还配额 ── */
void vAcqTask(void *arg)
{
    half_desc_t dsc;
    for (;;) {
        /* 等到一个就绪的半区。portMAX_DELAY = 一直等，不占 CPU */
        if (xQueueReceive(q_half_ready, &dsc, portMAX_DELAY) == pdPASS) {
            pack_and_send_async(dsc.buf, dsc.len, dsc.seq);   /* 打包 + 丢进发送队列，不做阻塞发送 */
            xSemaphoreGive(sem_half_free);                    /* 说明这一半用完了（见下方说明） */
        }
    }
}

/* ── 启动 ── */
void acq_start(void)
{
    q_half_ready   = xQueueCreate(4, sizeof(half_desc_t));  /* 深度 4：能容忍任务落后 2 个半区 */
    sem_half_free  = xSemaphoreCreateCounting(2, 2);        /* 两个半区，初始都空闲 */
    configASSERT(q_half_ready && sem_half_free);

    HAL_ADC_Start_DMA(&hadc1, (uint32_t *)adc_buf, ADC_BUF_LEN);  /* 循环模式，一次启动即可 */
    xTaskCreate(vAcqTask, "acq", 256, NULL, 4, NULL);
}

这段骨架里有两个地方值得展开，因为它们正是"能跑"和"跑得好"的分界线：

第一，队列深度决定了你能容忍多大的抖动。 这里深度取 4，意味着任务最多可以落后 4 个半区（512ms × 4 = 2 秒）而完全不丢数据。 深度不是越大越好：它占用内存（每项 12 字节，4 项才 48 字节，其实很小）， 但更重要的是它代表了你对"任务可能被饿多久"的假设—— 如果你知道有个 Flash 擦除任务会占住 CPU 100ms，那么深度至少要覆盖这 100ms。

第二，sem_half_free 在这个例子里其实没有被中断侧用上，这是刻意的。 循环模式的 DMA 不需要"归还"缓冲（它的目标地址是硬件定死的两个半区，不会因为你没归还就停）。 这个信号量的价值在于给"缓冲池"版本留接口： 如果你的 DMA 是单次模式、由中断动态指定下一个目标缓冲（比如零拷贝的环形缓冲方案 B）， 那么中断在提交描述符之前必须先 xSemaphoreTakeFromISR(sem_half_free, ...) 拿到一个空闲缓冲的配额， 任务处理完再 Give 回来——这时候信号量就从"装饰"变成了"安全的保证"： 它保证了任务没处理完的缓冲绝不会被 DMA 复用。例程二里两种架构的代码都在，可以对照着看。

仲裁 软件优先级（4 档）+ 通道号小者优先 每个流一个仲裁器，4 个流一组：先软件优先级，再流编号 同上，但 DMAMUX 可以给不同请求源设置不同的同步/触发条件
FIFO 没有（数据直接进数据寄存器） 有，4 个 32 位字 = 16 字节，阈值 1/4、1/2、3/4、满 有，容量更大；BDMA 侧也有
突发 没有 支持 INCR4 / INCR8 / INCR16 支持，且与 FIFO 阈值配合更灵活
硬件双缓冲 DBM 没有，只能在 HT/TC 中断里做软件 ping-pong 有：M0AR/M1AR 两个地址 + CT 位由硬件自动切换 有
数据一致性 Cortex-M3，没有数据 cache，不用管 Cortex-M4（F4）/ M7（F7）：F4 不用管；F7 要按 M7 处理 Cortex-M7，有 D-Cache，必须处理 clean / invalidate 或配 MPU
错误类型 只有 TE TE + FE + DME TE + FE + DME（另有 DMAMUX 侧的溢出标志）

从 F1 往 F4 移植，除了改名字（DMA1_Channel1 → DMA1_Stream0）， 真正要动脑子的有四处：

1

通道号从"身份"变成了"选择"

F1 上「ADC1 就是通道 1」；F4 上「ADC1 可以用数据流 0 的通道 0，也可以换别的流」——但要查表确认这个组合合法。CubeMX 里点 Add 的时候它只列合法的组合，是最好的参考。

2

FIFO 模式与直接模式的选择

FIFOThreshold 不是"填了更好"的选项：外设 → 内存 + 高带宽 + 能用突发 → 用阈值模式（把零散请求攒成突发，摊薄总线开销）；传输总量很小、或者外设不支持突发 → 用直接模式（DMA_FIFOMODE_DISABLE）。阈值大于本次传输总量时要格外小心——ST 的流式 DMA 在传输结束时会把 FIFO 里剩下的数据推出去，但这个行为与传输长度、突发配置耦合，是排查"最后几个字节丢"时的重点怀疑对象。

3

DBM 把 ping-pong 交给硬件

软件 ping-pong 要在 HT/TC 两个中断里判断"现在该处理哪一半"，判断错了就出错；DBM 用 M0AR/M1AR 两个目标地址 + CT 位，每次传输完成硬件自动切换目标，中断里读 CT 就知道刚填满的是哪一块。切换零开销、不会漏掉边界，代价是只有 F4 及以后的系列才有，而且 HAL 里要用 HAL_DMAEx_MultiBufferStart_IT() 这套专门的 API，不能混用普通启动函数。

4

F7/H7 上要处理 cache

这是唯一一个"不改就一定会错、而且错得很随机"的差异项，下面单独讲。

cache 一致性：问题的本质是"两个主设备各有一份副本"。 Cortex-M7 为了提高取数速度，在 CPU 和 SRAM 之间加了一层数据 cache： CPU 读内存时，数据被缓存进 cache line（32 字节一行），之后 CPU 再读同一个地址就直接命中 cache，不去 SRAM。 而 DMA 是总线上的另一个主设备，它读写的是 SRAM，完全不经过 cache。 于是同一个地址就有了两份可能不一样的副本，方向不同后果也不同： 

  【方向一：内存 → 外设（发送）】CPU 写、DMA 读

    CPU 写数据 ──→ D-Cache（还在这里，是"脏"的，SRAM 里还是旧值）
                      │
                      ╳  DMA 不会来看 cache，它直接去 SRAM
                      ↓
    DMA 从 SRAM 读 ──→ 读出【旧数据】 ──→ 串口发出去一串错的

    ★ 修法：启动 DMA 之前，把脏数据从 cache 写回 SRAM →  SCB_CleanDCache_by_Addr(buf, len)

  【方向二：外设 → 内存（接收）】DMA 写、CPU 读

    DMA 写 SRAM ──→ SRAM 里是【新数据】
                      │
                      ╳  CPU 读这个地址时，cache 里还留着上次的旧副本 → 命中，读到旧值
                      ↓
    CPU 读 ──→ 读到【旧数据】──→ 你以为收的是新帧，实际是上一帧

    ★ 修法：DMA 写完之后、CPU 读之前，把 cache 里对应的行作废 →  SCB_InvalidateDCache_by_Addr(buf, len)
            （作废后下次读会去 SRAM 重新取，拿到新数据）

  【力度更大的修法：根本不让它进 cache】
    用 MPU 把 DMA 缓冲区所在的 RAM 区配置成 Normal + Non-cacheable，
    于是 CPU 每次访问都真去 SRAM —— 上面两个方向的问题同时消失，
    代价是 CPU 访问这块内存变慢（每次都要等 SRAM，几十个周期）。

三条落地规则，照着做就不会错：

1

按方向配对操作，顺序不能反

发送方向：先写数据 → clean → 再启动 DMA。接收方向：DMA 完成 → invalidate → 再读数据。如果缓冲区是双向使用的（比如命令要原地修改后再发回），用 SCB_CleanInvalidateDCache_by_Addr()，或者收发各做一次对应操作。

2

接收缓冲在 DMA 写入期间，CPU 一个字节都不能写

原因是 invalidate 的语义：它直接丢掉 cache 里的内容，不管那是不是 CPU 刚写进去还没落盘的修改。如果 CPU 在 DMA 写目标缓冲的同时也往里写了东西，invalidate 会把 CPU 的修改一起丢掉。这也是为什么"双缓冲"在 M7 上不只是为了边界，还是为了让某一半在某一时刻只属于一个主人。

3

缓冲区对齐到 32 字节，长度补齐到 32 的倍数

clean/invalidate 的粒度是 cache line（Cortex-M7 上是 32 字节），你没法只作废"半个行"。缓冲区首地址不 32 对齐、或者长度不是 32 的倍数，操作就会波及邻居变量——invalidate 会把邻居还没写回的数据丢掉，造成"莫名其妙被改掉的全局变量"。写法是 __attribute__((aligned(32))) static uint16_t rx_buf[256];，长度按 32 的倍数配（也顺手补齐到 32 的倍数做 clean/invalidate）。具体丢多少字节，例 5 有完整的算术。

MPU 方案值得单独说一句，因为对长期运行的采集器来说它是最省心的选择： 配置一次，之后所有代码都不需要记得 clean/invalidate， 也就不会因为"某个新加的收发函数忘了加这句"而在半年后冒出一个偶发 bug。 代价是这块内存的 CPU 访问速度下降。所以工程上的标准做法是 「只把 DMA 缓冲区那一小块（比如 1KB）配成 non-cacheable，其余 RAM 照常缓存」—— DMA 缓冲区本来就不是 CPU 频繁访问的对象，慢一点无所谓。 实现上用 HAL_MPU_ConfigRegion() 配一个 region， 属性设为 TEX = 1、C = 0、B = 0、S = 1（Normal memory, Non-cacheable）， 注意 region 的基地址必须按 region 大小对齐（大小必须是 2 的幂，最小 32 字节）， 并且按 ST 官方例程的顺序：先配置 MPU，再使能 I-Cache 和 D-Cache。

第 2 节到这里结束：七个问题，一句话各一个

2.1 环形缓冲靠 HT/TC 两个硬件锚点切成两半，处理"刚满的那一半"，超过 T_half 就丢数据且必须计数； 2.2 NDTR 反推写指针在 IDLE/单次/健康检查三种场合是准的，在"精确边界"上是不可靠的； 2.3 帧接收要分三层，IDLE 中断只记账，重同步靠超时； 2.4 四级优先级只在通道仲裁里起作用，总线那一层是轮询，真正决定成败的是带宽预算； 2.5 DWT 给精确数字、GPIO + 示波器给真相，两者要互相验证； 2.6 TE 会自己刹车、FE/DME 不会，重启前要清标志、要限次数、要让上位机知道； 2.7 回调只发消息，缓冲所有权用队列 + 信号量交接； 2.8 换系列要重新想清楚映射、FIFO、DBM 和 cache 这四件事。

动手算一遍

前面七个小节讲了不少"应该这样做"，但工程上的每一个"应该"背后都应该有个数。 这一节把采集器从需求到实现要做的六笔账算完： 多大容量、半区取多大、四路怎么分带宽、DMA 到底省多少、cache 对齐差多少、队列要多深。 六个例子共用一套配置，前一个例子的结果就是后一个例子的输入，建议按顺序看。

共同前提（后面所有例子都基于这一套）

芯片 STM32F103C8T6（Cortex-M3，72MHz，64KB Flash，20KB SRAM）； 采集 1kHz、12 位、单通道，每个采样点用 uint16_t 存（高 4 位补 0），所以 2 字节/点； 总时长 10 分钟 = 600 秒；上传走 USART1，115200 8N1（每字节 10 位）； 另有一路 SPI1 读外部 Flash，9MHz；无 RTOS（例 6 会切到 FreeRTOS 算一遍）。 串口、SPI、ADC1 都挂在 APB2 上，APB2 = HCLK = 72MHz。

例 1：10 分钟的数据到底有多大？能不能先存下来再传？

第一问：总量。这一步只要乘三个数： 

  采样点数 N = f_s × T = 1000 点/秒 × 600 秒 = 600 000 点
  总字节数 B = N × 2 字节/点 = 600 000 × 2 = 1 200 000 字节 = 1.2 MB

  ── 和这块芯片比一比：
       SRAM 20 KB   →  1.2 MB 是其 60 倍
       Flash 64 KB  →  1.2 MB 是其 18.75 倍
     → 结论：本地存不下。必须"边采边传"，或者外挂存储（SPI Flash / SD 卡）。

  ── 数据率（这才是决定架构的那个数）：
       R_in = 1000 点/秒 × 2 字节 = 2 000 字节/秒 = 2 KB/s = 16 kbit/s
     → 它只占 115200 的 17.4%，看起来非常宽裕。这个"看起来"很重要，见第二问。

第二问：传得完吗？115200 8N1 下，每个字节在线上占 10 位 （1 位起始 + 8 位数据 + 1 位停止，无校验），所以有效字节率是： 

  串口字节率 R_out = 115200 bit/s ÷ 10 bit/字节 = 11 520 字节/秒

  【方案 A · 先存后传（假设外挂了 1.2MB 的存储）】
       纯二进制：1 200 000 ÷ 11 520 = 104.17 秒  ≈ 1 分 44 秒
       留 20% 余量（协议头、应答、重传）：
                 104.17 ÷ 0.8 = 130.2 秒 ≈ 2 分 10 秒

  【方案 B · 实时刻传（本项目的选择）】
       采集 600 秒，同时以 2 KB/s 上传：
       串口占用 = 2 000 ÷ 11 520 = 17.4%（剩下的留给下行命令和心跳）
       采集和上传同时完成，总时长就是 600 秒。 ✔

  【方案 C · 实时刻传，但是 ASCII 格式】
       "1234,\r\n" 这样的文本，每个点 ≈ 6 字节（4 位数字 + 逗号 + CR + LF）
       数据率 = 600 000 × 6 ÷ 600 秒 = 6 000 字节/秒
       串口占用 = 6 000 ÷ 11 520 = 52.1%（超过一半，下行命令开始被挤）
       如果是先存后传：3 600 000 ÷ 11 520 = 312.5 秒 = 5 分 12 秒

  ── 对比：同一份数据，ASCII 化之后是二进制的 3 倍大、3 倍慢。
     "用文本格式方便调试"的代价是可以量化的：3 倍。

这三行数字决定了一个非常重要的架构选择： 因为是实时刻传，所以缓冲区不需要存 10 分钟的数据，只需要存"从 DMA 写完到串口发完"这段时间的数据。 这句话是后面所有缓冲区大小的计算起点。如果你选的是方案 A，那你要算的是 1.2MB 的存储， 而例 2 的半区计算就完全用不上了——先想清楚架构，再算数。

例 2：半区该取多大？主循环最长能阻塞多久？

这是本文最核心的一个计算，因为它同时决定了两件事： 缓冲占多少 RAM，以及你的主循环有多少时间余量。 开始之前先把关系式摆出来（物理意义：一半缓冲被填满需要多久）：

半区时间的定义式

T_half = (N_buf ÷ 2) ÷ (f_s × B_sample)

其中 N_buf 是整个 DMA 缓冲的字节数（单位 字节），N_buf ÷ 2 是一个半区的字节数， f_s 是采样率（单位 Hz = 点/秒），B_sample 是每个采样点的字节数（本例 2 字节/点）， 分母 f_s × B_sample 就是数据率（单位 字节/秒）。

所以 T_half 的单位是秒，含义是「DMA 从半区开头写到半区结尾需要的时间」—— 也就是「你收到半区中断之后，有多久必须把它处理完，否则 DMA 就会转过头来盖掉它」。

取 N_buf = 1024 个半字（1024 个采样点、共 2048 字节）试试：

  半区点数 N_half = 1024 ÷ 2 = 512 个点 = 1024 字节
  数据率      R_in  = 1000 × 2 = 2 000 字节/秒

  T_half = 1024 ÷ 2 000 = 0.512 秒 = 512 毫秒

  ── 含义：每 512ms 收到一次半区中断，你必须在下一个 512ms 之内处理完。
     反过来说：主循环里任何一段超过 512ms 不理会采集的代码，都会造成数据丢失。

  ── 那么"最坏阻塞时间"包括哪些？
       · 主循环正在跑的一段耗时任务（打一帧包、算 CRC16、写 SPI Flash）
       · 更高优先级中断里花的时间（串口收发、SysTick、其他 DMA）
       · 关中断区（临界区、Flash 擦写等待、某些 HAL 函数的内部临界区）
     三者要加起来看最坏情况，不能只看你自己写的那段循环。

  ── 设计余量系数 K（工程经验取 3~5）：
       要求：最坏阻塞时间 T_block_max ≤ T_half ÷ K
       K = 4 时：T_block_max ≤ 512 ÷ 4 = 128 毫秒

  ── 反推（当你已知主循环最坏会阻塞多久时，用这个方向）：
       假设 SPI Flash 扇区擦除会阻塞 20ms（典型值 30~100ms，这里按乐观的 20ms 算）
       这 20ms 里产生的数据量 = 0.020 秒 × 2 000 字节/秒 = 40 字节
       乘上余量系数 K = 4 → 半区至少要 160 字节（80 个点）→ 就近取 256 个点（512 字节）的半区
       → 即 N_buf = 512 个半字（512 个点），此时 T_half = 512 字节 ÷ 2 000 字节/秒 = 256 毫秒

现在换一个采样率看看会发生什么。把 f_s 从 1kHz 提到 20kHz（做振动分析时的常见值）， 缓冲大小一个字都不改： 

  f_s = 20 000 点/秒，B_sample = 2 字节 → R_in = 40 000 字节/秒

  半区仍为 512 个点（1024 字节）：
       T_half = 1024 ÷ 40 000 = 0.0256 秒 = 25.6 毫秒     （原来是 512ms，缩小 20 倍）

  ── 结论：K = 4 时，主循环最多只能阻塞 6.4 毫秒。
     这个预算下，"在中断里跑一趟 HAL、打一条 printf、擦一个 Flash 扇区"全都不行了。
     要么把缓冲加大（N_buf = 8192 个半字 → T_half = 205ms），
     要么把处理逻辑彻底搬到"零拷贝"路径上（见 2.3 的架构 B）。

  ── 中断频率也随之变化（这个数直接决定 CPU 开销）：
       N_buf = 1024 个半字时，一次半区事件 = 512 个半字（1024 字节）
       1 kHz  ：1 000 ÷ 512 = 2.0 次/秒（HT + TC 合计 3.9 次/秒）
       20 kHz ：20 000 ÷ 512 = 39.1 次/秒（合计 78.1 次/秒）
     乘上 2.5 节实测的 300 周期/次：
       20 kHz 时 = 78.1 × 300 = 23 430 周期/秒 = 0.033% —— 依然微不足道。 ✔
半区取值的两张嘴：RAM 和余量

看到这里你可能会想"那半区取大一点不就行了"。 取大的代价是 RAM 和延迟：N_buf = 8192 个半字时，20KB 的 SRAM 已经被吃掉 80%， 而且 T_half 变长意味着半区中断变稀，但"发现丢失"也变慢—— 如果某一次处理失败，你要等 205ms 才知道。

所以半区大小的正确选法是：先算出"最坏阻塞时间 × 数据率 × K"得到下限， 再考虑 RAM 余量定上限，最后取一个 2 的幂次（512、1024、2048）， 因为 2 的幂次能让"半区边界"和"帧边界"对齐时好算得多。

例 3：四路 DMA 同时跑，总线到底被占了多少？

2.4 节讲了带宽预算的四步法，这里把数填进去。 先把四路的数据率各自算出来（都用真实配置，不用"大约"）： 

  ① ADC1（外设 → 内存）
       R = 1 000 点/秒 × 2 字节/点 = 2 000 字节/秒 = 2.0 KB/s

  ② USART1_TX（内存 → 外设，上传采集数据）
       R = 115 200 bit/s ÷ 10 bit/字节 = 11 520 字节/秒
       （例 1 方案 B 说实际只用 2 000 字节/秒，但预算要按【满速】算，才叫预算）

  ③ USART1_RX（外设 → 内存，收上位机命令）
       R = 11 520 字节/秒（同样按满速算）

  ④ SPI1_RX（外设 → 内存，读外部 Flash，9MHz 8 位模式）
       R = 9 000 000 bit/s ÷ 8 bit/字节 = 1 125 000 字节/秒 = 1.125 MB/s
       （注意：这是"SPI 时钟满速连续读"的极端值。实际读 Flash 时
         有命令字节、有等待周期、有换页间隙，有效值通常只有 40%~60%，
         但预算按满速算才不会出错。）

  ── 四路合计：2 000 + 11 520 + 11 520 + 1 125 000 = 1 150 040 字节/秒 ≈ 1.15 MB/s

有了字节率，再乘上"每个字节要花多少个总线周期"。 这个系数的推法在第 30 篇讲过（一次传输 = 读 + 写，各含地址相位和数据相位）， 这里直接取保守值 C = 6 个 AHB 周期/字节： 

  C 的构成（保守估算）：
       读源地址    1 地址相位 + 1 数据相位 = 2 周期
       写目的地址  1 地址相位 + 1 数据相位 = 2 周期
       APB 桥同步等待（外设挂 APB2）       ≈ 2 周期
       ─────────────────────────────────────────────
       合计 C = 6 AHB 周期 / 字节

  总周期需求 = Σ(R × C) = 1 150 040 × 6 = 6 900 240 AHB 周期/秒

  占用率 = 6 900 240 ÷ 72 000 000 = 0.09583 = 9.58%

  ── 分解到每一路（这样才知道该关注谁）：
       ADC1     ：2 000 × 6 = 12 000 周期/秒     → 0.0167%
       USART1_TX：11 520 × 6 = 69 120 周期/秒    → 0.096%
       USART1_RX：11 520 × 6 = 69 120 周期/秒    → 0.096%
       SPI1_RX  ：1 125 000 × 6 = 6 750 000 周期/秒 → 9.375%
       ─────────────────────────────────────────────────
       合计                                       9.58%

  ── 两个必须一起看的对照数：
       ① 字节带宽占比：1.15 MB/s ÷ (72MHz × 4 字节) = 1.15 ÷ 288 = 0.40%
          → 从"总吞吐量"看，你连 1% 都没用到，非常安全。
       ② 周期占用占比：9.58%
          → 从"总线时间"看，接近 10% 的时间总线在给 DMA 干活。

  ── 为什么这两个数差这么多？因为 DMA 一次只搬 1~2 个字节，
     却要走完整的"地址相位 + 数据相位"（4~6 个周期），效率很低。
     这也正是第 30 篇讲突发传输（burst）的原因：
     一次 INCR8 突发搬 8 个字节只用 8 个数据周期 + 1 个地址周期，
     平摊下来每字节不到 1.2 个周期，比这里的 6 个周期省 5 倍。
     F1 没有突发，所以只能吃这个 6 周期的系数。
9.58% 的占用，对 CPU 意味着什么？

不是"CPU 慢了 9.58%"。原因是两级结构： 第一级，DMA 控制器内部为每一路服务时是串行的，所以四路之间确实会互相等（2.4 节的两级仲裁）； 第二级，DMA 与 CPU 争同一个从设备（SRAM / APB 桥）时靠总线矩阵轮询—— CPU 的访问偶尔会被插一个等待周期。

所以更准确的表述是：CPU 访问 SRAM 的平均延迟会略微上升，而 SPI1_RX 那一路上， 会明显感到"总线被 CPU 和其他 DMA 挤"（它自己要吃掉 9.375% 的份额）。 真正需要警惕的阈值是：单一路 DMA 的占用率超过 25%~30%， 此时 CPU 访问同一个从设备会出现肉眼可见的变慢（比如本来 2 周期的 SRAM 读变成 5~10 周期）， 表现出来就是"加了 SPI 屏之后，主循环莫名其妙变慢了"。

把 SPI 提到 18MHz 会怎样？2.25 MB/s → 占用率翻倍到 18.75%。口径：本页按 C = 6 周期/字节（零等待、无仲裁冲突的理想值）估算；DMA 与总线矩阵 的同工况表按 C = 10 计算，属带等待周期的保守值（所以那边写 31.3%）。 还安全，但已经进入"要盯着看"的区间了。

例 4：中断搬 vs DMA 搬，到底差多少 CPU 周期？

用 2.5 节实测表里的两个数作为输入： 逐字节中断 108 周期/字节（裸机 ISR）、IDLE + DMA 按 512 字节半区 340 周期/次（含 IDLE 中断的记账开销）。 两个波特率各算一遍，你会看到一个很有意思的规律。 

  【中断方案】
       字节率 = 115 200 ÷ 10 = 11 520 字节/秒
       周期消耗 = 11 520 × 108 = 1 244 160 周期/秒
       占用率 = 1 244 160 ÷ 72 000 000 = 0.01728 = 1.728% ≈ 1.73%

  【DMA 方案】
       事件次数 = 11 520 字节/秒 ÷ 512 字节/次 = 22.5 次/秒
       （每次数据"攒够"512 字节才产生一次中断）
       周期消耗 = 22.5 × 340 = 7 650 周期/秒
       占用率 = 7 650 ÷ 72 000 000 = 0.0001063 = 0.0106% ≈ 0.011%

  【比值】1 244 160 ÷ 7 650 = 162.6 倍
  【中断方案】
       字节率 = 1 000 000 ÷ 10 = 100 000 字节/秒
       周期消耗 = 100 000 × 108 = 10 800 000 周期/秒
       占用率 = 10 800 000 ÷ 72 000 000 = 0.15 = 15.0%

  【DMA 方案】
       事件次数 = 100 000 ÷ 512 = 195.3 次/秒
       周期消耗 = 195.3 × 340 = 66 406 周期/秒
       占用率 = 66 406 ÷ 72 000 000 = 0.000922 = 0.0922% ≈ 0.092%

  【比值】10 800 000 ÷ 66 406 = 162.6 倍
比值恒等于 162.6，这个"巧合"说明了一切

两个方案的周期消耗都正比于数据率，所以比值与波特率无关。 这个比值只由两个数决定：单字节中断的开销（108 周期）和 单次半区中断的开销平摊到每个字节上（340 ÷ 512 = 0.664 周期/字节）。 108 ÷ 0.664 = 162.6。

换句话说：DMA 省的倍率，等于"半区越大，省得越多"，上限是 108 倍（当半区无限大、平摊到零时）…… 等等，这里要小心：平摊值可以无限小，但比值不能无限大—— 我们把 340 周期/次平摊成 0.664 周期/字节，而中断方案是 108 周期/字节， 所以只要半区足够大，比值可以做到几百倍。 真正限制它的是"余量"：半区越大，T_half 越长，但 RAM 也越费（例 2）。

现在看这张对比表里最要紧的一列——最坏情况。 这才是选择 DMA 的真正理由：

看第五行。115200 的中断方案还留着 85.3µs 的余量，看起来很安全； 到 1Mbps 就只剩 8.5µs——而 8.5µs 只是 612 个周期，比一次 Flash 页编程的中断关闭时间短得多。 这就是为什么"高速串口 + 中断搬数据"在实践中一定会翻车： 不是平均占用顶不住，而是它把整个系统的中断延迟预算压缩到了不可能满足的程度。

而 DMA 方案的约束换了一种形式：从"每个字节必须及时响应"变成"每个半区必须及时处理"—— 115200 下是每 512ms 一次（半区 512 字节、2KB/s 数据率……注意这里是按 512 字节半区算： 512 ÷ 11 520 = 44.4ms）， 1Mbps 下是 512 ÷ 100 000 = 5.12ms。 从 8.5µs 到 5.12ms，宽松了 600 倍——这才是 DMA 带来的真正自由。

例 5：cache line 32 字节，缓冲没对齐会波及多少数据？

这个例子只在有数据 cache 的芯片上成立（Cortex-M7，比如 STM32F7/H7）。 场景很普通：你的接收缓冲是 uint16_t rx_buf[128]（256 字节）， 它被编译器放在了 0x2000_0004——也就是距离 32 字节边界差了 4 个字节。 然后你在 DMA 收完之后调用了 SCB_InvalidateDCache_by_Addr(rx_buf, 256)。 

  Cortex-M7 的 D-Cache line = 32 字节。clean / invalidate 的最小粒度是【一整行】。

  缓冲区间：[0x20000004, 0x20000104)   ← 首地址 + 256 字节
  行边界  ：0x20000000, 0x20000020, 0x20000040, …（每 32 字节一个）

  需要作废的行：
       起始行 = floor(0x04 ÷ 32) = 第 0 行（0x20000000 ~ 0x2000001F）
       结束行 = ceil(0x104 ÷ 32) = 第 9 行…… 换个算法：
                末字节地址 0x103（即 0x20000103）落在第 floor(0x103 ÷ 32) = 第 8 行
       所以实际覆盖：第 0 行 ~ 第 8 行 = 9 行

  覆盖字节数 = 9 × 32 = 288 字节
  多覆盖     = 288 - 256 = 32 字节

  ── 这 32 个字节是"别人的"：
       开头多覆盖 4 字节（0x20000000 ~ 0x20000003）
       结尾多覆盖 28 字节（0x20000104 ~ 0x2000011F）
     如果这些地址上有别的全局变量，而它们的值此刻正躺在 cache 里还没写回 SRAM，
     invalidate 会【直接丢弃】这些尚未落盘的修改 → 变量神秘地丢更新。

  ── 对齐之后的账：
       __attribute__((aligned(32))) static uint16_t rx_buf[128];
       地址 0x20000000（或任意 32 的倍数）→ 覆盖第 0 行 ~ 第 7 行 = 8 行 = 256 字节
       多覆盖 0 字节。 ✔

  ── 顺带算一下开销（按典型值估算）：
       作废 8 行需要 8 次 cache 维护操作，M7 上约 5~15 周期/行 → 40~120 周期
       1Mbps 下每秒 195 次接收 → 195 × 80 ≈ 15 600 周期/秒 = 0.022%
     结论：clean/invalidate 的开销从来不是问题，问题永远是"忘了做"和"没对齐"。

顺便把这个例子的"另一面"也算清楚：并不是所有 DMA 缓冲都需要对齐。 只有那些会经过 cache 维护操作（clean / invalidate）的缓冲区才需要。 如果 DMA 的目标是不可能被 cache 的内存的——比如外设寄存器（CPAR 指向 USART1->DR）—— 那就不存在一致性问题。这也是为什么"把 DMA 缓冲区配成 non-cacheable（MPU）"能一劳永逸： 不进 cache，就没有行边界这回事，也不需要对齐。

例 6：队列要多深？背压什么时候会压垮你？

最后一个例子回到 2.7 节的 RTOS 骨架：中断往队列里放描述符，任务从队列里取。 队列深度不是"随便给个 4"，它有一个明确的计算依据： 生产者（DMA）在消费者（任务）被阻塞期间能产出多少东西。 

  【生产速率】R_in = 1 000 点/秒 × 2 字节 = 2 000 字节/秒
  【消费速率】R_out = 115 200 ÷ 10 = 11 520 字节/秒（串口满速上传）

  ── 第一步：先看"消费者跟不跟得上"
       11 520 ÷ 2 000 = 5.76 倍 → 串口速度是数据率的 5.76 倍，跟得上。 ✔

  ── 第二步：算任务可能被阻塞多久（T_block_max）
       假设系统里还有：SPI Flash 日志任务（最长占 CPU 20ms）、
       上位机命令处理任务（优先级更高，最长 5ms）、
       一个 10ms 周期的控制任务。
       最坏情况：采集任务被压住的累计时间 T_block_max ≈ 35 ms（按典型值估算，工程上再乘 2）
       取 T_block_max = 70 ms。

  ── 第三步：这 70ms 里 DMA 会填满多少数据？
       产出量 = R_in × T_block_max = 2 000 × 0.070 = 140 字节

  ── 第四步：换算成"几个半区"（队列里放的是半区描述符）
       队列深度 D ≥ 产出量 ÷ 半区字节数 = 140 ÷ 1024 = 0.14 → D = 1 就够
       工程上取 D = 4（余量 15 倍）

  ── 用"时间"来表示更直观（推荐给同事讲的时候用这个）：
       一个半区（1024 字节）代表 1024 ÷ 2 000 = 512 毫秒的数据
       队列深度 4 → 最多能容忍任务落后 4 × 512ms = 2048 毫秒 ≈ 2 秒

  ── 内存代价：每个描述符 = 指针(4) + 长度(2) + 序号(4) = 10 字节，
     对齐后 12 字节；深度 4 → 48 字节。对比 20KB 的 SRAM，可以忽略。

现在把采样率提到 20kHz，同一个架构会怎样？ 

  R_in  = 20 000 × 2 = 40 000 字节/秒
  R_out = 11 520 字节/秒

  ── 40 000 > 11 520 → 消费者【追不上】。差值 28 480 字节/秒会全部堆进队列。
     队列是有限长的，堆满之后只能丢弃（这就是背压），或者让 DMA 停下来（流控）。

  ── 三个出路，各自要付什么代价：
      ① 换 1 Mbps：R_out = 100 000 字节/秒 → 占用 40%，可行 ✔
      ② 降采样/抽点上传：只传每 4 个点里的 1 个 → R_in 降到 10 000 字节/秒 → 可行
         代价：丢掉高频信息（振动分析里恰恰不能丢）
      ③ 本地存储 + 事后导出：把 40KB/s 写进 SD 卡/SPI Flash（要算卡的写入速度）

  ── 队列深度在"追不上"的场景下变成另一个含义：
       它不再代表"能容忍多少抖动"，而代表"能缓冲多少数据"——
       D × 512 字节的缓冲 ÷ 28 480 字节/秒 = 能撑多久
       D = 4 → 2 048 ÷ 28 480 = 0.072 秒 = 72 毫秒
     也就是说：系统会在 72 毫秒内堆满队列，然后开始丢数据。
     【这时候你必须靠"队列满的次数"这个计数器报警，而不是靠感觉】
六道题的答案串起来就是一个设计流程

例 1 告诉你"存不下、必须实时传"，所以架构是"边采边传"； 例 2 由数据率和最坏阻塞时间定出半区大小（1024 个半字缓冲、T_half = 512ms）； 例 3 确认四路并发时总线占用不到 10%，优先级怎么排都不会出问题； 例 4 证明 DMA 方案的价值在于把"每字节 8.5µs 的响应预算"变成"每半区 5ms 的处理预算"； 例 5 只对有 M7 cache 的芯片成立，但结论很硬——对齐到 32 字节，多覆盖 32 字节，代价可忽略； 例 6 把队列深度从"随手写个 4"变成"由最坏阻塞时间反推出来的 4"。

这六笔账加起来大概 10 分钟的纸面工作，能省掉你后面几天的调试。 凡是要动缓冲区大小、采样率、波特率、任务优先级里的任何一个，就回来把相关的例子重算一遍。

这张图里有一个特别容易做错的地方值得单独提出来：1kHz 的采样率是怎么来的？ ADC 在连续模式下是"转完一个立刻转下一个"，速度由 ADC 时钟和采样时间决定—— 而 ADC 时钟 12MHz、采样时间 55.5 周期时，一次转换只要 5.67µs，也就是 176kHz。 如果你用连续模式，实际采样率是 176kHz 而不是 1kHz， DMA 会在 5.8ms 内把 1024 个点的缓冲写满一圈， 你的"每 512ms 处理一次"直接变成"每 5.8ms 处理一次"，全盘皆错。

正确的做法是用定时器触发 ADC，把"采样率"这件事交给定时器。 F103 的 ADC 规则组有 8 个可选的外部触发源（CR2.EXTSEL[2:0]）， 每个触发沿启动一次转换，这一次转换完成后产生一个 DMA 请求。 这样采样率 = 触发频率 = 定时器频率 ÷ (PSC+1) ÷ (ARR+1)，而定时器时钟来自晶振，精度比你想象的任何软件延时都高得多。 

/* 目标：每 1ms 产生一次 ADC 触发，硬件自动完成，CPU 不参与。 */

/* ── 第一步：TIM3 的时基 ──
 * TIM3 挂在 APB1 上。APB1 分频系数为 2（36MHz）时，定时器时钟是 72MHz，
 * 所以 PSC = 7199 得到 72MHz / 7200 = 10kHz 的计数频率。 */
TIM3->PSC = 7199;
TIM3->ARR = 9;                    /* 10kHz / (9+1) = 1kHz 更新事件 */

/* ── 第二步：让更新事件去触发 ADC（TRGO） ──
 * MMS[2:0] = 010 表示"更新事件作为 TRGO 输出"。
 * 注意：这一步是把 TIM3 的"内部事件"引到 TRGO 线上，它并不产生引脚输出。 */
TIM3->CR2 &= ~TIM_CR2_MMS;
TIM3->CR2 |= TIM_CR2_MMS_1;       /* MMS = 010 → TRGO = Update */

/* ── 第三步：ADC 改成"外部触发、单次转换" ──
 * 关键三处：
 *   CONT = 0    不要连续转换，每次触发只转一个
 *   EXTTRIG = 1 允许外部触发
 *   EXTSEL = 101 → TIM3_TRGO（查 F103 参考手册的 EXTSEL 表） */
ADC1->CR2 &= ~(ADC_CR2_CONT | ADC_CR2_EXTSEL | ADC_CR2_EXTTRIG);
ADC1->CR2 |= ADC_CR2_EXTSEL_2 | ADC_CR2_EXTSEL_0 | ADC_CR2_EXTTRIG;
/* 上面这句：EXTSEL_2|EXTSEL_0 = 101 = TIM3_TRGO。HAL 里对应
 * ADC_EXTERNALTRIGCONV_T3_TRGO，用 HAL 的话可以写得更清楚： */
/* ADC_HandleTypeDef 里：hadc1.Init.ContinuousConvMode    = DISABLE;
 *                       hadc1.Init.ExternalTrigConv      = ADC_EXTERNALTRIGCONV_T3_TRGO;
 *                       hadc1.Init.ExternalTrigConvEdge  = ADC_EXTERNALTRIGCONVEDGE_RISING; */

/* ── 第四步：启动。注意顺序：先开 DMA，再开定时器 ──
 * 反过来的话，定时器已经在触发 ADC，而 DMA 还没准备好，
 * 前几个转换结果会因为没人搬而白丢（ADC 的 OVR 会置位）。 */
HAL_ADC_Start_DMA(&hadc1, (uint32_t *)adc_buf, ADC_BUF_PTS);   /* 512 个【点】，不是字节 */
TIM3->CR1 |= TIM_CR1_CEN;                                        /* 最后才让定时器跑起来 */

/* ── 校验一下采样时间够不够 ──
 * 触发周期 = 1ms。一次转换需要 (采样周期 + 12.5) 个 ADC 时钟。
 * 取 SMPR = 55.5 周期：(55.5 + 12.5) × (1/12MHz) = 68 × 83.3ns = 5.67µs ≪ 1ms ✔
 * 如果触发频率提到 200kHz（周期 5µs），这 5.67µs 就【超标】了，
 * 必须把采样时间降到 7.5 周期（20 周期 × 83.3ns = 1.67µs）。 */
顺手记住那个"数量不是字节"的坑

HAL_ADC_Start_DMA(&hadc1, (uint32_t *)adc_buf, 512) 里的 512 是"要传输的转换个数"（也就是点数），不是字节数。 因为 ADC 的 DMA 请求是"半字"粒度的，HAL 内部调用 HAL_DMA_Start_IT() 时也是按个数传。

但如果你直接写寄存器，CNDTR 里装的也是"个数"—— 传输宽度是 16 位时，CNDTR = 512 表示搬 512 个半字 = 1024 字节。 凡是"个数"和"字节"混在一起的地方就是出 bug 的地方： NDTR 反推写指针时如果按字节算，指针会跑得比实际快一倍。

4.2 采集器主体：缓冲管理、打包与上传调度

现在写采集器的"心脏"。它由三个部分组成： ①中断侧——只做"标记哪一半满了"和"溢出计数"； ②主循环侧——发现标记就把那一半打包成一帧、丢给发送状态机； ③健康检查——用 NDTR 反推写指针，定期检查有没有跑偏。 先看双缓冲的时间关系，这张图把"两个半区如何交替成为生产者和消费者"画清楚了： 

  时间轴（每一格 = 128ms）
  ├────┼────┼────┼────┼────┼────┼────┼────┼────┼────┼────┼────┤
  0  128  256  384  512  640  768  896 1024  ...                (ms)

  DMA 正在写哪一半：
  [======= 半区 0 =======][======= 半区 1 =======][===== 半区 0 =====]
  ↑                     ↑                       ↑
  0ms                  512ms                 1024ms
                    HT 中断                 TC 中断

  中断发生的事情（只有两条语句）：
   HT @512ms ──→ half_ready[0] = 1;  半区 0 已经满了，等主循环来取
   TC @1024ms ──→ half_ready[1] = 1;  半区 1 已经满了，等主循环来取

  主循环看到的窗口（假设处理一次要 8ms）：
        ├─8ms─┤                                          ├─8ms─┤
        ↑ 处理半区 0（adc_buf[0..511]）                   ↑ 处理半区 1
        512ms 中断后立刻开始                             1024ms 中断后立刻开始

  关键时间预算（例 2 算过）：
  · 从 half_ready[x] = 1 到必须处理完，最多有 T_half = 512ms
  · 也就是说：主循环里任何一段阻塞 < 512ms 的代码都是安全的
  · 处理只花 8ms，余量 504ms —— 这就是"设计余量系数 K ≈ 64"的实际情况
  · 如果处理时间 > 512ms（比如 printf 一条 1024 字节的文本），
    DMA 会转过头来把半区 0 覆盖掉，而 half_ready[0] 还没来得及被清 → half_lost++

  ── 为什么不用"单缓冲 + 搬完再处理"？
     那样每次都要停下 DMA、等待、重启，两次传输之间必然有一段空窗，
     而且 DMA 停下来的时候定时器还在触发，ADC 的转换结果会进 OVR。
     双缓冲的全部意义就是：搬运和处理在时间上【重叠】，谁也不等谁。
#include "stm32f1xx_hal.h"

/* ── 缓冲与状态：全部是 volatile，因为中断和主循环都碰它们 ── */
#define ADC_BUF_PTS   1024                    /* 总点数（半字个数），= 2048 字节 */
#define HALF_PTS      (ADC_BUF_PTS / 2)       /* 512 点 = 1024 字节 */
#define HALF_MS       512u                    /* 一个半区代表的时间（例 2 算过） */

static uint16_t adc_buf[ADC_BUF_PTS];

volatile uint8_t  half_ready[2] = {0, 0};     /* [0]=前半区 [1]=后半区 */
volatile uint32_t half_seq      = 0;          /* 半区序号，用于对齐时间轴 */
volatile uint32_t half_lost     = 0;          /* 溢出次数：核心健康指标 */
volatile uint32_t half_ok       = 0;

/* ── 中断侧：HT 回调 = 前半区满，TC 回调 = 后半区满 ──
 * HAL 的两个回调分别对应 DMA 的 HT 和 TC 中断。
 * 注意它们是【同一个 DMA 通道】的两个不同中断源，不是两个通道。 */
void HAL_ADC_ConvHalfCpltCallback(ADC_HandleTypeDef *hadc)
{
    if (half_ready[0]) {
        half_lost++;              /* 上一轮的前半区还没被处理 → 已经被覆盖了 */
    }
    half_ready[0] = 1;
    half_seq++;
}

void HAL_ADC_ConvCpltCallback(ADC_HandleTypeDef *hadc)
{
    if (half_ready[1]) {
        half_lost++;
    }
    half_ready[1] = 1;
    half_seq++;
}

/* ── 健康检查：用 NDTR 反推"DMA 现在写到哪了" ──
 * CNDTR 是【剩余未搬的点数】。循环模式下它从 512 递减到 0 后自动重装为 512，
 * 所以 "已经搬走的点数 = 512 - CNDTR"，这个值对 512 取模就是写指针。 */
uint16_t acq_write_index(void)
{
    uint16_t ndtr = DMA1_Channel1->CNDTR;
    return (uint16_t)((ADC_BUF_PTS - ndtr) % ADC_BUF_PTS);   /* 0 ~ 511 */
}

/* 写指针在哪一半？（用途：判断"我们正在读的那一半"是不是安全） */
uint8_t acq_writing_half(void)
{
    return (acq_write_index() < HALF_PTS) ? 0 : 1;
}

/* ── 读数前的最后一道保险 ──
 * 主循环拿到 half_ready[0] = 1，准备读 adc_buf[0..511]。
 * 万一此刻 DMA 已经绕回来写半区 0 了（说明严重超时），读出来的就是半新半旧的数据。
 * 这里用写指针做一次校验：如果 DMA 正在写的就是我要读的那一半 → 放弃这次读取。 */
static uint8_t half_is_safe_to_read(uint8_t idx)
{
    return (acq_writing_half() != idx);
}

中断侧只有这几行，所有耗时的活都在主循环。下面是主循环侧的打包与上传调度—— 注意上传用的是"发送状态机"而不是"阻塞发送"， 这是保证主循环不会被串口拖住的关键（也是例 6 里"背压可观测"的前提）： 

/* ── 帧格式（与 2.3 一致）：AA 55 | LEN | CMD | SEQ | PAYLOAD | CRC16 | 0D 0A ── */
#define FRAME_MAX     600                     /* 512 字节负载 + 9 字节开销 + 余量 */
#define CMD_DATA      0x01

static uint8_t  tx_buf[FRAME_MAX];
static volatile uint8_t tx_busy = 0;          /* 1 = DMA 正在发这一帧 */

/* CRC16/MODBUS：多项式 0xA001（反射式 0x8005），初值 0xFFFF。
 * 用位运算版本，不查表——512 字节的一帧算下来约 4096 次循环，
 * 在 72MHz 上约 0.2ms，对 256ms 的节奏完全无压力。 */
static uint16_t crc16_modbus(const uint8_t *p, uint16_t len)
{
    uint16_t crc = 0xFFFF;
    while (len--) {
        crc ^= *p++;
        for (uint8_t i = 0; i < 8; i++) {
            if (crc & 1) crc = (uint16_t)((crc >> 1) ^ 0xA001);
            else          crc = (uint16_t)(crc >> 1);
        }
    }
    return crc;
}

/* ── 把一个半区打包成一帧，放进 tx_buf ──
 * 返回帧总长。注意这里是"字节流化"的地方：
 * 采样点在内存里是小端半字，线上也按小端发（低字节在前），上位机按同规则解析。 */
static uint16_t pack_half(const uint16_t *src, uint16_t pts, uint16_t seq)
{
    uint16_t n = 0;
    tx_buf[n++] = 0xAA;
    tx_buf[n++] = 0x55;
    tx_buf[n++] = (uint8_t)(pts * 2);        /* LEN = 负载字节数（低 8 位） */
    tx_buf[n++] = (uint8_t)((pts * 2) >> 8); /* LEN 高 8 位 */
    tx_buf[n++] = CMD_DATA;
    tx_buf[n++] = (uint8_t)seq;
    tx_buf[n++] = (uint8_t)(seq >> 8);
    tx_buf[n++] = (uint8_t)(seq >> 16);
    tx_buf[n++] = (uint8_t)(seq >> 24);
    for (uint16_t i = 0; i < pts; i++) {     /* 512 字节的纯拷贝：约 600 个周期 */
        tx_buf[n++] = (uint8_t)(src[i] & 0xFF);
        tx_buf[n++] = (uint8_t)(src[i] >> 8);
    }
    uint16_t crc = crc16_modbus(&tx_buf[2], (uint16_t)(n - 2));  /* 从 LEN 开始算 */
    tx_buf[n++] = (uint8_t)(crc & 0xFF);
    tx_buf[n++] = (uint8_t)(crc >> 8);
    tx_buf[n++] = 0x0D;
    tx_buf[n++] = 0x0A;
    return n;
}

/* ── 上传完成回调：把"忙"标志清掉，让下一次可以启动 ── */
void HAL_UART_TxCpltCallback(UART_HandleTypeDef *huart)
{
    tx_busy = 0;                              /* 只有一条语句：绝不在这里做别的 */
}

/* ── 非阻塞启动一次发送 ── */
static void tx_start(const uint8_t *buf, uint16_t len)
{
    tx_busy = 1;
    if (HAL_UART_Transmit_DMA(&huart1, (uint8_t *)buf, len) != HAL_OK) {
        tx_busy = 0;
        tx_err++;
    }
}

/* ── 主循环 ── */
uint32_t last_health_ms = 0;

void acq_loop(void)
{
    for (;;) {
        /* 1) 处理前半区 */
        if (half_ready[0]) {
            half_ready[0] = 0;                        /* 先清标志再处理：
                                                       * 万一处理期间新的 HT 到来，
                                                       * 标志会重新置 1，不会丢事件 */
            if (half_is_safe_to_read(0) && !tx_busy) {
                uint16_t len = pack_half(&adc_buf[0], HALF_PTS, half_seq_snapshot(0));
                half_ok++;
                tx_start(tx_buf, len);                /* 立刻启动，DMA 在后台发 */
            } else {
                half_lost++;                          /* 读不安全 / 串口还忙着 → 丢这一半 */
            }
        }

        /* 2) 处理后半区 */
        if (half_ready[1]) {
            half_ready[1] = 0;
            if (half_is_safe_to_read(1) && !tx_busy) {
                uint16_t len = pack_half(&adc_buf[HALF_PTS], HALF_PTS, half_seq_snapshot(1));
                half_ok++;
                tx_start(tx_buf, len);
            } else {
                half_lost++;
            }
        }

        /* 3) 命令解析（4.3 节的框架会往 cmd_queue 里放东西） */
        cmd_poll();

        /* 4) 每 1 秒做一次健康检查 + 上报状态 */
        uint32_t now = HAL_GetTick();
        if (now - last_health_ms >= 1000u) {
            last_health_ms = now;
            uint16_t w = acq_write_index();           /* 打印出来看它对不对得上时间 */
            send_health(half_ok, half_lost, w, tx_err);
        }
    }
}
这段代码里的四个设计决定，每一个都有代价

① 先清标志再处理。反过来的话，处理期间到来的新中断会被清掉，等于丢数据。 代价是"标志可能在处理过程中被重新置 1"，所以处理完要注意别把新数据当成旧数据（用序号区分）。

② 打包用的是同一个 tx_buf。 因为 tx_busy 保证同一时刻只有一帧在发。 代价是：如果串口还没发完、下一个半区又来了，只能丢掉（half_lost++）。 在这个项目里不会发生（2KB/s 对 11.52KB/s），但如果数据率接近串口速度，就得上第二块 tx_buf 做发送双缓冲。

③ CRC 用位运算版本而不是查表。省下 512 字节的 Flash，多花约 0.15ms 的 CPU。 对 256ms 的节奏来说完全划算。但 If 你把帧长做到 4KB 以上、频率又高，就该换查表版了。

④ 健康检查里读 NDTR，只是"看一眼"，不用它做精确的边界判断。 这就是 2.2 节讲的用法边界：诊断可以，同步不行。

4.3 不定长帧接收框架：四槽轮转 + 状态机 + 超时重同步

先把这一节的三个设计决定说清楚，因为它们决定了代码长什么样：

1

接收用「四槽轮转」，而不是「一个缓冲区 + 立刻解析」

IDLE 中断里做的事情越少越好。如果只有一块接收缓冲，你必须在中断里（或紧接着）把数据搬走才能重新武装 DMA——搬 256 字节约 300 周期，看着不多，但它占用了"所有其他中断"的延迟预算。四槽轮转让中断只需要改两个寄存器：把 DMA 指向下一个空槽，然后走人。数据本身一个字节都不搬（零拷贝）。

2

解析放在主循环，用逐字节状态机

状态机不依赖"一帧必须一次收完"，所以它天然能处理"分片到达"：一帧的前 100 字节在槽 A、后 50 字节在槽 B，状态机照样能拼出来。这是逐字节状态机相对"等一整帧再解析"的最大优势。

3

重同步靠超时，不靠"再来一个帧头"

如果线路中间丢了一个字节，状态机会停在一个错误的位置，后面所有字节都被当成"负载"吃掉。这时候再等一个帧头是没用的（那个帧头会被当成负载）。唯一可靠的恢复方式是超时：超过 T_resync（本例 100ms）没有新字节，就无条件回到"等帧头"状态。

#define RX_SLOT_SZ   256            /* 每个槽 256 字节 */
#define RX_SLOT_NUM  4              /* 4 个槽轮流用 */

/* 槽状态：0=空闲  1=DMA 正在写  2=已满待解析  3=解析中 */
#define SLOT_FREE    0
#define SLOT_FILLING 1
#define SLOT_FULL    2
#define SLOT_PARSING 3

typedef struct {
    uint8_t          buf[RX_SLOT_SZ];
    volatile uint16_t len;
    volatile uint8_t  state;
} rx_slot_t;

static rx_slot_t rx_pool[RX_SLOT_NUM];
static volatile uint8_t  rx_cur = 0;             /* DMA 正在写的槽号 */
volatile uint8_t  rx_has_data = 0;
volatile uint32_t rx_frames = 0, rx_badcrc = 0, rx_badlen = 0,
                  rx_resync = 0, rx_drop = 0, rx_ovr = 0;

/* ── 把 DMA 指向第 slot 个槽，并重新开始计数 ──
 * 顺序不能变：先清 EN（CNDTR 只在通道关闭时可写）→ 改地址/计数 → 再置 EN。 */
static void rx_arm_slot(uint8_t slot)
{
    DMA1_Channel5->CCR   &= ~DMA_CCR_EN;
    DMA1_Channel5->CMAR   = (uint32_t)rx_pool[slot].buf;
    DMA1_Channel5->CNDTR  = RX_SLOT_SZ;
    DMA1_Channel5->CCR   |= DMA_CCR_EN;
    rx_pool[slot].state   = SLOT_FILLING;
}

/* ── IDLE 中断的全部工作：结账 + 换槽。没有一次数据搬运。 ── */
static void rx_idle_handler(void)
{
    /* 这一槽收了多少？CNDTR 是"还剩多少没搬"，一减就得到实际长度。
     * 这是 IDLE + DMA 组合里唯一需要用到 NDTR 的地方，而且它【可靠】：
     * IDLE 中断发生时，DMA 早就把最后一个字节搬完了（这是 IDLE 的定义决定的）。 */
    uint16_t len = (uint16_t)(RX_SLOT_SZ - DMA1_Channel5->CNDTR);

    if (len == 0) {
        return;                              /* 线路空闲但没收到任何字节，忽略 */
    }
    if (rx_pool[rx_cur].state == SLOT_FILLING) {
        rx_pool[rx_cur].len   = len;
        rx_pool[rx_cur].state = SLOT_FULL;   /* 交给主循环解析 */
    }

    /* 找下一个空闲槽 */
    uint8_t next = (uint8_t)((rx_cur + 1) % RX_SLOT_NUM);
    for (uint8_t i = 0; i < RX_SLOT_NUM; i++) {
        if (rx_pool[next].state == SLOT_FREE) {
            break;
        }
        next = (uint8_t)((next + 1) % RX_SLOT_NUM);
    }
    if (rx_pool[next].state != SLOT_FREE) {
        rx_drop++;                           /* 四个槽都满了：解析器严重落后 */
        next = rx_cur;                       /* 只能复用当前槽，接受数据被覆盖 */
    }

    rx_arm_slot(next);
    rx_cur      = next;
    rx_has_data = 1;
}

/* ── USART1 的中断入口 ──
 * 注意：这里直接用 HAL 的标志宏，但整个处理流程是自己写的——
 * 因为 HAL_UART_IRQHandler 会把 DMA 停掉并调用一堆回调，开销大得多，
 * 而我们要的只是"IDLE 到了"这一个信息。 */
void USART1_IRQHandler(void)
{
    /* IDLE 标志的清除需要"先读 SR 再读 DR"。而读 DR 有可能从 DMA 手里
     * 抢走一个还没被搬走的字节，所以稳妥的顺序是：先关 DMA 请求，清标志，再开回来。 */
    if (__HAL_UART_GET_FLAG(&huart1, UART_FLAG_IDLE)) {
        CLEAR_BIT(USART1->CR3, USART_CR3_DMAR);
        __HAL_UART_CLEAR_IDLEFLAG(&huart1);
        rx_idle_handler();
        SET_BIT(USART1->CR3, USART_CR3_DMAR);
    }

    /* 溢出错误必须显式清，否则在某些系列上接收会一直不正常。
     * 这一条是"重启了 DMA 但还是收不到数据"的头号原因。 */
    if (__HAL_UART_GET_FLAG(&huart1, UART_FLAG_ORE)) {
        __HAL_UART_CLEAR_OREFLAG(&huart1);   /* 同样是读 SR + 读 DR 的序列 */
        rx_ovr++;
    }
}

中断侧到此结束，一共几十行。下面是解析状态机——它是整个框架里最长的一段， 但你可以把它当成一个"从字节流里挑出帧"的筛子，逻辑是线性的： 

#define FRAME_PAYLOAD_MAX  512
#define T_RESYNC_MS        100u          /* 超时重同步门限（2.3 节定过） */

typedef enum {
    PS_H1 = 0, PS_H2, PS_LENL, PS_LENH, PS_CMD, PS_SEQ,
    PS_PAY, PS_CRC_LO, PS_CRC_HI, PS_TAIL1, PS_TAIL2
} ps_state_t;

static ps_state_t ps        = PS_H1;
static uint16_t   f_len, f_got, f_crc_calc, f_crc_recv;
static uint8_t    f_cmd, f_seq_cnt;
static uint32_t   f_seq;
static uint8_t    f_pay[FRAME_PAYLOAD_MAX];
static uint32_t   ps_last_ms;

/* 命令队列：解析器 → 主循环的动作执行部分。小结构体，拷贝代价可忽略。 */
typedef struct { uint8_t cmd; uint16_t len; uint8_t data[32]; } cmd_item_t;
static volatile cmd_item_t cmd_q[8];
static volatile uint8_t cmd_head = 0, cmd_tail = 0;

/* 增量式 CRC16/MODBUS：进来一个字节就更新一次，不需要在最后重新扫一遍。 */
static inline uint16_t crc16_update(uint16_t crc, uint8_t b)
{
    crc ^= b;
    for (uint8_t i = 0; i < 8; i++) {
        crc = (crc & 1) ? (uint16_t)((crc >> 1) ^ 0xA001) : (uint16_t)(crc >> 1);
    }
    return crc;
}

/* 一个字节进入状态机 */
static void parser_byte(uint8_t b)
{
    ps_last_ms = HAL_GetTick();          /* 任何字节都算"线上还活着" */

    switch (ps) {
    case PS_H1:
        if (b == 0xAA) ps = PS_H2;
        break;

    case PS_H2:
        ps = (b == 0x55) ? PS_LENL : PS_H1;   /* 不是 55 就退回等帧头（可能又是个 AA） */
        break;

    case PS_LENL:
        f_len = b;
        f_crc_calc = crc16_update(0xFFFF, b);  /* CRC 从 LEN 开始算，覆盖到负载末尾 */
        ps = PS_LENH;
        break;

    case PS_LENH:
        f_len |= (uint16_t)b << 8;
        f_crc_calc = crc16_update(f_crc_calc, b);
        if (f_len > FRAME_PAYLOAD_MAX) {       /* 长度离谱：一定是错位了 */
            rx_badlen++;
            ps = PS_H1;
        } else {
            f_got = 0;
            ps    = PS_CMD;
        }
        break;

    case PS_CMD:
        f_cmd = b;
        f_crc_calc = crc16_update(f_crc_calc, b);
        f_seq_cnt = 0;
        ps = PS_SEQ;
        break;

    case PS_SEQ:                                /* 4 字节序号，小端 */
        f_seq      = (f_seq >> 8) | ((uint32_t)b << 24);
        f_crc_calc = crc16_update(f_crc_calc, b);
        if (++f_seq_cnt >= 4) {
            ps = (f_len > 0) ? PS_PAY : PS_CRC_LO;
        }
        break;

    case PS_PAY:
        f_pay[f_got++] = b;
        f_crc_calc     = crc16_update(f_crc_calc, b);
        if (f_got >= f_len) ps = PS_CRC_LO;
        break;

    case PS_CRC_LO:
        f_crc_recv = b;
        ps = PS_CRC_HI;
        break;

    case PS_CRC_HI:
        f_crc_recv |= (uint16_t)b << 8;
        ps = PS_TAIL1;
        break;

    case PS_TAIL1:
        ps = (b == 0x0D) ? PS_TAIL2 : PS_H1;    /* 帧尾不对，整帧作废 */
        if (ps == PS_H1) rx_badcrc++;
        break;

    case PS_TAIL2: {
        uint8_t ok = (b == 0x0A) && (f_crc_calc == f_crc_recv);
        if (ok) {
            rx_frames++;
            uint8_t next = (uint8_t)((cmd_head + 1) % 8);
            if (next != cmd_tail) {              /* 队列没满 */
                cmd_q[cmd_head].cmd = f_cmd;
                cmd_q[cmd_head].len = (f_len < 32) ? f_len : 32;
                for (uint8_t i = 0; i < cmd_q[cmd_head].len; i++) {
                    cmd_q[cmd_head].data[i] = f_pay[i];
                }
                cmd_head = next;
            } else {
                rx_drop++;                       /* 命令队列满，丢帧 */
            }
        } else {
            rx_badcrc++;
        }
        ps = PS_H1;
        break;
    }
    }
}

/* 一次处理一个槽的全部字节 */
static void parser_feed(const uint8_t *p, uint16_t n)
{
    for (uint16_t i = 0; i < n; i++) {
        parser_byte(p[i]);
    }
}

/* ── 主循环里调用：消耗所有 FULL 的槽 + 检查超时 ── */
void rx_poll(void)
{
    if (rx_has_data) {
        for (uint8_t i = 0; i < RX_SLOT_NUM; i++) {
            if (rx_pool[i].state == SLOT_FULL) {
                rx_pool[i].state = SLOT_PARSING;
                parser_feed(rx_pool[i].buf, rx_pool[i].len);
                rx_pool[i].state = SLOT_FREE;    /* 归还给池子，中断侧可以再用它 */
            }
        }
        rx_has_data = 0;
    }

    /* 超时重同步：停在半路超过 100ms 就无条件回到等帧头 */
    if (ps != PS_H1 && (HAL_GetTick() - ps_last_ms) > T_RESYNC_MS) {
        ps = PS_H1;
        rx_resync++;
    }
}

/* ── 动作执行部分：从队列取命令并执行 ── */
void cmd_poll(void)
{
    while (cmd_tail != cmd_head) {
        cmd_item_t it = cmd_q[cmd_tail];         /* 先拷出来再执行，避免执行期间队列变动 */
        cmd_tail = (uint8_t)((cmd_tail + 1) % 8);
        switch (it.cmd) {
        case 0x10: /* 设置采样率：4 字节小端 Hz */
            if (it.len >= 4) {
                uint32_t fs = (uint32_t)it.data[0] | ((uint32_t)it.data[1] << 8)
                            | ((uint32_t)it.data[2] << 16) | ((uint32_t)it.data[3] << 24);
                tim3_set_sample_rate(fs);        /* 只改 ARR，立即生效，无需停 ADC */
            }
            break;
        case 0x11: /* 开始 / 停止采集 */
            acq_set_running(it.data[0]);
            break;
        case 0x12: /* 读状态：把计数器打包回一帧 */
            send_health(half_ok, half_lost, acq_write_index(), tx_err);
            break;
        case 0x13: /* 擦除日志区：注意这里会阻塞几十毫秒 */
            spi_flash_erase_log();
            break;
        default:
            break;
        }
    }
}
为什么不在 IDLE 中断里直接解析这一帧？——三个可以量化的理由

① 时间开销。一帧 512 字节负载，位运算版 CRC16 要处理 512 × 8 = 4096 次循环， 约 8 000~12 000 个周期 = 0.11~0.17ms（按典型值估算）。 听起来不长，但这是在中断里：这段时间里 ADC 半区中断、其他 DMA 中断、SysTick 全部排队。 如果上位机以 100ms 间隔连发 5 帧，最坏情况就是 0.85ms 的额外延迟被摊到所有中断上。

② IDLE 标志只有一个。你在中断里慢慢解析的时候，下一帧的 IDLE 事件如果到来并结束， 标志位只会是"一次"——你处理完出来时看到 IDLE 还是置位的，于是你分不清那是一帧还是三帧。 用状态机 + 槽轮转就没这个问题：槽是四份，每帧独立存档，一帧一个脚印。

③ 你没法处理"分片到达"。中断里解析的写法默认"一次 IDLE = 一整帧"， 而现实中一帧可能被拆成几次到达（上位机分两次 write、USB-串口芯片的缓冲、 网络转串口设备的打包），也可能两帧黏在一起。 逐字节状态机对这种情形是天然免疫的——它不关心分片，只关心字节顺序。

那中断里该做多少？这里的中断做了三件事：结账（算长度）、标记槽、换槽（两个寄存器）。 实测约 120~160 个周期，比"拷贝 256 字节再解析"少了两个数量级。 判断标准很简单：中断里的代码，应该只有"记账"和"交接"，不该有"处理"。

4.4 实测框架：DWT 与 GPIO 双通道，一次把话说死

2.5 节讲了两种测量手段的原理，这里给出可以直接编进工程里的一套小框架。 它的设计目标只有一个：让"再来一次实验"变得没有成本—— 改一个宏切换"中断搬"和"DMA 搬"两种模式，跑 30 秒，读一串数字出来。 

#include "stm32f1xx_hal.h"

/* ══ 通道 1：DWT 周期计数 ══ */
typedef struct {
    uint32_t isr_sum;      /* 中断里累计的周期 */
    uint32_t isr_cnt;      /* 中断次数 */
    uint32_t isr_max;      /* 单次最长（最坏情况！） */
    uint32_t loop_sum;     /* 主循环处理累计周期 */
    uint32_t loop_cnt;
    uint32_t loop_max;
} prof_t;

volatile prof_t prof;

void prof_init(void)
{
    CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;
    DWT->CYCCNT = 0;
    DWT->CTRL  |= DWT_CTRL_CYCCNTENA_Msk;
}

/* 中断里用这三个宏，注意"最大值"要单独记——平均值会掩盖最坏情况 */
#define PROF_ISR_BEGIN()  uint32_t _t0 = DWT->CYCCNT
#define PROF_ISR_END()    do {                                              \
        uint32_t _d = DWT->CYCCNT - _t0;                                    \
        prof.isr_sum += _d; prof.isr_cnt++;                                 \
        if (_d > prof.isr_max) prof.isr_max = _d;                            \
    } while (0)

#define PROF_LOOP_BEGIN() uint32_t _l0 = DWT->CYCCNT
#define PROF_LOOP_END()   do {                                              \
        uint32_t _d = DWT->CYCCNT - _l0;                                    \
        prof.loop_sum += _d; prof.loop_cnt++;                               \
        if (_d > prof.loop_max) prof.loop_max = _d;                          \
    } while (0)

/* ══ 通道 2：GPIO 翻转（示波器用） ══
 * PB0 = 中断忙    PB1 = 主循环处理忙
 * 用 BSRR 直写：置位写低 16 位，复位写高 16 位，一条 STR 指令，1 个周期。 */
#define MARK_ISR_HIGH()    (GPIOB->BSRR = GPIO_BSRR_BS0)
#define MARK_ISR_LOW()     (GPIOB->BSRR = GPIO_BSRR_BR0)
#define MARK_LOOP_HIGH()   (GPIOB->BSRR = GPIO_BSRR_BS1)
#define MARK_LOOP_LOW()    (GPIOB->BSRR = GPIO_BSRR_BR1)

/* ══ 把两次测量拼进真实的回调里 ══ */
void HAL_ADC_ConvHalfCpltCallback(ADC_HandleTypeDef *hadc)
{
    PROF_ISR_BEGIN();
    MARK_ISR_HIGH();

    if (half_ready[0]) half_lost++;
    half_ready[0] = 1;
    half_seq++;

    MARK_ISR_LOW();
    PROF_ISR_END();
}

static inline void process_half_profiled(uint8_t idx)
{
    PROF_LOOP_BEGIN();

    if (half_is_safe_to_read(idx) && !tx_busy) {
        uint16_t len = pack_half(&adc_buf[idx * HALF_PTS], HALF_PTS, half_seq);

}

怎么用它做那个"中断 vs DMA"的对比实验？步骤如下，每一步都有明确的判据：

1

把测量代码只加在"接收路径"上，别加到别处

中断模式下测 USART1_IRQHandler 的入口到出口；DMA 模式下测 USART1_IRQHandler（IDLE）+ 槽轮转那几行。两次测量的"被测量"必须是同一件事——都是"把一个字节从串口搬进内存"这件事的 CPU 代价，只是一个是一个字节一次，一个是 512 字节一次。

2

让上位机以固定速率持续发数据，跑满 30 秒

用 115200 连续发 30 秒 = 345 600 字节。中断模式下应该看到 n ≈ 345 600；DMA 模式下看到 n ≈ 675（345600 ÷ 512）。先用 n 核对"测的是不是同一件事"，再看周期数。

3

读三个数：avg、max、以及"有没有丢"

预期结果（对照 2.5 节的实测表）：中断模式 avg ≈ 108 周期；DMA 模式 avg ≈ 340 周期但 n 小 512 倍。折算成占用率：1.73% vs 0.011%。max 更值得看：中断模式的 max 会明显高于 avg（因为偶尔撞上别的中断），而 DMA 模式的 max 抖动量级更小。

4

把波特率提到 1Mbps，再跑一遍

这一次你会看到更有说服力的东西：中断模式的占用率跳到 15%，而且 rx_ovr（溢出计数）开始增加——这就是"高速下中断方案必然翻车"的现场证据。DMA 模式的占用率仍然是 0.09% 左右，rx_ovr 保持 0。

5

用示波器交叉验证通道 2

把探头接在 PB0 和 PB1 上（双通道），触发电平设 1.65V。 你能看到：PB0 上的脉冲又窄又密（中断模式）或极稀（DMA 模式），PB1 上每 256ms 一根 8ms 宽的脉冲。 量一下 PB1 的高电平宽度，除以 256ms，应该和 loop_sum/loop_cnt 折算出来的比例对得上—— 两种方法互相印证，这个数字才可以写进报告。

测出"不对劲"的数字时，先怀疑测量本身

常见的三种"测量失真"，按出现频率：

① 你在中断里调了 printf。HAL 的 printf 重定向后面常常是阻塞发送， 一条 40 字节的日志在 115200 下要 3.5ms——比你测的那段代码贵几百倍。 测出来的数字全是串口的。规则：中断里永远不要 printf，要记就记进变量。

② 测量代码本身的开销。两个宏展开成"读 CYCCNT、累加、比较、写回"约 10~15 个周期。 测 108 周期的 ISR 时，这是 10% 的误差。要更准就用 GPIO（一个 BSRR 写只要 1~2 周期）， 但要记得 GPIO 翻转也要引脚翻转时间（几十纳秒）。

③ 优化级别变了。-O0 和 -O2 下同一段代码的周期数可以差 3 倍。 所有测量数字都必须连同编译器选项一起记录，否则半年后你自己都无法复现。

4.5 错误恢复的落地写法与 dma_snapshot()

2.6 节给了"六步重启法"，那是一个发生在单次错误上的流程。 真实系统里还需要一层跨次错误的管理：错一次重启没关系，错五次说明根因没除， 错五十次说明你的重启逻辑本身有问题。这一段给出带退避与熔断的恢复状态机， 以及那个"没有调试器也能量到寄存器"的快照函数。 

#include "stm32f1xx_hal.h"

typedef enum {
    RS_OK = 0,        /* 正常 */
    RS_RETRY,         /* 已重启，观察中 */
    RS_BACKOFF,       /* 连续错太多，等一段时间再试 */
    RS_FATAL          /* 放弃：等人工干预（或复位） */
} rs_state_t;

typedef struct {
    rs_state_t state;
    uint32_t   err_total;        /* 历史错误总数 */
    uint32_t   err_streak;       /* 连续错误次数（成功一次就清零） */
    uint32_t   retry_at_ms;      /* 退避到期时间 */
    uint32_t   last_err_code;    /* 最近一次错误码，上报用 */
} rs_t;

static rs_t rs = { RS_OK, 0, 0, 0, 0 };
#define RS_BACKOFF_MS   2000u
#define RS_STREAK_MAX   5u

/* ── 成功采集到一个完整半区时调用：证明"系统恢复正常了" ── */
void acq_note_success(void)
{
    if (rs.err_streak) {
        rs.err_streak = 0;                 /* 连续错误计数清零 */
        rs.state      = RS_OK;
    }
}

/* ── 错误发生时的统一入口 ── */
void acq_on_error(uint32_t err_code)
{
    rs.err_total++;
    rs.err_streak++;
    rs.last_err_code = err_code;

    if (rs.err_streak >= RS_STREAK_MAX) {
        /* 连续错够多次：不再无脑重启，进入退避，让总线/外设"冷下来" */
        rs.state       = RS_BACKOFF;
        rs.retry_at_ms = HAL_GetTick() + RS_BACKOFF_MS;
        return;
    }

    if (acq_restart() == HAL_OK) {
        rs.state = RS_RETRY;
    } else {
        rs.state = RS_FATAL;               /* 连重启都失败了，别再挣扎 */
    }
}

/* ── 主循环里定期调用：负责退避到期后的重试 ── */
void acq_error_poll(void)
{
    if (rs.state == RS_BACKOFF && (int32_t)(HAL_GetTick() - rs.retry_at_ms) >= 0) {
        if (acq_restart() == HAL_OK) {
            rs.state = RS_RETRY;
            /* 注意：此处【不】清零 err_streak —— 只有真正采到数据才算恢复 */
        } else {
            rs.state       = RS_BACKOFF;
            rs.retry_at_ms = HAL_GetTick() + RS_BACKOFF_MS * 2;   /* 退避加倍 */
        }
    }

    /* 退避次数过多（比如超过 10 次），说明不是临时干扰，进入熔断 */
    if (rs.state == RS_BACKOFF && rs.err_streak > 10u) {
        rs.state = RS_FATAL;
    }
}

/* ── acq_restart：把 2.6 节的六步压缩成一个可复用的函数 ── */
HAL_StatusTypeDef acq_restart(void)
{
    /* 1) 断外设侧的请求来源 */
    CLEAR_BIT(ADC1->CR2, ADC_CR2_DMA | ADC_CR2_DDS);
    /* 2) 停通道（HAL 的 Abort 内部带超时，不会死等） */
    if (HAL_DMA_Abort(&hdma_adc1) != HAL_OK) {
        return HAL_ERROR;                        /* 通道停不下来，别再往下走 */
    }
    /* 3) 清标志（通道 1 的全局中断标志） */
    DMA1->IFCR = DMA_IFCR_CGIF1;
    /* 4) 清外设侧的错误标志 */
    ADC1->SR = 0;                                /* 写 0 清 EOC/OVR 等（F1 的 SR 是 rc_w0） */
    __HAL_ADC_CLEAR_FLAG(&hadc1, ADC_FLAG_EOC | ADC_FLAG_OVR);
    /* 5) 重新配置 + 启动（循环模式，一次启动管到下次出错） */
    if (HAL_ADC_Start_DMA(&hadc1, (uint32_t *)adc_buf, ADC_BUF_PTS) != HAL_OK) {
        return HAL_ERROR;
    }
    /* 6) 重新武装接收侧的槽（接收路径可能也被错误影响过） */
    rx_arm_slot(rx_cur);
    return HAL_OK;
}

/* ── 把 HAL 的错误回调接进来 ── */
void HAL_ADC_ErrorCallback(ADC_HandleTypeDef *hadc)
{
    acq_on_error(hadc->DMA_Handle->ErrorCode ? hadc->DMA_Handle->ErrorCode : 0xFFFFFFFFu);
}

然后是那个在现场最有用的函数。它的价值在于"不需要调试器"： 设备装在机柜里、人在办公室里，你只能靠串口。让上位机发一条"读快照"的命令， 把它返回的结构体打出来，2.6 节那棵三步决策树要的每一个数都在里面。

    uint32_t dma_cmar;     /* 内存地址：应该是 adc_buf */

/* 上位机侧的建议解读顺序（和 2.6 节的三步决策树一一对应）：
 *
 *   ① dma_cndtr 两次快照不一样吗？
 *        不一样 → DMA 在动。问题在数据/协议，不在 DMA。
 *        一样   → 往下。
 *   ② dma_ccr 的 bit0（EN）是 1 吗？
 *        0 → 被关了。看 dma_isr 的 bit1（TEIF）：1 就是传输错误。
 *   ③ adc_cr2 的 bit8（DMA）是 1 吗？tim3_cnt 在变吗？adc_sr 的 EOC 在置位吗？
 *        请求源没问题 → 查 CPAR/CMAR 和请求映射。
 *   ④ 最后看计数器：half_lost 在涨但 rx_frames 不涨 → 问题在采集侧；
 *      rx_ovr 在涨 → 问题在串口侧（多半是被长关中断拖出来的）。
 *
 * 把 ④ 的这几个计数器做成"每秒上报一次"的心跳，你就能在故障发生【之前】
 * 看到趋势（half_lost 开始缓慢增长，比彻底死掉好查得多）。 */
一个真实的排障故事（网上的经典案例，值得记住它的形状）

某人的采集器每隔几小时丢一段数据。日志显示 half_lost 缓慢增长， 但 err_total 一直是 0——没有 DMA 错误，只是"处理不及时"。 加了快照和心跳之后发现：每次丢数据前，tim3_arr 都会短暂变成别的值， 而 half_lost 恰好在那之后开始涨。

原因是他写了一个"动态调整采样率"的命令处理，上位机偶尔发来一个很大的采样率（比如 100kHz）， 于是 T_half 从 512ms 掉到 5.12ms，主循环根本来不及处理。 修复方式很简单：在命令处理里加一个上限判断。

这个故事的价值在于它的形状：故障发生在"配置被改"之后，而配置的痕迹留在寄存器里。 如果你的快照里没有 tim3_arr、没有 half_lost， 这个 bug 会一直是一个"偶尔丢数据"的玄学问题。

static uint16_t adc_buf0[256];

void acq_start_dbmmode(void)
{
    /* 用专门的 MultiBuffer 启动函数，不能用 HAL_ADC_Start_DMA */
    HAL_StatusTypeDef st = HAL_DMAEx_MultiBufferStart_IT(
            &hdma_adc1,
            (uint32_t)&ADC1->DR,      /* 源：外设数据寄存器 */
            (uint32_t)adc_buf0,        /* 目标 0：M0AR */
            (uint32_t)adc_buf1,        /* 目标 1：M1AR */
            256);                      /* 每次传输的【个数】，两个缓冲各 256 个半字 */

        /* 注意：MultiBufferStart 失败时不会自动清理，
         * 要显式 HAL_DMA_Abort 再排查（DBM 对参数很挑：长度、对齐、循环模式都要对） */
        HAL_DMA_Abort(&hdma_adc1);
        return;
    }
    HAL_ADC_Start(&hadc1);            /* ADC 本体还是要启动的（触发由定时器给） */
}

/* ── 两个回调：哪一个被填满了，可以读 CT 位确认 ──
 * 在 DBM 模式下，HAL 的 ConvHalfCplt / ConvCplt 回调分别对应
 * "M0AR 那块填满了" 和 "M1AR 那块填满了"，语义清楚，不需要你自己判断。 */
void HAL_ADC_ConvHalfCpltCallback(ADC_HandleTypeDef *hadc)
{
    /* 读硬件 CT 位：0 表示当前 DMA 正在用 M0AR，1 表示正在用 M1AR。
     * 换句话说：CT 指出的是"下一块要写哪里"，所以【刚填满的那块是 ~CT】。 */
    uint32_t ct = (hdma_adc1.Instance->CR & DMA_SxCR_CT) ? 1u : 0u;
    submit_half(ct ? adc_buf0 : adc_buf1, 256);
}

void HAL_ADC_ConvCpltCallback(ADC_HandleTypeDef *hadc)
{
    uint32_t ct = (hdma_adc1.Instance->CR & DMA_SxCR_CT) ? 1u : 0u;

}

/* ── 方案 A：手动 clean / invalidate（灵活，但要记得每一处） ──

 *   内存 → 外设（发送）：先 clean，再启动 DMA

/* 必须 32 字节对齐，长度按 32 的倍数给 */

}

常见误解与坑

下面这十条，每一条都在真实项目里以"能跑但偶尔出错""重启一下就好了"的形式出现过。 它们的共同特点是：从原理上看都不是玄学，只是有一句话没想清楚。

① 「DMA 一开，CPU 就彻底解放了，什么都能丢给它」

错在哪：DMA 只会"按你给的参数搬字节"，它不做任何判断：不检查帧头、不算 CRC、不知道哪个字节重要、错了也不会告诉你它错了。所有"智力活"还是 CPU 的。更现实的一点：DMA 的配置本身要花 CPU 周期（HAL 启动一次约 400 周期），如果你写成了"每收一个字节就重启一次 DMA"，那比中断搬还慢。

正确做法：把 DMA 当成"一个只会搬箱子的搬运工"。你负责告诉它搬哪、搬多少、搬到哪（配置一次、循环模式最好），它负责不停搬；你还要负责检查它有没有搬错（错误中断 + 计数器）。判断"什么时候该用 DMA"的标准永远是：这件事能不能表达成"从 A 地址搬 N 个到 B 地址"。

② 「一个字节一次中断才 108 个周期、1.5µs，用不着 DMA」

错在哪：这是典型的用平均值替代最坏情况。115200 下一个字节的时间是 86.8µs，你还有 85µs 的余量，确实看不出来。但 1Mbps 下一个字节只有 10µs，余量 8.5µs——只要系统里存在任何一段超过 8.5µs 的关中断代码（Flash 写、某些 HAL 临界区、另一个高优先级中断），就必然丢字节。而且 1.73% → 15% 的占用跳变是指数级逼近极限的信号。

正确做法：判断标准不是"平均占用多少"，而是"允许关中断的最长时间是多少"（本例 115200 是 85.3µs、1Mbps 是 8.5µs）。当这个数掉到你无法保证的量级时，就必须上 DMA——它把约束从"每字节 8.5µs"放宽到"每半区 5ms"，宽了 600 倍。

③ 「用了 HT 和 TC 两个中断，就叫双缓冲了」

错在哪：HT/TC 只告诉你"硬件写到哪里了"，它们不管理"这两半的归属"。只开 HT 不开 TC，你会丢掉后半区的一半数据；把 HT 当成"数据已经处理完了"的信号，你会读到正在被写的那一半。还有人把 half_ready 标志在中断里清掉，结果主循环永远看不到它。

正确做法：把"半区"当成有状态的对象：half_ready[2] 记录"哪半满了"，中断只置位、主循环只清位；同时要检测"上一半还没处理完"的情况（置位前先看标志是不是已经 1，是 1 就说明被覆盖了，half_lost++）。这个计数器是整套架构里最重要的一个数——它把"偶尔丢数据"变成了一个可观测的指标。

④ 「CNDTR 能精确反推 DMA 写到哪了，拿它做同步最准」

错在哪：它看起来很准，但有三处不可靠：① 你读到 CNDTR 的那一刻，DMA 可能刚好又搬走了一个；② 循环模式下 CNDTR 装到 0 之后会重装为满值，那一瞬间读到的值是无意义的；③ 把它和"半区边界"比较时，边界值到底算 0 还是算满值，一不小心就差一个点。用它去做"精确的读写同步"，你会得到那个经典的"偶尔少一个采样点"的 bug。

正确做法：同步只依赖硬件事件——HT 中断代表"前半区完整地写完了"、TC 中断代表"后半区完整地写完了"，这两个事件是准的。CNDTR 拿来做诊断和健康检查（"现在写到哪了""是不是严重落后了"，见 4.2），以及在单次模式 + IDLE 这种"已经停了"的场合算长度（4.3 用的就是这一种）。

⑤ 「IDLE 中断来了就说明一帧收完了，在里面直接解析最省事」

错在哪：三个问题叠在一起：① 一帧可能分片到达（上位机分两次 write、USB 转串口芯片打包），"一次 IDLE = 一帧"这个假设不成立，也可能两帧黏在一起；② IDLE 标志只有一个，你在中断里慢慢解析的时候，后面几帧的 IDLE 会合并成一次，你分不清是几帧；③ 位运算版 CRC16 算 512 字节要 0.11~0.17ms，这段时间被算进所有其他中断的延迟预算里。

正确做法：中断只做三件事——算长度、标记槽、换槽（约 120~160 周期，零拷贝）；解析放在主循环，用逐字节状态机（天然免疫分片）。再加一条 100ms 的超时重同步：丢一个字节之后，靠再等一个帧头是救不回来的，只有超时能救。

⑥ 「四路 DMA 的优先级全设成最高，就谁都不会丢了」

错在哪：优先级只作用于第一级仲裁（DMA 控制器内部的通道之间），它管不到第二级——总线矩阵上 DMA 与 CPU、DMA 与 DMA 之间是轮询的，软件无法干预。四路都设最高，等价于四路都设成"相同优先级 + 按通道号排"，你还是排了一个次序，只是这个次序不是你想要的。更糟的是：把某一路的优先级设得过高，会让其他路的延迟被动变长。

正确做法：先用带宽预算确认总量安全（例 3 算下来 9.58%，很安全），再按"超时的后果可不可恢复"排相对紧急度：USART1_RX 最高（1 字节缓冲、丢了整帧作废）→ SPI1_RX → ADC1 → USART1_TX 最低（TXE 会一直等你，不紧急）。并且记住：采样率一变，这套排序就要重算。

⑦ 「TE 传输错误很少见，没必要专门处理」

错在哪：TE 的可怕之处不是它频繁，而是它安静：硬件会自动清掉 EN 位，通道就此停摆，没有 HardFault、没有断言、主循环照常跑。你的程序看起来一切正常，只是数据永远停在出错的最后一个值上。等用户投诉的时候，你已经不知道那是哪一天发生的了。而 TE 的三个常见成因（外设时钟没开、宽度没对齐、DMA 指向了函数内的局部数组）恰恰都是"写代码时很难自己发现"的类型。

正确做法：三个动作缺一不可：① 配置时打开 TEIE；② 在错误回调里记账（错误类型 + 次数），超过阈值熔断；③ 重启前按顺序做"断来源 → 停通道 → 清标志 → 清外设错误标志 → 重启"，并且把"这段时间数据不可信"告诉上位机（把 half_lost 一起报上去）。

⑧ 「DMA 的目标缓冲区就用函数里的局部数组，省全局内存」

错在哪：局部数组在栈上，函数一返回，那块栈内存就被别的函数复用了，而 DMA 还在往那里写。后果是随机的：有时覆盖的是已经没用的栈数据（看起来没事），有时覆盖的是正在用的局部变量或者函数的返回地址——表现为"某个变量莫名其妙被改了"或者直接跑飞。更隐蔽的一点：如果 DMA 在函数返回后才开始搬，而那段栈已经被下一个函数用掉了，你连现象都难复现。

正确做法：所有 DMA 缓冲区必须是静态存储期（static 全局或文件内 static），M7 上还要加 32 字节对齐；缓冲区的大小和生命周期要写成注释或常量（#define ADC_BUF_PTS 1024），别让"缓冲区"这个词散落在十几个地方各写一遍。另外别忘了：启动 DMA 之前要确认缓冲区地址真的有效（不是 NULL、不是已经释放的内存）。

⑨ 「RTOS 里在 DMA 回调里直接 xQueueSend 就行了」

错在哪：两处错。① 不带 FromISR 后缀的 API 不能在中断里调用，这是未定义行为（有时"看起来能跑"，是因为恰好没触发内部断言）。② 即使调用了 xQueueSendFromISR，忘了处理 pxHigherPriorityTaskWoken 并不会报错，只是任务要等到下一个 tick 才被调度——默认 tick 是 1ms，你的采集任务凭空多了 1ms 延迟。

正确做法：固定三行：BaseType_t woken = pdFALSE; → xQueueSendFromISR(q, &item, &woken); → portYIELD_FROM_ISR(woken);（放在回调最后一行）。并且回调里只发消息、不搬数据：队列里放"指针 + 长度 + 序号"的小描述符，拷贝和打包都留给任务——这样"来不及处理"才会表现为队列堆积（可观测的背压），而不是"中断变长了"（不可观测）。

⑩ 「换芯片移植 DMA 就是改改寄存器名，逻辑不用动」

错在哪：F1、F4、H7 的 DMA 是三套结构上不同的设计：请求映射从"硬件固定"变成"CHSEL 选择"再变成"DMAMUX 任意映射"；F4 起多出 FIFO 与突发（于是多出 FE、DME 两种错误）；F4 起有硬件双缓冲 DBM（但必须换用专门的 MultiBuffer API）；到 Cortex-M7 上，DMA 与 D-Cache 的一致性成为一个"不改就一定会错、而且错得很随机"的必答题。

正确做法：移植时按 4.6 那张检查单逐项过：映射、启动 API、FIFO/突发、错误类型、cache、缓冲对齐、优先级编号对象。其中只有三项会真正改变你的代码结构——DBM（换 API）、FIFO 阈值（换模式）、cache（加 clean/invalidate 或 MPU）。另外记住一个具体的坑：FIFO 阈值设得比本次传输总量还大时，最后几个字节的行为是排查重点，传输结束时 ST 的流式 DMA 会把 FIFO 里剩下的数据推出去，但这个行为与传输长度、突发配置耦合。

这十条的共同点

它们都是"把平均值当成保证"的产物：平均占用 1.73% 就以为不会丢； 平均 1.5µs 就以为来得及；平均不报错就以为没错误。 而 DMA 的工程问题几乎全在尾部：最坏延迟、边界条件、错误路径、异常时序。

所以这篇文章给你的最重要的习惯是：凡是要写进 DMA 相关的代码，先问自己三个问题—— 最坏情况下会发生什么？这件事怎么被观测到？出错之后怎么恢复？ 这三个问题答得出来，DMA 就不会再是玄学。

小结与自检

如果只带走一页纸，带走下面这十条要点。它们按"设计 → 实现 → 验证 → 移植"的顺序排列， 正好对应文章的前四节。

设计阶段（第 1~2 节）

  • 架构先于代码。先算"数据量 vs 传输能力"（例 1），确定是"先存后传"还是"边采边传"，后面的所有缓冲区计算才有意义。
  • 采样率必须由硬件定时器保证。ADC 连续模式的速度由 ADC 时钟决定（12MHz/55.5 周期 → 176kHz），要用 TIM 的 TRGO 触发 ADC 才是精确的 1kHz。
  • 半区大小由"最坏阻塞时间"反推。T_half = (N_buf/2) ÷ (f_s × B_sample)，要求最坏阻塞 ≤ T_half ÷ (3~5)。
  • 同步只依赖 HT/TC 事件，CNDTR 只用于诊断。循环模式下 NDTR 重装的那一瞬间不可靠，拿它做精确同步会丢一个点。
  • 帧接收要有三层：中断记账、槽轮转、状态机解析。再加 100ms 的超时重同步，否则丢一个字节就永久错位。
  • 优先级按"超时后果"排，不按"重要性"排。RX > 采集 > TX；而且总线那一级是轮询，改不了。

实现与验证（第 3~4 节）

  • 中断里只有"记账"和"交接"。结账（算长度）、标记、换槽——约 120~160 周期；解析、CRC、打包全在主循环。
  • 用 DWT 和 GPIO 两种办法互相验证。DWT 给精确数字（含最大值），示波器给"真相"（抖动与偶发长阻塞）；中断里永远不要 printf。
  • TE 会自己刹车，FE/DME 不会。TE 让通道静默停摆，必须开 TEIE 并记账；恢复流程"断来源 → 停通道 → 清标志 → 清外设标志 → 限次重启"。
  • 回调只发消息。队列里放"指针 + 长度 + 序号"，用计数信号量管缓冲配额，portYIELD_FROM_ISR 一定要写。
  • 换系列先想四件事：映射、FIFO、DBM、cache。M7 上缓冲要 32 字节对齐，clean 在启动前、invalidate 在读之前。

自测题（8 道，答案就在下面）

1. 半区 1024 字节、采样率 1kHz、每点 2 字节，T_half 是多少？如果取余量系数 K = 4，主循环最长能阻塞多久？

答：T_half = 1024 ÷ (1000 × 2) = 0.512 s = 512 ms；T_block_max ≤ 512 ÷ 4 = 128 ms。注意这 128ms 要包含所有中断时间和关中断区，不只是主循环里你自己的那段代码。

2. 为什么 1kHz 采样不能用 ADC 的连续转换模式？正确的做法是什么？

答：连续模式下 ADC 转完一个立刻转下一个，速度由 ADC 时钟和采样时间决定：12MHz、55.5 周期时一次转换 5.67µs，也就是 176kHz，根本不是 1kHz。正确做法是 CONT = 0 + 外部触发，用 TIM3 的更新事件作为 TRGO（MMS = 010、EXTSEL = TIM3_TRGO），每次触发转一个点、产生一次 DMA 请求。这样采样率 = 触发频率，精度来自晶振。

3. 循环模式下读到 CNDTR = 300，缓冲一共 1024 个点。DMA 已经搬了多少个点？现在的写指针落在哪一半？

答：已经搬了 1024 − 300 = 724 个点；724 ≥ 512，所以写指针在后半区。这个值只能用于诊断（"有没有严重落后"），不能用于精确同步——循环模式下 NDTR 从 0 重装为 1024 的瞬间读到的值是无意义的。

4. 四路 DMA：ADC 2 kB/s、USART_TX 与 RX 各 11.52 kB/s、SPI 1.125 MB/s，每个字节 6 个 AHB 周期，HCLK = 72MHz。总线占用率是多少？哪一路该给最高优先级？

答：总字节率 = 2 000 + 11 520 + 11 520 + 1 125 000 = 1 150 040 字节/秒；1 150 040 × 6 ÷ 72 000 000 = 9.58%。SPI 一路就占了 9.375%，其余三路合计 0.21%。最高优先级给 USART1_RX：它只有 1 个字节的缓冲，溢出后丢掉的字节永远回不来、整帧作废；而 SPI 是同步总线，慢一点不会丢数据，USART_TX 的 TXE 会一直等着你写。

5. TE 和 FE 最关键的区别是什么？各自会在什么系列上出现？

答：TE（传输错误）在所有系列上都有，发生条件是非法地址、宽度未对齐、外设时钟未开等；它的后果是硬件自动清 EN，通道静默停摆，必须靠 TEIE 中断 + 记账才能发现。FE（FIFO 错误）只在带 FIFO 的系列（F2/F4/F7/H7/G4）上有，条件是 FIFO 溢出或下溢；它不清 EN，DMA 继续跑，但数据已经坏了——属于"静默数据损坏"，比 TE 更隐蔽。

6. Cortex-M7 上"内存 → 外设"方向，该用 clean 还是 invalidate？放在什么时刻？接收方向呢？

答：发送方向用 SCB_CleanDCache_by_Addr()，在启动 DMA 之前——把 CPU 还留在 cache 里的脏数据写回 SRAM，DMA 才读得到新值。接收方向用 SCB_InvalidateDCache_by_Addr()，在 DMA 完成之后、CPU 读之前——丢掉 cache 里的旧副本。另外：接收缓冲在 DMA 写入期间 CPU 不能写，缓冲要 32 字节对齐、长度补齐到 32 的倍数（否则 256 字节会覆盖 9 行 288 字节，波及邻居）。

7. 为什么不在 IDLE 中断里直接解析整帧？说出三个理由。

答：① 时间被计入中断延迟：512 字节的位运算 CRC16 约 0.11~0.17ms，这段时间 ADC 半区、其他 DMA、SysTick 全部排队；② IDLE 标志只有一个，解析期间到来的多帧会被合并成一次事件，分不清几帧；③ "一次 IDLE = 一整帧"的假设不成立——一帧可能分片到达，也可能两帧黏在一起。逐字节状态机没有这些问题，它只关心字节顺序。

8. FreeRTOS 里，DMA 半区队列的深度该取多少？

答：由"最坏阻塞时间内的产出量"反推：D × 半区字节数 ≥ R_in × T_block_max。本例 R_in = 2 000 字节/秒、T_block_max = 70 ms → 产出 140 字节 → 半区 1024 字节时 D ≥ 0.14，取 4（可容忍落后 4 × 512ms ≈ 2 秒）。最坏阻塞时间要把系统里其他任务的占用也算进去。如果 R_out < R_in（消费追不上生产），队列深度的含义就变了——它变成"能缓冲多少数据"，此时必须靠"队列满的次数"来报警。

练习（5 项，从易到难）

1

把半区从 1024 字节改成 2048 字节，重算一遍并实测

改两个地方：ADC_BUF_PTS 从 1024 改成 2048、HALF_MS 从 512 改成 1024。先手算新的 T_half、中断频率、以及"能容忍的最坏阻塞时间"；然后用 4.4 的框架实测前后两版的 CPU 占用（应该几乎不变）和 half_lost（应该都是 0）。再做一次"故意超时"实验：在主循环里插一个 600ms 的延时，观察 half_lost 是不是按预期增长（1024 字节版本丢得比 2048 版本多）。

2

把采集器改成 8kHz、三通道（ADC 扫描模式 + DMA）

要点：ADC 要开扫描模式（三个通道按顺序转）、DMA 的传输量按"点数 × 通道数"算、帧里的每个采样点要带上通道号（或者在帧头声明通道顺序）。重算例 2（T_half 变成原来的 1/8）和例 3（ADC 那一路的字节率变成 6 倍），说明半区该怎么改、还有哪一路的优先级排序需要重新考虑。

3

给帧协议加一个"重传请求"命令，并算出重传缓冲要多大

上位机发现序号（SEQ）跳变时，回一条"请重传第 N 帧"的命令。你要解决三个问题：① 设备侧要保留最近几帧？（这就是重传缓冲的大小，按"往返延迟 ÷ 帧周期 + 余量"算）② 重传的帧和实时帧怎么共用串口带宽？（算出最坏情况下的总线占用）③ 如果重传缓冲也追不上，怎么让上位机知道"这段数据永久缺失"？

4

用 DWT 测出你手上任意一个 DMA 项目的真实占用率，写一份对比表

要求：① 至少测两个方案（中断搬 vs DMA 搬，或者两种不同的半区大小）；② 每个数字都要记录测试条件——芯片型号、主频、Flash 等待周期、编译器优化级别、库版本、数据率；③ 至少给出"平均值"和"最大值"两列，并解释最大值为什么比平均值大。把这份表和 2.5 节的表对照，差异在哪里、为什么。

5

（有 F4/H7 板子的话）把软件 ping-pong 换成硬件 DBM，做对比实验

在 F4 或 H7 上用 HAL_DMAEx_MultiBufferStart_IT() 实现 4.6 的 DBM 版本，和 4.2 的软件版本对比三件事：① 中断里判断"该处理哪一块"的代码量（DBM 靠读 CT 位，软件版靠自己的标志）；② 在同一个"故意让处理超时"的测试下，两种方案的丢数据模式有什么不同；③ 中断响应的最坏延迟（用 4.4 的框架量 isr_max）。

最后一句：DMA 的水平，体现在"出事之后"

两个人写的 DMA 代码，正常运行时看不出区别——都能把数据搬对。 区别在于：丢了一段数据之后，一个人能立刻说出"什么时候丢的、丢了多少、为什么丢"； 另一个人只能说"重启一下就好了"。

这篇文章里所有的计数器（half_lost、rx_ovr、rx_resync、 err_streak、isr_max）和那个 dma_snapshot()， 都是为了让你成为第一个人。它们加起来不到 100 行代码，但它们决定了一个项目能不能交付。
