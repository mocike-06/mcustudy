ESP32 与 FreeRTOS：任务与调度

上一篇《嵌入式软件架构》回答的是 「不用 RTOS 的时候，程序该怎么组织」：顺序、前后台、时间片轮询、 任务表调度器、环形缓冲、事件标志组，以及那一张「裸机机制 ↔ RTOS 概念」的对照表。 走到那一篇的结尾，你已经知道什么时候该上 RTOS了。

这一篇接着往下走，回答一个更具体的问题：决定用 RTOS 之后的第一个月，你会遇到什么。 对照表上的概念你都已经见过，但真把 xTaskCreate 敲进编辑器之后， 等着你的是一连串非常具体、非常不像「概念」的困惑：为什么 app_main 里 return 之后程序没有停？为什么栈大小写 2048 和写 128 都能编译，但一个正常一个立刻崩？ 为什么优先级 0 的任务永远抢不到 CPU？为什么加了一句 printf 就栈溢出？ 为什么一个任务里少写一句 vTaskDelay，整片芯片每 5 秒重启一次？

这一篇不是 FreeRTOS 的 API 手册——手册里每个函数都写得很清楚，缺的是这些函数凑在一起时的工程直觉。 我们只讲四件事：任务是怎么被创建的、怎么被调度的、 怎么被阻塞的、它的栈该怎么算。 队列、信号量、互斥量这些「任务之间怎么说话」的机制，全部留给下一篇。

为什么需要它

上一篇结尾那张「什么时候该上 RTOS」的清单，你大概是拿着自己的项目一条条对下来的。 任务数够了、优先级差异明显、有大量等待、需要阻塞式的编程模型——好，上 RTOS。 于是你打开 ESP-IDF，新建工程，在 app_main 里写下第一句 xTaskCreate，编译、烧写、打开串口监视器。

然后第一个月就开始了。 这一个月的绝大部分时间不是在写业务逻辑，而是在和内核打交道： 你的代码明明编译通过、逻辑没写错，但现象完全不像你想的那样。 下面这张表，是几乎所有人在第一个月里都会撞上的六件事—— 如果你现在正好卡在其中某一条上，直接跳到对应的小节。 

第 1 天  app_main 里建完任务就 return 了，串口再也没有输出
        原因：app_main 本身是一个任务，它 return 就等于这个任务结束、
              它栈上的局部变量（包括你刚建的任务句柄）全部失效。
              内核和其他任务都还活着，但没人再打印了。      → 2.1 节

第 2 天  两个任务都闪灯，一个 500 ms、一个 1000 ms
        跑了一晚上，第二个灯的周期变成了 1.013 s，累计慢了好几秒
        原因：vTaskDelay 是「延时 N 个 tick 之后再说」，
              不是「每隔 N 个 tick 做一次」，执行时间会一轮轮累加。 → 2.5 节

第 3 天  想让某个任务先跑，把优先级写成 0
        结果它永远抢不到 CPU，日志里一行都看不到
        原因：优先级 0 是空闲任务的档位，数值越大越优先。
              而且这个方向和 STM32 的 NVIC 刚好相反。        → 2.4 节

第 4 天  为了调试，在任务里加了一句 printf
        任务直接重启，日志里出现

        原因：printf / sprintf 家族单次调用能吃掉 1 KB 以上的栈，
              而你的任务栈可能只有 2 KB。                   → 2.6 节

        整片芯片每 5 秒重启一次，日志是

        原因：这是共享数据的同步问题，不是调度问题。

把这六条按「原因」归一下类，你会发现它们只落在四个主题上： 任务是怎么被创建出来的（第 1、3 条）、 任务是怎么被调度的（第 3 条）、 任务是怎么被阻塞的（第 2、7 条）、 任务的栈是多少（第 4 条）。 这一篇的第二节就按这四个主题分成八个小节，第三节用六道算式把里面的数量关系钉死， 第四节给你四个能直接烧进板子的完整程序。

为什么 ESP32 上这件事特别容易踩坑

在 51 或者「裸机 STM32」上，你写的程序就是全部：从 main 进去， 一个 while(1) 转到天荒地老，谁先谁后由你写的顺序决定。 ESP32 不是这样，而且不是「可以不是这样」——它默认就是这样。

因为 ESP-IDF 已经把 FreeRTOS 编译进固件了。你烧进去的固件一上电， 二级引导程序跑完就会启动调度器， 然后你写的 app_main 只是被创建出来的众多任务之一。 哪怕你一个任务都不建、只写一个空函数，芯片上也已经有空闲任务、定时器守护任务、 以及（如果你开了 WiFi）WiFi 任务和 TCP/IP 任务在跑了。

所以这一篇真正要教的不是「怎么用 RTOS」，而是「怎么和一个已经在跑的内核共处」

这是一个心态上的转变。你在裸机里的直觉是「我的代码在独占总线」， 在 RTOS 里的正确直觉是「我的代码只是众多执行流之一， 随时可能被切走，也随时可能被别人的行为影响」。 本篇后面所有的规则——为什么要给延时、为什么栈要单独算、为什么要检查创建返回值、 为什么看门狗会因为别人不干活而复位——全都是这一条直觉的推论。

核心概念

这一节分八个小节，顺序是「一个任务的一生」： 它从哪来（2.1 启动流程、2.2 创建）、 住在哪（2.3 哪颗核、2.6 哪个栈）、 怎么被选中运行（2.4 状态与调度）、 怎么让出 CPU（2.5 阻塞与延时）、 怎么被监视（2.7 看门狗）、 怎么结束（2.8 删除与生命周期）。

2.1 上电之后发生了什么：app_main 的真身与启动流程

先解决那个最反直觉的问题：为什么在 ESP-IDF 里找不到 main 函数？ 你新建一个工程，main 目录下只有一个 main.c， 里面只有一个 void app_main(void)。你从来没有写过 int main(void)， 也没有写过 vTaskStartScheduler()，但调度器确实跑起来了。

答案是：真正的 main 在 ESP-IDF 的组件里， 它做的事是「创建 app_main 这个任务，然后启动调度器」。 启动流程一共五步，看清楚这五步，后面所有的困惑都会自动解开： 

① 一级引导（ROM bootloader，出厂固化在芯片里，不可修改）
     上电 → CPU0 从 0x40000400 取第一条指令 → 读 strapping 引脚决定启动模式
     → 从 Flash 的 0x1000 处读出二级引导程序，搬进 IRAM 并跳过去

② 二级引导（bootloader，在 Flash 里，可以自己编译，就是我们烧的 bootloader.bin）
     初始化 Flash 与时钟 → 读分区表 → 校验并加载应用程序镜像到 IRAM/DRAM
     → 把控制权交给应用程序的入口

③ call_start_cpu0（应用程序的第一段代码，在 esp_system 组件里）
     初始化堆（把剩下没用到的 DRAM 全部交给堆管理器）
     初始化 RTC、时钟、看门狗、cache
     → 调用 esp_startup_start_app()

④ esp_startup_start_app
     ★ 这里是关键：它调用
       xTaskCreatePinnedToCore(main_task, "main",
                               CONFIG_ESP_MAIN_TASK_STACK_SIZE,   ← 默认 3584【字节】
                               NULL, ESP_TASK_MAIN_PRIO /* = 1 */, NULL, 0);
       然后调用 vTaskStartScheduler();          ← 到这里，调度器才真正开始跑

⑤ main_task → app_main
     调度器选中名为 "main" 的任务（优先级 1，钉在 CPU0）→ 它执行的函数体里
     调用一次 app_main() → 于是你写的代码终于开始跑了

     ★ app_main() 返回之后：main_task 会调用 vTaskDelete(NULL) 把自己删掉。
       注意——【调度器不会停】。内核还在跑，你创建的任务还在跑，
       WiFi 协议栈还在跑，只有那个叫 "main" 的任务没了。
       它栈上的所有局部变量（包括你在 app_main 里声明的任务句柄）也跟着没了。

把这五步记住，第一个月的第 1 号困惑就有答案了：

「我在 app_main 里 return 了，为什么程序没停，但打印也没了？」

程序本来就不该停。app_main 不是 main， 它是一个任务函数。你 return 之后发生的事是：

  • main 任务自己被删除，它在 RTOS 堆上的那块 3584 字节的栈被交还给堆（严格说是交给空闲任务回收）；
  • 你在 app_main 里用局部变量保存的任务句柄、last_wake、 各种配置结构体，全部随栈一起消失——如果别的任务还拿着这些变量的指针，那就是悬空指针；
  • 调度器、其他任务、协议栈照常运行，所以你「看不到打印」通常是因为打印循环本来就写在 app_main 里，而不是因为系统停了。

正确做法有两种，选哪种都行：① 让 app_main 在最后进入一个 for (;;) { vTaskDelay(...); }，把它当成一个「系统管理任务」用； ② 老老实实 return，但只把「永久的」东西放在全局变量或 static 变量里， 并且保证创建任务、申请内存这些事在 return 之前全部做完。 两种都可以，不可以的是「在栈上的局部变量里存着句柄，然后 return 之后再回来用它」。

顺便说一句栈：main 任务的栈大小由 CONFIG_ESP_MAIN_TASK_STACK_SIZE 决定，默认 3584 字节。 这个值可以在 idf.py menuconfig 的 Component config → ESP System Settings → Main task stack size 里改。 很多人把所有初始化代码都塞进 app_main，然后在里面调用 nvs_flash_init()、esp_wifi_init()、 一堆 printf——3584 字节真的不够， 现象就是启动到一半莫名其妙复位。这个值是「可以放心调大的」，别省。

你在裸机里的直觉ESP-IDF 里的实际情况后果
main 是程序入口 入口在 call_start_cpu0，app_main 是被创建的 main 任务 不能再自己写 int main(void)，会和组件里的定义冲突
main 返回 = 程序结束 app_main 返回 = 删掉 main 任务，其余照跑 局部变量与句柄失效，但系统没有停——比「停下来」更难查
程序只需要一个栈 每个任务一个独立栈，main 任务默认 3584 字节 把大数组放在 app_main 里会直接压爆 main 的栈
初始化代码写多少都行 main 任务的栈是有限的，WiFi 初始化、NVS、printf 都要吃栈 启动阶段随机复位，而报错信息可能在复位之后才打出来

2.2 任务是什么：函数签名、绝不能返回，以及六个参数

一个任务在 C 语言层面就是一个签名固定的函数： 

void 任务名(void *pvParameters);

三个要点，每一条都对应一个真实的坑：

  • 返回值必须是 void。 内核调用它的时候根本不看返回值，写成 int 只会让编译器和调用约定对不上。
  • 参数只有一个 void *。 这是「内核不知道你想传什么」的必然结果：它只能给你一个通用指针， 你在函数里自己转成想要的类型。不需要参数就传 NULL 进来、在函数里忽略它。
  • 绝对不能返回。不能用「返回值表达成功失败」， 也不能靠「跑完一轮就 return」来结束一个任务。任务体必须是一条不归路： 要么 for (;;) 永远转下去，要么显式调用 vTaskDelete(NULL) 结束自己。
任务函数真的返回了，会发生什么？

会走到移植层专门为这种错误准备的陷阱里。FreeRTOS 每个移植都会提供一个 「任务出口错误处理」：在 ESP-IDF 的移植里，它会打印一行 FreeRTOS Task "xxx" should not return, Aborting now! 然后调用 abort()，芯片复位； 在带 configASSERT 的 vanilla 移植（比如 STM32 上的）里， 通常会停在 prvTaskExitError() 的无穷循环里，表现为「卡死」。

特别注意：这不是 vTaskDelete(NULL)。 任务返回和主动删除自己完全是两件事——前者是编程错误，后者是正常退出。 想结束任务就明确写 vTaskDelete(NULL)， 让内核知道你是故意结束的，它才会去做正常的清理。

xTaskCreate：六个参数，一个一个说

BaseType_t xTaskCreate(TaskFunction_t  pxTaskCode,      /* ① 任务函数 */
                       const char   *pcName,          /* ② 任务名（调试用） */
                       const uint32_t usStackDepth,   /* ③ 栈深度 —— 单位是【字节】！ */
                       void         *const pvParameters, /* ④ 传给任务的参数 */
                       UBaseType_t   uxPriority,      /* ⑤ 优先级（越大越优先） */
                       TaskHandle_t *const pxCreatedTask); /* ⑥ 返回的任务句柄 */

/* 返回 pdPASS（成功）或 pdFAIL（通常是堆不够，建不出栈或 TCB） */
#参数怎么填坑在哪
① 任务函数 直接写函数名，不要加括号、不要加取地址符 写成 task_main() 就是「先调用一次再拿返回值当函数指针」，编译可能只给个警告
② 任务名 字符串，最长 16 个字符（configMAX_TASK_NAME_LEN） 名字是给 vTaskList 和崩溃日志看的，超过 16 会被截断，表格对不齐；名字内容会被内核保存，不是只存指针
③ 栈深度 ESP-IDF 里单位是字节，直接写 2048 就是 2 KB 头号误解在这：vanilla FreeRTOS 与 STM32 上的移植，这个参数的单位是字（4 字节）。见下面的专门说明
④ 任务参数 一个 void *。传 NULL 或任意指针 传局部变量地址：创建它的函数一返回，那块内存就没了。要用 static 变量、全局变量或堆内存；传一个小整数可以用 (void *)(intptr_t)值
⑤ 优先级 0 ~ 24，数值越大优先级越高 不要用 0（那一档是空闲任务的），也不要超过 configMAX_PRIORITIES - 1（创建会失败）。方向和 STM32 的 NVIC 相反，见 2.4 节
⑥ 任务句柄 TaskHandle_t 变量的地址；不需要就传 NULL 句柄是「以后操作这个任务」的唯一凭据：删它、量它的栈水位、改它的优先级都要用。建完就把句柄丢了，就只能靠名字找了（没有这种 API）
头号误解：栈深度到底是字节还是字？

这件事必须一次性说死，因为它每年都要坑掉一批从 STM32 转过来的人。

你在哪里写代码第三个参数的单位想要 2 KB 的栈，该写多少

ESP-IDF（本篇、以及所有 ESP32 + ESP-IDF 的官方例程） 字节（官方文档明确写了这一点，是相对 vanilla 的一处有意改动） 2048

两种错法的后果完全不同，而且都不报错：

  • 按「字」的习惯在 ESP-IDF 里写 128，你以为给了 512 字节， 实际只给了 128 字节——任何一次函数调用都会踩穿它， 现象是任务一启动就报栈溢出，或者更糟：踩坏了邻居的内存，表现为「另一个毫不相干的任务跑飞」。
  • 按「字节」的习惯在 vanilla FreeRTOS 里写 2048， 你以为给了 2 KB，实际给了 8 KB——不崩，但是白吃掉 6 KB 内存。 在只有 20 KB SRAM 的 STM32F103 上，这是要命的浪费。

防身办法：凡是允许的地方就写 sizeof(数组) 或 sizeof(StackType_t) * 字数，让单位显式地出现在代码里； 实在要写字面量，就在旁边写一行注释说明单位。 不确定的时候，用 2.6 节的栈水位函数量一下——量出来的数字比任何记忆都可靠。

2.3 双核：PRO_CPU 与 APP_CPU，以及「钉核」到底为了什么

ESP32（指经典的双核版本，比如 ESP32-WROOM-32 里的 ESP32-D0WDQ6）有两颗完全相同的 Xtensa LX6 核，最高 240 MHz。它们都有自己的寄存器组和自己的中断控制器视角， 但共享同一块 SRAM、同一套总线、同一个 cache 和外设—— 这一点很重要，它决定了「双核不等于双倍性能」。

PRO_CPU（CPU0）APP_CPU（CPU1）
名字的含义Protocol CPU，历史上是给协议栈用的Application CPU，历史上是给应用代码用的
硬件上是否对等完全对等。两颗核跑同一套指令集、同样的主频，任何任务都能跑在任何一颗上
ESP-IDF 默认往哪放二级引导、main 任务、WiFi 任务、蓝牙控制器任务、TCP/IP 任务默认什么都不放——你的任务如果不钉核，调度器可以把它放到任意一颗上
名字带来的实际后果「重量级」的系统任务默认都堆在 CPU0 上，所以 CPU0 通常更忙通常是「干净」的那颗核，这也是为什么推荐把实时性要求高的任务钉到这里

xTaskCreatePinnedToCore：多出来的第七个参数

不钉核的任务（用 xTaskCreate 创建的）在 ESP-IDF 里亲和性是 tskNO_AFFINITY，调度器可以把它放在任一核上运行。 想指定它就换成带核号的版本，参数只多一个： 

/* 不钉核：让调度器决定它在哪颗核上跑 */
xTaskCreate(task_fn, "name", 2048, NULL, 5, &handle);

/* 钉核：第七个参数写 0（PRO_CPU）或 1（APP_CPU），也可以写 tskNO_AFFINITY */
xTaskCreatePinnedToCore(task_fn, "name", 2048, NULL, 5, &handle, 1);

/* 想知道当前代码跑在哪颗核上（返回 0 或 1） */
int core = xPortGetCoreID();

/* 想知道这颗芯片一共有几颗核（双核版返回 2） */
int n = portNUM_PROCESSORS;
钉核不是「加速开关」，它换来的主要是可预测性

新手最常见的两个误解方向相反，但都是错的：

  • 「钉到 CPU1 就能快一倍」——错。两颗核共享内存与总线， 总吞吐受限于内存带宽而不是核数。纯寄存器运算的代码可能接近 2 倍， 但一个频繁读写 SRAM 的任务，实测通常只能拿到 1.6~1.8 倍 （按典型值估算，具体取决于内存访问密度）。
  • 「钉核是进阶技巧，新手不要用」——也错。对于实时性敏感的任务， 钉核是让响应时间可预测的最直接手段：把任务放到一颗「只有它在跑」的核上， 它就不会被 WiFi 的突发吃掉 CPU。第三节例 5 会把这两种情况的抖动算给你看。

所以正确的说法是：钉核解决的是「干扰」而不是「速度」。 而且它是有代价的——你把任务钉在 CPU1 之后，CPU0 上空出来的时间并不能自动被它利用， 相当于把这颗任务对 CPU0 的可用性上限锁死了。如果哪天 CPU1 上被塞进第二个重任务， 你又会回到「一核挤两任务」的局面。

为什么 ESP-IDF 默认把 WiFi 放在 CPU0

因为 WiFi 协议栈有硬实时要求：802.11 的时序（信标、ACK、 SIFS 间隔）是微秒级的，协议栈任务必须能在规定时间内被唤醒并处理， 否则丢包、掉线。所以 ESP-IDF 默认把 WiFi 任务 （由 CONFIG_ESP32_WIFI_TASK_CORE_ID 控制，默认 0） 和蓝牙控制器任务都钉在 CPU0 上，并且给它们很高的优先级 （WiFi 任务优先级 23，而 app_main 是 1）—— 这意味着只要 WiFi 有事，你的低优先级任务就得让路。

这解释了一个很常见的现象：一个纯计算的循环，在没开 WiFi 的时候耗时 3 ms， 开了 WiFi 之后偶发变成 5 ms 甚至更多。不是你的代码变慢了， 是它被切走了几次。把这种任务钉到 CPU1，它就不再受 WiFi 突发的影响—— 这就是「钉核」的真正用途。

单核模式：CONFIG_FREERTOS_UNICORE

在 menuconfig 里打开 Component config → FreeRTOS → Kernel → Run FreeRTOS only on first core （即 CONFIG_FREERTOS_UNICORE = y），FreeRTOS 就只在 第一颗核（CPU0 / PRO_CPU）上跑任务。这时：

  • xPortGetCoreID() 永远返回 0，portNUM_PROCESSORS 是 1；
  • 内核少了一个空闲任务、一套 SMP 自旋锁和调度结构，能省下一点内存和调度开销；
  • 好处是行为更接近「教科书上的 FreeRTOS」，并发问题更好推理； 代价是你放弃了一半的算力。

对绝大多数学习项目，保持默认的双核就好；只有当你在做「单核 MCU 移植到 ESP32」 或者追求「行为完全可复现」的时候，单核模式才值得考虑。 Arduino-ESP32 默认也是双核。

Blocked 是「它自己在等」——有超时、有唤醒条件，是正常且推荐的用法。 Suspended 是「别人不让它跑」——没有超时、没有唤醒条件， 只要没人 vTaskResume，它就永远停在那儿。

所以要停一个任务一段时间，用 vTaskDelay。 只有当你需要「确实地冻住某段逻辑，直到某个外部条件成立才放行」时才用挂起， 而且要保证每一对 vTaskSuspend 都有一条确定的恢复路径， 否则你就在系统里埋了一个永远不会醒的任务——它还占着 RAM 和句柄。

规则一：抢占——高优先级一就绪，立刻抢

ESP-IDF 的默认配置是抢占式调度 （configUSE_PREEMPTION = 1）。 它的规则只有一句话：任何时刻，CPU 属于「优先级最高且处于就绪态」的那个任务。

「立刻」两个字是认真的：抢占发生在任何一个让高优先级任务变为就绪的事件上—— 定时器到期、队列收到数据、中断里 Give 了信号量、别的任务恢复了它。 不需要等到下一个 tick，也不需要你手工让出。这一点和裸机的时间片轮询有本质区别： 轮询的响应延迟最坏是一个时间片，而抢占的响应延迟是一次上下文切换的时间 （ESP32 上通常几微秒量级，按典型值估算）。

规则二：同优先级才轮到时间片

如果好几个任务优先级相同且都就绪，它们就按时间片轮转 （configUSE_TIME_SLICING = 1，默认开启）。 时间片长度就是一个 tick， 而 tick 的频率由 configTICK_RATE_HZ 决定：

顺带一句：FreeRTOS 的任务优先级和中断优先级是两套完全独立的体系， 它们之间没有统一的排序。中断永远能打断任何任务（因为中断不走调度器）， 而任务永远不能「打断」中断。中断里要唤醒任务，靠的是 ...FromISR 版本的 API（第 41 篇展开）。

规则三：空闲任务优先级 0，负责回收垃圾——所以不能饿死它

调度器启动时会自动创建空闲任务：每一颗核一个， 名字分别是 IDLE0（CPU0）和 IDLE1（CPU1）， 优先级都是 0（tskIDLE_PRIORITY），也就是最低档。

它做的事看起来无关紧要，实际上有两件是系统级的必需工作：

  1. 回收被删除任务的内存。 调用 vTaskDelete() 只是把任务从各种链表里摘掉， 它占的栈和 TCB 内存不在这时候释放——真正的 free() 是在空闲任务的上下文里做的。所以如果空闲任务永远得不到 CPU， 每删除一个任务就泄漏一块内存：删着删着堆就空了，之后所有 xTaskCreate 都返回 pdFAIL。
  2. 喂任务看门狗（TWDT）。 空闲任务是默认被订阅进看门狗的。饿了它 5 秒，整片芯片就会因为 Task WDT 超时而复位（2.7 节详细讲）。
由此得到本篇最重要的一条纪律

任何任务都不能长时间霸占 CPU 而不阻塞。 优先级 5 的任务写一个纯计算的死循环，会让本核上所有优先级 ≤ 5 的任务 （包括优先级 0 的空闲任务）全部饿死。高优先级任务饿死低优先级任务是「设计」， 饿死空闲任务是「事故」——因为后者会直接导致整片芯片复位。

而且注意：taskYIELD() 和 vTaskDelay(0) 都救不了它。 这两种「让出」只会把 CPU 让给同优先级或更高优先级的就绪任务； 空闲任务的优先级是 0，永远排不上。只有真正的阻塞（vTaskDelay(≥1 tick)、 等队列、等信号量）才能把 CPU 交出去给低优先级任务。这一条在第四节程序三里会让你亲手复现一次。

把三条规则合起来看

调度器要选一个任务运行：
  1. 在【就绪】的任务里，找优先级最高的那一档
  2. 如果这一档有多个任务：
       - 开了时间片 → 取下一个（轮转），每个最多连跑 1 个 tick
       - 没开时间片 → 取当前这个，它不阻塞就不换人
  3. 如果一颗核上【没有任何就绪任务】→ 运行该核的空闲任务（IDLE0 / IDLE1）
  4. 只要有一个更高优先级的任务变成【就绪】，立刻重新选（这就是抢占）

【推论一】低优先级任务饿死高优先级任务：不可能（抢占保证）
【推论二】高优先级任务饿死低优先级任务：可能，而且是设计允许的
【推论三】任何任务饿死空闲任务：可能，但会触发 Task WDT 复位
【推论四】两个同优先级任务「轮流跑」：每个跑满 1 个 tick（10 ms）才换
【推论五】优先级差 1 档，就能决定「谁先谁后」；差 18 档（比如 5 和 23）
          意味着只要 WiFi 有事，你的任务这一轮就别想按时完成

2.5 阻塞与延时：把「等」这件事交给内核

在裸机里，「等」是一件很尴尬的事。你想等 100 ms，只有两种写法： HAL_Delay(100)（CPU 空转，什么都干不了） 或者「记住一个时间戳，每轮循环检查一次到点了没有」（不空转，但要在代码里到处散布时间戳判断， 而且响应延迟取决于循环周期）。RTOS 给了第三种写法： 调用一个会「阻塞」的函数，把自己的名字从就绪链表里摘出去， 等条件满足再由内核把你放回来。这段时间里 CPU 完全属于别的任务。

vTaskDelay(pdMS_TO_TICKS(100));

/* ---------- 固定周期：适合「控制环」「采样」「刷新」 ---------- */
TickType_t last_wake = xTaskGetTickCount();   /* ★ 必须初始化！ */
const TickType_t period = pdMS_TO_TICKS(10);

for (;;) {
    do_control_loop();                        /* 这一轮要干的活 */

    /* 把下一次唤醒时刻推进到 last_wake + period。
       返回 pdFALSE 表示「这个时刻已经过去了」——说明本轮的执行时间超过了周期，
       也就是【周期已经守不住了】。这种情况必须被记录下来，不能假装没发生。 */
    if (xTaskDelayUntil(&last_wake, period) == pdFALSE) {
        overrun_count++;
    }
}

/* ---------- 关于旧名字 ---------- */
/* vTaskDelayUntil() 是旧 API，返回 void，【不会告诉你有没有超时】。
   ESP-IDF 提供的是 xTaskDelayUntil()，返回 BaseType_t，能告诉你超没超时。
   新代码一律用 xTaskDelayUntil()。 */
pdMS_TO_TICKS：它不是单位换算，它是「向下取整到 tick 网格」

pdMS_TO_TICKS(ms) 的展开式是 ((TickType_t)((ms) * configTICK_RATE_HZ / 1000))， 整数除法意味着结果会被截断：

  • 在默认的 100 Hz tick 下，1 tick = 10 ms，所以 pdMS_TO_TICKS(25) = 2500/1000 = 2 tick = 20 ms（少了 20%）；
  • 更危险的是小于一个 tick 的值会直接变成 0： pdMS_TO_TICKS(5) = 500/1000 = 0。 而 vTaskDelay(0) 不会阻塞， 它只是让出一次 CPU 就立刻回来——你的「延时 5 ms」变成了忙等， 循环跑得飞快，还可能把空闲任务饿死。

所以只要你的周期或延时小于 10 ms，就必须重新考虑 tick 频率（见第三节例 1）， 或者改用微秒级的 esp_timer。 这一条是「我的任务明明写了延时，为什么 CPU 占用还是 100%」的最常见原因。

vTaskDelay(0) 和 taskYIELD() 有什么区别

这两个调用看起来都是「让一下 CPU」，而且效果确实很像，但它们的目的和作用范围不同：

很多人被看门狗复位教训过一次之后，就在死循环末尾加一句 taskYIELD() 或 vTaskDelay(0)， 发现「好像不重启了」——那是因为你的板子上恰好还有别的同优先级任务在跑， 或者你顺手把 printf 加进去了、串口驱动内部阻塞了一下。 本质上，空闲任务仍然没有机会运行。

唯一可靠的让出方式是真正进入阻塞态：vTaskDelay(pdMS_TO_TICKS(1)) （至少让出 1 个 tick）或者阻塞在队列/信号量上。 判断标准很简单：问自己「这一句执行完之后，空闲任务能不能跑到」。

为什么「任何轮询等待都应该换成阻塞」

这是裸机转 RTOS 时最需要改掉的一个习惯。下面这张表里的写法在裸机里全都是「对的」， 到了 RTOS 里全部有问题：

为什么要费这个劲？因为阻塞带来的收益不止「省 CPU」一条：

  • CPU 真的省下来了。在 ESP32 上还直接换算成功耗—— 空闲任务跑得越多，能进低功耗的机会越大（第 43 篇）。
  • 代码变成了顺序逻辑。「发命令 → 等应答 → 超时重试」 可以老老实实写成三行，而不是拆成一个状态机（上一篇 2.6 节讲过的那个困境， 到这里终于有了解药）。
  • 时间关系变得可预测。阻塞的唤醒由内核负责， 不再依赖「循环跑到那一行的时候正好到点了」。

2.6 栈：每个任务一块自己的内存，怎么估、怎么量、怎么爆

这是 RTOS 里最「不像编程、像算账」的一部分，也是新手最容易翻车的地方。 在裸机里，你从来不用想栈——链接脚本给一个几 KB 的栈，所有函数共用， 反正只要不写超大的局部数组就没事。到了 RTOS， 每个任务有自己的栈，而栈的大小要你自己报。 

【裸机：所有函数共用一个栈】
    主栈 ──┬── main()
           ├── 任务A的调用链
           ├── 任务B的调用链
           └── 中断的调用链（中断借用被中断代码的栈）
    好处：不知道谁用多少也没关系，反正共用一大块
    代价：一个任务写了个大数组，另一个任务就倒霉（栈溢出踩到别人）

【RTOS：每个任务一个栈，互相隔离】
    任务A 的栈（2 KB）  任务B 的栈（4 KB）   main 任务的栈（3.5 KB）
            ↑                    ↑                     ↑
    好处：A 栈溢出只会毁掉 A 自己（多数情况下）
    代价：每个栈都要单独算大小；给多了浪费 RAM，给少了直接崩

【三条必须记住的事实】
  ① 任务栈是【从 RTOS 堆里分配】的，不是编译器帮你摆好的全局数组
  ② 任务里声明的局部数组、局部结构体，全部吃在【这个任务自己的栈】上
  ③ 在 ESP32（Xtensa）上，中断服务程序会借用【被中断的那个任务的栈】——
     所以「栈要留余量」不只是为了你的函数调用深度，也是为了中断
为什么中断也要算进任务的栈

在 Xtensa 架构上，中断入口不会另换一套栈，而是直接在被中断任务的栈上保存现场并执行 ISR 的代码。也就是说，一个「只需要 800 字节」的任务， 如果正好在一个很深的调用点被一个栈用量 400 字节的中断打断， 峰值就变成了 1200 字节。

这解释了一类非常难查的崩溃：单独跑没问题，一开 WiFi / 一接串口中断就偶尔重启。 现象看起来像是「中断的问题」，实际上是你把某个任务的栈压得太紧， 加上中断那一层就踩穿了。工程上的规矩是：所有任务的栈都留 30% 以上余量， 「已经调好用了很久」的也不行——因为你迟早会往里面加代码。

怎么估：四个部分加起来再取整

估算栈用量不需要精确到字节，需要的是不低估。按下面四块加， 然后向上取到一个「好看的数」（比如 1 KB、1.5 KB、2 KB、3 KB、4 KB）：

组成部分怎么估典型量级（按典型值估算）
① 局部变量 把任务函数里（含它调用的所有函数的局部变量）最大的那些加起来。 数组和结构体按完整大小算 没有大数组：几十~200 字节；
有一个 float buf[64]：256 字节起
② 调用链的栈帧 每层函数调用要保存返回地址、被调用者保存寄存器、对齐填充。 粗略按「每层 32~64 字节 × 最大调用深度」 深度 5~8 层：200~500 字节
③ printf 家族的峰值 单次调用就能吃掉 1 KB 以上（格式化缓冲 + 数字转字符串 + 浮点处理）。 sprintf 比 printf 略小，但也是同一量级 1024~2048 字节
④ 中断借用 这颗任务运行时，可能打断它的最「重」的那个 ISR 要多少栈 200~500 字节
printf 是栈的头号杀手，而且它「看起来」很无辜

很多人的第一个栈溢出就是因为往任务里加了一句调试打印。原因很实在： 格式化输出要分配一块缓冲、把数字转成字符串、处理宽度和精度—— 在 ESP-IDF 的 newlib 里这整套流程走下来，单次 printf 就可能用掉 1 KB 以上的栈， 涉及浮点格式化（%f）时更多。

于是出现了一个很典型的画面：一个 2 KB 栈的任务平时跑得好好的 （水位还剩 60%），加了一句带 %f 的 printf 之后立刻报栈溢出复位。 这不是 printf 有问题，是你没给它留够地方。

三条实用建议： ① 带打印的任务，栈至少 3 KB 起； ② 用 ESP_LOGI 这类日志宏替代裸 printf，它的格式化开销更可控； ③ 绝不要在中断里打印——不只是栈，还有重入和实时性问题。

怎么量：uxTaskGetStackHighWaterMark

估算只是起点，真正的答案是量出来。 FreeRTOS 提供一个专门的函数，它返回的是「这个任务从创建到现在， 栈上剩余空间的历史最小值」——业内叫栈水位（high water mark）： 

/* 量当前任务自己：传 NULL 即可 */
UBaseType_t hw = uxTaskGetStackHighWaterMark(NULL);

/* 量别的任务：需要它的句柄（所以创建时要把句柄存下来） */
UBaseType_t hw = uxTaskGetStackHighWaterMark(handle_of_sensor_task);

/* hw 的含义：历史最小剩余。它只减不增——
   因为它是「历史最坏时刻」的记录，不是「现在还剩多少」。
   换句话说：hw 是保守值，看到 hw 很小就一定是真的紧张过。 */
单位陷阱又来了：这个返回值是字节还是字

和第三个参数一样，这里也存在 vanilla FreeRTOS 与 ESP-IDF 的差异： vanilla 按字返回，ESP-IDF 按字节返回。 所以你看到一个「2 KB 的栈」水位显示 1400，那是字节（还剩 68%）； 如果显示 350，那是字（350 × 4 = 1400 字节，同样的结论）。

不要去背这个。用第四节程序二里的办法： 把「配置的栈大小」和「水位返回值」一起打印出来， 两个数字一对比，你立刻就知道当前这个版本用的是哪种单位—— 而且从此对这篇文档里任何数字都有了免疫力。

怎么判断「够不够」：剩余 30% 是底线

水位剩余比例怎么判断该怎么办
< 10% 随时可能踩穿。哪怕现在不崩，也只是因为还没有人在这个任务里加代码 立刻加大栈，然后重新测
10% ~ 30% 危险区。今天能用，但一次中断、一次深一点的调用就爆 加大栈（至少翻倍），或者想办法减少局部变量/去掉打印
30% ~ 50% 可以接受。这是推荐的底线区间 保留，并且在代码里注释说明「已测水位」和测试条件
> 50% 宽裕，浪费了一点 RAM 在 RAM 紧张的项目里可以适度缩小，但要重新测量

怎么测才准：水位函数记录的是「历史最坏时刻」， 所以你必须把最坏情况跑出来再读数。 只在开机后读一次是没意义的——那时候大部分代码路径还没走过。 正确的测法是：让系统满载运行一段时间，把所有的功能分支都触发一遍 （所有传感器都接上、所有通信都连上、所有按键都按过），再打印水位。 有条件的话，在实验室里跑上几个小时再读。

栈溢出了会怎样：两种现场

【形态一：被内核抓个正着 —— 最好的情况】

    ***ERROR*** A stack overflow in task sensor has been detected.
    Backtrace: 0x400d1234:0x3ffb1a20 0x400d2345:0x3ffb1b40 ...

    内核在每次任务切换时检查栈指针有没有越界（配置项
    CONFIG_FREERTOS_CHECK_STACKOVERFLOW），或者在栈顶放一段「魔数」
    定期检查有没有被写坏。抓到就打印任务名并复位。
    ★ 这种情况其实很幸运：它明确告诉了你【哪个任务】的栈不够。

【形态二：踩坏了别人的内存 —— 最麻烦的情况】

    现象可能是：
      - 一个毫不相干的任务里的变量莫名其妙变了值
      - 堆管理器的链表被写坏，之后 malloc 随机失败或卡死
      - 某个函数返回地址被覆盖，跳到随机地址执行（Guru Meditation Error）
    这类问题极难定位，因为【报错的地方】和【出问题的地方】相隔十万八千里。

    ★ 形态二说明了为什么栈要留余量：不是为了「现在够用」，
      而是为了「出问题的时候能被抓住」，而不是悄悄毁掉别的内存。

除了内核自带的检查，还有一种「土办法」非常有效，而且能定量地告诉你 栈用了多少：往栈里填一串魔数，跑一段时间之后从栈顶往下扫， 数到第一个没被改动过的位置——那就是历史最高水位的位置。 原理很简单：栈是从高地址往低地址生长的，被用到的部分一定会把魔数覆盖掉。 这个方法的完整实现（含代码）在第四节程序二里。

什么时候用魔数扫描，什么时候用水位函数

日常用 uxTaskGetStackHighWaterMark() 就够了—— 一行代码，随时可查，不需要额外的栈数组。 魔数扫描的两个额外价值是： ① 当你想验证水位函数返回的单位时，两个数字对照一下立刻明白； ② 当你需要「不看内核、自己独立测量」时（比如怀疑内核的统计不准， 或者想测量一个用 xTaskCreateStatic 自己分配栈的任务）。 两者结果应当一致——不一致就说明有地方理解错了，这正是它的价值。

2.7 任务看门狗（TWDT）：为什么一个任务不放手，整片芯片重启

现在来解开本篇开头第 5 号困惑——那个「每 5 秒整片芯片重启一次」的现象。 它不是崩溃，是任务看门狗（Task Watchdog Timer，TWDT）主动复位了芯片。 这是 ESP-IDF 里最容易被误认为「玄学」的机制之一，但它的逻辑其实非常直白。

TWDT 是什么：一组「必须定期报到的任务」名单

TWDT 是 ESP-IDF 在 FreeRTOS 之上做的一层软件看门狗。它维护一份任务名单， 名单上的每个任务都必须周期性地「喂狗」 （专业说法是 reset）。它只有一个定时器，判定规则是： 名单上任何一个任务超过超时时间没来喂狗，就算整只狗没喂上。 

        ┌──────────────────── 看门狗定时器（超时 CONFIG_ESP_TASK_WDT_TIMEOUT_S，默认 5 秒）──┐
        │                                                                                    │
        │   名字名单（订阅者）                    每个任务的行为                             │
        │   ─────────────────────               ─────────────────                            │
        │   IDLE0  (CPU0 空闲任务)  ←默认订阅    每跑一圈就 reset 一次 → 一直很勤快            │
        │   IDLE1  (CPU1 空闲任务)  ←默认订阅    每跑一圈就 reset 一次 → 一直很勤快            │
        │   sensor （你自己的任务）  ←手动订阅    干活 → reset → 干活 → reset ...              │
        │   network（你自己的任务）  ←手动订阅    等 HTTP 响应 第 7 秒还没回来 ←【没喂上】      │

配置项（menuconfig → Component config → ESP System Settings）默认值含义
CONFIG_ESP_TASK_WDT_TIMEOUT_S 5 秒 超时时间，可设 1~60 秒。超过这个时间没有全部喂到就复位

最常见的触发路径：空闲任务被饿死

回头对照 2.4 节：空闲任务的优先级是 0，而它默认就在 TWDT 的名单上。 于是：

你在任何一个任务里写了「不阻塞的长时间运算」 → 本核的空闲任务拿不到 CPU → 空闲任务 5 秒喂不上狗 → TWDT 超时 → 整片芯片复位。

这就是为什么「一个任务不放手，整个芯片重启」。 看门狗在日志里点名的是 IDLE0 或 IDLE1， 但真正的凶手写在下面那两行 Tasks currently running 里—— 它会告诉你 CPU0 和 CPU1 当时分别在跑哪个任务。 只看「谁没喂狗」会误以为是空闲任务的问题，要看「谁在跑」才能找到霸占 CPU 的那个任务。

    .trigger_panic  = true,                    /* 超时就 panic（默认会复位） */
};
/* 如果启动阶段已经初始化过（CONFIG_ESP_TASK_WDT_INIT 默认开启），
   必须用 reconfigure；直接 init 会返回 ESP_ERR_INVALID_STATE */
esp_task_wdt_reconfigure(&cfg);

/* ② 把自己订阅进名单。传 NULL = 当前任务 */
esp_task_wdt_add(NULL);

/* ③ 喂狗。放在「这一轮完整的活干完了」的位置 */
esp_task_wdt_reset();

/* ④ 退出名单（任务要结束、或者不想再被监视时） */
esp_task_wdt_delete(NULL);

/* ⑤ 查自己有没有在名单上（排查「为什么我的任务没被监视」时有用） */
bool subscribed = esp_task_wdt_status(NULL);

/* 旧版本（ESP-IDF v5.0 之前）的初始化签名是两个参数：
     esp_task_wdt_init(uint32_t timeout_s, bool panic);
   看到这种写法不要慌，是老工程。 */
喂狗的位置比喂狗的频率重要得多

看门狗的价值完全取决于你把 esp_task_wdt_reset() 放在哪里。放错了，这条狗就变成了一条永远不会叫的狗——它还在，但它保护不了任何东西。

喂狗的位置它的语义评价
放在主循环末尾，一轮活干完之后 「我完整地干完了一轮」 正确。任何一步卡住，这一轮就走不完，狗就会叫
放在一个高频的独立小任务里，每 100 ms 喂一次 「这个喂狗任务还活着」 错误且危险。它把「别人卡死」这件事完全掩盖了。 狗永远不叫，你也就永远不知道有任务卡住了
放在循环开头 「我准备开始干活了」 半对。如果这一轮卡住，狗会叫，但也可能因为下一轮很快开始而掩盖部分问题。 比末尾差一点，比高频任务好得多
放在一个长任务的每个分段之间 「这一大坨活我又推进了一步」 对长任务正确。比如写 Flash、跑一次大数据计算， 拆段 + 段间喂狗是标准做法

2.8 删除与生命周期：任务怎么结束才是安全的

一个任务的完整生命周期是：被创建 → 就绪 → 运行 ⇄ 阻塞 → 被删除 → 内存被回收。 前面几节讲完了中间那段，最后这一段有两个容易出人命的细节。

细节一：删除只是「摘牌」，内存回收是别人的活

vTaskDelete() 做的事是把任务从各种内核链表里摘掉， 让它再也不会被调度。但它占用的栈和 TCB 两块内存不会立刻释放—— 真正的释放是在空闲任务的上下文里完成的（回到 2.4 节的第 1 条）。

于是得到一条推论，它能解释很多「删任务删出内存泄漏」的怪事： 如果你的系统一直很忙，空闲任务很少有机会运行， 那么被删除任务的内存就一直挂着不还。 短时间看不出来，长时间运行（比如一个「按需起停工作线程」的设计）就会慢慢把堆吃光， 最后所有 xTaskCreate 开始返回 pdFAIL。

vTaskDelete(NULL)：自杀vTaskDelete(handle)：他杀
谁在调用 任务自己，在自己函数体里 任何别的任务（不能在中断里调用）
什么时候生效 立刻，不再返回 立刻从链表摘除，不会再被调度
能自己清理吗 能。删之前可以关文件、释放内存、归还锁、通知同伴 不能。目标任务的清理代码一行都不会执行
内存回收 都是延后到空闲任务里做的（两种方式一样）
风险 低（只要你记得清理） 高。见下面那张「他杀前必须确认」的清单
推荐度 推荐。常态就应该用这个 只在「这个任务已经不可救药」时用，且必须先确保它不持有任何资源
他杀一个任务之前，必须先确认它不再持有任何资源

这是「他杀」的全部风险所在。目标任务被摘掉的那一刻，它手里拿着的东西还在它手里：

  • 互斥量 / 信号量——它拿着锁被杀了，锁永远不会被 Give 回去。 所有等这把锁的任务（包括高优先级任务）永久阻塞。这是最典型的死锁来源。
  • 动态内存——它 malloc 的缓冲区不会自动释放。 它自己的栈会被回收，但堆上那些块不会。
  • 外设 / 总线状态——它正在写 Flash、正在发 SPI 事务、正在驱动一个状态机。 半途而废会让外设停在不确定的状态，下一个使用者会拿到错误的结果。
  • 别人手里的指针——别的任务可能正持有指向它的数据结构（或者它栈上变量的指针）。 它一死，那些指针全部悬空。
  • 看门狗名单——如果它订阅了 TWDT，它死了以后就再也没人替它喂狗了。 TWDT 会在 5 秒后因为「这个任务没喂狗」而复位整片芯片—— 删掉一个订阅了看门狗的任务，如果不先 esp_task_wdt_delete()， 你会在 5 秒后收到一个看起来毫不相干的复位。

正确做法：优先「请它自己退出」，而不是「把它杀掉」。 也就是给它发一个事件（事件组、标志、任务通知），它自己从阻塞中被唤醒， 走完清理流程，然后 vTaskDelete(NULL) 结束自己。 这样做的好处是：资源释放的代码写在「知道这些资源长什么样」的那个任务里， 而不是散落在杀它的那个任务里。

细节二：创建失败怎么办

xTaskCreate 返回 pdFAIL， 绝大多数情况是堆里没有足够内存分配栈和 TCB。 在 ESP32 上这件事比想象的常见：WiFi 起来之后可用堆会明显变小， 如果你的创建动作发生在 WiFi 之后，就可能失败。

在哪个阶段失败为什么怎么处理
启动阶段（app_main 里） 申请的任务太多、栈给得太大；或者 WiFi 已经起来把堆吃掉了大半 打印任务名 + 当时的空闲堆，然后进入安全状态 （比如只保留最小功能并亮一个错误指示灯），而不是带着半配置的系统继续跑
运行阶段（按需创建） 堆碎片化，或者正好赶上别的地方在用内存 可以让调用者稍后重试（返回错误码给上层），或者降级运行； 不要用死循环反复重试——那会变成新的忙等
删除之后立刻创建（替换任务） 被删任务的栈还没被回收（等空闲任务），所以此时可用堆比你以为的少 先 vTaskDelay 让空闲任务跑一下， 或者干脆复用任务（让它自己循环处理新工作）而不是删掉重建
「按需创建、用完就删」是个反模式

从 PC 编程带过来的一个直觉是「需要的时候 new 一个线程，用完销毁」。 在嵌入式 RTOS 里这个模式代价很高： 每次创建都要分配栈 + TCB，每次删除都要等空闲任务回收， 中间还有堆碎片化的风险。而任务本身其实很便宜——它阻塞着的时候几乎不占 CPU。

所以更符合 RTOS 习惯的设计是：常驻任务 + 用「消息」驱动它干活。 任务一直存在、一直阻塞在收消息上；有活了就被唤醒处理一次，处理完继续睡。 第 41 篇的队列就是这个模式的标准载体，也是这一篇和下一篇的衔接点。

第 2 节到这里结束：八个小节，每句一个

2.1 ESP-IDF 里真正的 main 负责创建「main 任务」并启动调度器， app_main 只是那个任务的函数体，它 return 不等于系统停止；2.2 任务函数签名固定、绝不能返回，六个参数里最要命的是 「栈深度在 ESP-IDF 里是字节」；2.3 两颗核硬件上对等，WiFi 默认钉在 CPU0 且优先级很高， 钉核换来的是可预测性而不是双倍性能；2.4 四状态 + 抢占 + 同优先级时间片， 优先级数值越大越高（与 NVIC 相反），空闲任务优先级 0 却不能饿死； 2.5 vTaskDelay 是相对延时、xTaskDelayUntil 才是固定周期，pdMS_TO_TICKS 会截断，小于 1 tick 会变成 0； 2.6 栈要按「局部变量 + 调用深度 + printf 峰值 + 中断借用」四块估， 用水位函数实测，剩余 ≥ 30% 才安全；2.7 TWDT 是一票否决的名单制， 空闲任务默认在名单上，所以「霸占 CPU」的代价是整机复位； 2.8 删除只是摘牌、回收靠空闲任务，他杀前必须确认它不持有任何资源。

动手算一遍：六个必须自己动手的账

前面几节把机制讲完了，但 RTOS 里真正让人吃亏的不是概念，是数值： tick 是多少、周期取几、栈给多少、看门狗多久喂一次。这些数字都可以算出来， 而且算错一次的代价通常是一次「莫名其妙」的复位或者一个「偶尔」丢数据的 bug。 这一节六道题，全部按「已知 → 列式 → 答案 → 结论」走一遍。

例 1：tick 是 10 ms，我要 25 ms 的周期怎么办

已知： ESP-IDF 默认 configTICK_RATE_HZ = 100， 即 1 个 tick = 1000 / 100 = 10 ms。某个任务需要每 25 ms 采一次数据。 

方案 A：直接写 pdMS_TO_TICKS(25)

    1 tick = 1000 ms ÷ 100 Hz = 10 ms
    pdMS_TO_TICKS(25) = (TickType_t)(25 × 100 ÷ 1000) = (TickType_t)(2.5) = 2   ← 整数除法，截断
    实际延时 = 2 tick × 10 ms = 20 ms
    绝对误差 = 25 − 20 = 5 ms
    相对误差 = 5 ÷ 25 = 20%                    ← 一个 20% 的周期误差
    1000 次采样累计少花的时间 = 1000 × 5 ms = 5 s

    ★ 结论：pdMS_TO_TICKS(25) 得到的是 20 ms，不是 25 ms。
      而且这个偏差不是随机的，它【永远偏短】——系统会一直跑得比你要求的快。

方案 B：把 tick 频率提到 1000 Hz（CONFIG_FREERTOS_HZ = 1000）

    1 tick = 1000 ÷ 1000 = 1 ms
    pdMS_TO_TICKS(25) = 25 × 1000 ÷ 1000 = 25 tick = 25 ms      ← 精确命中
    代价 ① 每秒 1000 次 tick 中断（原来 100 次），中断开销 ×10
    代价 ② 每个 tick 都要做一次调度判断 + 时间片轮转检查
    代价 ③ 时间片从 10 ms 变成 1 ms，同优先级任务的切换频率 ×10

方案 C：把周期改成 tick 的整数倍（推荐先试这个）

    能改成 20 ms 就改成 20 ms，能改成 30 ms 就改成 30 ms。
    工程上「每 25 ms 采一次」这种需求，通常背后的真实要求是
    「不小于 20 ms 且不大于 30 ms」，改成 20 ms 完全可接受，而代价是 0。
    ★ 这是最省钱的一招：先问需求能不能迁就 tick，再考虑改 tick。

方案 D：用 1 ms 周期的 tick 量化补偿（不改 tick 频率）

    每 5 次延时里，4 次用 2 tick、1 次用 3 tick：
    平均周期 = (4 × 20 ms + 1 × 30 ms) ÷ 5 = 110 ÷ 5 = 22 ms    ← 还是不对
    要凑够 25 ms，正确配比是 1 次 3 tick + 1 次 2 tick：
    平均周期 = (30 + 20) ÷ 2 = 25 ms                            ← 精确命中
    这样做的代价是周期在 20/30 ms 之间跳，【抖动 10 ms】。
    只适合「长期平均频率要准、单次抖动无所谓」的场合（比如统计上报）。
    控制类应用不能用——它要的恰恰是单次都不要抖

方案 E：干脆不要用 tick 做这件事

    需要微秒级或严格周期时，用 esp_timer（微秒分辨率，独立于 tick）：
    esp_timer_create() + esp_timer_start_periodic()，周期可以精确到 25 ms。
    回调在 esp_timer 任务上下文或中断上下文里执行，适合「触发」而不是「干重活」。
方案实际周期误差代价什么时候选它
A：pdMS_TO_TICKS(25)20 ms−20% 无需求本来就是「大约 25 ms」
B：tick 提到 1000 Hz25 ms0 tick 中断 ×10，全局开销上升系统里多个任务都需要毫秒级精度时
C：需求改成 20 ms20 ms0（对需求 20 ms 而言） 无首选。先谈需求，再谈技术
D：2/3 tick 交替平均 25 ms，抖动 ±5 ms0（长期） 单次抖动 10 ms只关心长期平均频率的场合
E：esp_timer25 ms0 回调上下文受限，不适合干重活需要微秒级精度或严格周期触发
这道题真正的考点不是选哪个方案

而是「先算出实际值，再决定要不要改」。 绝大多数人写 pdMS_TO_TICKS(25) 的时候， 心里想的是 25 ms，代码里得到的是 20 ms，而他永远不知道这件事—— 直到某天做时间统计时发现「采样率怎么比设计值高 20%」。 把 tick 频率写在注释里、把换算结果也写在注释里，这个习惯值一个 bug。

例 2：vTaskDelay 的漂移账，一天能差多少

已知： 一个任务每轮要执行 1.3 ms 的实际工作，用 vTaskDelay(pdMS_TO_TICKS(10)) 控制节奏， 设计意图是「每 10 ms 跑一轮」。问 1000 轮之后偏差多少，一天呢？ 

【vTaskDelay 的语义】：从现在起，10 ms 内别叫我
    一轮的实际耗时 = 执行时间 + 延时 = 1.3 ms + 10 ms = 11.3 ms

【误差按比例累积】
    1000 轮实际耗时 = 1000 × 11.3 ms = 11300 ms = 11.3 s
    1000 轮设计耗时 = 1000 × 10   ms = 10000 ms = 10.0 s
    偏差 = 11.3 − 10.0 = 1.3 s
    相对偏差 = 1.3 ÷ 10 = 13%           ← 注意：13% = 1.3 ms ÷ 10 ms，一模一样
    ★ 偏差率恒等于「执行时间 ÷ 周期」，跟轮数无关，所以它【不会自己变好】

【一天（24 h）会怎样】
    设计：24 h = 86400 s，每 10 ms 一轮 → 应跑 8,640,000 轮
    实际：跑完 8,640,000 轮需要 8,640,000 × 11.3 ms = 97,632 s = 27.12 h
    结论：你以为跑了一天，其实慢了 3.12 小时（27.12 − 24 = 3.12 h）

【换算成「实际周期」】
    实际周期 = 11.3 ms → 等效频率 = 1 ÷ 0.0113 ≈ 88.5 Hz
    设计频率 = 1 ÷ 0.010  = 100 Hz
    少跑了 11.5%，这个数字可以直接在示波器/逻辑分析仪上量出来

【换成 xTaskDelayUntil 之后】
    last_wake 初始化 = xTaskGetTickCount()       ← 这一句必须写，忘了就错一轮
    每轮：干活 1.3 ms → xTaskDelayUntil(&last_wake, pdMS_TO_TICKS(10))
    内核算的是「下一次唤醒应该在 last_wake + 1 tick 这个绝对时刻」
    执行 1.3 ms 之后，它只延时 8.7 ms，把执行时间从延时里扣掉了
    周期 = 10 ms 恒定，漂移 = 0（只要每轮执行时间 < 10 ms）

【什么时候会失效】
    如果某轮执行时间变成了 12 ms（超过周期），就守不住了：
      → xTaskDelayUntil 返回 pdFALSE，并且【不会阻塞】，立刻开始下一轮
      → 这是内核在告诉你「你的周期设计不合理」
      → 必须记录这个返回值并计数，否则你会丢掉最重要的故障信息

哪些场合必须用 xTaskDelayUntil

判断标准只有一条：这个任务的周期对它自己有语义吗？ 有语义的场合——控制环（PID 的积分项按固定 dt 算）、数据采样、 周期性上报（心跳、1 秒一次的统计）、和外部设备保持同步的轮询—— 全部必须用 xTaskDelayUntil。 反过来，「读完了歇 100 ms 再说」「重试前等 500 ms」这种没有周期语义的等待， 用 vTaskDelay 更直白，也不会有人误解。

一个很现实的后果：如果你用 vTaskDelay 做「每秒上报一次」， 而这一轮的执行时间是 30 ms，那么你上报的其实是每 1.03 秒一次。 一天之后你的数据对不上——而问题出在几个月前写下的那一行。

例 4：优先级反转的最坏时长（预告）

这道题在本篇只算「有多严重」，怎么治（互斥量与优先级继承） 是第 41 篇的内容。之所以要在这里算，是因为它决定了你要不要在第 41 篇认真读那一节。

已知： 三个任务，共享一把锁（先当成普通的二值信号量）：

  • L：优先级 2，持锁进入临界区，临界区本身只要 30 μs；
  • M：优先级 8，不碰这把锁，但随时会有 5 ms 的计算要跑；
  • H：优先级 10，最高，也要这把锁。
【时间线（没有优先级继承）】

  t=0.000 ms   L 拿到锁，开始执行临界区（本来只需 0.030 ms）
  t=0.010 ms   M 变为就绪。M 的优先级 8 > L 的 2 → 【抢占】L，L 被踢下 CPU
               ★ 关键：L 是【拿着锁】被抢占的
  t=0.010 ms   H 变为就绪，需要这把锁 → 锁在 L 手里 → H 阻塞
  t=0.010 ms   此刻 CPU 上跑的是谁？是 M（优先级 8）。
               L 优先级 2，抢不过 M，所以【L 拿不到 CPU，也就没法释放锁】
  t=5.010 ms   M 终于跑完那 5 ms 的计算
  t=5.010 ms   L 重新拿到 CPU，把临界区剩下的一点跑完
  t=5.040 ms   L 释放锁 → H 被唤醒 → H 开始跑

【H 的等待时间】
    等待 = M 的执行时间 + L 临界区的剩余部分
         = 5.000 ms + 0.030 ms = 5.030 ms
    ★ 注意这 5 ms 跟 H 要保护的资源【毫无关系】——H 是被一个
      与它毫无关系的中等优先级任务拖住的

【如果有优先级继承（互斥量）】
    t=0.010 ms  H 阻塞在锁上 → 内核把【锁的持有者 L】的优先级临时提升到 10
    t=0.010 ms  现在 L 优先级 10 > M 的 8 → L 立刻抢占 M，继续跑临界区
    t=0.040 ms  L 跑完临界区，释放锁 → 优先级恢复为 2 → H 被唤醒
    t=0.040 ms  H 开始跑

【H 的等待时间】
    等待 = L 临界区的剩余部分 = 0.030 ms
    ★ 与 M 完全无关了

【两者对比】
    无优先级继承：5.030 ms
    有优先级继承：0.030 ms（临界区本身的长度，这是无法避免的下限）
    比值 = 5.030 ÷ 0.030 ≈ 168 倍

    换个说法：H 的响应延迟从 30 微秒变成了 5 毫秒。
    如果你的 H 是一个 1 kHz 的控制环（周期 1 ms），它【根本跑不起来】——
    每轮都要等 5 ms 以上，系统表现为彻底失控。
推论：临界区越短，反转的代价越小

上面这个算例给出的 0.030 ms 是理论上无法消除的下限—— 只要有人持锁，别人就得等。所以真正能做的两件事是：

  • 用互斥量而不是二值信号量来保护共享资源，拿到优先级继承这个保险。 第 41 篇展开。
  • 把临界区缩到极限：临界区里只做「读改写一个变量」， 绝不放 printf、不做除法、不调外设、不申请内存。 上面 L 的临界区是 30 μs，如果你在里面加一句串口打印，它就会变成 1~3 ms， 那时候就算有优先级继承，H 的最坏等待也变成了毫秒级。

这个「临界区里能放什么」的纪律，和第二节 2.4 节讲的 portENTER_CRITICAL 的范围纪律是同一条，只不过一个管的是「关中断太久会触发 Interrupt WDT」， 另一个管的是「别人等锁等太久」。

例 5：双核钉核，到底能提升多少

已知： 一个应用有两个计算型任务，周期都是 20 ms： 任务 A 每轮需要 6 ms CPU（占 30%），任务 B 每轮需要 8 ms CPU（占 40%）。 另外 WiFi 协议栈在 CPU0 上大约占 10~15%。 

【方案一：两颗核的任务都钉在 CPU0（或者干脆不钉，交给调度器碰运气）】

    CPU0 负载 = A(30%) + B(40%) + WiFi(12%) = 82%
    CPU1 负载 = 只有空闲任务                                    = 约 0%
    余量      = 100% − 82% = 18%

    ★ 问题不在「82% 能不能跑」，而在于【剩下的 18% 是碎成一片一片的】：
      A 要 6 ms 连续 CPU，B 要 8 ms 连续 CPU，WiFi 又要随时插进来。
      一旦三个需求在同 20 ms 窗口里叠在一起，就会出现
      「本核上一个任务都跑不完」的时刻 → 周期抖动、看门狗风险上升。
      而且空闲任务只剩 18%，TWDT 的余量变得很薄。

【方案二：A 钉 CPU0，B 钉 CPU1（各自和 WiFi 分开）】

    CPU0 负载 = A(30%) + WiFi(12%) = 42%      余量 58%
    CPU1 负载 = B(40%)             = 40%      余量 60%
    ★ 两个核的余量都回到了 55% 以上，两个任务各自独占一颗核的「主时段」，
      相互之间不再争抢。WiFi 只影响 A，不影响 B。

【方案三：两个计算任务都钉 CPU1，CPU0 留给 WiFi 和应用逻辑】

    CPU0 负载 = WiFi(12%) + 应用逻辑            余量很大
    CPU1 负载 = A(30%) + B(40%) = 70%          余量 30%
    ★ 这个方案看起来「把计算集中到一颗核」有点浪费，但对
      「WiFi 必须绝对稳定、计算可以慢一点但要准时」的产品是合适的：
      它把【抖动源和计算源物理隔离】了。

【理论加速比与实际加速比】

    把一个总工作量为 W 的计算切成两半、两颗核并行：
    理论时间 = W ÷ 2，理想加速比 = 2.0

    但两颗核共享 SRAM 与总线、共享缓存/PSRAM 控制器：
    实测加速比通常在【1.6 ~ 1.8】之间（取中值 1.7）

    例：一个需要 1000 ms 的批量数据处理
      单核        = 1000 ms
      双核（理想）= 1000 ÷ 2   = 500 ms
      双核（实测）= 1000 ÷ 1.7 ≈ 588 ms      ← 比理想慢 18%，但仍然接近翻倍

    ★ 所以「分核跑」对【计算密集】的任务是实打实的收益；
      对【大部分时间在阻塞等待】的任务（读传感器、等网络），收益接近 0 ——
      因为阻塞的任务本来就不占 CPU，分到哪颗核都一样。

【真正买到的不是性能，是可预测性】
    例：某任务的周期抖动（jitter）
      挤在一颗核上（方案一，负载 82%）：抖动可达 2 ~ 5 ms
      分开钉核（方案二，负载 42%）：抖动通常在 100 μs 量级
    提升的是【最坏情况】，而不是【平均情况】—— 而实时系统的质量
    恰恰由最坏情况定义。
指标方案一（都挤 CPU0）方案二（A→CPU0，B→CPU1）
CPU0 负载82%42%
CPU1 负载≈ 0%40%
空闲任务余量（喂狗余量）18%，很薄58% / 60%，健康
周期抖动2 ~ 5 ms 量级100 μs 量级

钉核的两条纪律

① 不要为了「看起来更专业」而到处钉核。 钉核的代价是「负载不能再自动均衡」：如果哪天 A 的负载涨到 90%， 你钉死了它就只能在 90% 上硬扛，而另一颗核闲着。 规则：先用不钉核的写法跑起来，测量之后发现确实需要可预测性，再钉。

② 钉核之前先确认 WiFi 在哪颗核上。 默认配置下 WiFi 任务（优先级 23）和 tcpip 任务（18）都在 CPU0—— 也就是说 CPU0 天生就比 CPU1 忙。 如果你的应用逻辑很在意时序稳定，把它钉到 CPU1 通常比钉到 CPU0 更好， 尽管 CPU0 是「主核」这个名字听起来更正式。 用 xPortGetCoreID() 打印出来确认，别靠猜。

例 6：看门狗预算——一个任务最长能「不放手」多久

已知： 默认配置 CONFIG_ESP_TASK_WDT_TIMEOUT_S = 5（5 秒）。 你的 sensor 任务订阅了 TWDT，需要在主循环末尾喂狗。 这个任务每轮要干三件事：读 I2C（1 ms 阻塞）、做一次数值滤波（不定长，最坏 200 ms）、 写 Flash 保存（不定长，最坏 1.8 s）。 

【第一步：算出「一轮最坏耗时」】
    读 I2C                     1 ms（这是阻塞的，不占 CPU，但仍然算在「一轮」里）
    数值滤波（最坏）          200 ms
    写 Flash（最坏）         1800 ms
    ────────────────────────────────
    一轮最坏耗时             ≈ 2001 ms ≈ 2.0 s

【第二步：这个 2.0 s 能不能放进 5 s 的超时窗口？】
    余量 = 5000 − 2001 = 2999 ms
    余量比例 = 2999 ÷ 5000 ≈ 60%          ← 可以，但只剩 60%

    ★ 注意这里还没有考虑：
      - 别的任务把你的任务抢占掉的时间
      - Flash 写入在 WiFi 同时工作时变慢（擦除/写入会被总线仲裁拉长）
      - 某个中断风暴短时间占住 CPU
      工程上要给这些留一倍余量，所以实际可用预算 ≈ 5000 × 0.5 = 2500 ms
      结论：2.0 s 的最坏耗时【贴着上限】，需要拆分

【第三步：把长任务拆段 + 段间喂狗】

    把 Flash 写入按 512 字节一页拆成 4 段：
      每段最坏 = 1800 ÷ 4 = 450 ms
      段间喂狗 → 单次最长不喂狗时间 = max(滤波 200 ms, 单段 450 ms) = 450 ms
      加上 I2C 1 ms 与其它固定开销，最坏「不喂狗间隔」≈ 460 ms

    新余量 = 5000 − 460 = 4540 ms        余量比例 ≈ 91%
    ★ 这才是可以交付的状态：即使 Flash 慢一倍（900 ms/段），也还在窗口内

【第四步：喂狗周期该取多少？（自查纪律）】

    经验规则：喂狗周期 ≤ 超时时间 ÷ 3
    5000 ÷ 3 ≈ 1667 ms
    取一个「好看的数」：1000 ms 或 500 ms
    正常情况下一轮 2.0 s > 1000 ms 的目标周期 —— 说明【正常路径就会超期】，
    这本身就是个信号：任务设计得太重，应该拆任务或者拆段。
    ★ 这条规则的作用是让「正常」和「异常」之间留出两个周期的缓冲，
      避免因为一次瞬时抖动就误触发复位。

【第五步：反向估算「这颗核能容忍多长的独占」】

    空闲任务也在名单上，它需要定期跑到才能喂狗。
    如果某个任务连续独占 CPU 达 T 秒，本核空闲任务就 T 秒没跑。
    要求 T < 5000 ms（超时）− 余量
    取一半余量：T_max ≈ 2500 ms
    ★ 也就是说：任何一个任务，连续不阻塞地跑【不能超过约 2.5 秒】。
      超过这个数，看门狗就会把整片芯片复位，日志里点名 IDLE0/IDLE1，
      而真凶是 Tasks currently running 里那个任务。

三个可以直接抄走的数

① 喂狗周期 = 超时 ÷ 3，且取整到 1000 ms 或 500 ms。 默认 5 s 超时下就是 1 s（或更保守的 500 ms）。 ② 单个任务连续不阻塞的上限 ≈ 超时 ÷ 2，默认配置下约 2.5 s。 超过就拆段、或者拆成两个任务。 ③ 一轮的最坏耗时应该 < 超时的 50%。 剩下的 50% 是留给「别的任务抢占、中断风暴、Flash 变慢」的。

反过来说：如果你的某个任务一轮就是需要 4 秒（比如一次大批量 Flash 写入）， 正确做法不是把看门狗超时调到 30 秒——那等于把整机的保护关掉； 而是拆段喂狗，或者把这件事移出这个任务。 看门狗超时值是一个「整机健康度」参数，不该为了一个任务的特例去动它。

在单片机上的样子：默认任务地图与四个完整程序

这一节全部是可编译、可上板的完整程序。但在写代码之前，先看一眼 一块刚烧好出厂固件的 ESP32 上已经跑着哪些任务—— 这件事决定了你的代码是在什么环境里被调度的，也决定了你该给 CPU 留多少余量。

4.1 平台地图：一块 ESP32 开机后有哪些任务

│ esp_timer          22     3584     esp_timer 的高精度定时服务任务                   │

│ ★ 这也是为什么「不钉核时任务默认落在 CPU0」常常让 WiFi 变得不稳 —— 它在跟你的任务抢  │
└────────────────────────────────────────────────────────────────────────────────────┘

┌───────────────────────────── CPU1（APP_CPU，应用核）─────────────────────────────┐
│ IDLE1              0     约 1536    空闲任务（默认订阅 TWDT）                       │
│ ipc1               24     约 1024    核间通信任务                                   │
│ （没有别的了 —— 除非你自己往上放东西，或者用 xTaskCreatePinnedToCore 指定）         │
└────────────────────────────────────────────────────────────────────────────────────┘

【要点】
  ① 你写的任务默认会落在 CPU0（xTaskCreate 的行为），而 CPU0 本来就是两颗核里更忙的
  ② 空闲任务的优先级是 0，但它【必须在 5 秒内跑到】，否则 TWDT 复位（第 2.7 节）
  ③ 优先级 24 被 ipc0/ipc1 占着，所以你的任务优先级【最高只能取 23】
     实际工程里给自己的任务取 5 ~ 15 就够了，取太高会和 WiFi 打架
  ④ 上面所有「约」都是典型值：具体数值取决于 menuconfig 和 IDF 版本，
     用 vTaskList() 打印出来看才是你的板子的真相（4.5 节）

4.2 程序一：两个闪烁任务——最小可用骨架

这是每个 RTOS 项目的起点，也是最值得反复看的一段代码： 它把「任务怎么创建、周期怎么固定、参数怎么传、任务怎么结束」四件事全用上了， 总共不到 60 行。 

/* =========================================================================
 * 程序一：两个闪烁任务
 * 平台  : ESP32 / ESP-IDF v5.x
 * 硬件  : GPIO2 与 GPIO4 各接一颗 LED + 限流电阻（共阴极接法，高电平点亮）
 * 目标  : 展示任务创建、参数传递、固定周期、任务自我结束
 * ========================================================================= */
#include <stdio.h>
#include <inttypes.h>            /* 提供了 PRIu32 这些格式宏 */
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"
#include "driver/gpio.h"
#include "esp_log.h"
#include "esp_system.h"          /* esp_get_free_heap_size() */

static const char *TAG = "blink";

/* 用结构体传参数：比起「传一个 int 再转型」，这样更清晰也更不容易错 */
typedef struct {
    gpio_num_t gpio;        /* 哪一颗 LED */
    uint32_t   period_ms;   /* 闪烁周期 */
    const char *name;       /* 任务名，打印用 */
} blink_cfg_t;

/* 两个配置对象必须是 static（或者全局）：
   任务函数在 app_main 返回之后仍然要访问它们，不能指向 app_main 的栈上变量 */
static const blink_cfg_t cfg_led_a = { .gpio = GPIO_NUM_2, .period_ms = 200, .name = "LED_A" };
static const blink_cfg_t cfg_led_b = { .gpio = GPIO_NUM_4, .period_ms = 700, .name = "LED_B" };

/* ---------------- 任务函数：注意签名是固定的，并且永远不要 return ---------------- */
static void blink_task(void *pvParameters)
{
    /* ① 取参数。这里传进来的指针必须在这颗任务的整个生命周期内有效 */
    const blink_cfg_t *cfg = (const blink_cfg_t *)pvParameters;

    /* ② 配置 GPIO（每个任务配置自己用的那个脚，互不干扰） */
    gpio_reset_pin(cfg->gpio);
    gpio_set_direction(cfg->gpio, GPIO_MODE_OUTPUT);

    /* ③ 记录「下一次该在什么时候醒」——【这一句必须初始化】，
          用 vTaskDelayUntil 时忘记初始化是最常见的错误，会导致第一轮被跳过 */
    TickType_t last_wake = xTaskGetTickCount();
    const TickType_t period = pdMS_TO_TICKS(cfg->period_ms);

    ESP_LOGI(TAG, "%s 启动：周期 %" PRIu32 " ms（%" PRIu32 " tick），运行在 CPU%d",
             cfg->name, cfg->period_ms, (uint32_t)period, xPortGetCoreID());

    uint32_t overrun = 0;       /* 周期守不住的次数 */

    /* ④ 任务主循环。for(;;) 是标准写法；while(1) 也行，但别写 while(true) 之外的怪东西 */
    for (;;) {
        /* 干活：翻转电平 */
        gpio_set_level(cfg->gpio, 1);
        vTaskDelay(pdMS_TO_TICKS(10));      /* 这里只是让 LED 有可见的亮/灭，不是周期 */
        gpio_set_level(cfg->gpio, 0);

        /* ⑤ 【核心】把下一次唤醒钉在 last_wake + period 这个绝对时刻上。
              返回 pdFALSE 表示这一轮执行时间已经超过了周期 —— 必须记下来 */
        if (xTaskDelayUntil(&last_wake, period) == pdFALSE) {
            overrun++;
            ESP_LOGW(TAG, "%s 周期来不及（overrun=%" PRIu32 "）", cfg->name, overrun);
        }
    }

    /* ⑥ 这一行永远不会被执行到。写在这里是为了告诉你：
          如果哪天真的要结束任务，正确写法是【先清理资源】再 vTaskDelete(NULL)。
          绝对不能 return —— 返回会触发断言并复位。 */
    /* vTaskDelete(NULL); */
}

/* ---------------------------- 程序入口 ---------------------------- */
void app_main(void)
{
    ESP_LOGI(TAG, "app_main 运行在 CPU%d，此时空闲堆 %" PRIu32 " 字节",
             xPortGetCoreID(), (uint32_t)esp_get_free_heap_size());

    TaskHandle_t h_a = NULL;
    TaskHandle_t h_b = NULL;

    /* xTaskCreate(函数, 名字, 栈大小【字节】, 参数, 优先级, 句柄地址)
       ★ 栈大小在 ESP-IDF 里是【字节】：3072 就是 3 KB，不是 12 KB */
    BaseType_t r1 = xTaskCreate(blink_task, "led_a", 3072,
                                (void *)&cfg_led_a, 5, &h_a);
    BaseType_t r2 = xTaskCreate(blink_task, "led_b", 3072,
                                (void *)&cfg_led_b, 5, &h_b);

    /* 创建失败必须处理：ESP32 上堆不够时真的会发生，静默忽略会得到
       「系统跑起来了但少了一个功能」这种最难查的现象 */
    if (r1 != pdPASS || r2 != pdPASS) {
        ESP_LOGE(TAG, "任务创建失败！剩余堆 = %" PRIu32, (uint32_t)esp_get_free_heap_size());
        /* 真实产品里这里应该进入安全状态：点亮错误灯、或者只保留最小功能 */
        return;
    }

    ESP_LOGI(TAG, "两个任务已创建，句柄 %p / %p", (void *)h_a, (void *)h_b);

    /* 句柄的用途演示：等 2 秒之后查一次 led_b 的栈水位 */
    vTaskDelay(pdMS_TO_TICKS(2000));
    if (h_b != NULL) {
        UBaseType_t hw = uxTaskGetStackHighWaterMark(h_b);
        ESP_LOGI(TAG, "led_b 的栈水位 = %" PRIu32 "（配置 3072）", (uint32_t)hw);
    }

    /* ★ app_main 返回之后会发生什么？
       内核会删除 main 任务（相当于 vTaskDelete(NULL)），它的栈由空闲任务回收。
       两个 blink 任务【继续运行】——程序不会停，芯片不会复位。
       这就是 2.1 节讲的那件事：app_main 只是一个普通任务。 */
    ESP_LOGI(TAG, "app_main 即将返回，但系统会继续运行");
}

上板后应该看到什么：两颗 LED 以 200 ms 和 700 ms 的周期独立闪烁，互不影响（注意 GPIO2 和 GPIO4 是真正并行的， 不是「轮流闪」）；串口里能看到两条启动日志、创建日志、以及 2 秒后的一行栈水位。

这段代码里有四个细节值得停下来想一下
  • 为什么配置对象要 static？如果它们是 app_main 里的局部变量， app_main 返回后那块栈就没了， 两个任务再读 cfg->gpio 就是读一段已经不属于自己的内存—— 典型的「运行几毫秒后开始乱闪」或者随机复位。
  • 为什么 last_wake 必须初始化？不初始化的话它是栈上的垃圾值， xTaskDelayUntil 会算出一个「早就过去了」的时刻， 于是第一轮立刻返回 pdFALSE 不阻塞—— 现象是「第一轮跑得飞快，日志里冒一条 overrun」。
  • 优先级为什么取 5？够用就行。取 5 意味着： 能被 WiFi（23）、tcpip（18）、esp_timer（22）抢占，但比空闲任务（0）和 main（1）高。没有理由给闪烁任务一个很高的优先级—— 优先级是给「有截止时间的事情」用的，不是给「重要的任务」用的。
  • 两个任务都用 vTaskDelay(pdMS_TO_TICKS(10)) 让 LED 亮 10 ms， 这一个延时不影响周期吗？不影响，因为周期由 xTaskDelayUntil 决定：它会把这 10 ms 从剩余延时里扣掉。 如果换成 vTaskDelay 做周期，这里就会变成 210 ms / 710 ms， 正是例 2 讲的漂移。
一个动手练习（5 分钟）

把 cfg_led_b.period_ms 改成 10 再烧一次。 观察两件事：① LED_B 是不是闪得肉眼看不见了（应该几乎全亮或者看起来半亮）； ② 串口里有没有出现 周期来不及 的警告。 然后把 xTaskDelayUntil 换成 vTaskDelay(period)，让程序跑 5 分钟， 算一算两个 LED 的相位关系漂了多少（提示：亮 10 ms + 延时，实际周期已经不是 700 ms 了）。 这个练习做完，例 2 的那张表就不再是纸上的数字了。

4.3 程序二：栈水位实测——两个任务、两种栈大小、两套测量法

这个程序做三件事：① 创建两个栈大小不同的任务， ② 每个任务既用内核的 uxTaskGetStackHighWaterMark() 量，也用它自己填魔数、 自己扫的方式量，③ 把两个数字对照打印出来—— 这样你既能亲眼看到「水位」是真的，也能一次性确认当前内核返回值的单位到底是字节还是字。 

/* =========================================================================
 * 程序二：栈水位实测
 * 平台  : ESP32 / ESP-IDF v5.x
 * 硬件  : 无外设，只看串口输出
 * 需要的菜单配置：无（uxTaskGetStackHighWaterMark 默认可用）
 * 目标  : ① 实测两个不同栈大小任务的剩余水位
 *         ② 用「自己填魔数、自己扫」的方式独立测量，并与内核结果对照
 *         ③ 由此确认 uxTaskGetStackHighWaterMark 的单位
 * ========================================================================= */
#include <stdio.h>
#include <stdint.h>
#include <inttypes.h>
#include <string.h>
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"
#include "esp_log.h"
#include "esp_system.h"

static const char *TAG = "stack";

/* ---------- 魔数与安全边界 ---------- */
#define MAGIC      0xA5A5A5A5u
/* 我们只填充到「估算栈底 + SAFE_GAP」为止。
   为什么留这个边界？因为进入任务时拿到的栈指针比真正的栈顶低了几十~一两百字节
   （内核保存的上下文 + 函数序言），用「入口指针 − 配置大小」估出来的栈底
   会比真实的栈底【更低】。如果不留边界就往那里写魔数，
   写的就是【栈外面的堆内存】——那就亲手制造了一个内存踩踏事故。 */
#define SAFE_GAP   512u

/* 每个任务的配置 */
typedef struct {
    const char *name;
    uint32_t    cfg_bytes;      /* 创建时传给 xTaskCreate 的栈大小（ESP-IDF 单位：字节） */
    uint32_t    work_depth;     /* 递归深度，用来制造不同的调用链 */
    uint32_t    window_len;     /* 局部数组长度（float），0 表示不要 */
    bool        use_printf;     /* 是否制造 printf 峰值 */
} probe_cfg_t;

/* 测量结果（每个任务一份） */
typedef struct {
    uint32_t sp_entry;      /* 任务入口处局部变量的地址，近似栈顶 */
    uint32_t fill_low;      /* 我们填充的最低地址 */
    uint32_t fill_high;     /* 我们填充的最高地址 */
    uint32_t deepest;       /* 扫描出的、被写过的最低地址 */
    uint32_t used_by_scan;  /* 由魔数扫描得到的「从入口算起用掉的字节数」 */
    UBaseType_t hw;         /* 内核给的水位返回值 */
} probe_result_t;

static probe_result_t res_small;
static probe_result_t res_big;

static const probe_cfg_t cfg_small = {
    .name = "probe_small", .cfg_bytes = 2048, .work_depth = 2,
    .window_len = 0, .use_printf = false,
};
static const probe_cfg_t cfg_big = {
    .name = "probe_big", .cfg_bytes = 4096, .work_depth = 4,
    .window_len = 128, .use_printf = true,
};

/* ---------- 制造调用深度的递归函数：每层吃掉一个 128 字节的局部数组 ---------- */
static uint32_t deep_work(uint32_t depth)
{
    uint8_t buf[128];                       /* ★ 每层 128 字节，全部吃在任务自己的栈上 */
    for (uint32_t i = 0; i < sizeof(buf); i++) {
        buf[i] = (uint8_t)(i + depth);
    }
    uint32_t sum = 0;
    for (uint32_t i = 0; i < sizeof(buf); i++) {
        sum += buf[i];
    }
    if (depth > 0) {
        sum += deep_work(depth - 1);        /* 递归：调用链越深，栈吃得越多 */
    }
    return sum;
}

/* ---------- 任务函数 ---------- */
static void probe_task(void *pvParameters)
{
    const probe_cfg_t *cfg = (const probe_cfg_t *)pvParameters;
    probe_result_t *res = (cfg == &cfg_small) ? &res_small : &res_big;

    /* ===== 第 1 步：拿到入口栈指针，算出要填充的范围 ===== */
    volatile uint32_t anchor = 0;                   /* 防止被优化掉 */
    uint32_t sp_entry = (uint32_t)(uintptr_t)&anchor;

    uint32_t fill_high = (sp_entry & ~0x7u) - 64u;   /* 入口指针下方 64 B 起（8 字节对齐） */
    uint32_t fill_low  = sp_entry - (cfg->cfg_bytes - SAFE_GAP);

    res->sp_entry  = sp_entry;
    res->fill_high = fill_high;
    res->fill_low  = fill_low;

    /* ===== 第 2 步：把这段栈填满魔数 ===== */
    for (uint32_t *p = (uint32_t *)fill_low; p < (uint32_t *)fill_high; p++) {
        *p = MAGIC;
    }

    ESP_LOGI(TAG, "%s 启动：配置栈 %" PRIu32 " B，运行在 CPU%d，填充区间 %" PRIu32 " B",
             cfg->name, cfg->cfg_bytes, xPortGetCoreID(), (fill_high - fill_low));

    /* ===== 第 3 步：跑真实负载，把栈用起来 ===== */
    uint32_t acc = 0;
    for (;;) {
        acc += deep_work(cfg->work_depth);

        if (cfg->window_len > 0) {
            /* 一个「看起来无害」的局部数组：128 个 float = 512 字节 */
            float window[128];
            for (uint32_t i = 0; i < cfg->window_len; i++) {
                window[i] = (float)i * 1.5f;
                acc += (uint32_t)window[i];
            }
            /* 把结果用掉，避免编译器把整个数组优化掉 */
            acc += (uint32_t)window[0];
        }

        if (cfg->use_printf) {
            /* ★ 故意制造 printf 峰值：带 %f 的格式化在 newlib 里非常吃栈 */
            char line[96];
            snprintf(line, sizeof(line), "acc=%" PRIu32 " avg=%.3f", acc, (double)acc / 3.0);
            printf("%s\n", line);       /* 这一句的单次栈峰值通常 1 KB 以上 */
        }

        /* ===== 第 4 步：扫描魔数，找出历史最深位置 ===== */
        uint32_t *p = (uint32_t *)fill_low;
        while (p < (uint32_t *)fill_high && *p == MAGIC) {
            p++;                                        /* 从低地址往高地址走，跳过没被碰过的魔数 */
        }
        res->deepest      = (uint32_t)(uintptr_t)p;
        res->used_by_scan = sp_entry - res->deepest;    /* 从入口指针算起，用掉了多少 */
        res->hw           = uxTaskGetStackHighWaterMark(NULL);

        /* ===== 第 5 步：打印报告（每 3 秒一次） ===== */
        uint32_t pct_scan = (uint32_t)((uint64_t)res->used_by_scan * 100u / cfg->cfg_bytes);
        ESP_LOGI(TAG,
                 "%s | 配置=%" PRIu32 "B 扫得使用=%" PRIu32 "B(%" PRIu32 "%%) "
                 "内核水位=%" PRIu32 " 推算使用=%" PRIu32 "B",
                 cfg->name, cfg->cfg_bytes, res->used_by_scan, pct_scan,
                 (uint32_t)res->hw, (uint32_t)(cfg->cfg_bytes - res->hw));

        vTaskDelay(pdMS_TO_TICKS(3000));
    }
}

/* ============================ 程序入口 ============================ */
void app_main(void)
{
    ESP_LOGI(TAG, "起始空闲堆 = %" PRIu32 " 字节", (uint32_t)esp_get_free_heap_size());

    /* 注意两个任务的栈大小不同：2048 与 4096。
       ★ 在 ESP-IDF 里这两个数字就是字节数 */
    xTaskCreate(probe_task, "probe_small", cfg_small.cfg_bytes,
                (void *)&cfg_small, 5, NULL);
    xTaskCreate(probe_task, "probe_big",   cfg_big.cfg_bytes,
                (void *)&cfg_big,   5, NULL);

    /* 5 秒后打印一次对照结论 —— 这一步才是本程序的重点 */
    vTaskDelay(pdMS_TO_TICKS(5000));

    ESP_LOGI(TAG, "---------- 单位自校准 ----------");
    ESP_LOGI(TAG, "probe_small：配置 2048 B，魔数扫描使用 %" PRIu32 " B，内核水位返回 %" PRIu32,
             res_small.used_by_scan, (uint32_t)res_small.hw);
    ESP_LOGI(TAG, "probe_big  ：配置 4096 B，魔数扫描使用 %" PRIu32 " B，内核水位返回 %" PRIu32,
             res_big.used_by_scan, (uint32_t)res_big.hw);
    ESP_LOGI(TAG, "判断方法：把「配置大小 − 内核水位」和「魔数扫描结果」比一比——");
    ESP_LOGI(TAG, "  两者接近        → 内核按【字节】返回（ESP-IDF 的行为）");
    ESP_LOGI(TAG, "  后者约为前者 4 倍 → 内核按【字】返回（vanilla FreeRTOS 的行为）");

    /* 顺便看一眼堆：每创建一个任务都会从堆里拿走「栈 + TCB」 */
    ESP_LOGI(TAG, "此时空闲堆 = %" PRIu32 " 字节，历史最低 = %" PRIu32 " 字节",
             (uint32_t)esp_get_free_heap_size(),
             (uint32_t)esp_get_minimum_free_heap_size());
    ESP_LOGI(TAG, "app_main 返回，两个探测任务继续运行（每 3 秒一条报告）");
}

     → 说明这一版 IDF 的水位函数【按字节】返回。结论确认。
  ② probe_big  使用 1490 B，其中约 1000 B 来自那一句带 %f 的 printf：

     ★ 这就是 2.6 节说的「printf 单次能吃 1 KB」的现场证据。

  ④ 两个任务都在 CPU0：xTaskCreate 默认落 CPU0。
关于这个程序的三点诚实说明
  • 魔数扫描的精度是「几十~一两百字节」级别，不是逐字节精确。 误差来自两处：进入任务时的栈指针已经比真正的栈顶低了一段（漏算了函数序言那部分）， 以及我们为了安全留出的 SAFE_GAP 512 字节。 它的价值在于独立复现内核的结论，而不是比内核更准。
  • 填充范围故意不覆盖整个栈。这是刻意的安全设计：宁可少测一点， 也绝不能让「测量代码」自己变成内存踩踏的原因。 真实工程里想做到精确的逐字节扫描，正确做法是用 xTaskCreateStatic() 自己提供栈数组—— 那时候栈的首尾地址你都清楚，扫描就没有任何盲区。 但静态创建的栈深度参数单位在各版本里的写法需要你自己对一遍文档， 所以本篇的例程统一用动态创建，避免踩这个坑。
  • 水位只减不增，所以要「跑够了再读」。程序里每 3 秒打印一次， 你会发现前几次的数字在缓慢下降（因为不同的代码路径陆续被走到）， 之后就稳定了。稳定的那个数字才是你要拿去做决策的数字。
把这个程序改造成你自己的「栈体检」

把 cfg_big 的 window_len 从 128 一路调大（128 → 160 → 200 → 256），每次烧写看水位： 在 window_len = 256（1 KB 数组）时， 4096 字节的栈会开始报出「使用 2500 B 左右」——余量掉到 40% 以下。 再往上调就能亲眼看到 ***ERROR*** A stack overflow in task probe_big has been detected. 然后芯片复位。

「在哪里翻车」比「会不会翻车」重要得多—— 亲手把一块板子推到栈溢出，你就永久性地记住了这件事的边界在哪里。 顺便注意：栈溢出之后你还能看到复位原因，用 2.7 节的 esp_reset_reason() 把它打印出来做确认。

4.4 程序三：亲手把看门狗踩响，再把它修好

看门狗这件事，读十遍不如被复位一次。这个程序默认写在「故障复现」模式下—— 烧进去以后它会稳定地重启，日志里留下完整的证据链。然后你把开头的一个宏改成 1， 同样的负载就不再触发了。整个过程你能学到：故障长什么样、日志怎么读、 修法为什么有效。 

/* =========================================================================
 * 程序三：任务看门狗（TWDT）复现与修复
 * 平台  : ESP32 / ESP-IDF v5.x
 * 硬件  : 无外设，只看串口（建议同时接一颗 LED 在 GPIO2 上观察复位）
 * 需要的菜单配置：保持默认即可
 *      CONFIG_ESP_TASK_WDT_TIMEOUT_S      = 5      （超时 5 秒）
 *      CONFIG_ESP_TASK_WDT_CHECK_IDLE_TASK_CPU0/1 = 开 （空闲任务在名单上）
 * 玩法  : 先按 FIXED_MODE = 0 烧一次，看它怎么死；
 *         再把 FIXED_MODE 改成 1，看它怎么活。
 * ========================================================================= */
#include <stdio.h>
#include <inttypes.h>
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"
#include "esp_log.h"
#include "esp_system.h"
#include "esp_timer.h"
#include "esp_task_wdt.h"

#define FIXED_MODE      0       /* ★ 0 = 复现故障（会重启）；1 = 修复版 */

static const char *TAG = "wdt-demo";
static volatile uint32_t g_spin = 0;    /* 空转计数器，让编译器不能把循环优化掉 */

/* ---------- 模拟「必须连续算完的一段重活」：纯空转，期间绝不阻塞 ---------- */
static void busy_work_ms(uint32_t ms)
{
    int64_t end = esp_timer_get_time() + (int64_t)ms * 1000;   /* 微秒 */
    while (esp_timer_get_time() < end) {
        g_spin++;                       /* ★ 这一句就是「不放手」的定义：
                                           循环里没有任何阻塞调用，
                                           本核的空闲任务完全拿不到 CPU */
    }
}

/* ---------- 罪魁祸首：一个长时间霸占 CPU 的任务 ---------- */
static void heavy_task(void *pvParameters)
{
#if FIXED_MODE
    /* 修复版第 1 步：把自己也纳入看门狗监视。
       注意——这一句不是修复的关键（空闲任务本来就在名单上），
       它的作用是【顺便把这个任务也保护起来】。
       esp_task_wdt_add(NULL) 里的 NULL 表示「当前任务自己」。 */
    esp_err_t err = esp_task_wdt_add(NULL);
    if (err != ESP_OK) {
        ESP_LOGW(TAG, "订阅看门狗失败: %s", esp_err_to_name(err));
    }
#endif

    ESP_LOGI(TAG, "heavy_task 开始，运行在 CPU%d，优先级 %d",
             xPortGetCoreID(), (int)uxTaskPriorityGet(NULL));

    for (;;) {
        /* 一轮的活总共要连续算 8 秒。分成 4 段，每段 2 秒。
           8 秒 > 5 秒超时 —— 所以「不喂狗」的版本必定触发。 */
        for (int chunk = 0; chunk < 4; chunk++) {
            busy_work_ms(2000);
#if FIXED_MODE
            /* 修复版第 2 步：★ 每段结束喂一次狗 ★
               最长不喂狗的间隔 = 2 秒 < 5 秒超时 → 不会触发 */
            esp_task_wdt_reset();
            ESP_LOGI(TAG, "第 %d 段完成（%" PRIu32 " 次空转），已喂狗", chunk + 1, g_spin);
#endif
        }

        /* 一轮结束，正常歇一下。这一句让本核的空闲任务有机会运行。
           ★ 注意：这【不能】救回故障版——因为看门狗在 5 秒时就已经开枪了，
             而这里要等到第 8 秒才轮到空闲任务。 */
        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

/* ---------- 修复方案 B：把「连续不放手」改成「分段 + 阻塞」 ---------- */
/* 如果你的重活本来就可以被打断，那最干净的做法根本不是喂狗，
   而是让它【定期阻塞一下】，把 CPU 还给系统。这样连订阅都不需要。 */
static void heavy_task_blocking(void *pvParameters)
{
    ESP_LOGI(TAG, "heavy_task_blocking 开始（每 300 ms 让出一次 CPU）");
    for (;;) {
        busy_work_ms(300);                 /* 连续占用不超过 300 ms */
        vTaskDelay(1);                     /* ★ 阻塞 1 个 tick（10 ms）：
                                              空闲任务立刻得到机会喂狗 */
    }
}

/* ============================ 程序入口 ============================ */
void app_main(void)
{
    /* ★ 排查任何复位问题的第一步：问内核「我上次是怎么死的」。
       故障版重启之后，这里会打印出 ESP_RST_TASK_WDT —— 证据确凿。 */
    esp_reset_reason_t reason = esp_reset_reason();
    const char *reason_str = "未知";
    switch (reason) {
    case ESP_RST_POWERON:   reason_str = "ESP_RST_POWERON（正常上电）";          break;
    case ESP_RST_TASK_WDT:  reason_str = "★ ESP_RST_TASK_WDT（任务看门狗复位）"; break;
    case ESP_RST_INT_WDT:   reason_str = "★ ESP_RST_INT_WDT（中断看门狗复位）";  break;
    case ESP_RST_PANIC:     reason_str = "ESP_RST_PANIC（异常/断言）";           break;
    case ESP_RST_BROWNOUT:  reason_str = "ESP_RST_BROWNOUT（电压跌落）";         break;
    case ESP_RST_SW:        reason_str = "ESP_RST_SW（软件重启）";               break;
    default:                break;
    }
    ESP_LOGW(TAG, "本次启动的复位原因：%s", reason_str);
    ESP_LOGI(TAG, "空闲堆 = %" PRIu32 " 字节", (uint32_t)esp_get_free_heap_size());

#if FIXED_MODE
    ESP_LOGI(TAG, "当前是【修复版】：分段喂狗");
    xTaskCreate(heavy_task, "heavy", 3072, NULL, 5, NULL);
#else
    ESP_LOGW(TAG, "当前是【故障复现版】：任务连续 8 秒不放手，5 秒后看门狗将复位芯片");
    ESP_LOGW(TAG, "如果没有复位，请检查 CONFIG_ESP_TASK_WDT_PANIC 是否被关掉了");
    xTaskCreate(heavy_task, "heavy", 3072, NULL, 5, NULL);
#endif

    /* app_main 返回后 main 任务被删除，heavy_task 继续跑（然后触发复位） */
}

4.5 程序四：双核钉核与运行时观察

最后一个程序解决两个问题：① 确认你的任务到底跑在哪颗核上 （xPortGetCoreID()，不要靠猜）； ② 亲眼看到「两颗核是真并行」， 以及钉核前后差多少。同时把 2.7 节讲的观察工具一起用上。 

/* =========================================================================
 * 程序四：双核钉核与运行时观察
 * 平台  : ESP32 / ESP-IDF v5.x
 * 硬件  : 无外设，只看串口
 * 需要的菜单配置（要看完整任务表就得开这三项）：
 *      CONFIG_FREERTOS_USE_TRACE_FACILITY          = y   （启用 vTaskList/uxTaskGetSystemState）
 *      CONFIG_FREERTOS_VTASKLIST_INCLUDE_COREID    = y   （任务表里显示核号）
 *      CONFIG_FREERTOS_GENERATE_RUN_TIME_STATS     = y   （启用 CPU 占用统计）
 * 玩法  : 先按 PIN_BOTH_TO_CPU0 = 1 跑一次，再改成 0 跑一次，对比计数与耗时。
 * ========================================================================= */
#include <stdio.h>
#include <stdlib.h>              /* malloc / free */
#include <inttypes.h>
#include <string.h>
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"
#include "esp_log.h"
#include "esp_system.h"
#include "esp_heap_caps.h"       /* heap_caps_get_largest_free_block() */
#include "esp_timer.h"

#define PIN_BOTH_TO_CPU0    1       /* ★ 1 = 两颗任务都挤在 CPU0；0 = 一核一个 */
#define SPIN_SECONDS        3       /* 每个任务空转多少秒 */
#define REPORT_BUF_SIZE     1024    /* vTaskList/vTaskGetRunTimeStats 的输出缓冲 */

static const char *TAG = "core";

/* 每个任务各写各的计数器：这样能直接看出「两个任务是不是真的同时在跑」。
   ★ 注意：这里【故意】不让两个任务写同一个变量 —— 跨任务共享数据的
     读改写不是原子操作，必须用临界区/原子操作保护，那是第 41 篇的内容。 */
static volatile uint32_t g_count_a = 0;
static volatile uint32_t g_count_b = 0;

typedef struct {
    const char *name;
    BaseType_t  core;           /* 期望钉在哪颗核 */
    volatile uint32_t *counter; /* 自己的计数器 */
} core_cfg_t;

static const core_cfg_t cfg_a = { .name = "worker_a", .core = 0, .counter = &g_count_a };
static const core_cfg_t cfg_b = { .name = "worker_b", .core = 1, .counter = &g_count_b };

/* ---------- 空转型负载：模拟「计算密集」的任务 ---------- */
static void worker_task(void *pvParameters)
{
    const core_cfg_t *cfg = (const core_cfg_t *)pvParameters;

    /* ★ 第一件事：报告自己实际跑在哪颗核上，以及内核认为自己在哪颗核上 */
    ESP_LOGI(TAG, "%s：期望钉在 CPU%d，实际 xPortGetCoreID() = %d（优先级 %d）",
             cfg->name, (int)cfg->core, (int)xPortGetCoreID(),
             (int)uxTaskPriorityGet(NULL));

    int64_t t_end = esp_timer_get_time() + (int64_t)SPIN_SECONDS * 1000000;
    uint32_t n = 0;
    while (esp_timer_get_time() < t_end) {
        n++;
        *cfg->counter = n;          /* 把进度写出去，方便外面观察 */
    }
    ESP_LOGI(TAG, "%s：%d 秒内跑了 %" PRIu32 " 次空转", cfg->name, SPIN_SECONDS, n);

    /* 演示完就睡下去，把 CPU 让出来（也让空闲任务能喂狗） */
    for (;;) {
        vTaskDelay(pdMS_TO_TICKS(5000));
    }
}

/* ---------- 打印任务表（需要 CONFIG_FREERTOS_USE_TRACE_FACILITY） ---------- */
static void dump_task_table(void)
{
    char *buf = (char *)malloc(REPORT_BUF_SIZE);
    if (buf == NULL) {
        ESP_LOGE(TAG, "分配打印缓冲失败");
        return;
    }
    ESP_LOGI(TAG, "---------- 任务表（vTaskList） ----------");
    vTaskList(buf);                 /* 列：名字/状态/优先级/剩余栈/序号/核号 */
    printf("%s\n", buf);
    free(buf);
}

/* ---------- 打印各任务的 CPU 占用（需要 GENERATE_RUN_TIME_STATS） ---------- */
static void dump_runtime_stats(void)
{
    char *buf = (char *)malloc(REPORT_BUF_SIZE);
    if (buf == NULL) {
        return;
    }
    ESP_LOGI(TAG, "---------- CPU 占用（vTaskGetRunTimeStats） ----------");
    vTaskGetRunTimeStats(buf);      /* 列：名字/累计运行时间/占比 */
    printf("%s\n", buf);
    free(buf);
}

/* ============================ 程序入口 ============================ */
void app_main(void)
{
    ESP_LOGI(TAG, "app_main 运行在 CPU%d，空闲堆 %" PRIu32 " 字节",
             xPortGetCoreID(), (uint32_t)esp_get_free_heap_size());

    int64_t t0 = esp_timer_get_time();

#if PIN_BOTH_TO_CPU0
    /* ① 两个计算任务都钉在 CPU0 —— 它们只能【轮流】用同一颗核 */
    ESP_LOGW(TAG, "模式：两颗任务都钉在 CPU0（互相争抢）");
    xTaskCreatePinnedToCore(worker_task, "worker_a", 3072, (void *)&cfg_a, 5, NULL, 0);
    xTaskCreatePinnedToCore(worker_task, "worker_b", 3072, (void *)&cfg_b, 5, NULL, 0);
#else
    /* ② 一个钉 CPU0、一个钉 CPU1 —— 它们可以【真正同时】跑 */
    ESP_LOGI(TAG, "模式：worker_a → CPU0，worker_b → CPU1（各占一核）");
    xTaskCreatePinnedToCore(worker_task, "worker_a", 3072, (void *)&cfg_a, 5, NULL, 0);
    xTaskCreatePinnedToCore(worker_task, "worker_b", 3072, (void *)&cfg_b, 5, NULL, 1);
#endif

    /* 等两个任务把 SPIN_SECONDS 秒的活干完 */
    vTaskDelay(pdMS_TO_TICKS(SPIN_SECONDS * 1000 + 500));

    int64_t elapsed_ms = (esp_timer_get_time() - t0) / 1000;
    ESP_LOGI(TAG, "两个任务合计空转次数：worker_a = %" PRIu32 "，worker_b = %" PRIu32,
             g_count_a, g_count_b);
    ESP_LOGI(TAG, "从创建到全部结束共耗时 %" PRId64 " ms", elapsed_ms);
    if (g_count_a > 0 && g_count_b > 0) {
        ESP_LOGI(TAG, "两者比值 b/a = %" PRIu32 "%%（接近 100%% 说明负载接近，"
                      "两个都远超 0 说明它们都真的跑起来了）",
                 (uint32_t)((uint64_t)g_count_b * 100u / g_count_a));
    }

    ESP_LOGI(TAG, "空闲堆 = %" PRIu32 "，历史最低 = %" PRIu32 "，最大连续块 = %" PRIu32,
             (uint32_t)esp_get_free_heap_size(),
             (uint32_t)esp_get_minimum_free_heap_size(),
             (uint32_t)heap_caps_get_largest_free_block(MALLOC_CAP_8BIT));

    dump_task_table();
    dump_runtime_stats();
    /* ★ vTaskGetRunTimeStats 的占用率看的是【从开机到现在】的累计值，
       所以要等系统跑一会儿再看才有意义（这里已经跑了 3.5 秒以上）。 */
}

常见误解与坑

下面十条，全部是「听起来很对」的说法。每一条都按「错误认知 → 为什么错 → 正确做法」拆开讲， 你可以拿它们去对照自己手上的工程。

误解 1：「第三个参数是栈大小，给 2048 就是 2048 字节。」

为什么错：这个参数叫 usStackDepth， 它的单位取决于移植层，不是标准规定的。vanilla FreeRTOS 和绝大多数 MCU 移植 （包括 STM32 上常见的那些）里，它按字计数，StackType_t 在 32 位机上是 4 字节， 所以「2048」实际是 8 KB。ESP-IDF 是官方明说的有意例外——它按字节计数。 两边都有人写代码，于是同一个数字在两块板子上差了四倍。

正确做法：写代码时永远用注释标明单位， 例如 xTaskCreate(..., 3072, ...) /* 3072 字节，ESP-IDF 按字节 */； 换平台移植时把这个参数当成必须重新核对的项，而不是复制粘贴。 另外用第 4 节程序二里的方法做一次单位自校准： 把「配置值」和 uxTaskGetStackHighWaterMark() 的返回值一起打印出来， 两个数字接近就说明按字节，差约四倍就说明按字。 五分钟的验证，能省掉几天的栈溢出排查。

误解 2：「app_main() 就是 main()，它 return 之后程序就结束了。」

为什么错：在 ESP-IDF 里，真正的 main() 藏在启动代码里：它创建内核对象、启动调度器；而 app_main() 只是被启动流程创建出来的一个普通任务的函数体（main 任务，栈由 CONFIG_ESP_MAIN_TASK_STACK_SIZE 决定，默认约 3584 字节，优先级 1，默认跑在 CPU0）。 它 return 的效果等同于 vTaskDelete(NULL)—— 这个任务结束了，但调度器还在跑，别的任务一个都不会停。

正确做法：把 app_main() 理解成 「系统启动好之后第一个跑起来的任务」，它只该干三件事：初始化、创建别的任务、然后优雅退出（或自己变成一个长期任务）。 这个认识还有两个立竿见影的推论：① 别在 app_main 里声明大数组—— 它吃的是那个约 3.5 KB 的 main 任务栈，不是「主栈」，写个 char buf[4096] 直接爆；② 初始化顺序要想清楚：如果 app_main 里创建了任务又立刻 return，那个任务可能还没被调度过，就赶上后面别的初始化在改它要用的资源。

误解 3：「任务函数用 while(1) 包起来就不会返回了，那我不写循环也行，函数末尾加个 return 更干净。」

为什么错：任务函数一旦返回，控制权就交回内核， 而内核从栈上取到的返回地址是垃圾值——这个任务从来没有「调用者」。 ESP-IDF 会在任务返回时直接报错： 

FreeRTOS Task "my_task" should not return, Aborting now!
abort() was called at PC 0x400d9a1b on core 0
Backtrace: 0x40088f2e:0x3ffb8a10 0x400d9a1f:0x3ffb8a30 ...

★ 这条日志是「任务函数返回」的专用指纹。看到它就往函数末尾看，
   八成是一个 if 分支里写了 return，把 while(1) 循环给逃出去了。

正确做法：把 for (;;) { ... } 当成任务函数不可省略的骨架（不要写成 while (1) 加一堆 break——那正是让循环被逃出去的经典路径）。真的要结束任务， 用明确的 vTaskDelete(NULL)，并且在它前面把资源清理干净； 绝不要用 return 或 break 离开循环。

误解 4：「死循环里加个 vTaskDelay(0) 或者 taskYIELD()，就等于让出 CPU 了。」

为什么错：这两个调用都不进入阻塞态。 它们只是把当前任务放在同优先级队列的末尾、请求一次切换， 所以只能让给「同优先级或更高优先级」的就绪任务。 空闲任务的优先级是 0，只要你的任务优先级高于 0，让出多少次都轮不到它。 于是空闲任务拿不到 CPU → 5 秒喂不上任务看门狗 → 整片芯片复位。 更阴险的是它「有时候看起来管用」：如果你的系统里恰好有另一个同优先级任务在跑， 或者循环里夹着 printf（串口驱动内部会阻塞）， 空闲任务就蹭到了一点时间，你会误以为修好了。

正确做法：让出 CPU 的唯一可靠方式是真正阻塞—— vTaskDelay(pdMS_TO_TICKS(1))（至少 1 个 tick）或阻塞在队列/信号量上。 判断标准很简单：问自己「这一句执行完之后，空闲任务能不能跑到」； 更工程化的答案是直接去看 vTaskGetRunTimeStats() 的输出， 看 IDLE0 / IDLE1 的占比是不是接近 0。

误解 5：「周期任务用 vTaskDelay(10) 就是每 10 ms 跑一次。」

为什么错：vTaskDelay 是相对延时， 它的语义是「从现在起，别叫我这么多 tick」。 于是每一轮的周期变成了「执行时间 + 延时」——你的任务干了 1.3 ms， 实际周期就是 11.3 ms，而且每一轮的误差都会累加到下一轮上。 1000 轮之后偏差 1.3 秒；按秒平均的日误差可以到小时级。 反过来，如果偶尔有一轮执行时间变长，它只会把那一轮拉长，不会「补回来」。

正确做法：要固定周期就用 xTaskDelayUntil(&last_wake, period)， 它把唤醒时刻锁在 last_wake + period 这个 tick 网格上， 自动把执行时间从延时里扣掉。两个配套要求不能忘： last_wake 必须在进入循环前用 xTaskGetTickCount() 初始化（否则第一轮的基准是 0， 如果系统已经跑了很久，第一次调用会立刻返回，你会在启动瞬间看到一阵爆发）； 以及检查它的返回值——返回 pdFALSE 说明 本轮的执行时间已经超过周期了，这是一个必须被记录的故障信号， 不是可以忽略的小事。

误解 6：「我要 5 ms 延时，写 pdMS_TO_TICKS(5) 就行。」

为什么错：pdMS_TO_TICKS 只是一个整数除法：ms * configTICK_RATE_HZ / 1000。 默认 100 Hz 下 1 tick = 10 ms，所以 pdMS_TO_TICKS(5) = 0， 而 vTaskDelay(0) 不阻塞—— 你的「延时 5 ms」变成了忙等。同理 pdMS_TO_TICKS(25) = 2 tick = 20 ms， 整整少 20%（见例 1 的五方案对比）。「写了延时 CPU 却还是 100%」 这条现象的根源几乎都在这里。

正确做法：三种选择，按情况挑： ① 需要毫秒级精度就把 configTICK_RATE_HZ 提到 1000 （代价见例 1 的权衡分析：tick 中断更频繁，唤醒精度换 CPU 开销）； ② 需要微秒级就用 esp_timer/硬件定时器， 不要试图靠 tick 达成微秒级时序； ③ 在代码里对截断做一次显式检查—— 至少要保证 pdMS_TO_TICKS(x) 的结果不为 0， 或者干脆写 vTaskDelay(1) 并注释「至少让出 1 tick」。

误解 7：「优先级数字越小越高，0 是最高优先级——STM32 的 NVIC 就是这么定的，FreeRTOS 也一样。」

为什么错：方向正好相反。FreeRTOS 里 数值越大、优先级越高：configMAX_PRIORITIES 默认是 25， 合法范围 0~24，24 最高，0 留给空闲任务。 而 STM32 的 NVIC 是数字越小优先级越高（0 最高）。 于是从 STM32 裸机转过来的人容易写出两种反过来的 bug： 把最要紧的任务给了优先级 0（结果它排在最底下）； 或者把日志打印、LED 闪烁这类任务给了优先级 20+（结果它把 WiFi 任务挤得没机会跑，网络莫名其妙掉线）。

正确做法：在脑子里给每个任务定一个 「它耽误不起多少时间」的排序，而不是「它重不重要」的排序—— 按截止时间的紧迫程度排。ESP-IDF 里已有的高位优先级是 WiFi 任务 23、esp_timer 22、tcpip 18、ipc 任务 24， 所以你自己任务的务实区间是 5~15， 最要紧的那一个也不该超过 WiFi（20 以上会开始和协议栈抢 CPU）。 更根本的一条：优先级的数量应当尽量少—— 设计成「控制器 / 通信 / 后台」三档就够， 每多一个不同优先级，就多一份不该抢占却抢占了的风险。

误解 8：「我看了空闲堆还有 90 KB，创建任务失败肯定是内核有 bug。」

为什么错：esp_get_free_heap_size() 返回的是总量，而分配需要的是连续内存。 一个跑了一段时间的系统，堆会被切成很多块：总量 90 KB， 但最大连续空闲块可能只有 8 KB。这时候你要创建一个 「栈 4 KB + TCB」的任务仍然可能成功， 但你要一次申请 16 KB 的缓冲区就必然失败—— 现象就是「明明还有那么多内存，malloc 却返回 NULL」。 任务创建失败还有另外两个常见原因：WiFi 起来之后可用堆明显变小 （协议栈要吃掉几十 KB，按典型值估算 40~60 KB）， 以及刚删掉的任务栈还没被回收（要等空闲任务，见 2.8 节）。

正确做法：排查内存问题要三个数一起看： esp_get_free_heap_size()（总量）、 heap_caps_get_largest_free_block(MALLOC_CAP_DEFAULT)（最大连续块—— 这个才是能不能分配成功的决定性指标）、 esp_get_minimum_free_heap_size()（历史最低， 判断有没有缓慢泄漏）。大缓冲区一次性在启动阶段申请好、之后不再动态申请， 是嵌入式里最省心的做法；长期运行的系统里频繁 malloc/free 不同大小的块，碎片化几乎不可避免。

误解 9：「任务不要了就 vTaskDelete() 删掉，反正内存会还回来。」

为什么错：这里有两个独立的坑。 第一，删除是「摘牌」，不是「回收」：vTaskDelete 只是把任务从内核链表里摘掉，它占的栈和 TCB 要等空闲任务运行到那一刻才真正释放。 如果你的系统一直很忙、空闲任务很少跑，这块内存就一直挂着， 「用完就删、需要再建」的循环用久了堆会被慢慢吃光。 第二，也是更致命的：他杀一个任务时，它手里拿着的东西不会自动归还—— 互斥量没 Give 回去（所有等这把锁的任务永久阻塞）、 malloc 的缓冲区没释放、外设停在半个事务中间、 别人的指针悬空。如果被删的任务订阅过任务看门狗而你没有把它摘出名单， 5 秒后 TWDT 会因为「这个任务没喂狗」而复位整片芯片—— 你会收到一个看起来毫不相干的复位。

正确做法：优先让任务自己结束自己： 给他发一个事件（事件组 / 任务通知 / 队列消息），它从阻塞中被唤醒， 走完自己的清理流程（归还锁、释放内存、esp_task_wdt_delete(NULL)）， 最后 vTaskDelete(NULL)。 这样做的好处是清理代码写在「知道这些资源长什么样」的那个任务里， 而不是散落在杀它的那个地方。 更好的做法是根本不要删：常驻任务 + 消息驱动， 任务阻塞着的时候几乎不占 CPU，创建/删除反而是最贵、最容易出错的操作。

误解 10：「在中断里也能调用 vTaskDelay、xQueueSend、printf，反正都是 C 函数。」

为什么错：三条独立的原因叠在一起。 ① 阻塞类 API 不能在中断里调用：ISR 不是任务，没有 TCB、没有优先级， vTaskDelay、xQueueReceive 这类会阻塞的函数 在中断上下文里调用是未定义行为（配置了断言的内核会直接报 configASSERT 失败）。 ② 能在中断里用的函数有专门的 FromISR 版本， 它们的签名和返回值都不一样（比如 xQueueSendFromISR 多一个 pxHigherPriorityTaskWoken 参数， 用来告诉内核「唤醒了一个更高优先级的任务，中断退出时记得切过去」）。 ③ 中断里打印是双重禁忌：printf 本身会吃掉 1 KB 以上的栈 （而中断借用的是被中断任务那点已经压得很紧的栈）， 而且串口输出是慢速阻塞操作，在中断里做它会让关闭中断的时间长到 触发中断看门狗（300 ms 超时）。

正确做法：中断服务程序里只做三件事： 读走数据、置标志、通知任务，然后立刻返回。 用 FromISR 系列 API，配上 portYIELD_FROM_ISR()； 需要「打印」的内容交给任务去做（ISR 推一条消息进队列，任务收到后打印）。 排查时如果看到 Interrupt wdt timeout on CPU0/CPU1， 第一个要查的就是「临界区有多长」和「中断里干了什么耗时的事」—— 这两者加上「在中断里等外设标志」构成了中断看门狗超时的全部常见原因。

小结与自检

把这一篇的结论收成十句话，再给你六道自测题和五项练习。 如果你能不看正文把它们答出来，那么「决定用 RTOS 之后的第一个月」要踩的坑，你已经提前绕过了大半。

要点清单

  • app_main 不是 main：ESP-IDF 真正的 main 负责创建内核对象、启动调度器；app_main 是启动流程创建出来的 main 任务的函数体（栈由 CONFIG_ESP_MAIN_TASK_STACK_SIZE 决定， 默认约 3584 字节，优先级 1，默认在 CPU0）。它 return 只是这个任务结束了， 系统照常运行。
  • 启动链：ROM 一级引导 → 二级引导 → call_start_cpu0 → esp_startup_start_app （创建 main 任务）→ vTaskStartScheduler()。
  • 任务函数的铁律：签名固定为 void task(void *pvParameters)， 绝对不能返回——返回会触发 FreeRTOS Task "xxx" should not return, Aborting now!。 要结束自己就用 vTaskDelete(NULL)。
  • 栈深度单位是头号误解：vanilla FreeRTOS 按字， ESP-IDF 按字节（官方有意改动）。uxTaskGetStackHighWaterMark() 的返回值也遵循同样的差异。不要背，要自校准：把配置值和水位返回值一起打印出来对照。
  • 优先级方向与 NVIC 相反：FreeRTOS 里 数值越大优先级越高（0~24，0 给空闲任务，24 最高）。WiFi 是 23、esp_timer 22、tcpip 18、 ipc 任务 24，所以自己的任务取 5~15 最务实。
  • 调度规则：抢占式（高优先级就绪立刻抢占）+ 只有同优先级之间才按时间片轮转（默认 1 tick）。vTaskDelay 是「睡多久」的相对延时，xTaskDelayUntil 才是固定周期； pdMS_TO_TICKS 会向下取整，小于 1 tick 直接变成 0， 而 vTaskDelay(0) 不阻塞。
  • 栈要按四块估、按水位实测：局部变量 + 调用深度 + printf 峰值（单次可达 1 KB 以上）+ 中断借用。 用 uxTaskGetStackHighWaterMark() 实测， 剩余 ≥ 30% 才算安全；测的时候要让系统跑过所有最坏分支。
  • TWDT 是一票否决的名单制：名单上任何一个任务 超过 CONFIG_ESP_TASK_WDT_TIMEOUT_S（默认 5 秒）没喂狗， 整片芯片就复位。两个空闲任务默认在名单上，所以 「霸占 CPU 不让出」的代价是整机重启—— 日志里 Tasks currently running 那两行才是真凶， 「谁没喂狗」只是受害者。
  • 两只狗要分清：Task WDT（默认 5 s，复位原因 ESP_RST_TASK_WDT，查「任务有没有按时报到」）与 Interrupt WDT（默认 300 ms，复位原因 ESP_RST_INT_WDT， 查「中断有没有被关闭太久」）。找错狗就会朝错误的方向改代码。
  • 删除只是摘牌、回收靠空闲任务： 他杀一个任务前必须确认它不再持有互斥量、动态内存、外设和看门狗订阅， 否则会留下永久阻塞的锁、泄漏的内存，以及 5 秒后一次莫名其妙的复位。 更好的设计是常驻任务 + 消息驱动，而不是「按需创建、用完就删」。

自测题（先自己想，再点开对答案）

第 1 题 · 你要一个 25 ms 的采样周期，在默认的 100 Hz tick 下应该怎么写？

板子是默认配置（configTICK_RATE_HZ = 100）， 你写了 vTaskDelay(pdMS_TO_TICKS(25))。请说出实际周期是多少、误差多少， 并给出两条改进路线。

答案 · 1 tick = 10 ms， pdMS_TO_TICKS(25) = 25 × 100 / 1000 = 2.5 → 取整为 2 tick = 20 ms，比目标短 5 ms，误差 20%。 两条路线：① 把 configTICK_RATE_HZ 改成 1000， 1 tick = 1 ms，pdMS_TO_TICKS(25) = 25 tick， 误差降到 0（代价是 tick 中断频率提高 10 倍，多了一点 CPU 开销和功耗）；② 保持 100 Hz， 接受 20 ms 或改成 30 ms 的周期，并且用 xTaskDelayUntil 而不是 vTaskDelay，让周期不随执行时间漂移。 顺带记住第三条：只要需要小于 10 ms 的延时，100 Hz 就一定不够—— pdMS_TO_TICKS(5) 会算成 0。

第 2 题 · 「每轮执行 1.3 ms，然后 vTaskDelay(10)」，1000 轮之后偏差多少？

算出实际轮周期、1000 轮累计偏差和相对误差，并说明为什么会这样。

答案 · 实际轮周期 = 执行时间 + 延时 = 1.3 + 10 = 11.3 ms（vTaskDelay 是相对延时， 它从「调用这一刻」开始数，所以执行时间白加）。 1000 轮 = 11 300 ms = 11.3 s，而期望是 10 000 ms， 累计偏差 1.3 s，相对误差 13%。按这个速率外推： 一小时差 4.68 s，一天差 112 s 以上（近 2 分钟）； 如果这是个按秒累计的计时功能，误差会一直线性增长。 换成 xTaskDelayUntil(&last_wake, pdMS_TO_TICKS(10)) 之后， 内核会把唤醒时刻锁在 tick 网格上，执行时间被自动从延时里扣掉， 偏差不再累加（单轮抖动由执行时间决定，长期平均周期准确）。

第 3 题 · 一个任务的栈报了 3072，水位函数返回 700。这说明什么？

在 ESP-IDF 里创建任务时栈参数写 3072， 后来 uxTaskGetStackHighWaterMark() 返回 700。 请判断：还剩多少、够不够、以及这个 700 是字节还是字？

答案 · 先做单位自校准： 把「配置值 3072」和「返回值 700」对照。如果 700 是字节， 剩余比例 = 700/3072 ≈ 22.8%，落在 10%~30% 的危险区， 必须加大栈（至少翻倍到 6144）或者减少局部变量/去掉打印后重测。 如果 700 是字，那实际剩余 2800 字节，比例 91%—— 但这对一个 3072 字节的任务来说意味着「几乎没用到栈」， 结合「任务里有没有局部数组和 printf」就能判断哪个解释更合理。 判断方法：ESP-IDF 按字节返回，所以大概率是 22.8% 的危险情况； 但要记住「水位是历史最小值」，它只减不增—— 现在的 700 不代表以后还是 700，只要你往这个任务里加一句 printf（可能一次吃掉 1 KB 以上），它立刻就会变成负数（也就是溢出）。

第 4 题 · 板子每 5 秒重启一次，日志里该找哪几行？

串口上看到 task_wdt: Task watchdog got triggered.， 接下来你要怎么定位「是谁干的」？如果换成 Interrupt wdt timeout on CPU1， 查法有什么不同？

答案 · Task WDT 的日志里要点名两处： ① 「The following tasks did not reset the watchdog in time」下面列的任务—— 通常就是 IDLE0 / IDLE1 （它们是受害者）；② 「Tasks currently running」下面两行—— CPU 0: xxx / CPU 1: xxx 才是当时霸占 CPU 的真凶。找到那个任务，检查它是不是有「不阻塞的长循环」， 改成阻塞或拆段 + 段间喂狗。再看一眼复位原因： ESP_RST_TASK_WDT 确认是任务看门狗， 超时时间由 CONFIG_ESP_TASK_WDT_TIMEOUT_S（默认 5 s）决定。 换成 Interrupt WDT 就完全不同了：那个默认只有 300 ms， 查的是「中断被关闭了多久」，所以要去查临界区的长度 （portENTER_CRITICAL / taskENTER_CRITICAL 里面干了什么）、中断服务程序里有没有耗时操作（尤其是等外设标志和打印）， 复位原因是 ESP_RST_INT_WDT。

第 5 题 · 死循环里加 taskYIELD() 为什么救不了看门狗？

一个优先级 5 的任务里写了长循环，末尾加 taskYIELD()。 系统看起来稳定了。请解释为什么这不可靠，以及正确的改法。

答案 · taskYIELD() （以及 vTaskDelay(0)）都不进入阻塞态， 它们只是请求一次切换、把当前任务放到同优先级队列的尾部， 所以只能让给同优先级或更高优先级的就绪任务。 空闲任务的优先级是 0，永远轮不到它 → 它 5 秒喂不上狗 → 整机复位。 「看起来稳定」通常是因为系统里恰好有另一个同优先级任务在跑， 或者循环里夹着 printf（串口驱动内部会阻塞）蹭到了时间。 正确改法只有一条：真正进入阻塞态—— vTaskDelay(pdMS_TO_TICKS(1))（至少 1 tick）， 或者把这个任务改成阻塞在队列/信号量/任务通知上（第 41 篇）。 验收标准：跑起来之后用 vTaskGetRunTimeStats() 看 IDLE0 / IDLE1 的 CPU 占比不再是 0。

第 6 题 · 为什么 app_main 里写 char buf[4096] 会出事？

一个初学者在 app_main() 里声明了一个 4 KB 的局部数组， 编译通过，一运行就报栈溢出。请解释原因，并说出他可能误以为的三件事。

答案 · app_main 不是 main，它是一个普通任务的函数体， 它用的是那个任务的栈——由 CONFIG_ESP_MAIN_TASK_STACK_SIZE 决定， 默认约 3584 字节。声明 4096 字节的局部数组，光这一个数组就超过了整个栈， 调用还没返回就已经踩穿了。他可能误以为： ① app_main 就是 main， 用的是「主栈」（其实无所谓，主栈也不会有几 KB 富余）； ② 声明数组不占栈（如果加 static 那确实不占栈—— 这是正确的改法之一，但那是另一回事）； ③ return 之后程序就结束了（错，见第 1 条要点）。 正确做法：大缓冲区用 static、全局变量， 或者在启动时用 heap_caps_malloc 从堆里申请； 需要长期运行的工作放到自己创建的任务里，并把栈按「局部变量 + 调用深度 + printf 峰值 + 中断借用」四块算够。

练习（动手才算学过）

  1. 把程序一跑起来，然后制造一次超时。 先按程序一创建两个闪烁任务（周期 500 ms / 200 ms，用 xTaskDelayUntil），确认两个灯互不干扰地闪。 然后把其中一个任务的 xTaskDelayUntil 临时删掉、 换成一个空转的 for 循环，观察串口： 记录从「开始空转」到「看门狗复位」之间过了多久， 并核对日志里 Tasks currently running 显示的是哪个任务。 实验目标：把「5 秒超时」从一个数字变成一次亲身经历。
  2. 用程序二给自己的任务量一次栈水位。 挑一个你手上真实的工程任务，把它的栈临时改成 2048、4096、8192 各跑一次， 记录 uxTaskGetStackHighWaterMark() 的返回值。 验证两件事：① 返回值和「配置的栈大小」对照，确认单位是字节还是字； ② 栈加大之后水位是否同步变大（如果不变，说明这个任务根本没用多少栈， 你之前给的余量纯属浪费）。最后按 30% 判据定一个正式值并写进注释。
  3. 把一段裸机轮询代码改写成阻塞式。 找一段你写过的「while (标志位 == 0) { }」或者 HAL_Delay 轮询的代码，改成 vTaskDelay 或（更好）阻塞在队列上。 改动前后各测一次 vTaskGetRunTimeStats()， 记录那个任务和 IDLE 的 CPU 占比变化。建议至少观察到 「IDLE 占比从接近 0 变成几十个百分点」这个量级的变化。
  4. 跑一次程序四的两种模式，自己算加速比。 先 PIN_BOTH_TO_CPU0 = 1 跑一遍， 记录两个任务各写多少次循环、总计多少毫秒； 改成 0（钉到不同核）再跑一遍。 用「两次的总耗时之比」算出实测加速比， 并解释它为什么明显小于 2（提示：共享的 SRAM 和总线带宽、 以及双核抢同一份内存时的仲裁开销）。 再顺手记录两种模式下「每轮周期的抖动」， 理解为什么说钉核买的是可预测性。
  5. 给你的下一个项目写一张任务表。 在动手写代码之前，先用一张纸列出：任务名、职责、周期或触发条件、 优先级、栈大小（按四块估）、是否需要订阅看门狗、它和别的任务之间传什么数据。 把「优先级」一列特别审一遍：是不是做到了「档次尽量少」？ 有没有哪个任务给了不该给的高优先级？ 有没有哪个任务本该阻塞却在轮询？ 这张表就是下一篇（队列、信号量与互斥量）的输入—— 先想清楚谁和谁要传数据，再去选队列还是信号量。
下一篇：任务之间怎么说话

这一篇把「任务」这个主角讲完了：它怎么被创建、被调度、被阻塞、被算栈、被监视、被删除。 但到目前为止，每个任务都是一座孤岛——它们各跑各的， 我们甚至专门强调过「不要在任务之间用全局变量传数据」。

下一篇文章回答的就是这个问题：任务之间怎么安全地交换数据、怎么互相通知、怎么共享一个外设。 队列、信号量、互斥量、事件组、任务通知—— 它们各自的语义、该用哪一个、以及那个在本篇埋下伏笔的 优先级反转到底怎么用优先级继承解决（例 4 里算过的那 168 倍差距， 下一篇会给它一个正式的解法）。
