原理介绍

先给这一篇定个位置。你已经会用 51 单片机：知道 P1 = 0xFE 能让某个引脚变低，知道寄存器就是「芯片里存着的一个字节」。STM32 让人不适应的地方在于——它的手册不再提 P1 这种好记的名字，而是满篇的 0x40011000、RCC->APB2ENR、AHB、NVIC。这些词看着吓人，其实背后只有一句话：

一句话概括 STM32 的硬件结构

STM32 = 一颗 ARM 设计的内核 + ST 公司自己加的一堆外设，它们全部挂在几条总线上，每个外设的每个寄存器都占有内存地址空间里的一个位置，你写 C 代码的「赋值」，硬件上就是往那个地址写了一个数。

ARM 到底是什么公司：只卖图纸，不卖芯片

这是新手最容易误会的一点。你手里那块印着 STM32F103C8T6 的芯片，不是 ARM 公司生产的，是 ST（意法半导体）生产的。那 ARM 做了什么？

用造车打个比方：ARM 是一家只设计发动机图纸的公司，它自己不建工厂、不卖整车。它把发动机图纸授权给全世界的车厂：ST 拿去做成 STM32，NXP 拿去做成 LPC，兆易创新拿去做成 GD32，树莓派基金会拿去做成 RP2040。所以你会看到一批「内核都是 ARM、外设各不相同」的芯片，它们互相不能直接跑对方的代码，但内核那一层的规则是一样的。

理解这一点有两个实际好处：① 以后查资料时，凡是讲「中断优先级分组、SysTick、内核寄存器」的，一定在 ARM 那份文档里；凡是讲「GPIO 模式、串口波特率」的，一定在 ST 那份文档里。② 你换一颗同样是 Cortex-M3 的芯片（比如 GD32F103），内核相关的知识完全可迁移，只需重新学外设。

Cortex-M3 内核里有什么：72MHz、哈佛结构、流水线、Thumb-2

STM32F103 系列用的内核叫 Cortex-M3，最高主频 72MHz。下面四个词是手册里的高频词，逐个解释：

  • 32 位——内核一次能处理 32 个二进制位（4 字节）的数据。51 是 8 位的，一次只能处理 8 位，要算一个 32 位数得拆成 4 次，这是 STM32 快的根本原因之一。
  • 哈佛结构——指的是「指令」和「数据」走两条不同的总线，可以同时取。对比 51 那类「冯·诺依曼结构」：它取指令和读数据共用一条通道，同一时刻只能干一件事。打个比方，哈佛结构像图书馆同时开了「借书窗口」和「还书窗口」，冯·诺依曼只有一个窗口要排队。Cortex-M3 实际采用改进的哈佛结构：内核通过 I-Code 总线取指令、通过 D-Code 总线读数据，两者可并行，所以同一个时钟周期里能「一边取下一条指令、一边读操作数」。
  • 指令流水线——把「取指令 → 译码 → 执行」拆成三级流水线，像工厂流水线一样，第一条指令在执行时，第二条正在译码，第三条已经在取了。结果是绝大多数指令能做到平均每个时钟周期执行一条（接近 1 MIPS/MHz）。51 完成一条指令平均要 12 个时钟周期，这就是差距的来源。
  • Thumb-2 指令集——ARM 有两种指令编码：32 位宽的 ARM 指令和 16 位宽的 Thumb 指令。Thumb-2 把两者混在一起用：常用的简单指令编成 16 位（省 Flash 空间），复杂指令用 32 位（功能全）。你不需要手写汇编，但要知道：Keil 编译出来的机器码里，大部分指令只占 2 字节，所以 64KB Flash 能装下的代码比你想的多。
72MHz 到底比 51 的 12MHz 快多少

不能只比频率数字，要乘上「每个时钟周期能干多少活」。51（STC89C52RC，12MHz 晶振）：大多数指令要 12 个时钟周期，折合 约 1 MIPS（每秒一百万条指令）。STM32F103（72MHz，Cortex-M3）：多数指令 1 个周期，折合 约 72 MIPS。再乘上「一条指令能处理的数据宽度」——51 是 8 位、STM32 是 32 位，差了 4 倍。两个因素叠起来，做 32 位数据处理时 STM32 相对 51 有几十倍的差距，这就是为什么 51 跑不动彩屏、跑不动 FFT，而 STM32 可以。

总线矩阵：AHB、APB1、APB2 分别挂什么

「总线」这个词听起来抽象，其实它就是芯片内部的一组公共导线，相当于公司里的一条走廊，所有部门（外设）的门都开在这条走廊上，内核要跟谁打交道，就走到谁门口。芯片内部不止一条走廊，而是分了快慢两档：

总线名全称与含义F103 上的最高频率挂在上面的东西
AHBAdvanced High-performance Bus，高性能总线72 MHz内核取指、SRAM、Flash 接口、DMA、RCC 时钟控制器、复位控制器
APB2Advanced Peripheral Bus 2，高速外设总线72 MHzGPIOA~GPIOE、AFIO、EXTI、USART1、SPI1、ADC1/2、TIM1
APB1Advanced Peripheral Bus 1，低速外设总线36 MHzUSART2/3、I2C1/2、SPI2、TIM2~TIM4、看门狗、电源管理、备份寄存器、USB、CAN

为什么要分成两条 APB 而不是全挂一起？因为外设的「手速」差别很大。GPIO 要跟着内核跑，翻转越快越好；而 I2C 总线本身最高才 400kHz，看门狗更是几秒钟才动一次，把它们和 GPIO 放在同一条总线上，等于让一条走廊里既有百米冲刺的又有散步的，快的会被拖慢。分开挂，各自按需要的速度跑，同时低速那条总线可以用更低的频率工作、更省电。

这件事和后面「配时钟」直接相关

记住这张表，你就能解释后面会反复遇到的一个问题：为什么时钟树里要分别配置 AHB、APB1、APB2 三个分频器？因为它们本来就是三条独立的总线，各跑各的频率。也正因为 USART1 在 APB2（72MHz）而 USART2 在 APB1（36MHz），同样写 115200 的波特率，两个外设算出来的分频值完全不同——这就是「同一个波特率、USART1 正常而 USART2 乱码」的根源。

存储器映射：4GB 地址空间是怎么切块的（本节重点）

这一节是整篇的核心概念，看懂它，STM32 手册里那些吓人的十六进制地址就全都讲得通了。

先建立第一个认知：Cortex-M3 是 32 位内核，它能发出的地址是 32 位，也就是从 0x00000000 到 0xFFFFFFFF，一共 2³² = 4294967296 个地址，即 4GB（每 1GB = 2³⁰ 字节）。这 4GB 并不是都装了东西，ARM 在规范里把它预先划分成若干区块，规定「哪一段该放什么」。这个规定就叫存储器映射（Memory Map）。

第二个认知更关键：外设不是「另外的东西」，它就是一段地址。你在 51 上写 P1 = 0xFE;，编译器把 0x90（P1 的字节地址）翻译成一条写指令。STM32 完全一样，只是地址变成了 32 位，而「GPIOB 的输出数据寄存器」这个位置，它的地址是 0x40010C0C。你写 GPIOB->ODR = 0xFE;，编译出来的就是「往 0x40010C0C 写 0xFE」。硬件那边有一块地址解码电路盯着这个地址：发现是 0x40010C0C，就把数据送给 GPIOB 的输出锁存器。

类比：旅馆房间号

把 4GB 地址空间想成一栋巨大的旅馆，房间号从 0 编到 4294967295。ARM 规定：0 楼那一大片给「程序存储（Flash）」，2 号楼那片给「内存（SRAM）」，4 号楼那片留给「外设」。ST 拿到这个规定后，把 GPIOA 安排在 4 号楼的 0x40010800 号房间，把 RCC 安排在 0x40021000 号房间。你写 RCC->APB2ENR |= 0x10;，就是「往 0x40021018 号房间送一个值」，那个房间里住着时钟控制器，它收到后就把 GPIOC 的时钟打开了。「寄存器」= 有门牌号的房间；「外设」= 一群连着的房间。

这里出现一个必须解释的小细节：上表说 Code 区从 0x00000000 开始，但 STM32 的 Flash 明明是从 0x08000000 开始的。原因是 ST 做了地址重映射（remap）：芯片里真实的 Flash 物理地址是 0x08000000 起，但为了让复位后 CPU 从 0 地址取向量表也能取到 Flash 的内容，ST 让 0x00000000 这一段变成 Flash 的「镜像」——访问 0x00000000 实际访问的是 0x08000000。这样做的好处是：改变 BOOT 引脚，就能让 0x00000000 镜像到「系统存储器（出厂 Bootloader）」或「SRAM」，实现「不拆板子也能换启动方式」。

外设概览：STM32F103C8T6 到底有哪些资源

外设（Peripheral）指的是内核之外、ST 加在芯片里、能独立完成某件事的功能模块。它之所以叫「外」是因为它在内核外面，而不是因为它在你板子外面——它们全都长在同一颗芯片的硅片上。

每个外设都由两部分组成：一组寄存器（你写代码操作的对象，挂在总线上、有地址）和一组引脚（对外连接的物理管脚，焊在芯片边上）。比如 USART1 这个外设：内部有「数据寄存器」「波特率寄存器」「控制寄存器」，外部占用了 PA9（发送）和 PA10（接收）两个引脚。

外设它是干什么的STM32F103C8T6 上有几个常见用途
GPIO通用输入输出口，把引脚设成高电平/低电平，或读回引脚上的电平37 个可用 I/O（PA0~PA15、PB0~PB15、PC13~PC15）点灯、按键、驱动继电器、软件模拟时序
USART通用同步/异步收发器，也就是常说的「串口」3 个（USART1 在 APB2，USART2/3 在 APB1）打印调试信息、和蓝牙/WiFi 模块通信、接上位机
TIM定时器，能按精确的时间间隔做事，也能输出 PWM 波4 个（TIM1 高级定时器，TIM2/3/4 通用定时器，均为 16 位）精确定时、PWM 调光调速、输入捕获测频率
ADC模数转换器，把引脚上的电压变成一个数字2 个 12 位 ADC，共 10 个外部通道读电位器、测电池电压、接光敏电阻
I2C一种只用两根线的总线，一根数据一根时钟2 个（I2C1、I2C2）接 OLED 屏、EEPROM、温湿度传感器
SPI比 I2C 快的四线总线，一主多从2 个（SPI1 在 APB2，SPI2 在 APB1）接 TFT 彩屏、SD 卡、无线模块
DMA直接存储器访问：不经过 CPU，自己把数据从一处搬到另一处1 个控制器，7 个通道串口大批量收数据、ADC 连续采样、刷屏
USB / CANUSB 2.0 全速设备接口 / CAN 总线控制器各 1 个（两者共用同一块 512 字节缓冲 SRAM，不能同时用）做 USB 键盘、HID 设备；汽车与工业现场总线

另外还有几个「不用配置、上电就在」的：RCC（复位与时钟控制，管全芯片的时钟）、FLASH 接口（管 Flash 的读写与等待周期）、PWR（电源管理，管睡眠/停机/待机三种低功耗模式）、AFIO（复用功能与重映射，管「这个引脚到底归哪个外设用」）。

型号里的学问：C8T6 是什么意思

STM32F103C8T6 每个字段都有含义：STM32 = ST 的 32 位 MCU 系列；F = 基础型（Foundation）；103 = 具体子系列（F103 属于「增强型」，带 USB 和 CAN）；C = 引脚数 48 脚（LQFP48）；8 = Flash 容量 64KB；T = 封装 LQFP；6 = 工业级温度范围 −40℃~85℃。换一个字母含义就全变，比如 STM32F103RCT6 是 64 脚、256KB Flash，外设数量也不一样（它才有 TIM5/6/7）。所以抄例程前先对一下型号。

中断向量表与 NVIC：谁在什么情况下叫醒 CPU

中断是指：CPU 正在执行主程序，硬件突然有事要报告（比如串口收到一个字节、定时器数到了零），于是 CPU 暂停当前的工作，跳去执行一段专门的代码（叫中断服务函数），处理完再回到刚才暂停的地方继续。它解决的是「CPU 不可能一直盯着所有外设」的问题——没有中断，你就得在主循环里不停轮询，既浪费算力又容易漏掉信号。

那么 CPU 被叫醒后该跳到哪一行代码？这就需要一个地址清单：「串口1 收到数据 → 跳到地址 A；定时器2 溢出 → 跳到地址 B……」。这份清单就叫中断向量表（Vector Table）。「向量」在这里是「入口地址」的意思，不是什么数学向量。表本身是一串 4 字节的地址，从 0x00000000 开始一个挨一个排好。第 0 项是「初始栈顶地址」而不是函数地址（这是 Cortex-M 的特殊设计，下一节会讲），第 1 项是复位入口，之后依次是各种异常的入口。

谁来决定「现在能不能响应这个中断、要先响应哪一个」？答案是 NVIC（Nested Vectored Interrupt Controller，嵌套向量中断控制器）。它在内核里面，属于 ARM 提供的那部分。它管三件事：① 每个中断有一个开关（使能位）和一个优先级；② 同时来了多个中断时，优先级高的先执行；③ 高优先级中断可以「插队」打断正在执行的低优先级中断，这叫嵌套。F103 的中断优先级用 4 个二进制位表示，可以分成 0~15 共 16 个等级，数值越小优先级越高。

最后说说 SysTick：它是 NVIC 旁边的一个 24 位递减计数器，属于内核而不属于 ST，所以任何 Cortex-M 芯片上都有它，代码可移植。它的典型用法是配成「每 1 毫秒减到零 → 产生一次中断 → 中断里把一个全局变量加一」，这个全局变量就是「系统运行了多久」的计时器。HAL 库里那个 HAL_Delay(500) 就是靠它实现的：调用时记下当前计数，然后死等，直到计数增加 500 才返回。这也是为什么你没调用 HAL_Init()，HAL_Delay() 就会立刻返回、一点都不延时——计时的心跳根本没启动。

上电启动流程：从按下电源到进入 main()

按下电源键（或按复位键）之后，到你的 main() 第一行被执行，中间发生了一串固定动作。理解它，你就能明白「为什么程序必须从 Flash 启动」「为什么全局变量有初始值而局部变量没有」这些平时想不通的问题。

  ① 上电 / 复位
      │  所有寄存器恢复默认值，外设时钟全部关闭
      ▼
  ② CPU 从 0x00000000 读出第 1 个 4 字节 → 送进 SP（栈指针）
      │  注意：这一步是硬件自动做的，不执行任何指令
      │  地址 0x00000000 的内容 = Flash 0x08000000 处的内容（重映射）
      │  所以栈顶初值就是编译时算好的 __initial_sp
      ▼
  ③ CPU 从 0x00000004 读出第 2 个 4 字节 → 送进 PC（程序计数器）
      │  这个地址指向的函数就是 Reset_Handler
      │  PC 一旦被赋值，CPU 就开始取指令执行了 —— 程序活了
      ▼
  ④ 执行 Reset_Handler（在启动文件 startup_stm32f103xb.s 里）
      │  它做四件事：
      │    a. 调用 SystemInit()：配置时钟相关的基础寄存器
      │    b. 把 .data 段从 Flash 拷贝到 SRAM   ← 有初值的全局变量靠它
      │    c. 把 .bss  段在 SRAM 里全部清零     ← 没写初值的全局变量靠它
      │    d. 调用 __main（C 库的入口），它最终调用你的 main()
      ▼
  ⑤ 进入 main()
      │  此时 SRAM 已经按 C 语言规则准备就绪，栈指针指向 RAM 顶端
      ▼
  ⑥ 执行 HAL_Init() → SystemClock_Config() → MX_GPIO_Init() → while(1)
         这一步是「你的程序」，前面五步是「芯片和工具链的事」
为什么栈顶地址要放在第 0 项

51 复位后是「把 PC 设为 0，然后从 0 地址开始执行指令」，栈指针另外初始化。Cortex-M 换了个更巧的做法：反正复位后一定要从向量表取地址，那就顺手把第 0 项约定为栈顶初值——硬件读出来直接装进 SP 寄存器，连一条指令都不浪费。所以第 0 项如果被写成了某个函数地址，芯片一上电 SP 就指到一个莫名其妙的地址，第一次压栈就会进 HardFault。

再说一下 .data 和 .bss，这两个词在 Keil 的编译输出里天天出现。它们是「有初值的全局变量」和「没写初值的全局变量」两拨：

  • uint8_t flag = 5; 定义在函数外 —— 归入 .data。它的初值 5 必须存在 Flash 里（掉电不丢），但变量本体在 SRAM 里（运行时可改），所以启动时必须从 Flash 拷贝到 SRAM，这就是第 ④ 步 b 的动作。
  • uint8_t buf[128]; 定义在函数外 —— 归入 .bss。它没有初值，C 语言规定它应该是 0。如果 128 个字节的 0 都存进 Flash 太浪费，所以 Flash 里只记录「有 128 字节需要清零」，启动时在 SRAM 里清 128 个 0，这就是第 ④ 步 c。
  • 函数内部的局部变量不在 .data/.bss 里，它们在栈上，所以局部变量不会有默认的 0，初值是「上一个函数用完后留下的垃圾」。这就是为什么 HAL 的类型定义局部变量总写成 GPIO_InitTypeDef GPIO_InitStruct = {0};——手动清零。

BOOT0 / BOOT1 跳线：决定芯片从哪读程序

上一节讲的「地址重映射」就是靠这两个引脚控制的。芯片复位时会在第 ② 步之前先采样这两个引脚的电平，据此决定把 0x00000000 映射到哪块存储区：

BOOT0BOOT10x00000000 映射到结果
0任意主 Flash（0x08000000）正常运行你的程序。这是唯一正确的日常工作状态
10系统存储器（出厂 Bootloader）进 ST 出厂的串口下载程序，可以用串口烧录，但你的程序不会跑
11片内 SRAM从 RAM 启动，用于调试，掉电即失，日常不用
「程序下载成功了，但一点动静都没有」的第一嫌疑人

如果 BOOT0 的跳线帽插在 1 一侧，芯片会从系统存储器启动，去跑 ST 出厂的那个串口下载程序，你的代码根本不会被执行——下载能成功（因为下载走的是 SWD，和 BOOT 无关），但现象是全无。拿到二手板子或刚焊好的板子，第一件事就是看一眼跳线帽在哪边。

完整代码

这一节不做功能花哨的东西，只做两件「看清地基」的事：先读一段真正的启动文件（就是上一节说的 Reset_Handler 所在的地方），再写一个完全不依赖 HAL 库的纯寄存器点灯程序——用它来证明「HAL 底层干的其实就是这几行」。

启动文件里的向量表长什么样

下面这段摘自芯片包里的 startup_stm32f103xb.s（符号名都是真实的）。它是汇编文件，但你不需要会写汇编，只要看懂「前两项是什么、Reset_Handler 做了什么」就够了。

; ==================== 栈与堆的大小设置 ====================
Stack_Size      EQU     0x00000400          ; 栈 1KB（0x400 = 1024 字节）

                AREA    STACK, NOINIT, READWRITE, ALIGN=3
Stack_Mem       SPACE   Stack_Size
__initial_sp                                ; ← 这就是向量表第 0 项要用的栈顶地址

Heap_Size       EQU     0x00000200          ; 堆 512 字节（malloc 用，一般用不到）

; ==================== 中断向量表本体 ====================
                AREA    RESET, DATA, READONLY
                EXPORT  __Vectors

__Vectors       DCD     __initial_sp        ; 0x00 栈顶地址（硬件直接装进 SP）
                DCD     Reset_Handler       ; 0x04 复位入口（硬件装进 PC）
                DCD     NMI_Handler         ; 0x08 不可屏蔽中断
                DCD     HardFault_Handler   ; 0x0C 硬件错误
                DCD     MemManage_Handler   ; 0x10
                DCD     BusFault_Handler    ; 0x14
                DCD     UsageFault_Handler  ; 0x18
                DCD     0                   ; 0x1C 保留，填 0
                DCD     0                   ; 0x20 保留
                DCD     0                   ; 0x24 保留
                DCD     0                   ; 0x28 保留
                DCD     SVC_Handler         ; 0x2C
                DCD     DebugMon_Handler    ; 0x30
                DCD     0                   ; 0x34 保留
                DCD     PendSV_Handler      ; 0x38
                DCD     SysTick_Handler     ; 0x3C 系统滴答

; ---- 下面是 ST 的外设中断，按 RM0008 的顺序排列 ----
                DCD     WWDG_IRQHandler     ; 0x40
                DCD     PVD_IRQHandler      ; 0x44
                ...
                DCD     EXTI0_IRQHandler    ; 0x58
                ...
                DCD     USART1_IRQHandler   ; 0xF0
                DCD     USART2_IRQHandler   ; 0xF4

; ==================== 复位处理函数 ====================
                AREA    |.text|, CODE, READONLY
                EXPORT  Reset_Handler
Reset_Handler   PROC
                LDR     R0, =SystemInit     ; 取系统初始化函数地址
                BLX     R0                  ; 调用它（在 system_stm32f1xx.c 里）
                LDR     R0, =__main         ; 取 C 库启动代码地址
                BX      R0                  ; 跳过去，它负责拷贝 .data、清 .bss、调 main
                ENDP

; ==================== 中断的默认实现（全是死循环）====================
NMI_Handler     PROC
                EXPORT  NMI_Handler   [WEAK]
                B       .                   ; B . 就是「跳到自己」，即死循环
                ENDP

HardFault_Handler PROC
                EXPORT  HardFault_Handler [WEAK]
                B       .
                ENDP

逐行要点：

  • 第 0 项 __initial_sp——它是链接器算出来的「栈顶地址」，等于「SRAM 起始地址 + SRAM 大小」附近的一个值，对 F103C8T6 大约在 0x20005000 附近。栈是从高地址往低地址生长的，所以初值设在顶端。
  • 第 1 项 Reset_Handler——复位后 CPU 直接跳到它，它是整个程序真正意义上的「第一条指令」。
  • DCD 是汇编伪指令，意思是「在这里放一个 4 字节的值」，效果等价于 C 语言里的 uint32_t table[] = { ... }。所以别看它是汇编，本质就是一张数组。
  • [WEAK]——标记为「弱符号」。意思是：如果工程里别处（比如 stm32f1xx_it.c）也定义了一个同名的 HardFault_Handler，就用你那一个，这里的被丢弃。这保证了「你不写中断函数也能编译通过」，是 HAL 工程能开箱即用的关键机制。
  • B .——「跳转到当前地址」，也就是原地死循环。默认的中断处理函数全是这个，意思是「这个中断发生了但我没处理」，程序会停在那里等你看门狗复位或调试器介入。

纯寄存器点灯：不用 HAL 库，直接写地址

下面这份代码不使用任何 HAL 函数、不依赖 CubeMX 生成的工程结构，但用到了 CMSIS 提供的寄存器定义头文件（stm32f103xb.h，它做的事就是「把 0x40010C00 这样的地址起个名字叫 GPIOB」）。它让 PC13 上的板载 LED 闪烁。

/* ============================================================================
 * main.c —— 纯寄存器版本：完全不用 HAL 库，直接操作地址点灯
 * 芯片：STM32F103C8T6   LED：PC13（板载，低电平点亮）
 * 目的：让你看清 HAL_GPIO_WritePin() 底层到底写了哪几个寄存器
 * ============================================================================ */

#include "stm32f103xb.h"      /* CMSIS 头文件：把外设地址定义成 GPIOC、RCC 这样的名字 */

/* ---------------------------------------------------------------------------
 * 软件延时：靠空循环消耗时间。
 * 这种写法不精确（编译器优化等级一变，循环次数就变），只适合看现象，
 * 正式代码请用 HAL_Delay() 或定时器。
 * --------------------------------------------------------------------------- */
static void delay_loop(volatile uint32_t count)
{
  /* volatile 是必须的：没有它，编译器会认为这个空循环什么也没干，
     直接把它优化掉，延时就会变成 0 */
  while (count-- > 0)
  {
    __NOP();              /* 内核自带指令：空操作，占一个时钟周期 */
  }
}

int main(void)
{
  /* ---------- 第 1 步：打开 GPIOC 的时钟门 ----------
   * RCC 是「复位与时钟控制器」，地址 0x40021000。
   * APB2ENR 是它的「APB2 外设时钟使能寄存器」，偏移 0x18，所以地址是 0x40021018。
   * 第 4 位（bit4）的名字叫 IOPCEN = IO Port C ENable。
   * 复位后这一位是 0，也就是 GPIOC 没有时钟；不打开它，
   * 下面所有对 GPIOC 的写入都会被硬件丢掉，而且不会有任何报错。
   * ------------------------------------------------------------------- */
  RCC->APB2ENR |= (1UL << 4);       /* bit4 = IOPCEN，写 1 使能 GPIOC 时钟 */

  /* ---------- 第 2 步：把 PC13 配成推挽输出 ----------
   * F103 的 GPIO 用「端口配置寄存器」描述每个引脚的工作模式，
   * 每个引脚占 4 个二进制位（CNF 2 位 + MODE 2 位），16 个引脚共 64 位，
   * 一个 32 位寄存器装不下，所以拆成两个：
   *   CRL（偏移 0x00）管引脚 0~7
   *   CRH（偏移 0x04）管引脚 8~15
   * PC13 属于 8~15，所以配 CRH；它在 CRH 里的位置：
   *   引脚 13 → 第 (13-8)=5 组 → 占 bit23~bit20
   * 取值含义（MODE 高位在前）：
   *   CNF=00 且 MODE=11 → 二进制 0011 = 0x3 → 通用推挽输出，最高 50MHz
   * ------------------------------------------------------------------- */
  GPIOC->CRH &= ~(0xFUL << 20);     /* 先清掉 bit23~20 这一组（读改写） */
  GPIOC->CRH |=  (0x3UL << 20);     /* 再写入 0011：推挽输出 / 50MHz */

  /* ---------- 第 3 步：主循环里翻转 PC13 ----------
   * ODR = Output Data Register（端口输出数据寄存器），偏移 0x0C。
   * 它的 bit13 直接对应 PC13 引脚上的电平：写 1 → 3.3V，写 0 → 0V。
   * 板载 LED 是 3V3 → 电阻 → LED → PC13 的接法，
   * 所以 PC13 输出 0（低电平）时电流流过 LED，灯亮。
   * ------------------------------------------------------------------- */
  while (1)
  {
    GPIOC->ODR &= ~(1UL << 13);     /* PC13 = 0 → 灯亮 */
    delay_loop(800000);

    GPIOC->ODR |=  (1UL << 13);     /* PC13 = 1 → 灯灭 */
    delay_loop(800000);
  }
}

/* ============================================================================
 * 对比一下 HAL 是怎么写的（同一个功能，三行替一行）：
 *
 *   __HAL_RCC_GPIOC_CLK_ENABLE();                  ← 展开后就是 RCC 的 APB2ENR 置 bit4
 *   GPIO_InitStruct.Mode = GPIO_MODE_OUTPUT_PP;    ← 最后落到 GPIOC 的 CRH 的那 4 个位
 *   HAL_GPIO_Init(GPIOC, 结构体地址);               ← 把结构体里的字段翻译成 CRH 的位
 *   HAL_GPIO_WritePin(GPIOC, GPIO_PIN_13, ...);    ← 就是写 GPIOC 的 ODR 的 bit13
 *
 * 结论：HAL 库不是「另一个硬件」，它只是把上面这些位操作包装成了函数。
 *       理解寄存器，你才能在 HAL 出问题时知道该去哪里查。
 * ============================================================================ */
在 Keil 里怎么单独跑这段代码

最省事的做法是：先用 CubeMX 生成一个标准 HAL 工程（保证启动文件、头文件路径、下载算法全都配好），然后把上面这段 main.c 的 main 函数体替换掉原来的内容。注意不要连 HAL_Init() 和 SystemClock_Config() 一起删——这段代码不依赖它们也能跑（因为只用了默认的 HSI 8MHz 时钟，GPIO 在 8MHz 下照样工作），但保留它们能让你后面继续加 HAL 功能。

常见报错排查方案

下面这些故障的共同点是：它们看起来都像「芯片坏了」，其实全是概念没打通。按「现象 → 原因 → 解决」的格式写，方便你直接比对。

下载成功、Verify OK，但程序就是不跑

原因：按可能性排序——① BOOT0 跳线在 1 侧，芯片从系统存储器启动，跑的是 ST 出厂的 Bootloader，你的程序压根没被执行；② 下载完没有复位（没勾 Reset and Run），CPU 还停在旧程序里；③ 程序确实在跑，但卡在某个死循环里（比如 Error_Handler()）。

解决：① 把 BOOT0 跳线帽插到 0 侧，按一次复位键；② 在 Options for Target → Debug → Settings → Flash Download 里勾上 Reset and Run；③ 进调试按暂停，看 PC 指针停在哪个函数。

代码全对、编译零错，引脚却纹丝不动

原因：外设时钟没使能。STM32 复位后所有外设时钟默认关闭，此时对 GPIOC 寄存器的写入会被硬件静默丢弃——不报错、不产生异常，程序照常往下跑。这是 STM32 新手的第一大坑，而且它是 51 上完全不存在的概念。

解决：在配置寄存器之前先开时钟。用 HAL 就写 __HAL_RCC_GPIOC_CLK_ENABLE();，用寄存器就写 RCC->APB2ENR |= (1UL << 4);。同时记住 GPIO 在 APB2，别去开 APB1 的位。验证办法：下载后进调试，在 Watch 窗口看 RCC 的 APB2ENR 的 bit4 是不是 1。

读出来的数值明显不对（比如读 IDR 得到 0x0000FF00 这种整齐的数）

原因：指针类型不对。C 语言里指针的「加一」是按它指向的类型大小走的：uint8_t *p; p+1 走 1 字节，uint32_t *p; p+1 走 4 字节。用错类型去读寄存器，读到的就是错位的字节组合；另一种情况是把 uint32_t* 强转成 uint8_t* 后按字节读，忘了 STM32 是小端序（低字节在低地址）。

解决：操作寄存器一律用 uint32_t*，因为 Cortex-M3 的寄存器宽度就是 32 位。CMSIS 头文件已经帮你定义好了正确的类型，所以优先写 GPIOC->IDR 而不是自己强转地址。要按字节观察时，记住小端序：地址 N 放的是最低字节。

程序跑几秒就复位 / 停在 HardFault_Handler

原因：最常见的是栈太小或栈溢出。启动文件里默认 Stack_Size EQU 0x00000400 只有 1KB。如果你在函数里定义了大数组（比如 uint8_t buf[2048]; 这种局部变量），栈立刻就冲出去了。栈溢出会踩坏别的变量或访问到非法地址，触发 HardFault，默认处理函数是个死循环，看门狗一超时就复位。其次是往只读区域写数据、或者数组下标越界。

解决：① 大数组一律定义在函数外（变成 .bss 里的全局变量），不要放栈上；② 确实需要大栈就把 Stack_Size 改成 0x00000800（2KB）以上；③ 调试时在 HardFault_Handler 里打断点，看 Call Stack 窗口的上一层，故障点就在那里。

编译报错：identifier "GPIOC" is undefined

原因：没有包含芯片头文件，或者工程里没有定义正确的宏。CMSIS 头文件 stm32f103xb.h 内部是靠条件编译区分型号的——只有定义了 STM32F103xB 这个宏，它才会把 GPIOC 的定义展开出来。宏没定义时，编译器看到的就是一个陌生的名字。

解决：Options for Target → C/C++ → Define 里确认有 STM32F103xB（注意末尾的 xB，对应 64KB/128KB Flash 的中容量型号）和 USE_HAL_DRIVER；源文件顶部确认写了 #include "stm32f1xx_hal.h" 或 #include "stm32f103xb.h"。

自己写的中断函数怎么都不执行，但编译通过

原因：函数名写错了。Cortex-M 的中断入口是靠符号名在链接期与向量表挂钩的：向量表第 0xF0 项写的是 USART1_IRQHandler，链接器就会去找这个符号。你写成 USART1_IRQhandler（小写 h）、Usart1_IRQHandler、或者 USART1_Handler，链接器找不到就退回用启动文件里的弱符号（那个 B . 死循环），于是你的函数永远不会被调用，而且不报任何错。

解决：从 startup_stm32f103xb.s 里直接复制函数名，不要手打。另外确认 NVIC 里已经使能了这个中断（HAL_NVIC_EnableIRQ(USART1_IRQn)），并且用 HAL_NVIC_SetPriority() 给了它一个优先级。

另一类：程序能跑，但一加 printf 就卡死

这不是报错。原因是 printf 默认往「标准输出」写，而单片机没有操作系统，这个「标准输出」指向一个没实现的底层函数，程序会卡在那里等一个永远不会来的返回。解决：把你的串口发送函数重定向过去，实现 fputc()（Keil 下还需勾选 Use MicroLIB），或者调试时改用 SWO/ITM 输出。这属于后面串口那一篇的内容，这里先知道「卡死是重定向没做」就够了。

小结与练习

这一篇讲的是「STM32 长什么样」。它不是操作手册，而是后面每一篇的地图。真正需要刻进脑子里的只有四句话：

  • STM32 = ARM 的内核 + ST 的外设——内核的规矩查 ARM 的文档，外设的规矩查 ST 的参考手册。
  • 外设就是一串有地址的寄存器——GPIOC 是 0x40011000，GPIOC->ODR 是 0x4001100C，写它们就是写硬件。
  • 总线分三档，时钟也分三档——AHB 管内核与内存、APB2 有 GPIO 和 USART1、APB1 是低速外设，这决定了时钟树为什么要分开配。
  • 复位后先取栈顶、再取复位向量——然后 Reset_Handler 拷 .data、清 .bss，最后才进你的 main()。
自检题（先自己答，再对下面的判据）
  1. 为什么同一个「115200 波特率」，USART1 和 USART2 需要填的分频值不一样？

    判据：因为 USART1 挂在 APB2（72MHz），USART2 挂在 APB1（36MHz），波特率分频值 = 总线时钟 ÷ 波特率 ÷ 16，总线时钟不同，结果就不同。

  2. 往 0x40010C0C 写一个数，硬件上发生了什么？

    判据：这个地址落在 Peripheral 区，是 GPIOB 的 ODR 寄存器。总线上的地址解码电路认出它，把数据送进 GPIOB 的输出锁存器，PB0~PB15 的引脚电平随即按这 16 个位变化。

  3. 复位后 CPU 执行的第一条指令在哪？它的地址是怎么被找到的？

    判据：CPU 先读 0x00000000 装进 SP，再读 0x00000004 装进 PC，这个位置存的是 Reset_Handler 的地址。而 0x00000000 是 Flash 的镜像（BOOT0 = 0 时），所以实际取到的是 Flash 里向量表的内容。

  4. 为什么函数里的局部变量不会有默认的 0，而全局变量有？

    判据：全局变量按有没有初值分别进 .data 和 .bss，启动时 Reset_Handler 会拷贝/清零它们；局部变量在栈上，栈只是「一块反复使用的内存」，没人负责擦干净，所以值是上一次留下的垃圾。

  5. 把 BOOT0 拨到 1 之后再下载程序，为什么现象完全消失？

    判据：BOOT0=1、BOOT1=0 时，0x00000000 被重映射到系统存储器（出厂 Bootloader）而不是 Flash，复位后跑的是 ST 的下载程序，你自己烧进 Flash 的代码虽然还在，但没有人去执行它。

动手练习
  1. 把地址读出来验一遍：在工程里写 uint32_t a = (uint32_t)GPIOC; uint32_t b = (uint32_t)&GPIOC->ODR;，用调试器的 Watch 窗口看它们的值，核对是不是 0x40011000 和 0x4001100C。再加一个 (uint32_t)&RCC->APB2ENR;，看是不是 0x40021018。
  2. 亲手制造第一次 HardFault：写一句 *(volatile uint32_t *)0x12345678 = 1;（这个地址在 F103 上没有任何设备），下载运行。观察程序是否立刻停在 HardFault_Handler 的死循环里，并用 Call Stack 窗口找出是谁闯的祸。做完删掉这一行。
  3. 把栈改小，复现栈溢出：在启动文件里把 Stack_Size EQU 0x00000400 改成 0x00000080（128 字节），然后在 main 里定义 uint8_t big[512]; 并往里写数据。观察现象，然后改回 0x00000400。
  4. 数一数向量表：打开 startup_stm32f103xb.s，数出 F103C8 一共定义了多少个 DCD 中断入口，再对照 RM0008 的「向量表」章节，找出第 0xF0 项和第 0x58 项分别是谁。
