有限状态机：从状态图到单片机程序

上一篇给电路装上了记忆——触发器能记住一位了。但记住一位只是原材料：真正让单片机「活」起来的，是一串有先后、有分支、还带记忆的行为。闪灯要 1 秒一次、按键按下要立刻响应、串口随时可能来一包数据、看门狗要按时喂——这几件事在时间上没有先后顺序，而你的程序是一条线。冲突就出在这里：那个「有时候按键不灵」「偶尔丢一包数据」「加个需求就改得到处都是」的根源，几乎都是同一个东西——你的程序需要记住自己走到哪一步了，但你没有给这个「记住」一个好名字。这一篇讲的就是那个名字，以及它背后一整套从阎石教材一直通到 STM32 的 switch 语句的方法。

为什么需要它

先说三个现场，你对号入座一下：

  • 现场一：你写了一个「闪灯 + 按键切换模式」的程序。LED 用 delay_ms(1000) 一闪一闪，主循环里再读一下按键。结果按键得按好几下才偶尔灵一次，按快了完全没反应。你换了个按键、换了根线、换了上下拉电阻，都没用。
  • 现场二：你写了个串口收包程序，协议是 AA 55 + 长度 + 数据 + 校验 + 0D。你的思路是「等一整包收完再解析」。实验室里单步调试一切正常，一上真实设备就丢包，而且丢得毫无规律。你在串口助手里看数据是完整的，程序却经常报校验错。
  • 现场三：你写了个「先自检、再等待、再测量、再上传、失败就重试」的流程，用一堆 if (step == 1) … else if (step == 2) … 垒起来。它能跑，但加一个「重试三次」的需求，你要改五个地方；加一个「测量超时就报警」，又要再改三个地方。到后来你自己都不敢动它了。

这三个现场表面上毫不相干，根子是同一个：你的程序需要「记住自己走到哪一步了」，但你没有给这个「记住」一个好名字，也没有把它画出来。

顺序执行的直觉是从哪来的，什么时候开始失效

你学 C 语言的时候，脑子里建立的程序模型是「一条线」：从 main 的第一行开始，一行一行往下走，走到底再回到开头。老师反复强调「程序是顺序执行的」，这个模型在「只做一件事」的时候完美够用——点亮一个 LED、打印一句话、读一次 ADC，都是这条线上的几段。

但只要需求里出现「同时」两个字，这条线就断了。想一想一个最普通的作品需求：LED 每 500ms 翻转一次、按键按下立刻改变模式、串口随时可能来数据、看门狗每秒要喂一次。这四件事在时间上没有先后顺序——串口数据不会等你闪完灯再来，按键也不会提前通知你它要什么时候按下。它们是并发的，而你的程序是一条线。

阻塞 1 秒 = 这一秒里世界消失了

把现场一的代码写出来，问题一目了然：

/* 版本 A：阻塞式闪灯 —— 15 行，编译通过，LED 也确实在闪 */
while (1)
{
    LED_Write(0);
    delay_ms(1000);          /* ← CPU 在这里等满 1000ms，什么都不做 */
    LED_Write(1);
    delay_ms(1000);          /* ← 又等满 1000ms */

    if (KEY_Read() == 0)     /* 每 2000ms 才有一次机会看按键 */
    {
        mode = (mode + 1) % 3;
    }
}

数一下时间：主循环一圈 2000ms，也就是说你每 2 秒才有一次机会看按键。而人手按一下键的持续时长，松松地按大约 100ms（按得干脆的人 60~80ms，犹豫的人 150ms 以上）。那么：

【时间轴：一个 2000ms 的主循环】

  0ms      500ms     1000ms    1500ms    2000ms    2500ms
   │         │         │         │         │         │
   ├─ 亮 LED ─┼──── delay(1000) ─────┤        │         │
   │         │         │         │         │         │
   │         │         │      灭 LED → delay(1000) ────┤
   │         │         │         │         │         │
   ▼         ▼         ▼         ▼         ▼         ▼
             ↑↑↑↑↑↑↑↑                        ↑↑↑↑
           按键按下又松开                   又一次按下
           （宽约 100ms）                 （宽约 100ms）

   ★ 按键的整个「按下 → 松开」过程，全部发生在 delay 里面。
     CPU 那一秒什么都没看见 —— 不是没响应，是根本没采样。

【捕获概率】
   采样周期       = 2000ms（主循环一圈）
   按键持续时间   = 100ms
   捕获概率       = 100 / 2000 = 5%
   → 100 次按键，约 95 次被丢掉。
   → 你感觉到的「按好几下灵一下」，正是 5% 该有的样子。

【结论：这不是「偶发不灵」，这是「大概率不灵」】
   你以为是按键硬件的问题、是上拉电阻的问题、是去抖的问题，
   实际上你把采样率降到了 0.5Hz —— 而按键是一个 10Hz 量级的信号。
   采样率低于信号变化率时，丢失是必然的，与硬件无关。
「世界消失了」这句话是字面意思

在 delay_ms(1000) 的这一秒里，消失的不只是按键。这一秒内到达的串口数据，如果没开中断/DMA，硬件接收寄存器被下一个字节覆盖，直接丢掉（STM32 上表现为 ORE 溢出错误标志置位）；这一秒内按下的按键，你永远不知道它存在过；如果看门狗窗口设得比这一秒短，芯片还会直接复位。所以阻塞式代码的问题从来不是「慢」，而是在这段时间里，程序对世界是完全瞎的、聋的。

一个具体的数字：9600 波特率下，一个字节（含起始位和停止位共 10 位）需要 10 / 9600 ≈ 1.04ms 才能传完。也就是说，STC89C52 或 STM32 的硬件在 1ms 内就能收到一个新字节。只要你的程序有 2ms 没去读，就一定会丢。

思维转变：从「一条线」到「一张图」

状态机带来的第一个改变不是代码技巧，而是你看程序的方式。顺序执行的程序是一条线，CPU 的位置就是你正在执行的那一行；状态机的程序是一张图，CPU 的位置是「我停在哪个状态上等事件」。时间不再是 delay 出来的，而是事件到达时才产生意义的。

你在想的问题顺序执行的答案状态机的答案
程序是什么形状一条线，从头走到尾一张图，状态是节点、事件是边
CPU 现在在哪正在执行第几行停在哪个状态上等事件
时间怎么过去用 delay 硬等出来时间戳一到就产生一个「超时事件」
怎么处理「同时」做不到，只能排成一队天然支持：每个状态只关心自己的事件
按键不灵时怎么查单步调试，看变量值把状态图摊开，问「这条边我考虑了吗」
加一个需求要改几处散落在各处的条件判断，到处都要改加一个状态、加几条边，改动是局部的
能不能画在纸上给别人看不能（除非画流程图，但往往和代码不一致）能，而且画出来的图就是代码的结构

五个信号：说明你其实已经在写状态机了

状态机不是一个「你要去学的新东西」，而是把你脑子里已经有的东西画出来、说清楚、写对。下面五条命中任意一条，你就该停下来画图了：

  1. 你声明了 step、phase、state、mode 这样的变量来记「进行到哪一步了」。那个变量就是状态变量，你已经写出状态机了，只是没画出来、没穷举它的取值。
  2. 你在纸上画了流程框图和箭头。那些方框和箭头，就是状态图——只不过状态图有几个更严格的规矩（边必须标输入/输出、每个状态必须对每个输入都有去处），这些规矩正是让它变得可靠的原因。
  3. 需求描述里出现「先…然后…如果…就回到…」。有先后顺序、有分支、有记忆，这三样凑齐了就是状态机。
  4. 你说过「这个按键有时候不灵」「偶尔丢一包数据」。「有时候」「偶尔」这类词，在单片机里几乎永远指向同一个原因：采样率不够或者状态漏了。
  5. 你修好一个 bug，另一个又冒出来。这通常意味着状态之间的耦合藏在 if/else 的嵌套里，而你的脑子里没有一个统一的「现在处于哪个状态」的概念。
一条最实用的建议：先画图，再写代码

遇到新需求，先用 5 分钟把状态图画在纸上：圈出所有状态，给每条边写上「什么输入 / 什么输出」。画完之后你会发现两件事——①有些需求你原来根本没想清楚（比如「长按的同时松手算不算短按」）；②有些状态是多余的。这 5 分钟省下的，通常是几小时的调试。而如果你跳过这一步直接写 if/else，那些没想清楚的地方就会变成日后某个「偶尔出现」的 bug。

为什么说它是「通用语言」：同一台状态机，两种载体

这是状态机最值得学的一点：同一台状态机，在硬件里是一组 D 触发器加组合逻辑，在软件里是一个枚举变量加一条 switch 语句。载体完全不同，描述却一模一样。

【硬件里的状态机】                        【软件里的状态机】

   ┌──────────────┐                        uint8_t state;
   │  D 触发器组   │  ── 状态码 Q2Q1Q0      ↑ 就是这几个触发器
   └──────┬───────┘                          （一个字节 = 8 个触发器）
          │ 现态
          ▼                                 switch (state)
   ┌──────────────┐                        {
   │  次态组合逻辑 │  ── 卡诺图化简出的方程   case ST_IDLE:
   └──────┬───────┘                            if (按键按下) state = ST_DEBOUNCE;
          │ 次态                               break;
          │                                 case ST_DEBOUNCE:
          └──────► 打回触发器（时钟沿）           ...
                                            }
   ┌──────────────┐
   │  输出译码逻辑 │  ── 输出方程 Z = f(Q, X)    switch (state) { case ...: LED_Write(1); }
   └──────────────┘

   两者的对应关系：
     现态      ↔  state 变量当前的值
     次态方程  ↔  switch 里对 state 的赋值
     状态转移  ↔  一次主循环 tick（或一个时钟沿）
     输出方程  ↔  根据 state 驱动 IO / 发串口 / 动作
     复位到初态 ↔  init 里写 state = ST_IDLE;

所以学会画状态图，你同时得到三种能力：能跟硬件工程师讨论（他画的是同一张图）、能跟提需求的人确认（把图给他看，问他「这里松手算不算」）、能把需求直接翻译成代码或电路（图上的每条边就是一行代码或一个乘积项）。这就是「通用语言」的含义。

阎石教材第 6 章和你的单片机代码是什么关系

教材第 6 章讲的是「同步时序逻辑电路的分析与设计」，那套流程——画状态图 → 列状态表 → 状态化简 → 状态编码 → 写次态方程和输出方程 → 画卡诺图 → 连电路——看起来非常像考试题，和写代码好像没关系。但请记住：你写 switch (state) 的时候，编译器在后台做的正是同一件事的逆运算。它把你的 case 分支翻译成跳转表或者一串比较，本质就是「根据现态和输入决定次态」。

更实际的关系是：教材教会你的那套方法，是唯一能保证「不漏边」的方法。随手写 if/else，你漏掉一条边自己都不知道；而按照状态表逐个格子填，漏了哪一格一眼就能看出来。所以本篇的安排是：第 2 节讲清语言和规矩，第 3 节手算几道题（体会「不漏边」是怎么做到的），第 4 节落到 STM32 的真实代码。

核心概念

这一节要把状态机的「语言」讲清楚。你会看到五样东西：三要素（状态集合、输入集合、输出集合）、四种描述方式（状态图 / 状态表 / 状态转移方程 / 输出方程）、两种流派（Moore 与 Mealy）、三种编码（二进制 / 格雷 / 独热）、以及两条可靠性防线（非法状态治理、亚稳态同步）。这些东西看着多，其实是同一台机器的不同侧面。

三要素与四种描述方式：同一台机器的四个侧面

严格地说，一个有限状态机是一个五元组 M = (S, I, O, δ, λ)。但真正要你记住的是三要素 + 两个函数：

符号名字含义规模在单片机代码里的对应物
S状态集合这台机器所有可能「停在哪里」的取值，通常记 S0, S1, S2…有限个（这就是「有限」状态机的意思）enum 里的每一个枚举值
I输入集合能让机器改变行为的外部事件，通常记 X有限个（1 位输入就是 {0,1}）按键电平、串口来的字节、超时标志
O输出集合机器对外产生的动作或信号，通常记 Z有限个点亮 LED、发一帧数据、置一个标志位
δ次态函数（状态转移方程）Q* 是「下一个状态」，是现态 Q 和输入 X 的函数：Q* = δ(Q, X)每个状态 × 每个输入都要有一条switch 里对 next 的赋值
λ输出函数（输出方程）Z 怎么算出来：Mealy 是 Z = λ(Q, X)，Moore 是 Z = λ(Q)—根据 state 驱动 IO 的那几行

「有限」这两个字很关键：状态数必须是有限的，所以上一篇讲的触发器正好是它的载体——m 个触发器能表示 2m 个状态，这就是「有限」的物理来源。

描述方式②：状态表（State Table）—— Mealy 型
现态X = 0：次态 / 输出X = 1：次态 / 输出
S0（还没见到 1）S0 / 0S1 / 0
S1（已经见到 1）S0 / 1 ← 检测到「10」S1 / 0

状态表是四种描述里最重要的一种，因为它是唯一「不会漏格」的形式：行数 = 状态数，列数 = 输入组合数，格子数是有限的，你可以用眼睛一格一格数过去，确认没有空格。状态图做不到这一点（你可以忘记画一条边而毫无察觉），代码也做不到（if 少写一个分支编译器不会提醒你）。

             1     │ 0 │    0        （S1 --X=0--> S0）
             1     │ 1 │    1        （S1 --X=1--> S1）

        观察这张表：次态 Q* 的值和 Q 完全无关，永远等于 X。所以

              Q* = X                        ← 状态转移方程

        （这就是「1 个触发器」的实惠之处：D 端直接接输入线 X 就行了。）

  ② 输出方程    Z = λ(Q, X)

        输出 Z 什么时候是 1？只有在「现态 Q = 1 且 X = 0」这一格：

              Z = Q · X'                    ← 输出方程

【Moore 型「10」检测器：需要 3 个状态、2 个触发器】

  Moore 型要求输出只由状态决定，所以「检测到 10」这件事
  必须自己变成一个状态：

        状态编码：S0 = 00（输出 0）、S1 = 01（输出 0）、S2 = 10（输出 1）

          现态     输出 Z   X=0 → 次态   X=1 → 次态
          ────────┼───────┼───────────┼───────────
            00    │   0   │    00     │    01
            01    │   0   │    10     │    01
            10    │   1   │    00     │    01

  状态转移方程（D2 = Q1*，D1 = Q0*，注意这里把位从高到低叫 Q1 Q0）：

        D1 = Q0 · X'        （只有 01 遇到 X=0 这一格让 Q1 变成 1）
        D0 = X · (Q1 · Q0)' （X=1 时次态的最低位是 1，
                              但非法状态 11 要强制回 000，所以多乘一项）
  输出方程：

        Z = Q1 · Q0'        （只有状态 10 输出 1，与 X 无关）

【把两版摆在一起看】

                 状态数  触发器数  输出方程        输出什么时候变
   ─────────────┼───────┼────────┼──────────────┼────────────────────
   Mealy 版     │   2   │   1    │ Z = Q · X'    │ X 一变就跟着变
   Moore 版     │   3   │   2    │ Z = Q1 · Q0'  │ 只在时钟沿之后变

   同一个功能，Moore 版多花一个触发器，换来的是「输出与输入解耦」。
   这个交易划不划算，就是下一小节的主题。
四种描述方式的互相转换：三条机械规则

图 → 表：一个状态一行，一个输入组合一列，把每条边上的「次态 / 输出」抄进对应格子。格子填不满就是漏了边。

表 → 方程：①先给状态编码；②把「次态」列按编码写成 0/1，得到状态转移表；③对每个触发器（每一位）单独画一张卡诺图，圈 1 得方程；④输出列同样处理。

方程 → 图：把每个状态码代进方程，逐个算「这个状态遇到 0 去哪、遇到 1 去哪」，画出来即可。这一步也常用来自检——如果你的方程算出来的转移和原图不符，说明中间某一步抄错了。

Moore 与 Mealy 的严格区别：输出到底依赖不依赖输入

这是状态机里最需要分清、又最容易被含糊过去的一对概念。严格定义只有一句话的差别：

类型输出方程输出画在哪电路上的含义
Moore 型Z = λ(Q)，只和现态有关写在圆圈里面（状态名/输出）输出 = 状态的译码 → 输出端没有输入信号的路径
Mealy 型Z = λ(Q, X)，和现态、当前输入都有关写在箭头上面（输入/输出）输出 = 状态与输入的组合逻辑 → 输入信号能穿透到输出

这个「一句话的差别」会引出一连串实际后果。用上面那台「10」检测器，喂同一串输入 1 1 0 1 1 0（每个时钟一位），把两版的波形画出来：

输入序列 X =  1    1    0    1    1    0        （每个时钟周期一位）

时钟周期      T1   T2   T3   T4   T5   T6   T7
──────────────────────────────────────────────────────────────
输入 X         1    1    0    1    1    0    …
──────────────────────────────────────────────────────────────
【Mealy 版】1 个触发器
现态 (进入本周期时)   S0   S1   S1   S0   S1   S1
次态 (本周期结束时)   S1   S1   S0   S1   S1   S0
输出 Z         0    0   (1)   0    0   (1)   …
                          ↑                ↑
                     T3 的「1」在 X 变成 0 的【那一刻】就出现，
                     不等时钟沿；T4 的 X 一变回 1，它立刻消失。
                     → 脉宽 = X 保持为 0 的那段时间，可长可短

──────────────────────────────────────────────────────────────
【Moore 版】2 个触发器
现态 (进入本周期时)   S0   S1   S1   S2   S1   S1   S2
输出 Z         0    0    0    1    0    0    1
                                    ↑              ↑
                              整整晚了一个周期才出现；
                              而且它的宽度【精确等于一个时钟周期】，
                              不管 X 在这一周期里怎么变。

──────────────────────────────────────────────────────────────
【一句话总结】
  Mealy：输出「跟着输入走」——快，但脉宽不确定、带毛刺。
  Moore：输出「跟着时钟走」——慢一拍，但干净、宽度精确。

注意上面 Mealy 那一行里我把 1 加了括号。这不是笔误，而是 Mealy 输出最危险的性质：它在 X 变化的那一刻就组合穿透到输出端，如果 X 恰好在一个时钟沿附近跳变，这个输出脉冲可能只有几纳秒宽——慢一点的下一级电路根本采不到它，而快一点的电路可能采到两次。更要命的是，X 上的任何毛刺（按键抖动、长线反射、电源噪声）都会原样出现在输出上。

什么情况下必须选 Moore（别犹豫，直接选）
  • 输出会接到「边沿敏感」的东西上。外部中断引脚、另一个状态机的时钟输入、异步复位端、DMA 触发、ADC 的外部触发、计数器的计数输入——这些器件把「电平变化」当成「事件」。Mealy 输出的毛刺在它们眼里就是一串真实事件，后果是凭空多出几次中断、多计几个数、甚至被误复位。
  • 输出要出芯片、走长线。板外走线是天线也是接收天线，Mealy 的组合输出会把线缆上的干扰原样放大到接收端。
  • 输出要驱动机械或慢速执行器。继电器、电磁阀、蜂鸣器这类器件要求脉冲宽度可控。Mealy 那种「可能只有几十纳秒」的脉冲，继电器根本来不及吸合，你却以为信号发了。
  • 输出会反馈回自己的输入（闭环）。Mealy 的穿透特性会让输出当拍就影响输入，一个不小心就构成组合环，产生自激振荡。
  • 安全相关的判断。宁可慢一拍，绝不能误触发——这是工程上一条不写在教科书里的铁律。
  • 需要精确计时。比如「输出持续正好 100 个时钟」，Moore 的脉宽天然是一个时钟的整数倍；Mealy 做不到。

那什么时候用 Mealy？三种情况：① 状态数要省（比如状态多到快撑爆编码位宽）；② 响应速度要求高，差一个时钟就来不及（高速协议里的位级判断）；③ 输出只被同一时钟域的同步电路采样，那点毛刺在下一次采样前就已经稳定了。在单片机的 C 代码里，这个区别常常被淡化——因为你的 switch 是自己一个 tick 执行一次的，输出和输入天然「同一拍」，既不会穿透也不会滞后。但一旦你的输出是「直接写寄存器去触发一个硬件事件」（比如手动置位定时器的 EGR 位、手动触发一次 ADC），Mealy 的那套风险就会原地复活。

一个真实的坑：Mealy 输出当异步复位用

有人为了「检测到错误就立刻复位从机」，把状态机的 Mealy 输出直接接到从机的 NRST 上。因为 Mealy 输出是组合的，在状态机切换的瞬间，译码逻辑上会出现几十纳秒的窄毛刺（不同路径延迟不同造成的竞争），从机就被这个毛刺复位了——而你的逻辑明明没有要复位它。现象是「从机偶尔自己重启」，抓破头也找不到原因。正确做法：把复位信号单独寄存一拍再输出（这就是三段式里「输出寄存」那一招），或者改用 Moore 输出。

状态编码：二进制 / 格雷 / 独热，三种方案的取舍

状态图的圆圈是抽象的，落到电路上必须给每个状态一个二进制码——这个动作叫状态编码（state assignment / state encoding）。同一台状态机，编码方案不同，触发器数量、译码逻辑的复杂度、速度、非法状态的数量全都不一样。设状态数为 n：

【方案一】二进制编码（Binary）—— 最少触发器

    m = ⌈log2 n⌉ 个触发器 —— 这是理论最少的位数，不可能更省了。
    n = 5  → m = 3 位，码：000 001 010 011 100（剩下 3 个码没用）
    n = 8  → m = 3 位，刚好用满，没有多余码
    n = 9  → m = 4 位

    代价：次态方程是 m 个变量的函数，每个触发器的卡诺图都很大
          （n=8、1 位输入时是 Q2 Q1 Q0 X 四变量，16 个格子），
          化简后乘积项多、门多、路径深 → 慢。
    非法状态数 = 2^m − n：
          n=5 → 3 个      n=6 → 2 个      n=8 → 0 个      n=9 → 7 个

【方案二】格雷码（Gray）—— 顺序转移时的最优解

    触发器数量同样是 m = ⌈log2 n⌉，一位都不多。
    但它要求【相邻的两个状态只差一位】：000 → 001 → 011 → 010 → 110 → …

    好处一：译码无毛刺。两个相邻状态之间只有一位在变，译码逻辑
            不会出现「两位同时翻转、先后到达」造成的瞬态错误码。
    好处二：翻转功耗最低。每个时钟只有一位触发器翻转，
            CMOS 电路的动态功耗 ∝ 翻转次数，可以省接近一半。
    好处三：跨时钟域采样安全。别的时钟域来采这个状态码时，
            最多把新值采成「一位还没变」的旧值，不会采出一个
            完全不着边际的错误码。（多位同时变就可能采出乱码。）
    好处四：次态逻辑常常能简化，因为「该位为 1 的那些状态」
            在卡诺图上是相邻的，能圈成更大的圈。

    适用：状态按固定顺序循环的场合 —— 计数器、扫描器、
          流水灯、ADC 多通道轮询、DMA 链表遍历。

【方案三】独热码（One-Hot）—— 触发器最浪费，逻辑最简单

    m = n 个触发器：一个状态占一位，状态 S3 就是 0000 1000。

    次态方程变得极其简单：第 i 位的次态 = 所有「指向 Si 的转移」
    的【或】。不需要译码！每个状态一位，判断「我现在在不在 S3」
    就是看一根线是高还是低，连一个门都不用。

    代价一：触发器数量线性增长（n=16 就要 16 个触发器）。
    代价二：非法状态数量【爆炸】：
          n=5  → 2^5 − 5  = 27 个
          n=8  → 2^8 − 8  = 248 个
          n=16 → 2^16 − 16 = 65520 个
            最典型的非法状态是「全 0」（一个都没选中）和
            「多热」（好几位同时为 1，等于同时处于两个状态）。

    适用：FPGA 里的状态机（触发器在 FPGA 里是「免费」的，
          每个 LUT 后面本来就带一个触发器，不用白不用），
          以及状态数少（≤ 16）而对时序要求高的场合。

把三种方案放进一张表，你就能拿着尺子挑：

对比项二进制编码格雷码独热码

选择准则（背下这六条就够用）
  1. FPGA 实现、状态数 ≤ 16 → 独热。FPGA 里一个触发器约等于「一个 LUT 的零头」，而译码逻辑要吃掉宝贵的 LUT。独热把逻辑换成触发器，在 FPGA 上是净赚。事实上 Vivado / Quartus 对状态机默认就选独热（综合属性 fsm_encoding 的 auto 模式）。
  2. ASIC 或 CPLD、面积敏感 → 二进制。在 ASIC 里一个 D 触发器大约相当于 6~10 个等效门，触发器是贵东西；而门电路是便宜的。用二进制把触发器数压到最少。CPLD 的宏单元资源也紧张，同理。
  3. 状态按固定顺序循环（计数、扫描、轮询）→ 格雷码。省功耗、无译码毛刺、跨时钟域友好，三重好处都吃到了。
  4. 状态数超过 16~32 → 二进制。独热的触发器数和非法状态空间都随 n 指数/线性恶化，到那个规模就无法管理了。
  5. 状态码要送到另一个时钟域 → 格雷码。这是唯一能保证「采样最多错一位」的编码。
  6. 用 MCU 的 C 语言实现 → 编码无所谓。你用 enum + switch，编码是编译器的事；此时最重要的指标变成了可读性——让枚举名直接说出状态的含义（ST_WAIT_HEADER 比 ST_3 好一百倍）。

非法状态：危害、锁死，以及四层防御

只要编码方案没有把 2m 个码用满，就一定存在非法状态（unused state / illegal state）——你的状态机理论上永远不会主动进入的码。问题是：理论上不会，不等于实际不会。

非法状态从哪来？五个来源，一个比一个隐蔽：

来源怎么发生的常见程度
编码冗余5 个状态用 3 位编码，剩下 3 个码天生非法必然存在
上电初值不确定触发器上电后的初值是随机的（不是 0！），如果复位没覆盖到某个触发器，它就从随机码开始跑很常见
复位释放不同步异步复位同时加在 m 个触发器上，但它们的复位释放时刻略有差异（走线长度不同、门延迟不同），可能在某个瞬间出现「一半复位了、一半没有」的中间码常见
亚稳态输入违反建立/保持时间，触发器输出停在中间电平，被后级解读成随机值偶发
单粒子翻转 / 噪声耦合宇宙射线、电源噪声、强电磁干扰让某个触发器自己翻了一位罕见但真实

进入非法状态之后会发生什么？最坏的情况是锁死（lock-up）：

【现象】3 位编码、5 个合法状态：000 001 010 011 100
        非法码：101、110、111

  你写次态逻辑时，对这三个码「没写」（或者写了 default: ; 空着）。
  综合工具于是把它们当【无关项】，随手分配了次态：

        101 ──► 110 ──► 111 ──► 101 ──► 110 ──► …
        └────────── 三个非法状态自己转圈 ──────────┘

  结果：状态机再也回不到合法状态。所有输出停在某个奇怪的组合上，
        所有输入都不再被响应 —— 看起来就像「程序卡死了」。
        而且时钟还在跑、电源还正常、看门狗（如果没开）也不会救你。

【为什么「没写」会变成随机分配？】
  在卡诺图里，「没写」的格子叫无关项（don't care，记作 × 或 d）。
  化简的时候，工程师（或工具）为了让圈更大、方程更简单，
  会自由地把这些 × 当成 0 或 1 —— 这在【数学上】完全合法，
  因为「非法状态不会出现」是前提。
  但一旦前提被打破（上电、亚稳态、噪声），
  你圈出来的那个「最简方程」就会把状态机带进锁死环。

【更危险的第二种后果：两个互斥输出同时有效】
  比如电机驱动：正转 = 状态 A，反转 = 状态 B。
  如果非法码让译码逻辑同时输出「正转」和「反转」，
  H 桥的上下管同时导通 → 电源直接对地短路 → 驱动芯片当场烧掉。
  这是非法状态在工程上最贵的后果，没有之一。
四层防御：从「不可能发生」到「发生了也能活下来」

第一层：编码上留余地（最根本）。能不用满就不用满。如果条件允许，选一个让非法状态数量为 0 的编码宽度（n = 2m 时刚好——这也是为什么很多教科书例子把状态数凑成 4、8、16）。另外，把复位状态选成「全 0 码」或「只差一位就能到达合法状态的码」，能显著降低上电跑飞的后果。

第二层：给非法状态显式安排默认转移（安全编码 / safe encoding）。这是最有效、最便宜的一招：在写次态逻辑时，先把「默认次态 = 复位态」写在最前面，再用 case 覆盖所有合法状态。这样所有你没提到的码都会自动落到复位态，而且是在一个时钟内就恢复。

在 HDL 里写：

state_next = S_IDLE; 写在 case 之前，或者写 default: state_next = S_IDLE; —— 千万不要写 default: ; 或者干脆不写 default，那等于把非法状态的命运交给工具。

在 C 里写：switch (st) { … default: st = ST_IDLE; break; }，并且把编译器的 -Wswitch-default 打开，让「漏写 default」直接变成编译警告。

第三层：加监视与自愈逻辑。针对独热码，加一条「零检测 / 多热检测」：if (state == 0) state <= S_IDLE;，或者用「优先级编码器 + 哨兵位」把多热状态强制收敛到一个合法状态。在 MCU 软件里，可以在 default 分支里上报一次诊断信息（串口打印 + 计数器 +1），这样你能知道「它真的跑飞过」，而不是永远蒙在鼓里。

第四层：看门狗兜底（最后一道防线）。前三层都防不住的情况（比如状态寄存器硬件损坏、两个触发器同时翻转），只有看门狗能救。关键要求是：喂狗动作必须放在「状态机正常推进」的路径上，而不是放在定时器中断里无脑喂。如果放在中断里喂，状态机卡死了中断照跑、狗照喂，看门狗就形同虚设——这是新手最常犯的看门狗错误。

状态化简：等价状态与隐含表

状态图刚画出来的时候，几乎总是「多画了」。因为你是按需求一步步想出来的，很容易出现两条不同的思考路径落到同一个行为上。这些多余的、行为完全一样的「孪生状态」，就是可以合并的对象。

等价状态的定义（严格版）：两个状态 Si 和 Sj 等价（记作 Si ≡ Sj），当且仅当对任意长度、任意内容的输入序列，从 Si 出发和从 Sj 出发产生的输出序列完全相同。

这个定义没法直接拿来用（要验证无穷多条序列），所以教材把它翻译成两条可操作的判据：

【判据一 · 输出一致】
   对【每一个】输入，S 和 S 的输出必须相同。
     · Moore 型：看状态自己的输出（写在圆圈里的那个）
     · Mealy 型：看每条边上的输出

【判据二 · 次态等价】
   对【每一个】输入，S 和 S 的次态必须【相同】或者【也等价】。
     次态相同  → 这一条自动满足
     次态不同  → 把这两个次态当成一对新的候选，要求它们也等价

【为什么必须迭代？】
   判据二会引出新的状态对，而新的状态对又要用判据一、二来判断 ——
   这是一个「互相依赖」的方程组，不是一次扫一遍就能解出来的。
   所以要反复迭代，直到不再有新的「不等价」被判定出来。
   这个方法在教材里叫【隐含表法】，在计算理论里叫
   「等价类逐步细分（partition refinement）」——同一个东西。

【一个重要提醒：等价和「输出相同」不是一回事】
   两个状态输出完全相同，但次态不同 —— 它们【不等价】，不能合并。
   例子：交通灯里「EW 绿 + NS 红」阶段结束后的全红，
        和「NS 绿 + EW 红」阶段结束后的全红，
        两者的输出完全一样（都是全红），但一个要转到 NS 绿、
        另一个要转到 EW 绿 —— 次态不同，所以是两个状态。
   这是状态化简里最容易犯的错：只看输出就合并。

隐含表法的五个步骤：

步骤做什么为什么
1画隐含表：n 个状态画一个右上三角表，共 n(n−1)/2 个格子，每格代表一个状态对把「所有可能等价的状态对」一次性列全，不漏
2第一遍筛选：凡是「存在某个输入使两者输出不同」的格子，直接打叉（✗）判据一，一步淘汰一大半
3剩下的格子里填「次态对」：对每个输入，把两者的次态写成一个状态对记录判据二的依赖关系
4迭代：任何一格里出现了已经打叉的状态对，本格也打叉；重复直到不再变化解那个互相依赖的方程组
5没有打叉的格子 = 等价对；取传递闭包（A≡B、B≡C 推出 A≡B≡C）得到最大等价类，每类合并成一个状态得到化简后的状态表

完整的手算例子放在第 3 节例三，那里会走完 5 个状态化简成 4 个的全过程。先记住「观察法」这个快速通道：如果两个状态的所有转移和所有输出一模一样，直接合并，不需要画隐含表——这是隐含表的特例，也是实际工作中最常遇到的情况（你复制粘贴了一段逻辑，改了名字忘了改内容）。

化简到底省了什么？算一笔账

触发器数：n 个状态需要 ⌈log2n⌉ 个触发器。所以只有跨过 2 的幂时才省得下来：9 → 8 省 1 个（4 位 → 3 位）、5 → 4 省 1 个（3 位 → 2 位）、17 → 16 省 1 个。而 6 → 5 一个都不省（都是 3 位）。

但省下的绝不止触发器：① 次态方程的乘积项变少 → 门变少 → 组合路径变短 → 最高时钟频率提高；② 非法状态数量减少（5 状态 3 位有 3 个非法，化简到 4 状态 2 位就一个都不剩）；③ HDL 代码变短，可读性变好；④ 验证的状态空间变小。

化简的代价，也要知道：合并之后，原来那两个状态的差别在运行时不可观测了——调试时你想知道「它刚才走的是哪条路」就看不到了。工程上有时会故意不合并，保留冗余状态用于诊断（比如 ST_SEND_A 和 ST_SEND_B 行为相同，但分开写便于在串口日志里区分）。能化简 ≠ 一定要化简，可观测性也是一种价值。

用 D 触发器实现一个 FSM：六步流程

这是教材第 6 章的核心方法，也是「状态图 → 电路」的标准通道。六步，一步都不能跳：

【第 1 步】把需求画成状态图
     · 先决定用 Moore 还是 Mealy（判断依据见上一小节）
     · 明确三要素：S（状态集合）、I（输入集合）、O（输出集合）
     · 给每个状态画全它的出边：每一个状态 × 每一个输入都要有去处
     · 标出初始状态

【第 2 步】化简
     · 用隐含表法合并等价状态（或者先用观察法找「长得一样」的）
     · 顺便删掉【不可达状态】：从初始状态出发、任何输入序列都到不了的状态
       （它们既没用，又会在代码里制造「看起来有但永远不走」的死逻辑）

【第 3 步】状态编码
     · n 个状态 → m = ⌈log2 n⌉ 位（二进制/格雷），或 n 位（独热）
     · 决定非法状态的处理方案：它们的次态统统指向复位态

【第 4 步】列状态转移表（最重要的一步）
     · 行 = 所有 2^m 个编码（【包括非法码！】），列 = 所有输入组合
     · 每格填两样东西：次态、输出
     · 合法状态行：从状态表抄
     · 非法码行：填「次态 = 复位态、输出 = 0」
     ★ 这一步是「不漏边」的保证：格子数是有限的，数一遍就知道对不对

【第 5 步】求激励方程
     · D 触发器的好处在这里体现：D = Q*（次态是什么，D 端就接什么）
     · 所以把第 4 步的「次态」列按每一位拆开，每一位画一张卡诺图
     · 圈 1 → 得到该位的方程 → 就是该触发器的 D 端表达式
     · 圈 0 得到的是 Q*'，也可以直接圈（反变量有时更省门）

【第 6 步】求输出方程 + 画电路
     · 输出列同样画卡诺图（Moore：只看状态列；Mealy：状态 × 输入）
     · 画电路：所有触发器的 CP 端【并联】接到同一个时钟，
                所有异步复位端【并联】接到同一个复位，
                D 端接第 5 步的方程，Q 端送回组合逻辑

第 5 步里「D = Q*」这句话，是 D 触发器统治现代数字设计的全部原因。对比一下四种触发器的激励表就明白了：

现态 → 次态D 触发器T 触发器JK 触发器SR 触发器
0 → 0（保持）D = 0T = 0J = 0，K = ×S = 0，R = ×
0 → 1（置 1）D = 1T = 1J = 1，K = ×S = 1，R = 0
1 → 0（清 0）D = 0T = 1J = ×，K = 1S = 0，R = 1
1 → 1（保持）D = 1T = 0J = ×，K = 0S = ×，R = 0
激励方程的复杂度D = Q*，最简要额外算 T = Q ⊕ Q*要算两个变量，最麻烦要算两个变量，还有不允许态

用 JK 或 T 触发器，你会多出一层「把次态翻译成激励」的组合逻辑；用 D 触发器，这层逻辑根本不存在——次态方程直接就是激励方程。用一句工程黑话总结：D 触发器把复杂度从「器件」推给了「综合工具」，而综合工具最喜欢处理的就是「一堆卡诺图圈 1」。所以今天你在芯片里能看到 D 触发器、看到 JK 只在老教材里出现。

最后是电路长什么样（以第 3 节例一的「1011」检测器为例，2 个触发器、5 个门）：

                      ┌────────────────────────────────────────────┐
                      │            次态组合逻辑（第 5 步的方程）      │
                      │                                            │
   X ─────┬──────────►│  D1 = Q0·X' + Q1·Q0'·X                     │
          │           │  D0 = X                                    │
          │           └───────┬───────────────────┬────────────────┘
          │                   │ D1                │ D0
          │            ┌──────▼──────┐     ┌──────▼──────┐
          │            │   D 触发器    │     │   D 触发器   │
   CLK ───┼───────────►│   CP     Q1  │     │   CP    Q0  │
          │            │              │     │             │
   RST ───┼───────────►│   R      Q1' │     │   R     Q0' │
          │            └──────┬──────┘     └──────┬──────┘
          │                   │ Q1                │ Q0
          │                   └─────────┬─────────┘
          │                             │
          │                             ▼  这两位就是「现态」，
          │                  送回上面的组合逻辑（闭环）
          │
          │           ┌──────────────────────────────┐
          └──────────►│  输出逻辑：  Z = Q1 · Q0 · X   │──────► Z
                      └──────────────────────────────┘

   三条工程规矩：
    ① 所有触发器的 CP 端必须【并联】接同一个时钟 —— 这是「同步」的含义。
       绝不能有的触发器用时钟、有的用输入的边沿（那就成了异步电路，
       会出现竞争和毛刺，分析方法完全不同）。
    ② 所有异步复位端并联接同一个复位信号，保证 m 位【同时】回到初态。
    ③ 组合逻辑的输入只有两类：现态 Q 和外部输入 X。没有第三类。

时序约束、复位与亚稳态：状态机为什么不能无限快

前五步做完，你得到了一个逻辑上正确的状态机。但它能不能按你想要的频率跑，取决于一条不等式。一个时钟周期内，信号必须从「上一个触发器输出」一路走完组合逻辑，赶在「下一个时钟沿到来之前」站稳：

   一个时钟周期里信号要走的路：

   ┌──────────┐          ┌────────────────┐          ┌──────────┐
   │ 触发器 A  │          │  次态组合逻辑   │          │ 触发器 B  │
   │    Q     │─────────►│ （卡诺图化简出  │─────────►│    D     │
   └──────────┘          │   来的那些门）  │          └──────────┘
        ▲                └────────────────┘               ▲
        │                                                 │
   时钟沿到达                                        必须在下一个时钟沿
   （Q 开始变化）                                    到来【之前】就站稳，
                                                     并保持一段时间

   ┌── t_cq ──┼──── t_logic（最坏情况）────┼─ t_setup ─┐
   │          │                             │           │
   │  触发器输出   │      组合逻辑传播延迟        │  建立时间  │
   │  的延迟      │                            │           │
   └──────────────┴────────────────────────────┴───────────┘
                                                    + t_skew（时钟偏斜）

   ══════════════════════════════════════════════════════════════

        T_clk ≥ t_cq + t_logic(max) + t_setup + t_skew

   其中：
     t_cq        时钟沿到 Q 输出稳定所需的时间（触发器自己的参数）
     t_logic     从 Q 到 D 的组合逻辑【最长路径】延迟（你的方程决定）
     t_setup     触发器要求 D 在时钟沿之前稳定多久（器件参数）
     t_skew      同一个时钟到达不同触发器的时间差（走线长度不同）

   于是：  f_max = 1 / T_clk(min)

【还有一条反向的约束：保持时间（hold）】

        t_cq(min) + t_logic(min) ≥ t_hold + t_skew

   注意它用的是【最短】路径延迟。这条约束的意思是：
   D 端的新值不能来得【太快】—— 如果一个时钟沿刚把新数据推出去，
   它太快地穿过组合逻辑冲到了下一级，而下一级的触发器还没
   「松手」（还在保持窗口里），那么它会把新数据当成旧数据采进去，
   相当于【这一拍被吃掉了】，状态机少走一步。

   ★ 两条约束的分工：
       建立时间约束 → 决定【最快能跑多快】 → 慢了就降频
       保持时间约束 → 决定【逻辑不能太短】 → 与频率无关，插缓冲器解决
   新手通常只知道第一条，但第二条才是「低速系统也会出错」的原因。

复位：让状态机每次都从同一个地方出发。上一小节说过，触发器上电后的初值是随机的。如果状态机没有复位，它就从随机码开始跑——而随机码很可能正是一个非法状态。所以复位不是「可选的礼貌」，而是状态机能工作的前提条件。两种复位各有取舍：

对比项异步复位同步复位
生效条件复位信号一来立刻生效，不需要时钟要等下一个时钟沿才生效
时钟停了能不能复位能（这是它最大的优点）不能
抗毛刺差：复位线上的毛刺会直接触发复位好：毛刺只要不在时钟沿附近就被忽略
资源触发器自带异步复位端，不花额外逻辑要占用数据通路上的一级逻辑（多路选择器）
释放时刻的问题有风险：m 个触发器释放时刻不同，可能产生中间码；而且释放沿落在时钟沿附近会导致亚稳态无：释放本身就是同步的
工程上的标准做法异步置位、同步释放：用两级触发器把复位信号同步一下再送到状态机（这就是下一段要讲的「打两拍」），既保留了「时钟停了也能复位」，又消除了释放时刻的风险

亚稳态：异步输入直接进状态机会发生什么。触发器能可靠工作，前提是数据在时钟沿附近不变化（守规矩的窗口就是 t_setup 和 t_hold）。如果数据刚好在窗口里跳变，触发器内部的正反馈来不及把它推向 0 或 1，输出就会停在一个既不是高也不是低的中间电平上，然后在一段不确定的时间之后才随机倒向某一侧——这就是亚稳态（metastability）。

如果你把一个异步信号（按键、外部模块的中断输出、另一个时钟域的完成标志）直接接到状态机的输入，那么：

  • 状态机会「看到」一个不存在的输入。中间电平被不同的后级门解读成不同的值——接在状态机前面的与门可能读成 1，直接到触发器的另一路可能读成 0，于是同一次输入变化被解读出两种结果。
  • 可能多走一步或者少走一步。状态机的次态逻辑是用 if (X) 分支写的，X 处于中间电平时不同晶体管的判断结果不同，可能这一拍判 1、下一拍判 0，状态机就多转移了一次。
  • 而且它是「偶发」的。亚稳态导致的错误和时钟频率、温度、电压、数据跳变与时钟沿的相对相位都有关，实验室里可能连续跑一个月不复现，到客户现场每天出一次。这类 bug 是最贵的。
解决办法：打两拍（两级同步器）

做法简单到令人怀疑：把异步输入先送进两级串联的 D 触发器（同一个时钟），再从第二级的输出接进状态机。第一级触发器可能进入亚稳态，但它有一整个时钟周期的时间自己恢复；等到第二级采样的时候，第一级的输出已经稳定成合法的 0 或 1 了。

关键认识：亚稳态不能「消除」，只能把它的概率压到可以忽略。第一级输出还处于中间电平的概率随时间指数下降，所以「打两拍」把故障率降低了好几个数量级。用平均无故障时间（MTBF）来说：在典型的 100MHz 系统里，一级同步器的 MTBF 可能只有几十分钟到几天，两级同步器可以达到 109 小时以上（这是量级估算，具体值必须拿器件手册里的 τ 和 T0 参数代入计算）。

打两拍只能用于单比特信号！如果跨时钟域的是一个多位的总线（比如一个 16 位的计数器值），打两拍是不够的——各位可能在不同的时钟沿被采到，你会得到一个「高 8 位是新值、低 8 位是旧值」的乱七八糟的数。多位跨时钟域要用三种办法之一：①格雷码（每次只变一位，最多错一位）、②握手（请求/应答两根线）、③异步 FIFO。这也是状态编码里推荐格雷码的第三个原因。

回到单片机：这些时序概念在 MCU 里长什么样？你用 C 写状态机，state 变量存在 SRAM 或寄存器里，看上去和「建立时间」毫无关系。但三件事一定要注意：① 如果你用外部中断来改变状态（比如按键中断里直接改 state），做了一次本质上的「异步输入」——正确做法是中断里只置一个标志，主循环读到标志再改状态；② 如果你在中断和主循环里都读写 state，必须加 volatile，否则编译器的优化会让主循环永远读到旧值；③ 用 millis() 或 HAL_GetTick() 做超时时，一定要用无符号减法 (now - t0) >= TIMEOUT，不要写 now >= t0 + TIMEOUT——前者在计时器溢出回绕时自动正确，后者会出错。下一节会详细算这个溢出。

三种写法：一段式、两段式、三段式

到了硬件描述语言（Verilog / VHDL）里，同一台状态机有三种主流写法。它们的区别不在功能，而在「什么时候变」和「变成什么」有没有被分开写。这个区别非常关键，因为它直接决定你的代码能不能被综合工具正确理解、能不能做时序分析、出了 bug 好不好找。

写法结构优点问题
一段式一个 always 块里同时做三件事：状态搬迁、次态计算、输出赋值代码最短次态变量和现态变量混用；输出与状态耦合，容易写出组合环；容易推出意外锁存器；仿真与综合结果可能不一致；无法对「次态逻辑」单独做时序约束
两段式第一段：时序块，只做 state <= state_next；第二段：组合块，算次态和输出比一段式清爽很多；状态与次态分离，能看出「什么时候变」输出仍在组合块里 → 输出是组合输出，带毛刺（本质是 Mealy）；输出路径延迟与次态逻辑纠缠在一起
三段式① 时序块：状态寄存器；② 组合块：只算次态；③ 单独的输出逻辑（可以再寄存一拍）职责单一、无毛刺（输出寄存后）、无意外锁存器、时序好约束、default 只写一处代码行数最多（这是它唯一的「缺点」）

为什么工程上推荐三段式？一句话：把「时序」和「组合」物理上分开，是同步数字设计的根本原则。一段式把这两件事搅在同一句代码里，等于让「什么时候变」和「变成什么」共用一个语义空间——你改一处逻辑，可能悄悄改变了时序含义，而工具和同事都看不出来。三段式则把三件事变成三个互不干扰的问题：状态存在哪（触发器）、下一拍去哪（组合逻辑）、现在输出什么（输出逻辑）。任何一个出问题，你都能单独把它拿出来看。

module seq_det_1011 (
    input  wire clk,
    input  wire rst_n,          // 低电平有效的异步复位
    input  wire x,              // 串行输入
    output reg  z               // 输出（这里寄存一拍，彻底消毛刺）
);

    // 状态编码：4 个状态刚好用满 2 位，没有非法状态
    localparam S0 = 2'b00,
               S1 = 2'b01,
               S2 = 2'b10,
               S3 = 2'b11;

    reg [1:0] state, state_next;
    reg       z_next;

    // ───────── 第 1 段：状态寄存器（只做一件事：把次态搬进现态）─────────
    always @(posedge clk or negedge rst_n) begin
        if (!rst_n) state <= S0;
        else        state <= state_next;
    end

    // ───────── 第 2 段：次态逻辑（纯组合，绝对不能有副作用）─────────
    always @(*) begin
        state_next = S0;                 // ★ 先给默认值 = 安全编码，
                                         //   所有没写到的码自动回 S0
        case (state)
            S0: state_next = x ? S1 : S0;
            S1: state_next = x ? S1 : S2;
            S2: state_next = x ? S3 : S0;
            S3: state_next = x ? S1 : S2;
            default: state_next = S0;    // 非法状态自恢复（写给读代码的人看）
        endcase
    end

    // ───────── 第 3 段：输出逻辑（读现态和输入，算出输出）─────────
    always @(*) begin
        z_next = (state == S3) && x;      // Mealy 输出：匹配完 1011 的那一拍
    end

    // 把输出寄存一拍：输出与时钟对齐，毛刺被彻底切断
    always @(posedge clk or negedge rst_n) begin
        if (!rst_n) z <= 1'b0;
        else        z <= z_next;
    end

endmodule

// 【为什么第 2 段里那行「先给默认值」的位置这么重要】
//   Verilog 的组合 always 块有一个规则：
//   如果某条路径下某个信号【没有被赋值】，综合工具就认为
//   「这种情况下它要保持原值」→ 于是给你推一个锁存器（latch）出来。
//   锁存器是电平敏感的，会带来毛刺和时序分析困难 —— 这是新手
//   最常见的综合警告「inferred latch」的来源。
//   把默认值写在 case 之前，保证每一次执行都给 state_next 赋了值，
//   既消灭了锁存器，又顺手做完了非法状态的安全处理。

好消息是：C 语言里也能写出同样结构的「三段式」。这不是文字游戏——把三段式的思想搬到单片机上，你的状态机代码会变得同样清晰、同样好测。下一节的每一段代码都会用这个结构：

typedef enum { S0 = 0, S1, S2, S3 } st_t;

static st_t state = S0;      /* ← 第 1 段：状态寄存器（就是那个变量） */

/* ── 第 2 段：次态逻辑 —— 纯函数，只算「下一拍去哪」，不碰任何硬件 ── */
static st_t next_state(st_t s, bool x)
{
    switch (s) {
    case S0:  return x ? S1 : S0;
    case S1:  return x ? S2 : S1;
    case S2:  return x ? S3 : S0;
    case S3:  return x ? S2 : S1;
    default:  return S0;            /* 非法状态自恢复 */
    }
}

/* ── 第 3 段：输出逻辑 —— 只看现态（和输入），产生动作 ── */
static void output(st_t s, bool x)
{
    if (s == S3 && x) {
        report_detected();          /* 动作集中在这里，一目了然 */
    }
}

/* ── 第 1 段的搬运：一个 tick 执行一次 ── */
void fsm_tick(bool x)
{
    st_t n = next_state(state, x);  /* 先算次态 */
    output(state, x);               /* 再按【现态】输出 */
    state = n;                      /* 最后才搬运 —— 顺序不能颠倒 */
}

/* 【为什么 fsm_tick 里的顺序不能颠倒】
   如果你先写 state = next_state(state, x); 再调用 output(state, x)，
   那么 output 拿到的已经是【新状态】，输出的语义就从 Moore 变成了
   「提前一拍」。这一拍的差别，在 Mealy 型状态机上会直接导致
   输出脉宽不对、甚至多输出/少输出一次。 */
三段式在软件里的三个具体好处

① next_state() 是一个纯函数，可以单独测试。给它一个状态和一个输入，它返回一个状态，没有任何副作用——这意味着你可以在 PC 上写单元测试，把状态转移表逐格验证一遍，不需要单片机、不需要按键。

② 输出动作集中在 output() 里，找 bug 时只看一处。「为什么这个灯该亮没亮」这个问题，答案永远在 output() 里，不会散落在十几个 if 中间。

③ 状态迁移只在一个地方发生。整个工程里对 state 赋值的地方只有 fsm_tick() 里那一行。你可以用这个性质做静态检查：搜索一下 state = 出现了几次，多一处就多一个隐患。

例一：「1011」序列检测器，从状态图一路走到电路

需求：有一路串行数据 X，每个时钟周期来一位。当输入序列中最近四位恰好是 1 0 1 1 时，输出一个脉冲。允许重叠（1011011 里应该检测到两次）。

第 1 步：定状态。序列检测器的状态定义有一个固定套路——用状态表示「已经匹配了模式的多长前缀」。模式 1011 的前缀有四个：空、1、10、101。所以需要四个状态：

状态含义
S0还没匹配上任何东西（初始态）：最近一位不是 1
S1已经匹配了 1
S2已经匹配了 10
S3已经匹配了 101

第 2 步：给每个状态画全两条出边（X=0 和 X=1）。这一步的规矩是：遇到「不匹配」时，不能一律回到 S0，而要回到「丢失最少、还能继续用」的那个状态——也就是最长的、仍然是模式前缀的那个后缀。这是序列检测器最容易错的地方。

同一个需求换成 Moore 型：多一个触发器，换来一个「干净」的输出

Moore 型要求输出只由状态决定，所以「已经匹配完整的 1011」这件事必须自己变成一个状态 S4：

现态输出 ZX = 0 → 次态X = 1 → 次态
S0（空前缀）0S0S1
S1（「1」）0S2S1
S2（「10」）0S0S3
S3（「101」）0S2S4
S4（「1011」）1S2S1

编码：S0 = 000、S1 = 001、S2 = 010、S3 = 011、S4 = 100。输出方程变成 Z = Q2 · Q1' · Q0'——里面没有 X，这正是 Moore 的定义。

两版对比：Mealy 版 4 状态 / 2 触发器 / 6 门 / 输出与输入同拍；Moore 版 5 状态 / 3 触发器 / 输出滞后一拍但脉宽精确。而且 Moore 版用 3 位编码 5 个状态，多出 3 个非法状态（101、110、111），次态逻辑里必须显式把它们指向 S0——这是「多一个状态」的隐藏代价，很多人在数触发器的时候忘了算。

例二：交通灯状态机——状态表示阶段，计数表示时间

需求：东西向（EW）和南北向（NS）两组灯，每组红/黄/绿三色。一个完整周期：

阶段EW 灯NS 灯持续时长为什么这么设计
①绿红30sEW 是主干道，放行时间长
②黄红3s黄灯是「即将变红」的预告
③红红1s全红安全间隔：清空路口里还没走完的车
④红绿20sNS 是支路
⑤红黄3s—
⑥红红1s另一侧的清空间隔

先算周期和占空比（这些数字后面要用来验证）：

【总周期】
   T = 30 + 3 + 1 + 20 + 3 + 1 = 58 s

【每个方向的通行时间】
   EW 绿 = 30 s          EW 黄 = 3 s       EW 红 = 58 − 30 − 3 = 25 s
   NS 绿 = 20 s          NS 黄 = 3 s       NS 红 = 58 − 20 − 3 = 35 s

   验算：EW 红应该等于「NS 绿 + NS 黄 + 两个全红」
        = 20 + 3 + 1 + 1 = 25 s ✓ 对上了

【通行效率】
   EW 绿信比 = 30 / 58 = 51.7%
   NS 绿信比 = 20 / 58 = 34.5%
   黄灯占比   =  6 / 58 = 10.3%
   全红占比   =  2 / 58 =  3.4%

【如果不用状态机，用「延时」实现会怎样】
   while(1) { EW绿; delay(30); EW黄; delay(3); 全红; delay(1); ... }
   6 个 delay 加起来 58 秒不响应任何东西 —— 紧急车辆来了也没法插队，
   行人按钮按了也不知道。这就是第 1 节那个「世界消失」的放大版。

关键设计决策一：两个「全红」不能合并。阶段③和阶段⑥的输出一模一样（EW 红 + NS 红），但它们不等价——③ 的下一个状态是「NS 绿」，⑥ 的下一个状态是「EW 绿」。次态不同 → 不能合并。这是状态化简里最容易犯的错：只看输出就合并。

关键设计决策二：时间不能用状态来表示。这是新手最容易做错的一步。30 秒意味着 30 个 1 秒的时钟节拍，如果你用状态去数它，就要画 30 个状态！正确做法是：

【错误做法】用状态表示每一个节拍

    S0(EW绿第1秒) → S1(EW绿第2秒) → … → S29(EW绿第30秒) → S30(EW黄第1秒) → …
    → 一共 58 个状态！
    → 触发器要 ⌈log2 58⌉ = 6 个（编码位宽从 3 位暴涨到 6 位）
    → 状态表从 6 行变成 58 行，卡诺图从 4 变量变成 7 变量
    → 任何一个「改一下绿灯时长」的需求，都要重画整张图

【正确做法】状态机管「阶段」，一个倒计时计数器管「还要等多久」

    ┌──────────────────────────────┐
    │  状态机：6 个状态、3 个触发器  │
    │  S0: EW绿  S1: EW黄  S2: 全红 │
    │  S3: NS绿  S4: NS黄  S5: 全红 │
    └───────────────┬──────────────┘
                    │ 进入一个状态时，装载该阶段的时长
                    ▼
    ┌──────────────────────────────┐
    │  倒计时计数器（一个 6 位寄存器）│
    │  每个 1Hz 节拍减 1            │
    │  减到 0 → 产生「阶段结束」事件 │
    └───────────────┬──────────────┘
                    │ 事件
                    └──────► 回到状态机，触发状态转移

    ★ 这条原则在单片机代码里同样成立，而且更重要：
      「状态表示我在做什么，变量表示我做了多久、做了几次」
      把「计时 / 计数」塞进状态里，是状态数量爆炸的头号原因。
      对应的 C 代码就长这样：
          case ST_EW_GREEN:
              if (--tick_left == 0) { tick_left = 3; st = ST_EW_YELLOW; }
              break;
      状态只有 6 个，而 30 这个数字只是一个可以随便改的常量。

列状态表、编码、求方程。6 个状态用 3 位二进制 Q2 Q1 Q0，按 000 → 001 → 010 → 011 → 100 → 101 顺序循环（就是模 6 计数），剩余的 110、111 是非法码，强制回 000：

【状态转移表：8 行全列，包括两个非法码】

   现态 Q2Q1Q0   阶段            次态 Q2*Q1*Q0*   D2  D1  D0
   ─────────────────────────────────────────────────────────
      000        ① EW绿  30s        001           0   0   1
      001        ② EW黄   3s        010           0   1   0
      010        ③ 全红   1s        011           0   1   1
      011        ④ NS绿  20s        100           1   0   0
      100        ⑤ NS黄   3s        101           1   0   1
      101        ⑥ 全红   1s        000           0   0   0
      110        【非法】            000           0   0   0   ← 安全编码
      111        【非法】            000           0   0   0   ← 安全编码

【对 D2、D1、D0 各画一张卡诺图，圈 1 得：】

   D2 = Q2' · Q1 · Q0  +  Q2 · Q1' · Q0'      （只在 011 和 100 两行是 1）
   D1 = Q2' · ( Q1 ⊕ Q0 )                     （只在 001 和 010 两行是 1）
   D0 = Q0' · ( Q2' + Q1' )                   （在 000、010、100 三行是 1）

   验算 D0 的三行：
     000 → D0 = 1 · (1 + 1) = 1，次态最低位是 1 ✓（001）
     010 → D0 = 1 · (1 + 0) = 1 ✓（011）
     100 → D0 = 1 · (0 + 1) = 1 ✓（101）
     110 → D0 = 1 · (0 + 0) = 0 ✓（强制 000）
     111 → D0 = 0 · (…) = 0 ✓
     ✓ 全部对上，而且两个非法码在【一个时钟内】就回到了 000。
       这就是安全编码的效果：不是「祈祷它不要发生」，
       而是「发生了也自动爬回来」。

【输出方程（1 = 亮）】

   EW 绿  EW_G = Q1' · Q0'          （只有 000：Q2 无所谓？
                                      不行，000 和 100 的 Q1Q0 都是 00，
                                      所以还要乘 Q2'）
           EW_G = Q2' · Q1' · Q0'
   EW 黄  EW_Y = Q2' · Q1' · Q0
   NS 绿  NS_G = Q2' · Q1  · Q0
   NS 黄  NS_Y = Q2  · Q1' · Q0'
   EW 红  EW_R = Q1 ⊕ Q2            （EW 不通行 = 010、011、100、101）
   NS 红  NS_R = ( NS_G + NS_Y )'   （NS 不通行 = 除 011、100 以外全部）

验证 EW_R = Q1 ⊕ Q2：逐行代进去看——000（EW绿）→ 0⊕0 = 0 ✓；001（EW黄）→ 0⊕0 = 0 ✓；010（全红）→ 1⊕0 = 1 ✓；011（NS绿）→ 1⊕0 = 1 ✓；100（NS黄）→ 0⊕1 = 1 ✓；101（全红）→ 0⊕1 = 1 ✓。六行全对。一个 XOR 门就搞定了红灯，这就是卡诺图化简的实惠。

最后对比一下两种编码方案在这道题上的成本：

触发器数量3 个6 个（一个状态一位）

例三：隐含表化简——5 个状态压到 4 个，顺手把非法状态清零

题目：下面是一台已经画好的 Mealy 型状态机（1 位输入 X，1 位输出 Z）。请用隐含表法化简，并算出化简前后触发器数量的变化。

现态X = 0：次态 / 输出X = 1：次态 / 输出
S0S0 / 0S1 / 0
S1S2 / 0S4 / 0
S2S0 / 0S3 / 0
S3S2 / 0S1 / 1
S4S2 / 0S1 / 0

第 1 步：画隐含表。5 个状态 → 5×4/2 = 10 个格子。行是 S1~S4，列是 S0~S3，第 i 行第 j 列的格子代表状态对 (Si, Sj)：

                 S0          S1          S2          S3
            ┌───────────┬───────────┬───────────┬───────────┐
      S1    │  S2S0     │           │           │           │
            │  S4S1     │     —     │           │           │
            ├───────────┼───────────┼───────────┼───────────┤
      S2    │  S3S1     │     ✗     │     —     │           │
            ├───────────┼───────────┼───────────┼───────────┤
      S3    │     ✗     │     ✗     │     ✗     │     —     │
            ├───────────┼───────────┼───────────┼───────────┤
      S4    │  S0S2     │     ?     │  S0S2     │     ✗     │
            │           │           │  S1S3     │           │
            └───────────┴───────────┴───────────┴───────────┘

  【第一遍打叉的依据（判据一：输出一致）】
     (S3,S0)：S3 在 X=1 时输出 1，S0 输出 0 → 输出不同 → ✗
     (S3,S1)：S3 在 X=1 时输出 1，S1 输出 0        → ✗
     (S3,S2)：S3 在 X=1 时输出 1，S2 输出 0        → ✗
     (S2,S1)：X=0 时 S2→S3、S1→S2，这一步输出都是 0，
              所以要靠【次态对】判断（见下面第 3 步）
     (S4,S3)：S4 在 X=1 时输出 0，S3 输出 1        → ✗

  【格子里填的是什么】
     每个输入列出一对「次态对」：
     (S1,S0)：X=0 → S1 去 S2、S0 去 S0，写「S2S0」
              X=1 → S1 去 S4、S0 去 S1，写「S4S1」
     意思：只要 S2≡S0 且 S4≡S1，那么 S1≡S0。
     这就是判据二的依赖关系 —— 一个「如果…那么…」的链条。

第 3 步：迭代打叉。规则只有一条：格子里列出的任何一个次态对如果已经被打叉，这一格也打叉。反反复复做，直到不再有新的叉出现：

【第一轮迭代】
   (S2,S1) 依赖 { S0S2, S3S4 }
           → S3S4 就是 (S4,S3)，它已经打叉了 → (S2,S1) 也打叉 ✗

   (S4,S2) 依赖 { S0S2, S1S3 }
           → S1S3 就是 (S3,S1)，已打叉 → (S4,S2) 打叉 ✗

   (S1,S0) 依赖 { S2S0, S4S1 }
           → 两个依赖目前都还活着 → 暂留
   (S2,S0) 依赖 { S3S1 }
           → (S3,S1) 已打叉 → (S2,S0) 打叉 ✗
   (S4,S0) 依赖 { S0S2 }
           → (S2,S0) 刚刚打叉了 → (S4,S0) 也打叉 ✗

【第二轮迭代】
   (S1,S0) 依赖 { S2S0, S4S1 }
           → (S2,S0) 这一轮已经打叉 → (S1,S0) 打叉 ✗

【第三轮迭代】没有新的叉了，矩阵稳定。

【最终结果：只剩一个格子活着】

   (S4,S1) —— 它的依赖是：
        X=0：S4 去 S2、S1 去 S2  → 次态【相同】，自动满足 ✓
        X=1：S4 去 S1、S1 去 S4  → 次态对是 (S1,S4)，
                                   也就是【它自己】！
        自己依赖自己 —— 这种「循环依赖」的处理办法是：
        先假设它成立，然后检查有没有矛盾。这里没有任何矛盾
        （输出一致 + 依赖闭合），所以假设成立。

   ⇒ S1 ≡ S4，可以合并。

【合并后的状态表（5 个状态 → 4 个状态）】

        现态         X = 0：次态 / 输出     X = 1：次态 / 输出
     ─────────────┼────────────────────┼────────────────────
        S0        │      S0 / 0        │      S1 / 0
       S1 (= S4)  │      S2 / 0        │      S1 / 0     ← 自环！
        S2        │      S0 / 0        │      S3 / 0
        S3        │      S2 / 0        │      S1 / 1

   注意合并带来的一个额外好处：原来 S1 --X=1--> S4 这条边，
   合并之后变成了 S1 --X=1--> S1 的【自环】，次态方程更简单了。

二进制 S0=00 S1=01 S2=10 S3=1122 张 3 变量卡诺图，约 6 个门Mealy，逐边译码，约 4 个门0合适（CPLD/ASIC 首选）
独热 0001 0010 0100 10004每位 = 入边的或，4 个门，路径只有 1 级0 个门（状态位直接就是译码结果）24 − 4 = 12 个FPGA 上合适；CPLD 上浪费

为什么这道题格雷码不合适：不是所有状态图都能排出格雷序

格雷码的好处（只翻一位）有一个前提：状态转移图必须是一条链或者一个环，这样才能顺着格雷码的顺序排下去。而这道题化简后的转移图里有两个三元环：S0→S1→S2→S0 和 S1→S2→S3→S1。

2 位格雷码只有 4 个码，构成一个 4 步的环 00→01→11→10→00。你想把任何三个状态排在环上的连续三段里，第三条边（回到起点的那条）必然要跨两位。逐个试各种分配方案会发现：这道题里至少有两条边无论如何都要两位同时翻转。

所以这里老老实实用二进制。记住这条判据：转移图是「链条/环」才用格雷，是「网状」就用二进制（或者独热，看载体）。

例四：最高时钟频率预算——顺便发现一个保持时间违例

题目：用例一的电路（D1 = Q0·X' + Q1·Q0'·X，D0 = X）搭一台真实的硬件状态机，用 74LVC74 双 D 触发器（3.3V 供电）。求它能跑多快，并检查两条时序约束。

先列器件参数。下面这些是 74LVC 系列在 3.3V、负载 15pF 条件下的典型量级（按典型值估算，不是数据手册的保证值；真做设计必须查手册里的 min/max 列）：

参数符号典型值含义
时钟到输出延迟tcq5 ns（最大）时钟沿来了之后，Q 稳定到新值要多久
建立时间tsetup1.5 nsD 要在时钟沿之前稳定这么久
保持时间thold1 ns时钟沿之后 D 还要保持这么久
单门传播延迟tpd4 ns一级逻辑门（AND/OR）的延迟
时钟偏斜tskew1 ns同一个时钟到达两个触发器的时间差（按走线长度差 15cm 估）

第一件事：数出最长的组合逻辑路径。看 D1 的方程 Q0·X' + Q1·Q0'·X：

【最长路径：到 D1】

   Q0 ──────────────►┌────────┐
                     │ AND2   │──┐
   X ──►[NOT]──X'───►└────────┘  │
                                 ├──►┌────────┐
   Q1 ──────────────►┌────────┐  │   │  OR2   │──► D1
                     │ AND3   │──┘   └────────┘
   Q0 ──►[NOT]─Q0'──►│        │
   X ───────────────►└────────┘
                          ↑
              这一条路上有：反相器 → 3 输入与门 → 或门
              = 3 级门 = 3 × 4ns = 12 ns

   ★ 反相器的延迟比普通门略小，这里保守地按一级门算。

   所以  t_logic(max) = 12 ns

【最短路径：到 D0】

   X ─────────────────────────────────────────────► D0
              一根线直接连过去，中间【没有任何门】
   所以  t_logic(min) = 0 ns

   ★ 这一条「太短」的路径，正是下面保持时间违例的根源。

第二件事：算最高频率（建立时间约束）。

   T_clk(min) ≥ t_cq + t_logic(max) + t_setup + t_skew
             = 5 ns + 12 ns + 1.5 ns + 1 ns
             = 19.5 ns

   f_max = 1 / 19.5ns = 51.3 MHz

【占时比例分析】
   触发器自己的开销   t_cq + t_setup = 5 + 1.5 = 6.5 ns   占 33%
   组合逻辑           t_logic       = 12 ns            占 62%
   时钟偏斜           t_skew        = 1 ns             占  5%

   ⇒ 想跑更快，最有效的办法是【缩短组合逻辑路径】。
     把 3 级门砍成 2 级（比如找等价方程、或共享公共项），
     t_logic 从 12ns 降到 8ns，T 就变成 15.5ns，f_max 升到 64.5MHz。
     —— 这就是卡诺图化简不只是"省门"，更是"提速"的原因。

【要不要流水线？】
   如果 51MHz 还不够，可以在组合逻辑中间插一级触发器（流水线）。
   代价是状态机的语义变了：输出会晚一拍，而且「一个状态转移」
   变成需要两个时钟周期才能完成。状态机加流水线要非常小心，
   它不再是「一个时钟走一条边」了。

第三件事：检查保持时间约束。这一步很多人会跳过，然后遇到「降频就好了、升频反而正常」的怪现象：

   要求：  t_cq(min) + t_logic(min) ≥ t_hold + t_skew

   代入（t_cq 的最小值按 1.5ns 估 —— 触发器输出可能"跑得很快"）：
           1.5 ns  +  0 ns      ≥  1 ns + 1 ns
           1.5 ns               ≥  2 ns        ✗ 违反！

   ★ 违例了。D0 = X 这条路径只有一个「0 级门」，
     时钟沿一到，触发器 A 把新状态推出去（1.5ns），
     而 X 这根线上的新数据几乎是立刻就到了触发器 B 的 D 端。
     但触发器 B 此刻还在保持窗口里没"松手"，
     于是它可能把【新】数据当成【旧】数据采进去 —— 状态机少走一步。

   ★ 关键点：这条约束和时钟频率【完全无关】。
     你把时钟降到 1Hz，这个违例依然存在。
     这就是为什么有些板子"降频也没用"。

【解决办法：给这条路径人为加延迟】

   X ──►[BUF]──►[BUF]──► D0        两个缓冲器 ≈ 7 ns

   再验算：1.5 + 7 = 8.5 ns ≥ 2 ns  ✓ 通过，还留了 6.5ns 余量。
   加两个缓冲器可以用一片 74LVC34（六缓冲器）里多余的两个门，
   也可以用综合工具自动插入（这叫「fix hold」，DC / Vivado 都能做）。

【如果换成低速的老器件呢？】

   用 74HC74（4.5V 供电，典型值）：
     t_cq = 15 ns   t_setup = 20 ns   t_pd = 15 ns   t_skew = 2 ns

   t_logic(max) = 3 级 × 15ns = 45 ns（HC 系列门延迟本来就大）
   T_clk(min) = 15 + 45 + 20 + 2 = 82 ns  →  f_max = 12.2 MHz

   ⇒ 同一台状态机，换器件从 51MHz 掉到 12MHz。
     「我的逻辑是对的，为什么跑不起来」—— 答案常常在这里。

【和单片机软件状态机比一比】

   STM32F103 @ 72MHz，用 C 写同一台状态机（放在 1kHz 定时器中断里）：
     中断响应（含入栈）        约 12 个时钟周期
     switch 分支 + 次态计算     约 10 ~ 30 个时钟周期
     输出动作（写 GPIO）        约 5 ~ 10 个时钟周期
     ─────────────────────────────────────────
     合计约 30 ~ 50 个时钟周期 = 0.42 ~ 0.69 µs

   ⇒ 软件状态机的一次转移要 0.5µs 量级，硬件只要 20ns 量级 ——
     差了大约 25~35 倍，也就是【一个半数量级】。
     所以判据是：
       · 响应延迟要求 > 10µs、事件间隔 > 100µs → 软件状态机完全够
       · 响应延迟要求 < 1µs、或者输入频率 > 几 MHz → 该上 CPLD/FPGA
       · 中间地带（比如伺服控制环、高速编码器）→ 用硬件外设
         （定时器、DMA、比较器）配合软件状态机
这一节四道题，各留了一句话给你

例一：「状态 = 已匹配的模式前缀长度」是序列检测器的万能套路；失配时回到最长的可用后缀，是它唯一的难点。

例二：输出相同的状态不一定能合并（次态不同就不行）；而状态机只该表示「阶段」，时间要用计数器，否则状态数会爆炸。

例三：隐含表的价值在于「不漏」——10 个格子摆在那里，你不可能漏掉任何一对；而化简的真正红利，是把非法状态从 3 个变成 0 个。

例四：时序有两条约束，一条管「不能太慢」，一条管「不能太快」。第二条和频率无关——这是很多人一辈子都没搞明白的一个坑。

在单片机上的样子

前面三节讲的都是「电路上的状态机」。这一节要把它搬到单片机上——你会发现同一套方法一个字都不用改，只是「状态寄存器」变成了一个变量，「时钟沿」变成了一个 tick，「组合逻辑」变成了一个 switch。下面每一段代码都是完整、可以直接编译运行的，不是伪代码。硬件相关的部分（读时间、读电平、写 IO）全部集中在三个小函数里，你在自己板子上补上这三个函数就能跑。

为什么裸机程序终究要写成状态机：从「阻塞闪灯」说起

所有裸机教程的第一个程序都是闪灯，第二个程序都是「按键控制闪灯」。而几乎所有的教程都会在这个地方给你一段会崩掉的代码：

/* ============================================================
 * blinky_blocking.c —— 「阻塞版」闪灯 + 按键
 *
 * 需求：① LED 每 1000ms 翻转一次
 *       ② 按住按键时，翻转周期切换成 100ms
 *
 * 这个版本是错的。它看起来能跑，实际上是靠运气。
 * ============================================================ */
#include <stdint.h>
#include <stdbool.h>

void board_init(void);          /* 你的板级初始化：时钟、GPIO */
bool key_is_pressed(void);      /* 读按键（这里故意不消抖） */
void led_toggle(void);

/* 粗糙的忙等延时：CPU 在这段时间里只在做一件事 —— 数数 */
void delay_ms(uint32_t ms)
{
    /* 72MHz 下大约每毫秒 7200 次循环（具体值随优化等级而变） */
    for (volatile uint32_t i = 0; i < ms * 7200u; i++) {
        /* 空转 */
    }
}

int main(void)
{
    static uint32_t period = 1000;      /* 当前闪烁周期，单位 ms */

    board_init();

    for (;;) {
        /* ★ 只有执行到这一行的那一瞬间，按键才有可能被看到 */
        if (key_is_pressed()) {
            period = (period == 1000u) ? 100u : 1000u;
        }

        led_toggle();
        delay_ms(period);               /* ← 灾难在这一行 */
    }
}

它错在哪？错在「阻塞 1 秒 = 这一秒里世界消失了」。把时间轴画出来就一目了然——假设读一次按键需要 1µs：

每个刻度 = 100ms，一整行 = 1 秒

主循环：
  [读按键][LED翻转][———————— 忙着数数 1000ms ————————][读按键][LED翻转][— …
   ↑1µs                                    ↑
   只有这一个点在看按键                     这一整段里发生了什么，
                                          程序完全不知道

用户在别处按下按键 300ms：
  [读按键][LED翻转][———————— 忙着数数 ————————][读按键][LED翻转][— …
                               ▓▓▓▓▓▓▓
                               └─ 用户按了 300ms，程序根本没看，
                                  这次按键【彻底消失】

【算一下捕获概率】
  主循环一圈              ≈ 1000ms + 几十微秒 ≈ 1000ms
  每次读按键占用的时间      ≈ 1µs
  人按下按键的持续时间      典型 50 ~ 150ms（颤抖的老人可能 300ms）

  捕获概率 = 按键时长 / 主循环周期
           = 100ms / 1000ms = 10%          ← 按 10 次只认出 1 次
           用 50ms 的轻点 = 5%              ← 按 20 次只认出 1 次

  而且这还是乐观估计：即使"看"到了，一次未消抖的采样也可能
  正好采在抖动的中间，读到的是弹起的电平 —— 那就白看了。

【更糟的是，这个 bug 会伪装成别的问题】
  · 「按键不灵敏」→ 你以为要换按键、加电容
  · 「偶尔没反应」→ 你以为电源不稳、接触不良
  · 真正的原因：程序 99.9999% 的时间根本没在听

【再加一个需求，立刻就崩】
  「按键要响应，同时串口收到的数据也不能丢。」
  阻塞版做不到 —— 因为 delay_ms(1000) 执行的时候，
  串口来 10 个字节都不会有人去拿，硬件 FIFO 只有几个字节深，
  多出来的字节直接被硬件丢掉。这不是"写得不好"，是"结构上做不到"。

现在看正确写法。同一个需求，改成一个状态机 + 一个时间戳，主循环一圈只要几微秒：

/* ============================================================
 * blinky_fsm.c —— 非阻塞状态机版闪灯（可以直接编译运行）
 *
 * 硬件相关只剩下面三个函数，你在自己板子上把它们实现掉就行：
 *     uint32_t tick_ms(void);        开机以来的毫秒数（无符号 32 位）
 *     bool     key_raw(void);        按键的原始电平，true = 按下
 *     void     led_write(bool on);   写 LED
 *
 * 编译：gcc -std=c99 -Wall -Wextra blinky_fsm.c -o blinky
 * ============================================================ */
#include <stdint.h>
#include <stdbool.h>

/* ---------- 移植层：只有这三个函数和硬件有关 ---------- */
extern uint32_t tick_ms(void);
extern bool     key_raw(void);
extern void     led_write(bool on);
void board_init(void);

/* ---------- 1. 常量：把"魔法数字"集中到一处 ---------- */
#define LED_SLOW_MS   1000u
#define LED_FAST_MS    100u

/* ---------- 2. 状态集合：一共只有 4 个状态 ---------- */
typedef enum {
    ST_LED_OFF = 0,     /* LED 灭，在等"该亮了"的时刻 */
    ST_LED_ON           /* LED 亮，在等"该灭了"的时刻 */
} led_st_t;

typedef enum {
    KEY_IDLE = 0,       /* 按键没按下（这里的消抖是简化版） */
    KEY_DOWN            /* 按键按下 */
} key_st_t;

/* ---------- 3. 状态变量（就是"状态寄存器"） ---------- */
typedef struct {
    led_st_t led_state;
    uint32_t led_stamp;     /* 进入当前 LED 状态的时刻 */

    key_st_t key_state;

    bool     fast_mode;     /* 当前是慢闪还是快闪 */
} app_t;

static app_t app;

/* ============================================================
 *  第 2 段：次态逻辑 —— 纯计算，不碰任何硬件
 * ============================================================ */
static led_st_t led_next_state(const app_t *a, uint32_t now)
{
    uint32_t interval = a->fast_mode ? LED_FAST_MS : LED_SLOW_MS;

    switch (a->led_state) {
    case ST_LED_OFF:
        /* ★ 注意用的是【无符号减法】：即使 tick_ms() 溢出回绕，
           这个比较依然正确（详见后面的 millis 溢出小节） */
        if ((uint32_t)(now - a->led_stamp) >= interval) {
            return ST_LED_ON;
        }
        return ST_LED_OFF;

    case ST_LED_ON:
        if ((uint32_t)(now - a->led_stamp) >= interval) {
            return ST_LED_OFF;
        }
        return ST_LED_ON;

    default:                    /* 非法状态：一个 tick 之内自恢复 */
        return ST_LED_OFF;
    }
}

/* ============================================================
 *  第 3 段：输出逻辑 —— 只看现态，产生动作
 * ============================================================ */
static void led_output(const app_t *a)
{
    /* Moore 型：输出只取决于"现态"，与输入无关 —— 天然无毛刺 */
    led_write(a->led_state == ST_LED_ON);
}

/* ============================================================
 *  第 1 段的搬运：一个 tick 执行一次
 * ============================================================ */
void app_tick(uint32_t now)
{
    /* ---- 先处理输入事件（按键） ---- */
    bool pressed = key_raw();

    switch (app.key_state) {
    case KEY_IDLE:
        if (pressed) {
            app.key_state = KEY_DOWN;
        }
        break;
    case KEY_DOWN:
        if (!pressed) {
            /* 松手：切换快慢模式。
               这一小段消抖是故意简化的 —— 完整版见下一小节。 */
            app.fast_mode = !app.fast_mode;
            app.key_state = KEY_IDLE;
        }
        break;
    default:
        app.key_state = KEY_IDLE;
        break;
    }

    /* ---- 再推进 LED 状态机 ---- */
    {
        led_st_t n = led_next_state(&app, now);   /* ① 先算次态 */
        led_output(&app);                         /* ② 再按【现态】输出 */
        if (n != app.led_state) {                 /* ③ 最后搬状态 + 打时间戳 */
            app.led_state = n;
            app.led_stamp = now;
        }
    }
}

/* ============================================================
 *  主循环：一圈只要几微秒，跑几万圈才过 1 毫秒
 * ============================================================ */
int main(void)
{
    board_init();

    for (;;) {
        app_tick(tick_ms());        /* 没有任何 delay */
    }
}

/* ============================================================
 * 【两个版本摆在一起对比】
 *
 *                     阻塞版                 状态机版
 *   ────────────────┼─────────────────────┼──────────────────────
 *    一圈耗时        1000ms 量级            3 ~ 5µs
 *    每秒看按键      1 次                   20 万次以上
 *    100ms 的按键    10% 概率被看到         100% 被看到
 *    时间精度        靠循环次数，误差累积    靠时间戳，误差 = 一个 tick
 *    能不能加任务    不能                   想加几个加几个（见时间片小节）
 *    代码可测性      没法测                 状态 + 输入 → 状态，可枚举
 *
 *  ★ 关键改变只有一句话：
 *    把「等 1 秒」从一条【指令】（delay）变成了一次【判断】
 *    （now - stamp 够不够 1 秒）。指令一执行就把 CPU 交出去了，
 *    判断执行完 CPU 还是你的 —— 这就是"非阻塞"的全部秘密。
 * ============================================================ */
「非阻塞」的三个固定套路，记住就能改写任何阻塞代码
  1. 把「等」拆成「时间戳 + 判断」。delay(1000) → 记住 stamp = now，然后在每个 tick 里判断 (now - stamp) >= 1000。
  2. 把「顺序执行」拆成「状态 + 转移」。A(); delay(100); B(); → 两个状态：ST_A（做完 A，记时间戳）→ ST_B。中间那 100ms 归世界所有，不归 A 所有。
  3. 把「循环等条件」拆成「每个 tick 检查一次条件」。while (!flag); → if (flag) { 转移 } else { 留在原状态 }。顺手再加一个超时计数，因为「永远等不到」才是嵌入式里最常见的情况。

按键完整状态机：消抖 / 短按 / 长按 / 双击

按键是单片机里最典型的「有记忆的顺序行为」：你要判断的不是「此刻电平是高是低」，而是「从按下到现在过去了多久、中间有没有松手、松手之后有没有再按」。后面这些全都是状态，全都要记。

先看机械按键到底有多脏：

理想的按键波形          实际测到的波形（按下一次）

   ────────┐             ────┐┌─┐  ┌──┐┌──────────────
           │                 ││ │  │  ││
           └────────        ──┘└─┘  └──┘└──────────────
           ↑                            ↑
        干净的一个下降沿           抖动 0.5 ~ 5ms

  【抖动（bounce）的实测数字】
     金属弹片按键：典型抖动 0.5 ~ 5ms，差的能到 10ms 以上
     薄膜按键：    典型 1 ~ 10ms
     一次按下产生的"假边沿"：5 ~ 20 个

  【如果用「边沿检测」直接数】
     if (level != last_level) { count++; }   ← 一次按键 = count 加了 10 几次
     现象：「按一下，菜单跳了 8 格」。这就是抖动在代码里的样子。

  【如果用「延时 20ms 再读一次」】
     if (key_is_pressed()) { delay_ms(20); if (key_is_pressed()) { … } }
     · 能解决抖动（20ms 大于大多数按键的抖动时间）
     · 但付出的代价是：
        ① 这 20ms 里 CPU 什么都干不了 —— 世界又消失了
        ② 只知道"按下了"，不知道按了多久 → 做不出长按
        ③ 松手时还会抖一次，于是还要在松手处再 delay(20)
        ④ 两个按键就要 delay(40)，n 个按键线性恶化
        ⑤ 双击？两击之间的间隔可能只有 80ms，
           你在 delay(20) 的时候已经错过了时序

  【正确思路：把"抖动"当成状态机的一个状态】
     看到电平变化 → 不立刻相信 → 进入「疑似」状态
     → 等 8ms 再看 → 电平还在 → 确认；电平变回去了 → 是抖动，回空闲
     ★ 这 8ms 不需要 CPU "等"，它只是状态里的一个时间戳。

下面是完整的四事件按键状态机。分成 .h 和 .c 两个文件，加上一段 PC 上的测试代码，全部可以直接编译运行。

/* ============================================================
 * key_fsm.h —— 消抖 / 短按 / 长按 / 长按连发 / 双击
 * ============================================================ */
#ifndef KEY_FSM_H
#define KEY_FSM_H

#include <stdint.h>
#include <stdbool.h>

/* ---------- 时间常量：全部集中在这里，方便按手感调 ---------- */
#define KEY_DEBOUNCE_MS     8u      /* 消抖窗口：电平稳定这么久才算数 */
#define KEY_SHORT_MIN_MS    20u     /* 短按的最短时长（更短的当干扰丢掉） */
#define KEY_LONG_MS         800u    /* 长按判定阈值 */
#define KEY_REPEAT_MS       100u    /* 长按之后，每隔多久再报一次 */
#define KEY_DOUBLE_GAP_MS   300u    /* 双击窗口：松手后多久内再按算双击 */

typedef enum {
    KEY_EV_NONE = 0,        /* 什么都没发生 —— 绝大多数 tick 都是它 */
    KEY_EV_SHORT,           /* 短按 */
    KEY_EV_LONG,            /* 长按【刚】达到阈值，只报一次 */
    KEY_EV_LONG_REPEAT,     /* 长按持续中，每隔 KEY_REPEAT_MS 报一次 */
    KEY_EV_DOUBLE           /* 双击 */
} key_event_t;

typedef enum {
    KS_IDLE = 0,        /* 空闲：等按下 */
    KS_DEBOUNCE,        /* 疑似按下：等电平稳定 */
    KS_PRESSED,         /* 已按下：数长按，等松手 */
    KS_WAIT_DOUBLE,     /* 已松手：等一个双击窗口 */
    KS_DEBOUNCE2        /* 疑似第二击：同样要消抖 */
} key_state_t;

typedef struct {
    key_state_t st;
    uint32_t    t_stamp;        /* 进入当前状态的时刻 */
    uint32_t    t_press;        /* 按键被"确认按下"的时刻 */
    uint32_t    t_last;         /* 上一次长按连发的时刻 / 第二击消抖起点 */
    bool        long_reported;  /* 本次按下的长按是否已经报过 */
    bool        is_second;      /* 本次按下是不是双击的第二击 */
} key_fsm_t;

/* 初始化：必须在开始 tick 之前调用一次 */
void        key_fsm_init(key_fsm_t *k, uint32_t now);

/* 每 1ms 调用一次（更快也行，更慢会掉手感）。
   raw_level：按键的【原始】电平，true = 按下（低电平有效的按键请自行取反）
   now      ：当前的毫秒时间戳
   返回     ：本次 tick 产生的事件，没有事件就返回 KEY_EV_NONE */
key_event_t key_fsm_tick(key_fsm_t *k, bool raw_level, uint32_t now);

#endif /* KEY_FSM_H */
/* ============================================================
 * key_fsm.c —— 按键状态机实现
 * ============================================================ */
#include "key_fsm.h"

/* 时间到了吗？
 * ★ 一定写成无符号减法。tick_ms() 到了 0xFFFFFFFF 会回绕到 0，
 *   如果用 now >= start + ms，回绕的那一刻就会算错一次；
 *   而无符号减法的结果【永远是真实的差值】，自动免疫回绕。 */
static bool elapsed(uint32_t now, uint32_t since, uint32_t ms)
{
    return (uint32_t)(now - since) >= ms;
}

void key_fsm_init(key_fsm_t *k, uint32_t now)
{
    k->st             = KS_IDLE;
    k->t_stamp        = now;
    k->t_press        = now;
    k->t_last         = now;
    k->long_reported  = false;
    k->is_second      = false;
}

key_event_t key_fsm_tick(key_fsm_t *k, bool raw_level, uint32_t now)
{
    key_event_t ev = KEY_EV_NONE;

    switch (k->st) {

    /* ---------------- 空闲：等按下 ---------------- */
    case KS_IDLE:
        if (raw_level) {
            k->st      = KS_DEBOUNCE;      /* 看到变化，先别信 */
            k->t_stamp = now;
        }
        break;

    /* ---------------- 疑似按下：等电平稳定 ---------------- */
    case KS_DEBOUNCE:
        if (!raw_level) {
            k->st = KS_IDLE;               /* 弹回去了 → 是抖动 */
        } else if (elapsed(now, k->t_stamp, KEY_DEBOUNCE_MS)) {
            k->st            = KS_PRESSED; /* 稳定了 → 确认按下 */
            k->t_press       = now;
            k->long_reported = false;
            k->is_second     = false;
        }
        break;

    /* ---------------- 已按下：数长按，等松手 ---------------- */
    case KS_PRESSED:
        if (!raw_level) {
            /* ===== 松手了，判断这是一次什么样的点击 ===== */
            uint32_t held = (uint32_t)(now - k->t_press);

            if (k->is_second) {
                k->st = KS_IDLE;           /* 双击的第二击：已经报过 DOUBLE 了 */
            } else if (held >= KEY_LONG_MS) {
                k->st = KS_IDLE;           /* 长按已报过，松手不再报短按 */
            } else if (held >= KEY_SHORT_MIN_MS) {
                k->st      = KS_WAIT_DOUBLE;   /* 先别急着报，等等看有没有第二击 */
                k->t_stamp = now;
            } else {
                k->st = KS_IDLE;           /* 短于 20ms，当干扰丢掉 */
            }
        } else {
            /* ===== 还按着，看有没有到长按 ===== */
            uint32_t held = (uint32_t)(now - k->t_press);

            if (held >= KEY_LONG_MS) {
                if (!k->long_reported) {
                    ev = KEY_EV_LONG;      /* 长按达成，报一次 */
                    k->long_reported = true;
                    k->t_last = now;
                } else if (elapsed(now, k->t_last, KEY_REPEAT_MS)) {
                    ev = KEY_EV_LONG_REPEAT;   /* 之后每 100ms 报一次 */
                    k->t_last = now;
                }
            }
        }
        break;

    /* ---------------- 松手后：等双击窗口 ---------------- */
    case KS_WAIT_DOUBLE:
        if (raw_level) {
            k->st     = KS_DEBOUNCE2;      /* 第二击来了，同样要消抖 */
            k->t_last = now;               /* t_stamp 留着，窗口时间不能重置 */
        } else if (elapsed(now, k->t_stamp, KEY_DOUBLE_GAP_MS)) {
            ev     = KEY_EV_SHORT;         /* 窗口过完，第一击就是一次短按 */
            k->st  = KS_IDLE;
        }
        break;

    /* ---------------- 疑似第二击：消抖 ---------------- */
    case KS_DEBOUNCE2:
        if (!raw_level) {
            k->st = KS_WAIT_DOUBLE;        /* 又是抖动，回窗口里继续等 */
        } else if (elapsed(now, k->t_last, KEY_DEBOUNCE_MS)) {
            ev           = KEY_EV_DOUBLE;  /* 确认双击 */
            k->st        = KS_PRESSED;     /* 继续当作"已按下"，长按依然可用 */
            k->t_press   = now;
            k->is_second = true;
            k->long_reported = false;
        }
        break;

    /* ---------------- 非法状态：一个 tick 内自恢复 ---------------- */
    default:
        k->st = KS_IDLE;
        break;
    }

    return ev;
}

注意上面代码里两个不起眼但极重要的小设计：① is_second 这个标志——如果少了它，双击之后松手会走到 KS_WAIT_DOUBLE，300ms 后再报一次 KEY_EV_SHORT，于是「一次双击」变成「双击 + 短按」，菜单会多跳一格。这正是状态机代码最容易出的那类 bug：漏掉一条边，或者两个状态共用了本该分开的出口。② KS_DEBOUNCE2 用 t_last 记消抖起点而不碰 t_stamp——因为 t_stamp 还担着「双击窗口从第一击松手开始算」的职责，被覆盖掉窗口就会变长，手感发飘。

/* ============================================================

{

    case KEY_EV_NONE:        return "NONE";
    case KEY_EV_SHORT:       return "SHORT";
    case KEY_EV_LONG:        return "LONG";
    case KEY_EV_LONG_REPEAT: return "LONG_REPEAT";

static int run_case(const test_case_t *tc)
{
    key_fsm_t   k;
    uint32_t    now = 0;
    key_event_t got;
    int         i, t, fails = 0;

    key_fsm_init(&k, 0);

    for (i = 0; i < tc->n; i++) {
        got = KEY_EV_NONE;
        /* 以 1ms 为步长推进，模拟真实的周期调用 */
        for (t = 0; t < (int)tc->steps[i].ms; t++) {
            key_event_t e = key_fsm_tick(&k, tc->steps[i].level, now);
            if (e != KEY_EV_NONE) {
                got = e;                 /* 只关心这一段里最后报出来的事件 */
            }
            now++;
        }
        if (got != tc->steps[i].expect) {
            printf("  [FAIL] %s 第 %d 段(t=%u)：期望 %s，实际 %s\n",
                   tc->name, i, (unsigned)now,
                   ev_name(tc->steps[i].expect), ev_name(got));
            fails++;
        }
    }
    printf("  [%s] %s\n", fails ? "FAIL" : " OK ", tc->name);
    return fails;
}

为什么不能用 delay(20) 消抖：五条理由
  1. 这 20ms 里整个世界消失了。如果你还要同时收串口，波特率 115200 时一个字节 86.8µs，20ms 里会来 230 个字节——硬件 FIFO 通常只有 8~16 字节深，剩下的全丢。
  2. 它只能回答「按下了吗」，回答不了「按了多久」。长按、连发、双击全都需要时间信息，而 delay(20) 把时间信息扔掉了。
  3. 松手时还会抖一次，于是你不得不在松手的分支里再写一个 delay(20)。两处延时，两处阻塞。
  4. 它不可扩展。两个按键 40ms，四个按键 80ms，按键越多越糟。而状态机版每多一个按键只多一个结构体（约 20 字节 RAM）。
  5. 它把「抖动」这个物理事实藏起来了。状态机版里 KS_DEBOUNCE 是一个看得见的状态——你可以打印它、可以统计"有多少次抖动被滤掉了"、可以按不同按键调整不同的消抖窗口。延时版里这些全都不可能。

通信协议解析是天然的 FSM：逐字节喂入的不定长帧

如果说按键是「最典型的」状态机场景，那协议解析就是「最标准」的状态机场景——因为协议本身就是用状态图定义的。你去看任何一份通信协议文档，它画的都是状态图。

我们定一个真实感的帧格式：

字节序：  ①      ②      ③     ④              ⑤       ⑥
        ┌──────┬──────┬──────┬────────────┬──────┬──────┐
        │ 0xAA │ 0x55 │ LEN  │ DATA[LEN]  │ XOR  │ 0x0D │
        └──────┴──────┴──────┴────────────┴──────┴──────┘
          帧头1   帧头2   长度    数据(1~32B)  校验    帧尾

  LEN   ：数据长度，1 ~ 32。LEN = 0 或 LEN > 32 一律视为非法帧
  XOR   ：LEN ⊕ DATA[0] ⊕ … ⊕ DATA[LEN-1]，从长度字节开始累加
  0x0D  ：帧尾（回车）。它只是"结束标记"，不参与校验

【为什么要有两个帧头字节】
   一个字节的帧头（比如只用 0xAA）抗干扰能力太差：
   数据里出现一个 0xAA 就会被误认为帧头。
   两个字节（0xAA 0x55）把误判概率降到 1/65536 量级。
   代价是多占一个字节，而且要处理「AA AA 55」这种情况 ——
   这正是状态机存在的意义（见下面代码里的 ★ 注释）。

【为什么长度和校验都要有】
   · 长度：让你知道"还要收几个字节"。没有它就只能靠帧尾找结尾，
           而数据里一旦出现 0x0D 就完蛋（除非做转义）。
   · 校验：让"收到了但收错了"能被发现。异或校验最弱但最便宜，
           要更强就换 CRC-8 / CRC-16（多几十个周期，值）。

六个状态，每个状态只回答一个问题：「我在等哪个字节」。

                    不是 0xAA                不是 0x55
                 ┌──────────────┐       ┌─────────────────┐
                 │              ▼       │                 ▼
            ╭─────────╮    ╭─────────╮    ╭─────────╮
   ────────►│  PRX_H1 │───►│  PRX_H2 │───►│ PRX_LEN │
   任意字节  │ 等 0xAA │    │ 等 0x55 │    │ 等长度   │
            ╰─────────╯    ╰─────────╯    ╰────┬────╯
                 ▲              ▲              │ 收到合法 LEN
                 │              │              ▼
                 │              │        ╭───────────╮  收满 LEN 个
                 │              │        │ PRX_DATA  │──────────┐
                 │              │        │ 收数据字节 │          │
                 │              │        ╰───────────╯          ▼
                 │              │                        ╭───────────╮
                 │              │      校验错，丢弃        │ PRX_CHECK │
                 │              └────────────────────────│ 校验异或   │
                 │                                       ╰─────┬─────╯
                 │                                    校验通过 │
                 │                                             ▼
                 │         帧尾不对，丢弃               ╭───────────╮
                 └────────────────────────────────────│ PRX_TAIL  │
                                                      │ 等 0x0D   │
                                                      ╰─────┬─────╯
                                                    帧尾正确 │
                                                            ▼
                                                      ★ 交付一整帧

   ★ 三个设计要点：
     ① 每个字节都"吃"掉：不管它是什么，一定有一个状态接住它。
        绝不出现"这个字节我不要"的悬空 —— 悬空就意味着丢字节。
     ② 失败要能续上：LEN 非法 / 校验错 / 帧尾错之后回到 PRX_H1，
        但那个出错的字节本身可能正是一个新的 0xAA，别浪费它。
     ③ 必须有超时：如果对方发一半就断了（拔线、从机复位），
        状态机会永远停在 PRX_DATA 里等 —— 必须有一个超时把它踢回来。
/* ============================================================
 * proto_rx.h
 * ============================================================ */
#ifndef PROTO_RX_H
#define PROTO_RX_H

#include <stdint.h>
#include <stdbool.h>

#define PRX_HEAD1   0xAAu
#define PRX_HEAD2   0x55u
#define PRX_TAIL    0x0Du
#define PRX_MAX_LEN 32u             /* 一帧最多带多少数据字节 */
#define PRX_TIMEOUT_MS 50u          /* 帧内超时：这么久没新字节就丢弃重来 */

typedef enum {
    PRX_H1 = 0,     /* 等第一个帧头 0xAA */
    PRX_H2,         /* 等第二个帧头 0x55 */
    PRX_LEN,        /* 等长度字节 */
    PRX_DATA,       /* 收数据 */
    PRX_CHECK,      /* 收校验字节 */
    PRX_TAIL        /* 等帧尾 0x0D */
} prx_state_t;

typedef struct {
    prx_state_t st;
    uint8_t     buf[PRX_MAX_LEN];
    uint8_t     len;        /* 本帧声明的数据长度 */
    uint8_t     idx;        /* 已经收到几个数据字节 */
    uint8_t     sum;        /* 异或累加值 */
    uint32_t    t_last;     /* 上一个字节到达的时刻 */
} proto_rx_t;

typedef struct {
    uint8_t data[PRX_MAX_LEN];
    uint8_t len;
} proto_frame_t;

typedef struct {
    uint32_t ok;
    uint32_t err_len;
    uint32_t err_check;
    uint32_t err_tail;
    uint32_t err_timeout;
} proto_stat_t;

extern proto_stat_t g_stat;     /* 统计量：调试时一眼看出是哪一类错误 */

void proto_rx_init(proto_rx_t *p, uint32_t now);

/* 喂一个字节进去。
 * 返回 true 表示【这一字节让一帧完整且校验通过地收完了】，
 * 此时 out 里是完整的一帧。 */
bool proto_rx_feed(proto_rx_t *p, uint8_t b, uint32_t now, proto_frame_t *out);

#include <string.h>
#include "proto_rx.h"

proto_stat_t g_stat;

void proto_rx_init(proto_rx_t *p, uint32_t now)
{
    memset(p, 0, sizeof(*p));
    p->st     = PRX_H1;
    p->t_last = now;
}

/* 出错之后回到起点时用：这个字节本身可能是一个新帧的开头，别浪费它。
 * 这就是"逐字节不丢"的具体体现 —— 一个检查失败不代表这一字节没用。 */
static prx_state_t prx_resync(uint8_t b)
{
    return (b == PRX_HEAD1) ? PRX_H2 : PRX_H1;
}

bool proto_rx_feed(proto_rx_t *p, uint8_t b, uint32_t now, proto_frame_t *out)
{
    p->t_last = now;            /* 每来一个字节都刷新"最后活动时刻" */

    switch (p->st) {

    /* ---------- 等第一个帧头 ---------- */
    case PRX_H1:
        if (b == PRX_HEAD1) {
            p->st = PRX_H2;
        }
        /* 不是帧头就留在原地 —— 垃圾数据被自动吃掉，
           不需要任何"跳过噪声"的额外处理 */
        break;

    /* ---------- 等第二个帧头 ---------- */
    case PRX_H2:
        if (b == PRX_HEAD2) {
            p->st = PRX_LEN;
        } else if (b == PRX_HEAD1) {
            p->st = PRX_H2;     /* ★ 关键：AA AA 55 要停在 H2！
                                   如果这里写 p->st = PRX_H1，
                                   那 0xAA 0xAA 0x55 就会被丢掉，
                                   因为第二个 AA 把第一个 AA 顶掉了。 */
        } else {
            p->st = PRX_H1;
        }
        break;

    /* ---------- 等长度 ---------- */
    case PRX_LEN:
        if (b == 0u || b > PRX_MAX_LEN) {
            g_stat.err_len++;
            p->st = prx_resync(b);      /* 长度非法：不可能是一帧 */
        } else {
            p->len = b;
            p->idx = 0u;
            p->sum = b;                 /* 校验从长度字节开始算 */
            p->st  = PRX_DATA;
        }
        break;

    /* ---------- 收数据 ---------- */
    case PRX_DATA:
        p->buf[p->idx] = b;
        p->idx++;
        p->sum ^= b;
        if (p->idx >= p->len) {
            p->st = PRX_CHECK;
        }
        break;

    /* ---------- 校验 ---------- */
    case PRX_CHECK:
        if (b == p->sum) {
            p->st = PRX_TAIL;
        } else {
            g_stat.err_check++;
            p->st = prx_resync(b);      /* 校验错：整帧丢弃，不重试 */
        }
        break;

    /* ---------- 帧尾 ---------- */
    case PRX_TAIL:
        if (b == PRX_TAIL) {
            memcpy(out->data, p->buf, p->len);
            out->len = p->len;
            g_stat.ok++;
            p->st = PRX_H1;
            return true;                /* ★ 交付这一帧 */
        }
        g_stat.err_tail++;
        p->st = prx_resync(b);
        break;

    /* ---------- 非法状态：立刻自恢复 ---------- */
    default:
        p->st = PRX_H1;
        break;
    }

    return false;
}

/* 帧内超时：如果一帧收了一半就没下文了，必须主动丢掉。
 * 没有这段代码，状态机会永远停在 PRX_DATA 里 —— 之后所有
 * 正常的数据帧都会被当成"半帧的续传"，全部错位、全部丢弃。 */
void proto_rx_tick(proto_rx_t *p, uint32_t now)
{
    if (p->st != PRX_H1 &&
        (uint32_t)(now - p->t_last) >= PRX_TIMEOUT_MS) {
        g_stat.err_timeout++;
        p->st = PRX_H1;
    }
}

/* ============================================================
 * proto_rx_bad.c —— 阻塞式收包（不要这样写）
 * ============================================================ */
bool uart_read_byte(uint8_t *b);        /* 从硬件 FIFO 取一个字节 */

void uart_task_bad(void)
{
    uint8_t b;
    uint8_t len;
    uint8_t buf[32];
    uint8_t sum;
    uint8_t i;

    for (;;) {
        /* ① 死等第一个帧头 */
        while (!uart_read_byte(&b)) { }
        if (b != 0xAA) continue;            /* ← 这个字节已经被消费掉了 */

        /* ② 死等第二个帧头 */
        while (!uart_read_byte(&b)) { }
        if (b != 0x55) continue;            /* ← 如果 b 是 0xAA，新帧的开头丢了 */

        /* ③ 死等长度 */
        while (!uart_read_byte(&b)) { }
        len = b;                            /* ← 没有校验长度合法性 */

        /* ④ 死等 len 个数据字节 */
        for (i = 0; i < len; i++) {
            while (!uart_read_byte(&b)) { } /* ← 对方断线了就永远卡在这里 */
            buf[i] = b;
        }

        /* ⑤ ⑥ 还要再死等校验和帧尾 … */

        process_frame(buf, len);            /* 终于可以处理了 */
    }
}

/* ============================================================
 * 【这段代码的六个问题，每一个都是真实会发生的】
 *
 *  1. 丢了字节就丢了帧头。第 ② 步里 if (b != 0x55) continue 把 b 扔了。
 *     如果那个 b 恰好是新一帧的 0xAA，你就永远收不到那一帧了 ——
 *     而且现象是"偶尔丢一帧"，不定期复现，极难查。
 *     状态机版不会丢，因为每个字节都会被某个状态"接住"。
 *
 *  2. 没有任何超时 → 永久卡死。对方发到一半断电，while 永不返回，
 *     整个任务停死。看门狗会复位，但那是崩溃，不是容错。
 *
 *  3. 长度不做校验 → 缓冲区溢出。len 是从线上来的一个字节，
 *     最大 255。若 buf 只有 32 字节，对方发一个 len=200 就把
 *     你的栈/全局区写穿了 —— 这是嵌入式里最经典的漏洞之一。
 *     状态机版在 PRX_LEN 里就挡住了（b == 0 || b > PRX_MAX_LEN）。
 *
 *  4. CPU 全被这个任务吃掉。整个函数里没有任何"干别的"的机会。
 *
 *  5. 不可重入、不可复用。两个串口就要复制一份，改一处忘一处。
 *
 *  6. 无法测试。它直接和 uart_read_byte 绑定，你不可能在 PC 上
 *     喂它一串字节看看它会不会正确拒绝非法帧。
 *     状态机版是纯函数：喂字节、返回结果，想测哪条边界就测哪条。
 * ============================================================ */

正确的结构：中断只负责搬字节，主循环负责喂状态机。这两件事必须分开——搬字节是硬实时的（一个字节 86.8µs 就得接住），解析不是。

void USART1_IRQHandler(void)            /* 函数名按你的芯片启动文件改 */
{
    if (uart_rx_data_ready()) {
        uint8_t  b    = uart_rx_read();
        uint16_t next = (uint16_t)((rx_head + 1u) & RXBUF_MASK);

        if (next == rx_tail) {
            rx_overflow++;              /* 满了：丢掉【最新】的字节并计数。
                                           不要覆盖旧数据 —— 旧数据是
                                           一帧的前半段，更有价值。 */
        } else {
            rxbuf[rx_head] = b;
            rx_head = next;
        }
    }
    uart_rx_clear_flag();
}

/* ------------------------------------------------------------
 * 主循环里调用：把缓冲里所有可读字节喂给状态机。
 *
 * 【为什么这套 head/tail 不需要关中断】
 *   这是"单生产者单消费者"结构：
 *     只有中断写 rx_head，只有主循环读 rx_head；
 *     只有主循环写 rx_tail，只有中断读 rx_tail。
 *   两个 16 位变量的读写都是原子的（32 位 MCU 上单次访问），
 *   所以不存在竞争 —— 一个 mutex 都不用加。
 * ------------------------------------------------------------ */
void proto_poll(uint32_t now)
{
    while (rx_tail != rx_head) {
        uint8_t b = rxbuf[rx_tail];
        rx_tail = (uint16_t)((rx_tail + 1u) & RXBUF_MASK);

        if (proto_rx_feed(&g_rx, b, now, &g_frame)) {
            on_frame(&g_frame);         /* 一帧完整且校验通过 */
        }
    }
    proto_rx_tick(&g_rx, now);          /* 帧内超时检查 */
}

/* ============================================================
 * 【算一算缓冲要多大】
 *
 *   波特率            每字节时间（10 位：1 起始 + 8 数据 + 1 停止）
 *   ────────────────┼──────────────────────────────
 *      9600 bps     │  10 / 9600  = 1.042 ms
 *     19200 bps     │  0.521 ms
 *     57600 bps     │  0.174 ms
 *    115200 bps     │  10 / 115200 = 86.8 µs
 *    921600 bps     │  10.9 µs
 *
 *   主循环一圈的耗时决定了缓冲至少要多大：
 *     缓冲字节数 > 主循环最坏一圈耗时 / 每字节时间
 *
 *   例：115200bps，主循环最坏一圈 2ms（有个慢任务）：
 *     需要的字节数 = 2ms / 86.8µs ≈ 24 字节
 *     一帧最长 = 2(帧头) + 1(长度) + 32(数据) + 1(校验) + 1(帧尾) = 37
 *     所以取 64 或 128 字节，留 2~3 倍余量。本题取 128。
 *
 *   ★ 只要用了中断+DMA搬字节，缓冲就只需要考虑"主循环最坏延迟"，
 *     不需要考虑"帧有多长" —— 因为缓冲是流式的，边收边解析。
 * ============================================================ */
顺带一说：DMA + IDLE 中断能不能替代状态机？

不能，它替代的是环形缓冲，不是解析。HAL_UARTEx_ReceiveToIdle_DMA() 这类接口利用串口的「空闲线检测」中断，一次把一整帧搬进内存——它解决的是「搬运效率」，你确实不用再自己写环形缓冲和中断了。但搬进来的那一块内存里有什么、合不合法、要不要重同步，仍然要靠状态机逐字节检查。

而且它还有一个副作用：IDLE 检测依赖「线路上出现空闲」。如果两帧连着发、中间没有足够长的空闲间隔，DMA 会把两帧粘成一块给你。这时候你还是得靠状态机在里面找到真正的帧边界。

AT 指令交互：发送 → 等响应 → 超时重试 → 成功 / 失败

如果你用过 ESP8266 / ESP32 / 4G 模块 / 蓝牙模块，就一定写过这种代码：发一条 AT+CWMODE=1，然后等它回 OK。这个「发—等—重试」的流程，天然是五个状态的状态机。它是「阻塞式思维」最后的堡垒——很多人的写法是 HAL_UART_Transmit 之后 HAL_UART_Receive 带 1000ms 超时，然后整个系统就在这 1 秒里停摆；而 AT+CWJAP（连 WiFi）可能要 5~15 秒，这个写法直接不可用。

   ★ 两个容易被忽略的设计点：
     ① 【ERROR 和超时要分开处理】。模块明确回 ERROR 说明指令有问题
        （参数错、不支持），重试通常没用，但工程上还是重试一次
        （因为模块也可能自己忙晕了）。而超时说明是链路问题，
        重试才是对症的。
     ② 【不同指令的超时时间不一样】。AT 查询类指令 100~200ms，
        AT+CWJAP 连接 WiFi 要 5~15 秒。用同一个 1000ms 常量，
        要么慢指令永远失败，要么快指令白等 15 秒。
/* ============================================================
 * at_fsm.h
 * ============================================================ */
#ifndef AT_FSM_H
#define AT_FSM_H

#include <stdint.h>
#include <stdbool.h>

#define AT_MAX_RETRY    3u          /* 最多重试几次（加上首次共 4 次尝试） */
#define AT_TIMEOUT_MS   1000u       /* 默认响应超时（慢指令请用 at_start_to） */
#define AT_RESP_MAX     64u         /* 响应缓冲区大小 */

typedef enum {
    AT_IDLE = 0,        /* 空闲 */
    AT_SEND,            /* 该把指令发出去了 */
    AT_WAIT,            /* 已发出，等响应 */
    AT_DONE,            /* 成功 */
    AT_FAILED           /* 重试用尽，彻底失败 */
} at_state_t;

/* 结果回调：ok = true 成功，false 失败 */
typedef void (*at_result_fn)(bool ok, const char *resp);

typedef struct {
    at_state_t   st;
    const char  *cmd;
    uint32_t     timeout_ms;        /* 本指令的超时时间 */
    uint8_t      retry;
    uint32_t     t_send;
    char         resp[AT_RESP_MAX];
    uint8_t      resp_len;
    bool         got_ok;
    bool         got_error;
    at_result_fn on_result;
} at_fsm_t;

void at_init(at_fsm_t *a, at_result_fn on_result);
void at_start(at_fsm_t *a, const char *cmd, uint32_t now);
void at_start_to(at_fsm_t *a, const char *cmd, uint32_t timeout_ms, uint32_t now);
void at_tick(at_fsm_t *a, uint32_t now);
void at_on_byte(at_fsm_t *a, uint8_t b);
bool at_is_busy(const at_fsm_t *a);

/* 移植层：你来实现 */
void at_uart_send(const char *cmd);     /* 把指令发出去（内部补 \r\n） */
void at_log(const char *s);             /* 日志输出 */

#endif /* AT_FSM_H */
/* ============================================================
 * at_fsm.c
 * ============================================================ */
#include <string.h>
#include "at_fsm.h"

void at_init(at_fsm_t *a, at_result_fn on_result)
{
    memset(a, 0, sizeof(*a));
    a->st        = AT_IDLE;
    a->timeout_ms = AT_TIMEOUT_MS;
    a->on_result = on_result;
}

bool at_is_busy(const at_fsm_t *a)
{
    return (a->st != AT_IDLE);
}

/* 内部统一入口：把状态机复位成"准备发第一条" */
static void at_begin(at_fsm_t *a, const char *cmd, uint32_t timeout_ms, uint32_t now)
{
    a->cmd        = cmd;
    a->timeout_ms = timeout_ms;
    a->retry      = 0u;
    a->resp_len   = 0u;
    a->got_ok     = false;
    a->got_error  = false;
    a->t_send     = now;
    a->st         = AT_SEND;
}

void at_start(at_fsm_t *a, const char *cmd, uint32_t now)
{
    at_begin(a, cmd, AT_TIMEOUT_MS, now);
}

void at_start_to(at_fsm_t *a, const char *cmd, uint32_t timeout_ms, uint32_t now)
{
    at_begin(a, cmd, timeout_ms, now);
}

void at_tick(at_fsm_t *a, uint32_t now)
{
    switch (a->st) {

    /* ---------------- 空闲 ---------------- */
    case AT_IDLE:
        break;                          /* 等别人调用 at_start() */

    /* ---------------- 发送 ---------------- */
    case AT_SEND:
        a->resp_len  = 0u;              /* 每次重发都清空响应缓冲 */
        a->got_ok    = false;
        a->got_error = false;
        at_uart_send(a->cmd);
        a->t_send = now;
        a->st     = AT_WAIT;
        break;

    /* ---------------- 等响应 ---------------- */
    case AT_WAIT:
        if (a->got_ok) {
            a->st = AT_DONE;
        } else if (a->got_error) {
            a->retry++;
            a->st = (a->retry <= AT_MAX_RETRY) ? AT_SEND : AT_FAILED;
        } else if ((uint32_t)(now - a->t_send) >= a->timeout_ms) {
            a->retry++;                 /* 超时也重试 */
            a->st = (a->retry <= AT_MAX_RETRY) ? AT_SEND : AT_FAILED;
        }
        break;

    /* ---------------- 成功 ---------------- */
    case AT_DONE:
        a->st = AT_IDLE;                /* 先回空闲，再回调 —— 防止回调里
                                           再次调用 at_start 造成状态混乱 */
        if (a->on_result) {
            a->on_result(true, a->resp);
        }
        break;

    /* ---------------- 失败 ---------------- */
    case AT_FAILED:
        a->st = AT_IDLE;
        if (a->on_result) {
            a->on_result(false, a->resp);
        }
        break;

    /* ---------------- 非法状态：自恢复 ---------------- */
    default:
        a->st = AT_IDLE;
        break;
    }
}

/* ------------------------------------------------------------
 * 由串口解析状态机调用：每收到一个响应字节就喂进来。
 * 注意这里【不解析协议】，只是"攒够字符串 + 找关键字"。
 * 更严格的做法是把 "OK" 换成本行完全等于 "\r\nOK\r\n"，
 * 因为数据里也可能恰好出现 "OK" 两个字母。
 * ------------------------------------------------------------ */
void at_on_byte(at_fsm_t *a, uint8_t b)
{
    if (a->st != AT_WAIT) {
        return;                         /* 不在等响应，直接丢掉 */
    }

    if ((uint32_t)a->resp_len + 1u < sizeof(a->resp)) {
        a->resp[a->resp_len] = (char)b;
        a->resp_len++;
        a->resp[a->resp_len] = '\0';
    } else {
        a->resp_len = 0u;               /* 响应太长：清空重来，绝不溢出 */
        a->resp[0]  = '\0';
    }

    if (strstr(a->resp, "OK")    != NULL) { a->got_ok    = true; }
    if (strstr(a->resp, "ERROR") != NULL) { a->got_error = true; }
}

/* ============================================================
 * 【超时时间怎么定：按最坏情况 × 2】
 *
 *   指令                      典型响应         建议超时
 *   ────────────────────────┼───────────────┼──────────
 *   AT（测试）               < 10 ms        100 ms
 *   AT+CWMODE=1              ~20 ms         200 ms
 *   AT+CIPSTART（建 TCP）    200 ms ~ 2 s    5 s
 *   AT+CWJAP（连 WiFi）      3 ~ 15 s        20 s
 *   AT+CIPSEND（发数据）     50 ~ 500 ms     2 s
 *
 *   重试总耗时（以超时 1s、重试 3 次为例）：
 *     首次 1s + 重试 1s + 重试 1s + 重试 1s = 最坏 4 s
 *   ⇒ 如果有 5 条指令要依次执行且都失败，最多 20 秒。
 *     所以界面上的"正在连接…"必须能被打断（用户点取消），
 *     否则用户会以为死机了。
 * ============================================================ */

用状态机做时间片轮转：不引入 RTOS 的最简调度器

到这一步，你手上已经有一堆状态机了：按键、协议解析、AT 交互、闪灯。它们各自的周期要求还不一样——按键要 1ms、协议解析 10ms、闪灯 1000ms。把它们塞进一个主循环里依次调用，就是最简的协作式调度器，一行 RTOS 代码都不用写。

/* ============================================================
 * coop_sched.c —— 不用 RTOS 的协作式调度器
 *
 * 核心思想只有一句：每个任务 = 一个函数 + 一个"下次该跑的时刻"。
 * 调度器只做一件事：到点了就调用它，然后算出下次的时刻。
 * ============================================================ */
#include <stdint.h>
#include <stdbool.h>

typedef void (*task_fn_t)(uint32_t now);

typedef struct {
    task_fn_t fn;
    uint32_t  period;       /* 周期，ms */
    uint32_t  t_next;       /* 下次该运行的时刻 */
    uint32_t  run_count;    /* 运行次数（调试用） */
    uint32_t  late_count;   /* 迟到次数：说明有别的任务太占时间了 */
} sched_task_t;

#define SCHED_MAX_TASK 8u

static sched_task_t s_tasks[SCHED_MAX_TASK];
static uint8_t      s_n;

bool sched_add(task_fn_t fn, uint32_t period_ms, uint32_t now)
{
    if (s_n >= SCHED_MAX_TASK) {
        return false;
    }
    s_tasks[s_n].fn         = fn;
    s_tasks[s_n].period     = period_ms;
    s_tasks[s_n].t_next     = now + period_ms;
    s_tasks[s_n].run_count  = 0u;
    s_tasks[s_n].late_count = 0u;
    s_n++;
    return true;
}

void sched_run(uint32_t now)
{
    uint8_t i;

    for (i = 0u; i < s_n; i++) {
        /* ★ 用【有符号的差值】判断到点没有。
         *   now - t_next 在无符号下会回绕，但转成有符号看符号位就对了：
         *   只要 t_next 在"过去"（差值小于 2^31），结果就是负数。
         *   这样即使 t_next 溢出了也依然正确。 */
        if ((int32_t)(now - s_tasks[i].t_next) >= 0) {

            s_tasks[i].fn(now);
            s_tasks[i].run_count++;

            /* ★ 关键：下次时刻 = 【上一次计划 + 周期】，而不是 now + 周期。
             *   前者能自动补偿调度抖动，长期平均周期精确；
             *   后者会把每次的调度开销累加进去，周期越跑越长。 */
            s_tasks[i].t_next += s_tasks[i].period;

            /* ★ 但如果落后超过一整个周期（比如被一个长任务卡了 500ms），
             *   补跑会引发"追赶风暴"：连续跑十几次，把后面所有任务
             *   全拖垮，形成雪崩。所以落后太多就直接跳过，并记一笔。 */
            if ((int32_t)(now - s_tasks[i].t_next) >= 0) {
                s_tasks[i].t_next = now + s_tasks[i].period;
                s_tasks[i].late_count++;
            }
        }
    }
}

/* ============================================================
 *  三个任务，周期分别是 1ms / 10ms / 1000ms
 *  注意：每个任务本身都是一个状态机，而且都必须【立刻返回】
 * ============================================================ */
extern void key_task(uint32_t now);      /* 1ms  : 按键状态机 */
extern void proto_task(uint32_t now);    /* 10ms : 协议解析状态机 */
extern void slow_task(uint32_t now);     /* 1000ms: 慢任务（上报、闪灯） */
extern uint32_t tick_ms(void);
void board_init(void);

int main(void)
{
    uint32_t now;

    board_init();
    now = tick_ms();

    sched_add(key_task,    1u,    now);
    sched_add(proto_task,  10u,   now);
    sched_add(slow_task,   1000u, now);

    for (;;) {
        now = tick_ms();
        sched_run(now);
    }
}

/* ============================================================
 * 【这个调度器和 RTOS 最大的区别：不需要锁】
 *
 *   所有任务都在主循环里【顺序】执行，任何一个任务都不会在
 *   "执行到一半"的时候被打断（除非中断里也去访问那个变量）。
 *   所以任务之间共享数据【不需要任何互斥】——
 *   这是协作式调度最大的优点，也是它写起来比 RTOS 简单得多的原因。
 *
 * 【代价：一个任务卡住，全系统卡住】
 *   如果你在 key_task 里写了一个 delay_ms(5)，那么：
 *     · 按键任务自己 5ms 才跑一次 → 手感变差
 *     · proto_task 被推迟了 5ms → 可能丢字节
 *     · 整条链路的时序全被拖偏
 *   ⇒ 所以"每个任务必须立刻返回"不是建议，是【铁律】。
 *     调度器里那个 late_count 就是用来抓这个问题的：
 *     某个任务的 late_count 一直涨 → 一定有别的任务超时了。
 *
 * 【任务周期的经验值】
 *     周期        适合什么
 *     ──────────┼──────────────────────────────────
 *       1 ms    按键扫描（手感靠它）、紧急状态监测
 *      10 ms    协议解析、传感器轮询、PID 中速环
 *     100 ms    显示刷新、状态上报
 *    1000 ms    统计输出、慢速诊断
 *   ⇒ 规则：一个任务的执行时间应当小于它周期的 10%。
 *     1ms 的任务必须在 100µs 内返回。做不到就把它拆小或者放慢。
 * ============================================================ */

状态机与 RTOS 的关系：正交，不是替代

这是初学者最容易混淆的一对概念。答案只有一句话：状态机是「一个任务内部」的实现结构，RTOS 是「多个任务之间」的组织方式，两者正交，可以任意叠加。

                       任务内部
                 顺序代码          状态机
              ┌────────────────┬────────────────┐
     单主循环  │ ① 最简单        │ ② 最常见        │
      （无RTOS）│ delay + 顺序    │ "主循环 + 状态机" │
   多任务        │ 小事够用        │ 本章的主角       │
   组织          │ 一旦并发就崩    │ 90% 的裸机项目   │
   方式        ├────────────────┼────────────────┤
              │ ③ 用更贵的方式   │ ④ 最强大        │
      RTOS    │ 重新发明 delay  │ 大项目的标准做法  │
              │ 每个任务里写     │ 任务之间用队列/   │
              │ delay / 死等     │ 信号量，任务内部  │
              │ 白买一个 RTOS   │ 用状态机          │
              └────────────────┴────────────────┘

  ★ ③ 是最常见的"花了钱没买到东西"：
     用了 FreeRTOS，占了几十 KB Flash，结果每个任务内部
     还是 vTaskDelay(1000) 的阻塞式流程 —— 你付出的调度开销
     一点收益都没换到。

  ★ ④ 才是 RTOS 的正确用法：
     任务之间用队列/信号量传递【事件】，任务内部用状态机
     组织【行为】。这样每个任务都是"不阻塞、可测、可画图"的。

有了 RTOS 之后，状态机反而变得更简单了。因为「等事件」这件事可以交给内核去做，状态机只需要处理「事件来了怎么办」：

/* ============================================================
 * 有 RTOS 之后：状态机不用再轮询了
 * ============================================================ */
#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"
#include "key_fsm.h"
#include "proto_rx.h"

static QueueHandle_t g_key_evt_q;       /* 中断 → 任务 的事件队列 */
static QueueHandle_t g_frame_q;         /* 解析任务 → 应用任务 */

/* ------------------------------------------------------------
 * 按键任务：阻塞等事件，不占 CPU
 * ------------------------------------------------------------ */
static void key_task(void *arg)
{
    key_event_t ev;

    (void)arg;

    for (;;) {
        /* ★ portMAX_DELAY = 一直睡到有事件为止，CPU 占用率 0%
         *   裸机版必须每 1ms 轮询一次；RTOS 版是事件驱动的。 */
        if (xQueueReceive(g_key_evt_q, &ev, portMAX_DELAY) == pdTRUE) {
            /* ▼ 醒来之后，状态转移逻辑和裸机版【完全一样】 */
            switch (ev) {
            case KEY_EV_SHORT:       ui_next_page();      break;
            case KEY_EV_DOUBLE:      ui_enter();          break;
            case KEY_EV_LONG:        ui_back();           break;
            case KEY_EV_LONG_REPEAT: ui_scroll();         break;
            default: break;
            }
        }
    }
}

/* ------------------------------------------------------------
 * 中断里往队列投事件 —— 必须用带 FromISR 后缀的版本
 * ------------------------------------------------------------ */
void EXTI0_IRQHandler(void)
{
    BaseType_t hpw = pdFALSE;
    key_event_t ev = KEY_EV_SHORT;      /* 简化示意 */

    /* ★ 错误写法：xQueueSend(g_key_evt_q, &ev, 0);
     *   ISR 里绝不能调用会阻塞的 API，而且不会触发任务切换。
     *   正确写法是 xQueueSendFromISR + portYIELD_FROM_ISR。 */
    xQueueSendFromISR(g_key_evt_q, &ev, &hpw);
    portYIELD_FROM_ISR(hpw);
}

/* ------------------------------------------------------------
 * 解析任务：它仍然是一个状态机，只是"喂字节"变成了阻塞等队列
 * ------------------------------------------------------------ */
static void rx_task(void *arg)
{
    proto_rx_t    p;
    proto_frame_t f;
    uint8_t       b;

    (void)arg;

    proto_rx_init(&p, 0);

    for (;;) {
        /* 阻塞等一个字节。没有字节就睡，不消耗 CPU。 */
        if (xQueueReceive(g_byte_q, &b, portMAX_DELAY) == pdTRUE) {
            if (proto_rx_feed(&p, b, tick_ms(), &f)) {
                /* 解析出来的一帧，转给应用任务处理 */
                xQueueSend(g_frame_q, &f, 0);
            }
        }
    }
    /* ★ 注意：因为收字节不再需要"帧内超时"来兜底（队列不会永久阻塞），
     *   但如果对端发了一半就停了，上面这个循环还是会一直等 ——
     *   所以 proto_rx_tick() 的超时判断依然要保留，
     *   只是改成用 xQueueReceive 带超时参数的版本：
     *       xQueueReceive(g_byte_q, &b, pdMS_TO_TICKS(PRX_TIMEOUT_MS))
     *   超时返回 pdFALSE 时调用 proto_rx_tick() 即可。 */
}

/* ============================================================
 * 【用不用 RTOS 的判据】
 *
 *   用裸机主循环 + 时间片调度，如果：
 *     · 任务数 ≤ 8 个
 *     · 所有任务都能写成"立刻返回"的状态机
 *     · 实时性靠"足够快的轮询"就能满足（比如 1ms 一次）
 *     · RAM 紧张
 *
 *   该上 RTOS 了，如果：
 *     · 任务数 > 10 个，或者任务之间的依赖关系开始变复杂
 *     · 需要【抢占】：某个事件必须在 X µs 内响应，而别的任务
 *       可能正在跑一个长任务（比如擦写 Flash 要几十毫秒）
 *     · 需要阻塞式 API（信号量、队列、事件组）来简化任务间通信
 *     · 需要优先级（高优先级任务可以打断低优先级任务）
 *
 * 【资源开销的实测量级（FreeRTOS on Cortex-M3）】
 *    最小内核（不要软件定时器、不要堆）  约 6 ~ 10 KB Flash
 *    每个任务的栈                        最小 128 字 = 512 字节
 *                                        实际常用 256 ~ 512 字
 *    每个任务控制块（TCB）               约 90 ~ 100 字节
 *    8 个任务的系统                      约 16 ~ 32 KB Flash
 *                                        + 4 ~ 8 KB RAM
 *
 *   对照：STM32F103C8T6 只有 64KB Flash / 20KB RAM。
 *   上 RTOS 意味着至少交出 1/4 的 Flash 和 1/3 的 RAM。
 *   值不值，要看你换到了什么 —— 如果换到的只是"把 delay
 *   改写成了 vTaskDelay"，那就不值。
 * ============================================================ */

再强调一次这个「正交」关系，因为它决定你怎么分工：

问题谁来回答典型手段
同一时刻有哪几件事在推进？任务组织形式（裸机调度器 / RTOS）主循环时间片、任务 + 优先级、队列
其中一件事下一步要做什么？状态机状态图、状态表、switch
两件事之间怎么传递信息？任务组织形式全局变量 + 标志、队列、信号量、事件组
一件事收到信息之后怎么反应？状态机状态转移 + 输出动作
一件事内部要不要加锁？任务组织形式协作式调度：不用；抢占式 RTOS：必须用

现实中最常见的错误分工是：把「一件事内部的顺序」交给 RTOS 去管——开一个任务专门做「先延时 100ms，再发指令，再等 1 秒」，于是任务里全是 vTaskDelay。这等于用几十 KB 的调度器换来了「更贵的 delay」。正确做法是反过来：任务内部用状态机做到「不阻塞」，任务之间才交给 RTOS 去调度优先级和消息。

状态机的可测试性：为什么它比一大坨 if/else 嵌套好用

前面几段代码里其实已经埋了一个设计原则，这里把它挑明：让状态机成为一个「不碰硬件」的纯函数。

回头看 key_fsm_tick() 的签名：

key_event_t key_fsm_tick(key_fsm_t *k, bool raw_level, uint32_t now);

             ▲            ▲          ▲              ▲
             │            │          │              │
             │            │          │              └── 时间从外面传进来，
             │            │          │                  函数【不】自己调用 millis()
             │            │          └───────────────── 输入从外面传进来，
             │            │                            函数【不】自己读 GPIO
             │            └──────────────────────────── 状态从外面传进来，
             │                                         函数没有 static 隐藏状态
             └───────────────────────────────────────── 结果从返回值出去，
                                                       函数【不】自己点亮 LED

  ★ 这四个"从外面进来 / 从外面出去"，把状态机变成了一台
    【纯计算机器】：给它状态 + 输入 + 时间，它给你新状态 + 事件。
    · 没有硬件依赖  → 可以在 PC 上编译运行
    · 没有隐藏状态  → 同样的输入必然得到同样的输出，可复现
    · 没有副作用    → 想测哪条边就测哪条边，不用管别的

  ★ 与之对比，一个"标准"的裸机按键处理函数通常长这样：
        void key_scan(void)
        {
            static uint32_t last = 0;        // ← 隐藏状态！
            static uint8_t  cnt  = 0;        // ← 隐藏状态！
            if (HAL_GPIO_ReadPin(KEY_PORT, KEY_PIN) == GPIO_PIN_RESET) {
                if (HAL_GetTick() - last > 20) { … }
            }
            …
        }
    它有三个致命问题：
      · static 变量 = 隐藏状态，你没法在测试里把它重置到已知初值
      · 直接读 GPIO = 你没法在 PC 上喂一个"抖动波形"进去
      · 直接点灯/改全局 = 副作用混在逻辑里，测试断言不知道看哪里
    ⇒ 结果是：这段代码永远只能"上板试"，而"上板试"永远试不全。

可测试性带来的具体好处，一条一条数：

维度状态机一大坨 if/else 嵌套
测试用例能不能列全能：状态数 × 输入数 = 有限的格子。8 个状态 × 3 种输入 = 24 条转移，24 条用例就能做到 100% 转移覆盖不能：判断路径随嵌套层数组合爆炸，20 个 if 就是 220 ≈ 100 万条量级
能不能在 PC 上跑能：只要有 stdint.h 和 stdbool.h 就能编译不能：直接调用 HAL/寄存器，只能在板子上跑
同样的输入能否复现能：状态全在参数里，初值可控不能：static 变量和硬件寄存器都是隐藏状态
改代码后能否回归测试能：跑一遍用例表，看一眼退出码只能重新上板手点，而且点不全
覆盖度能否量化能：状态覆盖率、转移覆盖率都能算出来没有对应指标，只能靠感觉
现场出问题怎么定位能：把状态变量 print 出来，立刻知道卡在哪一步只能看 PC 值和一堆变量猜
能不能做故障注入能：喂一个「校验错的帧」「超长的 LEN」，看它是否正确拒绝很难：你得在真实链路上制造这种错误

常见坑与易错点

下面 10 条，每一条都是「错误认知 → 为什么错 → 正确做法」。它们中的绝大多数不会让程序编译报错，也不会让程序立刻崩——它们只是在某个特定的时刻、特定的温度、特定的按键力度下让设备表现怪异。这才是嵌入式 bug 最难查的那一类。

坑 1：「状态机不就是 if/else 吗？我不用状态机也照样写。」

为什么错：能写出来 ≠ 能验证。「照样写」出来的通常是一堆靠 static 变量和嵌套判断堆起来的分支，它没有明确的状态集合，所以你既画不出图，也列不全用例，更说不出「它现在在哪一步」。等到出问题时，你手上唯一的工具是往里面加 printf。

正确做法：把「行为」这件事显式化——enum 列出状态、switch 写转移、每个状态都有名字。这不是形式主义：状态名本身就是最好的文档和日志。当你收到一份现场日志写着「卡在 ST_WAIT_ACK」时，你不需要读代码就知道问题在等应答那一步。

坑 2：「Mealy 比 Moore 快一个时钟，所以都用 Mealy。」

为什么错：那一个时钟是用三样东西换来的——输出脉宽不确定、输入毛刺会穿透到输出、跨时钟域时可能被采到一串乱跳的值。在 FPGA 里这直接表现为「仿真全对、上板偶尔抽风」，是最难定位的一类问题。

正确做法：默认用 Moore；或者用 Mealy 但把输出寄存一拍（三段式的第 3 段加一级触发器，等价于把 Mealy 变成 Moore 的时序特性，只是多等一拍）。只有在「输出只给同一时钟域的同步电路采样」并且「状态数确实紧张」时才裸用 Mealy。

坑 3：「状态机跑飞了也没事，我有看门狗。」

为什么错：看门狗复位的是整个系统——正在传的数据丢了、外设要重新初始化、继电器会「啪」一下全断、用户会看到设备重启。而安全编码（默认次态指向复位态）只需要一个时钟周期就能自愈，用户完全察觉不到。两者代价差了几万倍。

更糟的是，很多人的喂狗代码写在定时器中断里无脑喂：于是状态机卡死了、中断照跑、狗照喂，看门狗彻底失效——你以为有保护，其实什么都没有。

正确做法：① 次态逻辑里显式写 default（HDL）或 default:（C），把非法状态送回初始态；② 喂狗动作必须放在「所有任务都正常跑过一圈」之后，用一个「每个任务提交一次才放行喂狗」的标记；③ 在 default 分支里加诊断计数，让跑飞变成可观测的事件。

坑 4：「按键消抖？delay(20) 一下就行了。」

为什么错：① 这 20ms 里 CPU 什么都不干，115200 波特率下会来 230 个字节，硬件 FIFO 直接溢出丢数据；② 它只能告诉你「按下了」，做不出长按和双击（因为时间信息被扔掉了）；③ 松手时还要再抖一次，于是变成两处延时；④ 按键越多越糟。

正确做法：把抖动变成一个看得见的状态（KS_DEBOUNCE），用 8ms 的时间戳判断电平是否稳定。整个过程中 CPU 一秒都没被阻塞，而且顺手就有了长按需要的「按了多久」这个信息。

坑 5：「串口数据？等一整包收完再处理就行。」

为什么错：这是本节最贵的一个坑，因为它同时踩了三颗雷：①丢数据（阻塞期间字节被硬件丢掉，而且失败分支里已经消费掉的字节可能正是下一帧的帧头）；②没有超时 → 永久卡死（对方发一半断电，while 永不返回）；③长度不校验 → 缓冲区溢出（len 是从线上来的一个字节，最大 255，直接 buf[i] = b 就把栈写穿了）。

正确做法：中断/DMA 只负责把字节搬进环形缓冲，主循环逐字节喂给解析状态机；每个状态都检查边界（LEN == 0 || LEN > MAX）；加帧内超时把半帧踢掉。这三件事缺一件，远期的现场故障都跑不掉。

坑 6：「状态越多越精确，一个节拍一个状态。」

为什么错：状态是「离散的行为阶段」，不是定时器。用 58 个状态表示交通灯的 58 秒，会让编码位宽从 3 位涨到 6 位、状态表从 6 行涨到 58 行、卡诺图从 4 变量涨到 7 变量，而且「把绿灯从 30 秒改成 25 秒」这种需求要重画整张图。

正确做法：一句话——「状态表示我在做什么，变量表示我做了多久、做了几次」。状态机管阶段，计时/计数交给变量或硬件定时器。这条原则在 C 代码里的样子就是：case ST_EW_GREEN: if (--tick_left == 0) { … }。

坑 7：「上了 RTOS 就不用状态机了，一个任务一件事。」

为什么错：两者是正交的（详见第 4 节）。RTOS 解决的是「多件事之间怎么排优先级、怎么传消息」，它不解决「一件事内部按顺序分几步做」。用 vTaskDelay 在一个任务里写顺序流程，等于花了几十 KB Flash 买了一个更贵的 delay——而且这个任务在 vTaskDelay 期间虽然让出了 CPU，却依然无法响应任何新输入（它只是睡着了，醒来还是原计划）。

正确做法：任务内部用状态机做到不阻塞，任务之间用队列/信号量传递事件。这样每个任务都是「事件驱动 + 可画图 + 可测试」的，RTOS 的调度开销才真的换来了东西。

坑 8：「状态化简总是好的，能合并就合并。」

为什么错：三件事被忽略了：①只有跨过 2 的幂才省触发器（6 个状态化简到 5 个，还是 3 位，一个触发器都不省，只是逻辑简单一点）；②合并会丢掉可观测性（原来能区分「走的哪条路」，合并后在运行时看不见了）；③化简的前提是「输入序列不受限」，而真实系统里很多输入序列物理上不可能出现——保守化简反而会多留状态。

正确做法：化简前先算一笔账（跨没跨 2 的幂、省不省非法状态），再决定值不值。工程上「保留冗余状态用于诊断」是一个完全正当的理由——能化简不等于必须化简。

坑 9：「异步信号直接读进来就行，我读的是电平，跟时序没关系。」

为什么错：触发器有建立/保持窗口。异步信号在窗口内跳变会让触发器进入亚稳态——输出停在中间电平，然后随机倒向某一侧。后果是「同一个输入被不同的后级解读成不同的值」「状态机多走一步或少走一步」，而且偶发、不可复现、和温度电压有关。

还有一个更隐蔽的版本：多位总线打两拍是不够的。16 位的计数器值跨时钟域时，各位可能在不同时钟沿被采到，你会得到一个「高 8 位是新值、低 8 位是旧值」的混合值。

正确做法：单比特异步信号 → 打两拍（两级串联 D 触发器）再进状态机；多位信号 → 格雷码（每次只变一位）、握手（请求/应答）或异步 FIFO 三选一。在 MCU 软件里的等价物是：中断里只置标志，主循环读标志再改状态，不要从多个上下文同时改状态变量。

坑 10：「超时判断写 now >= t0 + TIMEOUT 和写 (now - t0) >= TIMEOUT 不是一样吗？」

为什么错：不一样。如果 now 是无符号 32 位毫秒计数（HAL_GetTick() / Arduino 的 millis() 都是），它会在 232 ms = 4294967296 ms ≈ 49.71 天之后回绕到 0。写 t0 + TIMEOUT 有两种翻车方式：t0 + TIMEOUT 自己先溢出回绕（如果 t0 靠近上限），或者 now 回绕之后永远小于 t0 + TIMEOUT——结果是超时永远不触发，状态机永远停在等待状态。

为什么无符号减法免疫：无符号减法的结果天然是模 232 的「真实时间差」。now 刚回绕到 5 而 t0 是 4294967290 时，(uint32_t)(now - t0) 算出来正好是 11，完全正确。只要两次采样的间隔小于 49.71 天，这个写法就永远对。

正确做法：统一写 (uint32_t)(now - t0) >= TIMEOUT。本节所有代码都遵循这一条（elapsed() 函数就是它的封装）。调度器里判「到点了吗」用有符号版本 (int32_t)(now - t_next) >= 0，原理一样。

小结与自测

如果把这一页压成一段话：状态机是「有记忆的顺序行为」的通用语言——它用有限的几个状态、一张转移表、两个方程（次态与输出），把「随时记住自己在哪里、根据事件决定下一步」这件事变成可以画出来、可以算出来、可以测出来的东西。落到硬件上是触发器加组合逻辑，落到单片机上是 enum 加 switch 加时间戳，两边的思维方式一模一样。

要点清单（可以对着检查自己有没有漏）
  • 三要素 + 两个函数：状态集合 S、输入集合 I、输出集合 O，次态函数 Q* = δ(Q, X)，输出函数 Z = λ(Q, X) 或 λ(Q)。
  • 四种描述方式可以机械互转：状态图 ⇄ 状态表 ⇄ 状态转移方程 + 输出方程。状态表是不漏边的唯一保证。
  • Moore 与 Mealy 的差别只有一句：输出是否直接依赖输入。Moore 慢一拍但干净、脉宽精确；Mealy 快但脉宽不定、毛刺会穿透。输出要出门、要触发边沿敏感器件、要闭环、要安全 → 选 Moore 或把输出寄存。
  • 状态编码三选一：二进制（触发器最少，ASIC/CPLD 首选）、格雷（只翻一位，适合顺序循环与跨时钟域）、独热（触发器最多但译码几乎为零，FPGA 首选）。状态数超过 16~32 就别用独热了。
  • 状态化简 = 合并等价状态：判据是「输出一致」+「次态等价」，两者互相依赖所以要用隐含表迭代。真正的红利常常是非法状态被清零（5 状态 3 位有 3 个非法，化简到 4 状态 2 位就一个不剩）。
  • D 触发器的核心优势：D = Q*。用 JK/T/SR 要多一层「次态 → 激励」的翻译逻辑，用 D 则直接画卡诺图。六步流程：状态图 → 化简 → 编码 → 状态转移表（含非法码）→ 激励方程 → 输出方程 + 电路。
  • 两条时序约束：T_clk ≥ t_cq + t_logic(max) + t_setup + t_skew 决定最高频率；t_cq(min) + t_logic(min) ≥ t_hold + t_skew 决定「逻辑不能太短」，与频率无关。
  • 非法状态必须显式处理：默认次态指向复位态（安全编码）+ 诊断计数 + 看门狗兜底（喂狗要放在所有任务都跑过的路径上）。
  • 亚稳态只能降低概率，不能消除：单比特打两拍，多比特要格雷码 / 握手 / 异步 FIFO。
  • HDL 三段式 = 状态寄存器 / 次态组合逻辑 / 输出逻辑分开写。在 C 语言里同样成立：next_state() 是纯函数、output() 集中动作、state 只在一处被赋值。
  • 裸机程序的终局是状态机：delay 把「等」变成指令，状态机把「等」变成判断——这是「阻塞」与「非阻塞」的全部分界。
  • 状态机与 RTOS 正交：状态机管任务内部，RTOS 管任务之间，可以叠加，不能互相替代。
  • 可测试性是状态机被低估的最大优点：把状态、输入、时间都做成参数，就能在 PC 上跑用例表，做到 100% 转移覆盖。

自测题（先自己答，再看下面的答案）

  1. Moore 型和 Mealy 型的严格区别是什么？各用一句话写出它们的输出方程。

    答：区别只有一处——输出是否直接依赖当前输入。Moore：Z = λ(Q)，只由现态决定；Mealy：Z = λ(Q, X)，由现态和输入共同决定。由此派生出的所有差别（状态数、响应速度、脉宽、毛刺）都是这一句话的推论。

  2. 一台状态机有 5 个状态，用二进制编码需要几个触发器？有几个非法状态？如果化简到 4 个状态呢？

    答：5 个状态需要 ⌈log25⌉ = 3 位 = 3 个触发器，23 − 5 = 3 个非法状态（101、110、111）。化简到 4 个状态只需 ⌈log24⌉ = 2 个触发器，22 − 4 = 0 个非法状态。这就是「跨过 2 的幂」才省触发器的典型例子。

  3. 为什么说 D 触发器最适合实现状态机？用 JK 触发器会多出什么工作？

    答：因为 D = Q*，激励方程就是次态方程本身，画完卡诺图直接得到 D 端表达式。用 JK 触发器则要先根据「现态 → 次态」查激励表，再为 J、K 分别画卡诺图——多出「把次态翻译成激励」这一整套逻辑，门数更多、更容易出错。同理，T 触发器要算 T = Q ⊕ Q*，SR 触发器还要处理不允许的输入组合。

  4. 在 T_clk ≥ t_cq + t_logic(max) + t_setup + t_skew 里，哪一项是你可以通过改写逻辑来优化的？怎么优化？

    答：只有 t_logic(max) 是设计者能动的——它是从触发器 Q 端到你方程里那些门的【最长路径】延迟。t_cq、t_setup 是器件参数，t_skew 由布线决定。优化手段：①用卡诺图把方程化到最简（减轻门数和级数）；②提取公共项、共享子表达式；③改变状态编码（独热码的次态逻辑通常只有一级门）；④必要时插入流水线寄存器（但这会改变状态机的语义）。

  5. 一个异步按键信号直接接进状态机会出什么问题？怎么解决？如果是一个 16 位的数据总线呢？

    答：异步信号在时钟沿附近跳变会让触发器进入亚稳态——输出停在中间电平，被不同的后级解读成不同的值，导致状态机多走一步或少走一步，且故障偶发、不可复现。解决办法是先打两拍（两级串联 D 触发器），把「进入亚稳态后没能及时恢复」的概率降到可以忽略。但对 16 位总线打两拍是不够的：各位可能在不同时钟沿被采到，会得到一个半新半旧的混合值。多位跨时钟域要用格雷码（每次只变一位）、握手或异步 FIFO。

  6. 为什么不能用 delay(20) 消抖？至少说出三条理由。

    答：① 这 20ms 里 CPU 完全阻塞，串口数据会丢（115200 波特率下 20ms 会来 230 个字节，硬件 FIFO 只有 8~16 字节深）；② 它扔掉了时间信息，只能判断「按下了」，做不出长按、连发、双击；③ 松手时还会抖一次，需要第二处延时；④ 不可扩展，n 个按键就是 n×20ms；⑤ 它把「抖动」这个物理事实藏起来了，你没法观察、统计、按按键单独调参。正确做法是把消抖做成一个状态（KS_DEBOUNCE）+ 8ms 的时间戳判断。

  7. HDL 的「三段式」把状态机分成了哪三段？为什么工程上推荐它而不是一段式？C 语言里怎么体现？

    答：三段是①状态寄存器（时序块，只做 state <= state_next）②次态组合逻辑（只算下一拍去哪）③输出逻辑（可以再寄存一拍）。推荐它的根本原因：把「什么时候变」和「变成什么」物理上分开，于是不会推出意外锁存器、输出无毛刺、时序好约束、default 只写一处、职责单一好排查。C 语言里完全对应：next_state() 是纯函数（可单独测试）、output() 集中所有动作、state 只在 fsm_tick() 里被赋值一次。

  8. 状态机跑飞进了一个非法状态，有哪几层手段可以救它？为什么看门狗是最不划算的那一层？

    答：四层：①编码上留余地（减少非法状态数量）②安全编码（默认次态指向复位态，一个时钟自恢复）③监视自愈逻辑（独热码的零检测/多热检测 + 诊断计数）④看门狗兜底。看门狗最不划算是因为它复位整个系统：正在传的数据丢了、外设要重新初始化、执行器会突然断电、用户看到设备重启。而安全编码只需要一个时钟周期，用户毫无察觉。此外还要注意：喂狗动作必须放在「所有任务都正常跑过」的路径上，否则状态机卡死了中断还在喂狗，看门狗形同虚设。

练习

  1. 自动售货机（完整设计）。饮料 1.5 元，只接受 0.5 元和 1 元两种硬币，投入超过 1.5 元要找零。要求：画出状态图（提示：用状态表示「已投入多少钱」，恰好是 0 元 / 0.5 元 / 1.0 元 / 1.5 元四档，投币和退币是输出）；列出状态表；用 2 位二进制编码；写出两个 D 触发器的激励方程和「出货」「找零」两个输出方程；检查有没有非法状态，如果有，给出安全编码方案。加分：如果改成「接受任意金额并可退币」，状态数会变成多少？为什么这时应该换一种设计思路（提示：状态表示「金额档位」会爆炸，改成「状态表示流程阶段 + 一个金额变量」）？
  2. 串口命令行解析器（写代码）。用状态机实现一个以换行符 \n 结尾的命令行解析器，支持 LED ON、LED OFF、GET TEMP 三条命令。要求：① 用 enum 定义状态（至少要有「等命令字符」「等参数」「完成」）；② 行缓冲必须有溢出保护（缓冲区满了不能写穿，要丢弃并回复错误）；③ 必须有行超时（收到半行之后再没有字节，要能自动丢弃）；④ 非法命令要回复 ERROR 而不是静默；⑤ 把它写成不碰硬件的纯函数，然后在 PC 上写至少 6 条用例（正常三条、超长一行、半行超时、非法命令）并全部跑通。
  3. 改造你自己的项目（最推荐做这个）。在你的板子上找一个用 delay 写成的顺序流程——比如「初始化传感器 → 等 100ms → 读 ID → 失败重试 3 次 → 上报结果」。把它改写成状态机。步骤：①先画出状态图（你会惊讶地发现有 5~8 个状态）；②把每个 delay 换成一个时间戳 + 一个判断；③把重试次数做成一个变量而不是嵌套的 for；④加一个总超时，避免永远重试；⑤加一个诊断计数，统计每一类失败发生了多少次。改完之后你会得到一个额外的收获：原来「卡在哪一步」是未知的，现在串口一打印就知道。
  4. 按键手感实验（需要逻辑分析仪或示波器）。把按键接上示波器，实测你自己板子上按键的抖动时间（看一眼从第一个边沿到电平稳定花了多少毫秒）。把实测值填进 KEY_DEBOUNCE_MS，然后用第 4 节的测试代码跑用例。进阶：把消抖窗口改成 2ms（故意偏小）和 50ms（故意偏大），分别在真板上按 50 次，记录误触发次数和「按了没反应」次数，体会一下这个参数的真实影响。
