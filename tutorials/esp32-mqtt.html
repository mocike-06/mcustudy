原理介绍

先说结论：MQTT 是一套为「设备之间隔着不可靠网络、还要省电」而设计的消息协议。 它不关心你传的是温度还是开关命令，只负责把一小段字节从 A 送到 B。 ESP32 在这里的角色叫 客户端（Client）， 中间那台负责转发的服务器叫 Broker（代理）。 你的板子只要跟 Broker 保持一条 TCP 长连接，就能既发数据、又收指令， 完全不需要知道对方是谁、IP 是多少。

为什么物联网用 MQTT 而不是 HTTP

你可能会想：我直接用 HTTP 请求一个网址把数据 POST 上去不行吗？当然行，很多云平台也支持 HTTP。 问题出在「谁主动」这件事上。 HTTP 是拉（Pull）模型：设备不主动问，服务器就没机会说话。 所以设备想接收控制指令，只能不停地问：「有我的新指令吗？没有。有我的新指令吗？没有。」 这种写法叫轮询（Polling），代价是双份的： 问得太慢，指令延迟高；问得太快，射频和 CPU 一直在醒着，电池撑不住。

MQTT 是推（Push）模型：设备跟 Broker 保持一条常连接， 有消息 Broker 直接推过来。空闲时双方只交换一个 2 字节的心跳包， 设备的数据只在「真的变了」的时候才发出去。对一块用电池供电、要跑几个月的节点来说，这个差别是决定性的。

对比项 HTTP 轮询（每 10 秒问一次） MQTT（长连接）
通信方向 只能设备主动请求，服务器无法主动通知 双向，Broker 可随时把消息推给设备
指令延迟 平均半个轮询周期，本例约 5 秒 毫秒级，收到即转发
单次协议开销 请求头通常 200~800 字节 固定头最少 2 字节，主题名另算
一天的流量（粗算） 8640 次请求，光请求头就 2~7 MB 约 5760 次心跳 × 2 字节 ≈ 11 KB，加上真实数据
一对多分发 每台设备各自去问一次 一条消息同时送达所有订阅者
适合的场景 网页、一次性查询、几分钟才上传一次的场合 遥测上报、远程控制、设备状态同步
一句话记住区别

HTTP 是你打电话去问，MQTT 是你留了个地址，有事邮局直接送到你家。 这个「邮局」就是 Broker。

Broker 与发布 / 订阅模型

MQTT 里没有「客户端 A 直连客户端 B」这种用法，所有消息都经过 Broker 转发。为什么非要绕一下？ 因为真实的物联网设备大多躲在路由器后面（NAT），IP 是动态的，还经常休眠。 让手机去直连一块 NAT 后面的 ESP32，几乎做不到；但让 ESP32 主动连上一台公网 Broker，再让手机也连上同一台 Broker，就非常简单。

  • Publisher（发布者）——往某个 Topic 发消息的一方。发布者不知道也不关心谁在听。
  • Subscriber（订阅者）——订阅了某个 Topic 的一方。Broker 会把匹配的消息投递给它。
  • Topic（主题）——消息的「信箱地址」，用斜杠分层的字符串，例如 home/livingroom/led/set。
  • Client ID（客户端标识）——连接时提交的身份证。全网必须唯一，重复会被踢。
  • Payload（载荷）——真正的内容，MQTT 不规定格式，纯文本、JSON、二进制都行。

这套模型的工程价值叫解耦：写单片机的人只管往 .../led/set 发 ON， 做手机 App 的人只管订阅同一个主题。双方甚至不需要同时在线—— 设备掉线时消息可以留在 Broker 上（配合 retained 或会话保持），等它回来再收。

本页用哪个 Broker

学习阶段不用自己搭服务器，用公共测试 Broker 就够了。本页代码默认连 broker.emqx.io 的 1883 端口； 也可以换成 test.mosquitto.org。 注意这两台都是公开免费、任何人可读写的测试服务器， 别往上发隐私数据，也别指望它 7×24 稳定。将来上生产环境时，换成自己搭的 EMQX / Mosquitto，或者阿里云、腾讯云、OneNET 这类平台给的接入地址即可，代码结构完全一样。

Topic 分层与通配符

Topic 用 / 分层，像文件夹路径。分层的意义是让订阅可以「按范围」而不是「按名字」： 你可以只订阅客厅的灯，也可以一次订阅整栋楼所有的灯。

建议的分层习惯是 项目/设备/功能/动作，例如：

  • mcustudy-a1b2/led/set——下行控制：别人发给我，我按这个动作执行。
  • mcustudy-a1b2/status——上行状态：我告诉别人我现在什么样。
  • mcustudy-a1b2/sensor/temp——只上报温度，将来加湿度就再开一个同级的主题。
写法 含义 能否用于发布
mcustudy-a1b2/led/set 精确匹配这一个主题 可以
mcustudy-a1b2/+/set + 匹配一层，如 led、lamp、fan 不可以，只能用来订阅
mcustudy-a1b2/# # 匹配剩下所有层，必须放在末尾 不可以，只能用来订阅
mcustudy-a1b2/led/set/ 末尾多一个斜杠，是另一个主题了 可以，但不建议
三个新手必踩的主题坑
  • Topic 大小写敏感：订阅 Led/Set，发布到 led/set，一辈子也收不到。
  • 不要以 / 开头。以斜杠开头是合法的，但会产生一个空的第一层，和别人的主题体系对不上。
  • 在公共 Broker 上，主题前缀一定要加自己的唯一标识（本页代码用芯片 ID 生成）。否则你发到 led/set，全世界测试的人都收到了。

QoS、keepAlive 与遗嘱消息

QoS（服务质量）决定了这条消息「送到」的严格程度。 它不是越高越好——等级越高，网络往返次数越多、延迟越大、对设备资源占用也越多：

等级 叫法 一次投递的往返 会丢吗 会重复吗 典型用途
0 至多一次 1 次（发完就不管） 可能丢 不会 高频传感器数据，丢一两个点无所谓
1 至少一次 2 次（PUBLISH → PUBACK） 不丢 可能重复 控制指令、状态上报，最常用的一档
2 恰好一次 4 次握手 不丢 不会 计费、开关柜动作等绝对不能重复的场景

注意 QoS 1 的「至少一次」意味着你的处理函数可能收到重复指令。 对「开灯 / 关灯」这种幂等操作无所谓，但如果指令是「余额扣 1 元」，就必须自己做去重。

keepAlive（保活间隔）解决的是「怎么发现对方已经死了」。 长连接上双方都不说话时，谁也不知道对面是还在待命还是已经断电。 MQTT 的约定是：客户端在 keepAlive 时间内必须至少发一次包（没有业务数据就发 2 字节的 PINGREQ 心跳），Broker 只要在 1.5 倍 keepAlive 的时间里没收到任何东西，就判定客户端掉线并断开连接。 PubSubClient 里这个值是宏 MQTT_KEEPALIVE，默认 15 秒， 也就是说你只要超过 22.5 秒没让库跑起来收发，就会被 Broker 踢掉。

遗嘱消息（LWT, Last Will and Testament）是给「设备猝死」准备的后事。 连接时就把一份消息寄存在 Broker 上，声明「如果我不正常掉线了，请帮我把它发出去」。 典型用法是遗嘱主题 = 状态主题、内容 = offline， 这样监控端能立刻知道设备不是主动下线的，而是掉电或断网了。 配合 retained（保留消息）， 后加入的订阅者一连上就能立刻拿到设备的最后状态，不用傻等下一次上报。

遗嘱消息的触发条件，很多人理解错

遗嘱只在异常断开时由 Broker 代发：拔电源、断网、死机、心跳超时。 设备主动调用 client.disconnect() 正常下线时， Broker 认为它是体面离开的，不会发遗嘱。 所以调试时拔 USB 线能看到 offline，正常关串口却看不到，这是对的，不是 bug。

硬件接线说明

MQTT 走的是 WiFi，本身不需要任何新增接线—— 只要能连上 2.4GHz 路由器的 ESP32 开发板就行。这一节主要是把「用来验证的 LED」和几根容易接错的线说清楚， 顺便强调几个 ESP32 特有的引脚约束。接线错了，代码再对也看不到现象。

要点：
1. GPIO2 上已经有板载 LED，先用它验证程序，成功率最高。
2. 外接 LED 时，限流电阻串在 GPIO 和 LED 长脚之间，短脚接 GND。
3. ESP32 的 GPIO6~GPIO11 内部接了 Flash，任何时候都不能拿来当普通 IO 用。

接线与上电顺序建议

  1. 先什么都不接，直接插 USB，确认设备管理器里出现了串口（CP2102 或 CH340）。
  2. 烧一个最简单的 Blink 确认板子和工具链都正常，再开始接外设——把「环境问题」和「接线问题」分开。
  3. 接外接 LED 时先断电，接完用万用表确认 GPIO4 与 GND 之间没有短路。
  4. 最后再上电，打开串口监视器看日志。日志是这一篇最重要的观察手段。
上电前必查
  • USB 线是不是数据线。现象是「板子亮了但电脑里没有串口」，换线即可。
  • 有没有把 5V 引脚当成 3.3V 用。ESP32 的 IO 是 3.3V 耐受，不耐 5V，直接把 5V 信号接进 GPIO 会烧引脚。
  • GPIO2 是启动模式相关引脚，但正常启动（GPIO0=1 → SPI Boot Mode）时它取任意值、不被检查；只有进串口/联合下载模式（GPIO0=0）才要求 GPIO2=0。芯片内部默认下拉，板载 LED 就接在这里。
  • 烧录时如果串口一直报 Failed to connect，按住 BOOT 键再点上传可以强制进下载模式。

完整代码

在 Arduino IDE 里先装库：工具 → 管理库，搜索 PubSubClient，安装 Nick O'Leary 那个版本（2.8 或更高）。 WiFi.h 是随 ESP32 板包自带的，不用单独装。 然后把下面的代码整段复制进 .ino 文件， 只需修改开头三行 WiFi 名称、密码和（可选的）Broker 地址。 

/* =====================================================================
 * esp32_mqtt_led.ino
 * 功能：ESP32 连接 MQTT Broker，订阅控制主题点灯 / 灭灯，并定时上报状态
 * 硬件：ESP32-WROOM-32 开发板（板载 LED 在 GPIO2，高电平点亮）
 * 依赖：PubSubClient（Arduino 库管理器安装，作者 Nick O'Leary）
 * ===================================================================== */

#include <WiFi.h>            // ESP32 的 WiFi 库，随板包自带
#include <PubSubClient.h>    // MQTT 客户端库，需要自己装

/* ------------------------- 需要你改的地方 ------------------------- */
const char* WIFI_SSID = "你的WiFi名称";     // 只能 2.4GHz，ESP32 不认 5GHz
const char* WIFI_PASS = "你的WiFi密码";
const char* MQTT_HOST = "broker.emqx.io";   // 公共测试 Broker，也可换 test.mosquitto.org

/* ----------------------------- 常量 ----------------------------- */
const uint16_t MQTT_PORT = 1883;     // 明文端口；8883 是 TLS 加密端口，本页不用
const uint8_t  LED_PIN   = 2;        // 板载 LED 接在 GPIO2
const uint32_t REPORT_MS = 10000;    // 状态上报间隔：10 秒
const uint32_t RETRY_MS  = 3000;     // 断线后每 3 秒尝试重连一次

WiFiClient   espClient;              // 底层 TCP 连接（MQTT 跑在 TCP 之上）
PubSubClient client(espClient);      // MQTT 客户端对象，构造时绑定这条 TCP 连接

String topicPrefix;                  // 本机专属主题前缀，避免和公共 Broker 上别人的主题撞车
String topicLedSet;                  // 下行：别人发指令给我
String topicStatus;                  // 上行：我上报自己的状态
char   clientId[40];                 // 客户端 ID，必须全网唯一

bool     ledState   = false;         // 当前 LED 状态，true = 点亮
uint32_t lastReport = 0;             // 上次上报的时刻
uint32_t lastRetry  = 0;             // 上次尝试重连的时刻

/* ---------------------------------------------------------------------
 * 【第一部分】收到订阅消息时的回调
 * 注意：payload 不是以 '\0' 结尾的字符串，长度由 length 给出，
 *      必须自己按长度拼成 String，不能直接当 C 字符串用。
 * ------------------------------------------------------------------- */
void onMqttMessage(char* topic, byte* payload, unsigned int length) {
  String msg;
  for (unsigned int i = 0; i < length; i++) {
    msg += (char)payload[i];         // 逐字节还原成文本
  }
  msg.trim();                        // 去掉首尾空白，手机端很容易多打空格
  msg.toUpperCase();                 // 统一转大写，ON / on / On 都能识别

  Serial.printf("[收到] 主题=%s 内容=%s\n", topic, msg.c_str());

  if (msg == "ON" || msg == "1") {
    ledState = true;
  } else if (msg == "OFF" || msg == "0") {
    ledState = false;
  } else {
    Serial.println("[忽略] 只认 ON / OFF / 1 / 0");
    return;                          // 未知指令不改状态
  }

  digitalWrite(LED_PIN, ledState ? HIGH : LOW);   // 真正执行动作

  // 执行完立刻回报一次，retained = true：
  // 后订阅的人一连上就能看到最新状态，不用等下一次定时上报
  client.publish(topicStatus.c_str(), ledState ? "led=on" : "led=off", true);
}

/* ---------------------------------------------------------------------
 * 连接 WiFi：只在 setup() 里调用一次
 * 此时还没进主循环，用阻塞等待是可以接受的
 * ------------------------------------------------------------------- */
void connectWiFi() {
  Serial.printf("[WiFi] 正在连接 %s", WIFI_SSID);
  WiFi.mode(WIFI_STA);                        // 站点模式：像手机一样去连路由器
  WiFi.begin(WIFI_SSID, WIFI_PASS);

  while (WiFi.status() != WL_CONNECTED) {     // 没连上就一直等
    delay(500);
    Serial.print(".");
  }
  Serial.printf("\n[WiFi] 连接成功，IP = %s\n", WiFi.localIP().toString().c_str());
}

/* ---------------------------------------------------------------------
 * 连接 MQTT Broker：断线时会被反复调用
 * ------------------------------------------------------------------- */
void reconnect() {
  if (WiFi.status() != WL_CONNECTED) {        // WiFi 都断了，先别谈 MQTT
    Serial.println("[MQTT] WiFi 未连接，等待自动重连");
    return;
  }

  Serial.printf("[MQTT] 正在连接 %s:%u ...", MQTT_HOST, MQTT_PORT);

  // connect(id, 用户名, 密码, 遗嘱主题, 遗嘱QoS, 遗嘱retain, 遗嘱内容)
  // 遗嘱消息 LWT：只有「异常掉线」（拔电、断网、死机）时由 Broker 代发，
  // 正常调用 client.disconnect() 不会触发。
  bool ok = client.connect(clientId, NULL, NULL,
                           topicStatus.c_str(), 1, true, "offline");

  if (!ok) {
    // client.state() 返回负数就是失败原因，排查时很有用
    Serial.printf(" 失败，client.state()=%d\n", client.state());
    return;
  }

  Serial.println(" 成功");
  client.publish(topicStatus.c_str(), "online", true);   // 上线通告
  client.subscribe(topicLedSet.c_str(), 1);              // 订阅控制主题，QoS 1
  Serial.printf("[MQTT] 已订阅 %s\n", topicLedSet.c_str());
}

void setup() {
  Serial.begin(115200);
  delay(300);                                 // 等 USB 串口稳定，否则前几行日志会丢

  pinMode(LED_PIN, OUTPUT);                   // GPIO2 设为输出
  digitalWrite(LED_PIN, LOW);                 // 上电默认灭

  connectWiFi();

  // 用芯片 MAC 生成唯一的 clientId 和主题前缀。
  // 同一个 clientId 被两个客户端同时使用，Broker 会把先连上的那个踢下线。
  uint64_t chipId = ESP.getEfuseMac();
  snprintf(clientId, sizeof(clientId), "mcustudy-%04X",
           (unsigned int)(chipId & 0xFFFF));

  topicPrefix = String("mcustudy/") + clientId;
  topicLedSet = topicPrefix + "/led/set";     // 例如 mcustudy/mcustudy-1A2B/led/set
  topicStatus = topicPrefix + "/status";

  client.setServer(MQTT_HOST, MQTT_PORT);
  client.setCallback(onMqttMessage);          // 注册回调：订阅主题来消息时执行它

  reconnect();
  lastReport = millis();
}

void loop() {
  /* ---------- 【第二部分】维持连接：这一段的写法决定你会不会掉线 ---------- */
  if (!client.connected()) {
    if (millis() - lastRetry >= RETRY_MS) {   // 限流，别把 Broker 打爆
      lastRetry = millis();
      reconnect();
    }
  } else {
    client.loop();   // ★ 最关键的一行：收发心跳、处理下行消息全靠它
  }

  /* ---------- 【第三部分】定时上报状态 ---------- */
  // 用 millis() 做非阻塞定时。绝不能用 delay(10000)：
  // delay 期间 loop() 不执行，client.loop() 也就不会跑，
  // 超过 1.5 倍 keepAlive（默认 22.5 秒）就会被 Broker 判定掉线。
  if (client.connected() && millis() - lastReport >= REPORT_MS) {
    lastReport = millis();

    char buf[80];
    snprintf(buf, sizeof(buf), "{\"led\":\"%s\",\"rssi\":%d,\"uptime\":%lu}",
             ledState ? "on" : "off", WiFi.RSSI(), millis() / 1000);

    client.publish(topicStatus.c_str(), buf, true);   // retained，便于新订阅者立刻看到
    Serial.printf("[上报] %s\n", buf);
  }

  delay(10);   // 很短的让步，给 WiFi 协议栈留出干活的时间
}

关键代码解析

  • PubSubClient client(espClient);——MQTT 库本身不实现网络， 它只负责协议打包，底层收发交给 WiFiClient。 所以断网时 MQTT 一定会失败，reconnect() 里第一件事就是查 WiFi 状态。
  • msg += (char)payload[i];——为什么不能直接 String(payload)？因为回调给的是一段没有结束符的字节区， 直接当字符串用会一路读到内存里的垃圾数据。按 length 逐字节还原才是正确写法。
  • client.loop();——整篇最重要的调用。它做两件事： 把收到的下行数据交给协议栈解析并触发回调；在空闲时按 keepAlive 发送 PINGREQ 心跳。 它必须在 loop() 里被高频调用， 一秒钟几十次毫无压力，但绝对不能几秒钟才轮到一次。
  • client.connect(clientId, NULL, NULL, topicStatus.c_str(), 1, true, "offline");—— 连接时就顺便把遗嘱登记好：一旦异常掉线，Broker 会往状态主题发一条 retained 的 offline，监控端立刻知道设备失联了。
  • client.subscribe(topicLedSet.c_str(), 1);—— 订阅要在连接成功之后调用。写在 setup() 里、 连接之前，第一次能收到消息是运气，重连之后就永远收不到了。
  • snprintf(clientId, ...) 用 MAC 生成唯一 ID—— 手工写死一个 "esp32" 是新手最痛的一课： 第二块板子一上电，第一块就被踢下线，两块板子轮流掉线，看起来像「WiFi 不稳定」。
  • millis() - lastReport >= REPORT_MS—— 这种「记录上次时刻 + 比较差值」的写法叫非阻塞定时。 它的好处是这段时间里 client.loop() 依然在跑，连接不会因为忙别的而断掉。
怎么在没有手机 App 的情况下先验证

先用电脑端客户端把链路跑通，再考虑手机。推荐 MQTTX（跨平台桌面客户端）或 EMQX 提供的在线 Web 客户端： 填入地址 broker.emqx.io、端口 1883， 订阅主题 mcustudy/#，就能看到板子发的每一条状态和遗嘱消息； 再往 mcustudy/<你的clientId>/led/set 发一条 ON，板载 LED 就会亮。 把串口监视器里的 clientId 抄下来，别拼错。

现象演示说明

这一节用来自查：串口日志里的每一行都有明确的含义， 现象对上了说明链路是通的；现象不对，也能根据停在哪一步直接定位。

正确现象

  1. 上电后串口以 115200 打印 [WiFi] 正在连接 ...，几秒内出现 [WiFi] 连接成功，IP = 192.168.x.x。
  2. 紧接着打印 [MQTT] 正在连接 broker.emqx.io:1883 ... 成功，再打印一行 [MQTT] 已订阅 mcustudy/.../led/set。
  3. 每 10 秒出现一行 [上报] {"led":"off","rssi":-55,"uptime":30}，uptime 每次加 10 左右。
  4. 在电脑端 MQTT 客户端订阅 mcustudy/#，能立刻收到一条 retained 的 online，之后每 10 秒收到一次状态。
  5. 向 .../led/set 发送 ON，板载 LED 在一秒内点亮，串口打印 [收到] 主题=... 内容=ON，同时客户端收到 led=on。
  6. 发送 off（小写）也能关灯——因为代码里做了 toUpperCase()。
  7. 发送 HELLO 这类未知内容，串口打印 [忽略]，灯的状态不变。
  8. 拔掉 USB 线约 22 秒后（keepAlive 超时），电脑端能通过订阅 .../status 收到 Broker 代发的 offline。
  9. 重新上电，一切自动恢复，不需要手动干预。

做课设或毕设时，这里有两个很值得量化记录的指标： 一是控制延迟——从客户端点击发送到 LED 亮起的时间差（可以用手机录屏逐帧看，一般在 100~400ms）； 二是长时间运行稳定性——让板子连续跑 8 小时，统计串口里出现 [MQTT] 正在连接 的次数。把这两个数字和「HTTP 轮询每 5 秒问一次」的方案对比一下， 你的报告就有了真正的工程量，而不只是「我做了一个灯」。

常见报错排查方案

下面这六条覆盖了 MQTT 入门阶段九成以上的卡点， 按「报错原文 → 原因 → 解决」组织，方便你直接按串口里看到的那一行搜索。

连接失败：[MQTT] 正在连接 broker.emqx.io:1883 ... 失败，client.state()=-2

原因：-2 是 MQTT_CONNECT_FAILED，意思是 TCP 层压根没连上：Broker 域名写错（多了个空格、拼成 .com）、端口写错，或者所在网络（校园网、公司网）封了 1883 出站端口。

解决：先用电脑在同一个 WiFi 下 ping broker.emqx.io 看域名解析是否正常；再换成 test.mosquitto.org 试一次，如果两台都连不上，基本就是网络出口限制了 1883，可用手机热点验证。

连上几十秒就掉线：串口反复出现 [MQTT] 正在连接 ... 成功，然后 state()=-3

原因：这是本文最想让你避开的一个坑。主循环里没有调用 client.loop()，或者某处用了 delay(5000)、while 死等之类的阻塞代码，导致心跳 PINGREQ 发不出去。Broker 在 1.5 倍 keepAlive（默认 22.5 秒）没收到任何包，就单方面断开连接。

解决：确认 loop() 每次循环都会执行到 client.loop()；把所有长延时改成 millis() 差值判断；确认没有在 loop() 里出现 while(1) 之类的死循环。

两块板子轮流掉线：A 连上几秒后 B 掉，然后 B 又连上、A 掉

原因：两块板子用了同一个 clientId。MQTT 规范要求 Broker 发现相同 clientId 的新连接时，必须把旧连接断掉——所以它们会互相「踢下线」。同理，电脑端 MQTTX 如果填了和板子一样的 clientId，也会把板子踢掉。

解决：用芯片 MAC 派生唯一 ID（本页代码的 ESP.getEfuseMac() 就是这么做的），每台设备都不一样；客户端软件的 clientId 也让它自动生成。

编译报错：fatal error: PubSubClient.h: No such file or directory

原因：库没有安装，或者装到了别的路径下（比如手动下载压缩包解压到了错误目录）。Arduino 只会搜索「项目文件夹/libraries」和系统的 sketchbook 库目录。

解决：用 工具 → 管理库搜索 PubSubClient 在线安装，装完重启 IDE。如果坚持手动安装，解压后的文件夹名必须是 PubSubClient，不能是 PubSubClient-master 这种带后缀的名字。

发布失败：publish() 返回 false，串口显示发送不出去（上报忽有忽无）

原因：PubSubClient 内部有一块固定大小的收发缓冲，宏 MQTT_MAX_PACKET_SIZE 默认只有 256 字节。你发的 JSON 一旦超过这个长度，库会直接拒绝发送并返回 false。

解决：优先精简 payload（去掉多余的字段名）；确实需要长报文时，在 setup() 里调用 client.setBufferSize(512);（PubSubClient 2.7 以上支持），并注意这会多占宝贵的 RAM。

订阅了却收不到消息：客户端订阅 mcustudy/# 一条都没有

原因：按可能性排序——一是 subscribe() 写在了连接成功之前，或者只在 setup() 里调用一次、重连之后忘了重新订阅；二是主题大小写或层级不一致；三是订阅时用了 # 但发布端发到了以 / 开头的主题上，空的第一层让通配符匹配不到。

解决：把 subscribe() 放进 reconnect() 里（每次连上都订阅一遍）；在串口里把发布和订阅的主题名都打印出来逐字符对比；先统一去掉主题开头的斜杠。

公共 Broker 本身的不确定性

如果你已经排除了上面所有可能，仍然每隔几十分钟断一次，那大概率不是你的问题： broker.emqx.io 和 test.mosquitto.org 是给全世界练手用的公共服务器，会重启、会限流、偶尔丢包。 正确的做法不是加长重连逻辑去硬扛，而是承认它不可靠： 代码里只要有「检测断线 + 限流重连 + 重连后重新订阅」这三件套，就能自愈。 做正式项目时，请换成自己部署的 EMQX / Mosquitto 或商业云平台的接入点。

小结与练习

这一篇把 ESP32 从「连上 WiFi 的孤岛」变成了「能被远程控制的节点」。 核心链路只有四步：连 WiFi → 连 Broker → 订阅主题 → 在主循环里持续跑 client.loop()。 真正需要记住的知识点有三个：MQTT 是推模型，比轮询省电； Topic 决定谁能收到，clientId 决定谁在线； 以及 client.loop() 不跑，连接必掉。

排错时也有一套固定顺序：先看 WiFi 有没有通（串口第一行），再看 MQTT 有没有连上（client.state()）， 再看订阅有没有成功，最后才怀疑业务代码。这个顺序能帮你跳过大半的无效折腾。

动手练习
  1. 把状态改成 retained + 上电即读。 现在的代码已经用 retained 发布状态了，请验证它：先把板子断电，在电脑端订阅 mcustudy/# 并等待，你会发现一连上就立刻收到最后一条 led=on——这条消息不是板子发的，而是 Broker 保存下来补发的。 想清楚：这个特性适合解决什么实际问题（提示：手机 App 打开时不知道灯是开还是关）。
  2. 加一个本地按键，做双向同步。 在 GPIO0 上接一个按键到 GND，按下时翻转 LED，并立刻把新状态 publish 到状态主题。然后用电脑端观察：远程控制和本地按键会不会打架？ 想一想 real-world 里怎么处理这种「两边同时改一个状态」的冲突。
  3. 做一次 QoS 对比实验。 把订阅和发布的 QoS 分别改成 0 和 1，在发送指令的瞬间拔掉 ESP32 的电源再插回， 统计各 20 次里有多少次指令没有生效。用数据回答：控制指令该用哪个等级？ 顺便试试 QoS 2，看看延迟有没有肉眼可见的变化。
  4. （进阶）用遗嘱消息做一个在线状态面板。 保持遗嘱内容为 offline、上线通告为 online， 都发到同一个主题；写一个简单的电脑端脚本或使用在线客户端，统计 5 分钟内板子的上下线次数。 如果次数异常多，回到排错表里找原因——这本身就是一套真实可用的设备健康监测。
