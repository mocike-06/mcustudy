嵌入式软件架构

前面几篇，你学的是「零件」：C 语言的 volatile 和位操作、中断怎么打断主程序、定时器怎么数出 1 毫秒、DMA 怎么不占 CPU 地搬数据。但真正动手做项目时，你会撞上一个新的问题——这些零件该怎么拼在一起？程序的控制流长什么样？一个功能一件事，还是要切成好几个「任务」？按键、数码管、串口、ADC 挤在同一个 while(1) 里，谁先谁后？中断收到了数据，凭什么交给主循环？ 这一篇讲的就是整个程序怎么组织：从最原始的「顺序执行 + 死循环」，到前后台系统为什么会崩，到带任务表的时间片轮询调度器，到任务怎么切分、消息怎么传递、模块怎么分层，最后落到一张「裸机 ↔ RTOS 概念对照表」上——你会看清 FreeRTOS 里那些名词，其实你在裸机上早就手工实现过一遍了。

为什么需要它

先讲一个你大概率会遇上的现场。

你的课设板子上星期还是好的：三个按键能设定温度，四位数码管显示当前值，风扇跟着转。答辩前三天，老师提了一句「最好能连电脑看曲线」，于是你在主循环末尾加了三行：

/* 每 100 ms 把温度发到串口 */
char buf[32];
int n = sprintf(buf, "T=%d.%d\r\n", t / 10, t % 10);
HAL_UART_Transmit(&huart1, (uint8_t *)buf, n, 1000);

加完之后的第一个晚上，现象是这样的：数码管开始明显发暗、偶尔跳字；按键要按两三次才有反应；风扇倒还转，但转速变化变得一顿一顿的。你把这三行注掉，一切恢复正常。你很自然地得出一个结论：「串口占用了 CPU，把别的功能挤慢了。」

这个结论只对了一半，而且是最不重要的那一半。真实的原因是：HAL_UART_Transmit 是一个阻塞函数——它把 15 个字节一个个塞进发送寄存器，一边塞一边等「发送寄存器空」标志，115200 波特率下每个字节约 86.8 µs，15 个字节就是 约 1.3 ms，这段时间里 CPU 什么都干不了，主循环原地卡住。而你的主循环本来一轮只需要 300 µs。也就是说，你往一个 300 µs 的循环里塞了一个 1.3 ms 的阻塞块，循环周期瞬间变成 5 倍。

数码管是动态扫描的：4 位轮流点亮，每位亮 2 ms，一轮 8 ms。主循环一旦变成 1.3 ms 起步、加上别的功能可能到 3 ms，某一位就会亮得特别久、其他位相对变暗——这就是你看到的「发暗、跳字」。按键更直接：你的消抖逻辑要求每 10 ms 采样一次、连续两次为按下才认，采样点被拉开到 3 ms 之后就变成「有时采到、有时采不到」。

真正的问题不是「串口慢」，而是「结构脆」

这个故障里没有一个器件坏掉、没有一行语法错误、没有一个寄存器配错。它坏在程序的骨架上：所有功能串在一条线上，任何一环变慢，所有其他功能跟着变慢。你加的是「一个通信功能」，付的代价却是「全系统实时性下降」。

这就是「软件架构」要解决的问题：不是让代码能跑，而是让一个功能的变化只影响它自己。

「能跑」和「能改」是两件事

单片机入门阶段，判据只有一个：功能实现了没有。灯亮了、温度读出来了、风扇转了，就算完成。这个判据在只有一两个功能时完全够用，因为程序短到你脑子里能装下全部。

一旦功能数超过三四个，判据就要换。你要开始回答另一类问题：

  • 加一个功能，要改几个地方？——如果答案是「主循环里插一段、还要去改另外两个功能的等待时间」，那你迟早会改崩。
  • 改坏的时候，你怎么知道是哪里坏？——如果现象是「数码管闪」，原因却可能是「串口发送」，你的排查成本会高到无法接受。
  • 能不能把某一个功能单独拿出来测？——如果每个功能都依赖「别的功能已经跑过了、某个全局变量已经算好了」，那你没法单独测。
  • 最坏情况下，按键多久能响应？——如果你答不出一个数字，说明你对系统的时序没有掌控，只是「碰巧够快」。
  • 换个芯片、换个显示器件，要重写多少？——如果业务逻辑里到处是 GPIOA->ODR，那就是全部重写。

这五个问题的答案，取决于你选的控制流结构（程序按什么顺序执行）、任务切分方式（哪些代码算一个独立单位）、通信机制（各部分之间怎么传数据）和分层方式（谁可以直接调用谁）。这四件事合起来，就叫嵌入式软件架构。

核心概念

这一节有八个部分，它们是按「从坏到好、从散到整」的顺序排的：先看三种控制流结构长什么样（2.1），再看最常用的前后台系统为什么会崩（2.2），然后是替代它的时间片轮询调度器（2.3）；接着是三个「怎么切、怎么传、怎么写」的问题——任务怎么切分（2.4）、消息怎么传递（2.5）、单个任务内部怎么写才不阻塞（2.6）；最后是两件工程上的事——怎么分层才能改得动、测得动（2.7），以及这套裸机架构怎么平滑长成 RTOS（2.8）。

2.1 三种基本控制流结构：同一需求的三版伪代码

「控制流结构」就是程序按什么顺序执行代码。单片机上只有三种常见的基本形态，从上到下依次是能力递增的：

① 顺序执行 + 死循环          ② 前后台系统（super-loop）      ③ 时间片轮询

     ▼                                     │ 置标志                       │
   while (1) {                             ▼                              ▼
     读按键();   ← 阻塞消抖          ┌ 后台：主循环 ────────┐       任务表：函数指针 + 周期

下面用同一个需求把三种方式各写一遍。需求是：3 个按键设定目标温度、4 位数码管显示当前温度、串口每 100 ms 上报一次、ADC 每 10 ms 采一次用于控温。芯片是 STM32F103C8T6（72 MHz），串口 115200 8N1。

版本 A：顺序执行 + 死循环。这是最原始的结构：把所有功能按顺序排进一个永远不退出的大循环，需要一个「延时」就原地等。它的优点是看得懂——从上到下就是执行顺序；缺点是只有一个时间尺度。

main:
    初始化()                       /* 时钟、GPIO、USART、ADC、TIM */

    while (1) {
        读按键()                   /* 内部 HAL_Delay(20) 做消抖 → 阻塞 20 ms */
        更新设定值()

        刷新数码管()               /* 4 位依次点亮，每位 HAL_Delay(2) → 阻塞 8 ms */

        启动一次 ADC 转换()
        while (!转换完成())        /* 原地等，典型 1~2 µs（这里短，但模式很危险） */
        温度计算()                 /* 一阶滤波 + 查表 */
        控制风扇()                 /* 更新 PWM 占空比 */

        串口上报("T=%d.%d\r\n")    /* 阻塞发送 15 字节 @115200 → 约 1.3 ms */
    }

/* 一轮的耗时 = 20 + 8 + 0.005 + 1.3 ≈ 29.3 ms
   于是：按键扫描周期 29.3 ms、数码管刷新率 1/(8 ms) 只在那一刻有效、
        ADC 采样周期 29.3 ms、串口上报周期 29.3 ms（而不是想要的 100 ms）
   —— 所有功能的「周期」被强行绑成同一个数字，而这个数字由最慢的那个环节决定 */

版本 A 在什么时候是对的？当整个系统只有一个功能、或者所有功能的节奏要求完全一致时。比如「读一次传感器、点一个灯、睡 100 ms」这种采集器，版本 A 最省事。但只要有两个节奏要求不同的功能，它就开始错了。上面这四件事的节奏要求分别是 20 ms、2 ms、10 ms、100 ms，差了两个数量级，塞进同一个循环必然互相牵制。

版本 B：前后台系统。把「需要立刻响应的事」交给中断（前台），把「需要计算和处理的事」留在主循环（后台）。中断里只做最少的事——取数据、置标志，然后马上退出。

/* ───── 前台：中断服务函数，越短越好 ───── */
SysTick_Handler:     每 1 ms     g_tick++
EXTI0_IRQHandler:                g_key_irq_flag = 1        /* 只置标志 */
USART1_IRQHandler:               g_rx_buf[g_rx_cnt++] = DR  /* 只搬字节 */
ADC1_IRQHandler:                 g_adc_raw = DR;  g_adc_flag = 1
TIM3_IRQHandler:                 翻转 PWM 引脚（或什么都不做，硬件自动输出）

/* ───── 后台：主循环，按「能做的事」顺序排 ───── */
main:
    初始化()
    while (1) {
        if (g_key_irq_flag) {                /* 事件驱动：有事才做 */
            g_key_irq_flag = 0
            处理按键()
        }
        if (g_adc_flag) {
            g_adc_flag = 0
            温度计算()
            控制风扇()
        }
        刷新数码管()                          /* 无条件刷新，内部含 HAL_Delay(2) ×4 = 8 ms */
        if (g_tick - t_last >= 100) {
            t_last = g_tick
            串口上报()                        /* 阻塞 1.3 ms */
        }
    }

版本 B 比版本 A 强在两点：① 按键和串口接收从「轮询等待」变成了「中断打断」，它们的捕获时刻不再受主循环节奏影响，掰掉了版本 A 最疼的那根刺；② 用 g_tick - t_last >= 100 这种时间戳比较代替了 HAL_Delay(100)，串口上报不再是「死等 100 ms」，而是「到点了就发」。这个转变非常关键——它是本章后面一切内容的地基。

但版本 B 仍然留着两个硬伤：刷新数码管() 里的 8 ms 阻塞和 串口上报() 里的 1.3 ms 阻塞。在这 9.3 ms 里，中断还在不断置标志（串口甚至可能因为来不及取走而溢出），但主循环出不来。中断解决了「不错过事件」，没有解决「及时处理事件」。这就是 2.2 要展开的六个死穴。

版本 C：时间片轮询。把每个功能变成一个「任务」，用一个 1 ms 的节拍中断做统一的时间基准，再用一张任务表记录每个任务的周期和上次运行时刻。主循环退化成一台极简的调度器：到点了就调用，没到点就跳过。

/* ───── 节拍中断：只做一件事 ───── */
SysTick_Handler:  每 1 ms   g_tick++          /* 一行代码，耗时约 0.1 µs */

/* ───── 任务表：整个程序的结构，一眼看得完 ───── */
任务表 = {
    { Key_Scan,     10, 0, 使能, 80  µs },    /* 3 键扫描 + 消抖状态推进 */
    { Seg_Scan,      2, 0, 使能, 60  µs },    /* 点亮 1 位，4 位轮转 → 8 ms 一轮 */
    { Adc_Sample,   10, 3, 使能, 120 µs },    /* 相位偏移 3 ms，避开撞车 */
    { Cmd_Parse,     5, 0, 使能, 180 µs },    /* 从环形缓冲取指令并解析 */
    { Fan_Ctrl,    100, 0, 使能, 200 µs },    /* 控温策略，更新 PWM */
    { Uart_Report, 100, 7, 使能, 350 µs },    /* 相位偏移 7 ms */
    { Led_Tick,    500, 0, 使能, 10  µs },    /* 心跳灯 */
}

/* ───── 调度循环：通用，加功能不用改它 ───── */
main:
    初始化()
    启动 1 ms 节拍()
    while (1) {
        now = g_tick                         /* 整轮用同一个时间基准 */
        对每个任务 t:
            if (t.使能 且 now - t.上次 >= t.周期) {
                t.上次 = now
                t.函数()                     /* 内部绝不允许阻塞 */
            }
    }

/* 每个任务内部都改写成「到点做一小步」：
   Seg_Scan  = 点亮第 n 位 → n = (n+1) % 4
   Key_Scan  = 读一次 GPIO + 推进消抖状态机（不延时）
   Uart_Report = 把数据放进发送队列，由串口中断/DMA 慢慢发（不等待） */

「三版伪代码」的读法：不是要你一次跳到版本 C

实际项目里，这三种结构是共存的：整个程序的时间基准用版本 C 的任务表；某个具体功能内部（比如一段通信协议解析）可能用版本 A 的思路写成一个线性流程；而中断仍然是版本 B 的角色——只置标志、只搬数据。

你要建立的判断力是：什么时候该从 A 升级到 B，什么时候该从 B 升级到 C。升级的信号很明确——出现「加了新功能，老功能变慢/失灵」这个现象时，就该升级了。

2.2 前后台系统：前台是中断，后台是主循环，以及它的六个死穴

前后台系统（super-loop，也叫「超循环系统」）是单片机世界里用得最多、也最容易写出隐藏 bug 的结构。它的全部内容可以用两句话说完：

前后台系统的定义

前台（foreground）＝ 中断服务函数。它由硬件事件触发，可以随时打断正在执行的任何代码。它负责「第一时间响应」：把数据取走、把标志置上、把最紧急的动作做掉，然后立刻退出。

后台（background）＝ 主循环。它是一个 while(1)，在没有中断发生的时候一直在跑。它负责「把事做完」：判断谁有请求、做计算、刷显示、发数据。

「前台」之所以叫前台，是因为它总是优先——只要中断来了，主循环立刻让路，等中断服务函数返回后再接着跑。所有中断服务函数加起来，构成了一个比主循环优先级别更高、但时间碎片化的执行层。

        时间 ──────────────────────────────────────────────────────────────▶

主循环   ──[ 处理按键 ][ 刷数码管 ][ 控温 ]──┐        ┌──[ 接着刷数码管 ]──[ 串口上报 ]──
（后台）                                     │        │

                                             │        │      它随时可能被切碎
中断请求 ─────────────────────────────────┐  │        │
（前台）                                  │  │        │

中断服务  ──────────────────────────────[按键]─────────[ADC]──[串口]────────────
                                          0.5 µs      1 µs   1.5 µs

                                     打断主循环    再打断   再打断（可能嵌套）

两条铁律：
  1. 中断服务函数必须短 —— 它执行时，后台彻底停摆，且同级中断被屏蔽
  2. 中断和主循环之间只能通过 volatile 变量和「置标志」通信，绝不用阻塞等待

这套结构有一个非常漂亮的思想，叫事件驱动（event-driven）：主循环不再「按顺序一路执行下去」，而是「检查有没有事件发生，有事才做」。中断是事件的产生者，主循环是事件的消费者。你在版本 B 里写的那几行 if (g_adc_flag) { g_adc_flag = 0; 温度计算(); }，就是事件驱动的最小形态。

但事件驱动只解决了「不错过事件」。它没有解决「事件来了之后，处理它要花的时间由谁承担」。后台还是一个串行的、所有功能排队共享的大循环。下面六个死穴，本质上都是这一件事的不同侧面。

死穴 ①：任何一个环节阻塞，都会拖垮全部功能。主循环是一条线，线上一处停下，整条线都停。HAL_Delay()、while(!flag);、HAL_UART_Transmit() 等待发送完成、HAL_ADC_PollForConversion() 等待转换——这些函数在等待期间 CPU 不是「顺便做点别的」，而是真的在原地空转。

故障现场 · 「每秒上报一次」把按键按死了

为了「每 1 秒把温度上报到电脑」，你在主循环末尾写了 HAL_Delay(1000); 上报();。想法是「反正每秒只花 1.3 ms 发数据」。

实际发生的是：主循环每转一圈，就有 1000 ms 完全停住。按键扫描代码也在这条线上，于是按键的实际采样周期变成了 1000 ms 以上。用户按下按键，程序平均要等 0.5 秒、最坏要等 1 秒才「看见」这一次按下；再经过两次确认消抖，最坏响应超过 2 秒。用户会认为「按键坏了」，然后开始使劲长按，触发你还没写好的长按逻辑。

这里最反直觉的一点是：你只加了「每秒一次」的功能，代价却是把整个系统的响应速度从毫秒级降到秒级。正确的写法是 if (g_tick - t_last >= 1000) { t_last = g_tick; 上报(); }——把「等 1000 ms」换成「每秒检查一次到点没有」。

死穴 ②：功能之间靠全局变量耦合，改一处崩三处。前后台系统里的通信方式通常只有一种：谁有数据就写进全局变量，谁要数据就去读那个全局变量。这看起来最省事，实际上把「模块的边界」彻底抹掉了——没人知道一个全局变量被几个地方读过、写出的值代表什么单位、处于什么范围。

故障现场 · 显示突然变成了 3276

原来的代码里，ADC 任务把 NTC 温度算成「0.1 ℃」为单位存进 g_temp（25.3 ℃ 存成 253），数码管任务负责拆成 4 位显示。某天你为了给串口上报省点事，把 ADC 任务的最后一行改成了直接存原始值：g_temp = adc_raw;（0~4095）。

编译通过，没有警告。板子跑起来之后，数码管上显示出 3276 这样的数字，风扇满速狂转（因为控温任务读到 3276，以为温度高达 327.6 ℃）。你只改了一个赋值，坏掉的却是显示和控温两个功能，而且报错的地方离出错的地方隔了两个函数。

更隐蔽的版本是「同名不同义」：按键任务把 g_mode 的 0 定义为「自动」，串口命令解析里把 0 定义为「手动」，两个人都觉得自己是对的。这种 bug 不会崩，只会让模式偶尔乱跳，你可能查一整晚。

死穴 ③：实时性完全取决于最慢的那个任务。主循环的周期等于「所有功能的耗时之和，加上所有阻塞等待」。你无法为某个功能单独承诺一个响应时间，因为它前面排着所有其他功能。

故障现场 · 加了 OLED，数码管开始闪

你原本用 4 位数码管显示，2 ms 点亮一位，一轮 8 ms（刷新率 125 Hz），很稳。后来为了「看起来高级」加了 0.96 寸 OLED，每轮主循环整屏刷新一次：1024 字节通过 I²C 400 kHz 送出去，约 23 ms。

加进去之后，主循环周期从 10 ms 变成 33 ms。数码管每 33 ms 才有机会切换下一位，某些位被点亮 23 ms、某些位只有 2 ms，亮度严重不均，肉眼看就是「闪」。你的第一反应是「数码管驱动有问题」，然后花两天时间去调定时器，其实问题根本不在数码管。

所有「主循环里的耗时大户」都会造成这种连带伤害：SD 卡写入（一次 20 ms）、Flash 页擦除（一次 30 ms 以上）、整屏刷新、大批量串口发送、等待传感器转换结束。它们的共同点是「我慢，但我不知道我还拖慢了别人」。

死穴 ④：无法给不同任务不同优先级。前后台系统只有两个优先级层次：中断层（由 NVIC 决定）和主循环层（内部一律平等）。主循环里排在前面的一段代码，就「天然」比后面的优先级高；而这段代码该不该排前面，取决于你写代码那天的直觉。

故障现场 · 过流保护晚到了 3 毫秒

你的电机驱动板上有过流检测（比较器输出接到 MCU 引脚），主循环里的顺序是：先解析上位机命令 → 再控温 → 最后检查过流。这个顺序看起来很合理，因为命令解析的代码最多。

某次上位机发来一帧 40 字节的配置命令（解析耗时约 3 ms），恰好此时电机堵转过流。等主循环走到「检查过流」这一行时，已经过去了 3 ms 以上，MOS 管在这 3 ms 里一直扛着 15 A 的堵转电流，温度骤升，最终击穿。

正确的做法不是「把过流检查挪到最前面」——那只是把风险换个位置。正确的是：过流这种「必须微秒级响应」的事件，必须走中断，且在中断里直接关断 PWM 输出，事后再让后台慢慢做记录和上报。换句话说，「优先级」这件事在前后台里表达不出来，只能靠「升格成中断」来绕过。

死穴 ⑤：栈与资源共享靠自觉。裸机只有一个栈指针（MSP），中断和主循环共用同一个栈。同时，中断和主循环可以访问同一批外设（SPI、I²C、Flash、DMA 通道），但没有任何机制规定「同一时刻谁能用」。

故障现场 · 中断里那个 256 字节的数组成为了随机重启的元凶

串口帧解析要缓存数据，你图省事，直接在中断服务函数里写了 uint8_t buf[256];。你觉得「局部变量，中断退出就没了，多安全」。确实「没了」——但它是从栈上分配的，而这 256 字节是从主循环正在用的那个栈里切出去的。

如果主循环此刻正在一个函数里，而这个函数又有一个 1 KB 的局部数组（比如从 SD 卡读一个扇区），加上中断的 256 字节，链接脚本里配的 1 KB 主栈就被击穿了。栈溢出的表现有很多种：有时是随机重启（踩到了别的变量），有时是 HardFault，有时什么都不发生——因为栈下面恰好是一块没人用的 RAM。它是嵌入式里最典型的「偶发、不可复现、换块板子就好了」的 bug。

资源共享的故障同样常见：主循环正在用 SPI 读 Flash（一次事务 200 µs），此时中断也要用 SPI 读一颗传感器，两段时序交错，读回来的全是错数据，而 SPI 外设本身不报任何错。

死穴 ⑥：测试时无法单独跑一个功能。前后台系统里的功能通过「全局变量的最终值」和「主循环里的执行顺序」互相依赖。你想测功能 C，必须先让功能 A、B 都跑过并留下正确的中间状态。这带来两个后果：① 你没法在电脑上跑单元测试（代码里全是 HAL_GPIO_ReadPin，PC 上编译都过不了）；② 由于实时性依赖主循环周期，实验室里的时序结论在现场会失效。

故障现场 · 实验室里长按 3 秒，现场要按 3.5 秒

长按判定逻辑是「按下持续 3 秒算长按」，靠比较 g_tick 实现。在实验室里，你的板子只跑按键这一件事，主循环 200 µs 一圈，长按 3.0 秒能稳定触发。

到了现场，板子还接了 SD 卡和显示屏，主循环周期变成 3.2 ms。按键扫描每 3.2 ms 才推进一次状态机，长按的时间判定因此有最多 3.2 ms 的偏差——这还好。真正的问题是：你为了「消抖更可靠」把扫描周期从 10 ms 调成了 30 ms，而判定阈值仍然是 3 秒的 tick 计数，没人注意到采样点和阈值之间的关系已经变了。

如果这段逻辑是一个「输入是 tick 差、输出是事件」的纯函数，你完全可以在电脑上跑 1000 组时间序列，验证边界情况。但在前后台结构里，它和 HAL、和全局变量、和主循环顺序缠在一起，你只能靠手按。

把六个死穴收进一张表，你会看到它们其实指向三个共同的根因：

死穴根因典型现象解决方向
① 阻塞拖垮全局串行执行 + 原地等待加一个功能，别的功能变慢主循环里禁止阻塞；用时间戳判到点
② 全局变量耦合没有接口约定改一处，崩三处分层 + 只暴露函数；集中访问
③ 实时性取决于最慢环节只有一个时间尺度加个大耗时功能，所有功能变慢给每个功能独立的周期（任务表）
④ 无法区分优先级只有中断 / 主循环两层不急的活挡住了急的活紧急事件升格为中断；或上 RTOS
⑤ 栈与资源共享靠自觉共用一个栈、外设无归属随机重启、数据错乱、偶发中断里不放大数组；共享资源归一个任务
⑥ 无法单独测试功能间靠执行顺序耦合实验室正常，现场不正常分层 + 依赖注入（见 2.7）

其中 ①③ 指向同一件事：主循环里不能有阻塞，而且每个功能要有自己的节奏。这正是时间片轮询要解决的。而 ④ 有一个更彻底的解法——让系统真的能「按优先级抢」——那是 RTOS（第 40 篇）。在此之前，先把 2.3 的结构学会，它在 90% 的项目里已经足够。

2.3 时间片轮询调度器：用一张任务表管住所有功能

时间片轮询（也有人叫「时间触发的前后台系统」「软件定时器调度」）的思路只有一句话：用一个固定节拍的时间中断做统一的时钟，把每个功能写成一个「每次只做一小步、绝不停留」的函数，主循环只负责检查「哪个函数到点了」并调用它。

它由三个部件组成，缺一不可：

① 节拍源（tick source）
     SysTick 定时器，每 1 ms 产生一次中断。
     HAL 环境下只要调用 HAL_Init()，SysTick 就已经配成 1 ms 了，
     你只需要在 SysTick 中断里加一行计数。

② 时间戳（tick counter）
     volatile uint32_t g_tick_ms;      每毫秒 +1
     它是整个系统唯一的「时间真值」。所有周期、超时、消抖都用它来算，
     而不是用 HAL_Delay 去「等」。
     ★ 用 32 位无符号数，回绕周期 2^32 ms ≈ 49.7 天，
       配合「无符号减法比较」可以安全地跨越回绕点（下面详述）。

③ 任务表（task table）
     一张数组，每一项记录一个任务的全部信息：
         函数指针      到点后调用谁
         周期          多少毫秒跑一次
         上次运行时刻  用来判断「到点没有」
         使能标志      可以运行时打开/关闭，方便调试
         名字          出问题时能打印出来（强烈建议加）
         最坏执行时间  用来算 CPU 占用率（可以是实测填回去的）

先看任务表的数据结构和调度循环长什么样。这是本章后面所有内容的核心，值得你逐行读懂：

/* ───────────── sched.h ───────────── */
#ifndef SCHED_H
#define SCHED_H

#include <stdint.h>
#include <stdbool.h>

typedef void (*task_fn_t)(void);          /* 任务函数的形状：无参、无返回 */

typedef struct {
    const char *name;        /* 任务名，调试用；编译进 Flash，不占 RAM */
    task_fn_t   fn;          /* 到点调用的函数 */
    uint16_t    period_ms;   /* 周期，0 表示「每一拍都跑」 */
    uint16_t    last_run;    /* 上次运行的 tick（调度器自己维护，不要手改） */
    uint16_t    worst_us;    /* 实测最坏执行时间，用于 CPU 占用率统计 */
    uint8_t     enabled;     /* 使能标志：0 关闭，非 0 开启 */
} task_t;

void     Sched_Init(void);                       /* 注册任务表并启动节拍 */
void     Sched_Run(void);                        /* 调度循环，main 里调用，不返回 */
uint32_t Sched_GetTick(void);                    /* 取当前 tick（毫秒） */
void     Sched_PrintUsage(void);                 /* 打印 CPU 占用率统计 */

#endif /* SCHED_H */
static volatile uint32_t g_tick_ms;       /* ① 时间戳：中断里写，主循环里读 */

/* ① 节拍中断：整个中断服务函数只做一件事，耗时约 0.1 µs
   在 HAL 工程里推荐挂在 HAL_SYSTICK_Callback() 上（见第 4 节），
   这样不会和 HAL 自己的 HAL_IncTick() 打架 */
void HAL_SYSTICK_Callback(void)
{
    g_tick_ms++;
}

/* ② 到期判断：只用「无符号减法」，绝不用 now >= last + period
   理由：g_tick_ms 会在 49.7 天后回绕。
        回绕瞬间 now 变成 0，而 last 还是 4294967000，
        now - last 按无符号运算仍然等于真实的时间差（差值远小于 2^31），
        所以比较结果依旧正确。写成加法则必然算错一次。 */
static inline bool task_is_due(const task_t *t, uint32_t now)
{
    if (t->period_ms == 0u) {
        return true;                                  /* 0 = 每拍都跑 */
    }
    return (uint32_t)(now - t->last_run) >= t->period_ms;
}

/* ③ 调度循环：它自己不懂任何业务，加功能只需要改任务表 */
void Sched_Run(void)
{
    uint32_t now;

    for (;;) {
        now = g_tick_ms;                 /* 整轮用同一个时间基准，保证判断一致 */

        for (uint8_t i = 0; i < g_task_count; i++) {
            task_t *t = &g_tasks[i];

            if (!t->enabled || t->fn == NULL) {
                continue;
            }
            if (!task_is_due(t, now)) {
                continue;
            }

            t->last_run = (uint16_t)now;      /* 先记录，再执行 */
            t->fn();                          /* 调用任务；任务内部绝不允许阻塞 */
        }
        /* 到这里的意义：系统空闲（idle）。
           可以在这里喂看门狗、进入 __WFI() 省电、或者统计空闲占用率。 */
        Sched_IdleHook();
    }
}

这段代码里有四个细节，每一个都值得单独讲清楚：

  • 为什么 now 要在整轮开始前取一次快照？因为如果每个任务单独去读 g_tick_ms，同一轮里前后任务看到的时间可能不同（中断随时在推进它）。取一次快照，同一轮里所有任务的到期判断基于同一个时刻，行为可复现，也更容易在纸面上算清楚。
  • last_run = now 还是 last_run += period？前者（以本轮快照为基准）简单、不会因为「追不上」而连续触发，但会引入最多「一个循环周期」的抖动：如果调度循环本身要跑 1.5 ms，周期 10 ms 的任务实际间隔会变成 10.5 ms 或 11.5 ms。后者（累加）精度更高、长期不漂移，但如果某次因为任务超时错过了好几拍，它会在恢复后「连补几拍」。课程设计与一般产品用前者就够了；如果你要做「每 10 ms 精确采一次样，长期不能漂」的数据记录仪，用累加版。
  • 为什么任务函数必须是 void f(void) 这种形状？因为调度器的全部本事就是「按时间调用一个函数」。任务之间要传数据，不能用参数——只能通过队列、事件标志或带访问函数的全局状态（2.5 节讲）。这个限制是好事：它逼着你把「任务之间的通信」显式设计出来，而不是随手抓一个全局变量。
  • 为什么要有 Sched_IdleHook()？它代表「所有任务都没到点时，CPU 在干什么」。裸机上这段时间会空转浪费电；常见做法是喂狗 + __WFI() 让 CPU 睡到下一次中断（第 38 篇讲低功耗时会用到）。

时间片轮询看起来已经很好了：周期显式、加功能只改一行、每个任务的最坏耗时可以逐个测量。但它有四个必须记住的局限，每一条都能让一个「看起来正常的程序」在某天突然崩掉。

局限 ①：每个任务必须自己保证在周期内返回，调度器不会管你。这是最重要的一条。调度器做的事只有「调用」，它没有能力打断一个正在执行的任务——因为任务是普通的函数调用，跑在同一个栈上，调度器自己也被这个调用挡住了。

后果是：如果某个任务超时了，后面所有任务全部顺延，而且不会有任何报错。程序不会崩，只会「有点不对劲」。你看到的可能是「数码管偶尔闪一下」「串口偶尔丢一帧」「按键偶尔要按两次」——这类现象最难查，因为它们在实验室压力小的时候不复现。所以任务表里的「最坏执行时间」不是写着好看的，它是你必须实测并持续监控的数字（第 4 节给了自动统计的实现）。

局限 ②：无法抢占。假设系统里有一个「收到上位机急停命令后 1 ms 内切断输出」的需求，你把急停处理写成了一个周期 1 ms 的任务。但如果此刻一个周期 100 ms 的「Flash 记录」任务已经在跑了（耗时 20 ms），急停任务只能等它跑完——20 ms 之后才轮到急停，需求直接违反。

这类「不管别人在干什么，我必须立刻执行」的需求，在时间片轮询里只有一个解法：把它做成真正的中断，在中断里完成最关键的动作（比如直接清 PWM 使能位），事后的记录、上报再交给任务。「中断做最紧急的动作，任务做剩下的全部」是裸机架构里最基本的分工。

局限 ③：优先级只能靠安排调用顺序。任务表里靠前的任务在同一拍内先跑。这能表达一点点优先级（比如把按键扫描排在串口上报前面），但它有两个明显的天花板：① 它只在「同一拍内撞车」时有效，跨周期的优先级表达不了；② 它和「周期」这个维度纠缠在一起——你不能既让一个任务「周期很长」又让它「优先级很高」。

所以实践中的排序原则是：把「周期最短、响应要求最硬」的任务放在最前面，让它们在每一拍里最先拿到 CPU；把「可以慢、可以等」的任务（上报、记录、显示刷新的大块）放到最后。

局限 ④：长任务会把节拍挤爆。如果一个任务的最坏执行时间是 8 ms，而它的周期是 2 ms，会发生什么？在它执行的 8 ms 里，SysTick 中断照常触发 8 次（g_tick_ms 正常前进 8），但调度循环一次都出不来；这 8 拍里本该运行的数码管刷新、按键扫描全部被跳过。等这个任务返回，now - last_run 已经远大于周期，那些任务会在下一轮「补跑」一次——数码管的 4 位里只有最后一位亮了 8 ms，其他三位等于没亮。

这里有一条经验红线：单个任务的最坏执行时间，不应超过它自己周期的 30%~50%；而所有任务耗时之和不应超过最短周期的 70%（第 3 节例题 1 会把这个 70% 讲透）。超了不代表立刻出错，代表「没有余量」——一旦某个任务因为数据特殊而变慢一点（比如串口收到一帧超长报文、ADC 遇到一个坏值进入重试），系统就开始漏拍。

还有一个隐藏问题：天然批次对齐

因为所有任务的周期都是 1 ms 节拍的整数倍，周期成倍数关系的任务必然会在某些拍上撞车。周期 10 ms 和周期 5 ms 的任务会在第 10、20、30…拍同时到点；周期 2 ms 的任务则「几乎每一拍都在」。

这就是上面那张时间轴里要标「相位偏移」的原因：让 Adc 从第 3 拍开始、让 Uart 从第 7 拍开始，把撞车摊开。实现方式很简单——初始化时把任务的 last_run 手动设成一个偏移值，或者干脆把周期设成 9 ms、11 ms 这种「质数化」的数字。

注意相位只能解决「平均值」问题，如果某一拍的总耗时本身就超过了 1 ms，怎么错开都没用，必须拆分任务或降低周期。第 3 节例题 1 就是算这笔账的。

最后强调一个容易误解的点：时间片轮询不是 RTOS。它没有「任务」这个概念——只有「函数」；它不会保存现场，切换「任务」只是普通的函数调用和返回；所有任务共用一个栈，所以一个任务的局部变量会挤占另一个任务的栈空间。它的强大来自「把时间这个维度显式写进程序结构」，而不是来自「并发」。理解了这一点，你就理解了 2.8 那张对照表的全部含义。

2.4 任务怎么切分：四条原则，以及一次完整的切分演练

切分任务是设计工作，不是编码工作。它决定的是「系统里有几个节奏、谁挡住谁、数据从哪流到哪」。切错了，后面写的每一行代码都在还债；切对了，代码会自己长得整齐。下面四条原则，每一条都可以用一个问句来判断。

原则一：按时间尺度分。判断问句是「这件事多久必须做一次？」。两件事的周期相差 10 倍以上，就应该分到两个任务里。

为什么 10 倍

如果一个任务里既有「每 1 ms 必须做」的代码，又有「每 100 ms 做一次就行」的代码，那么 100 ms 那份代码会被白白执行 100 次，而 1 ms 那份代码的节奏被绑死在整段代码的总耗时上。反过来，如果把 1 ms 的控制环放到 100 ms 的任务里，控制环就变成了 100 ms 一次——这已经不是「变慢」了，而是功能性质变了（1 kHz 的 PWM 环路变成 10 Hz，迟滞控制会明显振荡）。

反过来也成立：时间尺度相同的功能合在一个任务里更划算——少一次调度开销，少一次跨任务传数据（传数据是要拷贝的）。所以「按时间尺度分」不是「凡是不同的都分开」，而是「同一量级的合，跨量级的分」。

原则二：按数据来源分。判断问句是「这份数据从哪来？谁负责把它取回来？」。通常一个输入源对应一个任务——这几乎是天然的分法，因为输入源本身就已经被中断分好了：按键是 GPIO 扫描、温度是 ADC 转换完成中断、命令是串口接收中断、姿态是 I²C 传感器的数据就绪引脚。

这样分的好处是「采样点」和「处理逻辑」绑定在一起：谁取的数据谁负责解释。反例是把 ADC 采样和串口解析放进同一个任务——串口来了一帧 32 字节的报文，解析要 300 µs，这 300 µs 里 ADC 该采样的那一刻被错过了，温度曲线上出现一个尖刺。你在实验室里用稳定温度测不出来，现场升温过程中就会发现控温偶尔「慢半拍」。

注意一个例外：同一个物理总线上的多个设备，最好归一个任务。SPI 上挂了 Flash 和一颗传感器，如果两个任务各自去操作 SPI，就要处理「一次事务不能被打断」的互斥问题。裸机里没有互斥量，只能靠关中断硬扛（见 2.5）。把它们收归一个任务是最省事的解法。

原则三：按状态独立性分。判断问句是「这两件事是否共享同一份必须原子更新的状态？」。共享的必须放进同一个任务；不共享的应该分开。

把一个状态机切到两个任务里，会发生什么

按键处理通常包含三层：消抖（连续 3 次读到相同电平才算稳定）、事件判定（短按 / 长按 / 双击）、业务动作（切换模式、进入设置）。有人觉得「这是三件事」，于是切成三个任务，用三个全局变量传递中间结果：g_key_stable、g_key_event……

然后长按就时灵时不灵了。原因是：消抖任务在 g_key_event 里写下「短按」，长按判定任务读到并清掉；真正的长按事件在下一个 10 ms 才被写入，而按键判定任务在这一轮已经跑过了——事件在「被写入」和「被读取」之间没有任何排队机制，谁先谁后全靠运气。

正确做法是：消抖 + 事件判定 + 业务动作全部放在一个 Key_Scan 任务里，因为它们共享同一个「按键状态机」的静态变量。任务对外只暴露一个函数（比如 Key_GetEvent()），让别的任务来取。这条原则可以总结成一句话：状态机在哪里，判定逻辑就在哪里。

这条原则还有一个推论：一个任务的一次执行，应该是一个「做完一小步」的原子过程。任务可以被切成很多次执行（每次推进状态机一步），但不能在中途依赖「另一个任务帮我做完剩下的一半」——那就等于把一个原子过程撕成了两半。

原则四：按响应要求分。判断问句是「这件事最晚多久必须做完？」。这条原则决定了「哪些事根本不该是任务」：

  • 10 µs 级（过流关断、急停、编码器计数）：必须是中断，而且在中断里直接完成动作。放进任务表就一定不满足（2.3 局限②）。
  • 1 ms 级（闭环控制、PWM 更新、电流环）：最短周期的任务，且必须排在最前面。
  • 10~50 ms 级（温度采样、按键扫描、协议解析）：中等周期任务。
  • 100 ms 以上（上报、SD 记录、整屏刷新、心跳灯）：长周期任务，排在最后。它们允许延迟，也允许偶尔被跳过一拍。

还有一条反向约束：别切太细。每多一个任务，你就多付出四份成本：① 调度开销（判断 + 调用，约 1~2 µs，如果你的任务本身只有 5 µs，开销就占了 30%）；② 一张任务表项（占 Flash，还要人去维护）；③ 跨任务传数据要经过队列（数据要拷贝一次，还要处理满/空）；④ 调试变难（「谁改了这个变量」这个问题从「看函数」变成「看时序」）。

经验值：小项目 4~10 个任务比较合适。超过 15 个就该反问自己「是不是把一件原子的事切开了」。另一个可量化的信号是单个任务的最坏执行时间：如果超过 20 ms，说明它太粗了（它在执行期间把所有其他任务都挡住了）；如果小于 5 µs 却还要单独占一个任务，说明它太细了（开销比本体还大）。

现在算 CPU 占用率。这里要算两个口径，它们的含义完全不同，很多讲时间片轮询的资料只讲其中一个，导致你算完还是不知道自己的系统行不行。

【口径一 · 长期平均占用】把每个任务的执行时间按自己的周期摊开

  U = Σ (Ci / Ti)
    = 45/1000 + 60/2000 + 180/5000 + 80/10000
    + 120/10000 + 200/100000 + 350/100000 + 10/500000
    = 0.045 + 0.030 + 0.036 + 0.008 + 0.012 + 0.002 + 0.0035 + 0.00002
    = 0.1365  →  13.7%

  这个数字回答的是「CPU 平均有多忙」。13.7% 看起来非常空闲，
  但它会骗人：它假设任务被均匀地摊到了时间轴上，而实际上它们会撞车。

【口径二 · 最坏撞车占用】假设所有任务的最坏执行时间都挤在同一拍

  U_worst = Σ Ci / T_min = 1045 µs / 1000 µs = 104.5%

  这个数字大于 100%，说明：如果所有任务恰好落在同一拍，
  这一拍需要 1045 µs 才能跑完，而节拍只有 1000 µs
  → 这一拍必然被挤爆，会有任务被推迟到下一拍。
  （这就是 2.3 时间轴里 t = 0 / 500 / 1000 那几拍的隐患。）

【错开相位之后 · 真正要看的数字】
  把 Adc 偏移 +3 ms、Uart 偏移 +7 ms 之后，逐拍算一遍：
  最坏的一拍 = 45 + 60 + 180 + 80 + 200 + 10 = 575 µs（t = 500、1000）
  575 / 1000 = 57.5%  →  小于 70%，安全

【70% 这条线是怎么来的】
  留出的 30% 余量要装下四样东西：
  ① 节拍中断本身：SysTick + HAL_IncTick 约 1.5 µs / 1 ms ≈ 0.2%
  ② 其他中断：串口每 10 ms 收 32 字节 = 32 次中断 × 1.5 µs
     = 48 µs / 10 ms ≈ 0.5%；ADC 中断、EXTI 也各有零点几个百分点
  ③ 任务耗时的波动：数据特殊时任务会变慢（超长报文、坏值重试、
     整屏刷新），实测的「最坏值」永远只是「见过的最坏值」
  ④ 未来要加的功能：这是最现实的一条——没有余量，
     下一个需求就得靠删功能来腾地方

  经验结论：57.5% 这个占用率，在 72 MHz 的 STM32F103 上余量充足；
  如果算出来在 70%~90% 之间，说明系统能跑但没有退路，
  应该考虑拆任务或降低某些功能的频率；超过 90% 就必须重新设计。

注意口径二那个 104.5% 的用法：它不是在说「这个系统不行」，而是在说「这个系统不能容忍最坏撞车」。它是一个设计约束，直接告诉你必须做相位错开（或者把某些任务的周期改成互质的数字）。如果你算完口径一只得到 13.7%，就认为万事大吉，那第 500 ms 那一拍一定会给你上一课。

2.5 事件驱动与消息传递：从「全局变量 + 标志位」走到队列

前后台系统里最原始也最常见的通信方式是「全局变量 + 标志位」：中断把数据写进全局变量，再置一个标志；主循环看到标志就取数据、清标志、处理。

volatile uint8_t  g_adc_flag;      /* 中断置 1，主循环清 0 */
volatile uint16_t g_adc_value;     /* 中断写，主循环读 */

void ADC_IRQHandler(void)          /* 中断上下文 */
{
    g_adc_value = ADC1->DR;
    g_adc_flag  = 1;
}

void App_AdcTask(void)             /* 主循环上下文，10 ms 调用一次 */
{
    if (g_adc_flag) {
        g_adc_flag = 0;
        处理(g_adc_value);
    }
}

这段代码能跑，教科书上也常常这么写。但它有三个问题，随着功能变多会依次暴露出来。

问题一：标志位只能表达「有事」，不能表达「有几件事」。ADC 第一次转换完成，置 1；主循环还没来得及处理，第二次转换完成了，还是置 1。两次事件被合并成了一次，第二份数据永远丢失。

这里有一个重要的区分：如果事件表示的是「状态」，丢一次没关系（比如「按键被按下过」——主循环处理的时候读到的是最近的电平，最终结果一样）；如果事件表示的是「数据」，丢一次就是真的丢数据（串口收到的一帧、ADC 的一个采样点、编码器的一个脉冲）。前者可以用标志位，后者必须用队列。很多人在这里翻车，是因为他们用同一套「标志位」模式处理了两种性质完全不同的事情。

问题二：标志和数据的更新不是原子的，会出现「丢更新」和「重复处理」。上面的写法里，g_adc_value 和 g_adc_flag 是两个独立的对象，它们之间的一致性没有任何保证。看这条时间线：

【丢更新】主循环先清标志、再读数据

  主循环 reads g_adc_flag == 1
  ─────────────────────────────▶ 中断：g_adc_value = 新值;  g_adc_flag = 1;
  主循环 g_adc_flag = 0              ← 刚刚被中断置上的 1，被这一句清掉了
  主循环 处理(g_adc_value)           ← 处理的是新值，看起来没问题
  但！下一拍主循环看标志是 0，不会再来处理
  → 如果这一拍进中断的是「一份坏数据」，或者主循环读到的是「上一次的旧值」，
    那这次的新值就永远不会被处理。这就是丢更新。

【重复处理】主循环先读数据、再清标志（推荐顺序，但也有边界情况）

  主循环 处理(g_adc_value)           ← 用的是快照值，正确
  ─────────────────────────────▶ 中断：写入新值 + 置标志
  主循环 g_adc_flag = 0              ← 把「新值已就绪」这个事实清掉了
  → 新值这一次没被处理，下一次也不会（因为标志已经 0 了）
    如果数据是「一帧命令」，这条命令就被静默丢弃了

【根本原因】
  中断随时可能插在「读标志 / 读数据 / 清标志」这三步之间的任何位置。
  只要通信机制是「两个独立变量」，就必须在临界区里成套地读或写。

这个问题的正确解法有两个层次。第一层（治标）：把「读数据 + 清标志」放进一个关中断的临界区，并且约定一个明确的顺序——关中断 → 把数据拷到局部变量 → 清标志 → 开中断 → 用局部变量做处理。这样「读走的数据」和「清掉的标志」一定对应同一份数据，而处理过程在开中断之后，不会拖长临界区。第二层（治本）：改用队列——队列天然就是「数据 + 顺序」的容器，标志位想表达而表达不了的东西（有几件事、先后顺序），队列都替你管了。

问题三：无法扩展，耦合会指数增长。每加一个功能，你就要加一个全局变量、一个标志位，还要去中断函数里加一行「把数据也存一份给新功能用」。慢慢地，中断服务函数变成了「数据分发中心」——它必须知道所有关心这个数据的人是谁。等你发现「中断里居然写了 8 个全局变量」的时候，这段代码已经没人敢动了。

下面的三个机制，分别是这三个问题的答案：环形缓冲队列解决「有几件事 + 顺序」，事件标志组解决「多件事的状态如何用一个变量表达」，发布/订阅解决「生产者不该认识消费者」。

① 环形缓冲队列：生产者是中断，消费者是主循环。队列的思想很简单：一块固定大小的缓冲区，两个指针，一个指向「下一个要写的位置」（head），一个指向「下一个要读的位置」（tail）。写指针追上读指针就是满，两者相等就是空。

        head（下一个要写的位置）
        ↓
  ┌────┬────┬────┬────┬────┬────┬────┬────┐
  │ D0 │ D1 │ D2 │ D3 │    │    │    │    │
  └────┴────┴────┴────┴────┴────┴────┴────┘
    ↑
    tail（下一个要读的位置）

【空】tail == head
  ┌────┬────┬────┬────┬────┬────┬────┬────┐
  │    │    │    │    │    │    │    │    │
  └────┴────┴────┴────┴────┴────┴────┴────┘
    ↑
   head/tail 指向同一格 → 没有数据可读

【有 5 个字节待处理】写入时 head 前进，读取时 tail 前进，到末尾回卷到 0
  ┌────┬────┬────┬────┬────┬────┬────┬────┐
  │ D0 │ D1 │ D2 │ D3 │ D4 │    │    │    │
  └────┴────┴────┴────┴────┴────┴────┴────┘
    ↑                        ↑
   tail                     head
   待处理字节数 = (head - tail + 容量) % 容量 = 5

【满】head 的下一个位置 == tail  →  剩下最后一个空位不用
  ┌────┬────┬────┬────┬────┬────┬────┬────┐
  │ D0 │ D1 │ D2 │ D3 │ D4 │ D5 │ D6 │    │
  └────┴────┴────┴────┴────┴────┴────┴────┘
         ↑                             ↑
        head                          tail
   为什么牺牲一格？因为「满」和「空」都会让 head == tail，
   无法区分。牺牲一格是最省事的办法（另一个办法是加一个 count 变量，
   但那个变量两边都要读写，就需要原子操作了）。

三条铁律（背下来）：
  1. 容量取 2 的幂（8/16/32/64/128），这样「取模」可以用位与代替：
     next = (head + 1) & (SIZE - 1);   ← 比 % SIZE 快十倍以上
  2. 单生产者、单消费者：head 只被中断写、只被主循环读；
     tail 只被主循环写、只被中断读。每个变量只有一个写者
     → 不需要关中断，不需要原子指令，天然无锁
  3. 更新指针必须在写完数据之后（写数据 → 再动指针），
     读取方先读数据 → 再动指针。顺序反了会读到未初始化的一格

这三条铁律里，第 2 条是环形缓冲能在裸机上无锁工作的全部秘密。它让「关中断」这种粗暴手段变得不必要：只要每个共享变量只有一个写者，就不会有「两个写者互相覆盖」的竞争。而第 3 条（先写数据、后动指针）保证了「只要指针动到了这一格，这一格里的数据一定是完整的」。

队列的容量要按最坏情况算，不能按平均值算：消费者最慢的响应时间 × 生产者的最大速率，再乘一个安全系数。第 3 节例题 2 会算一遍串口收数据的例子——那个例子会告诉你「按平均值算出来的容量，在现场一定会溢出」。

② 事件标志组：一个 32 位变量表示 32 件事。当事件表示的是「状态」而不是「数据」时（有没有到点、有没有出错、某个外设是否就绪），用队列就太重了。这时用一个 uint32_t，每一位代表一件事，就叫事件标志组（event flags）。

/* ── 事件位定义：用宏，不要用魔法数字 ── */
#define EVT_KEY_PRESSED   (1uL << 0)    /* 有按键事件待处理 */
#define EVT_ADC_READY     (1uL << 1)    /* 温度采样完成 */
#define EVT_CMD_RECEIVED  (1uL << 2)    /* 收到完整一帧命令 */
#define EVT_OVERCURRENT   (1uL << 3)    /* 过流已发生（中断置位） */
#define EVT_UART_TX_DONE  (1uL << 4)    /* 一帧发送完成 */
#define EVT_1S_ELAPSED    (1uL << 5)    /* 满 1 秒 */

static volatile uint32_t g_events;

/* ── 置位：可以在中断里直接调用 ──
   g_events |= mask 在 Cortex-M 上编译成 LDR / ORR / STR 三条指令，
   会被中断打断。但因为「中断只置位、不读改写其他位」这个约定，
   实际风险只有一个：主循环正在清位时中断插入（下面讲）。
   而中断自己置位是无竞争的——只有它一个写者（在它执行期间，
   同级中断被屏蔽，主循环不会跑）。 */
static inline void Evt_Set(uint32_t mask)
{
    g_events |= mask;
}

/* ── 等待：返回「关心的位里哪些被置上了」，不阻塞 ── */
static inline uint32_t Evt_Peek(uint32_t mask)
{
    return g_events & mask;
}

/* ── 清除：这里必须进临界区，否则会丢掉「刚置上的位」 ──
   危险写法：g_events &= ~mask;
       编译成 LDR / BIC / STR 三条指令。如果中断恰好插在
       LDR 和 STR 之间置上了 mask 中的某一位（甚至别的位），
       STR 会把这个新位一起写回成 0 →  中断置的位被静默清除。
       这个 bug 一年可能只出现一次，出现时表现为「偶尔丢一次事件」。
   安全写法：关中断 2~3 条指令，代价约 0.1 µs。 */
static inline void Evt_Clear(uint32_t mask)
{
    uint32_t primask = __get_PRIMASK();
    __disable_irq();
    g_events &= ~mask;
    __set_PRIMASK(primask);          /* 恢复之前的中断状态，而不是无脑开中断 */
}

/* ── 推荐的使用姿势：快照 → 清位 → 处理（而不是 处理 → 清位）──
   为什么？因为「快照 + 清位」在临界区里是成套完成的，
   在它之后到来的事件一定会重新把位置上，不会被漏掉。
   而「先处理再清位」时，处理过程中到来的事件会被一起清掉。 */
void App_EventTask(void)
{
    uint32_t fired;

    __disable_irq();
    fired = g_events;                /* ① 快照 */
    g_events = 0;                    /* ② 把我们关心的位全部清掉（整体清，最省事） */
    __enable_irq();

    if (fired & EVT_ADC_READY)    { /* 处理温度采样 */ }
    if (fired & EVT_CMD_RECEIVED) { /* 处理一整帧命令 */ }
    if (fired & EVT_OVERCURRENT)  { /* 记录 + 上报 + 点故障灯 */ }
}

事件标志组最需要讲清楚的是「谁清标志」这个约定。它有三种常见写法，各有代价：

  • 中断清、消费者不管：只适合「状态型」事件（比如「收到一个字节」），消费者必须每次都去读外设寄存器拿数据，否则数据就永远丢了。
  • 消费者清（推荐）：中断只置位（一个写者、无竞争），消费者在临界区里快照 + 清位。这样「置位」这件事永远安全，而「清位」这件事被保护起来。
  • 双方都清：绝对不要。这是上一条 g_events &= ~mask 在中断里也会出现的情形，两个写者做读改写，丢位的概率会高到你能在一天内复现。

还有一个细节：清位时恢复 PRIMASK 而不是无脑 __enable_irq()。因为你不知道调用 Evt_Clear() 的那一刻自己是不是已经在某个临界区里——如果外层本来就关着中断，内层无脑开中断会把外层的保护破掉。这是裸机代码里最典型的「嵌套临界区」 Bug，也是后面 RTOS 用 taskENTER_CRITICAL() / taskEXIT_CRITICAL() 成对出现的理由。

③ 发布/订阅：让生产者不认识消费者。当「一个事件有多个关心者」时（比如「温度更新了」——显示要刷、控温要用、上报要发、记录要存），上面的标志组还是需要每个消费者自己去轮询 g_events。发布/订阅把这个关系反过来：消费者在启动时「告诉系统我关心哪些事件」，发布者只管发，完全不认识消费者。

typedef void (*sub_handler_t)(uint32_t events, void *arg);

#define SUB_MAX  8

static struct {
    uint32_t       mask;      /* 关心哪些事件位 */
    sub_handler_t  handler;   /* 被调用谁 */
    void          *arg;       /* 透传参数（可以是某个模块的上下文指针） */
} g_subs[SUB_MAX];

static uint8_t g_sub_count;

/* 订阅：模块初始化时调用一次 */
bool Evt_Subscribe(uint32_t mask, sub_handler_t handler, void *arg)
{
    if (g_sub_count >= SUB_MAX) { return false; }     /* 表满要有返回值，不能静默失败 */
    g_subs[g_sub_count].mask    = mask;
    g_subs[g_sub_count].handler = handler;
    g_subs[g_sub_count].arg     = arg;
    g_sub_count++;
    return true;
}

/* 发布：可以在任务里调用（不要在中断里调用，遍历 + 回调太耗时） */
void Evt_Publish(uint32_t events)
{
    for (uint8_t i = 0; i < g_sub_count; i++) {
        if (events & g_subs[i].mask) {
            g_subs[i].handler(events & g_subs[i].mask, g_subs[i].arg);
        }
    }
}

/* ── 用法：模块自己注册，别人都不用改 ──
   Seg_Init() 里:   Evt_Subscribe(EVT_ADC_READY, Seg_OnTempChanged, NULL);
   Uart_Init() 里:  Evt_Subscribe(EVT_ADC_READY | EVT_OVERCURRENT, Uart_OnEvent, NULL);
   以后再加一个「SD 卡记录」模块，只需要它自己订阅，
   温度采样任务、中断服务函数一个字都不用改。 */

这个实现只有二十几行，但它带来的是结构性的好处：新增功能不再需要修改已有代码（这就是「开闭原则」在单片机上的样子）。代价是每次发布都要遍历订阅表并调用回调——回调是普通函数调用，会占用发布者的执行时间。所以实践中要守两条规矩：① 不要在中断里发布（中断里只置事件位，让一个任务去发布）；② 回调里只做「标记 + 置位」这类极短的动作，重活留给这个回调所属的任务。

三种机制怎么选：一张对照表
机制解决的问题适用的信息类型典型场景
全局变量 + 标志位最省事的「有事通知我」单个状态，丢了不影响最终结果「有按键按下过」「到点了」
环形缓冲队列不丢数据、保持先后顺序数据流、事件序列串口收到的字节、待发送的报文
事件标志组用最少的空间表达「多件事的状态」位状态，可以合并「采样好了 + 一帧收全了 + 过流了」
发布/订阅生产者与消费者互不认识广播型通知「温度更新了」通知显示 / 控温 / 上报

注意最后一行和前两行常常配合使用：中断 → 环形缓冲（数据）+ 事件位（通知）→ 任务取出数据 → 发布/订阅广播给关心者。这就是第 4 节那套完整实现的数据流。

2.6 状态机作为任务的实现方式：把「等待」改写成「检查」

时间片轮询的四个局限里，第①条最要命：每个任务必须自己保证在周期内返回。那么问题来了——业务逻辑里天然就有「等待」：等用户按一下、等 200 ms 闪一下、等 5 秒超时、等串口回一个应答。这些「等待」怎么写才不违反这条铁律？

答案是：把「在这里等」改写成「下次再来时检查」。这就是非阻塞状态机。它不是什么高级技巧，而是把一个阻塞的时间轴「折叠」进一个变量里。下面用一个具体需求把两种写法放在一起看。

需求

按下按键后，LED 闪烁 3 次（亮 200 ms、灭 200 ms）；闪完之后如果 5 秒内没有再次按下，就关灯退出；期间任何时候再按一次，就重新从第 1 次开始闪。

注意这个需求的「形状」：它有一个明确的开始条件、一个重复动作、一个超时退出、一个可以打断它的外部事件。但凡业务逻辑里有「等」「超时」「重复 N 次」这三个词里的任何一个，就该用状态机写。

先看反面写法——它几乎是你第一次写这类功能时会写出来的东西：

void App_BlinkTask_Blocking(void)       /* 由调度器每 2 ms 调用一次 */
{
    if (Key_WaitPress()) {              /* 内部是 while(!key); ——死等，可能永不返回 */
        for (uint8_t i = 0; i < 3; i++) {
            LED_On();
            HAL_Delay(200);             /* 这 200 ms 里，整个系统只有它在「跑」 */
            LED_Off();
            HAL_Delay(200);
        }

        uint32_t t0 = HAL_GetTick();
        while ((HAL_GetTick() - t0) < 5000u) {   /* 又一个死等循环 */
            if (Key_WaitPress()) { break; }
        }
    }
    LED_Off();
}

/* 这个函数的最坏执行时间是多少？
   死等按键（可能是 0，也可能是永远）+ 3 × (200 + 200) + 最多 5000 ms
   = 最坏 6200 ms 以上，而且这个「最坏」还是不确定的。
   → 调度器在这一刻彻底失效：其他 7 个任务全部停摆 6 秒以上。
   → 数码管停在某一位上不动（看起来像死机）、串口收到的东西全丢、
     ADC 采样完全停止、心跳灯不闪。用户报告「按一下键就死机」。 */

再看正确写法。核心思想只有一句：把「我要等 200 ms」变成「我记住上次动手的时刻，下次进来时算一下够不够 200 ms」。

/* ── 状态定义：把「时间轴上的位置」变成「一个变量」 ── */
typedef enum {
    BLINK_IDLE = 0,        /* 空闲，等第一次按键 */
    BLINK_ON,              /* 灯亮着，等 200 ms 到点 */
    BLINK_OFF,             /* 灯灭着，等 200 ms 到点 */
    BLINK_WAIT_AGAIN       /* 闪完了，等 5 秒超时或再次按键 */
} blink_state_t;

/* ── 状态变量与时间戳：必须是 static ──
   任务的「记忆」只能放在 static 变量里（或者模块级变量），
   因为任务函数每次执行完就返回了，栈上的局部变量下一拍就没了。 */
static blink_state_t s_state  = BLINK_IDLE;
static uint32_t      s_t_last = 0;      /* 本次状态开始的时刻（tick） */
static uint8_t       s_count  = 0;      /* 已经闪了几次 */

#define BLINK_HALF_MS    200u          /* 亮/灭各持续多久 */
#define BLINK_TIMES      3u            /* 一共闪几次 */
#define AGAIN_TIMEOUT_MS 5000u         /* 闪完之后等多久退出 */

void App_BlinkTask(void)               /* 由调度器每 2 ms 调用一次 */
{
    switch (s_state) {

    case BLINK_IDLE:                                   /* 等第一次按键 */
        if (Key_GetEvent() == KEY_EVT_SHORT_PRESS) {
            s_count  = 0;
            s_t_last = Sched_GetTick();                /* ★ 记住「现在」，而不是等 */
            LED_On();
            s_state  = BLINK_ON;
        }
        break;

    case BLINK_ON:                                     /* 亮够了就灭 */
        if ((uint32_t)(Sched_GetTick() - s_t_last) >= BLINK_HALF_MS) {
            s_t_last = Sched_GetTick();
            LED_Off();
            s_state  = BLINK_OFF;
        }
        break;

    case BLINK_OFF:                                    /* 灭够了就亮，或者收尾 */
        if ((uint32_t)(Sched_GetTick() - s_t_last) >= BLINK_HALF_MS) {
            s_t_last = Sched_GetTick();
            s_count++;
            if (s_count >= BLINK_TIMES) {
                s_state  = BLINK_WAIT_AGAIN;           /* 闪完了，进入超时等待 */
            } else {
                LED_On();
                s_state  = BLINK_ON;
            }
        }
        break;

    case BLINK_WAIT_AGAIN:                             /* 等 5 秒，或者被再次按下打断 */
        if (Key_GetEvent() == KEY_EVT_SHORT_PRESS) {
            s_count  = 0;
            s_t_last = Sched_GetTick();
            LED_On();
            s_state  = BLINK_ON;                       /* 重新开始闪 */
        } else if ((uint32_t)(Sched_GetTick() - s_t_last) >= AGAIN_TIMEOUT_MS) {
            LED_Off();
            s_state  = BLINK_IDLE;                     /* 超时退出 */
        }
        break;

    default:                                           /* ★ 兜底分支：非法状态必须能自愈 */
        LED_Off();
        s_state = BLINK_IDLE;
        break;
    }
}

两个版本做的是同一件事，但它们的时间行为完全不同。

【阻塞式】调用一次就霸占 CPU 几秒钟
 主循环 │████████████████████████████████████████████████│
        │ 一次 App_BlinkTask_Blocking() 的调用            │
        └────────────────────────────────────────────────┘
        0 ms                                          6200 ms
 · 其他 7 个任务：6.2 秒内一次都没被调用
 · 数码管：停在某一位不动（肉眼是「死机」）
 · 串口：收到的字节全部丢失（没人取队列）
 · 按键：这 6.2 秒里的按键全部无效
 · 最坏执行时间：不确定（可能 forever）

【非阻塞状态机】每次调用只占 2 µs，剩下的时间全是别人的
 主循环 │▏  ▏  ▏  ▏  ▏  ▏  ▏  ▏  ▏  ▏  ▏  ▏  ▏  ▏  ▏  ▏│
        └┬─┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┘
         每 2 ms 进来一次，每次 2 µs（占 0.1% 的 CPU）
 · 其他 7 个任务：节奏完全不受影响
 · 功能表现：LED 依然是亮 200 ms、灭 200 ms（靠时间戳保证）
 · 最坏执行时间：2 µs，写进任务表就能算 CPU 占用率
 · 「等待」这件事没有消失，只是被折叠进了 s_state 和 s_t_last

写非阻塞状态机有四条规则，违反任何一条都会让它退化成阻塞版：

  • 任务里不允许出现 HAL_Delay()、sleep()、while(等某个条件)、for 里等外设。任何「原地等待」都是禁止的。判断标准很简单：函数的最坏执行时间能不能在纸上写出来？写不出来就说明有阻塞。
  • 每次调用只推进一步。处理完「当前状态下该做的一件事」就 return（switch 的 break 已经做到了）。不要在一拍里连续穿过三个状态——那会让这一拍的耗时随状态流转而波动。
  • 所有需要跨调用保留的东西一律用 static，所有时间判断一律用时间戳差。用 Sched_GetTick() 取当前时刻、用 (uint32_t)(now - last) 比较——和调度器里用的是同一个技巧，回绕安全（2.3）。
  • 必须有 default 分支，必须能从非法状态恢复。状态变量被异常改写（栈溢出、越界写、上电时的随机值）是真实会发生的，default 里的「关灯 + 回 IDLE」就是最后的保险丝。
状态机本身的知识在第 18 篇

本节只讲「怎么把状态机塞进一个任务里」。至于状态怎么编码、状态图怎么画、怎么化简、非法状态怎么处理、一段式 / 两段式 / 三段式写法的取舍，都在第 18 篇《有限状态机：从状态图到单片机程序》里，那里是状态机的正课，这一节是它在架构层面的用法。

两者是正交的：状态机决定「一个功能内部怎么走」，任务切分决定「系统里有几个功能、各自什么节奏」。一个任务里可以放一个状态机，也可以放两个互不干扰的小状态机（比如按键消抖 + 通信超时）。但如果一个任务里的 switch 超过 8~10 个状态，通常是信号——它其实是两个独立的业务流程，被硬塞进了一个任务，该拆了。

2.7 分层与模块化：让代码能长大、能替换、能测试

任务切分解决的是「时间上怎么组织」，分层解决的是「空间上怎么组织」。两者缺一不可：一个时间切分得很漂亮但全局变量乱飞的项目，仍然会在第三个功能加进来的时候变成一团泥。

嵌入式软件的经典分法是四层。注意每层的「依赖方向」——上层可以调用下层，下层绝不能反过来包含上层的头文件。

分层的收益是具体的、可以验证的：① 换板子只改 BSP（一天的工作量，而不是一周）；② 应用层可以在 PC 上编译并跑单元测试（因为不含任何 HAL_ 调用）；③ 两个人可以并行开发（一个人写 BSP，一个人写业务，只要接口先定下来）；④ 定位 bug 时能快速排除一大片代码（「现象只跟时间有关、和硬件无关」→ 去中间件层找）。

接口设计有三条原则，每一条都是在防止一类具体的痛苦：

原则一：只暴露必要的函数。一个模块对外提供的函数越少，别人就越难用错、你日后改内部实现就越自由。检验方法：如果某个函数只有模块自己会调用，它就不该出现在头文件里。

反例：头文件变成了「函数清单」

很多 bsp_dev.h 最后长成这样：Key_Init()、Key_Scan()、Key_Debounce()、Key_GetRawLevel()、Key_Reset()、Key_SetLongPressMs()…… 全部暴露出去。

后果是：应用层的同事在某个 if 里顺手调了 Key_GetRawLevel() 来判断「按键是不是还按着」，于是「按下」这件事有了两套判定逻辑（一套是他在应用层写的电平判断，一套是模块内部的消抖状态机）。以后你把消抖从 3 次改成 5 次，他的那处判断不会跟着变，行为就不一致了。

正确做法：对外只留 Key_Init() 和 Key_GetEvent()；Key_Debounce() 改成 static。把「别人可能用错的东西」藏起来，比写文档告诉他们「不要这样用」有效得多。

原则二：不暴露全局变量。全局变量一旦写进头文件，就等于把模块的内部状态交给了所有人。任何一处代码都能在不通知你的情况下改它，于是模块的行为不再由模块决定。

反例：extern 出来的那个变量

bsp_adc.h 里有 extern volatile uint16_t g_adc_raw;，本意是「方便调试看数」。三个月后，应用层里出现了 g_adc_raw = 0;——写这行的人想「复位一下看看」。而 Adc_Sample() 里那套「连续 3 次读到 0 认为是传感器掉线」的保护逻辑，从此开始随机误触发。

正确做法：要读值，提供 Adc_GetRaw()；要写值，提供 Adc_SetOffset() 之类的语义化接口。这样「可以做什么」由接口显式规定，「内部怎么存」由你自由决定（今天用变量，明天换成滤波器输出，调用方一行都不用改）。

原则三：出错要有返回值。裸机代码里最常见的错误处理是「什么都不做」：void Adc_Start(void) 内部发现外设正忙，直接 return，调用方以为采样已经启动了，5 ms 后去读结果，读到的是上一次的旧值。这种 bug 的排查成本极高，因为「什么都没发生」不留下任何痕迹。

/* ── 全项目统一的返回码：放在一个公共头文件里 ── */
typedef enum {
    BSP_OK = 0,             /* 成功 */
    BSP_ERR_PARAM,          /* 参数非法（指针为 NULL、通道号越界） */
    BSP_ERR_TIMEOUT,        /* 超时（外设没在规定时间内响应） */
    BSP_ERR_BUSY,           /* 忙（上一次操作还没完成） */
    BSP_ERR_NOT_READY,      /* 未就绪（还没初始化、数据还没到） */
    BSP_ERR_HW              /* 硬件错误（校验失败、外设报错标志） */
} bsp_status_t;

/* ── 接口一律返回状态；调用方「必须」处理，不能视而不见 ── */
bsp_status_t Adc_StartSample(void);

void App_AdcTask(void)
{
    bsp_status_t st = Adc_StartSample();

    if (st != BSP_OK) {
        g_adc_fail_cnt++;                    /* 计数，供状态上报和断言使用 */
        if (st == BSP_ERR_TIMEOUT) {
            Adc_Recover();                   /* 能自愈的错误就地自愈 */
        }
        return;                              /* 关键：出错时不要继续往下走 */
    }
    /* 只有 BSP_OK 才继续 */
}

经验法则：凡是「可能失败」的操作都要有返回值，凡是返回值都要被检查。如果某个函数的返回值在代码里从来没有被检查过，那它就是在告诉你「这里没有人处理失败」。更进一步的做法是把返回值接上断言（本节末尾会讲 assert_param），让「不该发生」的情况在开发阶段就停下来。

那么头文件里放什么、.c 里藏什么？这条界线可以用一句话划清：头文件是「这个模块对外承诺了什么」，.c 是「我打算怎么做到」。

位置放什么不放什么原因
模块名.hinclude guard、必要的 #include、类型定义（状态枚举、句柄结构体）、宏常量、函数声明、extern 声明（迫不得已时）函数实现、变量定义、内部状态变量、只在内部用的宏头文件会被多个 .c 包含，任何「定义」都会被重复定义
模块名.c函数实现、所有内部状态（static 变量）、内部辅助函数（static 函数）、寄存器操作不该被外部看到的任何东西static 把符号限制在本文件内，外部链接器根本看不见它

static 有三种用法，在 BSP 里全都会用到，值得单独记住：① 修饰文件内部的全局变量（模块状态）——别人即使写了 extern 也链接不到它；② 修饰内部辅助函数——不出现在头文件里，也不会和别的模块重名；③ 修饰函数内的局部变量——让它在两次调用之间保持（2.6 里的 s_state 就是这种），但注意它不是栈上的，中断和主循环同时访问它一样需要保护。

最后，一个设备驱动应该长什么样？无论驱动的是按键、EEPROM 还是传感器，一个「规矩」的驱动大致都有这四类接口：

/* ── xxx_init：初始化。必须幂等（重复调用不出错），必须能报错 ── */
bsp_status_t Dev_Init(const dev_cfg_t *cfg);

/* ── xxx_read：取数据。名字要体现「取什么」，不要叫 Xxx_Get() ── */
bsp_status_t Dev_Read(uint8_t *buf, uint16_t len);
/* 或者更贴合语义的： */
bsp_status_t Key_GetEvent(void);              /* 返回事件枚举 */
bsp_status_t Adc_GetTemperature(int16_t *out_mdeg);   /* 单位写进参数名 */

/* ── xxx_write：下命令。要检查参数范围，越界返回 BSP_ERR_PARAM ── */
bsp_status_t Dev_Write(const uint8_t *buf, uint16_t len);
bsp_status_t Seg_SetValue(int32_t value);     /* 显示模块的「写」 */

/* ── 回调注册：让中断产生的事件能通知到上层，而不必让上层轮询 ── */
typedef void (*dev_event_cb_t)(uint32_t event, void *arg);
bsp_status_t Dev_RegisterCallback(dev_event_cb_t cb, void *arg);

/* ── 中断上下文专用的接口：名字里必须带 Isr，告诉调用者「只能在中断里用」 ── */
void Dev_OnByteReceived_Isr(uint8_t byte);    /* 由串口中断调用 */

/* ── 一个容易被忽略但极其实用的接口：状态查询（给日志和自检用） ── */
typedef struct {
    uint32_t call_count;        /* 被调用次数 */
    uint32_t error_count;       /* 出错次数，按错误码分别计数更好 */
    uint32_t last_error_tick;   /* 最后一次出错的时刻 */
    uint16_t worst_exec_us;     /* 实测最坏执行时间（第 4 节的做法） */
} dev_stat_t;

void Dev_GetStat(dev_stat_t *out);

这四类接口的顺序也隐含着模块的生命周期：init 只调用一次 → register_callback 紧接着调用一次 → read/write 在运行期被反复调用 → get_stat 在需要时（心跳上报、故障记录）调用。第 4 节会给出一个完整的 bsp_key.h / bsp_key.c，你会看到 static 如何把内部的状态机彻底藏起来。

可测试性与解耦：分层真正的回报

前面那四层里，驱动层和 HAL 是「贴着硬件」的，而中间件层与应用层应该是纯 C 逻辑——它们的输入是数字，输出是数字或事件，完全不需要知道 STM32 长什么样。这条界线一旦守住，你就得到了一个很实在的好处：这些代码可以在 PC 上编译、运行、用 printf 调试，不需要板子、不需要下载器、不需要示波器。

怎么验证界线守住了？一个很朴素的办法：把 app/ 和 middleware/ 单独丢给 PC 上的 gcc 编译。如果它们一个 STM32 的头文件都不需要 #include 就能编译通过，说明边界是干净的。反过来，如果 temp_ctrl.c 里出现了 HAL_ADC_GetValue，那这个模块就永远只能在板子上测——每次改一行滤波系数，都要烧一次程序、按一次按键、用眼睛看数码管。

最适合搬到 PC 上测的是三类逻辑，它们有个共同点：输入输出都是数，不依赖时序，也不碰硬件。

  • 换算与滤波：ADC 原始值 → 电压 → 温度，以及中值滤波、滑动平均。给定一组输入，期望的输出是可以手算出来的。
  • 状态机：按键的消抖 / 短按 / 长按 / 双击，协议解析器的逐字节喂数据。这是最容易出错、也最值得测的部分。
  • 协议编解码：组帧、转义、累加和与 CRC 校验。可以造一万条随机报文，让 PC 上的编码器与解码器互相验证。

依赖注入：用函数指针把「硬件」传进去

「不 #include HAL」说起来容易，可 ADC 值总得有人去读。做法是：应用层不直接调用硬件，而是声明「我需要这几个能力」，由调用方在初始化时把具体实现传进来。在 C 里，这组「能力」就是一个装满函数指针的结构体。

#ifndef APP_IO_H
#define APP_IO_H

#include <stdint.h>
#include "bsp_status.h"

/* 应用层需要的全部硬件能力，只有四个函数指针 */
typedef struct {
    bsp_status_t (*adc_read_raw)(uint16_t *raw);        /* 读一次 ADC 原始值 */
    uint32_t     (*get_tick_ms)(void);                  /* 取毫秒时间戳 */
    void         (*pwm_set_duty)(uint16_t permille);    /* 0~1000 占空比 */
    void         (*log)(int level, const char *tag, const char *msg);
} app_io_t;

#endif /* APP_IO_H */

应用模块的每一处硬件访问，都改成 s_io->adc_read_raw()：

#include "temp_ctrl.h"
#include "app_io.h"

static const app_io_t *s_io;      /* 注入进来的硬件能力，初始化时赋值 */
static uint16_t s_raw;
static float    s_temp_c;

static void TempCtrl_ReadSensor(void)
{
    uint16_t raw = 0;

    if (s_io->adc_read_raw(&raw) != BSP_OK) {          /* 失败就走错误码分支 */
        s_io->log(LOG_LV_WARN, "TEMP", "adc read failed");
        return;                                        /* 保留上一次的有效值 */
    }
    s_raw = raw;
    /* 纯数学：可以在 PC 上拿计算器验算 */
    s_temp_c = 25.0f + ((float)raw - 2048.0f) * 0.0625f;
}

bsp_status_t TempCtrl_Init(const app_io_t *io, const temp_ctrl_cfg_t *cfg)
{
    if (io == NULL || cfg == NULL) {
        return BSP_ERR_PARAM;                          /* 参数错误用错误码返回 */
    }
    s_io    = io;
    s_cfg   = *cfg;
    s_state = TEMP_STATE_IDLE;
    return BSP_OK;
}

同一份 temp_ctrl.c，换一个 app_io_t 就从「跑在板子上」变成「跑在 PC 上」：

/* ===== 在板子上：填真实实现（main.c 或 bsp_board.c） ===== */
static uint32_t Board_GetTick(void)          { return Sched_GetTick(); }
static void     Board_PwmSetDuty(uint16_t d) { Fan_SetDuty(d); }
static void     Board_Log(int lv, const char *tag, const char *msg)
{
    Log_Write((log_level_t)lv, tag, "%s", msg);
}

static const app_io_t g_io_board = {
    .adc_read_raw = Bsp_Adc_ReadRaw,
    .get_tick_ms  = Board_GetTick,
    .pwm_set_duty = Board_PwmSetDuty,
    .log          = Board_Log,
};

/* ===== 在 PC 上：填桩函数（stub），想让它返回什么就返回什么 ===== */
static uint16_t g_stub_raw   = 2048;    /* 桩：模拟 25 ℃ */
static uint8_t  g_stub_fail  = 0;       /* 桩：模拟 ADC 超时 */
static uint32_t g_stub_tick  = 0;       /* 桩：时间戳由测试代码控制，想跳到哪就跳到哪 */
static uint16_t g_stub_duty  = 0;       /* 桩：记录最后一次输出，供断言检查 */
static char     g_stub_log[256];

static bsp_status_t Stub_AdcRead(uint16_t *raw)
{
    if (g_stub_fail) {
        return BSP_ERR_TIMEOUT;         /* 故障路径也能测：这在板子上几乎没法稳定复现 */
    }
    *raw = g_stub_raw;
    return BSP_OK;
}

static uint32_t Stub_GetTick(void)          { return g_stub_tick; }
static void     Stub_PwmSet(uint16_t d)     { g_stub_duty = d; }

static const app_io_t g_io_test = {
    .adc_read_raw = Stub_AdcRead,
    .get_tick_ms  = Stub_GetTick,
    .pwm_set_duty = Stub_PwmSet,
    .log          = Stub_Log,
};

/* ===== PC 上的测试用例：温度跳到 80 ℃，风扇应该在一个控制周期内满速 ===== */
int main(void)
{
    TempCtrl_Init(&g_io_test, &cfg_default);

    g_stub_raw = 2048 + (uint16_t)((80.0f - 25.0f) / 0.0625f);
    g_stub_tick = 1000;
    TempCtrl_Task();                        /* 任务函数可以直接调，不必起调度器 */
    APP_ASSERT(g_stub_duty == 1000);        /* 满速 */

    g_stub_fail = 1;                        /* 让传感器「掉线」，看它会不会乱输出 */
    g_stub_duty = 0;
    TempCtrl_Task();
    APP_ASSERT(g_stub_duty == 0);           /* 读失败时必须保持上一个有效输出，而不是清零 */
    printf("all tests passed\n");
    return 0;
}

这套做法有两个名字：把假实现叫桩（stub），把「由外部把依赖传进来」叫依赖注入。用函数指针做注入，比用 #ifdef TEST 条件编译好在两点：一是同一份二进制可以在运行时切换（比如上电自检模式用桩、正常模式用真实驱动）；二是可以为每个测试用例换一套桩，不必重新编译整个工程。

打桩最值钱的地方是「造故障」

正常情况下传感器都能读到数，所以「传感器读失败时程序会怎样」这条分支在板子上几乎测不到——而它恰恰是现场故障的主要来源。有了桩，你可以随手把 g_stub_fail 置 1、把 ADC 值设成 0 / 4095 极值、把时间戳一次性往前跳 60 秒（模拟超时），几分钟就能把错误分支全走一遍。

日志：现场唯一能带走的证据

产品在客户手里出问题的时候，你能拿到的只有日志。所以日志值得在设计之初就统一好，而不是到处 printf：

  • 分等级：LOG_E / LOG_W / LOG_I，再加一个发布版直接编译掉的 LOG_D。现场可以只保留 ERROR，省串口带宽也省得刷屏。
  • 带标签：每条日志标明是哪个模块写的（"FAN"、"UART"、"TEMP"），出问题时能一眼定位到子系统。
  • 绝不在中断里 printf：串口发送本身是阻塞的（HAL_UART_Transmit 的超时按毫秒计），printf 还不可重入、要格式化浮点、占用栈。中断里做这些会把整个系统拖住。正确做法是中断只往环形缓冲里塞一条记录，由一个低优先级任务慢慢输出——这正好复用 2.5 讲的队列，日志本身就是一次「发布 / 订阅」。
typedef enum {
    LOG_LV_ERROR = 0,
    LOG_LV_WARN,
    LOG_LV_INFO,
    LOG_LV_DEBUG
} log_level_t;

/* 非阻塞：格式化进一条记录，塞进环形缓冲就返回；
   真正往串口写由 log 任务（低优先级）完成 */
void Log_Write(log_level_t lv, const char *tag, const char *fmt, ...);

#define LOG_E(tag, ...)  Log_Write(LOG_LV_ERROR, tag, __VA_ARGS__)
#define LOG_W(tag, ...)  Log_Write(LOG_LV_WARN,  tag, __VA_ARGS__)
#define LOG_I(tag, ...)  Log_Write(LOG_LV_INFO,  tag, __VA_ARGS__)

#ifdef DEBUG
#define LOG_D(tag, ...)  Log_Write(LOG_LV_DEBUG, tag, __VA_ARGS__)
#else
#define LOG_D(tag, ...)  do { } while (0)      /* 发布版：一行代码都不生成 */
#endif

/* 用法：整数运算打印小数，避免在单片机上引浮点格式化 */
LOG_I("FAN", "duty=%u temp=%d.%d", duty, temp_x10 / 10, temp_x10 % 10);

断言：把「不该发生」变成「立刻停下」

错误码处理的是世界的错误——传感器会掉线、串口会超时、CRC 会校验失败，这些都是正常的，所以每一次都必须处理。断言处理的是程序员的错误——传进来一个空指针、占空比给了 1200（合法范围是 0~1000）、状态机走进了不可能的分支。这类情况一旦发生，说明代码本身就是错的，继续跑下去只会让错误扩散到更远的地方，最后在一个完全无关的地方炸掉。两者的分工可以列成一张表：

对比项断言（assert）错误码 / 返回值
应对什么程序员的错误：不该发生、不可能发生的情况世界的错误：掉线、超时、噪声、资源不足
典型场景参数越界、空指针、switch 走到 default、状态机的非法迁移传感器无响应、CRC 校验失败、队列满、等待超时
期望被发现的时间开发阶段：写错的那一天就暴露整个生命周期：每一次运行都要判断
失败后怎么办停下：断点、闪灯、把现场记下来降级、重试、上报、沿用上一次的有效值
发布版本可以整个关掉（省 Flash、省判断时间）永远保留，永远要处理
写在哪里每个对外接口的入口、每个 switch 的 default、每个「这里不该到」的分支每个可能失败的操作的调用点

自己写断言宏时，最关键的是把文件名与行号传出去。用 __FILE__ 和 __LINE__ 这两个编译期宏，断言失败的那条日志就会直接指向出错的源代码位置：

#ifndef APP_ASSERT_H
#define APP_ASSERT_H

void App_AssertFailed(const char *file, int line, const char *expr);

/* 用 do { } while (0) 包住，保证它在 if-else 里也当成一条语句 */
#define APP_ASSERT(expr)                                    \
    do {                                                    \
        if (!(expr)) {                                      \
            App_AssertFailed(__FILE__, __LINE__, #expr);    \
        }                                                   \
    } while (0)

#endif /* APP_ASSERT_H */

#include "app_assert.h"
#include "log.h"
#include "bsp_led.h"

void App_AssertFailed(const char *file, int line, const char *expr)
{
    __disable_irq();                 /* 先停住系统，别让它带着错误继续跑 */
    Log_Write(LOG_LV_ERROR, "ASSERT",
              "assert failed: %s (%s:%d)", expr, file, line);
    Log_FlushBlocking();             /* 断言路径允许阻塞：把最后一条证据完整送出去 */

#ifdef DEBUG
    __BKPT(0);                       /* 挂着调试器：直接断在这里，能看调用栈和变量 */
#endif

    for (;;) {                       /* 没有调试器：停在「一眼看得出错了」的状态上 */
        Bsp_Led_Toggle(BSP_LED_HEART);
        for (volatile uint32_t i = 0; i < 800000u; i++) {
            /* 这里故意用忙等：系统已经停机了，无所谓让不让 CPU，
               这个空循环只为把闪灯频率压到肉眼能看清（约 0.5 s 一次） */
        }
      }
}

看到了吗——同样是「忙等」，在任务里是 bug，在断言失败的死循环里却是合理的设计。判断标准从来不是「这个写法好不好」，而是「这个位置需不需要让出 CPU」。系统已经停机、必须让故障现场可见的时候，不让 CPU 正是你要的效果。

断言失败的那一刻，现场比继续运行值钱得多

不要一上来就把断言设计成「记录一条日志然后自动复位继续跑」。那样你会丢掉现场：故障从「每次必现、每次都停在同一行」变成「偶尔复位一次」，事后拿着日志也猜不出原因。开发版本一定要「停下」，生产版本才考虑「记录 + 复位」。

顺带说一个 ST 的 HAL 库里现成的断言：assert_param。你在 HAL 源码里到处能见到 assert_param(IS_GPIO_PIN(pin)) 这样的参数检查，但它的开关在 stm32f1xx_hal_conf.h 里的 USE_FULL_ASSERT，默认是关掉的——也就是说「HAL 帮你检查参数」这件事，需要你亲手打开。打开后，一旦参数非法它就会调用你在 main.c 里实现的 assert_failed(file, line)，你在里面照抄上面 App_AssertFailed 的做法即可。开发期建议打开，它能在你第一次把引脚传错的时候就明确指出是哪一行。

把这一节末尾的三件事合起来看：分层是「物理隔离」，依赖注入是「让隔离可替换」，日志与断言是「让问题暴露得足够早、足够准」。它们共同指向接下来这一节的主题——你现在已经有了一套能长大的裸机架构，那么它离 RTOS 到底还有多远？

2.8 从裸机到 RTOS：概念对照、迁移清单与「什么时候该上」

这一节是全篇的落点。走到这里，你手上已经有一套完整的裸机架构了：1 ms 节拍的时间片轮询、一张任务表、一个环形缓冲队列、一个事件标志组、几个非阻塞状态机、四层分层与干净的接口。现在把 RTOS 拿过来对比，你会发现它给你的不是一批全新的概念，而是同一批概念的加强版：把原先靠「约定」和「自觉」维持的东西，换成由内核保证的「机制」。

裸机里的做法RTOS 里的对应物RTOS 加强在哪里迁移时要注意什么
时间片任务：一个函数 + 一个周期 任务 Task：独立栈 + 优先级 + 多种状态 每个任务有自己的栈，局部变量和调用深度不再互相影响；任务可以被挂起、阻塞、唤醒，不必靠「时间戳到了没有」轮询 任务栈大小要自己给，默认的 configMINIMAL_STACK_SIZE 常常偏小；栈溢出是 RTOS 的头号杀手，用 uxTaskGetStackHighWaterMark() 查水位
任务表里的周期与调用顺序 任务优先级 + 调度器 调度器按优先级抢占：高优先级任务一就绪就运行，不需要你手工错开相位；实时性由优先级保证，而不是由「谁排在前面」保证 优先级配错会饿死低优先级任务；抢占意味着共享数据随时可能被切开——「写在 main 里的顺序」不再是执行顺序
环形缓冲队列（单生产者、单消费者） 消息队列 xQueueCreate / xQueueSend / xQueueReceive 多生产者多消费者都安全，入队出队由内核加锁；队列满或空时可以阻塞等待（带超时）——「等一个消息」不再需要轮询 中断里必须用 xQueueSendFromISR，并处理 pxHigherPriorityTaskWoken，否则高优先级任务要等到下一个节拍才被唤醒；队列传的是值拷贝，大结构体要传指针并明确谁负责释放
事件标志组：一个 32 位变量 + 临界区 事件组 Event Group 既能「等任意一位」也能「等所有位置齐」，等待时可以阻塞、可以带超时，还能在等到之后自动清位 中断里要用 xEventGroupSetBitsFromISR（它通过定时器守护任务完成），不能直接操作；「谁清标志」的约定改由 API 语义承担，别再自己写一套
二进制标志：volatile uint8_t 二值信号量 / 计数信号量 计数信号量天然表达「有几件事待处理」——这正是裸机里一个标志位表达不了的东西（2.5 讲过的丢更新）；Give / Take 是原子的，不需要你关中断 二值信号量不累积（连续 Give 两次只算一次），要累积就用计数信号量；它也是「中断通知任务」最轻量的手段
共享变量 + 关中断临界区 互斥量 Mutex 保护的临界区 互斥量带优先级继承，能缓解优先级反转；它保护的是一份「数据 + 访问它的代码」的配对关系，比「关中断保护一切」精细得多 互斥量不能在中断里 Give / Take；持锁时间要短，绝不要「拿着锁等外设」
HAL_Delay(100) 忙等 vTaskDelay / vTaskDelayUntil 延时期间 CPU 交给别的任务，不是空转 不能在临界区和中断里调用；周期任务要用 vTaskDelayUntil 才能保持稳定周期，否则周期会随执行时间漂移
主循环末尾的 Sched_IdleHook() 空闲任务 + vApplicationIdleHook 空闲任务优先级最低，天然是「后台杂活」的落点：低功耗、喂狗、统计 空闲钩子里不能阻塞（不能 vTaskDelay、不能等信号量），否则空闲任务永远跑不完，低功耗也进不去

哪些裸机习惯，到了 RTOS 里会变成 bug

概念对照是「学什么」，下面这三条才是真会让人栽跟头的地方。它们的共同点是：在裸机里是正确的、甚至是教科书推荐的写法，到了 RTOS 里却变成了故障源。

① 在任务里长时间关中断。

裸机时代关中断，只是让 SysTick 的计数停一下，主循环照跑，你根本感觉不到。到了 RTOS 里，关中断期间 SysTick 中断进不来，调度器直接停摆——不只是「当前任务继续跑」，而是所有任务一起被冻结，连外设中断的响应都被推迟。

故障现场：有人把一次 I2C 读传感器放进临界区，想着「读的时候别被打断」。一次事务 200 µs，内部还有超时重试，最坏三次就是 600 µs 以上。表面上只是「读个传感器」，实际上每读一次系统就整体抖动一次：只有 1 字节硬件 FIFO 的串口丢字节，1 ms 控制环连续漏拍，而现象是「偶尔按键失灵」「串口偶尔少一个字符」——完全联想不到是传感器那几行代码。

量化经验值：临界区长度控制在 10 µs 以内；任何超过 100 µs 的关中断都必须有充分理由，并且写进注释。正确做法是：临界区只包住「读写共享变量」的那几条指令，耗时的原子操作交给「一个任务 + 一个队列」，用互斥量保护资源，而不是用关中断保护时间。

② 用全局变量传数据。

裸机时代，全局变量 + volatile，谁写谁读约定好，跑得好好的。到了 RTOS 里，任务切换可能发生在任意一条指令之间，而不只是在节拍点上，于是一个「读—改—写」会被从中间切成两半。

故障现场：g_stat 是一个结构体（当前温度、设定温度、运行状态、报警标志），温控任务更新它，显示任务读它。温控任务写到「新温度」之后、还没来得及写「新状态」就被切换，显示任务于是读到了「新温度 + 旧状态」的组合，按错误的状态输出占空比。这类故障偶发、难复现，现场无法解释，抓波形也看不出来。

正确做法：跨任务的数据一律走队列（值语义，拷进拷出，天然不会读到半个状态），或者用互斥量保护整个结构体。要记住一句话：volatile 不是同步手段——它只阻止编译器优化，既不阻止并发，也不保证原子性。（在 Cortex-M 上，32 位对齐的单个变量读写本身是原子的，但「读—改—写」不是，结构体更不是。）

③ 在中断里做耗时操作。

裸机时代，中断里做 50 µs 的事，主循环让路，看起来没什么。到了 RTOS 里，中断上下文根本不允许调用任何会阻塞的 API：不能 vTaskDelay、不能拿互斥量、不能 xQueueSend（只能用 FromISR 版本）；而且执行中断期间同级中断被屏蔽，ISR 越长，系统的整体响应越差；printf 与浮点运算在中断里还有栈与重入的风险。

故障现场：有人在串口中断里直接把整条报文解析完并 printf 输出。波特率 115200 时，一条 32 字节的日志就要约 2.8 ms，这段期间其他外设中断全部排队，按键按下去没反应，1 ms 控制环连续漏掉三拍。更糟的是，如果串口发送本身也在中断里等标志位，那就成了「在中断里等中断」。

正确做法（和 2.5 的裸机写法完全一致）：中断只做「取数据 + 入队或置位 + 请求切换」，然后立刻退出。解析、打印、换算、状态机推进，全都放到任务里做。这就是「中断是鼻子，任务是手」这句说法的来源。

另外三个容易忽略的搬家类 bug：用忙等当延时（HAL_Delay 在 RTOS 里既不精确又霸占 CPU，一律换成 vTaskDelay）；任务函数写成会返回（裸机的时间片任务必须返回，RTOS 的任务绝不能返回，要么 for (;;) 要么 vTaskDelete(NULL)）；忘了任务栈只有几百字节（把原来放在全局的大数组挪成任务里的局部变量，栈立刻溢出，而且现象通常是「另一个毫不相干的任务莫名跑飞」）。

什么时候该上 RTOS：一张判断清单

RTOS 不是「更高级所以更好」，它是一套用 RAM 与复杂度换编程模型的工具。下面这些条件命中得越多，越值得上：

  • 任务数 ≥ 4，而且它们的时间尺度、优先级明显不同。两三个任务的时间片轮询完全够用，四五个以上任务表就开始难维护了。
  • 有明显的优先级差异：有的事必须立刻做（比如过流保护、通信应答），有的事可以慢慢来（比如刷新显示），而且它们不能互相挡。裸机里「排在前面」只是顺序，不是优先级。
  • 有大量等待：等事件、等数据、等超时、等外设。等待越多，RTOS 的收益越大——它把「等待」变成阻塞（不占 CPU），裸机只能用轮询（要么占 CPU，要么响应变慢）。
  • 需要阻塞式编程模型：你希望把流程写成「顺序读下来就对」的代码（发命令 → 等应答 → 超时重试），而不是写成状态机。RTOS 允许你在一个任务里「阻塞地等」，这让复杂流程的可读性大幅提升。
  • 需要中间件：TCP/IP、文件系统、USB 协议栈、蓝牙协议栈，这些通常已经假设运行在 RTOS 之上，自己用裸机去接会非常痛苦。
  • 代码规模与协作：超过两万行、多人并行开发时，任务边界比「一张任务表 + 一堆全局变量」更利于拆分职责。

反过来，下面这些情况不建议上 RTOS：

  • 单一功能、一个循环就够：比如 8 位机上的电饭煲定时器、一个只做 Modbus 从站的采集板。上 RTOS 只是徒增 RAM 占用与调试面。
  • RAM 极度紧张：每个任务都要独立栈，起步就是几百字节到 1 KB，外加内核自身的几 KB 与堆（configTOTAL_HEAP_SIZE）。总共只有 2 KB RAM 的芯片直接排除。
  • 实时性要求极高而且逻辑极简：微秒级、几条指令的响应，RTOS 的调度开销与不确定性反而是负担。
  • 团队不熟悉 RTOS：这一点最容易被低估。裸机写法不熟，最多是程序乱；RTOS 写法不熟，得到的是竞态、优先级反转、栈溢出——全是偶发故障，比「乱」难查十倍。不熟就先按本篇的方式重构。

真要迁移，路径是这样的

本篇给出的顺序本身就是一条低风险的迁移路径，你不需要一步跳到 RTOS：

  1. 先按本篇重构裸机程序：时间片轮询 + 任务表 + 队列 + 事件标志 + 分层。这一步的收益是立刻就能拿到的：实时性可控、功能互不拖累、能单独测试、CPU 占用率可以算出来。
  2. 很多项目到这里就该停。你的温控器、数据采集板、小控制器，用这套架构跑到产品生命周期结束都没问题，而且比 RTOS 更容易调试、更容易交接。
  3. 当出现「阻塞式等待」的需求，或者任务数继续增加、优先级差异变大时，才换 RTOS。这时候你要解决的问题是明确的，而不是「为了用 RTOS 而用」。
  4. 迁移时你会发现业务逻辑几乎不用改：任务表与调度循环换成 xTaskCreate 与优先级；环形缓冲队列换成 xQueue；事件标志组换成事件组；毫秒时间戳换成 xTaskGetTickCount；而状态机、滤波算法、协议解析、业务判断一行都不用动——这正是前面坚持分层的回报。
本篇只讲到「过渡」为止

RTOS 本身——任务状态与调度策略、队列与信号量的内部实现、优先级反转、内存管理与中断延迟——是第 3 层的内容，见《ESP32 / FreeRTOS》那一篇。你现在需要带走的不是 RTOS 的 API，而是这套对照关系：当你能一眼看出「我这行代码在裸机里是在做什么，换成 RTOS 之后它是哪个机制的简化版」，你选架构的时候就不会再凭感觉了。

架构选型最怕「凭感觉」。感觉「任务挺少的，应该跑得动吧」，感觉「队列开 64 字节够了吧」——这些感觉在实验室里通常都是对的，因为实验室里没有故障、没有重试、没有人连续按按键。而在现场，正是那些「感觉之外」的时刻决定了产品稳不稳。

例 1 · 四个任务，能不能扛住 1 ms 控制环

某电机控制板要做 1 ms 的电流环，规划了四个时间片任务，每个任务的最坏执行时间（用示波器翻转 IO 或者用 DWT 计数器实测得到，不是猜的）如下：

任务周期 Ti最坏执行 CiCi / Ti
Ctrl_Loop（电流环）1 ms90 µs9.0%
Enc_Sample（编码器采样）2 ms40 µs2.0%
Cmd_Parse（上位机命令解析）10 ms500 µs5.0%
Disp_Scan（数码管扫描）20 ms300 µs1.5%
合计—ΣCi = 930 µs17.5%

第一步，算平均占用率。把每个任务的占用率加起来：

U_平均 = Σ(Ci / Ti)
       = 90/1000 + 40/2000 + 500/10000 + 300/20000
       = 0.090 + 0.020 + 0.050 + 0.015
       = 0.175
       = 17.5%

结论：CPU 有 82.5% 的时间是空闲的。看起来非常宽松。

第二步，算最坏一拍。要提醒自己一句：平均占用率只说明「长期来看来得及」，不说明「任何一拍都来得及」。我们的四个周期（1、2、10、20 ms）都是最小周期 1 ms 的整数倍，所以必然存在这样的时刻——比如 t = 20 ms——四个任务同时到期。这一拍要连续做 930 µs 的活：

t = 20 ms 这一拍（Ctrl + Enc + Cmd + Disp 同时到期）
    90 µs (Ctrl_Loop)
  + 40 µs (Enc_Sample)
  + 500 µs (Cmd_Parse)
  + 300 µs (Disp_Scan)
  = 930 µs

U_最坏撞车 = 930 µs / 1000 µs = 93%

结论：这一拍只剩 70 µs 的余量。任何一次「多花了一点点时间」——
      一次 flash 写、一次 HAL 超时重试、一条长日志——
      都会让这一拍超过 1 ms，节拍被挤爆，后面的节拍全部顺延。

第三步，错开相位再算一遍。既然撞车是「相位对齐」造成的，那就把长任务的相位挪开。给 Cmd_Parse 设相位 +5 ms（在 t = 5、15、25… 运行），给 Disp_Scan 设相位 +1 ms（在 t = 1、21、41… 运行）：

t = 20 ms : 90 (Ctrl) + 40 (Enc) + 500 (Cmd)          = 630 µs   (Disp 挪到了 21)
t = 21 ms : 90 (Ctrl) + 300 (Disp)                    = 390 µs   (Enc 只在偶数拍)
t = 10 ms : 90 (Ctrl) + 40 (Enc) + 500 (Cmd)          = 630 µs
t = 1  ms : 90 (Ctrl) + 300 (Disp)                    = 390 µs
t = 3  ms : 90 (Ctrl)                                 =  90 µs

U_最坏 = 630 µs / 1000 µs = 63%

结论：63% < 70%，可以接受。

你看，同一套任务、同一批代码，只把两个任务的相位挪开，最坏一拍的占用率就从 93% 降到 63%。这就是为什么 2.3 那张任务表里会有「相位」这一列——它不是装饰，它是你唯一的调优旋钮。

最后把中断的开销也算上，得到一个诚实的数字：

  • 串口每 10 ms 收 32 字节，每字节一次接收中断、每次约 1.5 µs：32 × 1.5 µs / 10 ms ≈ 0.5%
  • SysTick 中断与 HAL 的 HAL_IncTick：约 0.2%
  • 再留一点给「偶发的中断风暴」（比如一次 DMA 完成中断 + 一次 flash 操作完成中断）

于是平均占用率约 18.2%，最坏一拍 63%。省下来的那 7 个百分点（70% − 63%）不是浪费，它是留给意外的保险——没有它，你的产品会在客户现场因为「恰好那一次重试」而死机。

答完这道题，还要补一句关于「抖动」的话

节拍式调度给的是「每个周期调用一次」，它不保证调用时刻的精确性：Ctrl_Loop 排在第一，但节拍到来时主循环可能正在执行 Cmd_Parse 那 500 µs，所以它的启动时刻抖动最坏约 500 µs。

如果电流环要求「采样时刻的抖动小于 50 µs」，那么软件节拍根本给不了——这不是代码写得不好，而是机制的上限。这种要求要交给硬件：用定时器触发 ADC、用 DMA 搬运结果，让采样时刻由硬件保证，软件只负责处理数据。

例 2 · 串口环形缓冲，到底要开多大

已知条件：串口每 10 ms 收到 32 字节（115200 波特率下的典型节奏），主循环周期 5 ms，消费者每 5 ms 出队一次。queue 至少开多大？

先算生产速率：32 B / 10 ms = 3.2 B/ms = 3200 B/s。

现在看两种算法。第一种是很多人下意识会用的「平均值算法」：

主循环周期 5 ms，5 ms 内最多进 3.2 × 5 = 16 字节
→ 队列开 16 字节就够？

错在哪里：这个算法假设「主循环绝不迟到」。
而主循环迟到恰恰是最常见的事——一次 flash 写入、
一次阻塞式串口发送、一次超时重试，都会让它迟到。
队列的作用不是应付平均情况，而是吸收突发。

第二种是工程上该用的「最坏停顿算法」：容量 = 生产者速率 × 消费者最坏停顿时间 + 一个完整报文。

消费者（主循环里的解析任务）可能被卡住多久？
  - 一次 flash 写入（参数保存）        ≈ 15 ms   ← 取它作为最坏停顿
  - 一次阻塞式串口发送 40 字节 @115200 ≈ 3.5 ms
  - 一次 ADC 轮询一轮                  ≈ 1 ms

最坏停顿 T_stall = 15 ms

积压字节数 = 生产速率 × T_stall
           = 3.2 B/ms × 15 ms
           = 48 字节

还要加上「整帧约束」：协议规定一帧最长 64 字节，
队列如果小于一帧长度，一帧会被切成两半，
解析器就永远等不到一个完整帧。

容量下限 = max(48, 64) = 64 字节
取 2 的幂（环形缓冲用位与代替取模）→ 64 字节
工程上再留一倍余量               → 128 字节

校验一下 128 字节够不够：128 B ÷ 3.2 B/ms = 40 ms——也就是说，消费者可以被卡住 40 ms 才开始丢数据。对比最坏停顿 15 ms，余量充足。

这道题还有两个容易被漏掉的追问。

追问一：出队之后做什么，也要算时间。每 5 ms 出队一次、一次取走 16 字节，这没问题；但如果出队之后是把这 16 字节「转发到另一个串口」（阻塞发送），115200 波特率下 16 字节要 1.4 ms，占 5 ms 周期的 28%——还行。可要是每帧 40 字节、每 10 ms 转发一次，那就是 3.5 ms / 10 ms = 35%，再叠加别的事情就不行了。出队的成本必须和入队的节奏一起算。

追问二：满了怎么办，必须提前定好。两种策略，各有适用场景：

  • 丢最新的（拒绝入队）：适合「旧数据更有价值」的场景，比如慢速传感器采样序列。缺点是新数据被丢，实时性变差。
  • 丢最旧的（覆盖）：适合「新数据更重要」的场景，比如控制指令队列。缺点是可能丢掉一帧的开始，让后面所有帧都错位。
  • 无论选哪种，都要有一个溢出计数器，并让它出现在日志或上报里。队列满却不告诉你，等于没有队列。

例 3 · 一句 HAL_Delay(100)，把按键响应拖到多少毫秒

这是一个真实得不能再真实的前后台程序：主循环里每个环节都「看起来只花了一点时间」。需求是按键按下后 50 ms 内必须有反应。

主循环里的环节耗时说明
数码管刷新一轮2 ms8 位，每位 0.25 ms 的软件扫描
HAL_Delay(100)100 ms写代码的人觉得「刷完屏歇一会儿」
串口发送一帧文本（40 字节 @115200）3.5 ms阻塞式发送，等最后一位发完才返回
ADC 轮询一轮（8 次）1 ms每次等转换完成约 12 µs，加处理
其他（标志判断、状态推进）1.5 ms真正干活的部分，反而是最便宜的
合计（一轮）108 ms按键扫描排在这一轮的最后
 
按键在任意时刻按下，最坏情况是「刚刚错过这次扫描」
最坏响应时间 = 一轮循环的总时间 = 2 + 100 + 3.5 + 1 + 1.5 = 108 ms
平均响应时间 ≈ 104 ms（按键落在一轮中的随机位置）

再叠加消抖：连续两次扫描到低电平才算按下
消抖成本 = 2 × 一轮循环时间 ≈ 216 ms   ← 注意这里！

总响应时间（最坏） ≈ 108 + 216 = 324 ms

需求是 50 ms，实际 324 ms —— 差了 6.5 倍。
用户的感觉是：「按了没反应，得多按一会儿」。

这里有个反直觉的地方值得单独说：在阻塞式写法里，消抖的成本也被放大了。因为「连续两次扫描到低电平」之间的间隔不是 10 ms，而是「一轮循环」的 108 ms——两次采样要隔 216 ms。消抖本来是个 20 ms 的事，在这里变成了 200 ms 的事。

改法（三步，都是本篇前面讲过的）：

  1. 删掉 HAL_Delay，需要「等一会儿」就用时间戳比较（2.6 的非阻塞写法）。这一条就省下 100 ms。
  2. 串口发送改成中断或 DMA 发送，主循环只负责把数据塞进发送缓冲，不等发完。再省 3.5 ms。
  3. ADC 改成定时器触发 + DMA，主循环只读结果。再省 1 ms。
主循环剩余工作量 = 数码管 2 ms + 其他 1.5 ms ≈ 3.5 ms   （取整 4 ms）
按键扫描 = 时间片任务，周期 10 ms，最坏执行 80 µs

按键响应（按下 → 消抖确认）：
  最坏等待扫描    ≤ 10 ms     ← 扫描周期，可预测
  消抖            = 20 ms     ← 两次扫描，间隔真的是 10 ms
  处理与输出      ≈  1 ms
  ------------------------------
  合计            ≈ 31 ms     < 50 ms ✓

余量 19 ms，而且这个数字是「算出来的」，不是「试出来的」。

把这道题的核心结论写下来：时间片轮询给的不只是「更快」，而是「可预测」。阻塞式写法下，按键的响应时间等于「一轮循环有多长」，而这个长度会随着你以后每加一个功能而变长——今天 108 ms，下周加了新功能就是 130 ms，你根本不知道什么时候会突破 50 ms 的红线。时间片写法下，响应时间由扫描周期决定，加功能不影响它。

例 4 · 一个任务比节拍还长，会发生什么

有人写了一个任务，最坏执行时间实测 Ci = 1.2 ms，而调度节拍是 1 ms。他问我：「能跑吗？平均占用率不到 100% 啊。」

先看平均口径，其实从这一步就已经暴露了：

如果这个任务周期也是 1 ms：
  Ci / Ti = 1.2 ms / 1 ms = 120%  > 100%

含义：它消耗的速度比它产生的速度还快。
      待办会无限堆积（如果用计数器标志，计数只增不减）。
      不管后面怎么调相位，都救不回来。

再看它怎么挤爆节拍：

时间轴（tick = 1 ms）：

tick N      : 节拍中断置位 → 主循环调用 Long_Task，开始执行
tick N+1    : Long_Task 还在跑（已跑 1.0 ms），SysTick 又置位一次
              → 它的执行时间跨越了节拍点
tick N+1.x  : Long_Task 返回（总耗时 1.2 ms）
              → 主循环立刻又看到「节拍到了」，于是再调用一次 Long_Task
tick N+2    : 它还在跑……

结果：这个任务事实上连跑了两拍（2 ms），
      而任务表里排在它后面的所有任务，在这 2 ms 里一次都没跑。
      如果这种状态持续，排在后面的任务会周期性「消失」——
      现象是「显示偶尔卡一下」「串口偶尔不回」。

于是我们得到时间片轮询的一条硬约束：

没有任何任务的最坏执行时间可以超过一个节拍

用 1 ms 节拍，就要求每个任务的 Ci < 1000 µs。这不是「建议」，而是机制本身的要求——因为调度器只有在主循环转回任务表时才能切换任务，一个任务跑得比节拍还久，就等于把节拍踩在脚下。

超过了怎么办？两条出路，都很实用：

  • 拆成分步执行：把「整帧 CRC 校验 1200 µs」改成「每拍算 64 字节，200 µs」，用状态机跨 6 拍完成。这正是 2.6 讲的非阻塞状态机的用武之地——把一个长任务摊到多个节拍上。
  • 搬给硬件或中断：能交给 DMA 的搬运、能交给硬件外设的计算（CRC 外设、定时器捕获、ADC 转换），就不要放在任务里做。

顺带解释一个设计细节：为什么任务表里的「节拍标志」用 uint8_t 计数，而不是布尔标志。计数版可以容忍「一拍内欠账」——如果某个任务这一拍没跑完，计数会累积，它一返回就能补上。但这个容忍是有代价的：欠账会累积，所以必须保证长期平均 Σ(Ci/Ti) < 100%。这就是为什么平均口径和最坏口径两个都要算：平均口径看长期会不会欠账，最坏口径看瞬时会不挤爆。

4.1 一个完整的 1 ms 时间片调度器

这个调度器一共三件事：① SysTick 中断把节拍计数 s_tick 加一；② 主循环遍历任务表，谁到期就调谁；③ 顺手把这一拍的执行时间量出来，换算成 CPU 占用率。任务表就是 2.3 讲的那个结构，只是这次把每个字段都写全了。

#ifndef SCHED_H
#define SCHED_H

#include <stdint.h>

#define SCHED_MAX_TASKS   10u     /* 任务表最多放几个任务 */
#define SCHED_TICK_MS     1u      /* 调度节拍：1 ms，与 SysTick 一致 */

/* 任务函数：无参数、无返回值。
   硬性约定：必须自己保证在一个周期内返回，绝不能阻塞（不许 HAL_Delay、
   不许等串口、不许等 ADC）。想「等」就用时间戳比大小，见 4.4 的状态机。 */
typedef void (*sched_task_fn)(void);

typedef struct {
    sched_task_fn fn;          /* 任务函数指针 */
    const char   *name;        /* 名字，只用于日志与统计 */
    uint32_t      period_ms;   /* 周期，必须是 SCHED_TICK_MS 的整数倍 */
    uint32_t      phase_ms;    /* 相位偏移：让长任务错开，避免同拍撞车 */
    uint32_t      last_run;    /* 上一次「计划运行」的节拍号（不是实际运行时刻） */
    uint32_t      run_count;   /* 运行次数：调试时看谁没跑最有用 */
    uint8_t       enabled;     /* 使能标志：0 = 暂时不调度，但保留在表里 */
} sched_task_t;

void     Sched_Init(void);
int8_t   Sched_Add(sched_task_fn fn, const char *name,
                   uint32_t period_ms, uint32_t phase_ms);  /* 返回下标，负数是失败 */
void     Sched_Enable(uint8_t idx, uint8_t on);
void     Sched_Run(void);                     /* 放进 main 的末尾，永不返回 */
uint32_t Sched_GetTick(void);                 /* 毫秒时间戳：全工程唯一的时间基准 */
uint32_t Sched_GetCpuPermille(void);          /* CPU 占用率，千分数（630 = 63.0%） */
uint8_t  Sched_GetTaskCount(void);
void     Sched_DumpTasks(void);               /* 把任务表打到日志里 */
void     Sched_OnTickFromISR(void);           /* 由 SysTick_Handler 调用 */
void     Sched_IdleHook(void);                /* 空闲钩子：可被用户覆盖 */

#endif /* SCHED_H */

实现里有三个值得停一下看的地方：节拍计数用无符号减法比较（天然处理回绕）、last_run 记的是「计划时刻」而不是「当前时刻」（这样迟到的任务能自动补上）、CPU 占用率用 DWT 周期计数器实测。

#include "sched.h"
#include "stm32f1xx_hal.h"      /* 只为了 __disable_irq / __NOP / CoreDebug / DWT */
#include "log.h"

/* ---------- 全部内部状态都是 static：外部一个都看不见 ---------- */
static sched_task_t      s_tasks[SCHED_MAX_TASKS];
static uint8_t           s_task_count;

/* 节拍计数：只在中断里自增，在 main 里读。32 位对齐的单次读写在 Cortex-M 上
   是原子的，所以两边都不需要关中断；volatile 只用来阻止编译器把它优化到
   寄存器里缓存起来（那样主循环就永远看不到它在变）。 */
static volatile uint32_t s_tick;

static volatile uint32_t s_cpu_permille;   /* 最近一次统计出来的占用率 */
static uint32_t          s_stat_tick;      /* 正在统计哪一拍 */
static uint32_t          s_busy_cycles;    /* 这一拍已经消耗掉的 CPU 周期数 */

/* ---------- DWT 周期计数器：用来实测任务执行时间 ---------- */
static void DWT_Init(void)
{
    CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;   /* 打开跟踪与调试 */
    DWT->CYCCNT = 0u;
    DWT->CTRL  |= DWT_CTRL_CYCCNTENA_Msk;             /* 使能周期计数器 */
}

static inline uint32_t DWT_Cycles(void)
{
    return DWT->CYCCNT;                               /* 每个 CPU 周期加一 */
}

static inline uint32_t DWT_UsPerCycle(void)          /* 把一个周期换算成 µs 的分母 */
{
    return (SystemCoreClock / 1000000u);             /* 72 MHz → 72 */
}

void Sched_Init(void)
{
    uint32_t i;

    for (i = 0u; i < SCHED_MAX_TASKS; i++) {
        s_tasks[i].fn        = 0;
        s_tasks[i].name      = 0;
        s_tasks[i].period_ms = 0u;
        s_tasks[i].phase_ms  = 0u;
        s_tasks[i].last_run  = 0u;
        s_tasks[i].run_count = 0u;
        s_tasks[i].enabled   = 0u;
    }
    s_task_count   = 0u;
    s_tick         = 0u;
    s_cpu_permille = 0u;
    s_stat_tick    = 0u;
    s_busy_cycles  = 0u;

    DWT_Init();
}

int8_t Sched_Add(sched_task_fn fn, const char *name,
                 uint32_t period_ms, uint32_t phase_ms)
{
    sched_task_t *t;

    if (fn == 0 || period_ms == 0u) {
        return -1;                                  /* 参数错误 */
    }
    if (s_task_count >= SCHED_MAX_TASKS) {
        return -2;                                  /* 任务表满了 */
    }
    if ((period_ms % SCHED_TICK_MS) != 0u) {
        return -3;                                  /* 周期不是节拍的整数倍，调度不了 */
    }

    t = &s_tasks[s_task_count];
    t->fn        = fn;
    t->name      = (name != 0) ? name : "?";
    t->period_ms = period_ms;
    t->phase_ms  = phase_ms % period_ms;
    t->run_count = 0u;
    t->enabled   = 1u;

    /* 让任务第一次恰好在 tick == phase_ms 时运行：
       last_run = phase - period（无符号回绕），于是
       (tick - last_run) >= period 在 tick == phase 时第一次成立。
       phase = 0 时 last_run 回绕成一个很大的数，第一拍就到期，符合预期。 */
    t->last_run = (uint32_t)(t->phase_ms - t->period_ms);

    return (int8_t)(s_task_count++);
}

void Sched_Enable(uint8_t idx, uint8_t on)
{
    if (idx < s_task_count) {
        s_tasks[idx].enabled = (on != 0u) ? 1u : 0u;
    }
}

/* 这一行由 SysTick_Handler 调用。整个调度器的「心跳」就在这里。 */
void Sched_OnTickFromISR(void)
{
    s_tick++;                                       /* 就一件事，越短越好 */
}

void Sched_Run(void)
{
    for (;;) {
        uint32_t i;
        uint32_t c0  = DWT_Cycles();
        uint8_t  ran = 0u;

        /* ---- 遍历任务表：谁到期就调谁 ---- */
        for (i = 0u; i < s_task_count; i++) {
            sched_task_t *t = &s_tasks[i];

            if (t->enabled == 0u) {
                continue;
            }

            /* 无符号相减：tick 回绕时结果依然正确，不需要额外的判断。
               这是嵌入式里比较时间戳的标准写法（2.6 也会用到）。 */
            if ((uint32_t)(s_tick - t->last_run) >= t->period_ms) {
                /* 关键：累加的是「计划时刻」而不是 s_tick。
                   如果某一拍因为别的事情耽误了，下次比较时它仍然欠着账，
                   于是会被立刻补上——这就是 2.3 说的「用时间戳容错」。 */
                t->last_run += t->period_ms;
                t->run_count++;
                t->fn();                             /* 调用任务 */
                ran = 1u;
            }
        }

        /* ---- CPU 占用率统计：先攒，跨拍时再发布 ---- */
        if (ran != 0u) {
            uint32_t c1       = DWT_Cycles();
            uint32_t tick_now = s_tick;

            s_busy_cycles += (c1 - c0);              /* 这一趟循环干了多少周期 */

            if (tick_now != s_stat_tick) {
                /* 进入新的一拍了：把上一拍攒下的忙碌周期换算成千分数 */
                uint32_t cycles_per_tick = (SystemCoreClock / 1000u) * SCHED_TICK_MS;

                s_cpu_permille = (s_busy_cycles * 1000u) / cycles_per_tick;
                s_stat_tick    = tick_now;
                s_busy_cycles  = 0u;
            }
        }

        Sched_IdleHook();                            /* 有空闲就做点后台杂活 */
    }
}

uint32_t Sched_GetTick(void)
{
    /* 32 位对齐变量的单次读取在 Cortex-M 上是原子的，这里不需要关中断。
       保留函数封装的意义是：将来如果换成 64 位计数或结构体，
       只需要改这一处，所有调用者不受影响。 */
    return s_tick;
}

uint32_t Sched_GetCpuPermille(void)
{
    return s_cpu_permille;                           /* 读一个 32 位变量，同样是原子的 */
}

uint8_t Sched_GetTaskCount(void)
{
    return s_task_count;
}

void Sched_DumpTasks(void)
{
    uint32_t i;

    for (i = 0u; i < s_task_count; i++) {
        Log_Write(LOG_LV_INFO, "SCHED", "%-6s period=%lums phase=%lums run=%lu",
                  s_tasks[i].name,
                  (unsigned long)s_tasks[i].period_ms,
                  (unsigned long)s_tasks[i].phase_ms,
                  (unsigned long)s_tasks[i].run_count);
    }
}

/* 空闲钩子：默认什么都不做。用户可以在自己的 .c 里重新实现它
   （GCC 用 __attribute__((weak))，Keil/IAR 用 __weak）。
   注意：这里绝不能阻塞、也不能耗时太久，否则等于把节拍挤爆。 */
#if defined(__GNUC__)
__attribute__((weak)) void Sched_IdleHook(void)
#else
__weak void Sched_IdleHook(void)
#endif
{
    __NOP();
}

中断侧只需要在 CubeMX 生成的 stm32f1xx_it.c 里加一行：

void SysTick_Handler(void)
{
    HAL_IncTick();              /* HAL 自己的毫秒计数：HAL_Delay / HAL_UART 超时还在用它 */
    Sched_OnTickFromISR();      /* ← 我们加的：调度器的心跳 */
}
不要自己再写一个 SysTick_Handler

CubeMX 已经在 stm32f1xx_it.c 里定义了这个函数，你在别处再定义一次，链接时会报重复符号。正确做法就是在它里面加一行。

另外，HAL_IncTick() 不要删——只要你还用着 HAL 的任何一个带超时的函数（HAL_UART_Transmit、HAL_ADC_PollForConversion），它就必须继续被调用。

然后是它在 main.c 里的完整用法，任务表就照着第 3 节例 1 的数字注册：

#include "main.h"
#include "sched.h"
#include "bsp_key.h"
#include "app_ctrl.h"
#include "app_fan.h"

static void Task_Ctrl(void);      /* 1 ms  电流环     */
static void Task_Enc(void);       /* 2 ms  编码器采样 */
static void Task_Cmd(void);       /* 10 ms 命令解析   */
static void Task_Disp(void);      /* 20 ms 数码管扫描 */
static void Task_Key(void);       /* 10 ms 按键扫描   */
static void Task_Adc(void);       /* 10 ms 温度采样   */
static void Task_Report(void);    /* 100 ms 上报      */
static void Task_Led(void);       /* 500 ms 心跳灯    */

int main(void)
{
    HAL_Init();
    SystemClock_Config();          /* 72 MHz */
    MX_GPIO_Init();
    MX_USART1_UART_Init();
    MX_ADC1_Init();
    MX_TIM1_Init();                /* PWM，给风扇 */
    MX_TIM3_Init();                /* 定时器触发 ADC */

    Log_Init();                    /* 日志：内部就是环形缓冲 + 中断发送 */
    Bsp_Key_Init();                /* 驱动层：注册回调，准备好硬件 */
    App_Ctrl_Init();
    App_Fan_Init();

    Sched_Init();

    /* 参数：函数、名字、周期(ms)、相位(ms)
       相位这一列就是第 3 节例 1 的调优结果：把 10 ms 的命令解析放在 +5、
       20 ms 的显示扫描放在 +1，最坏一拍的占用率从 93% 降到 63%。 */
    Sched_Add(Task_Ctrl,   "ctrl",   1u,   0u);
    Sched_Add(Task_Enc,    "enc",    2u,   0u);
    Sched_Add(Task_Cmd,    "cmd",    10u,  5u);
    Sched_Add(Task_Disp,   "disp",   20u,  1u);
    Sched_Add(Task_Key,    "key",    10u,  3u);
    Sched_Add(Task_Adc,    "adc",    10u,  4u);
    Sched_Add(Task_Report, "report", 100u, 7u);
    Sched_Add(Task_Led,    "led",    500u, 0u);

    Sched_Run();                   /* 从此不再返回，main 里不要再写 while(1) */
}

/* ---- 1 ms 电流环：最坏 90 µs，读不到数据就干净地跳过这一拍 ---- */
static void Task_Ctrl(void)
{
    int16_t i_meas;

    if (Adc_GetCurrent(&i_meas) != BSP_OK) {
        return;                    /* 失败不硬等，下一拍再试；这拍只有几微秒 */
    }
    App_Ctrl_Step(i_meas);         /* 纯计算：PI 调节 + 更新 PWM 占空比 */
}

/* ---- 10 ms 按键扫描：采样 + 推进状态机，全程不阻塞 ---- */
static void Task_Key(void)
{
    bsp_key_event_t ev;

    Bsp_Key_Poll();                /* 只做一次采样，内部状态机推进消抖 */
    while (Bsp_Key_GetEvent(&ev)) {  /* 可能有多个事件（比如同时短按两个键） */
        App_OnKeyEvent(&ev);
    }
}

/* ---- 100 ms 上报：把调度器自己的统计打出去 ---- */
static void Task_Report(void)
{
    uint32_t permille = Sched_GetCpuPermille();

    LOG_I("SCHED", "cpu=%lu.%lu%% tasks=%u tick=%lu",
          (unsigned long)(permille / 10u),
          (unsigned long)(permille % 10u),
          Sched_GetTaskCount(),
          (unsigned long)Sched_GetTick());
}

最后是空闲钩子的一个实用实现——喂狗和低功耗都放在这里，因为它们的前提都是同一件事：主循环还有空转的时间，说明系统是健康的。

#include "sched.h"
#include "bsp_wdg.h"
#include "stm32f1xx_hal.h"

/* 覆盖 sched.c 里的弱符号实现（同名函数，弱符号会被这里的强符号顶掉） */
void Sched_IdleHook(void)
{
    static uint16_t idle_ticks = 0u;

    Bsp_Wdg_Feed();                /* 喂狗：只要主循环还在转，就说明没死 */

    idle_ticks++;
    if (idle_ticks >= 100u) {      /* 连续 100 拍都没别的事，就睡一下省电 */
        idle_ticks = 0u;
        __WFI();                   /* 等中断；下一个 SysTick 会把它叫醒 */
    }
}
怎么看这个调度器到底跑了多少？

把 Sched_DumpTasks() 接到一个串口命令上，就能拿到每个任务的运行次数。这是排查「某个功能偶尔不响应」的第一招：如果某个任务的 run_count 明显比同期其他任务少，那它要么被挤掉了，要么自己超时了。

没有 DWT 的芯片（Cortex-M0/M0+）怎么办？两个办法：把 DWT_Cycles() 换成一个空闲定时器的计数值；或者干脆只统计「每拍任务耗时」的粗值——用 Sched_GetTick() 在进任务前和出任务后各读一次。精度差一些，但足够看出「哪一拍明显超了」。

4.2 环形缓冲：中断入队，主循环出队

这是 2.5 那张「环形缓冲三态图」的代码版。它有两个必须记住的设计点：容量取 2 的幂（用位与代替取模，也省掉一个「满 / 空」判断变量），以及写指针最后发布（先填数据、再动指针，消费者永远读不到写了一半的内容）。

#ifndef RINGBUF_H
#define RINGBUF_H

#include <stdint.h>

/* 用法约定：
   - 生产者：只能有一个，通常是中断（串口接收 / DMA 完成）
   - 消费者：只能有一个，通常是主循环里的一个任务
   只要守住「一个生产者 + 一个消费者」，这个队列就不需要关中断。 */
typedef struct {
    uint8_t          *buf;       /* 数据区：由调用方提供（静态数组，不用 malloc） */
    uint16_t          size;      /* 数据区大小，必须是 2 的幂 */
    uint16_t          mask;      /* size - 1，用来代替取模运算 */
    volatile uint16_t head;      /* 写指针：只有生产者改 */
    volatile uint16_t tail;      /* 读指针：只有消费者改 */
    volatile uint32_t drop_cnt;  /* 因为满而丢掉的字节数：一定要有这个计数器 */
} ringbuf_t;

void     Ring_Init(ringbuf_t *rb, uint8_t *buf, uint16_t size);
uint16_t Ring_Put(ringbuf_t *rb, const uint8_t *data, uint16_t len);
uint16_t Ring_Get(ringbuf_t *rb, uint8_t *out, uint16_t maxlen);
uint16_t Ring_Used(const ringbuf_t *rb);
uint16_t Ring_Free(const ringbuf_t *rb);
void     Ring_Flush(ringbuf_t *rb);

#endif /* RINGBUF_H */

#include "ringbuf.h"

void Ring_Init(ringbuf_t *rb, uint8_t *buf, uint16_t size)
{
    rb->buf      = buf;
    rb->size     = size;
    rb->mask     = (uint16_t)(size - 1u);   /* size 必须是 2 的幂，否则这里就错了 */
    rb->head     = 0u;
    rb->tail     = 0u;
    rb->drop_cnt = 0u;
}

/* ---------------- 生产者：在中断里调用 ----------------
   注意这里【没有关中断】。单生产者单消费者模型下：
     head 只有本函数改，tail 只有消费者改；
     两边各自「读对方的单个 uint16_t」在 Cortex-M 上是原子的。
   所以整个入队过程不需要临界区，中断里也就能用得放心。            */
uint16_t Ring_Put(ringbuf_t *rb, const uint8_t *data, uint16_t len)
{
    uint16_t head     = rb->head;      /* 自己改的，随便读 */
    uint16_t tail     = rb->tail;      /* 别人改的，读一次就固定下来用 */
    uint16_t used     = (uint16_t)((head - tail) & rb->mask);
    uint16_t free_cnt = (uint16_t)(rb->size - 1u - used);   /* 留一个空位区分满和空 */
    uint16_t n;
    uint16_t i;

    n = (free_cnt > len) ? len : free_cnt;
    if (n < len) {
        /* 满了。丢多少必须记账——队列悄悄丢数据是最难查的故障之一。
           策略选择：这里丢的是「最新的」（拒绝入队）；
           如果你的场景是「新数据更重要」（比如控制指令），
           就改成覆盖最旧的（tail 也跟着往前挪）。 */
        rb->drop_cnt += (uint32_t)(len - n);
    }

    for (i = 0u; i < n; i++) {
        rb->buf[head] = data[i];
        head = (uint16_t)((head + 1u) & rb->mask);
    }

    /* 关键的一行：数据写完了，才发布写指针。
       在它之前，消费者看到的 head 还是旧值，所以不会读到刚写了一半的内容。 */
    rb->head = head;

    return n;
}

/* ---------------- 消费者：在主循环任务里调用 ---------------- */
uint16_t Ring_Get(ringbuf_t *rb, uint8_t *out, uint16_t maxlen)
{
    uint16_t tail  = rb->tail;         /* 自己改的 */
    uint16_t head  = rb->head;         /* 别人改的，读一次固定下来 */
    uint16_t avail = (uint16_t)((head - tail) & rb->mask);
    uint16_t n;
    uint16_t i;

    n = (avail < maxlen) ? avail : maxlen;

    for (i = 0u; i < n; i++) {
        out[i] = rb->buf[tail];
        tail = (uint16_t)((tail + 1u) & rb->mask);
    }

    rb->tail = tail;                   /* 同样最后发布读指针 */
    return n;
}

uint16_t Ring_Used(const ringbuf_t *rb)
{
    /* 这里读了两个变量，中间可能被生产者改一次 head。
       影响只是「算出来的占用数略微偏小」——对统计来说完全可以接受。 */
    return (uint16_t)((rb->head - rb->tail) & rb->mask);
}

uint16_t Ring_Free(const ringbuf_t *rb)
{
    return (uint16_t)(rb->size - 1u - Ring_Used(rb));
}

void Ring_Flush(ringbuf_t *rb)
{
    rb->tail = rb->head;   /* 丢数据只是「消费者往前追」，生产者完全不受影响 */
}
volatile 在这里到底保证了什么

它保证两件事：① 编译器不会把 head / tail 缓存进寄存器（否则消费者可能永远看到循环开始时的旧值）；② 编译器不会调换「写数据」和「发布指针」这两步的顺序——这是「先填数据、再动指针」能成立的前提。

它不保证的是：多核之间的可见性，以及带 D-Cache 的芯片上的缓存一致性。单核 Cortex-M（F1/F4/G0 这一档）不需要额外处理；如果换成 STM32H7 这类带 D-Cache 的芯片，或者双核的 H7 / L4+，就要在发布指针前后加内存屏障 __DMB()，并且把数据区放在非缓存（或写穿）的内存里。这一点在第 3 层讲高性能 MCU 时还会遇到。

接上串口只需要两个函数：一个在中断里把字节塞进去，一个在主循环里把字节取出来。这就是「中断是生产者、主循环是消费者」最标准的落地。

#include "bsp_uart.h"
#include "ringbuf.h"
#include "stm32f1xx_hal.h"

static UART_HandleTypeDef huart1;

static uint8_t   g_rx_byte;                          /* 单字节接收的落脚点 */
static uint8_t   g_rx_storage[128];                  /* 数据区：静态数组 */
static ringbuf_t g_rx;                               /* 队列对象 */

void Bsp_Uart_Init(uint32_t baud)
{
    huart1.Instance          = USART1;
    huart1.Init.BaudRate     = baud;
    huart1.Init.WordLength   = UART_WORDLENGTH_8B;
    huart1.Init.StopBits     = UART_STOPBITS_1;
    huart1.Init.Parity       = UART_PARITY_NONE;
    huart1.Init.Mode         = UART_MODE_TX_RX;
    huart1.Init.HwFlowCtl    = UART_HWCONTROL_NONE;
    huart1.Init.OverSampling = UART_OVERSAMPLING_16;
    (void)HAL_UART_Init(&huart1);

    Ring_Init(&g_rx, g_rx_storage, (uint16_t)sizeof(g_rx_storage));

    /* 打开「收到 1 个字节就中断一次」：之后每来一个字节都会进下面的回调 */
    (void)HAL_UART_Receive_IT(&huart1, &g_rx_byte, 1u);
}

/* HAL 的回调：每收到一个字节调用一次。整个函数耗时不到 2 µs。
   这里【只做一件事】：把字节放进队列。
   不解析、不判断、不打印——判断和打印是应用层的事。 */
void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
{
    if (huart->Instance == USART1) {
        (void)Ring_Put(&g_rx, &g_rx_byte, 1u);         /* 满了会丢，并记进 drop_cnt */
        (void)HAL_UART_Receive_IT(&huart1, &g_rx_byte, 1u);  /* 重新武装，继续收下一个 */
    }
}

/* 消费者：在一个 5 ms 的时间片任务里调用（也可以放在 1 ms 任务里，
   但它要处理 32 字节，实测约 12 µs，放在 5 ms 任务里更省） */
void Bsp_Uart_Poll(void)
{
    uint8_t  chunk[32];
    uint16_t n;

    while ((n = Ring_Get(&g_rx, chunk, (uint16_t)sizeof(chunk))) > 0u) {
        Proto_Parse(chunk, n);       /* 逐字节喂给协议状态机，全程非阻塞 */
    }
}

/* 供上报任务查：丢了多少字节。这个数非 0 就说明队列小了或者消费者迟到了。 */
uint32_t Bsp_Uart_GetDropCount(void)
{
    return g_rx.drop_cnt;
}
波特率再高一点，就该换 DMA + 空闲中断

上面这个写法每收一个字节进一次中断，115200 波特率下是每秒 11520 次，约占 CPU 的 1.7%（按每次 1.5 µs 算）。到了 921600 或者要连续收大包的时候，就该换成 DMA 接收 + 串口空闲中断（IDLE）：DMA 把整包数据直接搬进缓冲，空闲中断只负责「置一个事件标志」（正好用 4.3 的事件标志组）。

注意这时候环形缓冲的角色变了：DMA 自己就是一个环形搬运工，你只需要在 IDLE 中断里算出「这次搬了多少字节」。这也是「机制在变、模式不变」的例子——生产者永远只搬数据，消费者永远只做处理。

同一套代码，换成「消息」而不是「字节」

实际项目里更常用的是「队列里放结构体」——比如按键事件、传感器读数、通信报文，一个个带类型的小结构体。实现和上面一模一样，只把 uint8_t 换成结构体，并且记住一条铁律：入队必须整体拷贝，绝不能让队列里存着指向「即将消失的局部变量」的指针。

typedef struct {
    uint8_t  type;      /* 消息类型：MSG_KEY / MSG_TEMP / MSG_FRAME ... */
    uint16_t value;     /* 附带数据 */
    uint32_t tick;      /* 产生时刻：调试时它比什么都管用 */
} app_msg_t;

#define MSGQ_SIZE   16u                 /* 2 的幂：8 个消息就够，取 16 留余量 */

static app_msg_t  g_msg_buf[MSGQ_SIZE];
static msgq_t     g_msgq;

/* 入队：整个结构体拷贝进去 */
uint8_t Msg_Post(const app_msg_t *m)     /* 返回 1 = 成功，0 = 队列满被丢弃 */
{
    return Ring_PutStruct(&g_msgq, m);    /* 内部就是 memcpy 到 buf[head]，再发布 head */
}

/* 出队：一次取一条，逐个处理 */
void Msg_Drain(void)
{
    app_msg_t m;

    while (Msg_Take(&m) != 0u) {          /* 队列空就立刻返回，绝不等待 */
        App_OnMessage(&m);
    }
}

/* 在中断里产生消息也是安全的（生产者只有一个） */
void HAL_ADC_ConvCpltCallback(ADC_HandleTypeDef *hadc)
{
    app_msg_t m;

    m.type  = MSG_TEMP;
    m.value = (uint16_t)Adc_GetRawDma();
    m.tick  = Sched_GetTick();            /* 中断里读时间戳是安全的（单个 32 位读） */
    (void)Msg_Post(&m);                   /* 结构体在栈上，拷完就随它去 */
}

4.3 事件标志组：一个 32 位变量表示 32 件事

有些「事件」不需要传递数据，只需要告诉别人「这件事发生了」：过流了、收到一帧了、1 秒到了、上位机要求保存参数了。为这些事各开一个队列是浪费——一个 32 位变量就够了，每一位代表一件事。它的核心难点不在置位，而在「谁清位、什么时候清」。

#ifndef EVT_H
#define EVT_H

#include <stdint.h>

/* 事件位定义：整个工程只在这里定义一次。
   裸写 Evt_Set(1 << 3) 的代码，三个月后你自己都不记得 3 是什么。 */
#define EVT_KEY_SHORT    (1UL << 0)    /* 短按 */
#define EVT_KEY_LONG     (1UL << 1)    /* 长按 */
#define EVT_ADC_DONE     (1UL << 2)    /* 一次 ADC 转换完成 */
#define EVT_UART_FRAME   (1UL << 3)    /* 收到一个完整报文 */
#define EVT_CMD_SAVE     (1UL << 4)    /* 上位机要求保存参数 */
#define EVT_FAULT_OC     (1UL << 5)    /* 过流 */
#define EVT_TICK_1S      (1UL << 6)    /* 每秒一次的心跳 */

typedef uint32_t evt_flags_t;

void        Evt_Init(void);
void        Evt_Set(evt_flags_t bits);            /* 置位：可以在中断里调用 */
evt_flags_t Evt_Peek(void);                       /* 只看不取（不改变任何状态） */
evt_flags_t Evt_Take(void);                       /* 取出全部已置位并清掉 */
evt_flags_t Evt_TakeMasked(evt_flags_t mask);     /* 只取自己关心的位，别的不动 */
void        Evt_Clear(evt_flags_t bits);          /* 显式清掉某几位 */
uint8_t     Evt_Check(evt_flags_t mask);          /* 关心的位是否全部置上（非阻塞） */
uint8_t     Evt_Wait(evt_flags_t mask, uint32_t timeout_ms);  /* 阻塞等待（见下方说明） */

#endif /* EVT_H */

#include "evt.h"
#include "sched.h"
#include "stm32f1xx_hal.h"      /* __get_PRIMASK / __set_PRIMASK / __disable_irq */

static volatile evt_flags_t s_flags;    /* 全部状态就这一个变量 */

void Evt_Init(void)
{
    s_flags = 0u;
}

/* ---------------- 置位 ----------------
   s_flags |= bits 是「读—改—写」三步，中间被中断打断就可能丢事件。
   所以要用临界区保护——但注意这个临界区只有几条指令（纳秒级），
   完全符合「临界区 10 µs 以内」的要求。                        */
void Evt_Set(evt_flags_t bits)
{
    uint32_t primask = __get_PRIMASK();   /* 先记住：调用者原来是不是关着中断 */

    __disable_irq();
    s_flags |= bits;
    __set_PRIMASK(primask);               /* 恢复原状。如果调用者本来就关着中断，
                                             这里绝不会替他打开——这是嵌套调用的基本礼貌 */
}

/* ---------------- 取出并清掉 ----------------
   返回的是「取出这一刻」的位图。之后新置的位不受影响，
   所以「取出 → 处理」这段时间里发生的新事件不会丢。            */
evt_flags_t Evt_Take(void)
{
    evt_flags_t got;
    uint32_t primask = __get_PRIMASK();

    __disable_irq();
    got     = s_flags;
    s_flags = 0u;
    __set_PRIMASK(primask);

    return got;
}

/* 只取自己关心的位：适合「多个消费者各管一摊」的场景。
   比如通信任务只取 EVT_UART_FRAME，控制任务只取 EVT_FAULT_OC。 */
evt_flags_t Evt_TakeMasked(evt_flags_t mask)
{
    evt_flags_t got;
    uint32_t primask = __get_PRIMASK();

    __disable_irq();
    got      = s_flags & mask;
    s_flags &= (evt_flags_t)(~mask);      /* 只清 mask 里的位 */
    __set_PRIMASK(primask);

    return got;
}

evt_flags_t Evt_Peek(void)
{
    return s_flags;                        /* 单个 32 位读，本身就是原子的 */
}

void Evt_Clear(evt_flags_t bits)
{
    uint32_t primask = __get_PRIMASK();

    __disable_irq();
    s_flags &= (evt_flags_t)(~bits);
    __set_PRIMASK(primask);
}

/* 非阻塞检查：在时间片任务里用这个（立刻返回） */
uint8_t Evt_Check(evt_flags_t mask)
{
    return ((Evt_Peek() & mask) == mask) ? 1u : 0u;
}

/* 阻塞等待：等 mask 全部置上，或者超时。
   ⚠ 只能用在「允许阻塞」的地方：上电初始化（等外设就绪）、
     以及还没有引入时间片调度的老代码里。
     时间片任务里绝不能用——它会占着 CPU 不放，
     把整张任务表拖垮（第 3 节例 4 的硬约束）。                */
uint8_t Evt_Wait(evt_flags_t mask, uint32_t timeout_ms)
{
    uint32_t start = Sched_GetTick();

    for (;;) {
        if ((Evt_Peek() & mask) == mask) {
            return 1u;                                  /* 等到了 */
        }
        /* 无符号相减比较时间戳：回绕也正确，而且越界风险为零 */
        if ((uint32_t)(Sched_GetTick() - start) >= timeout_ms) {
            return 0u;                                  /* 超时 */
        }
    }
}
「等待」有两种写法，别用错场合

Evt_Wait() 是忙等：它在循环里不停地读标志位，直到等到或超时。在初始化阶段这样等一个外设就绪完全没问题（反正这时候也没别的事可做，而且它自带超时不会死等）。

但在时间片任务里，一旦你写了「等一个事件」，就等于放弃了对 CPU 的控制权——调度器没法把 CPU 抢回来，因为它只能在你的任务返回之后才轮到下一个任务。所以任务里的等待必须写成「查一次、没到就返回、下一拍再来查」的状态机形式（4.4 就是完整的例子）。

「谁清标志」：三条约定，选一条并写进注释

事件标志组所有难查的 bug，几乎都来自「清位时机没约定清楚」。三种写法各有适用场景：

写法谁清适合什么场景风险
消费者取出即清
（Evt_Take）		 处理事件的那个任务 最常见、最推荐：一件事只被一个地方处理 几乎无。前提是「取出后一定会处理」，中途 return 要小心
消费者按位清
（Evt_TakeMasked）		 管这一位的那一个任务 多个消费者各管一摊（通信任务管收帧、控制任务管故障） 某个位没人管就会一直亮着——加一个「常亮检测」能提前发现
显式清
（Evt_Clear）		 处理完成的最后一步 处理过程分多拍完成，中途不能丢事件 忘了清 = 事件永久触发；清早了 = 丢事件。最考验纪律性

另外还有一条绝对不能做的：不要由生产者（置位方）来清。生产者只知道「事情发生了」，它不知道消费者处理完没有；它一清，事件就凭空消失了——这类 bug 的表现是「偶尔少响应一次」，几乎无法通过读代码发现。

最后提醒一句：事件标志是「发生过」的记录，不是计数器。同一个位在没被清掉之前，被置 100 次也只算 1 次。如果你的语义是「来了 5 个报文，要处理 5 次」，那就该用队列（4.2），而不是标志位——这正是 2.5 讲「丢更新」时的那张时间线图想说明的事。

/* ---------- 生产者：中断里只置位 ---------- */
void HAL_GPIO_EXTI_Callback(uint16_t pin)
{
    if (pin == KEY_PIN) {
        Evt_Set(EVT_KEY_SHORT);      /* 一行搞定，耗时几十纳秒 */
    }
}

void Adc_ConvCpltHook(void)          /* DMA 转换完成 */
{
    Evt_Set(EVT_ADC_DONE);           /* 中断里绝不做处理，只通知 */
}

/* ---------- 消费者：一个 10 ms 任务，按优先级顺序处理 ---------- */
static void Task_Event(void)
{
    /* 一次性把关心的事件全部取走并清位（没置位的位不受影响） */
    evt_flags_t f = Evt_TakeMasked(EVT_FAULT_OC | EVT_CMD_SAVE |
                                   EVT_KEY_SHORT | EVT_KEY_LONG | EVT_ADC_DONE);

    /* 顺序就是优先级：故障永远排第一个 */
    if (f & EVT_FAULT_OC) {
        App_Fault_Handle();          /* 过流：立刻关 PWM，几微秒 */
    }
    if (f & EVT_CMD_SAVE) {
        App_Param_SaveStep();        /* 注意：这里只写「一页」，跨多拍完成。
                                        整片 flash 写完要 15 ms，
                                        一次做完会把节拍挤爆（第 3 节例 4） */
    }
    if (f & EVT_ADC_DONE) {
        App_Adc_Consume();
    }
    if (f & EVT_KEY_SHORT) {
        App_Key_ShortPress();
    }
    if (f & EVT_KEY_LONG) {
        App_Key_LongPress();
    }
}

4.4 非阻塞状态机任务：等按键 → 闪烁 → 超时退出

这是 2.6 那个例子的完整实现。需求很朴素：按一下按键，LED 开始闪 500 ms 亮 / 500 ms 灭，闪 6 次；如果 10 秒内没有新的按键，就退出、回到待机。用阻塞式写法，这段逻辑大概是五行的 HAL_Delay；写成非阻塞状态机，就是下面这一百行。

#include "app_blink.h"
#include "evt.h"
#include "sched.h"
#include "bsp_led.h"
#include "app_assert.h"

/* ---------- 状态定义：只有三个 ---------- */
typedef enum {
    BLINK_IDLE = 0,        /* 待机：等按键 */
    BLINK_ACTIVE,          /* 闪烁中：翻转 LED，同时看超时 */
    BLINK_DONE             /* 收尾：灭灯，然后回到 IDLE */
} blink_state_t;

/* ---------- 全部状态都是 static ----------
   这不是为了「省内存」，而是为了「状态独立」：
   外部想捣乱都没有入口，这个模块的行为只由它自己的几个静态变量决定。
   这也意味着：它可以在 PC 上被单独测试（4.7 会用到这一点）。 */
static blink_state_t s_state;
static uint32_t      s_state_enter_tick;    /* 进入当前状态的时刻 */
static uint32_t      s_toggle_tick;         /* 上一次「计划翻转」的时刻 */
static uint8_t       s_led_on;
static uint8_t       s_blink_count;         /* 已经灭了几次 */

#define BLINK_PERIOD_MS    500u             /* 亮/灭各 500 ms */
#define BLINK_MAX_COUNT    6u               /* 闪 6 次算一轮 */
#define BLINK_TIMEOUT_MS   10000u           /* 10 秒没有新按键就退出 */

/* 所有状态切换都走这一个函数：顺便记下「进入时刻」 */
static void Blink_Enter(blink_state_t st)
{
    s_state            = st;
    s_state_enter_tick = Sched_GetTick();
}

void App_Blink_Init(void)
{
    s_led_on      = 0u;
    s_blink_count = 0u;
    Blink_Enter(BLINK_IDLE);
    Bsp_Led_Off(BSP_LED_RUN);
}

/* ---------------- 任务函数：由 1 ms 或 10 ms 的时间片任务调用 ----------------
   两条硬性保证：① 一定会返回；② 每次耗时就几微秒。
   注意它没有参数、没有返回值，状态全在 static 变量里。 */
void App_Blink_Task(void)
{
    uint32_t now = Sched_GetTick();

    switch (s_state) {

    /* ---------- 待机：等按键 ---------- */
    case BLINK_IDLE:
        /* 「等按键」不等于停下来等，而是每拍问一句「按了吗」 */
        if (Evt_Check(EVT_KEY_SHORT) != 0u) {
            Evt_Clear(EVT_KEY_SHORT);        /* 是我消费了它，就由我来清 */
            s_blink_count = 0u;
            Blink_Enter(BLINK_ACTIVE);
            /* 进入状态时立刻动作，不要等到下一拍——否则每次都有 1 拍延迟 */
            Bsp_Led_On(BSP_LED_RUN);
            s_led_on    = 1u;
            s_toggle_tick = now;
        }
        break;

    /* ---------- 闪烁中：翻转 + 三个退出条件 ---------- */
    case BLINK_ACTIVE:
        /* 1) 到点了吗？用时间戳比大小，而不是 delay */
        if ((uint32_t)(now - s_toggle_tick) >= BLINK_PERIOD_MS) {
            /* 累加「计划时刻」而不是直接 = now：
               否则每一拍的实际间隔都会多出「本次调用被延迟的时间」，
               长期累积就漂成了 520 ms、530 ms…… */
            s_toggle_tick += BLINK_PERIOD_MS;

            s_led_on = (uint8_t)((s_led_on == 0u) ? 1u : 0u);
            if (s_led_on != 0u) {
                Bsp_Led_On(BSP_LED_RUN);
            } else {
                Bsp_Led_Off(BSP_LED_RUN);
                s_blink_count++;             /* 灭一次算闪一下 */
            }
        }

        /* 2) 闪够了？ */
        if (s_blink_count >= BLINK_MAX_COUNT) {
            Blink_Enter(BLINK_DONE);
            break;
        }

        /* 3) 超时了？用「进入本状态的时刻」判断，不需要另开计时器 */
        if ((uint32_t)(now - s_state_enter_tick) >= BLINK_TIMEOUT_MS) {
            Blink_Enter(BLINK_DONE);
        }
        break;

    /* ---------- 收尾：只做一次，然后回待机 ---------- */
    case BLINK_DONE:
        Bsp_Led_Off(BSP_LED_RUN);
        s_led_on = 0u;
        Blink_Enter(BLINK_IDLE);             /* 本拍立刻回待机，下一拍就能响应新按键 */
        break;

    /* ---------- 兜底：状态变量被写坏了 ---------- */
    default:
        APP_ASSERT(0);                       /* 参数 / 状态非法，开发期就该停下来看 */
        Blink_Enter(BLINK_IDLE);             /* 生产版本：自愈回一个已知状态 */
        break;
    }
}

void App_Blink_Blocking(void)

写非阻塞状态机的五条实操规则

① 每次调用必须返回。出现 while (1)、HAL_Delay、阻塞发送、忙等标志位，都是违规。

② 状态与时间戳都放 static。不要用「函数里的局部变量 + 上电顺序」来记录状态，那样它就没法被单独测试，也没法被重入。

③ 时间比较用「无符号相减」。(uint32_t)(now - start) >= timeout，不要写 now > start + timeout——后者在 now 回绕时会失效（49.7 天一次，但一定会发生在你的客户那里）。

④ 定时用「计划时刻累加」，并且防一手迟到。如果发现已经晚了整整一个周期以上，说明中间漏拍了，这时直接对齐 = now，避免「补跑」出一串动作。

⑤ 每个 switch 都要有 default 加断言。状态机跑进非法状态，通常是别的 bug（栈溢出、指针越界）的症状，断言能让你在第一时间发现它。

/* 累加计划时刻，但要防止「补跑」 */
if ((uint32_t)(now - s_toggle_tick) >= (BLINK_PERIOD_MS * 2u)) {
    /* 已经晚了一个周期以上：中间漏拍了（被别的事情挡住）。
       这时候如果还累加，就会连续翻转好几次去「追账」，
       看起来就是「LED 抽风一样乱闪」。直接对齐才是对的。 */
    s_toggle_tick = now;
} else {
    s_toggle_tick += BLINK_PERIOD_MS;    /* 正常情况：累加，保持平均周期精确 */
}

4.5 分层驱动：一个按键驱动应该长什么样

/* 按键用「名字」寻址，不用「引脚号」。

数一数这个头文件里没有的东西

没有 GPIO_TypeDef、没有 GPIO_PIN_0、没有 stm32f1xx_hal.h、没有一个全局变量、没有「当前按到第几个键」的状态。它只说了三件事：有哪些键、会产生哪些事件、你可以调哪五个函数。

这不是形式主义。它带来的实际好处是：换芯片（F1 → F4 → G0）只改 bsp_key.c；换按键接法只改 bsp_key.c；在 PC 上测试应用层时，你可以写一个假的 bsp_key.c 直接喂事件进去，一行硬件代码都不用碰。

#include "bsp_key.h"
#include "sched.h"
#include "stm32f1xx_hal.h"

/* ---------------- 可调参数：全在这里，改行为不用翻代码 ---------------- */
#define KEY_DEBOUNCE_MS   20u     /* 消抖时间：电平要稳定这么久才算数 */
#define KEY_LONG_MS       1000u   /* 长按阈值 */
#define KEY_REPEAT_MS     100u    /* 长按连发周期 */
#define KEY_EVENT_QUEUE   8u      /* 事件队列深度（2 的幂） */

/* ---------------- 每个按键的上下文 ----------------
   这张表是驱动的「私有财产」：它出现在 .c 里，头文件看不见。 */
typedef struct {
    GPIO_TypeDef *port;             /* HAL 的类型只出现在这个文件里 */
    uint16_t      pin;
    uint8_t       stable;           /* 消抖之后的稳定电平：0 = 按下（上拉输入） */
    uint8_t       last_raw;         /* 上一次的原始采样 */
    uint32_t      raw_change_tick;  /* 原始电平最后一次变化的时刻 */
    uint32_t      press_tick;       /* 消抖后确认「按下」的时刻 */
    uint8_t       long_reported;    /* 长按事件是否已经报过 */
    uint32_t      repeat_tick;      /* 上一次连发上报的时刻 */
} key_ctx_t;

/* ---------------- 全部是 static：外部一个都访问不到 ---------------- */
static key_ctx_t s_keys[BSP_KEY_COUNT] = {
    { GPIOA, GPIO_PIN_0, 1u, 1u, 0u, 0u, 0u, 0u },   /* UP    : PA0 */
    { GPIOB, GPIO_PIN_1, 1u, 1u, 0u, 0u, 0u, 0u },   /* DOWN  : PB1 */
    { GPIOB, GPIO_PIN_2, 1u, 1u, 0u, 0u, 0u, 0u },   /* ENTER : PB2 */
};

static bsp_key_event_t s_events[KEY_EVENT_QUEUE];
static uint8_t         s_ev_head;                 /* 只在本文件的任务上下文里改 */
static uint8_t         s_ev_tail;
static void          (*s_callback)(const bsp_key_event_t *ev);   /* 可以为空 */

bsp_status_t Bsp_Key_Init(void)
{
    GPIO_InitTypeDef gpio = {0};
    uint8_t i;

    __HAL_RCC_GPIOA_CLK_ENABLE();
    __HAL_RCC_GPIOB_CLK_ENABLE();

    gpio.Mode  = GPIO_MODE_INPUT;
    gpio.Pull  = GPIO_PULLUP;                    /* 上拉：按下接地，读到低电平 */
    gpio.Speed = GPIO_SPEED_FREQ_LOW;            /* 按键不需要高速 */

    for (i = 0u; i < BSP_KEY_COUNT; i++) {
        gpio.Pin = s_keys[i].pin;
        HAL_GPIO_Init(s_keys[i].port, &gpio);

        s_keys[i].stable           = 1u;         /* 上电默认是「没按下」 */
        s_keys[i].last_raw         = 1u;
        s_keys[i].raw_change_tick  = Sched_GetTick();
        s_keys[i].press_tick       = 0u;
        s_keys[i].long_reported    = 0u;
        s_keys[i].repeat_tick      = 0u;
    }

    s_ev_head  = 0u;
    s_ev_tail  = 0u;
    s_callback = 0;

    return BSP_OK;
}

/* ---------------- 内部：产生一个事件 ----------------
   既推进内部队列，也顺手通知回调（如果有人注册）。
   注意这个函数运行在「任务上下文」（Bsp_Key_Poll 由 10 ms 任务调用），
   所以它不需要临界区——这也是把扫描放在任务里、而不是中断里的好处之一。 */
static void Key_Post(bsp_key_id_t id, bsp_key_event_type_t type, uint32_t tick)
{
    bsp_key_event_t ev;
    uint8_t         next;

    ev.id   = id;
    ev.type = type;
    ev.tick = tick;

    next = (uint8_t)((s_ev_head + 1u) % KEY_EVENT_QUEUE);
    if (next != s_ev_tail) {                 /* 队列没满才放，满了就丢（并保持仅记一次） */
        s_events[s_ev_head] = ev;
        s_ev_head = next;
    }
    if (s_callback != 0) {
        s_callback(&ev);
    }
}

/* ---------------- 对外：扫描 ----------------
   每 10 ms 调用一次，对 3 个按键各做一次采样，最坏耗时约 30 µs。
   全程没有阻塞、没有 delay，因为它要在一个时间片任务里跑。 */
void Bsp_Key_Poll(void)
{
    uint32_t now = Sched_GetTick();
    uint8_t  i;

    for (i = 0u; i < BSP_KEY_COUNT; i++) {
        key_ctx_t *k = &s_keys[i];
        uint8_t    raw;

        /* 读一次引脚。HAL_GPIO_ReadPin 返回 GPIO_PinState：
           GPIO_PIN_RESET = 低电平 = 按下；GPIO_PIN_SET = 高电平 = 没按 */
        raw = (HAL_GPIO_ReadPin(k->port, k->pin) == GPIO_PIN_RESET) ? 0u : 1u;

        if (raw != k->last_raw) {
            /* 原始电平刚变化：重新开始消抖计时，本拍不下结论 */
            k->last_raw        = raw;
            k->raw_change_tick = now;
        } else if (raw != k->stable) {
            /* 电平没变、且和稳定值不同：检查它稳定够久了吗 */
            if ((uint32_t)(now - k->raw_change_tick) >= KEY_DEBOUNCE_MS) {
                k->stable = raw;             /* 确认变化，更新稳定值 */

                if (raw == 0u) {             /* 边沿：按下 */
                    k->press_tick    = now;
                    k->long_reported = 0u;
                    k->repeat_tick   = now;
                    Key_Post((bsp_key_id_t)i, BSP_KEY_EVENT_DOWN, now);
                } else {                     /* 边沿：抬起 */
                    uint32_t held = (uint32_t)(now - k->press_tick);

                    Key_Post((bsp_key_id_t)i, BSP_KEY_EVENT_UP, now);
                    /* 只有「按住时间没到长按阈值」才算短按。
                       长按已经报过的，抬起时不再报短按。 */
                    if (held < KEY_LONG_MS && k->long_reported == 0u) {
                        Key_Post((bsp_key_id_t)i, BSP_KEY_EVENT_SHORT, now);
                    }
                }
            }
        }

        /* 长按判定：只要稳定值是「按下」，每拍都检查一次 */
        if (k->stable == 0u) {
            uint32_t held = (uint32_t)(now - k->press_tick);

            if (held >= KEY_LONG_MS) {
                if (k->long_reported == 0u) {
                    k->long_reported = 1u;   /* 长按只报一次 */
                    k->repeat_tick   = now;
                    Key_Post((bsp_key_id_t)i, BSP_KEY_EVENT_LONG, now);
                } else if ((uint32_t)(now - k->repeat_tick) >= KEY_REPEAT_MS) {
                    k->repeat_tick += KEY_REPEAT_MS;   /* 累加计划时刻：连发节奏不漂移 */
                    Key_Post((bsp_key_id_t)i, BSP_KEY_EVENT_REPEAT, now);
                }
            }
        }
    }
}

/* ---------------- 对外：拉取一个事件 ---------------- */
uint8_t Bsp_Key_GetEvent(bsp_key_event_t *out)
{
    if (out == 0) {
        return 0u;
    }
    if (s_ev_head == s_ev_tail) {
        return 0u;                            /* 空：立刻返回，绝不等待 */
    }
    *out      = s_events[s_ev_tail];
    s_ev_tail = (uint8_t)((s_ev_tail + 1u) % KEY_EVENT_QUEUE);
    return 1u;
}

bsp_status_t Bsp_Key_IsPressed(bsp_key_id_t id, uint8_t *out)
{
    if (id >= BSP_KEY_COUNT || out == 0) {
        return BSP_ERR_PARAM;                 /* 参数检查是驱动的义务，不是调用者的 */
    }
    *out = (uint8_t)((s_keys[id].stable == 0u) ? 1u : 0u);
    return BSP_OK;
}

bsp_status_t Bsp_Key_SetCallback(void (*cb)(const bsp_key_event_t *ev))
{
    s_callback = cb;                          /* 传 NULL 就是取消注册 */
    return BSP_OK;
}
回调与队列，二选一，别同时用

这个驱动同时提供了两种交付方式，是为了适应两种应用写法：回调适合「事件来了就立刻做一件小事」（比如闪一下指示灯）；队列适合「我想按自己的节奏、按自己的顺序处理」（比如按键要排队等状态机空闲）。

但如果两个都用（既注册回调，又在任务里 while (Bsp_Key_GetEvent(...))），同一个事件会被处理两次——短按一次、长按两次，这种 bug 特别好查（数事件次数就发现了），但也特别容易写出来。建议：驱动里保留两种，项目里只选一种，并在 Bsp_Key_Init 的注释里写清楚选了哪个。

应用层拿到事件之后做什么，是应用层自己的事。驱动只保证「事件是消抖过的、带时间戳的、不用等的」：

#include "app_key.h"
#include "bsp_key.h"
#include "evt.h"

/* 方式一：回调（事件一到就转成事件标志，交给事件任务统一处理）
   这是最推荐的组合：驱动回调只做「转发」，真正的处理集中在 4.3 的
   Task_Event 里，按优先级顺序执行，不会插队到关键任务前面。 */
static void OnKeyEvent(const bsp_key_event_t *ev)
{
    switch (ev->type) {
    case BSP_KEY_EVENT_SHORT:  Evt_Set(EVT_KEY_SHORT);  break;
    case BSP_KEY_EVENT_LONG:   Evt_Set(EVT_KEY_LONG);   break;
    default:                                            break;   /* 其他事件不需要 */
    }
}

void App_Key_Init(void)
{

       两者之间只通过「事件标志」通信，谁也不知道谁的存在。 */
}

4.6 把同一个应用从前后台重构成时间片轮询

前面五节都是零件。这一节把它们装到同一台机器上：一个温控风扇——NTC 测温（ADC）、PWM 调速、按键设目标温度、数码管显示、串口上报。需求是 2.4 那张任务表的来源，我们先把它写成最典型的「前后台系统」，再一步步改成时间片轮询。

/* ================= 改前：main.c ================= */

/* 全局变量：任何文件都能改，改的时候没有任何人知道 */
float             g_temp_c;                 /* 当前温度 */
float             g_target_c = 30.0f;       /* 目标温度 */
uint8_t           g_fan_duty;               /* 风扇占空比 0~100 */
char              g_disp[5];

volatile uint8_t  g_key_pressed;            /* 中断置位，主循环清零 */
volatile uint8_t  g_new_frame;              /* 收到一整帧命令了吗 */
volatile uint8_t  g_rx_buf[64];             /* 中断往里写，主循环拿来解析 */

int main(void)
{
    HAL_Init();
    SystemClock_Config();
    MX_GPIO_Init(); MX_ADC1_Init(); MX_TIM1_Init(); MX_USART1_UART_Init();

    Adc_Init(); Seg_Init(); Uart_Init(); Fan_Init();
    HAL_UART_Receive_IT(&huart1, (uint8_t *)&g_rx_buf[0], 1u);   /* 单字节接收 */

    while (1) {
        /* ---- 1) 采一次温度 ---- */
        g_temp_c = Adc_ToTemp(Adc_ReadOnce());   /* 阻塞等 ADC 转换完成 */
        HAL_Delay(100);                          /* ← 死穴①：整轮先固定停 100 ms */

        /* ---- 2) 控温 ---- */
        if (g_temp_c > g_target_c + 0.5f) {
            g_fan_duty = 100u;
        } else if (g_temp_c < g_target_c - 0.5f) {
            g_fan_duty = 0u;
        }
        Fan_SetDuty(g_fan_duty);                 /* ← 死穴②：控制周期靠「刚才那个 delay」脑补 */

        /* ---- 3) 刷数码管：整屏扫完 2 ms ---- */
        Seg_Display(g_temp_c, g_target_c);       /* ← 死穴③：这 2 ms 里谁来都不理 */

        /* ---- 4) 串口上报：阻塞发送 40 字节 ≈ 3.5 ms ---- */
        Uart_Printf("T=%.1f,D=%u\r\n", g_temp_c, g_fan_duty);   /* ← 死穴①：又堵一次 */

        /* ---- 5) 按键：改目标温度 ---- */
        if (g_key_pressed != 0u) {
            g_key_pressed = 0u;
            g_target_c += 1.0f;                  /* ← 死穴②：改了它，g_disp 里的字符串就过期了 */
            if (g_target_c > 60.0f) { g_target_c = 60.0f; }
        }

        /* ---- 6) 串口命令：解析 ---- */
        if (g_new_frame != 0u) {
            g_new_frame = 0u;
            ParseFrame((const uint8_t *)g_rx_buf);   /* ← 死穴⑤：解析到一半，中断把缓冲改了 */
        }

        /* ---- 7) 7 段码刷新率跟着上面的总时长走 ---- */
        /* ← 死穴④：想让「按键」优先于「上报」？没有优先级这个东西可以调 */
    }
}

void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
{
    static uint8_t n = 0u;

    if (n < 64u) { g_rx_buf[n++] = (uint8_t)(huart->Instance->DR); }
    if (n >= 64u) { n = 0u; g_new_frame = 1u; }

       中断从第 0 字节开始覆盖 → 解析出一个「半新半旧」的帧，

这段代码能跑，而且在实验室的桌上跑得很好——因为桌上没有「恰好在你解析到第 20 个字节时来一帧新命令」的运气问题。下面把它拆开重装。

/* ================= 改后：main.c =================
   同样的功能，同样的外设，一行硬件操作都没变。
   变的只有「谁在什么时候做什么」的组织方式。 */

int main(void)
{
    HAL_Init();
    SystemClock_Config();
    MX_GPIO_Init(); MX_ADC1_Init(); MX_TIM1_Init(); MX_USART1_UART_Init();

    /* ---------- 中间件层 ---------- */
    Sched_Init();
    Evt_Init();
    Ring_Init(&g_rx, g_rx_buf, sizeof(g_rx_buf));   /* g_rx_buf 现在只属于这一层 */

    /* ---------- 驱动层：每个初始化都要检查返回码 ---------- */
    if (Bsp_Key_Init()  != BSP_OK) { Bsp_Fatal("KEY");  }
    if (Bsp_Led_Init()  != BSP_OK) { Bsp_Fatal("LED");  }
    if (Bsp_Uart_Init() != BSP_OK) { Bsp_Fatal("UART"); }  /* 内部武装接收中断 */
    if (Bsp_Adc_Init()  != BSP_OK) { Bsp_Fatal("ADC");  }
    if (Bsp_Seg_Init()  != BSP_OK) { Bsp_Fatal("SEG");  }
    if (Bsp_Fan_Init()  != BSP_OK) { Bsp_Fatal("FAN");  }

    /* ---------- 应用层：只调自己的 Init，不碰 HAL ---------- */
    App_Fan_Init();      /* 温控状态机 */
    App_Blink_Init();    /* 4.4 的 LED 状态机 */
    App_Key_Init();      /* 注册回调：按键事件 → 事件标志 */

    /* ---------- 任务表：周期 + 相位 ----------
       相位来自 2.4 的错峰安排：把「爱撞车」的任务在时间上拉开，
       最坏一拍从 104.5% 降到 57.5%。 */
    Sched_Add(Task_Ctrl,   "Ctrl_Loop",    1u,  0u);
    Sched_Add(Task_Seg,    "Seg_Scan",     2u,  0u);
    Sched_Add(Task_Cmd,    "Cmd_Parse",    5u,  0u);
    Sched_Add(Task_Key,    "Key_Scan",    10u,  0u);
    Sched_Add(Task_Adc,    "Adc_Sample",  10u,  3u);   /* +3 ms：与 Key 错开 */
    Sched_Add(Task_Fan,    "Fan_Update", 100u,  0u);
    Sched_Add(Task_Report, "Uart_Report",100u,  7u);   /* +7 ms：与 Fan 错开 */
    Sched_Add(Task_Led,    "Led_Heart",  500u,  0u);

    LOG_I("MAIN", "sched start, tasks=%u", Sched_GetTaskCount());

    Sched_Run();     /* 调度循环，永不返回 */
}

/* ---------------- 任务们：每个都「只做一件事的当前一步」 ---------------- */

/* 1 ms：控制环。绝不在这里做 IO，只从「最近一次采样」里取值 */
static void Task_Ctrl(void)
{
    float    t;
    uint32_t now = Sched_GetTick();

    if (Adc_GetTemp(&t) != BSP_OK) {
        return;                          /* 采样还没好：干净地返回，下一拍再来 */
    }
    App_Fan_Update(t, now);              /* 滞环 + 软启动 + 状态机，全是计算，几十微秒 */
}

/* 2 ms：数码管扫描。一次只扫一位，2 ms 一轮刚好 4 位 8 ms 刷新 */
static void Task_Seg(void)
{
    Bsp_Seg_ScanStep();                  /* 驱动内部记住「下一位是第几位」 */
}

/* 5 ms：解析串口命令。数据来自环形缓冲，不再碰中断的变量 */
static void Task_Cmd(void)
{
    uint8_t chunk[32];
    int16_t n;

    Bsp_Uart_Poll();                                  /* 把收到的字节搬进环形缓冲 */
    while ((n = Ring_Get(&g_rx, chunk, sizeof(chunk))) > 0) {
        Proto_Parse(chunk, (uint8_t)n);               /* 协议解析器自己维护组帧状态 */
    }
}

/* 10 ms：按键扫描 + 事件分发 */
static void Task_Key(void)
{
    bsp_key_event_t ev;

    Bsp_Key_Poll();
    while (Bsp_Key_GetEvent(&ev) != 0u) {
        App_OnKeyEvent(&ev);
    }
}

/* 10 ms（相位 +3）：采一次 ADC。启动转换就返回，结果下一拍取 */
static void Task_Adc(void)
{
    Bsp_Adc_StartOnce();                 /* 定时器触发也行，这里用软件触发便于理解 */
}

/* 100 ms：温控状态机的「慢路径」：写 flash、算统计 */
static void Task_Fan(void)
{
    App_Fan_SlowPath(Sched_GetTick());   /* 参数保存按「一次一页」分步写，不阻塞 15 ms */
}

/* 100 ms（相位 +7）：串口上报。用非阻塞发送，发不完就等下一拍 */
static void Task_Report(void)
{
    static char line[80];

    (void)snprintf(line, sizeof(line), "T=%.1f,D=%u,K=%lu\r\n",
                   (double)App_Fan_GetTemp(), (unsigned)App_Fan_GetDuty(),
                   (unsigned long)Bsp_Uart_GetDropCount());   /* 丢字节数一定要报出来 */
    Bsp_Uart_SendAsync(line, (uint16_t)strlen(line));
}

/* 500 ms：心跳灯 */
static void Task_Led(void)
{
    Bsp_Led_Toggle(BSP_LED_HEART);
}

逐条对账：改前的六个死穴，在改后分别被哪一处消掉了。

改前的死穴（第 2.2 节）改前长什么样改后怎么解
① 一个环节阻塞拖垮全部HAL_Delay(100) 与阻塞发送 3.5 ms 一起把整轮撑到 108 ms所有等待改成「时间戳比较 + 下一拍再来」；发送改 Bsp_Uart_SendAsync()（中断/DMA 自己发完）
② 全局变量耦合，改一处崩三处g_temp_c/g_target_c/g_disp 谁都能改状态全部收进各自模块的 static；跨模块只走函数、事件标志、队列三种通道
③ 实时性取决于最慢的任务整轮 108 ms，按键最坏 324 ms（例 3）每个任务独立周期：控制环 1 ms、按键 10 ms，最坏响应 31 ms
④ 无法区分优先级想「按键优先于上报」没有旋钮可调任务表加 level（或按调用顺序）分两级；真要抢占就得上 RTOS（2.8）
⑤ 栈与资源共享靠自觉g_rx_buf 被中断和主循环同时读写生产者只写环形缓冲、消费者只读；volatile 指针 + 单生产者/单消费者约定，不关中断也安全
⑥ 无法单独测一个功能测按键要跑整块板硬件访问集中到 bsp_*；应用层用 app_io_t 注入桩函数，在 PC 上跑（4.7）

最后算一笔总账。同一块板子、同一套外设，重构前后：

指标改前（前后台）改后（时间片轮询）怎么来的
按键最坏响应324 ms ❌31 ms ✅（需求 50 ms）第 3 节例 3
平均 CPU 占用约 6%（大部分时间在空转 delay）13.65%（真干活）Σ(Ci/Ti)，2.4 的任务表

新增一个功能在 while (1) 里插一段，还要重算全局时序写一个任务函数 + 一行 Sched_Add()——
重构的顺序，别反过来

不要一上来就写调度器。按这个顺序走，每一步都能单独验证：① 先消灭所有 HAL_Delay 和阻塞等待（这一步不改结构，只改写法，收益最大）；② 再把硬件访问收进 bsp_*（此时应用层已经能看懂）；③ 然后把 while (1) 里的大段代码切成任务函数（一次切一个，切完就测）；④ 最后才引入任务表和 Sched_Add()。反过来做（先上调度器）会同时引入「结构变化」和「逻辑变化」两类 bug，调试成本翻几倍。

/* ============ PC 上测试 app_blink.c（4.4 那段状态机）============

#include <assert.h>
#include <stdio.h>
#include <string.h>

#include "../app/app_blink.c"          /* 直接编进来：它没有硬件依赖，编得过 */

uint32_t g_stub_tick;
int      g_stub_led[BSP_LED_COUNT];

/* 一次一毫秒地推进：这就是板子上 1 ms 任务在做的事 */

/* ---------- 用例 1：没人按键，待机 10 秒，灯始终不亮 ---------- */
static void Test_IdleNoBlink(void)
{

    App_Blink_Init();

    assert(LED_RUN == 0);              /* 灯没亮过 */

}

/* ---------- 用例 2：短按 → 立刻点亮（进入状态时就动作） ---------- */
static void Test_ShortPressStartsImmediately(void)
{
    g_stub_tick = 0u; LED_RUN = 0;
    App_Blink_Init();
    Evt_Set(EVT_KEY_SHORT);

    App_Blink_Task();                  /* 只跑一拍！ */
    assert(LED_RUN == 1);              /* 必须在这一拍就亮 */

}

/* ---------- 用例 3：翻转时刻严格落在 500/1000/1500… 拍上 ---------- */
static void Test_ToggleEdges(void)
{
    uint32_t edge[6];
    uint8_t  k = 0u;
    uint32_t i;
    int      last = 0;

    g_stub_tick = 0u; LED_RUN = 0;
    App_Blink_Init();
    Evt_Set(EVT_KEY_SHORT);

    for (i = 0u; i < 7000u && k < 6u; i++) {
        App_Blink_Task();
        if (LED_RUN != last) {         /* 抓到一次翻转 */
            edge[k++] = g_stub_tick;
            last = LED_RUN;
        }
        g_stub_tick++;
    }

    assert(k == 6u);
    /* 累加计划时刻的意义：误差不会累积，第 6 次翻转仍在第 3000 拍附近 */
    assert(edge[0] == 0u);             /* 进入状态时点亮 */
    assert(edge[1] == 500u);
    assert(edge[2] == 1000u);
    assert(edge[3] == 1500u);
    assert(edge[4] == 2000u);
    assert(edge[5] == 2500u);
    printf("  [OK] 用例 3：翻转时刻 = 0/500/1000/1500/2000/2500\n");
}

/* ---------- 用例 4：闪够 6 次 → 回待机；再按还能重新开始 ---------- */
static void Test_FinishAndRestart(void)
{
    g_stub_tick = 0u; LED_RUN = 0;
    App_Blink_Init();
    Evt_Set(EVT_KEY_SHORT);
    RunTicks(4000u);                   /* 6 次闪完（约 3000 拍）再多跑一会儿 */

    assert(LED_RUN == 0);              /* 已经灭灯回待机 */

    Evt_Set(EVT_KEY_SHORT);            /* 再来一次 */
    App_Blink_Task();
    assert(LED_RUN == 1);              /* 能重新开始，说明状态确实回到了 IDLE */
    printf("  [OK] 用例 4：结束后可重新触发\n");
}

/* ---------- 用例 5：闪烁中途 10 秒超时，且退出时刻精确 ---------- */
static void Test_Timeout(void)
{
    uint32_t exit_tick = 0u;
    uint32_t i;

    g_stub_tick = 0u; LED_RUN = 0;
    App_Blink_Init();
    Evt_Set(EVT_KEY_SHORT);

    /* 一直按住 SHORT 标志不放（模拟「每秒都有人按」），
       这样「闪够 6 次」这个条件不会先到（每 500 ms 会重新数吗？
       不会——BLINK_ACTIVE 里只在退出时才回 IDLE，所以重复的 SHORT 不影响本轮），
       于是只有超时能结束它。 */
    for (i = 0u; i < 20000u; i++) {
        Evt_Set(EVT_KEY_SHORT);        /* 每拍都置位，验证它不会打断本轮 */
        App_Blink_Task();
        g_stub_tick++;
        /* 超时后 LED 灭、状态回 IDLE：这里用「灭灯且之后不再亮」粗判 */
        if (i > 3000u && LED_RUN == 0) { exit_tick = g_stub_tick; break; }
    }
    (void)exit_tick;
    assert(g_stub_tick < 20000u);      /* 一定会退出，不会卡在 ACTIVE 里 */
    printf("  [OK] 用例 5：超时能退出（第 %lu 拍）\n", (unsigned long)g_stub_tick);
}

/* ---------- 用例 6：tick 回绕（板子上极难复现，PC 上一行） ---------- */
static void Test_TickWrap(void)
{
    g_stub_tick = 0xFFFFF000u;         /* 距回绕还有 4096 拍 */
    LED_RUN = 0;
    App_Blink_Init();
    Evt_Set(EVT_KEY_SHORT);
    RunTicks(4000u);                   /* 期间 g_stub_tick 会跨过 0xFFFFFFFF → 0 */

    /* 只要比较用的是 (uint32_t)(now - start) >= timeout，
       回绕就完全不产生影响：该闪还是照常闪。 */
    assert(g_stub_tick == 0x00000000u + 4000u - 4096u);
    printf("  [OK] 用例 6：tick 回绕过 0 后时序正常\n");
}

/* ---------- 用例 7：打桩造故障——事件永远不来 ---------- */
static void Test_EventLost(void)
{
    g_stub_tick = 0u; LED_RUN = 0;
    App_Blink_Init();
    /* 故意不置任何事件：状态机必须老老实实待在 IDLE，不能乱动 */
    RunTicks(5000u);
    assert(LED_RUN == 0);
    assert(g_stub_tick == 5000u);      /* 也没有死循环 */
    printf("  [OK] 用例 7：事件丢失时保持待机\n");
}

}
用例 6 才是「在 PC 上测」最值钱的地方

回绕、丢事件、队列刚好满、任务刚好迟到一整拍、超时刚好卡在边界——这些场景在板子上要么等着撞运气，要么根本造不出来。在 PC 上，它们是一行赋值。所以别把「PC 上只能测纯算法」当上限：只要状态机的输入全部来自函数调用（Evt_Check、Sched_GetTick），它的全部时序就都可以被脚本化地构造出来。

中间件层同样直接测。环形缓冲的边界最容易出错，而它又最不该出错：

#include <assert.h>
#include <stdio.h>
#include "../middleware/ringbuf.c"

static void Test_EmptyAndFull(void)
{
    uint8_t   mem[8];                  /* 2 的幂；有效容量 = 8 - 1 = 7 */
    ringbuf_t r;
    uint8_t   tmp[8];

    Ring_Init(&r, mem, sizeof(mem));

    /* 空：读不出来东西，且不改变任何状态 */
    assert(Ring_Used(&r) == 0);
    assert(Ring_Free(&r) == 7);
    assert(Ring_Get(&r, tmp, sizeof(tmp)) == 0);

    /* 写 7 个：刚好满 */
    assert(Ring_Put(&r, (const uint8_t *)"abcdefg", 7) == 7);
    assert(Ring_Used(&r) == 7);
    assert(Ring_Free(&r) == 0);

    /* 再写：一个都进不去，丢弃计数要加上 */
    assert(Ring_Put(&r, (const uint8_t *)"xy", 2) == 0);
    assert(r.drop_cnt == 2);           /* 丢了几个必须记下来 */

    /* 一次读出全部 7 个，顺序不能乱 */
    assert(Ring_Get(&r, tmp, 7) == 7);
    assert(memcmp(tmp, "abcdefg", 7) == 0);
    assert(Ring_Used(&r) == 0);
    printf("  [OK] 空/满/丢弃计数\n");
}

static void Test_WrapAround(void)
{
    uint8_t   mem[8];
    ringbuf_t r;
    uint8_t   tmp[8];

    Ring_Init(&r, mem, sizeof(mem));

    /* 反复「写 3 读 3」，让 head/tail 绕回来好几圈，
       这个用例专门抓「取模写成减法忘记 & mask」的错误。 */
    for (int round = 0; round < 20; round++) {
        assert(Ring_Put(&r, (const uint8_t *)"abc", 3) == 3);
        assert(Ring_Get(&r, tmp, 3) == 3);
        assert(memcmp(tmp, "abc", 3) == 0);
    }
    assert(Ring_Used(&r) == 0);
    printf("  [OK] 回绕 20 轮后仍正确\n");
}

/* 模拟 4.2 的「中断生产、主循环消费」：单生产者单消费者，
   不需要关中断也应该永远不丢、不重复、不乱序。 */
static void Test_ProducerConsumer(void)
{
    uint8_t   mem[64];
    ringbuf_t r;
    uint8_t   got[64];
    uint32_t  produced = 0u, consumed = 0u;

    Ring_Init(&r, mem, sizeof(mem));

    for (int step = 0; step < 1000; step++) {
        uint8_t one = (uint8_t)(produced & 0xFFu);      /* 每字节内容不同，便于查乱序 */

        /* 生产者：模拟中断，一次一个字节 */
        if (Ring_Put(&r, &one, 1) == 1) { produced++; }

        /* 消费者：模拟主循环，有时候一次多取几个 */
        if ((step % 3) == 0) {
            int16_t n = Ring_Get(&r, got, sizeof(got));
            for (int16_t i = 0; i < n; i++) {
                assert(got[i] == (uint8_t)(consumed & 0xFFu));   /* 顺序必须一致 */
                consumed++;
            }
        }
    }
    printf("  [OK] 生产 %lu / 消费 %lu / 丢弃 %lu（一致且有序）\n",
           (unsigned long)produced, (unsigned long)consumed, (unsigned long)r.drop_cnt);
}

int main(void)
{
    printf("test_ringbuf:\n");
    Test_EmptyAndFull();
    Test_WrapAround();
    Test_ProducerConsumer();
    printf("all passed\n");
    return 0;
}

常见误解与坑

下面十条，全部是「听起来很对」的说法。每一条都按「错误认知 → 为什么错 → 正确做法」拆开讲，你可以拿它们去对照自己手上的工程。

误解 1：「中断要尽量短，所以主循环慢一点没关系。」

为什么错：中断短是对的，但它只保证「事件不会被漏掉」，不保证「事件被及时处理」。按键的中断可能只花 2 µs，可它的响应时间取决于主循环什么时候转到那一段——3.2 节那个例子里，主循环一轮 108 ms，按键最坏要 324 ms 才被处理。前半句做得再好，也救不了后半句。

正确做法：把「中断耗时」和「主循环轮询周期」当成同一个指标的两个分量，一起算。中断负责记下事件（置标志位、推队列），主循环负责在可接受的周期内处理它；这两个周期都要写进需求，都要能算出来。

误解 2：「加个 SysTick，把 HAL_Delay 换成计数器，就等于上了 RTOS。」

为什么错：时间片轮询解决的是「按周期准时调用」，它没有解决 RTOS 解决的那三件事：抢占（高优先级任务能打断低优先级任务）、独立栈（每个任务有自己的调用栈，可以放心写递归和局部大数组）、阻塞（任务可以「等一个队列，等到再醒」而不占用 CPU）。所以时间片轮询里的任务必须自己保证快速返回，而 RTOS 里的任务可以直接写 xQueueReceive(..., portMAX_DELAY) 然后睡过去。

正确做法：把时间片轮询当成架构演进的第一站，不是终点。它能让你的代码结构变成「任务 + 通信」，这一步做完，将来换 RTOS 时业务逻辑几乎不用改（2.8 的四步迁移路径）。判断该不该继续往上走，看有没有出现「必须阻塞等待」的需求。

误解 3：「共享变量加了 volatile 就安全了。」

为什么错：volatile 只保证「每次都去内存里读，不缓存进寄存器」，它不保证原子性，也不保证顺序。一个 16 位变量在 8 位机上、一个结构体在任何机器上，读一半就被中断改写，得到的就是「半新半旧」的数据。更隐蔽的是 count++：它在机器码层面是「读—改—写」三条指令，主循环和中断同时做，就会丢一次计数。

正确做法：按「谁写、谁读」分三种情况处理：① 单写单读（一个生产者、一个消费者，如环形缓冲的 head/tail）——用 volatile + 「数据先写完、最后发布指针」的约定就够；② 多字节数据传递——不要共享，改成队列整体拷贝；③ 读改写（计数、状态字）——用最短临界区，或者干脆改成「只由一方写」。

误解 4：「队列开大点就不会丢数据了。」

为什么错：队列只能吸收「暂停时间 × 生产速率」这么多数据。如果消费者的平均处理速度本来就低于生产速度，再大的队列也只是推迟崩溃的时间，而且崩溃时更难查——前面丢的是几字节，后面丢的是几 KB。反过来，盲目开大还会吃掉宝贵的 RAM，并让「延迟」悄悄变大（里面的数据越来越旧）。

正确做法：按 3.2 节例 2 的算法算：先找出最长停顿时间（写 flash、擦除、整屏刷新），乘上生产速率，再取 2 的幂并留一倍余量。同时必须有一个丢弃计数器，并让它出现在正常日志里——「偶尔丢几个字节」和「一直在丢字节」是两种完全不同的故障。

误解 5：「任务切得越细越专业。」

为什么错：每个任务都有固定开销（调度判断、状态保存、通信），切得太细会让「协调成本」超过「并行收益」，代码从「一个 while 循环」变成「二十个互相等标志的小函数」——这比原来的前后台还难懂。更糟的是把一件完整的事拆到多个任务里，比如「读温度」在任务 A、「用温度控温」在任务 B，于是必须共享 g_temp，又退回到全局变量耦合。

正确做法：按 2.4 的四条原则切（时间尺度、数据来源、状态独立性、响应要求），并且遵守一条简单的验收标准：一个任务 = 一件完整的事的一个步骤。温控风扇切成 8 个任务是合适的；如果切成 30 个，多半是把「一件事」切碎了。

误解 6：「用了函数指针做任务表，就算是有架构了。」

为什么错：任务表只是「调度形式」。真正的架构是数据的所有权：谁能改 g_target_c？谁能写 g_rx_buf？如果这些问题没有答案，任务表只是给一团全局变量套了个好看的外壳，2.2 节的死穴②一条不少。

正确做法：把「不暴露全局变量」当硬规矩执行：模块内部状态一律 static，跨模块只能用函数、事件标志、队列。表里能查到的全局变量越少，架构越真实。

误解 7：「移植到 RTOS 就是给每个函数套一层 xTaskCreate。」

为什么错：裸机里三件「常识」在 RTOS 里会变成 bug：任务里长时间关中断（会破坏系统的实时性保证）、用全局变量传数据（多任务同时读写，且没有优先级继承，容易优先级反转）、在中断里做耗时操作（必须改用 *FromISR 版本，且不能阻塞）。此外还有两个「搬家 bug」：漏掉 HAL_Delay 改成 vTaskDelay，以及把原本的全局大数组挪成任务局部变量、直接把任务栈撑爆。

正确做法：先按 2.8 的对照表做一次「逐条替换」，再按 4.7 的方式在 PC 上把应用层逻辑测一遍（这部分代码不用改），最后才上板调栈与优先级。栈可以从「实测峰值 + 50%」起步，之后用 uxTaskGetStackHighWaterMark 盯着。

误解 8：「代码在板子上跑通了就算验证过了。」

为什么错：板子上跑通只证明「在这块板子、这个温度、这次上电、这个时序下没出问题」。而真正会咬人的场景——tick 回绕、队列刚好满、事件刚好丢一个、任务刚好迟到一整拍——在实验室里要么碰不到，要么无法复现。等到现场出现「偶尔失灵」，你手上连一条可复现路径都没有。

正确做法：分层之后，把有逻辑的部分拿到 PC 上测（4.7 那十几个用例，写一次管很久），板子上只验证「硬件相关的部分」：波形、时序、电平、功耗。这两类验证的成本差一个数量级。

误解 9：「任务的优先级就是它在任务表里的顺序。」

为什么错：调用顺序只决定「同一拍里谁先跑」，它不能打断一个已经在跑的任务。如果排在前面的是个 800 µs 的任务，后面那个「高优先级」任务照样要等它跑完。这就是 2.3 节的局限之二：非抢占。

正确做法：承认这个局限并把它算进最坏响应时间（例 1 的抖动就是 0 ~ 500 µs）；确实需要「立刻打断」的场景，只能用硬件手段：把关键动作放进中断（如过流保护直接关 PWM），或者上 RTOS。

误解 10：「事件标志由中断自己清掉最干净。」

为什么错：如果生产者在置位后立刻清掉，那么这个标志就变成了「一闪而过的脉冲」：主循环只要晚一拍看到，事件就永远丢了（这就是 2.5 节讲的「丢更新」）。反过来，如果永远不清，同一件事会被反复处理——保存参数被写了十次、日志刷屏。

正确做法：记住一句话——生产者只负责置位，消费者负责清除。清除时机有三种：取出即清、按位清（Evt_Clear(EVT_ADC_DONE)）、处理完成后显式清；无论选哪种，都要在代码注释里写明白，并且保证「同一位不会被两处消费」。

一个通用的判断法：这条规则的「单位」是什么

十条误解里有八条源于同一个错误——把「局部指标」当成了「系统指标」。中断耗时是局部的，响应时间是系统的；一个任务的执行时间是局部的，一拍内的总占用是系统的；一个队列的容量是局部的，生产与消费的速率差是系统的。每当你准备为某个局部数字（几个微秒、几个字节、几个百分比）下结论时，先问一句：它在系统层面被谁拖累？

小结与自检

这一篇从头到尾只回答一个问题：整个程序该怎么组织。把结论收成十句话，再给你六道自测题和五项练习。

要点清单

  • 三种控制流结构是一条演进线：顺序执行 + 死循环（只适合单一功能）→ 前后台系统（前台中断、后台主循环）→ 时间片轮询（有节拍、有任务表）。区别只有一句话：谁来决定「下一个该执行谁」——是程序员写死的顺序，还是调度器按时间算出来的。
  • 前后台系统的六个死穴：一处阻塞拖垮全部、全局变量耦合、实时性由最慢任务决定、无法区分优先级、栈与资源共享靠自觉、无法单独测试一个功能。它们不是「写得不好」，而是这种结构固有的代价。
  • 时间片轮询的四要素：1 ms 节拍（SysTick 中断里只做 tick++）、任务表（函数指针 + 周期 + 上次运行时刻 + 使能 + 相位）、调度循环（(uint32_t)(tick - last_run) >= period）、以及「每个任务必须自己保证在周期内返回」这条铁律。
  • 占用率要算两个口径：平均口径 U = Σ(Ci / Ti)（> 70% 警惕、> 90% 危险）和最坏一拍口径 ΣCi / 节拍（> 70% 就该错开相位）。前者决定「长期扛不扛得住」，后者决定「会不会偶发失灵」。
  • 任务切分四原则：按时间尺度分、按数据来源分、按状态独立性分、按响应要求分。验收标准是「一个任务 = 一件完整的事的一个步骤」，并且每个任务的最坏执行时间要明显小于它的周期（经验值 30%~50% 以内）。
  • 跨模块通信只有三条通道：环形缓冲／队列（搬数据）、事件标志组（通知「发生了」）、发布订阅（一对多通知）。共享全局变量 + 标志位不是第四条通道，它只是「还没设计」。
  • 事件标志的规矩：生产者只置位、消费者负责清除；标志是「发生过的记录」不是计数器；要计数就用队列。
  • 需要等待的逻辑一律写成非阻塞状态机：switch + static 状态变量 + Sched_GetTick() 时间戳；用「计划时刻累加 + 防迟到」保持长期精确；default 分支加断言。永远不要用 delay() 实现「等一会儿」。
  • 分四层，依赖方向永远向下：驱动层 bsp_*（唯一碰 HAL 的地方）→ 中间件（调度器、环形缓冲、事件、日志）→ 应用层（纯逻辑，可搬到 PC）→ 主程序（只做初始化和注册任务）。接口三原则：只暴露必要的函数、不暴露全局变量、出错要有返回值。
  • 裸机 ↔ RTOS 是同一套概念的加强版：任务表 ↔ 优先级与调度器、环形缓冲 ↔ 消息队列、事件标志 ↔ 事件组、二进制标志 ↔ 信号量、volatile + 临界区 ↔ 互斥量。什么时候上 RTOS：任务数 ≥ 4、有明显优先级差异、有大量等待、需要阻塞式编程模型。

自测题（先自己想，再点开对答案）

第 1 题 · 四个任务，平均占用率和最坏一拍各是多少？

某温控板有四个任务：Ctrl_Loop 周期 1 ms、最坏执行 45 µs；Adc_Sample 周期 10 ms、最坏 120 µs；Fan_Update 周期 100 ms、最坏 200 µs；Uart_Report 周期 100 ms、最坏 350 µs。请算平均 CPU 占用率，并且算出「四个任务恰好都落在同一拍」时这一拍的占用率，判断要不要错开相位。

答案 · 平均口径：45/1000 + 120/10000 + 200/100000 + 350/100000 = 4.5% + 1.2% + 0.2% + 0.35% = 6.25%，非常宽松。最坏一拍：45 + 120 + 200 + 350 = 715 µs，占 1 ms 节拍的 71.5%——已经超过 70% 的警戒线。虽然平均只有 6.25%，但这一拍里后面排队的任务会被推迟最多 715 µs，控制环的抖动就是这么来的。做法：给 Uart_Report 加相位 +7、给它 Fan_Update 错开，最坏一拍就能降下来（4.6 的任务表就是这么排的）。两个口径都要算，缺一个都会看走眼。

第 2 题 · 这个环形缓冲至少要多大？

串口对端每 10 ms 发来 32 字节，接收中断把它们推进环形缓冲；主循环每 5 ms 取一次，但每次保存参数时会连着 30 ms 不理串口（写 flash）。环形缓冲至少要多大？如果按「5 ms 主循环周期」算，会算出什么错误的答案？

答案 · 生产速率 32 B / 10 ms = 3.2 B/ms。要吸收的是最长停顿，不是平均周期：3.2 × 30 = 96 B，取 2 的幂并留余量 → 128 字节。按主循环周期算会得到 3.2 × 5 = 16 B——差了 6 倍，而且这个错误答案在实验室里完全看不出问题（因为实验室里没人碰巧在那 30 ms 里连续发数据）。另外别忘了：如果被保存的这 30 ms 里生产速率是满线速（115200 8N1 ≈ 11.52 B/ms），那就需要 11.52 × 30 ≈ 346 B，得开 512 字节——所以「对端按什么节奏发」是必须写进需求的一句话。

第 3 题 · 这个任务能不能放进 1 ms 节拍的调度器？

某任务的周期是 5 ms，实测最坏执行时间 1.2 ms。它占周期的比例是多少？这个比例看起来很安全，为什么它仍然是错的？

答案 · 1.2 / 5 = 24%，按「不超过周期的 30%~50%」看是合格的——但它违反了另一条硬约束：任何一次执行都不能跨越一个节拍（1 ms）。一旦某次执行超过 1 ms，节拍中断会在它执行期间再次到来，这一次的到点任务就只能等它跑完，后面所有任务整体顺延；如果它经常超过，tick - last_run 会累积成一笔还不完的账，表现就是「有些功能偶尔失灵」。正确做法：把它拆成多个步骤（状态机），每拍只做一步；或者把耗时的部分交给 DMA／硬件去做。

第 4 题 · volatile 能替代临界区吗？

中断里 g_stat.count++，主循环里也 g_stat.count++，给 g_stat 加上 volatile 是不是就安全了？

答案 · 不安全。volatile 只保证「每次都去内存里读写，不缓存进寄存器」，它不保证 ++ 这个「读—改—写」三步不会被打断，也不保证一个结构体的多个成员是同一时刻的快照。要安全只有三条路：① 改成单写单读（统计只由主循环累加，中断只推事件）；② 用队列把数据整体拷贝出去；③ 用最短临界区保护（__disable_irq() / __enable_irq()，或者用 __get_PRIMASK() 保存并恢复原有中断状态）。临界区的长度以「几微秒」为目标，超过 100 µs 必须写注释说明为什么。

第 5 题 · 事件标志谁清、什么时候清？

串口接收中断里 Evt_Set(EVT_UART_FRAME)。主循环里应该在什么时候 Evt_Clear？如果忘记清会怎样？如果在中断里清、主循环里再处理会怎样？

答案 · 规矩是生产者只置位、消费者负责清。忘记清：同一件事被反复处理——参数被存十次、日志刷屏、状态机被同一个事件推着走多次。如果在中断里清（生产中清除）：标志变成一闪而过的脉冲，主循环只要晚一拍看到，事件就永久丢了（2.5 的「丢更新」）。清除时机选一种并写进注释：取出即清（Evt_Take 返回时清零）、按位清（Evt_Clear(EVT_UART_FRAME)）、或处理完成后显式清。还要保证同一位不被两处消费，否则谁先清谁把事件吃掉。

第 6 题 · 我这个项目到底该不该上 RTOS？

给出「该上」的四条判断清单，并各举一个「不该上」的理由。

答案 · 该上的信号：① 任务数 ≥ 4 且各自周期差异很大（1 ms 和 1 s 混在一起）；② 有明显优先级差异，低优先级任务必须能被高优先级打断；③ 有大量「等待」型逻辑（等一个队列、等一个信号、等超时），用轮询写会写出一堆状态机；④ 需要阻塞式编程模型（xQueueReceive(..., portMAX_DELAY) 这种「等到再醒」的写法），或者要接 TCP/IP、文件系统这类中间件。不该上的理由：任务少、周期接近（时间片轮询足够，且省 10 KB 以上的栈与内核开销）；RAM 紧张（每个任务独立栈是实打实的内存）；只是想「显得专业」（引入 RTOS 会把「时序问题」变成「优先级与同步问题」，没有真实需求时纯属自找麻烦）；团队没人熟（内核本身也会带来新的调试成本）。

练习（动手才算学过）

  1. 给你手上的工程算一次体检。照 3.4 的六行体检表，把你现在这个工程的六个数字填出来：平均占用率、最坏一拍占用率、事件类任务最坏响应时间、单任务最坏执行时间、队列容量、栈余量。填不出来的格子，就是你现在最危险的地方。
  2. 把 4.6 的「改前」代码真的重构一遍。按四步顺序来：先消灭所有 HAL_Delay 与阻塞等待（这一步先别动结构），再把硬件访问收进 bsp_*，再把 while (1) 切成任务函数，最后才引入任务表。每做完一步，用串口打印一次「关键事件的时间戳」，对比重构前后。
  3. 给 bsp_key 写三个 PC 单元测试。用 4.7 的桩直接喂电平，测边界：① 电平抖动 15 ms 后恢复 → 不应该产生任何事件；② 抖动 25 ms 后稳定 → 应该产生一个 DOWN；③ 按住 1000 ms 整 → 产生 LONG，按住 1200 ms → 还要产生一次 REPEAT。这三个用例在板子上要按到手酸，在 PC 上是几十行代码。
  4. 抓一次「偶尔失灵」。在你手上的时间片工程里让某个任务偶尔超时（比如故意加一句 800 µs 的空转），然后用 Sched_DumpTasks() 的 run_count 和 DWT 的占用率数据定位它是谁。目标不是修好它，而是练出「用数据定位时序问题」的习惯——这是从「会写单片机程序」到「会做嵌入式系统」的分水岭。
  5. 把一个阻塞函数改成非阻塞状态机。挑你代码里最典型的那个 HAL_Delay 或 while (!flag)，用 4.4 的模板改写：定义状态、记录进入时刻、把「等」变成「每拍问一句」，加 default 断言，并写出它的「防迟到」分支。改完之后回来算一遍：这个改动让系统的最坏响应时间从多少变成了多少？
