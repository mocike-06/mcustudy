DHT11 / DS18B20 传感器读取

给项目装上「感官」。这一篇把两种最常见的温度传感器放在一起讲： 便宜但慢的 DHT11（温度 + 湿度）和精度更高、能一条总线挂一串的 DS18B20（仅温度）。 重点不是把库调通，而是讲清楚为什么 DHT11 会读失败、为什么 DS18B20 少了那只 4.7kΩ 电阻就读出 85.00℃。 前置知识：ESP32 会用 Arduino IDE 烧程序、看得懂串口输出。

原理介绍

一个温度传感器看起来只有三根线，但真正决定你能不能用好它的，是它怎么在一条线上把数据说出来。 DHT11 和 DS18B20 都只用一根数据线，都属于「单总线」家族，可它们的脾气完全不同： DHT11 用的是厂家自定义的私有单总线时序，讲究「读一次、歇一秒」； DS18B20 用的是 Maxim 的标准 1-Wire 协议，讲究「一条线上挂一串、靠身份证认人」。 先理解这两个脾气，再看代码就一目了然了。

DHT11 是怎么工作的

DHT11 把「测湿的电阻式湿敏元件 + 测温度的 NTC 热敏电阻 + 一颗 8 位单片机 + 一次性标定数据」封装在一起， 对外只留一根数据线。通信时主机先把线拉低至少 18ms 作为「我要开始读了」的起始信号， 然后释放；DHT11 回应一段 80µs 低 + 80µs 高的握手电平，接着连续吐出 40 位（5 字节）数据：

字节 内容 DHT11 的实际取值
第 1 字节湿度整数部分0~90，单位 %RH
第 2 字节湿度小数部分恒为 0，所以分辨率只有 1%RH
第 3 字节温度整数部分0~50，单位 ℃
第 4 字节温度小数部分恒为 0，所以分辨率只有 1℃
第 5 字节校验和前 4 字节相加，取最低 8 位；对不上说明数据传错了

每一位数据都以一段 50µs 的低电平开始，随后高电平的长短决定这一位是 0 还是 1： 高电平约 26~28µs 表示 0，约 70µs 表示 1。这个时序精度在微秒级， 所以库必须关中断、用忙等待来采样——这也是为什么读一次 DHT11 会「卡」几毫秒。 你不需要自己写这段时序，但理解它就能解释后面两个现象：

  • 为什么采样间隔不能小于 1 秒？ DHT11 每次被唤醒都要真正做一次温湿度转换，转换需要时间。手册要求采样周期不小于 1 秒， 实际工程里普遍用 2 秒。读得太快，器件要么还没转换完就应答、要么干脆不应答， 库拿到的是残缺数据，最终以 NAN 的形式还给你。
  • 为什么数据线上要有上拉电阻？ 单总线的电气结构是「双方都只能把线拉低，谁也不能主动输出高电平」。 空闲时线的高电平完全靠一只上拉电阻把线「拽」到电源。 少了它，线是悬空的，任何一点干扰都会让它乱跳，通信必然失败。 市面上三针的 DHT11 模块已经焊好了 10kΩ 上拉， 而四脚的裸元件没有，必须自己补一只。

DS18B20 与 4.7kΩ 上拉电阻

DS18B20 是 Maxim（原 Dallas）的标准 1-Wire 器件，功能上比 DHT11 强得多： 温度范围 -55~+125℃，在 -10~+85℃ 区间精度可达 ±0.5℃， 分辨率可以在 9~12 位之间配置，而且每个器件出厂时都烧了一个全球唯一的 64 位 ROM 地址， 所以一条数据线上可以并联很多个，靠地址区分谁是谁。

那 64 位地址不是随机数，它的结构值得记一下： 低 8 位是家族码（DS18B20 固定为 0x28）， 中间 48 位是出厂唯一序列号，最高 8 位是前面 56 位的 CRC 校验。 库在搜索总线时就是靠这套地址逐个「点名」，同时用 CRC 确认点到的是真器件而不是干扰。

分辨率配置 温度分辨率（LSB） 一次转换耗时 什么时候用
9 位0.5 ℃约 94 ms只关心整度、要求快
10 位0.25 ℃约 188 ms折中
11 位0.125 ℃约 375 ms折中偏精度
12 位（默认用这个）0.0625 ℃约 750 ms要精细曲线、不赶时间

现在回答那个最关键的问题：为什么 DS18B20 的数据线必须接一只 4.7kΩ 上拉电阻？

1-Wire 总线上的每一个器件（包括主机 ESP32 这边）输出级都是开漏结构： 它只能把线拉到 GND，松开手就变成高阻态，没有任何一方能主动输出高电平。 于是「高电平」这件事必须由外部元件来负责——就是那只上拉电阻。 它同时承担三个作用：

  • 定义空闲电平：没人拉低时，线被电阻拽到 3.3V，所有器件看到「总线空闲」。
  • 给总线电容充电：杜邦线和探头电缆都是有电容的，器件从「拉低」松手后，线要靠这只电阻的电流慢慢充回高电平。阻值太大充得慢，时序就对不上。
  • 决定通信距离：阻值小、上升沿快但功耗大；阻值大、省电但距离短。4.7kΩ 是几十厘米到几米范围内的标准答案。
少了这只电阻，你看到的不是「没数据」，而是「数据看着挺正常」

这是 DS18B20 最坑的地方：总线浮空时，主机发出的复位脉冲可能仍然被器件认出来（因为拉低是有效的）， 于是通信「看起来」在进行，但你读回的暂存器里是芯片上电复位的默认值—— 也就是那个著名的 85.00 ℃。 它不会报错、不会返回 -127，只是忠实地给你一个假数据。 所以：读数稳定在 85.00℃ 不动，第一件事就是查上拉电阻，而不是怀疑代码。

顺带说一下供电方式：DS18B20 有「外部供电（三线）」和「寄生供电（两线，靠数据线取电）」两种模式。 寄生供电对时序、上拉阻值和总线负载都很敏感，新手非常容易踩坑。 本页只用外部供电：VDD 接 3.3V、GND 接 GND、DQ 接 GPIO 加上拉。

  • 只是「看看室内温湿度」、做课设演示，DHT11 够了，便宜且一个引脚搞定。
  • 要测水温、油温、机箱温度（可能超过 50℃ 或低于 0℃），或者要多点同时测温，用 DS18B20（防水探头版本很常见）。
  • 对湿度精度有要求（比如做烘干箱、菌菇房），DHT11 的 ±5%RH 不够用，上 DHT22。

硬件接线说明

这一节的接线比上一篇复杂，因为多了两个器件和一只关键电阻。 请特别注意两件事：ESP32 的 GPIO34~39 只能当输入，不能用作这里的传感器引脚； 以及两个器件都接到 3.3V 而不是 5V。

关键点：
1. 两个器件都接 3.3V。若把 DS18B20 接 5V，它的 DQ 高电平会是 5V，会损伤 ESP32 的 3.3V 引脚。
2. 4.7kΩ 接在 DQ 与 3.3V 之间，不是串在数据线里——串进去就变成断路了。
3. 杜邦线尽量短（20cm 以内），面包板接触不良是「偶尔读不到」的头号原因。
4. GPIO34~39 只能输入，没有内部上拉，接在这里的传感器一定读不出来。

接线顺序建议

  1. 先接电源和地：两个器件的 VCC/VDD 到 3.3V、GND 到 GND，检查一遍没有接反。
  2. 再接数据线：DHT11 的 DATA 到 GPIO4，DS18B20 的 DQ 到 GPIO5。
  3. 最后接那只 4.7kΩ 电阻，跨在 GPIO5 与 3.3V 之间——接在面包板的不同行上最常见的错误就是跨错行，等于没接。
  4. 上电，先用串口看 DS18B20 的器件数量和地址，再去看温度数值。
ESP32 引脚避坑清单
  • GPIO34 ~ GPIO39：只能做输入、没有内部上拉/下拉。传感器接在这些脚上会一直读失败（这是 DHT 读 NAN 的高频原因之一）。
  • GPIO6 ~ GPIO11：内部连到 SPI Flash，绝对不能用。
  • GPIO0 / GPIO2 / GPIO12 / GPIO15：启动模式（strapping）引脚，上电瞬间的电平会影响能不能正常启动，别在这里挂会拉低电平的外设。
  • 推荐的安全引脚：GPIO4、GPIO5、GPIO13、GPIO14、GPIO16、GPIO17、GPIO18、GPIO19、GPIO21、GPIO22。

完整代码

下面的程序把两种传感器放在同一个 sketch 里，每 2 秒打印一次。 它同时演示了三件工程上必须做的事：读失败要判断、 85.00℃ 要识别出来、启动时打印每个 DS18B20 的 ROM 地址。

库的安装

打开 工具 → 管理库，依次搜索并安装下面四个。 注意 DHT 那个必须先装「统一传感器接口」库，否则编译一定报错找 Adafruit_Sensor.h：

库名（库管理器里搜这个） 作者 作用
DHT sensor libraryAdafruitDHT11 / DHT22 的时序实现，提供 readTemperature()
Adafruit Unified SensorAdafruit上面那个库的依赖，必须一起装
DallasTemperatureMiles BurtonDS18B20 的上层封装，管转换与读数
OneWirePaul Stoffregen底层 1-Wire 时序，被 DallasTemperature 调用
 
/* =====================================================================
 * esp32_sensor_dht11_ds18b20.ino
 * 功能：同时读取 DHT11（温度 + 湿度）与 DS18B20（温度），每 2 秒打印一次
 * 硬件：ESP32-WROOM-32，DHT11 数据线接 GPIO4，DS18B20 DQ 接 GPIO5
 * 依赖：DHT sensor library + Adafruit Unified Sensor
 *       DallasTemperature + OneWire
 * ===================================================================== */

#include <DHT.h>                  // DHT11 / DHT22 库
#include <OneWire.h>             // 1-Wire 底层时序
#include <DallasTemperature.h>   // DS18B20 上层封装

/* ----------------------------- 引脚 ----------------------------- */
#define DHT_PIN      4           // DHT11 数据线，不要用 34~39
#define DHT_TYPE     DHT11       // 用的是 DHT11；换成 DHT22 就改这里
#define ONEWIRE_PIN  5           // DS18B20 的 DQ 脚，记得对 3.3V 接 4.7kΩ

DHT           dht(DHT_PIN, DHT_TYPE);   // 构造 DHT 对象
OneWire       oneWire(ONEWIRE_PIN);     // 构造 1-Wire 对象
DallasTemperature ds(&oneWire);         // 把 1-Wire 对象交给 Dallas 库

const uint32_t READ_INTERVAL = 2000;    // 采样间隔 2 秒（DHT11 要求不小于 1 秒）
uint32_t lastRead = 0;                  // 上次采样的时刻

void setup() {
  Serial.begin(115200);
  delay(300);                           // 等串口稳定，否则开头几行会丢

  Serial.println("\n===== ESP32 温湿度采集实验 =====");

  /* ---------------- DHT11 ---------------- */
  dht.begin();                          // 只需调用一次，内部会做起始时序

  /* ---------------- DS18B20 ---------------- */
  ds.begin();                           // 搜索总线，把找到的器件登记下来

  int devCount = ds.getDeviceCount();   // 总线上找到几个 DS18B20
  Serial.printf("DS18B20 检测到 %d 个器件\n", devCount);

  if (devCount == 0) {
    Serial.println("没找到器件！依次检查：4.7kΩ 上拉、DQ 是否接 GPIO5、VDD 是否接 3.3V");
  }

  // 打印每个器件的 64 位 ROM 地址：多传感器时靠它区分谁是谁
  for (int i = 0; i < devCount; i++) {
    DeviceAddress addr;
    if (ds.getAddress(addr, i)) {
      Serial.printf("  器件 %d 地址：", i);
      for (uint8_t b = 0; b < 8; b++) {
        Serial.printf("%02X ", addr[b]);   // 最低位是家族码，DS18B20 固定 28
      }
      Serial.println();
    }
  }

  ds.setResolution(12);                 // 12 位分辨率，约 0.0625℃；转换耗时约 750ms
}

void loop() {
  // 时间没到就什么都不做：这种「记录时刻 + 比差值」的写法不会阻塞别的任务
  if (millis() - lastRead < READ_INTERVAL) {
    return;
  }
  lastRead = millis();

  Serial.println("------------------------------------------");
  Serial.printf("[时间] 已运行 %lu 秒\n", millis() / 1000);

  /* ================= DHT11 ================= */
  // 注意：库内部有读取频率保护，两次读得太近会直接返回缓存结果
  float humidity = dht.readHumidity();      // 相对湿度 %RH
  float tempDHT  = dht.readTemperature();   // 摄氏温度 ℃

  // 读失败时库返回 NAN（不是 0，也不是负数），必须用 isnan() 判断
  if (isnan(humidity) || isnan(tempDHT)) {
    Serial.println("DHT11 ：读取失败（NAN）→ 查采样间隔、上拉电阻、引脚是否在 34~39");
  } else {
    Serial.printf("DHT11 ：温度 %.1f C   湿度 %.1f %%RH\n", tempDHT, humidity);
  }

  /* ================= DS18B20 ================= */
  // requestTemperatures() 会触发一次转换并等它完成（12 位时约 750ms，期间阻塞）
  ds.requestTemperatures();

  for (int i = 0; i < ds.getDeviceCount(); i++) {
    float t = ds.getTempCByIndex(i);

    if (t == DEVICE_DISCONNECTED_C) {
      // -127℃ 是库定义的「器件不在总线上」标志
      Serial.printf("DS18B20 器件 %d：读取失败（器件掉线，返回 -127）\n", i);
    } else if (t == 85.0) {
      // 85℃ 是 DS18B20 上电复位的默认值，几乎总是「转换没真正发生」
      Serial.printf("DS18B20 器件 %d：85.00 C —— 这是上电默认值，先查 4.7kΩ 上拉\n", i);
    } else {
      Serial.printf("DS18B20 器件 %d：温度 %.2f C\n", i, t);
    }
  }
}

关键代码解析

  • DHT dht(DHT_PIN, DHT_TYPE);——同一套库同时支持 DHT11 和 DHT22， 靠第二个参数区分。参数写错了（比如 DHT11 的元件却填了 DHT22）， 库会按 DHT22 的时序去读，结果是持续的 NAN 或者明显偏掉的数值。
  • isnan(humidity)——DHT 库读失败时返回的是 NAN（Not a Number）。如果不判断直接格式化输出， 你会看到 nan 或者一串乱码；更糟的是拿它去比较大小， NAN 和任何数比较都是 false，逻辑会静默走偏。
  • ds.begin(); ds.getDeviceCount(); ds.getAddress(addr, i);—— 这三个调用是 1-Wire 的核心流程：枚举总线上的所有器件、把每个器件的 64 位 ROM 地址读出来。 DallasTemperature 内部会做 CRC 校验，所以能进到列表里的地址是可信的。
  • ds.getTempCByIndex(i) 里的 i—— 这个索引不是按接线顺序排的，而是按总线枚举顺序（取决于 ROM 地址）。 所以多传感器时不要「猜」，要先打印地址建立对应关系（见排错一节）。
  • ds.requestTemperatures();——一次广播，让总线上所有器件同时开始转换， 然后等最慢的那个转换完（12 位约 750ms）再返回。 这个等待是阻塞的。单独跑没问题， 但如果之后要和上一篇的 MQTT 结合，记住别再加额外的长延时—— 750ms 相对 15 秒的 keepAlive 还很安全，但再加几个 delay(5000) 就会掉线。
  • ds.setResolution(12);——分辨率是可以牺牲的： 只关心整度的话设成 9 位，转换时间从 750ms 降到 94ms，采样可以更密。 精度和速度在这里是一对矛盾，按项目需求选。
  • millis() - lastRead < READ_INTERVAL—— 非阻塞节流。如果写成 delay(2000)， 整个 CPU 会干等两秒，别的任务（按键、通信、显示）全都停摆。

换成 OLED 显示

串口只适合调试，做实物作品时一般要一块屏。最常见的 0.96 寸 SSD1306（128×64，I2C 接口） 只要两根信号线：SDA 接 GPIO21、SCL 接 GPIO22，模块地址通常是 0x3C。库管理器里装 Adafruit SSD1306 和 Adafruit GFX Library，然后在刚才的程序里加下面这些内容即可—— 传感器部分的代码一行都不用改： 

#include <Wire.h>                    // I2C 底层，SSD1306 依赖它
#include <Adafruit_GFX.h>           // 图形库
#include <Adafruit_SSD1306.h>      // 屏幕驱动

#define SCREEN_W 128                // 0.96 寸屏宽 128 像素
#define SCREEN_H 64                 // 高 64 像素

// 最后一个参数 -1 表示这块屏没有复位引脚
Adafruit_SSD1306 oled(SCREEN_W, SCREEN_H, &Wire, -1);

// ---------------- 放在 setup() 里 ----------------
void setupOLED() {
  Wire.begin(21, 22);               // ESP32 默认 SDA=21、SCL=22
  if (!oled.begin(SSD1306_SWITCHCAPVCC, 0x3C)) {
    Serial.println("OLED 初始化失败：查 SDA/SCL 接线与地址（也可能 0x3D）");
    return;
  }
  oled.clearDisplay();
  oled.setTextColor(SSD1306_WHITE); // 单色屏只有「亮 / 不亮」两种颜色
  oled.setTextSize(1);              // 1 号字每行约 21 个字符，够放三行数据
  oled.display();
}

// ---------------- 放在 loop() 采样成功之后 ----------------
void updateOLED(float tDHT, float hDHT, float tDS) {
  oled.clearDisplay();              // 先清空缓冲区，再整屏刷出去

  oled.setCursor(0, 0);
  oled.printf("T(DHT): %.1f C", tDHT);

  oled.setCursor(0, 16);
  oled.printf("H(DHT): %.1f %%", hDHT);

  oled.setCursor(0, 32);
  oled.printf("T(DS) : %.2f C", tDS);

  oled.setCursor(0, 48);
  oled.printf("间隔 %lus 刷新", READ_INTERVAL / 1000);

  oled.display();                   // ★ 必须调用，否则数据只在内存里，屏幕不动
}
接 OLED 时最容易忘的两件事
  • OLED 也要接 VCC 和 GND，很多人只接了 SDA/SCL 两根线，屏幕自然黑的。
  • oled.display() 才是真正推送到屏幕的动作。只写 printf 不调用它，屏幕会一直停留在上一帧——这个坑几乎每个人都踩过一次。

现象演示说明

这一节按顺序列出了「做对了应该看到什么」。特别注意第 1 步和第 4 步： 它们分别验证了 DS18B20 的器件枚举和 85.00℃ 判据，是这篇教程里最有价值的两个自查点。

正确现象

  1. 上电后串口第一行是 ===== ESP32 温湿度采集实验 =====。
  2. 紧接着打印 DS18B20 检测到 1 个器件。数字就是实际接的数量，接几个报几个。
  3. 打印出一行 8 字节的地址，形如 28 FF 64 1E 0D 20 01 5B——第一个字节一定是 28，这是 DS18B20 的家族码。
  4. 之后每 2 秒输出一段，温度数值在合理范围内浮动，绝不是恒定的 85.00，也不是 -127。
  5. DHT11 一行显示 温度 26.0 C 湿度 58.0 %RH，两个值都是整数或 .0——这正是 DHT11 分辨率 1℃ / 1%RH 的体现，不是 bug。
  6. 两个温度值应该彼此接近（同一房间内一般相差不超过 1~2℃）。用嘴对着 DHT11 哈气，湿度会明显上升、温度略升；捏住 DS18B20 的探头，它的读数会慢慢往上爬。
  7. 把 DS18B20 的探头浸入温水（注意防水探头才可入水），读数会跟着水温和缓上升，响应比 DHT11 慢一些（受 750ms 转换和器件热惯性影响）。
  8. 连续运行 10 分钟，不出现任何一次 NAN 或 -127。

观察点与判据

你观察到的 说明什么 下一步查什么
DS18B20 检测到 0 个器件 总线枚举失败，器件根本没被认出来 DQ 有没有接对引脚；4.7kΩ 有没有真的跨在 DQ 与 3.3V 之间；VDD/GND 有没有接反
温度恒定 85.00 一动不动 读到了上电复位默认值，转换没有真正发生 九成是缺 4.7kΩ 上拉；其次是数据线太长、接触不良
温度显示 -127.00 库明确报告「器件掉线」 接线松动、供电不足（别用 5V 混接）、探头线断
DHT11 一直是 NAN 单总线时序没有完成，校验失败 采样间隔是不是小于 1 秒；引脚是不是 34~39；裸元件有没有加上拉
DHT11 时好时坏，偶尔成功一次 典型的接触不良或线太长引入的干扰 换短线、压紧面包板、裸元件加 0.1µF 去耦电容
两个温度差 5℃ 以上 其中一个装的位置不对（贴着发热的稳压芯片、被 USB 口烤着） 把两个传感器并排放到同一位置再比对

顺手记录实验数据

这篇教程特别适合做「精度对比」类的实验报告。建议做这三组记录： 一是与标准温度计的偏差——把 DHT11、DS18B20 和一支普通温度计放在同一杯水里静置 3 分钟，记录三者读数，你会发现 DHT11 的 ±2℃ 误差是真实存在的； 二是响应时间——从把探头放进温水到读数稳定的秒数，DS18B20 因为要等 750ms 转换，往往比你想的慢； 三是连续 1 小时的读失败次数——这个数字直接反映你的接线质量，也是答辩时「系统稳定性」最好的证据。

常见报错排查方案

传感器类的「报错」很少以编译错误的形式出现，多数是「编译通过、读数不对」。 所以下面每一条都把你会看到的输出原文放在最前面，方便对照。

DS18B20 恒定为 85.00 C，其他一切正常

原因：85℃ 是 DS18B20 芯片上电复位后温度寄存器的默认值。出现这个数字，说明通信链路「半通」：命令发出去了，但真正的温度转换没有完成，读回的是那个默认值。最常见的原因是数据线上缺少 4.7kΩ 上拉电阻；其次是数据线过长（超过几米）导致上升沿太慢、器件供电不足、或面包板接触不良。

解决：确认电阻是跨接在 DQ 与 3.3V 之间（不是串在数据线里，也不是接到 GND）；换一只 4.7kΩ（4.7k~10k 都能工作，太小会费电、太大上升沿慢）；把杜邦线缩短到 20cm 以内；VDD 用稳定的 3.3V 供电，长线时在器件旁加 0.1µF 去耦电容。

DS18B20 检测到 0 个器件 / 读数恒为 -127.00

原因：总线枚举阶段的搜索没找到任何器件。DEVICE_DISCONNECTED_C（-127）正是库为这种情况定义的返回值。常见原因：DQ 接到了 GPIO34~39 这类只能输入的引脚；或者 VDD 与 GND 接反；或者 TO-92 的引脚顺序搞错了——DS18B20 的三只脚顺序是 GND、DQ、VDD，和很多三极管、温度传感器的排列都不一样。

解决：把 DQ 换到 GPIO4/5/13/14/16/17 这类安全引脚；用万用表量器件 VDD 脚对 GND 是不是稳定的 3.3V；确认 TO-92 的读法是「平面（印字面）朝自己、引脚朝下，从左到右 GND-DQ-VDD」；防水探头版按红 VDD、黑 GND、黄或白 DQ 接。

串口一直打印 DHT11：读取失败（NAN）

原因：按出现概率排序——一是采样间隔太短，两次读取间隔小于 1 秒，DHT11 还没完成内部转换就被再次唤醒；二是数据线缺上拉（四脚裸元件最容易犯）；三是引脚选到了 GPIO34~39，这些脚只能输入、没有内部上拉，读单总线必然失败；四是线太长或接触不良。

解决：把采样间隔改成 2 秒（代码里的 READ_INTERVAL）；裸元件在 DATA 与 3.3V 之间补一只 10kΩ；换到 GPIO4；杜邦线压紧、缩短；改完还是 NAN 就换一个 DHT11 元件试——廉价元件的个体差异确实存在。

编译报错：fatal error: Adafruit_Sensor.h: No such file or directory

原因：只装了 DHT sensor library，没装它依赖的 Adafruit Unified Sensor。DHT 库内部用这个统一接口来组织传感器的量纲和单位，所以它是硬依赖。

解决：在库管理器里再搜一次 Adafruit Unified Sensor 并安装，重启 Arduino IDE 后重新编译。装完列表里两个库都要在（库管理器里可以点「更多信息」看依赖）。

多传感器时读数对不上号（器件 0 和器件 1 换了位置）

原因：getTempCByIndex(i) 里的索引是按总线枚举顺序排的，本质上由 ROM 地址决定，和你的接线顺序没有任何关系。今天器件 0 是左边那个，重新上电或换一根线之后就可能是右边那个。

解决：不要用索引，用地址。启动时用 getAddress() 打印出每个探头的 8 字节地址，记下「地址 → 实际位置」的对应表，然后写死在代码里，读数时用 ds.getTempC(addr) 按地址取值。这样无论怎么上电、怎么插拔，读到的都是同一个物理位置。

编译警告：Multiple libraries were found for "OneWire.h"

原因：Arduino 的库目录里存在多个 OneWire 库（常见于你把示例压缩包手动解压过、或跟着不同教程装过好几遍）。IDE 会挑一个用，但挑中的那个可能不兼容 DallasTemperature。

解决：看编译输出里列出了哪几个路径，删掉多余的，只保留 Paul Stoffregen 的 OneWire（库管理器里作者显示为 Paul Stoffregen）。如果删不干净，把 sketchbook 目录下的 libraries 文件夹清理一遍再重装。

排错顺序建议：从外到内，别一上来就改代码

传感器类的故障有九成在硬件上。建议固定按这个顺序查，每一步只排除一类可能： ① 供电（万用表量器件 VDD 对 GND 是不是 3.3V）→ ② 上拉（DS18B20 的 4.7kΩ 是否真的跨在 DQ 与 3.3V 之间，用万用表电阻档量）→ ③ 引脚（是不是 34~39，编号有没有数错）→ ④ 线材与接触（换短线、换面包板孔位）→ ⑤ 最后才怀疑代码和元件本身。 按这个顺序走，平均十分钟就能定位；反过来先改代码，往往折腾两小时还在原地。

小结与练习

这一篇的实质内容可以压成三句话： 单总线器件的可靠性，取决于那只上拉电阻和采样节奏，而不是代码写得多漂亮； DHT11 慢而便宜，DS18B20 准且能一线多挂，按量程和精度需求选； 以及 永远要判断读失败—— NAN、85.00、-127 这三个数字各自对应一类明确的硬件问题， 认出它们，你就比只会抄代码的人多了一整套排错能力。

另外记住一个可迁移的经验：凡是「单总线 / I2C / 开漏输出」的器件， 都要先问一句「空闲时这根线的高电平由谁提供」。答不上来，就说明你的上拉还没接对。

动手练习
  1. 做一次「拆掉上拉」的对照实验。 在 DS18B20 的 DQ 上拉电阻完好时记录 10 次读数，然后拔掉这只 4.7kΩ，再记录 10 次。 把两次的数据都写进实验记录，并解释你看到的现象（提示：多半会出现 85.00℃， 也可能直接变成 0 个器件——取决于你的线长和面包板分布电容）。这种「人为制造故障」的实验， 比抄一遍正确接线更能让你记住原理。
  2. 把采样间隔改成 200ms，观察会发生什么。 把 READ_INTERVAL 改成 200，烧录后观察 DHT11 的输出。 再把间隔调回 2000ms 对比。用数据回答：DHT11 的「不小于 1 秒」是硬性要求还是建议值？ 顺便想想，为什么 DS18B20 反倒不怕读得快。
  3. 把读数接到 OLED 上，做成一个桌面温度计。 按前面 sub-oled 一节的片段改造程序， 要求屏幕上同时显示 DHT11 的温湿度、DS18B20 的温度和运行时间， 并且读失败时显示 -- 而不是 nan。 做出来的东西可以直接当课设实物。
  4. （进阶）接两个 DS18B20，做地址绑定。 把两个探头并联到同一根总线上（共用一只 4.7kΩ 上拉即可）， 先打印出两个 ROM 地址，再用 getTempC(addr) 分别读取， 把其中一个放进冰箱、另一个放在室温，验证你能稳定区分它们。 完成后你就掌握了 1-Wire 最实用的那项能力——一条线测多点。
