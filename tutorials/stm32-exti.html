外部中断

轮询按键的写法有个天生的毛病：主循环一旦在忙别的事，按键就会被漏掉。 外部中断解决的正是这个问题——引脚上一出现指定边沿，CPU 立刻放下手里的活去响应。 这一篇讲清楚 EXTI 线是怎么和引脚绑定的、NVIC 的抢占优先级和响应优先级到底差在哪里、 为什么 HAL 把 SysTick 的优先级固定成最低的 0x0F， 以及中断回调里绝对不能做的那几件事背后的硬件机制。读完你能写出不会卡死、不会丢按键的中断代码。

原理介绍

先说清楚中断到底解决了什么问题。 用轮询的方式读按键是这样的：主循环每隔几毫秒看一眼 PA0， 如果发现是低电平就认为按下了。这个办法有两个硬伤—— 主循环如果正在执行一个 200ms 的延时，这期间的按键就被彻底漏掉了； 而如果你为了不漏按键就把循环转得飞快，CPU 又一直在做无用功。

外部中断把这件事反过来了：不是 CPU 去问引脚，而是引脚来通知 CPU。 PA0 上出现一个下降沿，硬件立刻把这件事记下来并打断 CPU 当前的工作， 跳到一段专门的代码去处理。处理完再回到被打断的地方继续。 整个过程不需要 CPU 参与任何“盯着看”的动作—— 这就是中断最大的价值：让等待不占用 CPU。

19 条（EXTI0~EXTI18）

EXTI 线与引脚映射

从引脚到 CPU，一个外部中断要走完四步。 把这四步记住，后面所有的现象都能解释： 

  PA0 引脚上出现下降沿
        │
        ▼
  ① EXTI 边沿检测电路
       检测到设定的边沿 → 把挂起寄存器 PR 的对应位置 1
       └── 触发边沿由 RTSR（上升沿）/ FTSR（下降沿）两个寄存器决定
        │
        ▼
  ② EXTI 中断屏蔽寄存器 IMR
       如果这一位是 1（允许中断）→ 继续往下；是 0 就到此为止（只当事件，不产生中断）
        │
        ▼
  ③ NVIC 嵌套向量中断控制器
       查这张中断的优先级，和当前正在执行的中断比：
         新来的优先级更高（数字更小）→ 抢占，嵌套进去
         不更高 → 挂起等待，等当前中断处理完再说
        │
        ▼
  ④ 跳转到中断向量表里登记的入口函数
       EXTI0_IRQHandler()      ← 0 号线单独一个入口
       EXTI1_IRQHandler()      ← 1 号线单独一个入口
       ...
       EXTI9_5_IRQHandler()    ← 5~9 号线【共用】一个入口 ★
       EXTI15_10_IRQHandler()  ← 10~15 号线【共用】一个入口 ★

最容易踩的坑在最后那两行：5 到 9 号线共用一个中断入口， 10 到 15 号线共用另一个。这意味着如果你同时用了 PA9 和 PB5， 两者进的是同一个 EXTI9_5_IRQHandler， 在函数里必须判断到底是哪一条线触发的—— 这正是 HAL 回调函数那个 GPIO_Pin 参数的用途。

EXTI 线 可选的引脚 中断入口函数 说明
EXTI0PA0 / PB0 / PC0EXTI0_IRQHandler独占入口，一次只能选一个端口
EXTI1PA1 / PB1 / PC1EXTI1_IRQHandler独占入口
EXTI2PA2 / PB2 / PC2EXTI2_IRQHandler独占入口
EXTI3PA3 / PB3 / PC3EXTI3_IRQHandler独占入口
EXTI4PA4 / PB4 / PC4EXTI4_IRQHandler独占入口
EXTI5 ~ 9对应端口 pin5 ~ pin9EXTI9_5_IRQHandler五条线共用，必须在回调里按 GPIO_Pin 区分
EXTI10 ~ 15对应端口 pin10 ~ pin15EXTI15_10_IRQHandler六条线共用，同样要区分
同一时刻，一条 EXTI 线只能连一个端口

EXTI0 这条线通过 AFIO 的 AFIO_EXTICR1 寄存器来选择 “我是听 PA0、PB0 还是 PC0”。这个寄存器里写的是一个端口名，不是一个位掩码， 所以 PA0 和 PB0 不可能同时作为 EXTI0 的输入， 后配的那个会把前一个顶掉。

这个坑的典型现象是：“我明明配了两个按键中断，只有一个能用”。 解决办法是让两个按键用不同的 pin 号（比如 PA0 和 PA1）， 而不是不同的端口、相同 pin 号。

这几个引脚不要拿来做中断输入
  • PA13 / PA14——SWDIO 和 SWCLK，调试器靠它们下载和调试。占用之后下载会失败，严重时芯片被锁。
  • PA15 / PB3 / PB4——JTAG 的 JTDI / JTDO / NJTRST。默认被调试口占用，要用得先关掉 JTAG 复用（__HAL_AFIO_REMAP_SWJ_NOJTAG()）。
  • PC13 / PC14 / PC15——属于备份域，驱动能力弱（PC13 只能吸收 3mA 左右）且速度受限。拿 PC13 驱动一个 LED 没问题，但用它做高速中断输入要小心。

NVIC 优先级分组

Cortex-M3 内核给每个中断准备了一个 8 位的优先级寄存器， 但 STM32F1 只实现了高 4 位， 所以实际的优先级取值只有 0~15 共 16 级，数字越小优先级越高。 剩下的问题就是：这 4 位怎么分配？

这 4 个位可以被切成两段，一段管“抢占”，一段管“响应”：

  • 抢占优先级（Preemption Priority）—— 决定能不能打断正在执行的中断。 高抢占优先级（数值小）的中断可以打断低抢占优先级的 ISR，形成中断嵌套。
  • 响应优先级（Sub Priority，也叫子优先级）—— 只在两个中断同时挂起、都还没开始执行时决定谁先跑。 它完全没有嵌套能力：已经在执行的中断，不会被响应优先级更高的后来者打断。
CubeMX / HAL 里的分组 抢占位数 响应位数 抢占优先级取值范围 说明
NVIC_PRIORITYGROUP_004只有 0没有嵌套，全部靠响应优先级排队
NVIC_PRIORITYGROUP_1130 ~ 1很少用
NVIC_PRIORITYGROUP_2220 ~ 3需要细分子优先级时用
NVIC_PRIORITYGROUP_3310 ~ 7较常用
NVIC_PRIORITYGROUP_4400 ~ 15HAL 默认值，本页用的就是它

HAL 默认使用分组 4，也就是 4 位全部给抢占优先级，取值范围 0~15，响应优先级恒为 0。 这个设置在 CubeMX 生成的 stm32f1xx_hal_msp.c 里的 HAL_MspInit() 中，由这一行写死： 

void HAL_MspInit(void)
{
    __HAL_RCC_AFIO_CLK_ENABLE();        /* AFIO 时钟，EXTI 的引脚映射寄存器在这里 */
    __HAL_RCC_PWR_CLK_ENABLE();

    /* 关掉 JTAG、只保留 SWD，把 PA15/PB3/PB4 释放成普通 GPIO。
     * 如果你要用这三个脚做中断输入，这一句是必需的 */
    __HAL_AFIO_REMAP_SWJ_NOJTAG();

    /* ★ 这一行决定了整个工程的中断优先级分组方式。
     *   分组 4 = 4 位抢占 + 0 位响应，所以 HAL_NVIC_SetPriority 的
     *   第三个参数（响应优先级）实际上怎么填都不起作用 */
    HAL_NVIC_SetPriorityGrouping(NVIC_PRIORITYGROUP_4);
}
怎么给中断排优先级：一条实用规则

用“谁更不能等，谁优先级高”来排序。 对一个典型的电压表项目，我会这样分配：

中断源 抢占优先级 理由
USART1 接收1串口字节不来就永远丢了，必须最快响应
EXTI0（按键）2人的手指反应时间是几十毫秒，差几微秒无所谓
TIM2（定时采样）3晚一点只是采样周期略微抖动，可以容忍
SysTick（系统时基）15每 1ms 必然发生一次，不紧急，见下一小节

注意这套数字是相对的： 真正重要的是串口比按键高、按键比定时器高、时基最低这个次序， 至于具体是 1/2/3 还是 3/4/5，差别不大。

为什么 SysTick 优先级是 0x0F

你在 stm32f1xx_hal_conf.h 里能找到这样一行： 

/* 系统时基中断（SysTick）的优先级。
 * 0x0F = 15，是 Cortex-M3 在 STM32F1 上能设置的最低优先级。
 * HAL_InitTick() 会用它来给 SysTick 设优先级，HAL_Delay 就靠它计数。 */
#define TICK_INT_PRIORITY   0x0F

为什么 ST 要把它设成最低？有两个层面的原因。

第一，SysTick 不紧急，抢占式优先级应该留给真正紧急的事。 SysTick 每 1ms 无条件发生一次，它做的事情只是把全局变量 uwTick 加一。 而按键、串口这些中断是事件驱动的，不来就永远不来， 来了就说明有真实的外部事件需要立刻记录。 如果给 SysTick 高优先级，它就会每 1ms 打断一次正在执行的外设中断—— 单次只多几微秒，但对软件模拟 I2C、单总线温度传感器这类靠 精确延时翻转引脚的代码来说，被随机打断会让时序错乱、通信失败。 把 SysTick 放到最低，它会一直忍让到所有中断都处理完再执行， 代价只是 uwTick 的更新可能被推迟几十微秒—— 对 1ms 精度的软件时基来说完全可以接受。

第二，也是更关键的一点：它决定了“中断里不能调 HAL_Delay”这条铁律。 因为 SysTick 优先级最低，任何外设中断在执行期间都能挡住 SysTick。 于是就有了下面这条因果链： 

进入 EXTI0 中断服务程序
   │
   │  SysTick 优先级 15，EXTI0 优先级 2
   │  → SysTick 抢不过 EXTI0，它的中断请求只能排队等着
   │
   ▼
中断里调用 HAL_Delay(100)
   │
   │  HAL_Delay 的实现是：
   │      tickstart = HAL_GetTick();
   │      while ((HAL_GetTick() - tickstart) < 100) { }   ← 死等
   │  而 HAL_GetTick() 返回的就是 uwTick
   │
   ▼
uwTick 永远不会再增加（因为 SysTick 被挡在门外）
   │
   ▼
while 条件永远成立 → 中断永远不返回
   │
   ▼
系统假死：所有同优先级和更低优先级的中断再也不会被响应，
        主循环也永远不会恢复执行

★ 结论：中断里既不能 HAL_Delay，也不能依赖任何基于 uwTick 的超时。
把这条因果链记住，比记住“中断里不能延时”有用得多

“中断里不能 HAL_Delay”是一条结论， 而“SysTick 优先级最低，所以 ISR 执行期间 uwTick 不增长” 是这条结论的机制。 记住机制的好处是：你能自己推导出更多结论—— 比如“中断里也不能用 HAL_UART_Transmit 带超时的版本”， 因为它内部同样在等 uwTick； 也不能用 HAL_ADC_PollForConversion(&hadc1, 10)， 同样因为它靠 tick 判超时。 凡是以 uwTick 为时间基准的等待，在中断里都会变成永久等待。

回调函数是怎么被调用的

很多教程直接让你“在 main.c 里写一个 HAL_GPIO_EXTI_Callback 就行了”， 但不说清楚它是怎么被调用的。搞懂这条链路，遇到“回调不执行”时你才知道从哪查。 

第 1 层：中断向量表里的入口（CubeMX 生成在 stm32f1xx_it.c）

    void EXTI0_IRQHandler(void)
    {
        HAL_GPIO_EXTI_IRQHandler(GPIO_PIN_0);      ← 就这一句
    }

        ↓

第 2 层：HAL 库的统一处理函数（在 stm32f1xx_hal_gpio.c 里）

    void HAL_GPIO_EXTI_IRQHandler(uint16_t GPIO_Pin)
    {
        if (__HAL_GPIO_EXTI_GET_IT(GPIO_Pin) != 0x00u)   ← 先确认是不是这个脚触发的
        {
            __HAL_GPIO_EXTI_CLEAR_IT(GPIO_Pin);          ← ★ 清挂起标志
            HAL_GPIO_EXTI_Callback(GPIO_Pin);            ← 再调你自己的回调
        }
    }

        ↓

第 3 层：你的回调（写在 main.c 里，覆盖 HAL 的 __weak 版本）

    void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
    {
        if (GPIO_Pin == KEY_Pin) { g_key_pressed = 1; }
    }

★ 两个要点：
  1. HAL 是【先清标志、再调回调】。所以你在回调里不需要、也不应该再清一次标志。
  2. 回调的参数 GPIO_Pin 是从第 1 层一路传下来的，
     它就是“哪一条 EXTI 线触发了”的唯一线索。
     5~9 号线和 10~15 号线共用一个中断入口，
     不在回调里判断这个参数，多个按键就会互相串。

还有一个必须知道的细节：HAL 库里的回调函数是 用 __weak 修饰的弱符号。 所谓弱符号，意思是“如果工程里别处有一个同名同参数的强符号，链接器就用那个，丢掉我这个”。 所以你在 main.c 里写一个同名的函数， 不需要删掉 HAL 里的那个，链接器会自动用你的版本。 这也解释了一个非常隐蔽的坑：如果你的函数签名和 HAL 的不完全一致， 它就是一个新函数而不是覆盖，编译链接都不会报错， 但 HAL 仍然调用它自己那个空的弱版本——现象就是“中断能进去，但我的代码没执行”。 这个坑的排查方法写在后面的报错排查一节里。

回调函数的签名必须逐字一致

void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)

返回类型 void、参数类型 uint16_t、 参数名 GPIO_Pin（参数名其实不影响链接，但建议保持一致便于对照）。 最常见的错误是把参数写成 uint8_t 或者 GPIO_TypeDef *，觉得“反正都是表示哪个脚”—— 一旦写错，你的函数就再也不会被调用了。

硬件接线说明

这一节的例子是：一个按键接在 PA0，按下时翻转板载 LED（PC13）。 按键的接法决定了触发边沿怎么选，这是接线和代码之间唯一的耦合点，先想清楚再动手。

元件与接线表

元件 引脚 / 规格 连接到 说明
轻触按键 一端 蓝药丸的 PA0 PA0 配成 EXTI 输入，内部上拉
轻触按键 另一端 蓝药丸的 GND 接 GND 而不是 3.3V，这样按下是低电平，用下降沿触发
内部上拉 约 40kΩ CubeMX 里选 Pull-up 省掉外部电阻。空闲时 PA0 是高电平，按下被拉到 GND
硬件消抖电容（可选） 100nF 并在按键两端（PA0 与 GND 之间） 能把大部分抖动滤掉，但软件消抖仍然要做
板载 LED PC13 板上已接好，无需外部接线 低电平点亮，配成 GPIO_Output 即可
供电 3.3V / 5V ST-Link 或 USB 本页不需要串口，接线越少越容易排查

CubeMX 配置步骤

EXTI 的配置分散在三个页面上，顺序无所谓，但三处都要改到： 

【第 1 步】选引脚
   Pinout & Configuration 页，在芯片图上左键点 PA0
   → 弹出菜单里选 GPIO_EXTI0
   （选完引脚会变成绿色，标着 EXTI0）

【第 2 步】配 GPIO 参数
   System Core → GPIO → 点选 PA0 那一行，右边出现参数：

     GPIO mode            = External Interrupt Mode with Falling edge trigger detection
                            ★ 选 Falling（下降沿），因为按下时是高→低
     GPIO Pull-up/Pull-down = Pull-up
                            ★ 选上拉，空闲时引脚是高电平，不用外接电阻
     User Label           = KEY
                            ★ 这个标签决定了生成代码里的宏名，填 KEY
                              就会生成 KEY_Pin 和 KEY_GPIO_Port

   再点 PC13（板载 LED）：
     GPIO mode        = GPIO_Output
     GPIO output level= High        （高电平 = LED 灭，上电时不亮）
     GPIO Pull-up/Pull-down = No pull-up and no pull-down
     Maximum output speed   = Low   （驱动 LED 不需要快）
     User Label       = LED

【第 3 步】使能 NVIC 中断
   System Core → NVIC，找到 "EXTI line0 interrupt"

     勾选 Enabled 那一列的复选框        ★ 不勾这里，前面两步白做
     Preemption Priority = 2            （数值小的先执行）
     Sub Priority        = 0            （分组 4 下这个值不起作用）

   ★ 顺便确认右下角 NVIC 的 "Priority Group" 显示的是
     "4 bits for pre-emption priority"，这是 HAL 默认值。

如果你的板子上自带 KEY 按键

蓝药丸的很多版本板载了一个标着 KEY 或 USER 的按键。 但不同批次的接法不一定相同：

  • 如果 KEY 按下时 PA0 变低（另一端接 GND）——按本页的配置走，选下降沿 + 上拉。
  • 如果 KEY 按下时 PA0 变高（另一端接 3.3V，板上带下拉电阻）——把 GPIO 模式改成 Rising edge trigger detection，上拉/下拉改成 Pull-down。

分不清怎么办？最稳的办法是用万用表量： 断电，用蜂鸣档量按键两端，按下时导通的那一端就是 GND 侧。 或者干脆不纠结，外接一个轻触开关按本页的接法接——多花两分钟，少猜半小时。

完整代码

全部逻辑都在这一个 main.c 里。 请在 CubeMX 生成的 main.c 基础上， 把 USER CODE 注释块之间的内容换成下面的代码—— 这样下次重新生成代码时你写的东西不会被冲掉。 

/* =====================================================================
 * main.c —— PA0 按键外部中断翻转 PC13 板载 LED
 * 芯片：STM32F103C8T6（蓝药丸）
 * 库  ：STM32F1 HAL 库
 * 工具：STM32CubeMX 生成工程 + Keil MDK 5 编译
 * ---------------------------------------------------------------------
 * CubeMX 关键配置回顾：
 *   PA0  → GPIO_EXTI0，Falling edge，Pull-up，User Label = KEY
 *   PC13 → GPIO_Output，初始 High，User Label = LED
 *   NVIC → EXTI line0 interrupt 已勾选 Enabled
 *          Preemption Priority = 2，Sub Priority = 0
 *
 * 设计思路（本页的核心）：
 *   中断回调【只置一个标志位】，按键消抖和 LED 翻转都放在主循环里做。
 *   这样中断的执行时间只有几个时钟周期，
 *   既不会阻塞其他中断，也不可能因为等待而卡死。
 * ===================================================================== */
#include "main.h"
#include "gpio.h"

/* ---------------------------------------------------------------------
 * ★ 被中断和主循环同时访问的变量必须加 volatile
 *
 * volatile 告诉编译器：“这个变量的值可能在任何时刻被别处的代码改掉，
 * 每次用到它都要老老实实回内存里读，不许缓存进寄存器，也不许优化掉。”
 *
 * 不加会怎样？主循环写成 while (g_key_pressed == 0) {} 时，
 * 编译器会发现循环体里没有代码修改 g_key_pressed，
 * 于是把它的值读到寄存器里，之后一直拿寄存器里的旧值比较 ——
 * 结果是无论中断怎么改这个变量，主循环都看不见。
 * ------------------------------------------------------------------- */
static volatile uint8_t  g_key_pressed = 0U;    /* 1 = 有一次按下事件待处理 */
static volatile uint32_t g_key_count   = 0U;    /* 累计按下次数，调试和演示用 */

/* ---------------------------------------------------------------------
 * ★★★ 中断回调函数
 *
 * 它是 HAL 库的弱符号 HAL_GPIO_EXTI_Callback 的覆盖版本。
 * 函数签名必须和 HAL 里的【逐字一致】，否则就成了另一个函数，
 * HAL 永远不会调用它（而且编译链接都不报错，是最隐蔽的坑）。
 *
 * 参数 GPIO_Pin：告诉我们这一次是哪条 EXTI 线触发的。
 *   如果只配了一个中断，判断一下是防御性写法；
 *   如果配了多个（比如 PA0 和 PA1），这个判断就是必需的。
 *
 * ★ 这个函数运行在中断上下文里，所以它必须：
 *     - 极短。目标 10µs 以内，只做“记录事件”，不做“处理事件”。
 *     - 只碰 volatile 变量和简单计数器。
 *     - 不调用任何阻塞函数（HAL_Delay / printf / HAL_UART_Transmit ...）。
 *   详细的“为什么”见正文里“中断里绝对不能做的事”那一节。
 * ------------------------------------------------------------------- */
void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
{
    if (GPIO_Pin == KEY_Pin)        /* KEY_Pin 由 CubeMX 根据 User Label 生成 */
    {
        g_key_pressed = 1U;         /* 插一面旗子，就这一件事 */
        g_key_count++;              /* 一次自增，代价只有几个时钟周期 */
    }
    /* 注意：挂起标志已经由 HAL_GPIO_EXTI_IRQHandler 清掉了，
     * 这里不需要、也不应该再清一次。 */
}

/* ---------------------------------------------------------------------
 * 主循环里处理按键事件：消抖 + 翻转 LED
 *
 * 为什么消抖放在主循环而不是中断里？
 *   因为消抖需要等 20ms，而中断里不能做任何等待。
 *   主循环里 HAL_Delay 是完全合法的 —— 它本来就该在这里用。
 * ------------------------------------------------------------------- */
static void Key_Process(void)
{
    if (g_key_pressed == 0U)
    {
        return;                     /* 没有按键事件，直接走人，不浪费时间 */
    }

    /* 1) 先等 20ms 让机械抖动过去。
     *    机械按键在按下和松开的瞬间会产生持续几百微秒到几毫秒的
     *    一连串毛刺，每个下降沿都会触发一次中断。
     *    这里等一下，就把这一串毛刺压缩成“一次按键”。 */
    HAL_Delay(20);

    /* 2) 抖动过去之后再看引脚电平。
     *    如果还是低电平，说明手指真的按着，是一次有效按键；
     *    如果已经回到高电平，说明刚才只是毛刺，直接忽略。 */
    if (HAL_GPIO_ReadPin(KEY_GPIO_Port, KEY_Pin) == GPIO_PIN_RESET)
    {
        /* 3) 翻转板载 LED。PC13 是低电平点亮，
         *    所以 Toggle 之后亮灭状态就反过来了。 */
        HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);
    }

    /* 4) ★ 最后才清标志，这个顺序很重要。
     *    如果在第 1 步之前就清掉，那么这 20ms 抖动期间产生的
     *    新中断又会把标志置 1，下一轮循环就会重复翻转一次 LED ——
     *    按一下亮、再闪一下，看起来像“按一次跳两下”。
     *    放在最后清，抖动期间的所有中断都被这一次处理一并吃掉。 */
    g_key_pressed = 0U;
}

/* ---------------------------------------------------------------------
 * 主函数
 * ------------------------------------------------------------------- */
int main(void)
{
    /* HAL 库初始化：配置 SysTick 为 1ms 心跳。
     * 注意：HAL_Init() 内部就会调用 HAL_InitTick()，
     * 把 SysTick 的优先级设成 TICK_INT_PRIORITY = 0x0F。 */
    HAL_Init();

    /* 系统时钟配置到 72MHz，必须在所有外设初始化之前 */
    SystemClock_Config();

    /* CubeMX 生成的外设初始化。
     * MX_GPIO_Init() 里就包含了：
     *   - PA0 配成 EXTI 下降沿触发 + 上拉
     *   - PC13 配成推挽输出
     *   - HAL_NVIC_SetPriority(EXTI0_IRQn, 2, 0)
     *   - HAL_NVIC_EnableIRQ(EXTI0_IRQn)      ← 真正让中断生效的一句 */
    MX_GPIO_Init();

    /* 开机先让 LED 灭（高电平）并闪一下，证明程序确实跑起来了 */
    HAL_GPIO_WritePin(LED_GPIO_Port, LED_Pin, GPIO_PIN_RESET);  /* 亮 */
    HAL_Delay(200);
    HAL_GPIO_WritePin(LED_GPIO_Port, LED_Pin, GPIO_PIN_SET);    /* 灭 */
    HAL_Delay(200);

    while (1)
    {
        /* 主循环是干正事的地方：
         * 处理中断插下的旗子、做耗时计算、刷新显示、通信……
         * 本页只有一个按键要处理，所以就这一句。 */
        Key_Process();

        /* 让出一点时间，避免主循环空转把 CPU 占满。
         * 这个延时不会影响按键响应 —— 因为按键是靠中断记录的，
         * 就算主循环正在这 10ms 的延时里，按下按键也会被立刻记下来。 */
        HAL_Delay(10);
    }
}

关键代码解析

  • static volatile uint8_t g_key_pressed = 0U;—— 两个关键字各有分工。static 让变量只在 main.c 内部可见，避免和其他文件的同名变量冲突； volatile 则保证编译器每次都从内存读。 只要一个变量会被中断改写、又在主循环里被读，就必须加 volatile， 这是没有例外的规则。
  • if (GPIO_Pin == KEY_Pin)—— 为什么要判断？因为 EXTI9_5 和 EXTI15_10 这两组共用一个中断入口，回调被调用时并不自动知道是谁触发的， 全靠这个参数。即使现在只配了一个中断，写上判断也是好习惯—— 以后加第二个按键时，不加判断就会两个按键互相串。
  • g_key_pressed = 1U;—— 中断里只做这件事，是因为它只需要一条指令、几个时钟周期。 对比一下：如果在这里直接 HAL_GPIO_TogglePin， 倒也不会卡死（HAL_GPIO_TogglePin 只是读写寄存器，不依赖 tick）， 但那就把“按键事件”和“LED 行为”绑死了。 用标志位解耦之后，主循环里可以把同一个按键用来切菜单、改参数、启停采集—— 中断完全不用改。
  • HAL_Delay(20) 放在主循环里——完全合法。 主循环不是中断上下文，SysTick 可以正常打断它， uwTick 正常增长，延时正常工作。 同一个函数，在中断里是毒药，在主循环里是良药—— 区分标准就是“当前是不是在中断上下文里”。
  • if (HAL_GPIO_ReadPin(...) == GPIO_PIN_RESET)—— 消抖的经典两步法：先等一段时间，再看电平。 这里有个容易忽略的细节：判断用的是当前电平而不是 “又收到一次中断”，所以即使手指按了很久，也只会翻转一次。 如果改成“等 20ms 后再检查标志位”，长按就会连续翻转。
  • g_key_pressed = 0U; 放在函数末尾—— 顺序问题，前面代码注释里已经讲了完整原因。 这里再强调一次原则： “清标志”要放在“处理完事件”之后，而不是之前， 这样处理期间新产生的事件只会被合并，不会被漏掉也不会被重复处理。

中断里绝对不能做的事

下面这张表是这一篇最该背下来的内容。 注意每一行的“为什么”都指向同一个根源： 中断服务程序执行期间， 同优先级和更低优先级的中断全都被挡住了。

不要在中断里做 为什么 会看到什么现象 应该怎么做
HAL_Delay()
以及一切基于 uwTick 的等待		 SysTick 优先级 0x0F 最低，ISR 执行期间 uwTick 停止增长，延时条件永远不成立 中断永不返回，程序假死；其他中断全部无响应 只置标志位，延时和等待搬到主循环
printf()
大量数据打印		 printf 底层是阻塞发送。115200 波特率下 1 字节约 87µs，打印 20 字节就要 1.7ms ISR 长得离谱，期间其他中断被延迟；连续事件（比如编码器脉冲）大量丢失 中断里把数据存进缓冲区，主循环里统一打印
while 等硬件标志
（等 ADC 转换完、等 I2C ACK）		 在中断里“等”，期间所有同/低优先级中断都进不来。硬件出问题时就是死循环 偶发卡死，且难以复现（只在某个硬件异常时出现） 用带超时的版本，且超时值不能依赖 tick；更好的做法是整体搬到主循环
浮点运算 STM32F1 没有硬件浮点单元（FPU），一个浮点乘法要几百个时钟周期，且软件浮点库占用栈空间大 ISR 时间远超预期，串口/定时器中断开始丢事件 改用整数或定点运算（比如用毫伏代替伏特，用放大 1000 倍的整数代替小数）
长的 for 循环、大数组拷贝 同样是把 ISR 拉长。ISR 的目标时长是几十微秒，不是几十毫秒 系统响应变迟钝，高频率事件丢失 中断里只记录“有新数据”，主循环里做批量处理
判断标准：打断你的成本有多高

拿不准某个操作能不能放进中断时，问自己两个问题：

  1. 它要花多长时间？ 超过约 50µs 就该考虑搬到主循环。
  2. 它会不会等？ 只要带“等”的动作（等延时、等标志、等发送完），一律不能放中断里。

两个问题都过关，才可以在中断里做。 中断的职责是“记录发生了什么”，不是“处理发生的事情”。

现象演示说明

烧录完成后，下面这张表把“你看到的”和“它说明什么”对应起来。 按键实验的现象很直观，但“按一次跳两下”这类问题光看现象分不清原因，所以要对着表查。

正确现象

  1. 上电后板载 LED 先亮 200ms 再灭 200ms，这是程序启动的握手信号。
  2. 之后 LED 保持熄灭，直到你按下按键。
  3. 每按一次按键，LED 状态翻转一次：亮 → 灭 → 亮 → 灭，交替进行。
  4. 按一次只翻转一次，不会出现连跳两三下的情况。
  5. 手指按住不放，LED 只翻转一次，不会连续闪烁。
  6. 快速连续按十几次，每一次都会被记录并翻转，没有漏掉任何一次。

观察点与判据

你观察到的 说明什么 下一步查什么
LED 一直不亮，按键也没反应 程序可能根本没跑起来，或者卡在了某个地方 先确认开机的“亮 200ms → 灭 200ms”握手信号有没有出现；没有就是时钟或下载的问题
按一次 LED 跳两下或三下 典型的按键抖动没处理干净 确认 HAL_Delay(20) 还在、且是在清标志之前；把延时加到 30~50ms 试试；机械质量差的按键需要在两端并 100nF 电容
按住不放，LED 连续闪 触发边沿配成了双边沿，或者判断逻辑写成了“看标志位”而不是“看电平” CubeMX 里确认 PA0 是 Falling edge 而不是 Rising and Falling edge
按键完全没反应，但程序在正常跑 中断没使能，或者回调没被执行 ① NVIC 页里 EXTI line0 有没有勾 Enabled；② 在回调里翻转另一个 GPIO 或用调试器打断点，看它到底进没进去
松手时才翻转，方向反了 接法和你选的边沿不匹配：按键另一端接的是 3.3V 而不是 GND 万用表量一下空闲电平。空闲高、按下低 → 用下降沿；空闲低、按下高 → 用上升沿
不按按键 LED 也偶尔自己翻转 引脚悬空导致电平漂移，或长导线拾取了干扰 确认 GPIO 配了 Pull-up；缩短按键引线；在 PA0 与 GND 之间并 100nF 电容
程序下载一次之后就再也连不上调试器 可能误用了 PA13/PA14 做中断输入，把 SWD 口占了 按住复位键再点下载，松开复位进入下载模式；然后把中断换到别的引脚
用调试器看清楚“中断有多短”

这一步很值得做，因为它能把“中断要短”这句抽象的话变成看得见的数字：

  1. 在 HAL_GPIO_EXTI_Callback 的第一行和最后一行各设一个断点。
  2. 进入调试模式，全速运行，按一下按键。
  3. 程序停在第一个断点时，打开 Keil 的 States 窗口（View → Registers）， 或者用 Trace → 时间测量，看一下两次停住之间经过了多少个时钟周期。

你会发现这个回调只花了不到 10 个时钟周期，也就是 72MHz 下的零点几微秒。 然后做个对比实验：在回调里加一句 HAL_Delay(100)， 再按一次按键——程序会直接卡死在里面，再也回不到主循环。 亲手制造一次这个死锁，比读十遍“中断里不能延时”都记得牢。

常见报错排查方案

EXTI 的坑有个共同特点：大多数不报编译错误， 只是静静地不工作。所以下面每一节都给出“怎么用最短的时间判断问题出在哪一层”。

编译报错：error: #167: argument of type "GPIO_TypeDef *" is incompatible with parameter of type "uint16_t"

原因：回调函数的参数类型写错了。有人觉得“回调要知道是哪个引脚，那应该传端口指针”，于是写成 void HAL_GPIO_EXTI_Callback(GPIO_TypeDef *GPIOx)。但 HAL 里的原型是 uint16_t GPIO_Pin，类型不匹配。

解决：签名必须逐字对齐 HAL： void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)。 Keil 报 #167 时基本都是这一类“参数类型不兼容”。 如果报的是 #147: declaration is incompatible with previous， 意思一样，也是原型对不上。

现象：中断能进去（断点能停住），但我的代码没执行——而且一条错误都没有

原因：这是最隐蔽的坑。回调在 HAL 里是 __weak 弱符号，只有当你的函数名称和参数完全一致时才构成覆盖。如果你把函数名拼成了 HAL_GPIO_EXTI_CallBack（大写 B）、或者参数写成了 uint8_t，它就是一个全新的、没人调用的函数。链接器不会报错，因为弱版本已经存在了，你只是多定义了一个无关函数。

解决：两个确认办法。 ① 把你的回调函数临时删掉再编译——如果还能编译通过，说明 HAL 的弱版本确实在，你的覆盖关系要靠名字匹配才成立； ② 更快的办法是在回调第一行加一句 HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);， 如果按键时 LED 不翻转，就说明回调根本没被调用，直接回头核对拼写和参数类型。 建议从 HAL 头文件里把原型复制粘贴过来，不要手敲。

现象：一按按键程序就卡死，主循环再也不执行，LED 定在某个状态

原因：回调里调用了 HAL_Delay（或者任何依赖 uwTick 的函数）。 SysTick 优先级是 0x0F 最低，EXTI 优先级更高，所以中断执行期间 SysTick 完全被挡住， uwTick 不再增长，HAL_Delay 的循环条件永远成立。 这不是“延时不准”，而是永久死循环。

解决：把回调清理成只做“置标志位 + 简单计数”。 需要延时、需要等待的部分全部搬到主循环。 顺手检查一下有没有 printf—— 如果 printf 重定向用的是 HAL_UART_Transmit(..., HAL_MAX_DELAY)， 虽然它靠的是标志位而不是 tick（不一定会死锁），但同样会让 ISR 长达毫秒级，属于必须搬走的操作。

现象：中断只响应第一次，之后再按按键毫无反应

原因：挂起标志没被清掉。绝大多数情况是你自己写了 EXTI0_IRQHandler，在里面直接写业务代码，却没有清 EXTI 的挂起寄存器 PR。PR 位一直是 1，NVIC 认为这次中断还没被处理完，就不会再产生新的中断请求。另一种可能是你在 ISR 里阻塞了，后续边沿被吞掉。

解决： ① 推荐做法：不要在 stm32f1xx_it.c 里写业务代码，让 CubeMX 生成的 EXTI0_IRQHandler 保持原样（它只调用 HAL_GPIO_EXTI_IRQHandler，而后者会清标志并调你的回调）。 ② 如果你非要自己写：必须在处理完业务后手动清标志 __HAL_GPIO_EXTI_CLEAR_IT(GPIO_PIN_0);， 而且要在调用业务代码之前清，否则业务处理期间的新边沿会被丢掉。

现象：配了两个按键中断，只有一个能用；或者按 A 键触发的是 B 键的处理

原因：两种可能。 ① EXTI 线冲突：两个按键用了“同 pin 号、不同端口”，比如 PA0 和 PB0。 EXTI0 这条线只能映射到一个端口，后配置的会把前一个顶掉，所以只有一个能工作。 ② 回调里没做区分：如果两个按键是 PA6 和 PA7，它们共用 EXTI9_5_IRQHandler， 回调被调用时不判断 GPIO_Pin 就会两个都走同一段代码。

解决： ① 让两个按键用不同的 pin 号（PA0 配 PA1，而不是 PA0 配 PB0）。 记住这条规则：EXTI 按 pin 号分线，不按端口分线。 ② 在回调里老老实实写 if (GPIO_Pin == KEY1_Pin) {...} else if (GPIO_Pin == KEY2_Pin) {...}。

小结与练习

这一篇的主线是“中断让等待不占用 CPU，代价是中断里不能等”。 把下面五条结论带走就够用了：

  • EXTI 按 pin 号分线，一条线只能映射一个端口，且 5~9、10~15 两组共用中断入口，必须在回调里按 GPIO_Pin 区分。
  • 抢占优先级决定能不能嵌套，响应优先级只决定同时挂起时谁先跑；HAL 默认分组 4，全部 4 位都给抢占，取值 0~15，数字越小越优先。
  • SysTick 优先级固定 0x0F（最低），因为它不紧急，也因为它必须是“能被所有中断挡住”的那一个。
  • 中断执行期间 uwTick 不增长，所以一切基于 tick 的等待在中断里都会变成永久等待——这是“中断里不能 HAL_Delay”的硬件根据。
  • 回调只置标志位，主循环里处理事件。这样中断永远只有几微秒，消抖、显示、通信这些耗时操作都在可以安全等待的主循环里做。

最后再强调一下回调签名的价值： HAL 的所有回调都是弱符号，靠“名称 + 参数类型完全一致”来覆盖。 这一条不只适用于 HAL_GPIO_EXTI_Callback， 对 HAL_ADC_ConvCpltCallback、 HAL_UART_RxCpltCallback、 HAL_TIM_PeriodElapsedCallback 全都成立。 以后碰到“中断进去了但我的代码没跑”，第一反应就该是去核对原型。

动手练习
  1. 改成两个按键，用中断分别控制。 再加一个按键接到 PA1（注意：要用不同的 pin 号，不能接 PB0）。 PA0 翻转 LED，PA1 做另一个动作（比如让 LED 快闪三次再熄灭）。 要求：主循环里根据两个不同的标志位分别处理。 提示：EXTI0 和 EXTI1 的优先级可以设成一样； 想想看，如果两个按键几乎同时按下，谁会先被处理？为什么？
  2. 把消抖从“延时判断”改成“计数判断”。 现在的做法是在主循环里 HAL_Delay(20)， 这 20ms 里主循环什么也干不了。请改成非阻塞的写法： 用 HAL_GetTick() 记录按键事件发生的时间戳， 主循环里每次检查“距离上次事件是否已经过去 20ms”， 是的话再读电平并处理，否则直接跳过。 改完之后，主循环在等待消抖期间也能做别的事了。 再想一想：这种方式和 HAL_Delay(20) 相比， 在“主循环要做 300ms 一次的显示刷新”时有什么优势？
  3. 亲手做一次“中断里延时”的死锁实验，然后用调试器定位。 在回调里加一句 HAL_Delay(100)， 按一下按键，观察程序卡死。 然后用调试器点“暂停（Stop）”，看调用栈停在哪里 （应该在 HAL_Delay 的 while 循环里）。 记下你看到的现场，再把这个实验结论写进你的实验报告—— 这种“我制造了一个 bug 并定位了它”的记录， 比只写“中断里不能延时”有说服力得多。
