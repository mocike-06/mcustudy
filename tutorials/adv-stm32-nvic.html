STM32 中断系统与 NVIC 优先级

「中断」这件事的通用原理——向量表是什么、为什么要保护现场、为什么中断必须短—— 在 中断与异常机制 那一篇里已经讲透了。 这一篇不重复那些，只回答一个更具体的问题：这些原理在 STM32F103 这颗芯片上，具体是哪几个寄存器、哪几个函数、哪几行代码在负责？ 同样是「配一个外部中断」，51 上你写 IT0 = 1; EX0 = 1; EA = 1; 三行就够了； 在 STM32 上你要依次照顾引脚模式 → AFIO 时钟 → EXTICR 端口选择 → 触发沿 → EXTI 屏蔽位 → NVIC 使能 → 优先级数值七件事， 任何一件漏掉，现象都是同一句话：「中断没反应」。而配错了优先级分组或者把优先级数值写成了位， 现象又会变成「能进中断，但偶尔丢数据、偶尔卡死」——比完全不来更折磨人。

这一篇的钥匙只有一句话：中断是「外设 → EXTI → NVIC → 向量表 → 你的函数」这条链子， 链上任何一环没使能，现象都是「中断不来」；
而链上的优先级那一环写错，现象是「能来但乱」。

为什么需要它

先把这一篇的定位说清楚。上一层的 中断与异常机制 讲的是机制：中断向量表是一张「异常号 → 处理函数」的表格、中断比轮询省 CPU、进入中断要保护现场、 中断服务函数必须短、优先级决定了谁能打断谁。这些结论在 51、STM32、ESP32 上都成立，属于「换个芯片也不会变」的知识。

但真正动手写代码时，你面对的从来不是这些结论，而是这样三个现场。

三个故障现场，全都不是「原理没学会」造成的

现场一：两个按键，只有一个能用。你在 PA0 和 PB0 各接了一个按键，都配成了下降沿触发的外部中断， 代码编译通过、烧进去也能跑——但 PB0 那个键从头到尾没有反应。你去查中断原理，查不出任何问题， 因为问题出在 STM32 的一条硬约束上：EXTI 的线号等于引脚号，PA0 和 PB0 抢的是同一根 EXTI0 线， 而 AFIO 里那个 4 位的选择字段只能填一个值。你后初始化谁，谁就赢。

  PA0 ──┐
        ├──▶ [ AFIO_EXTICR1 的 EXTI0[3:0] 字段 ]  ──▶ EXTI0 线 ──▶ NVIC

                  │  初始化顺序：先 PA0 后 PB0

      PA0 (EXTI0) + PB0 (EXTI0)   ✘ 抢同一根线，只能活一个

现场二：按键按一下，中断进了七八次。示波器上看，一个机械按键按下的瞬间， 触点会在 5~10ms 里反复弹跳十几下。你开的是边沿触发，每一个下降沿都是一次合法中断， 于是「按一次，加七次」。这时候你会以为是中断配错了，其实是触发沿的选择与去抖的责任划分没想清楚。

现场三：中断里等一会儿，程序再也不动了。你在串口接收中断里想「等 1ms 再发下一帧」， 顺手写了 HAL_Delay(1)。程序没有报错，编译器也不警告， 但它就停在那里了——因为 HAL_Delay 等的是 uwTick 变大， uwTick 靠 SysTick 中断累加，而 HAL 把 SysTick 的优先级设成了最低的 15， 它永远抢不过你正在执行的那个中断。你在中断里等 SysTick，SysTick 在等你退出中断，死锁。

先给一个能保命的心智模型

在 STM32 上，一次外部中断从物理世界走到你的 C 函数，固定要过五道关卡， 顺序不能乱、一道不能少： 

①  引脚模式         GPIOx_MODE / CNF：必须配成「输入」且使能了复用（HAL 里的 GPIO_MODE_IT_xxx）
        ↓
②  端口选择         AFIO_EXTICR1~4：把 EXTI 线的输入源选到 PA / PB / PC …（需要 AFIO 时钟！）
        ↓
③  触发沿与屏蔽     EXTI->RTSR / FTSR / IMR：哪种边沿、要不要产生中断
        ↓
④  NVIC 使能        NVIC->ISER[n]：把这一路请求接到 CPU 上（EXTI 与 NVIC 是两级使能，都要开）
        ↓
⑤  优先级           NVIC->IPR[n] 的高 4 位 + AIRCR.PRIGROUP：能不能打断别人、谁先跑
        ↓
   向量表            SCB->VTOR 指向的那张表：异常号 → 函数地址（默认 0x08000000）
        ↓
   你的函数          EXTI0_IRQHandler() → HAL_GPIO_EXTI_IRQHandler() → HAL_GPIO_EXTI_Callback()
────────────────────────────────────────────────────────────
排查口诀：中断不来，从 ① 往下逐关查；中断来了但乱，直接查 ⑤。

异常向量表：表里放的是地址，地址最低位必须是 1

向量表的本质在 中断与异常机制 里已经定义过了：一张「异常号 → 处理函数地址」的数组，放在内存的固定位置，CPU 响应中断时按异常号去查表。 这里只补 STM32 这一侧你必须知道的三件事：表的尺寸与位置、表里的地址长什么样、表是谁写进去的。

Cortex-M3 规定异常号 0~15 属于内核异常（Reset、NMI、HardFault、SVCall、PendSV、SysTick 等）， 异常号 16 往上属于外部中断 IRQ，最多 240 个（IRQ0~IRQ239）。 ST 在 STM32F103 上排了 60 个外部中断（IRQ0~IRQ59），所以 F103 的向量表一共 16 + 60 = 76 项， 每项 4 字节，共 304 字节。

项 0 不是异常，是栈顶

很多人第一次看向量表会数错：表里的第 0 项（偏移 0x00）不是任何异常的处理函数， 它是「复位完成后，MSP 该被设成多少」，所以它填的是一个 RAM 地址（典型是 RAM 末尾 0x2000_5000）， 而不是代码地址。真正的 Reset 向量在偏移 0x04。这一点在你自己写 Bootloader 的链接脚本时极其重要： APP 的向量表也必须自己排好项 0，否则重定位之后一进中断就崩。

接下来是最容易被忽略、但一旦错就必死的一条规则：向量表里填的每一项，除了第 0 项，都是一个函数地址； 而 Cortex-M 要求这个地址的最低位（bit 0）必须是 1。 

真 实 的 向 量 表 内 容（用调试器看内存，以 0x08000000 开头）
────────────────────────────────────────────────────────────
0x08000000: 00 50 00 20     → 0x20005000   项0：栈顶（RAM 地址，最低位无意义）
0x08000004: A5 01 00 08     → 0x080001A5   项1：Reset_Handler
                                    ↑
                                    └── 这个 1 是 Thumb 标记，不是地址的一部分

为什么不加这个 1 就崩：
  Cortex-M3 只有 Thumb 指令集，没有 ARM 指令集
  CPU 从向量里取出地址后，用 BX 的方式跳过去
    · 地址最低位 = 1  →  进入 Thumb 状态  →  正常执行
    · 地址最低位 = 0  →  试图进入 ARM 状态 →  Cortex-M3 不支持 → HardFault
────────────────────────────────────────────────────────────
所以：用 C 写出来的函数，编译成 Thumb 之后符号值天然是最低位 1
      （链接器对 Thumb 函数的符号会 +1），你写 .word Reset_Handler 就自动带上了
      真正会踩坑的是「手写一个函数地址常量」的时候：
         uint32_t addr = 0x080001A4;        /* 从调试器抄下来忘了 …那是偶数地址 */
         ((void(*)(void))addr)();          /* → HardFault */
      正确写法：((void(*)(void))(addr | 1U))();
────────────────────────────────────────────────────────────

向量表默认住在 0x08000000。严格说，复位时 CPU 是从 0x00000000 取项 0、从 0x00000004 取 Reset 向量的——而 STM32 会把不同的物理存储区映射到 0x00000000： BOOT0 = 0 时映射的是 Flash（也就是 0x08000000 的那块），BOOT0 = 1 时映射的是系统存储器（出厂 Bootloader）。 这就是「启动模式」那三个 BOOT 配置真正在做的事（第 39 篇会展开讲）。 对你的影响只有一句：平常写代码时，把向量表的地址就当成 0x08000000 来理解。

真正需要「挪动」向量表的场景是 IAP（在应用编程，也就是自己做 Bootloader 升级固件）。 设想 Flash 被切成两块：Bootloader 占 0x08000000 起的 16KB，APP 从 0x08004000 开始。 上电后 CPU 从 0x08000000 取向量，跳进 Bootloader；Bootloader 判断要启动 APP，就跳到 0x08004000。 可是 APP 的代码和数据都住在 0x08004000 往后，它的向量表也在那里—— 而 CPU 仍然以为向量表在 0x08000000（那还是 Bootloader 的表）。 这时 APP 里任何一次中断，都会跳进 Bootloader 的中断处理函数，后果不可预测。

解法就是在 APP 启动的第一件事里，把 SCB->VTOR 改成 APP 自己的向量表地址： 

#include "stm32f1xx.h"

/* APP 在 Flash 里的起始地址，必须和 Bootloader 里的约定、以及 APP 工程的
   IROM1 起始地址、链接脚本里的 FLASH ORIGIN 完全一致 */
#define APP_BASE_ADDR     0x08004000U

/* 这个函数必须在 main() 里的第一件事就调用，而且要在
   HAL_Init()、任何 __enable_irq()、任何外设初始化之前。
   否则一旦在重定位前来了中断，跑的就是 Bootloader 的处理函数。 */
void app_relocate_vector_table(void)
{
    /* SCB->VTOR 是 32 位寄存器，低 7 位（有的内核是低几位）是保留位，
       写入的地址必须对齐：最小 128 字节，且不小于向量表实际大小
       向上取到 2 的幂。F103 的表是 304 字节 → 必须 512 字节对齐。
       0x08004000 % 512 == 0，满足。 */
    SCB->VTOR = APP_BASE_ADDR;

    /* 顺手确认一下：读回来应该等于你写进去的值（低 7 位会被硬件忽略） */
    if (SCB->VTOR != APP_BASE_ADDR) {
        /* 走到这里说明对齐算错了，或者写的是非法地址 */
        while (1) { }
    }
}

/* 从 Bootloader 跳转到 APP 的经典写法（放 Bootloader 侧，供对照） */
typedef void (*app_entry_t)(void);

void boot_jump_to_app(void)
{
    uint32_t app_msp  = *(volatile uint32_t *)(APP_BASE_ADDR);        /* 项0：栈顶 */
    uint32_t app_reset = *(volatile uint32_t *)(APP_BASE_ADDR + 4U);  /* 项1：Reset 向量 */

    /* 合法性检查：栈顶必须落在 RAM 范围内（F103C8T6 的 RAM 是 0x20000000~0x20004FFF） */
    if ((app_msp & 0x2FFE0000U) != 0x20000000U) {
        return;                        /* 表是空的，别跳，跳了就是 HardFault */
    }

    __disable_irq();                   /* 跳转前先关中断，别让残留的请求打进 APP */
    SysTick->CTRL = 0U;                /* 关掉 SysTick，否则它的中断会打到旧向量表 */

    /* 设好栈顶，再跳到复位向量。app_reset 的最低位天然是 1（Thumb 标记），
       所以这里不需要手动 | 1 —— 但如果你是从别处算出来的地址，必须自己补上 */
    __set_MSP(app_msp);
    ((app_entry_t)app_reset)();
}
为什么这段代码里到处是「必须第一件事」

因为 SCB->VTOR 换的是查表用的基地址，它管的是「下一次」中断去哪里。 已经挂起（pending）的中断不受影响，但站在代码顺序上，你不会希望有任何一次中断发生在重定位之前。 工程上的做法是：APP 的 Reset_Handler 里、进 main() 之前就重定位， 或至少是 main() 的第一行。第 39 篇会给出完整的两区工程。

.weak 是链接器的一个指令，意思是「这个符号的优先级很低」。 于是链接时会出现这样的裁决：启动文件里有一个弱的 EXTI0_IRQHandler， 你在自己的 main.c 或 stm32f1xx_it.c 里写了一个强的同名函数—— 链接器会选你的那个，丢掉 b .。 这就是「你只要写一个同名函数就能覆盖它」的全部原理。

它有两层实践意义：

  • 写错名字不会报错，只会卡死。把 EXTI0_IRQHandler 写成了 EXTI0_Handler、或者加了 static（那就变成内部链接，链接器看不见）、 或者在 C++ 里忘了 extern "C"（名字被修饰成 _Z16EXTI0_IRQHandlerv）—— 编译全都通过，链接也不报错，因为弱符号替你把缺补上了。运行时现象是：中断确实来了，但程序卡在启动文件的 b . 上， 你在 main 里打断点看不出任何问题。 排查方法：在调试器里暂停，看 PC 指向哪个地址，或者直接看反汇编窗口有没有停在 b . 那一行。

F103 的向量表排了 60 个 IRQ（IRQ0~IRQ59），但排了不等于实现了。 中容量型号 F103C8T6 没有 TIM5~TIM8、没有 ADC3、没有 FSMC/SDIO、没有 UART4/5、没有 DMA2， 所以真正有外设挂在后面的只有 IRQ0~IRQ42 这 43 个； IRQ43~IRQ59 是为大容量（F103ZET6 那类）和互联型预留的位置，在中容量上不会被触发。 你在 CubeMX 里选 F103C8T6 时，NVIC 列表里也只有这些——列表里没有的中断，写代码也没用。

NVIC 的六个寄存器组：五个管状态，一个管优先级

NVIC 全称 Nested Vectored Interrupt Controller（嵌套向量中断控制器），它不是 ST 加的外设， 而是 ARM 在 Cortex-M 内核里就做好的模块——所以它的寄存器地址在所有 Cortex-M 芯片上完全一样 （从 0xE000E100 开始），和 STM32 的 GPIO、USART 那些「厂商外设」不是一回事。 这也是为什么 core_cm3.h 里的 NVIC_EnableIRQ() 拿到任何一颗 Cortex-M 上都能用。 

寄 存 器      地 址 范 围              读 写 属 性      管 什 么
────────────────────────────────────────────────────────────────────────────

                                          (w1s)          「使能这一路中断」——开
ICER[0..7]   0xE000E180 ~ 0xE000E19C  写 1 清位       Interrupt Clear Enable
                                          (w1c)          「关掉这一路中断」——关
ISPR[0..7]   0xE000E200 ~ 0xE000E21C  写 1 置位       Interrupt Set Pending
                                                        软件把某路中断「挂起来」（让它排队等待）
ICPR[0..7]   0xE000E280 ~ 0xE000E29C  写 1 清位       Interrupt Clear Pending
                                                        取消排队（ISR 入口硬件也会自动清）
IABR[0..7]   0xE000E300 ~ 0xE000E31C  只 读           Interrupt Active Bit

  SCB->AIRCR  0xE000ED0C   优先级分组 PRIGROUP[10:8] + 系统复位请求
  SCB->VTOR   0xE000ED08   向量表基地址
  NVIC->STIR  0xE000EF00   软件触发任意一路中断（写中断号即可，调试神器）
────────────────────────────────────────────────────────────────────────────
为什么是 [0..7] 八个 32 位字？因为 8 × 32 = 256 路，覆盖 Cortex-M3 的 240 路上限。
F103 只有 60 路 → 实际只用到 ISER[0]、ISER[1] 的低 28 位（IRQ0~IRQ59）。

注意上表里的读写属性：ISER 和 ISPR 是 「写 1 有效、写 0 无影响」（write-1-to-set），ICER 和 ICPR 是 「写 1 清除、写 0 无影响」（write-1-to-clear）。 这个设计的好处是：想把 IRQ37（USART1）单独使能，你不必先读出整个字再改一位再写回（那会误伤别的中断）， 直接写一个只有 bit 5 为 1 的字就行。所以「开中断」的地址算式是固定的两段式：

/* ─── 手写版：使能 / 关闭 / 挂起 / 取消挂起 ─── */
static inline void nvic_enable_irq(IRQn_Type irq)
{
    /* irq >> 5 算出用第几个 32 位字，irq & 0x1F 算出字里的第几位 */
    NVIC->ISER[(uint32_t)irq >> 5U] = 1UL << ((uint32_t)irq & 0x1FU);
}

static inline void nvic_disable_irq(IRQn_Type irq)
{
    NVIC->ICER[(uint32_t)irq >> 5U] = 1UL << ((uint32_t)irq & 0x1FU);
}

static inline void nvic_set_pending(IRQn_Type irq)      /* 软件触发：让它排队 */
{
    NVIC->ISPR[(uint32_t)irq >> 5U] = 1UL << ((uint32_t)irq & 0x1FU);
}

static inline void nvic_clear_pending(IRQn_Type irq)    /* 取消排队 */
{
    NVIC->ICPR[(uint32_t)irq >> 5U] = 1UL << ((uint32_t)irq & 0x1FU);
}

static inline uint32_t nvic_is_active(IRQn_Type irq)    /* 正在执行中？ */
{
    return (NVIC->IABR[(uint32_t)irq >> 5U] >> ((uint32_t)irq & 0x1FU)) & 1U;
}

/* ─── 优先级：IPR 是「按字节」编址的，每个中断 1 字节 ─── */
/* 注意这一行的写法，它是这一节的核心陷阱：
     优先级数值要左移 (8 - __NVIC_PRIO_BITS) 位再写进去。
     在 F103 上 __NVIC_PRIO_BITS = 4，所以要左移 4 位。 */
static inline void nvic_set_priority(IRQn_Type irq, uint32_t prio)
{
    NVIC->IP[(uint32_t)irq] = (uint8_t)((prio << (8U - __NVIC_PRIO_BITS)) & 0xFFU);
}

/* ─── 用起来是这样 ─── */
void key_exti0_init(void)
{
    nvic_set_priority(EXTI0_IRQn, 5U);   /* 数值 5 → 实际写进 IPR 的是 0x50 */
    nvic_enable_irq(EXTI0_IRQn);
}

现在来看 IPR 那个「只用高 4 位」的设计，以及它带来的经典事故。 

一 个 中 断 的 优 先 级 字 节（NVIC->IP[n]）
────────────────────────────────────────────────────────────
   bit7  bit6  bit5  bit4 │ bit3  bit2  bit1  bit0
  ┌─────┬─────┬─────┬─────┼─────┬─────┬─────┬─────┐
  │  1  │  0  │  1  │  0  │  0  │  0  │  0  │  0  │   = 0xA0
  └─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┘
    └────── 已实现（STM32F103 实现 4 位）──────┘└─ 读出恒为 0，写入被丢弃 ─┘

  __NVIC_PRIO_BITS = 4  →  只有 2⁴ = 16 级优先级（0~15，0 最高）
  有些 Cortex-M0/M0+ 只实现 2 位 → 只有 4 级；M4/M7 常见实现 4 位（F4/F7 也是 16 级）

★ 于是「写 0x0F 会怎样」有了一个非常反直觉的答案：

     NVIC->IP[EXTI0_IRQn] = 0x0F;     /* 你以为设了 15（最低优先级） */
     读回来      → 0x00
     实际优先级  → 0（最高！可以抢任何东西，包括 SysTick 和 PendSV）

  因为 0x0F 的 4 个 1 全落在「未实现」的低 4 位里，被硬件丢弃；
  高 4 位是 0000，等于把这一路中断设成了最高优先级。
  更糟的是：它和「故意设成 0」的读回值一模一样，你无法从读回值反推自己写错了。

★ 正确写法（两种都行）：
      NVIC->IP[EXTI0_IRQn] = (uint8_t)(15U << 4);   /* = 0xF0 → 优先级 15 */
      NVIC_SetPriority(EXTI0_IRQn, 15U);            /* CMSIS 帮你移位 */
★ 自查方法：
      printf("%02X\r\n", NVIC->IP[EXTI0_IRQn]);      /* 应该是 0xF0 而不是 0x0F */

这个错误在真实项目里的表现形式

一个本该「最低优先级、谁都能打断它」的按键中断，被误设成了优先级 0。 于是它在执行期间连 SysTick 都打断不了它的反面——它谁都打断： HAL_GetTick() 突然不准了（tick 丢了几次）、 串口 DMA 的搬运节奏乱了、RTOS 里 PendSV 切换被推迟导致任务抖动。 现象是「偶发、难复现、换个板子又好了」，查一周都查不到—— 直到有人在调试器里看了一眼 NVIC->IP[] 的原始值。 养成习惯：优先级只通过 NVIC_SetPriority() 设，不手写 IPR。

优先级分组：4 个有效位切出 5 种分法

F103 只有 16 级优先级（0~15，数字越小越优先），但这 16 级不够用怎么办？ ARM 的办法很巧妙：把 4 个有效位切成两段，一段叫抢占优先级，一段叫响应优先级（也叫子优先级）， 切在哪里由 SCB->AIRCR 里的 PRIGROUP[10:8] 这 3 位决定。 

AIRCR 的 PRIGROUP[2:0] 决定「切在第几位」
────────────────────────────────────────────────────────────────
  4 个有效位（bit7~bit4）的两种切法示意：PRIGROUP = 5（2 抢占位 + 2 响应位）
  ┌─────┬─────┬─────┬─────┐
  │ b7  │ b6  │ b5  │ b4  │
  └──┬──┴──┬──┴──┬──┴──┬──┘
     └─────┴─────┘     └─────┴─────┘
       抢占优先级           响应（子）优先级
     （能不能打断）        （同时排队时谁先跑）
  取值 0~3（2 位）        取值 0~3（2 位）

  PRIGROUP = 3（4 抢占位 + 0 响应位）：4 位全是抢占
  ┌─────┬─────┬─────┬─────┐
  │ b7  │ b6  │ b5  │ b4  │      取值 0~15，共 16 个抢占级
  └──┬──┴──┬──┴──┬──┴──┬──┘      没有响应级，同优先级就是完全同优先级
     └─────┴─────┴─────┘
        全部是抢占优先级
────────────────────────────────────────────────────────────────
  ★ 无论怎么切，4 位能表达的组合总数恒为 16
    1×16 = 2×8 = 4×4 = 8×2 = 16×1 = 16
    分组不是「增加」优先级，而是「重新分配这 16 份给谁用」
────────────────────────────────────────────────────────────────

STM32 的参考手册（RM0008）给了一张确定的表。注意 PRIGROUP 写 0、1、2 时， 因为只有 4 位有效，效果和写 3 是一样的——所以真正有区别的只有 5 种分组：

分组 PRIGROUP[2:0] 抢占优先级位数 响应优先级位数 抢占级数 响应级数 抢占取值 响应取值 HAL 宏
分组 0 0b111 = 7 0 位 4 位 1（不可嵌套） 16 无 0~15 NVIC_PRIORITYGROUP_0
分组 1 0b110 = 6 1 位 3 位 2 8 0~1 0~7 NVIC_PRIORITYGROUP_1
分组 2 0b101 = 5 2 位 2 位 4 4 0~3 0~3 NVIC_PRIORITYGROUP_2
分组 3 0b100 = 4 3 位 1 位 8 2 0~7 0~1 NVIC_PRIORITYGROUP_3
分组 4（HAL 默认） 0b011 = 3 4 位 0 位 16 1 0~15 无 NVIC_PRIORITYGROUP_4
PRIGROUP = 2、1、0 在 F103 上与分组 4 等效（因为只有 4 位有效，多出来的位全是抢占位）。 来源：STM32F103 参考手册 RM0008 的「Priority grouping」表。
HAL 的组号是「反着」的，别被名字骗了

NVIC_PRIORITYGROUP_0 听起来像「第 0 组 = 最高优先级」，其实它是 0 个抢占位、4 个响应位——也就是完全不能嵌套的那一组，PRIGROUP 要写 7。 而 NVIC_PRIORITYGROUP_4（写 3）才是 4 个抢占位的「全抢占」模式。 记忆方法：HAL 的组号 = 抢占优先级的位数。组 4 = 4 位抢占，组 0 = 0 位抢占。 再记住 PRIGROUP = 7 - 抢占位数（在 4 位有效的前提下），两边就都通了。

然后是最核心的一条区别。抢占优先级决定「能不能打断正在执行的中断」，响应优先级只在「两个中断同时挂着等」的时候决定谁先跑，它永远不能造成嵌套。 

情 形 A：抢占优先级不同 → 可以嵌套

  TIM2 中断            EXTI0 中断
  抢占 = 1             抢占 = 0    ← 数值更小 = 更紧急
  ┌──────────────┐
  │ 正在执行      │
  │        ┌─────┼──────────┐
  │        │     │ EXTI0 打断│   ← 允许！EXTI0 抢占优先级更高
  │        │     │ 并开始执行 │
  │        └─────┼──────────┘
  └──────────────┘
  结论：EXTI0 的 ISR 与 TIM2 的 ISR 形成嵌套，TIM2 被挂起，等 EXTI0 执行完再继续

情 形 B：抢占优先级相同、响应优先级不同 → 不嵌套，先来的先跑完

  抢占 = 1 响应 = 3      抢占 = 1 响应 = 0   ← 响应更小，但没用

  │ 正在执行      │      EXTI0 只能一直等着（挂起位为 1）

  └──────────────┘
         ↓ TIM2 执行完，EXTI0 才开始
  结论：响应优先级只能决定「两者都还挂着的时候谁先被取走」

情 形 C：抢占与响应都相同 → 完全同级，硬件按中断号顺序取

  TIM2(抢占1,响应1) 与 TIM3(抢占1,响应1) 同时挂起
  → 谁先跑？硬件固定按「中断号小的先」：TIM2_IRQn = 28 < TIM3_IRQn = 29 → TIM2 先
  → 绝不能靠这个顺序做设计，它是硬件行为，不是你的语义

★ 一句话记法：抢占位管「打断」，响应位管「排队」
            
#include "stm32f1xx_hal.h"

分组的两个致命特性：全局 + 只能更粗

第一，分组是全局的。它不是「每个中断各有一套」，而是「整个 NVIC 共用一套解释规则」。 你在代码中途把分组从 4 改成 2，之前所有已经设好的优先级含义会瞬间全部改变： 原本 4 位全当抢占，现在高 2 位才是抢占、低 2 位变成响应位—— 一个原本抢占优先级 2 的中断，可能变成「抢占 0、响应 2」，优先级反而升高了。 这就是「我只用了一个中断，分组随便设」这个想法最危险的地方： 你用的不止一个，SysTick、PendSV、SVC 全都在同一个 NVIC 里。

第二，往细里改不回去。从分组 4（16 个抢占级）改成分组 2（4 个抢占级）之后， 原来抢占优先级 5 和 6 的两个中断会变成同级（都映射到 2）——你没法用「响应位」把它们再分开去实现嵌套， 因为响应位根本不参与嵌套判定。想恢复嵌套能力只能改回更粗的分组，然后重设所有优先级。

抢占与嵌套：硬件自动压的 8 字帧

嵌套的判定规则只有一句话，但它有三个条件，缺一不可。当一个新的中断请求到达时，CPU 会问： 

新 请 求 要 打 断「正 在 执 行 的 中 断」，必 须 同 时 满 足：
────────────────────────────────────────────────────────────
  ①  新请求的【抢占优先级】数值 < 当前正在执行的抢占优先级数值
        （严格小于。相等 = 同级 = 不能打断，哪怕响应优先级更小）

  ②  当前不在「优先级更高或相等的处理中」——内核只比较抢占优先级，
        响应优先级根本不参与这个比较

  ③  全局中断没被关：PRIMASK = 0（__enable_irq() 之后的状态）
        注意 __disable_irq() 关的是 PRIMASK，它挡不住 NMI 和 HardFault
────────────────────────────────────────────────────────────
反过来说，下面这些情况【绝对不会】发生嵌套：
  · 两个中断的抢占优先级相同（哪怕响应优先级差 3 级）
  · 新来的中断优先级数值更大（更不紧急）
  · 当前执行的是 HardFault / NMI（它们的优先级是负数，比任何外部中断都高）
  · 你在 ISR 里调了 __disable_irq() 还没调 __enable_irq()
────────────────────────────────────────────────────────────

一旦允许嵌套，硬件会替你做一件很漂亮的事：把 8 个寄存器自动压进栈（32 字节）， 取向量、跳进新的 ISR。这 8 个寄存器是固定的： 

压 栈 顺 序 与 栈 内 容（MSP 或 PSP 由 EXC_RETURN 决定）
────────────────────────────────────────────────────────────
      栈地址 ↑ 增大
      ┌──────────────────────┐ ← 压栈前的 SP
      │  旧 SP（空出来的）    │
      ├──────────────────────┤ ← 压栈后的 SP（= 旧 SP - 32）
      │  R0                  │   ← 压栈顺序是从低地址开始，最后压 xPSR
      │  R1                  │      所以 xPSR 在最高地址处
      │  R2                  │
      │  R3                  │
      │  R12                 │
      │  LR   (R14)          │   返回地址（被打断处的下一条指令）
      │  PC   (R15)          │   ★ 被打断处正在执行的那条指令地址
      │  xPSR                │   ★ 含条件标志位与 IPSR（当前异常号）
      └──────────────────────┘
  8 个字 × 4 字节 = 32 字节 / 每一层嵌套
────────────────────────────────────────────────────────────
为什么是这 8 个？因为 ARM 的调用约定（AAPCS）规定：
  R0~R3、R12 是「调用者保存」的，LR、PC、xPSR 是控制流状态
  → 硬件只保护这些就够让 ISR 正常返回；R4~R11 由编译器在 ISR 里按需压
★ 这也解释了为什么「进入 ISR 的延迟」里有一个固定成本：压 8 个字要时间
★ 更解释了为什么嵌套会吃栈：每嵌套一层，就多 32 字节硬件帧 + 该层 ISR 自己的局部变量
────────────────────────────────────────────────────────────
补充：xPSR 里保存的 IPSR 段是「被打断时的异常号」，
      而 LR 里保存的是一个特殊值 EXC_RETURN（不是普通地址），
      异常返回时往 PC 写这个值，硬件就知道「这是异常返回，该出栈了」。
      所以你在 ISR 里【不能随便改 LR】——改了就没法正常返回。

关于嵌套，还有两个一定要建立的直觉：

  • 嵌套是「栈」形状的，不是「链」形状的。它严格后进先出：谁最后进来，谁最先出去。 所以嵌套深度就是你最坏情况下的栈消耗倍数。深度 4 = 4 层硬件帧（128 字节）加上 4 层 ISR 各自的局部变量。
  • 嵌套深度是有上界的，但上界往往比你想的小。如果所有中断都用不同的抢占优先级， 最坏深度就是「有几种不同的抢占优先级」；如果把多个中断设成同一个抢占优先级， 它们之间就不嵌套——这是控制栈用量最有效的一招。工业代码里常常故意把一组相关中断 （比如所有按键、所有显示刷新）设成同一个抢占优先级，让它们排队而不是嵌套。

★ 注意：嵌套里【没有】优先级反转保护——高优先级打断低优先级是硬件行为，
  但低优先级 ISR 里如果握着共享资源，高优先级 ISR 就得等它（这就是 RTOS 要互斥量的原因）

最后补一个实战细节：为什么 __disable_irq() 不能保护共享数据到底？ 因为它只是把 PRIMASK 置 1，挡住所有可屏蔽中断——但挡不住 NMI 和 HardFault， 也挡不住 DMA（DMA 是硬件搬运，和 CPU 的中断屏蔽毫无关系）。 所以「关中断保护」只对「中断与主循环共享的普通变量」有效，对 DMA 完全无效。 这也是 中断与异常机制 里强调「volatile 只解决可见性、不解决原子性」的原因——按位或赋值丢标志的问题，关中断和原子指令才是解药。

中断延迟、尾链与迟来：那几十个周期花在哪

「中断延迟」的定义要卡死：从硬件/外设产生中断请求的那一刻，到 ISR 第一条指令开始执行， 而不是「到 ISR 执行完」（那是响应时间）。开路这一段时间，是一串可以逐项算出来的周期数。 

从 请 求 到 ISR 第 一 条 指 令
────────────────────────────────────────────────────────────────────
①  请求产生阶段
    · 同步请求（软件写 NVIC->STIR / 某外设的使能位就在 CPU 时钟域里）
        → 0 周期额外开销，CPU 下一个周期就能看见
    · 异步请求（EXTI 引脚上的电平变化、外部信号）
        → 信号要先被同步到 CPU 时钟域（2 级触发器采样）
        → 额外 2~3 个周期；如果正好在采样窗口边缘，还可能再多 1 个周期
        ★ 这就是「外部中断天生比内部中断慢几个周期」的原因

②  压栈阶段（硬件做）
    · 8 个字（xPSR/PC/LR/R12/R3~R0）写进栈
    · 零等待存储器时，ARM 给出的典型值是 12 个周期完成「压栈 + 取向量准备」
    ★ 栈放在有等待周期的 RAM、或者总线上正在被 DMA 抢占 → 这里会变长

③  取向量阶段（硬件做）
    · 从 SCB->VTOR + 4×异常号 处读出一个字，就是 ISR 的入口地址
    · 零等待存储器（Flash 有预取/缓存）时开销很小；如果 Flash 没开预取，这里会明显变慢
    ★ 这也是「Flash 预取 / 等待周期设置」会影响中断实时性的原因

④  ISR 入口指令取指与执行
    · 到这里才算「延迟结束」，你数延迟就数到这里
────────────────────────────────────────────────────────────────────
典 型 值（Joseph Yiu《The Definitive Guide to Cortex-M3》/ ARM 文档，
零等待周期存储器、无 FPU、无尾链）：             
   中断延迟（异步请求）        约 12 周期 + 2~3 周期同步 = 14~15 周期
   中断延迟（尾链进来的）      6 周期
   迟来（late-arriving）       6 周期（对那个高优先级中断而言）
   异常返回（出栈 + 恢复）      约 10 周期
★ 这些数字是「量级参考」，不是你芯片上的实测值。
  实测永远用第 4 节的 DWT->CYCCNT 方法，因为你的 Flash 等待周期、
  优化等级、ISR 有多大、栈在哪块 RAM，都会让实测值偏离典型值。
────────────────────────────────────────────────────────────────────

现在讲这两个把开销「吃掉一大半」的机制。它们的共同思想是： 中断处理完了要回到主程序，但如果这时候已经有下一个中断在等着，那就别回去了，直接接着干。 

前 提：两个中断【连续】到来（比如 50µs 定时器和另一个同频中断正好撞在一起）
────────────────────────────────────────────────────────────────────────
【A】没有尾链机制会怎样（假设硬件老老实实回主程序再重新进）
   ISR1 执行完 → 出栈(10) → 回主程序 → 发现又挂起 → 再压栈+取向量(12+2) → 进 ISR2
   中断之间的空隙开销 ≈ 10 + 14 = 24 周期，这期间 CPU 在「来回倒腾」而不是干活

【B】尾链 tail-chaining（Cortex-M3 的真实行为）
   ISR1 执行完 → 异常返回时【硬件检查还有没有挂起的中断】
        ├─ 没有 → 正常出栈(约 10 周期)，回主程序
        └─ 有   → ★ 不出栈、不回主程序，直接取下一个向量进 ISR2
                  这一段只花 6 个周期
   空隙开销从 24 周期压到 6 周期 → 省了 18 个周期，约 75%

【C】迟来 late-arriving（在压栈过程中就有更高优先级请求到达）
   时序：ISR_low 的压栈正在进行中 → 一个更高优先级的请求到了
        ├─ 没有迟来机制 → 必须先把 ISR_low 完整地进去（再压一次栈），
        │                 然后立刻被高优先级打断（又压一次栈）→ 白压一次
        └─ 有迟来机制   → 压栈继续做（反正栈帧格式一样），
                          但取向量时【改成取高优先级的向量】，
                          直接进高优先级 ISR，等它执行完再回来做 ISR_low
                          高优先级请求的等待被缩短到 6 个周期
────────────────────────────────────────────────────────────────────────
★ 一句话：尾链省的是「出栈 + 再压栈」，迟来省的是「白压一次多余的栈」。
★ 意义：中断越密集（高频定时器、连续串口字节、多个外设同时报告），
  尾链的收益越大——它把「每次中断固定几十周期」变成「第一个几十周期 + 后续每个几周期」。
────────────────────────────────────────────────────────────────────────

还有一个必须澄清的点：PRIMASK 关中断也会「吃掉」尾链的收益。 如果你在主循环里长时间 __disable_irq()，这段时间到达的中断全部被挂起； 等 __enable_irq() 之后它们会一起被处理——第一个正常压栈（12 周期）， 后面的全走尾链（各 6 周期）。 从「总 CPU 占用」看这甚至更省；但从「实时性」看这是灾难： 第一个中断的延迟被拉长到了「你关中断的时长 + 12 周期」。 这就是为什么临界区必须尽可能短——关中断不是在省时间，而是在借时间，利息是实时性。

第 4 节会给你一段用 DWT->CYCCNT 数周期的代码： 在一个中断里翻转一个 GPIO，用示波器量「触发信号上升沿 → GPIO 翻转」的延迟； 或者用 DWT 在 ISR 首尾各记一次数，算出 ISR 的周期数。 再用一个定时器故意以很高的频率触发两个中断，就能亲眼看到「单独一次中断的周期数」 和「连续中断的平均周期数」之间的差距——那个差距就是尾链。

关于这条链路，有五个寄存器必须能说出名字。它们全在 EXTI 结构体里 （基地址 0x40010400）：

寄存器 偏移 作用 怎么用
IMR 0x00 Interrupt Mask：这一路要不要产生中断 写 1 打开。EXTI->IMR |= (1 << 1); 打开 EXTI1 的中断
EMR 0x04 Event Mask：这一路要不要产生事件脉冲 写 1 打开。事件脉冲可以唤醒 CPU、触发 ADC/TIM，但不进中断
RTSR 0x08 Rising Trigger Selection：上升沿触发 EXTI->RTSR |= (1 << 1); 让 EXTI1 对上升沿敏感
FTSR 0x0C Falling Trigger Selection：下降沿触发 按键接地 + 上拉时用它。两个都置 1 = 双边沿触发
SWIER 0x10 Software Interrupt Event Register：软件触发 写 1 就相当于「假装来了一个边沿」，用来测中断通路，非常实用
PR 0x14 Pending Register：挂起位 读 1 表示「这条线有事件还没处理」；写 1 清除，写 0 无效
PR 必须清、而且要清对：忘了清就是「一次触发反复进」

完整的事件流是这样的：引脚上来了一个合法边沿 → 硬件把 PR 对应位置 1 → IMR 也开着 → 这一路的请求被送到 NVIC → NVIC 把这一路的 pending 置 1 → CPU 进入 ISR（进入时 NVIC 的 pending 会自动清掉）。 注意最后一句：清掉的是 NVIC 的 pending，不是 EXTI 的 PR。 如果 ISR 里没清 PR，它还是 1，也就是这条线的请求线一直是高的， NVIC 会在你退出 ISR 的下一个瞬间重新把它挂起——于是你一次按下，中断进来了成千上万次， 表现是「程序卡在中断里出不来」或者「主循环像是在原地打转」。

所以 PR 的清除必须写在 ISR 里，而且顺序有讲究， 两种写法对应两种语义： 

/* 写法 A：先清 PR，再干活（HAL 用的就是这一种） */
void EXTI1_IRQHandler(void)
{
    if (EXTI->PR & (1U << 1)) {
        EXTI->PR = (1U << 1);     /* ← 先清挂起位 */
        do_something();            /* ← 再处理业务 */
    }
}
/* 语义：清掉「这一次」之后进来的新边沿会重新置位 PR，
   于是它在 do_something() 执行期间或之后被记为「又一次中断」。
   抖动期间的每个边沿都会被如实记录 → 需要软件去抖配合。 */

/* 写法 B：先干活，最后清 PR */
void EXTI1_IRQHandler(void)
{
    if (EXTI->PR & (1U << 1)) {
        do_something();
        EXTI->PR = (1U << 1);     /* ← 最后清 */
    }
}
/* 语义：do_something() 期间产生的抖动边沿会被这一次清除一并抹掉，
   相当于「在 ISR 执行期间自动去抖」——但也可能抹掉一个真实的第二次按键！
   ★ 一般不用这种，除非你清楚地要它。 */

两条实用建议：① 清 PR 时用「写 1 写回读到的位」，不要用 EXTI->PR = 0xFFFF 一把全清 ——那会把别的线（你可能没处理的、或留给事件模式的）也一起清掉； ② 判 PR 用 if 而不是 while—— 进 ISR 时 NVIC 已经替你清掉 pending 了，没有「循环处理到没有为止」的必要， 写成 while (EXTI->PR & mask) 反而可能在抖动时把你锁在中断里出不去。

还有一组概念要分清：事件（event）模式和中断（interrupt）模式。它们共用同一条线的边沿检测器， 分岔点在 IMR 和 EMR：

对比项 中断模式（IMR 使能） 事件模式（EMR 使能）
目的 让 CPU 执行一段代码 让硬件之间互相触发，不打扰 CPU
是否置 PR 是 否
是否送 NVIC 是（还需要 NVIC 那一级使能） 否，直接变成一根内部脉冲
典型用途 按键、编码器、外部告警 把 EXTI 脉冲接到 TIM 的从模式触发 / ADC 的触发源；
或用它把 CPU 从睡眠/停止模式唤醒，但不进 ISR
优先级 受 NVIC 优先级管辖 无优先级概念（不经过 NVIC）
延迟 数十周期（要压栈、取向量） 几个周期（纯硬件连线，CPU 不参与）
开的写法 EXTI->IMR |= mask; EXTI->EMR |= mask;
事件模式是「低功耗设计的标配」

第 38 篇讲低功耗时会反复用到它：让一个 GPIO 的边沿通过 EMR 变成一个事件脉冲， 直接触发定时器开始计数或触发 ADC 采样，CPU 全程在睡觉。 代价是你失去了「在 ISR 里做判断」的能力——换来的是几微安级的待机电流。 现在只需要记住：中断和事件不是两种外设，是同一条线的两个出口。

最后是那句必须刻进肌肉记忆的话：EXTI 与 NVIC 是两级使能，两个都必须开。 只开 EXTI->IMR 不开 NVIC：请求被送到 NVIC 门口，但那一路上锁着，CPU 永远不知道； 请求会一直挂在 NVIC 的 pending 上，等你哪天开了 NVIC 使能，它会立刻补上一次（迟到的中断）。 只开 NVIC 不开 IMR：NVIC 永远收不到请求，开了也白开。 

EXTI->IMR    NVIC->ISER    结 果
────────────────────────────────────────────────────────────
   0            0          永不触发（默认状态）
   1            0          请求卡在 NVIC pending 上；一旦补开 ISER 会立刻进来一次
   0            1          永不触发（最常见的手误：EnableIRQ 写了，IMR 忘了）
   1            1          ✔ 正常触发

   · 引脚没配成输入（还在默认的浮空输入之外的模拟/输出模式）→ 边沿根本传不到 EXTI

/* ─── 第二层：转发。CubeMX 生成的 EXTI0_IRQHandler 里就是调它 ─── */
void HAL_GPIO_EXTI_IRQHandler(uint16_t GPIO_Pin)
{
    /* 先确认这条线的挂起位是不是真的置着（防止误进 ISR） */
    if (__HAL_GPIO_EXTI_GET_IT(GPIO_Pin) != 0x00u)
    {
        /* ★ 先清 PR。展开后就是一句 EXTI->PR = GPIO_Pin;（写 1 清除） */
        __HAL_GPIO_EXTI_CLEAR_IT(GPIO_Pin);

        /* 再交给用户。注意：GPIO_Pin 参数被原样传下去，
           这就是你能在回调里区分「是哪个引脚」的唯一依据 */
        HAL_GPIO_EXTI_Callback(GPIO_Pin);
    }
}

/* 展开后的宏（stm32f1xx_hal_gpio.h）：
     #define __HAL_GPIO_EXTI_GET_IT(__EXTI_LINE__)  (EXTI->PR & (__EXTI_LINE__))
     #define __HAL_GPIO_EXTI_CLEAR_IT(__EXTI_LINE__) \
                 do { EXTI->PR = (__EXTI_LINE__); } while (0u)
   注意 GET 返回的是「按位与的结果」，不是一个 0/1；
   所以判断写 != 0x00u，不能写 == 1U。 */

/* ─── 第三层：回调。定义为 __weak，你不重写它就是空函数 ─── */
__weak void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
{
    /* 这个空函数存在本身就是文档：它在告诉你「这里是你该写的地方」 */
    UNUSED(GPIO_Pin);
}

/* ─── 串口那一侧是同一个套路：判标志 → 分发 → 回调 ─── */
void HAL_UART_IRQHandler(UART_HandleTypeDef *huart)
{
    uint32_t isrflags = READ_REG(huart->Instance->SR);   /* 状态寄存器 */
    uint32_t cr1its   = READ_REG(huart->Instance->CR1);  /* 中断使能位 */
    uint32_t errorflags;

    /* ① 先把四种错误标志一起抠出来：PE 校验错、FE 帧错、ORE 溢出、NE 噪声 */
    errorflags = (isrflags & (uint32_t)(USART_SR_PE | USART_SR_FE |
                                        USART_SR_ORE | USART_SR_NE));
    if (errorflags == RESET)
    {
        /* 无错误 → 走正常接收分支 */
    }
    else { /* 有错误 → 里面会根据具体错误调 HAL_UART_ErrorCallback 或继续 */ }

    /* ② 接收：RXNE（收到一个字节）并且 RXNEIE 开着 */
    if (((isrflags & USART_SR_RXNE) != RESET) &&
        ((cr1its & USART_CR1_RXNEIE) != RESET))
    {
        UART_Receive_IT(huart);      /* ★ 真正的活在这里：读 DR、存缓冲区、计数 */
        return;                      /* 处理完接收就返回，不再往下判发送 */
    }

    /* ③ 发送：TXE（可以写下一个字节）→ 调 HAL_UART_TxCpltCallback（缓冲发完时） */
    /* ④ 其它：IDLE 空闲线检测、CTS、PE 等，各有分支 */
}

/* UART_Receive_IT 内部逻辑（简化）：
     *huart->pRxBuffPtr++ = (uint8_t)(huart->Instance->DR & 0xFF);   // 读 DR 顺便清 RXNE
     if (--huart->RxXferCount == 0) {
         huart->Instance->CR1 &= ~USART_CR1_RXNEIE;                   // 关掉 RXNE 中断
         HAL_UART_RxCpltCallback(huart);                              // ★ 收满了才回调你
     }
   ★ 所以 HAL_UART_RxCpltCallback 是「收满你指定的字节数」才调一次，
     不是「每收一个字节调一次」——这是很多人第一次用 HAL_UART_Receive_IT 时的困惑。
     收一个字节就处理一次，要自己写 HAL_UART_RxHalfCpltCallback 或者用 DMA + IDLE。 */
为什么 HAL_GPIO_EXTI_Callback 是所有引脚共用的一个函数

因为 HAL 的设计者没法预知你要用几个引脚。他只有两个选择： 要么为 16 条线准备 16 个不同的回调（HAL_GPIO_EXTI0_Callback…）， 要么只留一个、把引脚号当参数传进来。HAL 选了后者，理由是EXTI5~9 和 EXTI10~15 本来就共用一个中断向量， 在你写 EXTI9_5_IRQHandler 的时候，本来就得写五个 HAL_GPIO_EXTI_IRQHandler(GPIO_PIN_x) 去分发， 既然分发已经发生在你的 IRQHandler 里了，回调再合并成一个也不增加负担。

于是正确写法只有一种：回调的第一个动作就是判 GPIO_Pin。 忘了判、只写 key_flag = 1;，那么任何一个引脚的中断都会把「所有按键」的 标志一起点亮——现象是「按 A 键，程序认为 B、C 键也被按了」。第 4 节给的正确范式就是这么写的。

最后是那句被说了一万遍、但每天还在被违反的话：回调里绝对不能做重活。 下面这张清单请当成硬性规定：

不能做的事 为什么不行 正确做法
HAL_Delay() / 任何等 tick 的循环 tick 靠 SysTick 中断，而 SysTick 优先级最低（HAL 设成 15）抢不过当前 ISR → 死锁 置标志 + 记录 HAL_GetTick() 快照，主循环里判断时间差
HAL_UART_Transmit()（阻塞版） 它内部就是「死等 TXE 标志」，等的是外设；发 100 字节 @115200 要 8.7ms，全在中断里烧掉 HAL_UART_Transmit_IT() / _DMA()，或往环形缓冲区里塞、主循环发
printf() 大字符串 格式化浮点/长字符串要几千个周期；printf 还常带锁、不可重入 格式化放主循环；ISR 里最多写一个字节到缓冲区，或用 SWO/ITM 输出

优先级该怎么分配：按截止时间，不按重要性

这是这一节最「工程」的一段。绝大多数教程会告诉你「重要的中断给高优先级」——这句话是错的， 或者说它把问题描述得太粗了。正确的判据是「截止时间（deadline）」：谁晚了一点就会出错，谁就该高。

留空档是个好习惯

上表里 5~12 全是空的。这不是浪费，是给未来的自己留插队的位置。 真实项目的优先级列表总是会越长越长的——你加了蓝牙、加了 Flash 写入、加了看门狗喂狗， 如果一开始就把 0~15 排满，之后每加一个中断都要重新调整全局，改动风险极大。 用 0、2、4、6、8、14 这样「跳着排」，是最省心的工程习惯。

接着是裸机项目迟早会遇到的一步：上 FreeRTOS。这时候优先级这件事会多出一层约束， 而这一层的坑比前面所有坑加起来都更隐蔽。 

────────────────────────────────────────────────────────────────────────────
边 界 一：能不能调用 FreeRTOS 的 API，取决于「优先级数值」的大小
────────────────────────────────────────────────────────────────────────────
               数值小（更紧急）                                 数值大（更不紧急）
  ─────────────────┬───────────────────┬──────────────────────────────┬──────────
      0             │  1  2  3  4       │   5  (= configMAX_SYSCALL)    │   …  15
  ─────────────────┴───────────────────┴──────────────────────────────┴──────────
     ★ 禁区：这一区间的中断          ★ 可用区：这一区间的中断
       绝对【不能】调用任何             可以安全调用 FromISR 版本的 API
       FreeRTOS API（哪怕 FromISR）      （队列、信号量、任务通知…）
       因为它能抢占内核临界区，          FreeRTOS 会推迟调度、把临界区保护住
       会破坏内核数据结构 → 偶发崩溃
────────────────────────────────────────────────────────────────────────────
  configMAX_SYSCALL_INTERRUPT_PRIORITY 的典型值：5 << (8-4) = 0x50 = 80（"原始值"）
  而 NVIC_SetPriority(irq, 5) 里的 5 是「数值」——两者【不是一回事】！
────────────────────────────────────────────────────────────────────────────
边 界 二：FromISR 版本 + pxHigherPriorityTaskWoken，一个都不能少
────────────────────────────────────────────────────────────────────────────
   ✘ 错误：在 ISR 里调 xQueueSend(q, &d, 0);          → 用的是非 FromISR 版本
           → 它内部会进临界区、可能阻塞 → 在中断里是未定义行为
   ✘ 错误：xQueueSendFromISR(q, &d, NULL);            → 不传唤醒标志
           → 队列确实收到了，但被唤醒的高优先级任务要等到
             下一次 tick 才可能切换 → 延迟最多一个 tick（1ms）
   ✔ 正确：
        BaseType_t woken = pdFALSE;
        xQueueSendFromISR(q, &data, &woken);
        portYIELD_FROM_ISR(woken);     /* woken == pdTRUE 时立刻切到那个任务 */
────────────────────────────────────────────────────────────────────────────
为什么一定要 portYIELD_FROM_ISR：
  中断结束时硬件只会出栈回到「被打断的地方」。如果那个地方是低优先级任务，
  而你的中断刚刚叫醒了一个高优先级任务，不主动触发 PendSV 的话，
  这个高优先级任务就得等到调度器下一次自然抢占（下一个 tick）才运行。
  加上 portYIELD_FROM_ISR，ISR 退出时立刻走 PendSV 做一次任务切换，
  「中断 → 高优先级任务开始运行」的总延迟从「最多 1ms」降到「几个 µs」。
────────────────────────────────────────────────────────────────────────────
那个最经典的坑：把原始值当数值传给了 NVIC_SetPriority

configMAX_SYSCALL_INTERRUPT_PRIORITY 在 FreeRTOS 里是 「已经左移好的、要写进寄存器的原始值」（典型 0x50 = 80）。 而 NVIC_SetPriority(irq, x) 要的是没移位的数值（0~15）。 于是这个「看起来很合理」的写法： 

/* ✘ 错误！把原始值当数值用了 */
NVIC_SetPriority(USART1_IRQn, configMAX_SYSCALL_INTERRUPT_PRIORITY);
/*   configMAX_SYSCALL_INTERRUPT_PRIORITY = 80
     80 左移 4 位 = 1280 = 0x500
     截断成 8 位 = 0x00
     → 实际优先级 = 0（最高！）
     → 这个串口中断现在比内核还高，可以在内核临界区里横插一脚
     → 现象：偶发 HardFault、队列指针错乱、configASSERT 报
             "vPortValidateInterruptPriority" 里说的优先级非法 */

/* ✔ 正确：写数值（5 对应 MAX_SYSCALL 那条线） */
NVIC_SetPriority(USART1_IRQn, 5);
/* 或者干脆用 HAL： */
HAL_NVIC_SetPriority(USART1_IRQn, 5, 0);

/* 建议：给每个项目加一段开机自检，把说好的事变成代码检查 */
void irq_priority_sanity_check(void)
{
    /* 逐条核对：不许有任何一个「可调用 RTOS API 的中断」跑到禁区里 */
    assert_param( NVIC_GetPriority(USART1_IRQn) >= 5U );
    assert_param( NVIC_GetPriority(TIM2_IRQn)   >= 5U );
    /* NVIC_GetPriority 返回的是【数值】（0~15），不是原始值，正好可以直接比 */
}

为什么这个 bug 这么难查？因为你写的是 NVIC_SetPriority， 这个名字看起来「就是设优先级」，而参数语义（数值 vs 原始值）在函数原型里完全看不出来： 两个参数的 C 类型都是 uint32_t。编译器救不了你。 唯一的防线是知道这件事，以及那句 configASSERT。 FreeRTOS 在 port.c 里的 vPortValidateInterruptPriority() 就是专门抓这个的，只要打开 configASSERT，它会在第一次调用 API 时就告诉你哪一路中断越界了。

这一节到这里就完整了。八个子节合起来，其实就是一句话： 中断是「外设 → EXTI → NVIC（两级使能 + 优先级）→ 向量表 → HAL 转发 → 你的回调」的一条链， 链上每一环都有自己的寄存器、自己的默认值、自己的坑。 下一节我们用真实数字把这几十个周期和这 16 级优先级算一遍。

动手算一遍：六个必须会算的数

这一节的六个例题，覆盖了你配中断时真正要决定的六个数：优先级的组合空间、延迟的绝对大小、 栈要给多少、CPU 占用率是多少、线够不够用、以及最重要的——你这套优先级到底能不能满足截止时间。 每一个都给出完整的算式和结论，数字全部可以在你自己的板子上复算。

本节的统一前提

STM32F103C8T6，SYSCLK = HCLK = PCLK2 = 72MHz，PCLK1 = 36MHz（APB1 预分频 2）， 分组 = NVIC_PRIORITYGROUP_4（4 位抢占、0 位响应）， Flash 等待周期 2 WS（按 RM0008：48MHz < HCLK ≤ 72MHz 时需要 2 个等待周期）， 编译器 -O2。周期与微秒的换算基准： 1 周期 = 1/72MHz ≈ 13.89ns，反过来 1µs ≈ 72 个周期。

例 1：5 种分组各有几个抢占级与响应级

题目：F103 的优先级寄存器每个中断只有 4 个有效位。在 RM0008 定义的 5 种分组下， 分别能提供多少个抢占优先级、多少个响应优先级？如果我的系统里有 12 个中断， 希望它们两两之间都能互相嵌套，应该选哪个分组？如果我希望把 12 个中断分成 「4 个紧急度层次，每层内部再分先后」，又该选哪个分组？

解：把 4 位当资源来分。设抢占占 p 位、响应占 s 位，则 p + s = 4， 抢占级数 = 2p，响应级数 = 2s，且两者的乘积恒等于 24 = 16。

分组 抢占位 p 响应位 s 抢占级数 2p 响应级数 2s 能同时挂起并区分的中断数上限 乘积
分组 0（PRIGROUP=7） 0 4 1 16 16（全靠排队，绝不嵌套） 16
分组 1（PRIGROUP=6） 1 3 2 8 16 16
分组 2（PRIGROUP=5） 2 2 4 4 16 16
分组 3（PRIGROUP=4） 3 1 8 2 16 16
分组 4（PRIGROUP=3） 4 0 16 1 16（每个都能互相嵌套） 16

第一个问题：12 个中断两两都能互相嵌套。要「任意两个中断的抢占优先级都不相同」， 需要抢占级数 ≥ 12。分组 3 只有 8 级（0~7），不够；只有分组 4 的 16 级（0~15）够用。 所以在分组 4 下你可以给 12 个中断分别安排 0~11 的抢占优先级，任意两个都能嵌套。

第二个问题：4 个紧急度层次、每层内部再分先后。这正是分组 2 的定义： 抢占级 0~3 共 4 层，每层内部响应级 0~3 共 4 个先后顺序。 设抢占与响应时 要记住那句话——抢占管打断，响应管排队： 同一层里的 4 个中断互相不嵌套，但它们同时挂起时，响应级小的先跑。

「16」这个数字不变，变的是它的形状

五种分组下「能表达的不同优先级数值」永远是 16 个——不是 16 加 16。 分组改变的是这 16 份资源怎么切成两层树：切得越偏抢占，就越能嵌套、越不能排队； 切得越偏响应，就越能排队、越不能嵌套。 工程上 90% 的裸机项目直接用分组 4（HAL 默认），因为「16 个能互相嵌套的等级」 在中断数不超过 16 时是最直观、最不容易出错的模型。 只有在「中断数超过 16，必须让一部分中断共享优先级」时，才需要考虑分组 2 或 3。

例 2：从事件到 ISR 第一条指令要多少纳秒

题目：在 72MHz 下，一个定时器更新中断（同步请求）和一个按键 EXTI 中断（异步请求）， 从「事件发生」到「ISR 第一条指令开始执行」分别要多少周期、多少纳秒？ 把主频降到 8MHz 内部 RC 又会怎样？这个延迟相对于 115200 波特率下的字节间隔是什么量级？

解：逐段累加，用第 2 节给出的典型周期数（ARM 文档与 Joseph Yiu 的 Cortex-M3 权威指南，零等待存储器、无 FPU）：

周 期 换 算 基 准 ：1 周 期 = 1 / 72 MHz = 13.89 ns
────────────────────────────────────────────────────────────────────
【A】同步请求（TIM 更新事件、软件写 SWIER、内核异常）
   请求产生               0 周期（下一个 CPU 周期就能看见）
   压栈 8 字            + 12 周期
   取向量               + 已包含在上面 12 周期内（零等待 Flash + 预取开启）
   ────────────────────────────────
   合计                  12 周期 × 13.89 ns = 166.7 ns ≈ 0.17 µs

【B】异步请求（EXTI 引脚边沿、外部信号）
   同步到 CPU 时钟域      + 2~3 周期（两级触发器采样；正好卡在采样窗口边缘时再 +1）
   压栈 8 字            + 12 周期
   ────────────────────────────────
   合计                 14~15 周期 × 13.89 ns = 194.4 ~ 208.3 ns ≈ 0.19~0.21 µs

【C】把「工程上真实会遇到的额外开销」加上
   · Flash 有 2 个等待周期（72MHz 的必然配置）：
     如果 ISR 入口的取指正好没命中预取缓冲，多 1~2 周期
   · 栈指针指向的 RAM 若被 DMA 占用总线：一次压栈可能多几个周期
   · ISR 第一条指令本身要取指（1 周期 ICode 访问 + 执行）
   ────────────────────────────────
   现实中的实测值通常在 250 ~ 400 ns 之间
   ★ 所以第 4 节的 DWT 实验会教你实测，而不是信纸面数字

【D】把主频降到 8MHz（HSI 直连，无 PLL）
   1 周期 = 1 / 8 MHz = 125 ns
   14 周期 × 125 ns = 1750 ns = 1.75 µs
   ★ 比 72MHz 慢了整整 9 倍 —— 因为延迟的「周期数」几乎不随主频变，
     它是个常数；所以【主频越高，中断延迟的绝对时间越短】，线性关系。
────────────────────────────────────────────────────────────────────
【E】和 115200 波特率的字节间隔比一比
   1 个字节 = 10 位（1 起始 + 8 数据 + 1 停止）
   每个位的时间 = 1 / 115200 = 8.68 µs
   一个字节 = 10 × 8.68 µs = 86.8 µs
   → 中断延迟 0.21 µs 只占字节间隔的 0.24%
   → 也就是说：中断延迟本身从来不是串口丢字节的原因，
     【真正吃掉时间的是你的 ISR 执行时间和关中断时长】
────────────────────────────────────────────────────────────────────
【F】换个角度看这 15 个周期
   Cortex-M3 在 -O2 下，简单指令（MOV/ADD/比较/分支）CPI 约 1~1.2
   → 15 个周期 ≈ 本可以执行 12~15 条指令
   → 也就是每次中断「白扔」十几条指令的时间；
     每秒 20000 次中断（50µs 一个）时，光延迟就吃掉
     15 × 20000 = 300,000 周期/s = 300k / 72M ≈ 0.42% 的 CPU
────────────────────────────────────────────────────────────────────

结论：同步请求约 167ns（12 周期），异步请求约 194~208ns（14~15 周期）， 实测约 250~400ns。这些数字小到「几乎可以忽略」，所以 绝大多数实时性问题都不是中断延迟造成的，而是 ISR 太长或者关中断太久造成的—— 这个结论会在例 4 和例 6 里被反复验证。

例 3：嵌套深度 4 的最坏栈用量

题目：系统里有四个中断可以互相嵌套（抢占优先级 0、1、2、3）， 假设它们在最坏时刻同时叠加。请算出中断部分的最坏栈占用；如果栈总共只给了 1KB， 还剩多少给主程序？再算一下「某个 ISR 里手滑调了一次 printf」会发生什么。

解：栈用量分三块——硬件帧（每层固定 32 字节，不可协商）、 ISR 自身的局部变量与保存的寄存器（编译器决定，要看 .su 文件或反汇编）、 以及主上下文（主循环的调用链深度）。

栈 是 从 高 地 址 往 低 地 址 生 长 的
────────────────────────────────────────────────────────────────────
假设：栈顶 MSP 初始 = 0x20005000（RAM 20KB 的顶）
      分配给栈的空间 = 0x400 = 1024 字节 → 栈底警戒线 = 0x20004C00
────────────────────────────────────────────────────────────────────
地址            内容                                        用量
0x20005000  ┌──────────────────────────────────┐
            │  主上下文（main 调用链的最深处）      │ ← 先建立
            │  main → process_data → parse_frame │
            │  → 局部变量、保存的寄存器            │   约 260 字节
0x20004EFC  ├──────────────────────────────────┤
            │  第 1 层：EXTI0 ISR（抢占 3）        │
            │   硬件帧 8 字                      │   32 字节
            │   ISR 局部变量 + 调用 HAL 的保存      │   约 48 字节
            ├──────────────────────────────────┤
            │  第 2 层：TIM2 ISR（抢占 2）         │
            │   硬件帧                           │   32 字节
            │   局部变量                         │   约 64 字节
            ├──────────────────────────────────┤
            │  第 3 层：USART1 ISR（抢占 1）       │
            │   硬件帧                           │   32 字节
            │   局部变量 + HAL_UART_IRQHandler 帧  │   约 96 字节
            ├──────────────────────────────────┤
            │  第 4 层：TIM3 ISR（抢占 0）         │
            │   硬件帧                           │   32 字节
            │   局部变量                         │   约 40 字节
0x20004D??  └──────────────────────────────────┘ ← 最坏时的 SP
────────────────────────────────────────────────────────────────────
计 算 ：
  硬件帧合计 = 4 层 × 32 字节 = 128 字节
  ISR 局部变量合计 = 48 + 64 + 96 + 40 = 248 字节
  中断部分最坏 = 128 + 248 = 376 字节
  主上下文     ≈ 260 字节
  ────────────────────────────────
  最坏总用量   = 376 + 260 = 636 字节
  剩余         = 1024 - 636 = 388 字节（占 37.9% 余量）
────────────────────────────────────────────────────────────────────
★ 结论 1：栈余量 388 字节 —— 听起来还行，但这是【理想叠加】的估算。
  真实情况里，各层 ISR 的局部变量大小依赖编译器优化和调用链深度，
  你的估算误差可能达到 ±50%。所以【至少要留 30% 余量】，
  而且必须用实测方法验证（下面给方法）。
────────────────────────────────────────────────────────────────────
★ 结论 2：把 ISR 里塞进一个 printf 会怎样？
  newlib 的 printf（带 %f）单个调用就可能吃 200~500 字节栈，
  加上它内部的 vfprintf 递归调用链：
  最坏总用量 = 636 + 300 ≈ 936 字节 → 只剩 88 字节余量
  再深一层嵌套、或者主循环恰好在调用链深处被中断 → 直接越过 0x20004C00
  → 栈溢出 → 覆盖掉相邻的 .bss 变量（或者更糟：覆盖另一个任务的栈）
  → 现象：一个和中断毫无关系的全局变量莫名其妙被改、或者 HardFault
  ★ 这就是「HardFault 定位到 ISR 里 = 栈溢出」这条经验的来源：
    栈溢出本身不会立刻报错，它是【无声地破坏别人的数据】，
    直到某个倒霉的变量被踩坏才崩，而且崩的位置和原因隔了十万八千里。
────────────────────────────────────────────────────────────────────
★ 结论 3：嵌套深度直接决定最坏栈用量。
  上面 4 层嵌套 = 376 字节。如果把 TIM2 和 EXTI0 设成【同一个抢占级】，
  它们就不嵌套了 → 最坏深度降到 3 → 省下 32 + 48 = 80 字节。
  这是「故意让一部分中断共享优先级」最实在的收益：
  【用一点响应延迟，换稳定的栈预算】。
────────────────────────────────────────────────────────────────────
            
#include "stm32f1xx_hal.h"

/* 思路：开机时把整块栈区填成一个不会自然出现的图案（0xA5），
   跑完整套最坏场景后，从栈底往上扫，看有多少图案被改写。
   被改写到的最深位置，就是实际用到的最大栈深度。 */

#define STACK_FILL_BYTE   0xA5u
#define STACK_SENTINEL     0x400u   /* 给栈留 1KB，与例 3 一致 */

/* ★ 必须在 main 之前、栈还没被大量使用时装填。
   做法：在 Reset_Handler 跳到 main 之前插一句，或者在 main 的第一行调用。
   main 第一行调用是够用的，因为 main 自己还没用多少栈。 */
void stack_paint(void)
{
    extern uint32_t _estack;                 /* 链接脚本里的栈顶符号 */
    uint8_t *top = (uint8_t *)&_estack;
    uint8_t *bottom = top - STACK_SENTINEL;

    for (uint8_t *p = bottom; p < top; p++) {
        *p = STACK_FILL_BYTE;
    }
    /* 注意：这个循环自己也要用栈，但它只用几个字节，
       而且它写在栈底附近，影响的区域正是我们想测的最深处——
       所以更严谨的做法是把它放到 .data 之前、用汇编实现。
       对「量级估算」来说，这个版本已经够用。 */
}

/* 跑完一段最坏场景后调用，返回「从栈底算起的最大使用字节数」 */
uint32_t stack_used_bytes(void)
{
    extern uint32_t _estack;
    uint8_t *top = (uint8_t *)&_estack;
    uint8_t *bottom = top - STACK_SENTINEL;
    uint8_t *p;

    for (p = bottom; p < top; p++) {
        if (*p != STACK_FILL_BYTE) {        /* 找到一个被改写过的字节 */
            return (uint32_t)(top - p);     /* 从栈顶往下数，这就是用量 */
        }
    }
    return 0;                                /* 整个区域都没被动过 */
}

/* 使用方法：在调试会话里
     1) 复位后立刻调用 stack_paint()
     2) 触发最坏场景（比如同时按住所有按键 + 满速串口收发 + 让定时器最密）
     3) 在断点里执行 printf("stack = %lu\n", stack_used_bytes());
   反复几轮取最大值。它就作业余版「栈水位检测」。
   ★ 生产代码里更常见的做法是配合 MPU（带 MPU 的型号）把栈区设成
     「可读写但不可越界」，越界立刻触发 MemManage Fault，而不是静默破坏数据。 */

例 4：50µs 中断的 CPU 占用率与尾链收益

题目：一个定时器每 50µs 中断一次，ISR 本体（含 HAL 调用与清标志）执行 432 个周期。 求 CPU 占用率；其中「进出中断的固定开销」占多少？如果有两个中断都以 20kHz 触发、 且总是背靠背到来，尾链能省多少？再用一组不同长度的 ISR 看看尾链收益的规律。

解：先算出 50µs 在 72MHz 下是多少个周期，再算比例。

基 准 ：50 µs × 72 MHz = 3600 周期/次中断（20 kHz）
        432 周期 = 432 / 72 = 6.0 µs（ISR 本体执行时间）
────────────────────────────────────────────────────────────────────
【第 1 步】单次中断的固定开销（不干活、纯进出的那部分）
   压栈 + 取向量（异步）   14 周期
   异常返回（出栈）        10 周期
   ────────────────────────────
   合计                    24 周期 = 24 / 72 = 0.333 µs
   ★ 这 0.333µs 是「每次中断都要交的过路费」，和 ISR 里干了什么无关
────────────────────────────────────────────────────────────────────
【第 2 步】CPU 占用率
   每次中断实际耗时 = 432（本体） + 24（开销） = 456 周期
   占用率 = 456 / 3600 = 12.67%
   ────────────────────────────
   拆分看：ISR 本体 12.00%，固定开销 0.67%
   ★ 固定开销只占 0.67% —— 这就是为什么「优化中断开销」在多数项目里
     优先级极低；真正吃掉 CPU 的是本体。要降占用率，先缩短 ISR 本体。
────────────────────────────────────────────────────────────────────
【第 3 步】两个 20kHz 中断背靠背到来，尾链省多少
   场景：TIM3 和 DMA1_Channel4 都以 50µs 周期触发，且几乎同时到达
   设 ISR_A 本体 = 200 周期，ISR_B 本体 = 100 周期

   【无尾链（假设的硬件行为）】每次都完整进出：
     开销 = (14 + 10) × 2 = 48 周期
     总耗时 = 200 + 100 + 48 = 348 周期

   【有尾链（Cortex-M3 的真实行为）】
     第一个中断进来：压栈+取向量 14 周期
     做完 ISR_A 后：异常返回时发现 ISR_B 还挂着
        → 不出栈、不回主程序，直接取 ISR_B 的向量：6 周期
     做完 ISR_B 后：正常出栈返回：10 周期
     开销 = 14 + 6 + 10 = 30 周期
     总耗时 = 200 + 100 + 30 = 330 周期

   ────────────────────────────
   省下 18 周期 / 每 50µs
   固定开销从 48 周期降到 30 周期，【降低 37.5%】
   折算成 CPU：省 18 / 3600 = 0.50% 的 CPU
────────────────────────────────────────────────────────────────────
【第 4 步】规律：本体越短、中断越密，尾链收益占比越大
   固定开销：无尾链 48 周期 → 有尾链 30 周期（省 18 周期，恒定不变）
   ┌──────────────┬───────────┬───────────┬───────────┬──────────┐
   │ ISR 本体合计  │ 无尾链总   │ 有尾链总   │ 省下的比例 │ 折算 CPU  │
   ├──────────────┼───────────┼───────────┼───────────┼──────────┤
   │ 600 周期      │ 648       │ 630       │ 2.8%      │ 0.50%    │
   │ 300 周期      │ 348       │ 330       │ 5.2%      │ 0.50%    │
   │ 100 周期      │ 148       │ 130       │ 12.2%     │ 0.50%    │
   │ 30 周期       │ 78        │ 60        │ 23.1%     │ 0.50%    │
   └──────────────┴───────────┴───────────┴───────────┴──────────┘
   ★ 注意最后一列都是 0.50% —— 因为 50µs 的周期下，
     「省 18 周期」的绝对值是固定的。【尾链不会因为省比例高就多省 CPU】。
   ★ 但如果中断频率提高 10 倍（5µs 一次，200kHz），
     无尾链开销 = 48/360 周期 = 13.3% CPU，有尾链 = 8.3% CPU
     → 省 5% CPU，这时候尾链的收益就是真的了。
   ★ 换句话说：尾链是【高频中断场景下的救星】，
     在中低频（< 50kHz）场景下，它省下的 CPU 可以忽略。
     知道这一点，你就不会去为「尾链优化」做无用功，
     也不会在写高频中断驱动时忽略了它带来的 5% 收益。
────────────────────────────────────────────────────────────────────
【第 5 步】顺便算一下「关中断」的代价
   如果主循环里有一段 200µs 的临界区（__disable_irq / __enable_irq）：
     这段期间 50µs 的中断会被挂起 200 / 50 = 4 次（挂起位只记一次，不排队！）
     ★ 关键：NVIC 的 pending 是【一位一个中断】，不是队列。
       挂起 4 次，补上来只执行【1 次】→ 时基直接丢了 3 个 tick
     → 现象：HAL_GetTick() 比真实时间慢，或者定时任务被吞掉
   ★ 结论：临界区必须远小于中断周期，否则就是「时间丢失」。
     200µs 的临界区 + 50µs 的中断 = 3/4 的 tick 被吞掉，这是灾难。
────────────────────────────────────────────────────────────────────

结论：占用率 12.67%（本体 12.00% + 固定开销 0.67%）； 两个中断背靠背时尾链省 18 周期（固定开销降低 37.5%）， 折算 0.50% CPU。真正要盯的不是这 0.5%，而是： ① ISR 本体别写长；② 临界区别超过中断周期的几分之一。 一般工程经验是整体 CPU 占用率留 30% 以上余量（也就是别超过 70%）， 因为你要给「同时发生的最坏情况」和「以后新增的功能」留地方。

一个反直觉但不难理解的推论

既然固定开销在低频下可以忽略，那你为了「省掉进出中断的开销」而做的努力 （比如把两个中断合并成一个、或者把中断改成轮询）—— 省下的可能只是 0.67% 的 CPU，却损失了实时性。 「用轮询代替中断」在 51 时代是常见优化，在 72MHz 的 M3 上往往是亏的。 要不要合并，算一次就知道了：用这一节的算式，别用感觉。

例 5：EXTI 线够不够用

题目：一个项目要接 8 个独立按键，工程师把它们的引脚随手分配在 PA0~PA15、PB0~PB15、PC13~PC15 之间， 每接一个就用一次 EXTI。请问：① 这 37 个可用 GPIO 是否等于 37 个外部中断源？ ② 8 个按键「恰好互不冲突」的概率是多少？③ 冲突时「第二个按键」的响应概率是多少？ ④ 如果一定要用 EXTI 接 8 个键，正确的分配方式是什么？

解：先把「引脚数」和「中断源数」这两个概念掰开。

【问 ①】37 个 GPIO 等于 37 个外部中断源吗？
   ✘ 不等于。可用的 EXTI 线只有 EXTI0 ~ EXTI15 共 16 条。
   F103C8T6（LQFP48）的可用 GPIO 数量：
      PA0~PA15  = 16 个
      PB0~PB15  = 16 个
      PC13~PC15 =  3 个
      PD0~PD1   =  2 个（有些封装不引出）
      ────────────────────
      合计        37 个 GPIO（按 STM32F103C8 数据手册的引脚定义）
   → 37 个引脚，但只有 16 条 EXTI 线。
   → 【一根线号上，PA、PB、PC、PD 的同号引脚只能选一个走中断】
   → 所以「每个引脚一个独立中断」的方案，最多支持 16 个引脚，
      而且这 16 个的引脚号必须两两不同。
   ★ 这就是那条规则的真正含义：限制的不是引脚数量，
     而是【线号（= 引脚号）必须唯一】。
────────────────────────────────────────────────────────────────────
【问 ②】8 个按键随机分配在 0~15 的引脚号上，「互不冲突」的概率是多少？
   这是经典的「生日问题」：16 个格子（引脚号），8 个人（按键），
   求 8 个人占的格子全不相同的概率。
   第 1 个按键随便占一个格子          → 16/16
   第 2 个按键要避开第 1 个          → 15/16
   第 3 个要避开前 2 个              → 14/16
   ...
   第 8 个要避开前 7 个              →  9/16
   ────────────────────────────────
   P(全不冲突) = (16 × 15 × 14 × 13 × 12 × 11 × 10 × 9) / 16^8
              = 518,918,400 / 4,294,967,296
              = 0.1208 → 【只有 12.08%】
   → 反过来：【至少有 2 个按键冲突的概率 = 87.9%】
   ★ 换句话说，随手分配 8 个按键，「一定有键冲突」几乎是必然事件。
     这就是为什么「两个按键只有一个响应」是初学者最常见的故障之一，
     它不是运气不好，它是概率上的默认结果。
────────────────────────────────────────────────────────────────────
【问 ③】冲突时「第二个按键」的响应概率是多少？
   设 PA5 和 PB5 两个按键都想用 EXTI5，而 AFIO_EXTICR2 里
   EXTI5[3:0] 这个 4 位字段只能写一个值：
     写 0b0000（选 PA）→ PA5 的边沿能进中断；PB5 的边沿【永远进不来】
     写 0b0001（选 PB）→ 反过来
   → 于是「第二个按键的响应概率」不是 50%，不是随机，
     而是【0%：完全、稳定、必然地不响应】。
   ★ 这一点非常重要，因为它决定了排查难度：
     ✘ 如果它是「偶发不响应」，你会怀疑是抖动、是电气问题；
     ✔ 而它是「稳定不响应」，所以正确的排查方式是：
        - 按下不响应的那个键，看 EXTI->PR 对应位【有没有置 1】
          → 没置 1 = 边沿压根没到 EXTI = AFIO 选错了端口（就是本例）
          → 置了 1 但没进 ISR = NVIC 没使能 / 优先级被屏蔽
   ★ 还有一个更隐蔽的变体：两个键都在 PA 上（PA5 和 PA6），
     这样不冲突，但如果你只开了 EXTI5 没开 EXTI6，
     PA6 的键同样永远不响应——现象和线冲突【一模一样】。
     所以排查第二步必须看 PR 位，而不是猜。
────────────────────────────────────────────────────────────────────
【问 ④】正确分配方式（8 个按键都用 EXTI，且都要独立响应）
   目标：8 个按键的【引脚号】两两不同 = 落在 8 条不同的 EXTI 线上。
   推荐这样排（避开 JTAG/SWD 占用的 PA13/PA14/PA15/PB3/PB4）：
   ┌──────────┬──────────┬────────────┬──────────────────────────┐
   │ 引脚      │ 引脚号    │ EXTI 线     │ 中断向量（ISR 名）         │
   ├──────────┼──────────┼────────────┼──────────────────────────┤
   │ PA0      │ 0        │ EXTI0      │ EXTI0_IRQHandler         │
   │ PA1      │ 1        │ EXTI1      │ EXTI1_IRQHandler         │
   │ PA2      │ 2        │ EXTI2      │ EXTI2_IRQHandler         │
   │ PA3      │ 3        │ EXTI3      │ EXTI3_IRQHandler         │
   │ PB5      │ 5        │ EXTI5      │ EXTI9_5_IRQHandler  ←┐   │
   │ PB6      │ 6        │ EXTI6      │ EXTI9_5_IRQHandler  ←┤ 共用  │
   │ PB7      │ 7        │ EXTI7      │ EXTI9_5_IRQHandler  ←┤ 一个  │
   │ PB10     │ 10       │ EXTI10     │ EXTI15_10_IRQHandler←┘ 向量  │
   └──────────┴──────────┴────────────┴──────────────────────────┘
   ★ 注意 PB5/PB6/PB7 三个键共用 EXTI9_5_IRQHandler：
     ISR 里要【先判 PR 是哪一位、再判 GPIO_Pin】，这就是第 4 节范式代码的写法。
   ★ 还有个更省心的替代方案——【定时器轮询】：
     10ms 扫一次 GPIO IDR，8 个按键共用一个定时器中断，零线冲突风险，
     而且天然带 10ms 去抖。代价是最坏 10ms 的响应延迟，
     对按键这种 50ms 感知窗口的应用完全够用。
     工程上很多量产产品就是这么做的 —— 【能不用 EXTI 就不用】，
     因为 EXTI 的坑（线冲突、抖动、共用向量、清 PR）比它带来的收益多。
────────────────────────────────────────────────────────────────────

例 6：按截止时间定优先级后的最坏响应延迟

题目：用第 2 节那张建议表的中断集合，验证这套优先级到底能不能满足所有截止时间。 如果反过来把按键放在最高优先级（很多人凭直觉会这么做），后果是什么？

解：用实时系统里的响应时间分析（RTA）来算。 对某个中断 i，它的最坏响应时间 Ri 由三部分组成： 自己的执行时间 Ci + 被阻塞的时间 Bi（最长的关中断临界区）+ 被所有更高优先级中断抢占的时间。 最后一项要用迭代公式，因为「被抢占的时间里又可能被抢占」：

公 式 （RTA，适用于固定优先级抢占式调度，如 NVIC）：
   R_i = C_i + B_i + Σ_{j∈hp(i)} ⌈R_i / T_j⌉ × C_j
   其中：hp(i) = 所有抢占优先级比 i 高的中断集合
         T_j   = 中断 j 的触发周期
         ⌈ ⌉   = 向上取整（在 R_i 这段时间里，j 最多会来 ⌈R_i/T_j⌉ 次）
   迭代方法：先令 R_i = C_i + B_i，代入右边算出一个更大的值，
             再代回去，直到两次结果相同（收敛）。
────────────────────────────────────────────────────────────────────
输 入 数 据 （按截止时间排出的优先级）
   中断        抢占优先级   执行时间 C   周期 T     截止时间 D
   TIM3        0（最高）    6 µs       50 µs      50 µs
   USART1      1            8 µs       87 µs      87 µs
   TIM2        2            5 µs       1000 µs    1000 µs
   EXTI0       14（最低）    2 µs       随机（秒级） 50000 µs（人感知）
   最长临界区 B = 10 µs（主循环里一段关中断的环形缓冲区操作）
   中断进出开销已计入 C（每个 C 都按「本体 + 0.33µs 过路费」估算）
────────────────────────────────────────────────────────────────────
【算 TIM3（最高优先级）】
   hp 集合为空，Σ 项 = 0
   R = 6 + 10 + 0 = 16 µs
   检验：16 µs < 50 µs ✔ 余量 68%

【算 USART1】
   hp = {TIM3}：T=50, C=6
   ── 先插入一段【故意走错路】的演示：把 B 也放进迭代项会怎样 ──
   R₀ = 8 + 10 = 18
   R₁ = 18 + ⌈18/50⌉ × 6 = 18 + 1×6 = 24
   R₂ = 24 + ⌈24/50⌉ × 6 = 24 + 6 = 30
   R₃ = 30 + ⌈30/50⌉ × 6 = 30 + 6 = 36          ← 注意：R 变大了，但 ⌈R/50⌉ 还是 1
   R₄ = 36 + 1×6 = 42
   R₅ = 42 + ⌈42/50⌉ × 6 = 42 + 6 = 48
   R₆ = 48 + ⌈48/50⌉ × 6 = 48 + 6 = 54          ← 越过 50 了！取整变成 2
   R₇ = 54 + ⌈54/50⌉ × 6 = 54 + 2×6 = 66
   R₈ = 66 + ⌈66/50⌉ × 6 = 66 + 2×6 = 78
   R₉ = 78 + 2×6 = 90                            ← 又越过 87 了吗？不，是 TIM3 的 50，
                                                     ⌈90/50⌉ = 2，不变
   R₁₀= 90 + 2×6 = 102 ...
   ★ 等一下——收敛好像出问题了。继续代：
   R = 102 → ⌈102/50⌉ = 3 → R = 102 + 18 = 120
   R = 120 → ⌈120/50⌉ = 3 → R = 120 + 18 = 138
   R = 138 → ⌈138/50⌉ = 3 → R = 138 + 18 = 156
   R = 156 → ⌈156/50⌉ = 4 → R = 156 + 24 = 180
   ... 它在无限增长！
   ────────────────────────────
   ★★ 这说明用 RTA 时【绝不能把 B（临界区）算成"每周期都发生"】。
      我上面的代入犯了一个错：B 只在「你恰好撞上临界区」时发生一次，
      不是每轮迭代都加一次。正确的做法是【只加一次 B】，
      迭代时只让 Σ 项随 R 增长：
      R = C + B + Σ_j ⌈R/T_j⌉ × C_j    ← B 在初始化时加，后续迭代不再加
   重算 USART1：令 R = 8 + 10 = 18（含一次 B），后续只迭代 Σ：
      R = 8 + 10 + ⌈18/50⌉×6  = 18 + 6  = 24
      R = 8 + 10 + ⌈24/50⌉×6  = 18 + 6  = 24  ✔ 收敛
   → 【USART1 最坏响应时间 = 24 µs】
      检验：24 µs < 87 µs ✔ 余量 72%
────────────────────────────────────────────────────────────────────
【算 TIM2】
   hp = {TIM3 (T=50,C=6), USART1 (T=87,C=8)}
   初值 R = C + B = 5 + 10 = 15
   R = 15 + ⌈15/50⌉×6 + ⌈15/87⌉×8 = 15 + 6 + 8 = 29
   R = 29 + ⌈29/50⌉×6 + ⌈29/87⌉×8 = 29 + 6 + 8 = 29  ✔ 收敛
   → 【TIM2 最坏响应时间 = 29 µs】
      检验：29 µs < 1000 µs ✔ 余量 97%
────────────────────────────────────────────────────────────────────
【算 EXTI0（最低）】
   hp = {TIM3, USART1, TIM2}
   初值 R = 2 + 10 = 12
   R = 12 + ⌈12/50⌉×6 + ⌈12/87⌉×8 + ⌈12/1000⌉×5 = 12 + 6 + 8 + 5 = 31
   R = 31 + ⌈31/50⌉×6 + ⌈31/87⌉×8 + ⌈31/1000⌉×5 = 31 + 6 + 8 + 5 = 31  ✔ 收敛
   → 【EXTI0 最坏响应时间 = 31 µs】
      检验：31 µs < 50000 µs ✔ 余量 99.9%
────────────────────────────────────────────────────────────────────
汇 总 表
  中断      优先级  最坏响应 R   截止时间 D   R < D ?   余量
  TIM3      0       16 µs       50 µs        ✔        68%
  USART1    1       24 µs       87 µs        ✔        72%
  TIM2      2       29 µs       1000 µs      ✔        97%
  EXTI0     14      31 µs       50000 µs     ✔        99.9%
  ★★ 全部满足。这才是「配好了」的定义——不是"能跑"，而是
     【每一个中断的最坏响应时间都有据可查地小于它的截止时间】。
────────────────────────────────────────────────────────────────────
【反 面 案 例】把按键放到最高优先级（抢占 0），其他顺次下移
   EXTI0 = 0, TIM3 = 1, USART1 = 2, TIM2 = 3
   ────────────────────────────
   ① USART1 的最坏响应时间：
      hp = {EXTI0, TIM3}
      按键的「周期」不是固定的 —— 抖动时每分钟可能有几十个边沿，
      取最坏情况 T = 2.33µs（每次按键中断 = 2µs 本体 + 0.33µs 开销）
      R = 8 + 10 + ⌈R/2.33⌉×2.33 + ⌈R/50⌉×6
      当 R ≈ 100µs 时：⌈100/2.33⌉ = 43 → 43 × 2.33 = 100µs
      也就是说 R 会被按键完全填满，逐次迭代下去【不收敛】→
      系统在这个最坏假设下【不可调度】（实时性无从保证）
   ────────────────────────────
   ② 算一个具体的临界点：USART1 最多能容忍多少 µs 的阻塞？
      截止时间 87µs − 自身执行 8µs − 中断延迟 0.2µs ≈ 78.8 µs
      每个按键中断占用 2µs + 0.33µs = 2.33µs
      → 78.8 / 2.33 ≈ 【33 个】
      结论：按键的抖动边沿只要累计超过 33 次，串口就会开始丢字节。
      ★ 机械按键在按下/松开瞬间产生几十个抖动边沿是家常便饭，
        尤其是触点氧化的旧按键（可达上百次）。
        所以「按键抢最高优先级」不是理论风险，是必然出问题。
   ────────────────────────────
   ③ 对比「按键最低优先级」时：
      按键被推迟到 31µs 才响应 —— 用户完全感知不到（人的感知阈值约 50ms）
      而串口拿到了 24µs 的响应 —— 稳稳不丢字节
      【同一套中断，只换了一个优先级数字，一个丢数据一个不丢】
────────────────────────────────────────────────────────────────────
【附：利用率检验（快速判断"这套中断是不是太满了"）】
   U = Σ C_i / T_i
     = 6/50 + 8/87 + 5/1000 + (按键按 10ms 一次、C=2.33µs 估)
     = 0.120 + 0.0920 + 0.0050 + 0.000233
     = 0.2172 → 【21.7%】
   对 4 个任务，速率单调调度（RM）的可调度性充分条件是：
     U ≤ n(2^(1/n) − 1) = 4 × (2^0.25 − 1) = 4 × 0.1892 = 0.7568
   21.7% << 75.7% ✔ 有充足余量
   ★ 反过来，如果算出来 U 已经接近 70~80%，
     别急着加中断，先回去把 ISR 本体砍短 —— 那才是分母。
────────────────────────────────────────────────────────────────────

结论：按「截止时间」排出的优先级，四个中断的最坏响应时间分别是 16 / 24 / 29 / 31µs，全部远小于各自截止时间（50µs / 87µs / 1ms / 50ms）， 总利用率 21.7%，系统有充分余量。 而按「重要性」把按键放最高，会让 USART1 在最坏情况下不可调度， 并且只要按键抖动累计 33 次，串口就开始丢字节。 这就是「按截止时间排优先级」这句话的全部含义——它不是一个风格偏好，是一个可以算出来的结论。

RTA 迭代里那个必须避开的坑（上面例 6 特意演示了）

我第一次代入时把阻塞时间 B 放进了迭代公式里，结果 R 无限增长。 这不是数学问题，是我对模型的误解：B 是「最多被阻塞一次」的持续时间 （你不可能被同一段临界区阻塞两次），所以它只在初值里加一次， 迭代时只让 Σ（被更高优先级抢占）随 R 增长。 这个坑很典型：用公式算实时性的时候，模型搞错了比算错了更危险—— 算错你会得到一个偏保守的数，模型错你会得到一个无限增长、看似"系统完蛋"的假警报 （或者反过来，一个看似收敛、实则漏掉最坏情况的假安心）。

在单片机上的样子

这一节的代码都是可以直接编译的。前两段是同一个功能的两种写法（手写寄存器版和 HAL 版）， 建议你两个都跑一遍——手写版会让你彻底记住「两级使能」和「AFIO 时钟」， HAL 版会让你理解 CubeMX 到底替你做了什么。 后面四段是四个实验，每个实验都有一个明确的「你会看到什么」。

手写寄存器版：EXTI0 按键中断

目标：按键接 PA0，另一端接 GND，按下时 PA0 从高变低（下降沿）。 每按一次，主循环里的计数加一，并把结果从串口打出来。 这个版本不依赖 HAL，只用 CMSIS 提供的寄存器定义，所以你能看清每一步在写哪个位。 

/* ============================================================================
 * exti0_reg.c  ——  手写寄存器版：PA0 按键下降沿中断
 * 目标芯片：STM32F103C8T6（中容量），SYSCLK = 72MHz
 * 依赖：只依赖 CMSIS 的 stm32f103xb.h（提供 RCC / GPIOA / AFIO / EXTI / NVIC / SCB）
 *       不需要 HAL，也不需要 CubeMX 生成的代码
 * ============================================================================ */
#include "stm32f103xb.h"

/* ── 全局：中断与主循环之间传递信息的变量 ──
   ★ volatile 是必须的：
     没有它，编译器在 -O2 下会把 g_key_press_cnt 缓存进寄存器，
     主循环的 while 永远读到旧值，看起来像"中断没有生效"。 */
static volatile uint32_t g_key_press_cnt = 0;   /* 有效按键次数（已去抖） */
static volatile uint32_t g_ms_tick       = 0;   /* SysTick 维护的毫秒计数 */
static volatile uint32_t g_key_last_ms   = 0;   /* 上次有效按键的时间戳 */

#define EXTI0_LINE   (1UL << 0)                 /* EXTI0 这条线的位掩码 */
#define DEBOUNCE_MS  (20UL)                     /* 软件去抖窗口 */

/* ============================================================================
 * 1. 时钟：GPIOA + AFIO
 * ============================================================================
 * RCC->APB2ENR 的位定义（RM0008 第 8 章「RCC 寄存器描述」）：
 *   bit0  = AFIOEN    辅助功能 IO 时钟
 *   bit2  = IOPAEN    GPIOA 时钟
 *   bit3  = IOPBEN    GPIOB 时钟
 *   bit4  = IOPCEN    GPIOC 时钟
 * 复位后这些位全是 0 —— 也就是【所有外设默认都没有时钟】。
 * ★ 用按键的 EXTI 就必须开 AFIO 时钟：不开的话 AFIO->EXTICR 的写操作
 *   会被硬件直接丢弃（读回永远是 0），于是所有线都连在 PA 上，
 *   你用 PB 的引脚就永远不响应 —— 这是最难查的一类故障。 */
static void clk_init(void)
{
    RCC->APB2ENR |= RCC_APB2ENR_AFIOEN | RCC_APB2ENR_IOPAEN;
    (void)RCC->APB2ENR;     /* 读回一次：让写操作在慢速外设总线上落定（习惯做法） */
}

/* ============================================================================
 * 2. PA0 配成「上拉输入」
 * ============================================================================
 * F1 的 GPIO 配置寄存器是 CRL / CRH，每 4 位管一个引脚：
 *   CRL 管 pin0 ~ pin7，CRH 管 pin8 ~ pin15
 *   每个引脚的 4 位 = [ CNF1 CNF0 MODE1 MODE0 ]
 * 输入模式（MODE = 00）下的 CNF：
 *   CNF = 00 → 模拟输入（给 ADC 用）
 *   CNF = 01 → 浮空输入（复位默认值）
 *   CNF = 10 → 上拉 / 下拉输入，具体是哪一个由 ODR 决定
 *   CNF = 11 → 保留
 * 所以「上拉输入」的 4 位 = CNF=10, MODE=00 = 0b1000 = 0x8 */
static void gpio_init(void)
{
    GPIOA->CRL &= ~(0xFUL << (0 * 4));    /* 先清掉 PA0 的 4 个配置位 */
    GPIOA->CRL |=  (0x8UL << (0 * 4));    /* CNF=10 上拉/下拉输入，MODE=00 输入 */
    GPIOA->ODR |=  (1UL << 0);            /* ODR 置 1 → 选择【上拉】（按键另一端接 GND） */
}

/* ============================================================================
 * 3. AFIO：把 EXTI0 这条线接到 PA 上
 * ============================================================================
 * AFIO->EXTICR1 管 EXTI0 ~ EXTI3，每 4 位一个线号：
 *   [3:0]  = EXTI0    [7:4]   = EXTI1
 *   [11:8] = EXTI2    [15:12] = EXTI3
 * 取值：0b0000 = PA，0b0001 = PB，0b0010 = PC，0b0011 = PD，0b0100 = PE
 * ★ 这一句就是「线号 = 引脚号」规则的落地：
 *   EXTI0 只能连 PA0 / PB0 / PC0 / PD0 / PE0 中的一个，
 *   想同时用 PA0 和 PB0 的中断 —— 不可能，只能选一个。 */
static void afio_init(void)
{
    AFIO->EXTICR[0] &= ~(0xFUL << 0);
    AFIO->EXTICR[0] |=  (0x0UL << 0);      /* 0b0000 = 选 PA0 */
}

/* ============================================================================
 * 4. EXTI：屏蔽位 + 触发沿 + 清挂起位
 * ============================================================================
 * 顺序有意设计成这样：
 *   ① 先清 PR（写 1 清除，可能残留着复位期间的电平变化）
 *   ② 配置期间先屏蔽 IMR，避免配置到一半就有边沿进来
 *   ③ 最后才打开 IMR —— 到这里这一级使能才算完成 */
static void exti_init(void)
{
    EXTI->PR    = EXTI0_LINE;               /* 写 1 清除残留挂起位（写 0 无效！） */
    EXTI->IMR  &= ~EXTI0_LINE;              /* 配置期间先屏蔽这一路 */
    EXTI->RTSR &= ~EXTI0_LINE;              /* 不要上升沿 */
    EXTI->FTSR |=  EXTI0_LINE;              /* 要下降沿（按下时电平从高变低） */
    /* EXTI->EMR 保持 0：不要事件模式，我们要的是中断（要进 ISR） */
    EXTI->IMR  |=  EXTI0_LINE;              /* ★ 第一级使能：打开中断屏蔽位 */
}

/* ============================================================================
 * 5. NVIC：第二级使能 + 优先级
 * ============================================================================
 * EXTI0_IRQn = 6（见 CMSIS 的 IRQn_Type 枚举）
 *   中断号 6 落在 ISER[0]（管 0~31）的 bit 6
 *   优先级写在 NVIC->IP[6]，只有【高 4 位】有效
 *     → 数值 14 必须写成 14 << 4 = 0xE0
 *     → 直接写 14 会怎样？14 = 0b00001110，高 4 位是 0
 *       → 实际优先级变成 0（最高！）—— 见第 2 节的 0x0F 陷阱
 * 分组必须在写 IP 之前确定好，因为 IP 里的位【含义】由分组决定。 */
static void nvic_init(void)
{
    uint32_t aircr;

    /* 设分组为「4 位抢占 + 0 位响应」：PRIGROUP = 0b011 = 3
       AIRCR 的写入门票：高 16 位必须写 0x05FA，否则整个写操作被忽略 */
    aircr  = SCB->AIRCR;
    aircr &= ~((0xFFFFUL << 16) | (0x7UL << 8));
    aircr |=  (0x05FAUL << 16) | (0x3UL << 8);
    SCB->AIRCR = aircr;

    NVIC->IP[EXTI0_IRQn] = (uint8_t)(14UL << (8 - 4));   /* 数值 14 → 写 0xE0 */
    NVIC->ISER[0]        = (1UL << (EXTI0_IRQn & 0x1F)); /* ★ 第二级使能 */
    /* 通用写法（中断号可能 >= 32 时）：
       NVIC->ISER[irq >> 5] = 1UL << (irq & 0x1F);
       NVIC->IP[irq]        = (uint8_t)(prio << (8 - 4)); */
}

/* ============================================================================
 * 6. SysTick：自己数毫秒（用来做软件去抖）
 * ============================================================================
 * ★ 优先级要设低：SysTick 是【内核异常】，它的优先级写在 SCB->SHP 里，
 *   不在 NVIC->IP 里，而且 SHP 的下标是「异常号 - 4」：
 *     SysTick 异常号 = 15 → SHP[15 - 4] = SHP[11]
 *   注意 SHP 的字节同样「只有高 4 位有效」。 */
static void systick_init(void)
{
    SysTick->LOAD = 72000UL - 1UL;          /* 72MHz / 1000 = 72000 周期 → 1ms */
    SysTick->VAL  = 0UL;                    /* 写任何值都会清零当前计数 */
    SysTick->CTRL = SysTick_CTRL_CLKSOURCE_Msk   /* 用内核时钟 72MHz，不是 HCLK/8 */
                  | SysTick_CTRL_TICKINT_Msk     /* 计数到 0 时产生中断 */
                  | SysTick_CTRL_ENABLE_Msk;     /* 启动 */

    SCB->SHP[11] = (uint8_t)(15UL << (8 - 4));  /* 最低优先级，别抢别的东西 */
}

void SysTick_Handler(void)      /* 名字来自向量表，不能改 */
{
    g_ms_tick++;
}

/* ============================================================================
 * 7. 中断服务函数
 * ============================================================================
 * ★ 函数名 EXTI0_IRQHandler 是【固定的】，来自 startup_stm32f103xb.s 里的向量表。
 *   那里对每个中断都有一个 .weak 弱定义（死循环），
 *   你在 C 里写一个同名函数，链接器就会用你的强定义覆盖它 —— 见第 2 节。 */
void EXTI0_IRQHandler(void)
{
    /* 判挂起位：只有真的置着才处理（防止误进，也方便共用向量的情况） */
    if (EXTI->PR & EXTI0_LINE)
    {
        EXTI->PR = EXTI0_LINE;      /* ★★ 清挂起位！
                                       漏掉这一句 = 一次按键进千万次中断，
                                       现象是"程序卡死在中断里出不来" */

        /* 软件去抖：距离上次有效按键不到 20ms 就当作抖动丢弃。
           这样即使硬件边沿产生了 30 个抖动脉冲，也只会记 1 次。 */
        uint32_t now = g_ms_tick;
        if ((now - g_key_last_ms) > DEBOUNCE_MS)
        {
            g_key_last_ms = now;
            g_key_press_cnt++;      /* 只做「记录」：不延时、不打印、不发串口 */
        }
    }
    /* 退出 ISR 由硬件完成：出栈 8 个字、恢复 PC，回到被打断的地方 */
}

/* ============================================================================
 * 8. 主循环：真正干活的地方
 * ============================================================================ */
static void do_something_slow(uint32_t cnt);   /* 前向声明 */

int main(void)
{
    uint32_t seen = 0;

    clk_init();         /* ① 时钟：GPIOA + AFIO */
    gpio_init();        /* ② 引脚：PA0 上拉输入 */
    afio_init();        /* ③ AFIO：EXTI0 接到 PA0 */
    systick_init();     /* ④ 毫秒时基（用于去抖） */
    exti_init();        /* ⑤ EXTI：第一级使能 + 下降沿 */
    nvic_init();        /* ⑥ NVIC：第二级使能 + 优先级 */

    for (;;)
    {
        uint32_t cnt;

        /* 临界区：把共享变量「取出来看一眼」。
           单个 32 位对齐变量的读本身就是原子的（一条 LDR），
           这里加临界区是为了演示写法 —— 当共享数据是结构体、
           或者你要"读并清零"时，就【必须】这样保护。 */
        __disable_irq();
        cnt = g_key_press_cnt;
        __enable_irq();

        if (cnt != seen)
        {
            seen = cnt;
            /* ★ 所有耗时的事都放这里：它们不在中断上下文，
               花 1ms 还是 100ms 都只是让主循环变慢，不会破坏实时性 */
            do_something_slow(cnt);
        }
    }
}

static void do_something_slow(uint32_t cnt)
{
    /* 示例：把计数写进一个变量，供调试器观察；
       真实项目里这里可能是刷新 OLED、往 Flash 写日志、发一帧串口数据…… */
    static volatile uint32_t g_display_value;
    g_display_value = cnt;
}
怎么编译与验证

一个最小工程需要四样东西：exti0_reg.c、 启动文件 startup_stm32f103xb.s（ST 官网或 CubeMX 包里）、 链接脚本 STM32F103C8Tx_FLASH.ld、以及 system_stm32f1xx.c（负责把主频配到 72MHz）。 用 arm-none-eabi-gcc 编译， st-flash write build/exti0.bin 0x08000000 烧写。

不要把它和 HAL_Init() 混在一个工程里—— HAL_Init() 自己会配置 SysTick 和优先级分组， 和你这里的 systick_init()、nvic_init() 会互相覆盖，出现「优先级分组突然变了」这类怪事。 手写寄存器版和 HAL 版选一个，别两边都伸手。

HAL 版：同样功能的初始化

现在换 HAL 做同一件事。代码短了很多，但每一步都要能在心里映射回上面那段—— 否则你就只是在抄 CubeMX 生成的代码。 

/* ============================================================================
 * hal_exti.c  ——  HAL 版：和手写寄存器版完全相同的功能
 * ============================================================================ */
#include "stm32f1xx_hal.h"

static volatile uint32_t g_key_press_cnt = 0;
static volatile uint32_t g_key_last_ms   = 0;

/* ── 初始化 ──
   对照手写版看每一行在干什么：
     __HAL_RCC_AFIO_CLK_ENABLE()  ←→  RCC->APB2ENR |= AFIOEN
     __HAL_RCC_GPIOA_CLK_ENABLE() ←→  RCC->APB2ENR |= IOPAEN
     HAL_GPIO_Init()              ←→  GPIOA->CRL + AFIO->EXTICR + EXTI->IMR/RTSR/FTSR
     HAL_NVIC_SetPriority()       ←→  SCB->AIRCR + NVIC->IP[n]
     HAL_NVIC_EnableIRQ()         ←→  NVIC->ISER[n>>5]
*/
void key_exti_init(void)
{
    GPIO_InitTypeDef gpio_init;

    /* ★ AFIO 时钟。
       CubeMX 只在「用了重映射」或「用了 EXTI 的端口选择」时才生成这一句；
       手写代码最容易漏的就是它，而漏了的后果是 EXTICR 写不进（读回 0），
       所有线都连在 PA 上 —— 用 PB/PC 的按键永远不响应。 */
    __HAL_RCC_AFIO_CLK_ENABLE();
    __HAL_RCC_GPIOA_CLK_ENABLE();

    /* 引脚：输入 + 下降沿中断 + 内部上拉。
       HAL 把「输入模式」和「EXTI 触发沿配置」合并成了一个宏：
         GPIO_MODE_IT_FALLING 在 stm32f1xx_hal_gpio_ex.h 里展开后，
         除了把 CRL 配成输入，还会去写 EXTI->FTSR 和 EXTI->IMR。 */
    gpio_init.Pin   = GPIO_PIN_0;
    gpio_init.Mode  = GPIO_MODE_IT_FALLING;    /* 输入 + 下降沿触发中断 */
    gpio_init.Pull  = GPIO_PULLUP;             /* 内部上拉（按键另一端接 GND） */
    gpio_init.Speed = GPIO_SPEED_FREQ_LOW;     /* 输入模式下无意义，但结构体必须填全 */
    HAL_GPIO_Init(GPIOA, &gpio_init);

    /* NVIC：第二级使能 + 优先级。
       ★ HAL_NVIC_SetPriority 传的是【数值】（0~15），不是移好位的原始值。
       ★ HAL_GPIO_Init 已经替你开了 EXTI->IMR（第一级），
         但它【不会】碰 NVIC —— 所以下面这两行一行都不能省。 */
    HAL_NVIC_SetPriority(EXTI0_IRQn, 14, 0);
    HAL_NVIC_EnableIRQ(EXTI0_IRQn);
}

/* ============================================================================
 * 中断服务函数：CubeMX 生成在 stm32f1xx_it.c 里
 * ============================================================================
 * ★ 注意这里的函数体只有一行：把活交给 HAL。
 *   为什么？因为【清 PR 这件事必须由库来做】，
 *   如果让你自己清，每个人都会在某个时刻忘记，然后遇到"一次触发反复进"。
 *   HAL 的设计是：IRQHandler 只负责转发，清标志和分发都在库里。 */
void EXTI0_IRQHandler(void)
{
    HAL_GPIO_EXTI_IRQHandler(GPIO_PIN_0);
    /* 展开后的行为：
         if (EXTI->PR & GPIO_PIN_0) {        // 判挂起位
             EXTI->PR = GPIO_PIN_0;          // ★ 清挂起位
             HAL_GPIO_EXTI_Callback(GPIO_PIN_0);  // 调你的回调
         } */
}

/* ============================================================================
 * 你的业务：重写 __weak 的 HAL_GPIO_EXTI_Callback
 * ============================================================================
 * ★ 所有 EXTI 引脚【共用这一个函数】，所以第一个动作必须是判 GPIO_Pin。
 *   忘了判的后果：任何一个引脚的中断都会把「所有按键」的标志一起点亮，
 *   现象是「按 A 键，程序认为 B、C 键也按了」。 */
void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
{
    if (GPIO_Pin == GPIO_PIN_0)
    {
        uint32_t now = HAL_GetTick();
        if ((now - g_key_last_ms) > 20UL)     /* 20ms 软件去抖 */
        {
            g_key_last_ms = now;
            g_key_press_cnt++;                /* 只记录，不干活 */
        }
    }
    else if (GPIO_Pin == GPIO_PIN_1)
    {
        /* 第二个按键：注意它必须在【不同的 EXTI 线】上才可能进到这里 */
    }
    /* 没有 else 分支：别的引脚不该进这个回调 */
}

/* ============================================================================
 * 主循环
 * ============================================================================ */
int main(void)
{
    uint32_t seen = 0;

    HAL_Init();                 /* 配置 Flash 等待周期、SysTick(1ms)、优先级分组(4) */
    SystemClock_Config();       /* CubeMX 生成的 72MHz 时钟树配置 */
    key_exti_init();

    for (;;)
    {
        uint32_t cnt;
        __disable_irq();
        cnt = g_key_press_cnt;
        __enable_irq();

        if (cnt != seen)
        {
            seen = cnt;
            key_on_pressed(cnt);    /* 耗时的业务放这里 */
        }
    }
}
对比项 手写寄存器版 HAL 版
初始化代码行数 约 45 行（6 个函数） 约 20 行（1 个函数）
你能看见的寄存器 全部：APB2ENR / CRL / ODR / EXTICR / IMR / RTSR / FTSR / IP / ISER / SHP 一个都看不见（全被库函数包住）
出错的典型方式 漏写一句（比如忘了 AFIO 时钟）→ 现象明确，寄存器可查 调用顺序错（比如在 HAL_Init() 之前设优先级）→ 被库静默覆盖
清 PR 的责任 你自己写（写错了就是一次触发反复进） 库帮你写（你甚至不知道有 PR 这个寄存器）
换芯片的代价 寄存器名全变，代码要重写 改一下 HAL_GPIO_EXTI_Callback 就能移植
适合什么场景 学习、极简工程、需要精确控制时序的场合 产品开发、多外设、需要快速迭代
HAL 里最容易踩的三个顺序问题
  1. 在 HAL_Init() 之前设优先级分组： HAL_Init() 内部会调 HAL_NVIC_SetPriorityGrouping(NVIC_PRIORITYGROUP_4)， 把你之前设的分组覆盖掉。分组一定在 HAL_Init() 之后设。
  2. 在 SystemClock_Config() 之前初始化带超时的外设： 此时主频还没到 72MHz，HAL_GetTick() 的刻度也是错的， 超时时间会算错。
  3. 只调 HAL_NVIC_SetPriority() 忘了 HAL_NVIC_EnableIRQ()： 设优先级不等于使能。两个函数，两件事。

正确范式：中断只置标志，主循环去处理

这是整篇文章里最该带走的一段代码。规则只有一句话： ISR 里只做「记录事实」和「通知」，所有耗时的事都搬回主循环。 难点在于「怎么安全地把事实传出去」——这就是 volatile 和临界区的用武之地。 

/* ============================================================================
 * 范式一：单标志（最简单，也最容易写对）
 * ============================================================================
 * 适合：只关心"发生过至少一次"，不关心中间丢了几次的事件。
 * 典型：按键、看门狗喂狗请求、模式切换。
 * ============================================================================ */
static volatile uint8_t  g_uart_rx_flag = 0;      /* ISR 置 1，主循环清 0 */
static volatile uint8_t  g_rx_byte      = 0;

void USART1_IRQHandler(void)
{
    if (USART1->SR & USART_SR_RXNE)
    {
        g_rx_byte = (uint8_t)(USART1->DR & 0xFF);  /* 读 DR 顺便清 RXNE */
        g_uart_rx_flag = 1;                         /* ★ 只置标志 */
    }
}

void main_loop_rx(void)
{
    if (g_uart_rx_flag)                 /* 读 */
    {
        uint8_t b = g_rx_byte;
        g_uart_rx_flag = 0;             /* ★ 在主循环里清 */
        handle_byte(b);                  /* 这里可以做任何耗时的事 */
    }
}
/* ★ 单标志模式的固有缺陷：如果主循环处理慢，
   两次中断之间只有一个字节被处理，【其余全丢】。
   要一个都不丢，就得用范式二的环形缓冲区。 */

/* ============================================================================
 * 范式二：单生产者单消费者环形缓冲区（工业界最常用）
 * ============================================================================
 * 适合：串口接收、ADC 采样流、按键事件队列 —— 要求一个都不丢。
 * 关键结构：一个数组 + 一个写指针（只有 ISR 写）+ 一个读指针（只有主循环写）。
 * ★ 神奇之处：因为【head 只有一个写者、tail 也只有一个写者】，
 *   两个指针各自是"单写多读"，而 32 位对齐变量的读写本身是原子的，
 *   所以这个缓冲区【完全不需要关中断】就能安全工作。
 * ============================================================================ */
#define RX_BUF_SIZE 64                     /* 必须是 2 的幂，才能用 & 取模 */

static volatile uint8_t  g_rx_buf[RX_BUF_SIZE];
static volatile uint16_t g_rx_head = 0;    /* 只由 ISR 修改 */
static volatile uint16_t g_rx_tail = 0;    /* 只由主循环修改 */

void USART1_IRQHandler(void)
{
    if (USART1->SR & USART_SR_RXNE)
    {
        uint8_t  b    = (uint8_t)(USART1->DR & 0xFF);
        uint16_t next = (uint16_t)((g_rx_head + 1U) & (RX_BUF_SIZE - 1U));

        if (next != g_rx_tail)             /* 缓冲区没满才写 */
        {
            g_rx_buf[g_rx_head] = b;
            g_rx_head = next;              /* ★ 最后才更新 head：
                                              保证主循环看到 head 变了时，
                                              对应的数据一定已经写好了 */
        }
        else
        {
            g_rx_overflow_cnt++;           /* 满了：记一次溢出，用于事后诊断 */
        }
    }
}

/* 主循环里取一个字节；返回 0 表示目前没有数据 */
static int rx_get(uint8_t *out)
{
    if (g_rx_head == g_rx_tail) return 0;  /* 空 */
    *out = g_rx_buf[g_rx_tail];
    g_rx_tail = (uint16_t)((g_rx_tail + 1U) & (RX_BUF_SIZE - 1U));
    return 1;
}

/* ============================================================================
 * 范式三：多字节共享数据 —— 这里才【真的】需要临界区
 * ============================================================================
 * 危险场景：主循环要读一个结构体，而 ISR 可能在读的中途改写它的一半。
 *   struct { uint32_t ts; int16_t x, y, z; } g_sample;
 * 主循环读 ts 之后被中断，ISR 更新了 x/y/z 和 ts，
 * 于是主循环拿到的是「旧 ts + 新 x/y/z」—— 一组【从来没真实存在过】的数据。
 * 这种错误的可怕之处：它不崩溃，只是数据悄悄错了。
 * ============================================================================ */
typedef struct {
    uint32_t ts_ms;
    int16_t  ax, ay, az;
} sample_t;

static volatile sample_t g_sample;
static volatile uint32_t g_sample_seq = 0;   /* 序号：ISR 每次更新 +1 */

void EXTI1_IRQHandler(void)                  /* 假设加速度计的数据就绪中断接在这 */
{
    if (EXTI->PR & (1UL << 1))
    {
        EXTI->PR = (1UL << 1);
        /* ISR 写入：先写数据、再加序号。
           序号是"数据已就绪"的发布点，一定要最后写。 */
        g_sample.ax = read_accel_x();
        g_sample.ay = read_accel_y();
        g_sample.az = read_accel_z();
        g_sample.ts_ms = HAL_GetTick();
        g_sample_seq++;                       /* ★ 发布 */
    }
}

/* 主循环读取：用「双读序号」技巧，避免长时间关中断
   思路：读序号 → 读数据 → 再读序号。
        两次序号相同说明读的过程中没被 ISR 改写过，数据是完整的；
        不同就重读。这是无锁读取的经典做法，代价是可能重试几次。 */
static int sample_read(sample_t *out)
{
    uint32_t seq_before, seq_after;

    seq_before = g_sample_seq;
    __DMB();                                  /* 数据内存屏障：别让编译器/CPU 乱序 */
    out->ax = g_sample.ax;
    out->ay = g_sample.ay;
    out->az = g_sample.az;
    out->ts_ms = g_sample.ts_ms;
    __DMB();
    seq_after = g_sample_seq;

    return (seq_before == seq_after);         /* 1 = 成功，0 = 被改写过，请重试 */
}

/* 如果嫌上面的重试逻辑麻烦，用最简单的临界区也完全可以 ——
   只要临界区【足够短】（这里就是几条 LDR，约 10~20 个周期 = 0.3µs）： */
static void sample_read_locked(sample_t *out)
{
    __disable_irq();
    *out = *(sample_t *)&g_sample;
    __enable_irq();
}
/* ★ 判断该用哪种，只需要问一句：
   "这段关中断的时间，会不会让别的中断错过截止时间？"
   10~20 个周期（0.3µs）对 99% 的系统都无所谓；
   但如果你在临界区里拷贝一个 200 字节的缓冲区（约 200 个周期 2.8µs），
   就该考虑双读序号或者双缓冲了。 */

/* ============================================================================
 * 附：F103 上的一个小宝藏 —— 位带（bit-band）原子置位
 * ============================================================================
 * Cortex-M3 有"位带"机制：把 SRAM 和外设区的每一个位映射到
 * 别名区的一个 32 位字上。写那个字就等于原子地读改写那一个位。
 * 有了它，某些 "flags |= 1" 的竞态可以【不关中断】就解决。
 *
 * 别名地址公式（SRAM 区）：
 *   别名 = 0x22000000 + (字节地址 - 0x20000000) x 32 + 位号 x 4
 * ============================================================================ */
#define BITBAND_SRAM_WORD(addr, bit) \
    (*(volatile uint32_t *)(0x22000000UL \
        + (((uint32_t)(addr) - 0x20000000UL) * 32UL) \
        + ((uint32_t)(bit) * 4UL)))

static volatile uint32_t g_flags = 0;

/* 在 ISR 里置位：编译成一条 STR 指令，天然原子，不需要关中断 */
#define FLAG_KEY_PRESSED    BITBAND_SRAM_WORD(&g_flags, 0)
#define FLAG_RX_TIMEOUT     BITBAND_SRAM_WORD(&g_flags, 1)

void EXTI2_IRQHandler(void)
{
    if (EXTI->PR & (1UL << 2))
    {
        EXTI->PR = (1UL << 2);
        FLAG_KEY_PRESSED = 1;      /* ← 一条指令，绝无竞态 */
    }
}
/* ★ 对比一下这两种写法的区别：
     g_flags |= (1UL << 0);     ← 读-改-写三条指令，主循环同时改别的位就会丢更新
     FLAG_KEY_PRESSED = 1;      ← 一条 STR，原子
   第 27 篇讲过的 "flags |= 1 丢标志" 问题，在 M3 上就有了这个硬件解法。
   注意：位带只对【置位/清零单个位】有用。要"读并清零"、
   或者要更新一个 16 位数据，还是得用临界区。 */
这三种范式怎么选
场景 用哪种 理由
按键、模式切换、出错通知 范式一：单标志 丢几次无所谓，代码最短，最不容易写错
串口接收、ADC 采样流 范式二：环形缓冲区 一个都不能丢；单写者模型天然无锁
一组相关的数据（时间戳 + 三个轴） 范式三：序号双读 或 临界区 多字节数据必须保证「看到的是一组完整快照」
只想原子地置一个位 位带 一条指令搞定，连关中断都省了

复现实验：不清 PR 会怎样

这个实验十分钟就能做完，但它能让你永远记住清挂起位这件事。 做法是故意制造三种错误，看现象是否一致。 

准 备 ：用第 4 节的 exti0_reg.c 工程（或 HAL 版），能正常跑通。
       在 EXTI0_IRQHandler 的第一行下断点（或者在里面加一句 GPIO 翻转）。
────────────────────────────────────────────────────────────────────
【实验 1-A】把清 PR 那一句直接注释掉
   改动：  // EXTI->PR = EXTI0_LINE;
   现象：  按一次按键 → 断点第一次命中
          按"全速运行" → 立刻又命中
          再全速 → 又命中 …… 无限循环
          如果不设断点，表现是【主循环再也不执行了】，看起来像死机
   观察寄存器（调试器的 System Viewer 或 Watch 窗口）：
          EXTI->PR 的 bit0 = 1  （一直是 1，从没被清掉）
          NVIC->ISPR[0] 的 bit6 = 1（你退出 ISR 后立刻又被置 1）
   手动验证因果：在 Watch 窗口里把 EXTI->PR 的值写成 1（写 1 清除）
          → 立刻恢复正常，不再反复进中断
          ★ 这一步把"因果"钉死了：不是抖动、不是别的问题，就是 PR
────────────────────────────────────────────────────────────────────
【实验 1-B】写成"清 0"（这个变体比忘记清更常见！）
   改动：  EXTI->PR = 0;          ← 想当然地以为 0 表示清除
   现象：  和 1-A 完全一样，一次触发反复进
   原因：  PR 是【写 1 清除】（rc_w1）寄存器。
          写 0 到某一位 = 什么也不做。写 1 = 清除那一位。
   教训：  所有 rc_w1（read/clear by writing 1）寄存器都遵守这条规则，
          它和普通寄存器完全相反，是嵌入式的经典陷阱。
          同类的还有：USART->SR 的部分位、TIM->SR 的标志位、
          DMA 的 IFCR —— 全都"写 1 清除"。
────────────────────────────────────────────────────────────────────
【实验 1-C】清错了线号
   改动：  EXTI->PR = (1UL << 1);   ← 想清 EXTI1，实际是 EXTI0 在挂起
   现象：  和 1-A 一样。EXTI0 的 PR bit0 依然是 1
   原因：  PR 是 20 位一位一线的，清一位不会影响别的位。
          这也解释了为什么【不要写 EXTI->PR = 0xFFFF 一把全清】——
          那会把你没处理的其他线（比如事件模式留下的、或者留给别人的）一起抹掉。
────────────────────────────────────────────────────────────────────
【实验 1-D】用 SWIER 触发，不需要用手按（调试利器）
   在调试器里执行这一句（或者在 main 里加一行）：
        EXTI->SWIER = (1UL << 0);      // 软件触发 EXTI0
   效果：和"真的按了一下 PA0"完全一样（置 PR → 送 NVIC → 进 ISR）
   用途：  ① 没有硬件、或者按键接触不良时也能测中断通路
          ② 精确定位"是引脚没配好"还是"NVIC 没使能"：
             能进去 → 引脚配置/电气有问题
             进不去 → NVIC 或向量表有问题
          ③ 在高频循环里反复写 SWIER，可以制造"中断风暴"，
             用来测最坏情况下的 CPU 占用率
────────────────────────────────────────────────────────────────────
【怎么看到这些寄存器】
   · Keil MDK：View → System Viewer → EXTI / NVIC
   · STM32CubeIDE：调试时用 SFR 视图，或直接在 Watch 里写表达式

        *(volatile uint32_t*)0xE000E200       // NVIC->ISPR[0]
        *(volatile uint32_t*)0xE000E100       // NVIC->ISER[0]
        *(volatile uint32_t*)0xE000E400       // NVIC->IP[0..3]
   · OpenOCD + GDB：monitor mdw 0x40010414 1
   ★ 养成习惯：任何"中断不响应/反复进"的问题，
     第一步都是打开 PR 和 ISPR 这两个寄存器看一眼 ——
     它们的值能直接把故障范围砍掉一半。

测量中断延迟与尾链收益

Cortex-M3 内置了一个免费的周期计数器 DWT->CYCCNT， 它按 CPU 时钟计数，精度就是一个周期。用它可以把第 2 节那些"典型周期数" 换成你自己芯片上的真实数字。 

/* ============================================================================
 * measure.c  ——  用 DWT->CYCCNT 做周期级测量
 * ============================================================================
 * 为什么能用：Cortex-M3 的 DWT（Data Watchpoint and Trace）单元里有一个
 * 32 位的自由运行周期计数器 CYCCNT，它按 CPU 时钟递增，不需要调试器连着。
 * 在 72MHz 下它大约每 2^32 / 72e6 ≈ 59.6 秒回绕一次 ——
 * 用无符号减法 (now - t0) 天然处理回绕，不用管。
 * ============================================================================ */
#include "stm32f1xx_hal.h"

static void dwt_init(void)
{
    CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;   /* 打开跟踪/调试模块的时钟 */
    DWT->CYCCNT = 0;                                  /* 计数器清零 */
    DWT->CTRL |= DWT_CTRL_CYCCNTENA_Msk;              /* 启动计数 */
    /* ★ 如果读出来一直是 0：说明这颗芯片的 DWT 没实现 CYCCNT，
       或者 DEMCR 的 TRCENA 没打开。F103（M3 r1p1 及以后）都有。 */
}

/* ============================================================================
 * 测 1：ISR 本体到底花了多少个周期
 * ============================================================================ */
static volatile uint32_t g_isr_cycles_last = 0;
static volatile uint32_t g_isr_cycles_max  = 0;
static volatile uint32_t g_isr_count       = 0;

void EXTI0_IRQHandler(void)
{
    uint32_t t0 = DWT->CYCCNT;      /* 入口时间戳（这几条指令本身也占时间，
                                       所以要把它们从结果里扣掉，见下面的说明） */
    uint32_t dt;

    if (EXTI->PR & (1UL << 0))
    {
        EXTI->PR = (1UL << 0);
        g_key_press_cnt++;          /* 业务：这里只有一句，方便对照测量结果 */
    }

    dt = DWT->CYCCNT - t0;          /* ★ 无符号减法，天然处理计数器回绕 */
    g_isr_cycles_last = dt;
    if (dt > g_isr_cycles_max) { g_isr_cycles_max = dt; }
    g_isr_count++;
}
/* 测出来之后怎么解读：
   · 入口时间戳那两条语句（LDR CYCCNT + 压栈）约占 3~5 个周期，
     所以真实 ISR 时长 ≈ g_isr_cycles_last - 约 6
   · 典型值参考（-O2，无浮点）：
       "置一个标志"级     → 20~35 周期（0.3~0.5µs）
       "读 DR + 存环形缓冲区" 级 → 40~70 周期（0.6~1.0µs）
       调用 HAL_GPIO_EXTI_IRQHandler + 回调 → 60~110 周期（0.8~1.5µs）
   · 如果你测出 500 周期以上，去看是不是在 ISR 里调了什么重家伙。
   ★ g_isr_cycles_max 比平均值更有用：实时性看的是最坏情况。 */

/* ============================================================================
 * 测 2：从「引脚边沿」到「ISR 第一条指令」的真实延迟（要用示波器）
 * ============================================================================
 * 软件自己测不了这个延迟 —— 因为在 ISR 执行之前，
 * CPU 根本没有在跑你的代码，没人能打时间戳。
 * 唯一诚实的办法是在 ISR 入口【立刻】翻转一个 GPIO，用示波器量时间差。
 * ============================================================================ */
void EXTI0_IRQHandler_measure_latency(void)
{
    /* ★ BSRR 是"位设置/清除寄存器"，写它是一条 STR 指令、
       单周期生效，而且不需要读-改-写 —— 是 ISR 里最快的输出方式 */
    GPIOB->BSRR = (1UL << 12);     /* PB12 拉高（示波器 CH2） */

    if (EXTI->PR & (1UL << 0)) { EXTI->PR = (1UL << 0); }

    GPIOB->BSRR = (1UL << (12 + 16));   /* PB12 拉低：高电平的宽度 = ISR 时长 */
}
/* 接线与操作：
     CH1 接按键信号（PA0 那一侧，或者用一个信号发生器给它一个下降沿方波）
     CH2 接 PB12
     触发方式：CH1 下降沿触发
     测量：CH1 下降沿到 CH2 上升沿的时间差 = 中断延迟
   预期：72MHz 下 200~400ns（对应第 3 节例 2 的 14~15 周期 + 几周期指令开销）
   ★ 要扣掉的部分：ISR 第一条指令（BSRR 写）从取指到生效约 2~3 个周期
     （约 30~40ns），可以忽略也可以扣掉。
   ★ 想要更干净的测量：把触发源换成另一个定时器的 PWM 输出，
     让下降沿非常陡（几 ns），比按键的机械抖动好得多。
   ★ 把主频从 72MHz 降到 8MHz 再测一次，你会看到延迟变成 1.7µs 左右 ——
     和第 3 节例 2 的计算对上了，这就证明了"延迟周期数是常数"。 */

/* ============================================================================
 * 测 3：尾链（tail-chaining）到底省了多少
 * ============================================================================
 * 思路：让两个中断以相同的频率触发，比较两种情况的"平均每次中断周期数"：
 *   A 组：两个中断错开触发（各自独立，永远不背靠背）→ 每次都完整进出
 *   B 组：两个中断故意对齐触发（同一时刻到达）→ 触发尾链
 * 做法：把 TIM3 和 TIM4 都配成同样的周期，但让 TIM4 的计数器错开半个周期。
 * ============================================================================ */
static volatile uint32_t g_total_cycles = 0;   /* 累计：ISR 里的周期数 */
static volatile uint32_t g_irq_total    = 0;   /* 累计：中断次数 */

static void record_isr(uint32_t t0)
{
    g_total_cycles += DWT->CYCCNT - t0;
    g_irq_total++;
}

void TIM3_IRQHandler(void)
{
    uint32_t t0 = DWT->CYCCNT;
    if (TIM3->SR & TIM_SR_UIF) { TIM3->SR = ~TIM_SR_UIF; }
    record_isr(t0);
}

void TIM4_IRQHandler(void)
{
    uint32_t t0 = DWT->CYCCNT;
    if (TIM4->SR & TIM_SR_UIF) { TIM4->SR = ~TIM_SR_UIF; }
    record_isr(t0);
}

void measure_report(void)
{
    /* 平均每次中断的周期数。注意这个"平均"里【混着尾链的收益】，

复现 HAL_Delay 进中断的死锁

这是整篇文章的「点题实验」——计划表里那句话「中断里调用 HAL_Delay 为什么会死锁」， 就在这里给出完整解释。它不是"可能出问题"，而是必然会卡死。 

/* ── HAL_Delay：阻塞式延时的全部实现 ── */
__weak void HAL_Delay(uint32_t Delay)
{
    uint32_t tickstart = HAL_GetTick();      /* ① 取当前 tick */
    uint32_t wait = Delay;

    if (wait < HAL_MAX_DELAY)                /* 处理 HAL_MAX_DELAY 的特殊含义 */
    {
        wait += (uint32_t)(uwTickFreq);
    }

    while ((HAL_GetTick() - tickstart) < wait)   /* ② 死等，直到 tick 走过 wait */
    {
        /* 空循环 */
    }
}

/* ── HAL_GetTick：只返回一个变量 ── */
__weak uint32_t HAL_GetTick(void)
{
    return uwTick;                            /* ③ uwTick 就是"时间"本身 */
}

/* ── uwTick 是谁在维护？SysTick 中断 ── */
__weak void HAL_IncTick(void)
{
    uwTick += (uint32_t)uwTickFreq;           /* ④ 每次 tick 中断加 1 */
}

void SysTick_Handler(void)                    /* 中断向量表指向它 */
{
    HAL_IncTick();                            /* ⑤ 一切时间都从这一个中断来 */
    HAL_SYSTICK_IRQHandler();                 /* HAL 的内部 tick 回调 */
}

把上面五个步骤串起来看，死锁的链条就清楚了： HAL_Delay 等的是 uwTick 变化， 而 uwTick 只在 SysTick_Handler 里加一。 如果你在中断里调 HAL_Delay， 而这个中断的抢占优先级又比 SysTick 高（或者和它同值）， SysTick 就永远得不到执行机会，uwTick 冻住， while 的条件永远为真——死在这里，出不去。 

死 锁 的 精 确 条 件
────────────────────────────────────────────────────────────────────
   SysTick 的抢占优先级【数值】 ≥ 当前 ISR 的抢占优先级【数值】
   ⇔ SysTick 无法抢占当前 ISR（数值越大越低，相等则同级不嵌套）
────────────────────────────────────────────────────────────────────
【配置一：分组 4，SysTick 优先级 = 15（TICK_INT_PRIORITY 的常见默认值）】
   任何中断的优先级数值都 ≤ 15（0~15）
   → 所有 ISR 里的 HAL_Delay 都会死锁，没有例外
   → 现象：
       · 第一次按键，LED 不亮、串口没输出，主循环像是停了
       · 调试器按暂停 → 调用栈显示：
           HAL_Delay
           HAL_GPIO_EXTI_Callback
           HAL_GPIO_EXTI_IRQHandler
           EXTI0_IRQHandler
       · ★ 决定性证据：Watch 窗口里盯着 uwTick，它【不再增长】
         （正常情况下它应该每毫秒 +1）
   → 为什么是"死锁"而不是"延时变长"：
     没有任何外部力量能改变 uwTick，这不是等待，是永久停止。
────────────────────────────────────────────────────────────────────
【配置二：把 TICK_INT_PRIORITY 改成 0（SysTick 变成最高优先级）】
   打开你的 stm32f1xx_hal_conf.h，找到：
       #define  TICK_INT_PRIORITY   ...
   如果是 0（或者任何比你那个 ISR 数值更小的值）：
   → SysTick 能打断你的 ISR，uwTick 正常增长，HAL_Delay 能返回
   → 【不会死锁，但换成了另一个更隐蔽的问题】：
       · 你的 ISR 真的在里面停了 10ms
       · 这 10ms 里，所有优先级比 SysTick 低的中断全部被推迟
       · 而且 SysTick 每 1ms 都来打断你一次
     → 现象：平时看起来能跑，一旦串口/ADC 频率上来就开始丢数据
     → 这类"偶尔丢数据"的问题，比死锁难查十倍
   ★ 所以正确的结论不是"SysTick 优先级设高就能用 HAL_Delay"，
     而是【HAL_Delay 从来就不该出现在任何中断里】。
────────────────────────────────────────────────────────────────────
【同类的函数（都有一个 Timeout 参数，都依赖 HAL_GetTick）】
   HAL_UART_Transmit()      —— 超时判定用 tick；但等待 TXE 用的是硬件标志
                                所以它【可能】看起来能跑，直到某次 TXE 没来 → 卡死
   HAL_UART_Receive()
   HAL_I2C_Master_Transmit() / HAL_I2C_Mem_Read() 等在中断里调用必死
   HAL_SPI_Transmit()
   HAL_FLASH_Program() / HAL_FLASHEx_Erase()  —— 写 Flash 要几毫秒，还会【阻塞总线取指】
   ★ 判断标准很简单：【凡是带 Timeout 参数的阻塞式 HAL 函数，都不能进中断】。

/* ============================================================================
 * ✘ 错误写法 1：直接延时（必然死锁）
 * ============================================================================ */
void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
{
    if (GPIO_Pin == GPIO_PIN_0)
    {
        HAL_GPIO_WritePin(GPIOC, GPIO_PIN_13, GPIO_PIN_RESET);  /* 点亮 LED */
        HAL_Delay(10);                                          /* ★★ 死在这里 */
        HAL_GPIO_WritePin(GPIOC, GPIO_PIN_13, GPIO_PIN_SET);    /* 永远到不了 */
    }
}

/* ---- 复现步骤 ----
   1) 烧写上面这段，连上调试器
   2) 在 HAL_Delay(10); 这一行下断点，按一下按键
   3) 断点命中。把它删掉，改成在 HAL_Delay 之后的语句下断点
   4) 全速运行 → 永远不再命中
   5) 暂停调试器：调用栈停在 HAL_Delay 的 while 里
   6) 打开 Watch 窗口添加 uwTick → 它的值【始终不变】
      ★ 换成添加 DWT->CYCCNT，它却在飞快地涨 —— 这直接证明
        "CPU 在跑，但时间停了"，也就是 SysTick 中断没有执行
   7) 再看 NVIC->ISER[0] 的 bit15（SysTick 没有 ISER，看 SCB->SHP[11]）
      和 SCB->ICSR 的 PENDSTSET 位（SysTick 挂起位）
      → 你会看到 PENDSTSET = 1：SysTick 的请求【挂在那里没人处理】
    ★ 最后这一步是理解的关键：SysTick 的挂起位一直是 1，
      说明它想进但进不来 —— 因为它优先级比当前 ISR 低。
   ------------------------------------------------------------------ */

/* ============================================================================
 * ✔ 修正 1（推荐）：状态机 + 时间戳，延时逻辑搬到主循环
 * ============================================================================
 * 这是工业代码里 90% 的"ISR 里要等一会儿"该怎么写。 */
static volatile uint8_t  g_led_blink_req = 0;   /* ISR 只置请求 */
static volatile uint32_t g_led_req_ms    = 0;   /* 请求发生的时刻 */

void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
{
    if (GPIO_Pin == GPIO_PIN_0)
    {
        g_led_req_ms = HAL_GetTick();     /* ★ 只取一个时间快照，不做等待 */
        g_led_blink_req = 1;
    }
}

/* 主循环里的小状态机：把"点亮 → 等 10ms → 熄灭"拆成两个时刻 */
void led_task(void)
{
    static uint8_t  state = 0;            /* 0=空闲 1=已点亮 2=已完成 */
    static uint32_t t_on  = 0;

    switch (state)
    {
    case 0:
        if (g_led_blink_req)              /* 有请求 */
        {
            g_led_blink_req = 0;
            HAL_GPIO_WritePin(GPIOC, GPIO_PIN_13, GPIO_PIN_RESET);
            t_on = HAL_GetTick();
            state = 1;
        }
        break;

    case 1:
        /* ★ 时间比较要用无符号减法，不要写 (HAL_GetTick() > t_on + 10)
           —— 后者在 tick 回绕（约 49.7 天）时会失效 */
        if ((HAL_GetTick() - t_on) >= 10UL)
        {
            HAL_GPIO_WritePin(GPIOC, GPIO_PIN_13, GPIO_PIN_SET);
            state = 2;
        }
        break;

    case 2:
        state = 0;                        /* 回到空闲，等下一次请求 */
        break;
    }
}
/* ★ 这个写法的三个好处：
     ① ISR 里只有两条赋值（约 10 个周期），实时性无损
     ② 延时期间 CPU 完全空出来干别的事，不是空转
     ③ 可以同时有多个请求排队（把 req 换成计数器或队列即可）
   ★ 唯一要注意：g_led_req_ms 和 g_led_blink_req 之间要保证顺序。
     这个例子里即使主循环读到"req=1 但 ms 是旧值"，最坏也只是延时差一点，
     属于可接受的抖动。如果顺序有严格要求，用范式三的序号双读。 */

/* ============================================================================
 * ✔ 修正 2：如果真的要"等一小会儿"（微秒级），用 DWT 而不是 HAL_Delay
 * ============================================================================
 * 适用：等 ADC 稳定、等某个引脚变化，量级在 1~100µs，且你确切知道
 *       这几十微秒不会让别的中断错过截止时间。 */
static void delay_cycles(uint32_t cycles)      /* 阻塞式，但【不依赖任何中断】 */
{
    uint32_t start = DWT->CYCCNT;
    while ((DWT->CYCCNT - start) < cycles)
    {
        __NOP();
    }
}
/* 用法：delay_cycles(720);   // 72MHz 下约 10µs
   ★ 为什么它不会死锁：它数的是 CPU 周期，和中断、和 uwTick 完全无关。
   ★ 但它仍然是"在中断里空转"——只是不会死，不等于好。
     只在真的需要硬件级短延时（比如软件模拟某个时序）时才用。 */

/* ============================================================================
 * ✔ 修正 3：用硬件定时器代替软件延时（最"嵌入式"的做法）
 * ============================================================================
 * 需要"延时 10ms 后做某事"时，让定时器替你数，CPU 全程自由。 */
static void start_one_shot_10ms(void)
{
    /* 用一个基本定时器做单次触发（TIM6/TIM7 最合适，它们没有输出引脚，
       纯做时基）。思路：
         __HAL_RCC_TIM6_CLK_ENABLE();
         TIM6->PSC  = 7200 - 1;      // 72MHz / 7200 = 10kHz → 0.1ms 一格
         TIM6->ARR  = 100 - 1;       // 100 格 = 10ms
         TIM6->CR1  = TIM_CR1_OPM    // ★ One Pulse Mode：数完自动停
                    | TIM_CR1_URS    //   只由溢出产生更新事件
                    | TIM_CR1_CEN;
         TIM6->DIER |= TIM_DIER_UIE; // 开更新中断
         HAL_NVIC_SetPriority(TIM6_IRQn, 5, 0);
         HAL_NVIC_EnableIRQ(TIM6_IRQn);
       然后在 TIM6_IRQHandler 里做"延时之后"的那件事。
       因为 OPM 让定时器数完就停，所以不需要在 ISR 里关中断或清 CEN。 */
}
/* ★ 三种修正怎么选：
     要"等一会儿再做"且期间 CPU 有用  → 修正 1（状态机），首选
     要微秒级的硬件时序            → 修正 2（DWT 空转）
     要精确的 10ms / 1s 级定时       → 修正 3（硬件定时器）
     要"在中断里睡一觉"            → 【没有这种需求，重新想想设计】 */
这个死锁最难的地方：它只在"第一次按下按键"时才暴露

如果你用的是开发板，通常有个 LED 在别的地方闪、或者有个串口在主动发数据， 那些都不受影响（因为它们在别的中断里或者主循环里）。 于是你看到的是「按键没反应」，很容易去怀疑按键接触不良、怀疑 EXTI 配置。

最快的定位方法就是看 uwTick 有没有在涨。 这是「系统时间是否还活着」的唯一指标：

  • uwTick 冻结 → 有代码在比 SysTick 优先级更高的中断里等待（就是本例）
  • uwTick 正常但按键没反应 → 回到 EXTI->PR 和 NVIC->ISPR 两条线索
  • uwTick 涨得比真实时间慢 → 有很长的临界区在吞 tick（第 3 节例 4 第 5 步）

配置一个中断的七步检查清单（照着走一遍就不会漏）

  3. 选 EXTI 线：AFIO->EXTICR 选端口，并确认这个线号没被别的引脚占用。
  4. 配触发沿：RTSR / FTSR，以及先清 PR。
  5. 开第一级使能：EXTI->IMR（事件模式则用 EMR）。
  6. 开第二级使能 + 设优先级：NVIC->ISER + NVIC->IP（数值要左移 4 位）。
  7. 在 ISR 里清标志，并且只放"记录 + 置标志"的代码。

故障排查时反向走一遍：从 ISR 往回查——先看 PR 有没有置 1 （有 = 边沿到 EXTI 了，问题在后半段；没有 = 问题在前半段）， 再看 ISPR 有没有置 1（有 = NVIC 收到了，问题在优先级/使能；没有 = 还在 EXTI 那一侧）。 这两次观察能把七个步骤一刀切成三段，排查速度翻几倍。

常见误解与坑：十条逐条定位

这一节的十条，全部来自真实的调试现场。每一条都按「错误认知 → 为什么错 → 正确做法」写， 并且给出可观察的证据——因为只有能看见的东西才能被排查。

坑 1：「引脚上有边沿，就一定会进中断」

错误认知：我把 GPIO 初始化成 EXTI 模式，又调了 HAL_NVIC_EnableIRQ()，那就该进中断了。

为什么错：从引脚边沿到 ISR，中间有五道关卡，任何一道没开都不进中断， 而且五种情况的现象完全一样（都是"没反应"），所以必须靠寄存器区分。 最容易被漏的是 AFIO 时钟——不开它，EXTICR 的写操作会被硬件丢弃（读回 0）， 于是所有线都连在 PA 上，你用 PB 的按键永远不响应；这个故障甚至不是偶发的，是必然的， 但因为现象和"漏开中断使能"一模一样，很多人会查错方向。

正确做法：按第 4 节那张「七步检查清单」写代码； 排查时用「EXTI->PR 有没有置 1」把故障一刀切成两段： PR = 0 → 问题在前半段（时钟/引脚/AFIO/触发沿）；PR = 1 → 问题在后半段（IMR/NVIC/优先级）。

坑 2：「清标志随便写，反正库会清」

错误认知：中断挂了、反复进，我加一句 EXTI->PR = 0; 清一下就好了。

为什么错：PR 是 rc_w1（写 1 清除）寄存器——写 0 到某一位等于什么也不做，写 1 才清除那一位。 所以 EXTI->PR = 0; 完全没有效果，现象和"忘了清"一模一样。 这个变体比"忘记清"更常见，因为它看起来像是在"清零"。 同类的还有 USART->SR 的部分位、TIM->SR 的标志、 DMA 的 IFCR、ADC 的 SR——它们全都是「写 1 清除」。

正确做法：只清你刚刚确认过的那一位： EXTI->PR = (1UL << line);。 不要写 EXTI->PR = 0xFFFF; 一把全清——那会抹掉别的线（包括事件模式留下的）的状态。 用 HAL 时，HAL_GPIO_EXTI_IRQHandler() 已经替你清好了， 你千万不要在回调里再清一次（双重清除会让你漏掉紧跟其后的第二个边沿）。

坑 3：「优先级数字越大，优先级越高」

错误认知：我要让串口最紧急，给它设 15。

为什么错：Cortex-M 的规则是数值越小优先级越高，0 是最高。 这和很多人的直觉（也和一些其他架构）正好相反。 更隐蔽的一层：NVIC_SetPriority() 收的是数值（0~15）， 而 configMAX_SYSCALL_INTERRUPT_PRIORITY 那种宏是已经左移好的原始值（典型 0x50 = 80）， 把后者传给前者，会在左移时溢出截断成 0——优先级反而变成最高。见第 2 节的那个坑。

正确做法：给每组中断在注释里写清「数值 + 是数值还是原始值」， 例如 HAL_NVIC_SetPriority(USART1_IRQn, 2, 0); /* 数值 2，第二紧急 */； 开机时加一段 NVIC_GetPriority() 自检断言。

坑 4：「把响应优先级设高，就能打断别人」

错误认知：两个中断抢占优先级都是 1，但我给重要的那个设了响应优先级 0， 所以它应该能打断另一个（响应优先级 3）。

为什么错：响应（子）优先级只参与"同时挂起时谁先被取走"这一个判断， 永远不能造成嵌套。抢占优先级相同 = 同级 = 不能互相打断，不管响应优先级差多少。 这条规则违反了不会报错、不会 HardFault，只会让你"看起来配了其实没配上"， 于是延迟比设计值大很多，很难联想到原因。

正确做法：需要嵌套的，就必须用不同的抢占优先级； 用响应优先级只是为了"同层内排先后"，别指望它做实时性保证。 反过来，如果你不想让两个中断嵌套（比如为了控制栈用量）， 就把它们的抢占优先级设成相同——这是有意为之的工程手段，不是疏漏。

坑 5：「按键最重要，给它最高优先级」

错误认知：用户操作是产品的核心，按键中断当然要最高优先级，不能被别的东西拖慢。

为什么错：优先级的依据是截止时间，不是重要性。 按键的截止时间是 50ms（人的感知阈值），而串口在 115200 下的字节间隔只有 87µs—— 两者差三个数量级。把按键放最高，意味着每次按键抖动都会打断串口； 按第 3 节例 6 的算式，抖动边沿累计超过 33 次串口就开始丢字节， 而机械按键产生几十次边沿是常态。更糟的是这属于"概率性丢数据"， 在实验室按几下测不出来，到用户手里才暴露。

正确做法：按第 3 节例 6 的方法，为每个中断写下它的截止时间， 然后按截止时间从小到大分配抢占优先级数值（0 给最紧的）。 按键、显示、RTC 这类"人机类"给最低的那几级。

坑 6：「回调里不用判 GPIO_Pin，反正只会有一个引脚触发」

错误认知：我只有一个按键用 EXTI，回调里直接写业务就行，判 GPIO_Pin 是多余的。

为什么错：因为 HAL_GPIO_EXTI_Callback() 是 所有 EXTI 引脚共用的一个函数。今天只有一个按键，等三个月后你加了第二个传感器中断 （比如红外接收头、或者霍尔传感器），你会忘记回来补判断—— 那时现象是「传感器一有信号，程序就认为按键被按了」。 而且这个 bug 在开发阶段完全看不到（因为你只接了按键），是典型的"埋雷"。

正确做法：回调第一行永远是 if (GPIO_Pin == GPIO_PIN_x)，有多少个引脚就有多少个分支。 更进一步：把"引脚 → 动作"做成一张表，回调里查表分发，加新引脚时只改表不改逻辑。

坑 7：「中断里延时/打印一下，只是慢一点而已」

错误认知：HAL_Delay(10)、 HAL_UART_Transmit()、printf() 放进中断，无非是慢一点，功能还是对的。

为什么错：它们不是"慢一点"，而是分三种不同程度的灾难： ① 必然死锁：HAL_Delay 等的是 uwTick， 而 uwTick 靠 SysTick 中断增长；SysTick 优先级比你低（或同级）就永远涨不了， 于是永久卡住——第 4 节给了完整的复现步骤和决定性证据（uwTick 冻结）。 ② 栈溢出：printf 单个调用可能吃 200~500 字节栈， 在深度 4 的嵌套里足够让 1KB 的栈爆掉，而且爆掉的表现是"某个无关变量被改坏"或 HardFault。 ③ 破坏数据：printf、malloc 都是不可重入的，中断里调用会破坏主循环正在维护的内部状态。

正确做法：ISR 里只做「记录 + 置标志」； 需要打印就往环形缓冲/队列里塞原始数据，主循环格式化输出； 需要延时就用第 4 节的三种修正（状态机 / DWT 空转 / 硬件定时器）。 一条硬判据：凡是带 Timeout 参数的阻塞式 HAL 函数，都不能进中断。

坑 8：「变量加了 volatile 就安全了」

错误认知：我把共享变量声明成 volatile， 中断和主循环都读写它，这就万无一失了。

为什么错：volatile 只保证 「每次都从内存重新读、不许优化掉」（可见性），它不保证任何原子性。 具体有两个层级的坑： ① 位操作丢更新：flags |= (1 << 2); 在汇编上是 「读 flags → 或上掩码 → 写回」三条指令，如果在这中间被中断打断、而中断改了别的位， 你的写回会把中断的修改覆盖掉（第 27 篇讲过这个反汇编对照）。 ② 多字节数据撕裂：主循环读一个结构体读到一半被中断，得到「新的一半 + 旧的一半」， 这组数据从来没有真实存在过。这类错误不崩溃、只出错，是最难查的一类。

正确做法：按第 4 节的三种范式选： 单标志（不用保护）/ 环形缓冲区（单写者模型天然无锁）/ 多字节数据（序号双读或临界区）； 只想原子地置一个位，用 F103 的位带别名，一条 STR 指令搞定。

坑 9：「优先级分组随便设一个就行」

错误认知：我只有一个中断自用，分组设几都无所谓。

为什么错：分组是全局的、作用于整个 NVIC， 不是你新加的那个中断的私有设置。你用的不止一个中断—— SysTick、PendSV、SVC 以及 HAL 内部用到的都在同一个 NVIC 里。 中途改分组会让所有已经设好的优先级含义瞬间改变（因为同一个字节的两段被重新划分了）。 而且分组只能往粗里改：从 16 个抢占级改到 4 个之后， 原来能嵌套的中断会变成同级，你没法用响应位把它们再分开。 还有一个静默覆盖：HAL_Init() 内部会调 HAL_NVIC_SetPriorityGrouping(NVIC_PRIORITYGROUP_4)， 你在它之前设的分组会被无声抹掉。

正确做法：在 main() 里 HAL_Init() 之后设一次，写清注释， 之后全局都不再动；代码评审时把"改分组"当成和"改时钟树"同级的危险操作。

坑 10：「FreeRTOS 的 FromISR 和唤醒标志，加不加都行」

错误认知：我在中断里用 xQueueSendFromISR(q, &d, NULL) 也能把数据发出去，那个 pxHigherPriorityTaskWoken 参数传 NULL 省事。

为什么错：传 NULL 确实"能发出数据"，所以它在功能测试里看起来是对的。 但被唤醒的高优先级任务不会立即运行——它要等到调度器下一次自然抢占（下一个 tick）才可能切换， 于是「中断 → 任务开始处理」的延迟从几个µs 变成最多 1ms。 对需要快速响应的场合（比如串口协议的应答、步进电机的脉冲），这 1ms 就是功能失效。 另一半更危险：如果这个中断的优先级数值小于 configMAX_SYSCALL_INTERRUPT_PRIORITY （也就是比那条线更紧急），它根本不允许调用任何 FreeRTOS API—— 因为它能抢占内核临界区，会破坏内核数据结构，现象是随机 HardFault 或队列指针错乱。

正确做法：ISR 里三步走全写： BaseType_t woken = pdFALSE; → xQueueSendFromISR(q, &d, &woken); → portYIELD_FROM_ISR(woken);； 并且把所有会调用 RTOS API 的中断优先级数值限制在 ≥ 5（即 configMAX_SYSCALL_INTERRUPT_PRIORITY 对应的数值）， 打开 configASSERT 让 FreeRTOS 自己在 vPortValidateInterruptPriority() 里替你抓违规。

十条里最该背下来的三条

如果只记三条，记这三条： ① PR 是写 1 清除，而且必须清； ② 优先级数值越小越高，且分组的位含义是全局的； ③ 中断里只置标志，凡是带 Timeout 的阻塞函数一律不准进中断。 这三条覆盖了初学者 80% 的中断故障。

小结与自检

要点清单

  • 中断是一条链，不是一件事。 完整链路是：外设事件 → EXTI（边沿检测、PR、IMR）→ NVIC（两级使能、优先级）→ 向量表（VTOR + 4×异常号）→ XXX_IRQHandler → HAL 转发层（清 PR）→ 你的 Callback → 置标志 → 主循环处理。每一环都有自己的寄存器和默认值。
  • 向量表里放的是地址，不是函数。 第 0 项是初始栈顶（不是代码地址），第 1 项才是 Reset_Handler； 每个 ISR 地址的最低位必须是 1（Thumb 标记）。 默认表在 0x08000000，Bootloader/IAP 场景要用 SCB->VTOR 重定位，跳转前必须 __disable_irq() 且重定位后的表要对齐到 128 字（512 字节）边界。
  • .weak 是"可以被覆盖"的声明。 启动文件里每个 ISR 都有一条弱定义（跳到死循环）， 你在 C 里写一个同名函数，链接器就会用你的强定义替换它—— 这就是"为什么写同名函数就能接管中断"，也是为什么函数名拼错不会报错（会静默死循环）。
  • NVIC 六个寄存器组各管一件事。 ISER/ICER 管使能， ISPR/ICPR 管挂起（软件也能手动置位/清除）， IABR 是只读的"正在执行哪一路"（调试时很有用）， IPR 管优先级。它们都是按 32 位一组寻址的： 中断号 n 落在 [n >> 5] 的 1 << (n & 0x1F) 位上。
  • IPR 只有高 4 位有效。F103 只实现了 4 位优先级 → 16 个等级， 数值要左移 4 位再写（prio << 4）。 直接写 NVIC->IP[n] = 14 会得到优先级 0（最高）—— 因为 14 = 0b00001110，硬件只看高 4 位。
  • 抢占位管"能不能打断"，响应位只管"同时挂起时谁先跑"。 5 种分组下（抢占位, 响应位）分别是 (0,4)、(1,3)、(2,2)、(3,1)、(4,0)， 抢占级数 × 响应级数恒等于 16。 抢占优先级相同就绝不嵌套，不管响应优先级差多少。
  • 嵌套由硬件自动压 8 字帧（32 字节）。 R0~R3、R12、LR、PC、xPSR，顺序固定、不可配置。 嵌套深度直接决定最坏栈用量， 把一组中断设成同一个抢占优先级是控制栈用量最有效的手段。
  • 延迟是常数周期数，不是常数时间。 同步请求约 12 周期、异步请求约 14~15 周期（要加 2~3 周期做时钟域同步）， 72MHz 下约 0.2µs。主频翻倍，延迟减半——因为周期数不变。 尾链把连续中断的进场开销从 14 周期压到 6 周期，迟来则省掉"白压一次多余的栈"。
  • EXTI 的线号 = 引脚号，一根线只能连一个端口。 PA0/PB0/PC0 共用 EXTI0，AFIO->EXTICR 只能选一个。 8 个按键随机分配引脚号，"互不冲突"的概率只有 12%； 冲突时另一个键的响应概率不是 50%，而是稳定的 0%。
  • EXTI 与 NVIC 是两级使能，两个都要开。 只开 IMR 不开 ISER，请求会挂在 NVIC 的 pending 上， 等你哪天补开 ISER，它会立刻补上一次"迟到的中断"—— 这是"改了无关代码，突然多进一次中断"的原因。
  • HAL 的转发层存在的唯一目的是清除标志。 HAL_GPIO_EXTI_IRQHandler = 判 PR → 清 PR → 调回调； HAL_UART_IRQHandler = 判各种标志 → 分发到 HAL_UART_RxCpltCallback 等。 所有引脚的 EXTI 回调共用一个函数，所以第一行必须判 GPIO_Pin。
  • 优先级的依据是截止时间，不是重要性。 先写出每个中断的截止时间，再按从小到大分配抢占优先级数值（0 给最紧的）。 按键的截止时间是 50ms 级，串口是 87µs 级——差三个数量级， 所以按键应该垫底而不是居首。
  • ISR 里只置标志，主循环去处理。 volatile 解决可见性，环形缓冲区的单写者模型解决原子性， 多字节数据用序号双读或临界区。凡是带 Timeout 的阻塞式 HAL 函数进中断就是 bug—— HAL_Delay 会死锁（等 uwTick， 而 uwTick 靠比它优先级更低的 SysTick）。
  • 排查的顺序永远是从寄存器倒着走。 EXTI->PR 置了没？→ NVIC->ISPR 置了没？→ NVIC->ISER／IP 对不对？→ 最后才是看代码。两次寄存器观察能把七个步骤一刀切成三段。

自测题

先自己想一遍再看答案。八道题覆盖本篇的全部关键结论。

  1. F103 的优先级寄存器每个中断只有 4 个有效位。如果写下 NVIC->IP[6] = 0x0F;， 那么 EXTI0 这个中断的实际优先级是几？为什么？
  2. 在分组 2（2 位抢占 + 2 位响应）下，中断 A 设成抢占 = 1、响应 = 3， 中断 B 设成抢占 = 1、响应 = 0。B 正在 A 的 ISR 执行期间到来， B 能打断 A 吗？如果两个中断是同时挂起的，谁先执行？
  3. 异常向量表的第 0 项和第 1 项分别是什么？ 为什么每个 ISR 地址的最低位必须是 1？如果你用 C 数组手写一张向量表放到 RAM 里 并通过 SCB->VTOR 重定位，最容易犯什么错？
  4. PA0 和 PB0 各接一个按键，两块代码都配了 EXTI0 和 NVIC_EnableIRQ(EXTI0_IRQn)。 会出现什么现象？排查时为什么必须先看 EXTI->PR？
  5. SysTick 的优先级是 15，EXTI0 的优先级是 0。 在 EXTI0_IRQHandler() 里调用 HAL_Delay(10) 会发生什么？ 把两个优先级对调（SysTick = 0，EXTI0 = 15）会不会就好了？
  6. 一个定时器每 50µs 中断一次，ISR 本体（含 HAL 调用）执行 300 个周期。 它的 CPU 占用率是多少（要含进出中断的固定开销）？ 如果有两个这样的中断总是背靠背到来，尾链能省多少周期、占固定开销的百分之多少？
  7. NVIC_SetPriority(USART1_IRQn, configMAX_SYSCALL_INTERRUPT_PRIORITY); 这一行哪里错了？实际写进寄存器的是什么值？会导致什么后果？
  8. 调试器显示一次 HardFault 发生在某个 ISR 内部， 但那段 ISR 的代码只有几句赋值，看起来毫无问题。 列出三个最可能的原因，以及各自的验证方法。
答案与解析
  1. 实际优先级是 0，也就是最高。 因为 F103 只实现了 4 个优先级位，硬件读取的是这个字节的高 4 位。 0x0F = 0b00001111，高 4 位全是 0 → 优先级 0。 要设成数值 14，必须写 14 << (8 - 4) = 0xE0。 这是个纯粹由"位布局"造成的静默错误：不会报错，只会让一个本该垫底的中断 悄悄爬到最高，然后把系统实时性搞乱。
  2. 不能打断。两者的抢占优先级都是 1，同级之间绝不嵌套—— 响应优先级（3 和 0）不参与嵌套判定，它只在"两者同时处于挂起状态、 等待被取走"的时候决定顺序。 所以 B 会一直等到 A 的 ISR 执行完；如果两个中断是同时挂起的 （比如你在同一个时刻手动置了两个 ISPR 位），那么 B（响应 0）先被取走执行。 一句话记法：抢占位管打断，响应位管排队。
  3. 第 0 项是初始栈顶值（MSP 的初值），第 1 项才是 Reset_Handler 的地址。 第 0 项不是函数地址这件事，是很多人第一次读向量表时最大的困惑。 最低位为 1 是 Thumb 标记：Cortex-M 只支持 Thumb 指令集， 硬件靠地址最低位判断"目标是 Thumb 代码"，同时把这一位从实际跳转地址里去掉 （所以不会跳错到奇数地址）。 手写向量表最常见的错就是忘了 | 1—— 症状通常是直接进 HardFault，或者跳到一个奇怪的地址执行。 另外还有两个约束：重定位的向量表必须对齐到 128 字（512 字节）边界 （因为 VTOR 的低 9 位被硬件忽略），以及跳转前必须关中断 （否则重定位的中间状态可能被中断用到）。
  4. 只有一个按键能响应，另一个稳定地完全不响应。 因为 EXTI0 这条线只能连 PA0/PB0/PC0/PD0/PE0 中的一个， AFIO->EXTICR[0] 的 4 位字段只保留最后一次写入的值， 之前配置的那个端口就被彻底断开了。 必须先看 EXTI->PR，因为它能把故障一刀切成两段： 按下不响应的那个键，如果 PR 的 bit0 不置 1， 说明边沿根本没到 EXTI，问题在 AFIO 的端口选择或引脚模式； 如果 PR 置 1 了却没进 ISR， 说明是 NVIC 那一侧的问题（没使能、优先级、或者被更高优先级挡住）。 不看 PR 就开始猜，通常会在错误的一半里查很久。
  5. 必然死锁。HAL_Delay 的核心是一个 while ((HAL_GetTick() - tickstart) < wait) 空循环， 而 HAL_GetTick() 返回的 uwTick 只在 SysTick_Handler() 里增长。 SysTick 的优先级数值是 15，比 EXTI0 的 0 更低 → SysTick 无法抢占正在执行 EXTI0 ISR 的 CPU → uwTick 冻住 → while 条件永远为真。 决定性证据：Watch 窗口里 uwTick 不再变化， 但 DWT->CYCCNT 在飞快增长—— "CPU 在跑，时间停了"。 对调之后不会死锁，但换来一个更隐蔽的问题： SysTick 能打断 ISR 了，HAL_Delay 会正常返回， 但你的 ISR 真的在里面停了 10ms，这期间所有优先级低于它的中断全被推迟， 而且每 1ms 被 SysTick 打断一次。 结论不是"调整优先级就能用 HAL_Delay"，而是 阻塞式延时从来就不该出现在中断里。
  6. 占用率 = (300 + 24) / 3600 = 9.0%。 50µs × 72MHz = 3600 周期是分母； 固定的进出开销是「压栈取向量 14 + 异常返回 10」= 24 周期， 占 0.67% 的 CPU。 两个这样的中断背靠背时： 无尾链的固定开销是 2 × 24 = 48 周期； 有尾链则是「14（第一个进来）+ 6（尾链切到第二个）+ 10（最后出去）」= 30 周期， 省下 18 周期，占固定开销的 37.5%，折算 CPU 只有 0.50%。 这道题的意义在于让你看清：固定开销和尾链在几十 kHz 以下的频率里几乎可以忽略， 真正吃 CPU 的是 ISR 本体（这里 300 周期占了 8.3%，是开销的 12 倍）。 要降占用率，先砍 ISR 本体。
  7. 错在把"原始值"当"数值"传了。 configMAX_SYSCALL_INTERRUPT_PRIORITY 是已经左移好、准备直接写进寄存器的原始值（F103 上典型是 5 << 4 = 0x50 = 80）； 而 NVIC_SetPriority() 要的是没移位的数值（0~15）， 它内部会自己左移。 于是 80 被再左移 4 位 → 1280 = 0x500 → 截断成 8 位 → 0x00 → 实际优先级 0（最高）。 后果：这个中断现在能抢占 FreeRTOS 的内核临界区， 会破坏内核数据结构，表现为偶发 HardFault、队列/链表指针错乱， 或者 configASSERT 在 vPortValidateInterruptPriority() 里报错。 正确写法是 NVIC_SetPriority(USART1_IRQn, 5) 或 HAL_NVIC_SetPriority(USART1_IRQn, 5, 0)。 两个参数的 C 类型都是 uint32_t，编译器救不了你—— 唯一的防线是知道这件事。
  8. 三个最可能的原因（按概率排序）：
    ① 栈溢出。这是首选怀疑对象——"故障在 ISR 里、但 ISR 代码没问题" 几乎就是栈溢出的典型特征。因为栈溢出本身不报错，它只是无声地覆盖别人的数据， 直到某个被踩坏的变量（可能是返回地址、可能是指针）被使用才崩， 所以崩溃位置和真正原因隔了十万八千里。 验证：用第 4 节「填 0xA5 + 扫栈」的方法测最坏水位； 在调试器里看崩溃瞬间的 SP 是否已经接近栈底；查 ISR 调用链里有没有 printf／大数组／浮点格式化。
    ② 访问了没有时钟的外设寄存器，或者用了野指针。 在 ISR 里写一个"看起来正常"的赋值语句，如果目标地址落在没有使能时钟的外设区， 或者结构体指针从未初始化（是 NULL 或随机值）， 都会触发总线错误并升级成 HardFault。 验证：读 SCB->CFSR 判断是哪一类故障 （IMPRECISERR / PRECISERR / IBUSERR）， 再读 SCB->BFAR 看是不是有个可疑的访问地址。
    ③ 调用了不可重入函数。最常见的是在 ISR 里 printf 或 malloc： 它们内部有静态状态（stdio 的缓冲、堆的空闲链表）， 被中断打断主循环正在进行的同一次调用后，状态会被破坏。 验证：把可疑调用临时搬回主循环看是否消失； 或者看反汇编里 ISR 是否调用了 _malloc_r／_vfprintf_r。
    共同的方法论：不要读 ISR 的代码找 bug—— 它只是"受害者"。去查栈、查故障状态寄存器、查有没有调用不该调的东西。

练习

  1. 中断风暴实验。用 EXTI->SWIER 在主循环里 以可控的频率反复触发 EXTI0（不需要按键，也不需要外部信号）， 从 1kHz 逐步提到 100kHz，每一档用 DWT 数出「主循环每秒能跑多少圈」， 画出「中断频率 → 主循环吞吐量」的曲线。 然后把 ISR 本体从"只置标志"换成"调用 HAL_GPIO_EXTI_Callback 里做一次 HAL_UART_Transmit"，再画一次。 两次曲线的差别，就是"ISR 本体 vs 固定开销"的直观量化。
  2. 把按键做成短按 / 长按识别。基于第 4 节的 exti0_reg.c， 改成双边沿触发（RTSR 和 FTSR 都置位）， 在 ISR 里读 GPIOA->IDR 的 bit0 判断这是"按下"还是"松开"， 只把「按下时刻」和「松开时刻」记进一个环形缓冲区； 所有判定逻辑（去抖、短按、长按 1s、双击）都写在主循环里。 要求：ISR 的周期数用 DWT 实测并记录下来，证明它没有随着功能增加而变长。
  3. 实测中断延迟，验证"周期数是常数"。 用第 4 节「测 2」的方法（ISR 入口翻转 GPIO + 示波器）， 先在你的板子上测出 72MHz 下的真实延迟； 再把时钟树改成 8MHz 内部 RC（或者 24MHz）重测一次。 要求：两次结果都换算成"周期数"，证明它们是同一个量级（14~20 周期）， 并解释为什么会比 ARM 文档说的 12 周期多一些。
  4. 人为制造一次 EXTI 线冲突，并证明因果。 PA1 和 PB1 各接一个按键，代码里只配 EXTI1 且 AFIO_EXTICR[0] 选 PA。用调试器逐一按下两个键，观察 EXTI->PR 的 bit1： 记录哪种情况会置 1。然后给出两种修法： ① 换成引脚号不同的两个引脚（并说明你选的两个引脚为什么安全）； ② 改成 10ms 定时器轮询 GPIOA->IDR 和 GPIOB->IDR， 并比较两种方案的代码量、中断次数和最快响应时间。
  5. 做一个 8 通道按键扫描器，和 8 路 EXTI 对比。 用定时器每 10ms 中断一次，在 ISR 里把 GPIOB->IDR 整个读一次做快照、 和上一次快照异或得到"变化的位"、把变化写入环形缓冲区； 主循环做去抖（连续 2 次相同才确认）和短按/长按识别。 要求：统计并对比 ① 中断次数（8 路 EXTI 在按键抖动时 vs 10ms 轮询）； ② 最坏响应时间； ③ 代码行数与需要配置的寄存器数量。 给出你的场景下该选哪个方案的结论和理由。
