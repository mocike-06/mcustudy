原理介绍

串口（UART）是单片机工程师用得最多的一个外设，原因很实在：它只需要两根线， 却能把单片机里的变量、状态、错误码实时送到电脑屏幕上。 你以后遇到的蓝牙模块、WiFi 模块、GPS、很多工业传感器，接口也都是串口。 换句话说，学不会串口，就没法调试任何稍微复杂一点的系统。

一帧数据长什么样

UART 是异步串行通信，这四个字要拆开理解：

  • 串行——一位一位地发，一根线就够了（还有一根地线）。代价是慢：8 位数据要花 10 个位时间。
  • 异步——没有时钟线。既然没有时钟告诉接收方“什么时候该读下一位”， 双方就只能提前约定好每一位持续多久，这个约定就是波特率（每秒多少位）。 接收方靠自己的波特率在每一位的中间时刻采样。 
空闲（高电平）
        ┌───┐                                                ┌───────
        │   └──┐   ┌──┐   ┌──┐   ┌──┐   ┌──┐   ┌──┐   ┌──┐   │
   ─────┘      └───┘  └───┘  └───┘  └───┘  └───┘  └───┘  └───┘
        起始位  D0    D1    D2    D3    D4    D5    D6    D7  停止位
         (0)    └──────────── 8 位数据，低位 D0 先发 ────────┘   (1)

  每一位宽度 = 1 / 9600 ≈ 104us，一帧 = 1 起始 + 8 数据 + 1 停止 = 10 位 ≈ 1.04ms

  接收方在每一位的“中点”采样：中点离边沿最远，最不容易被抖动和误差影响

注意两个容易忽略的细节：起始位必须是低电平， 这就是接收方判断“有数据来了”的依据（空闲时线是高电平）； 数据位是低位先发（LSB first）， 所以你在示波器上看到的第一个数据位是 D0 而不是 D7。

SCON 与 PCON 寄存器

串口的行为由 SCON（字节地址 0x98，可位寻址）和 PCON（0x87，不可位寻址）两个寄存器决定。 SCON 的 8 位每一位都有明确分工：

位 名称 含义
SCON.7SM0工作方式选择高位
SCON.6SM1工作方式选择低位，与 SM0 组合选方式
SCON.5SM2多机通信控制位；方式 1 下不用，写 0
SCON.4REN允许接收：1 = 允许，0 = 禁止（只发不收时才是 0）
SCON.3TB8方式 2 / 3 发送的第 9 位数据
SCON.2RB8方式 2 / 3 接收的第 9 位数据
SCON.1TI发送完成标志：硬件置 1，必须软件清零
SCON.0RI接收完成标志：硬件置 1，必须软件清零

所以最常见的初始化只写一行：SCON = 0x50;。 0x50 = 0101 0000，拆开来就是 SM0 = 0、SM1 = 1（选方式 1）、REN = 1（允许接收）， TI 和 RI 清 0。以后看到这行代码，脑子里要能自动展开成这个二进制。

四种工作方式，为什么方式 1 最常用

SM0 SM1 方式 说明 波特率
0 0 方式 0 同步移位寄存器，不是常规串口，用来配 74HC595 扩 IO fosc / 12
0 1 方式 1 8 位 UART：1 起始 + 8 数据 + 1 停止，波特率可变，与 PC 通信就用它 定时器 1 溢出率 / 32 × 2SMOD
1 0 方式 2 9 位 UART，波特率固定不可调，很少用 fosc / 64 或 / 32
1 1 方式 3 9 位 UART，多出来的那位可做校验位 同方式 1

方式 1 胜出的原因很朴素：它和电脑串口助手默认的“8 数据位、无校验、1 停止位”完全一致，而且波特率可以用软件随便调。 方式 2 波特率固定，方式 0 压根不是异步串口，方式 3 多出来的第 9 位在没有校验需求时纯属浪费。 所以 99% 的场景写 SCON = 0x50; 就对了。

PCON 里的 SMOD 位

PCON（电源控制寄存器）只有最高位和串口有关： SMOD（PCON.7）是波特率倍增位， 写 1 时波特率翻倍。其余位是 IDL（空闲模式）和 PD（掉电模式）等电源管理位， 串口初始化时不要用 PCON = 0x80; 这种整字节赋值去清掉它们， 用 PCON |= 0x80; 或 PCON &= 0x7F; 只动这一位。

波特率与 11.0592MHz 之谜

方式 1 / 3 的波特率由定时器 1 的溢出率决定。 这里有个前提：定时器 1 必须工作在方式 2（8 位自动重装）， 它的溢出周期是固定的 12 × (256 − TH1) / fosc， 溢出率再除以 32（还要乘 2 的 SMOD 次方）就是波特率： 

                   2^SMOD      fosc
        波特率  =  ───────── × ──────────────────
                     32       12 × (256 − TH1)

        反过来解出初值：

                              2^SMOD × fosc
        TH1  =  256  −  ────────────────────────
                        384 × 波特率

  注意：TH1 只能是 0~255 的整数！
        如果算出来不是整数，实际波特率就会和约定值有偏差，
        偏差太大 → 接收方采样点跑偏 → 满屏乱码。

先看 11.0592MHz、SMOD = 0、目标 9600bps 的情况： 11059200 / (384 × 9600) = 3，正好是整数， 所以 TH1 = 256 − 3 = 253 = 0xFD，误差 0%。

换成 12MHz 呢？ 12000000 / (384 × 9600) = 3.255，不是整数！ 只能取 3，于是实际波特率变成 12000000 / (384 × 3) = 10417bps， 误差 (10417 − 9600) / 9600 ≈ +8.5%。

+8.5% 的误差为什么就是乱码

一帧 10 位。接收方用自己的波特率计时，误差会在整帧上逐位累积： 到第 10 位（停止位）时，采样时刻已经偏了约 9.5 × 8.5% ≈ 0.8 个位宽， 早就跨过位边界，采到隔壁位上去了。行业经验是收发双方合计误差要控制在 ±2% 以内，超过 5% 基本必然乱码。8.5% 属于“有时候能出几个对字符、大部分是乱码”的典型表现。

11.0592MHz 这个看起来“奇怪”的频率，正是为了让上面那个除法能整除： 11059200 = 9600 × 1152 = 19200 × 576 = 4800 × 2304， 常用波特率全是它的因数。这就是串口通信几乎一律用 11.0592MHz 晶振的全部原因， 和“精度更高”无关，纯粹是“除得尽”。

两个连带结论
  • 换上 11.0592MHz 之后，机器周期从 1µs 变成 12 / 11.0592 ≈ 1.085µs， 软件延时会整体慢约 8.5%。上一篇里的延时常数需要重新标定，别直接照抄。
  • 定时器 1 之所以必须用方式 2（自动重装），是因为方式 2 溢出后 TL1 会自动从 TH1 重新装载，溢出周期恒定；如果用了方式 1， 每溢出一轮都要靠中断重装初值，中断一旦被抢占，波特率就会抖一下，直接表现为丢字节。

发送、接收与中断写法

发送：写 SBUF 就开始了

发送数据只需要一句 SBUF = byte;——写进去就等于“开始发送”， 硬件会自己把起始位、8 个数据位、停止位一位一位推出去。 发完一帧后硬件把 TI 置 1，程序靠它判断“发完了没有”。 查询式发送就是最常见的 while (TI == 0); TI = 0;。

接收：REN 必须置 1

接收的前提是 REN = 1（也就是 SCON 的 bit4）。 收到完整一帧后，硬件把数据放进 SBUF、把 RI 置 1。 “收不到数据”的第一嫌疑人永远是 REN 忘了置 1， 第二嫌疑人才是接线。 

/* ---------- 查询式接收：简单，但 CPU 被彻底绑住 ---------- */
while (RI == 0);            /* 死等，这期间不能干任何别的事 */
ch = SBUF;                  /* 读走数据 */
RI = 0;                     /* 手动清标志 */
/* 缺点：主循环里有 Delay_ms(1000) 时，这一秒内来的数据全丢失 */

/* ---------- 中断式接收：事件驱动，主循环照常干活 ---------- */
void Uart_ISR(void) interrupt 4
{
    if (RI == 1)            /* 是“接收完成”触发的中断 */
    {
        ch = SBUF;          /* 第一件事：把数据取走 */
        RI = 0;             /* 第二件事：软件清零 */
        /* 第三件事：处理数据。原则仍然是“越快越好” */
    }
}
TI 和 RI 都在一个中断入口里，必须判断是谁触发

发送完成和接收完成共用同一个中断号 4、同一个中断服务函数。 所以进中断后一定要先判断 RI / TI， 再分别处理；漏清任何一个标志，中断就会反复进入，主循环再也跑不动—— 这是串口最经典的“程序卡死”原因。

TI 到底该在哪里清零

很多教材都写“TI 要在中断里清零”，这句话本身没错，但和查询式发送混用时会出大问题： 主循环正在 while (TI == 0); 里等发送完成， 结果中断先进来把 TI 清成了 0，主循环就永远等不到 TI 变成 1，卡死在那里。

本篇采用的规则是：谁等待，谁清零。 发送用查询方式，就在发送函数里等 TI 并清零；中断服务函数里不碰 TI， 只处理接收。这样两边各管一个标志，互不干扰。 如果你以后改成“发送也用中断”（配合环形缓冲区），那才需要把 TI 也交给中断去清。

printf 重定向是怎么做到的

能用 printf("温度 = %d 度\r\n", temp); 调试，比手动把数字拆成字符再发送舒服太多。 Keil C51 的 printf 内部并不直接操作串口， 而是每输出一个字符就调用一次 putchar。 库里的 putchar 默认是个空函数，所以只要自己实现一份， printf 的输出就自动流向串口了： 

#include <stdio.h>              /* 必须包含，否则报 error C267 */

/* Keil C51 的 printf 会为每个字符调用这个函数 */
char putchar(char c)
{
    SBUF = c;                   /* 写 SBUF → 硬件开始发送 */
    while (TI == 0);            /* 等这一帧发完（9600bps 下约 1ms） */
    TI = 0;                     /* 软件清零，准备下一个字符 */
    return c;                   /* 标准要求返回写出的字符 */
}
用 printf 之前必须知道的三件事
  • 它会占代码空间。 拉进格式化输出库大约要多占 1~2KB Flash， STC89C52 的 8KB 还扛得住，但如果你已经用了很大的数组就要留意。
  • 千万别用 %f 打印浮点。 一旦用到 %f， 链接器会把整个浮点库拖进来，代码体积可能直接翻倍。 正确做法是把数值放大成整数打印，例如温度 25.4℃ 就发 %d.%d 打印 25 和 4。
  • 换行要写 \r\n。 只写 \n 在多数串口助手里只是回到行首不换行， 必须“回车 + 换行”两个字符。

硬件接线说明

单片机说不了 USB，所以中间需要一个 USB 转 TTL 串口模块 （常见芯片 CH340G、CP2102、PL2303）。它一头插电脑 USB，另一头引出 TXD / RXD / GND / 5V 四根线。 接线本身只有三根线，但“TXD 接 RXD”这个交叉关系是新手最容易接反的地方。

元件与接线表

模块引脚 规格 连接到 说明
USB-TTL 的 TXD 模块的发送脚 单片机 P3.0（RXD） 模块发 → 单片机收，必须交叉
USB-TTL 的 RXD 模块的接收脚 单片机 P3.1（TXD） 单片机发 → 模块收，必须交叉
USB-TTL 的 GND 地 单片机 GND（第 20 脚） 必须共地，否则电平没有参考，收发全乱
USB-TTL 的 VCC 5V（跳线选 5V 档） 板子已单独供电时不接 不要用模块的 3.3V 档，见下方警告
晶振 11.0592MHz XTAL1 / XTAL2 串口通信的硬性要求，两端各 30pF 到地
USB-TTL 模块 CH340G / CP2102 电脑 USB 口 装好驱动后设备管理器里会出现 COM 号
电源 5V 第 40 脚 VCC、第 20 脚 GND 和 USB-TTL 共地；供电不足会导致乱码

上位机软件设置

  1. 串口助手（或 SSCOM、XCOM）里选择设备管理器中的那个 COM 号。
  2. 参数固定为：波特率 9600、数据位 8、停止位 1、校验位无、流控无，和 SCON = 0x50 的方式 1 一一对应。
  3. 勾上“发送新行 / 回车换行”，否则你在发送框里敲的字符串末尾不带 \r\n，单片机那边看不出“一句话说完了”。
  4. 下载程序和串口助手会抢同一个 COM 口：STC-ISP 下载时必须先关闭串口助手，下载完再打开串口助手重新连接。这不是 bug，是串口独占机制。
上电前必查（第 2 条最容易被忽略）
  • TXD / RXD 是不是交叉接的；GND 有没有真的连上。
  • CH340 模块的供电跳线必须在 5V 档。 如果跳在 3.3V，它的 TXD 高电平只有 3.3V， 而 51 的输入高电平门限是 0.7 × 5V = 3.5V—— 单片机根本认不出这个高电平，现象就是“单片机发得出去，但怎么都收不到”。 很多人在这里查一整天。
  • 晶振实物是不是 11.0592MHz（很多开发板出厂焊的是 12MHz，丝印上写着 12.000）。
  • 单片机和 USB-TTL 是否共用同一路 5V；用两路电源时更要确认共地。

完整代码

这份代码实现了三件事：上电打印一行欢迎信息（验证发送通路）、 每秒打印一次计数（验证 printf 重定向）、 收到任何字符立刻原样发回（验证接收通路与中断）。 三件事合起来，就把串口的收发双向通道都验证完了。 

#include <reg52.h>
#include <stdio.h>            /* 用 printf 必须包含；同时必须自己实现 putchar */

#define FOSC    11059200UL    /* 晶振频率，串口场景必须是 11.0592MHz */
#define BAUD    9600          /* 目标波特率，要和串口助手一致 */

/* ------------------------------------------------------------------
 * 软件延时：只给主循环用，绝对不要放进中断服务函数
 * 11.0592MHz 下内层循环 110 次约 1.08ms（换晶振要重新标定）
 * ------------------------------------------------------------------ */
void Delay_ms(unsigned int ms)
{
    unsigned int i, j;
    for (i = ms; i > 0; i--)
        for (j = 110; j > 0; j--);
}

/* ------------------------------------------------------------------
 * 串口初始化：方式 1 + 9600bps + 允许接收 + 开中断
 * ------------------------------------------------------------------ */
void Uart_Init(void)
{
    /* ---- 1. 定时器 1 工作在方式 2（8 位自动重装），专门做波特率发生器 ---- */
    TMOD &= 0x0F;                  /* 先清掉 T1 的配置位（高 4 位），保留 T0 的配置 */
    TMOD |= 0x20;                  /* T1：M1=1 M0=0 → 方式 2，自动重装 */

    /* ---- 2. 波特率初值：TH1 = 256 − FOSC / (384 × 波特率)，SMOD = 0 ----
     * 11059200 / 384 / 9600 = 3  →  TH1 = 253 = 0xFD，误差 0%
     * 如果晶振是 12MHz，这个除法就不是整数，波特率会偏 +8.5%，必然乱码
     */
    TH1 = (unsigned char)(256 - (FOSC / 384UL / BAUD));
    TL1 = TH1;                     /* 方式 2 下 TL1 是计数器，初值必须和 TH1 一致 */
    TR1 = 1;                       /* 启动定时器 1，波特率时钟开始输出 */

    /* ---- 3. 串口本身：方式 1 + 允许接收 ---- */
    SCON = 0x50;                   /* SM0=0 SM1=1 → 方式 1；REN=1 → 允许接收 */
    PCON &= 0x7F;                  /* SMOD = 0，波特率不倍增（只动这一位） */

    /* ---- 4. 中断：分开关 + 总开关 ---- */
    ES = 1;                        /* 串口中断允许 */
    EA = 1;                        /* 总中断允许 */
}

/* ------------------------------------------------------------------
 * 发送一个字节（查询方式：发完才返回）
 * ------------------------------------------------------------------ */
void Uart_SendByte(unsigned char byte)
{
    SBUF = byte;                   /* 写 SBUF 就等于“开始发送” */
    while (TI == 0);               /* 等硬件把 TI 置 1，表示这一帧发完了 */
    TI = 0;                        /* 谁等待谁清零：清零放在这里，不放进中断 */
}

/* 发送一个以 '\0' 结尾的字符串 */
void Uart_SendString(char *s)
{
    while (*s != '\0')
        Uart_SendByte((unsigned char)(*s++));
}

/* ------------------------------------------------------------------
 * printf 重定向：Keil C51 的 printf 每输出一个字符就调用一次 putchar
 * 我们自己实现它，printf 的内容就从串口出去了
 * ------------------------------------------------------------------ */
char putchar(char c)
{
    Uart_SendByte((unsigned char)c);
    return c;                      /* 标准要求返回写出去的字符 */
}

/* ------------------------------------------------------------------
 * 串口中断：中断号 4，发送完成（TI）和接收完成（RI）共用这个入口
 * 本程序把 TI 交给发送函数处理，中断里只处理接收
 * ------------------------------------------------------------------ */
void Uart_ISR(void) interrupt 4
{
    unsigned char ch;

    if (RI == 1)                   /* ---- 收到一个字节 ---- */
    {
        ch  = SBUF;                /* 第一件事：把数据取走（读 SBUF 会同时影响 RI 的清除条件） */
        RI  = 0;                   /* 第二件事：软件清零，否则会反复进中断 */
        SBUF = ch;                 /* 原样回显：直接写 SBUF，不在中断里傻等 TI */
    }

    /* TI 故意不在这里清零：
     * 主循环的 Uart_SendByte 正用 while (TI == 0) 等发送完成，
     * 如果中断先把 TI 清掉，主循环就永远等不到，程序会卡死。
     */
}

void main(void)
{
    unsigned int count = 0;

    Uart_Init();                   /* 必须先初始化串口，再谈收发 */

    /* ---- 上电先打两行，验证“单片机 → 电脑”这条路是通的 ---- */
    Uart_SendString("51 UART echo test\r\n");
    printf("FOSC = %lu Hz, BAUD = %d\r\n", FOSC, (int)BAUD);
    printf("type something, the MCU will echo it back\r\n");

    while (1)
    {
        /* ---- 每秒打印一次计数，验证 printf 重定向 ---- */
        printf("running... count = %u\r\n", count++);
        Delay_ms(1000);
    }
}

关键代码解析

  • TMOD &= 0x0F; TMOD |= 0x20;——先用“与”把 T1 的 4 个配置位清零、 保留 T0 的设置，再用“或”写入方式 2。直接写 TMOD = 0x20; 会顺手把 T0 的配置抹掉，如果主程序里还用了定时器 0，那里就会莫名其妙失效。 改寄存器用位操作，不做整字节覆盖，这是个通用习惯。
  • TH1 = 256 - (FOSC / 384UL / BAUD);—— 把波特率公式直接写成表达式，比硬编码 TH1 = 0xFD; 更好： 以后改晶振或改波特率只动宏定义，初值自动跟着变。 384UL 里的 UL 是提醒编译器按无符号长整型运算， 避免 16 位溢出——11059200 用 16 位是存不下的。
  • SCON = 0x50;——SM0=0、SM1=1（方式 1）、REN=1（允许接收）。 这个字节可以整写，因为它没有别的模块共用。
  • PCON &= 0x7F;——只清 SMOD 这一位，保留 PCON 里的电源管理位。 想改成 19200bps 时把它换成 PCON |= 0x80; 即可（TH1 仍然是 0xFD）。
  • while (TI == 0);——查询等待。注意末尾那个分号， 这是有意写的空循环；写成 while (TI == 0) TI = 0; 之类反而会出错。
  • char putchar(char c)——名字、参数、返回值都必须和库里的一致， 参数类型写成 unsigned char 或返回值写成 void 都会让重定向失效。
  • if (RI == 1)——进中断先判断来源。这里还要注意： 读 SBUF 和清 RI 的顺序建议“先读后清”， 先清再读在某些型号上会读到旧值。

现象演示说明

正确现象

  1. 给单片机复位（或重新上电），串口助手接收区立刻出现三行文字：欢迎语、晶振与波特率信息、操作提示。
  2. 之后每隔约 1 秒出现一行 running... count = N，N 从 0 开始递增，从不断行、从不错字。
  3. 在串口助手的发送框里输入 hello 并点击发送，接收区立刻多出 hello——这就是回显。
  4. 连续快速发送多个字符，回显一个都不少（说明中断接收没有丢数据）。
  5. 回显的字符有时会插在 running... 那一行中间，这是正常的：发送和接收共用一套硬件，两路数据在时间上会交叉。

观察点与判据

你观察到的 说明什么 下一步查什么
接收区全是乱码（随机符号） 双方波特率不一致，最常见的是晶振不是 11.0592MHz 看晶振丝印；核对串口助手是不是 9600 8 N 1；把 FOSC 宏改成实际频率
一个字都没有，接收区空白 发送通路断了：接线、串口没打开、或程序没跑起来 查 P3.1 → 模块 RXD 这根线、GND 是否共地、串口助手有没有点“打开串口”
能看到打印，但发过去的数据没有回显 接收通路断了，或单片机侧收不到 查 P3.0 ← 模块 TXD；确认 REN = 1、ES = 1、EA = 1；确认 CH340 跳线在 5V
只有第一个字符正确，后面错乱 波特率存在中等偏差，逐位累积到后半帧就采错 用 11.0592MHz；或把波特率降到 4800 观察是否变好
收到一堆多余的空行或奇怪符号 数据位 / 校验位设置不匹配，或发送端把 \n 当成 \r\n 发了两遍 把串口助手改回 8 数据位、无校验；检查代码里用了 \r\n 还是 \n
打印几行之后程序不动了 中断里把 TI 清掉了，查询式发送卡在 while (TI == 0); 检查中断服务函数有没有多余的 TI = 0;
顺手标定一下时间

串口助手接收区一般会带时间戳。数一下 10 行 running... 占用的实际时间，理论上应该约 10 秒。如果明显偏大，多半是 Delay_ms 的常数按 12MHz 标准写的而晶振是 11.0592MHz（慢约 8.5%）。 把实测值记进实验报告，就是一份很标准的“软件延时精度分析”。

常见报错排查方案

编译报错：error C267: 'printf': requires ANSI-style prototype

原因：调用了 printf 却没包含头文件。Keil C51 的库函数要求先有原型声明，否则按老式 C 语法处理并报错。

解决：在文件顶部加 #include <stdio.h>。如果加了还报同样的错，检查是不是把它写在 #include <reg52.h> 之前被条件编译跳过了。

链接警告：*** WARNING L15: MULTIPLE CALL TO SEGMENT（指向 _PUTCHAR 或 _UART_SENDBYTE）

原因：同一个函数既被主程序调用，又被中断服务函数调用。51 的普通 C 函数默认不可重入——参数和局部变量放在固定的内存里，中断打断主程序后会把中间结果覆盖掉，于是偶发乱码或死机。

解决：首选“不要让中断调用它”：中断里只写 SBUF 或只置一个标志，把打印和拼字符串留在主循环。确实需要在中断里调用时，把函数声明为可重入（void f(char c) reentrant，注意这样参数会走栈，速度变慢、代码变大）。

现象：串口助手满屏乱码

原因：按可能性从高到低：① 晶振实际是 12MHz，波特率偏 +8.5%；② 串口助手的波特率 / 数据位和代码不一致；③ TH1 初值和 SMOD 不配套（例如代码算的是 SMOD=0 的初值，却把 SMOD 置了 1，波特率直接翻倍）；④ 供电不稳、共地不良导致的位错误。

解决：先量晶振（示波器或频率计看 XTAL2），不是 11.0592MHz 就换掉；再核对串口助手 9600 8 N 1；然后检查 PCON 那一位有没有被别的代码改过（PCON = 0x80; 这种整写是隐患）。

现象：单片机打印正常，但电脑发过去的数据一个都收不到

原因：接收方向与发送方向是两根独立的线，所以“能发不能收”一定出在接收链路上：① 模块 TXD 没接到 P3.0（或接到了 P3.1 上）；② REN 不是 1——只发不收；③ ES 或 EA 没开，RI 根本没人处理；④ CH340 跳线在 3.3V，51 认不出高电平。

解决：按 ④ → ③ → ② → ① 的顺序查（先看跳线，因为最容易忽略）。快速验证办法：把 SCON = 0x50; 临时改成查询式接收，在主循环里 while (RI == 0); ch = SBUF; RI = 0; printf("got %c\r\n", ch);，能收到就说明是中断配置的问题。

现象：程序跑着跑着卡死，只剩前几行打印

原因：两个经典死法。一是查询式发送撞上“中断里清 TI”：主循环在 while (TI == 0); 里等，TI 却被中断清掉了，永远等不到。二是中断里漏清 RI，中断反复进入，主循环再也得不到执行机会。

解决：记住两条规则——接收标志 RI 在中断里清，发送标志 TI 在发送函数里清（谁等待谁清零），任何情况下都别漏清 RI。排查时可以在主循环里翻转一个 LED，看它在卡死时是否停止翻转，就能立刻区分“卡在中断里”还是“卡在等待里”。

小结与练习

串口是“配置多、时序少”的典型外设：一旦寄存器配对，剩下的就是收发数据， 不像 DHT11 那样需要掐着微秒算时间。把下面五句话记住，串口基本不会再出问题：

  • TMOD |= 0x20;——定时器 1 方式 2，自动重装，做波特率发生器。
  • TH1 = 256 − FOSC / (384 × 波特率);——初值必须整除，所以才要用 11.0592MHz 晶振。
  • SCON = 0x50;——方式 1 + 允许接收，和电脑串口助手默认参数一致。
  • ES = 1; EA = 1;——两级中断开关都要开。
  • RI 在中断里清，TI 在发送函数里清，谁等待谁清零。

还有一条工程经验值得单独记住：串口是你调试一切其它外设的工具。 后面做 DHT11、做 LCD、做电机控制，遇到“读数不对”时， 第一个动作都应该是把中间量用 printf 打出来，而不是盯着代码猜。

动手练习
  1. 改成 19200bps。 根据公式重新算一遍 TH1 和 SMOD，改完用串口助手验证。 提示：19200 需要 SMOD = 1，而 TH1 仍然是 0xFD； 改完想一想，为什么 SMOD 加倍之后“除数”反而没变？
  2. 亲手复现一次乱码。 借一块 12MHz 晶振的开发板（或把晶振换成 12MHz），保持代码里 FOSC 不变跑一遍， 记录乱码的表现；再用公式算出实际波特率与实际误差，写进实验报告。 这个“理论预测 → 实测验证”的闭环，是工科报告里最有价值的部分。
  3. 做一个命令行控制。 约定：收到字符 'A' 点亮 P1.0，'B' 熄灭 P1.0，'?' 回复一行帮助信息。 要求中断里只把字符存进变量并置标志，判断和动作全部放在主循环里做， 并在报告里说明为什么这样分工。
  4. 进阶：改成中断发送。 用环形缓冲区（一个数组 + 读指针 + 写指针）实现“主循环只管往缓冲区里塞字符， 中断负责从缓冲区取出来发”，彻底避免查询式发送浪费 CPU 时间。 提示：这时候 TI 才需要交给中断去清。
