从 51 和 STM32 到 ESP32：它到底多了什么

原理介绍

从 51 换到 ESP32，很多人第一周的感受是「代码明明没错，但行为完全不像我预期」： 多打印一行字就重启、加个 delay 就掉线、内存还越用越少。 这些都不是错觉，而是因为 ESP32 的「身体结构」和 51 完全不是一类。 这一节先把这个结构讲清楚，后面所有的坑都能自己推出来。

ESP32 到底是什么

先破除一个流传很广的说法：ESP32 不等于「单片机 + WiFi 模块」。 用 51 做联网项目时，你的典型方案是 STC89C52 加一块 ESP8266 模块，两块板子用串口连起来。 那种结构里，51 干自己的活，ESP8266 干联网的活，两者之间靠一串「AT 指令」文本互相喊话。

打个比方：这就像两个人隔着墙用对讲机喊话。 一个人负责车间里的活（你的 51 程序），另一个人在门口负责收发信件（ESP8266）。 想让车间把温度发出去，你得先教会他喊「AT+CIPSEND」这种暗号， 喊错了、喊慢了、对方没听清，事情就办不成。这也是为什么用 AT 指令做项目时， 代码里一半篇幅都在等回复、判断「OK」。

ESP32 换了一种做法：把收发信件的那个部门整个搬进同一个人的脑子里。 射频电路、WiFi 协议栈、蓝牙协议栈、两个 CPU 核，全都在同一颗硅片上， 内部用总线和共享内存通信，而不是用串口喊暗号。 于是你在代码里写一句 WiFi.begin(ssid, password)， 调用关系是直接的函数调用，不再有「等对方回 OK」这回事。

SoC 这个词

SoC 是 System on Chip 的缩写，中文叫「片上系统」。 字面意思就是：以前需要好几颗芯片加一堆外围元件才能组成的一个「系统」， 现在全部集成到一颗芯片里。ESP32 就是典型的 SoC—— 它内部除了 CPU，还塞进了射频收发器、内存、各种外设控制器， 所以它工作时几乎不需要外部元件，只有一颗存程序的 Flash 芯片和几颗退耦电容。

SoC：一整块电路板塞进一颗芯片

理解 SoC 的分层结构，对后面写代码很重要。因为 ESP32 内部是「分层」的， 你的代码处在这一摞的最上层，向下每一层都在替你完成越来越细的杂活： 

  ┌───────────────────────────────────────────────────────────┐
  │ 第 5 层  你的代码                                          │
  │          setup() / loop()：读传感器、控继电器、做判断       │
  ├───────────────────────────────────────────────────────────┤
  │ 第 4 层  Arduino-ESP32 封装层                              │
  │          digitalWrite() / analogRead() / WiFi.begin()      │
  │          把复杂的底层调用包装成一行好记的函数               │
  ├───────────────────────────────────────────────────────────┤
  │ 第 3 层  ESP-IDF（乐鑫官方 SDK）                            │
  │          任务调度、WiFi 状态机、TCP/IP 协议栈、文件系统      │
  ├───────────────────────────────────────────────────────────┤
  │ 第 2 层  FreeRTOS 实时操作系统内核                          │
  │          决定此刻哪个任务在用 CPU、谁在等、谁被唤醒          │
  ├───────────────────────────────────────────────────────────┤
  │ 第 1 层  硬件寄存器 + 射频电路                              │
  │          真正翻转电平、真正把 2.4GHz 电磁波发出去的地方      │
  └───────────────────────────────────────────────────────────┘

  你在 51 上的经验：直接在第 1 层和第 5 层之间来回，
  写 P1 = 0xFE 就是直接操作寄存器。

  你在 ESP32 上要做的事：大部分时间待在第 5 层。
  但要知道下面还有 4 层，出问题时才知道该往哪一层找原因。

用 51 的视角对照一下就很清楚：51 上你写 P1 = 0xFE;， 这一行直接落到「寄存器」这一层，中间没有别的东西。 而 ESP32 上你写 digitalWrite(2, LOW);， 这个调用要穿过封装层、IDF 层，最后才去改 GPIO 的输出寄存器。 中间这几层不是「多余的累赘」——它们顺便帮你做了引脚复用配置、输入输出方向检查、 以及和 WiFi 抢引脚时的冲突处理。

双核：Core0 与 Core1 的分工

ESP32-WROOM-32 里面的主控是 Xtensa LX6， 而且有两颗，官方叫 双核。 两个核都能独立执行指令，主频最高 240MHz。 在 Arduino 里查看主频就是 ESP.getCpuFreqMHz() 这一句，正常返回 240。

这两颗核不是随便分的，乐鑫在出厂时就给它们定了角色：

核官方名字默认负责什么对你的影响
Core 0PRO_CPUWiFi 协议栈、蓝牙协议栈、大部分系统任务这里已经有很多活，别再往里塞重活，否则 WiFi 会卡
Core 1APP_CPUArduino 的 loop() 任务默认跑在这里这里是「你的地盘」，放耗时的计算、刷屏、读传感器

为什么这么分？因为 WiFi 协议栈是一个对时间极其敏感的东西。 无线通信有严格的时序：信标帧每隔约 100ms 来一次，收到数据后必须在几十微秒内回应确认帧， 晚了对方就认为丢包要重发。如果这段时间 CPU 正在跑你的图形刷新循环， 协议栈就只能干等，表现出来就是「一刷屏 WiFi 就掉线」。 把协议栈单独放到 Core0，再用 FreeRTOS 的优先级保证它随时能抢到 CPU， 这个矛盾就解决了。

那怎么知道自己写的代码跑在哪颗核上？Arduino 提供了 FreeRTOS 的函数 xPortGetCoreID()，它返回当前正在执行这行代码的核编号（0 或 1）。 你可以用下面这一句打印出来： 

void setup() {
    Serial.begin(115200);
    delay(1500);
    /* xPortGetCoreID() 来自 FreeRTOS，Arduino 环境里已经自动包含，
     * 不需要额外 #include。返回 0 或 1，
     * 也可以打印宏 ARDUINO_RUNNING_CORE 做对照。 */
    Serial.printf("setup() 跑在 Core%d\n", xPortGetCoreID());
    Serial.printf("Arduino 定义的工作核是 Core%d\n", ARDUINO_RUNNING_CORE);
}

void loop() {
    Serial.printf("loop()  跑在 Core%d\n", xPortGetCoreID());
    delay(2000);
}

当你想把一段任务明确指定到某一颗核上时， 用的是 FreeRTOS 的函数 xTaskCreatePinnedToCore()。 先只看它的概念（函数的完整参数在本页 关键代码解析里逐项拆开）：

  • 「Task」= 任务，就是一段可以独立运行的函数，这个概念下一节细讲。
  • 「Pinned」= 钉住、绑定。表示这个任务只许在指定的那颗核上跑，不许调度器把它挪到另一颗核。
  • 「ToCore」= 目标是哪颗核，末尾的参数写 0 或 1。
常见误解：两个核 = 程序快一倍

不会。双核只在你的程序真的能拆成两件互不依赖的事时才有用， 比如一颗核负责刷新屏幕、另一颗负责读传感器并联网上报。 如果两件事都要访问同一份数据，就还需要加锁（信号量、互斥量）来防止打架，反而更慢。 新手阶段最正确的做法是：什么都不指定， 让 Arduino 把 loop() 放在 Core1，WiFi 自己待在 Core0，各干各的。

FreeRTOS：为什么不能再写 while(1) 大循环

这是 51 学生转 ESP32 时最需要「换脑子」的一处。在 51 上，标准写法是： 

/* STC89C52RC 的典型结构 */
void main(void) {
    init_timer0();      /* 初始化：只做一次 */
    init_uart();

    while (1) {         /* 超级循环：反复做 */
        scan_key();     /* 读按键 */
        update_led();   /* 刷新显示 */
        report_temp();  /* 上报温度 */
    }
}

这个结构叫 超级循环（Super Loop）， 或者叫「前后台系统」：中断是前台，while(1) 里的代码是后台。 它的隐含假设是：每一件事都足够快，并且必须等别人做完才能做。 如果 report_temp() 里要等 WiFi 回应、耗时 800ms， 那这 800ms 里按键完全不会被扫描——按下去没反应。

用过 51 的人会想到「那就放中断里」。但在 ESP32 上这条路走不通，原因有三条：

  1. WiFi 的连接、握手、收发数据包本身就要等几百毫秒到几秒，中断里不能等这么久。
  2. 中断服务函数要求执行时间极短（微秒级），做长操作会触发「中断看门狗」直接复位。
  3. 协议栈内部的状态机需要「在等待时让出 CPU」的能力，这是中断做不到的。

所以 ESP32 用的是完全不同的模型：FreeRTOS 任务（Task）。 一句话解释：任务就是一段「能随时被暂停、也能随时被恢复」的函数。 每个任务有自己独立的栈空间和优先级，操作系统内核（调度器）负责决定此刻让谁用 CPU。

打个比方。超级循环像一个厨师从头到尾做一桌菜： 必须先把汤炖上，炖的时候他只能站着等，什么也做不了。 任务模型像餐厅的后厨： 炖汤的厨师把汤放到灶上就转身去切菜了，灶上的汤好了会有人喊他。 多个厨师（多个任务）同时在场，谁手上有活谁就干活，灶（CPU）只有两个，但没人闲着。

对比项51 的超级循环ESP32 的 FreeRTOS 任务
并发单位整个 while(1) 是一个整体每个任务是一段独立的函数
栈空间全局共用（51 靠编译器分配，128 字节 RAM 根本没得选）每个任务独立分配，Arduino 的 loop 任务默认 8KB
等待时只能原地空转（忙等），CPU 被白白浪费调用 vTaskDelay() 让出 CPU，其他任务接着跑
优先级没有，中断优先级另算每个任务有自己的优先级，高的可以抢占低的
典型数量1 个ESP32 开机后系统就有十几个任务在跑，再加上你的

现在回答最关键的一个问题：那我写的 setup() 和 loop() 算什么？ 答案是——它们本身就是一个 FreeRTOS 任务。 你在 Arduino 里写的代码并不是「裸机程序」，而是被包装成了一个叫 loopTask 的任务。核心源码里的结构（为便于理解做了简化）大致是这样： 

/* 这段代码在 Arduino-ESP32 核心内部，你不需要自己写，看懂即可 */

/* 第一步：芯片上电后，ESP-IDF 会调用 app_main() */
extern "C" void app_main(void) {
    initArduino();                 /* 初始化串口、GPIO 等基础设施 */

    /* 第二步：创建一个任务，把这个任务"钉"在 ARDUINO_RUNNING_CORE 上。
     * 第 2 个参数 "loopTask" 是任务名（调试时能看到），
     * 第 3 个参数是给这个任务分配的栈大小（默认 8192 字节）。 */
    xTaskCreatePinnedToCore(loopTask, "loopTask", 8192, NULL, 1, NULL,
                            ARDUINO_RUNNING_CORE);
}

/* 第三步：任务体。注意它是一个「永不返回」的函数 */
void loopTask(void *pvParameters) {
    setup();                       /* 只执行一次 */

    for (;;) {                     /* 相当于 51 的 while(1) */
        loop();                    /* 反复执行 */
        /* 这里还有一些看门狗喂狗动作，省略 */
    }
}

看懂这三步，很多困惑就自动消失了：

  • 「setup 执行几次？」一次。它在 for(;;) 之前，只在任务启动时执行。
  • 「loop 返回后会怎样？」立刻被再调一次。你写 return; 不等于结束程序，只等于「这次循环到此为止」。
  • 「我怎么没看到 main()？」因为 main() 由核心库提供，它负责启动 FreeRTOS 调度器，然后才有 app_main()。所以 Arduino 程序里写 int main(void) 会和核心库冲突。
  • 「那 loop 卡住会怎样？」整个 loopTask 卡住，其他任务（包括 WiFi）照跑，但你的程序不再响应。而且核心默认开启了任务看门狗，loop() 连续 5 秒不返回就会打印报错并复位。
  时间轴 ──────────────────────────────────────────────────────▶

  Core0 │ [WiFi 协议栈任务] [WiFi] [蓝牙任务] [IDF 系统任务] [WiFi] …
        │  优先级较高，随时可以抢占，你基本感觉不到它们的存在
        │
  Core1 │ [loopTask: 你的 loop()] [空闲] [loopTask: 你的 loop()] …
        │  优先级 1（最低的一档之一），没人抢时就一直跑你
        │
        └─ 你调用 delay(1000) 的那 1 秒里，Core1 会去跑"空闲任务"，
           同时把 CPU 让给任何就绪的高优先级任务；
           这就是 delay() 和 51 上"空转 for 循环延时"的本质区别。
一句话记住 delay 与 vTaskDelay

Arduino 的 delay(ms) 在 ESP32 上内部就是调用 FreeRTOS 的 vTaskDelay(ms / portTICK_PERIOD_MS)。 它的含义不是「死等」，而是「我暂时不用 CPU 了，谁要用谁拿去」。 所以在 ESP32 上用 delay() 并不会像 51 那样把整个系统卡死—— 但它会卡住你自己这个任务， 按键扫描、状态机全都会停摆，所以长延时依然要尽量避免。

内存：520KB SRAM 与 4MB Flash

51 最让人难受的就是内存：STC89C52RC 一共 512 字节 RAM，其中真正能随便用的内部 RAM 只有 128 字节， 还要分给位寻址区、寄存器组、堆栈。写个 20 个元素的 int 数组就要开始算账。

ESP32 在这方面的感受是降维的宽裕： 芯片内部有 520KB SRAM 给程序运行用， 模组上还另焊了一颗 4MB Flash 用来存程序。 但这两块内存的分工和 51 的「内部 RAM / 外部 XRAM」不是一回事，值得单独讲清楚： 

  两块物理上完全不同的存储：

  ┌────────────── ESP32 芯片内部（SoC 的一部分）───────────────┐
  │  SRAM  520 KB   —— 掉电就丢，程序运行时的工作台            │
  │    ├─ DRAM 区：全局变量、堆(heap)、各个任务的栈             │
  │    ├─ IRAM 区：指令，中断服务函数必须放在这里               │
  │    └─ RTC 慢速内存 8KB：深度睡眠时唯一还活着的部分          │
  │         （注意：520KB 不是全部给你用，WiFi 协议栈、蓝牙、   │
  │           IDF 内核会先占掉一大块。Arduino 里开机后           │
  │           用 ESP.getFreeHeap() 看到的通常是 30 万字节上下）  │
  └─────────────────────────────────────────────────────────────┘

  ┌────────── 模组上另一颗芯片（WROOM 模组里，不在 SoC 内）────┐
  │  Flash  4 MB    —— 掉电不丢，存放程序本体和常量数据         │
  │    默认分区：bootloader / 分区表 / NVS / app0 / app1 / SPIFFS│
  │    其中 app0 这块应用程序分区默认约 1.2MB，                   │
  │    这就是编译时提示 "Sketch uses ... of program storage" 的 │
  │    那个 100% 到底指多少。                                    │
  └─────────────────────────────────────────────────────────────┘

  在 51 上的对应关系（便于你迁移概念）：
    51 的 128 字节内部 RAM   ≈  ESP32 的 SRAM（工作台）
    51 的 4KB 程序 Flash     ≈  ESP32 的 4MB Flash（存程序）
    51 的 XRAM（外扩）        ≈  ESP32 没有这个必要，SRAM 已经够用

为什么要在意「一个变量放在哪」？因为 ESP32 有一个 51 上不存在的限制： CPU 读取 Flash 要走缓存（cache）。 平时这没问题，但当你正在擦写 Flash 的时候，缓存是失效的—— 如果此刻恰好发生中断，而中断服务函数的代码还在 Flash 里，CPU 就取不到指令，直接崩溃。 这就是两个特殊宏存在的原因：

宏作用什么时候必须用
IRAM_ATTR把这个函数编译到 IRAM（内部 RAM）里，而不是留在 Flash写中断服务函数时。例如 void IRAM_ATTR onButton() { }。不写它，中断偶尔会崩，而且这种崩极难复现
PROGMEM在 AVR（Arduino UNO）上用来把常量放进 Flash 省 RAM在 ESP32 上基本不需要。因为 ESP32 的 Flash 被映射进地址空间，普通的 const 全局数组本来就已经在 Flash 里，写了也不会报错，但没用处。看到老教程里的 PROGMEM 不用照抄
常见误解：520KB 很大，随便用

520KB 是芯片的 SRAM 总容量，不是你能用的堆大小。 WiFi 一连上，协议栈、缓冲区、TCP/IP 状态就要吃掉几十 KB；再开蓝牙又是几十 KB。 典型 Arduino ESP32 程序开机后 ESP.getFreeHeap() 报 30 万字节左右， 连着 WiFi 做收发时会掉到 20 万上下。 所以「堆内存还够不够」是 ESP32 程序必须持续观察的指标， 这一点和 51 上「RAM 不够编译器会直接报错」完全不同—— ESP32 的堆不够是运行时才炸，表现为莫名其妙的死机重启。 这个坑在第 4 篇讲 String 时会详细展开。

WiFi 与蓝牙：协议栈意味着什么

ESP32 的无线能力是它和 51、STM32F103 最大的区别，规格如下：

什么叫「内置协议栈」？用打电话类比就清楚了。 你以为 WiFi.begin() 只是「打开开关」， 实际上它触发了一整套跨设备的握手流程： 

  WiFi.begin("MyHome", "12345678");
        │
        ▼
  ① 扫描（Scan）
     在 2.4GHz 的 13 个信道上来回听，找出哪个信道上有名叫
     "MyHome" 的路由器，并记下它的信号强度、加密方式。
     耗时：约 1~3 秒

        ▼
  ② 认证（Authentication）
     向路由器证明"我知道密码"。密码不是直接发出去的，
     而是用 WPA2 算法算出一个摘要，路由器用同样的算法验证。
     密码错了就卡在这一步，Arduino 表现为 WiFi.status() 一直是
     WL_DISCONNECTED，什么提示都没有。

        ▼
  ③ 关联（Association）
     路由器同意你接入，给你分配一个"连接编号"（AID），
     从此你俩之间建立了一条独占的无线链路。

        ▼
  ④ 四次握手（4-Way Handshake）
     协商出真正的数据加密密钥。到这一步之前，你发的所有数据
     都是密文，连路由器都解不开（这是 WPA2 的设计目标）。

        ▼
  ⑤ 请求 IP（DHCP）
     广播"我是新来的，谁给我个地址？"，路由器（DHCP 服务器）
     回一个 192.168.1.103 这样的地址，连同子网掩码、网关、
     DNS 服务器一起给你。这几样东西的含义在第 5 篇细讲。

        ▼
  ⑥ 连接完成
     WiFi.status() 返回 WL_CONNECTED，
     此时你才能用 WiFi.localIP() 拿到自己的地址。

  整段流程通常 3~8 秒。这就是为什么 setup() 里连 WiFi
  必须写成"循环等待 + 超时"，而不能连上就直接往下跑。

看懂这六步，就能理解一个新手最常见的困惑：为什么密码打错了不报错？ 因为在第 ② 步失败时，协议栈只会「断开重试」，没有给 Arduino 层提供「密码错误」这种细分状态。 这是无线通信的特点：失败原因经常是不可观测的， 你只能通过「连不上」这个结果去反推。第 5 篇会给出完整的排查顺序。

如果你学过 STM32F103C8T6，下面的对照会更有针对性。 这两颗芯片的定位差别很大：STM32F103 是「通用 MCU」，强调外设丰富、实时性好； ESP32 是「物联网 SoC」，强调集成度和联网能力。

表里有两行值得单独说：

第一，时钟树不用你操心了。 在 STM32 上开一个新工程，光 RCC 配置就要选 HSE、配 PLL 倍频、设 AHB/APB 分频， 配错了串口波特率就不对。ESP32 的 Arduino 环境里，这些核心库已经做完， 上电跑 240MHz，Serial.begin(115200) 就是 115200。 代价是你失去了精细控制，需要改主频时要到 ESP-IDF 层去调 （Arduino 里也有 setCpuFrequencyMhz() 可以改， 但它会影响串口时钟，新手别动）。

第二，GPIO 矩阵是个巨大的便利。 STM32 上想把 UART 换一组引脚，要去查数据手册的复用表，还要开 AFIO 时钟。 ESP32 上你写 Serial2.begin(9600, SERIAL_8N1, 16, 17)， 意思是「把第二路串口的 TX 放 GPIO16、RX 放 GPIO17」， 换成任何两个空闲引脚都行，芯片内部有个交换矩阵自动接线。 这就是为什么 ESP32 的接线教程看起来「很随意」——它是真的随意。

但它有代价：没有 SWD 调试

ESP32-WROOM-32 没有像 ST-Link 那样好用的单步调试通道 （要用 JTAG 得另外接一堆线，而且会占用 GPIO12~15）。 所以玩 ESP32 的核心技能是串口打印： 在关键位置打印变量、打印状态、打印内存，用日志反推程序走到哪一步。 这也是第 4 篇把「串口是调试的眼睛」单独作为一节的原因。

绝对不能碰的 6 个引脚

GPIO6 / 7 / 8 / 9 / 10 / 11：接上任何东西都可能让板子变砖

这六个引脚在模组内部已经连到 SPI Flash 芯片上了——Flash 就是存放你程序的那颗存储器。 它们承担的是 SPI 总线的时钟、数据、片选信号。 你在外面接一个 LED、接一根杜邦线、甚至只是接一根长导线当天线， 都会给这条高速总线引入额外的电容和干扰。

后果分三档： 轻则程序时好时坏、偶尔跑飞；中度则无法上传（esptool 读 Flash 校验失败）； 最重则写坏了 bootloader 或分区表，板子从此只能靠串口手动救砖。 这不是「概率很低的小问题」，是新手烧板子的头号原因。

开发板上之所以还印着 GPIO9、GPIO10，是因为有些 ESP32 模组没占用它们。 ESP32-WROOM-32 用满了，你就当这几个脚不存在。

启动绑带引脚

绑带引脚（strapping pin）这个名字听起来很怪， 但机制很简单：ESP32 每次上电或复位的最初几微秒里，会去「读」几个特定引脚的电平高低， 用读到的组合来决定以什么模式启动。 就像开机时按着 F2 进 BIOS 一样——这几个脚就是「开机时要检查的按键」。

这个「检查」只在上电瞬间发生。之后这几个脚就变回普通 GPIO，可以正常用。 问题在于：如果你给它们接的下拉或上拉电路恰好把电平定在了「另一种模式」上， 芯片开机就走错了路。

引脚开机瞬间它决定什么芯片内部默认你要注意什么
GPIO0低 = 进入下载模式（等串口烧录）；高 = 正常运行程序内部上拉（默认高）板上的 BOOT 键就是把它拉低。你外接电路如果长期把它拉到低电平，板子每次上电都停在下载模式，程序永远不跑
GPIO2正常启动时取任意值、不被检查（GPIO0=1 → SPI Boot Mode）；只有进串口/联合下载模式（GPIO0=0）才要求 GPIO2=0内部下拉（默认低）板上 LED 就接在这里。正常启动不受它影响；下载/烧录时被外接电路顶在高电平会导致连不上
GPIO12低 = Flash 供电用 3.3V（正常）；高 = 用 1.8V（WROOM 模组会直接起不来）内部下拉最危险的一个。它是内部下拉的，所以你外接的上拉电阻或某个模块的漏电流很容易把它抬到高电平，结果就是「上电后串口一片乱码、程序不跑」
GPIO15高（默认，内部上拉）= 输出启动日志；低 = 关闭启动日志（MTDO=1 使能 U0TXD 打印，拉低反而关掉）内部上拉拉低不影响运行，只是看不到 bootloader 的启动信息；但接上拉负载时要小心
GPIO5决定开机时 SDIO 的时序延迟内部上拉影响很小，一般可以正常使用
实用结论

绑带脚不是「不能用」，而是「上电瞬间的电平不能被你带偏」。 给新手的安全用法是：

  • 接 LED、继电器这类输出负载：可以，但先上电再让它动作。
  • 接按键、传感器这类输入：尽量换到 GPIO13、14、16~19、21~23、25~27 上。
  • 一定要用 GPIO12 时，确认它外接的东西在断电时不会给它灌电流（比如传感器模块自己的上拉电阻就可能坏事）。
  • 调试阶段如果板子莫名其妙不启动，第一件事就是把这几个脚上的线全部拔掉再上电。

芯片信息打印程序

下面这段程序把本篇讲到的每一个概念都在真实硬件上「量」出来： 芯片型号、核数、主频、Flash 容量、堆内存、当前核编号、复位原因。 建议先原样跑一遍，再逐行删掉看看会发生什么，这是理解 API 最快的办法。 

/* =====================================================================
 *  esp32-basic-compare-info.ino
 *  目标板：ESP32 Dev Module（ESP32-WROOM-32）
 *  作用：把"双核 / 内存 / 协议栈版本 / 复位原因"这些抽象概念
 *        在真实硬件上量出来，建立对 ESP32 的直观认识
 *  波特率：115200（串口监视器右下角必须选同一个值）
 * ===================================================================== */

#include <esp_system.h>    /* esp_reset_reason()：判断上次为什么复位 */
#include <esp_heap_caps.h> /* heap_caps_get_free_size()：分类看内存 */

/* 把复位原因翻译成中文。ESP32 会自己复位，而复位原因会明确
 * 告诉你是供电问题还是代码问题，这是排查"反复重启"的第一现场证据。 */
const char* resetReasonText(esp_reset_reason_t r) {
    switch (r) {
        case ESP_RST_POWERON:   return "上电复位 / 按了 EN 键（正常）";
        case ESP_RST_SW:        return "软件复位（调用了 ESP.restart()）";
        case ESP_RST_PANIC:     return "程序崩溃复位（空指针、越界、除零等）";
        case ESP_RST_INT_WDT:   return "中断看门狗复位（中断里耗时太久）";
        case ESP_RST_TASK_WDT:  return "任务看门狗复位（loop 被阻塞超过 5 秒）";
        case ESP_RST_BROWNOUT:  return "掉电复位：供电不足！换 USB 口或换线";
        case ESP_RST_DEEPSLEEP: return "深度睡眠唤醒（正常）";
        default:                return "其他原因";

}

void loop() {
    /* 每 3 秒报一次心跳，观察堆内存有没有持续下降。
     * 用 millis() 做非阻塞定时而不是 delay(3000)：
     * delay 会让 loop 停住，以后加了 WiFi 或按键就会出问题，
     * 从一开始就养成"用时间戳判断"的习惯。 */
    static uint32_t lastTick = 0;   /* static：值在两次 loop 之间保留 */
    if (millis() - lastTick >= 3000) {
        lastTick = millis();
        Serial.printf("[心跳] 运行 %lu 秒 | 空闲堆 %u | 当前核 Core%d\n",
                      millis() / 1000, ESP.getFreeHeap(), xPortGetCoreID());
    }
}

关键代码解析

  • .ino 文件不需要写 #include <Arduino.h>——Arduino IDE 在编译前会自动加。但如果你把代码拆成 .cpp 文件，就必须自己写这一行，否则 Serial、pinMode 全都找不到。这是从单文件走向多文件时第一个会撞到的墙。
  • xPortGetCoreID()——返回当前代码实际执行所在的核编号。它比看文档可靠得多：你的板子到底把 loop 放在哪颗核上，跑一次就知道。Arduino 用宏 ARDUINO_RUNNING_CORE 定义这个默认值，两个值都打印出来对照，比记结论强。
  • xTaskCreatePinnedToCore(函数名, "任务名", 栈大小, 参数, 优先级, 句柄, 核编号)——七个参数一次说清：① 要执行的函数（必须是 void 函数名(void *参数) 形式）；② 任务名，字符串，调试时能看见，最长 16 字符；③ 栈大小，单位是字节（不是字），常用 2048~8192；④ 传给函数的参数，不需要就写 NULL；⑤ 优先级，数字越大越优先，Arduino 的 loop 任务用的是 1；⑥ 任务句柄的地址，想以后删除或控制这个任务就传变量地址，不需要写 NULL；⑦ 钉在哪颗核，写 0 或 1。返回值是 pdPASS（成功）或 pdFAIL（通常是内存不够建栈）。
  • ESP.getHeapSize() 与 ESP.getFreeHeap()——前者是「堆的总容量」，后者是「当前还能用多少」。两者的差就是被系统和你自己吃掉的量。做联网项目时请习惯性打印这两个数，它们能在死机之前几秒钟给你预警。
  • heap_caps_get_free_size(MALLOC_CAP_DMA)——ESP32 的内存不是「一块」而是「好几块」，有的区域能被 DMA（直接内存访问，外设自己搬数据）访问，有的不能。WiFi 收发缓冲区必须在 DMA 区域里，所以有时候「总空闲堆还有 100KB，但 WiFi 就是连不上」——因为 DMA 区域已经空了。这个坑在后面的网络篇会再遇到。
  • ESP.getSketchSize() 与 ESP.getFreeSketchSpace()——前者是你的程序编译后占了多少字节，后者是应用程序分区还剩多少。把这两个数和编译时那句 Sketch uses 823456 bytes (62%) of program storage space 对照着看，就明白百分比是怎么来的。

在第二颗核上跑一个任务（进阶，但值得看一遍）

下面这段代码演示「把一件事交给另一颗核去做」。它做的事情本身很无聊（每 500ms 闪一次灯）， 但你要看的是结构： 任务的函数形态、怎么传参数、怎么确认它真的跑在另一颗核上。 

/* =====================================================================
 *  esp32-dualcore-demo.ino
 *  目标板：ESP32 Dev Module（ESP32-WROOM-32）
 *  作用：演示 xTaskCreatePinnedToCore 的完整用法
 *        Core1（默认）：loop() 负责串口打印
 *        Core0：一个独立任务负责闪灯
 *  注意：Core0 上还住着 WiFi 协议栈，所以这个任务里
 *        绝对不能出现长时间阻塞（不要在里面写 delay(5000)）
 * ===================================================================== */

#define LED_PIN   2        /* 多数 ESP32-WROOM-32 开发板的板载 LED */

/* ---------------------------------------------------------------------
 * 任务的函数形态是固定的，必须长这样：
 *     void 函数名(void *参数)
 * 不能是 void 函数名(void)，也不能有返回值。
 * 参数是一个 void 指针，表示"什么都能传"，实际类型由你自己约定。
 * ------------------------------------------------------------------- */
void ledTask(void *pvParameters) {
    /* 把传进来的参数还原成整数。这里传的是闪烁周期（毫秒）。
     * 先转 intptr_t 再转 int，是嵌入式里的惯例写法。 */
    const int period = (int)(intptr_t)pvParameters;

    Serial.printf("[ledTask] 启动，跑在 Core%d，周期 %d ms\n",
                  xPortGetCoreID(), period);

    for (;;) {                      /* 任务体必须永不返回 */
        digitalWrite(LED_PIN, LOW); /* 板载 LED 低电平点亮 */
        vTaskDelay(pdMS_TO_TICKS(period));

        digitalWrite(LED_PIN, HIGH);
        vTaskDelay(pdMS_TO_TICKS(period));
    }
    /* 如果这里真的返回了，FreeRTOS 会认为任务异常结束并触发断言，
     * 所以任务函数最后一行永远写不到，也不需要写 vTaskDelete(NULL)。 */
}

void setup() {
    Serial.begin(115200);
    delay(1500);

    pinMode(LED_PIN, OUTPUT);

    Serial.printf("setup() 跑在 Core%d\n", xPortGetCoreID());

    /* 把闪灯任务钉到 Core0 上。
     * 参数顺序：函数 / 名字 / 栈字节数 / 传参 / 优先级 / 句柄 / 核编号 */
    BaseType_t ok = xTaskCreatePinnedToCore(
        ledTask,               /* 任务函数 */
        "ledTask",             /* 任务名 */
        2048,                  /* 栈大小，单位字节。这个任务很简单，2KB 够用 */
        (void *)(intptr_t)500, /* 传给任务的参数：闪烁周期 500ms */
        1,                     /* 优先级，和 loop 任务同级 */
        NULL,                  /* 不需要句柄，传 NULL */
        0                      /* 钉在 Core0 上 */
    );

    if (ok != pdPASS) {
        Serial.println("任务创建失败：通常是内存不足（栈申请不到）");
    } else {
        Serial.println("任务创建成功，观察 Core0 的闪灯日志与 Core1 的心跳交替出现");
    }
}

void loop() {
    /* loop 默认跑在 Core1。它和 ledTask 是并发的：
     * 你会看到串口打印和闪灯同时进行，互不干扰。 */
    static uint32_t lastTick = 0;
    if (millis() - lastTick >= 2000) {
        lastTick = millis();
        Serial.printf("[loop] 我是 Core%d，空闲堆 %u\n",
                      xPortGetCoreID(), ESP.getFreeHeap());
    }
}
新手的纪律：先不要用 xTaskCreatePinnedToCore

这段代码是给你「看懂」的，不是给你「照抄到项目里」的。 理由很实际：一旦程序里有多个任务同时访问同一个变量（比如一个任务在改 float temperature，另一个任务在读它）， 就必须用信号量或互斥量保护，否则会读到「改了一半」的数据， 而且这种 bug 出现的概率很低、极难复现。 在你能熟练写出稳定的单任务程序之前， 所有逻辑都放在 loop() 里就够了。 绝大多数 ESP32 项目根本不需要你自己建任务。

常见报错排查方案

下面七条覆盖了「从 51/STM32 转 ESP32」阶段绝大多数「代码看着没问题但就是不对」的情况。 每条都按「现象 → 原因 → 解决」写。

现象：接上外设后板子根本不启动，串口一片空白或只有乱码，拔掉外设就正常

原因： 你碰了 GPIO6~GPIO11。这六个脚在模组内部连着 SPI Flash 的总线， 外部接线的分布电容和漏电流会干扰 Flash 通信。 表现为三个阶段：能开机但偶尔跑飞 → 开机就乱码 → 完全无法上传。 另一个常见变体是：接的是 GPIO12，你的模块自带的上拉电阻把它抬到高电平， 芯片按「Flash 用 1.8V 供电」启动，而 WROOM 模组的 Flash 是 3.3V 的，直接起不来。

解决： ① 把所有杜邦线拔掉，只留 USB，确认板子能正常跑； ② 对照本页的引脚表，把外设换到 GPIO13、14、16~19、21~23、25~27、32、33 上； ③ 如果确实要留在 GPIO12 上，检查那条线上的模块是否自带 10kΩ 上拉， 有的话串一个 1kΩ 以上的电阻或改用其他引脚。 记牢：6、7、8、9、10、11 永远不接任何东西。

现象：上传总是失败（Failed to connect to ESP32），或者按了 EN 后程序不跑，非要按一下 BOOT 才正常

原因： 绑带引脚被外部电路拉到了「下载模式」的电平。 GPIO0 在上电瞬间是低电平的话，芯片会停在下载模式等串口烧录， 程序永远不会开始执行。你外接的按键、传感器、或者一根没焊好、一直碰着 GND 的线， 都可能造成这个结果。

解决： ① 先断开所有外接电路，只留 USB，重新上传一次，确认板子本身没问题； ② 检查 GPIO0、GPIO2、GPIO12、GPIO15 上有没有外接电路； ③ 如果外设确实要接在 GPIO0 上（比如做唤醒按键）， 确认它在断电和上电瞬间都是「断开（高电平）」状态，而不是「闭合（低电平）」； ④ 记住 BOOT 键与 GPIO0 是同一个网络，按下去就等于把 GPIO0 接地。

现象：连上 WiFi 后程序变得一卡一卡，串口打印断断续续，甚至掉线重连

原因： 你把耗时的工作 pin 到了 Core0，和 WiFi 协议栈抢 CPU。 典型写法是 xTaskCreatePinnedToCore(heavyTask, "heavy", 4096, NULL, 5, NULL, 0)， 而且这个任务里还有大循环、忙等或长计算。 协议栈被饿到，收发时序错过，就表现为卡顿、掉线。

解决： ① 最省事的做法：把这类任务钉到 Core1（也就是和 loop 同一颗核）， 让 WiFi 独占 Core0； ② 如果一定要用 Core0，就在任务的大循环里插入 vTaskDelay(pdMS_TO_TICKS(1)) 或更长的让出时间， 别让循环里出现「永不阻塞」的忙等； ③ 检查任务优先级：给自定义任务一个不高于 WiFi 的优先级（写 1 或 2），不要写 10 这种高优先级； ④ 用 xPortGetCoreID() 在任务里打印一次，确认它真的跑在你以为的核上。

报错：Guru Meditation Error: Core 1 panic'ed ... / Task watchdog got triggered

原因： 两种情况，靠报错文字区分：
① 出现 Task watchdog got triggered：你的 loop() 或某个任务连续 5 秒没有「让出 CPU」。 典型元凶是 delay(10000) 这种超长延时， 或者 while (!WiFi.isConnected()) { } 这种没有超时的死等。
② 出现 Guru Meditation Error 加一串 Backtrace:：程序真的崩了，常见原因是空指针、 数组越界、用了已经释放的内存。

解决： ① 看门狗问题：把长延时改成循环里的小延时， 所有「等待某个条件成立」的循环都加上超时计数，例如 while (!WiFi.isConnected() && millis() - t0 < 10000) { delay(100); }； ② 崩溃问题：把 Backtrace 那一串地址复制下来， 用 Arduino IDE 自带的 ESP32 Exception Decoder 或在线的解码工具还原成函数名与行号， 它会直接告诉你崩在哪一行，比猜快得多。

现象：程序跑十几分钟或几小时后突然重启，复位原因显示 PANIC 或 BROWNOUT

原因： 堆内存被慢慢吃光。ESP32 上堆不足不会在编译期报错， 而是在运行到某个时刻 malloc() 返回 NULL，代码没检查就用了这个空指针，于是崩溃。 最常见的两种吃法：在 loop() 里不断用 String 拼接字符串（产生内存碎片）， 以及 new 了对象从来不 delete。 BROWNOUT 则是另一回事——那是供电问题，不是内存问题。

解决： ① 在心跳打印里加上 ESP.getFreeHeap() 与 ESP.getMinFreeHeap()，让它长期挂着跑，观察曲线； ② 如果空闲堆持续下降，就是泄漏； ③ 拼字符串改用 char buf[64] 加 snprintf()，这一点在第 4 篇有完整对比； ④ BROWNOUT 就去查供电：换线、换 USB 口、别用没独立供电的集线器。

报错：region iram0_0_seg overflowed by N bytes（IRAM 溢出）

原因： 你放进 IRAM 的东西太多了。IRAM 是专门放「必须在内部 RAM 里执行的代码」的区域， 容量有限（约 128KB，还要分给中断向量表和 WiFi 的关键代码）。 这条报错通常出现在：给一堆函数加了 IRAM_ATTR、 或者开了蓝牙之后又加了很多中断处理、或者固件本身就很大。

解决： ① 检查 IRAM_ATTR 是不是加得太随意—— 只有真正的中断服务函数才需要，普通函数加了只会白占 IRAM； ② 关掉不需要的功能：Arduino IDE 的「工具」菜单里把 Core Debug Level 设为「无」，能省下一些空间； ③ 如果同时开了 WiFi 和蓝牙，确认两者是否都必要——同时开启会显著抬高 IRAM 占用。

现象：程序一启动就复位，报错里出现 assert failed / cpu_id 相关内容

原因： xTaskCreatePinnedToCore() 的最后一个参数（核编号） 传了非法值。合法值只有 0、 1，或者表示「不限定」的 tskNO_AFFINITY。 常见的错误是顺手写了 2， 或者把参数顺序记错、把优先级填到了核编号的位置上。

解决： ① 老老实实按七个参数的顺序数一遍： 函数、名字、栈字节数、参数、优先级、句柄、核编号； ② 核编号只写 0 或 1； ③ 顺便检查第五个参数（优先级）是不是写成了 0—— FreeRTOS 不允许优先级为 0 的任务被创建，空闲任务占着那一档。

小结与练习

这一篇的目的是「换脑子」，不需要记住任何 API，只需要把三个认知装进去：

第一，ESP32 是 SoC，不是单片机加模块。 射频、协议栈、双核 CPU 都在同一颗芯片里， 所以 WiFi.begin() 只是一次函数调用， 不用再像 AT 指令那样靠文本喊话。 第二，你的程序天生就跑在 RTOS 上。 setup() 和 loop() 本身就是一个任务， 系统里还有十几个任务在同时跑。这既解释了为什么 delay() 不会像 51 那样卡死整个系统， 也解释了为什么长时间阻塞 loop() 会触发看门狗。 第三，引脚不是等价的。 GPIO6~11 禁用、34~39 只能输入、0/2/12/15 是绑带脚， 这三句话能挡掉新手一半的「玄学故障」。

自检练习（做完再看答案）
  1. 题 1：在 setup() 里写 pinMode(34, OUTPUT); 然后 digitalWrite(34, HIGH);，接一个 LED 到 GPIO34 对地。LED 会亮吗？为什么？
    答：不会亮。pinMode(34, OUTPUT) 会编译通过、运行也不报错，但 GPIO34~39 在芯片内部根本没有输出驱动电路，它们只接到了 ADC 的输入选择器上。判据：用万用表量 GPIO34 对 GND 的电压，写 HIGH 后仍然接近 0V。这就是「编译通过不等于硬件支持」的典型例子。
  2. 题 2：你的程序在 loop() 开头写了 delay(8000);，上电后大约 5 秒会看到什么？
    答：会看到任务看门狗报错并复位，报错文本是 Task watchdog got triggered，并指出是 loopTask 没有喂狗。原因是 Arduino 的 loop 任务默认开启了看门狗，超时 5 秒，而 delay(8000) 让这个任务连续 8 秒没有回到 for(;;) 的喂狗点。解决办法是把长延时拆成多次短延时，或者在循环里调用 vTaskDelay() 分批等待。
  3. 题 3：你的板子接了一个继电器模块到 GPIO12，每次断电再上电，串口都会先出现一段乱码，然后程序才开始跑。拔掉继电器就正常。问题在哪？
    答：GPIO12 是绑带脚，内部默认下拉，它在上电瞬间的电平决定 Flash 的供电电压选择（3.3V 还是 1.8V）。继电器模块上的上拉电阻或驱动电路把它抬到了高电平，芯片于是以为 Flash 是 1.8V 的，用错误的方式去读 Flash，读出来的是垃圾数据，所以串口出现乱码。解决：换到 GPIO13、14、16~19、21~23、25~27 上；实在要留在 GPIO12，就确认上电瞬间这条线上没有外部上拉。
  4. 题 4：你的程序编译通过、上传成功，串口打印的 [心跳] 每 3 秒一行，但「空闲堆」的数字每行都比上一行少 200 字节左右。这说明什么？怎么查？
    答：存在内存泄漏。每 3 秒少 200 字节，说明每轮 loop() 都在申请内存而不释放。查法：先看 loop() 里有没有 String 拼接、new、malloc，有没有对应的 delete / free；重点怀疑把 String 当全局累加器用（拼得越长，碎片越多）。判据：把可疑代码注释掉重新跑，数字稳定不变就锁定了它。
  5. 题 5：为什么 xTaskCreatePinnedToCore() 的第三个参数写 2048 就够，而写 8192 也不算浪费？
    答：因为这个参数的单位是字节，不是字。一个简单的闪灯任务只需要几百字节栈，2048 字节已经很宽裕。但栈太小的后果很严重：任务一旦调用层级变深（比如里面调了 Serial.printf 加格式化大字符串），就会栈溢出并触发 ***ERROR*** A stack overflow in task ... 复位。而 ESP32 有 520KB SRAM，多给几 KB 完全负担得起。判据：宁可一次给够，也不要为了「省内存」把栈压到 512 这种危险值。
