综合项目：ESP32 蓝牙遥控器

把蓝牙串口和 GPIO 输出整合成一个能拿去做课设演示的作品： 手机连上 ESP32，发一条 LED:ON，板上的灯亮，手机立刻收到 OK:LED=ON。 不用路由器、不用云平台，教室和实验室里都能演示。 这一篇的重点不是「让灯亮」，而是像工程师一样设计一套通信协议—— 这就是抄代码和自己做项目的分界线。前置知识：GPIO 输出、串口收发的基本概念。

本页只用板包自带的 BluetoothSerial， 不需要在库管理器里额外装任何库。

原理介绍

这个小项目的技术含量不在「点灯」，而在中间那条链路上传的到底是什么。 手机和 ESP32 之间只有一条字节管道，没有任何「开灯」「关灯」的概念—— 所谓遥控，本质上是你自己在两端约定了一套协议， 把人类的意图翻译成字节，再在另一端翻译回来。这一节把这条链路拆开看。

经典蓝牙串口是怎么工作的

ESP32-WROOM-32 里集成了两套完全不同的蓝牙：经典蓝牙（Bluetooth Classic，含 BR/EDR） 和 低功耗蓝牙（BLE）。本页用的是经典蓝牙里的 SPP（Serial Port Profile，串口透传剖面）： 它把蓝牙连接虚拟成一条串口，一端是 ESP32，另一端是手机，双方都能像操作 Serial 一样读写字节。Arduino-ESP32 内核把这个过程封装成了 BluetoothSerial 对象， 用法和硬件串口几乎一模一样。

对比项 经典蓝牙 SPP（本页） BLE（低功耗蓝牙）
代码难度低，SerialBT.read() / print() 直接收发较高，要理解服务、特征值、通知
Android 支持好，串口类 App 很多好，但 App 生态偏调试工具
iPhone 支持不支持 SPP支持，iPhone 只能用 BLE
吞吐与延迟吞吐较高，连接建立稍慢吞吐较小，延迟低、省电
同时连接数通常只允许 1 个客户端可以多个中心设备
两个必须先知道的限制
  • ESP32-S3 / C3 / S2 没有经典蓝牙。这些型号只支持 BLE， 编译时会直接报错找不到 BluetoothSerial。 本项目请用 ESP32-WROOM-32（开发板选项选 ESP32 Dev Module）。
  • iPhone 连不上。iOS 从系统层面就不开放 SPP， 蓝牙列表里能看到设备名，但任何串口 App 都连不出数据。 用 iPhone 演示的同学只能改用 BLE 方案，或者借一台安卓机来做展示。

为什么要设计指令协议

最省事的写法是「收到什么字符就干什么」：收到 '1' 就亮灯，收到 '0' 就灭灯。 三行代码搞定。但这种写法一旦项目稍微长大一点，就会同时冒出五个问题：

  • 没有边界，不知道一条消息什么时候结束。 蓝牙是字节流，不是消息流。LED:ON 这 6 个字节可能是分三次送到的， 你如果每收到一个字节就立刻处理，第一次只会拿到 L，判断必然失败。 必须有一个明确的结束标志——本页用换行符 \n。
  • 手一抖就误动作。 单个字符的容错空间为零，误触屏幕上的任意键都可能触发电平变化。 而 LED:ON 这种「有意义」的字符串，打错了就会被明确拒绝。
  • 表达不了参数。 「把亮度调到 60%」用单字符怎么发？而 DUTY:153 天然就能带参数， 协议框架不用改。
  • 无法扩展。 第二路、第三路负载接上来时，单字符方案就得重新分配字符表； 而 通道:动作 的框架只要往表里加一行（这就是后面「指令表驱动」的由来）。
  • 出错时无法告知对方。 这是工程上最要命的一点：如果设备收到无法理解的指令却毫无反应，用户分不清是「没发出去」还是「不认这条指令」， 只能反复试。所以协议里必须留出回传的位置。

本页设计的协议很朴素，但五个要素齐全——有边界、有语义、能带参数、可扩展、有回执：

LED:OFF熄灭板载 LEDOK:LED=OFF

为什么用纯文本而不是二进制帧

纯文本指令的字节效率不如二进制，但调试时可以直接用手机敲出来、肉眼看得懂， 不需要额外的解析工具。在教学项目和中小型工程里，可读性带来的收益远大于多传的那几个字节。 等你以后做高频采集（比如每秒几百帧的传感器数据），再考虑二进制帧 + CRC 校验， 那时你会自然理解为什么工业协议长成另一个样子。

一条指令的完整旅程

把整条链路画出来，你就知道代码里的每一段在解决什么问题了： 

① 手指点击手机键盘          App 把字符串按 UTF-8 编码成字节流
        │
        ▼
② 手机 App 追加换行符        "LED:ON" + '\n'   ← 这一步是边界所在，App 里叫 Send newline
        │
        ▼
③ 蓝牙 SPP 透传              6+1 个字节分片进入 ESP32，时序不保证
        │
        ▼
④ 接收缓冲（rxBuf）          来一个字节就追加，遇到 '\n' 才认为一帧结束
        │                      同时防超长：超过 32 字节就丢弃并回 ERR:TOOLONG
        ▼
⑤ 规范化                     trim() 去空白 → toUpperCase() 统一大写
        │
        ▼
⑥ 解析与分发                 按 ':' 切成「通道」和「动作」两个字段
        │                      通道名 → 在 channels[] 表里查下标
        │                      动作名 → ON / OFF / TOGGLE / ?
        ▼
⑦ 执行                       digitalWrite(channels[idx].pin, HIGH / LOW)
        │
        ▼
⑧ 状态回传（ack）            "OK:LED=ON" + "\r\n"  回去走同一条管道
        │
        ▼
⑨ 手机屏幕显示               你看到 OK:LED=ON，确认动作真的执行了（而不是"以为"执行了）

整段链路里，第 ④ 步和第 ⑧ 步是新手最容易漏掉的两步： 前者决定你能不能正确「切分」多字节消息，后者决定你能不能判断指令是否真的生效。 下面代码里的三个部分，就是分别对付这三类问题的。

硬件接线说明

这个项目有两种玩法：零接线的板载 LED 版（先跑通逻辑） 和 外接负载版（做出真实作品）。强烈建议按这个顺序来—— 先用板载 LED 把协议链路验证通，再去动接线，能省掉大量的排查时间。

要点：
1. 先用 GPIO2 的板载 LED 把协议跑通，再接外接负载 —— 这是最省时间的顺序。
2. ESP32 是 3.3V 逻辑：GPIO 输出高电平约 3.3V，驱动 LED 直接用，驱动继电器必须加三极管或买模块。
3. 继电器线圈电流通常在 70mA 以上，远超 GPIO 的安全输出能力，直接接会烧引脚。
4. GPIO2 是启动模式（strapping）引脚：正常启动（GPIO0=1 → SPI Boot Mode）时它取任意值、不被检查；只有进串口/联合下载模式（GPIO0=0）才要求 GPIO2=0，芯片内部默认下拉。

接线顺序建议

  1. 先什么都不接，只插 USB，烧录代码，用手机连上并发送 LED:ON，看板载蓝灯是否亮。
  2. 链路通了之后，再断电接外接 LED：GPIO4 → 220Ω → 长脚，短脚 → GND。
  3. 要控制真实负载时，最后再上继电器或三极管驱动板，并且先单独测试继电器是否吸合（能听到「嗒」的一声），再接负载。
  4. 每次改动接线都重新上电一次，观察串口有没有异常复位信息。
上电与演示前的检查清单
  • 外接 LED 极性有没有插反（长脚接电阻一侧，短脚接 GND）。
  • 继电器模块是「高电平触发」还是「低电平触发」——低电平触发的模块，代码里的 ON/OFF 要反过来写。
  • 烧录时如果报 Failed to connect to ESP32，先拔掉 GPIO2 上挂的外接电路再试，或者按住 BOOT 键点上传。
  • 用充电宝演示时注意：部分充电宝在电流很小（比如只有蓝牙在工作）时会自动断电，选支持小电流输出的那种。

完整代码

这份代码不需要安装任何库——BluetoothSerial 随 ESP32 板包一起提供。 整份程序按功能分成三段，每段前面都有明显的注释横幅： 接收解析、指令分发、状态回传。 直接整段复制进 .ino 文件即可编译上传。 

/* =====================================================================
 * esp32_bt_remote.ino  —— 综合项目：ESP32 蓝牙遥控器
 * 功能：手机通过经典蓝牙串口（SPP）发送文本指令，控制板载 LED 与外接负载，
 *       执行后回传结果；支持查询状态、批量控制与心跳测试
 * 硬件：ESP32-WROOM-32；板载 LED = GPIO2，外接 LED / 继电器 = GPIO4
 * 依赖：BluetoothSerial（ESP32 板包自带，无需额外安装）
 *
 * 协议：<通道>:<动作>\n
 *       例：LED:ON     点亮板载 LED
 *           LAMP:OFF   熄灭外接负载
 *           LED:TOGGLE 翻转
 *           LED:?      查询该通道
 *           ALL:ON     全部打开
 *           STATE      查询全部状态
 *           PING       心跳测试，回 PONG
 *           HELP       列出所有指令
 * ===================================================================== */

#include "BluetoothSerial.h"    // ESP32 经典蓝牙串口，板包自带

// 型号自检：ESP32-S3 / C3 / S2 只有 BLE，没有经典蓝牙。
// 这段在编译期就会挡住你，避免白折腾半天。
#if !defined(CONFIG_BT_ENABLED) || !defined(CONFIG_BLUEDROID_ENABLED)
#error "This board has no Bluetooth Classic. Please select ESP32 Dev Module instead of ESP32-S3/C3."
#endif

BluetoothSerial SerialBT;

const char* BT_NAME = "ESP32-Remote";   // 手机蓝牙列表里显示的名字

/* =====================================================================
 * 通道表：项目的「配置中心」
 * 想再加一路控制？在下面加一行就够了，其他代码一行都不用改。
 * =================================================================== */
struct Channel {
  const char* name;     // 指令里的通道名，必须全大写
  uint8_t     pin;      // 对应的 GPIO 编号
  bool        on;       // 当前状态：true = 输出高电平
};

Channel channels[] = {
  { "LED",  2, false },   // 第一路：板载 LED（GPIO2，高电平点亮）
  { "LAMP", 4, false },   // 第二路：外接 LED 或继电器（GPIO4，高电平有效）
};

const size_t CH_COUNT    = sizeof(channels) / sizeof(channels[0]);
const size_t MAX_CMD_LEN = 32;    // 单条指令的最大长度，超出就丢弃并报错

String rxBuf    = "";             // 接收缓冲：攒够一帧再处理
bool   overflow = false;          // 本帧是否已经超长

/* =====================================================================
 * 【第三部分】状态回传
 * 所有回复都从这里出去，将来要改成 MQTT 或屏幕输出，只改这一处
 * =================================================================== */
void reply(const String& text) {
  SerialBT.print(text);
  SerialBT.print("\r\n");         // 手机端串口 App 习惯按 \r\n 断行
  Serial.print("[回传] ");        // 同时镜像到 USB 串口，方便电脑上调试
  Serial.println(text);
}

/* 帮助信息：让手机端不用猜有哪些指令 */
void sendHelp() {
  reply("CMD LIST:");
  reply("  LED:ON | LED:OFF | LED:TOGGLE | LED:?");
  reply("  LAMP:ON | LAMP:OFF | LAMP:TOGGLE | LAMP:?");
  reply("  ALL:ON | ALL:OFF");
  reply("  STATE | PING | HELP");
}

/* 按名字查通道下标，找不到返回 -1 */
int findChannel(const String& name) {
  for (size_t i = 0; i < CH_COUNT; i++) {
    if (name == channels[i].name) {   // String 可以直接和 const char* 比较
      return (int)i;
    }
  }
  return -1;
}

/* 真正操作硬件：表里的状态和引脚电平一起改，两者永远保持一致 */
void setChannel(size_t idx, bool on) {
  channels[idx].on = on;
  digitalWrite(channels[idx].pin, on ? HIGH : LOW);
}

/* 汇总所有通道状态，例如 STATE:LED=ON,LAMP=OFF */
String buildState() {
  String s = "STATE:";
  for (size_t i = 0; i < CH_COUNT; i++) {
    if (i > 0) s += ",";
    s += channels[i].name;
    s += "=";
    s += channels[i].on ? "ON" : "OFF";
  }
  return s;
}

/* =====================================================================
 * 【第二部分】指令分发
 * 把「通道」和「动作」拆开，再分别查表 → 执行 → 回传
 * =================================================================== */
void handleCommand(String line) {
  line.trim();                       // 去掉首尾空白（手机输入法容易多打空格）
  line.toUpperCase();                // 统一大写，手机端发 led:on 也能识别
  if (line.length() == 0) return;    // 空行直接忽略（很多 App 会多发一个换行）

  Serial.print("[收到] ");
  Serial.println(line);

  /* ---------- 不带参数的整体指令 ---------- */
  if (line == "PING")  { reply("PONG");  return; }
  if (line == "HELP")  { sendHelp();     return; }
  if (line == "STATE") { reply(buildState()); return; }

  /* ---------- 带参数的指令必须含冒号 ---------- */
  int sep = line.indexOf(':');
  if (sep < 0) {
    reply("ERR:FORMAT  格式应为 通道:动作，例如 LED:ON");
    return;
  }

  String name   = line.substring(0, sep);
  String action = line.substring(sep + 1);
  name.trim();
  action.trim();

  /* ---------- 批量控制：ALL:ON / ALL:OFF ---------- */
  if (name == "ALL") {
    if (action == "ON" || action == "OFF") {
      bool on = (action == "ON");
      for (size_t i = 0; i < CH_COUNT; i++) setChannel(i, on);
      reply(buildState());
    } else {
      reply("ERR:ACTION  ALL 只支持 ON / OFF");
    }
    return;
  }

  /* ---------- 单通道控制 ---------- */
  int idx = findChannel(name);
  if (idx < 0) {
    reply("ERR:CHANNEL  没有这个通道：" + name);
    return;
  }

  if (action == "ON") {
    setChannel(idx, true);
  } else if (action == "OFF") {
    setChannel(idx, false);
  } else if (action == "TOGGLE") {
    setChannel(idx, !channels[idx].on);      // 翻转，手机端可以只放一个按钮
  } else if (action == "?") {
    // 查询：什么都不做，直接走到下面的回传
  } else {
    reply("ERR:ACTION  只支持 ON / OFF / TOGGLE / ?");
    return;
  }

  // 执行成功：回一条 OK，手机端凭这一行确认动作真的生效了
  reply("OK:" + String(channels[idx].name) + "=" +
        (channels[idx].on ? "ON" : "OFF"));
}

/* =====================================================================
 * 【第一部分】接收与解析
 * 蓝牙是字节流：必须靠换行符判断「一帧结束」，靠长度上限防止缓冲被撑爆
 * =================================================================== */
void pollBluetooth() {
  while (SerialBT.available()) {          // 有多少读多少，不阻塞
    char c = (char)SerialBT.read();

    if (c == '\n') {                      // 换行 = 一帧结束
      if (overflow) {
        reply("ERR:TOOLONG  指令超过长度上限，已丢弃");
        overflow = false;
      } else if (rxBuf.length() > 0) {
        handleCommand(rxBuf);             // 交给分发器
      }
      rxBuf = "";                         // 清空，准备接下一帧
      continue;
    }

    if (c == '\r') continue;              // 忽略回车，兼容 \r\n 和 \n 两种结尾

    if (rxBuf.length() >= MAX_CMD_LEN) {
      overflow = true;                    // 超长：标记一下，剩余字符一路丢到本帧结束
      continue;
    }
    rxBuf += c;                           // 正常字符：追加进缓冲
  }
}

/* =====================================================================
 * 初始化与主循环
 * =================================================================== */
void setup() {
  Serial.begin(115200);
  delay(300);                             // 等 USB 串口稳定

  Serial.println("\n===== ESP32 蓝牙遥控器 =====");

  // 把每个通道的引脚初始化成输出，并置于关闭状态
  for (size_t i = 0; i < CH_COUNT; i++) {
    pinMode(channels[i].pin, OUTPUT);
    digitalWrite(channels[i].pin, LOW);
    Serial.printf("通道 %s -> GPIO%d\n", channels[i].name, channels[i].pin);
  }

  SerialBT.begin(BT_NAME);                // 启动蓝牙串口，名字会出现在手机列表里
  Serial.printf("蓝牙已启动，设备名 = %s\n", BT_NAME);
  Serial.println("请用手机上支持经典蓝牙 SPP 的串口 App 连接，然后发送 HELP");
}

void loop() {
  pollBluetooth();   // 唯一的任务：不停地收、解析、执行、回传
  delay(5);          // 极短的让步，避免 while 空转把 CPU 占满
}

接收与解析：换行和超长输入

  • while (SerialBT.available())——把「读」和「处理」分开： 先把这一轮能拿到的字节全部收进缓冲，只有遇到 \n 才调用解析函数。 这样即使手机把 LED:ON 拆成三次发送，程序也能拼回完整的一帧。
  • if (c == '\r') continue;——世界上的换行有两种： Unix 的 \n（LF）和 Windows 的 \r\n（CRLF）。 手机 App 的设置里两者都可能出现，所以这里把 \r 直接丢掉， 两种结尾都能正确处理。
  • if (rxBuf.length() >= MAX_CMD_LEN) { overflow = true; continue; }—— 防的是「App 一直发但从不发换行」这种情况。没有长度上限时，rxBuf 会一直增长，最后把 ESP32 的内存吃光并复位。 注意这里的处理方式：打上标记后继续丢弃到本帧结束， 而不是立刻清空缓冲——否则超长数据后面的尾巴会被当成一条新指令来解析， 产生莫名其妙的「幽灵指令」。
  • rxBuf = "";——每帧处理完必须清空。忘了这一行， 下一条指令就会和上一条粘在一起（变成 LED:ONLED:OFF）， 表现为「第二条指令永远无效」。

指令分发：用表驱动代替一堆 if

  • struct Channel { const char* name; uint8_t pin; bool on; };—— 把「通道名、引脚号、当前状态」绑在一个结构体里。 这三个信息本来就是同一个东西的三个属性，分开写成三个数组或三组 if 是新手最常见的写法，一旦加一路就要改五个地方，必然漏掉一个。
  • int idx = findChannel(name);——先用名字查出下标， 后面所有操作都只用这个下标。好处是新增通道完全不用改逻辑代码： 往 channels[] 里加一行，解析、控制、状态汇总全都自动支持。 这就是「表驱动」的价值，也是本页最值得带走的一个编程习惯。
  • setChannel(idx, !channels[idx].on);——TOGGLE 动作的实现。 注意翻转的依据是表里记录的状态，而不是去读引脚电平 （digitalRead() 在输出模式下读回的是输出锁存值，虽然也能用， 但表里维护一份显式状态在扩展成 PWM、继电器反相时更灵活）。
  • 每一次失败都有明确的错误码：ERR:FORMAT（没有冒号）、 ERR:CHANNEL（通道不存在）、ERR:ACTION（动作不支持）、 ERR:TOOLONG（超长）。错误也必须回传， 这样你在手机上就能立刻知道自己拼错了什么，而不是对着一个不反应的板子发呆。

状态回传与多路扩展

回传看似只是「回一句话」，工程意义却很大：它把一条不可靠的单向命令 变成了可确认的交互。没有回传时，你永远分不清「指令没发出去」「板子没收到」 还是「收到了但执行失败」；有了 OK:LED=ON 这行字，问题立刻二分： 收到了回传说明链路和执行都没问题，没收到就是没送到。

把项目扩展成多路控制，只需要动两处：往表里加行、在动作分支里加分支。 下面的扩展片段在原有两条通道的基础上加了两路，并额外支持一个 PWM 调光指令： 

/* ---------- 改动 1：通道表里加两行，逻辑代码不需要任何修改 ---------- */
Channel channels[] = {
  { "LED",   2,  false },   // 板载 LED
  { "LAMP",  4,  false },   // 外接 LED / 继电器
  { "FAN",   13, false },   // 新增：风扇（经三极管或继电器模块）
  { "PUMP",  14, false },   // 新增：小水泵
};
// CH_COUNT 是用 sizeof 算出来的，自动变成 4，不用手改

/* ---------- 改动 2：在 handleCommand() 的动作分支里加 PWM ---------- */
// 先声明 PWM 通道（需要 ESP32 的 ledc 外设）
const uint8_t  PWM_PIN  = 4;    // 让 LAMP 这一路支持调光
const uint8_t  PWM_CH   = 0;    // 使用 0 号 PWM 通道
const uint16_t PWM_FREQ = 5000; // 5kHz，肉眼看不出闪烁
const uint8_t  PWM_BITS = 8;    // 8 位分辨率：占空比 0~255

void setupPwm() {
  ledcSetup(PWM_CH, PWM_FREQ, PWM_BITS);   // 配置 PWM 通道
  ledcAttachPin(PWM_PIN, PWM_CH);          // 把 GPIO 绑到这个通道上
}

 *
 *   } else if (action.startsWith("DUTY:")) {
 *     int duty = action.substring(5).toInt();     // 取出冒号后面的数字
 *     duty = constrain(duty, 0, 255);             // 夹到合法范围，防止乱传
 *     ledcWrite(PWM_CH, duty);                    // 输出占空比

 *     reply("OK:" + String(channels[idx].name) + "=DUTY" + String(duty));
 *     return;
 *   }
 *
 * 手机端发送：LAMP:DUTY:153   →  回传 OK:LAMP=DUTY153
 * 注意：一旦改用 PWM，就不要再对这个引脚调用 digitalWrite()，两种方式会互相打架。
 */

/* ---------- 想加一条全新指令？在整体指令区再加一行就行 ---------- */

表驱动的真正好处：改需求不改结构

假设答辩前老师临时要求「再加两路」：单字符方案要重新设计字符表、 重写判断逻辑、重测所有分支；而表驱动方案只需要在 channels[] 里加两行、接两根线， 解析、分发、状态回传全都自动支持——因为逻辑代码里从头到尾没有出现过一个具体的通道名。 这种「数据和逻辑分离」的写法，就是本项目最值得写进实验报告的设计点。

这一节先讲手机端怎么选 App、怎么配对连接（这是新手最容易卡住的地方）， 再给出「做对了应该看到什么」，最后是一张判据表。

配对与连接步骤（Android）

  1. 给 ESP32 上电，串口应打印 蓝牙已启动，设备名 = ESP32-Remote。
  2. 手机打开「设置 → 蓝牙」，在可用设备列表里找到 ESP32-Remote，点击配对。经典蓝牙通常不会要求输入 PIN；如果系统提示，试 1234 或 0000。
  3. 打开 Serial Bluetooth Terminal，点左上角菜单 → Devices，在已配对列表里选择 ESP32-Remote。
  4. 连接成功后界面顶部会显示 Connected。配对成功不等于连接成功，这一步必须做。
  5. 进入 App 设置，把 Send newline 设为 LF (\n)。这一步不做，后面发什么都不会有反应——因为程序就是靠换行判断一帧结束的。
  6. 在输入框发送 HELP，应当收到指令列表。
  7. 发送 LED:ON，板载 LED 亮起，同时收到 OK:LED=ON。
  8. 把 LED:TOGGLE 存成 App 里的一个按钮，演示时点一下就能翻转，效果比手打指令好得多。

正确现象

  1. 上电后串口打印设备启动信息，并逐个列出通道，例如 通道 LED -> GPIO2、通道 LAMP -> GPIO4。
  2. 手机连接成功前，板载 LED 保持熄灭（初始化时被置为低电平）。
  3. 发送 HELP，手机屏幕收到 5 行指令列表，串口同步打印 [回传] CMD LIST: 等行。
  4. 发送 LED:ON，串口打印 [收到] LED:ON 和 [回传] OK:LED=ON，板载 LED 立即亮起，手机屏幕出现 OK:LED=ON。
  5. 发送 led:off（故意用小写），同样能执行成功——代码里做了统一大写处理。
  6. 发送 LAMP:ON，外接 LED 亮起（或继电器发出「嗒」的吸合声），回传 OK:LAMP=ON。
  7. 发送 STATE，收到 STATE:LED=OFF,LAMP=ON，与两个灯的实际状态逐项一致。
  8. 发送 FAN:ON（一个不存在的通道），收到 ERR:CHANNEL 没有这个通道：FAN，且两个灯的状态完全不变。
  9. 发送 PING 收到 PONG，说明链路双向通畅。
  10. 断开手机连接再重连，功能立刻恢复，不需要重启 ESP32。

演示与答辩小技巧

这类项目答辩时最容易被问两个问题：「你怎么知道指令真的执行了？」 和 「想加一路控制要改多少代码？」 第一个问题用状态回传回答（OK:LED=ON 就是执行成功的证据）； 第二个问题当场演示：往 channels[] 表里加一行、接一根线， 重新烧录后 STATE 里就多了一项。 另外建议把演示过程录一段视频：蓝牙现场连接偶尔会被教室里的信号环境干扰， 有备份视频能避免讲台上尴尬。

常见报错排查方案

蓝牙项目的故障点集中在三处：板型选错、没配好换行符、 把配对当成连接。下面六条按「报错原文 → 原因 → 解决」整理。

编译报错：fatal error: BluetoothSerial.h: No such file or directory

原因：开发板型号选错了。ESP32-S3 / C3 / S2 这类较新的芯片只有 BLE，没有经典蓝牙，板包里自然没有 BluetoothSerial 这个类。另一种可能是 ESP32 板包压根没装，或者装的是 ESP8266 的板包。

解决：在 工具 → 开发板 里选择 ESP32 Dev Module（或 ESP32-WROOM-DA Module）；确认板包是 Espressif 官方的 esp32（首选项里那个 package_esp32_index.json）；实在要用 S3/C3，就得改用 BLE 方案（NimBLE-Arduino 或 BLEDevice）。

编译报错：#error "This board has no Bluetooth Classic. Please select ESP32 Dev Module..."

原因：这是代码里主动加的自检。它触发说明当前编译目标的 CONFIG_BT_ENABLED 或 CONFIG_BLUEDROID_ENABLED 没有定义——也就是这块板子没有经典蓝牙协议栈。

解决：换用 ESP32-WROOM-32 系列的板子。如果手头确实只有 S3/C3，把本项目的通信层换成 BLE：用 BLEDevice 建一个串口透传服务，逻辑层（表驱动、协议解析、回传）可以一字不改地复用——这也是把协议和传输分开设计的好处。

手机蓝牙设置里配对成功，但 App 连不上或连接后没数据

原因：有四种常见情况。一是把配对（Pairing）当成了连接（Connect）——配对只是交换密钥建立信任，SPP 连接要由 App 发起；二是用的 App 只支持 BLE，扫描不到经典蓝牙的 SPP 服务；三是 ESP32 同一时刻只允许一个 SPP 客户端，另一个 App 还占着连接；四是系统缓存了旧的配对信息。

解决：在 App 的 Devices 列表里主动选择已配对的 ESP32-Remote 建立连接；换用 Serial Bluetooth Terminal 这类支持经典蓝牙 SPP 的 App；关掉手机上其它可能的串口 App 并重启蓝牙；还不行就在系统蓝牙设置里「取消配对 / 忘记此设备」，然后重新扫描配对。

发送 LED:ON 完全没反应，串口也没有 [收到]

原因：九成是 App 没有发送换行符。代码是「收到 \n 才算一帧结束」，如果 App 只发了 LED:ON 这 6 个字节，程序会一直把它攒在缓冲里等换行，永远不触发解析。剩下的可能是 App 与板子实际上没连上（界面看着是 Connected，其实是上一个设备的残留状态）。

解决：进入 App 设置，把 Send newline 设为 LF (\n)（有些 App 写作 \n 或 Newline）；或者发送时手动带一个回车。判断方法：按下发送后看串口有没有 [收到] 打印，没有就是帧没结束，有就是不认识这条指令。

iPhone 能找到 ESP32-Remote，却怎么都连不出数据

原因：这不是配置问题，是系统限制。iOS 不开放经典蓝牙的 SPP 剖面，任何 App 都无法在 iPhone 上使用串口透传。你在蓝牙列表里能看到设备名，是因为扫描和配对是系统级功能，但数据传输通道根本没有对第三方开放。

解决：三条路——① 演示时换一台安卓手机（最省事）；② 把项目改成 BLE 方案（ESP32 用 BLEDevice 建服务，逻辑层不动）；③ 如果只是要控制，用手机浏览器访问 ESP32 自建的网页（改成 WiFi AP + WebServer 方案）。做毕设时建议在报告里写明这个限制，答辩时还能当作一个加分点。

烧录失败：Failed to connect to ESP32: Timed out waiting for packet header

原因：ESP32 进不了下载模式。下载模式要求 GPIO0=0 且 GPIO2=0（正常启动时 GPIO0=1，GPIO2 取任意值、不被检查）。常见原因有三个：GPIO0 没有被拉低——板上自动下载电路失效，或外接电路把它顶在高电平；GPIO2 被外接电路顶在高电平；USB 线是只充电的线或者 USB Hub 供电不足。

解决：先把 GPIO2、GPIO0 上挂的外接电路全部拔掉；按住板上的 BOOT 键不放，点「上传」，等串口出现 Connecting... 再松开；换成主板上的 USB 口、换一根确定能传数据的线。下载完成后断电重插，外设再接回去。

一个容易被忽略的安全问题

本项目的协议没有任何认证：只要有人配对成功，就能发 ALL:ON 控制你的设备。 教学演示无所谓，但如果要控制真实负载（台灯、风扇、门锁）， 至少要在协议里加一层最简单的口令，例如手机必须先发 AUTH:1234， 校验通过之前拒绝执行任何动作指令。更严谨的做法是把经典蓝牙换成 BLE 并启用配对加密。 这一点写进报告里，说明你意识到「能跑通」和「能上线」之间差着一整个安全层。

小结与练习

这个项目一共不到 200 行代码，但它把前面几篇学过的东西都串了起来： GPIO 输出（控制 LED）、 串口收发（BluetoothSerial 的读写）、 数据结构（用结构体数组组织多路通道）、 以及最重要的 协议设计（帧边界、字段语义、错误码、回执）。

如果只带走三点，请带走这三条： 字节流必须自己划边界（换行符就是边界，超长必须防）； 数据和逻辑要分离（通道表驱动，加功能只加数据不改结构）； 每条指令都要有回执（否则你无法判断失败发生在哪一环）。 这套思路换个传输层照样成立——下一篇要做的 MQTT 项目里，Topic 是通道、payload 是动作， 结构上和这里完全一致。

动手练习
  1. 加一路真实负载。 接一个继电器模块（或三极管驱动电路）控制台灯或小风扇，作为第三路 FAN。要求：① 在 channels[] 里只加一行； ② 若是低电平触发的模块，在结构体里加一个 activeLow 字段并在 setChannel() 里处理；③ 用 STATE 验证状态依然正确。 完成后数一数你一共改了几行代码。
  2. 做周期上报。 让板子每 5 秒主动发一次 STATE:...， 用 millis() 做非阻塞定时，不要用 delay()。 做好后思考：这种「不问也报」的模式，和手机发 STATE 才回答的 「请求-响应」模式，各适合什么场景？（这个思考会直接迁移到下一篇 MQTT 的发布/订阅模型。）
  3. 加 PWM 调光。 按前面的扩展片段，让 LAMP 通道支持 LAMP:DUTY:153（0~255）。 要求 constrain() 夹住非法数值，越界时回 ERR:RANGE；并且验证 PWM 与 ON/OFF 能共存 （提示：OFF 可以把占空比写成 0）。
  4. （进阶）加一层口令保护。 规定手机必须先发送 AUTH:1234， 校验通过之前，除 AUTH、PING、HELP 之外的指令一律回 ERR:AUTH。再想一步：口令明文写在代码里安全吗？ 断线重连后要不要要求重新认证？（提示：这是几乎所有物联网设备都要回答的问题。）
