STM32 时钟树与 RCC 配置

从这里开始，我们进入第三层「STM32 深入」。前两层讲的是「所有单片机共通的原理」——CPU 怎么取指、中断怎么嵌套、定时器怎么数数，这些在 51、STM32、ESP32 上都成立。 这一层不一样：我们挑一颗具体的芯片（STM32F103），把它内部真正的外设一层层拆开，讲到寄存器名、位域、手册页码、以及配错之后板子上会出现什么现象。 结论不再是「原理上应该怎样」，而是「这颗芯片上就是这几个位，写错了就是这个后果」。

第一站必须是时钟。因为在这颗芯片上，时钟不是「一个外设」，而是所有外设共同签署的一份合同： 串口的波特率、定时器的 PWM 频率、ADC 的采样时间、SysTick 的 1ms、SPI 的速率、RTC 的走时，全部是从同一个源头分下来、除下来、倍上来的。 这一篇不重讲「时钟是什么」（那是基础篇的事），只讲三件更硬的事：完整时钟树怎么算、RCC 的寄存器怎么配、配完怎么证明它真的对了。 最后一件事最重要——因为「时钟配错了但程序还能跑」是这颗芯片上最阴险的故障形态。

这一篇的钥匙是一句反直觉的话：时钟配错了，程序往往照样能跑。
它不报错、不进 HardFault，只是让每一个跟时间有关的数字都错一点点—— 直到你在串口里看到一屏乱码，或者在示波器上量到一个差一倍的 PWM。

为什么需要它

先看三个真实现场。它们的共同点是：你盯着代码看，代码全都是对的；问题不在代码里，在你对这颗芯片时钟的假设里。

现场一：串口每秒钟吐出一屏乱码

你按教程把 USART1 配成 115200，编译、下载、打开串口助手——满屏的乱码方块。你换了三根 USB 线、两个串口助手、四种波特率，全都一样。然后你开始怀疑代码：把 HAL_UART_Init() 抄了三遍。

真实的答案往往和你写的代码无关：这颗芯片实际跑的不是 72MHz。可能是外部晶振根本没起振（焊接不良、负载电容配错、晶振是坏的），HAL 在 HAL_RCC_OscConfig() 里等了 100ms 之后放弃，返回了一个你没检查的错误码；于是程序继续以复位默认的 HSI 8MHz 往下跑——USART1 的 BRR 寄存器还是按 72MHz 算出来的那个值，波特率差了 9 倍，除了乱码不可能有别的结果。

现场二：PWM 频率和算出来差整整一倍

你用 TIM2 输出 1kHz 的 PWM 驱动一个蜂鸣器。计算书上写着：定时器时钟 72MHz，预分频 PSC = 71，重装载 ARR = 999，于是 72MHz / (72 × 1000) = 1kHz。示波器一量：2kHz，正好一倍。你回头把 ARR 改成 1999，波形对了，但你不明白为什么公式里要多乘一个 2。

这就是这篇最值钱的一条规则：TIM2 挂在 APB1 上，而 APB1 的时钟是 36MHz；但 APB1 预分频系数不为 1 时，挂在它上面的定时器时钟会被硬件自动乘 2，也就是 72MHz。所以那套公式本来就是对的——错的是你以为「定时器时钟 = PCLK1 = 36MHz」，于是套了一个错的前提去反算参数。这是 PWM 频率算错的头号原因，第 2 节会把它彻底讲透。

现场三：程序下载进去，压根不跑

第三种现场最直接：LED 一点都不亮，串口一个字都不吐，调试器一暂停，发现 PC 停在 SystemInit() 或者 HAL_RCC_OscConfig() 里面不出来了。原因非常简单——代码在等一个永远不会到来的「HSE 就绪」标志：

/* 传统写法：使能 HSE，然后死等就绪标志 */
RCC->CR |= RCC_CR_HSEON;
while (!(RCC->CR & RCC_CR_HSERDY)) {
    /* 空转。晶振没起振 → HSERDY 永远是 0 → 永远出不去 */
}
/* 于是时钟切不到 PLL，SYSCLK 还停在 HSI 8MHz，
 * 而你连串口都还没初始化，什么也打印不出来 —— 板子看起来「死」了 */

这三个现场分别对应了这篇的三条主线：算不对（时钟树与定时器时钟）、配不牢（使能-轮询-超时的握手）、验不出（不检查、不回读、不打印）。而且它们的破坏力是递进的：算不对只是功能错，配不牢是程序不跑，验不出最危险——因为你根本不知道自己在错的那条路上走了多远。

这张图里有 四个容易被忽略的「暗门」，先点出来，后面逐个展开：

  • 暗门一：HSI 和 HSE 都能直接当 SYSCLK，不必过 PLL。所以「时钟切换失败」不一定意味着没时钟——你很可能是在 8MHz 上正常跑着，只是自己不知道（现场一）。
  • 暗门二：挂在 APB 上的定时器，时钟不等于 PCLK。预分频系数不为 1 时硬件自动 ×2，这是第 2 小节的全部内容。
  • 暗门三：ADC 和 USB 的时钟不在 APB 树上直连，它们各自还有一级专属预分频（ADCPRE、USBPRE），各有各的上限。
  • 暗门四：LSI 和 LSE 完全不经过上面任何一个分频器。它们直接喂给 RTC、IWDG 和 MCO——这也是为什么「主时钟全死了，看门狗和 RTC 还活着」。

定时器时钟不是 PCLK

现在把「暗门二」打开。这是整篇里最容易被误解、也最容易在项目里咬人的一条规则。先把它写成一句话：

定时器时钟规则（APB1 与 APB2 都适用）

若该 APB 的预分频系数 = 1，则挂在它上面的定时器时钟 = PCLK；
若该 APB 的预分频系数 ≠ 1，则定时器时钟 = PCLK × 2。

注意「×2」不是近似、不是额外误差，而是硬件里真的有一条 ×2 的旁路：APB 总线本身被分频了，但定时器的计数时钟从分频器之前取，并且额外翻倍。

为什么 ST 要这么设计？因为 APB1 的上限只有 36MHz，而定时器（尤其是电机控制里的 TIM1）需要 72MHz 的计数分辨率。如果定时器老老实实跟着 PCLK1 走，那在标准 72MHz 配置下，TIM2~TIM4 就只能拿到 36MHz——PWM 的分辨率凭空掉一半。 于是硬件做了这件事：让总线变慢（照顾外设），让定时器保持快（照顾时间精度）。你只要记住「总线速度」和「定时器速度」在这颗芯片上是两个独立的概念，就不会再算错。

PLL：8MHz 怎么算成 72MHz

PLL（锁相环）本身是一个模拟电路，但在这颗芯片上你只需要把它当成一个「只能整数倍频的黑盒子」：给它一个 4~16MHz 的输入，它输出输入频率的 2~16 倍，但输出必须落在 16~72MHz 之间。你要做的唯一一件事就是把倍频系数选对。

完整算式只有一行，但每个符号都要对上寄存器里的位：

                    ┌──────────────────────────────────────────────┐
                    │            HSE                                 │
                    │  SYSCLK = ─────────── × PLLMUL                 │
                    │           (PLLXTPRE + 1)                       │
                    │                                                │
                    │  其中：PLLSRC = 1（选 HSE 路径，SW 最终切 PLL）│
                    │        PLLXTPRE = 0 → 除以 1（不分频）         │
                    │        PLLXTPRE = 1 → 除以 2（HSE/2）          │
                    │        PLLMUL = 2 ~ 16 的整数，见下面的编码表  │
                    └──────────────────────────────────────────────┘

  走 HSI 时（PLLSRC = 0）那条路是固定的：
                    SYSCLK = 4MHz × PLLMUL        ← HSI 8MHz 先被硬件固定 /2

  三个必须同时满足的约束（少一个都可能不锁或超限）：
    ① PLL 输入（上式括号里算完的结果）       必须在 4 ~ 16MHz
    ② PLL 输出（= SYSCLK 的本值）            必须在 16 ~ 72MHz
    ③ 最终 SYSCLK                            不得超过 72MHz

              ↓

              ↓

              输入 8MHz   ∈ [4, 16]     ✓

              ↓

超频的板子在实验室里往往表现完美：室温 25℃、USB 供电 5.0V、只跑点灯和串口。但芯片的时序余量是随温度、电压、批次一起变的——数据手册给的 72MHz 上限，是「全温度范围、全电压范围、全批次」都保证的值。你超到 80MHz，本质上是把「保证」换成了「抽奖」。

这一类问题在毕设答辩或小批量试产时通常看不出来，在两个月的现场运行里才集中爆发。所以规则很简单：不要超频，一个兆赫兹也不要。

RCC_CR / RCC_CFGR / RCC_CIR：三个决定主频的寄存器

整个时钟系统，日常要打交道的寄存器其实不多。最核心的是三个，它们的地址固定在 0x40021000 开始的 RCC 区块里（RCC_CR = 0x40021000、RCC_CFGR = 0x40021004、RCC_CIR = 0x40021008，见 RM0008 的 RCC 寄存器映射表）。

写分频器与切时钟的顺序，是有讲究的

升频（8MHz → 72MHz）时：先把 Flash 等待周期调到 2，再把 HPRE/PPRE1/PPRE2 设好，最后才写 SW 切到 PLL。原因很直接：分频器必须先就位，否则在切过去的那一瞬间 APB1 会短暂地跑在 72MHz，超过它 36MHz 的上限。

降频（72MHz → 8MHz）时顺序相反：先切 SW 回 HSI，再改分频器，最后把等待周期降下来。

这不是「风格问题」，而是这颗芯片的硬件要求。HAL 的 HAL_RCC_ClockConfig() 内部就是按这个顺序做的（先设 latency、再设分频、再切源、再等 SWS），第 4 节会逐行拆给你看。

CSS 与「自己写超时回退」的分工

两者解决的是不同时刻的问题：自己写的超时回退管「上电启动阶段」（HSE 从一开始就没起来）；CSS 管「运行过程中」（晶振跑着跑着失效了，比如温度剧变、机械振动、虚焊）。 产品级的固件两个都要有：启动时超时回退到 HSI 并报警，运行时开 CSS 让硬件兜底。

要留意的是，CSS 触发的是 NMI——它不能被普通的中断优先级屏蔽，也不能被 __disable_irq() 关掉。所以你如果在 NMI 处理函数里写下不去的循环，整块板子就会死在那里。NMI 里只做「记录 + 报警」两件事，剩下的交给主循环。

外设门控与备份域：三个 ENR 与 BDCR

到这里，SYSCLK / HCLK / PCLK1 / PCLK2 都已经算对了。但总线上的时钟信号并不会自动送到每一个外设——每个外设前面还有一道独立的闸门（gating），默认全部关闭。 这就是为什么你会遇到那个经典现象：寄存器地址没写错、位也没写错，可写进去读回来全是 0，外设一点反应没有。

「寄存器写了没反应」的第一嫌疑人：外设时钟没使能

时钟被闸断时，外设的寄存器接口没有时钟驱动：写进去的数据被静默丢弃，读回来是复位值（多数情况下是 0）。 它不报错、不进 HardFault、不产生任何提示——只是「没反应」。所以以后碰到某个外设完全不工作，第一件事是查它的 ENR 位，而不是怀疑地址或数据类型。

三个容易踩的门控细节

  • AFIO 必须单独使能。不做引脚重映射、不用 EXTI 的人常常忘记它；一旦你要「把 USART1 挪到 PB6/PB7」或者「用 EXTI 做外部中断」，就得先 __HAL_RCC_AFIO_CLK_ENABLE()，否则重映射寄存器（AFIO_MAPR）和 EXTI 配置写不进去。
  • PWR 时钟是写电源寄存器的前提。低功耗、备份域、电压监测都涉及 PWR_CR，而它同样有闸门：__HAL_RCC_PWR_CLK_ENABLE() 之后写 PWR->CR 才有效。忘了它的典型症状是「明明把 STOP 位写进去了，芯片却不睡」。
  • 关时钟 ≠ 复位外设。闸断时钟只是让外设「停止工作并冻结寄存器」，它内部的状态和寄存器值还在。要让外设回到复位状态，得用 RCC_APB1RSTR / RCC_APB2RSTR（HAL 里是 __HAL_RCC_USART1_FORCE_RESET() / __HAL_RCC_USART1_RELEASE_RESET()）。重新开时钟之后接着用旧配置，是一种很隐蔽的 bug 来源。

RCC_BDCR：备份域、LSE 与 RTC 的时钟源

备份域（Backup Domain）是一块独立供电、独立复位的小天地：它包含 RTC、备份寄存器（BKP_DRx）和 LSE 振荡器。主电源断了，只要 VBAT 上还挂着一颗纽扣电池，RTC 就继续走时——这正是「设备断电后时间不丢」的实现方式。

但它前面还站着一个守卫：备份域写保护。默认情况下，往 RCC_BDCR 写的任何东西都会被丢弃。要开锁，得先给 PWR 时钟、再置 PWR_CR.DBP（bit 8，Disable Backup Domain write Protection）：

/* ① 先给电源控制器（PWR）时钟，否则下面那行写不进去 */
RCC->APB1ENR |= RCC_APB1ENR_PWREN;
__DSB();                                   /* 等时钟真正到位再访问，保险起见 */

/* ② 解除备份域写保护：PWR_CR 的 bit 8 = DBP */
PWR->CR |= PWR_CR_DBP;

/* ③ 现在才能配置 LSE 与 RTC 时钟源 */
RCC->BDCR |= RCC_BDCR_LSEON;                       /* 开 LSE */
while (!(RCC->BDCR & RCC_BDCR_LSERDY)) {          /* 等就绪 —— 这一等可能是秒级 */
    if (++timeout > 5000000U) break;               /* 记得带超时 */
}

/* ④ 选 RTC 时钟源并打开 RTC —— RTCSEL 一旦写定，只能靠 BDRST 改 */
RCC->BDCR = (RCC->BDCR & ~RCC_BDCR_RTCSEL) | RCC_BDCR_RTCSEL_0;  /* 01 = LSE */
RCC->BDCR |= RCC_BDCR_RTCEN;

/* ⑤ 用完可以重新锁上（可选）：PWR->CR &= ~PWR_CR_DBP; */
两个和 RTC 有关的「坑王」

坑一：忘了 DBP，一切静默失败。你写了 RCC->BDCR |= RCC_BDCR_LSEON;，读回来还是 0，LSE 永远不就绪，RTC 也不走。程序不报错，只是「时间永远是 0」。

坑二：LSE 没起振，RTC 悄悄退回 LSI。有些例程的写法是「LSE 起不来就用 LSI」，这在功能上是对的，但 LSI 是 ±50% 量级的 RC 振荡器——用它走时，一天能差几十分钟（第 3 节例 3 的姊妹题里会用 ee-pulse 的精度算式说明）。所以回退 LSI 时一定要置一个标志位、报警、或者干脆不启动 RTC，而不是「假装什么都没发生」。

顺带一提：32.768kHz 之所以是这个奇怪数字，是因为 32768 = 2¹⁵，做 15 级二分频正好得到 1Hz。这条来自 《脉冲波形的产生与整形》 里讲晶体振荡器的部分，不重复了。

所以 Flash 等待周期的正确策略是：按当前 SYSCLK 查表取值，并且「宁大勿小」。手动改主频时，最容易漏掉的就是它——把 PLL 从 ×9 改成 ×2 却忘了改 LATENCY，或者反过来把频率拉上去却没加等待周期，都会得到「程序莫名其妙跑飞」这个最难查的现象。

预取缓冲，以及一个常见的名词混淆

CPU 取指是顺序的（执行完这一条，下一条多半就在后面），而 Flash 的等待周期是「每次访问都要等」的。于是 Flash 接口里放了一个预取缓冲：它在你还没要下一条指令的时候，就提前把后面的指令读回来放着。等 CPU 真的要时，数据已经在缓冲区里了，等周期就被「藏」掉了一部分。

代价是遇到分支就失效：if、for、函数调用会让 CPU 跳到一个新地址，缓冲区里预取的内容全作废，得重新填。所以「预取带来的加速」和你的代码里分支的密度直接相关——循环体紧密的代码受益最大，一堆 if-else 和函数调用的代码受益最小。

F103 只有预取缓冲，没有 F4 那种 cache

你在别的教程里一定看过「指令 cache / 数据 cache」的说法——那是 STM32F4 的 ART Accelerator（自适应实时加速器），它有独立的指令 cache 和数据 cache，命中时零等待周期。 STM32F103 没有 cache，它只有一个简单的预取缓冲。所以： ① 不要把 F4 的「开了 cache 就几乎没有等待周期」的经验套到 F103 上； ② 在 F103 上评估「这段代码跑多快」时，必须老老实实把等待周期算进去（第 3 节例 5 就是这件事）； ③ 反过来，如果你从 F103 换到 F4，会发现同样的代码快得多——很大一部分功劳就是 cache 与更宽的 Flash 接口。

那么这 2 个等待周期到底把 CPU 拖慢了多少？数据手册里有一组常被引用的典型值：开预取、2 个等待周期时，顺序执行的代码平均约 1.5 个周期一条指令；关掉预取则要约 3 个周期一条指令（按 STM32F103 数据手册的性能表典型值估算，具体数字以你手上的手册版本为准）。第 3 节例 5 会把这两个数字换算成 MIPS 和实际代码耗时。

HAL_RCC_OscConfig() 与 HAL_RCC_ClockConfig() 都返回 HAL_StatusTypeDef：HAL_OK / HAL_ERROR / HAL_TIMEOUT。 F1 的 HAL 里，等待 HSE 就绪的超时常量来自 stm32f1xx_hal_conf.h 的 HSE_STARTUP_TIMEOUT（默认 100ms），LSE 的等待宽松得多（5000ms 量级，因为 LSE 起振本身就慢）。

CubeMX 生成的代码是这么写的：if (HAL_RCC_OscConfig(&RCC_OscInitStruct) != HAL_OK) { Error_Handler(); }。问题出在 Error_Handler() 的默认实现上——它通常是关中断 + 死循环。于是「晶振没起振」最终的表现就是板子完全没反应，和现场三一模一样。

所以第一件该做的事，就是把 Error_Handler 改成「快闪 LED + 记录错误码 + 可选复位」。同一个故障，改了之后你 3 秒钟就能判断出是时钟没配起来，而不是花两小时怀疑下载器。

为什么不建议手改 CubeMX 生成的时钟配置

你迟早会冒出这个念头：「反正就是那几个位，我直接在 SystemClock_Config() 里把 ×9 改成 ×8 不就行了？」短时间里它确实能跑，但会给你埋下三颗雷：

  1. 下次重新生成代码就被覆盖。CubeMX 生成的文件（main.c 的 SystemClock_Config()）里，只有 USER CODE BEGIN/END 之间的内容会被保留，时钟配置函数体本身每次都按 .ioc 文件重写。你手改的那一行会在某次「重新生成」后无声无息地消失，而依赖它的外设参数还在——于是故障以「上周还好好的」的形式出现。
  2. 联动关系断了。CubeMX 生成的配置是一整套自洽的东西：HAL_RCC_ClockConfig() 会顺手设好 FLASH_ACR.LATENCY，HAL 初始化 SysTick 时会按新的 HCLK 重算重载值，HAL_UART_Init() 会按 HAL_RCC_GetPCLKxFreq() 重算 BRR。 你只改其中一个数字（比如把 PLLMUL 从 9 改成 8）而不同步改 FLASH_LATENCY_2 之类的配套项，就会出现「等待周期与频率不匹配」——回到上一小节那个「跑飞」的坑。
  3. 时序已经算出去的外设不会自动跟着变。SPI 的分频比、I²C 的时序寄存器、ADC 的采样时间、定时器的 PSC/ARR——这些都是在你初始化那一刻按当时的时钟算好的。你在运行中改了时钟（或者让两次上电跑在不同频率上），它们的实际速度就全变了，而代码里的注释还写着旧值。

所以正确做法有三条，按推荐程度排序：① 要改时钟，回 CubeMX 改（它会重新校验上限、重算 Flash latency）再生成；② 如果项目不用 CubeMX，就把时钟配置集中写在自己维护的一份 SystemInit() / bsp_clock_init() 里，并且把所有「依赖时钟的常数」都改成从 HAL_RCC_GetPCLKxFreq() 现算，而不是写死；③ 无论哪条路，都在启动时打印一次三个频率（下一小节）。

怎么验证时钟配对了

前面所有内容都在说「怎么配」。但真正把新手和老手分开的，是这一步：你怎么知道它真的配对了？靠「串口能打印」是远远不够的——串口在 8MHz 上也能打印（乱码也是打印）；靠「LED 会闪」更不行。你需要的是能读到数字的手段。下面四种，从最硬到最方便排列。

方法一：MCO 输出到 PA8，用示波器量（最硬的证据）

STM32F103 有一个专门的调试引脚功能 MCO（Microcontroller Clock Output）：它把芯片内部的一路时钟直接送到 PA8 引脚上。这是唯一一个「不信任任何软件、直接看硬件」的验证手段——示波器量到的频率就是芯片真实的频率。

        ┌──────────────────────┐
        │      STM32F103       │
        │                      │
        │   PA8 (MCO) ●────────┼──────────●  示波器探头（CH1）
        │                      │          │
        │   GND       ●────────┼──────────●  探头地线夹（必须共地！）
        │                      │
        └──────────────────────┘

  MCO 可选源（RCC_CFGR.MCO[2:0]）与你应该量到的频率（假设 SYSCLK = 72MHz）：
  ┌──────────┬──────────────┬────────────────────┬──────────────────────────┐
  │ MCO[2:0] │ 输出源       │ 应该量到           │ 判读                     │
  ├──────────┼──────────────┼────────────────────┼──────────────────────────┤
  │   100    │ SYSCLK       │ 72MHz（周期 13.9ns)│ 最直接的证据             │
  │   101    │ HSI          │ 8MHz（周期 125ns） │ 验证内部 RC 是否工作     │
  │   110    │ HSE          │ 8MHz（周期 125ns） │ 验证晶振起振与实际频率   │
  │   111    │ PLL / 2      │ 36MHz（周期 27.8ns)│ PLL 锁没锁、倍频对不对   │
  │   010    │ LSI          │ 约 40kHz           │ 看门狗/RTC 的备用源      │
  │   011    │ LSE          │ 32.768kHz          │ RTC 晶振起没起           │
  └──────────┴──────────────┴────────────────────┴──────────────────────────┘

  【量不到 / 量不准的常见原因，按概率排】
   ① 探头地线太长：几厘米的地线在 36MHz 上就是一根天线，
      波形会变成圆钝的正弦、幅度不足 —— 换成弹簧地针或短线。
   ② 探头带宽不够：100MHz 探头量 72MHz 方波只能看到「勉强能辨认的方波」，
      频率读数仍然可信，但上升沿不可信。
   ③ GPIO 没配成复用推挽：PA8 必须配成 AF 推挽输出（CRH 的 CNF=10, MODE=11），
      配成普通输出则 MCO 出不来。
   ④ MCO 源没选：MCO[2:0] = 000/001 时该引脚没有时钟输出。
   ⑤ AFIO 时钟没开（部分型号需要）：__HAL_RCC_AFIO_CLK_ENABLE()。
   ⑥ 量到的频率是「一半」：看看是不是选了 PLL/2（MCO=111），那不是故障。

MCO 最大的价值在于它能把所有「软件以为」的东西一次性推翻。比如你以为在 72MHz 上跑（代码里写了 PLLMUL=9），MCO 一量是 8MHz——立刻就知道问题出在「HSE 没起来 / SW 没切过去」，而不用再猜串口乱码是谁的错。

方法二：SysTick 已知延时反推

SysTick 的重载值是由 HAL 按 HCLK 算出来的（1ms 一次中断）。于是「SysTick 中断里翻转一次 LED，示波器量周期」就变成了一个主频探针：量到 2ms 的方波周期，说明 SysTick 每 2ms 才中断一次，也就是 HCLK 只有预期的一半（或者反过来，你配置的重载值是按更低的频率算的）。

这个方法的优点是不需要额外引脚和示波器以外的设备，而且顺带验证了「HAL_Delay 到底准不准」——因为 HAL_Delay() 就是靠 SysTick 累加出来的。

方法三：用定时器输出一个「人眼可读」的方波

把 TIM4 配成 1 秒更新一次、在中断里翻转 LED（或者直接输出 PWM），然后用秒表量「LED 亮灭 10 次」的总时间。预期 20 秒（每 2 秒一个完整亮灭周期，10 次 = 20 秒）。如果量到 2 秒或者 160 秒，你就知道定时器时钟差了 10 倍或 8 倍——顺着这个倍数回去查 PSC/ARR 和 TIMxCLK 的算法，很快能定位。

方法一和二需要示波器，这个方法只需要一块表——所以在没有仪器的场合特别有用。第 4 节会给完整代码。

方法四：上电打印三个频率（最省事，也最该做的习惯）

HAL 提供了三个函数，它们直接读寄存器算出频率，不是读你代码里的常量：

函数返回什么怎么算出来的
HAL_RCC_GetSysClockFreq()SYSCLK读 SWS 判断当前源，再按 HSI/HSE/PLLMUL 算出频率
HAL_RCC_GetHCLKFreq()HCLKSYSCLK ÷ HPRE 对应的分频值
HAL_RCC_GetPCLK1Freq()PCLK1HCLK ÷ PPRE1 对应的分频值

把这个习惯刻进你的工程模板

在 main() 的开头、初始化任何外设之前，先把这四个频率打印出来（或者至少打印 SYSCLK / HCLK / PCLK1），并且与你在设计文档里写的预期值比对，不一致就报警并停下来。

这一行打印的价值，超过你后面写的所有调试代码：它把「时钟对不对」这个前提，从一个假设变成了一条有证据的日志。 以后遇到串口乱码、定时偏长、PWM 差倍，你第一眼就能排除掉最大的一类原因。第 4 节的 clock_selfcheck() 就是这个习惯的完整实现。

这四个方法不是四选一，而是互相印证的组合：MCO 量到 72MHz（硬件证据）+ 打印出来 72/72/36（软件视角）+ 定时器 1 秒方波量到 2 秒总周期（时间视角）。三个都对上，你才可以说「时钟这块没问题了」。任何一个对不上，就去查那一段路径上的选择器与分频器——时钟树的每一处都只有「对」和「错」两种状态，没有「大概对」。

动手算一遍

下面六道题，全部用真实数字、全部给出完整过程。建议你先拿纸自己算一遍再看答案——时钟这件事看别人算一百遍，不如自己错一次。

例 1：8MHz 晶振配 72MHz 的完整算式

题目：板子上是一颗 8MHz 晶振，VDD = 3.3V。请给出把 SYSCLK 配到 72MHz 的完整过程：PLL 的每一个参数（PLLSRC / PLLXTPRE / PLLMUL）、各级预分频（HPRE / PPRE1 / PPRE2 / ADCPRE）、Flash 等待周期，以及最终各定时器的计数时钟。顺便回答：如果换成 12MHz 或 16MHz 晶振，参数怎么变？

【第 1 步】PLL 输入源
    PLLSRC = 1                    /* 选 HSE，不用 HSI/2 */
    理由：有晶振就必须用晶振（精度差 500 倍，见 ee-pulse 例六）

【第 2 步】HSE 要不要先除 2（PLLXTPRE）
    HSE = 8MHz，PLL 输入要求 4 ~ 16MHz
    8MHz 已经在范围内 → 不需要除 2
    PLLXTPRE = 0                  /* ÷1 */

【第 3 步】反算倍频系数
    PLLMUL = 目标 SYSCLK ÷ PLL 输入 = 72MHz ÷ 8MHz = 9
    是整数 → 可行 ✓
    PLLMUL = 9 → 编码 0111（见第 2 节编码表）

【第 4 步】校验三条约束
    ① PLL 输入  8MHz  ∈ [4, 16]    ✓
    ② PLL 输出  72MHz ∈ [16, 72]   ✓
    ③ SYSCLK    72MHz ≤ 72MHz      ✓
    三条同时成立，这套参数是合法的。

【第 5 步】各级预分频
    HPRE  ：想让内核跑满 → HCLK = SYSCLK ÷ 1 = 72MHz   → HPRE  = 0xxx
    PPRE1 ：APB1 上限 36MHz → 只能 ÷2   → PCLK1 = 36MHz → PPRE1 = 100
    PPRE2 ：APB2 上限 72MHz → 可以 ÷1   → PCLK2 = 72MHz → PPRE2 = 0xx
    ADCPRE：ADC 上限 14MHz，源是 PCLK2 = 72MHz
            72 ÷ 2 = 36MHz  ✗ 超限
            72 ÷ 4 = 18MHz  ✗ 超限
            72 ÷ 6 = 12MHz  ✓ 合规，且是「合规档里最高的一档」
            72 ÷ 8 =  9MHz  ✓ 合规但更慢
            → ADCPRE = 10（÷6），ADC 时钟 = 12MHz

【第 6 步】Flash 等待周期
    72MHz、VDD 在 2.7~3.6V → 查表得 LATENCY = 2
    → FLASH_ACR.LATENCY = 010，HAL 里写 FLASH_LATENCY_2

【第 7 步】定时器实际拿到多少
    TIM1 / TIM8（APB2，PPRE2 = 1）→ TIMxCLK = PCLK2 = 72MHz（不 ×2）
    TIM2~TIM7（APB1，PPRE1 = 2 ≠ 1）→ TIMxCLK = PCLK1 × 2 = 36 × 2 = 72MHz
    结论：标准配置下，所有定时器都是 72MHz

【第 8 步】汇总：要写进寄存器的值
    RCC_CFGR = 0x001D8402   ← 标准 72MHz 配置的实际值
      拆开看：SW=10(PLL)  HPRE=0000(÷1)  PPRE1=100(÷2)  PPRE2=000(÷1)
              ADCPRE=10(÷6)  PLLSRC=1(HSE)  PLLXTPRE=0(÷1)  PLLMUL=0111(×9)
    FLASH_ACR.LATENCY = 2

换晶振：

晶振PLLXTPREPLL 输入PLLMUL = 72 ÷ 输入结论
8MHz÷18MHz72 ÷ 8 = 9 ✓编码 0111，得到 72MHz
12MHz÷112MHz72 ÷ 12 = 6 ✓编码 0100，得到 72MHz
16MHz÷116MHz72 ÷ 16 = 4.5 ✗ 不是整数F103 没有 ×4.5 这一档，配不出 72MHz；只能 ×4 得 64MHz
16MHz÷28MHz72 ÷ 8 = 9 ✓先 PLLXTPRE = 1 再 ×9，得到 72MHz
4MHz÷14MHz72 ÷ 4 = 18 ✗ 超过 ×16 上限最高 ×16 = 64MHz；想上 72MHz 得换晶振
这道题真正要你记住的三件事

① PLLXTPRE 不是装饰品：它存在的意义就是把 16MHz 这类「偏高」的晶振降到 8MHz 再用 ×9，从而凑出 72MHz。忘了它，16MHz 晶振最多只能到 64MHz。 ② ADCPRE 是被动选出来的：不是你想要多少，而是「在不超过 14MHz 的前提下取最高档」。PCLK2 = 72MHz 时答案是 ÷6（12MHz），写成 ÷4 就是 18MHz——ADC 直接不准。 ③ 这整套数字是可以反查的：给你 0x001D8402，你应该能倒着拆出 72/36/72 和 ×9。这是第 6 节自测题的必考项。

例 2：APB1 分频 2 时 TIM2 的时钟，以及据此算 PWM 频率

题目：标准 72MHz 配置（SYSCLK = HCLK = 72MHz、PPRE1 = ÷2、PPRE2 = ÷1）。 （1）TIM2 的计数时钟是多少？（2）要用 TIM2 输出 1kHz 的 PWM，PSC 与 ARR 怎么取？（3）如果错误地认为 TIM2 的时钟是 PCLK1 = 36MHz，会算出什么参数、实际输出多少赫兹？（4）用 TIM1 输出 50Hz 的舵机信号，又该怎么取。

【(1) TIM2 的计数时钟】
    TIM2 挂在 APB1 上
    PPRE1 = ÷2 ≠ 1  → 套用「定时器时钟 = PCLK × 2」规则
    PCLK1 = 72 ÷ 2 = 36MHz
    TIM2CLK = 36MHz × 2 = 72MHz          ← 关键的一步

【(2) 1kHz PWM 的 PSC 与 ARR】
    PWM 频率 = TIM2CLK ÷ [(PSC+1) × (ARR+1)]
    → (PSC+1) × (ARR+1) = 72 000 000 ÷ 1000 = 72000

    分配这 72000，有几种方案：
    方案 A：PSC+1 = 72     → PSC = 71，ARR+1 = 1000 → ARR = 999
            分辨率 = 1/1000 = 0.1%      ← 推荐，占空比调得细
    方案 B：PSC+1 = 720    → PSC = 719，ARR+1 = 100 → ARR = 99
            分辨率 = 1/100 = 1%         ← 够用但粗
    方案 C：PSC+1 = 1      → PSC = 0，ARR+1 = 72000 → ARR = 71999
            ✗ ARR 超过 16 位上限 65535，不可行

    → 取方案 A：PSC = 71，ARR = 999
    验算：72 000 000 ÷ (72 × 1000) = 1000.0Hz，误差 0 ✓

    顺便算占空比：想要 30% → CCR = 0.30 × (ARR+1) = 0.30 × 1000 = 300

【(3) 如果误以为 TIM2CLK = 36MHz】
    会算出：(PSC+1) × (ARR+1) = 36 000 000 ÷ 1000 = 36000
    按同样的分配习惯取 PSC = 71（÷72）→ ARR+1 = 500 → ARR = 499
    实际输出频率 = 72 000 000 ÷ (72 × 500) = 2000Hz  ← 正好差一倍！

    这就是现场二：示波器量到 2kHz，于是把 ARR 改成 999 手动凑对，
    但代码注释里那个错误的「36MHz」还留着，下次换定时器又错一遍。

【(4) TIM1 输出 50Hz 舵机信号】
    TIM1 挂在 APB2，PPRE2 = ÷1 = 1  → 不 ×2
    TIM1CLK = PCLK2 = 72MHz
    周期 20ms → (PSC+1) × (ARR+1) = 72 000 000 ÷ 50 = 1 440 000
    分配：取 PSC+1 = 144 → PSC = 143（计数时钟 500kHz，1 个数 = 2µs）
          ARR+1 = 10000 → ARR = 9999（一圈 20ms）
    验算：72 000 000 ÷ (144 × 10000) = 50.0Hz ✓

    舵机脉宽 0.5ms ~ 2.5ms 对应的 CCR：
        0.5ms ÷ 2µs = 250     → CCR = 250
        1.5ms ÷ 2µs = 750     → CCR = 750（中位）
        2.5ms ÷ 2µs = 1250    → CCR = 1250
    分辨率 2µs，对舵机来说绰绰有余（舵机本身的分辨率是几十微秒量级）。
再补一刀：把 PPRE1 改成 ÷1 会怎样

有人为了让 PCLK1「快一点」，把 PPRE1 设成 ÷1。此时 PCLK1 = 72MHz——直接超过 APB1 的 36MHz 上限，属于违规配置。 有意思的是：按规则，此时 PPRE1 = 1，定时器时钟 = PCLK1 = 72MHz，不做 ×2——TIM2 拿到的时钟仍然是 72MHz，和 ÷2 时完全一样。

这条对比很能说明问题：×2 规则的作用不是「让定时器更快」，而是「让定时器在总线被分频之后保持不变慢」。你改 PPRE1 只会让 APB1 上的外设（USART2/3、I2C、SPI2）时钟变化，定时器基本不动。所以想让 PWM 更快/更慢，该改的是 PSC 和 ARR，不是 APB 预分频。

例 3：HSE 起振失败回退 HSI 后，串口会错成什么样

题目：USART1 挂在 APB2 上，目标 115200 8N1。代码原本按 72MHz 设计。现在 HSE 起振失败，程序按你写的超时逻辑回退到 HSI，SYSCLK 变成 8MHz。 （1）如果 BRR 是按 72MHz 算的旧值，实际波特率是多少、偏差多少？（2）如果 HAL_UART_Init() 是在回退之后才执行的（BRR 按实际 PCLK2 重算），结果如何？（3）这两种情形分别该怎么修？

【预备知识】USART 的波特率公式
    波特率 = PCLKx ÷ (16 × USARTDIV)
    BRR 寄存器 = 整数部分 × 16 + 小数部分 × 16（小数只有 4 位，即 1/16 的刻度）
    即：USARTDIV 的整数部分放 BRR[15:4]，小数部分（0~15）放 BRR[3:0]

【(1) BRR 按 72MHz 算，但实际 PCLK2 = 8MHz】
    ① 按 72MHz 算 USARTDIV：
       USARTDIV = 72 000 000 ÷ (16 × 115200) = 39.0625
       整数 39，小数 0.0625 × 16 = 1
       → BRR = 39 × 16 + 1 = 625 = 0x271

    ② 实际 PCLK2 只有 8MHz，而这个 BRR 没变：
       实际波特率 = 8 000 000 ÷ (16 × (39 + 1/16))
                  = 8 000 000 ÷ (16 × 39.0625)
                  = 8 000 000 ÷ 625
                  = 12 800 bps

    ③ 偏差 = (12800 − 115200) ÷ 115200 = −88.9%
       —— 相当于双方速率差了 9 倍，收到的每一个位都对不齐采样点，
          结果只能是「一屏乱码」，没有任何一个字节能对。

【(2) HAL_UART_Init() 在回退之后才执行】
    此时 HAL_RCC_GetPCLK2Freq() 读到的是真实值 8MHz：
       USARTDIV = 8 000 000 ÷ (16 × 115200) = 4.3403
       整数 4，小数 0.3403 × 16 = 5.44 → 取最近的 5
       → USARTDIV = 4 + 5/16 = 4.3125
       实际波特率 = 8 000 000 ÷ (16 × 4.3125) = 115 942 bps
       偏差 = (115942 − 115200) ÷ 115200 = +0.64%
       —— 能正常通信（远小于串口允许的百分之几量级）

    再把 HSI 本身的精度算进来（±1% 量级，25℃ 出厂校准）：
       最坏情况偏差 ≈ 0.64% + 1% = 1.64% 量级
       —— 已经接近一帧 10 位所能容忍的边界，
          短帧大多能过，长时间运行会偶发错字节。

【(3) 两种情形分别怎么修】
    情形 (1)：真正的病根是「时钟假设与现实不一致」。
             修法有两种：
               · 上策：超时回退时立刻把 BRR 重算一遍，并把「已降级」的标志
                       置起来、报警、降低功能等级（比如只保证 9600 的调试口）；
               · 下策（不可取）：不管，靠运气 —— 于是你得到一屏乱码。
    情形 (2)：功能能跑，但你有责任让用户知道这块板子「不完整」：
              打印一条时钟降级告警，并且不要在这块板子上做任何
              依赖精确时间的功能（PWM 调光、长积分采样、RTC）。
这道题最重要的结论，与你的直觉相反

「HSE 挂了 → 串口乱码」这个因果链里，真正的凶手不是 HSI 精度不够，而是「时钟变了但 BRR 没跟着变」。 情形 (2) 里 HSI 的 ±1% 只贡献了 0.64% 左右的额外误差，串口照样能通——这也解释了为什么很多人用 HSI 调试也能看到正常打印。

所以：看到乱码先查时钟假设与 BRR，而不是先怪晶振精度。反过来，如果 BRR 是按真实 PCLK 算的、字还是偶尔错，那才轮到 HSI 精度出场（这时候去看 《脉冲波形的产生与整形》 例六的容差推导）。

另外注意一个细节：HAL_Delay 在这个故障里仍然是准的，因为 SysTick 的重载值是 HAL 按当前 HCLK（8MHz）重算的。所以「延时正常但串口乱码」是一对非常有辨识度的症状组合——它几乎可以直接指认「某个外设的参数是按旧的时钟假设算出来的」。

例 4：MCO 输出 72MHz÷2，示波器上该看到什么

题目：你把 MCO 配成输出 PLL 的 2 分频（RCC_CFGR.MCO = 111），程序里 PLLMUL = ×9、HSE = 8MHz。 （1）示波器上应该量到多少赫兹、一个周期多少纳秒？（2）如果用 100MHz 带宽的探头，波形会是什么样、读数还可信吗？（3）如果量到的是 18MHz，最可能是什么错了？（4）如果量到 8MHz，又说明什么？（5）量到 什么都没有，查什么？

【(1) 应该量到什么】
    HSE = 8MHz，PLLXTPRE = ÷1，PLLMUL = ×9
    PLL 输出 = 8MHz × 9 = 72MHz
    MCO = 111 → 输出 PLL ÷ 2 = 72MHz ÷ 2 = 36MHz

    周期 T = 1 ÷ 36 000 000 = 27.78ns
    半周期 = 13.89ns

    示波器设置建议：
      时基 5ns/div  → 一个完整周期约 5.6 格，看着舒服
      或  10ns/div  → 一个周期约 2.8 格，能同时看几个周期
      触发电平取幅值的一半，边沿触发、上升沿

【(2) 100MHz 探头下会看到什么】
    36MHz 方波的主要谐波在 36MHz、108MHz、180MHz…（奇次谐波）
    100MHz 带宽意味着 108MHz 以上的谐波被大幅衰减：
      → 波形不再是方波，而是一个「圆角、略有倾斜」的近似正弦波
      → 幅度会比理论值略小（探头/示波器都是低通特性）
      → 上升沿明显变缓（可能到 3~5ns 而不是理想的亚纳秒）
    但「频率读数」仍然完全可信：
      因为基波 36MHz 远在带宽之内，周期/频率测量只依赖过零点间隔。
      → 结论：波形丑 ≠ 频率错。判读时钟看读数，不要看形状。
      要看清沿的形状，需要 ≥200MHz 带宽的探头（或至少 100MHz 探头 + 短地线）。

【(3) 量到 18MHz 说明什么】
    MCO = 111 输出的是 PLL ÷ 2，量到 18MHz
    → 反推 PLL 输出 = 18 × 2 = 36MHz
    → PLL 只有 36MHz，而预期是 72MHz

    36MHz 是怎么来的？8 ÷ 2 × 9 = 36MHz
    → 输入是 4MHz，正是 HSI(8MHz) ÷ 2 的结果
    → 结论：PLLSRC 选成了 HSI/2，而不是 HSE！
       （RCC_CFGR.PLLSRC = 0 而不是 1）

    这是非常有价值的一次判读：它一句话告诉你
    「晶振没被用上，芯片现在跑在 36MHz」
    ——瞬间解释了串口乱码和 PWM 频率不对两个现象。

【(4) 量到 8MHz 说明什么】
    8MHz 恰好是 HSI 和 HSE 的频率，但 MCO = 111 是 PLL/2：
      若真是 PLL/2 = 8MHz → PLL 输出只有 16MHz
      → 不可能来自 8MHz 输入（×2 才是 16MHz，可你就配了 ×9）
      更合理的解释有两条，用 MCO = 100(SYSCLK) 复量一次即可区分：
        A. 你选错了 MCO 源（比如实际写成了 101 = HSI，直接输出 8MHz）
        B. 系统根本没切到 PLL：SW 还停在 HSI，SYSCLK = 8MHz，
           而 MCO 输出的是「某一路 8MHz」——此时把 MCO 改成 100
           再量，仍然是 8MHz，就确认是 B。
    判读方法：把 MCO 依次设成 100 / 111 各量一次。
       100 = 8MHz 且 111 = 8MHz  → SW 没切过去（或 PLL 没锁上）
       100 = 72MHz 且 111 = 36MHz → 一切正常，第一次是你选错源了

【(5) 什么都没有（一条直线）】
    按概率查这几处：
      ① GPIOA->CRH 的 PA8 没配成复用推挽（必须 MODE8=11, CNF8=10 → 0xB）
      ② RCC_CFGR.MCO 还是 000/001（无输出）
      ③ 忘了开 GPIOA 时钟（APB2ENR 的 IOPAEN），GPIO 配置寄存器写不进去
      ④ 探头接错引脚（MCO 固定是 PA8，不能重映射）
      ⑤ 探针没接触好、地线没夹（这条最常见，也最容易被忽略）
      ⑥ 该型号/封装的 PA8 被复用为其他功能（比如用于外部晶振输入时
         要确认你板上 PA8 是否真接到了排针）
把 MCO 当成「时钟树的路标」

这道题真正的技巧不是算 36MHz，而是「用两级 MCO 读数把故障范围一刀切开」： 先量 MCO = 100（SYSCLK）。如果 SYSCLK 就对不上，问题在 PLL/源选择那一段，后面全都不用查；如果 SYSCLK 对了但功能不对，问题在分频器和外设参数那一段。

这个「先量总干路、再查支路」的排故思路，和电路调试里先量电源、再量各级工作点是一个道理——时钟树就是芯片里的「电源树」。

例 5：由 Flash 等待周期与预取，估算 72MHz 下每条指令几个周期

题目：72MHz、2 个 Flash 等待周期、预取缓冲开启。数据手册给的经验值是「平均约 1.5 个周期/指令」。 （1）这个 1.5 是怎么来的？（2）平均一条指令多少纳秒、折合多少 MIPS？（3）关掉预取会变成多少？（4）一个 1000 次的空循环大概需要多久？（5）为什么实际程序往往到不了 48MIPS？

【(1) 1.5 周期/指令是怎么来的】
    先算「一次 Flash 访问要几个周期」：
      Flash 访问周期 = 1 个访问周期 + LATENCY 个等待周期
                     = 1 + 2 = 3 个 HCLK 周期

    再看「一次访问能取回多少指令」：
      Cortex-M3 的指令总线是 32 位宽，而 Thumb-2 指令大多是 16 位
      → 一次 32 位取指里通常装着 2 条 16 位指令

    于是：3 个周期 ÷ 2 条指令 = 1.5 个周期/指令        ← 这就是那个 1.5

    这个推导同时解释了三件事：
      · 为什么 72MHz 必须配 2WS 才「够快」——1WS 会取指出错，不是变慢的问题
      · 为什么开预取能接近 1.5——预取把「下一次访问」提前做掉，
        顺序执行时等待被打包隐藏
      · 为什么 32 位指令（如 LDR.W / BL）比例高时 CPI 会上升
        —— 一次取指只装得下 1 条指令，等于摊到 3 个周期/指令

【(2) 换算成时间与 MIPS】
    每个 HCLK 周期 = 1 ÷ 72MHz = 13.89ns
    平均一条指令 = 1.5 × 13.89ns = 20.83ns

    吞吐率 = 72 MIPS 指令周期 ÷ 1.5 = 48 MIPS
    也就是说：72MHz 的 F103，实际指令吞吐大约 48 百万条/秒。

    记忆锚点（都是按手册典型值估算，不是保证值）：
      1 条指令   ≈ 20.8ns
      50 条指令  ≈ 1.04µs
      100 条指令 ≈ 2.08µs

【(3) 关掉预取（PRFTBE = 0）会怎样】
    没有预取，每次取指都老老实实等 3 个周期，
    而一条 16 位指令要从这 3 个周期里摊到一半：
    实际表现是每次访问只有约 1 条指令被有效利用

    手册给出的经验值：关预取时约 3 个周期/指令
      → 平均一条指令 3 × 13.89ns = 41.7ns
      → 吞吐率降到约 24 MIPS，正好是原来的一半

    → 结论：预取缓冲不是「优化」，它是 72MHz 能跑出性能的前提之一。
      复位后 PRFTBE 的默认状态请以你芯片的参考手册为准，
      但工程上一律显式打开：FLASH->ACR |= FLASH_ACR_PRFTBE;

【(4) 1000 次空循环要多久】
    假设循环体编译后是 4 条指令（比较、自减/自增、条件跳转、再加一条空操作，
    具体条数取决于编译器优化等级——按典型值估算，别当成精确值）：
      每次循环 = 4 × 20.83ns ≈ 83.3ns
      1000 次   = 83.3µs

    如果实测是 166µs，那就是「每条指令比预期多花一倍时间」——
    请立刻回头查 Flash 等待周期与预取位，而不是怀疑编译器。

    顺便：这也是「软件空循环做延时」为什么不可靠的原因之一：
      它随编译器版本、优化等级、指令对齐而变化，
      误差动辄 ±50%。（要精确延时请用定时器或 SysTick。）

【(5) 为什么实测常常到不了 48 MIPS】
    因为 1.5 是「顺序执行 + 预取命中」的理想值。以下情况都会让它变差：
      · 分支/跳转：预取队列里取到的下一条指令被丢弃，流水线要重新填充
        （if/else 密集、函数调用频繁的代码，CPI 可能升到 2~3）
      · 32 位指令占比高（长立即数、大偏移访问、BL 调用）
      · 访问 SRAM/外设的 LDR/STR 受总线仲裁影响
      · 中断频繁，每次进出栈都要额外周期
    所以「72MHz = 每秒 7200 万条指令」是常见误解。
    工程口径：按 30~45 MIPS 估算你的时间预算，比较稳。
这道题对「性能优化」的直接指导

既然 CPI 的瓶颈在取指，那么把热点代码放进 SRAM 执行（F103 没有指令 cache，但有 SRAM）是一件立竿见影的事：SRAM 访问不需要等待周期。 不过要注意 AHB 上 SRAM 与 Flash 的分工，以及 F103 的 SRAM 只有 20KB（中容量）～64KB（大容量）——把几十字节的热点函数搬过去划算，把整个库搬过去就不划算了。

更常用的优化顺序是：① 先减少分支密度和函数调用开销（这对 CPI 的影响比想象中大）；② 减少 32 位指令的使用（能用 16 位立即数就别用大的）；③ 最后才考虑搬 SRAM。至于「超频到 96MHz 换取性能」——第 6 题会告诉你为什么别这么干。

例 6：超频 80MHz 与欠频 64MHz，分别会发生什么

题目：两块板子，晶振都是 8MHz。 A 板把 PLLMUL 改成 ×10（SYSCLK = 80MHz），B 板改成 ×8（SYSCLK = 64MHz），其它配置（含 BRR 与定时器参数）都还是按 72MHz 算的。 （1）A 板的 Flash 等待周期该怎么设？设得出来吗？（2）A 板会有什么现象？（3）B 板的定时器输出多少赫兹的 PWM（原本设计 1kHz）？（4）B 板的串口会怎样？（5）B 板跑一天的时间误差是多少？

【(1) A 板 80MHz 的等待周期——答案是「设不出来」】
    查 wait state 表（2.7~3.6V）：
      ≤ 24MHz → 0 WS
      ≤ 48MHz → 1 WS
      ≤ 72MHz → 2 WS
      80MHz   → 需要 3 WS …… 但 LATENCY 只有 3 位里的 0/1/2 三档
                （F103 只定义了 0、1、2，2 是最大值）

    → 也就是说：72MHz 就是「这套 Flash 等待周期机制能支撑的上限」。
      超出之后，没有任何合法配置能让取指可靠。

【(2) A 板的现象（超频的典型症状）】
    相对超频量 = 80 ÷ 72 = +11.1%
    ——这不是「快一点」，而是把全部时序余量吃成负数：

      常温、3.3V、短时间跑 → 大概率「看着能跑」
      一加热到 60℃ 以上、或电压掉到 3.0V 附近 → 开始随机 HardFault、
      变量被写坏、程序跳到奇怪的地方
      有时表现为「下载后能跑，断电再上电就跑不起来」
      串口可能时好时坏（外设的分频器是按 72MHz 的假设算的）

    为什么会这样？因为芯片内部所有路径的时序都是按「不超过 72MHz
    下的最坏情况」设计并测试的。你把它推到 80MHz，等于
    把「设计余量」当成了「免费性能」——而余量本来是用来兜住
    温度、电压、工艺分散的。

    更要命的是：等一下 ADC。
      ADC 时钟 = PCLK2 ÷ ADCPRE = 80 ÷ 6 = 13.33MHz ≤ 14MHz ✓ 侥幸没超
      但如果你的 ADCPRE 是 ÷4：80 ÷ 4 = 20MHz，直接超限 43%，
      采样结果会明显偏小/不稳。
    → 结论：超频不是「有风险」，而是「没有合法等待周期可用」，
      它属于禁止项，不该出现在任何要交付的工程里。

【(3) B 板 64MHz：定时器输出多少赫兹】
    定时器参数是按 72MHz 算的：PSC = 71、ARR = 999
    （设计意图：(71+1) × (999+1) = 72000，72 000 000 ÷ 72000 = 1000Hz）

    但实际 TIMxCLK = 64MHz：
      实际频率 = 64 000 000 ÷ (72 × 1000) = 888.9 Hz
      偏差 = (888.9 − 1000) ÷ 1000 = −11.1%

    → 和频率偏差完全一致（时钟本质上就是「时间的尺子」，
      尺子短了 11.1%，量出来的所有频率都少 11.1%）。
    现象：PWM 调光会有可感知的闪烁差；舵机周期变成 22.5ms 而不是 20ms，
      会有轻微抖动甚至「行程不足」；步进电机的转速差 11.1%。

【(4) B 板的串口】
    分两种情况（和例 3 同一个道理）：
      情况一：BRR 是写死的 / 按 72MHz 算的（BRR = 0x271，USARTDIV = 39.0625）
              实际波特率 = 64 000 000 ÷ (16 × 39.0625) = 102 400 bps
              偏差 = (102400 − 115200) ÷ 115200 = −11.1%
              → 远超串口容差，乱码
      情况二：HAL_UART_Init() 在时钟配置之后调用，BRR 按实际 PCLK2 重算
              → 串口正常。也就是说：单纯降频不一定会让串口坏，
                坏的是「假设与实际的错配」。

【(5) B 板跑一天的时间误差】
    时钟慢 11.1%，任何基于主频的计时都会慢 11.1%：
      1 天 = 86400 秒 → 误差 = 86400 × 11.1% = 9590 秒 ≈ 2.66 小时
    → 一个「每天记录一次数据」的采集器，会在一个月后把日期整体错开。
      （注意：这里说的是基于主频的计时；如果 RTC 用的是 LSE 32.768kHz，
        那它不受 SYSCLK 影响——这正是 RTC 必须有自己的晶振的原因。）

 * bsp_clock.c  ——  STM32F103 纯寄存器时钟初始化
 * 目标：SYSCLK = 72MHz, HCLK = 72MHz, PCLK1 = 36MHz, PCLK2 = 72MHz
 * 特点：不依赖 HAL / 标准库，只用 CMSIS 的寄存器定义；
 *       每一处等待都有超时；HSE 起不来就自动降级到 HSI 8MHz 并上报。
 * ========================================================================== */
#include "stm32f10x.h"

/* HSE 等待上限：与 ST 官方 system_stm32f10x.c 里的 HSEStartUp_TimeOut 一致 */
#define HSE_STARTUP_TIMEOUT   ((uint32_t)0x0500)

/* CMSIS 的 RCC_CFGR 里只有 SW/SWS 的位置掩码，没有「SW=PLL」这种命名值，
   为了不依赖标准库，这里按参考手册自己定义一次 */
#define CFGR_SW_MASK      (0x3UL << 0)
#define CFGR_SW_HSI       (0x0UL << 0)
#define CFGR_SW_HSE       (0x1UL << 0)
#define CFGR_SW_PLL       (0x2UL << 0)
#define CFGR_SWS_MASK     (0x3UL << 2)
#define CFGR_SWS_HSI      (0x0UL << 2)
#define CFGR_SWS_HSE      (0x1UL << 2)
#define CFGR_SWS_PLL      (0x2UL << 2)

typedef enum {
    CLOCK_OK = 0,                 /* 72MHz，一切正常 */
    CLOCK_ERR_HSE_TIMEOUT,        /* 晶振没起振，已回退 HSI */
    CLOCK_ERR_PLL_TIMEOUT,        /* PLL 没锁上，已回退 HSI */
    CLOCK_ERR_SWS                 /* SW 写了但 SWS 没跟上，已回退 HSI */
} clock_status_t;

static clock_status_t g_clock_status = CLOCK_OK;

clock_status_t bsp_clock_get_status(void) { return g_clock_status; }

/* --------------------------------------------------------------------------
 * 起 HSE，带超时。返回 0 成功，-1 失败（失败时已把 HSEON 关掉）
 * ------------------------------------------------------------------------ */
static int hse_start(void)
{
    uint32_t timeout = HSE_STARTUP_TIMEOUT;

    RCC->CR |= RCC_CR_HSEON;                      /* ① 使能 */
    while ((RCC->CR & RCC_CR_HSERDY) == 0) {     /* ② 轮询 RDY */
        if (--timeout == 0) {                    /* ③ 超时判据 */
            RCC->CR &= ~RCC_CR_HSEON;             /* 关掉，别让它半死不活拖着 */
            return -1;
        }
    }
    return 0;
}

/* --------------------------------------------------------------------------
 * 回退路径：切到 HSI 8MHz，并关掉 PLL。
 * 这段代码必须绝对可靠——它是「已经出事了」之后才走的路，
 * 所以里面除 HSI 就绪之外不再做任何有风险的等待（HSI 起振是纳秒级）。
 * ------------------------------------------------------------------------ */
static void sysclk_fallback_to_hsi(void)
{
    RCC->CR |= RCC_CR_HSION;
    while ((RCC->CR & RCC_CR_HSIRDY) == 0) { }   /* HSI 必起，但保留等待 */

    RCC->CFGR = (RCC->CFGR & ~CFGR_SW_MASK) | CFGR_SW_HSI;
    while ((RCC->CFGR & CFGR_SWS_MASK) != CFGR_SWS_HSI) { }  /* 回读确认 */

    RCC->CR &= ~RCC_CR_PLLON;                    /* 切走之后再关 PLL，顺序不能反 */
    while (RCC->CR & RCC_CR_PLLRDY) { }

    /* 8MHz 只需要 0WS，但保留 2WS 也无害（只是慢一点），
       这里选择保守：不动 Flash 配置，避免在降级路径上再引入新变量 */
}

/* --------------------------------------------------------------------------
 * 时钟初始化主流程
 * ------------------------------------------------------------------------ */
clock_status_t bsp_clock_init(void)
{
    /* ---- 步骤 1：Flash 先准备好（升频前设等待周期 + 开预取） ---- */
    FLASH->ACR = FLASH_ACR_PRFTBE | FLASH_ACR_LATENCY_2;   /* 2WS @72MHz/3.3V */

    /* ---- 步骤 2：起 HSE ---- */
    if (hse_start() != 0) {
        g_clock_status = CLOCK_ERR_HSE_TIMEOUT;
        sysclk_fallback_to_hsi();
        return g_clock_status;                   /* 调用者必须处理！ */
    }

    /* ---- 步骤 3：配置并启动 PLL：源选 HSE、HSE 不分频、×9 ---- */
    RCC->CFGR &= ~(RCC_CFGR_PLLSRC | RCC_CFGR_PLLXTPRE | RCC_CFGR_PLLMULL);
    RCC->CFGR |= RCC_CFGR_PLLSRC | RCC_CFGR_PLLMULL9;   /* PLLXTPRE=0 → ÷1 */

    RCC->CR |= RCC_CR_PLLON;
    {
        uint32_t timeout = HSE_STARTUP_TIMEOUT;
        while ((RCC->CR & RCC_CR_PLLRDY) == 0) {         /* 等 PLL 锁定 */
            if (--timeout == 0) {
                g_clock_status = CLOCK_ERR_PLL_TIMEOUT;
                sysclk_fallback_to_hsi();
                return g_clock_status;
            }
        }
    }

    /* ---- 步骤 4：设各级分频。必须在切 SW 之前就位 ----
     * 否则在「SYSCLK 已经是 72MHz、PPRE1 还是 ÷1」的那一瞬间，
     * PCLK1 = 72MHz 会短暂超限（虽然只有几个周期，但没必要冒险）。
     * HPRE  = 0000 → HCLK  = 72MHz
     * PPRE1 = 0100 → PCLK1 = 36MHz（上限 36MHz）
     * PPRE2 = 0000 → PCLK2 = 72MHz（上限 72MHz）
     * ADCPRE= 10   → ADC   = 12MHz（上限 14MHz）
     */
    RCC->CFGR &= ~(RCC_CFGR_HPRE | RCC_CFGR_PPRE1 | RCC_CFGR_PPRE2 | RCC_CFGR_ADCPRE);
    RCC->CFGR |= RCC_CFGR_PPRE1_DIV2 | RCC_CFGR_ADCPRE_DIV6;

    /* ---- 步骤 5：切 SYSCLK 到 PLL，并回读 SWS 确认 ---- */
    RCC->CFGR = (RCC->CFGR & ~CFGR_SW_MASK) | CFGR_SW_PLL;
    {
        uint32_t timeout = HSE_STARTUP_TIMEOUT;
        while ((RCC->CFGR & CFGR_SWS_MASK) != CFGR_SWS_PLL) {   /* 回读！ */
            if (--timeout == 0) {
                g_clock_status = CLOCK_ERR_SWS;
                sysclk_fallback_to_hsi();
                return g_clock_status;
            }
        }
    }

    g_clock_status = CLOCK_OK;
    return CLOCK_OK;                             /* 72MHz 就绪 */
}

/* --------------------------------------------------------------------------
 * 给上层用的小工具：读出当前四个频率（按寄存器反算，不是查表）
 * ------------------------------------------------------------------------ */
uint32_t bsp_get_sysclk(void)
{
    uint32_t pllmul, pllsrc, prediv, sysclk;

    switch (RCC->CFGR & CFGR_SWS_MASK) {
    case CFGR_SWS_HSI:  return 8000000UL;                    /* HSI 固定 8MHz */
    case CFGR_SWS_HSE:  return 8000000UL;                    /* 按板上晶振改这里 */
    default:            break;                               /* 余下是 PLL */
    }

    pllsrc  = RCC->CFGR & RCC_CFGR_PLLSRC;                   /* 0=HSI/2, 1=HSE */
    prediv  = (RCC->CFGR & RCC_CFGR_PLLXTPRE) ? 2UL : 1UL;   /* ÷1 或 ÷2 */
    pllmul  = ((RCC->CFGR & RCC_CFGR_PLLMULL) >> 18) + 2UL;   /* 编码 0 → ×2 */

    sysclk  = pllsrc ? (8000000UL / prediv) : (4000000UL);   /* HSI/2 = 4MHz */
    return sysclk * pllmul;
}
这段代码里三个「不这么做就会出事」的细节

① FLASH->ACR 必须先设、且要在升频之前设。升到 72MHz 的那一瞬间开始，取指就需要 2 个等待周期了。先切频再设等待周期，中间那几个周期的取指结果不可靠——虽然通常「侥幸能过」，但这属于不可交付的写法。

② 回退路径里「先切 SW，再关 PLL」。如果反过来（先关 PLL 再切 SW），在 PLL 被关掉、SYSCLK 还指着 PLL 的那一小段时间里，系统时钟源消失了——芯片会立刻挂掉。正确的顺序永远是：先切到安全源并确认切过去了，再关掉旧源。

③ bsp_get_sysclk() 里 pllmul 的算法要多加 2。因为 PLLMUL 的编码是 0000 → ×2，不是 ×0：编码 + 2 = 倍频数。这个「偏移 2」在手册的编码表里一眼能看出来，但自己写代码时极易漏掉——漏掉的后果是所有频率读数都少 2 倍。

忘记更新 SystemCoreClock 会怎样

标准库/HAL 里有一个全局变量 SystemCoreClock，很多延时函数、外设初始化都默认它是对的。用上面的 bsp_clock_init() 改了时钟之后，如果你不更新它，库里那些「按 SystemCoreClock 算时间」的函数就会算错。

两种做法：① 自己维护——在 bsp_clock_init() 末尾写 SystemCoreClock = bsp_get_sysclk();（HCLK 在这个配置里等于 SYSCLK）；② 交给库——如果你用的是标准库/HAL，调用 SystemCoreClockUpdate()，它会自己读 RCC 寄存器反算 HCLK 并刷新变量。别两个都写，重复调用无害但容易让人看糊涂。

代码二：HAL 版 SystemClock_Config 逐行注释

下面是 CubeMX 生成的那段 SystemClock_Config() 的等价形式（去掉了 CubeMX 的注释框），每一行都标注了它实际写了哪个寄存器位。建议对照第 2 节的寄存器表读一遍——读完你会发现，HAL 没有做任何你没学过的事，它只是把你的意图翻译成了寄存器操作，并且在每个 while 里加了超时。

/**
  * @brief  系统时钟配置：HSI 起步 → HSE 8MHz → PLL ×9 → 72MHz
  *         对应 RCC_CFGR = 0x001D8402（可自行验算）
  */
void SystemClock_Config(void)
{
    RCC_OscInitTypeDef RCC_OscInitStruct = {0};
    RCC_ClkInitTypeDef RCC_ClkInitStruct = {0};

    /* ---------------- 第一部分：源与 PLL ---------------- */
    __HAL_RCC_PWR_CLK_ENABLE();          /* 开 PWR 时钟（F1 上严格说不是必须，
                                            但 CubeMX 习惯带上，为后面调压做准备） */

    RCC_OscInitStruct.OscillatorType = RCC_OSCILLATORTYPE_HSE;
                                         /* → 本次只操作 HSE 相关的位 */
    RCC_OscInitStruct.HSEState       = RCC_HSE_ON;
                                         /* → RCC_CR.HSEON = 1，并等 HSERDY */
    RCC_OscInitStruct.HSEPredivValue = RCC_HSE_PREDIV_DIV1;
                                         /* → RCC_CFGR.PLLXTPRE = 0（÷1） */
    RCC_OscInitStruct.HSIState       = RCC_HSI_ON;
                                         /* → RCC_CR.HSION = 1（保留 HSI 作为退路） */
    RCC_OscInitStruct.PLL.PLLState   = RCC_PLL_ON;
                                         /* → RCC_CR.PLLON = 1，并等 PLLRDY */
    RCC_OscInitStruct.PLL.PLLSource  = RCC_PLLSOURCE_HSE;
                                         /* → RCC_CFGR.PLLSRC = 1 */
    RCC_OscInitStruct.PLL.PLLMUL     = RCC_PLL_MUL9;
                                         /* → RCC_CFGR.PLLMUL = 0111（×9） */

    if (HAL_RCC_OscConfig(&RCC_OscInitStruct) != HAL_OK)
    {
        /* 走到这里 = HSE 没起振 / PLL 没锁上（内部等 HSERDY 的超时约 100ms）
           → 默认的 Error_Handler() 是「关中断 + 死循环」，
             表现出来就是「板子完全没反应」，务必改成 LED 快闪 + 记录状态！ */
        Error_Handler();
    }

    /* ---------------- 第二部分：分配（谁当 SYSCLK、各级分频） ---------------- */
    RCC_ClkInitStruct.ClockType = RCC_CLOCKTYPE_HCLK | RCC_CLOCKTYPE_SYSCLK
                                | RCC_CLOCKTYPE_PCLK1 | RCC_CLOCKTYPE_PCLK2;
                                         /* → 本次要配置这四级 */
    RCC_ClkInitStruct.SYSCLKSource   = RCC_SYSCLKSOURCE_PLLCLK;
                                         /* → RCC_CFGR.SW = 10，并回读 SWS 确认 */
    RCC_ClkInitStruct.AHBCLKDivider  = RCC_SYSCLK_DIV1;
                                         /* → RCC_CFGR.HPRE  = 0000（HCLK  = 72MHz） */
    RCC_ClkInitStruct.APB1CLKDivider = RCC_HCLK_DIV2;
                                         /* → RCC_CFGR.PPRE1 = 0100（PCLK1 = 36MHz） */
    RCC_ClkInitStruct.APB2CLKDivider = RCC_HCLK_DIV1;
                                         /* → RCC_CFGR.PPRE2 = 0000（PCLK2 = 72MHz） */

    if (HAL_RCC_ClockConfig(&RCC_ClkInitStruct, FLASH_LATENCY_2) != HAL_OK)
    {
        /* 第二个参数直接写成 FLASH_LATENCY_2：
           HAL 会先设 FLASH_ACR.LATENCY = 2，再切 SW —— 顺序是对的。
           这三档的对应关系：FLASH_LATENCY_0 → ≤24MHz
                             FLASH_LATENCY_1 → ≤48MHz
                             FLASH_LATENCY_2 → ≤72MHz（3.3V）
           传错档位不会报错，但会在高频下取指出错、表现为「莫名跑飞」。 */
        Error_Handler();
    }
}

/* ==========================================================================
 * 推荐的 Error_Handler：不要死循环，要「看得见 + 能恢复」
 * ========================================================================== */
void Error_Handler(void)
{
    __disable_irq();                          /* 先停掉中断，避免干扰判断 */

    /* 用一个 LED 把错误码「闪」出来，人眼可读：
       快闪 1 次 → HSE 超时；快闪 2 次 → PLL 超时；快闪 3 次 → 其它 */
    while (1)
    {
        for (volatile uint32_t i = 0; i < 200000; i++) { }   /* 粗延时 */
        HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);
    }
    /* 如果板子上有独立看门狗，也可以在这里等它复位，实现「自动重试」 */
}
HAL 帮你挡住的两个坑

① HAL_RCC_ClockConfig() 会在切 SW 之前先把 FLASH_ACR.LATENCY 设成你传的那一档——顺序和上面寄存器版一致。你要是自己写而忘了这一步，就是那个「取指错误」的坑。

② HAL_RCC_OscConfig() 内部对每个 RDY 位都有超时，返回 HAL_TIMEOUT。所以你只要检查返回值，就自动获得了「晶振没起振不会卡死」这个保护。这就是为什么「检查返回值」不是一句客套话——它是 HAL 时代版的超时保护。

代码三：上电打印三个频率，不等就报警

这是整篇文章里最值得抄进你工程模板的一段代码：不到 100 行，却能挡掉后面 80% 的「玄学故障」。它的逻辑非常朴素——把寄存器算出来的真实频率，和你设计时写在纸上的预期值比一比；不相等就打印 FAIL、快闪 LED、停在报警状态。

先给串口的 printf 重定向（用寄存器直接写 USART1，不依赖 HAL 的 UART 驱动；如果你已经在用 HAL 的串口驱动，把 fputc 里的发送部分换成 HAL_UART_Transmit() 即可）：

#include "stm32f10x.h"
#include <stdio.h>

/* 按实际的 PCLK2 算 BRR，写死 0x271 只适用于 PCLK2 = 72MHz */
void uart1_init(uint32_t pclk2, uint32_t baud)
{
    RCC->APB2ENR |= RCC_APB2ENR_IOPAEN | RCC_APB2ENR_USART1EN;

    /* PA9 = TX，复用推挽输出 50MHz：CRH 的高 4 位 = 0xB */
    GPIOA->CRH &= ~(0xFUL << 4);
    GPIOA->CRH |=  (0xBUL << 4);
    /* PA10 = RX，浮空输入：CNF=01, MODE=00 → 0x4 */
    GPIOA->CRH &= ~(0xFUL << 8);
    GPIOA->CRH |=  (0x4UL << 8);

    /* 波特率：BRR = PCLK2 ÷ 波特率，整数部分在高 12 位、小数 4 位在低 4 位。
       这里用「四舍五入到 1/16」的写法，避免直接截断带来的偏差。 */
    USART1->BRR = (pclk2 + baud / 2) / baud;

    USART1->CR1 = USART_CR1_UE | USART_CR1_TE | USART_CR1_RE;
}

int fputc(int ch, FILE *f)
{
    while ((USART1->SR & USART_SR_TXE) == 0) { }   /* 等发送寄存器空 */
    USART1->DR = (uint8_t)ch;
    return ch;
}
重定向 printf 的三个常见坑

① Keil（ARMCC/AC5）需要勾选 Use MicroLIB，否则要自己实现 __use_no_semihosting 与 _sys_exit 等桩函数，否则程序会卡在未定义的信号量上。 ② 想打印浮点（比如频率的 MHz 小数）还要额外加 -u _printf_float；滑头的做法是全部用整数打印——频率本来就是整数赫兹，没必要用浮点，还省 Flash。 ③ 别在中断里 printf：它是阻塞式的（等 TXE），放在中断里会拖长中断时间、破坏时序。

/* ==========================================================================
 * clock_selfcheck.c —— 上电时钟自检
 * 用法：在 main() 里、初始化任何外设之前第一个调用：
 *          HAL_Init();                 // 先把 SysTick 配好，才能用 HAL_Delay
 *          clock_selfcheck();
 *       不一致时：打印 FAIL 明细 → LED 快闪 → 停在报警状态（不进主循环）
 * ========================================================================== */
#include "stm32f10x.h"
#include <stdio.h>

/* ------- 设计预期：改板子/改配置时只改这四处 ------- */
#define EXPECTED_SYSCLK   72000000UL
#define EXPECTED_HCLK     72000000UL
#define EXPECTED_PCLK1    36000000UL
#define EXPECTED_PCLK2    72000000UL
#define LED_GPIO_Port     GPIOB
#define LED_Pin           GPIO_PIN_0        /* 按你的板子改 */

/* ------- 内部小工具 ------- */
static uint32_t apb_presc(uint32_t ppre_bits)
{
    /* PPRE 编码：0xx=÷1, 100=÷2, 101=÷4, 110=÷8, 111=÷16
       注意 0xx（bit2=0）全是 ÷1，不能直接拿寄存器值当下标用 */
    static const uint8_t tbl[8] = {1, 1, 1, 1, 2, 4, 8, 16};
    return tbl[ppre_bits & 0x7UL];
}

static uint32_t get_tim_clk(uint32_t pclk, uint32_t ppre_bits)
{
    uint32_t presc = apb_presc(ppre_bits);
    /* ★ 核心规则：APB 预分频 = 1 → 定时器时钟 = PCLK
                   APB 预分频 ≠ 1 → 定时器时钟 = PCLK × 2  */
    return (presc == 1UL) ? pclk : (pclk * 2UL);
}

static void led_alarm_blink(uint8_t times)
{
    for (uint8_t n = 0; n < times; n++) {
        HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);
        HAL_Delay(80);
        HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);
        HAL_Delay(120);
    }
    HAL_Delay(600);        /* 组间长间隔，方便数次数 */
}

/* ------- 主自检函数：返回 0 = 通过，-1 = 失败（失败时不会返回，停在报警里） ------- */
int clock_selfcheck(void)
{
    uint32_t sysclk = HAL_RCC_GetSysClockFreq();
    uint32_t hclk   = HAL_RCC_GetHCLKFreq();
    uint32_t pclk1  = HAL_RCC_GetPCLK1Freq();
    uint32_t pclk2  = HAL_RCC_GetPCLK2Freq();

    uint32_t tim1_clk = get_tim_clk(pclk2, (RCC->CFGR >> 11) & 0x7UL);  /* APB2 */
    uint32_t tim2_clk = get_tim_clk(pclk1, (RCC->CFGR >> 8)  & 0x7UL);  /* APB1 */
    uint32_t adc_clk  = 0;                                   /* 下面按 ADCPRE 算 */

    /* ADC 分频在 RCC_CFGR.ADCPRE[15:14]：00=÷2, 01=÷4, 10=÷6, 11=÷8 */
    {
        static const uint8_t adc_tbl[4] = {2, 4, 6, 8};
        adc_clk = pclk2 / adc_tbl[(RCC->CFGR >> 14) & 0x3UL];
    }

    /* 波特率反算：BRR 里已经包含了「整数 + 小数/16」，直接除即可 */
    uint32_t baud = (USART1->BRR) ? (pclk2 / USART1->BRR) : 0;

    int ok = 1;
    printf("\r\n============ 时钟自检 ============\r\n");
    printf(" SYSCLK : %9lu Hz   预期 %9lu   %s\r\n",
           sysclk, EXPECTED_SYSCLK, (sysclk == EXPECTED_SYSCLK) ? "OK" : "FAIL");
    printf(" HCLK   : %9lu Hz   预期 %9lu   %s\r\n",
           hclk, EXPECTED_HCLK, (hclk == EXPECTED_HCLK) ? "OK" : "FAIL");
    printf(" PCLK1  : %9lu Hz   预期 %9lu   %s\r\n",
           pclk1, EXPECTED_PCLK1, (pclk1 == EXPECTED_PCLK1) ? "OK" : "FAIL");
    printf(" PCLK2  : %9lu Hz   预期 %9lu   %s\r\n",
           pclk2, EXPECTED_PCLK2, (pclk2 == EXPECTED_PCLK2) ? "OK" : "FAIL");
    printf(" TIM1   : %9lu Hz  (APB2, %s)\r\n", tim1_clk,
           (apb_presc((RCC->CFGR >> 11) & 0x7UL) == 1) ? "预分频=1, 不×2" : "预分频≠1, ×2");
    printf(" TIM2   : %9lu Hz  (APB1, %s)\r\n", tim2_clk,
           (apb_presc((RCC->CFGR >> 8) & 0x7UL) == 1) ? "预分频=1, 不×2" : "预分频≠1, ×2");
    printf(" ADC    : %9lu Hz  (上限 14MHz)\r\n", adc_clk);
    printf(" USART1 : BRR=0x%03lX → 实际 %lu bps\r\n", (uint32_t)USART1->BRR, baud);
    printf("=================================\r\n");

    if (sysclk != EXPECTED_SYSCLK) ok = 0;
    if (hclk   != EXPECTED_HCLK)   ok = 0;
    if (pclk1  != EXPECTED_PCLK1)  ok = 0;
    if (pclk2  != EXPECTED_PCLK2)  ok = 0;
    if (adc_clk > 14000000UL)      ok = 0;      /* 硬约束也要查 */
    if (tim2_clk != EXPECTED_SYSCLK) ok = 0;    /* 标准配置下 TIM2 应为 72MHz */

    if (!ok) {
        printf("\r\n[FAIL] 时钟与设计预期不符！\r\n");
        printf("  最可能的原因，按概率排序：\r\n");
        printf("   1) HSE 没起振，系统回退到 HSI 8MHz（查晶振、负载电容、焊接）\r\n");
        printf("   2) PLLMUL / PLLXTPRE 配错，PLL 输出不是 72MHz\r\n");
        printf("   3) HPRE/PPRE1/PPRE2 与设计不符\r\n");
        printf("   4) SW 写了但 SWS 没切过去（PLL 没锁上）\r\n");
        printf("  处理：停止进入主循环，LED 快闪报警，等待人工介入。\r\n");

        while (1) {
            led_alarm_blink(3);      /* 停在「看得见」的状态，而不是死循环 */
        }
    }
    printf("[PASS] 时钟正常，进入主循环。\r\n\r\n");
    return 0;
}
一个反直觉的用法：让「打印不出来」也成为一种诊断

这个自检函数依赖串口能读。但如果故障恰好是「串口乱码」呢——你看到的是一屏乱码，而不是这份漂亮的报告。这本身就是信息：

乱码 = 时钟自检报告的第 8 行（USART1 的 BRR）与当前的 PCLK2 不匹配。此时最有用的手段不是再调串口，而是掏出示波器量 MCO（下一小节）——它不依赖任何软件，能立刻告诉你真实的 SYSCLK。 如果你手上没有示波器，那就换个笨办法：把波特率降到 9600 甚至 1200 再试一遍——低波特率对时钟偏差的容忍度高得多，往往能让你把报告读出来。

把这个函数的返回值用起来

如果你不想「停下来」，也可以把 clock_selfcheck() 改成返回错误码，然后由上层决定策略，例如：时钟不对 → 关闭所有依赖精确时间的模块（PWM、ADC 连续采样、RTC 校准）→ 只保留一个 9600 的调试口 → 让设备进入「可服务」状态而不是彻底躺下。

这种「降级可用」的设计，比「出错就死给你看」更适合要交付的产品。关键不是选哪种策略，而是你必须在代码里显式地做出这个选择——不能让它默默降级然后假装一切正常。

代码四：把时钟输出到 PA8（MCO）

MCO 只有两个动作：把 PA8 配成复用推挽输出、选一路时钟送出去。但这两个动作各自都有一个「忘了就什么都没有」的前提——所以两版代码都写出来，你把它们对照着看。

/* ==========================================================================
 * 版本一：纯寄存器
 * mco_bits 取值（RCC_CFGR.MCO[2:0]）：
 *   RCC_CFGR_MCO_SYSCLK         100 → SYSCLK
 *   RCC_CFGR_MCO_HSI            101 → HSI
 *   RCC_CFGR_MCO_HSE            110 → HSE
 *   RCC_CFGR_MCO_PLLCLK_Div2    111 → PLL ÷ 2
 *   RCC_CFGR_MCO_LSI            010 → LSI
 *   RCC_CFGR_MCO_LSE            011 → LSE
 * ========================================================================== */
void mco_enable_reg(uint32_t mco_bits)
{
    RCC->APB2ENR |= RCC_APB2ENR_IOPAEN;      /* ★ 前提一：GPIOA 时钟必须先开，
                                                否则下面两行「写了没反应」 */
    GPIOA->CRH &= ~(0xFUL << 0);             /* 清 PA8 的 4 个配置位 */
    GPIOA->CRH |=  (0xBUL << 0);              /* MODE8=11(输出 50MHz)
                                                CNF8 =10(复用推挽) → 0b1011 */
    RCC->CFGR &= ~RCC_CFGR_MCO;              /* 清 MCO[2:0] */
    RCC->CFGR |= mco_bits;                   /* ★ 前提二：选一路源，否则引脚无输出 */
}

/* ==========================================================================
 * 版本二：HAL
 * 注意 F1 的 HAL 里第三个参数（分频）是被忽略的 —— F1 的 MCO 没有分频器，
 *      只是为了函数签名统一才保留。F4/F7 上它才有用。
 * ========================================================================== */
void mco_enable_hal(uint32_t hal_source)     /* 例如 RCC_MCO1SOURCE_SYSCLK */
{
    GPIO_InitTypeDef GPIO_InitStruct = {0};

    __HAL_RCC_GPIOA_CLK_ENABLE();            /* ★ 同样先开时钟 */

    GPIO_InitStruct.Pin   = GPIO_PIN_8;
    GPIO_InitStruct.Mode  = GPIO_MODE_AF_PP;         /* 复用推挽 = CNF 10 */
    GPIO_InitStruct.Speed = GPIO_SPEED_FREQ_HIGH;    /* MODE 11 = 50MHz */
    HAL_GPIO_Init(GPIOA, &GPIO_InitStruct);

    /* 可选源：RCC_MCO1SOURCE_SYSCLK / _HSI / _HSE /
                RCC_MCO1SOURCE_PLLCLK_DIV2 / _LSI / _LSE */
    HAL_RCC_MCOConfig(RCC_MCO1, hal_source, RCC_MCODIV_1);
}

/* ---------- 典型用法：上电先输出 SYSCLK，量完再换 ---------- */
void mco_probe_demo(void)
{
    mco_enable_reg(RCC_CFGR_MCO_SYSCLK);     /* 先量总干路 */
    HAL_Delay(3000);                         /* 给示波器留 3 秒 */
    /* 这一步量到 72MHz → 源与 PLL 都没问题，可以往下查分频器了 */

    mco_enable_reg(RCC_CFGR_MCO_PLLCLK_Div2);/* 再量 PLL ÷ 2，应为 36MHz */
    HAL_Delay(3000);
}
没有示波器也能用 MCO

如果手边只有万用表：MCO 输出测不了频率，但能测到「约一半 VDD 的直流平均值」（方波的平均值 = 50% × 3.3V ≈ 1.65V）。这足以证明「这一路时钟在跑」，虽然量不出频率。

另一个土办法：把 MCO 输出接到一个 RC 低通 + 万用表——频率不同、平均电压几乎不变，所以意义不大。要么找个带频率档的万用表，要么借一台示波器；MCO 的价值就在于「硬件证据」，用软件手段替代它就失去意义了。

代码五：用定时器与 DWT 反推主频

示波器不总有。下面两段代码让你用「一块表」和「一块屏幕」也能把主频量出来。

/* ==========================================================================
 * 方法一：TIM4 每秒中断一次翻转 LED —— 用一块秒表反推定时器时钟
 * 硬件：任意一个 LED（这里用 PB0，按你的板子改）
 * 判读：见下方表格
 * ========================================================================== */
void tim4_1hz_init(void)
{
    RCC->APB2ENR |= RCC_APB2ENR_IOPBEN;      /* LED 在 PB0 */
    GPIOB->CRL &= ~(0xFUL << 0);
    GPIOB->CRL |=  (0x3UL << 0);              /* PB0 推挽输出 50MHz */

    RCC->APB1ENR |= RCC_APB1ENR_TIM4EN;      /* ★ TIM4 挂 APB1 */

    /* 按 TIM4CLK = 72MHz 计算：
       PSC = 7199 → 计数时钟 72MHz / 7200 = 10kHz
       ARR = 9999 → 更新频率 10kHz / 10000 = 1Hz（每秒中断一次） */
    TIM4->PSC  = 7199;
    TIM4->ARR  = 9999;
    TIM4->EGR  = TIM_EGR_UG;                 /* 产生一次更新事件，让 PSC 立即生效 */
    TIM4->SR   = 0;                          /* 清掉 UG 顺带置起的更新标志 */
    TIM4->DIER = TIM_DIER_UIE;               /* 允许更新中断 */
    TIM4->CR1  = TIM_CR1_CEN;                /* 启动计数 */
    NVIC_EnableIRQ(TIM4_IRQn);
}

void TIM4_IRQHandler(void)
{
    if (TIM4->SR & TIM_SR_UIF) {
        TIM4->SR = ~TIM_SR_UIF;              /* 写 0 清标志（rc_w0） */
        GPIOB->ODR ^= (1UL << 0);             /* 翻转 LED */
    }
}

/* 判读（用秒表量「亮一次 + 灭一次」共 10 个完整循环的总时间）：
 *
 *   量到 20 秒  → TIM4CLK = 72MHz，全部正确
 *   量到 40 秒  → TIM4CLK 只有 36MHz：PLL 输出不是 72MHz，
 *                或 PPRE1 被设成了 ÷4（PCLK1 = 18MHz，×2 = 36MHz）
 *   量到 160 秒 → TIM4CLK 只有 9MHz：PPRE1 是 ÷16 那一档
 *   量到 10 秒  → TIM4CLK 有 144MHz？不可能 —— 先检查你的计数口径，
 *                多半是把「亮 1 秒」当成了整个循环
 *   完全不闪    → TIM4 时钟没开（APB1ENR.TIM4EN）或中断没使能
 */
/* ==========================================================================
 * 方法二：用 DWT 的周期计数器（Cortex-M3 自带）测「每条指令花几个周期」
 * 前提：SystemCoreClock 已经更新为真实的 HCLK（否则换算出来的 ns 是错的）
 * ========================================================================== */
static void dwt_init(void)
{
    CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;   /* 打开跟踪与调试模块 */
    DWT->CYCCNT = 0;
    DWT->CTRL |= DWT_CTRL_CYCCNTENA_Msk;              /* 开始数周期 */
}

/* 返回 loops 次空循环总共花掉的 CPU 周期数 */
static uint32_t dwt_bench_nop(uint32_t loops)
{
    dwt_init();
    DWT->CYCCNT = 0;
    for (volatile uint32_t i = 0; i < loops; i++) {
        __NOP();
    }
    return DWT->CYCCNT;
}

void measure_cpu_speed(void)
{
    #define LOOPS 1000UL
    uint32_t cyc = dwt_bench_nop(LOOPS);
    uint32_t mhz = SystemCoreClock / 1000000UL;       /* 72 */

    /* 每个循环的纳秒数（整数运算，避免用浮点 printf） */
    uint32_t ns_per_loop = cyc * 1000UL / (LOOPS * mhz);
    /* 假设循环体编译后是 4 条指令（比较/自增/跳转/空操作）
       —— 按编译器实际生成的条数估算，别当精确值 */
    uint32_t cpi_x100 = cyc * 100UL / (LOOPS * 4UL);

    printf("DWT: %lu 个循环 = %lu 周期\r\n", LOOPS, cyc);
    printf("     每循环 %lu ns\r\n", ns_per_loop);
    printf("     每条指令 %lu.%02lu 个周期（假设每循环 4 条指令）\r\n",
           cpi_x100 / 100UL, cpi_x100 % 100UL);
    printf("     吞吐约 %lu MIPS\r\n",
           (mhz * 100UL) / (cpi_x100 ? cpi_x100 : 1UL));

    /* 正常值参考（72MHz / 2WS / 预取开）：
         每循环约 55 ~ 60ns，CPI 约 1.0 ~ 1.1（循环体内指令都是 16 位、连续取指）
         吞吐约 45 ~ 50 MIPS
       如果 CPI 明显大于 2：
         ① Flash 等待周期配少了 → 立刻查 FLASH_ACR.LATENCY
         ② 预取没开 → FLASH_ACR.PRFTBE 置 1
         ③ 优化等级太低、编译器生成了大量 32 位指令
       注意 CYCCNT 是 32 位：72MHz 下约 59.6 秒就回绕一次，
       所以测量时间必须远小于这个数（这也是要先算周期再除以循环数的原因）。 */
}
为什么 DWT 这招值得学

因为它把「性能」变成了一个可观测的数字。以后你改了一段算法想知道快了多少、想确认「编译器有没有把那层循环优化掉」、想验证「热点函数搬到 SRAM 有没有效果」，都可以用这几行代码得到答案，而不是靠感觉。

它和时钟的关系在于：同一个函数的周期数，在配错 Flash 等待周期时会直接翻倍。所以它也是一个隐蔽的「时钟配置验证器」——如果你发现所有代码都慢了一倍，先查 FLASH_ACR，再查时钟。

代码六：关掉不用的外设时钟，以及低功耗下的时钟处理

外设时钟是实打实的功耗。F103 在全速 72MHz 下，一个没关的 SPI、一个没用的 ADC 都能占掉几百微安到毫安级（具体数值请查你芯片数据手册的电流消耗表，各型号差别很大）。对于电池供电的设备，「忘了关时钟」是最常见也最容易修的功耗问题。

/* ==========================================================================
 * 关掉本工程用不到的外设时钟。
 * 原则：默认全关，用到哪个开哪个 —— 而不是默认全开，出问题了再关。
 * 用法：在时钟初始化之后、外设初始化之前调用；
 *       之后每个外设模块自己负责开自己的那一位。
 * ========================================================================== */
void clock_disable_unused(void)
{
    /* ---------------- APB1：本工程只用 TIM2 ---------------- */
    RCC->APB1ENR &= ~( RCC_APB1ENR_TIM3EN  | RCC_APB1ENR_TIM4EN  | RCC_APB1ENR_TIM5EN
                      | RCC_APB1ENR_TIM6EN  | RCC_APB1ENR_TIM7EN  | RCC_APB1ENR_TIM12EN
                      | RCC_APB1ENR_TIM13EN | RCC_APB1ENR_TIM14EN | RCC_APB1ENR_WWDGEN
                      | RCC_APB1ENR_SPI2EN  | RCC_APB1ENR_SPI3EN  | RCC_APB1ENR_USART2EN
                      | RCC_APB1ENR_USART3EN| RCC_APB1ENR_UART4EN  | RCC_APB1ENR_UART5EN
                      | RCC_APB1ENR_I2C1EN  | RCC_APB1ENR_I2C2EN  | RCC_APB1ENR_USBEN
                      | RCC_APB1ENR_CAN1EN  | RCC_APB1ENR_CAN2EN  | RCC_APB1ENR_DACEN );

    /* ★ 注意：不要顺手把 PWREN 和 BKPEN 关掉，如果你打算用 RTC 或改 PWR 寄存器：
       · PWREN = 0 → PWR->CR 写不进去（调压器/低功耗模式全都配不了）
       · BKPEN = 0 → 备份域寄存器（BKP_DRx）读写不了
       这两个缺了会以「寄存器写了没反应」的形式出现，非常难查。 */

    /* ---------------- APB2：本工程只用 GPIOA/GPIOB 与 USART1 ---------------- */
    RCC->APB2ENR &= ~( RCC_APB2ENR_IOPCEN | RCC_APB2ENR_IOPDEN | RCC_APB2ENR_IOPEEN
                      | RCC_APB2ENR_IOPFEN | RCC_APB2ENR_IOPGEN
                      | RCC_APB2ENR_ADC1EN | RCC_APB2ENR_ADC2EN | RCC_APB2ENR_ADC3EN
                      | RCC_APB2ENR_TIM1EN | RCC_APB2ENR_TIM8EN
                      | RCC_APB2ENR_TIM9EN | RCC_APB2ENR_TIM10EN| RCC_APB2ENR_TIM11EN
                      | RCC_APB2ENR_SPI1EN );
    /* ★ AFIOEN 也没关？对 —— 只要你还可能用到外部中断（EXTI）或引脚重映射，
       就必须保留它。这类「按需保留」的位，宁可多留一个，也不要事后拍脑袋查。 */

    /* ---------------- AHB ---------------- */
    RCC->AHBENR &= ~(RCC_AHBENR_DMA1EN | RCC_AHBENR_DMA2EN | RCC_AHBENR_CRCEN);
    /* ★ 两个绝对不能关的：
       · SRAMEN  —— 关了 SRAM 时钟，栈就没了，立刻 HardFault
       · FLITFEN —— 关了 Flash 接口时钟，取不到代码与常量，立刻跑飞 */
}

/* ==========================================================================
 * 低功耗：各时钟源在不同模式下的状态（按参考手册整理）
 *
 *   时钟源 │ Sleep（__WFI）  │ Stop            │ Standby
 *   ───────┼────────────────┼─────────────────┼──────────────────
 *   HSI    │ 运行           │ 停              │ 停
 *   HSE    │ 运行           │ 停              │ 停
 *   PLL    │ 运行           │ 停              │ 停
 *   LSI    │ 运行           │ 可保持（可选）  │ 可保持（RTC/IWDG）
 *   LSE    │ 运行           │ 可保持（可选）  │ 可保持（RTC）
 *
 *   ★ 关键结论：STOP / Standby 下高速时钟全停，只有 LSI/LSE 能继续跑
 *     —— 这正是「RTC 和独立看门狗在低功耗下还能工作」的原因，
 *        也是它们必须用 32.768kHz 晶振、不能用 HSI 的原因。
 * ========================================================================== */
void enter_stop_mode(void)
{
    RCC->APB1ENR |= RCC_APB1ENR_PWREN;       /* 先开 PWR 时钟，否则下面写不进去 */
    PWR->CR |= PWR_CR_LPDS;                  /* 深睡：调压器进低功耗（更省电） */
    PWR->CR &= ~PWR_CR_PDDS;                 /* PDDS = 0 → 选 STOP 而不是 Standby */
    PWR->CR |= PWR_CR_CWUF;                  /* 清唤醒标志 */
    SCB->SCR |= SCB_SCR_SLEEPDEEP_Msk;       /* ★ 让 WFI 进入「深睡」而不是普通 Sleep */

    /* 唤醒源：任意外部中断（EXTI）。注意 —— EXTI 的配置需要 AFIO 时钟，
       所以别在省电优化时把 AFIOEN 关掉。 */
    __WFI();

    /* ★★ 唤醒之后必做的一件事 ★★
       按参考手册，从 STOP 唤醒后系统时钟会回到 HSI，不再是你原来的 PLL 72MHz。
       如果这里不重新配置 PLL，就会出现「休眠前一切正常、唤醒后串口乱码 /
       定时器慢 9 倍」这种诡异故障 —— 而且它只在低功耗项目里出现，
       排查起来非常费时间。 */
    SystemClock_Config();                    /* 重新上一次 72MHz */

    /* 顺便：IWDG（独立看门狗）挂在 LSI 上，STOP 期间它继续计数！
       如果休眠时间可能超过看门狗超时，必须在休眠前喂狗、或改用
       窗口看门狗 / 定期唤醒喂狗的策略。（见 ee-pulse 里关于
       「看门狗时钟为什么必须独立」的讨论） */
}
省电优化最容易踩的两个坑

① 把「关时钟」当成「复位外设」。关掉外设时钟只是停止它的时钟供给，寄存器内容通常还在（取决于该外设的时钟域设计）。所以「关掉再打开」不等于「恢复出厂设置」——要复位请用 RCC_APBxRSTR 里的复位位。这个区别在调试串口/SPI 卡死时很关键：正确的复位顺序是「关时钟 → 置复位位 → 清复位位 → 开时钟 → 重新初始化」。

② 在中断里关时钟。如果某个外设正在产生中断，而你从别处关掉了它的时钟，中断标志不会被清除、中断会反复触发（或者外设行为未定义）。关时钟之前，先 NVIC_DisableIRQ() 并清掉挂起标志。

另外提醒一句：低功耗项目里，时钟配置的验证比普通项目更重要——因为你会反复切换频率和模式，任何一次切换后的状态都可能和上一次不同。这也是为什么下一节的自检函数值得放进你的工程模板：每次唤醒后都跑一遍。

常见错误与排查

下面十条，每一条都是一个真实的错误认知。我按「错误认知 → 为什么错 → 正确做法」写，你可以当成一份自查清单：如果某一条让你心里一虚，那一节就值得回去重读。

错误认知 1：「TIM2 挂在 APB1 上，PCLK1 = 36MHz，所以定时器时钟就是 36MHz」

为什么错：这是本篇最想纠正的一条。APB 预分频不等于 1 时，送给定时器的时钟是 PCLK × 2。漏掉这一步，所有定时时间会差一倍（PWM 频率差一倍、定时中断快一倍、延时短一半）。

正确做法：先看 RCC_CFGR.PPRE1[2:0]：是 0xx（÷1）就 TIMxCLK = PCLK1，否则 TIMxCLK = PCLK1 × 2。标准 72MHz 配置下它是 ÷2，所以 TIMxCLK = 36 × 2 = 72MHz——定时器和内核跑得一样快，这个结论请记牢。

错误认知 2：「既然 ≠1 时要 ×2，那我干脆把 APB1 设成 ÷1，让定时器更快」

为什么错：方向搞反了。÷1 时 PCLK1 直接等于 72MHz，违反 APB1 ≤ 36MHz 的硬约束；而定时器时钟此时是 PCLK1（不 ×2）= 72MHz——和 ÷2 时完全一样，一点没变快。

正确做法：×2 规则的作用是「让定时器在总线被分频之后保持不变慢」，不是给你超频用的。要改定时速度请改 PSC / ARR；APB 预分频就按上限来（APB1 = ÷2、APB2 = ÷1）。

错误认知 3：「72MHz 是标称值，我超到 96MHz 就更快；不行再降回来」

为什么错：不是「有风险」，而是物理上没有可用的等待周期档。2.7~3.6V 下 2WS 对应 ≤72MHz，而 LATENCY 只定义了 0/1/2 三档——超过 72MHz 之后，Flash 取指无法可靠完成，等于把「设计余量」当性能花掉了。它会以「常温能跑、加热后随机 HardFault」的形式报复你，而这类故障极难定位。

正确做法：守住 ≤72MHz。真需要性能，先按第 3 节例 5 的思路优化 CPI（减少分支、把热点搬 SRAM），而不是拉高频率。另外记住：如果 VDD 低于 2.7V，连 72MHz 都不允许——2.0~2.7V 区间 2WS 只能到 48MHz。

错误认知 4：「while(!(RCC->CR & RCC_CR_HSERDY)); 一行搞定，最简洁」

为什么错：这一行没有出路。晶振没起振（虚焊、负载电容不对、晶振坏、板子上没焊）时，程序会永远停在这里。看起来的现象是「板子完全没反应」——没有打印、没有 LED、连下载器都可能连不上，于是你把时间花在换下载器、重装驱动、怀疑工程配置上。

正确做法：每处「等待 RDY」都必须有超时判据（参考 HSE_STARTUP_TIMEOUT 的做法：计数 → 用尽 → 关源 → 降级 → 上报）。用 HAL 就检查 HAL_RCC_OscConfig() 的返回值，并把默认的 Error_Handler() 改成 LED 闪码或打印。

错误认知 5：「Flash 等待周期是性能选项，配少了只是慢一点」

为什么错：配少不是「慢」，是「错」。等待周期是「硬件答应你在这么多周期后才给数据」，你把等待周期设得比实际需要的小，Flash 就会在数据还没稳的时候就交出去——取指结果错误、跳转地址错误、变量读到脏数据，表现为「莫名跑飞」「程序走进不该进的 if」。

正确做法：严格按数据手册的 wait state 表设（3.3V：≤24MHz→0WS、≤48MHz→1WS、≤72MHz→2WS），并且在升频之前就设好；同时把预取打开（FLASH_ACR.PRFTBE = 1），它是 72MHz 能跑出性能的前提。

错误认知 6：「SW 写了就切过去了，还有什么好看的」

为什么错：SW 只是「你的意愿」，SWS 才是「实际状态」。如果 PLL 没锁上（比如 PLLMUL 超范围、PLLSRC 选了个没起振的源），硬件会拒绝切换，SW = 10 而 SWS 仍然是 00（HSI）。此时你的代码以为自己跑在 72MHz，实际跑在 8MHz——串口乱码、定时器慢 9 倍，而所有寄存器看起来都「配对了」。

正确做法：切完必须回读 SWS 确认，并且带超时（HAL 的 HAL_RCC_ClockConfig() 内部就是这么做的，所以返回值一定要检查）。调试时用 MCO 量 SYSCLK，一眼就能看出 SWS 到底切没切过去。

错误认知 7：「时钟在 main 里配一次就够了，之后它就一直是对的」

为什么错：有三种情况会打破这个假设：① 从 STOP/Standby 唤醒后，系统时钟会回到 HSI（不再是你的 PLL 72MHz），不重新配置就会出现「休眠前正常、唤醒后乱码」；② CSS 检测到 HSE 失效时会自动切到 HSI；③ 掉电/复位后从 HSI 重新起步。这三种情况都不是「出故障」，而是芯片的正常行为。

正确做法：把「配置时钟」写成一个可以反复调用的函数（如 SystemClock_Config()），并在每个可能改变时钟状态的事件之后调用一次：唤醒后、CSS 中断里、复位流程里。更稳的做法是让自检函数常驻——每次状态切换后跑一遍，频率不对就上报。

错误认知 8：「外设时钟使能位无所谓，CubeMX/库会帮我开」

为什么错：库确实会在初始化函数里帮你开它自己那个外设的时钟，但有两类位是「库不会帮你开，忘了就完全没反应」的：AFIOEN（配外部中断、引脚重映射、AFIO_MAPR 时必须先开）和 PWREN（改 PWR_CR、用低功耗模式、开备份域写保护 PWR_CR.DBP 时必须先开）。它们缺了的表现就是那句经典的「寄存器写了，但一点反应都没有」。

正确做法：养成「写某个寄存器之前，先确认它的时钟开了」的条件反射（第 2 节三张 ENR 位表就是给你查这个的）。排查「写了没反应」时，第一件事就是查 ENR，第二件事才是查位域写错没有。

错误认知 9：「ADC 采样不准是 ADC 的事，跟时钟没关系」

为什么错：ADC 的时钟来自 PCLK2 经过 ADCPRE 分频，上限 14MHz（F103）。PCLK2 = 72MHz 时只能选 ÷6（12MHz）或 ÷8（9MHz）；如果按印象选了 ÷4，得到 18MHz——超限运行会让采样结果偏小、不稳、随温度漂。另外 ADC 的「采样时间」是按 ADC 时钟周期数的，时钟不对，采样时间就不对。

正确做法：把 ADC 时钟算出来写进注释（PCLK2 ÷ ADCPRE = 12MHz），并在自检里核对它是否 ≤14MHz。第 3 节代码三的自检函数已经把这一项加进去了——这类「跨模块的硬约束」，只有写进自检才有机会被发现。

错误认知 10：「RTC 走时不准是 RTC 配置问题；MCO 是高级功能，我用不上」

为什么错（前半句）：RTC 走时不准最常见的原因是时钟源不对：LSE（32.768kHz 晶振）没起振，代码回退到 LSI（约 40kHz，且随温度和电压漂 ±50% 量级），一天能差出几十分钟。这时你改 RTC 的分频寄存器是白费力气——要去查 LSE 起没起振（先看 RCC_BDCR.LSERDY，再用 MCO 把 LSE 输出到 PA8 量一量）。

为什么错（后半句）：MCO 不是高级功能，它是唯一一个不依赖任何软件的时钟验证手段。整篇文章讲的都是「怎么配」，而 MCO 是「怎么证明你配对了」。一个引脚、两行代码，换来的排故效率远超它的成本。把它当成必备的调试外设，而不是选修内容。

正确做法：RTC/看门狗这类「低功耗下也要活着」的功能，时钟必须是 LSE/LSI；上电自检里加上「LSE 是否就绪」这一项，并在硬件设计阶段就给它配好负载电容与走线（见 《脉冲波形的产生与整形》 里的晶振排查清单）。

小结与自测

这一篇的内容量不小，但真正的「骨架」只有几句话。先把要点收一遍，再做题——做题时如果卡住，回到对应小节重读，比看答案有用得多。

要点清单

  1. 时钟是芯片的节拍器：所有波特率、定时、采样时间都是从它派生出来的。所以时钟错了，整个系统都错，而且错得「有规律」——通常成整数倍。
  2. 四个时钟源各有分工：HSI 8MHz（内部的、精度差、但一定起振，是救命通道）、HSE 4~16MHz 晶振（精度高，正常工作的主源）、LSI 约 40kHz（独立看门狗和 RTC 的备用源）、LSE 32.768kHz（RTC 的正牌源）。
  3. 一主一备是核心思想：所有配置流程都是「先试好源 → 失败退回坏源但一定能跑的源」；每一处等待都要有超时。
  4. PLL 算式：SYSCLK = 输入源 ÷ (PLLXTPRE+1) × PLLMUL；8MHz → ×9 = 72MHz，12MHz → ×6 = 72MHz，16MHz 要么 ÷2 再 ×9、要么只能到 64MHz。三条约束（输入 4~16MHz、输出 16~72MHz、SYSCLK ≤ 72MHz）必须同时成立。
  5. 标准 72MHz 分配：HCLK = 72MHz（HPRE ÷1）、PCLK1 = 36MHz（PPRE1 ÷2）、PCLK2 = 72MHz（PPRE2 ÷1）、ADC = 12MHz（ADCPRE ÷6）。
  6. 定时器时钟那条 ×2 规则：APB 预分频 = 1 → 定时器时钟 = PCLK；≠ 1 → 定时器时钟 = PCLK × 2。所以标准配置下所有定时器都是 72MHz。这是 PWM 频率算错的第一大原因。
  7. 寄存器三件套：RCC_CR 管源的开关与就绪，RCC_CFGR 管选择与分频（SW 写、SWS 读），三个 ENR 管每个外设的时钟使能。没有「默认开」的外设时钟。
  8. Flash 等待周期是硬约束：3.3V 下 0WS ≤24MHz、1WS ≤48MHz、2WS ≤72MHz；VDD 低于 2.7V 时上限还会下降。配错的后果是「取指错误、莫名跑飞」，不是「慢一点」。
  9. 切换顺序有讲究：升频前先设 Flash 等待周期、先设好各级分频；切 SW 之后必须回读 SWS；降回安全源并确认之后，才能关掉旧源。
  10. CubeMX 界面 ↔ 寄存器是一一对应的，它还是个很好的时钟计算器；但生成的时钟配置不要手改（会被覆盖、会破坏联动）。要改就回 CubeMX 改。
  11. 验证四招：MCO 输出到 PA8 用示波器量（硬件证据）、SysTick 已知延时反推、定时器 1 秒方波 + 秒表、打印三个频率（HAL_RCC_GetSysClockFreq/GetHCLKFreq/GetPCLK1Freq）。最该养成的习惯是最后一条——上电先打印三个频率。
  12. 外设时钟速查：GPIO 全在 APB2；USART1 在 APB2，USART2/3 在 APB1；TIM1/8 在 APB2，TIM2~7 在 APB1；ADC 在 APB2；DMA 在 AHB。关掉不用的外设时钟是最省事的省电手段。
  13. 低功耗下高速时钟全停：STOP/Standby 只保留 LSI/LSE；从 STOP 唤醒后系统时钟回到 HSI，必须重新配置 PLL——否则「唤醒后串口乱码」会来找你。
  14. 故障定位有一条捷径：先把本文第 3 节的「症状 → 原因」对照表过一遍。串口乱码 = 时钟假设与 BRR 错配；PWM 差一倍 = 漏了 ×2；程序完全不跑 = 卡在没有超时的 while 里；延时不准 = SysTick 时钟源或重载值不对；ADC 不稳 = ADCPRE 超限；RTC 走时不准 = LSE 没起振退回了 LSI。

自测题（先自己算，再看答案）

  1. 板上晶振 8MHz，请写出把 SYSCLK 配到 72MHz 所需的 PLLSRC、PLLXTPRE、PLLMUL 三个字段的取值，并说明为什么要校验三条约束。
  2. 某工程里 RCC->CFGR = 0x001D8402。请反查出它的 SYSCLK、HCLK、PCLK1、PCLK2 和 PLLMUL。
  3. TIM3 挂在 APB1 上，PPRE1 = ÷4（PCLK1 = 18MHz）。TIM3 的计数时钟是多少？要输出 2kHz PWM，PSC 与 ARR 怎么取（要求占空比分辨率不低于 0.1%）？
  4. 换成 12MHz 晶振，想跑 72MHz，PLLMUL 取几？如果误配成 ×5，SYSCLK 是多少、偏差多少？串口（BRR 按 72MHz 算死）会怎样？
  5. 系统供电 2.4V，你仍然把 SYSCLK 配成 72MHz、FLASH_ACR.LATENCY = 2。有什么问题？应该怎么改？
  6. MCO 配成 111（PLL ÷ 2），示波器量到 18MHz。请说明 PLL 的实际输出是多少，以及最可能的配置错误。
  7. 为什么 72MHz 下必须用 2 个 Flash 等待周期？而 2WS 又为什么对应「平均 1.5 个周期/指令」？
  8. 代码里写了 GPIOB->CRL |= 0x3; 想让 PB0 变推挽输出，但用万用表测 PB0 一直没反应。你第一时间查什么？为什么 AFIO 和 PWR 这两个时钟要单独记住？

参考答案

第 1 题：PLLSRC = 1（选 HSE）、PLLXTPRE = 0（8MHz 在 4~16MHz 内，不用除 2）、PLLMUL = 0111（×9，72 ÷ 8 = 9）。 校验三条约束是因为它们分别限制「PLL 的输入」「PLL 的输出」「系统的输出」，任何一条越界，硬件都可能拒绝锁定或工作不稳定——而且很多时候不会报错，只会「看起来能跑」。

第 2 题：按位拆开：SW = 10（PLL）、SWS 忽略、HPRE = 0000（÷1）、PPRE1 = 100（÷2）、PPRE2 = 000（÷1）、ADCPRE = 10（÷6）、PLLSRC = 1（HSE）、PLLXTPRE = 0、PLLMUL = 0111（×9）。于是 SYSCLK = 8 × 9 = 72MHz，HCLK = 72MHz，PCLK1 = 36MHz，PCLK2 = 72MHz，PLLMUL 为 ×9。

第 3 题：PPRE1 = ÷4 ≠ 1 → TIM3CLK = PCLK1 × 2 = 18 × 2 = 36MHz。 2kHz 要求 (PSC+1) × (ARR+1) = 36 000 000 ÷ 2000 = 18000；取 PSC = 17（÷18）、ARR = 999（÷1000），验算 36 000 000 ÷ (18 × 1000) = 2000Hz ✓，占空比分辨率 1/1000 = 0.1% ✓。（若取 PSC = 0，ARR = 17999 已经超过 16 位上限 65535 的一半但仍合法——不过分辨率与灵活性不如上面的组合。）

第 4 题：12MHz 在 4~16MHz 内，不用除 2，PLLMUL = 6（编码 0100），得到 72MHz。 误配 ×5 → SYSCLK = 60MHz，偏差 = (60 − 72) ÷ 72 = −16.7%。 串口：BRR 按 72MHz 写死（0x271），实际 PCLK2 = 60MHz → 实际波特率 = 60 000 000 ÷ 625 = 96 000 bps，偏差 −16.7%，远超容差 → 乱码。（如果 HAL_UART_Init() 在时钟配置之后调用、BRR 按实际 PCLK2 重算，串口反而是正常的。）

第 5 题：问题在于电压，而且这一档不是一个整体：2.4~2.7V 区间 2WS 只支持到 48MHz（0WS ≤16MHz、1WS ≤32MHz、2WS ≤48MHz），再低一档 2.0~2.4V 就只有 8/16/24MHz（0WS ≤8MHz、1WS ≤16MHz、2WS ≤24MHz）。跑 72MHz 属于取指时序不足，会出现随机的取指错误、跑飞、HardFault；而且这个区间没有更高的等待周期档可用。 正确做法：要么把 SYSCLK 降到 ≤48MHz（同时按实际频率下调 Flash 等待周期），要么把供电电压提到 2.7V 以上。另外降压时还要注意 PLL 与 Flash 的工作电压范围，别只看主频。

第 6 题：MCO 输出的是 PLL ÷ 2，量到 18MHz → PLL 实际输出 = 36MHz，而不是预期的 72MHz。 最可能的原因：PLLSRC 选成了 HSI/2（4MHz × 9 = 36MHz）——也就是 PLLSRC = 0，晶振根本没被用上。次可能：PLLXTPRE 被设成了 ÷2（8 ÷ 2 × 9 = 36MHz）。两种情况都用「读 RCC->CFGR 的 PLLSRC / PLLXTPRE 位」或「再用 MCO 量一次 HSE（应为 8MHz）」来区分。

第 7 题：因为 Flash 的访问时间跟不上 72MHz：一次取指需要 1 个访问周期 + LATENCY 个等待周期。72MHz 时必须 LATENCY = 2，于是一次 Flash 访问要 3 个 HCLK 周期；而 32 位的指令总线上一次能装下 2 条 16 位 Thumb 指令，所以 3 ÷ 2 = 1.5 个周期/指令（这是顺序执行 + 预取命中的理想值，分支密集时会变差）。

第 8 题：第一时间查 RCC_APB2ENR.IOPBEN 是否为 1——GPIOB 挂在 APB2 上，时钟没开的话对 GPIOB->CRL 的写操作根本不会落到寄存器里（读回来还是 0），现象就是「写了没反应」。 AFIO 和 PWR 要单独记住，是因为它们不属于「某个外设自己的时钟」，而是配置类功能的开关：AFIO 管外部中断线（EXTI）、引脚重映射、AFIO_MAPR；PWR 管 PWR_CR（低功耗模式、调压器）和备份域写保护 DBP（不开它，改 RCC_BDCR 配 RTC 会被静默拒绝）。这两类操作看起来和「时钟」没关系，所以最容易漏，而且在 CubeMX 工程里也常常需要手动补 __HAL_RCC_AFIO_CLK_ENABLE() / __HAL_RCC_PWR_CLK_ENABLE()。

练习（建议动手做一遍）

  1. 在你自己的板子上把 MCO 依次配成 100（SYSCLK）、110（HSE）、111（PLL ÷ 2），各量一次频率，并把量到的值与 HAL_RCC_GetSysClockFreq() 的打印值做成一张对照表。这张表以后就是你的排故基线。
  2. 把第 4 节代码三的 clock_selfcheck() 移植进一个能跑的工程，然后故意把 PLLMUL 从 ×9 改成 ×8，观察自检报告和 LED 报警；改回来再跑一次，记录两次输出的差异。这一步能让你真正体会「有自检」和「没自检」的差距。
  3. 用 DWT 那段代码测同一段空循环，在两种条件下各测一次：① 72MHz + FLASH_LATENCY_2 + 预取开；② 降到 24MHz + FLASH_LATENCY_0 + 预取开。解释两次测得的「每条指令周期数」为什么不同（提示：不同频率下 Flash 等待周期占的比例不同）。
  4. 做一个「晶振失效」实验：把 PLLXTPRE、或者干脆让 HSE 起不来（比如把晶振一脚悬空，注意别损坏板子），验证你代码里的 HSE 超时回退路径是否真的生效——并通过 LED 闪码或打印把「已降级到 HSI」这件事上报出来。如果程序卡死了，说明你的 while 还缺超时。
  5. 用 TIM4 输出 1Hz 更新中断翻转 LED，用秒表验证「10 个完整亮灭循环 = 20 秒」；然后把 PPRE1 从 ÷2 改成 ÷4，重新测量并解释时间为什么翻倍（提示：TIM4CLK 从 72MHz 变成 36MHz）。
