中断与异常机制

到这一篇为止，你写的每一行代码都是「从上到下、一条道走到黑」的：CPU 顺着你的指令一条条执行，什么时候查按键、什么时候读串口，全由你写在 while(1) 里的顺序决定。中断是这套规则唯一合法的例外——它允许一块外设电路在任意时刻打断 CPU，把程序拉到一个你事先写好的函数里去，办完事再原样放回来。这件事听起来只是「多了一种调用函数的方式」，实际上它是嵌入式与 PC 编程最根本的分野：所有实时性都从它来，所有「程序忽然跑飞」「串口莫名丢数据」「按键偶尔没反应」也从它来。这一篇要把这条链路从「外设置了一个标志位」一路讲到「ISR 返回后 PC 回到原处」，中间每一步是谁干的、Cortex-M 为什么会把内存错误一律变成 HardFault、优先级数字为什么越小越高、以及中断里到底哪些事绝对不能做，都说清楚。

为什么需要它

先说一件你大概已经踩过的事。

你在 51 上写过一个跑得好好的程序：主循环里查按键、读串口、刷新数码管，一秒钟循环几百次，什么问题都没有。换成 STM32 之后，你照着同样的结构写了一遍，结果三件事同时发生：

  • 上位机每 100ms 发一帧数据，你的程序五帧里能收到两帧，其余全丢，而且丢的位置毫无规律。
  • 按键按得快一点就没反应，按住不放倒是每次都能触发；换个便宜按键，情况又不一样。
  • 你只是在 while(1) 里加了一句 HAL_Delay(500) 让 LED 闪一下，串口就彻底收不到东西了。

这三个现象看起来互不相关，其实是同一个原因：你的程序是「同步执行」的——CPU 同一时刻只能待在一个地方。它在执行 HAL_Delay(500) 的那 500 毫秒里，物理上不可能同时去看串口寄存器；它在刷新数码管的那 3 毫秒里，物理上不可能同时去读按键引脚。外设不会等你。

你原本的解法是「把主循环跑快一点」：只要一圈足够快，就什么都不会漏。但主循环一圈的时间取决于里面最慢的那件事——只要有一件事要花 20ms，主循环一圈就至少 20ms，所有比 20ms 短的事件都有概率被漏掉。这就是轮询的天花板：你的响应速度被最慢的那个任务绑架了。

中断提供的是一条完全不同的路：不让 CPU 去问外设，而是让外设来叫 CPU。CPU 在没事的时候尽管去干慢活、甚至可以睡觉；一旦外设那边发生了变化，由硬件强行把 CPU 拽过来执行一小段专门的代码，办完再放回去。这段专门的代码叫中断服务函数（ISR，Interrupt Service Routine），而「拽过来」这个动作由芯片内部的电路完成，不需要你的程序配合。

这一节先把「轮询到底亏在哪里」用数字算清楚，你才知道后面那些复杂机制（优先级、嵌套、现场保护）是在为什么东西买单。

三个故障现场：把「为什么会漏」拆开看

逐个复盘开头那三个现象，你会发现每一个都能用「时间轴」解释清楚。

【场景】主循环里有 HAL_Delay(500) 闪灯，上位机每 100ms 发 8 个字节

时间轴（单位 ms）：
   0                      100     200     300     400     500
   │                       │       │       │       │       │
主循环：├── 闪灯：HAL_Delay(500) ─────────────────────────┤── 其他事 ──
上位机：        ▼       ▼       ▼       ▼       ▼
              发8字节  发8字节  发8字节  发8字节  发8字节
                │       │       │       │       │
                ✗       ✗       ✗       ✗       ▼
                                              第 5 帧被读到

【为什么】HAL_Delay 是「死等」，它把整个 CPU 锁在延时循环里 500ms。
          串口硬件其实把每一帧都收下来了（USART 的 DR 寄存器里确实有数据），
          但是：
            · 只有 1 个字节的接收寄存器（DR），第 2 个字节到达时
              第 1 个字节还没被读走 → ORE（溢出错误）标志置位 → 数据丢
            · 没有人在 500ms 内读 DR，所以除了每帧的第一个字节，其余全丢
            · ORE 置位后如果不软清除，后续接收会一直异常

【结论】轮询方式下，你的「读取速度」必须 ≥ 对端「发送速度」，
        而 HAL_Delay 把读取速度直接压到了 0。
【场景】主循环一圈 30ms（里面有 ADC 采样 + 数码管刷新），按键按下持续 5ms

主循环：│←──────── 一圈 30ms ────────→│←──────── 一圈 30ms ────────→│
          ↑ 查按键   ↑ 采样   ↑ 刷屏   ↑ 查按键   ↑ 采样   ↑ 刷屏
          t=0                        t=30                        t=60

按键：                          ├─5ms─┤
                                t=40  t=45（按下又松开）

        ↑ 下一次查按键发生在 t=60，此时按键早已松开
        → 这一次按下【完全丢失】，程序永远不会知道用户按过

【为什么会这样】采样定理的直觉版本：
   要保证不漏，查询间隔必须 小于 事件的最短持续时间。
   事件只持续 5ms，你 30ms 才看一次 —— 漏掉是必然的。

   注意这里有个反直觉的地方：
   按住不放（持续几百 ms）几乎不会被漏，因为总有一次查询会撞上；
   按得【快】才会漏。所以用户的描述是「按快了没反应」，
   而不是「按键坏了」。这个描述本身就是轮询的指纹。
【场景】你想在主循环里用 HAL_Delay(1) 累加出一个 1ms 时基

uint32_t tick = 0;
while (1) {
    HAL_Delay(1);        /* 你以为是「延时 1ms」 */
    tick++;              /* 你以为是「1ms 加一」 */
    do_everything_else();/* 但这一句也要花时间 */
}

【实际时间轴】
   │←─ 延时 1ms ─→│← 其他工作 0.4ms ─→│←─ 延时 1ms ─→│
   tick++          do_everything_else()  tick++

   真实的 tick 周期 = 1ms + 0.4ms + 循环开销 = 约 1.4ms，不是 1ms！
   跑一天（86400 秒）累积误差：
        86400 × (1.4 - 1.0) / 1.4 ≈ 24686 秒 ≈ 6.9 小时

【结论】「软件延时 + 累加」永远得不到准确的时间基准，
        因为延时函数管不住它后面的那句代码要跑多久。
        时间基准必须由一个【与主循环完全独立】的硬件来产生 ——
        这就是定时器中断存在的理由。
一句话总结这三个现场

它们不是三个 bug，而是同一个结构性缺陷的三种表现：同步执行把「什么时候处理事件」的决定权交给了主循环。主循环越忙，事件的响应就越晚、越不可靠。中断要做的事只有一件——把这个决定权从主循环手里拿走，交给硬件。硬件在任何时刻都可以打断 CPU，所以「响应时刻」不再受主循环影响。

轮询的代价：每秒 100 万次白干

讲到这里，很多人会有一个自然的反驳：「那我把轮询写快一点不就行了？反正 CPU 跑得快。」这个反驳值得认真算一笔账，因为算完之后你会看到轮询真正的成本在哪里。

取一个最朴素的例子：一个每 10ms 变化一次的按键。事件率 = 1 / 10ms = 100 次/秒。

要让它「不漏」，查询间隔必须小于事件的最短持续时间。问题在于，最短持续时间是多少？如果只考虑「人的手指按住」这个尺度，10ms 就是答案，1ms 查一次足够。但真实的按键不是理想开关：金属触点在闭合和断开的瞬间会弹跳，产生一串宽度可能只有几微秒的窄脉冲。如果你的程序声称「任何电平变化都要被捕获」，那么查询间隔必须压到 1µs——也就是每秒 100 万次查询。

【前提】STM32F103C8T6，系统时钟 72MHz（1 个周期 = 13.9ns）
        事件：按键每 10ms 变一次 → 100 次/秒
        要求：不漏任何一次电平变化（含 1µs 级的抖动窄脉冲）

【第一步：需要多快的查询频率？】
   查询间隔必须 ≤ 最短脉冲宽度 = 1µs
   → 查询频率 = 1 / 1µs = 1,000,000 次/秒（每秒 100 万次）

【第二步：一次查询本身要花多少周期？】
   最简版（读引脚 + 判断 + 跳转）：
       LDR   r1, [IDR]        ; 读 GPIOA->IDR，约 2 个周期（外设总线访问）
       ANDS  r1, r1, #0x01    ; 取 bit0，1 个周期
       BEQ   loop             ; 相等则跳回，1~3 个周期（取平均 2）
                              ; 循环回跳与流水线开销 1 个周期
       ─────────────────────────────────────
       合计 ≈ 6 个周期

   完整版（还要记录状态、更新时间戳、消抖判断）≈ 20 个周期

【第三步：CPU 占用】
   最简版：1,000,000 × 6  = 6,000,000  周期/秒
           6,000,000 / 72,000,000 = 8.33%   ← 只用掉 8.3%
   完整版：1,000,000 × 20 = 20,000,000 周期/秒
           20,000,000 / 72,000,000 = 27.8%  ← 用掉超过四分之一

【第四步：这些周期里有多少是「有用功」？】
   每秒 1,000,000 次查询中，真正撞上事件的只有 100 次
   → 有效查询占比 = 100 / 1,000,000 = 0.01%
   → 白干的查询占比 = 99.99%

   ★ 也就是说：CPU 每烧掉 27.8% 的时间，只为了处理 100 次/秒的事件，
     其中 99.99% 的查询得到的答案是「什么都没发生」。

这里必须补一句公道话，否则这笔账就成了稻草人：现实工程里没有人会真的用 1µs 去轮询按键。正常的做法是 1ms 查一次（1000 次/秒），开销立刻降到 1000 × 20 = 20000 周期/秒 = 0.028%，几乎可以忽略。所以「轮询费 CPU」这个说法其实是站不住的——轮询真正的代价不是 CPU 占用，而是它把「响应及时性」和「主循环的进度」焊死在了一起：

对比项轮询（1ms 查一次）中断
CPU 占用（100Hz 事件） 0.028% 0.009%
最快响应时间 最坏 = 一轮主循环的时间（可能 30ms） 典型 0.2µs 级（十几个周期）
响应时间由什么决定 由主循环里最慢的那件事决定 由优先级决定，与外设何时来数据无关
能不能漏事件 能，凡短于查询间隔的脉冲一律丢 不会，硬件的挂起位会把请求锁存住
CPU 能不能睡觉 不能，必须一直转着查 能，进 WFI 省电，事件来了自动醒
新增一个外设的成本 主循环多一份查询，一圈时间变长，所有响应一起变慢 几乎为零，互不干扰（只要有优先级用）
最怕什么 主循环里有任何耗时操作 ISR 写太长、共享数据没保护
那什么时候还是该用轮询？

别把中断当成万能药。以下三种情况，老老实实轮询反而更好：

  • 事件本身就是慢的、且不紧急：比如每 500ms 读一次温度传感器，用定时器轮询比中断干净得多。
  • 有强烈的抖动或噪声：一个机械按键进中断，抖动会产生几十次中断；用 10ms 定时器扫描反而简单可靠。
  • 需要一批数据凑齐了再统一处理：比如 LCD 刷新，逐条进中断反而零碎，攒够了再一次性刷更省事。

判断标准很简单：「这件事必须在某个时间窗内被响应吗？」必须 → 中断；不必须 → 怎么简单怎么来。工业上最常见的组合是「定时器中断扫描 + 主循环处理」：定时器每 1ms 或 10ms 打断一次去做统一采样，主循环专心处理这些已经采好的数据。

最后说清中断的代价——这一段比前面那些好处重要得多，因为好处是白送的，代价是要还的：

  • 时间不再是顺序的。在轮询里，「读按键」这句话在第 3 行执行，那它就一定在「刷屏」之前发生。有了中断之后，第 3 行可能执行到一半就被打断，回来的时候世界已经变了。你写代码时脑子里那条时间线，从此只是无数种可能顺序中的一种。
  • 数据一致性成了新问题。ISR 和主循环同时碰一个变量时，「读—改—写」这三步可能被切开，出现「丢更新」「读到半个数据」。这件事在轮询里根本不存在。
  • 编译器成了你的对手。编译器看不见中断，它会理直气壮地把你「主循环里没改过」的变量缓存在寄存器里，于是中断改了内存，主循环却永远读不到——这就是 volatile 存在的理由。
  • 调试变难。单步调试会不停被中断打断；在 ISR 里打断点会让其他中断超时；很多「只在全速运行时出现」的 bug 是被中断时序触发的。
  • 优先级成了一个必须设计的参数。51 只有两级，随便填都能跑；Cortex-M 有 16 级加子优先级，填错了会出现「高优先级中断永远收不到数据」这种极难查的问题。

后面第二节的每一个子节，本质上都在回答这些代价怎么办。

核心概念

这一节是整篇的骨架。八个部分按「是什么 → 硬件怎么做 → 软件怎么配 → 时间怎么算」的顺序展开：先把中断这件事本身定义清楚，再看一次中断从发生到返回的完整链条，然后逐个拆开链条上的四个关键零件（向量表、异常分类、NVIC 寄存器、优先级），最后看嵌套发生时时间是怎么花的、以及那 8 个寄存器是谁压的栈。

中断的本质与术语

先给一句可能有点刺耳的定义，但记住它能省掉后面很多困惑：

中断是什么

中断是一次由硬件发起、由硬件完成跳转、由硬件负责返回的函数调用。它的入口地址不写在你的 main() 里，而是写在芯片内部一张固定的地址表上；它的触发时机不由你决定，而由外设的电平或脉冲决定；它返回时 CPU 会原样回到被打算的那条指令上，你完全感觉不到（除了时间过去了）。

拆开看，这里有三个和普通函数调用根本不同的地方：

  • 发起者在代码之外。普通函数是你在某一行写下 foo() 才被调用；ISR 是被外设电路「叫」起来的，你的代码里没有任何一行写着要调用它。这也是为什么很多人第一次看到 ISR 会觉得「这函数谁调用的？」，答案是：硬件调用的。
  • 入口地址是查表得来的，不是写死的。普通函数调用时，编译器把地址直接编进 BL 指令；中断时，CPU 只知道「异常号是 6」，它必须去一张表里查第 6 项，才能知道该跳到哪。这张表就是向量表。
  • 被打断的那段代码不知情，也不受影响。CPU 会把被打断处需要的一切寄存器存到栈上，所以主循环里的 for 循环被中断打断一千次，它的循环变量、累加结果都不会错。代价是这 8 个寄存器必须由硬件来存——因为如果交给软件，编译器就不得不为每一行代码都假设「随时可能被切走」，那生成的代码会慢得没法看。

然后是术语。这几个词在数据手册和同学的口语里经常混着用，但它们的含义不一样，先对齐：

术语英文 / 手册写法含义与使用场合
中断源 interrupt source 能产生中断请求的那个硬件。可能是外设（USART1、TIM2、EXTI0），也可能是芯片内部模块（SysTick）。
中断请求 interrupt request / IRQ 中断源发出的那个「信号」。注意它只是一个电平或脉冲，本身不带任何数据。
挂起 pending 「请求已收到，但还没被执行」。挂起是一个可以被硬件置位、也可以被软件置位/清除的位，它存在的唯一意义是：请求不会因为你正忙就消失。
活动 active 「这个中断的 ISR 正在执行中」。同一个中断可以同时是活动 + 挂起（执行中又来了新请求）。活动与挂起是两个独立的位，别混。
中断服务函数 ISR / handler 中断发生时被执行的那段代码。在 STM32 标准库/HAL 里就是形如 void EXTI0_IRQHandler(void) 的函数。
向量 vector 表里的一项，本质是一个 4 字节的地址。说「取向量」就是「从表里读出这个地址」。
异常 exception ARM 官方术语，是上位概念：所有能打断正常执行流程的事件都叫异常，包括复位、HardFault、SVC 这些「不是外设引起」的。外设中断只是异常的一种。「异常号」和「中断号」是同一套编号。
抢占 preemption 高优先级中断打断正在执行的 ISR。只有抢占优先级能造成嵌套，子优先级不能（第 6 小节详述）。
嵌套 nesting ISR 里又进了 ISR，一层套一层。它由抢占自动产生，不需要你写任何代码。
尾链 tail-chaining 一个 ISR 刚结束、下一个挂起的中断立刻接上时，硬件把「出栈 + 再压栈」合并省掉，从一个 24 周期的过程压缩到 6 周期。

还有一个贯穿全篇的计时单位要先约定好。Cortex-M 的「进入中断要花 12 个周期」这类说法里的「周期」，指的是处理器时钟周期（CPU clock，STM32F103 最高 72MHz），不是总线周期、也不是纳秒。72MHz 下 1 个周期 = 1 / 72 000 000 s ≈ 13.9ns；反过来说 1µs ≈ 72 个周期。后面所有的算账都建立在这个换算上。

最后，一次中断要真的发生，必须同时满足三个条件。记住这三条，第 3 节后面的「中断不响应排查顺序」就是它的逐条展开：

  1. 中断源真的产生了一个请求（外设寄存器里的标志位置位，并且这个标志被允许传到 NVIC）。
  2. 这个中断在 NVIC 里被使能了（ISER 对应的那一位是 1）。
  3. 当前允许它执行——没有更高（或同等）抢占优先级的 ISR 正在跑，并且全局中断没有被 PRIMASK 关掉。

⑦「清标志」的位置有讲究，而且触发方式不同结论相反

脉冲/跳沿触发（EXTI 的上升沿/下降沿、USART 的 RXNE）：尽早清。因为「标志被清掉之后」才到来的新事件可以把标志重新置起来，退出时就会再进一次 ISR，一个都不丢。如果拖到最后才清，那么 ISR 执行期间到来的那个事件，它的标志会在你已经处理完之后被你亲手抹掉——丢事件。

电平触发（51 的 INT0 低电平触发就是典型）：不能只清标志，必须让中断源本身恢复。因为只要引脚还是低电平，标志立刻又被置起来，你会立刻再进一次 ISR，出不去——这不是「死循环忘了清标志」，而是「清了也没用」。

最稳的习惯：在 ISR 开头把外设标志读进一个局部变量（很多标志读一下就自动清了），确认它确实置位过，再处理。这样既不会丢事件，也不会因为「没置位也进中断」而误判。

为什么「没置位也会进中断」不是天方夜谭

两个原因：其一，多个中断源可能共用一条 IRQ 线（比如 EXTI15_10_IRQn 一条线管 EXTI10 到 EXTI15 六个源），进 ISR 后你必须自己逐个查 EXTI->PR 判断是谁触发的；其二，如果标志被别的地方提前清掉了（比如 DMA 把数据搬走了、或者另一个 ISR 清了共享的 USART 标志），NVIC 的挂起位可能还在，于是你进来时外设标志已经是 0。所以 ISR 的第一件事应该是「确认并清标志」，而不是「直接开始处理」。

向量表：异常号到处理函数地址的数组

第 ⑤ 步里硬件「查表」查的就是向量表。它的定义朴素到有点让人失望：

向量表的定义

向量表就是一个放在内存里的 32 位数组，下标是异常号，元素值是对应的处理函数地址。第 n 项的地址 = 表基址 + n × 4。每一项就叫一个向量（vector），因为它「指向」该跳去的地方。

因为每一项是 4 字节，所以「异常号 × 4」就是这一项相对表头的偏移。这个乘法关系值得记住，因为查问题时你经常要在「异常号」和「地址」之间来回换算。Cortex-M3 最多支持 16 个系统异常 + 240 个外设中断，所以表最多 256 项 × 4 = 1024 字节 = 1KB。

关于开头那两项，值得单独说清楚，因为它是「为什么向量表必须放在 Flash 起始处」这个问题的完整答案：

1

复位的那一刻，CPU 还不知道你的程序在哪

上电瞬间，Flash 里的代码对 CPU 来说只是一堆未知的字节。它需要一个永远固定、不需要任何配置就存在的约定，才能找到第一条指令。ARM 把这个约定定死为：复位时，从地址 0x00000000 读第 1 个字当作 MSP 的初值，从 0x00000004 读第 2 个字当作 PC 的初值。

2

所以表里的第 0 项不是函数，而是「栈顶地址」

0x20005000 不是一个代码地址，它是 SRAM 的最高地址 +1（F103C8T6 有 20KB SRAM，起始 0x20000000，所以栈顶初值是 0x20005000）。Cortex-M 的栈是向下生长的满栈：压栈时先减 SP 再写，所以初始 SP 指向「最后一个字节的上面一格」。这一项由链接脚本里的 _estack 符号自动填，你不需要手写。

3

第 1 项就是「复位向量」，也就是 Reset_Handler 的地址

CPU 从 0x00000004 读到这个地址后直接跳过去，执行启动文件里那段汇编：初始化 .data 段、清零 .bss 段、配好时钟，最后 BL main。从这一刻起才轮到你的 C 代码。「复位」在 ARM 的体系里就是一个异常号 1 的异常——这是理解向量表的第一把钥匙。

4

「0x00000000」在 STM32 上是一张「别名面具」

STM32F103 的 Flash 物理上从 0x08000000 开始，但复位后 CPU 从 0x00000000 取指。这两个地址能对上，是因为芯片内部的启动模式选择电路把 0x00000000 这一段「映射」到了 Flash（BOOT0 = 0）、系统存储器（BOOT0 = 1, BOOT1 = 0，也就是出厂 Bootloader）或 SRAM（BOOT0 = 1, BOOT1 = 1）。改变启动模式，本质就是改变「0x00000000 指向谁」。

到这里「为什么在 Flash 起始处」已经答完了：因为它必须在一个复位时就存在、地址固定、且不需要初始化的地方。SRAM 不行（上电时内容随机），外部存储器不行（还没配好总线）。

但接下来的问题是：如果真的永远钉死在 0x00000000，那 Bootloader 和 APP 就没法共存了——APP 的向量表不可能也放在开头。所以 Cortex-M 提供了一个后门：

VTOR：向量表偏移寄存器

项目内容
寄存器名SCB->VTOR（Vector Table Offset Register）
地址0xE000ED08
复位值0x00000000
有效位bit[31:7]，低 7 位（bit[6:0]）被硬件强制为 0
这个「低 7 位为 0」意味着表基址必须 128 字节对齐。因为表最多 256 项 × 4 字节 = 1024 字节，128 字节对齐其实远远不够松（ARM 的要求是表大小对齐，V7-M 里最小对齐就是 128 字节），但配置时你只要保证基址是 0x80 的整数倍就不会错。
谁可以改软件可写，通常在启动早期改一次，之后不再动

硬件取向量的公式因此完整版是：

向量地址 = VTOR[31:7] + 异常号 × 4

复位后 VTOR = 0，所以「向量地址 = 异常号 × 4」，正好落在 0x00000000 那张被映射到 Flash 的别名区里——这就是为什么单区程序（只有一个 APP、没有 Bootloader）什么都不用配也能跑中断。而一旦你的程序里出现了「Bootloader 把 APP 搬到 0x08004000 然后跳过去」这种结构，APP 就必须在 main 的最开头做这件事：

#include "stm32f1xx.h"

/* APP 区起始地址：0x08000000 起 16KB 留给 Bootloader */
#define APP_BASE_ADDR      (0x08000000UL + 0x4000UL)   /* = 0x08004000 */

int main(void)
{
    /* ---------------------------------------------------------------
     * 这一句必须在【任何中断被允许】之前执行。
     * 否则一旦来了中断，CPU 会去 VTOR 指向的旧表取向量，
     * 取出来的是 Bootloader 的 handler，你的 APP 就"活"不起来。
     * --------------------------------------------------------------- */
    SCB->VTOR = APP_BASE_ADDR;

    /* 等价写法（CMSIS 封装，效果完全一样，可读性更好）：
     *   NVIC_SetVectorTable(NVIC_VectTab_FLASH, 0x4000);
     * 第二个参数是【相对 0x08000000 的偏移】，不是绝对地址。
     */

    HAL_Init();           /* HAL_Init 内部会调 HAL_MspInit 配时钟树 */
    SystemClock_Config();
    /* ... 之后才可以初始化外设、使能中断 ... */

    while (1) { }
}

/* ---------------------------------------------------------------
 * 配套工作（缺一不可，少一个 APP 就跑不起来）：
 *
 * 1) 链接脚本 / Keil 的 IROM1 起始地址改成 0x08004000，长度相应减小
 *      Keil: Options for Target → Target → IROM1: Start 0x08004000
 *
 * 2) 中断向量表要真的在 0x08004000 处存在
 *      startup_stm32f103xb.s 里的 __Vectors 段会被链接到 IROM 起始处，
 *      所以改了 IROM1 起始地址，向量表自动就搬过去了。
 *
 * 3) Bootloader 跳转前必须做的事（见下面这段）
 * --------------------------------------------------------------- */

/* ------------------------- Bootloader 侧：跳转到 APP ------------------------- */
typedef void (*pFunction)(void);          /* 函数指针类型 */

void jump_to_app(uint32_t app_addr)
{
    uint32_t stack_top;
    uint32_t reset_vec;
    pFunction app_entry;

    /* ① 检查 APP 区第一个字是不是一个"像样的栈顶地址"
     *    （在 SRAM 范围内：0x20000000 ~ 0x20005000）—— 防止跳到空白区 */
    stack_top = *(volatile uint32_t *)app_addr;
    if ((stack_top & 0x2FFE0000UL) != 0x20000000UL) {
        return;                            /* APP 不存在或已损坏，直接返回 */
    }

    /* ② 关掉所有已使能的中断，防止跳转瞬间有中断打进来 */
    __disable_irq();

    /* ③ 把 SysTick 也关掉（它不属于 NVIC 的普通外设中断） */
    SysTick->CTRL = 0;
    SysTick->LOAD = 0;
    SysTick->VAL  = 0;

    /* ④ 清掉所有 NVIC 的使能与挂起位（32 个一组，F103 有 3 组有效） */
    for (int i = 0; i < 8; i++) {
        NVIC->ICER[i] = 0xFFFFFFFFUL;
        NVIC->ICPR[i] = 0xFFFFFFFFUL;
    }

    /* ⑤ 设置主栈指针为 APP 的栈顶（APP 的第一个字） */
    __set_MSP(stack_top);

    /* ⑥ 取复位向量（APP 的第二个字），跳过去 */
    reset_vec = *(volatile uint32_t *)(app_addr + 4U);
    app_entry = (pFunction)reset_vec;
    app_entry();

    /* 正常情况下永远不会执行到这里 */
    while (1) { }
}
VTOR 最常踩的两个坑
  • 忘了改 VTOR，只改了 Keil 的 IROM1 起始地址。现象非常迷惑人：程序能跑、串口能收发（因为那些是你主动调用的），但只要一开中断就跳回 Bootloader 的 handler，或者直接进 Default_Handler 里死循环。只要用了 Bootloader，就必须设 VTOR。
  • 把 VTOR 设成了 0x4000 这种「偏移」而不是绝对地址。VTOR 要的是绝对地址（0x08004000），而 CMSIS 的 NVIC_SetVectorTable(NVIC_VectTab_FLASH, 0x4000) 第二个参数才是偏移。NVIC_SetVectorTable 内部做的是 SCB->VTOR = base | offset，其中 NVIC_VectTab_FLASH = 0x08000000。两者别搞混。

Cortex-M 的异常分类：15 个系统异常与「故障升级」

ARM 把所有能打断程序的事件统称为异常，编号从 1 开始（异常号 0 不存在，因为 0 会让「异常号 × 4」和「向量表第 0 项 = 初始 MSP」撞车）。异常号 1~15 是 15 个系统异常，由 CPU 内核自己产生；异常号 16 起是外设中断，编号 IRQ0、IRQ1……（IRQn 从 0 开始，所以 异常号 = 16 + IRQn，这就是前面那个换算式）。

异常号IRQn名称什么时候被触发优先级
1—Reset 上电复位、按下 NRST、独立/窗口看门狗超时复位、NVIC_SystemReset() 软件复位。复位后从向量表第 1 项开始执行。 固定 −3（最高）
2—NMI 不可屏蔽中断。STM32F103 上由时钟安全系统 CSS 触发：HSE 外部晶振失效时自动切到 HSI 并报 NMI，用来在时钟故障时救急。 固定 −2
3−13HardFault 所有故障的兜底。三种情况会进来：① 某个 fault 的 handler 没使能，故障被「升级」；② 在某个 fault handler 里又出了 fault；③ 取向量时总线出错（VECTTBL）。 固定 −1
4−12MemManage MPU 保护违规：访问了 MPU 配置为「不可访问」的区域，或者违反特权/用户权限。F103 没有 MPU，所以这个异常在 F103 上实际不会由 MPU 触发。 可配
5−11BusFault 总线访问出错：访问了不存在或未映射的地址（如 0x60000000 空白区）、外设时钟没使能就去读它的寄存器（F1 上非常常见！）、写只读区域。 可配
6−10UsageFault 指令用法错误：执行未定义指令、非对齐访问（需 CCR.UNALIGN_TRP = 1 才报，默认不报）、除零（需 CCR.DIV_0_TRP = 1 才报，默认不报）、试图切入 ARM 状态。 可配
7~10—（保留） ARM 保留，向量表里填 0。不要往这里写东西。 —
11−5SVC 执行了 SVC #imm 指令。RTOS 的「系统调用」入口：用户任务通过它请求内核服务（创建任务、申请内存），imm 是服务号。 可配
12−4DebugMon 调试监视器异常，由调试器配置触发，用于「不停止 CPU 的断点」。平时用不到，保持默认即可。 可配
13—（保留） ARM 保留。 —
14−2PendSV 软件挂起：软件写 ICSR.PENDSVSET 就能「挂起」它，它会在所有高优先级中断都结束后才执行。RTOS 用它做任务上下文切换——故意设成最低优先级，保证切换不被别的中断打断。 可配
15−1SysTick 内核自带的 24 位递减计数器减到 0。HAL 用 1ms 周期做 HAL_Delay 的时基、RTOS 用它做调度节拍。 可配

表里「固定」三个字的含义是：Reset、NMI、HardFault 的优先级由硬件写死，不能改。Reset 最高（−3），NMI 次之（−2），HardFault 再次（−1）。注意这里是「负数越小越优先」的另一套编号体系，它和后面 NVIC 的 0~15 是两码事——ARM 故意把这三个放在「负优先级」里，保证任何可配置的优先级都比它们低。

「为什么我的程序永远进 HardFault」——故障升级

这是初学者遇到的最典型的困惑：明明看手册说「非对齐访问会触发 UsageFault」，明明写了一个空的 UsageFault_Handler，结果打断点一看，进的是 HardFault。原因是这几个 fault 的 handler 默认是关闭的：

【硬件里的三个开关】SCB->SHCSR（System Handler Control and State Register，0xE000ED24）

    bit16  MEMFAULTENA   MemManage  handler 使能
    bit17  BUSFAULTENA   BusFault   handler 使能
    bit18  USGFAULTENA   UsageFault handler 使能

【复位值全部是 0 —— 也就是三个 handler 默认都是关闭的】

【升级规则】
  ┌─────────────────────────────────────────────────────────────┐
  │ 发生了 MemManage / BusFault / UsageFault 故障               │
  │        ↓                                                    │
  │ 对应的 xxxFAULTENA 位是 1 吗？                              │
  │        ├─ 是 → 正常进入对应的 fault handler                 │
  │        └─ 否 → ★ 升级（escalate）为 HardFault ★            │
  └─────────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────────┐
  │ 已经在一个 fault handler 里，又发生了任何 fault             │
  │        ↓                                                    │
  │      ★ 一律升级为 HardFault ★（防止故障处理程序自己出错）  │
  └─────────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────────┐
  │ 在 NMI 或 HardFault handler 里又发生了 fault                │
  │        ↓                                                    │
  │      ★ 进入 LOCKUP 状态 ★（芯片"锁死"）                    │
  │      表现为：程序完全停住，调试器也连接困难，                    │
  │      只能靠看门狗或复位恢复。                                   │
  └─────────────────────────────────────────────────────────────┘

【结论】只要你不主动打开这三个开关，所有内存/总线/用法错误
        都会以 HardFault 的形式出现。
        HardFault 不是"某一种错误"，它是"错误的集合"。
        想区分具体是什么错，要么打开开关分别建 handler，
        要么在 HardFault_Handler 里读 CFSR 寄存器（见第 4 节）。

打开这三个开关的标准写法：

#include "stm32f1xx.h"

/* 在 main 的最开头、初始化外设之前调用 */
void fault_handlers_enable(void)
{
    /* ① 使能三个 fault handler，让它们不再升级成 HardFault */
    SCB->SHCSR |= SCB_SHCSR_MEMFAULTENA_Msk      /* bit16 */
               |  SCB_SHCSR_BUSFAULTENA_Msk      /* bit17 */
               |  SCB_SHCSR_USGFAULTENA_Msk;     /* bit18 */
    __DSB();   /* 数据同步屏障：确保写操作真正生效后再往下走 */

    /* ② 打开严格检查（可选，但强烈建议在开发阶段打开）
     *    CCR = Configuration and Control Register，地址 0xE000ED14
     *    bit4 DIV_0_TRP  = 1 → 整数除以 0 触发 UsageFault
     *    bit3 UNALIGN_TRP= 1 → 非对齐访问触发 UsageFault
     *
     *    默认这两个都是 0，也就是"除零返回 0、非对齐访问被硬件悄悄
     *    拆成两次对齐访问"——所以你写错了也不报错，直到某天
     *    换了个编译器优化等级，行为突然变了。
     */
    SCB->CCR |= SCB_CCR_DIV_0_TRP_Msk | SCB_CCR_UNALIGN_TRP_Msk;
    __DSB();
}

/* 然后把这四个 handler 从"死循环"改成"报错 + 记录" */
volatile uint32_t g_mmfsr, g_bfsr, g_ufsr, g_hfsr;

void MemManage_Handler(void)
{
    g_mmfsr = SCB->CFSR & 0xFFUL;          /* MMFAR = SCB->MMFAR 出错地址 */
    __disable_irq();
    while (1) { }                          /* 开发阶段停在这里，方便看变量 */
}

void BusFault_Handler(void)
{
    g_bfsr = (SCB->CFSR >> 8) & 0xFFUL;    /* BFAR = SCB->BFAR 出错地址 */
    __disable_irq();
    while (1) { }
}

void UsageFault_Handler(void)
{
    g_ufsr = (SCB->CFSR >> 16) & 0xFFUL;
    __disable_irq();
    while (1) { }
}

与故障有关的寄存器不多，记住下面这五个就够定位九成问题：

寄存器地址作用关键位
SHCSR0xE000ED24 系统异常的使能与活动状态 bit18/17/16 = USGFAULTENA / BUSFAULTENA / MEMFAULTENA
CFSR0xE000ED28 可配置故障状态寄存器，定位故障的主战场 bit[7:0] MMFSR、bit[15:8] BFSR、bit[23:16] UFSR
HFSR0xE000ED2C 硬故障状态 bit30 FORCED = 1 表示「是被升级上来的」，真正的错误在 CFSR 里；bit1 VECTTBL = 取向量时总线错误
MMFAR0xE000ED34 MemManage 出错地址（需 CFSR.MMARVALID 有效） 直接告诉你哪个地址惹的祸
BFAR0xE000ED38 BusFault 出错地址（需 CFSR.BFARVALID 有效） 访问了不存在的地址时，这里就是那个地址
F103 上「进 BusFault」的头号原因：外设时钟没开

STM32 的每个外设时钟默认是关闭的（为了省电），只有 RCC->APB2ENR / APB1ENR / AHBENR 里对应的位为 1，那个外设的寄存器才可访问。时钟没开就去读写它的寄存器，总线会返回错误 → BusFault。典型现场：你写了 GPIOA->ODR = 0x01; 但忘了 __HAL_RCC_GPIOA_CLK_ENABLE()，于是程序一跑到这句就进 fault。

用 HAL 库的人反而容易漏这件事：HAL_GPIO_Init() 自己不会开时钟，它需要你提前调 __HAL_RCC_GPIOx_CLK_ENABLE()。而 HAL 的 HAL_XXX_MspInit() 回调里就有这句——这就是为什么用 CubeMX 生成的工程里，时钟使能都藏在 MspInit 里。你一旦手写初始化而跳过 MspInit，就会踩这个坑。

NVIC 寄存器组：6 类寄存器管住所有中断

NVIC（Nested Vectored Interrupt Controller，嵌套向量中断控制器）是 Cortex-M 内核里的一个硬件模块，专门负责第 ③ 步那份工作：接收所有中断请求、比较优先级、决定谁先执行、产生嵌套。它不是外设，是内核的一部分——所以它的寄存器地址在所有 Cortex-M 芯片上都是同一套，从 0xE000E100 开始。

逐类说明，每一类都给出「怎么用裸寄存器操作」和「CMSIS 封装函数」两种写法——裸寄存器写法能让你看清硬件到底在干什么，CMSIS 写法是你实际写项目时该用的。

ISER / ICER：使能与除能

ISER 是「写 1 置位」的寄存器，写 0 没有任何作用——这是它和普通寄存器的最大区别，也是必须记住的：

#include "stm32f1xx.h"

/* ---------- 写法一：裸寄存器（能看清硬件） ---------- */
/* EXTI0_IRQn = 6，落在 ISER[0] 里，对应 bit6 */
NVIC->ISER[0] = (1UL << 6);        /* 使能 EXTI0：写 1 到 bit6 */
NVIC->ICER[0] = (1UL << 6);        /* 除能 EXTI0：写 1 到 bit6 */

/* ★ 常见错误：想除能却写 0 */
NVIC->ICER[0] = 0;                 /* 什么都没发生！中断还是使能的 */

/* ★ 常见错误：想"只改这一位"用了读-改-写 */
NVIC->ISER[0] |= (1UL << 6);       /* 危险！读回来的是【当前使能状态】，
                                    * 如果 bit6 已经是 1，读-改-写会把它
                                    * 又写一遍（无害）；但如果别的位也是 1，
                                    * 你等于把它们全部重新使能一遍。
                                    * ISER/ICER 就该直接 = ，不要 |= 。 */

/* 通用公式：IRQn 落在哪个寄存器、哪一位 */
#define NVIC_ISER_SET(IRQn)  (NVIC->ISER[(uint32_t)(IRQn) >> 5] = \
                              (uint32_t)(1UL << ((uint32_t)(IRQn) & 0x1F)))
#define NVIC_ICER_SET(IRQn)  (NVIC->ICER[(uint32_t)(IRQn) >> 5] = \
                              (uint32_t)(1UL << ((uint32_t)(IRQn) & 0x1F)))

/* ---------- 写法二：CMSIS（推荐） ---------- */
NVIC_EnableIRQ(EXTI0_IRQn);        /* 内部就是 NVIC->ISER[0] = ... */
NVIC_DisableIRQ(EXTI0_IRQn);

/* 读回使能状态：ISER 是可读的，读出来就是使能位 */
uint32_t enabled = (NVIC->ISER[0] >> 6) & 1UL;

ISPR / ICPR：挂起位的软件操作

这两个寄存器解决一个很实际的需求：「我想让某个中断现在就跑一次，但外设并没有真的产生请求」。ISPR 同样是写 1 有效。它有三种典型用法：

/* ---------- 用法 1：软件触发一次中断（调试/自检） ---------- */
/* 用途：不接任何外部电路，验证你的 ISR 和 NVIC 配置对不对 */
NVIC->ISPR[0] = (1UL << 6);        /* 手工把 EXTI0 挂起 */
/* 立刻会进 EXTI0_IRQHandler —— 但注意：
 * ISR 里那句"清挂起"清的是 EXTI->PR（外设标志），
 * 而 NVIC->ISPR 这一位是【进 ISR 时硬件自动清掉】的，
 * 所以不会死循环。（这正是"外设标志"与"NVIC 挂起位"是两件事的证明） */

NVIC_SetPendingIRQ(EXTI0_IRQn);    /* CMSIS 写法 */

/* ---------- 用法 2：清掉误挂起，防止上电就乱进中断 ---------- */
/* 现场：初始化外设时配置过程本身可能产生一次虚假请求，
 *       等你 NVIC_EnableIRQ 的那一刻，挂起位已经是 1 了，
 *       于是刚使能就立刻进一次 ISR，处理一个"并不存在"的事件。*/
NVIC_ClearPendingIRQ(EXTI0_IRQn);  /* CMSIS 写法 */

/* 标准初始化顺序：先清挂起，再使能 */
EXTI_ClearITPendingBit(EXTI_Line0);   /* ① 清外设标志 EXTI->PR */
NVIC_ClearPendingIRQ(EXTI0_IRQn);     /* ② 清 NVIC 挂起位 */
NVIC_EnableIRQ(EXTI0_IRQn);           /* ③ 最后才使能 —— 顺序别反 */

/* ---------- 用法 3：查询状态 ---------- */
if (NVIC_GetPendingIRQ(EXTI0_IRQn)) {  /* 读 ISPR 对应位 */
    /* 有请求还没被处理 */
}

/* ★ 注意：ISPR 也是"写 1 有效"，不能用 |= 读-改-写 */
NVIC->ISPR[0] |= (1UL << 6);   /* 不推荐：会把当前所有挂起的中断
                                 * 又全部重新置一遍 */

IABR：看谁正在跑

IABR 是只读的，它反映「此刻哪些中断的活动位是 1」，也就是「哪些 ISR 正在执行（或者已经被抢占但还没返回）」。两个最实用的场合：

/* 用法 1：在 HardFault 或意外复位后，判断"卡在哪个中断里"
 *        —— 排查"程序莫名卡死"的利器 */
void check_after_fault(void)
{
    /* IABR[0] 的 bit n 对应 IRQn = n；若某个位是 1，
     * 说明那个中断的活动位没被清掉，程序很可能就是死在它的 ISR 里 */
    for (int i = 0; i < 3; i++) {              /* F103 只有 43 个 IRQ */
        if (NVIC->IABR[i] != 0) {
            /* i == 0 时，bit 的位置就是 IRQn */
            volatile uint32_t stuck = NVIC->IABR[i];
            (void)stuck;
        }
    }
}

/* 用法 2：判断"当前是否在中断上下文中"（写驱动时非常有用） */
uint32_t in_isr(void)
{
    /* IPSR = 正在执行的异常号，0 表示在"线程模式"（主循环） */
    return (__get_IPSR() != 0U);
}

/* 更严格一点的判断：
 *   如果在 Handler 模式，且异常号不是 SysTick/PendSV，
 *   那基本可以确定是在普通外设中断里。 */
uint32_t get_current_exception(void)
{
    return __get_IPSR() & 0x1FFUL;   /* IPSR 低 9 位就是异常号 */
}

/* 用法 3：CMSIS 直接查某个中断是否活动 */
if (NVIC_GetActive(TIM2_IRQn)) {
    /* TIM2 的 ISR 正在执行（或已被更高优先级抢占） */
}
__get_IPSR() 是写驱动的必备工具

很多库函数会明确规定「只能在任务上下文调用，不能在中断里调用」（比如 FreeRTOS 的 xQueueSend 和 xQueueSendFromISR 是两套 API）。如果你不确定自己现在在哪种上下文里，用 __get_IPSR() 判断一下，比猜可靠得多。它读的是 IPSR 寄存器，不需要任何初始化，任何时候都能读。

IPR：优先级寄存器，每 8 位管一个中断

这是 NVIC 里结构最反直觉的一个寄存器组，必须单独强调：

  • 它是字节数组，不是 32 位数组。ISER[0] 是一个 32 位寄存器管 32 个中断，而 IPR[0] 只占一个字节，只管 1 个中断。IPR[0] 管 IRQ0，IPR[1] 管 IRQ1，依次类推，共 60 字节管 240 个中断。
  • 一个字节 8 位，但 STM32 只用高 4 位。所以优先级只有 16 级（0~15），低 4 位读出来是 0、写进去也没用（ARM 允许厂商只实现高位，STM32 全系列都是 4 位）。为什么要放在高位而不是低位？因为这样不同厂商的芯片（实现 3 位、4 位、8 位的）用同一份代码写优先级时，数值的相对大小关系不变，迁移时不用改代码。
  • 地址怎么算：0xE000E400 + IRQn。不是 0xE000E400 + IRQn × 4！这一条几乎每个人都会错一次。
/* ---------- 错误写法：当成 32 位数组 ---------- */
/* NVIC->IPR[6] = ... ;   ★ 错！IPR[6] 管的是 IRQ6 没错，但它是个字节，
 *                          而且编译器会按 uint32_t 指针访问，
 *                          等于一次写了 4 个中断的优先级！ */

/* ---------- 正确写法 1：CMSIS（推荐，永远不会错） ---------- */
/* 参数是【已经左移到高 4 位的值】，即 0x00, 0x10, 0x20 ... 0xF0 */
NVIC_SetPriority(EXTI0_IRQn, 5);              /* 优先级 5（占高 4 位 → 0x50）*/
uint32_t prio = NVIC_GetPriority(EXTI0_IRQn);  /* 读回来也是 0~15 */

/* ---------- 正确写法 2：裸寄存器 ---------- */
/* 方法 A：用 CMSIS 定义的字节数组下标访问 */
NVIC->IPR[6] = (uint8_t)(5U << 4);     /* EXTI0_IRQn = 6，优先级 5 */

/* 方法 B：自己算地址（理解硬件） */
#define NVIC_IPR_BYTE(IRQn)  (*(volatile uint8_t *)(0xE000E400UL + (uint32_t)(IRQn)))
NVIC_IPR_BYTE(6) = (uint8_t)(5U << 4);

/* ★ 验证一下：读 IPR[6] 应该得到 0x50（二进制 0101 0000）
 *   高 4 位 = 0101 = 5，低 4 位 = 0000（硬件不实现） */

/* ---------- 一个真实的坑 ---------- */
/* 你以为这两个是同一个东西： */
NVIC->IPR[6] = 5;      /* 写成了 0x05：高 4 位是 0000 → 优先级变成 0（最高！）*/
                       /* 你本意是"给你一个低优先级 5"，实际给了"最高优先级"，
                        * 于是这个中断开始抢占一切，包括 SysTick，
                        * 导致 HAL_Delay 永久卡死。 */
NVIC->IPR[6] = 5 << 4; /* 正确：0x50 */
系统异常的优先级不在 IPR 里

SysTick、PendSV、SVC、三个 fault 这些系统异常没有 IRQn 编号（CMSIS 里是负数），它们的优先级不在 0xE000E400 那块 IPR 里，而在 SCB 的 SHPR1/2/3 三个寄存器里（0xE000ED18 ~ 0xE000ED20）：SHPR1 管 MemManage/BusFault/UsageFault，SHPR2 管 SVCall，SHPR3 管 PendSV 和 SysTick。用 CMSIS 的 NVIC_SetPriority(SysTick_IRQn, 15) 时，函数内部会自动判断 IRQn 正负、去操作正确的寄存器——这就是该用 CMSIS 而不是裸寄存器的理由。

优先级机制：16 级、五种分组、抢占与子优先级

这一节是整篇最容易记反、也最容易配错的地方。把下面四件事按顺序记牢，优先级就不会再出问题。

第一件事：数值越小，优先级越高

这条规则和 51 正好相反，务必先记住

STM32（Cortex-M）：数值越小 = 优先级越高。优先级 0 是最高级，15 是最低级。
51 单片机：数值越大 = 优先级越高。IP 里写 1 是高优先级，写 0 是低优先级。

为什么 ARM 选了这个方向？因为 NVIC 内部做的是「无符号数值比较，小的赢」，这和「异常号小的先执行」是同一套逻辑，硬件实现最简单。而 8051 那边的 IP 寄存器每个位就是「高优先级使能位」，1 表示「升到高优先级」——它的语义是「开关」而不是「等级」，所以方向相反。从 51 转过来的人，这是第一个必踩的坑。

记忆口诀可以这样用：「零号老大」——优先级 0 最横，谁都得让着它。

第二件事：一个字节 8 位，但只实现高 4 位 → 只有 16 级

前面讲 IPR 时提过：每个中断的优先级占一个字节，但 STM32 只用高 4 位，低 4 位读出来是 0。所以实际可用的优先级只有 16 个值：0 ~ 15。

在寄存器里它长这样（以优先级 5 为例）：

bit:    7    6    5    4    3    2    1    0
      ┌────┬────┬────┬────┬────┬────┬────┬────┐
      │ 0  │ 1  │ 0  │ 1  │ 0  │ 0  │ 0  │ 0  │
      └────┴────┴────┴────┴────┴────┴────┴────┘
        └─────── 已实现 ───────┘└─ 未实现，读回恒为 0 ─┘
             高 4 位 = 0x5

    → 寄存器值 0x50，代表优先级 5
    → 你用 CMSIS 的 NVIC_SetPriority(irq, 5) 时，库函数帮你做了 "5 << 4"

【为什么 ARM 要把优先级放在【高位】而不是低位？】
   假设厂商 A 实现 8 位（支持 256 级），厂商 B 实现 4 位（16 级）。
   如果都放在低位：
        厂商 A 写优先级 5 → 0x05
        厂商 B 写优先级 5 → 0x05  （只用低 4 位）
        看起来一致，但比较时 A 的 0x05 与 B 的 0x05 地位不同
   放在高位后：
        厂商 A：优先级 5 → 0x50
        厂商 B：优先级 5 → 0x50
        "数值大小关系"在两种芯片上完全一致
    → 同一份代码换芯片不用改优先级数值。
    ★ 副作用：如果你直接操作寄存器，必须自己写 << 4。

第三件事：这 4 位怎么用？——优先级分组

如果 4 位只表示一个「等级」，那就只有 16 级，做不了「两层」的优先级语义。但实际工程里我们经常需要两种不同性质的优先关系：

  • 「谁可以打断谁」——这是硬关系。比如电机 PWM 的更新中断必须能打断串口接收中断。
  • 「谁先谁后」——这是软关系。比如串口接收和 ADC 采样优先级相同，都不可打断对方，但如果两个请求恰好同时到，先处理串口。

ARM 的解法是把这 4 位切成两段：高的一段叫抢占优先级（preemption priority，决定能不能打断），低的一段叫子优先级（subpriority，决定同时挂起时谁先执行）。切几刀由优先级分组（priority grouping）这个全局设置决定，写在 SCB->AIRCR 的 PRIGROUP[10:8] 里。

五种分组，一张表说清（STM32 全系列都是 4 位，所以下表是定论，不是估计）：

HAL 宏AIRCR
PRIGROUP		 抢占
位数		子优先级
位数		 抢占级数子级数 参数范围
(Preempt, Sub)		 典型用途
NVIC_PRIORITYGROUP_07 04 1（不能抢占）16 (0, 0~15) 完全不要嵌套，只排先后顺序
NVIC_PRIORITYGROUP_16 13 28 (0~1, 0~7) 只要一个「紧急 / 普通」的分界

HAL 库默认就是 GROUP_4

HAL_Init() 内部的第一件事就是 HAL_NVIC_SetPriorityGrouping(NVIC_PRIORITYGROUP_4)。所以只要你用的是 HAL，默认就是 4 位全给抢占、子优先级位数为 0。这意味着：

  • HAL_NVIC_SetPriority(irq, 3, 2) 里的那个 2（子优先级）会被完全丢弃，没有任何作用。
  • 任何两个抢占优先级不同的中断都能互相嵌套；抢占优先级相同的两个中断永远不会嵌套，只会依次执行（走尾链）。
  • 如果你在 CubeMX 里看到「Preemption Priority / Sub Priority」两栏，必须先在 NVIC 配置页确认分组，否则两栏的含义会跟你以为的不一样。

改分组的写法（必须在初始化阶段改，运行时不要动）：

/* ---------- 裸寄存器：理解 AIRCR 的写法 ---------- */
/* AIRCR = Application Interrupt and Reset Control Register, 0xE000ED0C
 *   bit[31:16] VECTKEY：必须写 0x05FA，否则整个写入被硬件忽略
 *   bit[10:8]  PRIGROUP：优先级分组
 * 这个 VECTKEY 机制是防止程序跑飞时误改内核配置。*/
#define SCB_AIRCR_VECTKEY   (0x05FAUL << 16)

SCB->AIRCR = SCB_AIRCR_VECTKEY | (5UL << 8);   /* PRIGROUP = 5 → GROUP_2 */

/* ---------- CMSIS / HAL：实际项目该这么写 ---------- */
HAL_NVIC_SetPriorityGrouping(NVIC_PRIORITYGROUP_2);   /* 2 位抢占 + 2 位子优先级 */

/* ---------- 设置优先级：HAL 会按当前分组自动编码 ---------- */
HAL_NVIC_SetPriority(EXTI0_IRQn,  1, 0);   /* 抢占 1，子 0 */
HAL_NVIC_SetPriority(USART1_IRQn, 1, 3);   /* 抢占 1，子 3 —— 不能抢占 EXTI0 */
HAL_NVIC_SetPriority(TIM2_IRQn,   0, 0);   /* 抢占 0 —— 能抢占上面两个 */

/* ---------- 编码过程（GROUP_2：2 位抢占 + 2 位子优先级） ----------
 *   抢占 = 1 (二进制 01)   子 = 3 (二进制 11)
 *   拼成 4 位：  01 11  = 0b0111
 *   左移 4 位放进 IPR 字节： 0b01110000 = 0x70
 *   于是 NVIC->IPR[6] == 0x70
 * ------------------------------------------------------------ */
uint8_t raw = NVIC->IPR[6];          /* 读出来验证：应该是 0x70 */
uint32_t pre = (raw >> 6) & 0x03UL;  /* 取最高 2 位 = 1 */
uint32_t sub = (raw >> 4) & 0x03UL;  /* 取次高 2 位 = 3 */

/* ---------- ★ 一个静默的坑：超出范围不是报错，是"静默截断" ---------- */
HAL_NVIC_SetPriority(TIM3_IRQn, 5, 0);   /* GROUP_2 下抢占只有 2 位 */
/* 期望：抢占 5。实际：5 & 0b11 = 1 → 抢占变成 1！
 * NVIC_EncodePriority 只是做位与掩码，不做范围检查，也不报错。
 * 结果：你以为 TIM3 是低优先级，实际它和 EXTI0 一样高。 */
/* 结论：设优先级之前，先确认当前分组的位数，参数别超范围。 */

第四件事：抢占与子优先级的差别（最关键的一条）

这一条被误解的次数最多，所以分成「抢占能做什么」「子优先级能做什么」「子优先级不能做什么」三段来讲。

设定：分组 = GROUP_2（2 位抢占 + 2 位子优先级）
     中断 A：抢占 1，子 0
     中断 B：抢占 1，子 3      ← 注意 A 与 B 抢占【相同】
     中断 C：抢占 0，子 0      ← C 抢占最高

   抢占优先级 = "能不能插队"（硬的，能打断别人）

为什么很多人坚信「子优先级能嵌套」

因为他们看到的现象是这样的：两个中断 A、B 抢占相同、A 的子优先级数值更小。测试时观察到「A 总是先执行」，就得出结论「A 抢占了 B」。但真正发生的是：请求几乎同时到达，NVIC 按子优先级排序，让 A 先执行——不是 A 打断了 B，而是 B 压根还没开始。

验证方法很简单：在 A 的 ISR 里加一句 HAL_Delay 或者一段明显的延时，然后在 B 的中断源上人为制造一个「A 已经开始执行之后」的请求。你会看到 B 老老实实等到 A 结束。要区分「先执行」和「打断」，唯一的标准是看时间轴有没有重叠。

最后，把优先级相关的三个「不要」列在这里，都是真实项目里出过事的：

  • 不要在运行时改优先级分组。分组是全局的，改一次会把你之前设的所有中断的优先级含义全部重解释一遍。而且正在执行的中断可能因此产生意料之外的行为。只在 main() 开头设一次。
  • 不要只改分组而忘了重新设优先级。从 GROUP_4 换到 GROUP_2 时，原来「抢占 8」这种值会变成「抢占 2、子 0」，你原来的设计意图全丢了。
  • 不要给所有中断都设优先级的数值 0。这样它们全都是最高优先级、互相不能抢占，看起来「跑得都很及时」，但实际上任何两个同时挂起的中断都没有确定的执行顺序，系统的时序变得不可预测。该排的序还是要排。

嵌套、尾链与中断延迟

前面反复出现「嵌套」「尾链」这两个词，现在把时间账算清楚。先明确一件事：

嵌套不需要你写任何代码，但它的前提是「抢占」

你不需要在 ISR 里写「保存现场 / 恢复现场 / 允许中断」之类的东西。硬件会自动压栈、自动判断优先级、自动恢复。你唯一要做的是把抢占优先级配成正确的层次关系，剩下的硬件全包了。这也是为什么「子优先级不能嵌套」这件事很重要——你没配抢占，嵌套就永远不会发生。

三个关键时间：进入 12 周期、退出 12 周期、尾链 6 周期

下面的周期数是 ARM 在 Cortex-M3 技术参考手册里给出的典型值（表 8-1「Exception timing」），前提是零等待态的存储器。真实芯片上还要加上 Flash / SRAM 的等待周期，后面会补这一段。

【基准】STM32F103C8T6，CPU 时钟 72MHz → 1 周期 = 13.89ns

① 进入异常（从"被允许执行"到 ISR 的第一条指令）
═══════════════════════════════════════════════════════════════════════
   压栈 8 个寄存器 ................. 8 周期   （每个寄存器 1 个周期）

   合计 ........................... 12 周期 = 166.7ns

   【不尾链时】：先退出，再进入
        12（退出）+ 12（进入） = 24 周期 = 333.3ns
   【尾链时】：跳过"出栈 8 + 再压栈 8"，只做取向量与流水线重填
        6 周期 = 83.3ns

   省下 18 周期 = 250ns（每次）

   ★ 什么情况会尾链？
     当前 ISR 结束、返回时，如果还有【能打断即将返回的那个上下文】的挂起中断，
     硬件就跳过出栈、直接取新向量执行。
     ★ 关键推论：同抢占优先级的挂起中断【也会走尾链】（连续执行但不嵌套），
       因为它们虽然打不断"跑在同一个优先级上的前一个 ISR"，
       但相对于被中断的主循环（背景优先级）来说，优先级是够的。

═══════════════════════════════════════════════════════════════════════
④ 迟到中断（late-arriving）
═══════════════════════════════════════════════════════════════════════
   情形：正在为中断 A 压栈（还没压完 / 还没取到 A 的向量），
         突然来了优先级更高的中断 B。
   硬件行为：直接改取 B 的向量，先执行 B，B 结束后【尾链】到 A。
   代价：**不再额外增加周期**（B 在 A 压栈完成前到达时）。
   意义：ARM 用这个机制证明了自己的诚意 —— 高优先级中断不会因为
         "硬件正在忙别的"而被推迟哪怕几个周期。
   ★ 如果 B 在 A 的向量取完后才到，就按普通抢占处理：
     等 A 的 ISR 执行到某个可打断点（一般就是第一条指令之后），
     再压栈、进入 B。

中断延迟的完整构成

「中断延迟」指的是从中断请求产生，到 ISR 第一条指令开始执行的这段时间。它不是那 12 个周期，那 12 个周期只是其中一段：

请求产生
   │
   ├─ ① 挂起位被置起 ──────────────────────── 约 1 个周期（组合逻辑）
   │
   ├─ ② NVIC 仲裁 + 等待当前指令执行完 ────── 0 ~ 12 个周期 ★ 不可忽略
   │      Cortex-M 是【指令边界】才响应中断的（不像某些架构可以中途插入）。
   │      最长的情况：正在执行 32 位除法（SDIV/UDIV，2~12 周期，此处取 12）
   │      或多寄存器加载 LDM（每多一个寄存器 +1 周期）。
   │      取平均，实际工程上按"半条指令"估比较合理。
   │
   ├─ ③ 硬件压栈 + 取向量 + 流水线重填 ───── 12 个周期
   │
   └─ ④ 存储器等待态 ─────────────────────── 0 ~ 若干周期
          ①SRAM 访问如果是零等待态，压栈就是 8 周期；
            若 SRAM 时钟低于内核时钟（F103 上 SRAM 与内核同频，没问题；
            某些低功耗芯片 SRAM 会降频），要相应加长。
          ②向量表放在 Flash 里，72MHz 下 F103 的 Flash 需要 2 个等待周期
            （FLASH_ACR.LATENCY = 2）。但 F103 有【预取缓冲区】，
            取向量若命中预取缓冲，仍是 1 个周期；未命中最多 3 个周期。
            ★ 把向量表搬到 SRAM 或用 ART 加速器（F4）能吃掉这一项。

【合计（典型值）】
   72MHz 下：约 12 ~ 20 个周期 ≈ 0.17 ~ 0.28µs
   ★ 业界常说的"STM32 中断响应是亚微秒级"，出处就是这里。

【对比：如果用"主循环轮询"】
   最坏情况 = 一整轮主循环的时间
   一轮 30ms → 响应延迟 30000µs
   ★ 差了 5 个数量级。这就是中断存在的意义。
延迟里有一项你可以控制：Flash 等待周期

第 ④ 项里的 Flash 等待周期是唯一能在软件层面优化掉的。两种做法：① 把向量表复制到 SRAM，然后改 VTOR 指过去——SRAM 零等待，取向量稳定 1 个周期；② 在 F4/F7 这类带 ART 加速器的芯片上打开指令缓存与预取。但在 72MHz 的 F103 上，这 1~2 个周期（约 28ns）不值得为它增加复杂度——先看看你的实时性要求是不是真的卡在这几十纳秒上。绝大多数项目卡住的地方是 ISR 写得太长，不是延迟太高。

现场保护：硬件压栈的 8 个寄存器

第 ④ 步那 8 个寄存器为什么偏偏是这 8 个？这个问题看起来是细节，实际上它是「为什么 ISR 可以写成普通 C 函数」的完整答案。

先看 ARM 的调用约定（AAPCS，ARM Architecture Procedure Call Standard）把寄存器分成两类的规定：

寄存器AAPCS 里的角色调用普通函数时谁负责保存中断时谁保存
R0参数 1 / 返回值调用者保存（caller-saved）
被调函数可以随意破坏它们，调用方如果还需要就得自己先存起来		硬件（自动压栈）
R1参数 2 / 返回值
R2参数 3
R3参数 4
R12IP，链接器临时寄存器
R4 ~ R11通用变量被调用者保存（callee-saved）
被调函数如果用到了，必须自己压栈、返回前恢复		编译器（在 ISR 序言里压）
R13SP 栈指针—硬件切换 / 由栈帧隐含
R14LR 链接寄存器调用者保存硬件（自动压栈）
R15PC 程序计数器—硬件（压入返回地址）
xPSR程序状态（含条件标志 N/Z/C/V/Q、IPSR 等）—硬件（不存的话主循环里的 if 判断会错）

所以硬件压栈的这 8 个，正好是「调用者保存」的那 6 个（R0~R3、R12、LR）加上 PC 和 xPSR。这个设计非常聪明：

  • 中断在语义上就是一次函数调用，只不过调用者是硬件。既然是调用，那么「调用者保存」的那批寄存器必须由发起方（硬件）负责——这和普通 BL 指令之前编译器要保存 R0~R3、R12 是同一个道理。
  • 而 R4~R11 是「被调用者保存」，本来就该由 ISR 自己负责。编译器为 EXTI0_IRQHandler 生成的序言里，如果函数体用到了 R4~R11 中的某几个，就会自动 PUSH {r4-r7, lr}。这部分不是不保存，而是「按需保存」。
  • PC 必须存：不然 ISR 返回时不知道该回哪。xPSR 也必须存：不然 ISR 里做的算术把标志位改了，主循环里那个 if (a > b) 的结果就错了。

把两段合起来看，一个 ISR 真正动用的栈空间是这样构成的：

【入口处，硬件自动压入的 32 字节（8 个寄存器 × 4 字节）】

        高地址  ┌──────────────┐ ← 压栈【前】的 SP（= 被打断处的 SP）
                │ xPSR         │  ← 存标志位和异常号
                │ PC           │  ← 返回地址（被打断处的【下一条】指令）
                │ LR           │
                │ R12          │
                │ R3           │
                │ R2           │
                │ R1           │
        低地址  │ R0           │ ← 压栈【后】的 SP = ISR 里看到的 SP
                └──────────────┘
                  ★ 共 32 字节，固定开销，一次中断必付

【接着，编译器为 ISR 生成的函数序言（按需）】

    void EXTI0_IRQHandler(void)
    {
        uint32_t a, b, c;      /* 如果这些变量被分配到 R4~R7 */
        ...
    }

    编译出来的开头可能是：
        PUSH  {r4, r5, r6, r7, lr}     ; ★ 多压 20 字节
        ...
        POP   {r4, r5, r6, r7, pc}     ; 注意最后弹到 PC，一次返回

    ★ 用了几个 R4~R11，就压几个。用得多，栈就吃得深。
    ★ 注意那条 POP {... , pc}：Cortex-M 允许把 LR 弹回 PC 直接返回，
      这是 ARM 的"返回指令优化"。

【所以单层中断的实际栈开销】

    32 字节（硬件） + 4 × n 字节（编译器，n = 用到的 R4~R11 个数）
                    + 局部变量（如果溢出到栈上）
                    + 调用子函数时的额外开销

    典型值：一个只改几个全局变量的 ISR ≈ 32 + 4×1 ~ 4×4 ≈ 36 ~ 48 字节

【嵌套时会怎样？】

    每一层嵌套都重新付一次这个账：
        主循环
          └─ ISR_A（优先级 3）   +32 字节（硬件）
               └─ ISR_B（优先级 2）+32 字节（硬件）
                    └─ ISR_C（优先级 1）+32 字节（硬件）

    3 层嵌套 ≈ 96 字节 + 各层 ISR 自己的局部变量

【★ 这就是"中断里嵌套太深会爆栈"的完整原因】
    · 每次嵌套至少 32 字节是【硬件强制】的，你省不掉
    · 如果每层 ISR 还有 100 字节的局部变量和子函数调用，3 层就是 400 字节
    · 而栈的总量是链接时才确定的（F103C8T6 上常见的是 1KB 或 1.5KB，
      由 startup 文件里的 Stack_Size 定义）
    · 栈一溢出，它会【悄悄】覆盖掉紧邻的全局变量区
      （栈在 SRAM 顶部向下生长，下面就是 .bss / .data）
      → 症状是"某个全局变量莫名变成随机值"，而不是干脆的崩溃
      → 这类 bug 极难查，因为破坏现场的人和受害者毫无关系
如果用了 RTOS，栈是两个：MSP 和 PSP

Cortex-M 有两个栈指针，硬件根据当前模式自动选用：

  • MSP（主栈指针）：复位后的默认栈，也是所有异常处理（包括所有 ISR）用的栈。
  • PSP（进程栈指针）：线程模式下可以用它，RTOS 用它给每个任务一份独立的栈。

这会带来一个很反直觉的后果：任务栈设得再小，也救不了「ISR 嵌套太深导致 MSP 栈溢出」这件事。在 FreeRTOS 里，configMINIMAL_STACK_SIZE 管的是任务栈（PSP），而 ISR 用的 MSP 栈大小由启动文件里的 Stack_Size 决定（CubeMX 生成的 FreeRTOS 工程里通常自动放大到 0x400）。排查栈溢出时，两个都要看。

硬件压栈还有一个细节值得知道：Cortex-M 压栈时用的是「双重压栈」（stack alignment + MSP/PSP 双写）。具体地说，进入异常时硬件会把 SP 同时压入 MSP 和 PSP（是的，两个栈指针都会保留同一份值），这样即使 ISR 里切换了栈指针，退出时也能正确恢复。这也是为什么「在 ISR 里改了 SP」这种事故在小芯片上通常不会立刻爆炸——硬件替你兜了一层。别依赖这个特性，但知道它存在能解释一些奇怪现象。

为什么 ISR 必须短：每一项都有具体的后果

讲完了栈的账，就能算清「ISR 为什么必须短」了。这不是风格问题，而是三条硬约束：

  1. ISR 在跑的时候，所有优先级更低的中断都在等。你的 ISR 每多跑 1µs，那些中断的响应就晚 1µs。这不是「稍微慢一点」，而是直接吃掉了别人的实时性预算。
  2. ISR 里拿不到「时间」。任何依赖时基的等待（HAL_Delay、osDelay、查 HAL_GetTick() 的循环）在中断里都可能永久卡住。
  3. ISR 和主循环共享一切资源，任何不可重入的操作（malloc、库函数里的静态缓冲区）都可能被切坏。

下面这张表把「不能在 ISR 里做的事」逐条列开，重点是最后一列「后果」——你必须能说出后果，才记得住这条规矩：

阻塞等待

把 HAL_Delay 死锁这件事彻底算清楚

假设你写了这样一个 ISR：

void EXTI0_IRQHandler(void)
{
    if (EXTI_GetITStatus(EXTI_Line0) != RESET) {
        HAL_GPIO_TogglePin(GPIOA, GPIO_PIN_5);
        HAL_Delay(100);           /* ★ 灾难在这里 */
        EXTI_ClearITPendingBit(EXTI_Line0);
    }
}

逐步分析：

  • HAL_Delay(100) 的内部实现是一个 while 循环，条件是「HAL_GetTick() 与起始 tick 的差是否达到 100」。
  • HAL_GetTick() 返回的就是全局变量 uwTick，而 uwTick 只在 SysTick 中断里被 uwTick++。
  • 你设的 EXTI0 抢占优先级假设是 1（HAL 里常见），SysTick 是 15。数值 1 < 15，所以 EXTI0 优先级更高，它执行时 SysTick 进不来。
  • 于是 uwTick 冻住了，HAL_GetTick() 永远返回同一个值，while 永远不退出。

而且这个死锁会锁住整个系统：EXTI0 的 ISR 不出来 → 它的活动位一直是 1 → 所有优先级低于它的中断（包括 SysTick）永远无法执行 → uwTick 永远不动。你会看到的现象是：程序没复位、LED 不闪、串口不收、按键没反应，但调试器挂上去能看到 PC 卡在 HAL_Delay 里面。如果你在 ISR 里真的需要一个准确的短延时，用 for 循环空转（并且注释清楚"这里约 X µs"），或者更好——重新设计，别延时。

动手算一遍

中断的所有参数——周期数、优先级、频率——都是可以算的。这一节五道题，全部围绕一个核心问题：我的 CPU 时间预算够不够，怎么分配才不出事。所有周期数按 ARM Cortex-M3 技术参考手册与 STM32F103 数据手册的典型值取，芯片统一按 72MHz、Flash 2 个等待周期。

算之前先备好这几个换算
  • 72MHz → 1 周期 = 1 / 72 000 000 s = 13.89ns
  • 反过来：1µs = 72 个周期；1ms = 72000 个周期
  • 中断进出固定开销（不含 ISR 主体）：12 + 12 = 24 周期 = 333ns
  • 尾链而不是完整返回时：进入那段只算 6 周期
  • CPU 占用率 = （每秒中断次数 × 每次中断总周期数）÷ 72 000 000

例题 1：10µs 一次的定时器中断，能吃多少 CPU，ISR 最多写几条指令

【题目】
  STM32F103C8T6，系统时钟 72MHz。
  用 TIM2 产生一个 10µs 周期的更新中断（也就是 100kHz 中断频率）。
  问：(1) 光中断进出本身占多少 CPU？
      (2) 如果希望这个中断总共不超过 CPU 的 20%，ISR 主体最多能执行多少周期？
      (3) 换算成指令数和 C 语句数大概是多少？

【第一步：每次中断之间的时间预算】
  中断周期 T = 10µs
  → 中断频率 f = 1 / 10µs = 100,000 次/秒 = 100kHz
  → 每次中断之间 CPU 能执行的周期数：
        72,000,000 / 100,000 = 720 个周期
  ★ 也就是说：每 720 个周期，你就必须"浪费"掉一部分给中断机制。

【第二步：纯进出开销】
  进入 12 周期 + 退出 12 周期 = 24 周期
  → 每秒消耗：100,000 × 24 = 2,400,000 周期/秒
  → CPU 占用：2,400,000 / 72,000,000 = 0.0333 = 3.33%
  ★ 结论：光是"进中断、出中断"这个动作，就固定吃掉 3.33%，
     哪怕 ISR 里一行代码都不写。这是硬成本。

【第三步：20% 预算下 ISR 主体能动用多少周期】
  允许的总预算：72,000,000 × 20% = 14,400,000 周期/秒
  减去进出开销：14,400,000 - 2,400,000 = 12,000,000 周期/秒
  分给每次中断：12,000,000 / 100,000 = 120 周期
  ★ 答案：ISR 主体最多 120 个周期。

【第四步：120 周期能写多少代码？】
  Cortex-M3 指令周期数（取典型值）：
      大部分数据处理指令（MOV/ADD/AND/CMP） ...... 1 周期
      LDR / STR（访问 SRAM） ..................... 2 周期
      访问外设寄存器（APB 外设，要过总线桥） ...... 2~4 周期
      条件跳转（预测成功 / 失败） ................ 1 / 3 周期
      乘法 MUL ................................... 1~2 周期
      除法 SDIV / UDIV ........................... 2~12 周期
  按加权平均 1.5 个周期/条汇编指令估算：
      120 / 1.5 = 80 条汇编指令
  C 语言与汇编的换算（-O0 约 5 条汇编/条语句，-O2 约 2~3 条）：
      -O0：80 / 5 ≈ 16 条 C 语句
      -O2：80 / 3 ≈ 26 条 C 语句
  ★ 答案：ISR 主体大概只能写 16 ~ 26 条 C 语句。

【第五步：如果不管这个预算，会发生什么？】
  假设你在 ISR 里调用了 HAL_GPIO_TogglePin 并顺手做了点判断，
  实测约 500 周期（很常见，HAL 的函数层层调用，光参数检查就几十条指令）：
      CPU 占用 = 100,000 × (24 + 500) / 72,000,000
               = 100,000 × 524 / 72,000,000
               = 52,400,000 / 72,000,000
               = 72.8%
  ★ 72.8% 的 CPU 花在一个本该只占 3% 的中断上，
    剩下的 27.2% 要跑主循环 + 其他所有中断 —— 系统基本瘫痪。

【工程结论】
  100kHz 的中断频率下，ISR 里只够做"读一个值 + 置一个标志"。
  任何需要判断、计算、访问外设的操作都必须挪到主循环里。
  ★ 这也是为什么高频控制环路（比如 20kHz 的电流环）通常
    直接在 ISR 里用裸寄存器写，而不是调 HAL 函数。

例题 2：同一个事件，轮询和中断各要多少 CPU

【题目】
  某个传感器每 10ms 输出一次有效数据（事件率 100 次/秒）。
  系统要求：从数据出现到被程序处理，最坏延迟不超过 200µs。
  硬件：STM32F103C8T6 @72MHz。
  问：轮询方案和中断方案各需要多少 CPU？哪个可行？

──────────────────────────────────────────────────────────────
【方案 A：轮询】
──────────────────────────────────────────────────────────────
  ① 查询间隔怎么定？
     要保证最坏延迟 ≤ 200µs，查询间隔必须 ≤ 200µs。
     取 200µs 作为间隔（再快就是浪费）：
        查询频率 = 1 / 200µs = 5,000 次/秒

  ② 一次查询的开销（读外设寄存器 + 判断 + 跳转）：
        读状态寄存器（APB 总线访问） ...... 3 周期
        测试标志位 ANDS .................... 1 周期
        条件跳转（未就绪，跳回） ........... 3 周期
        循环开销 ........................... 1 周期
        ─────────────────────────────────────────
        合计 ............................... 8 周期
     （如果要读数据、存缓冲、更新时间戳，完整处理约 20 周期，
       但那些只在真正有数据时才做，摊到 5000 次里可以忽略）

  ③ CPU 占用：
        5,000 × 8 = 40,000 周期/秒
        40,000 / 72,000,000 = 0.0556% ≈ 0.06%

  ④ ★ 致命问题：这个方案成立的前提是"主循环每 200µs 能回到查询点一次"
     —— 而这一条根本不成立！
        主循环里要刷数码管（3ms）、要算 PID（1ms）、要存 Flash（50ms）……
        一轮主循环可能要 55ms。
        → 最坏延迟变成 55ms，比要求的 200µs 超标 275 倍！
        → 轮询的 CPU 占用很低，但它【做不到】200µs 的响应保证。

  ★ 轮询方案的真实结论：CPU 占用 0.06%，但延迟不达标，方案不可行。

──────────────────────────────────────────────────────────────
【方案 B：中断】
──────────────────────────────────────────────────────────────
  ① 中断延迟（最坏）：
        当前指令执行完（最坏，比如正在做除法） .... 12 周期
        压栈 + 取向量 + 流水线重填 ............... 12 周期
        Flash 取向量未命中预取缓冲 ............... 2 周期
        ─────────────────────────────────────────────────
        合计 ..................................... 26 周期 = 0.36µs（不含中断源检测，另加 2~3 周期）
     ★ 0.36µs 远小于 200µs，而且【与主循环在干什么完全无关】。

  ② 一次中断的总开销（含 ISR 主体）：
        进入 + 退出 ............................. 24 周期
        ISR 主体（读数据、存缓冲、置标志、清标志） 60 周期
        ─────────────────────────────────────────────────
        合计 ..................................... 84 周期

  ③ CPU 占用：
        100 × 84 = 8,400 周期/秒
        8,400 / 72,000,000 = 0.0117% ≈ 0.012%

──────────────────────────────────────────────────────────────
【对比结论】
──────────────────────────────────────────────────────────────
  指标                    轮询（200µs 间隔）    中断
  ─────────────────────────────────────────────────────────
  CPU 占用                0.06%                 0.012%
  最坏响应延迟            55ms（被主循环绑架）   0.36µs
  是否满足 200µs 要求      ✗ 不满足              ✓ 满足，余量 555 倍
  主循环能不能加慢任务     不能，会拖垮延迟       能，延迟不受影响
  
  ★ 两点值得记住：
    1) CPU 占用谁高谁低【不是重点】——两个方案都低到可以忽略。
       真正的分野是【延迟能不能保证】。
    2) 中断方案的 CPU 占用还比轮询低 5 倍，因为它是"有事才干活"，
       而轮询是"没事也要天天问"。这就是事件驱动的价值。

例题 3：中断延迟加 ISR 执行时间，能不能满足硬实时截止时间

【题目】
  三相电机控制：PWM 载波 20kHz，每个 PWM 周期要采一次相电流并算完 PID。
  截止时间（deadline）：从中断请求产生到计算完成，必须在 15µs 内结束。
  否则下一个 PWM 周期开始时占空比还没更新，电流环就失控了。
  估算：ADC 启动 + 读取 2 路采样 + 定点 PID + 更新比较寄存器
        ≈ 400 个周期。
  问：(1) 单独看，满足吗？
      (2) 如果系统里还有 USB 中断（8µs）和串口中断（4µs），还满足吗？

──────────────────────────────────────────────────────────────
【第一步：中断延迟（最坏情况）】
  ① 当前指令执行完 ..................... 12 周期（最坏，如 SDIV 或长 LDM）
  ② 压栈 + 取向量 + 流水线重填 ......... 12 周期
  ③ Flash 取向量未命中 .................. 2 周期
  ────────────────────────────────────────────────
  中断延迟 = 26 周期 = 26 × 13.89ns = 361ns ≈ 0.36µs（不含中断源检测，另加 2~3 周期）

  ④ 再算 NVIC 仲裁本身：它是纯组合逻辑，与时钟同步，
     不额外占用周期（可以认为包含在 ① 的边沿对齐里）。

──────────────────────────────────────────────────────────────
【第二步：不带嵌套时的总时间】
  ISR 主体 400 周期 = 400 × 13.89ns = 5.56µs
  总时间 = 0.36 + 5.56 = 5.92µs
  截止时间 = 15µs
  余量 = 15 - 5.92 = 9.08µs  → 余量充足，✓ 满足
  时间轴：
    0µs        0.36µs                              5.92µs        15µs
    │ 请求     │ ISR 开始 ──────────────────────── │ 完成        │ 截止
    │←─ 延迟 ─→│←────────── ISR 执行 5.56µs ─────→│←─ 余量 9.08µs ─→│

──────────────────────────────────────────────────────────────
【第三步：加入两个更高优先级中断后】
  假设优先级配置成了：USB 抢占 0、串口抢占 1、电流环抢占 2
  （典型的"配错了"——很多人生怕 USB 丢包，把它设成最高）

  最坏情况：电流环 ISR 刚开始就被 USB 抢占，USB 执行完又被串口抢占
    ├─ 电流环延迟 .............................. 0.36µs
    │  （USB 恰好也在电流环请求之前挂起的话，还要加上它 8µs）
    ├─ USB ISR ..................... 8.00µs
    ├─ 串口 ISR .................... 4.00µs
    ├─ 电流环 ISR 主体 ............. 5.56µs
    ────────────────────────────────────────────────
    最坏合计 = 0.36 + 8 + 4 + 5.56 = 17.92µs
    ★ 17.92µs > 15µs  → ✗ 超标 19%，电流环失控！

  再考虑更坏的情况：USB 在电流环请求之前就已经开始执行，
  电流环还得等它 8µs 才能启动：
    最坏 = 8（等 USB 让出）+ 0.36 + 8（USB 又插一次）+ 4 + 5.56
         = 25.92µs  → ✗ 超标 73%

──────────────────────────────────────────────────────────────
【第四步：正确的优先级设计】
  原则：谁的截止时间最紧，谁的抢占优先级最高。
    电流环：截止 15µs、需要 6µs  → 抢占 0（最高）
    USB   ：截止 1ms 量级、需要 8µs → 抢占 1
    串口  ：截止 10ms 量级、需要 4µs → 抢占 2

  重新核算最坏情况（电流环最高，谁也抢不了它）：
    电流环自身 = 0.36 + 5.56 = 5.92µs  ✓ 满足
    电流环抢占 USB/串口时，它们的 ISR 被推迟 5.92µs：
        USB 最坏延迟 = 5.92 + 0.36 + 8 = 14.28µs  ✓ 远小于 1ms
        串口最坏延迟 = 5.92 + 0.36 + 4 = 10.28µs  ✓ 远小于 10ms

  ★ 结论：不是"把所有人都设成最高优先级"能解决问题，
    而是必须【算清楚每个人的截止时间和执行时间】再排队。

──────────────────────────────────────────────────────────────
【第五步：加一层保险 —— CPU 总占用核算】
  20kHz 电流环：20,000 × (26 + 400) = 8,520,000 周期/秒 = 11.8%
  USB（假设 1kHz 中断）：1,000 × (26 + 8µs×72=576) = 602,000 = 0.84%
  串口（假设 11,520 次/秒，见例题 5）：11,520 × 54 = 622,080 = 0.86%
  ────────────────────────────────────────────────
  合计 ≈ 13.5% CPU
  ★ 看起来很宽松，但要记得：这只是【平均占用】。
    真正决定成败的是【最坏情况下的时间叠加】，
    也就是前面第三步算的那种"三件事挤在一起"的场景。

例题 4：优先级分组下，两个中断能构成嵌套的组合有多少种

【题目】
  4 位优先级，五种分组。考虑两个中断 A 和 B（A、B 代表任意两个不同的中断源）。
  问：(1) 一共有多少种不同的优先级编码？
      (2) 其中"A 能抢占 B"（也就是能构成嵌套）的有序组合有多少种？
      (3) 为什么分组越"细"（抢占位越多），能嵌套的组合反而越多？

──────────────────────────────────────────────────────────────
【第一步：算总编码数 —— 五种分组都一样，都是 16】
  4 位优先级，无论怎么切，总的不同编码 = 2^4 = 16 种。
  ★ 分组不改变"总量"，只改变"这 16 种怎么解释"。

【第二步：以 GROUP_2（2 位抢占 + 2 位子优先级）为例逐类数】
  抢占取值范围：0~3（4 个值）
  子优先级取值范围：0~3（4 个值）
  编码总数 = 4 × 4 = 16 ✓

  两个中断 A、B 的有序对 = 16 × 16 = 256 种

  按抢占关系分三类：
   ┌─ 类型 ①：A 的抢占值 < B 的抢占值  → A 能抢占 B（可嵌套）
   │    抢占取值：A=0 时 B 有 3 种；A=1 时 B 有 2 种；
   │              A=2 时 B 有 1 种；A=3 时 B 有 0 种
   │              合计 3 + 2 + 1 + 0 = 6 种抢占组合
   │    子优先级任意：4 × 4 = 16 种
   │    → 6 × 16 = 96 种
   │
   ├─ 类型 ②：A 的抢占值 = B 的抢占值  → 不能嵌套（只能先后执行）
   │    抢占相同：4 种取值
   │    子优先级任意：16 种
   │    → 4 × 16 = 64 种
   │
   └─ 类型 ③：A 的抢占值 > B 的抢占值  → B 能抢占 A
       对称，也是 96 种

  校验：96 + 64 + 96 = 256 ✓

──────────────────────────────────────────────────────────────
【第三步：五种分组全部算一遍】
  通用公式：设抢占级数为 P、子优先级的取值数为 S（P × S 恒等于 16）
    能嵌套的有序对数 = C(P, 2) × S²
      （C(P,2) 是从 P 个抢占级里"选一个高的、一个低的"并有序排列）
    不能嵌套的对数 = P × S²

  分组      P     S    能嵌套       不能嵌套      校验
  ─────────────────────────────────────────────────────────
  GROUP_0   1     16   C(1,2)=0    1×256=256     256 ✓
  GROUP_1   2     8    C(2,2)=1    2×64=128      64+128=192
                       ×64=64                    +64=256 ✓
  GROUP_2   4     4    6×16=96     4×16=64       96+64+96=256 ✓
  GROUP_3   8     2    28×4=112    8×4=32        112+32+112=256 ✓
  GROUP_4   16    1    120×1=120   16×1=16       120+16+120=256 ✓
  ─────────────────────────────────────────────────────────
  （GROUP_1 / GROUP_3 的"能嵌套"和"反向"对称，各占一半）

──────────────────────────────────────────────────────────────
【第四步：这张表说明了什么】
  ① 抢占位越多 → "能嵌套的组合"越多：
        0 → 64 → 96 → 112 → 120
     因为抢占位越多，可区分的"等级层次"越细。
  ② 但代价是子优先级的区分能力越来越弱：
        16 → 8 → 4 → 2 → 1
     GROUP_4 下子优先级只剩 1 个值，等于完全没有子优先级。
  ③ 极端情况：
     GROUP_0：抢占值全是 0 → 【任何两个中断都不能嵌套】，
              只能用子优先级排先后。适合"完全不要嵌套"的场合。
     GROUP_4：子优先级全一样 → 【同时挂起时没有确定的先后】，
              只能靠抢占关系区分。适合"层次清晰、不需要排队"的场合。

【工程建议（按经验值）】
  · 中断数量少于 5 个、嵌套关系简单：GROUP_4，抢占值手排 0~5
  · 中断 5~10 个、需要"分组"感（比如通信类、采样类）：
    GROUP_2，用抢占分"紧急层次"，用子优先级排"同层次内的顺序"
  · 明确不要任何嵌套（希望所有 ISR 顺序执行，避免并发问题）：
    GROUP_0，全部用子优先级排序
  ★ 无论用哪种，都必须在 main() 开头设一次，然后写一张
    "中断名 → 抢占 → 子优先级"的表格贴在代码注释里。
    没有这张表，三个月后你自己也看不懂。

例题 5：115200 波特率下，逐字节接收中断到底有多忙

【题目】
  上位机通过 USART1 持续向 STM32 发送数据，波特率 115200，格式 8N1。
  问：(1) 逐字节接收中断（RXNE 中断）每秒触发多少次？
      (2) 这种方式的 CPU 占用是多少？
      (3) 如果换成"空闲中断 + DMA"接收 20 字节的定长帧，
          帧率 100 帧/秒，CPU 占用降到多少？

──────────────────────────────────────────────────────────────
【第一步：一个字节要传多少位？】
  8N1 的含义：8 位数据位、N 表示无校验、1 位停止位
  一个字符帧 = 1 位起始位 + 8 位数据位 + 0 位校验 + 1 位停止位
             = 10 位
  ★ 注意：是 10 位，不是 8 位。这个"1 + 8 + 1"是算串口时间的第一坑。

【第二步：波特率 → 字节速率】
  115200 bps 表示每秒传 115200 个【位】
  每字节 10 位 → 每秒字节数 = 115200 / 10 = 11,520 字节/秒
  → 每个字节耗时 = 1 / 11520 = 86.8µs

【第三步：中断频率】
  逐字节接收中断：每收到 1 个字节触发 1 次
  → 中断频率 = 11,520 次/秒（连续满速接收时）
  → 换算成"每毫秒"：11.52 次/ms
  ★ 也就是说：不管你有没有在处理别的事，每 86.8µs 就会被叫一次。

【第四步：一次 RXNE 中断的开销（裸寄存器版本）】
  进入（硬件压栈 + 取向量 + 流水线重填） ......... 12 周期
  ISR 主体：
      读 SR 判断错误标志（PE/FE/NE/ORE） ......... 3 周期
      读 DR（这一读就自动清了 RXNE） ............. 3 周期
      计算写指针下一位置 & 边界回绕 .............. 6 周期
      写入环形缓冲区 ............................. 3 周期
      更新写指针 ................................. 2 周期
      函数序言/尾声（PUSH/POP） .................. 4 周期
      ─────────────────────────────────────────────────
      主体合计 ................................... 21 周期
  退出（出栈 + 恢复） ............................. 12 周期
  ─────────────────────────────────────────────────────
  单次总计 ≈ 45 周期

  CPU 占用 = 11,520 × 45 / 72,000,000
           = 518,400 / 72,000,000
           = 0.72%

【第四步（补充）：如果用的是 HAL 库】
  HAL_UART_IRQHandler() 会依次检查 PE、FE、NE、ORE、IDLE、RXNE
  等等一堆标志位，还要做句柄状态机判断、调用回调函数，
  实测典型开销 150 ~ 300 周期（-O0 下更多）。
  按 250 周期算：
      单次总计 = 12 + 250 + 12 = 274 周期
      CPU 占用 = 11,520 × 274 / 72,000,000
               = 3,156,480 / 72,000,000
               = 4.38%
  ★ 0.72% → 4.38%，翻了 6 倍。这就是"库函数在中高频中断里很贵"的具体数。

【第五步：波特率提高会怎样？】
  最高能支持到多少？关键看"每字节时间"和"ISR 时间"的比值：
      裸寄存器版：ISR 45 周期 = 0.625µs
      字节时间必须 > ISR 时间，否则中断处理不过来（会丢字节）
      最坏情况：921600 bps → 92160 字节/秒 → 每字节 10.85µs
      占用 = 92,160 × 45 / 72,000,000 = 5.76%  → 裸寄存器还撑得住
      但 HAL 版 = 92,160 × 274 / 72,000,000 = 35.1% → 基本不可用
  ★ 所以高波特率下必须放弃逐字节中断，改用 DMA。

──────────────────────────────────────────────────────────────
【第六步：空闲中断 + DMA 方案】
  原理：DMA 负责"把每个字节从 DR 搬到内存"，不用 CPU 参与；
        只在【一帧结束、总线空闲 1 个字符时间】时产生一次 IDLE 中断。
  IDLE 中断频率 = 帧率 = 100 次/秒（不是 11,520 次/秒！）

  一次 IDLE 中断的处理（算帧长 + 置标志给主循环 + 重启 DMA）：
      进入 ........................................ 12 周期
      主体（读 NDTR 算长度、置标志、重装 DMA） ..... 约 200 周期
      退出 ........................................ 12 周期
      ─────────────────────────────────────────────────
      合计 ≈ 224 周期

  CPU 占用 = 100 × 224 / 72,000,000
           = 22,400 / 72,000,000
           = 0.031%

──────────────────────────────────────────────────────────────
【对比总表】
──────────────────────────────────────────────────────────────
  方案                        中断频率        每次开销    CPU 占用
  ────────────────────────────────────────────────────────────────
  逐字节中断（裸寄存器）      11,520 次/秒    45 周期     0.72%
  逐字节中断（HAL 库）        11,520 次/秒    274 周期    4.38%
  空闲中断 + DMA              100 次/秒       224 周期    0.031%
  ────────────────────────────────────────────────────────────────
  ★ 空闲中断 + DMA 的 CPU 占用比 HAL 的逐字节方案低 141 倍。
  ★ 更重要的还不是占用，而是：
     · 逐字节方案下，如果任何一个更高优先级 ISR 执行超过 86.8µs，
       就会丢字节（ORE 溢出）
     · DMA 方案下，即使主循环和所有中断都忙 1ms，
       数据也照样被 DMA 搬进内存，一个都不会丢
    → 这就是"用 DMA 换取时序上的松弛度"，比省 CPU 更值钱。

【补充：为什么不定长帧特别适合"空闲中断 + DMA"】
  定长帧：可以用 DMA 的"传输完成中断"（TC），精确知道收满了 N 个字节。
  不定长帧：你不知道对方会发几个字节，怎么办？
      · 逐字节中断 → 每字节都要打断 CPU，还要在软件里判断"帧头、帧尾"
      · 用超时定时器 → 需要额外的定时器资源，且超时值要试
      · ★ 空闲中断 → 利用 UART 协议本身的特性：
        一帧发完，总线上会保持空闲（高电平）至少 1 个字符时间，
        USART 硬件检测到这一点就置 IDLE 标志并产生中断。
        此时 DMA 的 NDTR 里还剩多少没搬，就能反推出这一帧有几个字节：
            接收长度 = 缓冲区大小 - DMA_GetCurrDataCounter()
        一次中断就把整帧拿到了，不依赖任何额外的定时器。
  ★ 这就是"不定长帧更适合空闲中断 + DMA"的完整理由。
五道题的共同结论
  1. 中断的固定开销（24 周期）在高频中断下会变成主要成本：100kHz 下光进出就吃 3.33%。
  2. 决定方案可行性的从来不是 CPU 占用，而是最坏情况下的响应时间。轮询的占用可以很低，但它给不出时间保证。
  3. 实时性核算必须按最坏情况叠加算，而不是按平均值算。平均值 13.5% 完全掩盖了"三件事撞在一起超标 73%"。
  4. 优先级分组的本质是在「能嵌套的层次数」和「同时排队的区分度」之间做权衡，不是越细越好。
  5. 凡是"高频、定长、批量"的数据搬运，先想 DMA；中断只用来处理事件，不用来搬运数据。

在单片机上的样子

前面三节讲的是机制，这一节全部是可编译的代码。先从你熟悉的 51 开始做对照——因为只有看清 51 的中断长什么样，你才知道 STM32 那套复杂度是在解决什么问题。

对照：51 的中断系统

51 单片机的中断系统可以用一句话概括：5 个中断源、2 个寄存器（IE / IP）、2 级优先级、入口地址写死在 ROM 开头。

【5 个中断源】

  中断号  名称        中断源                    请求标志   入口地址   优先级控制位
  ─────────────────────────────────────────────────────────────────────────────
    0     INT0      外部中断 0（P3.2 引脚）      IE0       0x0003     PX0
    1     T0        定时器/计数器 0             TF0       0x000B     PT0
    2     INT1      外部中断 1（P3.3 引脚）      IE1       0x0013     PX1
    3     T1        定时器/计数器 1             TF1       0x001B     PT1
    4     UART      串行口（收 / 发共用）        RI 或 TI  0x0023     PS
  ─────────────────────────────────────────────────────────────────────────────
  ★ 注意间隔：0x0003 → 0x000B 是 8 字节，0x000B → 0x0013 也是 8 字节。
    每个中断入口只有 8 字节空间！放不下几行代码，
    所以 51 的 ISR 通常第一句就是 LJMP 跳到真正的位置：
         ORG  0003H
         LJMP INT0_ISR      ; 8 字节刚好够一条 LJMP
  ★ 这就是"为什么 51 的 ISR 开头总要写 ORG"的原因。

【为什么只有 5 个？】
  因为 51 的架构最初就是这么设计的，外设也就这么几个。
  你要更多中断，得换 52 系列（多一个定时器 2，中断号 5，入口 0x002B）。

────────────────────────────────────────────────────────────────────────────
【IE 寄存器（0xA8，可位寻址）—— 中断使能】

  位:    7      6      5      4      3      2      1      0
      ┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐
      │  EA  │  —   │ ET2  │  ES  │ ET1  │ EX1  │ ET0  │ EX0  │
      └──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┘
         │             │      │      │      │      │      │
         │             │      │      │      │      │      └─ 外部中断0 使能
         │             │      │      │      │      └──────── 定时器0 使能
         │             │      │      │      └─────────────── 外部中断1 使能
         │             │      │      └────────────────────── 定时器1 使能
         │             │      └───────────────────────────── 串行口 使能
         │             └──────────────────────────────────── 定时器2 使能（52系列）
         └────────────────────────────────────────────────── 全局中断允许（总开关）

  ★ 两个层次：EA 是总开关，EX0/ET0/... 是分开关。
    必须【两个都是 1】才会响应。这就是"51 版的 NVIC 使能位"。

  典型初始化写法：
        MOV   IE, #10000001B      ; EA=1, EX0=1，其他全关
     或 C51 写法：
        IE = 0x81;                /* 或 EA = 1; EX0 = 1; */

【IP 寄存器（0xB8，可位寻址）—— 中断优先级】

  位:    7      6      5      4      3      2      1      0
      ┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐
      │  —   │  —   │ PT2  │  PS  │ PT1  │ PX1  │ PT0  │ PX0  │
      └──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┘

  ★ 方向与 STM32 相反：写 1 = 高优先级，写 0 = 低优先级（默认）。
  ★ 只有两级：高和低。
  ★ 同一级内的顺序由【自然优先级】决定，也就是中断号的顺序：
         INT0 > T0 > INT1 > T1 > UART
    （中断号小的自然优先级高，这和 STM32"数值小的优先级高"倒是同向的）

电平触发与跳沿触发是 51 外部中断的经典考点，也是「中断请求的撤销」这个概念的来源。控制它的是 TCON 寄存器里的 IT0 / IT1 两位：

IT0 / IT1触发方式请求标志 IE0 / IE1 怎么置位请求怎么撤销（关键）
0 低电平触发 CPU 在每个机器周期的 S5P2 时刻采样引脚，只要还是低电平就置位 IE0 = 1 硬件不会自动清！因为采样是电平敏感的——必须在 ISR 里让引脚本身恢复高电平（比如让外部电路撤掉信号，或者用一根 IO 去复位请求源）。只写 IE0 = 0 是没用的：引脚还是低电平，下一个机器周期立刻又置成 1 → 反复进中断
1 下降沿（跳沿）触发 采样到从高到低的跳变时置位 IE0 = 1，之后不管引脚保持多久都只置一次 硬件在进入中断服务程序时自动清 IE0。所以不会重复进中断，也不需要在 ISR 里清标志
各种中断源的标志位，谁清、怎么清，一张表记住
中断源标志位谁清说明
外部中断 0/1（跳沿触发）IE0 / IE1硬件自动进 ISR 时由硬件清 0
外部中断 0/1（电平触发）IE0 / IE1撤掉电平才行软件清标志无效
定时器 0/1TF0 / TF1硬件自动进 ISR 时自动清（这就是为什么定时器中断不用清标志）
串行口RI / TI必须软件清★ 最经典的考点：ISR 里一定要写 RI = 0; 或 TI = 0;，忘了就死循环

STM32 的情况正好反过来：绝大多数外设标志都要软件清（EXTI->PR、TIM 的 SR、USART 的部分标志），只有少数是"读一下就自动清"（比如读 DR 清 RXNE）。所以从 51 转过来的人最容易犯的错是「以为硬件会帮我清」。

51 的中断响应过程和 STM32 一样可以分成几步，但现场的保存方式完全不同：

【51 的中断响应过程】

  ① 中断源置请求标志（IE0 / TF0 / IE1 / TF1 / RI 或 TI）
  ② 检查 IE 里的分开关 + EA 总开关是否都为 1
  ③ 检查有没有【同级或更高级】的中断正在服务
     （51 内部有一组"优先级状态触发器"记录这件事）
  ④ 等当前指令执行完；★ 如果当前正在执行 RETI，
     或者正在读写 IE / IP 这两条指令，则要再执行一条指令才响应
     （防止中断响应破坏这两条特殊指令的语义）
  ⑤ 硬件做两件事：
        · 把当前 PC 压栈（保护断点）—— 这是 51 唯一自动保存的东西
        · 把中断入口地址（0x0003 / 0x000B / ...）装入 PC
  ⑥ 执行 ISR
  ⑦ 执行 RETI 指令：
        · 清除对应的"优先级状态触发器"（否则低优先级中断永远进不来）
        · 从栈中弹出断点，送回 PC
        · 返回被中断处

────────────────────────────────────────────────────────────────────────────
【★ 最关键的区别：51 必须自己写 PUSH / POP】
────────────────────────────────────────────────────────────────────────────

void INT0_ISR(void) interrupt 0        /* Keil C51 的写法，interrupt 0 = INT0 */
{
    PUSH  ACC;      /* 累加器 */
    PUSH  PSW;      /* 程序状态字（含进位标志 CY、寄存器组选择位 RS0/RS1）*/
    PUSH  DPL;      /* 数据指针低字节 */
    PUSH  DPH;      /* 数据指针高字节 */
    PUSH  B;        /* B 寄存器（做乘法/除法时要用）*/
    /* ... 如果你在 ISR 里用了 R0~R7，还要 PUSH 对应的寄存器 ... */

    /* ---- 真正的中断处理 ---- */

    POP   B;
    POP   DPH;
    POP   DPL;
    POP   PSW;
    POP   ACC;
}

  ★ 少 PUSH 一个就会出错，而且症状极其诡异：
    比如忘了 PUSH PSW，主循环里的 if 判断会时对时错；
    忘了 PUSH DPH/DPL，主循环里用指针访问数组会跑到随机位置。
  ★ Keil C51 的编译器会【自动】为 interrupt 函数加上寄存器的
    PUSH/POP（前提是你开了相应的优化选项，并且它知道你用了哪些寄存器）。
    但只要你写了汇编，或者用了寄存器组切换，就必须自己管。

【对比：Cortex-M3 只需要写】
void EXTI0_IRQHandler(void)
{
    /* 什么都不用 PUSH！R0~R3、R12、LR、PC、xPSR 由硬件自动压栈，
       R4~R11 由编译器在函数序言里按需压栈。*/
}

  ★ 这个差别带来的后果非常大：
    51 上嵌套两层，你得手工维护两层的 PUSH/POP 顺序；
    Cortex-M 上嵌套十层，硬件和编译器全帮你管好了。
    ★ 这正是 ARM 把"自动压栈"做进硬件的动机 —— 让中断可以安全地嵌套。

把两套机制放在一张表里对照，你就明白 STM32 的复杂度花在哪了：

对比项51（8051 / STC89C52）STM32（Cortex-M3 / F103）
中断源数量 5 个（INT0、T0、INT1、T1、UART） F103 中容量 43 个（IRQ0~IRQ42）+ 15 个系统异常
使能寄存器 一个 IE（0xA8），8 位搞定 ISER[8] + ICER[8]（8 个 32 位寄存器）+ 系统异常另用 SHCSR
优先级寄存器 一个 IP（0xB8），每位一个开关 IPR[60]（字节数组）+ SHPR1/2/3（系统异常）
优先级级数 2 级（高 / 低） 16 级，还可再分成"抢占 + 子优先级"两段
优先级方向 数值大 = 优先级高（IP 写 1 是高） 数值小 = 优先级高（0 最高）
同级多个中断同时请求 按自然优先级（中断号小的先），不可配置 由子优先级决定，完全可配置
中断嵌套 能，高优先级可打断低优先级，但只有两层 能，最多可嵌套到 16 层（受栈深限制），由抢占优先级决定
现场保护 全靠软件：硬件只压 PC，其余自己 PUSH/POP 硬件自动压 8 个寄存器（32 字节），其余编译器按需压
入口地址 写死在 ROM 里（0x0003 / 0x000B / ...），每个只有 8 字节 向量表放在 Flash / SRAM，可以用 VTOR 搬移，每项 4 字节放一个完整地址
ISR 写法 Keil 的 interrupt n 关键字，或手写 ORG + LJMP 函数名必须是芯片规定的名字（EXTI0_IRQHandler），靠启动文件的弱符号绑定
响应延迟 至少 2 个机器周期（12 时钟周期 @12MHz = 1µs） 典型约 14~17 个周期 @72MHz ≈ 0.19~0.24µs（最坏约 29 周期 ≈ 0.40µs）
有没有 Fault 机制 没有。程序跑飞就是跑飞，只能靠看门狗 有：HardFault / BusFault / UsageFault / MemManage，能把"跑飞"变成一个可定位的中断
为什么 STM32 的机制要复杂这么多？

一句话：因为要"能嵌套"就必然要复杂。

  • 51 只有 2 级优先级、5 个中断源，你靠人脑就能排出所有组合。STM32 有 43 个中断源，43 个东西两两之间的先后关系有 1806 种——必须用一套可配置的编码体系（4 位优先级 + 分组）来管理，不能靠人脑硬记。
  • 51 的现场保护全靠软件，所以嵌套两层就要手工维护两套 PUSH/POP，嵌套三层以上几乎没法写对。ARM 把压栈做进硬件，正是为了支持任意深度的嵌套。
  • 51 的入口地址写死，所以"Bootloader + APP"这种结构在 51 上很难做（要重定位整个中断向量区）。Cortex-M 用 VTOR 一个寄存器就解决了，代价是多了一个必须配对的软件动作。
  • 51 没有 Fault 机制，出错只能靠现象猜。Cortex-M 用 CFSR/BFAR 把出错原因记下来，把"玄学问题"变成了"读寄存器"。

复杂度的每一分都对应着一个能力的增加。你不用一开始就掌握全部——先会用 EXTI + 一个优先级，剩下的等需求出现再回来查这一节。

EXTI 外部中断完整配置链

下面这段代码是本节最该抄下来的一段。它是 STM32 上「一个引脚的电平变化引起一次中断」的完整链条，用标准外设库（STM32F10x Standard Peripheral Library V3.5）写——因为《STM32 库开发实战指南》就是基于它。代码后面会逐句解释每一步在干什么，以及为什么少一步就不行。

#include "stm32f10x.h"
#include "exti_key.h"

/* 全局事件标志：中断里只置这个，处理留给主循环 */
volatile uint8_t g_key_pressed = 0;

/* ============================================================================
 *  EXTI0（PA0）初始化：五步，一步都不能少
 * ==========================================================================*/
void KEY_EXTI_Init(void)
{
    GPIO_InitTypeDef GPIO_InitStructure;
    EXTI_InitTypeDef EXTI_InitStructure;
    NVIC_InitTypeDef NVIC_InitStructure;

    /* ------------------------------------------------------------------
     * 第 1 步：开时钟 —— 注意是【两个】时钟，漏掉 AFIO 是最常见的错误
     *
     *   GPIOA：引脚本身在 GPIOA 上，不开时钟读写 GPIOA->CRL 会进 BusFault
     *   AFIO ：★ EXTI 的"线映射"寄存器（AFIO_EXTICR1）在 AFIO 里！
     *          不开 AFIO 时钟，GPIO_EXTILineConfig() 写进去的值无效，
     *          现象是"中断完全不响应"，而且没有任何报错。
     * ------------------------------------------------------------------ */
    RCC_APB2PeriphClockCmd(RCC_APB2Periph_GPIOA | RCC_APB2Periph_AFIO, ENABLE);

    /* ------------------------------------------------------------------
     * 第 2 步：把 PA0 配成输入
     *
     *   GPIO_Mode_IPU = 上拉输入。这个选择很关键：
     *   按键另一端接 GND 的接法下，没按下时引脚必须有确定的高电平，
     *   否则悬空引脚会被外部噪声拉低，产生【随机中断】。
     *   按键接 VCC 的接法就要用 GPIO_Mode_IPD（下拉输入）。
     * ------------------------------------------------------------------ */
    GPIO_InitStructure.GPIO_Pin  = GPIO_Pin_0;
    GPIO_InitStructure.GPIO_Mode = GPIO_Mode_IPU;   /* 上拉输入 */
    GPIO_InitStructure.GPIO_Speed = GPIO_Speed_50MHz; /* 输入模式下这项无实际作用 */
    GPIO_Init(GPIOA, &GPIO_InitStructure);

    /* ------------------------------------------------------------------
     * 第 3 步：把 EXTI0 这条线映射到 PA0
     *
     *   ★ 这是 STM32 独有的、也是最容易漏的一步。
     *   STM32 有 16 条 EXTI 线（EXTI0~EXTI15）能给 GPIO 用，
     *   但每条线只能【同时】接一个端口：
     *       EXTI0  可以接 PA0 / PB0 / PC0 ... 但只能选一个！
     *       EXTI1  可以接 PA1 / PB1 / PC1 ... 但只能选一个！
     *   选择权在 AFIO_EXTICR1~4 里，每个端口占 4 位。
     *
     *   ★ 硬约束：PA0 与 PB0 不能同时做 EXTI0。
     *     如果你先用 PB0 配 Key1、再用 PA0 配 Key2，两次都调用
     *     GPIO_EXTILineConfig() 配 EXTI0，那么后一次会覆盖前一次 ——
     *     结果只有一个按键能用，另一个永远不触发（也没有任何报错）。
     *     解决办法：换线（比如把 Key2 挪到 PA1），或者把两个按键
     *     用【二极管的线与】接到同一个引脚上（硬件方案）。
     * ------------------------------------------------------------------ */
    GPIO_EXTILineConfig(GPIO_PortSourceGPIOA, GPIO_PinSource0);

    /* ------------------------------------------------------------------
     * 第 4 步：配置 EXTI 本体
     *
     *   EXTI_Mode：Interrupt（中断）还是 Event（事件）？
     *      · Interrupt → 置挂起位并送给 NVIC，会产生中断，CPU 会跳进 ISR
     *      · Event     → 只置挂起位送给其他外设（比如触发 ADC 开始转换），
     *                    【不产生中断】。典型用途：外部信号触发 ADC 采样，
     *                    由硬件自动完成，CPU 完全不用参与。
     *
     *   EXTI_Trigger：Rising / Falling / Rising_Falling
     *      · Falling      → 下降沿触发（按键接 GND 的接法：按下产生下降沿）
     *      · Rising       → 上升沿触发（按键接 VCC 的接法：按下产生上升沿）
     *      · Rising_Falling → 两个边沿都触发（适合测脉冲宽度，但中断次数翻倍）
     *      ★ 如果按键接 GND 却配了 Rising，现象就是"按下没反应、松开才响应"。
     * ------------------------------------------------------------------ */
    EXTI_InitStructure.EXTI_Line    = EXTI_Line0;
    EXTI_InitStructure.EXTI_Mode    = EXTI_Mode_Interrupt;
    EXTI_InitStructure.EXTI_Trigger = EXTI_Trigger_Falling;
    EXTI_InitStructure.EXTI_LineCmd = ENABLE;
    EXTI_Init(&EXTI_InitStructure);

    /* ------------------------------------------------------------------
     * 第 5 步：配置 NVIC 优先级并使能
     *
     *   ★ 顺序很重要：先清挂起，再使能。
     *     配置 EXTI 的过程中可能已经产生了一次虚假请求，
     *     如果不先清干净，NVIC_Init 使能的那一刻就会【立刻进一次 ISR】，
     *     处理一个并不存在的事件。
     * ------------------------------------------------------------------ */
    EXTI_ClearITPendingBit(EXTI_Line0);          /* 清外设挂起位 */
    NVIC_ClearPendingIRQ(EXTI0_IRQn);            /* 清 NVIC 挂起位 */

    NVIC_InitStructure.NVIC_IRQChannel                   = EXTI0_IRQn;
    NVIC_InitStructure.NVIC_IRQChannelPreemptionPriority = 2;
    NVIC_InitStructure.NVIC_IRQChannelSubPriority        = 0;
    NVIC_InitStructure.NVIC_IRQChannelCmd                = ENABLE;
    NVIC_Init(&NVIC_InitStructure);
}

/* ============================================================================
 *  中断服务函数
 *  ★ 函数名必须【一字不差】是 EXTI0_IRQHandler，大小写都不能改。
 *    这个名字由启动文件 startup_stm32f10x_md.s 里的向量表规定，
 *    它把向量表第 22 项（异常号 16+6）指向这个名字的弱符号。
 *    你写不出这个名字，链接器就会用默认的 Default_Handler —— 一个死循环。
 * ==========================================================================*/
void EXTI0_IRQHandler(void)
{
    /* ★ 第一件事：确认是不是这条线触发的，同时把标志读出来。
     *   为什么必须判断？因为 EXTI9_5 / EXTI15_10 这类一条线管多个源，
     *   进 ISR 时不一定是你要的那个源触发的。 */
    if (EXTI_GetITStatus(EXTI_Line0) != RESET) {

        /* 只置标志，绝不在这里做耗时处理 */
        g_key_pressed = 1;

        /* ★ 清挂起标志：写 1 清除（不是写 0！）。
         *   EXTI_ClearITPendingBit 内部就是 EXTI->PR = EXTI_Line0;
         *   忘了这一句 → 退出后挂起位还是 1 → 立刻又进一次 → 死循环。 */
        EXTI_ClearITPendingBit(EXTI_Line0);
    }
}

/* ============================================================================
 *  主循环：在这里处理事件
 * ==========================================================================*/
int main(void)
{
    KEY_EXTI_Init();

    while (1) {
        if (g_key_pressed) {
            g_key_pressed = 0;
            /* 真正的按键处理写在这里（可以延时、可以刷屏、可以发串口） */
        }
    }
}

上面每一步在寄存器层面到底动了什么？这张表让你把库函数和硬件对上：

步骤库函数实际操作的寄存器漏掉的后果
开 GPIO 时钟 RCC_APB2PeriphClockCmd(RCC_APB2Periph_GPIOA, ENABLE) RCC->APB2ENR bit2 = 1 读写 GPIOA->CRL 触发 BusFault
开 AFIO 时钟 RCC_APB2PeriphClockCmd(RCC_APB2Periph_AFIO, ENABLE) RCC->APB2ENR bit0 = 1 线映射写不进去，中断完全不响应（且无报错）
GPIO 配输入 GPIO_Init(GPIOA, &…) with GPIO_Mode_IPU GPIOA->CRL 的 CNF0[1:0]=10, MODE0[1:0]=00 引脚悬空 → 噪声引起随机中断
EXTI 线映射 GPIO_EXTILineConfig(GPIO_PortSourceGPIOA, GPIO_PinSource0) AFIO->EXTICR[0] 的 bit[3:0] = 0000（选中 PA） EXTI0 接在默认端口上，中断不响应或响应错的引脚
EXTI 中断使能 EXTI_Init(…) with EXTI_LineCmd = ENABLE EXTI->IMR bit0 = 1 边沿被检测到但不会送到 NVIC
EXTI 触发方式 EXTI_Trigger_Falling EXTI->FTSR bit0 = 1（上升沿则 RTSR） 触发边沿与硬件相反 → 按下没反应
NVIC 使能 NVIC_Init(…) with NVIC_IRQChannelCmd = ENABLE NVIC->ISER[0] bit6 = 1 请求到了 NVIC 但被拦在门外，永远不进 ISR
NVIC 优先级 NVIC_IRQChannelPreemptionPriority = 2 NVIC->IPR[6] = 2 << 4 = 0x20 用默认值 0，意外成为最高优先级
写 ISR void EXTI0_IRQHandler(void) 向量表第 22 项指向它 落到 Default_Handler 死循环里
同一个功能的 HAL 版写法（对照一下）

用 HAL 库时，链条是一样的，只是名称变了，而且AFIO 时钟被藏进了 MspInit 回调——这就是"用 CubeMX 生成的工程能跑、手写 HAL 初始化却跑不起来"的原因。

#include "stm32f1xx_hal.h"

static void key_exti_init(void)
{
    GPIO_InitTypeDef GPIO_InitStruct = {0};

    /* ① 时钟：GPIOA + AFIO（HAL 里 AFIO 时钟宏叫 __HAL_RCC_AFIO_CLK_ENABLE） */
    __HAL_RCC_GPIOA_CLK_ENABLE();
    __HAL_RCC_AFIO_CLK_ENABLE();          /* ★ 漏掉这句 = 中断不响应 */

    /* ② GPIO 输入 */
    GPIO_InitStruct.Pin  = GPIO_PIN_0;
    GPIO_InitStruct.Mode = GPIO_MODE_IT_FALLING;   /* 输入 + 下降沿中断，一步到位 */
    GPIO_InitStruct.Pull = GPIO_PULLUP;
    HAL_GPIO_Init(GPIOA, &GPIO_InitStruct);

    /* ③ NVIC 优先级与使能（HAL_GPIO_Init 内部已经根据 Mode 配好了 EXTI，
     *    但 NVIC 的优先级和使能必须自己设） */
    HAL_NVIC_SetPriority(EXTI0_IRQn, 2, 0);
    HAL_NVIC_EnableIRQ(EXTI0_IRQn);
    /* ★ HAL_NVIC_SetPriority 的第 2、3 个参数的含义取决于当前【优先级分组】，
     *   HAL_Init() 默认设成 NVIC_PRIORITYGROUP_4 → 只有抢占有效，子优先级被忽略。 */
}

/* HAL 的中断服务函数 */
void EXTI0_IRQHandler(void)
{
    /* HAL 的 GPIO 扩展回调模式：交给 HAL_GPIO_EXTI_IRQHandler 处理清标志，
     * 然后在回调里写你的逻辑 */
    HAL_GPIO_EXTI_IRQHandler(GPIO_PIN_0);
}

/* 回调函数：HAL_GPIO_EXTI_IRQHandler 清完标志后会调用它 */
void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
{
    if (GPIO_Pin == GPIO_PIN_0) {
        g_key_pressed = 1;                /* 依然只置标志 */
    }
}

注意 HAL_GPIO_EXTI_IRQHandler() 帮你清了 EXTI 挂起标志——这是 HAL 的约定：HAL_XXX_IRQHandler() 负责清标志 + 调回调，回调里你只管业务逻辑。但如果你写的是裸寄存器版本或者标准库版本，清标志就是你自己的事。

EXTI 的几个容易忽略的细节
  • EXTI 线 0~15 给 GPIO 用，16~19 是固定功能：EXTI16 = PVD 输出、EXTI17 = RTC 闹钟、EXTI18 = USB 唤醒、EXTI19 = 以太网唤醒（F103 的互联型才有）。这些不需要 GPIO_EXTILineConfig。
  • 一条 IRQ 线管多个 EXTI 源：EXTI9_5_IRQn 管 EXTI5~EXTI9，EXTI15_10_IRQn 管 EXTI10~EXTI15。写这两个 ISR 时必须逐个检查挂起位，否则会漏掉同组的其他中断源。
  • EXTI->PR 是「写 1 清除」：写 0 没作用，写 1 才清对应位。EXTI->PR = EXTI_Line0; 是对的，EXTI->PR &= ~EXTI_Line0; 是错的。
  • STOP 模式唤醒必须用 EXTI：低功耗设计里按键唤醒只能靠 EXTI（因为 CPU 停clock了，没有"主循环"在跑）。这是 EXTI 唯一不可替代的场合。

按键中断：硬件去抖不够怎么办

把机械按键接到 EXTI 上，你马上会遇到一个新问题：按一次键，进了好几次中断。原因在第 1 节讲过——触点闭合瞬间的弹跳会产生一串窄脉冲，每一个下降沿都会触发一次中断。典型机械按键的抖动时间是 5~20ms，其中可能包含几十个跳变。

【理想按键】                        【真实按键】
  高 ────┐                           高 ────┐  ┌┐ ┌─┐ ┌┐
         │                                  │  ││ │ │ ││
  低     └────────                    低     └──┘└─┘ └─┘└──────
         ↑ 一次干净的下降沿                  ↑
                                            └─ 5~20ms 抖动区 ─┘
                                              （可能几十个跳变）

  接 EXTI 下降沿触发 → 抖动区里每一个下降沿都进一次 ISR
  → 按一次键进 3~30 次中断！

═══════════════════════════════════════════════════════════════════════
方案 A：中断里只置标志，主循环里延时确认
═══════════════════════════════════════════════════════════════════════
   中断：      ▼▼▼▼▼▼▼  （多次进，但每次都只做一件事：置 flag=1）
   主循环：                    ┌─ 检测到 flag → 延时 20ms ─┐
                               │                           │
                               └─ 再读一次引脚 ─────────────┘
                                  还是低 → 确认按下，只算一次！
   优点：ISR 极短；防抖逻辑简单直观
   缺点：主循环必须"很快"看到 flag，否则会错过（但按键不急，20ms 无所谓）

═══════════════════════════════════════════════════════════════════════
方案 B：中断里启动一个单次定时器，定时器中断里确认
═══════════════════════════════════════════════════════════════════════
   中断：      ▼（只响应第一次）
               └→ 启动 TIM3（20ms 单次，一个脉冲模式）
                        │
                        │←──── 20ms 抖动期，标志一直被清，不进 EXTI ────→│
                        ▼
                 TIM3 中断：再读引脚
                    还是低 → 确认按下 → 置事件标志 → 停止 TIM3
                    已变高 → 是干扰 → 丢弃 → 停止 TIM3
   优点：完全在中断侧完成，主循环零负担；响应速度固定 20ms
   缺点：占一个定时器；ISR 里多了启动定时器的开销（几十周期）

═══════════════════════════════════════════════════════════════════════
方案 C：硬件去抖（RC 滤波 + 施密特触发器，或专用去抖芯片）
═══════════════════════════════════════════════════════════════════════
   PA0 ──┬── R(10k) ──┬── 按键 ── GND
         │            │
        ===  C(0.1µF) │
         │            │
        GND           └── 到 MCU 引脚（经过施密特触发器整形，如 74HC14）
   RC 时间常数 τ = 10k × 0.1µF = 1ms
   施密特触发器提供迟滞，把缓慢的 RC 充放电曲线整形成干净的数字边沿
   优点：软件完全不用管，中断次数天然只有 1 次
   缺点：占板面积和成本；RC 太大还会让"连按"变迟钝
   ★ 很多开发板的按键电路上那个 0.1µF 电容就是这个作用。
     如果你的板子上没有，方案 C 就用不了。

方案 A 和方案 B 的完整代码：

#include "stm32f10x.h"

volatile uint8_t g_key_flag = 0;      /* ★ 中断和主循环共享，必须 volatile */

void EXTI0_IRQHandler(void)
{
    if (EXTI_GetITStatus(EXTI_Line0) != RESET) {
        g_key_flag = 1;                       /* 就这一句，多一句都不加 */
        EXTI_ClearITPendingBit(EXTI_Line0);
    }
}

/* 主循环里的处理 */
int main(void)
{
    KEY_EXTI_Init();

    while (1) {
        if (g_key_flag) {
            g_key_flag = 0;

            /* ① 等抖动过去（20ms 足够覆盖绝大多数机械按键） */
            for (volatile uint32_t i = 0; i < 1440000; i++) { }   /* 约 20ms @72MHz */
            /* 也可以用 HAL_Delay(20)，但那是阻塞的；
             * 在主循环里用没问题，在 ISR 里绝对不行。 */

            /* ② 再看一眼引脚：还是低电平，说明是真按下，不是抖动 */
            if (GPIO_ReadInputDataBit(GPIOA, GPIO_Pin_0) == Bit_RESET) {

                /* ③ 真正的按键动作（只执行一次！） */
                key_action();

                /* ④ 等按键松开，防止"按住不放"被识别成连按 */
                while (GPIO_ReadInputDataBit(GPIOA, GPIO_Pin_0) == Bit_RESET) { }
                /* ★ 这一句是【阻塞】的，但它在主循环里，可以接受。
                 *   副作用：按住不放期间主循环会卡在这里，
                 *   如果你需要"长按"功能，就不能这么写 —— 改成
                 *   记录按下时刻，用状态机在主循环里判断。 */
            }
        }
    }
}

/* ★ 关于那个 for 循环延时的提醒：
 *   1440000 次循环 ≈ 20ms 是按 -O0 编译、每次循环 1 个周期估的。
 *   开了 -O2 之后编译器可能把空循环优化掉，或者用更少的周期。
 *   正式项目请用 HAL_Delay，或者用定时器时基判断，不要靠空循环数数。 */
#include "stm32f10x.h"

volatile uint8_t g_key_event = 0;      /* 确认后的按键事件，给主循环用 */

/* ---------------------------------------------------------------------------
 * TIM3 配成 20ms 周期的【单次】定时器
 *   系统时钟 72MHz → 预分频 7199 → 计数时钟 72MHz / 7200 = 10kHz
 *   周期寄存器 199 → 每 200 个计数溢出一次 = 200 / 10kHz = 20ms
 * -------------------------------------------------------------------------*/
void TIM3_OneShot_Init(void)
{
    TIM_TimeBaseInitTypeDef TIM_TimeBaseStructure;
    NVIC_InitTypeDef NVIC_InitStructure;

    RCC_APB1PeriphClockCmd(RCC_APB1Periph_TIM3, ENABLE);   /* TIM3 在 APB1 上 */

    TIM_TimeBaseStructure.TIM_Period        = 199;    /* 自动重装载值 */
    TIM_TimeBaseStructure.TIM_Prescaler     = 7199;   /* 预分频 */
    TIM_TimeBaseStructure.TIM_ClockDivision = TIM_CKD_DIV1;
    TIM_TimeBaseStructure.TIM_CounterMode   = TIM_CounterMode_Up;
    TIM_TimeBaseInit(TIM3, &TIM_TimeBaseStructure);

    /* ★ 关键：配成单次（One Pulse）模式 —— 溢出一次后自动停止，
     *   不需要在 ISR 里手动 TIM_Cmd(DISABLE)。 */
    TIM_SelectOnePulseMode(TIM3, TIM_OPMode_Single);

    TIM_ClearITPendingBit(TIM3, TIM_IT_Update);
    TIM_ITConfig(TIM3, TIM_IT_Update, ENABLE);

    NVIC_InitStructure.NVIC_IRQChannel                   = TIM3_IRQn;
    NVIC_InitStructure.NVIC_IRQChannelPreemptionPriority = 3;
    NVIC_InitStructure.NVIC_IRQChannelSubPriority        = 0;
    NVIC_InitStructure.NVIC_IRQChannelCmd                = ENABLE;
    NVIC_Init(&NVIC_InitStructure);

    /* 初始不启动，等按键中断来启动 */
    TIM_Cmd(TIM3, DISABLE);
}

/* ---------------- 按键中断：只做一件事 —— 启动定时器 ---------------- */
void EXTI0_IRQHandler(void)
{
    if (EXTI_GetITStatus(EXTI_Line0) != RESET) {
        /* 清掉计数器，保证从 0 开始计满 20ms */
        TIM_SetCounter(TIM3, 0);
        TIM_Cmd(TIM3, ENABLE);          /* 启动单次定时 */
        EXTI_ClearITPendingBit(EXTI_Line0);
    }
    /* ★ 抖动期内的后续跳变还会进好几次这个 ISR，
     *   每次都是"重新启动 20ms 定时器" —— 这正好是我们想要的：
     *   只要还在抖，定时器就一直被重置，永远到不了 20ms。
     *   只有抖动结束后 20ms 内没有新跳变，定时器才会真的溢出。 */
}

/* ---------------- 定时器中断：此时才是"真正按下" ---------------- */
void TIM3_IRQHandler(void)
{
    if (TIM_GetITStatus(TIM3, TIM_IT_Update) != RESET) {
        TIM_ClearITPendingBit(TIM3, TIM_IT_Update);

        /* 再读一次引脚确认 */
        if (GPIO_ReadInputDataBit(GPIOA, GPIO_Pin_0) == Bit_RESET) {
            g_key_event = 1;            /* 确认按下，交给主循环 */
        }
        /* 单次模式下硬件已经停了，不用再 TIM_Cmd(DISABLE) */
    }
}

/* ---------------- 主循环：只管处理确认后的事件 ---------------- */
int main(void)
{
    KEY_EXTI_Init();
    TIM3_OneShot_Init();

    while (1) {
        if (g_key_event) {
            g_key_event = 0;
            key_action();
        }
    }
}
但是——工业项目里最常用的其实是「不接 EXTI」

说完上面两种方案，要给你一个更重要的建议：按键这类"慢速、有抖动、不紧急"的输入，最好的做法是不要用中断，而是用一个 10ms 的定时器中断去轮询扫描。

  • 10ms 扫一次，抖动（5~20ms）天然被滤掉，不需要任何额外逻辑；
  • 不需要为每个按键占一条 EXTI 线（16 条线很宝贵，多按键项目根本不够用）；
  • 多个按键共享一个定时器中断，代码量比每个按键配一遍 EXTI 少得多；
  • 天然支持"长按""连按""组合键"这些状态机逻辑，因为这些逻辑本来就需要周期性采样。

那 EXTI 该用在哪？两种情况：① 低功耗唤醒——CPU 已经进 STOP 模式了，没有"10ms 定时器"在跑，只有 EXTI 能把芯片叫醒；② 真正高速的信号——旋转编码器的脉冲、外部传感器的就绪信号、过零检测，这些事件之间的间隔可能只有几微秒，定时器扫描必然漏掉。判断标准还是那句：这件事必须在某个时间窗内被响应吗？

串口接收中断与 115200 的频率账

串口是中断用得最多的外设，也是最容易用错的地方。先看逐字节进中断的写法——这是最直观的方案，也是最容易在高波特率下出事的地方。

#include "stm32f10x.h"
#include <string.h>

/* ---------------------------------------------------------------------------
 * 环形缓冲区（Ring Buffer / FIFO）
 *   写指针：只在中断里改
 *   读指针：只在主循环里改
 *   ★ 这样设计的好处：写指针和读指针各自只有一个"作者"，
 *     不需要任何锁。缓冲区满/空的判断用"写指针是否追上读指针"。
 * -------------------------------------------------------------------------*/
#define UART_RX_BUF_SIZE   256          /* 必须是 2 的幂，方便用 & 取模 */

typedef struct {
    volatile uint8_t  buf[UART_RX_BUF_SIZE];
    volatile uint16_t w;                /* 写指针：ISR 改 */
    volatile uint16_t r;                /* 读指针：主循环改 */
    volatile uint32_t overflow;         /* 溢出计数：用来发现"来不及读" */
} ring_t;

static ring_t g_rx;

/* ---------------------------------------------------------------------------
 * USART1 接收中断：115200 下每 86.8µs 进来一次，所以必须极短
 * -------------------------------------------------------------------------*/
void USART1_IRQHandler(void)
{
    /* ★ 这里检查的是"接收非空"标志。注意：
     *   HAL 库用户写的是 HAL_UART_IRQHandler(&huart1)，
     *   那一个函数内部要做十几项判断（PE/FE/NE/ORE/IDLE/RXNE），
     *   实测 150~300 周期。裸寄存器版本只要 3 个周期读 SR。 */
    if (USART_GetITStatus(USART1, USART_IT_RXNE) != RESET) {

        /* ★ 读 DR 这一动作【本身】就清掉了 RXNE 标志，
         *   这是 USART 里最特殊的一点：不需要写 1 清除。 */
        uint8_t data = (uint8_t)USART_ReceiveData(USART1);

        uint16_t next = (uint16_t)((g_rx.w + 1U) & (UART_RX_BUF_SIZE - 1U));

        if (next == g_rx.r) {
            /* 缓冲区满了：主循环读得太慢。丢掉新数据并计数。
             * ★ 绝不要在这里等待！等待就是死锁。 */
            g_rx.overflow++;
        } else {
            g_rx.buf[g_rx.w] = data;
            g_rx.w = next;
        }
    }

    /* ★ 顺手检查溢出错误（ORE）：接收寄存器还没被读走，下一个字节就来了。
     *   发生 ORE 后必须先读 SR 再读 DR 才能清掉它，
     *   而且这一帧剩下的数据已经不可信了。 */
    if (USART_GetFlagStatus(USART1, USART_FLAG_ORE) != RESET) {
        (void)USART1->SR;      /* 读 SR */
        (void)USART1->DR;      /* 再读 DR，两步才能清 ORE */
        g_rx.overflow++;       /* 记一笔：说明中断延迟太大了 */
    }
}

/* ---------------------------------------------------------------------------
 * 初始化：只开 RXNE 中断
 * -------------------------------------------------------------------------*/
void USART1_Init(uint32_t baud)
{
    GPIO_InitTypeDef  GPIO_InitStructure;
    USART_InitTypeDef USART_InitStructure;
    NVIC_InitTypeDef  NVIC_InitStructure;

    RCC_APB2PeriphClockCmd(RCC_APB2Periph_GPIOA | RCC_APB2Periph_USART1, ENABLE);

    /* PA9 = TX（复用推挽），PA10 = RX（浮空输入或上拉输入） */
    GPIO_InitStructure.GPIO_Pin   = GPIO_Pin_9;
    GPIO_InitStructure.GPIO_Mode  = GPIO_Mode_AF_PP;
    GPIO_InitStructure.GPIO_Speed = GPIO_Speed_50MHz;
    GPIO_Init(GPIOA, &GPIO_InitStructure);

    GPIO_InitStructure.GPIO_Pin  = GPIO_Pin_10;
    GPIO_InitStructure.GPIO_Mode = GPIO_Mode_IN_FLOATING;
    GPIO_Init(GPIOA, &GPIO_InitStructure);

    USART_InitStructure.USART_BaudRate            = baud;
    USART_InitStructure.USART_WordLength          = USART_WordLength_8b;
    USART_InitStructure.USART_StopBits            = USART_StopBits_1;
    USART_InitStructure.USART_Parity              = USART_Parity_No;
    USART_InitStructure.USART_HardwareFlowControl = USART_HardwareFlowControl_None;
    USART_InitStructure.USART_Mode                = USART_Mode_Rx | USART_Mode_Tx;
    USART_Init(USART1, &USART_InitStructure);

    /* ★ 顺序：先清挂起、再开外设中断、最后开 NVIC */
    USART_ClearITPendingBit(USART1, USART_IT_RXNE);
    USART_ITConfig(USART1, USART_IT_RXNE, ENABLE);   /* 外设级：USART->CR1 的 RXNEIE */
    USART_Cmd(USART1, ENABLE);

    NVIC_InitStructure.NVIC_IRQChannel                   = USART1_IRQn;
    NVIC_InitStructure.NVIC_IRQChannelPreemptionPriority = 3;
    NVIC_InitStructure.NVIC_IRQChannelSubPriority        = 0;
    NVIC_InitStructure.NVIC_IRQChannelCmd                = ENABLE;
    NVIC_Init(&NVIC_InitStructure);
}

/* ---------------------------------------------------------------------------
 * 主循环侧：从环形缓冲区取数据处理
 * -------------------------------------------------------------------------*/
uint16_t uart_available(void)
{
    return (uint16_t)((g_rx.w - g_rx.r) & (UART_RX_BUF_SIZE - 1U));
}

uint8_t uart_getc(void)
{
    uint8_t d = g_rx.buf[g_rx.r];
    g_rx.r = (uint16_t)((g_rx.r + 1U) & (UART_RX_BUF_SIZE - 1U));
    return d;
}

/* ★ 注意 uart_available 的写法：(w - r) 用了无符号减法，
 *   在 w 回绕的时候结果依然正确。不要写成 w >= r ? w - r : ... */

这套写法在 115200 下每秒要进 11,520 次中断，每次约 45 个周期（裸寄存器）——CPU 占用 0.72%，看起来完全可以接受。但例题 5 已经算过：换成 HAL 库就变成 4.38%，波特率提到 921600 就变成 35.1%。所以逐字节中断的真正问题不是平均占用，而是这两条：

  • 每 86.8µs 就必须响应一次，这是硬约束。只要有任何更高优先级的 ISR 执行超过 86.8µs，或者主循环关中断超过 86.8µs，USART 的接收寄存器就会被新数据覆盖 → ORE 溢出，丢字节。而且丢了一个字节之后，后面的协议解析全部错位。
  • 这个约束会传染给整个系统。你为了"不丢串口数据"，就得保证所有中断和所有临界区都短于 86.8µs。一条本来无关紧要的 Flash 写入操作（擦除一个页要 20~40ms）就能把你逼疯。

所以对"不定长帧"的协议，正确的做法是空闲中断 + DMA：

#include "stm32f10x.h"

#define UART_RX_DMA_BUF_SIZE   128

static uint8_t  g_rx_dma_buf[UART_RX_DMA_BUF_SIZE];
static volatile uint16_t g_rx_frame_len = 0;      /* 本帧长度 */
static volatile uint8_t  g_rx_frame_ready = 0;    /* 帧就绪标志 */

/* ---------------------------------------------------------------------------
 * 初始化：DMA 循环模式 + IDLE 中断
 * -------------------------------------------------------------------------*/
void USART1_DMA_Idle_Init(uint32_t baud)
{
    DMA_InitTypeDef DMA_InitStructure;
    /* ... GPIO / USART 配置同方案一，此处省略 ... */

    RCC_AHBPeriphClockCmd(RCC_AHBPeriph_DMA1, ENABLE);   /* ★ DMA1 在 AHB 上 */

    /* ★ DMA 配成【循环模式】（Circular）的关键理由：
     *   如果配成普通模式，一次传输完成就停了，必须软件重新启动，
     *   而"什么时候重新启动"这件事本身又需要一个中断 —— 循环往复。
     *   循环模式下 DMA 永不停止，写满缓冲区就自动回到开头，
     *   我们只在 IDLE 中断里读一次 NDTR 就知道这一帧多长。 */
    DMA_DeInit(DMA1_Channel5);                    /* USART1_RX 固定用 DMA1 通道 5 */
    DMA_InitStructure.DMA_PeripheralBaseAddr = (uint32_t)&(USART1->DR);
    DMA_InitStructure.DMA_MemoryBaseAddr     = (uint32_t)g_rx_dma_buf;
    DMA_InitStructure.DMA_DIR                = DMA_DIR_PeripheralSRC;
    DMA_InitStructure.DMA_BufferSize         = UART_RX_DMA_BUF_SIZE;
    DMA_InitStructure.DMA_PeripheralInc      = DMA_PeripheralInc_Disable;
    DMA_InitStructure.DMA_MemoryInc          = DMA_MemoryInc_Enable;
    DMA_InitStructure.DMA_PeripheralDataSize = DMA_PeripheralDataSize_Byte;
    DMA_InitStructure.DMA_MemoryDataSize     = DMA_MemoryDataSize_Byte;
    DMA_InitStructure.DMA_Mode               = DMA_Mode_Circular;   /* ★ 循环 */
    DMA_InitStructure.DMA_Priority           = DMA_Priority_Medium;
    DMA_InitStructure.DMA_M2M                = DMA_M2M_Disable;
    DMA_Init(DMA1_Channel5, &DMA_InitStructure);

    USART_DMACmd(USART1, USART_DMAReq_Rx, ENABLE);   /* 告诉 USART：接收走 DMA */
    DMA_Cmd(DMA1_Channel5, ENABLE);                  /* 启动 DMA */

    /* ★ IDLE 中断必须使能，否则不知道"一帧什么时候结束" */
    USART_ClearITPendingBit(USART1, USART_IT_IDLE);
    USART_ITConfig(USART1, USART_IT_IDLE, ENABLE);

    NVIC_InitTypeDef NVIC_InitStructure;
    NVIC_InitStructure.NVIC_IRQChannel                   = USART1_IRQn;
    NVIC_InitStructure.NVIC_IRQChannelPreemptionPriority = 3;
    NVIC_InitStructure.NVIC_IRQChannelSubPriority        = 0;
    NVIC_InitStructure.NVIC_IRQChannelCmd                = ENABLE;
    NVIC_Init(&NVIC_InitStructure);
}

/* ---------------------------------------------------------------------------
 * 中断服务函数：一帧只进一次！
 * -------------------------------------------------------------------------*/
void USART1_IRQHandler(void)
{
    /* ★ IDLE 标志的清除方式很特别：
     *   标准库的 USART_ClearITPendingBit 对 IDLE 无效！
     *   必须"先读 SR、再读 DR"这两步才能清掉 IDLE。
     *   这是 STM32F1 上最著名的坑之一，忘了清就会反复进中断。 */
    if (USART_GetITStatus(USART1, USART_IT_IDLE) != RESET) {
        volatile uint32_t tmp;
        tmp = USART1->SR;      /* ① 读 SR */
        tmp = USART1->DR;      /* ② 再读 DR，清 IDLE 标志 */
        (void)tmp;

        /* ★ 用 DMA 剩余计数反推本帧长度：
         *   NDTR 从 UART_RX_DMA_BUF_SIZE 递减，已经搬走了
         *   (BUF_SIZE - NDTR) 个字节，那就是本帧的长度。 */
        g_rx_frame_len = (uint16_t)(UART_RX_DMA_BUF_SIZE
                                    - DMA_GetCurrDataCounter(DMA1_Channel5));
        g_rx_frame_ready = 1;      /* 告诉主循环：一帧到了 */

        /* ★ 循环模式下不需要重启 DMA，它自己继续跑。
         *   （如果配的是普通模式，这里必须 DMA_SetCurrDataCounter + DMA_Cmd 重启，
         *     但那样做有个副作用：重启前到达的字节会丢。这也是推荐循环模式的原因。） */
    }
}

/* ---------------------------------------------------------------------------
 * 主循环：处理整帧
 * -------------------------------------------------------------------------*/
int main(void)
{
    USART1_DMA_Idle_Init(115200);

    while (1) {
        if (g_rx_frame_ready) {
            __disable_irq();                        /* 进入临界区，防止被下一帧打断 */
            uint16_t len = g_rx_frame_len;
            uint8_t  local[UART_RX_DMA_BUF_SIZE];
            memcpy(local, g_rx_dma_buf, len);       /* 拷出来再慢慢处理 */
            g_rx_frame_ready = 0;
            __enable_irq();                         /* 出临界区 */

            parse_frame(local, len);                /* 解析、校验、执行 */
        }
    }
}
为什么不定长帧特别适合「空闲中断 + DMA」

UART 协议的物理特性帮了大忙：一帧数据发完之后，发送方会停止发送，总线保持在空闲电平（高电平）至少 1 个字符时间。USART 硬件能检测到这一点，并置起 IDLE 标志、产生中断。

于是整条链路变成：DMA 负责把每个字节搬进内存（CPU 完全不参与），IDLE 中断负责告诉你「这一帧结束了，长度是 N」。一帧 20 个字节只产生 1 次中断，而不是 20 次。而且长度不是靠"猜协议"得来的，而是从 DMA 的剩余计数里精确推出来的。

对比其他方案：定长帧可以用 DMA 的传输完成中断（TC），简单直接；不定长帧如果不用 IDLE，就只能靠"逐字节中断 + 软件找帧头帧尾"，或者"额外配一个超时定时器"——前者中断太密，后者多占一个定时器资源且超时值难调。IDLE 中断是硬件免费送的礼物，没有理由不用。

定时器中断做系统时基

第 1 节第三个故障现场讲过：「软件延时 + 累加」永远得不到准确的时间基准，因为延时函数管不住它后面的代码要跑多久。正确做法是让硬件来数——一个 1ms 的定时器中断，每次中断把计数器加一。

#include "stm32f10x.h"

/* ---------------------------------------------------------------------------
 * 全局毫秒计数：中断里加，任何地方读
 * ★ volatile 是必须的 —— 否则主循环里的读会被编译器优化掉
 * -------------------------------------------------------------------------*/
volatile uint32_t g_tick_ms = 0;

/* ---------------------------------------------------------------------------
 * 用 TIM2 做 1ms 时基（不用 SysTick，把 SysTick 留给 HAL 或 RTOS）
 *   72MHz 经过预分频 7199 → 72MHz / 7200 = 10kHz（计数周期 100µs）
 *   自动重装载 9 → 每 10 个计数溢出一次 = 10 × 100µs = 1ms
 * -------------------------------------------------------------------------*/
void TIM2_Tick_Init(void)
{
    TIM_TimeBaseInitTypeDef TIM_TimeBaseStructure;
    NVIC_InitTypeDef NVIC_InitStructure;

    RCC_APB1PeriphClockCmd(RCC_APB1Periph_TIM2, ENABLE);

    TIM_TimeBaseStructure.TIM_Period        = 9;      /* ARR */
    TIM_TimeBaseStructure.TIM_Prescaler     = 7199;   /* PSC */
    TIM_TimeBaseStructure.TIM_ClockDivision = TIM_CKD_DIV1;
    TIM_TimeBaseStructure.TIM_CounterMode   = TIM_CounterMode_Up;
    TIM_TimeBaseInit(TIM2, &TIM_TimeBaseStructure);

    TIM_ClearITPendingBit(TIM2, TIM_IT_Update);
    TIM_ITConfig(TIM2, TIM_IT_Update, ENABLE);

    NVIC_InitStructure.NVIC_IRQChannel                   = TIM2_IRQn;
    NVIC_InitStructure.NVIC_IRQChannelPreemptionPriority = 1;   /* 时基要准，给高一点 */
    NVIC_InitStructure.NVIC_IRQChannelSubPriority        = 0;
    NVIC_InitStructure.NVIC_IRQChannelCmd                = ENABLE;
    NVIC_Init(&NVIC_InitStructure);

    TIM_Cmd(TIM2, ENABLE);
}

/* ---------------------------------------------------------------------------
 * 中断服务函数：就加一，别的什么都不做
 * -------------------------------------------------------------------------*/
void TIM2_IRQHandler(void)
{
    if (TIM_GetITStatus(TIM2, TIM_IT_Update) != RESET) {
        g_tick_ms++;                          /* ★ 只这一句 */
        TIM_ClearITPendingBit(TIM2, TIM_IT_Update);   /* ★ 这一句也不能少 */
    }
}

/* ---------------------------------------------------------------------------
 * 时基的三个用法
 * -------------------------------------------------------------------------*/

/* 用法 1：取当前时刻 */
uint32_t millis(void)
{
    return g_tick_ms;
}

/* 用法 2：非阻塞延时判断（★ 溢出安全的写法） */
uint8_t time_elapsed(uint32_t start, uint32_t interval)
{
    return ((uint32_t)(g_tick_ms - start) >= interval) ? 1U : 0U;
}

void example_nonblocking_delay(void)
{
    uint32_t t0 = g_tick_ms;

    /* 做点别的事，不去等 */
    do_something();

    if (time_elapsed(t0, 500)) {
        /* 500ms 到了 */
    }
}

/* 用法 3：周期性任务（不用 HAL_Delay 也能让 LED 闪） */
void blink_task(void)
{
    static uint32_t last = 0;

    if (time_elapsed(last, 500)) {
        last = g_tick_ms;                     /* ★ 用 last += 500 会更准，见下文 */
        GPIO_WriteBit(GPIOC, GPIO_Pin_13,
                      (BitAction)(1 - GPIO_ReadOutputDataBit(GPIOC, GPIO_Pin_13)));
    }
}

/* ---------------------------------------------------------------------------
 * ★★★ 溢出问题：这一段是很多人栽过的地方
 * -------------------------------------------------------------------------*/
void overflow_explained(void)
{
    /* ① uint32_t 的毫秒计数能撑多久？
     *      2^32 = 4,294,967,296 ms
     *           = 4,294,967.296 s
     *           = 71,582.8 分钟
     *           = 1,193.05 小时
     *           = 49.71 天
     *    → 连续运行 49.7 天后 g_tick_ms 会从 0xFFFFFFFF 回绕到 0。 */

    /* ② ★ 错误写法：直接比大小
     *      if (g_tick_ms >= start + 500) { ... }
     *    回绕时刻的灾难：
     *      start      = 0xFFFFFF00（快要溢出了）
     *      start+500  = 0x000000F4（已经溢出回绕了！）
     *      g_tick_ms  = 0x00000010（回绕后的实际时间）
     *      判断 0x10 >= 0xF4  → 假 → 永远等不到
     *    → 现象：设备连续运行 49.7 天后，所有基于时间的逻辑全部卡死。 */

    /* ③ 正确写法：用无符号减法
     *      if ((uint32_t)(g_tick_ms - start) >= 500) { ... }
     *    无符号减法在 C 语言里就是"模 2^32 的减法"，天然处理回绕：
     *      g_tick_ms - start = 0x00000010 - 0xFFFFFF00
     *                        = 0x00000110 （模 2^32 后）= 272
     *      272 >= 500 → 假 → 正确（确实还没到 500ms）
     *    ★ 前提：间隔 < 2^32 ms（49.7 天），这对任何实际应用都够。
     *      只要不跨越两个回绕点，这个写法就永远正确。 */

    /* ④ 还有一个精度问题：last = g_tick_ms 会让周期"漂移"
     *    因为任务执行本身要花时间，每次都会晚一点点，误差累积。
     *    改进：last += 500;
     *    这样即使某次晚了 3ms，下次会自动补偿回来（前提是不要连着晚太久）。 */
}
1ms 时基的 CPU 代价与选型建议

代价：1ms 一次中断 → 1000 × (24 周期进出 + 约 20 周期主体) = 44,000 周期/秒 = 0.061% CPU。几乎免费，可以放心用。

用 TIM2 还是 SysTick？

  • SysTick：内核自带，不占外设定时器资源，HAL 库默认已经在用它做 HAL_Delay 的时基。缺点：一个系统只有一个，被 HAL/RTOS 占住之后你自己就没法改周期了。
  • 普通定时器（TIM2 等）：灵活，可以随便改周期，可以同时有好几个不同周期的时基（比如 1ms 给控制、10ms 给按键扫描、100ms 给显示刷新）。缺点：占一个定时器资源。

建议：纯裸机项目直接复用 HAL 的 HAL_GetTick() 就行；一旦你有多个不同周期的定时任务需求，就自己开一个 TIM 做 g_tick_ms，别去动 SysTick。无论如何，不要在 tick 中断里做任何耗时的事——它是所有时间逻辑的地基，地基一歪，全系统的时间都不准了。

中断与主循环共享数据

这一节是中断带来的全部新麻烦的集中地。第 1 节说过，中断的代价里有一条是「数据一致性成了新问题」——现在把它彻底讲清楚，一共五个要点。

要点一：volatile 为什么必不可少

编译器看不见中断。在它的视角里，你的程序是一条顺序执行的指令流，没有任何东西能在两条语句之间"从旁边"改变一个变量。于是它会理直气壮地做优化：

/* ================= 场景 ================= */
volatile uint8_t g_flag_ok  = 0;   /* ISR 里会置 1 */
uint8_t          g_flag_bad = 0;   /* 忘了 volatile */

void EXTI0_IRQHandler(void) { g_flag_ok = 1; g_flag_bad = 1; }

int main(void)
{
    while (1) {
        if (g_flag_ok)  { do_something(); }
        if (g_flag_bad) { do_something_else(); }
    }
}

/* ================= -O2 编译结果（ARMCC / GCC 都类似）================= */

/* ---- g_flag_ok（有 volatile）---- */
    LDR     r1, =g_flag_ok          ; 每轮循环都取一次地址
loop_ok:
    LDRB    r0, [r1]                ; ★ 每次都真的从内存读
    CMP     r0, #0
    BEQ     loop_ok
    BL      do_something
    B       loop_ok

/* ---- g_flag_bad（没有 volatile）---- */
    MOVS    r0, #0                  ; 编译器"证明"了它永远是 0
loop_bad:
    B       loop_bad                ; ★ 整个 if 被优化掉了！
                                    ;   do_something_else 一次都不会执行

/* ================= 结论 =================
 * 没有 volatile：编译器把变量缓存在寄存器里，或者干脆证明它是常量。
 *   中断改了内存，主循环看不到。
 *   现象：中断明明触发了（用调试器能看 ISR 进过），但主循环毫无反应。
 *
 * 有 volatile：每次都从内存重新读，"意外改变"被允许。
 *
 * ★ volatile 的准确语义（这个必须说清楚，很多人误解）：
 *   "这个变量可能被程序流程之外的力量改变，所以不要优化掉对它的访问"
 *   —— 它保证的是【每次访问都真的发生】，不是【访问是原子的】！
 *   volatile 解决不了 读-改-写 的竞态（见要点三），它只是让编译器别捣乱。 */

/* ================= 什么时候需要 volatile =================
 *   ① 中断和主循环共享的变量（无论读写）
 *   ② 硬件寄存器映射的内存（外设寄存器）
 *   ③ RTOS 里任务间共享、且可能被编译器"看不见地"改变的变量
 *   ④ 会被 DMA 写入的缓冲区
 *
 * 什么时候不需要：
 *   · 只在一个函数内使用的局部变量
 *   · 只在主循环里用、中断完全不碰的变量
 * ★ 不要为了"保险"给所有变量都加 volatile：
 *   它会让编译器放弃优化，代码变慢；而且会掩盖真正的设计问题。 */

要点二：临界区与关中断保护的正确写法

当一件事需要"要么全做完、要么一点没做"时，就需要临时关掉中断，做完再开。听起来很简单，但「不能只开不管」这一条会让很多人栽跟头。

/* ================= 错误写法 1：用完无脑开中断 ================= */
void bad1(void)
{
    __disable_irq();          /* PRIMASK = 1 */
    /* 临界区 */
    __enable_irq();           /* ★ PRIMASK = 0 —— 不管之前在什么状态 */
}

/* 灾难场景：如果这个函数是在【已经关中断的上下文】里被调用的
 *   （比如另一个临界区内部，或者 RTOS 的调度器里），
 *   那么返回时你会把中断【提前打开】，破坏外层的临界区保护。
 *   典型的症状：嵌套临界区里偶发的数据错乱，只在特定时序下出现。 */

/* ================= 错误写法 2：自己数嵌套层数 ================= */
static uint32_t g_critical_nesting = 0;
void bad2_enter(void) { if (g_critical_nesting++ == 0) __disable_irq(); }
void bad2_exit(void)  { if (--g_critical_nesting == 0) __enable_irq(); }
/* 看起来对了，但 g_critical_nesting 本身的读-改-写就不是原子的，
 * 而且它在多任务环境中会打架。不要自己造这个轮子。 */

/* ================= 正确写法：保存并恢复 PRIMASK ================= */
void good(void)
{
    uint32_t primask_saved = __get_PRIMASK();   /* ① 保存当前状态 */

    __disable_irq();                            /* ② 关中断（PRIMASK = 1） */

    /* ---------- 临界区：这段代码不会被任何中断打断 ---------- */
    /* 只放必须原子完成的【最短】操作！
     * 典型 3~10 条指令，超过 100 个周期就该重新设计。 */
    shared_counter++;
    shadow_copy = shared_counter;
    /* ------------------------------------------------------ */

    __set_PRIMASK(primask_saved);               /* ③ 恢复【原来的】状态，
                                                 *    而不是无脑开中断 */
}

/* ★ 用 CMSIS 的另一个等价写法（更简洁） */
void good2(void)
{
    uint32_t primask_saved = __get_PRIMASK();
    __set_PRIMASK(1);                 /* 关 */
    /* 临界区 */
    __set_PRIMASK(primask_saved);     /* 恢复原状 */
}

/* ================= 有哪些手段可以关中断 =================
 *   ① PRIMASK（CMSIS: __disable_irq / __enable_irq / __get_PRIMASK）
 *      · 只关【可配置优先级】的中断，NMI 和 HardFault 关不掉
 *      · 位宽 1 位，是最常用的全局开关
 *   ② BASEPRI（CMSIS: __set_BASEPRI / __get_BASEPRI）
 *      · 关掉"优先级数值 >= BASEPRI"的中断，也就是【只屏蔽低优先级】
 *      · ★ RTOS 用它做临界区：高优先级的实时中断照样能响应，
 *        只挡住低优先级的中断，减少对实时性的伤害
 *      · 用法：__set_BASEPRI(configMAX_SYSCALL_INTERRUPT_PRIORITY << (8 - 4))
 *   ③ FAULTMASK
 *      · 连 HardFault 都能关掉，只留 NMI。几乎不用，误用会导致
 *        程序出错时连 fault 都进不去，直接锁死。
 * ======================================================== */

要点三：读-改-写不是原子的，标志位会丢更新

这是最隐蔽、也最常见的中断并发 bug，而且它只在大压力下偶尔出现，能折磨你几个星期。

/* ================= 出问题的代码 ================= */
volatile uint8_t flags = 0;

/* 主循环 */
void main_loop(void) {
    if (some_condition) {
        flags |= 0x01;            /* 置位 bit0：表示"主循环这边有事件" */
    }
}

/* 中断 */
void EXTI0_IRQHandler(void) {
    flags |= 0x02;                /* 置位 bit1：表示"中断那边有事件" */
}

/* ================= 为什么错？看编译出来的三条指令 =================
 *
 *   flags |= 0x01;  编译成：
 *       LDRB  r0, [flags_addr]     ; ① 读
 *       ORR   r0, r0, #0x01        ; ② 改
 *       STRB  r0, [flags_addr]     ; ③ 写
 *
 * ★ 这三条指令【不是】原子的，中间任何时刻都可能进中断。
 *
 * ================= 丢更新的完整时序 =================
 *
 *   时间 →   主循环                        中断
 *   ─────────────────────────────────────────────────────────────
 *   ①        LDRB r0, [flags]  → r0 = 0x00
 *   ②                     ←──── 中断发生！────→
 *   ③                                       LDRB r1, [flags] → 0x00
 *   ④                                       ORR  r1, r1, #0x02
 *   ⑤                                       STRB r1, [flags] → flags = 0x02
 *   ⑥                     ←──── 中断返回 ────→
 *   ⑦        ORR  r0, r0, #0x01  → r0 = 0x01（r0 里还是旧的 0x00）
 *   ⑧        STRB r0, [flags]    → flags = 0x01
 *   ─────────────────────────────────────────────────────────────
 *   最终 flags = 0x01
 *   ★ 中断设的 bit1 被【完全抹掉】了！中断自己以为设成功了。
 *
 *   后果：偶发丢事件。计数器少加一次、状态机卡在某个状态、
 *         "偶尔丢一包数据" —— 这类 bug 能查到你怀疑人生，
 *         因为它只在两个事件的相对时序碰巧落在 ①②之间时才发生。
 *
 * ================= 三种正确写法 =================
 *
 * 【写法 1 · 最推荐】一个事件一个独立的标志字节 —— 消灭共享读-改-写
 * ------------------------------------------------------------------ */
volatile uint8_t g_flag_main  = 0;     /* 只有主循环写 */
volatile uint8_t g_flag_isr   = 0;     /* 只有 ISR 写 */

void main_loop(void) {
    if (some_condition) { g_flag_main = 1; }    /* 整字节写，原子 */
    if (g_flag_isr) { g_flag_isr = 0; /* 处理中断事件 */ }
}
void EXTI0_IRQHandler(void) {
    g_flag_isr = 1;                              /* 整字节写，原子 */
}
/* ★ 为什么这样就安全了：每个变量只有一个"作者"，
 *   写入是【单字节写】——在 Cortex-M 上对对齐的字节/半字/字的
 *   访问是单次总线事务，也就是【单拷贝原子】的。
 *   没有读-改-写的中间态，冲突就没有了。
 * ★ 代价：多占几个字节内存。值得。 */

/* 【写法 2】用临界区包住读-改-写
 * ------------------------------------------------------------------ */
volatile uint8_t flags = 0;

void main_loop_safe(void) {
    if (some_condition) {
        uint32_t pm = __get_PRIMASK();
        __disable_irq();
        flags |= 0x01;                 /* 关中断期间的读-改-写是安全的 */
        __set_PRIMASK(pm);
    }
}
void EXTI0_IRQHandler(void) {
    /* 中断里【不需要】关中断 —— 它自己就在中断上下文里，
     * 同级或低级中断进不来。只有更高优先级的中断才可能打断它，
     * 而那些中断不应该碰同一个 flags（否则是设计问题）。 */
    flags |= 0x02;
}
/* ★ 注意：如果两个【不同】的中断（不同优先级）都要改 flags，
 *   那么高优先级那个能打断低优先级那个，低优先级那边也必须加保护。 */

/* 【写法 3】位带（Bit-Band）—— 可选，理解原理即可
 * ------------------------------------------------------------------
 * Cortex-M3 支持"位带"：把某个内存区域的每一个位，映射成别名区的一个字。
 *   对别名区写 1 / 写 0，就等于直接操作目标位，硬件完成读-改-写。
 *
 *   SRAM 位带区：  0x20000000 ~ 0x200FFFFF
 *   SRAM 别名区：  0x22000000 ~ 0x23FFFFFF
 *   换算公式：别名地址 = 0x22000000 + (字节偏移 × 32) + (位号 × 4)
 *
 * #define BITBAND_SRAM(addr, bit) \
 *     (*(volatile uint32_t *)(0x22000000UL + \
 *       (((uint32_t)(addr) - 0x20000000UL) * 32UL) + ((bit) * 4UL)))
 *
 * volatile uint8_t flags = 0;   // 放在 SRAM 里
 *   BITBAND_SRAM(&flags, 0) = 1;     // 主循环置 bit0
 *   BITBAND_SRAM(&flags, 1) = 1;     // 中断置 bit1 —— 不会互相覆盖
 *
 * ★ 位带的写操作在总线层面是一次完整的读-改-写事务，
 *   不会被处理器上运行的中断"切开"。
 * ★ 缺点：地址换算容易写错；代码可读性差；换到没有位带的芯片
 *   （比如 Cortex-M0/M0+）就不能用了。
 * ★ 建议：知道有这回事就行，实际项目优先用写法 1。
 * ================================================================ */

要点四：多字节数据共享要加锁或双缓冲

单个 8/16/32 位对齐变量的读写是原子的，但一旦超过 32 位，或者是一个结构体，就会出问题：

数据类型中断与主循环共享时安全吗原因怎么做
uint8_t / uint16_t / uint32_t（对齐） 读/写安全（但读-改-写不安全） 单次总线事务，单拷贝原子 加 volatile 即可
uint64_t / double 不安全 要两条 32 位指令，可能被切开，读到"半个新值半个旧值" 临界区包住读写，或用序号/翻转标记
结构体 / 数组 / 字符串 不安全 要多次访问，中途被改写就自相矛盾（比如长度字段和内容不匹配） 双缓冲或临界区拷贝
DMA 写入的缓冲区 不安全 DMA 与 CPU 并行工作，缓冲区内容随时在变 用 NDTR 算长度后拷出来；或半传输/传输完成中断里处理 
/* ================= 双缓冲（Double Buffering）=================
 * 核心思路：准备【两份】缓冲区，交替使用。
 *   中断只写"当前写入缓冲"，主循环只读"上一份完成的缓冲"。
 *   两边永远不碰同一块内存 → 不需要任何锁。
 * ============================================================= */

typedef struct {
    uint8_t  data[64];
    uint16_t len;
    uint32_t timestamp;
    uint8_t  crc;
} frame_t;

static frame_t  g_buf[2];                    /* 两份缓冲 */
static volatile uint8_t g_writing = 0;       /* 中断正在写哪一份（0 或 1）*/
static volatile uint8_t g_ready   = 0;       /* 主循环可以读哪一份 */
static volatile uint8_t g_has_new = 0;       /* 有没有新帧 */

/* 中断侧：写完整的一帧 */
void USART1_IRQHandler(void)
{
    if (/* 一帧接收完成 */) {
        uint8_t w = (uint8_t)(g_writing ^ 1U);   /* 写"另一份" */

        /* 把这一帧完整地写进 g_buf[w] */
        build_frame(&g_buf[w]);

        /* ★ 关键：等整个结构体写完了，最后【一次性】发布。
         *   这个赋值是单字节写，是原子的。
         *   主循环看到 g_has_new 变 1 时，g_buf[w] 已经完整了。 */
        g_ready   = w;
        g_has_new = 1;

        g_writing = w;                            /* 下次写另一份 */
    }
}

/* 主循环侧：读走已经完成的那一份 */
void main_loop(void)
{
    if (g_has_new) {
        uint8_t r = g_ready;          /* 先取出索引 */
        process_frame(&g_buf[r]);     /* 慢慢处理，中断在写另一份，互不干扰 */
        g_has_new = 0;
    }
}

/* ★ 为什么不需要关中断？
 *   · 中断只写 g_buf[g_writing ^ 1]，主循环读的 g_buf[g_ready]
 *     在 g_has_new 置 1 之前就已经完整了
 *   · "发布"这个动作只用一个字节的赋值完成，本身原子
 * ★ 唯一的边界情况：如果中断在极短时间内连续来两帧，
 *   而主循环还没处理完第一帧，第二帧会覆盖 g_buf[g_writing ^ 1] ——
 *   也就是覆盖那份"还没被读走"的数据。
 *   解决办法：加一个"缓冲区忙"标志，中断发现忙就直接丢弃并计数；
 *             或者用 3 个以上的缓冲区（多缓冲 / 队列）。 */

要点五：FromISR 版本 API 的规则

如果你用了 FreeRTOS，一定会看到每个 API 都有两个版本：xQueueSend() 和 xQueueSendFromISR()。在中断里必须用带 FromISR 后缀的那个，这不是风格建议，是硬性规则。

/* ================= 普通版 API 在中断里调用会怎样 =================
 *
 * 以 xQueueSend() 为例，它内部会做这些事：
 *   ① 调用 taskENTER_CRITICAL() —— 关中断 + 内核嵌套计数 +1
 *   ② 操作队列的读写指针和等待任务链表
 *   ③ 如果有任务因为等这个队列而被阻塞，把它移出阻塞列表、加入就绪列表
 *   ④ 调用 taskEXIT_CRITICAL()
 *   ⑤ ★ 最后可能调用 portYIELD() 触发一次任务切换（PendSV）
 *
 * 在中断里调用的问题：
 *   · ③ 里操作内核链表时，如果当前就在中断上下文，
 *     内核的"当前任务"状态是不完整的（任务栈不在 PSP 上，
 *     pxCurrentTCB 指向的任务可能正准备被切换掉）
 *   · ⑤ 的 portYIELD() 会立刻尝试切换任务，
 *     但中断还没返回、硬件栈帧还在 MSP 上 → 内核状态机彻底乱掉
 *   · FreeRTOS 通常用 configASSERT() 拦住这种情况：
 *          configASSERT( ( portNVIC_INT_CTRL_REG & portVECTACTIVE_MASK ) == 0 );
 *     也就是"断言当前不在中断上下文"。如果你看到这个断言失败，
 *     就是你误用了普通版 API。
 * ================================================================ */

/* ================= 正确用法 ================= */
#include "FreeRTOS.h"
#include "queue.h"
#include "task.h"

QueueHandle_t g_queue;

void EXTI0_IRQHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;   /* ★ 必须初始化为 pdFALSE */

    if (EXTI_GetITStatus(EXTI_Line0) != RESET) {

        uint32_t event = 0x01;

        /* ① 用 FromISR 版本：它内部【不关中断】（因为已经在中断里了，
         *    同级中断进不来），只操作内核链表；
         *    而且它不会自己触发任务切换，而是把"需不需要切换"
         *    通过第 3 个参数告诉你。 */
        xQueueSendFromISR(g_queue, &event, &xHigherPriorityTaskWoken);

        EXTI_ClearITPendingBit(EXTI_Line0);
    }

    /* ② ★ 在 ISR 的【最后】、返回之前，统一请求切换。
     *
     *   portYIELD_FROM_ISR 做的事：
     *     · 如果 xHigherPriorityTaskWoken 是 pdTRUE（说明刚才那个操作
     *       让一个比当前任务优先级更高的任务变成了就绪态）
     *     · 就挂起 PendSV 异常（写 ICSR.PENDSVSET）
     *     · PendSV 优先级最低，所以它会等【所有】中断都执行完、
     *       在最后一个中断退出时才真正做任务切换
     *   → 这样任务切换永不会打断任何 ISR，内核状态是安全的。
     *
     *   如果 xHigherPriorityTaskWoken 是 pdFALSE，这个宏什么都不做，
     *   也就是说"没必要切换，直接返回接着跑当前任务"。 */
    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

/* ================= 三个必须记住的规则 =================
 *   ① 中断里只能用带 FromISR 后缀的 API
 *      （FreeRTOS 里以 FromISR 结尾的函数，都保证不关中断、不切任务）
 *   ② xHigherPriorityTaskWoken 必须初始化为 pdFALSE，
 *      并且用【取地址】传进去（它是输出参数）
 *   ③ 一个 ISR 里可能有多次 FromISR 调用，它们会累加同一个变量，
 *      所以只需要在【整个 ISR 的最后】调用一次 portYIELD_FROM_ISR
 * ===================================================== */

/* ================= 顺带一提：FreeRTOS 的临界区是两个不同的宏 =================
 *   任务里：  taskENTER_CRITICAL() / taskEXIT_CRITICAL()
 *             → 用 BASEPRI 屏蔽低优先级中断，允许嵌套（内部有嵌套计数）
 *   中断里：  taskENTER_CRITICAL_FROM_ISR() / taskEXIT_CRITICAL_FROM_ISR()
 *             → ★ 必须用这一对，而且它们的返回值【必须】用来恢复状态：
 *                 UBaseType_t saved = taskENTER_CRITICAL_FROM_ISR();
 *                 ...  // 临界区
 *                 taskEXIT_CRITICAL_FROM_ISR(saved);
 *               调用 taskEXIT_CRITICAL_FROM_ISR() 时不传参数 =
 *               无脑把 BASEPRI 清零 = 破坏外层的保护。
 * ========================================================================= */

HardFault 定位：从栈帧里把出错的 PC 捞出来

第 2 节讲过「故障升级」，知道几乎所有内存/总线/用法错误最终都会以 HardFault 的形式出现。但知道"进了 HardFault"没有用——你需要知道"哪一行代码触发的"。好消息是：硬件已经把答案压在栈上了，只要你会读。

#include "stm32f1xx.h"
#include <stdint.h>

/* ---------------------------------------------------------------------------
 * 现场记录：全部声明为全局，方便在调试器的 Watch 窗口里直接看
 * -------------------------------------------------------------------------*/
volatile uint32_t g_hf_r0;
volatile uint32_t g_hf_r1;
volatile uint32_t g_hf_r2;
volatile uint32_t g_hf_r3;
volatile uint32_t g_hf_r12;
volatile uint32_t g_hf_lr;         /* 出错时的 LR：能看出是从哪个函数调过去的 */
volatile uint32_t g_hf_pc;         /* ★★★ 出错时正在执行的指令地址 —— 就靠它定位 */
volatile uint32_t g_hf_xpsr;
volatile uint32_t g_hf_lr_exc;     /* EXC_RETURN：判断当时用的是哪个栈 */
volatile uint32_t g_hf_cfsr;       /* 具体故障原因 */
volatile uint32_t g_hf_hfsr;
volatile uint32_t g_hf_mmfar;
volatile uint32_t g_hf_bfar;
volatile uint32_t g_hf_psp;        /* 出错时的 PSP（如果用的是 PSP）*/
volatile uint32_t g_hf_msp;        /* 出错时的 MSP */

/* ---------------------------------------------------------------------------
 * HardFault_Handler：必须用 __attribute__((naked)) 或汇编，
 * 因为 C 函数的序言会改变栈指针，栈帧的位置就不对了。
 *
 * 这里做三件事：
 *   ① 读 LR 判断出错时用的是 MSP 还是 PSP
 *   ② 把对应的栈指针传给 C 函数
 *   ③ 跳到 C 处理函数（不返回）
 * -------------------------------------------------------------------------*/
__attribute__((naked)) void HardFault_Handler(void)
{
    __asm volatile (
        "tst    lr, #4          \n"   /* 测 EXC_RETURN 的 bit2        */
        "ite    eq              \n"
        "mrseq  r0, msp         \n"   /* bit2 == 0 → 用的是 MSP（裸机常见）*/
        "mrsne  r0, psp         \n"   /* bit2 == 1 → 用的是 PSP（RTOS 任务）*/
        "mov    r1, lr          \n"   /* 把 EXC_RETURN 也传进去      */
        "b      hardfault_report\n"   /* 跳到 C 函数（不返回）        */
    );
}

/* ---------------------------------------------------------------------------
 * C 处理函数：参数 sf 指向硬件压的那个栈帧
 * -------------------------------------------------------------------------*/
void hardfault_report(uint32_t *sf, uint32_t exc_return)
{
    /* ------------------------------------------------------------------
     * ① 栈帧布局：8 个寄存器，顺序固定（这是硬件约定，不会变）
     *      sf[0] = R0      sf[4] = R12
     *      sf[1] = R1      sf[5] = LR
     *      sf[2] = R2      sf[6] = PC   ← ★ 就是它
     *      sf[3] = R3      sf[7] = xPSR
     * ------------------------------------------------------------------ */
    g_hf_r0   = sf[0];
    g_hf_r1   = sf[1];
    g_hf_r2   = sf[2];
    g_hf_r3   = sf[3];
    g_hf_r12  = sf[4];
    g_hf_lr   = sf[5];
    g_hf_pc   = sf[6];          /* ★ 出错指令的地址 */
    g_hf_xpsr = sf[7];
    g_hf_lr_exc = exc_return;

    /* ------------------------------------------------------------------
     * ② 读故障原因寄存器（这些才是"为什么出错"的答案）
     * ------------------------------------------------------------------ */
    g_hf_cfsr  = SCB->CFSR;
    g_hf_hfsr  = SCB->HFSR;
    g_hf_mmfar = SCB->MMFAR;
    g_hf_bfar  = SCB->BFAR;
    g_hf_psp   = __get_PSP();
    g_hf_msp   = __get_MSP();

    /* ------------------------------------------------------------------
     * ★ 顺手解码一下 CFSR，常见的几位：
     *   CFSR 是一个 32 位寄存器，分三段：
     *     bit[7:0]   MMFSR  —— MemManage 故障状态
     *         bit0 IACCVIOL    取指访问违规
     *         bit1 DACCVIOL    数据访问违规
     *         bit7 MMARVALID   MMFAR 里的地址有效
     *     bit[15:8]  BFSR   —— BusFault 故障状态
     *         bit0 IBUSERR     取指总线错误
     *         bit1 PRECISERR   精确数据总线错误（出错地址在 BFAR 里）
     *         bit2 IMPRECISERR 不精确总线错误（BFAR 里没有地址，难查）
     *         bit7 BFARVALID   BFAR 里的地址有效
     *     bit[23:16] UFSR   —— UsageFault 故障状态
     *         bit0 UNDEFINSTR  未定义指令
     *         bit1 INVSTATE    无效状态（比如试图进入 ARM 状态）
     *         bit3 NOCP        没有协处理器（比如 F103 上用浮点指令）
     *         bit8 UNALIGNED   非对齐访问
     *         bit9 DIVBYZERO   整数除零
     *   HFSR：
     *     bit30 FORCED = 1  → 这个 HardFault 是【升级】来的，
     *                          真正的错误原因看 CFSR
     *     bit1  VECTTBL = 1 → 取中断向量时总线出错
     *                          （几乎总是 VTOR 配错了）
     * ------------------------------------------------------------------ */
    if ((g_hf_hfsr & (1UL << 30)) != 0U) {
        /* FORCED = 1：是被升级上来的，去 CFSR 里找真凶 */
        if ((g_hf_cfsr & 0x000000FFUL) != 0U) {
            /* MemManage：看 g_hf_mmfar */
        }
        if ((g_hf_cfsr & 0x0000FF00UL) != 0U) {
            /* BusFault：看 g_hf_bfar */
        }
        if ((g_hf_cfsr & 0x00FF0000UL) != 0U) {
            /* UsageFault：看 g_hf_ufsr 的低几位 */
        }
    }

    /* ------------------------------------------------------------------
     * ③ 停在这里，方便你在调试器里看上面那些全局变量
     * ------------------------------------------------------------------ */
    __disable_irq();
    while (1) {
        /* 打断点在这一行，然后在 Watch 窗口里加 g_hf_pc、g_hf_cfsr */
    }
}

/* ===========================================================================
 *  怎么用 g_hf_pc 定位到具体代码行？
 * ===========================================================================
 *
 * 【方法 1 · Keil MDK：用 .map 文件】
 *   编译后会生成 Project.map（在 Objects 或 Listings 目录）。
 *   打开它，搜索 g_hf_pc 的值（比如 0x08000F2C），你会看到类似的段：
 *
 *       i.key_action      0x08000f2c   Section   16   main.o(.text.key_action)
 *       i.pid_calc        0x08000f50   Section  120   control.o(.text.pid_calc)
 *
 *   → 0x08000F2C 正好是 key_action 的起始地址，说明错误在这个函数里。
 *   ★ 注意地址是【十六进制】，map 里通常写成 0x08000f2c（小写）。
 *
 * 【方法 2 · 反汇编精确定位（推荐）】
 *   Keil:  fromelf --text -c -o dis.txt Project.axf
 *   GCC :  arm-none-eabi-objdump -d Project.elf > dis.txt
 *   在 dis.txt 里搜索那个地址，能直接看到是哪一条指令：
 *
 *       8000f2c:  6803        LDR   r3, [r0, #0]
 *       8000f2e:  2100        MOVS  r1, #0
 *       8000f30:  f7ff fffe   BL    8000f20 <malloc>
 *
 *   ★ 再配合 g_hf_r0 ~ g_hf_r3、g_hf_r12、g_hf_lr，
 *     就能还原"当时各个寄存器里是什么"，进而知道为什么出错。
 *     比如 LDR r3, [r0, #0] 出错，而 g_hf_r0 = 0x00000000，
 *     那就是典型的空指针解引用。
 *
 * 【方法 3 · 在线调试（最方便）】
 *   Keil 的 Debug → 打开 Disassembly 窗口 → 在地址栏输入 g_hf_pc 的值 →
 *   光标就跳到那条出错的指令上。同时在 Registers 窗口对照栈里的值。
 *
 * 【一个重要的提醒】
 *   g_hf_pc 指向的是【出错的那条指令】。但如果是"调用了一个野指针函数"，
 *   PC 会落在一个完全无关的地址（甚至不是合法代码区）——
 *   这时要看 g_hf_lr（出错时的链接寄存器），它指向"调用发生的位置"，
 *   用 g_hf_lr - 4 去 map 里搜，就能找到那个野指针是从哪里来的。
 * ========================================================================= */

光会读栈还不够，还得知道什么代码会让它进 HardFault。下面五个例子都是真实项目里最常遇到的，可以自己抄下来跑一遍，看看 CFSR 各是哪一位：

#include "stm32f1xx.h"

volatile uint32_t g_zero = 0;
volatile uint32_t g_result;
volatile int32_t  g_a = 100, g_b = 0;

/* ===========================================================================
 * 例 1：整数除零 —— UsageFault 的 DIVBYZERO（CFSR bit25）
 * ===========================================================================
 * ★ 前提：必须先把 CCR.DIV_0_TRP 置 1，否则硬件不报错，
 *   而是【返回 0】作为商 —— 这才是更危险的情况：
 *   你算出一个错误的 0，程序继续跑，错误扩散到很远的地方才暴露。
 * =========================================================================*/
void example_div_by_zero(void)
{
    SCB->CCR |= SCB_CCR_DIV_0_TRP_Msk;   /* 打开除零检查 */

    g_result = (uint32_t)(g_a / g_b);    /* g_b = 0 → ★ 触发 UsageFault
                                          *   → CFSR bit25 = 1
                                          *   → 因为没使能 UsageFault handler，
                                          *     升级成 HardFault，
                                          *     HFSR bit30 FORCED = 1 */
}

/* ===========================================================================
 * 例 2：访问 0x00000000（空指针 / 野指针）—— BusFault 的 PRECISERR
 * ===========================================================================
 * ★ 地址 0x00000000 在 STM32 上是被【启动模式电路】映射的：
 *   BOOT0=0 时它映射到 Flash（0x08000000）。
 *   所以访问 0x00000000 不一定是"访问不存在的内存" ——
 *   它可能是"访问 Flash 的第一个字"，那就不会出错！
 *   ★ 真正会出错的是访问【没有映射的地址】，比如 0x60000000 空白区。
 * =========================================================================*/
void example_null_pointer(void)
{
    uint32_t *p = (uint32_t *)0x00000000;

    g_result = *p;      /* 如果 0x00000000 映射到 Flash → 读到栈顶地址，不报错
                         * 如果映射到别的地方 → BusFault PRECISERR，
                         *   CFSR bit9 = 1（PRECISERR），BFAR = 出错地址 */

    /* 更典型的例子：结构体指针没初始化 */
    /* typedef struct { uint32_t a; } dev_t; */
    /* dev_t *dev = NULL; */
    /* dev->a = 1;   ← ★ 这才是真实项目里的头号 HardFault 来源 */
}

/* ===========================================================================
 * 例 3：非对齐访问 —— UsageFault 的 UNALIGNED（CFSR bit24）
 * ===========================================================================
 * ★ 前提：必须先把 CCR.UNALIGN_TRP 置 1。
 *   默认情况下 Cortex-M3 允许非对齐访问，
 *   硬件会悄悄拆成两次对齐访问，你完全感觉不到。
 *   这既是"方便"也是"陷阱"：在 x86 上写惯了的代码搬到 M0 上
 *   （M0 不支持非对齐访问）就会崩，而你完全不知道为什么。
 * =========================================================================*/
void example_unaligned(void)
{
    SCB->CCR |= SCB_CCR_UNALIGN_TRP_Msk;   /* 打开非对齐检查 */

    static uint8_t buffer[8] = {0};

    /* 取 buffer + 1 这个地址：它不是 4 的倍数 → 非对齐 */
    uint32_t *p = (uint32_t *)(void *)(buffer + 1);
    g_result = *p;      /* ★ 触发 UsageFault，CFSR bit24 = 1 */
    /* ★ 正确做法：buffer 定义为 uint32_t 数组，
     *   或者用 __attribute__((aligned(4))) / __align(4) 强制对齐。 */
}

/* ===========================================================================
 * 例 4：外设时钟没开 —— BusFault（★ F103 上头号原因）
 * ===========================================================================
 * 这个例子不会真的崩，因为 0x40010800 是 GPIOA 的地址，
 * 它在 AHB2 总线上，即使时钟关了读操作通常也不报错
 * （读回 0 或随机值）。但写法上它是最容易出错的地方：
 * =========================================================================*/
void example_no_clock(void)
{
    /* ★ 忘了 __HAL_RCC_GPIOA_CLK_ENABLE(); */

    GPIOA->CRL = 0x00000001U;   /* 时钟没开时写这个寄存器，
                                 * 在 APB 外设上可能触发 BusFault；
                                 * 也可能"写进去了但没用"，
                                 * 表现为"配置了 GPIO 但引脚没反应" */
    /* ★ 排查顺序：先确认时钟使能位，再看配置。
     *   外设"配置了但完全没反应"十有八九是时钟没开。 */
}

/* ===========================================================================
 * 例 5：栈溢出 —— 症状最不典型、最难查的一种
 * ===========================================================================
 * 栈从 SRAM 顶部向下生长，下面是 .bss / .data 段。
 * 栈溢出会【悄悄覆盖】全局变量，而不是立刻崩溃。
 * =========================================================================*/
void example_stack_overflow(void)
{
    /* 声明一个 2KB 的局部数组，而栈总共只有 1KB */
    uint8_t big_buffer[2048];

    for (uint32_t i = 0; i < 2048; i++) {
        big_buffer[i] = (uint8_t)i;    /* ★ 写穿栈底，覆盖全局变量和堆 */
    }
    /* 症状：
     *   · 某些全局变量莫名变成随机值（实际是 big_buffer 的内容）
     *   · 函数返回时跳到随机地址 → HardFault 或 LOCKUP
     *   · 调试器单步走几步就"跑飞"
     * 排查方法：
     *   · 看编译报告里的 "Stack Usage"（Keil 的 --callgraph 选项能生成）
     *   · 在启动文件里把 Stack_Size 加大再试
     *   · 给栈底下填魔术数字（0xDEADBEEF），运行时检查有没有被改
     *   · 用 FreeRTOS 的话打开 configCHECK_FOR_STACK_OVERFLOW */
}

 * 附：五个例子的 CFSR 判读速查
 * ===========================================================================
 *   例 1 除零        CFSR = 0x02000000（bit25 DIVBYZERO）
 *   例 2 空指针      CFSR = 0x00000200（bit9  PRECISERR），BFAR = 出错地址
 *   例 3 非对齐      CFSR = 0x01000000（bit24 UNALIGNED）
 *   例 4 时钟没开    CFSR = 0x00000200 附近，BFAR 指向外设地址
 *   例 5 栈溢出      CFSR 五花八门（因为跳到随机地址，
 *                    可能是不精确总线错误 IMPRECISERR bit10）
 *
 * ★ 共同点：HFSR 的 bit30（FORCED）永远是 1，

「中断不响应」的排查顺序

写中断的时候，"配好了但就是不响应"是最高频的问题。好消息是：从外设到 CPU，中断信号要穿过五道关卡，按顺序查一遍就能找到是哪一道没放行。按下面的顺序查，比乱试要快十倍。

外设 ────► ①外设标志 ────► ②外设中断使能 ────► ③NVIC使能 ────► ④优先级放行 ────► ⑤全局开关 ────► CPU
  信号         (SR/PR)          (CR/DIER/IMR)        (ISER)         (抢占比较)        (PRIMASK)

═══════════════════════════════════════════════════════════════════════════════
第 ① 关：中断源到底有没有产生请求？
═══════════════════════════════════════════════════════════════════════════════
  怎么查：
    · 在调试器里看外设的状态寄存器：
        外部中断 → EXTI->PR        （bit n = 1 表示第 n 线有请求）
        定时器   → TIMx->SR 的 UIF
        串口     → USARTx->SR 的 RXNE / IDLE / ORE
        ADC      → ADCx->SR 的 EOC
    · 或者用万用表/示波器直接量引脚：PA0 上到底有没有电平跳变？
    · 或者临时把引脚配成"推挽输出"翻转一下，看外部电路是否正常

  常见问题：
    · 引脚接错（接到了 PA1 但代码配的是 PA0）
    · 按键接 VCC 却配了下降沿（应该配上升沿）
    · 硬件上拉/下拉电阻没焊，引脚悬空，电平不确定
    · 外面的信号源本身没输出（比如光耦的限流电阻太大，输出不到低电平）

  ★ 这一关的判定：如果 EXTI->PR 的对应位【始终是 0】，
    那问题 100% 在"信号没到"或者"边沿配反了"，跟 NVIC 无关。

═══════════════════════════════════════════════════════════════════════════════
第 ② 关：外设自己的中断使能位开了吗？
═══════════════════════════════════════════════════════════════════════════════
  ★ 这一关最容易被忽略 —— 因为它和 NVIC 的使能是【两个完全独立的位】，
    很多教程只讲 NVIC_EnableIRQ，让人以为开了 NVIC 就够了。

  必须检查的位：
    · EXTI  → EXTI->IMR 的 bit n（Interrupt Mask Register，1 = 允许中断）
              ★ 注意别配成 EXTI->EMR（Event Mask Register）——
                那是"事件模式"，只送给其他外设，不产生中断！
    · TIM   → TIMx->DIER 的 UIE / CC1IE 等（Update Interrupt Enable）
              ★ 忘了 TIM_ITConfig(TIMx, TIM_IT_Update, ENABLE) 是很常见的漏
    · USART → USARTx->CR1 的 RXNEIE / TXEIE / IDLEIE
              ★ IDLEIE 忘了开 → 空闲中断永远不来
    · ADC   → ADCx->CR1 的 EOCIE / JEOCIE / AWDIE
    · DMA   → DMA_Channelx->CCR 的 TCIE / HTIE / TEIE（传输完成/半完成/错误）

  标准库对应的函数：
    EXTI_Init(…) 里 EXTI_LineCmd = ENABLE   → 配 EXTI->IMR
    TIM_ITConfig(TIMx, TIM_IT_Update, ENABLE) → 配 DIER
    USART_ITConfig(USARTx, USART_IT_RXNE, ENABLE) → 配 CR1
    DMA_ITConfig(DMA1_Channelx, DMA_IT_TC, ENABLE) → 配 CCR

═══════════════════════════════════════════════════════════════════════════════
第 ③ 关：NVIC 使能位开了吗？
═══════════════════════════════════════════════════════════════════════════
  怎么查：
    · 调试器里看 NVIC->ISER[IRQn >> 5] 的第 (IRQn & 31) 位
      例：EXTI0_IRQn = 6 → NVIC->ISER[0] 的 bit6
    · 代码里 NVIC_EnableIRQ(EXTI0_IRQn) 或 NVIC_Init(…Cmd=ENABLE) 有没有执行到
    · ★ 断点确认：这句代码真的跑过了吗？（会不会被前面的某个
      return / if 分支跳过去了，或者初始化函数压根没被调用）

  常见问题：
    · 写了 NVIC_EnableIRQ 但初始化函数没被 main 调用
    · 用了 NVIC->ICER 想除能结果写 0（写 1 才有效），实际没除能
    · 上电初始化的"虚假挂起"没清，导致刚使能就进一次然后
      在 ISR 里卡住（看起来像"只响应一次"）

═══════════════════════════════════════════════════════════════════════════════
第 ④ 关：优先级放行了吗？
═══════════════════════════════════════════════════════════════════════════════
  这一关有两个子问题：

  (a) 这个中断自己的优先级数值是多少？
      · 调试器看 NVIC->IPR[IRQn]
      · ★ 记住：数值越小优先级越高。有人把它设成 15（最低），
        然后主循环里另一个抢占 0 的中断一直在跑，它就永远排不上队。

  (b) 当前有没有更高优先级的 ISR 正卡在那里不出来？
      · 看 NVIC->IABR：哪个位是 1，就说明那个中断的活动位没清掉，
        也就是"它的 ISR 还没返回"
      · 看 __get_IPSR()：非 0 就说明现在在某个 ISR 里
      · ★ 经典现场：一个更高优先级的 ISR 里写了 HAL_Delay 或者
        一个死等循环 → 它永远不出来 → 所有低优先级中断全部停摆。
        现象是"高优先级中断正常，其他所有中断都死了"。

  ★ 还有一个隐蔽的子问题：优先级分组。
    如果你在别处改了分组（或者说 HAL_Init 把它设成了 GROUP_4），
    而你按 GROUP_2 的语义去理解优先级，就会误判抢占关系。

═══════════════════════════════════════════════════════════════════════════════
第 ⑤ 关：全局中断有没有被关掉？
═══════════════════════════════════════════════════════════════════════════════
  怎么查：
    · __get_PRIMASK() 返回值：1 表示可配置中断【全部关闭】
    · __get_BASEPRI() 返回值：非 0 表示屏蔽了"优先级数值 >= BASEPRI"的中断
      （注意 CMSIS 里 BASEPRI 是左对齐的，要 >> 4 才是优先级数值）
    · __get_FAULTMASK()：几乎不该是 1

  常见问题：
    · 某个函数 __disable_irq() 之后在返回路径上漏了恢复 → 中断永久关闭
    · 用了 __enable_irq() 而不是恢复 PRIMASK，破坏了外层临界区
    · RTOS 里 taskENTER_CRITICAL() 没有配对的 taskEXIT_CRITICAL()，
      内核嵌套计数一直 > 0，BASEPRI 一直被设着
    · HardFault_Handler 里 __disable_irq() 之后卡住（这种情况下
      整个系统都不响应，不只是某一个中断）

  ★ 最可靠的检查方式：在调试器里停下来，直接在 Watch 窗口写
      __get_PRIMASK()  、 NVIC->ISER[0] 、 NVIC->IABR[0]
    这三项一起看，五关的状态基本就全知道了。

═══════════════════════════════════════════════════════════════════════════════
【额外第 ⑥ 关：中断向量和 ISR 名字对不对？（前面五关都过了才查这里）
═══════════════════════════════════════════════════════════════════════════════
  · ISR 函数名必须和启动文件里向量表规定的名字【一字不差】：
        EXTI0_IRQHandler   ✓
        EXTI0_IRQhandler   ✗（大小写错了）
        EXTI0_Handler      ✗
  · ★ 查法：打开 startup_stm32f10x_md.s，搜索你的中断名，
    看它那一行写的是不是你要的名字。
  · 用 Bootloader 的话，VTOR 设了吗？（忘了设 VTOR 是"中断全部不响应"的经典原因）
  · 用 extern "C" 了吗？（C++ 里函数名会被 name mangling，链接器找不到）
  · ★ 最狠的验证法：用软件直接触发中断，绕过前面所有关卡 ——

        NVIC_SetPendingIRQ(EXTI0_IRQn);   /* 直接挂起，不经过外设 */
        （或者 NVIC->ISPR[0] = (1UL << 6); ）

    如果这样能进 ISR → 说明 ③④⑤关和 ISR 本身都是好的，
                        问题一定在 ①②关（外设侧）
    如果这样也进不去 → 说明问题在 ③④⑤关或 ISR 名字
    ★ 这一个测试就能把排查范围砍掉一半，是最该先做的事。

把这段做成一个 checklist 贴在工位上

真实项目里最省时间的做法是把五关的检查代码写成一个 irq_debug(IRQn) 函数，一次性把该中断的全部状态打印/存到变量里：

typedef struct {
    uint32_t irqn;
    uint32_t nvic_enabled;    /* ISER 对应位 */
    uint32_t nvic_pending;    /* ISPR 对应位 */
    uint32_t nvic_active;     /* IABR 对应位 */
    uint32_t priority;        /* 优先级数值 0~15 */
    uint32_t primask;
    uint32_t basepri;
    uint32_t ipsr;            /* 当前异常号，0 = 在主循环里 */
} irq_state_t;

void irq_debug(uint32_t irqn, irq_state_t *st)
{
    uint32_t idx = irqn >> 5;
    uint32_t bit = irqn & 0x1FUL;

    st->irqn          = irqn;
    st->nvic_enabled  = (NVIC->ISER[idx] >> bit) & 1UL;
    st->nvic_pending  = (NVIC->ISPR[idx] >> bit) & 1UL;
    st->nvic_active   = (NVIC->IABR[idx] >> bit) & 1UL;
    st->priority      = NVIC-GetPriorityRaw(irqn);   /* 注意要 >> 4 */
    st->primask       = __get_PRIMASK();
    st->basepri       = __get_BASEPRI();
    st->ipsr          = __get_IPSR();
}

/* 在调试器的 Watch 窗口里看 st 的所有字段：
 *   nvic_enabled = 0  → 第 ③ 关没过
 *   nvic_pending = 1 且 nvic_active = 0 且 ipsr != 0
 *                     → 请求到了但被优先级挡住（第 ④ 关），
 *                       或者正卡在更高优先级的 ISR 里
 *   primask = 1       → 第 ⑤ 关没过
 *   全都正常但就是不来 → 回去查第 ①② 关（外设侧） */

常见误解与坑

下面这十条，是我见过（以及自己踩过）最多次的。每一条都按「错误认知 → 为什么错 → 正确做法」写，你可以当成一张检查表来对照自己的代码。

坑 1 · 「中断服务函数就是个普通函数，写长一点没关系」

错误认知：ISR 也是 C 函数，我在里面加点延时、刷个屏、算一小段 PID，能跑就行。

为什么错：ISR 执行期间，同级和更低优先级的中断全部被挡住。一个耗时 1ms 的 ISR，意味着所有低优先级中断都要额外延迟最多 1ms。如果这个 ISR 每 100µs 触发一次、每次要 200µs，那 CPU 有 100% 的时间在中断里，主循环一行都跑不了——而且更糟的是，低优先级中断会因为不断被抢占而永远得不到执行。中断是实时性的来源，一个长 ISR 会把整个系统的实时性一起拖垮。

正确做法：ISR 里只做三件事——清标志、搬数据、置标志，目标控制在几十个周期内。所有处理逻辑放主循环（或 RTOS 任务）里。判断标准：如果 ISR 里出现了 while、Delay、printf、malloc、浮点运算，那就是设计错了，回去重构。

坑 2 · 「优先级数字越大，优先级越高」

错误认知：我在 51 上习惯了「IP 写 1 是高优先级」，到了 STM32 也把最要紧的中断设成 HAL_NVIC_SetPriority(IRQn, 15, 0)，觉得 15 是最高级。

为什么错：Cortex-M 的方向与 51 完全相反：数值越小，优先级越高。0 是最高优先级，15 是最低。你把最紧急的中断设成 15，它就变成了全场最不着急的那一个——任何抢占优先级 0~14 的中断都能打断它，而它永远打断不了别人。这个错误不会报错、不会崩，只会表现为「这个中断的响应时间莫名其妙地长」，非常难查。

正确做法：记住一句话——「0 号最急」。给中断排优先级时，先在心里列一个「谁最不能等」的清单，最急的给 0 或 1，最不急的给 15。另外记住 HAL 库的默认值：HAL_Init() 会把 SysTick 的优先级设成 15（最低），这通常是对的——时基被打断几毫秒不影响系统运行。

坑 3 · 「子优先级高的也能打断正在执行的中断」

错误认知：中断 A 抢占优先级 1、子优先级 3；中断 B 抢占优先级 1、子优先级 1。我觉得 B 的子优先级更高，所以 B 应该能打断 A。

为什么错：这是最容易被误解的一条规则。子优先级只有一个作用：当多个中断同时处于挂起状态时，决定先执行谁。它完全不能让一个中断打断另一个正在执行的中断。上面那个例子里，A 和 B 的抢占优先级相同，所以它们之间没有任何嵌套关系——B 必须等 A 执行完才能开始。你会看到「B 明明优先级更高，却要等 A 跑完」的现象，然后开始怀疑芯片有问题。

正确做法：把两条规则分开记：抢占优先级 → 决定能不能打断（嵌套）；子优先级 → 决定同时挂起时谁排队靠前。要让两个中断能嵌套，必须让它们的抢占优先级不同。还有一个容易忽略的推论：在 NVIC_PRIORITYGROUP_0 分组下（0 位抢占、4 位子优先级），所有中断的抢占优先级都是 0，也就是全部同级，系统里根本不会有任何嵌套。推理题里问「这个分组下能嵌套的有序对有几组」，答案就是 0。

坑 4 · 「在中断里调用 HAL_Delay 等一小会儿没关系」

错误认知：我需要在中断里等 1ms 让硬件稳定，HAL_Delay(1) 就一行，很简单。

为什么错：HAL_Delay 的实现是一个死循环，等的是全局变量 uwTick 往前跳，而 uwTick 只在 SysTick 中断里才加一。如果你当前所在的 ISR 的抢占优先级 大于等于 SysTick 的优先级（数值上小于等于，也就是「不比 SysTick 低」），那么 SysTick 中断进不来 → uwTick 永远不变 → 这个死循环永远出不去。整个系统就此卡死，连看门狗都可能因为喂狗任务在主循环里而被复位。而在 51 上，Delay 通常是空循环数数，进中断也能出来——所以从 51 转过来的人特别容易犯这个错。

正确做法：绝不在任何 ISR 里调用依赖中断的延时函数。需要「等一会儿再做事」，就让 ISR 置一个标志，由主循环处理；或者启动一个单次定时器，在定时器中断里做后续动作（这正是前面按键去抖方案 B 的思路）。如果一定要在 ISR 里等硬件，也只能用不依赖中断的空循环，但那依然是个坏主意——它会拉长 ISR。

坑 5 · 「忘了 volatile 只是性能问题」

错误认知：加 volatile 会让编译器不能优化、代码变慢，不加也能跑，那就不加。

为什么错：这不是性能问题，是正确性问题。编译器看不见中断，它会认为「主循环里没改过的变量就是不变的」，于是把变量缓存在寄存器里，甚至直接证明「它永远是 0」而把整个 if 删掉。结果就是：中断确实进了、确实改了内存，但主循环永远读不到。症状极有迷惑性——用调试器看内存里那个变量是 1，主循环却毫无反应；把优化等级从 -O2 改成 -O0 又突然好了。这类 bug 会随着你「优化代码」而突然出现。

正确做法：中断和主循环共享的每个变量都加 volatile；被 DMA 写入的缓冲区也要加。同时记住 volatile 保证不了原子性——它只保证「每次访问都真的发生」，不保证「读-改-写」不被打断（见坑 6）。另外，不要为了保险给所有变量都加，那会放弃优化、掩盖真正的设计问题。

坑 6 · 「flags |= 1 这种写法我用了很多年，没出过问题」

错误认知：标志位用 |= 置位是最自然的写法，编译出来就一条指令，不会有事。

为什么错：flags |= 0x01 编译出来是三条指令：读（LDRB）、改（ORR）、写（STRB）。这三条之间任何时刻都可能进中断。经典的丢更新时序是：主循环读完（读到 0x00）→ 中断进来把 flags 置成 0x02 并返回 → 主循环用刚才那份旧的 0x00 做或运算得到 0x01 并写回 → 中断设的 bit1 被彻底抹掉。问题是这个窗口只有几个周期宽，两个事件的相对时序必须恰好落在里面才发生——所以它表现为「一天偶发一两次丢事件」，你能查到自己怀疑人生。

正确做法：首选「一个事件一个独立的标志字节」——每个变量只有一个「作者」（要么主循环写、要么 ISR 写），整字节写是单次总线事务、天然原子，冲突就不存在了，代价只是多几个字节内存。次选是用临界区把读-改-写包起来（保存并恢复 PRIMASK）。如果实在要用位操作，可以了解 位带（bit-band）：对别名区的写是一次完整的读-改-写事务，不会被中断切开。

坑 7 · 「关中断只要 __disable_irq() 和 __enable_irq() 成对就行」

错误认知：临界区就是「关中断 → 做事 → 开中断」，一关一开，成对出现就没问题。

为什么错：__enable_irq() 做的事是把 PRIMASK 无条件清成 0——也就是「不管之前什么状态，现在开」。如果这个函数是在已经关中断的上下文里被调用的（嵌套的临界区、RTOS 的调度器内部、另一个库函数的保护段里），返回时你就把中断提前打开了，外层的临界区保护被无声地破坏。症状是「嵌套临界区里偶发数据错乱，只在特定时序下出现」，和坑 6 一样难查。「只开不管」是嵌入式里最经典的并发错误之一。

正确做法：保存并恢复 PRIMASK：uint32_t pm = __get_PRIMASK(); __disable_irq(); /* 临界区 */ __set_PRIMASK(pm);。用 RTOS 的话用 taskENTER_CRITICAL()/taskEXIT_CRITICAL()（它内部用 BASEPRI，只屏蔽低优先级中断，允许嵌套，并且自己维护嵌套计数）；在 ISR 里则必须用 taskENTER_CRITICAL_FROM_ISR() 并且用返回值恢复。

坑 8 · 「中断里用 printf、浮点运算、malloc 也没什么，能跑就行」

错误认知：我在中断里 printf 打印一句调试信息，或者算个浮点、动态申请一小块内存，程序看起来跑得挺好。

为什么错：这三件事各有各的坑，而且都是「暂时能跑，压力大了就崩」的类型：① printf 通过串口发送是阻塞的（等 TXE 标志），一句 40 字符的打印在 115200 下要 3.5ms，而且 printf 内部有缓冲区和锁，不可重入——两个中断同时打印会输出乱码甚至破坏内部状态。② 浮点运算：F103 的 Cortex-M3 没有硬件 FPU，浮点靠软件模拟，一条乘法可能几百个周期；即使用有 FPU 的 M4，默认的「惰性保护」如果没使能，编译器会在 ISR 序言里额外压 16~17 个 FPU 寄存器。③ malloc 要操作堆的空闲链表，是典型的不可重入操作——中断打断了一次 malloc 再调用一次 malloc，链表指针就废了，之后所有的内存分配都可能返回重叠的地址。

正确做法：ISR 里只做整数运算、只搬数据。要打印调试信息，用「ISR 往环形缓冲区写字节 → 主循环取出来打印」，或者用 SWO/ITM 输出。要用浮点，必须确认 SCB->FPU->FPCCR 的 ASPEN/LSPEN 惰性保护已使能，且理解它的代价。要动态内存，改在初始化阶段一次性分配好。

坑 9 · 「按键接 EXTI 是最专业的做法」

错误认知：中断比轮询高级，所以按键当然要接外部中断，这样响应最快、最省 CPU。

为什么错：机械按键的特性正好和中断的强项相反：它又慢又脏。按一次键的抖动会产生 3~30 次中断，每一次都要进 ISR 清标志，你等于自己制造了一堆「假事件」再花代码把它们滤掉。现实还有两个硬约束：EXTI 线只有 16 条（EXTI0~EXTI15），一个 4×4 矩阵键盘就把它们全占满了；而且 PA0 与 PB0 不能同时做 EXTI0——你在两块板上各接一个按键，扩到一块板上就会冲突。最后，「长按」「连按」「组合键」这些真正要用的功能，本质上都需要周期性采样，光靠边沿中断反而更难写。

正确做法：按键用 10ms 定时器中断扫描——抖动时间（5~20ms）天然被滤掉，不需要任何额外逻辑；多个按键共享一个中断；状态机逻辑自然成立。EXTI 留给它真正不可替代的两种场合：① 低功耗唤醒（CPU 已进 STOP 模式，只有 EXTI 能叫醒它）；② 真正高速的信号（旋转编码器脉冲、过零检测、外部传感器就绪信号）。

坑 10 · 「NVIC_EnableIRQ 都写了，中断还不来，肯定是芯片坏了」

错误认知：我把外设配好了、NVIC_EnableIRQ() 也调了、ISR 也写了，中断就是不进——换块板子试试，或者怀疑是库的 bug。

为什么错：「配好了」通常只是你以为配好了。中断信号从外设到 CPU 要穿过五道独立的关卡：①外设标志、②外设中断使能位（EXTI->IMR/TIMx->DIER/USARTx->CR1）、③NVIC 使能位、④优先级放行、⑤全局开关（PRIMASK）。其中第 ② 关和第 ③ 关是完全独立的两个位，很多教程只讲 NVIC，让人以为开一个就够。另外还有三个高频原因：忘了开 AFIO 时钟（线映射写不进去，且毫无报错）、ISR 函数名写错一个字母（落到 Default_Handler 的死循环里）、Bootloader 场景忘了设 VTOR。

正确做法：按五道关卡的顺序查（第 4 节 sub-noirq 那张图），不要跳步。最有效的一招是先用 NVIC_SetPendingIRQ(EXTI0_IRQn) 直接软件触发：能进 ISR，就说明问题在 ①②关（外设侧）；进不去，就说明在 ③④⑤关或 ISR 名字。这一个测试就能把排查范围砍掉一半，是最该先做的事。清理完再补一个 irq_debug() 一次性打印五关状态。

如果只记一条

把上面十条压成一句：中断是一个「只允许它打断别人、不允许别人等它」的东西。所以 ISR 必须短（坑 1、4、8），共享数据必须防并发（坑 5、6、7），优先级必须想清楚（坑 2、3），配置必须按顺序查（坑 10），而该不该用中断本身也要判断（坑 9）。

小结与自检

这一篇东西不少，但真正需要你记住的其实只有一条主线：中断是把「什么时候处理事件」的决定权从主循环交给硬件。所有的机制——向量表、NVIC、优先级、嵌套、现场保护——都是为了在这件事发生的时候，让系统还能保持秩序。

要点清单

  • 中断解决的不是 CPU 占用，是响应及时性。现实中的轮询只花 0.028% CPU，并不费；它真正的问题是响应时间被主循环里最慢的那件事绑架，而且短于查询间隔的事件必然丢失。
  • 中断的代价有五个：时间不再顺序、数据一致性成新问题、编译器成了对手、调试变难、优先级成了必须设计的参数。后面所有复杂机制都是在为这五条买单。
  • 一次中断分 9 步：请求 → 挂起位 → NVIC 判优先级 → 硬件压栈 → 查向量表取地址 → 跳转 → 清挂起 → 出栈 → 返回。其中只有两步是「你」的（写 ISR、清挂起），其余全是硬件自动完成。
  • 挂起位是硬件对你唯一的承诺。它只保证「事件被记住了」，绝不保证「被处理几次」。所以 ISR 里读到两个事件却只处理一次，是允许的；反过来凭空处理一次，硬件做不到。
  • 向量表就是「异常号 → 函数地址」的数组，每项 4 字节；复位时 CPU 从 0x00000000 取走前两个字当初始 MSP 和复位向量，所以它必须在启动最前面。
  • VTOR 让向量表可以搬移，这是 Bootloader + APP 双区设计的物理基础。APP 里 SCB->VTOR = 0x08008000; 那一行不能少，忘了的现象是「所有中断都不响应」。
  • 异常号 1~15 是系统异常，16 起是外设中断。MemManage / BusFault / UsageFault 默认没使能，它们的错误会升级成 HardFault——这就是初学者看到「永远进 HardFault」的原因。查真凶读 SCB->CFSR（HFSR 的 FORCED 位 = 1 就是升级来的）。
  • NVIC 的六个寄存器组：ISER/ICER（使能/除能）、ISPR/ICPR（置/清挂起）、IABR（只读活动）、IPR（优先级，每中断一个字节）。基址 0xE000E100。
  • 数值越小优先级越高（与 51 相反，0 号最急）。只有高 4 位有用，所以最多 16 级。
  • 抢占优先级决定「能不能打断」，子优先级只决定「同时挂起时谁先」。子优先级不能嵌套——这是最容易误解的一条。NVIC_PRIORITYGROUP_0 下全部同级，系统里不会有任何嵌套。
  • 尾链把「退出 + 再进入」从 24 周期压到 6 周期，迟到中断连这套都省了，直接换成高优先级向量。中断延迟典型构成：检测 2~3 周期 + 等待当前指令执行完 0~12 周期 + 异常进入 12 周期（异常进入这 12 个周期 = 压栈 8 + 取向量 1 + 流水线重填 3，不要重复相加）≈ 典型 14~17 周期、最坏约 29 周期。
  • 硬件自动压 8 个寄存器（R0、R1、R2、R3、R12、LR、PC、xPSR），顺序固定，因为它们正好是 AAPCS 里的「调用者保存」集合。R4~R11 由编译器在 ISR 序言里按需压——这就是「嵌套太深会爆栈」的原因。
  • ISR 必须短。不能阻塞等待、不能 HAL_Delay（会死锁）、不能浮点、不能 printf、不能动态分配、不能长循环。ISR 里只做三件事：清标志、搬数据、置标志。
  • 共享变量必须 volatile（否则编译器把读优化掉，中断改了内存主循环也看不到），但 volatile 保证不了原子性。
  • 读-改-写不是原子的。flags |= 1 是三条指令，会被中断切开导致丢更新。首选「一个事件一个独立标志字节」，次选临界区包住。
  • 临界区要「保存并恢复 PRIMASK」，不能 __disable_irq() 配 __enable_irq()——后者会破坏外层的保护。
  • 中断里必须用 ...FromISR 版本的 API，并在 ISR 最后调用一次 portYIELD_FROM_ISR(xHigherPriorityTaskWoken)。
  • EXTI 的三条硬约束：必须开 AFIO 时钟；PA0 与 PB0 不能同时做 EXTI0；EXTI->PR 是写 1 清除。
  • 不定长帧用「IDLE 中断 + DMA 循环模式」：一帧只进一次中断，长度从 NDTR 精确反推。IDLE 标志必须「读 SR 再读 DR」才能清。
  • 时间基准必须由硬件产生，并且比较时用无符号减法 (uint32_t)(now - start) >= interval 来处理 49.7 天的回绕。
  • HardFault 并不可怕：照着栈帧取 sf[6] 就是出错的 PC，用它去 .map 或反汇编里定位；读 CFSR 知道是哪一类错误。
  • 「中断不响应」按五道关卡顺序查：外设标志 → 外设中断使能位 → NVIC 使能位 → 优先级放行 → PRIMASK。先用 NVIC_SetPendingIRQ() 软件触发一次，能把范围砍掉一半。

自测题（先自己答，再点开对照）

下面 8 道题覆盖了这一篇的全部重点。能全部答对，说明你已经掌握了；有一两道卡住，回去看对应的小节就行。

1. Cortex-M 的优先级数值是越大越高还是越小越高？一个抢占优先级为 15 的中断，响应速度会怎样？

越小越高，0 是最高优先级（与 51 的 IP 寄存器方向相反，这是最容易记反的一点）。

抢占优先级 15 是最低优先级，意味着任何抢占优先级 0~14 的中断都可以打断它，而它永远打断不了任何中断。如果系统里有频繁触发的高优先级中断（比如 1ms 的时基、115200 的串口接收），这个中断的响应时间会被它们反复推迟，表现为「响应时间莫名其妙地长」，而且不报任何错。

2. 抢占优先级和子优先级的关键差别是什么？子优先级更高的中断能打断正在执行的 ISR 吗？

不能。子优先级的唯一作用是：当多个中断同时处于挂起状态时，决定谁先执行。它完全没有「打断正在执行的 ISR」的能力。

只有抢占优先级更高（数值更小）的中断才能打断正在执行的 ISR。两个抢占优先级相同的中断之间不存在任何嵌套关系——即使子优先级不同，也必须排队等前一个执行完。

推论：NVIC_PRIORITYGROUP_0（0 位抢占、4 位子优先级）下所有中断的抢占优先级都是 0，也就是全部同级，系统里不会有任何嵌套；反过来说这五种分组里能嵌套的有序对数量分别是 0 / 64 / 96 / 112 / 120。

3. 硬件自动压栈压了哪 8 个寄存器？按什么顺序？为什么是这 8 个？

8 个寄存器：R0、R1、R2、R3、R12、LR(R14)、PC、xPSR，一共 32 字节。

压栈顺序（从高地址到低地址，也就是内存里从低到高排列的顺序）：xPSR 在最低地址（先压），然后是 PC、LR、R12、R3、R2、R1、R0 在最高地址（最后压）。这也是为什么 C 里的栈帧指针 sf[0] 是 R0、sf[6] 是 PC、sf[7] 是 xPSR。

为什么是这 8 个：它们正好是 AAPCS 调用标准里定义的「调用者保存」（caller-saved）寄存器——也就是「子函数可以随便用、用坏了由调用者自己负责保存」的那些。中断在语义上就是一次「硬件发起的函数调用」，所以被中断的代码（调用者）本来就该假定这些寄存器会被改掉；硬件替它压好，等于把「保护现场」这件事做成了免费且不可遗漏的动作。剩下的 R4~R11 是「被调用者保存」，由编译器在 ISR 的序言里按需压栈——所以 ISR 里用多少局部变量，就额外压多少栈，这也是嵌套太深会爆栈的原因。

4. 一个 ISR 的抢占优先级是 3，SysTick 的优先级是 15。在这个 ISR 里调用 HAL_Delay(1) 会发生什么？为什么？

系统死锁。HAL_Delay 会永远不返回。

原因：HAL_Delay 内部是一个死循环，等待全局变量 uwTick 变化，而 uwTick 只在 SysTick 中断里加一。当前 ISR 的抢占优先级是 3，SysTick 是 15。数值 3 < 15，说明当前 ISR 的优先级高于 SysTick，所以 SysTick 中断被完全挡住、进不来 → uwTick 永远不变 → 死等循环永远出不去。

关键判断规则：只要「当前 ISR 的抢占优先级数值 ≤ SysTick 的抢占优先级数值」，SysTick 就进不来，任何依赖 uwTick 的等待都会死锁。正确做法：ISR 里绝不做任何等待，需要延时就让 ISR 置标志、由主循环处理，或者启动一个单次定时器到定时器中断里做后续动作。

5. flags |= 0x01 在中断和主循环里同时执行会丢更新，为什么？给出两种正确写法。

原因：flags |= 0x01 编译出来是三条指令——LDRB（读）、ORR（改）、STRB（写），这三条之间不是原子的，任何时刻都可能被中断打断。丢更新的时序：主循环读到 0x00 → 中断进来把 flags 置成 0x02 并返回 → 主循环用那份旧的 0x00 做或运算得到 0x01 写回 → 中断设的 bit1 被彻底抹掉。

写法一（首选）：一个事件一个独立的标志字节。每个变量只有一个「作者」（要么主循环写、要么 ISR 写），整字节写是单次总线事务、天然原子，冲突就消失了，代价只是多几个字节内存。

写法二：用临界区把读-改-写包起来——uint32_t pm = __get_PRIMASK(); __disable_irq(); flags |= 0x01; __set_PRIMASK(pm);。注意必须恢复 PRIMASK 而不是无脑 __enable_irq()。

补充：如果两个不同优先级的中断都要改同一个变量，那么低优先级那边也必须加保护，因为高优先级中断能打断它。

6. 向量表为什么必须能搬移？VTOR 在 Bootloader + APP 结构里起什么作用？忘了设置会怎样？

因为它必须跟着代码走。向量表里装的是一个个绝对地址，而这些地址是链接时确定的。如果 Bootloader 在 0x08000000、APP 在 0x08008000，那么 APP 里链接出来的 EXTI0_IRQHandler 地址就是 0x08008xxx 这样的值，全部基于「我的代码住在 0x08008000」这个前提。可硬件复位后只会从 0x00000000（映射到 0x08000000）取向量表——那里装的是 Bootloader 的向量表。所以必须有一个寄存器告诉内核「真正的向量表在别处」，这就是 VTOR（向量表偏移寄存器，0xE000ED08）。

作用：APP 在 main() 最开始执行 SCB->VTOR = 0x08008000;（在开任何中断之前），内核之后所有的异常取向量都从这个新基址加偏移去取。

忘了设的后果：所有中断都会跳到 Bootloader 的向量表里对应的那一项——也就是 Bootloader 的 ISR（通常是 Default_Handler 的死循环）。现象是「APP 的程序主体正常运行，但所有中断都不响应」，或者一开中断就卡死。这是 Bootloader + APP 项目里第一大坑。

另外 VTOR 的低 7 位必须为 0，也就是向量表基址必须 128 字节对齐；为了和链接脚本、Flash 页大小对齐，实际项目通常取 0x8000（32KB）这类页的整数倍。

7. 串口 115200 用逐字节中断，每秒进多少次中断？为什么不定长帧更适合「空闲中断 + DMA」？

每秒最多 11,520 次中断（115200 波特率 = 每秒 11520 个字节，8 位数据 + 起始位 + 停止位共 10 位，115200 / 10 = 11520 字节/秒），也就是每 86.8µs 一次。

CPU 占用本身并不吓人：裸寄存器版每次约 45 周期，11520 × 45 / 72,000,000 = 0.72%；HAL 版约 273 周期，4.38%。真正的问题是那个 86.8µs 的硬约束——只要任何更高优先级的 ISR 或任何临界区超过 86.8µs，USART 的接收寄存器就会被新字节覆盖，产生 ORE 溢出错误、丢字节，而丢一个字节会让后续整个协议解析错位。

IDLE + DMA 为什么更好：一帧数据发完后总线会空闲至少 1 个字符时间，硬件能检测到并置起 IDLE 标志。于是 DMA 负责把每个字节搬进内存（CPU 完全不参与），IDLE 中断负责告诉你「这一帧结束了」。一帧 20 字节只产生 1 次中断，中断频率降低 20 倍，而且长度可以从 DMA 的 NDTR 剩余计数里精确反推，不需要猜协议。这才是「不定长帧」的正解——定长帧可以退而用 DMA 的传输完成中断，不定长帧如果不用 IDLE，就只能靠逐字节中断加软件找帧头帧尾，或者额外配一个超时定时器。

实现要点两条：DMA 要配循环模式（永不停止，不需要软件重启）；IDLE 标志必须「先读 SR、再读 DR」才能清掉，标准库的 USART_ClearITPendingBit 对它无效。

8. 你的 EXTI0 中断完全不响应。写出你的排查顺序（至少四步），以及最快缩小范围的办法。

按信号穿过的五道关卡顺序查：

  1. 中断源有没有真的产生请求——看 EXTI->PR 的 bit0；量 PA0 引脚上是否真有电平跳变；确认上升沿/下降沿配对了（按键接 GND 就该配下降沿）。
  2. 外设自己的中断使能位——EXTI->IMR 的 bit0（1 = 允许中断）。注意别错配成 EMR（事件模式，不产生中断）。另外确认 AFIO 时钟开了，否则 GPIO_EXTILineConfig 写的线映射根本不生效。
  3. NVIC 使能位——NVIC->ISER[0] 的 bit6（EXTI0_IRQn = 6）。
  4. 优先级放行——看 NVIC->IPR[6] 的数值，以及有没有更高优先级的 ISR 卡住不出来（看 NVIC->IABR 和 __get_IPSR()）。顺便确认优先级分组没有被改过。
  5. 全局开关——__get_PRIMASK() 是否为 1；__get_BASEPRI() 是否设了。
  6. 额外一关——ISR 名字是否一字不差（EXTI0_IRQHandler）、有没有 extern "C"、Bootloader 场景 VTOR 设了没。

最快缩小范围的办法：用 NVIC_SetPendingIRQ(EXTI0_IRQn)（或写 NVIC->ISPR[0] = (1UL << 6)）绕过外设直接软件触发。能进 ISR，说明 ③④⑤关和 ISR 本身都没问题，故障一定在 ①②关（外设侧）；进不去，说明问题在 ③④⑤关或 ISR 名字。这一个测试就能把排查范围砍掉一半。

练习

  1. 带 20ms 去抖的按键计数（基础）

    用 EXTI + TIM3 单次模式实现一个按键，要求：ISR 内不超过 20 行、不调用任何阻塞函数、按一次键只在串口打印一次计数。然后故意把去抖时间改成 1ms，观察按一次键会打印几次，用这个现象理解「抖动」到底是什么。加分项：改用「10ms 定时器扫描」实现同样的功能，比较两版代码行数与实测的中断次数。

  2. 非阻塞的 500ms 闪灯 + 200ms 报时（时基）

    用 TIM2 做 1ms 时基，用 g_tick_ms 的非阻塞写法让 PC13 的 LED 以 500ms 周期闪烁，同时每 200ms 通过串口发送一次当前 tick 值。要求全程不用 HAL_Delay。然后用逻辑分析仪（或者串口打印的时间戳）验证：连续跑 10 分钟，LED 的周期有没有漂移？如果把 last = g_tick_ms 改成 last += 500 再测一遍，差别有多大？

  3. 亲手制造并定位一次 HardFault（调试）

    把第 4 节的 hardfault.c 抄进工程，然后分别制造这四种错误：空指针解引用、非对齐访问（记得先置 CCR.UNALIGN_TRP）、整数除零（先置 CCR.DIV_0_TRP）、访问一个没有映射的地址。每一种都记录 g_hf_pc 和 g_hf_cfsr 的值，拿去 .map 文件里定位到具体函数，并说明 CFSR 是哪一位。

  4. 用「五道关卡」反向验证一次（排查）

    先写一个能正常工作的 EXTI0 中断。然后按顺序做三次破坏：① 注释掉 RCC_APB2Periph_AFIO 的时钟使能；② 把 EXTI_LineCmd 改成 DISABLE；③ 把中断函数名改成 EXTI0_Handler。每一次都用 irq_debug() 把五关状态打出来，说说现象有什么不同、哪一关的读数指出了问题所在。这个练习做完，你以后遇到「中断不响应」会快得多。

  5. 实测 ISR 的执行时间（进阶）

    挑一个空闲的 GPIO（比如 PB0），在例题 3 那个「电机电流环」ISR 的开头把引脚拉高、结尾拉低，用示波器量这个脉冲的宽度——那就是 ISR 的真实执行时间。和例题 3 算出来的 5.92µs 对比一下（假设 ADC 转换时间按 1µs 算）。差异大的话，去反汇编里数一数到底执行了多少条指令，看看是哪部分比估算的慢（提示：Flash 预取、外设总线访问延迟、编译器插的额外压栈都可能是原因）。
