CPU 架构与指令执行

你的程序烧进 Flash 之后，就变成了一串二进制数字。芯片上电的那一刻，有一样东西开始以每秒 7200 万次的节奏重复同一个动作： 取一条指令、算一下、存回去。它不知道什么是「按键消抖」，也不知道什么是「PID」，它只会重复这三件事。 这一篇要回答的就是：这几千万次重复，究竟在重复什么。搞清楚之后， 「为什么我的中断里塞不下这段代码」「为什么程序卡在 HardFault」「为什么加了 volatile 就好了」「为什么函数指针能跳到另一个函数去」 这些问题会从玄学变成算术。

为什么需要它

先看两个真实的现场。这两个现场我在实验室里见过太多次，它们看起来毫不相干，其实是同一个知识缺口造成的。

现场一：一个「算不过来」的中断。你写了一个 1ms 的定时器中断，里面做三件事：读一次 ADC、算一个简单的滤波、把一个变量累加。代码不到二十行。烧进去之后，主循环卡死了，串口再也不打印。你怀疑是自己逻辑写错，把中断里的代码一行行注释掉测试，注释到某一行就好了——于是你以为「这一行有问题」。

其实一行问题都没有。真相是：1ms 里只有 72000 个时钟周期，而你那二十行 C 编译出来可能是几百条指令，如果里面还藏着一个除法、一次浮点运算、或者一次串口发送，几千个周期就没了。中断没退出，主循环自然没机会跑。

现场二：停在 HardFault 里的调试器。你按下 Keil 的「停止」，发现程序停在一个只有两行的函数里：

void HardFault_Handler(void)
{
    while (1)
    {
    }
}

; 反汇编窗口里它长得像这样：
HardFault_Handler
    0x08000234    B    .        ; 死循环，什么都不告诉你
    0x08000236    B    .        ; ← 调试器就停在这里

你盯着这个死循环看了两个小时。它不告诉你哪条指令出错了、也不告诉你出错时寄存器里是什么。而实际上，答案就躺在栈里——CPU 在冲进这个处理函数之前，已经把「出错时正在执行哪条指令」压进了栈。只要你认识 xPSR、PC、LR 这几个寄存器，五分钟就能定位到那一行 C 代码（第 4 节会给你完整做法）。

CPU 里有什么：四个部件，一条数据通路

把 CPU 想象成一个只会做三件事的工人：

  • 取指令——从存储器里拿一条待办事项（它自己不知道该干什么，必须先拿到指令才知道）。
  • 算——按照指令说的，把几个数加一加、与一与、比一比。
  • 存回去——把结果放回寄存器或者存储器。存完立刻回到第一步，永远这样循环。

这三件事，就是 CPU 的一生。它不会「顺便」做点别的：不会自动帮你滤波、不会自动帮你消抖、也不会自己判断「这个按键该不该响应」。所有高级功能，都是这三件事按不同顺序重复几百万次拼出来的。

这是 RISC 架构最重要的特征，也是新手最容易搞混的一点。在 Cortex-M 上，除了专门的 LDR/STR 系列指令，其他所有指令都只能操作寄存器。你想把两个内存里的数相加，硬件上没有「内存加内存」这种指令，只能：LDR 把第一个数搬到寄存器 → LDR 把第二个数搬到寄存器 → ADD → STR 存回去，四条指令。

这条规则解释了后面很多现象：为什么 a += b; 这样的语句会编译出好几条指令、为什么局部变量放在寄存器里比放在数组里快得多、为什么 volatile 会明显拖慢循环——因为它把本来能留在寄存器里的值，强行变成每次都要 LDR/STR 的真实内存访问。

还有一个部件在这张图外面，但决定了整张图能不能工作：时钟。CPU 内部所有动作都跟着时钟节拍走，一个节拍叫一个时钟周期（cycle）。72MHz 的意思是每秒 7200 万个节拍，每个节拍 13.89ns。CPU 不是「想跑多快跑多快」，而是每个节拍做一步——这正是后面「CPI」这个概念存在的意义：一步不等于一条指令。

冯·诺依曼、哈佛与「统一编址」并不矛盾

理解了 CPU 只做三件事之后，马上会遇到一个结构问题：指令和数据，放在一起还是分开放？这个问题的两种答案，就是冯·诺依曼结构和哈佛结构。

冯·诺依曼结构的核心思想是「程序和数据一视同仁」：指令和数据存在同一个存储器里，用同一组总线传输。它的好处是简单、灵活——程序可以像数据一样被修改（这就是「可编程」的原始含义）。它的代价是著名的冯·诺依曼瓶颈：同一时刻，总线要么在送指令、要么在送数据，不能同时干两件事。而 CPU 恰恰每时每刻都需要同时干这两件事（取下一步要执行的指令 + 读写刚才算出来的数据）。

哈佛结构的做法相反：指令和数据各用一套存储器、各走一组总线。取指和取数可以真正并行——取指走指令总线去 Flash，取数走数据总线去 SRAM，两条路互不干扰。

【冯·诺依曼结构】指令和数据共用一条总线

        ┌─────────┐
        │  CPU    │
        └────┬────┘
             │   ★ 只有这一条路
      ┌──────┴──────┐
      │   存 储 器   │   ← 指令和数据都住在这里
      │  (指令+数据) │
      └─────────────┘

   时刻 T1：总线上跑的是指令  ──► 想同时取数据？排队等。
   时刻 T2：总线上跑的是数据  ──► 想同时取指令？流水线停一拍。

   ★ 这就是"冯·诺依曼瓶颈"：CPU 越快，这条总线越堵。

【哈佛结构】指令和数据各有各的路

        ┌─────────┐
        │  CPU    │
        └──┬───┬──┘
           │   │
     指令总线  数据总线     ★ 两条路可以同时工作
           │   │
      ┌────┴┐ ┌┴────┐
      │Flash│ │SRAM │
      │指令 │ │数据 │
      └─────┘ └─────┘

   时刻 T1：指令总线上取第 N+1 条指令，同时
            数据总线上读写第 N 条指令要用的数据  ✅ 互不干扰

【Cortex-M3/M4 为什么叫"哈佛改良结构"】

   它有两套总线接口，但【对外仍是一个统一的地址空间】：

        I-Bus     ──► 0x00000000~0x1FFFFFFF 区（Flash / 代码区）
        D-Bus     ──► 同一片 Flash、SRAM 等的数据访问
        System Bus──► 0x20000000 以上的 SRAM 与外设区
最容易混淆的一点：「统一编址」和「哈佛结构」不矛盾

很多同学学到「STM32 是哈佛结构」之后，会立刻产生一个疑问：那为什么我们还能用一个统一的地址空间去访问外设？比如 GPIOA->ODR 就是地址 0x4001080C，Flash 是 0x08000000，SRAM 是 0x20000000——这不就是冯·诺依曼那一套统一编址吗？

答案是：这两件事说的根本不是同一个层面。

  • 地址空间回答的是「门牌号怎么分配」：整个 4GB 空间被划成几块，Flash、SRAM、外设各占一段，用同一套 LDR/STR 指令就能访问。这是「对外」的视角，程序员看到的就是这个。
  • 哈佛/冯·诺依曼回答的是「马路有几条」：内核内部到存储器的物理通路是分开的还是共用一条。这是「对内」的视角，硬件工程师看到的是这个。

所以正确的说法是：Cortex-M 对外是一个统一编址的 4GB 地址空间（所以你好写好读），对内是多条独立的物理总线（所以取指和取数能并行）。门牌号是一套，马路有好几条——这两件事完全可以同时成立。

Cortex-M3/M4 的三条总线各管一段，分工如下：

总线接什么典型地址范围特点
I-Bus
（指令总线）		Flash 里的指令0x00000000 ~ 0x1FFFFFFF（代码区）只用于取指，32 位宽，带预取缓冲。优化过，只取指令不取数据
D-Bus
（数据总线）		数据访问（含对代码区的数据读取，如查表、常量）同代码区，但也参与 SRAM 访问与 I-Bus 物理分开，所以取指和取数能同时进行

（系统总线）		SRAM、外设寄存器（AHB/APB）0x20000000 以上访问外设走这条。外设慢，这条路上的访问通常要等好几个周期
为什么单片机普遍选哈佛结构，而不是「教科书上的纯冯·诺依曼」

三个很实际的理由：

  • 单片机的 Flash 很慢。STM32F103 在 72MHz 下读 Flash 需要插入 2 个等待周期（第 3 节会算）。如果取指和取数还共用一条通路，那就不是「慢一点」，而是慢一倍以上。
  • 取指和取数天然是同时发生的。流水线一旦铺开，每个周期都在「取第 N+2 条指令」和「访存第 N 条指令的数据」，把它们塞进一条总线，等于强行让流水线每隔一拍停一次。
  • 成本并不高。在芯片内部多布一组总线，比把 Flash 和 SRAM 都提速一倍便宜得多。这也是为什么连 PC 上的 x86 处理器（对外是典型的冯·诺依曼）内部也早就分成了 L1 指令缓存和 L1 数据缓存——结构上是「对外冯·诺依曼、对内哈佛」。

顺带说一句：51 单片机（8051）在这一点上是哈佛结构的——程序存储器（code）和数据存储器（xdata/idata）分开编址，这也是为什么 51 的 C 语言里会有 code、xdata、idata 这些关键字。你当年写 unsigned char code table[] 的时候，其实已经在用哈佛结构的特性了。

一条指令的一生：取指 → 译码 → 执行 → 访存 → 写回

现在把镜头拉近，看一条具体的指令。我们选 LDR R0,[R1,#4] 作为主角——它的意思是「把内存地址 (R1+4) 处的一个 32 位数读出来，放进 R0」。这条指令同时用到了 ALU、寄存器组和总线接口，是把 CPU 四个部件全部串起来的最好例子。

  ADD R2, R0, R1   →  IF  ID  EX  WB          （没有 MEM：不碰内存）
  STR R0, [R1, #4] →  IF  ID  EX  MEM         （没有 WB：不写寄存器）
  B   label        →  IF  ID  EX              （改 PC，旧流水线作废）
  LDR R0, [R1,#4]  →  IF  ID  EX  MEM  WB     （五个阶段全占满）

  ★ 记住这个规律：越"贴近内存"的指令，阶段越多、周期越多。
重要澄清：五个阶段是「功能划分」，不等于「五个周期」

上面这套 IF/ID/EX/MEM/WB 模型是教科书的经典五级流水线模型（吴银琴第 2 章讲的就是它），它描述的是「一条指令要经过哪些功能环节」，而不是「Cortex-M3 真的分了五级」。

真实的 Cortex-M3/M4 是三级流水线：取指（Fetch）、译码（Decode）、执行（Execute）。它在「执行」这一级里，一个周期内就完成了「ALU 算地址 + 发起访存」，所以 LDR R0,[R1,#4] 在 Cortex-M3 上只需要 2 个周期（第 1 周期算地址并启动读，第 2 周期数据到手写回寄存器），而不是五级模型里的 5 个周期。

为什么要先学五级模型？因为「取指、译码、执行、访存、写回」这五件事在逻辑上确实都发生了，只是硬件把它们压缩到了更少的节拍里。理解了这五件事的责任划分，你才能理解后面的流水线冒险（比如「数据冒险」本质上就是 WB 还没做完，下一条指令的 EX 就要用这个值）。五级是逻辑，三级是硬件——记住这句话，两边就都通了。

流水线：把重复的五个阶段叠起来

如果不做任何优化，一条指令走完五个阶段才轮到下一条，那么每条指令要花 5 个周期——即便每级都只用 1 个周期。这显然太浪费了：当 ID 阶段在工作时，IF 阶段的硬件是空着的；当 EX 在工作时，IF 和 ID 都空着。

工业上的解决办法和工厂流水线一模一样：让不同的指令同时待在不同的阶段上。当第 1 条指令进入译码时，第 2 条刚好进入取指；当第 1 条进入执行时，第 2 条译码、第 3 条取指。这样虽然单条指令的完成时间（延迟）没变，但单位时间完成的指令数（吞吐率）变成了 1 周期 1 条。

用「洗衣服」来类比最容易懂：洗、烘、叠三道工序各要 30 分钟。如果一个人从头做到尾，洗一件要 90 分钟；但如果按流水线安排——洗衣机洗第 1 桶时，你烘第 2 桶、叠第 3 桶——那么第一件还是 90 分钟出来，但之后每 30 分钟就出一桶。延迟没变，吞吐率提高了 3 倍。

M3 和 M4 的差别不在流水线，在「指令扩展」

这是很多人误以为的一点：Cortex-M4 并不是「流水线更深的 M3」，两者的流水线都是三级、都带 I-Bus/D-Bus/System Bus 三条总线、分支处理方式也基本相同。M4 真正多出来的是：

  • DSP 扩展：SIMD 指令（一条指令同时做两个 16 位运算，如 SADD16）、单周期 32×32 乘加（MLA、SMLAL）、饱和运算、前导零计数等。
  • 可选的单精度浮点单元（FPU）：M4F 才有。带 FPU 的型号执行 VADD.F32 这类指令，而 M3 上的浮点运算要靠软件库模拟（一次 float 加法可能是几十条指令，甚至可能触发库函数调用）。
  • FPU 带来的额外上下文：异常入口时若用到 FPU，硬件会「惰性压栈」额外的浮点寄存器（最多 68 字节），这也是第 3 节算栈容量时要考虑的一项。

所以「STM32F103（M3）做浮点运算慢」这句话的真正原因不是主频低，而是没有 FPU，浮点要靠软件实现；这也是为什么 STM32F4（M4F）特别适合做电机控制与信号处理。

流水线冒险：理想 CPI=1 为什么做不到

流水线的理想状态是「每周期完成一条」，但现实中有三种情况会打破它。这三种情况叫流水线冒险（hazard），是理解「实测性能为什么总是低于理论值」的关键。

① 结构冒险（Structural Hazard）：两个阶段抢同一个硬件。

最典型的就是「取指」和「访存」都想用存储器/总线。如果只有一条总线，那么第 N 条指令在执行 MEM 的时候，第 N+2 条指令的 IF 就没法进行，只能停一拍。

【单总线结构下的冲突】

   周期 →   1    2    3    4    5
  指令1    IF   ID   EX   MEM  WB
  指令2         IF   ID   EX  ⚡MEM←── 想访存
  指令3              IF  ⚡IF  ←── 想取指
                          ↑
                    同一时刻都要用存储器 → 必须有一个等

  解决：加一条独立的指令总线（哈佛结构）→ 取指走 I-Bus，
        访存走 D-Bus，谁也不挡谁。★ 这就是 STM32 用哈佛结构的原因之一。

【对比：51 上的表现】
   51 的取指和数据访问共享存储器接口，所以 51 取指要占 1 个机器周期
   （12 个时钟）；这就是为什么 51 在 12MHz 下大约只有 1 MIPS。

② 数据冒险（Data Hazard）：后一条指令要用前一条还没算完的结果。

看这段代码：

ADD  R0, R1, R2      ; 第 1 条：R0 = R1 + R2
ADD  R3, R0, R4      ; 第 2 条：R3 = R0 + R4   ← 要用 R0 的新值

在五级流水线里，第 1 条指令要走到 WB 阶段才把结果写进 R0，而第 2 条指令在 ID 阶段就要读 R0——那时第 1 条还在 EX。如果什么都不做，第 2 条只能等，白白浪费 3 个周期。硬件的对策叫转发（forwarding，也叫旁路 bypass）：不等结果写回寄存器，而是直接从 ALU 的输出口「抄近路」送给下一条指令的输入端。有了转发，绝大多数相邻的运算指令可以背靠背每周期一条。

但有一种情况转发也救不了：load-use 冒险——紧跟在 LDR 后面就用载入的值。因为 LDR 的数据要到 MEM 阶段结束才拿到，转发路径上还没有值可抄，所以必须停顿一个周期（插入气泡 bubble）。

LDR  R0, [R1]        ; 从内存载入 R0 —— 数据要到第 2 周期末才有
ADD  R2, R0, #1      ; 立刻用 R0 → 硬件插一个气泡，等一拍

【时间线】
   周期 →   1    2    3    4
  LDR      F    D    E(访存完成，R0 到手)
  ADD           F    D    ⏸    E     ← 第 3 周期停顿（气泡）
                               ↑
                        这一拍 CPU 什么也没干

【编译器怎么帮你】
   -O2 下编译器会把中间无关的指令调度进来填这个空档：
       LDR  R0, [R1]
       MOV  R5, R6        ← 编译器插进来的无关指令
       ADD  R2, R0, #1    ← 此时 R0 已经就绪
   所以在 C 里"把相关的计算写在一起"不一定慢，
   编译器常常已经帮你把顺序重排过了。

③ 控制冒险（Control Hazard）：跳转把后面已经取好的指令作废。

流水线的本质是「猜着往下取指」：在译码第 N 条指令的同时，硬件已经把 PC+2 的指令取进来了。可如果第 N 条是跳转指令，PC 要跳到别的地方去，那条已经取进流水线的指令就是错的，必须丢掉，再去新地址重新取指、重新译码——这个「清空并重新填充」的过程叫冲刷流水线（pipeline flush），代价就是分支惩罚。

【没有跳转：一路顺畅】（顺序执行）

   周期 →   1    2    3    4    5    6
  指令A    F    D    E
  指令B         F    D    E
  指令C              F    D    E        ✅ 每周期一条

【遇到跳转：目标地址算出来时，流水线里已经有"错的人"】

  地址 0x1000:  CMP  R0, #10
  地址 0x1002:  BEQ  target        ← 条件成立，要跳到 0x2000
  地址 0x1004:  MOV  R5, #1        ← 已经取进来了 ✗ 作废
  地址 0x1006:  MOV  R6, #2        ← 也取进来了 ✗ 作废

   周期 →   1    2    3    4    5    6    7
   CMP      F    D    E
   BEQ           F    D    E(算出目标 0x2000)
   MOV#1              F    D    ✗ 冲刷
   MOV#2                   F    ✗ 冲刷（如果已取）
   0x2000:                      F    D    E  ← 重新开始

   ★ Cortex-M3 一次成功跳转的代价约 3 个周期（厂商数据手册标 P=3）。
     也就是说：每执行 100 次跳转，相当于白白扔掉约 300 个周期。

【硬件的三种对策】

  ① 提前算目标：在译码阶段就把跳转目标算出来，而不是等到执行阶段，
     这样能少冲刷一级。
  ② 分支预测：猜跳不跳。M3/M4 做了很有限的静态预测
     （后向跳转——也就是循环回跳——预测为"跳"；前向跳转预测为"不跳"），
     猜对时几乎没有惩罚，猜错才付代价。
     M7 更强：BTAC 缓存跳转历史，预测准确率更高。
  ③ 条件执行：干脆不用跳转。Thumb-2 的 IT 块能让几条指令"带条件执行"，
     条件不成立时就当 NOP 流过，没有 PC 跳变 → 没有冲刷。
     ★ 这是 Thumb-2 相对 16 位 Thumb 最重要的性能改进之一。

【另一种古老的对策：延迟槽（delay slot）】
   经典 ARM7TDMI 的做法是"跳转后面那一条指令无论跳不跳都会执行"，
   编译器负责往那个位置塞一条有用的指令。
   ★ Cortex-M 系列已经取消了延迟槽——新代码不要依赖这个行为。

厂商标的 72MHz 是时钟频率，不是指令频率。真实程序里，每个周期都有东西在「偷走」指令。把 CPI（每条指令平均周期数）拆开看：

RISC 与 CISC：本质差别不在「指令条数」

「RISC 就是指令少的 CPU，CISC 就是指令多的 CPU」——这是流传最广的误解。事实上，今天没有任何一款 CPU 是「按指令条数」来分类的。x86 的指令上千条，ARM 也有几百条，数量上早就不在一个数量级之外了。真正的分界线是下面四条结构性差别。

① 定长指令 vs 变长指令。ARM 的 Thumb 指令统一 16 位，Thumb-2 是 16 位和 32 位两种；x86 的指令长度从 1 字节到 15 字节不等。定长意味着译码器可以在固定位置切出操作码，逻辑简单、快、可并行；变长意味着译码器要先「猜长度、再回头确认」，很难做深流水线。

② load-store 结构 vs 允许内存操作数。这是差别最「体感」的一条。在 ARM 上，只有 LDR/STR 系列能碰内存，所有运算都发生在寄存器之间（这就是前面那句「ALU 碰不到内存」）。而 x86 允许一条 ADD [eax], ebx 直接把内存里的数加上一个寄存器——一条指令干完 ARM 要三条才能干的事。

③ 寻址方式少而规整 vs 多而复杂。ARM 的访存寻址基本就是「基址 + 偏移」「基址 + 索引」这几种组合，格式高度统一；x86 有基址、变址、比例因子、位移的复杂组合，还有字符串操作、位操作等特殊寻址。寻址方式多，单条指令能做的事就多，但译码与流水线实现也复杂得多。

④ 硬布线控制 vs 微码控制。CISC 的复杂指令通常由存储在芯片内的一小段「微程序」（微码）来解释执行，一条指令可能要跑好几个微操作；RISC 的指令简单到可以直接用组合逻辑（硬布线）产生控制信号，一条指令一个周期就能发射。微码的好处是灵活（同一套硬件换微码就能改指令集），代价是慢。

对比维度RISC（ARM Cortex-M 这一侧）CISC（x86、51 这一侧）
指令长度定长（Thumb 16 位；Thumb-2 有 16/32 位两种）变长（1 ~ 15 字节）
能否直接操作内存不能。只有 LDR/STR/LDM/STM 访存，运算只在寄存器间能。绝大多数运算指令都可以带内存操作数
指令数量与寻址方式少而规整，格式统一，寻址方式有限多而复杂，同一条指令有大量寻址组合
控制方式硬布线为主，一条指令一个周期发射复杂指令多用微码，一条指令拆成多个微操作
流水线容易做深、做整齐（这正是 RISC 的初衷）译码是瓶颈，需要大量硬件把变长指令「拆解对齐」
编译器负担重（要自己安排寄存器、拆分复杂操作为多条指令）轻（一条高级语句可能就对应一条指令）
代码密度相对差（定长、操作少，需要更多指令），Thumb 就是为解决这个问题而生好（一条复杂指令顶好几条）
功耗与面积小、低（对 MCU 至关重要）大、高（译码与微码逻辑占比可观）

把同一个 C 语句 a[i] = b + c; 放到两种架构上，差别一眼就能看出来：

; ---------- CISC 风格（x86 示意）：一条指令里有内存操作数 ----------
    mov   eax, [b]        ; 读内存 b 到寄存器
    add   eax, [c]        ; ★ 直接"寄存器 += 内存"，不需要先搬到寄存器
    mov   [a + esi*4], eax ; ★ 一条指令里完成 基址+变址*比例 的复杂寻址

; ---------- RISC 风格（ARM Cortex-M）：内存和运算彻底分开 ----------
    LDR   R0, [R1]        ; 先把 b 搬进寄存器
    LDR   R2, [R3]        ; 再把 c 搬进寄存器
    ADD   R0, R0, R2      ; 只在寄存器之间做加法
    LSL   R2, R4, #2      ; 下标 i 乘 4（ARM 的寻址不能自带比例因子）
    STR   R0, [R5, R2]    ; 基址 + 索引 存回内存（这是 ARM 支持的组合形式）

; ★ 结论：RISC 不是"不能做复杂的事"，而是"把复杂的事拆成简单指令，
;   让硬件保持简单"——代价是程序里的指令条数变多、代码变大。
为什么 ARM 选 RISC，而现代 CISC 却在「偷偷变成 RISC」

两个方向的历史，最终撞到了同一个点上：

  • 当年 ARM 选 RISC 的理由很朴素：1980 年代的 ARM 是个小团队，做不出复杂的微码和变长译码逻辑，只能靠「指令简单、译码器就能小、流水线就能整齐、面积和功耗就能低」这条路。而嵌入式市场恰恰最在乎面积、功耗和确定性——这个初心一直保留到今天：Cortex-M0+ 内核面积只有几万门，能塞进几分钱的芯片里。
  • 现代 x86 的做法是「外面 CISC，里面 RISC」：CPU 拿到变长指令后，前端的译码器把它翻译成一到几条定长的微操作（μop / micro-op），后面的执行单元、流水线、乱序调度全部按 RISC 的方式工作。定长、load-store、一个周期发射——RISC 的这些特征，在 x86 内部同样成立。
  • 反过来，ARM 也在往「不那么纯」的方向走：Thumb-2 是变长的（16/32 位混合），LDM/STM 一条指令搬多个寄存器，IT 块让最多四条指令带条件执行——这些都是典型的 CISC 味道。

所以更准确的说法是：RISC 和 CISC 不是两个阵营，而是同一条设计轴上的两个位置，两边都在向中间靠拢。对写代码的人来说，实际影响只有一条：在 Cortex-M 上，尽量把变量留在寄存器里，减少不必要的 LDR/STR——因为每一次访存都是一条独立指令，都要占一个流水线槽。

Thumb 与 Thumb-2：一条 16 位、一条 32 位，混在一起用

ARM 的指令集历史上分成两条线，理解这两条线是理解「为什么 Cortex-M 的汇编长这样」的前提：

ARM 指令集（32 位）Thumb 指令集（16 位）
指令宽度固定 32 位固定 16 位
能力全功能：所有寄存器、所有寻址方式、条件执行受限：只能直接访问 R0~R7、条件执行只有分支指令能用
代码体积大（同样功能的代码大约是 Thumb 的 1.3~1.5 倍）小（约省 30%~35% 的 Flash）
执行效率每条指令做的事多，性能略好指令条数变多，但很多情况下性能接近
Cortex-M 支持吗不支持（ARMv7-M 没有 ARM 状态）这是 Cortex-M 唯一的指令集

Thumb-2 是把两者合到一起的技术：指令流里既有 16 位指令，也有 32 位指令，硬件通过指令头几位判断这条是 16 位还是 32 位（所以取指时 PC 步进是 +2 还是 +4，取决于指令本身）。常用的简单操作（MOV、ADD 小立即数、LDR 小偏移）用 16 位编码保证密度；复杂的操作（大立即数、条件执行、DSP 指令）用 32 位编码保证能力。结果就是「16 位的体积、32 位的能力」，这也是 Cortex-M3 及以上最核心的卖点之一。

【Thumb-2 指令流：靠高位判断长度】

   地址        指令编码            宽度    说明
   0x08000100  4B 01 (01001 011)  16 位   LDR  R3, [PC, #4]     ← 短，常用
   0x08000102  00 BF (1011 1111)  16 位   NOP
   0x08000104  F04F 0000          32 位   MOV.W R0, #0          ← .W 后缀，32 位编码
   0x08000108  1C 40              16 位   ADDS R0, R0, R1
   0x0800010A  F5B1 7F00          32 位   CMP.W R1, #0x8000     ← 大立即数必须 32 位

   ★ 硬件取指时先读 16 位，如果发现是 32 位指令的前半，就再读 16 位凑成一条。
   ★ 汇编里看到的 .W 后缀 = "强制用 32 位编码"，.N = "强制用 16 位编码"。

【为什么选 Thumb-2 而不是纯 32 位 ARM】

   代码密度直接换算成钱：Flash 从 128KB 降到 96KB，芯片成本就下来了。
   而且 Flash 里的指令是"一条一条"取出来的——同样功能的程序，
   用 Thumb-2 写的版本从 Flash 取的总字节数更少，
   在带预取缓冲的 Cortex-M 上反而常常【更快】。

【为什么 51 那样的 8 位机不用考虑这个问题】

   ① 51 只有一套指令集，没有"为了兼容旧代码而保留两套"的历史包袱；
   ② 51 的指令本来就是 1~3 字节变长的，编码上不需要区分"状态"；
   ③ 51 是累加器架构（一条指令通常围绕累加器 A 进行），
      而 ARM 是通用寄存器架构——要让 16 位指令编码塞下 32 位寄存器号，
      就必须限制"只用低寄存器"，这才有了 Thumb 的那些约束。
   ★ 简而言之：Thumb 是 ARM 为了让 32 位 RISC 指令塞进 16 位编码、
     同时保持向后兼容而发明的折中方案，8 位机没有这个矛盾。
一个「冷知识」但很有用的推论：Cortex-M 上不存在 ARM 状态

在 Cortex-A（手机、树莓派主芯片那一类）上，代码可以在 ARM 状态和 Thumb 状态之间切换，靠 BX/BLX 目标地址的最低位来指示用哪种状态（最低位 = 1 表示 Thumb）。但 Cortex-M 只支持 Thumb/Thumb-2，永远处于 Thumb 状态——EPSR 里的 T 位必须恒为 1，向它写 0 会直接触发异常。

这对你有两个实际影响：第一，你不可能在 STM32 上写「纯 ARM 汇编」，网上抄来的一些 ARM 汇编代码（尤其是启动文件或 bootloader 里的）可能在 Cortex-M 上汇编不过去；第二，函数指针的最低位天生就是 1，所以用函数指针调用不会有状态切换问题（第 4 节会再讲一遍这个机制）。

寄存器组：要能背下来的 17 个名字

前面反复说「ALU 只能操作寄存器」，那 Cortex-M 到底有几个寄存器？答案是16 个 32 位通用寄存器（R0~R15，其中后 4 个有特殊用途）+ 1 个状态寄存器（xPSR）。这张表值得背下来——调试时看寄存器窗口、读反汇编、写内联汇编、理解 RTOS 上下文切换，全都靠它。

名字别名 / 用途详细说明谁负责保存
R0 ~ R7低寄存器通用。只有这 8 个能被 16 位 Thumb 指令直接访问（16 位编码里寄存器号只占 3 位）调用者保存（caller-saved）
R8 ~ R12高寄存器通用。要访问它们通常得用 32 位 Thumb-2 指令，所以写汇编时编译器更爱用 R0~R7调用者保存（caller-saved）
R13SP（Stack Pointer）栈指针。硬件强制低 2 位为 0（4 字节对齐）。有两个物理栈指针 MSP / PSP，同一时刻只有一个可见（由 CONTROL 决定）硬件在异常入口自动切换
R14LR（Link Register）链接寄存器。执行 BL 时硬件自动把返回地址写进来；异常时硬件把 EXC_RETURN 写进来被调用者保存（callee-saved）
R15PC（Program Counter）程序计数器，指向「正在取的那条指令」。读它得到的是当前指令地址 + 4；写它就等于跳转—（由硬件更新）
xPSR程序状态寄存器APSR + IPSR + EPSR 三合一，见下文。异常入口时自动压栈，返回时自动恢复硬件自动压栈/出栈
「低寄存器 / 高寄存器」这个区分，会直接影响你写的汇编

Thumb 的 16 位编码里，寄存器号字段只有 3 位，所以只能表示 R0~R7。这就是为什么：

  • 编译器生成的 16 位指令里，你几乎只看得到 R0~R7；想用 R8~R12 时，指令会自动变成 32 位编码（汇编里常写成 .W 后缀）。
  • 手写内联汇编时，把参与运算的变量尽量放在 R0~R7，代码会更短、取指更快。
  • 一条 16 位的 MOV 只能搬低寄存器；MOV R8, R0 这种跨高低寄存器的搬运必然占 32 位。

R13（SP）：为什么必须 8 字节对齐，为什么有两个栈指针

Cortex-M 的栈是满递减栈（full descending）：压栈时「先减 SP、再写入」，SP 永远指向最后一个已入栈的元素。硬件保证 SP 的低 2 位恒为 0，也就是 SP 一定是 4 字节对齐的。

但 AAPCS（ARM 调用标准）要求更严：在函数入口和出口，SP 必须是 8 字节对齐的。原因很实在——Cortex-M4F 的浮点寄存器是 64 位（双字）的，LDRD/STRD 这类双字访问要求地址 8 字节对齐；一些 C 库函数（尤其是 printf 家族、double 运算）还会用 8 字节对齐的指令批量搬运数据。如果你的汇编函数破坏了 8 字节对齐，症状往往是「浮点算出垃圾值」或者「进 printf 就 HardFault」——非常难查。

【两个物理栈指针，同一时刻只有一个"可见"】

   ┌─────────────────────────────────────────────────────────────┐
   │  MSP  Main Stack Pointer   ← 复位后默认用它                  │
   │      中断/异常处理程序【永远】用它（Handler 模式强制 MSP）     │
   │      裸机程序、RTOS 内核用它                                  │
   ├─────────────────────────────────────────────────────────────┤
   │  PSP  Process Stack Pointer ← 需要软件显式切换才用得上        │
   │      典型的用法：RTOS 里【每个任务一个 PSP 值】               │
   │      任务代码运行在 Thread 模式 + PSP                         │
   └─────────────────────────────────────────────────────────────┘

   哪一个可见 = CONTROL 寄存器的 SPSEL 位（bit 1）：
       SPSEL = 0 → 当前用 MSP
       SPSEL = 1 → 当前用 PSP   （只有 Thread 模式允许置 1）

【为什么要这么设计：安全隔离】

   假设只有 MSP 一个栈：
     任务 A 的栈越界了 → 把中断处理程序的栈帧踩烂 →
     中断里再存数据 → 整个系统崩溃，还不知道是谁干的。

   有 PSP 之后：
     任务 A 有自己的栈段（PSP 指向它），中断处理程序用 MSP（内核栈），
     两者物理上分开。任务 A 把栈写爆 → 踩的是自己的栈 →
     触发 MemManage/BusFault 异常（或至少不会立刻毁掉内核）。

【满递减栈的压栈顺序（异常入口，硬件自动做）】

   高地址  ┌──────────────┐
           │  ...          │
           │  xPSR        │ ← SP + 28
           │  PC（返回地址）│ ← SP + 24
           │  LR          │ ← SP + 20
           │  R12         │ ← SP + 16
           │  R3          │ ← SP + 12
           │  R2          │ ← SP + 8
           │  R1          │ ← SP + 4
   低地址  │  R0          │ ← SP + 0   ← 压栈后 SP 指向这里
           └──────────────┘
   ★ 一次异常入口固定压 8 个字 = 32 字节（这就是第 3 节算栈容量的依据）。
     带 FPU 的 M4F 如果异常发生时正在用浮点，还会再多压 17 个字（68 字节）。

R14（LR）：为什么需要一个专门的「返回地址寄存器」

在 51 上，子程序返回靠的是把返回地址压到栈上，返回时再从栈里弹回 PC。ARM 换了个思路：调用时把返回地址写进一个专门的寄存器 LR，不压栈。

这么做的好处很直接：省掉一次内存访问。叶子函数（不再调用别的函数的函数）可以完全不碰栈——不压返回地址、不弹返回地址，一次调用只花 3 个周期左右。

代价也很明确：LR 只有一个。如果函数 A 调用 B，B 又调用 C，那么 C 的返回地址会把 B 的返回地址覆盖掉。所以非叶子函数必须在调用别人之前，把自己的 LR 压进栈，返回时再弹出来。这正是你在反汇编里几乎每个函数开头都会看到 PUSH {..., LR}、结尾看到 POP {..., PC} 的原因。

; 叶子函数：不动栈，直接用 LR 返回
leaf:
    ADD   R0, R0, #1      ; 干活
    BX    LR              ; ★ 返回调用者（跳回 LR 里的地址）

; 非叶子函数：必须先保存 LR，否则调用别人时会覆盖它
nonleaf:
    PUSH  {R4, LR}        ; ★ 把 LR 和自己的局部变量一起压栈
    BL    leaf            ; 这一步会把 LR 改写成"返回 nonleaf 的地址"
    POP   {R4, PC}        ; ★ 出栈时把保存的返回地址直接弹进 PC → 返回

; ★ 注意 POP {..., PC} 这个技巧：它一条指令同时完成
;   "恢复寄存器" 和 "返回" 两件事，比 POP 完再 BX 更省。

; 那么"谁在调用 nonleaf"？调用者的返回地址也写在 LR 里，
; 但它被 nonleaf 用 PUSH 保存了，所以不会丢。
;
; ★ LR 的第二种用途：异常返回。
;   进入异常时，硬件把 EXC_RETURN 写进 LR：
;     0xFFFFFFF9  → 返回 Thread 模式，用 MSP
;     0xFFFFFFFD  → 返回 Thread 模式，用 PSP（RTOS 里最常见）
;     0xFFFFFFF1  → 返回 Handler 模式（嵌套中断的返回）
;   异常处理程序执行 BX LR，硬件看到这个特殊值就知道"该恢复现场了"，
;   于是自动把压栈的 8 个寄存器恢复（也叫"异常返回的魔法值"）。
;   ★ 这也是为什么在中断函数里乱改 LR 会直接跑飞。

R15（PC）：读到的值为什么是「当前指令 + 4」

因为流水线的存在，当一条指令在执行阶段读 PC 时，硬件早已把 PC 指向了后面几条指令。ARM 把这个偏移固定成 +4，也就是说：

; 假设下面这段代码从地址 0x08000100 开始，LDR 在 0x08000100：
;
;   0x08000100:  LDR  R0, [PC, #8]
;   0x08000104:  B    next
;   0x08000108:  ...
;   0x0800010C:  .word  0x12345678   ← 想读的常量
;
; 执行 LDR 时 PC 的读值 = 0x08000100 + 4 = 0x08000104
; 地址 = 0x08000104 + 8 = 0x0800010C   ✅ 正好是常量所在处
;
; ★ 所以在 Cortex-M 上，"PC 的值"永远是【当前指令地址 + 4】，
;   而不是当前指令地址。写汇编时如果算错这 4 个字节，
;   读到的就是隔壁的指令编码（一半的 bug 都长这样）。

; 写 PC 就是跳转：
      MOV   PC, R0        ; 可以，但不推荐（不更新标志、语义弱）
      BX    R0            ; ★ 推荐：跳转并保持 Thumb 状态
      BLX   R0            ; 跳转并写 LR（带链接）
      POP   {PC}          ; 出栈并返回 —— 函数结尾最常见的"跳转"
      B     label         ; 相对跳转（范围 ±16MB，Thumb-2）
      BL    func          ; 相对调用（范围 ±16MB）

xPSR：APSR + IPSR + EPSR 三合一

xPSR 是一个 32 位寄存器，但它是三个寄存器的「拼接体」。初学时容易糊涂，因为手册和调试器有时用总名 xPSR，有时用分名 APSR、IPSR。记住它们的定位：APSR 管「上次运算的结果特征」，IPSR 管「现在在哪个异常里」，EPSR 管「CPU 当前处于什么执行状态」。

位号   31  30  29  28  27   26:25   24    23:16    15:10    9    8:0
名称   N   Z   C   V   Q    ICI     T    保留     IT[7:2]  保留  IPSR[8:0]
      └──────── APSR ─────┘  └── EPSR ──┘         └─ EPSR ─┘       └─ IPSR ─┘

  另外 APSR 的 bit 19:16 是 GE[3:0]（SIMD 指令的比较结果），M4 的 DSP 扩展用。

【APSR：条件标志位】—— 每次影响标志的运算后自动更新

   N (bit31) Negative  : 结果为负（最高位为 1）
   Z (bit30) Zero      : 结果为零
   C (bit29) Carry     : 无符号进位/借位（加法有进位、减法无借位时为 1）
   V (bit28) Overflow  : 有符号溢出（正+正得负，或负+负得正）
   Q (bit27) Saturation: 饱和标志（DSP 指令饱和运算发生过一次就置 1，
                         ★ 它是"粘性"的：只能靠写 APSR 清零，
                            这一点在调试电机控制/音频算法时很关键）

   ★ 判断有符号大小要用 N 和 V 组合（N == V 表示"大于等于"），
     判断无符号大小要用 C 和 Z —— 见下一节的 CMP 与条件后缀。

【IPSR：异常号】—— 回答"此刻在哪个中断里"

   IPSR[8:0] = 0        → 正在 Thread 模式（普通代码/任务代码）
   IPSR[8:0] = 2        → NMI
   IPSR[8:0] = 3        → HardFault     ← 调试"死机"时最先看这个
   IPSR[8:0] = 11       → SVCall
   IPSR[8:0] = 14       → PendSV        ← RTOS 上下文切换用
   IPSR[8:0] = 15       → SysTick
   IPSR[8:0] = 16 及以上 → 外部中断（IRQ0 对应 16，IRQ1 对应 17…）

   ★ 调试技巧：程序停在 HardFault_Handler 里时，
     读 IPSR 只能告诉你"现在在 HardFault"，
     真正有用的信息在【压栈的 xPSR/PC/LR】里（第 4 节详述）。

【EPSR：执行状态】

   T  (bit24) Thumb 状态位：Cortex-M 上必须恒为 1。
              若被清零（例如某些非法跳转），立刻触发 INVSTATE 异常 → HardFault。
   IT[7:2]    IT 块状态：执行 IT 指令时记录"后面几条指令各带什么条件"。
              ★ 这也是为什么在 IT 块中间插指令会出问题。
   ICI[7:2]   中断继续指令状态（跟 LDM/STM 被打断后继续有关，一般不用管）。
标志位放在 xPSR 里的最大好处：中断进出时自动保存

为什么 N/Z/C/V 这些标志不单独放一个寄存器，而要塞进 xPSR 再跟异常号、状态位拼在一起？因为异常入口时硬件会自动把 xPSR 压栈（就在前面那张栈布局图里，SP+28 的位置），异常返回时自动恢复。

这意味着：中断服务程序可以随便改标志位，不会影响被打断的那段代码。如果没有这一条，一个在中断里做的 CMP 就会悄悄改掉主程序下次跳转要用的条件标志——这类 bug 会飘、会随机复现，是最难查的一类。硬件在入口自动压 xPSR，等于把这个坑提前填掉了。

CONTROL 寄存器、Thread/Handler 模式与特权级

前面提到「两个栈指针同一时刻只有一个可见」，那个开关就在 CONTROL 寄存器里。CONTROL 只有 2 个有效位（Cortex-M3/M4），却决定了整个系统的运行姿态：

CONTROL 寄存器（只有低 2 位有效）

  bit 1  SPSEL  0 = 使用 MSP（主栈）
                1 = 使用 PSP（进程栈）   ★ 只有 Thread 模式能置 1
  bit 0  nPRIV  0 = 特权（privileged）
                1 = 非特权（unprivileged） ★ 只有 Thread 模式能改

  bit 2  FPCA（仅 M4F）浮点上下文活跃标志，一般不用手动管。

  ★ 关键限制：一旦进入 Handler（中断）模式，硬件切换到 MSP + 特权级，
    并且【在 Handler 模式下写 CONTROL 的 SPSEL/nPRIV 会被忽略】。
    这保证了"中断处理程序一定是特权的、一定用内核栈"——
    恶意或有 bug 的任务代码没法把中断拖下水。

【四种组合（模式 × 特权 × 栈指针）】

  模式      特权     栈      谁能进入        典型用途
  ─────────────────────────────────────────────────────────────────────
  Thread    特权     MSP     复位后的默认     裸机程序、RTOS 内核启动阶段
  Thread    特权     PSP     RTOS 切换后       FreeRTOS 的"特权任务"（可选）
  Thread    非特权   PSP     RTOS 切换后       ★ 普通应用任务（推荐配置）
  Handler   特权     MSP     ★ 只能由异常进入   所有中断服务程序、内核代码
  ─────────────────────────────────────────────────────────────────────
  ★ Handler 模式永远特权 + 永远 MSP，没有例外。
  ★ 想从 Handler 回到 Thread 且换栈/换特权级，靠异常返回时 LR 里的
    EXC_RETURN 值（0xFFFFFFF9 用 MSP / 0xFFFFFFFD 用 PSP）。
为什么 RTOS 一定要用这套机制（不这么做会怎样）

裸机程序不需要 Thread/Handler、特权/非特权之分——它从头到尾就一段代码。但 RTOS 一旦引入「多个任务并发」，就必须回答三个硬件层面的问题：

  • 每个任务的现场存在哪？→ 答案：存在各自的 PSP 指向的栈里。上下文切换的本质就是「把当前任务的 R4~R11、LR、PC、xPSR 压到它自己的栈上，记下它的 SP，然后换另一个任务的 SP，把那些寄存器恢复回来」。没有双栈指针，这个切换就只能靠软件搬来搬去，慢得多。
  • 任务怎么"进入"运行态？→ 答案：伪造一个异常返回。RTOS 启动第一个任务时的经典做法是：手工在该任务的栈上按「异常压栈格式」摆好 R0~R3、R12、LR、PC、xPSR（PC 就是任务函数的入口），然后设置 PSP 指向这个栈，最后执行一条异常返回（BX 到 0xFFFFFFFD）。硬件就会像「刚从异常返回」一样，把寄存器恢复好并跳到任务函数——这叫「任务上电」的魔术。
  • 任务写坏了内存/越权访问外设怎么办？→ 答案：非特权级 + MPU。任务跑在 Thread 模式的非特权态，它去读 0xE000ED00（内核外设区）会直接被硬件拦下来，触发 MemManage Fault，而不是「静默地改坏了 SysTick 配置」。出了问题能定位到是哪个任务，而不是眼睁睁看着系统变砖。

所以「Thread/Handler + 特权/非特权 + 双栈指针」这套东西，不是为裸机程序准备的，而是为 RTOS 准备的地基。你在裸机项目里几乎感觉不到它，但一旦上了 FreeRTOS，你调试时看到的「任务栈溢出」「HardFault 里 PC 指向某个任务函数附近」，背后都是这套机制在工作。第 4 节会用一个 HardFault 的真实例子把它串起来。

寻址方式：CPU 怎么找到那个数

「寻址方式」听起来抽象，其实就是回答一个问题：这条指令要操作的那个数，藏在哪，怎么把它找出来？可能藏在指令自己身上（立即数）、可能已经在一个寄存器里、也可能在内存的某个地址上——而那个地址又需要算出来。

先解决新手最常撞的一个疑问：为什么「随便一个常数」不能直接塞进指令里？

立即数的编码限制：为什么 MOV R0, #0x12345678 汇编不过去

一条指令总共只有 16 位或 32 位，其中还要分配给「操作码」「目的寄存器」「源寄存器」。留给立即数的位置本来就不多，而且 ARM 的设计是：只把立即数存成「一个 8 位数 + 一个循环右移量」（32 位编码下是 12 位字段：8 位数据 + 4 位移位量）。

这个编码方式能表示很多「看起来不规则」的数——比如 0xFF000000（8 位数据 0xFF 循环右移 8 位）、0x80000001 这类。但它表示不了 0x12345678：因为它的 1 太分散，凑不出「同一个字节循环移位」的形式。

那编译器怎么处理？三条路：

  • 用两条指令拼：MOVW R0, #0x5678（写低 16 位）+ MOVT R0, #0x1234（写高 16 位），拼出 0x12345678。MOVW/MOVT 是 Thumb-2 的重要能力，没有它们就只能靠常量池。
  • 放到常量池，用 PC 相对 LDR 取：编译器在代码段里（通常是函数末尾或跳转指令之后）放一个字面量，然后 LDR R0, [PC, #offset]。你写 C 时从来看不到这一步，但它天天在发生。
  • 用移位/加法组合：小常数如 #0x500 可以用 MOV R0, #0x50 + LSL R0, R0, #4 凑出来，有时比访存更快。

在 16 位 Thumb 指令里，立即数限制更狠：MOVS R0, #imm8 只有 8 位、ADD R0, #imm3 只有 3 位、LDR R0, [R1, #imm5] 的偏移只有 5 位（最大 31 字节，还要乘 4）。这就是为什么偏移量大一点，指令就从 16 位膨胀成 32 位。

Cortex-M 支持的寻址方式不多（这是 RISC 的特点），但每一种都很常用。下面这张表值得收藏：

寻址方式写法示例含义典型 C 对应
立即数寻址MOV R0, #100数就在指令里，不访存x = 100;
寄存器寻址ADD R0, R1, R2两个数都在寄存器里x = a + b;（a、b 已优化进寄存器）
寄存器间接LDR R0, [R1]R1 里放的是地址，去那个地址取数x = *p;
基址 + 偏移LDR R0, [R1, #4]地址 = R1 + 4（R1 不变）x = p[1]; / 结构体成员访问
基址 + 索引（可带移位）LDR R0, [R1, R2, LSL #2]地址 = R1 + (R2 << 2)，专门服务数组x = a[i];（元素 4 字节，i 要乘 4）

前索引和后索引这一对最容易搞混，但其实只要记一句话：「感叹号在哪边，就先动哪边」——[R1, #4]! 是先把 R1 加 4 再用（先动地址，再访存）；[R1], #4 是先用 R1 访存、访存完再加 4（先访存，后动地址）。这里「动」的都是 R1 本身（写回），所以叫「带写回」。

; 初始状态：R1 = 0x20000000，内存里 4 个连续的字是 11, 22, 33, 44
;
; 地址          内容
; 0x20000000    0x0000000B   (11)
; 0x20000004    0x00000016   (22)
; 0x20000008    0x00000021   (33)
; 0x2000000C    0x0000002C   (44)

; ---------- 前索引：先移动指针，再取 ----------
    LDR   R0, [R1, #4]!     ; R1 = R1 + 4 = 0x20000004，然后 R0 = 内存[0x20000004] = 22
                            ; ★ 执行后 R1 = 0x20000004（指针已经动了）
                            ; 等价于 C 的  x = *(++p);

; ---------- 后索引：先取，再移动指针 ----------
    LDR   R0, [R1], #4      ; R0 = 内存[0x20000000] = 11，然后 R1 = R1 + 4
                            ; ★ 执行后 R0 = 11，R1 = 0x20000004
                            ; 等价于 C 的  x = *p++;

; ---------- 后索引是"遍历数组"的最优写法 ----------
copy_loop:
    LDR   R2, [R1], #4       ; 取源、源指针 +4   ← 一条指令 = 访存 + 指针自增
    STR   R2, [R3], #4       ; 存目的、目的指针 +4
    CMP   R1, R4
    BNE   copy_loop
    ; ★ 如果用前索引写，每次循环还要单独加一条 ADD 来推进指针，
    ;   多出来的指令会实实在在占时间（第 3 节会算这笔账）。

; ---------- 数组下标访问：带移位的基址+索引 ----------
    ; C: x = a[i];  其中 a 在 R1，i 在 R2
    LDR   R0, [R1, R2, LSL #2]   ; 地址 = R1 + i*4 —— 一条指令完成
                                  ; ★ LSL #2 就是"乘 4"，因为 int 是 4 字节

; ---------- PC 相对：取常量池里的字面量 ----------
    LDR   R0, [PC, #8]       ; 从 (当前地址+4+8) 处取出 32 位字面量
    ; ... 中间隔开两条指令 ...
    .word 0x12345678         ; ← 编译器自动放在这里的"常量池"
    ; ★ 为什么要 PC 相对？因为这条指令在任何地址都能正确工作
    ;   —— 这就是"位置无关代码"（PIC）的基础。
PC 相对寻址与「位置无关代码」到底有什么关系

如果一条指令写死了「去 0x08001234 取数」，那么这段代码一旦被搬到别的地方执行（比如被 bootloader 复制到 RAM 里跑，或者链接地址变了），它就会去一个错误的地方取数。用「PC 相对」的方式写就没事：基准点跟着代码一起搬家，相对距离不变，所以到哪都对。

实际开发中你会遇到它的三种场景：

  • 常量池天然是 PC 相对的：编译器把字面量塞在代码附近，用 [PC, #imm] 取。好处是不占寄存器（不像 RISC 有些架构要专门留一个「全局指针」寄存器，在中断里还得小心保存）。
  • 取函数/变量的地址：C 里写 &func、跳转表、函数指针数组，编译器都会用 ADR 或常量池 LDR 来取地址（Thumb 没有「把标号地址直接装进寄存器」的 16 位指令）。
  • bootloader 跳转到 APP：APP 的向量表地址要写进 SCB->VTOR，跳转靠函数指针调用。如果 APP 是位置无关编译的，它的地址在链接时就不需要固定死。

常用指令分类、条件执行与调用约定

Cortex-M 的指令有几百条，但日常真正会反复出现的就那么几十条。按用途分成六类，就足够覆盖 95% 的场景：

先说清楚 B / BL / BX / BLX 这四个到底差在哪——它们的区别只有一个：「跳过去之后，还回不回得来」。写 LR 的那两个，就是「带链接」（Branch with Link）。

指令跳转目标怎么给写 LR 吗用来干什么
B label相对当前 PC 的偏移（±16MB）不写循环、if-else 跳转、goto。不需要回来
BL func相对当前 PC 的偏移（±16MB）写：LR = 下一条指令地址函数调用。返回地址自动存好，函数用 BX LR 就能回来
BX Rm寄存器里的地址不写按寄存器跳转（函数指针、跳转表）；返回调用者（BX LR）
BLX Rm寄存器里的地址写：LR = 下一条指令地址通过函数指针调用——「调用」和「间接」两件事合一
「带链接」这个词的具体含义，一次讲清

「链接」指的是把返回地址链接到 LR 里。注意两个容易忽略的细节：

  • LR 里存的是「BL 的下一条指令的地址」，不是 BL 自己的地址。因为返回时要接着往下执行，所以是「下一条」。
  • 只有 BL/BLX 会写 LR，B/BX 不会。所以 B 可以随便用（跳走了就不回来），而 BX LR 之所以能返回，靠的正是之前某条 BL 写下的值。

再补一个新手常问的问题：为什么函数返回用 BX LR，不用 MOV PC, LR？因为在经典 ARM 上，BX 会根据目标地址的最低位切换 ARM/Thumb 状态，而 MOV PC, LR 不会。在 Cortex-M 上虽然只有 Thumb 状态、两者效果一样，但 BX LR 已经成了惯例，编译器也一律用它（而且 BX 是 16 位指令，MOV PC, LR 占 32 位——更短）。

接着是 条件执行——ARM 最有特色的一条设计。基本思想是：每条指令都可以「带上一个条件」，条件不成立时就当它不存在（相当于 NOP），而不是跳过去。这样就没有 PC 跳变，也就没有流水线冲刷开销。

; ---------- 写法一：传统分支（有跳转、有分支惩罚） ----------
;   C:  if (a > b)  x = 1;  else  x = 2;
    CMP   R0, R1          ; 比较 a 和 b，更新标志
    BLE   else_branch     ; 若 a <= b 就跳走  ← ★ 这里可能付 3 周期分支惩罚
    MOVS  R2, #1
    B     done            ; ★ 又一次跳转
else_branch:
    MOVS  R2, #2
done:
    ; 执行路径上有 1~2 次跳转，最坏情况约 6 个周期

; ---------- 写法二：Thumb-2 的 IT 块（无跳转） ----------
    CMP   R0, R1          ; 比较 a 和 b
    ITE   GT              ; ★ If-Then-Else：下一条按 GT 执行，再下一条按"相反"执行
    MOVGT R2, #1          ; a > b  → R2 = 1
    MOVLE R2, #2          ; 否则   → R2 = 2
    ; ★ 全程没有 PC 跳变，不需要冲刷流水线，稳定 3 个周期

; ---------- IT 块的语法规则（Thumb-2 汇编器要求） ----------
;   IT       x      →  1 条指令带条件 x
;   ITT      xy     →  2 条指令，分别带条件 x、y
;   ITE      xy     →  2 条指令，第 1 条带 x，第 2 条带"x 的反面"
;   ITTT / ITET / ITEE / ITTTT … 最多 4 条
;   ★ 条件字母的组合必须"合法"：例如 ITE EQ 后面两条分别是 EQ 和 NE。
;   ★ IT 块内部的指令不能再带条件后缀（由 IT 统一指定）。

; ---------- 单条指令带条件：ARM 的传统强项 ----------
    CMP   R0, #0
    ADDNE R1, R1, #1      ; ★ 只有 R0 != 0 时才执行这条加法
    SUBS  R2, R2, #1
    ; 在 16 位 Thumb 里，只有 B 系列指令能带条件；
    ; 想给"任意指令"加条件，就得靠 IT 块或改用 32 位编码。
条件后缀速查（判断无符号还是有符号，是这里最大的坑）

无符号比较用 CS/CC/HI/LS，有符号比较用 GT/LT/GE/LE。写错了不会报错，只会在负数时得到完全相反的结果——这是嵌入式里最经典的一类隐蔽 bug。

现在进入本节最后、也是最重要的一块：函数调用时，参数放哪、返回值放哪、谁负责保存什么。这套规则叫 AAPCS（ARM Architecture Procedure Call Standard，ARM 架构过程调用标准）。它是编译器、汇编代码、C 库之间的「交通规则」——不遵守它的后果是「C 调汇编时参数全错」。

寄存器AAPCS 角色谁负责保存说明
R0第 1 个参数 / 返回值调用者函数返回时把结果放这里；返回结构体指针也放这里
R1 ~ R3第 2 ~ 第 4 个参数调用者不够放的参数（第 5 个起）从栈上传递
R4 ~ R8局部变量被调用者函数想用就必须先 PUSH、返回前 POP 恢复
R9 ~ R11局部变量（R9 在有些平台是平台寄存器）被调用者同上。R9 在 AAPCS 里可以是"平台相关"，跨平台时别依赖
R12 (IP)临时寄存器（Intra-Procedure scratch）调用者函数可以随便用，不需要保存
R13 (SP)栈指针—函数返回时必须还原；且必须 8 字节对齐
R14 (LR)返回地址被调用者若本函数还要调用别人，必须先把自己的 LR 压栈
R15 (PC)程序计数器—不参与参数传递
S0 ~ S15浮点参数与返回值（M4F）调用者带 FPU 时，浮点参数走 S0~S15，整数参数仍走 R0~R3
S16 ~ S31浮点局部变量（M4F）被调用者想用就得压栈保存

把 AAPCS 归纳成五条「背下来就够用」的规则：

  • 前 4 个整型参数用 R0~R3，第 5 个起从栈上传（在函数入口，第 5 个参数位于 [SP+0]，第 6 个在 [SP+4]…）。
  • 返回值放 R0；64 位返回值（如 long long）放 R0:R1；返回大结构体时，调用者传入一个隐藏指针（放 R0），被调用者把结果写到那个地址。
  • R0~R3、R12 是「调用者保存」：调用一个函数之后，这几个寄存器的值可能已经被改掉了。你（调用者）如果需要它们，得自己先存。
  • R4~R11 是「被调用者保存」：被你调用的函数如果要使用 R4，它必须自己 PUSH/POP。所以你可以放心：调用前后 R4~R11 的值不变。
  • SP 必须 8 字节对齐，而且在函数返回时恢复原值。这就是反汇编里到处是 SUB SP, SP, #8、PUSH {R4-R7, LR}（压 5 个字 = 20 字节 → 会再补一次调整凑成 8 的倍数）的原因。

int add3(int a, int b, int c)
{
    return a + b + c;
}

// ---------- 例 2：带局部数组和循环 ----------
int sum_array(int n)
{
    int buf[4];          // ★ 局部数组：必须占用栈空间（不能全放寄存器）
    int i;
    int s = 0;

    for (i = 0; i != 4; i++) {
        buf[i] = i * n;  // 写数组 → 必须真的写内存
    }
    for (i = 0; i != 4; i++) {
        s += buf[i];
    }
    return s;
}

int apply(int (*fn)(int, int), int x, int y)

volatile unsigned int flag;      // 可能被中断改掉

; int add3(int a, int b, int c)   ← 按 AAPCS：a=R0, b=R1, c=R2，返回值也是 R0
; 编译器生成（-O2）：

add3:
    ADD     R0, R0, R1      ; 第 1 步：R0 = a + b
    ADD     R0, R0, R2      ; 第 2 步：R0 = (a + b) + c  → R0 就是返回值
    BX      LR              ; ★ 返回调用者（LR 里是 BL 写下的返回地址）
    ; 函数结束。

; ★ 观察三件事：
;   ① 参数已经在 R0~R3 里了，【不需要任何压栈】。
;   ② 返回值本来就要放 R0，所以就地累加到 R0，【连一次 MOV 都省了】。
;   ③ 这是"叶子函数"（没调用别人），LR 没被覆盖，所以【不用保存 LR】。
;   总开销：3 条指令、约 3 个周期。一次 C 函数调用可以便宜到这个程度。

; ---------- 对比：6 个参数的版本 ----------
; int add6(int a, int b, int c, int d, int e, int f)
;   按 AAPCS：a=R0, b=R1, c=R2, d=R3, e=[SP+0], f=[SP+4]

add6:
    ADD     R0, R0, R1      ; a + b
    ADD     R2, R2, R3      ; c + d（用 R2 做累加，避免动 R0 以外还有用的人）
    ADD     R0, R0, R2      ; (a+b) + (c+d)
    LDR     R2, [SP, #0]    ; ★ 第 5 个参数 e 从栈上读回来（没有寄存器给它了）
    ADD     R0, R0, R2      ; + e
    LDR     R2, [SP, #4]    ; ★ 第 6 个参数 f
    ADD     R0, R0, R2      ; + f
    BX      LR
    ; ★ 结论：参数超过 4 个，每次访问都要多花一条 LDR ——
    ;   这就是"函数参数别太多"在硬件层面的真实原因（不是风格问题）。
; int sum_array(int n)     ← n = R0
; 编译结果（-O2，简化后）：

sum_array:
    PUSH    {R4, R5, LR}    ; ★ 保存要用的被调用者保存寄存器 + 返回地址
                            ;   3 个字 = 12 字节；再补 4 字节凑成 8 的倍数
    SUB     SP, SP, #20     ; ★ 为局部数组 buf[4]（16 字节）+ 对齐，分配栈空间
                            ;   ★ 注意：这一步就是"栈帧"的诞生 ——
                            ;     SP 往下走 20 字节，这块内存从此归本函数所有

    ; ---------- 第一个循环：buf[i] = i * n ----------
    MOVS    R1, #0          ; i = 0（16 位短指令）
    MOVS    R2, #0          ; 循环计数器
loop1:
    MULS    R3, R1, R0      ; R3 = i * n        ← 一条 MULS 就够
    STR     R3, [SP, R2]    ; ★ buf[i] = R3：把结果真的写进栈上的数组
                            ;   地址 = SP + i*4
    ADDS    R1, R1, #1      ; i++
    ADDS    R2, R2, #4      ; 字节偏移 += 4
    CMP     R2, #16
    BNE     loop1           ; 循环 4 次

    ; ---------- 第二个循环：s += buf[i] ----------
    MOVS    R3, #0          ; s = 0
    MOVS    R2, #0
loop2:
    LDR     R4, [SP, R2]    ; ★ 从栈上把 buf[i] 读回寄存器
    ADDS    R3, R3, R4      ; s += buf[i]
    ADDS    R2, R2, #4
    CMP     R2, #16
    BNE     loop2

    MOVS    R0, R3          ; ★ 返回值必须放 R0（s 一直在 R3 里，要搬一次）
    ADD     SP, SP, #20     ; ★ 释放局部变量空间（SP 回到原位）
    POP     {R4, R5, PC}    ; ★ 恢复 R4/R5，并把返回地址直接弹进 PC → 返回

; ---------- 这个例子里最重要的三行 ----------
;   SUB SP, SP, #20     ← 分配栈帧（局部变量住在 SP 之上）
;   STR R3, [SP, R2]    ← 数组元素【必须】写内存，编译器无法把它优化进寄存器
;   ADD SP, SP, #20     ← 释放栈帧
; ★ 这就是"为什么局部数组比局部 int 慢"的硬件原因：
;   局部 int 可以待在一个寄存器里（零访存），
;   局部数组的每个元素都必须真的住进栈内存（每次访问一条 LDR/STR）。
; int apply(int (*fn)(int, int), int x, int y)
;   按 AAPCS：fn = R0（第 1 个参数），x = R1，y = R2

apply:
    PUSH    {LR}            ; ★ 因为下面要 BLX，LR 会被覆盖，先保存起来
    MOV     R3, R0          ; R3 = fn（函数地址）
    MOV     R0, R1          ; ★ 把 x 挪到 R0 —— 因为被调用函数的第 1 个参数必须在 R0
    MOV     R1, R2          ; ★ 把 y 挪到 R1 —— 第 2 个参数在 R1
    BLX     R3              ; ★★ 关键一条：跳到 R3 里的地址，同时把返回地址写进 LR
                            ;    "带链接的间接跳转"—— 调用 + 间接，一条指令搞定
    POP     {PC}            ; ★ 返回：把保存的返回地址弹进 PC（同时修正 SP）
    ; ★ 返回值不用动：fn 的返回值在 R0，正好也是 apply 的返回值所在的位置。

; ---------- 三个概念连起来看 ----------
;   ① 函数指针在 C 里就是一个"地址"，存在变量里、放在寄存器里。
;   ② BLX 让 CPU 跳到那个地址去执行 —— 硬件不关心它是"函数"还是"数据"，
;      它只知道"我要跳到这个地址"。
;   ③ 返回靠 LR：BLX 把"下一条指令的地址"写进 LR，
;      被调用的函数执行 BX LR 就回来了。
;      ★ 这就是"函数指针能工作"的全部秘密 ——
;        没有魔法，就是 BX/BLX 这两个指令 + LR 这一个寄存器。
;
; ---------- 为什么 Cortex-M 上不用担心"状态切换" ----------
;   在经典 ARM 上，目标地址的最低位表示"用 ARM 还是 Thumb 状态"。
;   Cortex-M 只有 Thumb 状态，函数地址的最低位恒为 1（编译器保证），
;   所以 BLX 到任何合法函数都不会出状态问题。
;   ★ 但要注意：如果函数指针的低位因为某种原因被清成 0，
;     BLX 会触发 INVSTATE 异常 → HardFault。手工给函数指针赋值时别乱做位运算。
调用者（比如 main）在调用 sum_array(5) 之前和之后：

   高地址 ┌────────────────────────────┐
          │  调用者的局部变量            │
          ├────────────────────────────┤ ← 调用者的 SP
          │  （参数超过 4 个时才在这里压）│
          ├────────────────────────────┤
          │  返回地址/保存的寄存器        │
   低地址 └────────────────────────────┘

【进入 sum_array 之后，栈往下长】

   高地址 ┌────────────────────────────┐
          │  调用者的局部变量            │
          ├────────────────────────────┤
          │  R5（被调用者保存，先存起来） │ ┐
          │  R4                          │ │ PUSH {R4, R5, LR}
          │  LR（返回地址）              │ ┘  12 字节
          ├────────────────────────────┤
          │  （凑 8 字节对齐的填充 4 字节）│ ← ★ AAPCS 的强制要求
          ├────────────────────────────┤
          │  buf[3]  ← SP+12            │ ┐
          │  buf[2]  ← SP+8             │ │ SUB SP, SP, #20
          │  buf[1]  ← SP+4             │ │ 局部数组住在这里
          │  buf[0]  ← SP+0             │ ┘
   低地址 └────────────────────────────┘ ← 进入函数体后的 SP（8 字节对齐 ✅）

【函数返回时，这些动作按相反顺序发生】

   ① ADD SP, SP, #20      释放局部变量空间
   ② POP {R4, R5, PC}     恢复 R4/R5，同时把返回地址装进 PC → 跳回调用者
   ③ 调用者的 SP 回到调用前的值（这一步"恢复 SP"是 AAPCS 的硬要求）

【三个必须记住的推论】

  ① 嵌套调用的深度决定栈用量：每进一层函数至少多消耗
     "8 字节（对齐）+ 保存的寄存器 + 局部变量"。
  ② 递归函数每层都要留一份完整的栈帧 → 栈溢出（Stack Overflow）
     是递归最现实的限制（第 3 节会算 8KB 栈能递归多少层）。
  ③ 中断随时会插进来，而且要占用【当前栈】的 32 字节（异常压栈 8 字）
     —— 算栈容量时必须把这部分留出来，这也是"栈高水位"监控的意义。

最后把 volatile 说清楚。这是嵌入式面试与实战都绕不开的关键字，而它的作用只有从汇编层面看才真正明白。

; ---------- 不加 volatile：编译器把变量"缓存"进寄存器 ----------
; unsigned int plain_flag;   while (plain_flag == 0) { }
;
wait_plain:
    LDR     R1, =plain_flag    ; R1 = 变量地址（从常量池取）
    LDR     R0, [R1]           ; ★ 只读了一次！
loop:
    CMP     R0, #0             ; 之后每次都拿寄存器里的旧值比较
    BEQ     loop               ; ★ 如果一开始是 0，这里就是【死循环】
    BX      LR
    ; ★ 问题：这个变量如果在中断里被改成 1，主循环【永远看不到】——
    ;   因为 CPU 一直在比较寄存器里的旧副本，根本没再去内存读。
    ;   ★ 编译器这么做完全合法：在单线程语义下，plain_flag 的值
    ;     在循环中没有任何"能改变它"的语句。

; ---------- 加 volatile：每次都真的去内存读 ----------
; volatile unsigned int flag;   while (flag == 0) { }
;
wait_volatile:
    LDR     R1, =flag
loop:
    LDR     R0, [R1]           ; ★ 每一轮循环都重新访存（不能被优化掉）
    CMP     R0, #0
    BEQ     loop               ; 中断把 flag 改成 1 → 下一轮就能读到 → 退出循环
    BX      LR

; ---------- volatile 阻止的四类优化（按重要性排） ----------
;   ① 阻止"把变量缓存进寄存器"：每次访问都必须真的读写内存。
;   ② 阻止"删除看似无用的写入"：比如给未使用的变量赋值，
;      不加 volatile 时可能被整条删掉，加了就必须留下。
;   ③ 阻止"合并/重排对同一 volatile 对象的访问"：
;      写两次 = 真的写两次（这对硬件寄存器至关重要，
;      比如"先写 1 再写 0"来产生一个脉冲，绝不能被合并）。
;   ④ 阻止"循环不变量外提"：不会把循环里反复读的值提到循环外只读一次。

; ---------- ★ volatile 做不到的三件事（非常重要的澄清） ----------
;   ① 【不保证原子性】：volatile int x; x++; 依然是"读-改-写"三步，
;      中途可以被中断打断。要原子，请用临界区或 __disable_irq()。
;   ② 【不保证内存屏障】：它只约束编译器，不约束 CPU 的乱序与缓存。
;      跨核/多主设备（DMA、双核）场景要用 __DMB()/__DSB()。
;   ③ 【不是多线程同步手段】：两个任务共享的变量，volatile 不能代替
;      互斥锁或临界区，只能保证"不骗你"，不能保证"不被抢"。
;   ★ 一句话：volatile 的语义是"这个值可能会在意料之外被改变，
;     每次都要老老实实去内存拿" —— 它是【防优化】的，不是【防并发】的。
看懂 C 与汇编对应的三个要点（本节小结）
  • 参数与返回值的位置是固定的（R0~R3 / R0），认准它就能看懂任何一个函数的开头。
  • 函数开头的 PUSH 和 SUB SP 就是「栈帧的诞生」，结尾的 POP / ADD SP 是「栈帧的消亡」。看到 SUB SP, SP, #N 就知道这个函数有局部变量（N 就是它们的大小）。
  • C 里的每一次「取地址、写数组、访问结构体、volatile 访问、函数指针调用」都会在汇编里留下痕迹（LDR/STR/BLX），而纯粹的局部 int 运算可以完全不访存。性能差距主要来自「访存次数」，不是「指令条数」。

动手算：把「周期」换算成「毫秒」

这一节的五道例题，全都是嵌入式开发里真实会遇到的估算：这段代码要跑多久？能塞进 1ms 中断吗？栈够不够？开了预取能快多少？位带别名地址怎么算？

估算的价值在于「在写代码之前就知道大概要多久」，从而避免设计阶段的错误（比如「这个算法根本不可能在 1ms 里跑完」）。但估算永远会有误差——真正要下结论时，标准的做法是：用 DWT->CYCCNT 或者定时器实测，把实测值和估算值对一遍。误差如果在 20%~30% 以内，说明你对这段代码的理解是对的；误差巨大，通常意味着有你在估算里漏掉的东西（Flash 等待周期、DMA 抢总线、中断嵌套、库函数里的循环）。

例题 1：72MHz 的理论 MIPS 与「有分支之后」的实际 MIPS

题面：一颗 STM32F103 跑在 72MHz。(1) 如果 CPI = 1（理想情况），理论峰值是多少 MIPS？(2) 真实程序里有 20% 的指令是分支指令，且每次跳转成功要付 3 个周期的惩罚，此时 CPI 是多少、实际 MIPS 是多少？(3) 再考虑 10% 的指令是 LDR，其中 30% 紧跟一条使用该结果的指令（每次停 1 个周期），CPI 和 MIPS 又是多少？

【第一问：理想 CPI = 1 的峰值性能】

   MIPS 的定义：每秒执行多少【百万条】指令

   每秒周期数   = 72,000,000
   每条指令周期 = CPI = 1
   每秒指令数   = 72,000,000 / 1 = 72,000,000 条/秒
   换算成 MIPS  = 72,000,000 / 1,000,000 = 【72 MIPS】

   ★ 这就是"主频 = MIPS"的那种理想情况：72MHz → 72 MIPS。

【第二问：插入 20% 分支，每次惩罚 3 周期】

   关键：惩罚是"按次数收费"的，所以要摊到每条指令上。

   每 100 条指令里，有 20 条是分支 → 20 次跳转
   额外周期数 = 20 次 × 3 周期/次 = 60 个额外周期
   这 60 个周期是为 100 条指令付的
   平均到每条指令 = 60 / 100 = +0.6 周期/条

   CPI = 基础 1.0 + 分支惩罚 0.6 = 【1.6 周期/条】

   实际速率 = 72,000,000 / 1.6 = 45,000,000 条/秒 = 【45 MIPS】
   每条指令平均耗时 = 13.89 ns × 1.6 = 【22.2 ns】

   ★ 结论：仅仅"每 5 条指令里有 1 条分支"，性能就从 72 MIPS
     掉到 45 MIPS，【损失 37.5%】。这就是"实测 MIPS 总低于主频"的主因。

【第三问：再加上 load-use 停顿】

   每 100 条指令里：10 条是 LDR，其中 30% 后面紧跟使用者
   会停顿的次数 = 10 × 30% = 3 次
   额外周期 = 3 次 × 1 周期 = 3 个周期（每 100 条指令）
   平均到每条 = 3 / 100 = +0.03 周期/条

   CPI = 1.0 + 0.6 + 0.03 = 【1.63 周期/条】
   实际速率 = 72 / 1.63 ≈ 【44.2 MIPS】

   ★ 结论：load-use 停顿的影响（约 2%）比分支惩罚（37.5%）小得多。
     所以优化顺序应该是：【先想办法减少分支，再考虑访存】。

【第四问（补充）：如果把分支减少一半会怎样？】

   分支比例 20% → 10%：额外 CPI = 0.1 × 3 = 0.3
   CPI = 1.3 → 速率 = 72 / 1.3 ≈ 【55.4 MIPS】（提升约 23%）

   ★ 工程上的对应做法：
     · 循环展开（把 4 次循环体写在一起，少跳 3 次）
     · 用条件执行（IT 块）替换短小的 if-else
     · 把"每周期都要判断"的短分支改成"状态机 + 表驱动"
     · 用 DSP/位运算做无分支求绝对值、限幅（M4 上尤其划算）
为什么「分支惩罚按次收费」这个思路这么重要

因为它把「性能」变成了一道可以心算的乘法题：额外 CPI = 该类事件的频率 × 单次代价。这个公式对分支、load-use、除法、非对齐访问、Flash 等待周期全都成立。学会用它，你在读代码时就能一眼看出「这段代码大概比理想情况慢多少」——不需要跑 benchmark。

例题 2：1000 次循环要跑多久？能塞进 1ms 的定时器中断吗？

题面：下面这段 C 代码在 1ms 周期的定时器中断里执行（72MHz，Flash 已开预取、CPI 基准按本节口径）：

volatile unsigned int sum;
const unsigned int buf[1000];   // 假设在 Flash 里

void TIM2_IRQHandler(void)
{
    unsigned int i;
    unsigned int s = 0;

    for (i = 0; i != 1000; i++) {
        s += buf[i];            // 累加 1000 个元素
    }
    sum = s;                    // 写回全局变量
}

问：这个循环要花多少时间？占 1ms 中断预算的百分之几？如果这段代码改在 24MHz 下跑（比如为了降功耗），还能塞得进去吗？

【第一步：数清楚循环体有几条指令】

   编译器生成的循环体（-O1，简化）：
       LDR    R2, [R3], #4     ; ① 读 buf[i]，同时指针 +4（后索引，一条顶两条）
       ADD    R0, R0, R2       ; ② 累加
       CMP    R3, R4           ; ③ 判断是否到结尾
       BNE    loop             ; ④ 没到就继续  ← 这是分支
   → 循环体 = 4 条指令/次

   循环外还有：初始化 R0=0、R3=buf、R4=buf+4000、写回 sum
   → 约 5 条指令（一次性开销，1000 次里可忽略，但要算进去）

【第二步：算总指令数】

   循环体：4 条 × 1000 次            = 4,000 条
   循环外：                               5 条
   合计                                = 4,005 条指令

【第三步：算 CPI（重点是分支惩罚）】

   循环里每次迭代都有 1 次 BNE，其中 999 次跳转成功（最后一次不跳）
   分支惩罚 = 999 次 × 3 周期 ≈ 2,997 个额外周期

   摊到每条指令 = 2997 / 4005 ≈ +0.75 周期/条
   （★ 分支越密集，这个数字越大：这里每 4 条指令就有 1 条分支，
      比例高达 25%，比例题 1 假设的 20% 还高）

   CPI ≈ 1.0 + 0.75 = 【1.75 周期/条】

【第四步：算周期数与时间】

   总周期数 = 4,005 条 × 1.75 ≈ 7,009 个周期（取整 7,000）
   时间 = 7,000 / 72,000,000 秒
        = 97.2 微秒（µs）

   也可以用"每周期 13.89ns"直接乘：
       7,000 × 13.89 ns = 97,230 ns ≈ 【97 µs】

【第五步：和 1ms 预算对比】

   1ms 的周期预算 = 72,000,000 × 0.001 = 【72,000 个周期】
   本次占用     = 7,000 个周期
   占用比例     = 7,000 / 72,000 ≈ 【9.7%】

   ★ 结论：塞得进去，而且只占约 1/10 的预算。
     但别忘了中断本身还有入口/出口开销（约 12 + 12 = 24 周期），
     以及"中断执行期间主程序完全停摆"这个事实：
     如果这个中断真的每 1ms 来一次，主程序将永久损失约 10% 的算力。

【第六步：换成 24MHz 会怎样】

   周期数不变（7,000），但每个周期变长了：
       时间 = 7,000 / 24,000,000 ≈ 292 µs
   1ms 预算的周期数 = 24,000
   占用比例 = 7,000 / 24,000 ≈ 【29.2%】

   ★ 结论：还能塞进去，但预算已经用掉近 1/3。
     再叠加别的中断（串口、ADC、SysTick），很快就会撑不住。
     ★ 这也解释了为什么"降频省电"往往要在功能上做取舍。

【第七步：反推——1ms 中断里最多能放多少条指令？】

   预算 72,000 周期 ÷ CPI 1.75 ≈ 【41,000 条指令】
   ★ 记住这个数量级：1ms 中断里"能写"的指令是万级，不是百万级。
     一个 printf（可能几千条指令 + 内部循环）就能吃掉一大块预算。
一个容易踩的坑：这里的 buf 在 Flash 里，如果开预取呢？

本题假设"Flash 开了预取，取指不成为瓶颈"。如果没开预取，每次取指都要额外等 2 个周期，那么循环体 4 条指令（16 位编码时约 8 字节，一次 64 位取指能覆盖）的取指开销会明显上升——最坏情况下 CPI 会从 1.75 涨到 3 以上，时间直接翻倍。这就是为什么 FLASH->ACR 里的预取位和等待周期配置是系统初始化里最不能省的一步，也是例题 4 要专门算的东西。

例题 3：递归函数每层占多大栈？8KB 栈能递归多少层？

题面：一个递归函数，每层栈帧的构成是：保存 3 个被调用者保存寄存器（R4/R5/R6，12 字节）+ 保存 LR（4 字节）+ 4 个局部变量（16 字节）+ 8 字节的中间结果暂存区。系统的栈总容量是 8KB（8192 字节），其中需要预留 1KB 给中断和库函数。问：(1) 每层栈帧多大？(2) 理论最大递归深度是多少？(3) 工程上应该把递归深度上限设在多少？

【第一步：算每层栈帧大小（并注意 8 字节对齐）】

   内容                                        字节
   ────────────────────────────────────────────────
   保存 R4 / R5 / R6（3 个字）                    12
   保存 LR（1 个字）                               4
   4 个局部变量（4 个字）                          16
   中间结果暂存（2 个字）                           8
   ────────────────────────────────────────────────
   小计                                            40 字节

   ★ 关键一步：AAPCS 要求 SP 8 字节对齐！
     40 不是 8 的倍数 → 编译器【一定会再补 8 字节填充】
     → 实际每层栈帧 = 【48 字节】

   ★ 这就是"算栈容量时一定要向上取整到 8 的倍数"的原因。
     如果你只算 40 字节，估算会偏乐观 20%。

【第二步：算理论最大深度】

   可用栈 = 总栈 - 预留 = 8192 - 1024 = 7,168 字节
   理论最大层数 = 7,168 ÷ 48 = 149.3 → 【149 层】

   ★ 这是"最好情况"：假设递归期间【没有中断发生】。

【第三步：把中断考虑进来（这一步最容易被忘掉）】

   每次中断入口，硬件自动压 8 个字 = 32 字节【在当前的栈上】
   如果中断服务程序里还调用了函数（常见！比如 HAL 库、
   printf、浮点运算），再吃掉 100 ~ 500 字节

   保守预留：32（异常压栈） + 300（中断内调用） = 332 字节 ≈ 0.35KB

   重新计算：
     可用栈 = 8192 - 1024 - 332 ≈ 6,836 字节
     最大层数 = 6,836 ÷ 48 ≈ 【142 层】

【第四步：如果这个函数编译时带了浮点（M4F）】

   FPU 惰性压栈：最多再加 17 个字 = 68 字节
     可用栈 = 6,836 - 68 = 6,768
     最大层数 = 6,768 ÷ 48 ≈ 【141 层】
   ★ 影响不大，但"原来够用的栈突然不够用了"常常就是这类
     "后来加了一个功能"引起的。

【第五步：工程上该设多少上限？】

   原则：不要用"理论最大值"，要留 2 倍余量。
     建议递归深度上限 = 142 ÷ 2 ≈ 【70 层】

   更稳妥的做法（真实项目推荐全部用上）：
   ① 在递归函数入口加显式检查：
        if (depth > MAX_DEPTH) { 返回错误码 / 记录日志 / 复位 }
      这比"等栈溢出之后 HardFault"好得多 ——
      因为栈溢出【不一定立刻崩】，可能踩坏别人的变量后
      在完全无关的地方发作。
   ② 把栈区末尾留一块"哨兵"（canary）：
      在栈底写入固定模式（如 0xDEADBEEF），定期检查有没有被改写。
      这就是 FreeRTOS 的 vTaskList / uxTaskGetStackHighWaterMark 的原理。
   ③ 递归能改成循环就改成循环 —— 循环版【栈用量恒定】，
      不受输入规模影响，这才是嵌入式里更常见的做法。

【★ 本题的真正结论】
   栈不是"差不多够就行"的资源。算栈用量时要：
     每层栈帧（向上取整到 8 的倍数）
     × 最坏递归深度
     + 中断压栈（32 字节）
     + 中断内的调用开销
     + 库函数（printf 家族最凶）
     + 2 倍安全余量
   缺了任何一项，都会在"压力测试时才偶发"的 HardFault 上还债。

例题 4：Flash 等待周期到底吃掉多少性能？

题面：STM32F103 在 72MHz 下访问 Flash 需要插入 2 个等待周期。(1) 如果代码从 Flash 执行、且没有开启预取缓冲，那么"取一条 32 位指令"要花几个周期？等效 MIPS 是多少？(2) 开启预取缓冲（一次填充可服务多条顺序指令）之后，为什么性能能大幅回升？(3) 哪些代码模式会让预取缓冲"白开"？

【第一步：算一次 Flash 访问的真实开销】

   一次 Flash 访问 = 1 个访问周期 + 2 个等待周期 = 【3 个周期】
   时间 = 3 × 13.89 ns ≈ 41.7 ns

   ★ 注意：等待周期是硬件总线层面的事，和你的代码无关。
     只要地址落在 Flash 区（0x08000000 起），就必然要付。

【第二步：没有预取时，等效性能是多少】

   假设指令是 32 位（Thumb-2 常见），每次取指都独立去 Flash 拿：

     每条指令取指开销 = 3 周期
     → 即使执行只需要 1 周期，也要被取指拖成 3 周期/条
     等效 MIPS = 72,000,000 ÷ 3 = 【24 MIPS】

   ★ 结论：光是不开预取，就把 72MHz 的芯片用成了 24MHz 的手感，
     性能直接打掉 2/3 ！这不是理论推导 —— 这是很多人
     "代码没改，只是改了一个配置位，速度差三倍"的真实原因。

【第三步：预取缓冲是怎么救回来的】

   预取缓冲的工作方式：Flash 控制器【提前】把连续地址的数据读进缓冲，
   CPU 来取指时直接从缓冲拿（1 个周期）。

   设缓冲一次填充 64 位 = 4 条 16 位指令：

     填充一次的花费 = 3 周期
     服务 4 条指令
     → 摊到每条指令 = 3 ÷ 4 = 【0.75 周期/条】

     再叠加执行本身：若流水线能重叠取指与执行，
     取指开销被"藏"在后面，CPI 可以回到接近 1.0

   对比表：
   ┌────────────────────┬──────────────┬─────────────┐
   │ 配置               │ 取指开销/条   │ 等效性能     │
   ├────────────────────┼──────────────┼─────────────┤
   │ 无预取、无缓存      │ 3.0 周期      │ ~24 MIPS    │
   │ 开预取、顺序代码    │ ~0.75 周期    │ 接近理想     │
   │ 开预取、频繁跳转    │ 接近 3 周期   │ 大幅下降     │
   └────────────────────┴──────────────┴─────────────┘
   ★ 注意最后一行：预取缓冲只对【顺序执行】有效。

【第四步：哪些代码会让预取"白开"】

   ① 密集的小分支：每次跳转，预取缓冲里"顺着往下取"的内容
      全部作废，要重新填充 → 又回到 3 周期起。
   ② 函数调用极密集：每个 BL 都是一次跳转。
   ③ 查表跳转（switch 生成的大跳转表）：目标地址分散，预取命中率极低。
   ④ 在 Flash 上跑但数据也在 Flash（常量表）：取指和取常数抢同一条路。

   ★ 对策：
     · 把最热的循环搬到 SRAM 执行（0 等待周期）：
       在 GCC 里用 __attribute__((section(".RamFunc")))，
       在 Keil/IAR 里用相应的段属性；代价是占用宝贵的 SRAM。
     · 减少循环内的分支（循环展开）。
     · 别在中断里做长跳转链。

【第五步：把这一节和例题 1、2 合起来看】

   例题 1 得到的 CPI 1.6、例题 2 得到的 CPI 1.75，
   都【假设 Flash 取指不成为瓶颈】—— 也就是假设预取开着、
   代码顺序性好、等待周期已正确配置。

   如果这些前提不成立，把 CPI 再乘以 1.5 ~ 3 才是真相：
     例题 2 的 97 µs 可能变成 150 ~ 300 µs
     1ms 中断里的"41,000 条指令预算"可能只剩 15,000 条

   ★ 这就解释了"为什么同一份代码在不同板子上速度差几倍"：
     主频可能一样，但等待周期配置、预取开关、代码是否在 SRAM、
     有没有别的主机在抢总线，这四项完全不同。
记忆锚点：把「等待周期」换算成「等效主频」

一个非常好用的心算技巧：等待周期数 W 意味着「Flash 只能按主频的 1/(1+W) 供料」。
W = 2（72MHz）→ 1/3 → 等效 24MHz；W = 5（168MHz 的 F4）→ 1/6 → 等效 28MHz，靠预取、指令缓存（F4 有 ART Accelerator）和 6 级流水线弥补。所以「跑得快」的芯片不是主频高就行，取指通路必须跟得上。

例题 5：位带别名地址怎么算（第 4 节要用）

题面：要把 GPIOA->ODR 的 第 5 位（也就是 PA5 的输出电平）用位带别名的方式访问。GPIOA 的基址是 0x40010800，ODR 相对偏移是 0x0C，所以 GPIOA->ODR 的地址是 0x4001080C。求别名地址。

【位带别名公式（Cortex-M3/M4 的外设位带区）】

   别名地址 = 0x42000000 + (目标地址 - 0x40000000) × 32 + 位号 × 4

   ★ 为什么是 ×32？ 因为每个"位"在别名区占【4 个字节 = 32 个位】。
   ★ 为什么是 ×4？  因为位号 0 对应别名区第 0 个字节、
                     位号 1 对应第 4 个字节……每个位占 4 字节。

【第一步：算目标地址相对外设基址的偏移】

   目标地址 = 0x4001080C
   基准地址 = 0x40000000（位带区起点）
   偏移 = 0x4001080C - 0x40000000 = 0x0001080C = 67,596（十进制）

【第二步：偏移 × 32】

   67,596 × 32 = 2,163,072
   用移位更直观：0x1080C << 5 = 0x210180
   验证：0x210180 = 2 × 16⁵ + 0x10180 = 2,097,152 + 65,920 = 2,163,072 ✅

【第三步：位号 × 4】

   位号 = 5  →  5 × 4 = 20 = 0x14

【第四步：加上别名区基址】

   别名地址 = 0x42000000 + 0x210180 + 0x14
            = 0x42210180 + 0x14
            = 【0x42210194】

   ★ 这与 ST 官方与各家教程里给出的 GPIOA 第 5 位别名地址完全一致。

【第五步：为什么要这么麻烦？—— 因为它把"读-改-写"变成了一条指令】

   普通写法（三条指令，而且不原子）：
       LDR   R0, [R1]         ; ① 读出整个 ODR（32 位）
       ORR   R0, R0, #0x20    ; ② 置位 bit5（<< 1<<5）
       STR   R0, [R1]         ; ③ 写回整个 ODR
   ★ 危险点：如果在这三条指令之间来了一个中断，
     中断里也改了 ODR 的另一个位，那么中断改的那个位
     会被第 ③ 步【用旧值覆盖掉】—— 这就是经典的"丢位"bug。

   位带写法（一条指令，天然原子）：
       LDR   R1, =0x42210194  ; 别名地址（编译器从常量池取）
       MOVS  R0, #1
       STR   R0, [R1]         ; ★ 一条 STR 就完成"置位 PA5"
   ★ 硬件在别名区内部完成了"读-改-写"，对 CPU 来说就是一次
     普通的 32 位写操作 —— 【不会被打断，也不可能丢位】。

【第六步：位带的两个区域与容量账】

   外设位带区：0x40000000 ~ 0x400FFFFF（1MB）
     → 别名区：0x42000000 ~ 0x43FFFFFF（32MB）
    SRAM 位带区：0x20000000 ~ 0x200FFFFF（1MB）
     → 别名区：0x22000000 ~ 0x23FFFFFF（32MB）

   换算关系：1MB × 32 = 32MB（因为每个位膨胀成 4 字节 = 32 倍）
   ★ 所以位带别名区是"用 32 倍的地址空间，换一条指令的原子性"。
     在 SRAM 里滥用位带会显得很浪费，在外设寄存器上则非常划算。

Keil 的 .lst 长什么样？先认识它的「四列」

一行典型的 .lst 内容是这样的（左边是地址，中间是机器码，右边是指令，穿插其间的 12: 是 Keil 帮你加上的 C 源码行号）：

0x08000100  4408  ADD  R0, R0, R1
0x08000102  4410  ADD  R0, R0, R2
0x08000104  4770  BX   LR

列内容有什么用
第 1 列0x08000100地址：这条指令在 Flash 里的绝对地址——定位问题时靠它（例如把 HardFault 里读到的 PC 拿来对比）
第 2 列4408机器码：真正烧进芯片的字节。Thumb 指令多为 2 字节，Thumb-2 的 32 位指令是 4 字节——从这一列能直接看出「这条指令占多宽」
第 3 / 4 列ADD  R0, R0, R1助记符与操作数：人读的部分。注意 Thumb 的写法与教科书里的 ARM 汇编略有差别（如 ADDS 带 S 后缀表示会更新标志位）
穿插的 C 行13:  return a + b + c;源码路标：这正是 .lst 比纯反汇编好读的地方——你能立刻知道这几条指令对应哪一行 C

三处各自「看懂」了什么
  • 看懂点 1：PUSH {R4, LR} + SUB SP, SP, #8——这就是「栈帧的建立」。看到 PUSH 里有没有 LR，就知道这个函数是不是叶子函数（有 LR 说明它要调用别人，或者需要对齐）。看到 SUB SP 就知道有局部变量。函数序言是判断一个函数开销大小的最快入口。
  • 看懂点 2：循环体的三条指令 + 结尾的 BNE——注意 ADDS R3, R3, #4 这一行：C 里写的是 i++，但汇编里加的是 4。因为编译器把「下标 i」直接变成了「字节偏移」，省掉一次「i×4」的乘法。这就是「编译器比你想象的聪明」的典型例子——你不需要手工做这种优化，读懂它就行。另外注意 BNE 回跳这条分支：995 次成功跳转 × 3 周期 ≈ 3,000 个周期，这就是循环的主要开销。
  • 看懂点 3：BLX R3 + 常量池里的 DCD 0x08000201——函数指针就是一个「存在内存里的地址」。注意那个地址的最低是 1（0x08000201 而不是 0x08000200），这是 Thumb 状态的标记位；BLX 会忽略它并跳到 0x08000200。这一条把「函数指针为什么能工作」从抽象变成了具体的两行。

HardFault 定位：读 xPSR、PC、LR 找出那条出错的指令

这是本节最有实战价值的一段。「程序跑飞了，停在 HardFault_Handler 里的 B . 上」是每个嵌入式工程师都会遇到的画面，而绝大多数人第一次遇到时的做法是「随便改改代码再看」——其实硬件已经把答案完整地压在你的栈上了，只是没人教你怎么读。

先看一个真实的场景。有一个结构体 Item { unsigned int id; unsigned int value; }，和一个忘了初始化的全局指针：

Item *g_item = 0; // ① 指针是 NULL
Item *p = g_item;                // ② p = NULL
p->value = 0x1234;              // ③ 向地址 0x00000004 写数据 → 总线错误 → HardFault

而另一种常被误认为「一定会 HardFault」的写法是 volatile unsigned int c = a / b;（其中 b = 0）——它在 Cortex-M 上默认什么异常都不会产生，具体原因见下面的说明。

先纠正一个流传很广的错误说法：「除零会 HardFault」

在 Cortex-M3/M4 上，整数除零默认不会产生任何异常：UDIV/SDIV 的结果是 0，同时把 APSR 的 C 标志置 1（可以在事后检查）。

如果你希望「除零立刻报错」，只需要在初始化里打开陷阱位，两行代码就够：

SCB->CCR |= SCB_CCR_DIV_0_TRP_Msk;    // 除零 → UsageFault →（未使能时）HardFault
SCB->CCR |= SCB_CCR_UNALIGN_TRP_Msk; // 非对齐访问也触发异常（默认允许部分非对齐）

为什么这件事重要？因为「算出来是 0」会安静地污染后面所有计算（比如 PID 的输出、滤波的系数），而没有任何报错。这比 HardFault 更难查——HardFault 至少会停下来喊一声。所以做除法前判断除数、或者打开陷阱位，是两种都合理的工程选择。

现在回到野指针这个例子上。发生故障的一瞬间，硬件做了两件事：(1) 把 8 个寄存器压到当前栈上；(2) 把 EXC_RETURN 写进 LR，然后跳到 HardFault_Handler。所以那一刻的现场是这样的：

硬件在跳进异常处理程序之前，会把 8 个寄存器自动压到当前栈上（满递减，所以 SP 指向的位置正好就是 R0），再把 EXC_RETURN 写进 LR。那一刻的现场是这样的：

[SP+0]0x00000000R0出错瞬间 R0 的值
[SP+4]0x20000A18R1一个合法的 SRAM 地址（看起来像某个指针）
[SP+8]0x00000000R2—
[SP+12]0x00000000R3—

[SP+24]0x080011A2PC★ 最关键：触发异常的那条指令的地址。拿它去查反汇编或 addr2line，就能直接落到 C 代码的某一行

同一时刻，内核里的几个故障寄存器也在「作证」：

寄存器值怎么读
SCB->HFSR0x40000000bit30 = FORCED：说明「有一个更具体的可配置故障被升级成了 HardFault」。也可能是直接 HardFault，要靠 CFSR 区分
SCB->CFSR0x00008200★ 这一行信息量最大：bit15 = BFARVALID（BFAR 里的地址有效）+ bit9 = PRECISERR（精确总线错误——「就是刚才那条指令干的」，能精确回溯，是最理想的情况）
SCB->BFAR0x00000004★ 出错的「访问地址」：正好等于 NULL + 4（结构体第二个成员 value 的偏移量）→ 立刻可以断定是空指针解引用
SCB->MMFAR0x00000000无效（MMARVALID = 0）——说明不是 MPU 越权，而是总线错误

xPSR 怎么读：把 0x61000000 拆开看——bit24 (T) = 1 说明处于 Thumb 状态（正常）；IPSR[8:0] = 0x03 = 3 说明当前异常号是 3 = HardFault（与「停在 HardFault_Handler 里」一致）；高位是 APSR 部分（这里 Z=1、C=1…）。如果 IPSR 显示的不是 3 而是别的异常号（比如 5 = BusFault），说明故障是从更「具体」的异常升级上来的，这时就要去看 CFSR 里哪一段非零。

LR 怎么读（两个用途）：

  • 在 HardFault_Handler 里看到的 LR 是 EXC_RETURN：0xFFFFFFF9 → 进入异常前用的是 MSP（裸机 / 内核代码）；0xFFFFFFFD → 进入异常前用的是 PSP（★ 说明出错的是某个 RTOS 任务）；0xFFFFFFF1 → 嵌套在另一个 Handler 里出错。0xFFFFFFFD 一出现，你立刻知道「要去查任务」，而不是在主程序的代码里瞎找。
  • 栈上压着的那个 LR（[SP+20]）= 出错前最后一条 BL/BLX 的返回地址，顺着它能还原调用链。

知道现场长什么样之后，就能写出一个「把现场打出来」的 HardFault 处理程序——这是每个 STM32 工程都值得加的一份代码：

#include <stdint.h>

// 硬件压栈的 8 个寄存器，顺序与硬件约定完全一致
typedef struct {
    uint32_t r0;
    uint32_t r1;
    uint32_t r2;
    uint32_t r3;
    uint32_t r12;
    uint32_t lr;      // 出错前的返回地址
    uint32_t pc;      // ★ 出错的那条指令
    uint32_t xpsr;
} StackFrame_t;

// 故障寄存器（Cortex-M3/M4 内核外设，地址固定）
#define SCB_CFSR   (*(volatile uint32_t *)0xE000ED28)
#define SCB_HFSR   (*(volatile uint32_t *)0xE000ED2C)
#define SCB_MMFAR  (*(volatile uint32_t *)0xE000ED34)
#define SCB_BFAR   (*(volatile uint32_t *)0xE000ED38)

// ★ 不要写 __attribute__((naked)) 以外的花活：
//   这个函数必须是裸函数，否则编译器插入的序言会改掉 SP，
//   你就读不到正确的栈帧了。
__attribute__((naked)) void HardFault_Handler(void)
{
    __asm volatile (
        "tst   lr, #4          \n"   // 测 EXC_RETURN 的 bit2
        "ite   eq              \n"
        "mrseq r0, msp         \n"   // bit2 == 0 → 用的是 MSP
        "mrsne r0, psp         \n"   // bit2 != 0 → 用的是 PSP（任务里出的事）
        "mov   r1, lr          \n"   // 把 EXC_RETURN 也传进去
        "b     hardfault_report\n"   // 跳到 C 函数去处理
    );
}

// 用 noinline + optimize("O0") 保证参数不会被优化乱
__attribute__((noinline, optimize("O0")))
void hardfault_report(StackFrame_t *sf, uint32_t exc_return)
{
    volatile uint32_t cfsr  = SCB_CFSR;
    volatile uint32_t hfsr  = SCB_HFSR;
    volatile uint32_t bfar  = SCB_BFAR;
    volatile uint32_t mmfar = SCB_MMFAR;

    (void)exc_return;
    (void)hfsr;

    // ★ 在这里下断点，然后在调试器里看下面这几个值：
    //   sf->pc    → 出错指令地址（丢进反汇编窗口就能看到 C 行）
    //   sf->lr    → 出错前的调用点
    //   sf->xpsr  → 低 9 位是异常号
    //   cfsr      → 哪一类故障（bit15 = 地址有效，bit9 = 精确总线错误）
    //   bfar/mmfar→ 出错时访问的【那个地址】（野指针时一眼看出是 NULL+偏移）

    for (;;) {
        // 死循环等调试器；正式产品里可以改成"记录到备份寄存器 + 复位"
    }
}
定位 HardFault 的六步流程（照着做就行）
  1. 确认不是硬件问题：先看是不是电源/时钟/看门狗导致的复位（读 RCC->CSR 的复位标志）。
  2. 读 CFSR：非零的那一段告诉你故障大类——MMFSR（低 8 位）是内存保护/越权，BFSR（8~15 位）是总线错误（野指针、访问不存在的外设），UFSR（16~31 位）是用法错误（除零陷阱、非对齐、非法状态、非法指令）。
  3. 看 CFSR 的 bit15（BFARVALID）和 bit7（MMARVALID）：如果为 1，BFAR/MMFAR 里就是出错时访问的那个地址——这一步常常直接给出答案（比如 0x00000004 → 空指针解引用；0x20010000 → 数组越界写穿了 SRAM）。
  4. 取栈上压着的 PC：把它丢进反汇编窗口（Keil：Disassembly 窗口按地址跳转；命令行：arm-none-eabi-addr2line -e firmware.elf -f -C 0x080011A2），直接落到 C 代码行。
  5. 看 LR 的 EXC_RETURN 值：0xFFFFFFFD 表示出错在任务上下文（查 FreeRTOS 任务），0xFFFFFFF9 表示在主程序/内核上下文。
  6. 看栈上压的 xPSR 的 IPSR：如果是 3 以外的值，说明你是在某个中断里出的错，范围立刻缩小到那个中断服务程序。

一句话总结这套机制的精妙之处：硬件在跳进异常处理程序之前，自动帮你保存了「出错的那条指令地址、出错前的调用点、当时的所有通用寄存器、以及当时的标志位」，而且保存位置是确定且有文档的。所以 HardFault 从来不是「信息不足」，只是「大多数人不知道去哪里读」。

顺手解决一个常见疑问：为什么 HardFault 里常常只见 B .

因为启动文件（startup_stm32f10x.s）里的默认实现只有一行有效代码：

HardFault_Handler  PROC
    EXPORT  HardFault_Handler
    B   .              ; ★ 原地死循环，等调试器
    ENDP

B . 的意思是「跳到自己」——一条指令组成的死循环。它唯一的用途就是「把 CPU 定在这里，让调试器有机会接管」。你在调试器里看到 PC 停在 B .，说明程序确实停下来了，但答案不在这一行上，而在栈里（也就是上面那六步）。把默认实现换成上面那份 hardfault_report，你的调试效率会有质的变化。

内联汇编与 CMSIS 内建函数：什么时候需要「自己插一条指令」

99% 的 C 代码不需要汇编。但有那么几件事，C 语言无法表达，必须由一条具体的指令来完成：让 CPU 睡下、关中断、保证写操作真的到达了外设、精确插入一个空操作。ARM 把这些封装成了 CMSIS 内建函数（__NOP() 这类），定义在 cmsis_gcc.h / core_cm3.h 里，不需要写内联汇编，直接调用即可。

#include "stm32f1xx.h"      // 已经包含 core_cm3.h → CMSIS 内建可用

// ---------- ① 可嵌套的临界区（最容易写错的一个） ----------
static volatile uint32_t shared_counter;

void counter_add(uint32_t n)
{
    uint32_t primask = __get_PRIMASK();   // ★ 先记下"原来是不是关着中断"
    __disable_irq();                      // 关中断，进入临界区

    shared_counter += n;                  // 这段里不可能被中断打断

    __set_PRIMASK(primask);               // ★ 按原值恢复（而不是无条件开中断）
    // 如果这里写 __enable_irq()，就会把"外层本来就关着的中断"意外打开，
    // 这是嵌套临界区里最经典的 bug。
}

// ---------- ② 配置外设后的屏障：确保真的写进去了 ----------
void clock_enable_gpioa(void)
{
    RCC->APB2ENR |= RCC_APB2ENR_IOPAEN;   // 打开 GPIOA 时钟
    (void)RCC->APB2ENR;                    // ★ 读回一次，保证写操作完成
    __DSB();                               // ★ 数据同步屏障：等写操作真正到达

    // 之后才去配置 GPIOA。少了这一步，某些芯片/某些优化等级下
    // 会出现"时钟还没生效就开始配置寄存器"的诡异现象。
}

// ---------- ③ 低功耗等待：让 CPU 睡到下一个中断 ----------
void idle_loop(void)
{
    for (;;) {
        // 有活干活……
        __WFI();        // ★ CPU 停机，等中断唤醒（SysTick、串口、EXTI 都行）
    }
    // ★ 注意：如果所有中断源都被关了，这里会永久睡死。
    //   产品代码里通常配合看门狗使用。
}

// ---------- ④ 内联汇编：C 表达不了的动作 ----------
static inline uint32_t read_msp(void)
{
    uint32_t val;
    __asm volatile ("mrs %0, msp" : "=r" (val));   // 把 MSP 读进一个通用寄存器
    return val;
}

static inline void precise_nop_x4(void)
{
    // ★ asm volatile 表示"不要优化掉、不要重排"
    __asm volatile ("nop\n\tnop\n\tnop\n\tnop\n" ::: "memory");
}

}

{

三条最容易犯的错
  • 临界区里干太多事。__disable_irq() 屏蔽的是所有可屏蔽中断，包括 SysTick。如果里面跑了几十微秒，系统的时基就开始抖，串口可能丢字节。规则：临界区只放几条指令，绝不放循环、延时、串口打印。
  • 关中断不恢复原值。见上面 ① 的注释——嵌套场景下会提前打开中断。
  • 忘了 memory clobber。内联汇编如果访问了内存（读外设寄存器、改全局变量），末尾必须写 ::: "memory"，否则编译器可能把外面的读写挪到汇编前后，产生你完全看不懂的时序问题。

位带操作为什么是原子的：一条 STORE 而已

第 3 节的例题 5 算出了别名地址（GPIOA 第 5 位 → 0x42210194），这里把「为什么它就原子了」讲透。用 C 宏写出来大概是这样：

// 位带别名区基址（两个区域）
#define BITBAND_PERIPH_BASE   0x42000000UL   // 外设位带别名区
#define PERIPH_BASE           0x40000000UL   // 外设区起点
#define BITBAND_SRAM_BASE     0x22000000UL   // SRAM 位带别名区
#define SRAM_BASE             0x20000000UL

// 把"某个地址的某一位"翻译成"别名区里某个 32 位字的地址"
#define BITBAND_PERIPH(addr, bit) \
    (*(volatile uint32_t *)(BITBAND_PERIPH_BASE + \
        (((uint32_t)(addr) - PERIPH_BASE) * 32UL) + ((uint32_t)(bit) * 4UL)))

// 用起来是这样（GPIOA->ODR 的 bit5）：
#define PA5_BITBAND   BITBAND_PERIPH(&GPIOA->ODR, 5)

void led_on(void)  { PA5_BITBAND = 1; }   // ★ 一条 STR：置位 PA5
void led_off(void) { PA5_BITBAND = 0; }   // ★ 一条 STR：清零 PA5

// ---------- 展开看汇编（-O2） ----------
//   led_on:
//       LDR  R1, =0x42210194    ; 别名地址（从常量池取）
//       MOVS R0, #1
//       STR  R0, [R1]           ; ★★ 就这一条，没有 LDR-ORR-STR 三步
//       BX   LR
//
// ---------- 为什么"一条 STR"就等于原子 ----------
//   ① CPU 执行一条 STR，是"一个不可分割的总线事务"。
//      中断只会在【指令边界】被响应，不可能插进这条 STR 中间。
//   ② 读-改-写由【别名区硬件】完成：
//      写别名地址 = 自动去读原地址 → 只改对应那一位 → 写回。
//      这个过程 CPU 看不见，自然也插不进去。
//   ③ 对比普通写法（LDR → ORR → STR）：三条指令之间【可以】来中断，
//      中断如果改了同一个寄存器的别的位，
//      第 ③ 步就会用旧值把它覆盖掉 —— 这就是"丢位"bug。
//
// ---------- ★ 一个必须知道的现实限制 ----------
//   位带是 Cortex-M3/M4 的【可选】特性：
//     · STM32F1（Cortex-M3）支持外设位带与 SRAM 位带
//     · STM32F4 / L4 / G4 等较新系列【不支持位带】（地址空间被挪作他用）
//   在不支持位带的芯片上，要达到同样的原子置位/清零效果，
//   标准做法是用 GPIO 的 BSRR 寄存器（Set/Reset 分开写）：
//       GPIOA->BSRR = GPIO_BSRR_BS5;   // 置位 PA5（写 1 有效，一条 STR）
//       GPIOA->BSRR = GPIO_BSRR_BR5;   // 清零 PA5（也是同一条 STR 的另一半）
//   ★ BSRR 的思想和位带完全一样：【把"读-改-写"变成"只写"，从而原子】。
//     这也是为什么 ST 要在 GPIO 上专门放一个 BSRR —— 它是位带的替代品。

「汇编难不难」——一个诚实的回答

网上对这个问题有两种极端回答：「汇编没用，别学」和「不懂汇编就不算嵌入式工程师」。都不准确。更实用的分法是把「会汇编」拆成三层，各有各的必要性：

层次要求要不要学能达到什么程度
读懂 看懂函数序言与结尾、参数怎么传、循环与分支、LDR/STR 在干什么、常量池与函数指针 必须学。这是排查底层问题的唯一手段，投入约 2~3 周（每天 1 小时，配合 objdump 对照自己的 C 代码） HardFault 能定位到行、性能问题能看出是哪里的访存太多、能验证编译器有没有按你预期优化

从零手写 整个函数用汇编写，自己分配寄存器、自己调度指令 几乎不需要。现代编译器 -O2 的寄存器分配和指令调度通常比人写得好 只有这些场合值得手写：启动代码（复位向量）、RTOS 上下文切换、DSP 内核循环、极端时序（如软件 SPI 的位翻转）

给初学者的建议路径（按这个顺序走，不绕路）
  1. 先学会「读函数」：随便找一个自己的 C 文件，编译出 .lst，把每个函数的开头三行和结尾两行翻译出来（哪些参数用寄存器、栈帧多大、有没有调用别人）。这一步做完，你就已经超过了大多数人。
  2. 再学 AAPCS 那张表（R0~R3 传参、R0 返回、R4~R11 被调用者保存）。它是「读汇编」的钥匙：所有函数的参数位置都由它决定。
  3. 然后专攻三个场景：循环、函数调用、结构体访问。这三个覆盖了日常 80% 的代码。
  4. 最后学调试技能：Keil/CubeIDE 的寄存器窗口 + 反汇编窗口 + 单步，加上本节的 HardFault 六步法。
  5. 关于手写汇编：等你真的需要「精确控制某个时序」的时候再学，那时候你会发现自己一学就会——因为读得够多了。

最后一句实话：汇编不是「另一门语言」，而是你写的每一行 C 代码的最终形态。读懂它，等于给你的 C 代码装上了一双能看穿代价的眼睛——你会突然明白为什么「把 int 换成 float 慢了十倍」、为什么「这个循环去掉一次除法就快了 30%」、为什么「加了 volatile 之后时序变了」。这种「知道自己每一行代码要花多少周期」的能力，才是嵌入式工程师和普通程序员的真正分界线。

常见误区：十个「听起来很对」的错误认知

这一节列的十条，全部是真实项目里能见到、而且会造成实际损失的误解。每条都按「错误认知 → 为什么错 → 正确做法」三段写。

误区 1：72MHz 就是每秒 7200 万条指令

为什么错：主频是时钟周期的频率，不是指令的频率。一条指令平均要花 CPI 个周期，而 CPI 因为分支惩罚、load-use 停顿、Flash 等待周期、多周期指令（除法 2~12 周期）而高于 1。真实程序里 CPI 通常在 1.2 ~ 1.6，也就是 72MHz 大约只等于 45 ~ 60 MIPS。

正确做法：估算时用 频率 ÷ CPI，并且永远用 DWT->CYCCNT 实测一遍。另外记住：性能优化要看「周期数」而不是「指令条数」——一条 2 周期的指令可能比三条 1 周期的指令更划算。

误区 2：Cortex-M4 是「流水线更深的 M3」，所以更快

为什么错：M3 和 M4 的流水线都是三级，总线结构、分支处理方式也基本相同，DMIPS/MHz 都是约 1.25。M4 快的地方来自指令扩展：DSP 的 SIMD 指令（一条顶两条）、单周期乘加、饱和运算，以及可选的单精度 FPU。如果你的代码全是普通的整数加减，M3 和 M4 跑出来几乎一样快。

正确做法：选型时问「我的算法能不能用上 DSP/FPU」，而不是「M4 是不是更快」。带 FPU 的 M4F 做浮点滤波、电机 FOC、音频处理是质变；只做逻辑控制和简单整数运算，M3 完全够。

误区 3：STM32 是哈佛结构，所以不可能统一编址

为什么错：这两件事不在一个层面上。统一编址说的是「门牌号怎么分配」（对外一个 4GB 地址空间，Flash 在 0x08000000、SRAM 在 0x20000000、外设在 0x40000000）；哈佛说的是「马路有几条」（对内有 I-Bus、D-Bus、System Bus 三条并行通路）。门牌号一套、马路好几条，两者完全可以同时成立。

正确做法：写代码时按统一编址的思路随便用指针和结构体访问（这是对的）；但在理解性能时，要意识到「取指走 I-Bus、取数走 D-Bus」，所以把常量表放在 Flash 会同时占用两条路，热点数据放 SRAM 更划算。

误区 4：除零会触发 HardFault，所以我不用检查除数

为什么错：Cortex-M3/M4 上 UDIV/SDIV 默认不产生异常：除零的结果是 0，同时把 APSR 的 C 标志置 1。结果是「安静地算错」——比如 PID 的积分项变成 0、滤波系数变成 0，系统照跑，只是行为不对。这比崩溃难查得多。

正确做法：三选一或全用：① 除法前判断除数（if (d != 0)）；② 打开陷阱位 SCB->CCR |= SCB_CCR_DIV_0_TRP_Msk;，让除零立刻变成 UsageFault → HardFault；③ 用定点数运算彻底避开除法（很多控制算法本来就这么做）。

误区 5：加了 volatile 就线程安全了

为什么错：volatile 只阻止编译器把访问优化掉（不缓存进寄存器、不删除、不合并、不重排）。它不保证原子性（x++ 依然是读-改-写三步，能被中断打断），不提供内存屏障（对 DMA、双核、乱序无效），更不是互斥手段。

正确做法：分清目的——「让中断里改的变量被主循环看到」用 volatile 就够；「多个执行流同时改一个变量」必须用临界区（关中断 / LDREX-STREX / 互斥锁）。跨 DMA 或双核共享内存时，还要加 __DMB()。

误区 6：函数指针又慢又危险，能不用就不用

为什么错：函数指针调用的额外开销只有「一次间接跳转」，最终就是一条 BLX（对比直接调用的 BL），差别通常只有一两个周期。它不危险——危险的是「指针没初始化」「指向了签名不匹配的函数」「指向了已经被释放的东西」。

正确做法：放心用它（状态机、驱动接口、回调、命令表都靠它）。但要：① 定义时初始化（哪怕先指向一个安全的空函数）；② 调用前判空；③ 用 typedef 固定函数签名，避免参数不匹配；④ 别对函数地址做位运算（Cortex-M 上最低位是 Thumb 标记）。

误区 7：栈 8 字节对齐只是个「建议」

为什么错：AAPCS 强制要求在函数入口和出口 SP 必须是 8 字节对齐。破坏它不会立刻报错，但会在这些地方暴雷：双字访问指令（LDRD/STRD）、FPU 的 64 位寄存器保存、某些 C 库函数（printf、double 运算）内部的批量搬运。症状是「浮点算出垃圾值」或「进 printf 就 HardFault」，非常难查。

正确做法：写汇编函数时，压栈的字数必须是偶数（不够就补一个字，比如 PUSH {R4, LR} 是两个、PUSH {R4-R6, LR} 是四个；三个字就再补一个）。用 SUB SP, SP, #N 分配空间时，N 也要是 8 的倍数。

误区 8：LR 是硬件自动管理的，嵌套调用不用管

为什么错：LR 只有一个。函数 A 调 B、B 调 C 时，C 的返回地址会覆盖掉 B 的返回地址。非叶子函数如果在调用别人之前不保存 LR，返回时就会跳错地方——症状通常是「莫名其妙跑飞」或者 HardFault。

正确做法：写汇编函数时，只要函数体内有 BL/BLX，就必须在序言里 PUSH {..., LR}，结尾用 POP {..., PC}。读别人的汇编时，也可以用它来判断函数是不是叶子函数。（用 C 写代码时编译器会自动处理，不用操心。）

误区 9：调试用 -O0、发布用 -O2 就行，没什么坑

为什么错：优化等级改变了指令的数量、顺序和访存次数，因此会改变：① 时序（用 -O0 调好的延时循环，换成 -O2 后可能被整个删掉或加速几十倍）；② 调试体验（-O2 下变量可能只在寄存器里、断点会跳行、单步会乱跳）；③ 共享变量的可见性（本来能跑的中断通信，在更高优化下因为缓存进寄存器而失效）。

正确做法：① 调试用 -Og（GCC 为调试优化的等级）或 -O0，发布用 -O2，但两者都要测一遍；② 精确延时不要靠空循环，用 DWT->CYCCNT 或硬件定时器；③ 中断与主循环共享的变量一律 volatile；④ 关键外设配置后加 __DSB()。

误区 10：位带操作到处都能用（以及「16 位 Thumb 指令性能差」）

为什么错：两个都需要纠正。(1) 位带是可选特性：STM32F1（M3）支持外设与 SRAM 位带，但 STM32F4/L4/G4 等较新系列已经不支持位带——在那些芯片上照抄位带代码，写进去的地址是无效的，可能触发 HardFault 或毫无效果。(2) 「16 位指令性能差」也不对：Thumb-2 的 16 位编码指令与 32 位指令在同一个周期里同样执行，只是能力受限（只能访问 R0~R7、立即数更小）。代码更小意味着从 Flash 取的总字节更少，在带宽受限的场合反而更快。

正确做法：① 需要「原子置位/清零」时，优先用 GPIO 的 BSRR（写 1 有效的一条 STR），或者用 __LDREXW/__STREXW 实现无锁操作——这两者在所有 Cortex-M 上都可用；② 别为了「性能」放弃 16 位编码，让编译器自己选，它会在密度和性能之间做合理取舍。

小结与自测

回到开头那个问题：一颗 CPU 每秒钟执行几千万条指令，它到底在重复做什么？现在你应该能一口气答出来——它在重复「取指令 → 译码 → 执行 → 访存 → 写回」这五件事，而流水线让五个阶段同时忙起来，于是「平均每个周期完成一条」。这一页的全部内容，都是这句话的展开。

要点清单

一 · 部件与结构
  • CPU 内部四大件：ALU、控制器（取指/译码/时序）、寄存器组、总线接口。
  • ALU 碰不到内存：所有运算数据必须先经 LDR 进寄存器。
  • 冯·诺依曼：一套总线，取指与取数抢路（瓶颈）；哈佛：分开的通路。
  • Cortex-M 是改良哈佛：I-Bus 取指、D-Bus 取数、System Bus 管外设，三条并行。
  • 统一编址 ≠ 冯·诺依曼：门牌号是一套，马路可以有好几条。
二 · 指令的一生与流水线
  • 五阶段 IF → ID → EX → MEM → WB；LDR R0,[R1,#4] 五步全部用上，ADD 不用 MEM。
  • 三级流水线（M3/M4）：取指 / 译码 / 执行，五级是逻辑模型，三级是硬件实现。
  • 三类冒险：结构（加缓存）、数据（转发 + 气泡）、控制（分支预测 + 冲刷）。
  • M3 分支惩罚约 3 个周期；回跳循环每圈都要付这个代价。
  • 所以 实测 MIPS 永远低于主频：72MHz 的真实吞吐约 45~60 MIPS。
三 · 指令集与寄存器
  • RISC / CISC 的本质差别：定长 vs 变长、load-store vs 内存操作数、寻址少而规整 vs 多而复杂、硬布线 vs 微码。
  • ARM 选 RISC（面积/功耗/流水线简单）；现代 x86 内部译码成定长 μops，两者在融合。
  • ARMv7-M 只有 Thumb 状态：T 位必须为 1；函数指针最低位是 Thumb 标记。
  • Thumb-2 = 16 位编码的密度 + 32 位编码的能力混编，编译器自动选择。
  • 寄存器 16 个：R0~R12 通用、R13=SP、R14=LR、R15=PC，外加 xPSR（APSR+IPSR+EPSR 三合一，含 N/Z/C/V/Q 与异常号）。
  • MSP / PSP 双栈指针 + CONTROL（SPSEL 选栈、nPRIV 选特权级）。
  • Thread / Handler 两种模式 × 特权 / 非特权 = RTOS 的立足点：任务跑在非特权级 + PSP，越权即触发异常。
四 · 写法与调用约定
  • 寻址九式：立即数、寄存器、间接、基址+偏移、前索引 [R0,#4]!、后索引 [R0],#4、PC 相对……
  • 立即数受编码限制：大常数靠 MOVW+MOVT 或常量池（LDR Rn,=0x...）。
  • 跳转四兄弟：B 不回来、BL 写 LR、BX 可换状态、BLX 两者兼有。
  • AAPCS：R0~R3 传参、R0 返回、R4~R11 被调用者保存、SP 8 字节对齐。
  • volatile 只阻止编译器优化（不缓存/不删除/不合并/不重排），不保证原子与线程安全。
  • 会读汇编的三个用处：定位 HardFault、看懂性能、验证编译器有没有按你的预期干活。

自测题（先自己答，再看答案）

  1. CPU 执行一条 LDR R0, [R1, #4] 时，五个阶段分别有哪些部件在工作？这条指令在第几阶段访问了存储器？

    答案：IF 取指（控制器 + I-Bus，从 Flash 取出指令编码，PC 自增）；ID 译码（控制器识别出「基址寄存器 R1 + 偏移 4 的加载」并读出 R1）；EX 执行（ALU 把 R1 的值加 4，算出有效地址）；MEM 访存（只有这一步访问数据存储器，走 D-Bus 把 [R1+4] 处的内容读出来）；WB 写回（把读到的数据写进目标寄存器 R0）。关键点：访存只在 MEM 阶段——这正是 load-store 结构的体现，运算指令不会有 MEM 阶段。

  2. 为什么说「流水线并没有让一条指令变快，却让程序变快了」？

    答案：因为拆成多级后，单条指令的延迟（latency）反而增加（每级要过一个寄存器、多级之间要同步），但它提高了吞吐（throughput）：理想情况下每个周期都有一条指令完成，而不是每五个周期才完成一条。程序是由成千上万条指令组成的，所以决定总时间的是吞吐而不是单条延迟。推论：分支会打断这种「稳定流水」，所以跳转的代价特别高（冲刷已取入的指令，M3 约 3 个周期）。

  3. 「STM32 是哈佛结构，但它用统一编址访问 Flash、SRAM 和外设」——这两句话矛盾吗？为什么？

    答案：不矛盾。编址方式说的是地址空间怎么划分（一整套 4GB 门牌号：Flash 在 0x08000000、SRAM 在 0x20000000、外设在 0x40000000），这是程序员视角；哈佛结构说的是 CPU 内部有几条独立通路（I-Bus 取指、D-Bus 取数、System Bus 管外设），这是硬件视角。「一套门牌号 + 多条马路」完全可以共存，Cortex-M 正是这么做的（常称为改良哈佛结构）。

  4. 主频 72MHz、理想 CPI = 1 时峰值是多少 MIPS？如果程序里 20% 是指令是分支、每次分支惩罚 3 个周期，实际 MIPS 是多少？

    答案：峰值 = 72 ÷ 1 = 72 MIPS。加上分支惩罚后 CPI = 1 + 0.2 × 3 = 1.6，实际吞吐 = 72 ÷ 1.6 = 45 MIPS，比峰值低 37.5%。再考虑 load-use 停顿（约 +0.03）和中断、Flash 等待周期，真实值还会更低。结论：永远不要用主频当性能指标。

  5. R14（LR）为什么必须存在？如果汇编函数里要调用另一个函数却不保存 LR，会发生什么？

    答案：LR 保存子程序返回地址，让 BX LR / POP {PC} 能一条指令返回，而不必把返回地址压栈（这是 RISC 精简指令、减少访存的典型设计）。LR 只有一个：非叶子函数（体内有 BL/BLX）如果不把 LR 压栈，第二次调用就会覆盖掉自己的返回地址，函数返回时会跳到错误的位置——现象是「跑飞」或 HardFault。正确做法：序言 PUSH {..., LR}，结尾 POP {..., PC}。

  6. RTOS 为什么需要「Thread/Handler 模式 + 特权/非特权 + MSP/PSP」这一整套？

    答案：它解决三个具体问题。① 栈的隔离：每个任务有自己的栈，内核用 MSP、任务用 PSP，切换任务就是改 PSP——没有 PSP 就无法实现「任务私有栈」。② 权限的隔离：任务跑在非特权级，碰 MPU 禁止的区域或执行特权指令会触发异常（变成可控的故障），而不是安静地改坏别人的内存。③ 内核与任务的区分：中断和内核服务运行在 Handler 模式 + 特权级，任务运行在 Thread 模式 + 非特权级，边界清晰。此外，RTOS 启动第一个任务时用的正是「伪造一个异常返回帧、写 EXC_RETURN = 0xFFFFFFFD」这个技巧。

  7. 函数指针为什么能工作？调用它和执行普通函数调用在硬件上有什么差别？

    答案：因为函数名在编译后就是一个地址，存进变量后再取出来用，对 CPU 来说就是「跳到一个运行时才知道的地址」。硬件上：普通调用是 BL 目标（目标地址编码在指令里，相对跳转）；函数指针调用是「先把地址装进寄存器，再 BLX Rn」（间接跳转）。BLX 同样会把下一条指令的地址写进 LR，所以返回机制完全一样——这就是它能工作的全部秘密。唯一的坑：Cortex-M 上地址最低位是 Thumb 标记（必须为 1），编译器会自动处理，但手写时不加就会 HardFault。

  8. 发生 HardFault 时，你怎么在 30 秒内找到出错的那条指令？

    答案：按六步法。① 在 HardFault_Handler 里用 __attribute__((naked)) 取出被压栈的栈帧（R0,R1,R2,R3,R12,LR,PC,xPSR，PC 就是出错指令的地址）；② 读 SCB->CFSR 看是哪类故障（PRECISERR / IMPRECISERR / UNDEFINSTR / UNALIGNED / DIVBYZERO）；③ 如果 BFARVALID 置位，读 SCB->BFAR 得到出错时访问的地址（例如 0x00000004 ⇒ 空指针 + 偏移 4）；④ 用 addr2line -e firmware.elf -f -C 0x出错PC 把 PC 翻译成源码行号；⑤ 看 LR 判断故障发生在任务里（0xFFFFFFFD，用 PSP）还是中断里（0xFFFFFFF9）；⑥ 回头检查那行代码的指针/数组下标/除数。

练习（建议动手做，每项 15~40 分钟）

1

用 DWT 实测三种操作的周期数

初始化 DWT->CYCCNT，分别测：① 一次 GPIO 翻转（GPIOA->ODR ^= (1<<5)）；② 一次 float 乘法（没有 FPU 的芯片上会调用库函数，差距会很震撼）；③ 一次 printf。把结果做成表格，算出各自占 72MHz 下的微秒数。做完这一题，你会对「C 语言每一行的代价」产生全新的直觉。

2

从自己的 .lst 里读三个函数

打开 Keil 的 Listing 选项生成 .lst（或用 arm-none-eabi-objdump -d -S），挑三个不同类型的函数：一个纯计算的、一个带局部数组的、一个内部调用别人的。对每个函数回答三个问题：参数在哪些寄存器里？栈帧多大？它是不是叶子函数（有没有 PUSH LR）？

3

故意制造一次 HardFault 并用六步法定位

写一个 typedef struct { uint32_t a, b; } T; T *p = NULL; p->b = 1; 的小程序，把本节给的 HardFault_Handler + hardfault_report() 抄进去，跑一次，记录：出错 PC、CFSR、BFAR、LR（EXC_RETURN），然后用 addr2line 验证它指向的源码行是否就是那一行赋值。（这个练习做过一次，以后遇到跑飞就不会慌。）

4

用 BSRR 和「读-改-写」各翻转一次 LED，比较波形

版本 A：GPIOA->ODR |= (1<<5); GPIOA->ODR &= ~(1<<5);（三条指令、非原子）；版本 B：GPIOA->BSRR = GPIO_BSRR_BS5; GPIOA->BSRR = GPIO_BSRR_BR5;（一条指令、原子）。用逻辑分析仪或示波器看波形，再用 objdump 对比两者的指令条数。思考：为什么 BSRR 在 F4/L4/G4 上也能用，而位带不行？

5

（进阶）量化一次优化

找一段耗时循环（例如软件 I2C 的位翻转、定点滤波），先用 DWT 测出周期数，再：① 打开 -O2；② 把循环内的除法改成移位或乘法；③ 把频繁访问的数组下标变量改成指针自增（省掉「取下标 → 左移 → 加基址」）。每次改动都用 DWT 重新测量并记录收益。你会发现：真正的性能优化发生在「指令与周期」的层面，而不在代码风格层面。
