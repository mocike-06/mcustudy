定时器与计数原理

单片机里有一个外设，它的全部本事就是「数数」：来一个时钟沿加一，数到头了就举手报告一次。 听起来简单得不像话，但你把它的输入换个来源（自己的时钟、外部引脚、另一个定时器），把它的「数到头」接个不同的出口（中断、DMA、引脚翻转、触发 ADC）， 它就变成了延时、频率计、PWM 发生器、电机换相器、正交编码器接口、系统心跳——所有这些功能共用同一个计数器。 这一篇要讲的就是那个计数器，以及它身上挂的几件「外挂」。搞懂这一套之后你会发现：输入捕获、输出比较、PWM、编码器接口，不再是四个要分别背下来的外设，而是同一个东西的四种用法。

这一篇的钥匙只有一句话：定时器和计数器是同一套硬件。 差别只在「数的是自己的时钟，还是外面的脉冲」；
再往上，输入捕获 / 输出比较 / PWM / 编码器接口， 都是同一个计数器换了不同的「外挂」。

为什么需要它

先看一个几乎每个人都写过的延时函数。你在 51 上点灯、在 STM32 上写流水灯，第一次学「延时」的时候都是这么写的：

void delay_ms(uint32_t ms)
{
    /* 空循环硬耗时间：靠 CPU 一条一条执行指令来「数」出这段延时 */
    for (uint32_t i = 0; i < ms * 1000U; i++) {
        __NOP();          /* 什么也不干，纯粹烧时间 */
    }
}

这段代码能跑，你按一下、灯亮一下，看起来没问题。但它身上背着三个致命问题，而且这三个问题全都会在真实项目里咬你一口。

问题一：它占着 CPU 不放

空循环的本质是「让 CPU 原地踏步」。这段时间里 CPU 什么都做不了——不能读按键、不能刷数码管、不能回应串口。你延时 500ms，就等于把整台单片机的 500ms 白白扔掉。

更麻烦的是它是串行叠加的。假设你要同时做三件事：按键扫描（每 20ms 一次）、数码管刷新（每 5ms 一次）、串口上报（每 1s 一次）。用软件延时，你只能这样排：

while (1) {
    key_scan();       /* 假设内部 delay 20ms  */
    seg_refresh();    /* 假设内部 delay 5ms   */
    delay_ms(975);    /* 再凑够 1 秒，然后串口上报 */
    uart_report();
}
/* 于是：
 *  · 串口周期 = 20 + 5 + 975 + 上报耗时，永远不会正好是 1 秒；
 *  · 只要 uart_report() 今天多花了 3ms，明天数码管刷新就变成 5ms + 3ms；
 *  · 想再加一个「每 100ms 读一次 ADC」，你得回去把 975 重新分配一遍。 */

问题二：它的时间是不确定的——换台电脑编译一遍就变了

这是最容易被低估的一条。软件延时的真实时长取决于三件你控制不了的事：

  • 编译优化等级：Keil 里把优化从 -O0 改成 -O2，编译器发现这个空循环「没有副作用」，可能把它整个删掉或者合并掉，延时直接变成几乎为零。你调好的 20ms 消抖变成 0.2ms，按键立刻开始疯狂误触发。
  • 主频：同样一份代码，STM32 跑 72MHz 和跑 8MHz（比如你改错了 PLL 配置、或者程序掉进了内部 HSI），延时差 9 倍。
  • 中断：延时期间来一个中断，CPU 去处理中断，循环被暂停，实际延时会变长。中断越频繁，偏差越大，而且是不可预测的抖动。

还有一条更隐蔽的：不同型号、不同编译器版本、不同库版本的指令周期数都不一样。所以「我用 1000 次空循环大概是 1ms」这种结论，换一个人编译就不成立了。它不是一个可以写进设计文档的数字。

问题三：它无法与其它任务并行

第三点是前两点的必然结果。你的项目最后一定长成这样：采样要 10ms、显示要 50ms、上报要 1s、还有一路 PWM 要一直输出。用软件延时，这四件事只能抢同一个 CPU 时间轴，谁也不能「同时在跑」——你在等 1 秒的时候，PWM 的引脚是不会自己翻转的（除非你用中断，而中断又回到了「谁来数时间」的问题上）。

核心转折：让「时间」变成一种硬件资源

定时器做的事，就是把「数时间」这件事从 CPU 手里拿走，交给一个独立的硬件去数。你只需要在初始化时告诉它：数到多少个时钟沿，就举手报告一次。之后它自己在那儿数，CPU 该干嘛干嘛，等它举手（中断）的时候你再去处理。

这一下就同时解决了三个问题：CPU 被解放（不用原地踏步了）、时间是硬件给的（只要晶振准，它就是准的，和编译器、优化等级、中断都无关）、多个时间尺度天然并行（多个定时器各自数各自的，或者一个定时器数基准、软件在里面分频出不同周期）。

从这一刻起，「时间」和 GPIO、串口、ADC 一样，成了一种可以被分配、被配置、被复用的硬件资源。这是嵌入式开发里最重要的一个观念转变。

顺便说一句：这一篇对你在 51 上学的东西是完全兼容的。51 的 T0/T1 也是同一套思路——TH0/TL0 装初值、溢出置 TF0、进中断。你在 51 上被「重装初值」折磨过的那些细节，到了 STM32 会变成「为什么它不用重装」，所以这一篇的很多地方都会把两边摆在一起讲。

定时器的本质：一个会自己数数的寄存器

如果只允许用一句话概括定时器，那就是：它就是一个加一（或减一）的寄存器，每来一个时钟沿加一；加到某个上限时归零，并顺手发一个「我数满了」的通知。

很多人以为这是两个外设。其实它们是同一套硬件，区别只在时钟从哪来：

  • 数自己的系统时钟（分频之后）→ 因为时钟频率是已知且精确的，数的个数换算成时间就是确定的 → 这时候叫定时器。
  • 数外部引脚上来的脉冲→ 数出来的是「外面来了几个脉冲」，和时间无关 → 这时候叫计数器。

51 上这个开关就是 TMOD 里的 C/T 位：0 是定时、1 是计数。STM32 上没有这一位，因为它做得更彻底——时钟源是一个四选一的多路开关（下一小节就讲）。所以「定时器/计数器」不是两种外设，是同一个外设的两种接法。

时钟源：数自己的钟，还是数外面的脉冲

STM32 的定时器在时钟入口处放了一个多路选择器，一般有四路可选。你可以把它想成一个「节拍从哪来」的开关：

CK_INT		 APB 总线时钟（经倍频规则后的定时器时钟） 99% 的场景：延时、PWM、系统 tick、测量本机时间
外部时钟模式 1

STM32 特有的坑：APB 预分频不为 1 时，定时器时钟会「倍频」

这一条不看时钟树一定会算错。规则是：如果 APBx 预分频系数不是 1，那么挂在这条总线上的定时器，时钟 = 2 × PCLKx；如果预分频系数正好是 1，定时器时钟就等于 PCLKx。

在 STM32F103C8T6 上跑标准 72MHz 配置时：

SYSCLK = 72MHz（外部 8MHz 晶振 × PLL 9 倍频）
   │
   ├─ AHB 预分频 ÷1 ──► HCLK = 72MHz   （内核、DMA、存储器用这个）
   │
   ├─ APB1 预分频 ÷2 ─► PCLK1 = 36MHz
   │                     │
   │                     └─ 因为预分频 ÷2 ≠ 1，所以要 ×2 补回来
   │                        ──► TIM2 / TIM3 / TIM4 的时钟 = 36MHz × 2 = 72MHz ✅
   │
   └─ APB2 预分频 ÷1 ─► PCLK2 = 72MHz
                         │
                         └─ 因为预分频 ÷1 = 1，所以不倍频
                            ──► TIM1 的时钟 = 72MHz ✅

【一个常见的自相矛盾】
   有人看到 PCLK1 = 36MHz，就以为 TIM2 的时钟是 36MHz，
   于是按 36MHz 算 PSC 和 ARR —— 结果定时时间整整差了一倍。

【更隐蔽的另一种情况】
   如果你把 APB1 预分频改成 ÷1（PCLK1 = 72MHz），
   那 TIM2 的时钟就【不倍频】了，正好还是 72MHz —— 结果一样。
   所以「PCLK1=36 时定时器是 72」和「PCLK1=72 时定时器是 72」都成立，
   这也是为什么很多人根本没意识到有倍频这回事，
   直到换了个主频配置才突然发现定时全乱。

怎么避免踩这个坑？两个办法：① 用 CubeMX 的 Clock Configuration 页，把鼠标放在定时器那一行，它会直接告诉你这个定时器的实际时钟是多少；② 在程序里用 HAL_RCC_GetPCLK1Freq() 读出来自己算：if (prescaler != 1) timer_clk = 2 * pclk;。绝对不要凭印象写死 72 这个数字。

什么时候必须用外部时钟？判断标准很简单：当你要「数的东西」不是时间，而是外面发生的事件次数时。

  • 水表、电表、流量计输出的脉冲 → 每一个脉冲代表一个计量单位，你要数的是脉冲个数，不是时间 → 用 ETR 外部时钟模式 1。这样做的好处是 CPU 完全不用管，数到一定个数（ARR）才进一次中断，1 万个脉冲只需要进 1 次中断。
  • 电梯/机床的限位开关抖动计数、霍尔传感器的转速脉冲 → 同样用外部时钟模式。
  • 要做一个 24 小时甚至几天的超长定时 → 内部时钟数不了那么久（16 位不够），用级联（外部时钟模式 2）把上一级的溢出当节拍。
  • 反过来说：如果只是想「测一下这段代码跑了多久」，那永远用内部时钟，不要去接外部信号。

另外提醒一句：走 ETR 或外部触发时，引脚上的信号不是「直接」驱动计数器的，中间通常还有极性选择（上升沿/下降沿/双边沿）、预分频（每 2/4/8 个脉冲算一次）、数字滤波（连续采样 N 次一致才认账）三级处理。这一套和后面输入捕获用的是同一套滤波电路，所以信号有毛刺的时候，不用额外加 RC 电路，先试试把滤波器的值调大。

定时时间的计算：PSC 与 ARR

这是全篇最重要的一个公式，先把每一项的物理意义说清楚：

            (PSC + 1) × (ARR + 1)
      T  =  ───────────────────────
                   f_clk

  T      一次「数满一圈」需要的时间（秒）。也就是两次更新事件之间的间隔。
  f_clk  定时器的输入时钟频率（Hz）。注意：是【倍频规则之后】的时钟，
         不是 PCLK，也不是 SYSCLK 想当然的那个值。
  PSC    预分频寄存器里的值。实际分频系数是 (PSC + 1)，所以 PSC=0 表示不分频。
  ARR    自动重载寄存器里的值。实际一圈数 (ARR + 1) 个数，所以 ARR=0 表示每来一个沿就满。

  【为什么处处都是 +1？】
    因为这两个寄存器都是「从 0 开始数」的：
      PSC = 0  → 不分频（÷1），不是 ÷0（÷0 没有意义）
      PSC = 71 → ÷72
      ARR = 999 → 一圈 1000 个数（0,1,2,...,999 正好 1000 个）
      ARR = 0  → 一圈只有 1 个数
    这个 +1 忘了写，算出来的时间就是错的，而且是「差一点点」这种最难发现的错。

把公式倒过来，你会看到一件重要的事：PSC 和 ARR 的乘积决定了周期，但这个乘积怎么分配，决定了「分辨率」。

反算 PSC 与 ARR 的四步法（照这个顺序做，不会错）
  1. 确认定时器时钟 f_clk。查时钟树或读 HAL_RCC_GetPCLK1Freq()，别忘了「预分频不为 1 就 ×2」这一条。
  2. 先算总的计数次数 N = T × f_clk。这一步就把单位换算做完了（毫秒换成秒，别搞错 1000 倍）。
  3. 先定 ARR 的位数上限，再分频。16 位定时器的 ARR 最大 65535，所以 (ARR+1) ≤ 65536。为了让分辨率尽量高（比较值能调的档数尽量多），先取 ARR 尽可能大，剩下的留给 PSC：PSC+1 = N / (ARR+1)。如果 N 大于 65536 × 65536，那这个定时器一次根本定不了那么久，必须级联（见例 2）。
  4. 回代核对误差。因为 PSC 只能取整数，除不尽就会有误差：T实际 = (PSC+1)×(ARR+1) / f_clk，误差 = (T实际 − T目标)/T目标。误差在 ppm 级（百万分之几）就完全够用。

实务上更省事的做法是第 3 步反过来：先把 PSC 定成一个能让计数时钟变成「整数 MHz」的值（比如 72MHz ÷ 72 = 1MHz），这样 ARR 就正好等于「多少微秒」，心算非常快——1MHz 计数时钟下 ARR+1 就是微秒数。这也是为什么 72 分频（PSC=71）在 72MHz 的板子上出现频率极高。

ARR 的位数，决定了一次能定多长。这一点在选型时非常关键：

看到「16 位最长 59.65 秒」这个数字，你就明白为什么会有「级联」这个需求了：要定 1 小时，单个 16 位定时器从原理上就做不到，只能让定时器去数另一个定时器的溢出。这一块在例 2 和第 2 节最后一小节会详细展开。

和 51 定时器的对应关系

你在张毅刚那本书第 5 章学的 51 定时器，和 STM32 的定时器是同一个思想的两个版本。把两边摆在一起看，你会发现 STM32 只是把 51 里「隐含的东西」显式地做成了寄存器。

先回忆 51 的四种工作方式（这里只讲和定时/计数相关的部分）：

方式 0：13 位定时/计数器
        ┌──────────── TH0（8 位）────────────┬─── TL0 低 5 位 ───┐
        最大计数值 2^13 = 8192
        初值要装两次（TH0 和 TL0 各一次），溢出后要【手动重装】
        这是 8048 时代留下的兼容方式，新设计基本不用

方式 1：16 位定时/计数器  ★ 最常用
        ┌──────────── TH0（8 位）────────────┬──── TL0（8 位）────┐
        最大计数值 2^16 = 65536
        初值 = 65536 − 需要计的个数
        溢出后 TF0 置 1，【必须在中断里手动重装初值】

方式 2：8 位自动重装  ★ 相当于 STM32 的 ARR
        ┌── TH0（8 位，只当重载值用，不参与计数）──┐
        └── TL0（8 位，真正的计数器）─────────────┘
        TL0 溢出时，硬件自动把 TH0 的值复制进 TL0
        → 不需要在中断里重装，中断响应慢一点也不会丢时间

方式 3：双 8 位（只有 T0 有）
        TL0 用 T0 自己的控制位（TR0/TF0）当 8 位定时器
        TH0 借用 T1 的 TR1/TF1 位，再当另一个 8 位定时器
        此时 T1 只能当波特率发生器用（不产生中断）

【51 的两个硬约束，STM32 都没有】
  ① 51 的时钟是固定的：机器周期 = 12 / f_osc。
     12MHz 晶振 → 机器周期 1µs，定时器每个机器周期加 1。
     【没有预分频器】—— 想要更长的定时，只能在中断里用软件再数一个变量。
  ② 51 的外部计数最高频率 = f_osc / 24。
     因为外部脉冲要保证高电平、低电平各自至少维持一个机器周期。
     12MHz 晶振 → 最高只能数 500kHz 的脉冲。

为什么 STM32 不需要「每次在中断里重装初值」

因为 51 的方式 0 和方式 1 不是自动重装：溢出后 TH0/TL0 从 0 继续数（或者从你上次装的值继续数到溢出），你必须在中断服务函数里重新写一遍初值。这带来两个后果：

  • 中断响应有延迟，时间就有误差。从溢出到你把新初值写进去，中间过了多少个机器周期，取决于当前在执行什么指令、有没有更高级的中断在跑。所以 51 用方式 1 做长时间累计的时候，误差会一点点攒起来。
  • 丢初值是经典 bug。如果中断被关了、或者中断函数里忘了重装，定时器会以 65536 个机器周期为周期一直跑——很多人「定时器突然慢了几十倍」就是这么来的。

STM32 的 ARR 是硬件自动重装：CNT 撞到 ARR 的那一刻，硬件在同一拍里把 CNT 清零（或按方向重载），不需要任何软件参与。所以：你的中断服务函数晚进 1µs、10µs，定时精度都不会受影响——中断里做的事只是「响应这个事件」，而不是「维持这个周期」。这是 51 到 STM32 最重要的一个观念升级。

顺便回答一个常见困惑：那 STM32 的中断里到底要不要操作 ARR？一般不要。如果你的中断延迟已经大到影响定时精度，说明你的中断写得太长了，应该去优化中断，而不是去中断里重装寄存器。

还有一个观念上的差异值得单独说：51 的「软件分频」思维在 STM32 上要改掉。51 因为不能预分频，想要 1 秒定时，标准做法是让定时器 50ms 中断一次，然后在中断里累加一个变量数到 20。到了 STM32，你既可以用 PSC/ARR 直接把周期做长（一个 16 位定时器在不级联的情况下最长约 59 秒），也可以沿用累加变量的办法（后面第 4 节「一个 1ms 中断带多个任务」讲的就是这种混合做法，它其实是最灵活的）。两种都可以，但要知道硬件能做到什么程度，别让软件去干硬件本来就能干的事。

再说那条很容易被忽略的 DMA 路：更新事件可以触发一次 DMA 请求（把 DIER 里的 UDE 置 1）。这条路的经典用法是让 DMA 每次更新事件时自动把下一个 CCR 值搬进比较寄存器——于是你可以预先在内存里放一张 1000 个点的正弦表，让定时器一个周期一个点地把它「播」出去，CPU 完全不参与。这就是「定时器 + DMA 做任意波形发生器」的原理。它也是「定时器是很多外设的节拍源」的一个例子：DMA、ADC 都可以被定时器的事件驱动。

影子寄存器：为什么改了 ARR 不会立刻生效

这是新手最容易困惑的一点，值得单独讲。你写代码 __HAL_TIM_SET_AUTORELOAD(&htim2, 1999)，然后发现定时周期还是原来的值，要等到「下一次溢出」之后才变。这不是 bug，是设计。

原因在于：ARR（以及 PSC、CCR）这些寄存器实际上是成对存在的——你写进去的那个叫预装载寄存器（preload register），真正被硬件拿去比较的那个叫影子寄存器（shadow register）。写了预装载寄存器之后，值要等到下一个更新事件才被搬进影子寄存器。

【为什么非要这么设计？】
  假设你正在输出一个 PWM，ARR 决定频率。如果写进去立刻生效，
  而写入的时刻又恰好落在计数周期中间，那这一圈就会变成一个
  「半截长」的畸形周期 —— 输出波形上会出现一个不该有的窄脉冲。

  有了影子寄存器，所有修改都被推迟到「这一圈数完」这个整齐的时间点上，
  波形永远是完整的整数个周期。这是【用延迟换稳定】的经典硬件设计。

【怎么控制这个行为？】
  ARR 的预装载由 CR1 的 ARPE 位控制：
    ARPE = 1（CubeMX 默认 Enable）→ 有影子寄存器，修改在下一个 UEV 生效
    ARPE = 0                      → 写 ARR 立刻生效（此时才等价于 51 的直接写）

  PSC 也有影子寄存器，但它在 STM32 上【总是】在 UEV 时才被重新加载，
  没有开关可关 —— 所以「启动后再改 PSC」几乎不会立刻看到效果。
  正确做法是：停止定时器 → 改 PSC → 重新启动，
  或者干脆重新初始化一次（HAL_TIM_Base_Init + Start）。
想让修改立刻生效的两种做法（以及一个副作用）

做法一：软件触发一次更新事件。把 EGR 寄存器的 UG 位置 1，硬件会立刻「假装数满了一圈」，把预装载值搬进影子寄存器。副作用：这个动作同时会把 CNT 清零、并（在 URS=0 时）置起 UIF 标志——如果你开了更新中断，就会多进一次中断。所以要么接受这次多余的中断，要么临时把 URS 位设成「只由硬件溢出产生中断」。

做法二：把 ARPE（自动重载预装载）关掉。此时写 ARR 立刻生效。代价是失去了波形完整性保护，适合「我只在停止状态下改参数」的场合。

最省心的建议：需要动态改变频率时（比如做可调频的 PWM），在更新中断里改 ARR——那一刻本来就正好是 UEV，新值会马上被搬进影子寄存器，既及时又不会撕裂波形。这也是日志里「在中断里改 ARR」唯一正当的理由。

  · 中央对齐是「三角波」式计数，一个周期 2×ARR 个数，波形左右对称。
  · 中央对齐时更新事件可能在上溢和下溢两端都产生，

    高级定时器（TIM1/TIM8）还额外提供了重复计数器 RCR，

为什么电机的 PWM 喜欢中央对齐

两个原因，都来自「对称」这两个字：

  • 谐波更小。边沿对齐的 PWM 在每个周期里只有一个边沿在「抖动」（调制时边沿位置变化），它的频谱里偶次谐波很丰富；中央对齐的波形左右对称，对称波形只含奇次谐波，偶次谐波被抵消掉。对电机来说，谐波意味着额外的铁损、铜损、转矩脉动和可听噪声。所以同样的开关频率下，中央对齐的电机运行更安静、发热更小、转矩更平稳。
  • 死区对称。互补输出的上下两个管之间必须插死区（下一小节详述）。边沿对齐时，一个周期里只有两个开关边沿集中在周期的固定位置；中央对齐时，两个边沿分别位于三角波的两个对称位置，死区带来的「有效占空比损失」在两个半周期里是对称抵消的，而边沿对齐会造成输出电压的直流偏移，这个偏移在低速时会变成明显的转速/转矩误差。

代价也要知道：同样的计数时钟下，中央对齐的频率比边沿对齐低一半（分母是 2×ARR），而且分辨率相同的情况下 ARR 要取一半，所以「要 20kHz 的中央对齐 PWM」比「要 20kHz 的边沿对齐 PWM」更吃定时器资源。

输入捕获：把外部的时间抓进来

前面讲的都是「定时器自己数自己的时钟」。从这一小节开始，我们给这个计数器挂上不同的「外挂」。第一件外挂叫输入捕获（Input Capture，IC），它解决的问题是：怎么用定时器测量外部信号的频率、周期、脉宽、占空比？

原理简单得惊人：在外部信号出现指定边沿的那一瞬间，把 CNT 的当前值抄一份存进 CCR 寄存器。因为 CNT 是随时间匀速增加的，两次捕获得到的两个 CCR 值之差，就是这两次边沿之间过了多少个计数时钟——时间就出来了。

测频法和测周法：两种测频率的思路，适用区间完全不同

「测一个信号的频率」有两种思路，而它们各有各的死角。这一段是这一小节最重要的内容。

【测频法】固定一个「闸门时间」Tg，数闸门内来了多少个脉冲

   外部信号  ─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌
              └─┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘
   闸门      ┌──────────────────────────────────────┐   Tg = 1 秒
             │         数到 N = 50 个脉冲            │
             └──────────────────────────────────────┘
   结论：频率 f = N / Tg         误差来源：±1 个脉冲（边界上数不完整）

【测周法】用已知的高频时钟去数「一个信号周期」有多少个计数

   外部信号  ─┐                    ┌────────
              └────────────────────┘
              │◄──── 一个完整周期 T ────►│
   内部时钟  ─┴┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─ 每个数字代表 1 个计数
              数到 N = 20000 个计数
   结论：周期 T = N / f_clk，频率 f = f_clk / N
         误差来源：±1 个计数（起点和终点各差一个刻度）

【两者的误差公式（这是选型的依据）】

   测频法的相对误差 ≈ 1 / (f × Tg)
       → 频率越高，误差越小；频率越低，误差越大（因为分母小）

   测周法的相对误差 ≈ f / f_clk
       → 频率越低，误差越小；频率越高，误差越大（因为周期短、数的数少）

【分界点】让两者相等：1/(f·Tg) = f/f_clk  →  f = √(f_clk / Tg)
   取 f_clk = 72MHz、Tg = 1 秒：
        f = √(72 000 000) ≈ 8485 Hz ≈ 8.5 kHz
   →  低于约 8.5kHz：用测周法更准
   →  高于约 8.5kHz：用测频法更准
   （注意这个分界点会随你的闸门时间和时钟频率变化，公式记牢就行）
对比项测频法（数脉冲个数）测周法（数时钟个数）
数的是什么外部信号的脉冲个数内部高频时钟的周期数
谁的精度决定结果闸门时间的准确度（一般是晶体，很准）内部计数时钟的准确度（同样来自晶体）
误差公式±1/(f·Tg)±f/f_clk（测 N 个周期时是 ±f/(N·f_clk)）
适合的频率段高频（几十 kHz 以上）低频（几十 Hz ~ 几 kHz）
在 50Hz 上的表现1 秒闸门下只有 50 个数，误差 ±2%1MHz 计数下数 20000 个，误差 ±0.005%
在 20kHz 上的表现1 秒闸门下数 20000 个，误差 ±0.005%72MHz 计数下只数 3600 个，误差 ±0.028%
响应速度慢：必须等满一个闸门（1 秒）才有结果快：一个（或几个）信号周期就能出结果
占用资源需要一个精确的闸门定时（另一个定时器或 SysTick）+ 脉冲计数（ETR 或外部中断）一个输入捕获通道 + 一个溢出计数（周期超过量程时）
实现难度闸门同步麻烦（闸门开始/结束时的半个脉冲），要用「等精度」技巧才准简单直接，一个捕获通道搞定，还能顺便测占空比
还有第三种：多周期同步法（等精度测量）

工程上真正做频率计，用的往往是两者的结合：用被测信号的边沿去「开门」和「关门」，同时数被测脉冲个数和被时钟个数。这样闸门时间不再是固定的 1 秒，而是被测信号周期的整数倍，边界上的 ±1 误差只发生在时钟那一侧：相对误差 ≈ 1/(Tg · f_clk)，与被测频率无关——所以叫「等精度」。

举例：闸门约 1 秒（由被测信号自己决定）、时钟 72MHz，则不管测 50Hz 还是 20kHz，相对误差都是 1/(1×72e6) ≈ 1.4×10⁻⁸，也就是 0.014ppm 量级。这就是市面上几百块的频率计的底牌。实现方式就是第 4 节要讲的「PWM 输入模式 + 溢出补偿」的加强版：一路通道捕被测信号（同时用来复位计数器），另一路通道捕时钟。

PWM 输入模式：一个通道同时得到周期和占空比

要测一个 PWM 的频率和占空比，朴素的做法是用两个捕获通道、或者用同一个通道捕两次（先上升沿后下降沿）。但 STM32 提供了一个更漂亮的做法：PWM 输入模式（PWM Input Mode）。它只用一个引脚，硬件自动把「周期」和「高电平时间」分别存进两个 CCR，软件一减一除就得到占空比。

                    ┌──────────────────────────────────────────┐
   外部 PWM 信号      │              一个定时器                    │
        │            │                                          │
        └──► TI1 ────┼──┬──► TI1FP1（上升沿）──► IC1 ──► CCR1 = 周期
                     │  │                                       │
                     │  └──► TI1FP2（下降沿）──► IC2 ──► CCR2 = 高电平时间
                     │                                          │
                     │  同时：TI1FP1 还被接到【从模式控制器】上，
                     │        配置成 Reset 模式 ——
                     │        每个上升沿都把 CNT 清零！          │
                     └──────────────────────────────────────────┘

   波形上就是这样的（CNT 每个周期都从 0 重新开始数）：
                                    ┌──────────────────────┐
   PWM 输入   ─────────────────────┘                      └──────────
              ▲                                            ▲
              │ 上升沿：CNT 清 0，同时 CCR1 记下【上一圈的周期】
              │
              ▼ 下降沿：CCR2 记下 CNT 此刻的值 = 高电平持续了多少个计数
   CNT        0 ──► 高电平段 ──► CCR2 ──► 继续数 ──► CCR1 ──► 被清 0
                                                        （下一圈开始）

   于是：  周期 = CCR1 / f_cnt
           占空比 = CCR2 / CCR1   ← 注意分母是 CCR1，不是 ARR！

   【为什么分母不是 ARR？】
     因为从模式配置成了 Reset，CNT 是被外部信号清零的，
     它数到多少完全取决于外部信号的周期，和 ARR 没关系。
     ARR 在这里只要设成 0xFFFF（最大）即可，防止还没数到就被自己溢出清零。

   【代价 / 限制】
     · 占用两个捕获通道（IC1 和 IC2），而且它们必须都映射到 TI1 上。
     · 只支持 TI1 和 TI2 两组，不是任意通道都能做。
     · 外部信号周期不能超过定时器的量程（16 位时是 65535 个计数），
       否则要先加大 PSC，或者做溢出计数。
溢出处理：两次捕获之间定时器自己先转了一圈怎么办

这是输入捕获最容易被忽略的一个坑，而且它在「测低频信号」时必然发生。假设你的计数时钟是 1MHz、ARR = 65535（量程 65.5ms），要测一个 1Hz 的信号（周期 1000ms）：两次捕获之间，定时器自己已经溢出 15 次了。这时候直接相减 CCR_new − CCR_old，得到的是一个完全错误的数字。

解决办法只有一个：给溢出次数单独记一个数。两种实现方式：

  • 软件计数（常用）：开更新中断，在中断里 overflow_cnt++；捕获中断里算 总计数 = overflow_cnt × (ARR+1) + CCR_new − CCR_old，算完把 overflow_cnt 清 0。这个写法在下面第 4 节有完整代码。
  • 硬件帮忙（更稳）：在捕获中断里顺便查一下更新标志 UIF 是不是也被置起来了——如果置了，说明在这次捕获前后正好发生了一次溢出，而更新中断可能还没来得及执行（比如优先级更低）。这时候把溢出计数再补 1。这个「补一刀」的细节，是保证长时间测量不错数的关键。

判断「要不要处理溢出」的准则很简单：只要被测信号的最长周期超过 ARR 对应的量程，就必须处理。做设计时可以先估算一下：量程 = (ARR+1)/f_cnt，留 2~3 倍余量最舒服。

输出比较与 PWM：把时间送出去

第二件外挂叫输出比较（Output Compare，OC），它和输入捕获正好是一对镜像：输入捕获是「外面的事件 → 抄走 CNT」，输出比较是「CNT 到点了 → 改变输出引脚」。

比较的对象是 CCR 寄存器：硬件不停地比较 CNT 和 CCR，相等的那一刻（或者说满足某种不等关系的那一刻），按照你配置的动作去动引脚。可选的动作有：翻转、强制为高、强制为低、保持不变。其中「翻转」这一个动作，就足以做出任意频率的方波：让 CNT 每数到 CCR 就翻转一次引脚，得到的就是一个半周期等于 CCR 个计数的方波。

但真正在工程里天天用的是 PWM 模式，因为它比「翻转」多了一个关键能力：每个周期自动重置输出电平，占空比由 CCR 单独决定。看波形就明白了：

【PWM 模式 1（向上计数）】CNT < CCR 时输出【有效】电平

   ARR = 999, CCR = 300  （占空比 = 300/1000 = 30%）
   CNT  0 ────────► 300 ──────────────► 999 ─► 0
        ┌──────────┐
        │  有效     │
   ─────┘          └──────────────────────────────
        │◄─ 300 ──►│◄────── 700 ─────────────────►│
        高电平 30%          低电平 70%
        （假设极性配置为「有效=高」）

【PWM 模式 2（向上计数）】CNT < CCR 时输出【无效】电平 —— 正好反过来

   ARR = 999, CCR = 300
        ┌────────────────────────────────────────┐
        │              有效（高）                 │
   ─────┘                                        └──────
        │◄────── 300 ──────►│◄──── 700 ──────────►│
        低电平 30%（无效）        高电平 70%（有效）

【两个「极性」概念要分清，这是最容易混的地方】

   ① OC 模式（PWM1 / PWM2）：决定「CNT 和 CCR 的大小关系」对应哪种电平
   ② 输出极性（CCxP 位）    ：决定「有效电平」到底是高还是低
                               CCxP=0 → 有效电平 = 高；CCxP=1 → 有效电平 = 低

   两者组合出四种结果，但工程上【只用一种组合】最不容易乱：
        PWM 模式 1 + 极性不反相（CCxP = 0）
   这时候一切都直观：占空比 = CCR/(ARR+1)，CCR 越大高电平越长。
   其它三种组合都对，但会让「占空比公式」变成一个要查表的条件式，
   除了「驱动低电平有效的 LED / 反相驱动」这种明确需求，别去动它。

【占空比公式（PWM 模式 1、极性不反相、向上计数）】
        占空比 = CCR / (ARR + 1)
   【注意分母是 (ARR+1)】
        CCR = 0        → 占空比 0%（输出一直无效，全低）
        CCR = ARR+1    → 占空比 100%（输出一直有效，全高）
        CCR > ARR+1    → 硬件不会报错，效果等同于 100%
   这给了你一个安全范围：写 CCR 时不用小心翼翼地避免越界，
   但反过来，如果你算错了导致一直 100%，波形上就再也看不出调制了。

把频率和占空比两个公式放在一起，你就得到了 PWM 的全部设计流程：先用 PSC 和 ARR 定频率，再用 CCR 定占空比。它们之间有一个必须权衡的东西：分辨率。

频率与分辨率的权衡：这是 PWM 设计里唯一需要动脑子的地方

一圈数 (ARR+1) 个数，就意味着占空比只能分成 (ARR+1) 档。ARR = 999 时每档 0.1%，ARR = 99 时每档 1%，ARR = 9 时每档 10%（这时候调占空比是「跳」的，做呼吸灯会看到明显的台阶）。

而 f_pwm = f_clk / ((PSC+1)(ARR+1))——ARR 大则分辨率高、频率低。所以流程是：

  1. 先定 PWM 频率（电机一般 10~20kHz，避开人耳听觉范围；LED 调光 1~5kHz 足够；加热丝可以几百 Hz）。
  2. 用 (PSC+1)(ARR+1) = f_clk / f_pwm 算出总的分频比。
  3. 优先把 ARR 取到 1000~4000 这个量级（分辨率 0.1%~0.025%，呼吸灯非常顺滑），剩下的分给 PSC。
  4. 如果算出来 ARR 只能取到很小的值（说明频率太高、时钟不够快），那就是硬件到极限了——要么降频率，要么换更高主频的芯片，不要指望软件补偿。

互补输出与死区：为什么半桥驱动必须要有它

到目前为止 PWM 都是「一个通道一根线」。但只要你去驱动电机、逆变器、大功率加热，就一定会遇到半桥（H 桥的一半）这种结构：

              VCC（比如 24V / 310V）
                │
                ├──────────────┐
                │              │
                │         ┌────┴────┐
                │         │  上管 Q1 │◄── 由 CH1（主输出）驱动
                │         └────┬────┘
                │              │
                │              ├────────► 输出到电机 / 负载
                │              │
                │         ┌────┴────┐
                │         │  下管 Q2 │◄── 由 CH1N（互补输出）驱动
                │         └────┬────┘
                │              │
                └──────────────┴──────  GND

   【致命场景：直通（shoot-through）】
     如果 Q1 和 Q2 同时导通 —— 电源正极和地之间只剩两个
     导通电阻（毫欧级），电流 = VCC / (Rds_on_Q1 + Rds_on_Q2)。
     24V / 0.02Ω = 1200A（理论值，实际会被电源和引线限制）。
     结果：不是「工作不正常」，而是【瞬间烧毁】两个管子，
     严重时连驱动芯片和电源一起带走。

   【为什么会同时导通？】
     因为 MOS 管的关断不是瞬间的：
       · 栅极电荷要泄放，关断有几十到几百纳秒的延迟；
       · 上管还带着米勒电容和体二极管的反向恢复。
     所以「给下管发导通命令」的时刻，必须比「给上管发关断命令」
     晚一段时间 —— 这段时间就叫【死区时间（Dead Time）】。
【没有死区】两路驱动信号的边沿完全对齐

   CH1  ────┐                    ┌────────────
            └────────────────────┘
   CH1N ────────────────┐                    ┌──
                        └────────────────────┘
                        ▲▲
                        └┴── 这段时间【理论上】两管同时收到导通命令
                            实际因为关断延迟，会真的出现同时导通 → 直通

【插入死区后】上下管之间强制留出空档

   CH1  ────┐                    ┌────────────
            └────┐               │
                 │ 死区          │
   CH1N ─────────┘  ┌────────────┘         ┌──
                    └──────────────────────┘
            ▲        ▲
            │        └─ 下管导通前，上管必须已经可靠关断
            └─ 上管导通前，下管必须已经可靠关断
            期间两管都不导通，负载电流走【体二极管】续流

【死区带来的代价（要心里有数）】
   · 输出电压损失：死区期间输出电压由体二极管钳位（约 -0.7V 或 VCC+0.7V），
     所以实际输出比理论占空比少一点点 → 低速时表现为转矩/转速偏差。
   · 死区是【时间】单位，不是占空比单位：PWM 频率越高，
     死区占整个周期的比例越大，损失越明显。
     20kHz（周期 50µs）配 1µs 死区 → 理论最大占空比已经损失 2%！
   · 所以死区要「够用就好」：够覆盖关断延迟 + 余量，不要盲目设大。

STM32 把这个功能做在了硬件里：高级定时器（TIM1、TIM8）的每个通道都有 CHx 和 CHxN 一对互补输出，死区由 BDTR 寄存器里的 DTG[7:0] 字段生成，不需要软件去算延时。这个死区发生器的工作细节：

BDTR 寄存器（Break and Dead-Time Register）

  ┌──────┬──────┬─────┬─────┬──────┬─────┬─────┬──────┐
  │ MOE  │ AOE  │ BKP  │ BKE │ OSSR │ OSSI│ LOCK │ DTG  │
  └──────┴──────┴─────┴─────┴──────┴─────┴─────┴──────┘
     │      │      │      │      │      │              │
     │      │      │      │      │      │              └─ 死区时间（8 位）
     │      │      │      │      │      └─ 空闲时输出状态：0=释放(高阻)，1=保持无效电平
     │      │      │      │      └─ 关闭时（MOE=0）输出状态：同上

     │      │      └─ 刹车输入极性
     │      └─ 自动恢复输出：刹车解除后，在下一个更新事件自动重新使能 MOE
     └─ 主输出使能：=0 时所有输出被强制到空闲状态
        【这是 PWM 没输出的头号原因之一，见第 4 节排查清单】

【死区时间的计算】DTG 分了 4 段，越往后的段步进越大：

  DTG[7:5] = 0xx  →  DT = DTG[7:0]          × t_DTS     范围 0 ~ 127 t_DTS
  DTG[7:5] = 10x  →  DT = (64 + DTG[5:0])   × 2 t_DTS   范围 128 ~ 254 t_DTS
  DTG[7:5] = 110  →  DT = (32 + DTG[4:0])   × 8 t_DTS   范围 256 ~ 504 t_DTS
  DTG[7:5] = 111  →  DT = (32 + DTG[4:0])   × 16 t_DTS  范围 512 ~ 1008 t_DTS

  其中 t_DTS 是死区发生器的时钟周期，由 CR1 的 CKD 位选择：
      CKD = 00 → t_DTS = 1 / f_timer
      CKD = 01 → t_DTS = 2 / f_timer
      CKD = 10 → t_DTS = 4 / f_timer

  例：f_timer = 72MHz，CKD = 00 → t_DTS = 13.89ns
      想要 1µs 死区：1µs / 13.89ns = 72 → 取第一段，DTG = 72 = 0x48
      想要 10µs 死区：10µs / 13.89ns = 720 → 落在第 4 段，
                      720 / 16 = 45，再减 32 = 13 → DTG = 0b111_01101 = 0xED
      （注意第 4 段的步进是 16 t_DTS = 222ns，所以【设不出】任意精确值，
        只能设成 16 的倍数附近 —— 这是硬件限制，不是 bug）

【刹车输入 BKIN】
   BKIN 是一根专门的输入（也有极性选择），一旦有效：
     · 硬件【异步】地把 MOE 清零 —— 不等时钟，立刻生效；
     · 所有输出按 OSSI 的配置进入空闲状态；
     · 置起 BIF 标志，可以进刹车中断。
   典型用法：把过流比较器（比如采样电阻 + LM393）的输出直接接到 BKIN，
   一旦电流超标，硬件在纳秒级就把六个输出全关掉，
   比软件进中断再关快了几个数量级 —— 这是保护功率管最关键的一道防线。
   AOE = 1 时，刹车解除后会在下一个更新事件自动恢复输出，
   适合「过流是瞬态、可以自动重启」的场合（比如有刷电机的堵转保护）。
上电顺序里的一个致命细节

MOS 管的栅极在上电时可能是浮空的，这时候上下管有可能都处于半导通状态。所以做功率驱动时：① 先让定时器把两路输出都置为「无效电平」并且死区已经配好，再让功率级的电源上电；② 用 MOE 作为总开关——初始化完成后才置 MOE；③ 有条件的话给栅极加下拉电阻，让驱动芯片没上电时栅极被可靠拉低。

我见过太多「一上电就炸管」的案例，最后查出来是「程序还没跑到初始化，驱动芯片的输出已经因为浮空而乱跳」。软件的顺序，决定硬件的生死。

级联与编码器接口

这一小节讲两件「外挂」，它们看起来毫不相关，但本质上都是「不数自己的时钟，而是数别人给的事件」——正好回到本文开头那句话：定时器和计数器是同一套硬件。

定时器级联：让一个定时器去数另一个的溢出

前面算过，16 位定时器在 72MHz 下、PSC 拉满，一圈最长也就 59.65 秒。要定 1 小时、1 天怎么办？答案是级联：把上一级定时器的「更新事件」当成下一级定时器的时钟。

这件事需要两个配置配合：

  • 主定时器要「把更新事件输出到 TRGO 引脚」。TRGO 是定时器内部的一根广播线（TRGO = Trigger Output），它可以选择输出什么东西，由 CR2 的 MMS 位决定：可以输出「更新事件」（MMS=010，级联时最常用）、「使能」（001）、「比较脉冲」（011）、或者某个通道的 OCxREF（100~111）。选 010，就是「我每数满一圈，就在 TRGO 上发一个脉冲」。
  • 从定时器要「用外部时钟模式 2 或内部触发，把 TRGO 当自己的节拍」。从定时器通过 SMCR 寄存器选择触发源（TS 位选 ITR0~ITR3）和工作方式（SMS 位）。

这里有一个必须查表的细节：ITR0~ITR3 不是「任意定时器都能选」。芯片内部只有四条固定的触发线，每条线硬连接到某个特定的定时器，具体对应关系写在参考手册的「TIMx 内部触发连接（TIMx internal trigger connection）」表里。所以级联之前一定要查那张表——CubeMX 里反而更省事：在 Slave Mode 选好 Trigger Mode 之后，Trigger Source 的下拉框里能选到的，就是硬件上真的连了的。在 F103 上，「TIM2 当主、TIM3 当从」是一个很常见的组合。

【目标】先用 TIM2 把 72MHz 分到 1kHz，再用 TIM3 数 TIM2 的溢出得到 1Hz

   ┌──────────────────────────┐         ┌──────────────────────────┐
   │        TIM2（主）         │         │       TIM3（从）          │
   │                          │         │                          │
   │  CK_INT = 72MHz          │         │  时钟源 = TRGO of TIM2    │
   │      │                   │         │       ▲                  │
   │      ▼                   │         │       │                  │
   │  PSC = 7199  → ÷7200     │         │  PSC = 0  → ÷1           │
   │      │                   │         │       │                  │
   │      ▼  10kHz            │         │       ▼  1kHz            │
   │  CNT 数到 ARR = 9        │         │  CNT 数到 ARR = 999      │
   │      │  （即 ÷10）        │         │      │  （即 ÷1000）     │
   │      ▼                   │         │      ▼                  │
   │   1kHz 更新事件 ─────────┼─ TRGO ─►│   1Hz 更新事件 → 中断     │
   │   （MMS = 010）           │         │   （SMS = 外部时钟模式2） │
   └──────────────────────────┘         └──────────────────────────┘

   验算：72 000 000 / 7200 / 10 = 1000 Hz          （TIM2 的更新频率）
         1000 / 1 / 1000 = 1 Hz                    （TIM3 的更新频率）
         1Hz → 周期 1 秒，误差为 0（三个数都是整除）

【级联的好处】
   · 把一个 16 位定时器「扩」成 32 位：两级各 16 位，
     理论最大分频比 65536 × 65536 ≈ 4.3 × 10^9，
     72MHz 下可以定出 59.65 秒 × 65536 ≈ 45 天。
   · 每一级的中断都可以单独使用：比如 TIM2 的 1kHz 用来做
     控制环，TIM3 的 1Hz 用来做数据记录 —— 一份时钟，多个节奏。
   · CPU 负担为零：所有分频都是硬件做的，不占一次中断。
不止两级：级联是可以叠的

理论上可以把 TIM2 → TIM3 → TIM4 → TIM5 一路串下去，每一级再除 65536 倍。实际做「1 小时定时」只需要三级就够（例 2 给了完整算法）。要注意的是：级联链越长，最后一级的「分辨率」越差——第一级数 72000 个时钟才出 1 个脉冲，最后一级每动一下就是 1 秒，你想在这上面做微调是不可能的。所以级联适合做「粗时间基准」，精细的时间还得靠专门的定时器。

编码器接口：让硬件替你数电机的转角

旋转编码器（正交编码器）输出两路方波 A 和 B，它们频率相同、相位相差 90°。这 90° 的相位差就是「方向」的全部信息，而 STM32 的定时器可以靠纯硬件把它解出来：根据两相的电平关系，决定 CNT 是加还是减。

【正转（A 相超前 B 相 90°）】

   A  ────┐       ┌───────┐       ┌────
          └───────┘       └───────┘
   B  ────────┐       ┌───────┐       ┌
              └───────┘       └───────┘
          S1      S2      S3      S4     S1  ...

   状态序列：S1 → S2 → S3 → S4 → S1 → ...
   每个状态对应 (A,B) 的一组编码：
        S1 = (1,0)    S2 = (1,1)    S3 = (0,1)    S4 = (0,0)

【反转（B 相超前 A 相 90°）】状态序列反着走
   状态序列：S1 → S4 → S3 → S2 → S1 → ...

【四倍频是怎么来的 —— 这是本节的关键】
   一个完整的正交周期 = 信号走完 S1→S2→S3→S4 四个状态。
   而在这四个状态之间，有【4 个边沿】：
        A 的上升沿（S4→S1）      A 的下降沿（S2→S3）
        B 的上升沿（S1→S2）      B 的下降沿（S3→S4）

   → 编码器接口模式 3（Encoder Mode 3）会在【两相的每一个边沿】都计数
   → 机械上转一格（一个正交周期），CNT 变化 4
   → 这就是【四倍频】：把编码器的分辨率直接提高 4 倍

   模式 1 / 模式 2 只在一个相的边沿计数（2 倍频），
   工程上基本都用模式 3，白拿 4 倍分辨率为什么不用。

【方向识别】
   硬件在每个边沿都会看「另一相此刻的电平」：
     正转时，A 的上升沿总落在 B 为低的时候
     反转时，A 的上升沿总落在 B 为高的时候
   → 硬件据此决定 CNT++ 还是 CNT−−，不需要软件判断

   → 所以 CNT 里装的就是【带符号的位置】，读出来转成 int16_t
     直接就是「正转了多少格 / 反转了多少格」。

【机械抖动的影响，必须知道】
   普通的旋钮式编码器（不带定位、或者用机械触点的那种）在转动时
   触点会弹跳，产生一串快速的 A/B 跳变。硬件会把它们全部计进去 ——
   表现为：手明明只转了一格，CNT 却跳了 2~3 个数，或者来回抖。

   对策（按有效性排序）：
     ① 打开输入滤波器（CCMR 里的 IC1F/IC2F），连续采样一致才认账；
        这是最省事、最可靠的一招，编码器模式下的滤波字段同样有效。
     ② 换用光电编码器 / 磁编码器（AS5600 等），从根本上没有抖动。
     ③ 软件侧做「最小变化量」过滤：只有 CNT 变化超过阈值才认，
        或者周期性采样并做滑动平均（代价是响应变慢）。
     ④ 硬件加 RC 滤波（10kΩ + 100nF，截止约 160Hz）——只在转速很低时可用。

   ⚠ 不要用「软件延时消抖」去处理编码器：转速快的时候会把真实边沿也吃掉。
编码器接口为什么是「同一个计数器」的最好例证

回头看一下子：编码器接口没有引入任何新的硬件资源——它就是那个 CNT，只不过「加还是减」不再由计数方向位决定，而是由 A/B 两相的电平决定。CNT 还是那个 CNT，ARR 还是那个 ARR（编码器模式下一般把 ARR 设成 65535，让它能正反转都能数很大范围），CCR 依然可以用来在特定位置触发中断（比如「转到这里就输出一个信号」）。

这就是本文反复强调的那句话最好的例子：输入捕获、输出比较、PWM、编码器接口，全都是同一个计数器换了不同的外挂。你不需要把它们当成四块知识去背——你只需要记住那个计数器，再记住四根线怎么接。

动手算一遍

定时器这一块的坑，九成以上都是算错的，不是配错的。所以这一节不厌其烦地把最常见的五类计算从头做一遍：正着算（给定时间求 PSC/ARR）、反着算（给定频率求参数）、算极限（最长能定多久）、算误差（两种测频方法的胜负）、以及 51 那边的老算法。每个例子的单位换算都写出来，你照着走一遍就不会错。

例 1：72MHz 反算 1ms / 20ms / 1s 的 PSC 与 ARR

已知定时器时钟 f_clk = 72MHz（已按倍频规则确认：这是倍频之后的定时器时钟，不是 PCLK1 的 36MHz）。我们分别要 1ms、20ms、1s 三个周期，求 PSC 和 ARR。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【第 0 步】先算总的分频比 N = T × f_clk
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   1ms：N = 0.001 s × 72 000 000 Hz = 72 000
   20ms：N = 0.020 s × 72 000 000 Hz = 1 440 000
   1s ：N = 1.000 s × 72 000 000 Hz = 72 000 000

   注意单位：T 必须换成【秒】再乘，否则会差 1000 倍。
   这三个 N 就是 (PSC+1)×(ARR+1) 需要等于的数。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【1ms】N = 72000
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   习惯做法：先让计数时钟变成「整数 MHz」，这样 ARR 就等于微秒数。

       PSC + 1 = 72          →  PSC = 71
       计数时钟 = 72MHz ÷ 72 = 1MHz（即 1µs 一个数，心算极快）

       ARR + 1 = 72000 ÷ 72 = 1000
       ARR = 999

   验算：T = (71+1) × (999+1) / 72 000 000
           = 72 × 1000 / 72 000 000
           = 72000 / 72 000 000
           = 0.001 s = 1.000 ms        ✅ 误差 0

   分辨率：一圈 1000 个数 → 最小可调 1µs，占 1ms 的 0.1%。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【20ms】N = 1 440 000
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   ★ 推荐配法（保持 1µs 分辨率，和 1ms 那个共用同一个计数时钟）：

       PSC = 71                            → 计数时钟 1MHz
       ARR + 1 = 1 440 000 ÷ 72 = 20 000
       ARR = 19 999

   验算：T = 72 × 20000 / 72 000 000 = 0.02 s = 20.000 ms   ✅ 误差 0
   检查：ARR = 19999 ≤ 65535，没超 16 位              ✅

   ☆ 另一种配法（周期相同，但分辨率差很多）：
       PSC = 719（÷720）→ 计数时钟 100kHz（10µs 一个数）
       ARR = 199       → 一圈 200 个数
       T = 720 × 200 / 72e6 = 0.002 s ... 等等，这是 2ms，不是 20ms！
       → 正确写法：PSC+1 = 7200（PSC = 7199）→ 10kHz；ARR+1 = 200 → ARR = 199
       T = 7200 × 200 / 72e6 = 0.02 s                      ✅
       但分辨率只有 200 档（10µs），做输入捕获测脉宽时会明显不够细。
   → 结论：同样的周期，【PSC 越小、ARR 越大，分辨率越高】。
     只要 ARR 没超过 65535，就优先把分频比堆到 ARR 上。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【1s】N = 72 000 000 —— 这里有个绕不开的矛盾
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   如果还想保持 1µs 分辨率，ARR + 1 就得是 72 000 000，
   而 16 位定时器的 ARR 最大只有 65535（一圈最多 65536 个数）。
   → 【1µs 分辨率和 1 秒周期，一个 16 位定时器给不了】
     必须二选一：要么牺牲分辨率加大 PSC，要么用级联（见例 2）。

   方案 A：整数配比，误差 0（推荐，好算好调）

       PSC + 1 = 7200        →  PSC = 7199    （计数时钟 10kHz，即 100µs 一个数）
       ARR + 1 = 10 000      →  ARR = 9999
       T = 7200 × 10000 / 72 000 000 = 72 000 000 / 72 000 000 = 1.000000 s  ✅

   方案 B：把分辨率榨到最大（接受一点点误差）

       ARR + 1 取满 = 65536  →  ARR = 65535
       PSC + 1 = 72 000 000 ÷ 65536 = 1098.63…  ← 除不尽，只能取整
       取 PSC + 1 = 1099     →  PSC = 1098
       反算 ARR + 1 = 72 000 000 ÷ 1099 = 65514.65…  → 只能取 65514，ARR = 65513

       验算：T实际 = 1099 × 65514 / 72 000 000
                    = 71 999 886 / 72 000 000
                    = 0.99999842 s

       误差 = (0.99999842 − 1) / 1 = −1.58 × 10⁻⁶ = −1.58 ppm
       → 每秒短 1.58µs。跑一天（86400 秒）累计短 0.137 秒。

       这个误差大不大？看你干什么：
          · 做数据记录的时间戳：完全够用（一天差 0.14 秒无所谓）。
          · 做实时时钟（RTC）：不够，一天差 0.14 秒意味着一个月差 4 秒。
          · 做串口波特率：够用，1.58ppm 远小于串口能容忍的 2%。

   ★ 结论：能凑出整数就凑整数（方案 A），凑不出来再接受 ppm 级误差，
     并且【一定要把这个误差算出来写进设计文档】——
     「大概准」和「准到多少」是两回事。
把「1MHz 计数时钟」变成条件反射

在 72MHz 的板子上，PSC = 71 出现频率极高，因为 1MHz 的计数时钟意味着 CNT 每加 1 就是 1 微秒、ARR = 999 就是 1ms、ARR = 19999 就是 20ms，全都是心算。做输入捕获测脉宽时更是如此——捕到的 CCR 差值直接就是微秒数，不用再换算。养成「先问计数时钟是多少」的习惯，能省掉大量计算错误。

这道题在做「定时记录数据」「超时保护」「整点上报」这类需求时必算，而且它的结论会直接决定你要不要动级联。

【第一步】单个 16 位定时器的极限
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   要让周期最长，就要让 (PSC+1)×(ARR+1) 最大。
   PSC 和 ARR 都是 16 位寄存器，最大值都是 65535，所以：

       (PSC+1)最大 = 65536      (ARR+1)最大 = 65536
       总计数个数 = 65536 × 65536 = 4 294 967 296

       T_max = 4 294 967 296 / 72 000 000 = 59.6522 秒

   → 【结论一】f_clk = 72MHz 时，一个 16 位定时器最长只能定约 59.65 秒。
     注意这不是「推荐值」，而是两面都拉满的极限值：
     此时 ARR 和 PSC 都写到了 65535，一次溢出要等将近 1 分钟，
     定时器的分辨率也低到没法看（改一个 ARR 就是几十微秒）。
     工程上一般不会这么用，真正要长周期请直接级联。

   【顺便算一下：如果是 32 位定时器呢？】
     STM32F4/F7 上的 TIM2、TIM5 是 32 位的，ARR 最大 0xFFFFFFFF。
     仍然配上 16 位 PSC 拉满：
       T = 4 294 967 296 × 65536 / 72 000 000
         = 2.8147 × 10¹⁴ / 7.2 × 10⁷
         = 3 909 000 秒 ≈ 45.2 天
     → 一颗 32 位定时器，单级就能做到 45 天的周期，不需要级联。
       （这也是为什么 F4/F7 的电机和 RTOS 项目很少做定时器级联。）

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【第二步】要定 1 小时，需要多大的总分频比？
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   1 小时 = 3600 秒
   总分频比 N_total = 3600 × 72 000 000 = 2.592 × 10¹¹

   单级上限 4.295 × 10⁹，比 N_total 小了 60 倍
   → 单级【不可能】做到，必须级联。
   两级上限 = (4.295×10⁹)² ≈ 1.84×10¹⁹ ≫ 2.592×10¹¹
   → 两级【绰绰有余】。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【方案 A：两级级联（最省资源，推荐）】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   第一级 TIM2：把 72MHz 分成 1kHz（顺手留下一个 1ms 的节拍，很实用）

       PSC = 7199（÷7200）  →  计数时钟 10kHz（100µs 一个数）
       ARR = 9    （÷10）    →  更新频率 1kHz，周期 1ms
       验算：72 000 000 / 7200 / 10 = 1000 Hz        ✅

   第二级 TIM3：时钟来自 TIM2 的 TRGO（即 1kHz 的更新事件）
                再分 3 600 000 倍，得到 1/3600 Hz（周期 1 小时）

       PSC = 3599（÷3600）
       ARR = 999 （÷1000）
       分频比 = 3600 × 1000 = 3 600 000     （≤ 4.295×10⁹，合法）✅
       输出频率 = 1000 Hz / 3 600 000 = 2.7778 × 10⁻⁴ Hz
       周期 = 1 / 2.7778×10⁻⁴ = 3600 秒 = 1 小时        ✅ 误差 0

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【方案 B：三级级联（每一级的周期都是「整数好记的时间」）】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   有时候你希望每一级都有自己的用途（1ms 做控制、1s 做记录、
   1 小时做上报），那就串三级，每一级的数都特别好记：

       TIM2：PSC = 7199, ARR = 9      →  1ms  (1kHz)     ← 主，MMS = 010 输出 UEV
       TIM3：PSC = 0,    ARR = 999    →  1s   (1Hz)      ← 从，时钟 = TIM2 的 TRGO
       TIM4：PSC = 35,   ARR = 99     →  1 小时          ← 从，时钟 = TIM3 的 TRGO

   最后一级验算：(35+1) × (99+1) = 3600
                 输入 1Hz ÷ 3600 = 2.7778 × 10⁻⁴ Hz → 周期 3600 秒 ✅

   总级联比 = 72000 × 1000 × 3600 = 2.592 × 10¹¹
             → 2.592 × 10¹¹ / 72 000 000 = 3600 秒 ✅

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【别忘了：还有两条不用级联的路】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   路一：软件累加。让定时器每 1 秒中断一次，在中断里把一个
         uint32_t 变量加 1，加到 3600 就认为过了一小时。
         优点：简单、参数好调、随时能改。
         缺点：需要 1 秒一次的更新中断（CPU 有负担）；
               如果中途关过中断，累计会丢。
         → 这是 51 时代的标准做法（因为 51 连 1 秒都定不了）。

   路二：用 RTC（实时时钟外设）。RTC 有独立的 32.768kHz 晶振和
         日历寄存器，本来就是干这个的，还能在主电源断电后靠
         纽扣电池继续走。做「整点上报」这类需求，
         正确答案通常是 RTC，而不是定时器级联。
         → 定时器级联适合「我必须精确知道过了多长时间，
            并且需要它在主时钟域里跟其它任务同步」的场合。

   【选择建议】
     · 只要一个「很久之后叫我一次」的定时 → 软件累加足够。
     · 要精确、不想占中断、且要在主时钟域 → 两级级联（方案 A）。
     · 要真实日期时间、要掉电继续走 → RTC。

例 3：由 PWM 频率反算 ARR 与 PSC，再算占空比和实际输出电压

这次的已知条件是 PWM 的三个需求：频率 1kHz、占空比 30%、引脚高电平 3.3V，用的定时器时钟仍然是 72MHz。要求给出 PSC、ARR、CCR，算出实际输出的平均电压，并评估分辨率够不够。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【第一步】算总的分频比
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   边沿对齐、向上计数：
       f_pwm = f_clk / ((PSC+1) × (ARR+1))
       →  (PSC+1) × (ARR+1) = f_clk / f_pwm = 72 000 000 / 1000 = 72 000

   （和例 1 的 1ms 定时是同一个式子 ——
     因为 1kHz 的周期就是 1ms，PWM 的本质就是一个定时器
     加上「在周期中间再比一次」而已。）

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【第二步】分配 72000 给 PSC 和 ARR —— 优先喂饱 ARR
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   ★ 常用配法：PSC = 71（÷72）→ 计数时钟 1MHz；ARR = 999 → 一圈 1000 个数

       验算：72 000 000 / 72 / 1000 = 1000 Hz              ✅

       分辨率：一圈 1000 档 → 占空比步进 0.1%
       验证「够不够」：人眼对亮度变化的感知大约在 1% 量级，
       0.1% 的步进做呼吸灯已经非常顺滑（1000 级灰阶）。

   ☆ 追求更细的配法：PSC = 7（÷8）→ 计数时钟 9MHz；ARR = 8999 → 9000 档
       验算：72 000 000 / 8 / 9000 = 1000 Hz               ✅
       分辨率：0.011%（9000 级）——但一圈要数 9000 个数，
       改 ARR 之后要等一圈才生效，动态变频时响应更慢。

   ✗ 糟糕的配法：PSC = 7199（÷7200），ARR = 9（10 档）
       频率也是 1kHz，但占空比只能取 0%、10%、20%…100% 这 11 个值，
       做呼吸灯会看到明显的台阶 —— 这就是【分辨率被 PSC 吃掉】的典型后果。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【第三步】算 CCR：占空比 30%
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   PWM 模式 1、极性不反相（有效电平 = 高）：
       占空比 = CCR / (ARR+1) = CCR / 1000 = 30%
       →  CCR = 300

   【注意分母是 ARR+1 = 1000，不是 ARR = 999】
        如果按 CCR/ARR 算，会得到 CCR = 299.7，取 300 之后
        实际占空比是 300/1000 = 30.0%（对的），看起来「碰巧对了」——
        但周期改成 ARR = 99 时差别就出来了：
        CCR/ARR 会算出 29.7，CCR/(ARR+1) 算出 30 整。
        养成写 (ARR+1) 的习惯，别赌。

   另外算两个边界，确认自己对公式的手感：
       要 5%  →  CCR = 0.05 × 1000 = 50
       要 0%  →  CCR = 0
       要 100% → CCR = 1000（= ARR+1，此时 CNT 永远小于 CCR，输出恒为有效）
       要 50% →  CCR = 500（此时 CCR 正好等于 ARR/2，是最「对称」的位置）

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【第四步】算实际输出电压（PWM 最常用的意义就在这里）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   PWM 经过低通滤波（或者驱动一个「响应不过来」的负载，比如电机、
   加热丝、LED），等效出来的就是【平均电压】：

       方法一：直接接 LED 调光（看的是平均亮度）
           平均电压 = 高电平 × 占空比 = 3.3V × 30% = 0.99 V

       方法二：用 MOS 管开关 12V 的加热丝
           平均电压 = 12V × 30% = 3.6 V
           （注意：这里 12V 是负载电源的电压，
             STM32 引脚只是控制 MOS 的栅极，本身仍在 3.3V 域里。）

       方法三：用 RC 滤波 + ADC 读回来做反馈
           RC 时间常数要远大于 PWM 周期（1ms），
           比如 R = 10kΩ、C = 10µF → τ = RC = 0.1 s = 100ms，
           纹波峰峰值 ≈ 高电平 × (T/τ) = 3.3 × 0.001/0.1 = 33 mV，
           平均值 = 0.99V（误差 1% 量级，够 ADC 用）。

   【反查：如果你的 ADC 读回 1.65V，占空比是多少？】
       假设 3.3V 域、RC 滤波后读数：
       占空比 = 1.65 / 3.3 = 50%   →  CCR = 0.5 × 1000 = 500
       这就是「闭环调压 / 闭环调光」的基本算式。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【第五步】换成中央对齐，参数要重算（这是最容易忘的一步）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   中央对齐的频率公式分母多了个 2：
       f_pwm = f_clk / ((PSC+1) × 2 × ARR)

   仍然用 PSC = 71（计数时钟 1MHz）：
       1000 Hz = 1 000 000 / (2 × ARR)  →  ARR = 500

   验算：1 000 000 / (2 × 500) = 1000 Hz                  ✅

   占空比公式也换了：
       占空比 = CCR / ARR = CCR / 500 = 30%  →  CCR = 150

   【对比一下两个方案的「代价」】
       边沿对齐：ARR = 999，一圈 1000 个数，分辨率 0.1%
       中央对齐：ARR = 500，一圈 2×500 = 1000 个数，分辨率 0.2%
    → 同样的计数时钟和同样的 PWM 频率下，
      中央对齐的分辨率是边沿对齐的一半。
      换来的是：波形对称、谐波小、死区对称。
      做电机驱动，这笔账是划算的；做 LED 调光，就没必要。

例 4：测频法与测周法，在 50Hz 和 20kHz 上谁更准

这道题是「输入捕获」这一块的选型依据。已知条件：内部时钟 f_clk = 72MHz（可以分频使用），测频法的闸门时间 Tg = 1 秒，被测信号有两个：工频 50Hz 和超声/开关电源常见的 20kHz。两种方法各测一次，比一比相对误差。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【方法一：测频法】固定 1 秒闸门，数被测信号来了多少个脉冲
              误差来源：闸门开始/结束时的 ±1 个脉冲
              相对误差 ≈ 1 / (f × Tg)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   ▸ 测 50Hz：
       计数值 N = 50 × 1s = 50
       ±1 个数 → 相对误差 = 1/50 = 2%
       结果表述：50 Hz ± 1 Hz（也就是 49 ~ 51 Hz 之间都可能）
       → 【完全不可用】。工频测量、转速测量里 2% 的误差毫无意义。

   ▸ 测 20kHz：
       计数值 N = 20000 × 1s = 20000
       ±1 个数 → 相对误差 = 1/20000 = 0.005% = 50 ppm
       结果表述：20000 Hz ± 1 Hz
       → 【非常好】。而且注意：闸门固定 1 秒时，
         测频法的【绝对】误差永远是 ±1Hz，
         频率越高，相对误差越小 —— 这就是它适合高频的原因。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【方法二：测周法】用内部时钟数「一个信号周期」有多少个计数
              误差来源：起点和终点各差 1 个计数 → ±1 个数
              相对误差 ≈ f / f_clk（测 1 个周期时）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   ▸ 测 50Hz（周期 20ms）：
       先看量程：72MHz 不分频时，一个周期需要
                 20ms × 72MHz = 1 440 000 个计数
                 —— 远超 16 位的 65535！直接测会溢出。
       → 方案 A：PSC = 71 把计数时钟降到 1MHz
                 计数值 N = 20ms / 1µs = 20000
                 相对误差 = 1/20000 = 0.005%（比测频法的 2% 好 400 倍）
       → 方案 B：保持 72MHz，但做溢出补偿（下一节的代码）
                 计数值 N = 1 440 000（跨越 21 次溢出）
                 相对误差 = 1/1 440 000 = 0.0000694% ≈ 0.69 ppm
                 （每 20ms 的绝对误差只有 13.9ns）
       → 【低频必须用测周法】，这句话在这里体现得淋漓尽致。

   ▸ 测 20kHz（周期 50µs）：
       72MHz 不分频：N = 50µs × 72MHz = 3600 个计数
       相对误差 = 1/3600 = 0.0278% = 278 ppm
       结果表述：20000 Hz ± 5.56 Hz
       → 【不如测频法的 ±1Hz】。因为周期太短，数的数太少，
         一个计数的量化误差就占了 1/3600。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【汇总对比表】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   被测频率   测频法（1s 闸门）          测周法（72MHz）           胜者
   ────────  ────────────────────────  ───────────────────────  ──────
    50 Hz     ±1/50   = ±2%      ✗      ±1/1440000 = ±0.69ppm ★  测周法
   500 Hz     ±1/500  = ±0.2%           ±1/144000  = ±6.9ppm ★  测周法
     5 kHz    ±1/5000 = ±0.02%          ±1/14400   = ±69ppm   ★  测周法
     8.5kHz   两者打平（分界点 ≈ √(f_clk/Tg) = √72e6 ≈ 8485 Hz）
    20 kHz    ±1/20000 = ±50ppm   ★     ±1/3600    = ±278ppm     测频法
   100 kHz    ±1/100000 = ±10ppm  ★     ±1/720     = ±1390ppm    测频法

   【结论与用法】
     · 低于约 8.5kHz → 用测周法（输入捕获），而且【顺便就能测占空比】。
     · 高于约 8.5kHz → 用测频法（ETR 外部计数 + 精确闸门）。
     · 分界点不是固定的：把闸门时间从 1s 延长到 10s，
       分界点降到 √(72e6/10) ≈ 2683 Hz；把时钟换成 168MHz，
       分界点升到 √(168e6) ≈ 12961 Hz。公式记住就行。

【如果两个频段都要测？用「多周期测周法」把低频优势搬到高频】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   测周法数 1 个周期的误差是 ±1 个数。
   如果【连续数 M 个周期】再一起算，误差仍然是 ±1 个数，
   但分母变成了 M × N：

       测 20kHz，连续测 100 个周期（总时长 5ms）：
           N = 72 000 000 / 20000 × 100 = 360 000
           相对误差 = 1/360000 = 2.78 ppm = 0.00028%
           频率误差 = 20000 × 2.78e-6 = 0.056 Hz   ★ 比测频法还好！
       （代价：要等 5ms 才出一个结果，响应变慢，而且 360000
         超出 16 位量程，需要溢出补偿或降低计数时钟。）

   这就是「用响应速度换算精度」的经典权衡 ——
   和示波器上「慢扫描更稳」是同一个道理。
别忘了一个前提：这些误差都是「量化误差」

上面算的全是±1 计数的量化误差，前提是你的晶振是准的。普通的 HC-49S 无源晶振，标称精度通常是 ±20ppm ~ ±30ppm（含温度漂移），也就是说测 20kHz 时晶振本身就会带来 0.4~0.6Hz 的误差——和测周法的量化误差同一个量级。

所以：当量化误差已经小于 10 倍晶振误差时，再折腾算法就没意义了。想要更准，第一步是换温补晶振（TCXO）或者用外部的高稳频率基准，而不是去优化算法。这条在仪器类项目里是必须知道的。

例 5：51 的 50ms 定时初值（张毅刚 第 5 章的老算法）

这道题是给你「对照」用的。51 的定时器初值算法和 STM32 的 PSC/ARR 算法在思路上是同一件事，但有个关键区别：51 算的是「往上数到哪里溢出」，STM32 算的是「数满一圈要多少个数」。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【已知】晶振 f_osc = 12MHz，要定时 50ms，用 T0、方式 1
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   第一步：算机器周期（51 的一个机器周期 = 12 个振荡周期）
       机器周期 = 12 / f_osc = 12 / 12 000 000 = 1 × 10⁻⁶ s = 1µs
       → 【51 定时器每 1µs 加 1】

   第二步：算需要多少个机器周期
       N = 50ms / 1µs = 50 000
       检查量程：方式 1 是 16 位，最多 65536 个数
                 50000 < 65536  ✅ 方式 1 装得下
       （如果算出来超过 65536，就只能先定一个短时间，
         再在中断里用软件变量累加，这是 51 上的常规操作。）

   第三步：算初值
       51 的定时器是【向上数到溢出】，所以初值要从满量程倒着减：
           初值 = 2¹⁶ − N = 65536 − 50000 = 15536
       转成十六进制：15536 = 0x3CB0
           （核对：0x3CB0 = 3×4096 + 12×256 + 0 + 176
                      = 12288 + 3072 + 176 = 15536 ✅）

       装载：
           TH0 = 0x3C;      /* 高 8 位 */
           TL0 = 0xB0;      /* 低 8 位 */
           TMOD = 0x01;     /* T0，方式 1（16 位定时器） */
           TR0  = 1;        /* 启动计数 */
           ET0  = 1; EA = 1;/* 开 T0 中断、开总中断 */

   第四步：中断服务函数里必须重新装初值
       void Timer0_ISR(void) interrupt 1
       {
           TH0 = 0x3C;      /* ← 这两行不能省！ */
           TL0 = 0xB0;
           /* 你的 50ms 任务 */
       }

【同样的 50ms，STM32 怎么写？对照看差异】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   f_clk = 72MHz，计数时钟取 1MHz（PSC = 71）：

       ARR + 1 = 50ms / 1µs = 50 000     →  ARR = 49 999
       验算：72 × 50000 / 72 000 000 = 0.05 s ✅  误差 0
       检查：ARR = 49999 ≤ 65535 ✅

   中断服务函数里【什么都不用装】：
       void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim)
       {
           if (htim->Instance == TIM2) {
               /* 直接写你的任务，不需要重装任何寄存器 */
           }
       }
   硬件会在 CNT 撞到 ARR 的同一拍里自动把 CNT 清零。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【误差对比：这才是「自动重装」真正的价值】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   ▸ 51 方式 1 的误差来源：
       ① 重装初值需要时间。从 TF0 置位到你的 ISR 执行完
          「TH0=…; TL0=…;」这两条指令，中间至少有
          中断响应延迟（几个机器周期）+ 流水线打断 + 现场保护。
          保守估计 5~10µs。这段时间里定时器【已经又数了几个数】，
          而你把初值一装，这几个数就白丢了 —— 于是每个周期
          都长一点点，误差【逐周期累积】。
       ② 中断被更高优先级中断打断 → 延迟更长 → 丢得更多。
       ③ 如果中断被关了（EA=0）整段没响应，那就不只是误差，
          而是直接丢了一整个周期。

   ▸ 数量级感受（按典型值估算）：
       假设每次重装平均丢 3 个机器周期 = 3µs，
       50ms 周期 → 每周期误差 3µs / 50ms = 60 ppm
       累积 1 分钟（1200 个周期）→ 累计偏差 1200 × 3µs = 3.6ms
       累积 1 小时 → 累计偏差 216ms

   ▸ STM32 的误差来源：
       只有晶振本身的误差（±20~30ppm，就是那颗 8MHz 晶振的锅）。
       硬件自动重装，中断晚进 100µs 都不影响周期。
       → 「定时准不准」这件事，从「取决于你的中断写得好不好」
         变成了「取决于你的晶振买得好不好」。
         这就是硬件替你干活的价值。
五道例题的「一句话总结」
  • 例 1：先算 N = T × f_clk，再优先把分频比堆给 ARR（分辨率），凑不出整数就算 ppm 级误差。
  • 例 2：16 位 72MHz 最长 59.65 秒；1 小时要两级级联（÷72000 → 1kHz，再 ÷3600000）。
  • 例 3：PWM 先按 (PSC+1)(ARR+1) = f_clk/f_pwm 定频率，再用 CCR/(ARR+1) 定占空比；中央对齐记得分母多乘 2。
  • 例 4：分界点 f = √(f_clk/Tg)，72MHz + 1 秒闸门 → 约 8.5kHz；低频测周、高频测频。
  • 例 5：51 的初值 = 满量程 − 计数值，而且每周期都要重装；STM32 用 ARR，一次配置永久生效。

TIM2 配成 1ms 更新中断：从参数推导到完整代码

第一步：确认时钟。CubeMX 的 Clock Configuration 页把 SYSCLK 配到 72MHz（HSE 8MHz × PLL 9）。此时 APB1 预分频 = 2 → PCLK1 = 36MHz → 因为预分频不是 1，TIM2 的时钟 = 36 × 2 = 72MHz。这一步千万别凭印象，把鼠标放在 CubeMX 时钟树上 TIM2 那一格，它会直接告诉你实际频率。

第二步：算参数。用例 1 的结论：PSC = 71（计数时钟 1MHz，1µs 一个数）、ARR = 999（一圈 1000 个数）→ 更新周期 72 × 1000 / 72 000 000 = 1.000 ms，误差 0。

【CubeMX → Timers → TIM2】

  Clock Source            : Internal Clock          ← 时钟源选内部
  Channel1~4              : Disabled                ← 只要时基，不用通道

  ── Parameter Settings ──────────────────────────────────────────
  Prescaler (PSC - 16 bits value)      : 71          ← ÷(71+1) = ÷72
  Counter Mode                         : Up          ← 向上计数
  Counter Period (AutoReload Register) : 999         ← 一圈 1000 个数
  Internal Clock Division (CKD)        : No Division ← 死区/滤波用的分频，这里无所谓
  auto-reload preload                  : Enable      ← ARPE=1，改 ARR 在 UEV 生效
  Trigger Event Selection              : Reset       ← 不用 TRGO 时可不管

  ── NVIC Settings ───────────────────────────────────────────────
  TIM2 global interrupt                : ☑ Enabled   ← 必须勾！
  Preemption Priority                  : 1           ← 比 SysTick(15) 高，比紧急中断低
  Sub Priority                         : 0

  【关键提醒】上面这个 NVIC 勾选框，是「定时器不进中断」的第一号原因。
  参数区（Parameter Settings）只管定时器自己数不数，
  勾了 NVIC 才管「数满了要不要叫 CPU」——【两件事，两个地方】。

CubeMX 生成的初始化代码大致长这样，你要能看懂每一行的意思：

#include "tim.h"

TIM_HandleTypeDef htim2;

void MX_TIM2_Init(void)
{
    TIM_ClockConfigTypeDef  sClockSourceConfig = {0};
    TIM_MasterConfigTypeDef sMasterConfig = {0};

    htim2.Instance = TIM2;
    htim2.Init.Prescaler         = 71;      /* ÷72  → 72MHz/72 = 1MHz */
    htim2.Init.CounterMode       = TIM_COUNTERMODE_UP;
    htim2.Init.Period            = 999;     /* 一圈 1000 个数 → 1ms */
    htim2.Init.ClockDivision     = TIM_CLOCKDIVISION_DIV1;
    htim2.Init.AutoReloadPreload = TIM_AUTORELOAD_PRELOAD_ENABLE;
    if (HAL_TIM_Base_Init(&htim2) != HAL_OK) {
        Error_Handler();
    }

    /* 时钟源：内部时钟（CK_INT）。这一步不能省，
       否则时钟源选择位不会被写进 SMCR。 */
    sClockSourceConfig.ClockSource = TIM_CLOCKSOURCE_INTERNAL;
    if (HAL_TIM_ConfigClockSource(&htim2, &sClockSourceConfig) != HAL_OK) {
        Error_Handler();

接下来是你自己要写的两段：启动定时器，以及在那个人人都会用到的回调函数里累加软件 tick。

#include "main.h"
#include "tim.h"

/* volatile 必须有：这个变量在中断里被改、在主循环里被读，
   编译器不知道它会「自己变」，不加 volatile 优化后可能读到旧值。
   （这一点在讲 C 语言进阶那篇里重点说过。） */
volatile uint32_t g_ms_tick = 0;

int main(void)
{
    HAL_Init();                     /* 这里面会配好 SysTick 的 1ms 时基 */
    SystemClock_Config();           /* 72MHz */
    MX_GPIO_Init();
    MX_TIM2_Init();

    /* ★ 启动定时器并【同时开更新中断】
       不加 _IT 就是只启动、不进中断 —— 这是第二个高频翻车点。 */
    if (HAL_TIM_Base_Start_IT(&htim2) != HAL_OK) {
        Error_Handler();
    }

    while (1) {
        /* 主循环里可以放心地用这个 tick 做非阻塞的定时 */
        static uint32_t t_last = 0;
        if ((g_ms_tick - t_last) >= 500U) {   /* 每 500ms */
            t_last += 500U;                   /* 注意是 +=，不是 = ，
                                                 这样不会累积漂移 */
            HAL_GPIO_TogglePin(GPIOC, GPIO_PIN_13);   /* 板载 LED */
        }
    }
}

/* ★ 更新中断最终会走到这里。
   HAL 已经在 stm32f1xx_it.c 的 TIM2_IRQHandler 里调用了
   HAL_TIM_IRQHandler(&htim2)，它会清标志、判断事件类型，
   然后回调下面这个弱函数 —— 你只要重写它就行。 */
void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim)
{
    if (htim->Instance == TIM2) {
        g_ms_tick++;                /* 就这么一行。硬件负责准，软件负责数 */
    }
}
这段代码里有三个「少一个字就废掉」的地方
  • HAL_TIM_Base_Start_IT() 的 _IT 后缀。HAL_TIM_Base_Start() 只让计数器跑起来，不会开更新中断，现象是「定时器明明在跑，回调函数一次都不进」。
  • 回调函数名必须是 HAL_TIM_PeriodElapsedCallback（周期溢出）——不要写成 HAL_TIM_OC_DelayElapsedCallback（输出比较）或者 HAL_TIM_IC_CaptureCallback（输入捕获）。三个回调对应三种事件，名字差一点就永远不进。
  • volatile 不能省。省了以后在 -O2 下，主循环里那个 while ((g_ms_tick - t) < 500) 有可能被优化成死循环——编译器认为循环里没人改这个变量。

TIM3_CH1 输出 1kHz PWM：呼吸灯的完整实现

这个例子的参数和例 3 完全一致：72MHz、1kHz、CCR 从 0 到 1000 慢慢来回走，LED 就会呼吸。先看 CubeMX 里多出来的那几步——PWM 比纯时基多了一个「引脚要复用成 AF 模式」的环节，这也是 PWM 没输出的常见原因。

【第一步：先想清楚用哪个引脚】
  TIM3_CH1 在不同封装上映射到不同引脚：
     · 默认（无重映射）：PA6
     · 部分重映射      ：PB4
     · 完全重映射      ：PC6
  Blue Pill 上最省事的是 PA6，不用动 AFIO 重映射。
  CubeMX 里直接在芯片图上点 PA6 → 选 TIM3_CH1 即可。
  【注意】一旦选了重映射的引脚，CubeMX 会自动生成
  __HAL_AFIO_REMAP_TIM3_PARTIAL() 之类的调用 —— 这行必须保留。

【第二步：Timers → TIM3】

  Clock Source : Internal Clock
  Channel1     : PWM Generation CH1        ← 关键！选 PWM Generation

  ── Parameter Settings ──────────────────────────────────────────
  Prescaler (PSC)     : 71        → 计数时钟 1MHz
  Counter Mode        : Up
  Counter Period(ARR) : 999       → 1kHz（1MHz / 1000）
  auto-reload preload : Enable
  PWM Mode            : PWM mode 1  ← CNT < CCR 时输出有效电平
  Pulse (CCR1)        : 0           ← 初值 0，占空比 0%，由程序改
  Output compare preload : Enable   ← ★ CCR 的预装载，改 CCR 不会撕裂波形
  CH Polarity         : High        ← 有效电平为高（不反相）

  ── GPIO Settings（CubeMX 自动带到这个标签页）────────────────────
  PA6 Mode            : Alternate Function Push Pull
  PA6 Pull            : No pull-up and no pull-down（外部有驱动电路时）

  PA6 Alternate Function  : 自动显示为 TIM3_CH1（AF 编号由 CubeMX 填）

    int32_t  step = 2;        /* 每次变化的步进 */

    while (1) {
        ccr += step;

        /* 到两头就反向：0 → 1000 → 0 → 1000 ... */
        if (ccr >= 1000) { ccr = 1000; step = -step; }
        if (ccr <= 0)    { ccr = 0;    step = -step; }

/* __HAL_TIM_SET_COMPARE 展开后就是一次对 CCR1 寄存器的写：
 *     (htim)->Instance->CCR1 = (__COMPARE__);
 * 16 位寄存器一次写完，是原子的，不存在「高低字节撕裂」的问题。
 * （如果在 8 位机上，写 16 位寄存器就有撕裂风险 —— 这也是
 *   51 上读 TH0/TL0 必须用特殊技巧的原因，见坑 7。） */
为什么呼吸灯的 CCR 一定要在主循环里改，而不是在中断里改

新手有一个直觉：「PWM 是定时的东西，那改占空比也应该放在定时器中断里，才『同步』、才『精确』」。这个直觉在呼吸灯这个场景下是错的，理由有三条：

  • 这个任务根本不需要精确的时刻。呼吸灯是给人眼看的，人眼对 1ms 量级的时间抖动完全无感。把不需要精确的事放进中断，是浪费中断资源。
  • CCR 有预装载（OC1PE），你在任何时刻写都是安全的。HAL 的 HAL_TIM_PWM_ConfigChannel 已经帮你把输出比较预装载打开了，所以你写进去的值会被硬件推迟到下一个更新事件才生效——不管你在主循环的哪一句改写它，波形都不会出现半个周期的畸形脉冲。既然硬件已经保证了同步，你就不需要用中断来「人工同步」。
  • 中断里做事越少越好。这一条是中断那一篇的核心结论：中断服务函数应该「记录事件、置个标志，赶紧回去」。在中断里做浮点运算、查表、改一堆寄存器，会拖长中断时间，影响其它中断的响应——呼吸灯占用了中断，代价是别的地方的实时性。

那什么时候必须在中断里改 CCR？两种场合：① 你要做的是变频（改 ARR）而不是变占空比——改 ARR 需要卡在更新事件那一刻，放在更新中断里最自然；② 你要让占空比的变化与某个外部事件严格对齐（比如「每次过零点之后的第 N 个周期才开始新占空比」）。除此之外，主循环里改就够了。

还有一个实践上的小问题：呼吸灯用 HAL_Delay(2) 是可以的，但如果你同时还要做别的事，就该换成时间戳比较：

/* 非阻塞版呼吸灯：主循环永不停留，其它任务照常执行 */
static void breath_led_poll(void)
{
    static uint32_t t_last = 0;
    static int32_t  ccr    = 0;
    static int32_t  step   = 2;

    if ((g_ms_tick - t_last) < 2U) {
        return;                 /* 还没到 2ms，直接返回，不阻塞 */
    }
    t_last = g_ms_tick;         /* 是赋值不是累加：呼吸灯不需要防漂移 */

    ccr += step;
    if (ccr >= 1000) { ccr = 1000; step = -step; }
    if (ccr <= 0)    { ccr = 0;    step = -step; }

    __HAL_TIM_SET_COMPARE(&htim3, TIM_CHANNEL_1, (uint32_t)ccr);
}

 *   while (1) {

 *       uart_poll();            // 串口处理，不受影响
 *   }

TIM4 输入捕获：测一个外部方波的频率和占空比

这个例子的目标是「给一个外部方波，报出它的频率和占空比」。为了不和上面的 PWM 例子抢引脚，这里改用 TIM4 的 CH1（PB6）和 CH2（PB7）：CH1 抓上升沿，CH2 抓下降沿，两者配合就能同时拿到周期和高电平宽度。

【CubeMX → Timers → TIM4】

  Clock Source : Internal Clock
  Channel1     : Input Capture direct mode      ← CH1 直接接到引脚，测上升沿
  Channel2     : Input Capture direct mode      ← CH2 直接接到引脚，测下降沿

  ── Parameter Settings ──────────────────────────────────────────
  Prescaler (PSC)     : 71      → 计数时钟 1MHz（1 个数 = 1µs）
  Counter Period(ARR) : 65535   ← ★ 一圈拉到最大（65.535ms）
  auto-reload preload : Enable

  ── Input Capture Channel 1 / Channel 2 ────────────────────────
  Polarity            : Rising Edge（CH1） / Falling Edge（CH2）
  IC Prescaler        : No division  ← 每个边沿都抓，不做 N 分频
  Input Filter (IC1F) : 0x3          ← ★ 采样 8 次全同才算有效边沿，
                                        是「读数乱跳」的第一号解药

  ── GPIO Settings ───────────────────────────────────────────────
  PB6 / PB7           : 自动配成 Input floating（浮空输入）
                        如果信号源是开漏输出（比如某些传感器），
                        要改成 Pull-up。

  ── NVIC Settings ───────────────────────────────────────────────
  TIM4 global interrupt : ☑ Enabled    ← 捕获中断和溢出中断共用这一个入口
  Preemption Priority   : 2

【注意】输入捕获【不需要】外部中断（EXTI）。
  引脚上的边沿是送到定时器的捕获单元，由定时器硬件记录 CNT，
  和 EXTI 那条「外部中断线」是两套完全不同的东西。
  很多人在这里绕弯路：把 PB6 配成 EXTI 再自己读时间戳，
  那样只能得到「大致时刻」，精度被中断延迟吃掉，
  而且做不到硬件同时记录两个边沿。

/* ────────────────────────────────────────────────────────────────
   测量结果。全部是 volatile：中断里写、主循环里读。
   ──────────────────────────────────────────────────────────────── */
typedef struct {
    uint32_t period_us;      /* 一个完整周期的微秒数 */
    uint32_t high_us;        /* 高电平的微秒数     */
    uint32_t freq_hz;        /* 换算出来的频率     */
    uint32_t duty_permille;  /* 占空比，千分数（0~1000） */
    uint8_t  valid;          /* 收到过至少一对边沿才置 1 */
} capture_result_t;

volatile capture_result_t g_cap = {0};

static volatile uint32_t s_ovf_cnt    = 0;   /* 溢出次数累加器 */
static volatile uint32_t s_last_rise  = 0;   /* 上一次上升沿的 CNT */
static volatile uint32_t s_rise_ovf   = 0;   /* 上升沿那一刻的溢出计数 */
static volatile uint32_t s_last_fall  = 0;   /* 上一次下降沿的 CNT */
static volatile uint32_t s_fall_ovf   = 0;
static volatile uint8_t  s_rise_ready = 0;   /* 收到过上升沿？ */
static volatile uint8_t  s_fall_ready = 0;   /* 收到过下降沿？ */

/* 【这一句是全部精力的关键】把「CNT 的圈数」和「圈内的位置」
   合成一个单调递增的 32 位时间戳。
   s_ovf_cnt 每 65.536ms 加 1，2³² × 65.536ms ≈ 8.1 年才会回绕，
   在这类测量里可以认为永不溢出。 */
static inline uint32_t make_stamp(uint32_t ovf, uint32_t cnt)
{
    return (ovf << 16) | cnt;      /* 因为一圈正好是 2¹⁶ 个数 */
}

int main(void)
{
    HAL_Init();
    SystemClock_Config();
    MX_GPIO_Init();

       注意 HAL_TIM_IC_Start_IT 只开捕获中断，
       它【不会】帮你开更新中断 —— 溢出计数必须自己另开。 */

    HAL_TIM_IC_Start_IT(&htim4, TIM_CHANNEL_2);   /* CH2 捕获中断 */

                      g_cap.duty_permille / 10,

        }
    }

/* ────────────────────────────────────────────────────────────────
   ① 溢出中断：只做一件事 —— 把圈数加一
   ──────────────────────────────────────────────────────────────── */
void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim)
{
    if (htim->Instance == TIM4) {
        s_ovf_cnt++;
    }
}

/* ────────────────────────────────────────────────────────────────
   ② 捕获中断：两个通道共用这一个回调，靠 htim->Channel 区分
   ──────────────────────────────────────────────────────────────── */
void HAL_TIM_IC_CaptureCallback(TIM_HandleTypeDef *htim)
{
    if (htim->Instance != TIM4) {
        return;
    }

    /* ★★★ 溢出竞态补偿 ★★★
       有一种情况必须处理：边沿到来的那一瞬间，CNT 已经回绕，
       但溢出中断还没被 CPU 响应（NVIC 还没来得及进 ISR）。
       此时 s_ovf_cnt 还停留在旧值，直接算差值会得到一个
       「少了整整一圈」的结果 —— 表现为偶尔蹦出一个
       巨大或极小的错值。

       判断方法：如果 UIF 已经置位，说明【刚刚发生过溢出】。
       我们就地补上这一圈，并清掉标志
       （清掉之后 HAL_TIM_IRQHandler 就不会再调一次
         PeriodElapsedCallback，正好避免重复计数）。 */
    if (__HAL_TIM_GET_FLAG(htim, TIM_FLAG_UPDATE) != RESET) {
        s_ovf_cnt++;
        __HAL_TIM_CLEAR_FLAG(htim, TIM_FLAG_UPDATE);
    }

    uint32_t ovf = s_ovf_cnt;                        /* 先锁存，保证两个通道一致 */
    uint32_t cnt = HAL_TIM_ReadCapturedValue(htim, htim->Channel);

    if (htim->Channel == HAL_TIM_ACTIVE_CHANNEL_1) {
        /* ── 上升沿：一个周期的起点 ── */
        if (s_rise_ready) {
            uint32_t now  = make_stamp(ovf, cnt);
            uint32_t prev = make_stamp(s_rise_ovf, s_last_rise);
            uint32_t period = now - prev;           /* 自动回绕，不受 32 位溢出影响 */

            g_cap.period_us = period;
            if (period > 0U) {
                g_cap.freq_hz = 1000000UL / period; /* 1MHz 计数时钟 → 1 个数 1µs */
            }

            /* 如果这一刻也已经收到了下降沿，就可以算占空比了 */
            if (s_fall_ready) {
                uint32_t fstamp  = make_stamp(s_fall_ovf, s_last_fall);
                uint32_t high    = fstamp - prev;
                g_cap.high_us    = high;
                g_cap.duty_permille = (uint32_t)((uint64_t)high * 1000ULL / period);
                g_cap.valid = 1;
            }
        }
        s_last_rise  = cnt;
        s_rise_ovf   = ovf;
        s_rise_ready = 1;
        s_fall_ready = 0;                   /* 新周期开始，等这一轮的下一个下降沿 */

    } else if (htim->Channel == HAL_TIM_ACTIVE_CHANNEL_2) {
        /* ── 下降沿：高电平的终点 ── */
        s_last_fall  = cnt;
        s_fall_ovf   = ovf;
        s_fall_ready = 1;
    }
}
这段代码里的三个关键设计，值得逐条看懂
  • 把「圈数」和「圈内位置」拼成一个时间戳。(ovf << 16) | cnt 之所以成立，是因为 ARR 取满 65535，一圈正好 2¹⁶ 个数。这样两个时间戳相减就是真正的「过了多少个计数」，中间溢出了多少次都自动包含在内。这是定时器做长时间测量的通用套路（RTOS 的 tick、里程计、编码器计数都用它）。
  • 差值用的是无符号减法。now - prev 在 uint32_t 上是「模 2³² 减法」，就算时间戳回绕，结果也是对的——前提是两个时间戳相差不超过 2³¹ 个计数（约 8.1 年 / 2）。所以永远不要写 if (now > prev) diff = now - prev;，那个判断反而会把回绕的那一刻算错。
  • 占空比用 (uint64_t)high * 1000 / period。先乘后除是为了保住精度。如果写成 high / period * 1000，整数除法会先把小数部分丢掉，结果永远是 0 或 1000；而且 high × 1000 在 period 很大时有溢出 32 位的风险，所以强转成 64 位。「先乘后除、必要时升位宽」是所有定点运算的基本功。

选 1MHz 还是 72MHz 做计数时钟？这是这道题里唯一需要权衡的参数，算一下就清楚了（被测信号设为 20kHz 方波）：

计数时钟（PSC）20kHz 时的计数值量化误差一圈时长（ARR=65535）低频时会不会溢出
1MHz（PSC=71）50 个数±1/50 = ±2%65.5ms 低于约 15Hz 才可能溢出，很安全
8MHz（PSC=8）400 个数±0.25%8.2ms 低于约 122Hz 就可能溢出一次
72MHz（PSC=0）3600 个数±0.028%0.91ms 低于 1.1kHz 就会溢出（靠补偿解决）

结论很直白：被测信号频率越高，就越要把 PSC 调小；而调小 PSC 带来的溢出问题，正好由上面那段「圈数 + 圈内位置」的补偿逻辑解决。有了溢出补偿，你就没必要为了低频而牺牲分辨率了——例 4 里说的「方案 B」就是它。这也是为什么工程代码里几乎都会保留一个溢出计数器，哪怕当前测试条件下根本用不上。

如果只要测「PWM 的周期和占空比」这一件事，STM32 还提供了一个更省事的硬件模式，连溢出补偿都不太需要：

【原理】把从模式配成「复位模式」，触发源选 TI1FP1，
       并且让 IC2 间接映射到 TI1FP1（而不是 TI2）：

       CH1（直接 TI1，上升沿）→ 既触发捕获，又复位 CNT
       CH2（间接 TI1，下降沿）→ 同一个引脚上的下降沿

       于是硬件自动得到：
           CCR1 = 整个周期的计数  （CNT 从 0 数到下一个上升沿）
           CCR2 = 高电平的计数    （CNT 从 0 数到下降沿）
       占空比 = CCR2 / CCR1 —— 不需要中断，随时读随时有。

【CubeMX 配置】

  TIM4 → Channel1 : Input Capture direct mode
         Channel2 : Input Capture indirect mode   ← ★ 注意是 indirect
  Combined Channels : PWM Input on CH1            ← ★ 选了这个会自动配好上面
  Trigger Source    : TI1FP1（自动）
  Slave Mode        : Reset mode（自动）
  CH1 Polarity      : Rising Edge
  CH2 Polarity      : Falling Edge
  IC Prescaler      : No division

【读结果的代码，只有三行】

    /* 不需要捕获中断，也不需要溢出计数 —— 因为每个周期
       CNT 都被硬件复位，永远不会累积到溢出。 */
    uint32_t period = HAL_TIM_ReadCapturedValue(&htim4, TIM_CHANNEL_1);
    uint32_t high   = HAL_TIM_ReadCapturedValue(&htim4, TIM_CHANNEL_2);
    uint32_t duty   = (uint32_t)((uint64_t)high * 1000ULL / period);

  ★ 唯一的坑：【先读 CCR1 再读 CCR2】。因为 CCR1 那一读会
    顺带把「周期在更新」的锁存逻辑走一遍，反过来读
    （先 CCR2 后 CCR1）在更新事件刚好发生的瞬间可能读到
    上一周期的半个值，占空比会瞬间蹦到离谱的数。
    HAL 库在 HAL_TIM_ReadCapturedValue 里没有替你做这个保护。

【什么时候用 PWM 输入模式，什么时候用两次捕获法？】

  用 PWM 输入模式：     信号频率稳定、你只要周期和占空比、
                        不想写中断、要低 CPU 占用。
  用两次捕获法：        信号频率变化很大（换量程）、要测
                        频率的同时还要测多个通道、
                        或者需要记录「每一个周期分别是多少」
                        （PWM 输入模式每周期更新一次，
                         你只能读到最新值）。

用定时器做软件定时器：一个 1ms 中断带起一堆任务

这是定时器最实用、也最能体现「时间是一种资源」的用法。需求很常见：一个 LED 要每 500ms 闪一下、一个传感器要每 100ms 读一次、一个状态机要每 10ms 跑一步、一个超时判断要每 1 秒检查一次——但你手上一共只有 4 个定时器，还想留两个做 PWM 和捕获。答案是：只需要一个 1ms 的更新中断，剩下的全部用软件在它的基础上「切片」。

┌──────────────────────────────────────────────────────────────┐
│  硬件层：TIM2 每 1ms 产生一次更新中断                        │
│          ISR 里只做一件事：g_ms_tick++                       │
│          （它是一把「时间的尺子」，不干任何业务）             │
└──────────────────────────┬───────────────────────────────────┘
                           │  每 1ms 加 1
                           ▼
┌──────────────────────────────────────────────────────────────┐
│  调度层：软件定时器表（一张 const 数组 + 一次遍历）          │
│          每项 = {周期, 上次运行时刻, 函数指针, 使能标志}     │
│          「到点了吗？到了就跑一下，然后把时刻推后一个周期」   │
└──────────────────────────┬───────────────────────────────────┘
                           │  调用
                           ▼
┌──────────────────────────────────────────────────────────────┐
│  任务层：led_task() / sensor_task() / sm_task() / timeout()  │
│          每个任务都必须是【短小、不阻塞】的                   │
│          它们的节拍全部来自同一个 1ms 中断                    │
└──────────────────────────────────────────────────────────────┘

  时间轴（每格 1ms，横轴是时间）：

  TIM2 ─┤1ms├─┤1ms├─┤1ms├─┤1ms├─┤1ms├─┤1ms├─┤1ms├─┤1ms├─┤1ms├─
        tick 累加： 1    2    3    4    5    6    7    8    9

  1ms  任务： ●    ●    ●    ●    ●    ●    ●    ●    ●   （每格都跑）
  10ms 任务：●                   ●                   ●        （每 10 格）
  100ms任务：●                                       ●        （每 100 格）
  500ms任务：●                                                （每 500 格）
             └── 全部由同一个 CNT 的溢出事件驱动 ──┘

   ──────────────────────────────────────────────────────────────── */
soft_timer_t g_timers[] = {
    /* name            period_ms  last_ms  fn                   enable */
    { "led",              500,       0,   task_led,            1 },
    { "sensor",           100,       0,   task_sensor,         1 },
    { "sm",                10,       0,   task_state_machine,  1 },
    { "timeout",         1000,       0,   task_timeout_check,  1 },
    { "hello",           2000,       0,   task_hello,          0 },  /* 先关着 */
};
const uint32_t g_timer_count = sizeof(g_timers) / sizeof(g_timers[0]);

/* ────────────────────────────────────────────────────────────────
   ★ 调度器：在主循环里被反复调用，绝不放在中断里
   ──────────────────────────────────────────────────────────────── */
void soft_timer_poll(void)
{
    uint32_t now = g_ms_tick;            /* 先锁存：遍历过程中 tick 还会变 */

    for (uint32_t i = 0; i < g_timer_count; i++) {
        soft_timer_t *t = &g_timers[i];

        if (!t->enable) {
            /* 暂停的任务：把时刻跟着 tick 走，
               这样重新使能时会从「现在」开始重新计时，不会补跑。 */
            t->last_ms = now;
            continue;
        }

        /* ★ 无符号减法：就算 g_ms_tick 回绕（49.7 天）也依然正确 */
        if ((now - t->last_ms) >= t->period_ms) {

            /* 【关键】先把时刻推进一个周期，再执行任务。
               这样即使任务执行中 tick 又走了几毫秒，
               下次的节拍也不会被推后 —— 这叫「不累积漂移」。 */
            t->last_ms += t->period_ms;

            /* 【补拍保护】如果任务被卡住太久（比如某个任务阻塞了 30ms），
               last_ms 会远远落后于 now，上面的 += 追不上，
               于是下一轮 poll 会连续触发好几次 —— 这叫「补拍风暴」。
               把落后超过一个周期的直接丢帧，只保留最新节拍。 */
            if ((now - t->last_ms) >= t->period_ms) {
                t->last_ms = now;        /* 丢帧：宁可漏一次，不要连跑五次 */
            }

            t->fn();                     /* 执行任务本体 */
        }
    }
}

void soft_timer_enable(const char *name, uint8_t en)
{
    for (uint32_t i = 0; i < g_timer_count; i++) {
        if (strcmp(g_timers[i].name, name) == 0) {
            g_timers[i].enable = en ? 1 : 0;
            return;
        }
    }
}

   ★★ 全系统唯一的周期中断：只累加 tick，别的什么都不干。
   为什么不在这个中断里直接调用任务函数？
     · 任务函数一多、一慢，中断时间就被拉长，
       高优先级中断（比如串口、ADC）的响应会变差。
     · 中断里不能调用 HAL_Delay、不能做阻塞操作。
     · 中断里做业务，代码极难调试（不能在断点停、变量要 volatile）。
   所以：中断只负责「记录时间」，业务永远在主循环里跑。
   ──────────────────────────────────────────────────────────────── */
void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim)
{
    if (htim->Instance == TIM2) {
        g_ms_tick++;
    }
}
时间片轮询的三个硬约束（违背了就会出玄学 bug）
  • 所有任务必须「短小且非阻塞」。任何一个任务里写了 HAL_Delay(50)，整个系统的节拍就垮了——别人都在等它。要等待就在任务里置个状态、下次进来再看，用状态机代替延时。
  • 任务的最坏执行时间之和，必须小于最短周期。1ms 那个任务如果跑了 1.5ms，它就永远追不上节拍。工程上一般要求总占用率低于 50%，留一半余量给突发情况。
  • 调度器必须在主循环里调用，不能放在中断里。如果把 soft_timer_poll() 塞进 HAL_TIM_PeriodElapsedCallback，它就退化成了「在中断里跑所有业务」——上面列的三条坏处全中。中断与主循环的分工，就是这一节最想让你记住的东西。
这套框架 vs SysTick vs RTOS：什么时候该升级

同样一个 1ms 节拍，三种用法，各占一个复杂度台阶：

  • 只用 HAL_GetTick() 比较时间戳：任务只有两三个、彼此独立时，最省事。缺点是每个任务都要自己写 if (now - last >= N)，代码重复。
  • 本文这套软件定时器表：任务五个以上、需要统一开关和统一节拍管理时用。代码量很小（一百行以内），可读性好，可调试性好（断点随便打）。中小项目的最佳选择。
  • 上 RTOS（FreeRTOS 等）：任务之间有复杂的同步/通信需求、需要优先级抢占、需要阻塞式 API（信号量、队列、任务通知）时再上。上了 RTOS 之后，本文这套框架和 RTOS 的 vTaskDelay 是两套并存的时间体系，不要混用——否则很容易出现「HAL_Delay 在 RTOS 下不准」这类经典困惑（见下一小节）。

定时器不够用怎么办

F103C8T6 上只有 4 个定时器，而一个稍微像样的项目往往同时需要：系统节拍、两路 PWM 调光、一路输入捕获测转速、一路编码器接口、还要一个做超时——五个需求，四个定时器，怎么办？答案是：大部分需求其实不需要独占一个定时器。下面按「先省钱、后花钱」的顺序给你五条路。

第一招（首选）：一个定时器的多个通道输出多路 PWM。这是最常见也最容易被忽略的用法。TIM1~TIM4 每个都有 4 个独立通道，共用同一个 CNT、同一个 PSC、同一个 ARR，但每个通道有自己独立的 CCR。

│  ARR  ← 周期（决定 PWM 频率）★ 所以【四路的频率必须完全相同】                 │
│  CNT  ← 唯一的那个计数器，四路同时和它比较                                    │
│  计数模式、CKD、时钟源                                                        │

    /* 频率？四路都是 1kHz，改不了单独一路 —— 这就是共用的代价。 */

【要变频？四路必须一起变，而且 CCR 要跟着重算】
    改 ARR 之后，原来写死的 CCR 含义就变了。
    正确做法：把「占空比」存成百分比，变频时重算 CCR：

        uint32_t new_arr = 719;                 /* 想改成 100kHz */
        __HAL_TIM_SET_AUTORELOAD(&htim3, new_arr);
        __HAL_TIM_SET_COMPARE(&htim3, TIM_CHANNEL_1, (new_arr + 1) * 10 / 100);
        __HAL_TIM_SET_COMPARE(&htim3, TIM_CHANNEL_2, (new_arr + 1) * 30 / 100);
        /* …把四路都按新 ARR 重新算一遍 */
    如果只是改占空比、不改频率，就【不需要】动 ARR，
    直接写 CCR 就够了（下一小节的排查顺序里会用到这一点）。

第二招：一个定时器的一个中断，带一堆软件定时器。上一小节的框架就是干这个的——无论你有多少个「每 N 毫秒做一次」的需求，都只花一个定时器。这条几乎能消掉一半的定时器需求，因为工程里大多数「定时」根本不是硬件时序，只是「过一会儿提醒我一下」。

第三招：用 SysTick 当业务节拍。SysTick 是内核自带的，不占 F103 那 4 个定时器里的任何一个。HAL 已经把它配成 1ms 了，直接 HAL_GetTick() 就能拿来比较时间戳。代价是：它属于 HAL 的时基，你不能改它的频率（改了 HAL_Delay 就全乱），也不能在它上面挂自己的回调（除非你重写 HAL_IncTick 或 SysTick_Handler，那样容易和 HAL 打架）。结论：用它读时间可以，用它做精确硬件时序不行。

第四招：软件 PWM。当你要的是「八路 LED 各自调光」这种慢速、不需要精确波形的需求时，完全可以省掉硬件 PWM，用一个定时器中断自己刷引脚：

/* ────────────────────────────────────────────────────────────────
   原理：把 100µs 分成 100 份，每一份里逐个通道比较「计数 < 占空比」，
   是就拉高、不是就拉低。
       100 份 × 100µs = 10ms 一整轮 → PWM 频率 100Hz，分辨率 1%
   ──────────────────────────────────────────────────────────────── */
#define SWPWM_CH     8
#define SWPWM_LEVELS 100        /* 分辨率：1% */

static volatile uint8_t s_duty[SWPWM_CH] = {0};   /* 0~100 */
static uint8_t          s_phase = 0;

/* 引脚表：把 8 个 GPIO 端口和引脚号放在一张表里，方便循环 */
static GPIO_TypeDef *const s_port[SWPWM_CH] = {
    GPIOA, GPIOA, GPIOA, GPIOA, GPIOB, GPIOB, GPIOB, GPIOB
};
static const uint16_t s_pin[SWPWM_CH] = {
    GPIO_PIN_1, GPIO_PIN_2, GPIO_PIN_3, GPIO_PIN_4,
    GPIO_PIN_5, GPIO_PIN_6, GPIO_PIN_7, GPIO_PIN_8
};

/* ★ 这个函数由定时器中断每 100µs 调用一次 */
void swpwm_tick(void)
{
    s_phase++;
    if (s_phase >= SWPWM_LEVELS) {
        s_phase = 0;
    }
    for (uint8_t i = 0; i < SWPWM_CH; i++) {
        /* 低电平有效还是高电平有效，按你的驱动电路定 */
        if (s_phase < s_duty[i]) {
            HAL_GPIO_WritePin(s_port[i], s_pin[i], GPIO_PIN_SET);
        } else {
            HAL_GPIO_WritePin(s_port[i], s_pin[i], GPIO_PIN_RESET);
        }
    }
}

/* 设置占空比（0~100）。注意 s_duty 是 8 位，读写是原子的，
   所以主循环里直接赋值就行，不需要关中断。 */
void swpwm_set(uint8_t ch, uint8_t duty)
{
    if (ch < SWPWM_CH && duty <= SWPWM_LEVELS) {
        s_duty[ch] = duty;
    }
}

/* ────────────────────────────────────────────────────────────────
   【代价分析 —— 什么时候能用、什么时候别用】

   ① CPU 开销：100µs 一次中断 = 每秒 10000 次。
      每次中断要循环 8 个通道（每个通道一次 HAL_GPIO_WritePin，
      约 10~20 个周期），算上进出中断的开销，
      每次大约 1~2µs → 占用率约 1%~2%。可以接受，
      但别忘了【它只在 100Hz 以下好用】。

   ② 抖动：软件 PWM 的边沿时刻取决于中断响应延迟。
      如果恰好有个串口中断在处理，边沿可能晚几微秒 ——
      对 LED 完全无所谓，对音频/电机就是致命伤。

   ③ 频率上限：想要 1kHz 的软件 PWM（1ms 一轮、100 级），
      中断间隔就要 10µs → 每秒 10 万次中断 → CPU 直接烧掉。
      【1kHz 以上必须用硬件 PWM。】

   ④ 低功耗杀手：100µs 一次中断意味着 CPU 永远没法进深度睡眠。
      电池项目里这是硬伤。

   ⑤ 引脚必须是【普通推挽输出】，不能配成 AF 模式 ——
      因为这次真的是「软件在控制引脚电平」。

   【结论】软件 PWM 只适合：LED 调光、继电器、蜂鸣器、
   加热丝这类「慢速、对波形不敏感」的负载，
   而且通道数多、硬件定时器实在不够的时候。
   电机、音频、开关电源 → 老老实实上硬件 PWM。

第五招（最后一招）：换型号。如果算下来确实需要 6 路不同频率的硬件 PWM 加两路编码器接口，那就别硬省了——把 F103C8T6 换成 F103RCT6（TIM1~TIM8 全有，还多 256KB Flash）或者 F407（两个 32 位定时器 + 更快的时钟）。选型阶段多花十块钱，比在软件里绕三个月便宜得多。这一条同样适用于引脚不够：F103C8T6 只有 37 个 IO，很多「功能实现不了」最后都是引脚问题。

SysTick 与 HAL 的时基：HAL_Delay 背后的那套东西

前面所有的例子里，HAL_Delay 和 HAL_GetTick 都像是「天上掉下来的」——现在该把它拆开了。SysTick 不属于 ST 的任何一个外设，它是 Cortex-M3 内核里自带的一个 24 位递减计数器，所有 Cortex-M 芯片都有，地址在系统控制空间里，跟 TIM1~TIM4 完全不是一回事。

┌─────────────────────── Cortex-M3 内核 ───────────────────────┐
│                                                              │
│   SysTick（24 位【递减】计数器，不是递增！）                  │
│                                                              │
│     CTRL  (0xE000E010)  控制：使能、中断使能、时钟源、计数标志│
│     LOAD  (0xE000E014)  重装载值（24 位，最大 0xFFFFFF）      │
│     VAL   (0xE000E018)  当前值（读它得到「还剩多少」）        │
│     CALIB (0xE000E01C)  校准值（一般不用）                    │
│                                                              │
│     工作方式：VAL 从 LOAD 开始每来一个时钟减 1，              │
│               减到 0 → 下一拍重装成 LOAD、置 COUNTFLAG、      │
│               如果 TICKINT=1 → 触发【SysTick 异常】（异常号 15）│
└──────────────────────────────┬───────────────────────────────┘
                               │
                               ▼
     HAL_Init()
        └─ HAL_InitTick(TICK_INT_PRIORITY = 15)
              └─ HAL_SYSTICK_Config(SystemCoreClock / (1000U / uwTickFreq))
                    uwTickFreq = HAL_TICK_FREQ_DEFAULT = 1（也就是 1ms）
                    → 72 000 000 / 1000 = 72000
                    → LOAD = 72000 − 1 = 71999
                    → 每 1ms 触发一次 SysTick 异常

     SysTick_Handler()            【在 stm32f1xx_it.c 里】
        └─ HAL_IncTick()
              └─ uwTick += uwTickFreq;      /* uwTick 每 1ms 加 1 */

     HAL_GetTick()  →  return uwTick;       /* 就是一个全局变量 */

     HAL_Delay(ms)
        └─ tickstart = HAL_GetTick();
           while ((HAL_GetTick() - tickstart) < ms) { }   ← 死等

     ★ 所以 HAL_Delay 的真相：它【不睡眠、不省电、不让出 CPU】，
       就是在主循环里空转，一直问到 uwTick 涨够了为止。
为什么 HAL_Delay 绝对不能在中断里调用（会死锁，不是「不准」）

这是新手最容易踩、而且症状最吓人的一个坑：程序不是变慢，是整个卡死。原因是一个再简单不过的循环依赖：

  • HAL_Delay 要等 uwTick 变大才返回；
  • uwTick 只在 SysTick 中断里变大；
  • 而你现在正待在另一个中断里。Cortex-M 的中断不会互相抢占，除非新来的中断优先级数值更小。SysTick 的优先级被 HAL 设成了 15（最低）；
  • 所以只要你这个中断的优先级数值 ≤ 15（实际上就是你配的任何值），SysTick 都无法抢占它——它得等你返回才轮得到；
  • 你等它，它等你 → 死锁，永远出不来。看门狗喂不上，几秒后复位——于是现象变成「设备每隔几秒重启一次」，更难查。

正确做法：中断里只记录时刻，不做等待。需要「过一会儿再做事」，就在中断里记个时间戳或置个标志，让主循环去判断：

/* ✗ 错误：直接等待 —— 死锁 */
void HAL_GPIO_EXTI_Callback(uint16_t pin)
{
    HAL_Delay(10);                  /* 永远卡在这里 */
    do_something();
}

/* ✓ 写法一：记录时刻，主循环里判断（最通用） */
static volatile uint32_t s_event_tick = 0;
static volatile uint8_t  s_event_flag = 0;

void HAL_GPIO_EXTI_Callback(uint16_t pin)
{
    s_event_tick = HAL_GetTick();   /* 读一个变量，安全，不阻塞 */
    s_event_flag = 1;
}

/* 主循环里： */
void event_poll(void)
{
    if (s_event_flag && (HAL_GetTick() - s_event_tick) >= 10U) {
        s_event_flag = 0;
        do_something();
    }
}

/* ✓ 写法二：中断里数中断次数（不需要 HAL 时基） */
static volatile uint8_t s_skip = 0;
void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim)
{
    if (htim->Instance == TIM2) {
        if (++s_skip >= 10) {       /* 10 个 1ms = 10ms */
            s_skip = 0;
            do_something();
        }
    }
}

/* ✓ 写法三：真要微秒级精确延时，用 DWT 周期计数器
   （Cortex-M3 的调试单元里有一个自由运行的 CYCCNT，
     不占任何定时器，也不依赖中断） */
static inline void dwt_delay_us(uint32_t us)
{
    uint32_t start = DWT->CYCCNT;
    uint32_t ticks = us * (SystemCoreClock / 1000000U);
    while ((DWT->CYCCNT - start) < ticks) { }
}
/* 用之前要开：CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;
                DWT->CYCCNT = 0;
                DWT->CTRL  |= DWT_CTRL_CYCCNTENA_Msk;
   注意：某些调试器连接状态下 DWT 才可用，
         而且它同样【不能在长时间里空转】——只是把等待从 ms 缩到 µs。 */

SysTick 还有一个必须知道的地方：它只有 24 位，而且 HAL 把它用掉了。24 位意味着 LOAD 最大 16777215，按 72MHz 算，一次最长只能数 16777215 / 72 000 000 = 233ms。这刚好够做 1ms 的时基，但想做更长的周期就必须靠 uwTick 累加。uwTick 是 32 位、单位 1ms，能表示 2³² ms ≈ 49.7 天——所以嵌入式设备连续运行超过 49.7 天后，所有用 HAL_GetTick 做绝对比较的代码都会突然出错，而用无符号差值比较（now - last >= N）的代码则安然无恙。这就是前面几段代码里反复强调「用差值、不要用绝对值比较」的原因。

【裸机：1ms 节拍由 SysTick 提供，HAL_Delay 消费它】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   SysTick ──每 1ms──▶ uwTick++        （系统时基：记录「现在几点」）
                          │
                          ├──▶ HAL_Delay / HAL_GetTick
                          └──▶ 你的时间戳比较、软件定时器表

   TIM2/TIM3 等 ───────▶ PWM、输入捕获、死区、编码器
                          （业务定时器：产生和测量【精确的硬件时序】）

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【RTOS：同样需要这个节拍，但它叫「tick」，而且用途变了】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   FreeRTOS 需要【周期性的 tick 中断】来驱动内核，没有 tick 它就不转：

     · 任务的时间片轮转（同优先级任务每 tick 换一次）
     · vTaskDelay / vTaskDelayUntil 的计时（延时是「让出 CPU」，
       不是空转 —— 这是它和 HAL_Delay 的本质区别）
     · 超时判断（信号量、队列、事件组带超时的等待）
     · 软件定时器（FreeRTOS 的 xTimerCreate）的时基
     · 统计任务的运行时间

   典型配置（FreeRTOSConfig.h）：
       #define configTICK_RATE_HZ  ((TickType_t)1000)   /* 1kHz = 1ms 一个 tick */
       #define configUSE_PREEMPTION 1
       #define configUSE_TIME_SLICING 1

   【关键问题：tick 从哪来？】
     默认是 SysTick（port.c 里的 xPortSysTickHandler）。
     但 SysTick 只有一个，而 HAL 也在用它做时基 → 【冲突】。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【冲突的三种表现（CubeMX 上 FreeRTOS 之后常见）】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   ① HAL_Delay 卡死或者时间完全不对
      → HAL 的时基被 RTOS 接管了，uwTick 不再按 1ms 增长。

   ② HAL_InitTick 报错 / 编译警告
      → HAL 想初始化 SysTick，RTOS 也想，两边打架。

   ③ 在中断里调 HAL_Delay —— 依然是死锁，而且更隐蔽
      → 和裸机同理，SysTick 优先级最低，等不到 tick。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【正确做法】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   ① CubeMX 里把 HAL 的时基【挪走】：
        Project Manager → Advanced Settings → Timebase Source
        选 TIM6 或 TIM7（基本定时器，没有引脚、没有 PWM 能力，
        专门干这个最合适。板上只有 TIM1~TIM4 的话选一个你不用的，
        比如用 TIM4，反正它只产生 1ms 中断）。
       这样：SysTick 归 FreeRTOS（tick），TIM6 归 HAL（uwTick），
             各用各的，互不干扰。

   ② 业务代码里【统一用 RTOS 的 API】，不要混着用：
        HAL_Delay(10)      →  vTaskDelay(pdMS_TO_TICKS(10))
        HAL_GetTick()      →  xTaskGetTickCount()
       （osDelay / osKernelGetTickCount 是 CMSIS-RTOS 的等价写法。）
       混用两套时间体系，等于在自己脚下埋雷。

   ③ 硬件时序【永远留给定时器外设】，不要交给 RTOS：
       1kHz 以上的 PWM、死区、输入捕获 —— 这些是硬件的活儿。
       RTOS 的 tick 是 1ms 级的，用它做时序精度差了三个数量级。
       任务里要调 PWM，就是改一个 CCR 的值，然后继续让硬件去跑。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   项目              系统时基（SysTick / HAL / RTOS tick）  业务定时器（TIMx）
   ────────────────  ─────────────────────────────────────  ──────────────────
   精度              1ms 级（软件节拍）                      纳秒~微秒级（硬件）
   谁在数            CPU 每 tick 干一件事                    纯硬件，不占 CPU
   中断负担          每 1ms 一次（很轻）                     只在需要时开中断
   用途              记录时刻、任务调度、超时判断            PWM、捕获、死区、编码器

   低功耗友好度      差（永远在唤醒）                        好（用完就关）

「定时器不中断 / PWM 没输出」的排查顺序

这两个现象占了初学者定时器问题的绝大多数。不要一上来就怀疑硬件、也不要瞎改代码——按下面的顺序走，每一步都能把范围砍掉一半。这个顺序不是我编的，它就是信号从时钟到引脚的传播路径：时钟 → 计数 → 事件 → 中断 → 输出 → 引脚。

╔══════════════════════════════════════════════════════════════╗
║  第 1 步：RCC 时钟使能了吗？（外设的「电源开关」）           ║
╚══════════════════════════════════════════════════════════════╝

  查什么：__HAL_RCC_TIM2_CLK_ENABLE() 有没有被调用
          （CubeMX 生成的 MX_TIMx_Init 里，它会出现在 MspInit 中）
  怎么看：调试器里看 RCC->APB1ENR 的 TIM2EN 位（bit 0）是不是 1
          TIM3/TIM4 = bit 1 / bit 2；TIM1 在 APB2ENR 的 bit 11
  症状特点：★★★ 最阴的一种 —— 【不报错、不 HardFault、寄存器写不进去】。
          因为时钟没开时，写定时器寄存器的操作被总线静默丢弃，
          读回来永远是 0。你以为配好了，其实一个字节都没写进去。
  顺便查：AFIO 时钟（__HAL_RCC_AFIO_CLK_ENABLE）——
          只有用重映射时才需要，但漏了会导致引脚复用无效。

╔══════════════════════════════════════════════════════════════╗
║  第 2 步：PSC / ARR 算对了吗？（数得对不对、快不快）         ║
╚══════════════════════════════════════════════════════════════╝

  查什么：① f_clk 到底是多少（别忘了 APB 预分频 ≠ 1 时定时器时钟要 ×2）
          ② PSC / ARR 的数值是不是按例 1 的步骤算出来的
          ③ 计数模式对不对（中央对齐会让频率减半！）
  怎么看：调试器里【连续读两次 TIMx->CNT】：
            · 两次值在变      → 时钟到了，计数正常 ✅ 往下走
            · 两次值都不变    → 计数器没启动，或时钟源没配上 → 回第 1 步
            · 值变得极快/极慢 → PSC 算错了，或者 f_clk 不是你以为的那个
          再读 TIMx->SR 的 UIF 位：为 1 说明【确实溢出过】——
          只要你停下来看，它几乎总该是 1（因为 1ms 就溢出一次）。
          UIF 是 0 而且 CNT 在动 → ARR 设得太大，你等的时间不够长。
  常见错：把 1ms 写成 1s（少乘了 1000）、把 72MHz 当成 36MHz、
          中央对齐时忘了分母 ×2。

╔══════════════════════════════════════════════════════════════╗
║  第 3 步：中断使能位与 NVIC 使能了吗？（要不要叫 CPU）       ║
╚══════════════════════════════════════════════════════════════╝

  这一层有两个「开关」，【两个都得开】，而且它们在两个不同的寄存器里：

     ① 外设级：TIMx->DIER 的 UIE 位（bit 0）
        —— 定时器自己的「允许我发中断请求」
        —— 代码里是 __HAL_TIM_ENABLE_IT(&htim, TIM_IT_UPDATE)
     ② 内核级：NVIC->ISER[0] 里 TIM2_IRQn（28 号）对应的位
        —— 内核的「我允许这个中断进来」
        —— 代码里是 HAL_NVIC_EnableIRQ(TIM2_IRQn)
        —— CubeMX 里就是那个 NVIC Settings 的勾选框

  症状区分（很有用）：
     UIE=1、NVIC=0  → 定时器 SR 的 UIF 一直是 1（没人清），
                      但回调函数永远不进 —— 现象就是「不中断」
     UIE=0、NVIC=1  → 同上，进不去
     两个都是 1     → 那问题不在这一层

  还要查三件事：
     · 优先级分组与优先级数值（HAL_Init 里设的分组）
     · 【全局中断有没有被关】：程序里有没有残留 __disable_irq()；
       HAL 的临界区用的是 PRIMASK，进了临界区就别想响应中断
     · 有没有硬件故障把中断卡住了：调试器停在哪？是不是在
       HardFault_Handler / Error_Handler 里死循环？

╔══════════════════════════════════════════════════════════════╗
║  第 4 步：启动函数调了吗？（而且调的是「带 _IT」那个吗）     ║
╚══════════════════════════════════════════════════════════════╝

常见误解与坑

下面这十条，是定时器这一块最典型、也最费时间的认知偏差。每一条都按「错误认知 → 为什么错 → 正确做法」写，建议对照自己的代码过一遍——尤其第 4、5、7 条，很多人是在被坑过好几次之后才真正记住的。

坑 1：把定时器当成「一个延时函数」

错误认知：「定时器就是用来延时的，我要延时的时候调它一下。」

为什么错：延时只是它在「数自己的时钟」这件事上顺带产生的一个副产品。定时器真正的身份是一个能被 CPU 读写的计数器 + 一整套比较/捕获/触发电路。把它当延时函数用，等于买了一台机床只用它压纸——你会觉得定时器「不够用」，其实是没意识到它同时能做时基、PWM、捕获、编码器、触发 ADC、产生 DMA 请求。

正确做法：配置定时器时先问三个问题：它在数谁（时钟源）？数到多少（ARR）？数到之后要干什么（更新事件→中断/DMA/触发/输出）？「延时」只是第三个问题的一种答案。同样一个 TIM2，可以既做 1ms 系统节拍、又用它的 TRGO 去触发 ADC 采样，还能把 CH1 配成输出比较去翻转一个引脚——一份硬件，多份产出。

坑 2：以为定时器的时钟就是 PCLK1（36MHz）

错误认知：「APB1 的时钟是 36MHz，所以 TIM2 的时钟是 36MHz，PSC 要按 36MHz 算。」

为什么错：STM32 有一条专门的规则：当 APB 预分频系数不为 1 时，挂在这条总线上的定时器时钟会被自动 ×2。所以 APB1 = 36MHz 时，TIM2~TIM4 拿到的是 72MHz。按 36MHz 去算 PSC，得到的时间会正好差一倍——而且「差一倍」这种错误特别隐蔽，因为它看起来很合理，你不会怀疑。

正确做法：永远不要在脑子里推算这个频率。CubeMX 的时钟树上把鼠标悬停在那颗定时器上，它会直接显示实际时钟（比如 "TIM2 clock: 72 MHz"）；或者代码里用 HAL_RCC_GetPCLK1Freq() 读出来，按「预分频是否为 1」判断要不要 ×2。更重要的是：算完参数后用示波器或逻辑分析仪量一下实际周期，花三十秒就能把这个隐藏错误钉死。

坑 3：改 ARR 之后以为立刻就生效了

错误认知：「我在主循环里写了 __HAL_TIM_SET_AUTORELOAD(&htim, 999)，下一个周期就是 1ms 了。」

为什么错：当 ARPE（自动重载预装载使能）= 1 时（CubeMX 里那个 "auto-reload preload: Enable" 就是它），你写的值先进预装载寄存器，要等到下一个更新事件 UEV 才被搬进真正起作用的影子寄存器。你的本意是「防止改到一半的周期被用上」，而延迟生效正是它的目的，不是 bug。所以现象是：改了 ARR 以后，这一个周期还是旧的，从下一个周期起才变。

正确做法：想要「写完立即生效」，就把 ARPE 关掉（htim.Init.AutoReloadPreload = TIM_AUTORELOAD_PRELOAD_DISABLE）——但那样在动态变频时，可能产生一个畸形的短周期或长周期。更好的做法是接受延迟、并利用它：要平滑变频就配合更新中断，在中断里（也就是 UEV 刚发生时）写下一个值；要做「频率渐变」就在每个更新中断里按表推进一格。另外注意：中央对齐模式下分频比的分母是 2×ARR，改 ARR 时别忘了这一点。

坑 4：在中断里给定时器「重装初值」（51 的后遗症）

错误认知：「51 里中断服务函数第一件事就是 TH0 = 0x3C; TL0 = 0xB0;，STM32 肯定也要重装，不装就不准了。」

为什么错：STM32 的 ARR 是硬件自动重装的：CNT 撞到 ARR 的同一拍里，硬件已经把 CNT 清零、把 ARR 的预装载值搬进影子寄存器、置 UIF、再问你要不要中断。你什么都不用做，周期就已经是精确的。反过来，如果你在中断里手动写 ARR 或 CNT，反而会破坏这个精确性：中断响应有延迟（几微秒到几十微秒），你写进去的时刻已经晚于溢出时刻，周期的抖动就被你亲手引进来了。

正确做法：中断里只做业务，不碰 ARR、不碰 CNT、不碰 PSC。唯一可以在中断里改的是 CCR（改占空比、改输出比较值），因为它也有预装载保护。要理解这个差别，记住一句话：51 的初值计算里包含了「软件重装的延迟」，STM32 的 PSC/ARR 计算里没有任何软件参与——这是两种计时哲学。（想知道「自动重装」到底省掉了多少误差，回看例 5 的误差对比。）

坑 5：把占空比算成 CCR / ARR

错误认知：「ARR = 999，CCR = 300，那占空比就是 300/999 = 30.03%，差不多是 30% 嘛。」

为什么错：一个完整的周期有 (ARR+1) 个计数，因为 CNT 的取值是 0、1、2 … ARR，一共 ARR+1 个值。所以分母是 ARR+1 = 1000，不是 999。CCR = 300 时占空比精确是 30.00%，而不是 30.03%。这个「差不多」在 ARR 很大的时候看起来无所谓，但当 ARR 很小（比如 9）时，误差会放大到 10%——而且它还会污染你的反算：用 CCR/ARR 反推「想要 30% 时 CCR 该填多少」，会算出 299.7，四舍五入到 300，看起来又对了，于是这个错误被永久地藏起来了。

正确做法：一律背这个式子：边沿对齐向上计数 → 占空比 = CCR / (ARR+1)。还想再确认一遍，就把两个边界代进去：CCR = 0 应该是 0%，CCR = ARR+1 应该是 100%（此时 CNT 永远小于 CCR，即永远处于有效电平）。中央对齐是例外：向上向下各走一趟，一圈是 2×ARR 个计数，占空比 = CCR / ARR（严格说是 (2·ARR − 2·CCR)/(2·ARR) 那份推导，工程上用 CCR/ARR 这个近似就够了，因为它是硬件在上下两段分别比较的结果）。

坑 6：以为 HAL_Delay 是「精确延时」、可以在任何地方用

错误认知：「HAL_Delay(1) 就是精确的 1 毫秒，在中断里用一下也没事。」

为什么错：两层错。① 它不精确：它只是「等到 uwTick 长了至少 1 才算完」，而 uwTick 是 1ms 一跳的，加上中断延迟，HAL_Delay(1) 实际可能是 1.0~2.0ms；② 在中断里用它必然死锁：uwTick 只在 SysTick 中断里增加，而 SysTick 的优先级被 HAL 设成最低的 15，任何中断都能把它挡住——你在中断里等它，它等你退出中断，互相等到天荒地老（详见第 4 节的死锁分析）。

正确做法：主循环里可以用（可读性好、够用），但要清楚它是忙等——浪费 CPU、不让 CPU 睡觉，电池项目里要慎用。中断里绝对不能用，改成「记录时间戳 + 主循环判断」或者「数中断次数」。需要微秒级精度就用 DWT 的 CYCCNT（第 4 节有现成函数）或者干脆交给定时器硬件去产生时序。需要「不浪费 CPU 的等待」就上 RTOS 的 vTaskDelay（它会让出 CPU）。

坑 7：以为一个定时器的四路 PWM 可以输出四种频率

错误认知：「TIM3 有 4 个通道，那我 CH1 输出 1kHz 的调光、CH2 输出 4kHz 的蜂鸣器、CH3 输出 20kHz 的电机驱动，正好一个定时器全包了。」

为什么错：四个通道共用同一个 CNT、同一个 PSC、同一个 ARR。频率由 CNT 数到 ARR 的时间决定，所以四路的频率必然完全相同，能各自独立的只有 CCR（占空比）、极性、输出使能。上面那个需求在一个 TIM3 上物理上做不到——这不是库的限制，是硬件的结构。

正确做法：① 需求合并：调光和蜂鸣器如果都能接受 1kHz，就用同一个定时器的不同通道；② 拆到不同定时器：频率真的不同就用 TIM3 + TIM4（F103C8T6 上就这四颗，要提前规划引脚）；③ 要变频就四路一起变：把占空比存成百分比，改 ARR 时把所有 CCR 按新 ARR 重算一遍（第 4 节有代码）；④ 慢速负载考虑软件 PWM（LED、继电器这类），用普通 IO 刷出来，省下整个定时器。

坑 8：互补输出不做死区，直接接半桥

错误认知：「互补输出就是一个高一个低，正好驱动上下管，接上就能用。」

为什么错：理想波形是「互补」，现实中的 MOS 管关断需要时间（几百纳秒到几微秒，取决于驱动电阻和栅极电荷）。只要上下管的导通时刻出现哪怕一丁点重叠，电源正极就通过两个管子直接连到地——这就是短路（直通、shoot-through）。短路电流可以到几十上百安培，轻则烧保险、重则炸管炸驱动芯片，而且它发生在微秒级，你根本来不及反应。这一条不是「可能出问题」，而是「一定会出问题」——只是早晚和严重程度的问题。

正确做法：必须用硬件死区：高级定时器 TIM1/TIM8 的 BDTR 寄存器有 DTG（死区时间发生器），CubeMX 里在 Break and Dead Time 那一栏填 Dead Time（通常给 500ns~2µs，要按你的 MOS 关断时间和驱动能力来定），它会自动在 CHx 和 CHxN 的翻转之间插入延迟，整个过程由硬件保证，软件不用管。同时在硬件上也要留后手：把 BKIN 刹车输入接到驱动芯片的故障输出脚上，一旦过流/过温，硬件会在几个时钟内把所有输出拉到安全状态（并清 MOE），比软件响应快几个数量级。另外：死区时间是「先关后开」的净空时间，它会略微改变实际占空比——高精度场合要把它算进去补偿。

坑 9：以为「测周法一定比测频法准」（或反过来）

错误认知：「测周法用内部高速时钟去数，精度肯定比测频法高，所以测频率一律用输入捕获。」

为什么错：两种方法都是量化测量，误差都是一个计数：测频法是「闸门边界的 ±1 个信号脉冲」，测周法是「起止边界的 ±1 个时钟计数」。谁的相对误差小，取决于被测频率、内部时钟频率和闸门时间三者的关系。分界点在 f ≈ √(f_clk / Tg)：72MHz、1 秒闸门下，分界点约 8.5kHz。低于它测周法赢，高于它测频法赢——例 4 里 20kHz 那一行，测周法（±278ppm）就输给了测频法（±50ppm）。「一律用哪种」这个想法本身就是错的。

正确做法：先估被测频率落在哪个区间，再选方法：低频（< 分界点）用输入捕获测周法（顺便还能测占空比）；高频用 ETR 外部计数 + 精确闸门（软件定时器给一个准确的 1 秒闸门，读 CNT 就是频率）。还有两个通用改进：多周期测周法（连数 M 个周期再除，把 ±1 摊薄到 M×N 上）和溢出补偿（让高分辨率时钟也能测低频）。最后别忘了：当量化误差已经小于晶振本身误差（±20~30ppm）时，继续优化算法毫无意义，该换 TCXO 了。

坑 10：定时器不中断 / PWM 没输出，先怀疑芯片坏了

错误认知：「配置和例程一模一样，就是不动，肯定是芯片/板子坏了，换一块试试。」

为什么错：这两类现象里，九成以上是软件问题，而且集中在同样的五个地方：外设时钟没使能、PSC/ARR 算错、NVIC 没使能、启动函数用错（少了 _IT）、引脚没配复用。更关键的是：这些问题全都可以在不换任何硬件的前提下、用调试器在一分钟内定位。先换板子，等于放弃了唯一能学到东西的机会——而且换完板子问题大概率还在，因为它们本来就不是硬件问题。

正确做法：按第 4 节那个六步排查顺序走（它本身就是信号从时钟到引脚的传播路径）：RCC 时钟使能 → PSC/ARR 对不对（读两次 CNT 看变不变）→ DIER 的 UIE 与 NVIC → 启动函数（HAL_TIM_Base_Start_IT / HAL_TIM_PWM_Start）→ 引脚 AF 模式与引脚冲突（TIM1 还要看 BDTR.MOE）→ 最后才是硬件。调试器里读五样东西（APB1ENR、CR1.CEN、CNT、DIER.UIE + NVIC->ISER、CCER.CC1E + BDTR.MOE）就能把范围锁死在一层。把它变成一个肌肉记忆式的流程，比记住任何一个具体答案都有用。

小结与自检

一、要点清单

  • 定时器和计数器是同一套硬件，区别只在时钟源是「自己的内部时钟」还是「外面的脉冲」。理解了这一点，ETR 外部计数、编码器接口、输入捕获就都成了同一件事的不同说法。
  • 结构永远是：时钟源 → PSC → CNT → 和 ARR 比较 → 归零产生更新事件。后面所有的 Input Capture / Output Compare / PWM / 编码器接口，都是在这条链路上挂不同的「外挂」——捕获是「把 CNT 抄到 CCR」，比较是「拿 CNT 和 CCR 比」，PWM 是「比较的结果直接驱动引脚」。
  • 定时时间 T = (PSC+1)(ARR+1) / f_clk。反算的顺序是：先算 N = T × f_clk → 优先把分频比堆给 ARR（保分辨率）→ ARR 装不下再加大 PSC → 凑整数，凑不出就算出 ppm 级误差并写进设计文档。
  • 定时器时钟不等于 PCLK。APB 预分频 ≠ 1 时要 ×2（F103 上 APB1 = 36MHz → TIM2~4 = 72MHz）。这个 ×2 是「差一倍」类错误的头号来源。
  • ARR 的位数决定一次能定多长。16 位 + 72MHz 的极限是 59.65 秒；要更长就级联（TRGO → ITR），或者用 32 位定时器（F4/F7 的 TIM2/TIM5，单级可达 45 天）。
  • 更新事件 UEV 一次性干四件事：置 UIF（可以中断）、发 DMA 请求、让 ARR 的预装载值生效（影子寄存器）、把 CNT 清零。所以「改 ARR 不会立即生效」不是 bug，是预装载机制在保护你的波形。
  • 51 和 STM32 的分水岭是「谁负责重装」。51 在中断里用软件重装初值，重装延迟逐周期累积成误差；STM32 硬件自动重装，「定时准不准」从「看你中断写得好不好」变成了「看晶振买得好不好」。
  • 测频还是测周，先算分界点 √(f_clk/Tg)。72MHz + 1 秒闸门 ≈ 8.5kHz：低频用输入捕获测周（顺带得占空比），高频用 ETR 计数闸门。溢出补偿 + 多周期测量是两个通用的精度放大器。
  • 一个定时器的多路 PWM 频率必然相同（共用 CNT/ARR），只有占空比能各自独立。这是规划引脚和定时器时最容易忘的硬约束。
  • 系统时基和业务定时器是两回事。SysTick（或 RTOS 的 tick）负责「现在几点、该调度谁」，精度 1ms、每毫秒都要打扰 CPU；定时器外设负责「产生和测量精确的硬件时序」，纳秒到微秒级、不占 CPU。别让 HAL_Delay 进中断，别拿 tick 当波形源。

二、自测题（8 道，先自己想再看答案）

  1. 定时器时钟 72MHz，要一个 500ms 的更新中断。请给出 PSC 与 ARR 的取值、写出验算过程，并说明你为什么这么分配（提示：ARR 最大 65535）。
  2. 为什么你在 CubeMX 里看到 APB1 = 36MHz，而 TIM2 的时钟却是 72MHz？这个规则在什么情况下不成立？
  3. 你配好了 TIM2 的更新中断，但 HAL_TIM_PeriodElapsedCallback 一次都不进。请按可能性从高到低列出至少四个原因，并各给一句确认方法。
  4. PWM 模式 1、极性高、ARR = 999、CCR = 250。占空比是多少？引脚在周期里的哪个阶段输出高电平？如果把极性改成 Low，又变成什么样？
  5. 用输入捕获测一个 8Hz 的方波，计数时钟 1MHz、ARR = 65535，会遇到什么问题？请给出两种解法并比较它们的精度。
  6. 为什么 HAL_Delay 不能在中断服务函数里调用？请把「谁等谁」的循环依赖说清楚，并给出两种正确的替代写法。
  7. 同一个 TIM3 的 CH1 和 CH2 都配成了 PWM 输出，你希望 CH1 是 1kHz、CH2 是 5kHz。能不能做到？如果不能，给出三种可行的替代方案。
  8. 要用一个 16 位定时器（72MHz）做到「1 小时一次」的事件，请说明为什么单级做不到、需要几级、并给出一套具体的参数（写清 PSC 和 ARR）。
答案与解析
  1. N = 0.5s × 72 000 000 = 36 000 000。先试「把分频比堆给 ARR」：ARR 最大 65535，36e6 / 65536 = 549.3——除不尽，会引入误差。改用整数配比：PSC = 7199（÷7200 → 计数时钟 10kHz，1 个数 = 100µs）、ARR = 4999（一圈 5000 个数）。验算：7200 × 5000 / 72 000 000 = 36 000 000 / 72 000 000 = 0.5s，误差 0，且 ARR = 4999 ≤ 65535。为什么这么分：ARR 越大分辨率越好（这里 100µs 的刻度对 500ms 的周期完全够用），而 PSC 只是为了让计数时钟落在一个好算的整数上。
  2. 因为 STM32 有一条专门的规则：APB 预分频系数不为 1 时，该总线上定时器的时钟会被自动 ×2。F103 的标准配置里 APB1 预分频 = 2（PCLK1 = 36MHz），所以 TIM2~TIM4 拿到 36 × 2 = 72MHz；APB2 预分频 = 1（PCLK2 = 72MHz），TIM1 本来就是 72MHz。不成立的情况：APB 预分频 = 1——此时定时器时钟就等于 PCLK，没有 ×2。所以「×2」这件事必须结合预分频系数一起看，不能无条件套用。
  3. 按概率排：① 启动函数用错——用了 HAL_TIM_Base_Start() 而不是 HAL_TIM_Base_Start_IT()；确认方法：看调试器里 TIM2->DIER 的 UIE 位是否为 1。② NVIC 没使能——CubeMX 里 NVIC Settings 那个勾没打；确认方法：看 NVIC->ISER[0] 对应 TIM2_IRQn（28 号）的位。③ 外设时钟没使能——__HAL_RCC_TIM2_CLK_ENABLE() 没被调用（此时写寄存器被静默丢弃、读回来是 0）；确认方法：看 RCC->APB1ENR 的 bit 0。④ 回调函数名写错——写成了 HAL_TIM_OC_DelayElapsedCallback 或自己拼错；确认方法：在 TIM2_IRQHandler 里打个断点，看它到底有没有被调用（进了 IRQHandler 但不进回调 = 名字问题）。另外还有两个次要原因：中断标志没清（自己重写了 IRQHandler）、全局中断被 __disable_irq() 关掉了。
  4. 占空比 = CCR / (ARR+1) = 250 / 1000 = 25%。PWM 模式 1 + 极性高：向上计数时 CNT < CCR 输出有效电平，而「极性高」意味着有效电平就是高电平——所以每个周期的前 250 个计数（前 25% 的时间）引脚是高，后 75% 是低。把极性改成 Low，则「有效电平」变成低电平：前 25% 变低、后 75% 变高——占空比从「高电平占 25%」翻转成「高电平占 75%」，波形整体反相，但周期和 CCR 都没变。这一条是理解「PWM 模式 1/2」与「极性」这两个独立旋钮的关键：模式 1 和模式 2 决定「CNT 小于还是大于 CCR 时有效」，极性决定「有效到底是高还是低」，两者组合出四种等效波形。
  5. 问题：溢出。计数时钟 1MHz、ARR = 65535 时，一圈只有 65.535ms，而 8Hz 的周期是 125ms——一个周期里会溢出一次（125 / 65.535 = 1.9，即跨过一次甚至两次溢出）。如果直接用「本次捕获值 − 上次捕获值」，会算出一个远小于真实值的周期，频率自然也就错得离谱。解法一（保精度）：加一个溢出计数器，在更新中断里 +1，用 (ovf << 16) | cnt 拼成完整时间戳再相减（第 4 节的代码就是它）——精度仍然是 1µs，相对误差 1/125000 ≈ 8ppm。解法二（降分辨率换简单）：加大 PSC，把计数时钟降到 100kHz（PSC = 719），则 125ms 对应 12500 个数，一圈 655.35ms 装得下，不需要补偿——但分辨率从 1µs 变成 10µs，相对误差 1/12500 = 80ppm。结论：溢出补偿用十行代码换来了 10 倍精度。
  6. 因为存在循环依赖：HAL_Delay 的循环条件是 (HAL_GetTick() - tickstart) < ms，也就是等 uwTick 变大；而 uwTick 只在 SysTick 中断里增加；SysTick 的优先级被 HAL 设为 15（最低），Cortex-M 的中断又必须优先级数值更小才能抢占——于是 SysTick 无法抢占你正在执行的那个中断。结果：你在中断里等 uwTick，uwTick 在等 SysTick，SysTick 在等你退出中断。三者互等，死锁。两种正确替代：① 记录时间戳 + 主循环判断（中断里只写 s_event_tick = HAL_GetTick(); s_flag = 1;，主循环里判断差值到没到）；② 数中断次数（在 1ms 的定时器中断里 if (++n >= 10)，凑够 10 次就是 10ms）。要微秒级延时用 DWT->CYCCNT。
  7. 不能。因为四个通道共用同一个 CNT、PSC 和 ARR，而频率完全由「CNT 数到 ARR 的时间」决定——同一个定时器的所有通道频率必然相同，能独立配置的只有 CCR（占空比）、极性和输出使能。三种替代方案：① 拆到两个定时器：把 5kHz 那一路挪到 TIM4（F103C8T6 上还有 TIM1/TIM4 可用），代价是额外占一个定时器和一个引脚；② 合并频率需求：如果 5kHz 只是「蜂鸣器听起来更响」，其实 1kHz 也能响，那就都用 1kHz，省下一个定时器；③ 软件 PWM / 外部器件：慢速负载（LED、继电器）用普通 IO 在主循环或 100µs 中断里刷出来，省掉硬件 PWM；或者用带 PWM 的 IO 扩展芯片、可编程时钟芯片（如 NE555、专用的 LED 驱动）。选哪种，取决于你的频率需求是否真的不可让步。
  8. 单级做不到：1 小时 = 3600s，总分频比 N = 3600 × 72 000 000 = 2.592 × 10¹¹；而一个 16 位定时器即使 PSC 和 ARR 都拉满，最多也只有 65536 × 65536 = 4.295 × 10⁹（对应 59.65 秒）——差了 60 倍，所以必须级联。两级就够了（(4.295e9)² ≈ 1.8e19 ≫ 2.592e11）。一套具体参数（两级方案）：TIM2 作为主：PSC = 7199（÷7200 → 10kHz）、ARR = 9（÷10）→ 更新频率 1kHz（周期 1ms），并把 MMS = 010（TRGO 输出更新事件）；TIM3 作为从：时钟源选 ITR（Internal Trigger）接 TIM2 的 TRGO，PSC = 3599（÷3600）、ARR = 999（÷1000）→ 分频比 3600 × 1000 = 3 600 000 → 输出频率 1000 / 3 600 000 = 2.7778e-4 Hz → 周期正好 3600 秒 = 1 小时，误差 0。如果想要「每一级的周期都是整数好记的时间」（1ms / 1s / 1 小时各有用处），就串三级：TIM2 出 1kHz、TIM3 出 1Hz（PSC=0, ARR=999）、TIM4 再 ÷3600（PSC=35, ARR=99）。

三、练习（5 项，建议按顺序做）

  1. 亲手验一遍「1ms 到底是不是 1ms」。把 TIM2 配成 1ms 更新中断，在回调里累加 g_ms_tick；主循环里每 1000 个 tick 翻转一次 LED，同时用手机秒表或逻辑分析仪量「翻转 10 次」的总时间。预期 20 秒，实测差多少？如果差了整整一倍，回去看坑 2；如果只是差几十毫秒，那正是晶振误差，用本文的公式估一下是否吻合。
  2. 把呼吸灯升级成「按键调速 + 非阻塞」。要求：按住按键时呼吸变快、松开变慢，全程不能使用 HAL_Delay；按键消抖也用时间戳判断。验收标准：在呼吸的同时，串口仍能每 100ms 打印一次当前 CCR 值——这就是「非阻塞」的直接证据。
  3. 用输入捕获做一个「转速表」。用一个定时器（TIM3）产生 1kHz~5kHz 的可变频率方波，用另一个（TIM4）去捕获它，算出频率并打印到串口；再用逻辑分析仪测出真实频率，把两者列成表，算出每个频点的相对误差。然后把 PSC 从 71 改成 0（72MHz 计数时钟）重做一遍，对比误差——你会亲眼看到例 4 那张表。
  4. 用 TIM1 的互补输出驱动一个半桥，先用示波器确认死区。把死区时间设成 1µs，同时观察 CH1 和 CH1N 两路波形，量出实际死区是多少（注意别把探头地线接错，双通道要共地）。然后逐步加大负载电流，观察波形是否出现异常尖峰。再做一次「故意把死区设成 0」的实验——用低压小电流的电源、并串上保护电阻，看看波形会出现什么（这一步是为了让你对坑 8 有身体记忆，不要在高压下做）。
  5. 把软件定时器框架扩展成「任务体检器」。在调度器里用 DWT->CYCCNT 记录每个任务执行前后的周期数，算出每个任务的执行时间；把最长执行时间存起来，如果某个任务超过设定阈值（比如周期的 20%），就置一个错误标志并打印任务名。验收标准：故意在某个任务里写一个 HAL_Delay(5)，你的体检器能报出是哪一个任务拖垮了节拍。这个练习做完，你对「中断只记录时间、业务在主循环」这条原则会有完全不同的体会。
回到这一篇的主线

如果这篇只留一句话，那就是开头那句：定时器和计数器是同一套硬件，区别只在数的是自己的时钟还是外面的脉冲。

而 PSC、CNT、ARR、CCR、UEV、TRGO/ITR 这几个寄存器，构成了一个「可以任意拼接的时间工具箱」：

  • 把 CNT 和一个固定值比 → 定时中断（本文第 4 节的第一个例子）
  • 把 CNT 和 CCR 比、结果送到引脚 → PWM（呼吸灯）
  • 把 CNT 抄到 CCR（由外部边沿触发）→ 输入捕获（测频率、测占空比）
  • 把外部脉冲当计数时钟 → 计数器（ETR 计脉冲、编码器接口测正反转）
  • 把 UEV 送给另一个定时器当时钟 → 级联（做出任何长度的周期）
  • 把 UEV 送给 ADC/DAC/DMA → 精确等间隔采样（这是下一篇之后会反复遇到的手法）

下一次你面对一个「需要一个周期性动作」的需求时，别再写 for 空循环了——先想清楚这个动作要多准、要不要和别的任务并行，然后决定它是该交给硬件定时器，还是交给一个小小的软件定时器表。这个判断能力，就是这一篇真正想给你的东西。
