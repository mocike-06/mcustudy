为什么需要它

先讲一个几乎每年都会发生在课设答辩现场的场景。

大三上学期，你花两周把课设做完了：一块 STM32 最小系统板、一个 0.96 寸 OLED、一个 DS18B20 温度传感器、一个用 PWM 驱动的直流风扇，按键可以设定目标温度。演示那天一切正常，风扇该转就转、OLED 上的数字该跳就跳。然后老师问了三个问题：

三个让「会做」和「懂了」分开的问题
  • 「你这里为什么要用 STM32？用 51 行不行？」——你答：「因为 STM32 性能好。」老师追问：「好在哪里？这颗芯片的哪一项资源是这个项目必需的？」你答不上来。
  • 「你这个程序占了芯片多少 Flash、多少 RAM？还剩多少？」——你答：「能跑就行，没看过。」你甚至不知道这两个数字可以在编译输出里直接看到。
  • 「如果这个东西要做成产品卖一万台，三年后你还能买到这颗芯片吗？固件出了问题怎么给已经卖出去的一万台升级？」——你从来没想过「出厂以后」这段时间。

这三个问题，正好对应本篇的三个部分：选型、资源账、产品生命周期。它们不属于任何一个外设，但决定了一个项目成不成立。

再讲一个更日常的困惑。你在电脑上写程序的经验，搬到单片机上会大面积失效。你习惯了：一个死循环卡住了就 Ctrl+C、内存不够就再买一条、变量名打错了编译器会告诉你、程序崩了会弹一个带行号的报错框、改完代码双击一下就重新跑起来。

到了单片机上，这七件事没有一件是理所当然的：程序卡死了没有 Ctrl+C，你只能拔电；内存不够没有「再买一条」，你得回去删数组；栈溢出不会弹报错，它表现为「板子随机重启」；你想单步调试，得先有一根 SWD 线和一个能停在断点上的调试器；你甚至连「把代码编译成能在这颗芯片上跑的机器码」这件事都做不到——因为你手上这台电脑的 CPU 和单片机里那颗 CPU 根本不是同一个东西。

这些都是「嵌入式系统」这门知识要回答的问题。它不是某一颗芯片的手册，而是一整套关于「在资源受限的专用计算机上做工程」的常识。缺了这套常识，你会一直停在「照着例程改参数」的水平上：能跑通，但说不清为什么；出了新问题，只能继续搜例程。

这一层要解决的问题：把「零件」组装成「整机」

第一层（第 1~23 篇）你学的都是零件：电阻、电容、二极管、三极管、逻辑门、触发器、存储器。零件知识的特点是每一条都独立成立——你会算分压，这件事本身就是对的。

第二层不一样。从这一篇开始的十篇讲的是芯片内部这个系统怎么运转、以及你怎么和它打交道：CPU 怎么执行一条指令、变量到底住在哪个地址、中断是怎么打断主程序的、定时器怎么数到 1 毫秒、数据怎么不经过 CPU 自己搬走、程序为什么必须写成非阻塞的、出问题了用什么工具看。这些东西单独看都像「原理」，但它们是同一个系统的十个侧面——任何一篇缺了，你在实际项目里都会撞上一堵说不清的墙（比如：不懂中断优先级，就会出现「串口一收数据按键就失灵」这种查不出来原因的怪事）。

核心概念

这一节是整篇的骨架，八个小节可以当手册查。先说明一件事：「嵌入式系统」这个词指的不是一颗芯片，也不是一块板子，它指的是一个「为了某个具体用途而被做进一台机器里的计算机系统」。芯片和板子只是它最常见的实现形式。

2.1 什么是嵌入式系统：定义的三层含义

国内教材普遍采用的定义是（IEEE 与国内《嵌入式系统》教材口径一致，张毅刚《单片机原理及应用》第 4 版第 1 章、吴银琴《嵌入式系统原理及应用》第 2 版第 1 章都引用了它）：

定义

嵌入式系统（Embedded System）是以应用为中心、以计算机技术为基础，软件硬件可裁剪，适应应用系统对功能、可靠性、成本、体积、功耗严格要求的专用计算机系统。

这句话信息量很大，但它是「压缩过」的。把它拆开，你会得到三层含义——这三层里任何一层不成立，它就不该叫嵌入式系统。

第一层含义：它是「嵌入」到对象体系里的

「嵌入式」三个字的字面意思就是：它是被塞进另一台机器里的一个部件。洗衣机里的控制板、汽车里的 ECU、电梯里的召唤板、心脏起搏器里的那颗芯片——它们都不是独立的产品，而是被控对象（对象体系）的一部分。它没有自己的键盘显示器，它对外只有传感器信号和执行器动作，以及一根和外界说话的线（串口、CAN、Wi-Fi）。

这一层含义带来一个极其重要的推论：嵌入式系统的正确性判据来自对象体系，而不是来自它自己。PC 上的程序崩溃了，最坏结果是重启一下；汽车刹车控制器「算错了」是要出人命的。同样一段代码，放在 PC 上叫「有点卡」，放在对象体系里可能叫「不合格」。

第二层含义：以应用为中心

PC 的设计思路是「我把平台做通用，让所有人来适配我」；嵌入式的设计思路是「我有一个明确的应用，我按它去定制」。所以嵌入式开发的第一步永远是把需求写清楚，而不是「先把板子跑起来再说」——你的每一分硬件成本和每一 KB RAM，都应该对应到需求清单上的某一项。

这一层含义也是「专用」与「通用」的分野所在。下面这张表把两者的差别摆在明处：

维度通用计算机（PC / 服务器）嵌入式系统
服务对象未知的、多样的用户与任务一个确定的用途、一个确定的对象体系
设计目标追求通用性与峰值性能在满足功能的前提下追求成本 / 体积 / 功耗 / 可靠性的最优组合
软硬件形态标准化的通用硬件 + 可任意安装的软件软硬件一起裁剪，不用的直接砍掉
人机接口键盘、鼠标、显示器必备常常没有人机接口，或只有一个指示灯、一个按键
程序载体硬盘、SSD，程序可随时安装卸载程序固化在 Flash / ROM 里，出厂即定型
生命周期3~5 年，坏了换新常要求 10 年以上（汽车、工业、医疗）
失效后果重启、重装、丢数据可能是设备损坏、生产事故、人身伤害

第三层含义：软件硬件可裁剪

这是嵌入式最有「工程味」的一条。裁剪的意思是「按需保留」：硬件上，你不需要 CAN 就不要选带 CAN 的型号（省几块钱）；软件上，你不用操作系统就不要把操作系统编进去（省几 KB RAM 和几 KB Flash）。

反过来讲，「裁剪」也意味着你必须知道自己用了什么。PC 上你可以说「反正库会处理」，嵌入式里每一个 #include 都会在最终的 Flash 占用上留下痕迹（第 3 节会教你把这个数字读出来）。

定义说完了，我们来看反例。因为初学者最常见的误解，恰恰是把「能跑程序的芯片」当成了嵌入式系统。

反例一：桌上一块跑着 LED 闪烁例程的开发板。它能跑程序，芯片也是标准的 MCU，但它没有嵌入任何对象体系——它谁都不控制，它只是在给你演示。它的身份是「学习平台」，不是「嵌入式系统」。（当然，你把它装进风扇里控制转速，它立刻就是了。）

反例二：一块树莓派，插上显示器键盘当小电脑用。树莓派用的是嵌入式处理器（Cortex-A、没有 MMU 之外的差异其实很大——它有 MMU），跑的是完整的 Linux 桌面，装的是通用软件。它能做嵌入式，但「当小电脑用」的这个用法里，它扮演的是通用计算机。说明一件事：是不是嵌入式系统，取决于用途与形态，不取决于芯片型号。

反例三：一张按一下唱三秒的音乐贺卡。它只有一颗几毛钱的 8 位芯片、一小段固化在 ROM 里的音乐数据、一个压电蜂鸣器。它才是标准的嵌入式系统：嵌进「贺卡」这个对象体系、只为一个应用存在、软硬件都是裁剪过的。

三问判据

拿不准一个东西算不算嵌入式系统时，问三个问题：① 它嵌进哪个对象体系里了？② 它为哪一个具体应用而存在？③ 它的软硬件是被裁剪过的吗？三个都答得上来，它就是。三个都答不上来（或者只能答「它能跑程序」），那它多半只是个通用计算平台或实验装置。

最后补一句衔接：单片机（MCU）是嵌入式系统里最典型、最底层、也最适合入门的一支。它不是嵌入式系统的全部（还有以 ARM Cortex-A 为核心的嵌入式 Linux 系统、以 DSP/FPGA 为核心的系统），但它的每一个概念——内核、存储器、外设、中断、时钟——都会在你后面遇到的所有系统里以某种形式复现。所以从它入门是划算的。

2.2 嵌入式系统的四层组成：每层替上面屏蔽了什么

「一个嵌入式系统由什么组成」这个问题，如果只回答「CPU 加内存加外设」，你只能画出一张硬件框图。有工程价值的回答是分层的回答：硬件层、硬件抽象层、系统软件层、应用层。分层的意义不在于把东西归堆，而在于每一层都替它的上一层屏蔽掉一批细节——你只和下一层给你的接口打交道。

系统软件层 裸机主循环 / 时间片轮询框架 / FreeRTOS、RT-Thread / 嵌入式 Linux；协议栈、文件系统、GUI 库 「多个任务怎么共享一个 CPU」「什么时候该切到谁」「任务之间怎么传数据」 Flash 与 RAM 开销（一个 FreeRTOS 内核典型要吃 5~8 KB RAM）；调度带来的不确定性（需要算任务栈）
硬件抽象层
HAL / BSP		 厂商 HAL 库、板级支持包 BSP、自己写的寄存器驱动与引脚宏定义 「寄存器的第几位该置 1」「时钟要先使能谁」「引脚复用到哪个功能」 执行效率与代码体积（HAL 库比裸寄存器慢、占 Flash 多）；抽象泄漏（有些时序必须直接操作寄存器）
硬件层 MCU / MPU、Flash、SRAM、GPIO、定时器、串口、ADC、DMA、电源、时钟、外部器件 ——（它是最下面一层，物理世界本身） 成本、体积、功耗、采购周期；改硬件要重做 PCB

关于第 2 层，有一个判断需要提前建立：「系统软件层」不等于「必须有操作系统」。一个 while(1) 的主循环 + 中断，本身就是一个最简的系统软件层（俗称前后台系统）；它同样在替你回答「多个任务怎么共享一个 CPU」这个问题，只是答案简单粗暴：轮流跑，谁也别停太久。什么时候这个答案不够用了，第 4 节会用温控风扇这个例子给你一条明确的判断线。

2.3 和 PC 编程的八个根本差别

这一小节要写透，因为它是初学者最容易带着错误直觉过来的地方。你把 PC 上的编程习惯原样搬过来，几乎每一条都会在某个深夜变成查不出来的 bug。八条差别按「最容易被忽略」的顺序排列，第 3 条（交叉编译）是重头戏。

① 专用 vs 通用：你的程序只服务一个场景，但必须服务到极致

PC 上写程序，你要考虑「用户会怎么折腾我」；嵌入式里，你面对的是一个已知且固定的输入输出集合。好处是你不需要做兼容层（省资源），坏处是你失去了「以后再说」的余地：内存不够没法加、功能没做就是没做、需求变了要重新选型甚至重新做板。所以嵌入式项目里，「需求分析」不是走形式，它直接决定了后面所有决定。

② 资源受限：KB 级 RAM、MHz 级主频、没有 MMU 和虚拟内存

这一条是其他所有差别的根源。把两边的典型量级摆在一起看：

资源你桌上的 PC典型入门 MCU（如 STM32F103C8T6）差距
主频3~5 GHz72 MHz约 50 倍
内存（RAM）16~32 GB20 KB约 100 万倍
程序存储512 GB SSD64 KB Flash约 800 万倍
取指方式指令存在内存里，由 CPU 缓存预取指令直接从 Flash 取（多数型号无指令缓存）取指速度受 Flash 访问速度限制
地址翻译有 MMU + 虚拟内存，进程互不干扰没有 MMU，指针写错就写错到别人头上没有内存保护这个安全网
操作系统必备可以没有，也可以只有个内核你要自己管时间与资源

这带来几个非常具体的后果，请逐条记住：

  • 数组越界不再是「大概会崩」，而是「一定改坏了别的东西」。PC 上有 MMU 兜着，越界通常触发段错误；MCU 上越界会安静地覆盖掉旁边变量的值，表现为「改了一个无关变量，另一个功能就怪了」。
  • malloc / free 能不用就不用。堆会把有限的 RAM 切碎，长期运行的程序可能因为碎片而分配失败（这不是内存泄漏，是碎片）。嵌入式里更常见的做法是静态分配：全局数组、编译期就把大小定死。
  • 栈的大小要你自己算。链接脚本里 .stack 段的大小是写死的（比如 1 KB）。递归、大局部数组、printf 家族（它们内部栈开销很大）都可能把栈撑爆，而栈溢出不会报错，它会把紧挨着的变量踩烂，最后表现为「随机重启」。
  • int 的宽度在两边可能不一样。PC 上 int 通常是 32 位，而某些 8/16 位单片机上 int 只有 16 位（最大 32767）。跨平台代码里请明确用 stdint.h 里的 uint8_t / int16_t / uint32_t，把宽度写死。

③ 交叉编译：你写的代码，是在一台完全不同的机器上编译给另一台机器用的

这一条值得单独写透，因为它解释了整套嵌入式工具链为什么长成现在这个样子。

为什么不能在单片机上编译自己？先看编译器本身有多大：一个完整的 gcc 加上它的前端后端，可执行文件是几十 MB 量级；编译一个中等大小的 C 文件，编译器进程的峰值内存占用是几十 MB 量级。而我们的目标芯片有 64 KB Flash、20 KB RAM。也就是说：把编译器装进这颗芯片，光是它自己的体积就是芯片容量的上百倍；再加上编译器依赖文件系统（要读 .c 文件、要写 .o 文件）、依赖进程管理、依赖动态内存分配，这些前提在裸机上一样都不具备。

所以流程变成了这样：你在自己的电脑（宿主机，host）上运行编译器，编译器产出的机器码是给单片机（目标机，target）用的。这个动作就叫交叉编译（cross compile）。两个名词请记住：

  • 宿主机（host）：运行编译工具链的那台机器，通常是你的 Windows / Linux 电脑，CPU 是 x86-64。
  • 目标机（target）：最终运行程序的机器，这里是 STM32，CPU 是 ARM Cortex-M3。

工具链名字的每一段都有含义。以最常用的 arm-none-eabi-gcc 为例，它由三段前缀加一个工具名组成：

片段名字确切含义写错会怎样
arm 目标架构 生成的机器码面向 ARM 32 位架构（注意不是 x86_64，也不是 64 位的 aarch64） 写成 aarch64 会生成 64 位 ARM 指令，Cortex-M 根本不认
none 厂商 / 系统字段 表示不绑定某个操作系统。裸机（bare metal）工具链就是 none；如果目标跑 Linux，这里会变成 linux-gnueabihf 之类 用 Linux 版工具链编裸机程序，链接时会找不到 C 运行库的入口
eabi 应用二进制接口 Embedded Application Binary Interface：规定函数调用时参数放哪个寄存器、返回值放哪、哪些寄存器由被调用者保存、结构体怎么对齐。裸机用 eabi，带浮点硬件时常见 eabihf ABI 不匹配时，两段分别编译好的代码链接在一起能通过，但一运行就错乱（参数传丢、栈被写坏）
gcc 工具名 具体要调用的那一个程序。同一套前缀下还有 g++（C++ 编译器）、as（汇编器）、ld（链接器）、objcopy（格式转换）、size（看段大小）、objdump（反汇编）、gdb（调试器）、nm（看符号表） ——

这里有一个必须点破的坑：如果你的电脑上装了 MinGW 或 Visual Studio，直接敲 gcc main.c 也能编译成功，但那生成的是 x86 机器码。它在你的电脑上跑得挺好，烧进 STM32 一定不工作——因为两种 CPU 的指令集完全不同。这就是「换了编译器」和「交叉编译」的区别，也是初学者第一次烧录失败的最常见原因之一（另一个是链接脚本没配对）。

除了「用哪个编译器」，交叉编译还带来两个 PC 上没有的步骤：

  • 你得告诉链接器「内存长什么样」——这就是链接脚本（linker script，.ld 文件）的作用。PC 上这件事由操作系统和可执行文件格式（ELF）自动处理，因为 PC 的内存是运行时才分配的；而单片机上的 Flash 固定从 0x08000000 开始、RAM 固定从 0x20000000 开始，程序将来要住在哪个地址，必须在链接时全部定死。链接脚本里会写：Flash 多大、RAM 多大、代码放 Flash 的哪一段、变量放 RAM 的哪一段、栈顶在哪。
  • 你还得准备「启动文件」，因为目标机上没有操作系统来装载你的程序。PC 上双击一个程序，是操作系统把它读进内存、建好进程、跳到入口；单片机上没有这个角色，所以必须有一段汇编写好的启动代码，负责把中断向量表放在最前面、把已初始化的全局变量从 Flash 拷贝到 RAM、把未初始化的变量区清零、设置栈指针，最后才跳到 main。这段代码通常由芯片厂商提供（startup_stm32f103xb.s 之类），你平时看不见它，但它必须在。

最后，编译产物还要「变形」一次：链接器产出的 .elf 文件带着调试符号和段信息，不能直接烧进 Flash，要用 objcopy 把它转成纯二进制（.bin）或带地址信息的 Intel HEX（.hex）。整条数据流是这样的：

  main.c  led.c  startup_stm32f103xb.s      （源文件，人看的）
     │
     │  ① 编译  arm-none-eabi-gcc -c -mcpu=cortex-m3 -mthumb
     ▼
  main.o  led.o  startup.o                    （目标文件，含机器码 + 符号表）
     │                                          每个 .c 单独编成一个 .o
     │  ② 链接  arm-none-eabi-gcc ... -T stm32f103c8t6.ld -Wl,-Map=out.map
     ▼
  firmware.elf                                （可执行文件，已按地址排好）
     │        ├─ .isr_vector  中断向量表，固定在 Flash 最前面
     │        ├─ .text        代码 + 常量，住 Flash（0x08000000 起）
     │        ├─ .data        有初值的全局变量，住 RAM，初值存在 Flash 里
     │        └─ .bss         无初值的全局变量，住 RAM，启动时清零
     │
     │  ③ 转换  arm-none-eabi-objcopy -O ihex firmware.elf firmware.hex
     ▼
  firmware.hex                                （只有地址 + 数据，烧录器认这个）
     │
     │  ④ 烧录  ST-Link / J-Link / 串口 ISP / DFU
     ▼
  STM32 内部 Flash 的 0x08000000 开始处       （断电不丢，上电即跑）

  同时看一眼：arm-none-eabi-size firmware.elf
     text    data     bss     dec     hex   filename
     9840     112    1620   11572    2d34   firmware.elf
     └代码和常量  └有初值变量 └无初值变量   └三者合计（不是 dec 十进制，是总和）
     Flash 占用 = text + data       RAM 占用 = data + bss

记住最后那两行公式，第 3 节的第一道例题就是用它算账的：Flash 占用 = text + data（因为 .data 的初值也要存在 Flash 里等着被拷到 RAM）；RAM 占用 = data + bss。

④ 没有操作系统的日子：裸机前后台 vs RTOS

PC 上你写的每一个程序都活在操作系统里：进程调度、内存管理、文件读写、网络收发，全都有人替你做了。单片机上，这些「有人替你做了」的事情，要么你自己做，要么你请一个很小的操作系统来做。

  • 裸机前后台系统：一个 while(1) 主循环（后台）轮流处理所有事务，中断（前台）负责处理「必须马上响应」的事件，处理完立刻退出。最简单的系统就是它，很多工业产品至今也是它。它的致命弱点是：主循环里任何一个环节耗时过长，其他所有事情都要排队等——包括「按键响应」这种对人来说必须及时的事。
  • RTOS（实时操作系统）：把功能拆成多个任务，每个任务有自己的栈，调度器按优先级决定谁先跑。它解决的是「多个实时性要求不同的功能怎么共存」。代价是：内核本身要占 5~8 KB RAM（第 3 节会细算），每个任务都要单独的栈，还要学会信号量、队列、互斥这些新概念，以及它们带来的新 bug（优先级反转、栈溢出、死锁）。

判断线：如果所有功能的实时性要求都能被一个 1 ms 的时间片满足，而且最慢的那个功能不会超过时间片，裸机就够了；如果存在「某个功能必须在微秒级响应」，那用中断解决；只有当功能多到「时间片排不下」或者「任务之间需要复杂的同步与通信」时，才值得上 RTOS。「上 RTOS」是工程决策，不是水平证明。

⑤ 实时性：正确但迟到的结果，等于错误的结果

「实时」这个词在中文里容易被误解成「快」。它的准确含义是：系统必须在确定的截止时间（deadline）之前给出正确的结果。注意两个关键词：确定（不是平均快，是最坏情况也能满足）和截止时间（是需求给的，不是你能商量的）。按错过截止时间的后果，分三档：

类别判据错过截止时间的后果典型例子（含量级）
硬实时 必须在截止时间前完成，没有例外 灾难性：设备损坏、人员伤亡 安全气囊点火（碰撞后数十毫秒内必须动作）、电机磁场定向控制（电流环常见 10~100 µs 周期）、心脏起搏器
软实时 偶尔错过可以接受，但会明显变差 体验下降、画面卡顿、数据重传 视频播放（丢一帧只是画面顿一下）、键盘扫描、温控风扇的显示刷新
非实时 只要最终算完就行 只是慢，不影响正确性 数据记录上传、固件压缩、日志整理

注意这张表里最容易被低估的一点：同一个系统里可以同时存在三档要求。温控风扇的 PWM 输出是硬实时（频率错了风扇会啸叫），按键响应是软实时（慢一点人不舒服但没关系），而「把温度记录写到 Flash」是非实时。区分它们，决定了你把哪段代码放进中断、哪段放进主循环。

⑥ 调试方式不同：你没有屏幕，也没有 printf

PC 上程序不按预期跑，你几乎只有一招：在可疑的地方打一行打印，再跑一遍。单片机上这一招还在，但形式变了，而且多了几个选择：

  • 串口打印：把 UART 接到 USB-TTL 模块上，在电脑的串口助手里看输出。这是最常用的手段，但有两个陷阱：一是打印本身耗时（一个 115200 bps 的串口，发 10 个字符要将近 1 ms），会改变程序的时序，让原本存在的 bug 消失（这叫海森堡 bug）；二是程序卡死时打印也会停，所以你得自己设计「看到哪一行停下」的定位点。
  • SWD / JTAG 硬件调试：用 ST-Link、J-Link 或 DAPLink 接到芯片的 SWD 引脚上，可以在代码里设断点、单步、看任意变量的值、看每一个寄存器、看调用栈。这是最强大的手段，代价是要多两根线、芯片上要留出这几只引脚（做产品时经常被复用掉，所以要提前规划）。
  • 示波器 / 逻辑分析仪：当问题出在「时序」上时（PWM 波形不对、SPI 通信失败、中断响应延迟），只有它们能看清。经验做法是：在代码里选一个空闲 GPIO，在进入某段逻辑时拉高、退出时拉低，然后用示波器量这个方波的宽度——这是测量代码执行时间最直接的办法。
  • 只留一个 LED：在引脚紧张或没有调试口的产品上，用 LED 的闪烁次数编码错误码是最原始也最有效的手段。

⑦ 功耗与长期无人值守：没人会来帮你重启

PC 插着市电，功耗从来不是设计目标；嵌入式的很多形态是电池供电、装在别人够不着的地方（水表、井盖、车载模块、农业传感器），这时功耗直接决定产品能不能用：

  • 用一块 CR2032 纽扣电池（约 220 mAh）做笔算就会明白：如果平均电流是 1 mA，理论寿命只有 220 小时，也就是 9 天；如果降到 20 µA（靠定期唤醒、其余时间深度睡眠），理论寿命约 11000 小时，约 1.25 年。差 50 倍的电流，差 50 倍的寿命，这就是为什么低功耗设计里第一条永远是「让 CPU 尽量睡」。
  • 长期无人值守意味着可靠性要求变成「自我恢复」：程序跑飞了没人拔电，所以必须开看门狗（硬件定时器，到点没喂就复位）；电源波动、静电、雷击都要能扛；复位原因要记录（这次的复位是上电、看门狗还是掉电？）以便事后追查。
  • 参数要能存下来：设备重启后不能回到出厂状态，配置（目标温度、校准系数、运行时长）必须存在 Flash 或 EEPROM 里。注意 Flash 有擦写次数上限（常见 1 万~10 万次），频繁写会写坏，所以要加缓存或做磨损均衡。

⑧ 一旦出厂就难以召回：软件缺陷的代价被放大了一万倍

PC 上发现 bug，你发个更新包，用户点一下就完事。嵌入式设备卖出一万台，可能装在全国各地的天花板、机柜、汽车里——你没有办法让用户「拆下来寄回来」。所以嵌入式软件有一条特别的纪律：凡是交付到现场的代码，都要假设它再也改不了了。

缓解手段是在硬件和软件的架构里预先埋好升级通道：

  • IAP（In-Application Programming，在应用编程）：程序自己（通过串口、SD 卡、USB 等）接收新固件并写进自己的 Flash。做法是把 Flash 划分为 Bootloader 区（永不更新，只负责接收和烧写）和应用区。
  • OTA（Over-The-Air，空中升级）：通过无线网络远程升级，物联网设备的标配。为了保证「升级失败不变成砖头」，成熟做法是双分区（A/B）：新固件先写到备份分区，校验通过后再切换启动分区；如果新固件启动失败，Bootloader 自动回滚到旧版本。
  • 为此在硬件设计阶段必须留的东西：足够的 Flash 余量（双分区意味着固件的两倍空间）、一个复位/升级按键或跳线、以及把调试口（SWD 或串口）引到可接触的位置。这些决定一旦 PCB 做完就改不了了，所以升级方案要在画板之前想清楚。
把八条压缩成一句话

PC 编程是在资源充裕、有操作系统兜底、错了可以改的环境里做软件；嵌入式编程是在资源紧张、没有兜底、错了改不了的环境里做软硬件一体的工程。你每写一行代码，都要同时想它在哪颗 CPU 上跑、占多少 Flash 和 RAM、多久跑完一次、出错时谁来收拾。

2.4 嵌入式系统的分类：四个常用维度

分类不是为了背名词，而是为了在看到一个新需求时，能迅速把它归到一个已知的「档位」上，从而知道该用什么样的芯片、该配什么样的软件。工程上最常用的四个维度是：位宽、用途、实时性要求、有没有操作系统。

维度一：按处理器位宽分

位宽典型家族特点今天的位置
8 位 8051 系列、PIC、AVR（ATmega） 一次处理 8 位数据，指令简单，寄存器少，外设少；功耗可以做到很低；开发工具相对简陋 仍是教学和超低成本产品的主力（家电面板、玩具、充电器、遥控器），几毛钱到两三块钱
16 位 MSP430、PIC24、MSP432 前代 功耗极低是最大卖点，MSP430 常见休眠电流在微安级；生态比 8 位好、比 32 位弱 低功耗计量仪表（水表、气表）、部分医疗设备
32 位 ARM Cortex-M（STM32、GD32、nRF、ESP32 内核）、RISC-V 32 位 性能、外设、工具链、生态全面碾压 8/16 位，价格已经下探到个位数；是今天绝对的主流 工业控制、汽车电子、物联网、消费电子的默认选择
64 位 ARM Cortex-A（树莓派、i.MX、全志）、RISC-V 64 能寻址大内存、跑完整操作系统；成本、功耗、启动时间都显著上升 需要跑 Linux/Android 与复杂界面的场合，见 2.5 小节

这里有个反直觉的事实值得记住：位宽不等于性能档次。一颗 8 位芯片只要 0.5 元还能用十年，它就不会消失——选型看的是「够不够用」，不是「先不先进」。

维度二：按用途分

用途典型设备对这个领域的额外要求对软件的影响
工业控制PLC、变频器、伺服驱动、仪表、传感器变送器宽温（常见 −40~85 ℃）、抗干扰、长期连续运行、现场总线（CAN、RS-485、Modbus、EtherCAT）必须开看门狗；通信要做超时与重传；参数掉电保存；不能有阻塞式延时
消费电子家电、电动牙刷、玩具、可穿戴成本极致敏感、外观与交互体验、电池续航代码要小而快；低功耗管理是核心；经常用「能省就省」的 8 位芯片
汽车电子ECU、车身控制、BMS、仪表、ADAS 域控制器车规认证（AEC-Q100 器件、ISO 26262 功能安全流程）、温度等级、CAN/LIN/车载以太网、极长生命周期必须用符合功能安全的开发流程（需求可追溯、代码规范如 MISRA C、单元测试）
医疗电子监护仪、输液泵、血糖仪、助听器、起搏器高可靠、低功耗、法规认证（如 IEC 60601）、失效模式必须可分析软件要做失效安全设计（故障时进入安全状态）；计算与通信要可验证
通信与网络路由器、交换机、基站、光模块高吞吐、低延迟、协议栈复杂多数跑嵌入式 Linux；关键转发路径可能由专用芯片或 FPGA 承担
物联网智能家居节点、环境监测、共享设备、农业传感无线连接（Wi-Fi/BLE/LoRa/NB-IoT）、电池供电、批量部署必须有 OTA 升级通道；低功耗协议（休眠—唤醒—上报）；设备身份与安全启动

维度三：按实时性要求分

就是 2.3 第 ⑤ 条那张表（硬实时 / 软实时 / 非实时）。在工程上它有一个非常实际的用法：把需求清单里的每一项功能，都标注上它的实时性等级。标完之后，代码该怎么组织几乎是自动浮现的——硬实时的部分交给中断或专用硬件（定时器、DMA），软实时的部分放进主循环的时间片，非实时的部分用「有空就做一点」的方式拆碎。

维度四：按有没有操作系统分

形态典型 RAM 占用适用场景开发方式
无操作系统（裸机 / 前后台） 几百字节到几 KB 功能不多、实时性要求靠中断就能满足、成本敏感 一个 while(1) + 中断服务函数；用标志位和时间戳做协作
RTOS
FreeRTOS / RT-Thread / µC/OS / Zephyr		 内核 5~8 KB 起，加上各任务栈通常 10 KB 以上 多功能并发、需要任务间同步与通信、有的功能要求微秒级确定响应 任务 + 优先级 + 信号量/队列/事件组；要算每个任务的栈
嵌入式 Linux / Android 几十 MB 起（需要外部 DDR） 复杂界面、网络协议栈、文件系统、多进程、需要跑现成的开源软件 内核 + 设备树 + 驱动 + 应用（C/C++/Python/Qt）；需要 Cortex-A 级 MPU

这三种形态不是「谁更高级」的关系，而是针对不同问题规模的三档工具。一个只测温度、转风扇的产品上 Linux，等于给自行车装飞机发动机——不但贵，还更难维护（启动要十几秒、断电容易损坏文件系统）。反过来，一个要接 4G 模块、跑 MQTT、还要显示图表的设备用裸机，会让你的主循环里塞满状态机，最后谁也不敢动。

2.5 典型芯片家族与定位

国内教学与项目里最常出现的四类「目标平台」。这张表的作用是让你在听到一个需求时，能立刻判断该往哪个方向选——后面第 4 节会用温控风扇这个实例，在三选一里走一遍完整的推理。

家族内核与典型资源定位优势它的局限（什么时候别选它）
51 系列
STC89C52 / STC15 / AT89C51		 8 位内核，典型 8~64 KB Flash、512 B~4 KB RAM，主频 12~35 MHz（传统 12T 模式下等效 1MHz 量级） 教学与超低成本：理解寄存器、时序、最小系统的经典载体 结构简单到可以逐条讲清楚；价格低到几毛钱；资料极多（中文教程最多） RAM 只有几百字节、外设少、没有硬件浮点、多数型号没有硬件调试口（只能串口下载）；做稍微复杂一点的功能就会「挤爆」
STM32
F0/F1/F4/H7、L 系列低功耗、G0/G4		 32 位 ARM Cortex-M0/M0+/M3/M4/M7，Flash 16 KB~2 MB，RAM 4 KB~1 MB，主频 48~480 MHz；M4/M7 带 FPU 与 DSP 指令 工业主流：从入门到高端全覆盖，生态与工具链最完整 HAL 库 + CubeMX 图形化配置 + 完整中文资料；型号谱系极宽，几乎任何需求都有对应型号；工业级温度范围与长期供货型号多 价格高于 51（常见 3~30 元）；HAL 库有一定体积与开销；没有内置无线，做物联网要外挂模组
ESP32
ESP32 / ESP32-S3 / ESP32-C3		 双核（或单核 RISC-V）240 MHz、SRAM 数百 KB、内置 Wi-Fi + 蓝牙、Flash 通常外挂 4 MB 起 物联网首选：需要无线的场合，一颗芯片全包 自带 Wi-Fi/蓝牙，省掉一颗模组和一堆调试；官方支持 FreeRTOS，能跑 ESP-IDF，也能用 Arduino 和 MicroPython 快速出原型；价格低（常见 10~25 元） 严格工业实时控制与车规场合不合适（外设与定时器精度、认证生态不如 STM32）；功耗对电池设备偏高；封装多为模块形式，做超小体积或超低成本产品不划算
MPU
Cortex-A：i.MX、全志、瑞芯微、树莓派方案		 32/64 位应用处理器，主频 1~2 GHz+，需外接 DDR 内存与 eMMC，带 MMU、常带 GPU 与显示/摄像头接口 需要完整操作系统与复杂人机界面的场合 能跑 Linux/Android，复用海量开源软件；支持大屏、摄像头、多路网络、文件系统 成本高（芯片 + DDR + eMMC + 电源管理，往往 50 元起）；启动慢（几秒到几十秒）；功耗高（几百 mW 到数瓦）；开发复杂；实时性差——普通 Linux 做不到微秒级确定响应，硬实时场合需要 PREEMPT_RT 或再配一颗 MCU
什么时候真的需要 MPU（Cortex-A + Linux）？

给三条硬判据，满足其中之一才考虑：

  1. 需要「跑别人写好的大软件」：完整的 TCP/IP + TLS + MQTT + Web 服务器、数据库、Python 脚本、Qt 图形界面。这些在 MCU 上不是不能做，而是工作量与维护成本会失控。
  2. 需要大内存与文件系统：要缓存几百 MB 的数据、要同时处理多路视频流、要频繁读写大量文件（日志、图片、录音）。MCU 加上外部 Flash 也做不到这个量级。
  3. 需要复杂的显示与交互：触摸屏、多窗口、动画、视频播放。MCU 能驱动小尺寸屏和简单 UI，但做不了「像手机一样」的界面。

反过来说：只要一个 MCU 能做完，就不要上 MPU。因为 MPU 带来的是「一整套系统工程」——内核、设备树、驱动、文件系统掉电保护、启动时间、散热。而工业上非常常见的一种方案是双芯：MPU 负责人机界面与联网，MCU 负责实时控制，两者用串口或 SPI 通信。各干各擅长的事，比强行让一颗芯片干两件事更可靠。

除了这四类，还会遇到：低功耗专用（TI MSP430、STM32L 系列、nRF52）、无线专用（LoRa 的 SX1278 方案、NB-IoT 模组、BLE 的 nRF 系列）、DSP/FPGA（需要做大量乘加运算或并行逻辑时）、RISC-V 新秀（如沁恒 CH32V、平头哥系列，性价比高、生态在成长中）。它们的定位都可以用同一套框架去理解：内核性能 + 存储容量 + 外设组合 + 生态与供货。

2.6 一颗 MCU 里到底有什么

现在把镜头拉近，看一颗单片机内部。你以后写的每一行固件，最终都要落到这张表里的某一项上。这张表建议你对照自己手上芯片的数据手册（Datasheet）和参考手册（Reference Manual）读一遍，你会发现原本抽象的「资源」二字变得非常具体。

部件它是什么软件里怎么用没有它会怎样
CPU 内核
Cortex-M3 等		 取指、译码、执行指令的单元，含通用寄存器、栈指针、程序计数器 你写的每一行 C 都会被翻译成它认识的指令；性能、位宽、有没有 FPU/DSP 都由它决定 ——（这是 MCU 的定义性部件）
Flash
程序存储器		 非易失存储器，断电不丢；存代码、常量、中断向量表 程序的「家」；容量决定你能写多少功能；擦写次数有限（1 万~10 万次），不适合当数据盘频繁写 掉电后程序就没了，得每次上电重新下载
SRAM
数据存储器		 易失存储器，读写快、掉电即失；存全局变量、栈、堆 最稀缺的资源；数组、缓冲区、每个任务的栈都从这里分配 没有地方放变量，程序无法运行
GPIO 通用输入输出引脚，可以配置为输入、输出、上拉/下拉、开漏/推挽，还能被复用给其他外设 点灯、读按键、驱动继电器、给出片选信号（CS）；做软件调试时也靠它翻转发波形 无法与外部世界做最简单的数字交互
定时器
TIM		 硬件计数器，可按预分频后的时钟计数，支持自动重载、比较输出、输入捕获、PWM、编码器模式 产生精确的时间基准（1 ms 心跳、PWM 调速、舵机控制）、测量脉宽与频率、给 DMA 做触发源 所有延时只能靠空转循环，精度和效率都会崩
串口
UART / SPI / I²C		 三类最常用的串行通信外设，分别适合「点对点异步」「高速同步多线」「两根线挂多个器件」 接传感器、显示屏、无线模组、上位机；UART 还是你最常用的调试输出通道 只能和芯片自己说话，无法接外设，也无法调试
ADC
模数转换器		 把模拟电压转成数字量，常见 10/12 位、多通道、支持规则与注入两组序列 读电位器、NTC 热敏电阻、电流采样、电池电压检测 无法感知连续变化的物理量，只能读开关量
DMA 直接存储器访问控制器：不经过 CPU，由硬件把数据在内存与外设之间搬运 ADC 连续采样、串口大批收发、内存到内存拷贝；把 CPU 从搬运里解放出来 每次传一个字节都要 CPU 参与，高速数据流会把 CPU 吃满
中断控制器
NVIC（Cortex-M）		 管理所有中断源：谁可以打断谁、优先级多少、挂起与清除 按键、串口接收、定时器溢出、ADC 转换完成都用它来「通知」CPU CPU 只能不停轮询每个外设，效率极低且响应慢
时钟树
RCC 与 PLL		 把外部晶振（如 8 MHz）通过锁相环倍频成系统时钟（如 72 MHz），再分频给各条总线与外设 系统初始化里必须最早配置；外设时钟不使能，寄存器写了也没反应（初学者第一大坑） 芯片没有心跳，所有时序都无从谈起
看门狗
IWDG / WWDG		 独立的递减计数器，到点没被「喂」就强制复位整个芯片 主循环里定期喂狗；是产品在现场「程序跑飞后自我恢复」的最后一道防线 程序一旦跑飞就永远卡死，现场只能靠人拔电

看完这张表，你会理解那句被反复说的话：一颗 MCU 就是一台完整的计算机。把它和 PC 对应起来看：

PC 里的角色MCU 里的对应物关键区别
CPUCPU 内核（Cortex-M3 等）位宽更窄、主频低两个数量级、没有 MMU
内存条（DRAM）片内 SRAM容量小 5~6 个数量级，但访问速度与内核同频，无需刷新
硬盘 / SSD片内 Flash代码与数据同处一块存储，可直接原地执行（XIP）；擦写次数有限
主板芯片组与各类扩展卡片上外设（定时器、串口、ADC、DMA……）不是插卡，而是同一块硅片上的电路，通过寄存器访问
主板晶振与时钟发生器时钟树（外部晶振 + PLL + 分频）要手动配置，且是初始化的第一步
操作系统可以没有；或者一个几 KB 的 RTOS没有 OS 时，「调度」由你的主循环和中断完成
BIOS / 引导程序启动文件 + 复位向量固定死在 Flash 开头，不可更换，只做最必要的初始化

所以在嵌入式里，你写的代码和硬件之间的距离，比在 PC 上近得多。在 PC 上你写的是「给操作系统的请求」，在 MCU 上你写的是「给一片硅片的命令」。

2.7 完整开发流程与每一步的产出物

一个嵌入式产品从想法到量产，走的是一条比「写代码」长得多的路。下面八步是通用骨架。请特别留意「产出物」这一列——工程能力的一个直接体现，就是每一步都能拿出一份可以给别人看、可以被检查的东西，而不是只存在于你的脑子里。

① 需求分析 把「做个温控风扇」拆成可验证的条目：测什么、测多准、控什么、控多快、怎么显示、怎么交互、供电方式、工作环境、成本上限、预期产量 需求规格说明书：每条需求都要能回答「怎么验证它满足了」。含验收测试清单 最贵的一步。需求漏一项，可能意味着重新选型、重画板子
② 芯片选型 按 2.8 的九项考量逐条打分，在 2~3 个候选里做决定；同时确认封装、引脚数、供货周期、是否有参考设计 选型对比表（含否决理由）+ 关键外设清单 选小了做不出来，选大了成本失控；选到缺货型号会直接延期几个月
③ 硬件设计 画原理图（电源、晶振、复位、下载接口、外设接口、保护电路）、分配引脚、画 PCB、出 BOM、打样贴片 原理图 + PCB + 引脚分配表 + BOM + 测试点定义 板子打回来发现引脚冲突或电源不够，就要重新投板（一周以上 + 打样费）
④ 软件设计 先写驱动（点灯、串口、定时器、ADC、显示屏），再写中间件（滤波、协议、状态机），最后写应用逻辑；同时定好软件架构（前后台还是时间片轮询） 分层清晰的代码 + 编译产物（hex/elf/map）+ 版本记录 架构没想清楚就开写，功能加到第三个时主循环会变成一团乱麻
⑤ 联调 把固件烧进真板子，用示波器/串口打印确认时序、用调试器确认变量，逐个功能点亮；解决「代码对但硬件不配合」的问题 联调记录：每个功能对应的实测数据（波形、串口日志、测量值） 跳过联调直接测试，会在测试阶段把硬件问题和软件问题混在一起查
⑥ 测试验证 功能测试（每条需求逐条过）、边界测试（0 ℃ / 上限温度 / 传感器断线 / 按键狂按）、长时间运行（老化 72 小时以上）、环境测试（高低温、湿度）、EMC（电磁兼容，辐射与抗扰度）、供电波动与掉电测试 测试报告：测试项、方法、实测值、判定结论、未通过项的处理 现场才暴露的缺陷，修复成本是实验室里的几十倍
⑦ 试产 小批量（几十到几百台）走完真实产线：贴片、烧录、校准、整机测试、包装；暴露「实验室里不会发生」的装配与一致性问题 生产工艺文件：烧录文件与步骤、校准流程、出厂测试项、不良品处理规则 量产时才发现某道工序做不了，会整批返工
⑧ 量产与维护 批量生产、出厂一致性抽检、现场问题跟踪、固件升级（OTA/IAP）、备件与版本管理、生命周期内的替代料评估 版本管理记录 + 升级通道 + 故障统计 + 变更记录 没有升级通道，一个软件 bug 就可能导致召回或整批报废

学生做课设通常只走 ④⑤ 两步（有时加一点 ③），这不奇怪——课设的目标是学会技术。但你要清楚企业里 ①③⑥⑦⑧ 花掉的时间和钱，往往比 ④ 多。这也是为什么面试官喜欢问「你这个项目的需求是什么、怎么验证的、如果量产你会改哪里」——他在问的其实是这张表。

动手算一遍

这一节有四道题，都来自真实项目里会遇到的判断。它们的共同特点是：答案不是「大概够用」，而是一个能写进选型报告的确定数字。请跟着算一遍，尤其是第 1 题和第 2 题——它们分别对应「芯片选小了」和「循环跑不完」这两种最常见的翻车方式。

开始前先约定三件事，后面所有题目都用它们：

  • 1 KB = 1024 字节（B），1 MB = 1024 KB。存储容量的换算用 1024，不用 1000（这一点和硬盘厂商的宣传口径不同）。
  • Flash 占用 = text + data，RAM 占用 = data + bss（2.3 节第 ③ 条那张数据流图的最后两行）。栈也在 RAM 里，别忘了算。
  • 时间 = 周期数 ÷ 主频。STM32F103 主频 72 MHz，也就是每秒 72×10⁶ 个时钟周期，一个周期约 13.9 ns。

例题 1：64 KB Flash / 20 KB RAM 的芯片，装得下这套功能吗？

题目。你要做一个带 OLED 显示的温控器，候选芯片是 STM32F103C8T6（64 KB Flash、20 KB RAM）。功能清单与实测/估算的资源占用如下：

功能项Flash 占用算它的依据
启动文件 + 中断向量表1.5 KB向量表 60 个中断项 × 4 B = 240 B，加启动代码与默认处理函数
HAL 库（只用到 GPIO / TIM / ADC / UART / I²C / RCC）8.0 KB实测：开了这 6 个模块的 HAL 源文件后 text 段的增量
OLED（SSD1306）驱动3.0 KB初始化序列 + 画点/画线/显示字符串
ASCII 字库 8×161.5 KB96 个可打印字符 × 16 B = 1536 B
中文字库 16×16（64 个常用字）2.0 KB64 字 × 32 B = 2048 B
printf（精简整型版）2.5 KB串口调试输出用；带浮点的完整版会到 8~10 KB
应用逻辑（状态机 + 按键 + 温控）3.5 KB约 1500 行 C，平均每行折合 2~3 B 机器码
NTC 温度查表（256 点）0.5 KB256 × 2 B = 512 B，放 Flash 的 const 区
滑动平均滤波 + 限幅0.7 KB定点实现的算法代码
合计23.2 KB

第一问：单分区方案够不够？

把算式写开：

  • 固件占用 = 23.2 KB
  • 参数存储区（保存目标温度、校准系数、运行时长）= 2 KB（2 个 Flash 页）
  • 总占用 = 23.2 + 2 = 25.2 KB
  • 剩余 = 64 − 25.2 = 38.8 KB，余量比例 = 38.8 ÷ 64 = 60.6%

按 2.8 的红线（至少留 30%），60.6% 远远够用。单分区方案通过。

第二问：但是你还想做 OTA 升级，需要 Bootloader + A/B 双分区，还够吗？

先把 Flash 分区画出来。STM32F103C8T6 的 Flash 按 1 KB 一页，共 64 页：

  地址          内容                     大小        说明
  0x08000000 ┌ Bootloader              8 KB       永不更新，只负责收固件、校验、烧写、切分区
  0x08002000 ├ 参数区（配置 + 升级标志） 2 KB      每次升级写一次，注意擦写次数
  0x08002800 ├ 分区 A（当前运行固件）    27 KB      27 页，装得下 23.2 KB 的固件
  0x08009400 └ 分区 B（新固件暂存）      27 KB      27 页，与 A 等大，A/B 必须对称
  0x08010000   越界（超出 64 KB）       ──         27+27+8+2 = 64 KB，刚好用尽，一点不剩

算式：

  • 可用于固件的空间 = 64 − 8（Bootloader）− 2（参数区）= 54 KB
  • A、B 必须等大，所以每个分区 = 54 ÷ 2 = 27 KB
  • 每个分区的余量 = 27 − 23.2 = 3.8 KB
  • 余量比例 = 3.8 ÷ 27 = 14.1%
结论：不满足

14.1% 远低于 30% 的余量红线。这意味着你做完 A/B 双分区之后，几乎没有空间再加功能、加调试打印、或者接受厂商库的版本更新。更危险的是：一旦某一版固件超过 27 KB，OTA 会在写分区时写到分区 B 之外，直接破坏别的区域。

正确做法有两个：① 换 Flash 更大的型号——STM32F103CBT6 是 128 KB Flash / 20 KB RAM，与 C8T6 引脚完全兼容（pin-to-pin），只有 Flash 容量不同；换成它以后每个分区的空间是 (128−8−2)÷2 = 59 KB，余量 (59−23.2)÷59 = 60.7%，完全达标。② 砍掉中文字库和 printf（省 4.5 KB），把固件压到 18.7 KB，此时余量 (27−18.7)÷27 = 30.7%，刚过线——但你就再也没有余量了。

这道题真正的教学点：64 KB 这个数字在「单分区裸机」时显得很宽裕（60% 余量），在做 OTA 时立刻变成不够。所以「要不要远程升级」这个需求必须在选型之前就定下来——它会直接把你的 Flash 需求翻一倍还多。

第三问：RAM 够不够？同一颗芯片有 20 KB SRAM。逐项算：

RAM 用途占用算它的依据
OLED 显存（1 bpp 全屏缓冲）1.0 KB128 × 64 ÷ 8 = 1024 B。没有它就只能整屏重画
ADC 采样缓冲（DMA 循环填充）0.5 KB256 个采样点 × 2 B（12 位结果用 uint16_t）
串口收发缓冲0.5 KB收 256 B + 发 256 B（中断方式，防止丢数据）
滤波滑动窗口0.125 KB32 个历史值 × 4 B（float）
温度历史记录（1 分钟）0.12 KB60 点 × 2 B
全局状态、标志、配置副本0.06 KB约 60 B 的零散变量
全局变量小计≈ 2.3 KB
主栈（链接脚本里的 _Min_Stack_Size）1.0 KB默认 0x400；所有函数调用、局部变量、中断嵌套都吃它
堆0 KB不用 malloc，堆设为 0
合计≈ 3.3 KB

算式：3.3 ÷ 20 = 16.5%，剩余 20 − 3.3 = 16.7 KB，余量 83.5%。RAM 非常宽裕。

把两个结论放在一起，你会看到一条很重要的经验：

Flash 和 RAM 是两笔独立的账，而且先见底的往往不是你以为的那个

这个项目里 Flash 占了 36%（单分区）到 86%（双分区），而 RAM 只占了 16.5%。原因很容易理解：字库、库函数、协议栈这些「代码和常量」全在 Flash 里，它们的体积随功能线性增长；而 RAM 里放的缓冲区是你自己定的，可以随时改小。所以做预算时，先把 Flash 算清楚（尤其是字库和 printf 这两个「隐形大户」），RAM 反而是后面可以调的空间——唯一不能随便调的是栈，它小了会以「随机重启」的形式报复你。

例题 2：这个控制循环，1 ms 跑得完吗？

题目。温控器的控制环要求每 1 ms 执行一次（通过定时器中断触发）。这段控制逻辑的指令数估算如下，主频 72 MHz。问：最坏情况下的执行时间是多少？能不能满足 1 ms 的周期？另外，OLED 刷新能不能也放进这 1 ms 里？

控制环内的步骤指令数（估算）估算依据
读 ADC 结果 + 换算为电压/电阻200含 32 位乘除、查表前的准备
一阶数字滤波（定点）40两次乘加 + 移位
NTC 查表 + 线性插值60比较查找 + 一次插值计算
PID 计算（整数实现）120三项各含一次乘加与限幅
写 PWM 比较寄存器 + 更新状态30寄存器写入与标志位
更新显示缓冲与历史记录150数组搬运与格式化
合计600 条指令

第一步：把指令数换成时钟周期数。Cortex-M3 是流水线内核，大部分简单指令 1 个周期完成，但有三类开销要算进去：

  • Flash 取指等待：代码在 Flash 里执行，而 Flash 的访问速度慢于 72 MHz 的内核，需要插入等待周期（STM32F103 在 48~72 MHz 时通常配 2 个等待周期，配合预取缓冲可部分掩盖）。
  • 分支与流水线冲刷：条件跳转、函数调用的开销高于 1 个周期。
  • 多周期指令：32 位除法在 Cortex-M3 上要 2~12 个周期，浮点运算在这颗没有 FPU 的芯片上要靠软件库，一条浮点乘法可能就要几十个周期。

工程上常用的简化假设是平均每条指令折合 1.5 个时钟周期（如果代码里大量使用浮点，这个系数要放大到 5 以上）。取 1.5：

  • 所需周期数 = 600 × 1.5 = 900 个周期
  • 所需时间 = 900 ÷ (72 × 10⁶) 秒 = 12.5 × 10⁻⁶ 秒 = 12.5 µs

第二步：和周期比。

  • 控制周期 = 1 ms = 1000 µs
  • CPU 占用率 = 12.5 ÷ 1000 = 1.25%

结论：远远满足。12.5 µs 只占 1 ms 的 1.25%，剩下的 987.5 µs 都归主循环用。你可以放心地把这个控制环放进定时器中断里，它会非常稳定。

第三步（关键）：换一个主频再算一次，看看安全感从哪来。如果你忘了配置 PLL，芯片以内部 8 MHz RC 振荡器运行（很多初学者「点灯成功但串口乱码」就是这个原因）：

  • 所需时间 = 900 ÷ (8 × 10⁶) = 112.5 µs，是 72 MHz 时的 9 倍
  • 占用率 = 112.5 ÷ 1000 = 11.25%

11.25% 仍然满足 1 ms 周期。所以这道题给出的余量很大——但请注意：这是「600 条指令」的结果。如果控制算法改用浮点（没有 FPU 时要调软件浮点库），每条浮点运算按 40~100 个周期算，只要环里有 20 次浮点操作，就会额外增加 20 × 70 = 1400 个周期，也就是 19.4 µs，直接翻倍还多。这就是为什么数字控制里，「用定点还是用浮点」是一个非常具体的性能决策，而不是风格偏好。

第四步：OLED 刷新能不能也塞进这 1 ms？算一下就知道不行。OLED 用的是 I²C，速率 400 kHz，全屏刷新要发 1024 B 显存：

  • 每个字节在 I²C 上要 8 位数据 + 1 位应答 = 9 个时钟
  • 总时钟数 = 1024 × 9 = 9216 个
  • 传输时间 = 9216 ÷ (400 × 10³) = 23.04 × 10⁻³ 秒 = 23 ms

也就是说，刷一帧全屏的时间是 23 ms，是控制周期的 23 倍。如果把它整段塞进 1 ms 的时间片，这一个时间片会被拉长到 23 ms，其他所有事情（按键、串口、控制环）全部延迟 23 ms——按键会明显迟钝，人一眼就能看出来。

正确的做法：把长任务切成片

把 1024 B 分成 23 份，每份约 45 B，在每个 1 ms 的时间片里只发一份：

  • 每个时间片花在显示上的时间 = 45 × 9 ÷ 400000 = 1.01 ms……等等，这已经超过 1 ms 了。
  • 那就再切细一点：每片只发 16 B，耗时 16 × 9 ÷ 400000 = 0.36 ms（占时间片 36%），一帧需要 1024 ÷ 16 = 64 个时间片 = 64 ms，也就是每秒刷新约 15 帧。

15 fps 对显示温度数字来说完全够用（人眼看数字变化根本察觉不到）。如果你想要更快的刷新，就不是改软件而是改硬件了：换 SPI 接口的屏（STM32 的硬件 SPI 可以跑到 18 MHz，整屏 1024 B × 8 位 ÷ 18 MHz ≈ 0.46 ms，一次就能刷完），或者干脆用 DMA 把显示数据搬出去，让 CPU 完全不参与。

这道题的教学点是：「算一遍」能立刻把「感觉应该行」变成「知道行不行、余量多少」。上面这两个结论——控制环 12.5 µs 用 1.25%、显示必须切片——就是时间片轮询架构的全部依据（第 4 节会把它写成代码）。

例题 3：改用 RTOS 之后，RAM 要多吃多少？

题目。还是那颗 20 KB RAM 的芯片。你的裸机版本占 3.3 KB RAM（例题 1 第三问）。现在考虑改用 FreeRTOS，把功能拆成 5 个任务。问：RAM 总占用变成多少？还剩下多少余量？

先记两个前提：Cortex-M3 上一个 StackType_t 是 4 字节，所以任务栈的深度单位是「字（word）」，1 word = 4 B；FreeRTOS 里的 configMINIMAL_STACK_SIZE 常见配置是 128 words = 512 B。

开销项数量 / 深度RAM 占用说明
控制任务栈256 words1024 B含 PID 的定点运算与函数调用
显示任务栈256 words1024 B驱动内部有较深的调用层次，栈要留宽
按键任务栈128 words512 B逻辑简单，等于最小栈
通信任务栈192 words768 B要组包、算校验
记录任务栈128 words512 B周期性写 Flash 参数
空闲任务栈（IDLE）128 words512 B调度器自动创建，不能不建
定时器服务任务栈（Tmr Svc）256 words1024 B用了软件定时器就必须有；不用可关掉省下这 1 KB
任务栈小计5376 B1024+1024+512+768+512+512+1024

注意：在 FreeRTOS 里，上面这些栈、TCB、队列都是从内核堆（ucHeap）里分配的，所以 configTOTAL_HEAP_SIZE 至少要设成 6420 B（实际建议设 8 KB 留出余量），这 8 KB 就是 RAM 里的一个静态数组 ucHeap[]。

再算总账：

  • 裸机版本：全局缓冲区 2.3 KB + 主栈 1.0 KB = 3.3 KB（占 20 KB 的 16.5%）
  • RTOS 版本：应用全局缓冲区 2.3 KB（各任务的栈已单列，不再共用那 1 KB 主栈）+ 内核堆 8 KB = 10.3 KB（占 51.5%）
  • 多出来的部分 = 10.3 − 3.3 = 7.0 KB，正好是「把一份栈拆成七份 + 内核数据结构」的代价
结论：还算得过来，但余量从 83.5% 掉到 48.5%

20 KB 的芯片跑这个 RTOS 方案是可行的，但你只剩不到一半 RAM。如果当初为了省钱选了只有 10 KB RAM 的型号（比如一些 Cortex-M0 的入门片），这个方案会直接装不下——这也说明「上 RTOS」不是免费的架构升级，它在选型阶段就要算进去。

关于栈大小的两个实用建议：① 栈不能凭感觉填。先把每个任务的栈设得偏大（比如都先给 256 words），跑通全部功能后调用 FreeRTOS 的 uxTaskGetStackHighWaterMark()，它会告诉你这个任务历史上最多用掉了多少栈；再按实测峰值留 30%~50% 余量收回去。② 经验参考值：只做算术和简单调用的任务 128 words 起；任务里用到 printf、浮点运算、或者调用层次较深的驱动库（如文件系统、图形库）时，栈要 256~512 words 起——这些函数内部会吃掉大量栈空间，是栈溢出最主要的来源。

例题 4：便宜芯片省下来的钱，够不够抵消多花的开发时间？

题目。同一个温控器产品，要在两种方案里做决定。年产量按一万台估。

  • 方案 A（STM32F103C8T6）：芯片 6.0 元；生态成熟，驱动与算法示例现成，开发工作量 3 人月。
  • 方案 B（STC89C52，8 位 51）：芯片 2.0 元；RAM 只有 512 B（塞不下 OLED 显存 1 KB），没有硬件 I²C 与硬件浮点，PID 要自己写成定点、显示要自己写分页刷屏逻辑，开发工作量 5 人月。
  • 两方案共有的部分：传感器、显示屏、风扇与驱动、结构件、电源等，单台 34.5 元。
  • 差异部分（A：晶振 + LDO + 复位电路 + PCB = 3.7 元；B：对应 1.3 元 + PCB 3.0 元 = 4.3 元）。
  • 人力成本按 1.5 万元 / 人月 计；认证与测试费用两方案都按 3.0 万元 计。

第一步：算单台 BOM。

  • 方案 A 的 MCU 周边 = 6.0（芯片）+ 0.7（晶振/LDO/复位）+ 3.0（PCB）= 9.7 元
  • 方案 B 的 MCU 周边 = 2.0（芯片）+ 0.3（晶振/复位）+ 3.0（PCB）= 5.3 元
  • 单台总 BOM：A = 34.5 + 9.7 = 44.2 元；B = 34.5 + 5.3 = 39.8 元
  • 单台 BOM 差额 = 44.2 − 39.8 = 4.4 元（方案 B 便宜）

第二步：算一次性成本（开发人力 + 认证测试）。

  • 方案 A：3 × 1.5 = 4.5 万元人力 + 3.0 万元认证 = 7.5 万元
  • 方案 B：5 × 1.5 = 7.5 万元人力 + 3.0 万元认证 = 10.5 万元
  • 一次性成本差额 = 10.5 − 7.5 = 3.0 万元（方案 A 便宜）

第三步：按一万台算总账。

  • 方案 A：44.2 × 10000 + 75000 = 442000 + 75000 = 517,000 元，折合单台 51.7 元
  • 方案 B：39.8 × 10000 + 105000 = 398000 + 105000 = 503,000 元，折合单台 50.3 元
  • 差额 = 517000 − 503000 = 1.4 万元，单台差 1.4 元（方案 B 略便宜，约 2.7%）

第四步：找盈亏平衡点——换个产量，答案会不会翻转？设产量为 N 台，令两方案总成本相等：

  • 44.2 × N + 75000 = 39.8 × N + 105000
  • 移项：(44.2 − 39.8) × N = 105000 − 75000
  • 4.4 × N = 30000
  • N = 30000 ÷ 4.4 = 6818 台

在 1000 台的规模上，方案 A（贵芯片 + 省人力）反而比方案 B 便宜 25.6 元/台，总成本少 2.6 万元。这就是为什么很多小批量、定制化的产品宁愿用贵一点的平台——省下来的两个月开发时间，比芯片差价值钱。

到了一万台，两者的成本只差 2.7%，而这时候决定性的因素已经不再是成本，而是方案 B 根本做不到的事情：

  • 512 B RAM 装不下 1 KB 的 OLED 显存，只能用「分页刷屏 + 边算边写」的写法，界面稍微复杂一点就写不动；
  • 没有 OTA 升级通道（8 KB Flash 连 Bootloader 都装不下），出厂后发现问题只能召回；
  • 没有硬件调试口，现场问题无法用调试器定位，只能靠串口打印猜；
  • 后续要加 WiFi 上报、要加数据记录、要改成 PID 自整定，每一样都要重写算法。

所以这个项目的正确结论是：选方案 A。而且你答辩时可以说得非常具体：「在年产量一万台的假设下，两颗芯片的总成本差 2.7%（1.4 元/台）；但 51 方案的 512 B RAM 装不下 OLED 显存，且无法实现 OTA，因此否决。」——这就是 2.8 那张选型表要你写出来的东西。

三条否决理由（这就是答辩时要说的答案）

① 51 出局：RAM 只有 512 B，而 OLED 的显存就需要 1 KB。这不是「优化一下能过」的问题，是物理上装不下——只能改成不做显存、边算边分页刷屏，界面稍复杂一点就写不动。另外它没有硬件 I²C，软件模拟 I²C 会占用大量 CPU 时间，与本项目 1 ms 的控制周期冲突；它也没有硬件调试口，R9（72 小时老化）出问题时无法定位。

② ESP32 出局（本项目）：需求里没有任何一条需要无线，而它比 STM32 贵约 10 元（10000 台就是 10 万元），峰值电流 300 mA 需要重新设计电源，模块尺寸也更大。但请注意这条否决是有条件的——只要需求里加上一条「手机能查看温度」，整个结论立刻翻转，ESP32 会变成最优解（自带 Wi-Fi 省掉一个模组，还省掉调试无线的时间）。选型结论永远依赖于需求，这就是为什么需求要先定。

③ STM32 另一个候选被成本否决：STM32F030F4P6（TSSOP20，约 3 元）虽然更便宜、更小，但只有 16 KB Flash。而例题 1 算过，这套功能的固件是 23.2 KB——16 < 23.2，装不下，直接出局，连讨论功耗的必要都没有。这就是「先算账再选型」的价值：它能在五分钟内砍掉一个看起来更划算的选项。

纯前后台
超级循环		 while(1) 里顺序做所有事：读温度、刷显示、扫按键；紧急事件用中断 直接违反 R4。OLED 全屏刷新要 23 ms（例题 2 算过），这 23 ms 里按键完全没人管；人按一下按键的持续时间约 50~100 ms，会出现「按了没反应」。而且温度采样周期随代码改动而漂移（加一行代码，采样率就变了），R1 的「1 s 刷新」也无法保证 否决
全部放进中断 显示刷新、控制、按键全都写在中断服务函数里 更糟。在中断里做 23 ms 的 I²C 传输，会让 1 ms 的控制定时器中断被推迟到几十毫秒之后，控制环的抖动巨大，R2/R5 全部失控；而且中断函数的栈开销叠加，RAM 账要重算 否决
时间片轮询 1 ms 定时器中断只做一件事：给全局 g_tick_ms 加一。主循环按「周期表」检查每个任务是否到点，到点执行一次，长任务切片 每个任务的执行频率由周期表写死，不再随代码而漂移；最慢的任务（显示切片 0.36 ms）也小于 1 ms 时间片，不会拖累别人；RAM 额外开销为 0；不需要学 RTOS 的同步原语 选中
RTOS 拆成 5 个任务，用信号量和队列通信 能力过剩。本项目只有 6 个周期任务，任务间数据流是单向的（传感器 → 控制 → 显示），没有需要复杂同步的场景；而按例题 3 的账，引入 FreeRTOS 会让 RAM 占用从 3.4 KB 涨到 10 KB 以上 留到以后

选定架构之后，把它落成一张时间片调度表。这张表是软件设计的核心产出物，它同时也是「例题 2 那道时间账」的摊开版本：

时间片轮询的三条铁律
  1. 主循环里不许出现任何阻塞延时。HAL_Delay(100)、while(!flag); 这类写法会把整个调度表毁掉。所有「等一会儿再做」都要写成「记录一个时刻，到点再做」（下一小节的代码里有一个 time_reached() 函数专干这件事）。
  2. 每个任务的耗时必须算过，且明显小于自己的周期。本例中显示任务耗 360 µs、周期 1 ms，占比 36%，是安全的；如果哪天有人把屏幕换成 2.4 寸彩屏（一帧要几百 KB），这条架构会立刻崩溃——那时候就该换 SPI + DMA，而不是硬扛。
  3. 中断里只做「搬数据」和「置标志」，不做运算，更不做通信。中断服务函数的执行时间应该是几十微秒量级；把解析协议、算 PID 这类事情留给主循环。

顺带说清「以后什么情况下该换成 RTOS」：当出现① 任务数量增长到十几个、周期表开始互相打架；② 需要「一个任务等另一个任务的数据」（生产者—消费者）；③ 需要优先级抢占（某个任务必须在 50 µs 内响应，而它不能被别的任务挡在后面）这三种情况之一时，就是升级的时机。本项目三条都不满足，所以时间片轮询是正确选择——这就是 2.3 第 ④ 条那条判断线在真实项目里的样子。

4.5 交叉编译与链接的完整命令行

这一小节是 2.3 第 ③ 条那张数据流图的「可执行版本」。下面这些命令你可以原样复制去用（前提是把工具链 arm-none-eabi-gcc 装好并加进 PATH；Windows 上通常由 STM32CubeIDE 或 ARM 官方工具链安装包提供）。

这次我们把五步都写全：编译 → 链接 → 转换 → 称重 → 烧录。请注意每一步的注释，它们解释的是「为什么要有这个参数」，而不是「这个参数是什么意思」——后者你可以查手册，前者才是经验。

# ============================================================
#  温控风扇固件构建脚本（目标：STM32F103C8T6，72 MHz）
#  工具链：arm-none-eabi-gcc（交叉编译器，跑在你的电脑上，产出 ARM 机器码）
# ============================================================

# ---------- 0. 定义工具链前缀与公共编译参数 ----------
TC=arm-none-eabi

CFLAGS="-mcpu=cortex-m3 -mthumb -O2 -g3 -gdwarf-2 \
        -ffunction-sections -fdata-sections -Wall -Wextra \
        -DSTM32F103xB \
        -ICore/Inc \
        -IDrivers/STM32F1xx_HAL_Driver/Inc \
        -IDrivers/CMSIS/Device/ST/STM32F1xx/Include \
        -IDrivers/CMSIS/Include"

#  -mcpu=cortex-m3       目标内核：告诉编译器「哪些指令可以用」
#  -mthumb               使用 Thumb 指令集（16/32 位混合），比全 32 位编码省约 30% Flash
#  -O2                   优化级别：调试期用 -O0（变量不被优化掉，好打断点），
#                        空间紧张时用 -Os，追求性能用 -O2 / -O3
#  -g3 -gdwarf-2         生成调试信息，供 gdb 与 IDE 显示源码行、变量名
#  -ffunction-sections -fdata-sections
#                        让每个函数、每个变量各自成为一个独立的段，
#                        这样链接器才能逐个丢弃「没被引用到」的段（配合第 2 步的 --gc-sections）
#  -Wall -Wextra         打开全部常用警告。嵌入式的警告基本都该当错误看：
#                        一个「可能未初始化」的警告，在 PC 上可能只是打印乱码，
#                        在这里可能是一个随机动作的继电器
#  -DSTM32F103xB         宏定义：告诉 CMSIS 头文件这是 F103 中容量产品（64/128 KB Flash）
#  -I...                 头文件搜索路径

# ---------- 1. 编译：每个 .c 单独编成一个 .o ----------
#  注意最后一行：汇编文件（.s）也用 gcc 驱动，它会自动调用汇编器 as
$TC-gcc $CFLAGS -c Core/Src/main.c          -o build/main.o
$TC-gcc $CFLAGS -c Core/Src/fan.c           -o build/fan.o
$TC-gcc $CFLAGS -c Core/Src/oled.c          -o build/oled.o
$TC-gcc $CFLAGS -c Core/Src/ntc.c           -o build/ntc.o
$TC-gcc $CFLAGS -c Core/Src/key.c           -o build/key.o
$TC-gcc $CFLAGS -c Core/Src/stm32f1xx_it.c  -o build/it.o
$TC-gcc $CFLAGS -c Core/Startup/startup_stm32f103xb.s -o build/startup.o

# ---------- 2. 链接：按链接脚本把 .o 排进 Flash 与 RAM ----------
#  这是整个流程里最「嵌入式」的一步：PC 上链接器只要把程序拼成一个文件，
#  而在这里它必须知道每一样东西将来住在哪个物理地址。
#
#  -T stm32f103c8t6.ld     链接脚本：声明 Flash 从 0x08000000 起 64 KB、
#                          RAM 从 0x20000000 起 20 KB，并规定
#                          .isr_vector / .text / .data / .bss / .stack 各放在哪里
#  -Wl,-Map=build/firmware.map
#                          生成 map 文件：每个函数、每个变量最终占了多少字节、
#                          被放在哪个地址，一查便知（排查「谁把 Flash 吃掉了」靠它）
#  -Wl,--gc-sections       删除没有被引用到的段（必须配合第 0 步的两个 -f...-sections）
#  -Wl,--print-memory-usage  链接完直接打印 Flash / RAM 的占用百分比
#  --specs=nano.specs      用精简版 C 库 newlib-nano，printf 的体积大幅缩小
#  --specs=nosys.specs     不链接需要操作系统的系统调用（裸机没有 read/write/sbrk）
$TC-gcc -mcpu=cortex-m3 -mthumb \
        -T stm32f103c8t6.ld \
        -Wl,-Map=build/firmware.map \
        -Wl,--gc-sections \
        -Wl,--print-memory-usage \
        --specs=nano.specs --specs=nosys.specs \
        build/startup.o build/main.o build/fan.o build/oled.o \
        build/ntc.o build/key.o build/it.o \
        -o build/firmware.elf

# 链接成功时你会看到这样的输出（--print-memory-usage 的功劳）：
#   Memory region         Used Size  Region Size  %age Used
#              FLASH:      23828 B        64 KB     36.36%
#                RAM:       2472 B        20 KB     12.07%
#  注意：这里的 RAM 数字不含栈，栈是在链接脚本里用 _estack 定位的，要自己加上去

# ---------- 3. 转换：elf 转成烧录器认识的格式 ----------
#  .elf 里有调试符号和段信息，体积大且不能直接烧；两种常用输出：
$TC-objcopy -O ihex   build/firmware.elf build/firmware.hex   # Intel HEX：带地址信息
$TC-objcopy -O binary build/firmware.elf build/firmware.bin   # 纯二进制：从 0x08000000 起

# ---------- 4. 称重：读出各段大小，和例题 1 的预算对账 ----------
$TC-size build/firmware.elf
#    text    data     bss     dec     hex   filename
#   23716     112    2360   26188    664c   firmware.elf
#
#  Flash 占用 = text + data = 23716 + 112 = 23828 B = 23.27 KB
#               （例题 1 的预算：23.2 KB —— 吻合，误差来自代码里多写的自检部分）
#  RAM   占用 = data + bss  =   112 + 2360 =  2472 B =  2.41 KB
#               再加上链接脚本里的主栈 1 KB = 3.41 KB
#               （例题 1 第三问的预算：3.3 KB —— 多出的 0.1 KB 来自对齐与临时缓冲）

$TC-size -A build/firmware.elf
#   -A 参数会分段列出，能看出哪一段是大头（本项目里是 HAL 库与字库），
#   这是「Flash 快满了该砍谁」时最先敲的一条命令

# 想更细地知道「哪个函数最占地方」，用：
$TC-nm --size-sort --print-size build/firmware.elf | tail -20

# ---------- 5. 烧录 ----------
st-flash write build/firmware.hex 0x08000000
#  或者用 OpenOCD（同一套硬件，不同的命令）：
#  openocd -f interface/stlink.cfg -f target/stm32f1x.cfg \
#          -c "program build/firmware.elf verify reset exit"
#  也可以直接用 IDE 的「下载」按钮——它内部跑的就是上面这一整套
三个最容易出错的地方

① 用了宿主机（x86）的编译器。如果输出里出现「文件格式无法识别」或者烧进去完全不跑，先确认你敲的是 arm-none-eabi-gcc 而不是 gcc。用 arm-none-eabi-gcc -v 可以看到它的 target 字段确实是 arm-none-eabi。

② 忘了 -T 链接脚本。没有它，链接器会用宿主机默认的地址布局（比如从 0x00000000 或某个 Linux 地址开始排段），生成的固件地址全是错的。表现是「烧录成功后芯片毫无反应」，或者调试器一运行就跳进 HardFault。

③ --specs=nosys.specs 忘了加。裸机上没有操作系统，C 库默认会去找 _write、_sbrk 这些系统调用，链接时会报一堆 undefined reference to _exit 之类的错误。报这种错不是你的代码错了，是链接参数少了一行。

4.6 从复位向量到 main：芯片上电后到底发生了什么

这是「没有操作系统的日子」最具体的体现。PC 上双击一个 exe，是操作系统帮你把它读进内存、建好进程、跳到入口；单片机上没有这个角色，所以从「复位」到「你的 main」之间那段路，是被一段汇编代码铺出来的。那段代码就在工程里的 startup_stm32f103xb.s。

  上电 / 按下复位键 / 看门狗超时
        │
        │ ① 硬件取向量表：Cortex-M 规定，复位后从地址 0x00000000 起读两个 32 位字
        │    · 第 0 个字 → 装入 SP（主栈指针寄存器）
        │    · 第 1 个字 → 装入 PC（程序计数器），也就是跳过去执行
        │    STM32 把 Flash 起始地址 0x08000000 映射到 0x00000000，
        │    所以向量表其实就在 Flash 的最开头，由链接脚本里 .isr_vector 段保证
        ▼
  Reset_Handler                      （startup_stm32f103xb.s，一段汇编）
        │
        │ ② 初始化时钟：调用 SystemInit()
        │    · 使能外部 8 MHz 晶振（HSE）
        │    · 启动 PLL：8 MHz × 9 = 72 MHz，并把系统时钟切过去
        │    · 设置 Flash 等待周期（72 MHz 下必须插 2 个等待周期，否则取指出错）
        │    ★ 这一步不做或做错，后面所有延时和串口波特率都会偏，
        │      典型症状：「点灯正常，但串口全是乱码」
        ▼
        │ ③ 搬运 .data 段：把有初值的全局变量从 Flash 拷贝到 RAM
        │    （因为这些变量的「初值」烧在 Flash 里，但运行时要住在 RAM）
        │ ④ 清零 .bss 段：把没有初值的全局变量在 RAM 里全部写 0
        │    ★ 这两步不做，全局变量的值就是随机垃圾 —— 表现为「有些板子正常、有些板子疯跑」
        │ ⑤（C++ 项目）调用 __libc_init_array() 运行全局对象的构造函数
        ▼
  main()                             （终于轮到你写的代码了）
        │
        │ ⑥ HAL_Init()：初始化 Flash 预取与等待周期、把 SysTick 配成 1 ms 中断、
        │    设置 NVIC 优先级分组（HAL 默认分组 4，全部 4 位都给抢占优先级）
        │ ⑦ SystemClock_Config()：CubeMX 生成的时钟树配置（HSE + PLL = 72 MHz）
        │ ⑧ 初始化外设：GPIO → DMA → ADC1 → TIM3(PWM) → I2C1 → USART1
        │    ★ 顺序不能乱：DMA 必须在 ADC 之前配好，否则 ADC 的 DMA 请求没有响应者
        │ ⑨ 应用级初始化：oled_init()、读回掉电保存的目标温度、启动看门狗
        ▼
  for (;;) { 时间片调度循环 }          （永不返回）
        │
        └─ 若中途跑飞：看门狗超时 → 硬件自动复位 → 回到最上面 ①

理解这张图能解释三个非常常见的现象：

  • 「为什么我 main 里的第一行断点一直停不住？」——因为程序根本没走到 main，卡在 SystemInit 里了（最常见的原因是晶振没起振，而代码却死等 HSE 就绪标志）。排查方法：在 Reset_Handler 里下断点，然后单步跟下去。
  • 「为什么全局变量的初值有时对、有时不对？」——多半是自己的链接脚本没把 .data 的搬运地址写对，或者启动文件里那段拷贝循环的边界写错。
  • 「为什么加了看门狗之后板子反复重启？」——喂狗必须在主循环里完成。如果某个任务卡住导致主循环转不动，看门狗就该复位——这正是它存在的意义（而不是把喂狗挪进中断去「让它别复位」）。

4.7 可编译的最小框架代码

下面这段代码就是 4.4 那张调度表的直接翻译。它的重点是「结构」而不是「功能」：所有驱动函数（写 PWM、读按键、刷 OLED）都只留了声明，你要用自己的实现去填。请对照注释逐段读——尤其是 time_reached() 和主循环里那几行调度。

/* ============================================================
 *  温控风扇 · 时间片轮询最小框架
 *  目标：STM32F103C8T6 @ 72 MHz，SysTick 每 1 ms 中断一次
 *  要点：主循环里没有任何阻塞延时，所有「等待」都用时间戳比较实现
 * ============================================================ */
#include <stdint.h>
#include "stm32f1xx_hal.h"        /* 厂商 HAL；也可以换成自己写的寄存器定义 */

/* ---------- 其它文件里实现的驱动函数（这里只声明，便于对照阅读） ---------- */
void     fan_set_duty(uint8_t pct);                     /* fan.c  : 写 TIM3 的 CCR1 */
void     oled_init(void);                               /* oled.c : SSD1306 初始化 */
void     oled_flush_slice(uint8_t idx, uint8_t len);    /* oled.c : 只发第 idx 片 */
uint8_t  key_read(uint8_t idx);                         /* key.c  : 0 = 按下，1 = 松开 */
void     key_on_press(uint8_t idx);                     /* app.c  : 按键语义处理 */
void     iwdg_start(void);                              /* wdg.c  : 看门狗，超时 2 s */
void     iwdg_feed(void);                               /* wdg.c  : 喂狗 */
uint16_t flash_load_target(void);                       /* param.c: 读回掉电保存的目标温度 */
void     system_self_check(void);                       /* app.c  : 传感器断线等自检 */

static void task_ctrl(void);
static void task_key(void);
static void task_sample(void);
static void task_disp(void);
static void task_uart(void);

/* ---------- 1. 系统心跳：由 SysTick 中断每 1 ms 累加一次 ---------- */
static volatile uint32_t g_tick_ms = 0;   /* volatile 必须有：中断里改、主循环里读，
                                             不加的话编译器可能把它优化成「只读一次」 */

void SysTick_Handler(void)                /* 每 1 ms 被硬件自动调用一次 */
{
    g_tick_ms++;                          /* 中断里只做这一件事，越快越好 */
}

/* 无阻塞延时：判断「到点了吗」，而不是「死等到点」。
   用无符号减法做比较，可以天然处理 32 位计数器的回绕（约 49.7 天一次）。 */
static inline uint8_t time_reached(uint32_t now, uint32_t due)
{
    return (uint8_t)((int32_t)(now - due) >= 0);
}

/* ---------- 2. 任务周期表：整个架构的核心，也是 4.4 那张表的代码版 ---------- */
enum { TASK_CTRL = 0, TASK_KEY, TASK_SAMPLE, TASK_DISP, TASK_UART, TASK_SLOW, TASK_COUNT };

static const uint16_t k_period_ms[TASK_COUNT] = {
    1,      /* TASK_CTRL  : 控制环。例题 2 算过：耗时 12.5 µs，占 1.25% */
    5,      /* TASK_KEY   : 按键扫描（连续 4 次一致才认定，即 20 ms 消抖） */
    20,     /* TASK_SAMPLE: 温度采样与滤波。NTC 热惯性大，用不着更快 */
    1,      /* TASK_DISP  : 显示分片。每片 16 B 约 360 µs，64 片 = 64 ms 一帧 */
    100,    /* TASK_UART  : 串口上报（调试与验收用） */
    1000    /* TASK_SLOW  : 喂狗、自检、参数落盘 */
};

/* ---------- 3. 全局状态（全部用整数，避免在这个项目里引入浮点） ---------- */
static uint16_t g_temp_c10   = 250;    /* 当前温度 ×10，250 表示 25.0 ℃ */
static uint16_t g_target_c10 = 300;    /* 目标温度 ×10，可按键修改、掉电保存 */
static uint8_t  g_fan_pct    = 0;      /* 风扇占空比 0~100 */

/* ---------- 4. 各任务的实现 ---------- */

/* 4.1 控制环：整数 PI + 滞回，1 ms 一次 */
static void task_ctrl(void)
{
    static int32_t integ = 0;                              /* 积分累加器 */
    int32_t err = (int32_t)g_target_c10 - (int32_t)g_temp_c10;

    /* 滞回：误差在 ±1.0 ℃ 以内就不调整，避免风扇在目标温度附近来回变速
       （这一条直接对应需求 R5「低噪声」） */
    if (err > 10 || err < -10) {
        integ += err;                                      /* 累加误差 */
        if (integ > 4000) integ = 4000;                    /* 积分限幅：防止饱和后回调迟钝 */
        if (integ < 0)    integ = 0;                       /* 风扇只能正转，积分不允许为负 */

        int32_t out = err * 2 + integ / 20;                /* 纯整数 PI：比例 + 积分 */
        if (out < 0)   out = 0;
        if (out > 100) out = 100;                          /* 输出限幅到 0~100% */

        g_fan_pct = (uint8_t)out;
        fan_set_duty(g_fan_pct);                           /* 内部写 TIM3 的 CCR1 寄存器 */
    }
}

/* 4.2 按键扫描：状态机消抖，绝不用 HAL_Delay */
static void task_key(void)
{
    static uint8_t  stable[3]   = {1, 1, 1};   /* 稳定电平：1 = 松开（引脚上拉） */
    static uint8_t  count[3]    = {0, 0, 0};   /* 连续读到不同电平的次数 */
    static uint32_t press_ms[3] = {0, 0, 0};   /* 按下时刻，给长按判断用 */

    for (uint8_t i = 0; i < 3; i++) {
        uint8_t raw = key_read(i);             /* 读 GPIO：按下为 0 */
        if (raw == stable[i]) {
            count[i] = 0;                      /* 电平没变，计数清零 */
            continue;
        }
        if (++count[i] >= 4) {                 /* 连续 4 次（5 ms × 4 = 20 ms）都不同 → 认定 */
            stable[i] = raw;
            count[i]  = 0;
            if (raw == 0) {                    /* 按下沿 */
                press_ms[i] = g_tick_ms;
                key_on_press(i);               /* 交给应用层：改目标温度 / 保存参数 */
            }
        }
    }
}

/* 4.3 温度采样：读 DMA 缓冲、平均、查表插值 */
static void task_sample(void)
{
    /* adc_dma_buf 由 DMA 在后台循环填充，这里只取最新的 32 个点做平均。
       注意：读之前要先停 DMA 或用双缓冲，否则可能读到「半新半旧」的数组，
       这是嵌入式里非常经典的隐蔽 bug（数据看起来会周期性跳动）。 */
    uint32_t sum = 0;
    for (uint8_t i = 0; i < 32; i++) sum += adc_dma_buf[i];
    uint16_t adc = (uint16_t)(sum / 32);

    /* 查表 + 线性插值把 ADC 值换成温度，全程整数运算（×10 保存一位小数） */
    g_temp_c10 = ntc_adc_to_temp_c10(adc);

    /* 把最新温度放进显存对应的位置，供显示任务分片发送 */
    oled_set_temp(g_temp_c10, g_target_c10, g_fan_pct);
}

/* 4.4 显示分片：把 23 ms 的全屏刷新切成 64 片，每毫秒发一片 */
static void task_disp(void)
{
    static uint8_t slice = 0;
    oled_flush_slice(slice, 16);               /* 只发 16 B：16 × 9 bit ÷ 400 kHz ≈ 360 µs */
    if (++slice >= 64) slice = 0;              /* 64 片 × 1 ms = 64 ms 刷完一帧 */
}

/* 4.5 串口上报：格式化成文本发出去（只在调试版里编译） */
static void task_uart(void)
{
    printf("T=%u.%u C  target=%u.%u C  fan=%u%%\r\n",
           g_temp_c10 / 10, g_temp_c10 % 10,
           g_target_c10 / 10, g_target_c10 % 10,
           g_fan_pct);
}

/* ---------- 5. 主函数：初始化一次，然后永不退出的调度循环 ---------- */
int main(void)
{
    HAL_Init();                    /* Flash 等待周期、SysTick 1 ms、NVIC 优先级分组 */
    SystemClock_Config();          /* 8 MHz 晶振 ×9 = 72 MHz（少了这行，一切都慢 9 倍） */

    MX_GPIO_Init();                /* 顺序有讲究：DMA 必须在 ADC 之前 */
    MX_DMA_Init();
    MX_ADC1_Init();
    MX_TIM3_Init();                /* 20 kHz PWM：72 MHz ÷ 72 = 1 MHz，ARR = 49 */
    MX_I2C1_Init();
    MX_USART1_UART_Init();

    oled_init();
    iwdg_start();                              /* 开看门狗：2 s 内必须喂一次 */
    g_target_c10 = flash_load_target();        /* 读回掉电保存的目标温度（需求 R7） */
    fan_set_duty(0);                           /* 上电先让风扇停转，避免突然启动 */

    uint32_t next[TASK_COUNT];
    for (uint8_t i = 0; i < TASK_COUNT; i++) {
        next[i] = g_tick_ms;                   /* 首轮让每个任务都立即执行一次 */
    }

    for (;;) {                                 /* ★ 调度循环：从头到尾没有一句 delay */
        uint32_t now = g_tick_ms;

        if (time_reached(now, next[TASK_CTRL])) {
            next[TASK_CTRL] += k_period_ms[TASK_CTRL];
            task_ctrl();
        }
        if (time_reached(now, next[TASK_KEY])) {
            next[TASK_KEY] += k_period_ms[TASK_KEY];
            task_key();
        }
        if (time_reached(now, next[TASK_SAMPLE])) {
            next[TASK_SAMPLE] += k_period_ms[TASK_SAMPLE];
            task_sample();
        }
        if (time_reached(now, next[TASK_DISP])) {
            next[TASK_DISP] += k_period_ms[TASK_DISP];
            task_disp();
        }
        if (time_reached(now, next[TASK_UART])) {
            next[TASK_UART] += k_period_ms[TASK_UART];
            task_uart();
        }

        /* 慢任务：喂狗 + 自检。
           喂狗必须留在主循环里，不能挪进中断 —— 否则「主循环已经死了、中断还活着」
           的时候狗照样被喂，看门狗就失去了它唯一的意义。 */
        if (time_reached(now, next[TASK_SLOW])) {
            next[TASK_SLOW] += k_period_ms[TASK_SLOW];
            iwdg_feed();
            system_self_check();               /* 传感器断线检测等（需求 R6） */
        }
    }
}

这段代码里有四个地方值得你反复看，它们都是「嵌入式写法」和「PC 写法」分道扬镳的位置：

  • volatile uint32_t g_tick_ms：中断里写、主循环里读的变量必须加 volatile，否则编译器完全可能认为「这个变量在循环里从来没被改过」，从而只读一次、拿一个死值去比较，你的整个调度表就失效了。
  • time_reached() 用无符号减法而不是 now >= due：因为 g_tick_ms 会溢出回绕（约 49.7 天一次），直接比大小会在回绕瞬间出错；而 (int32_t)(now - due) 的写法在回绕前后都是正确的。
  • next[i] += k_period_ms[i] 而不是 next[i] = now + k_period_ms[i]：用加法累加可以避免「每次执行都晚一点点，误差逐渐累积」，让任务的长期平均周期严格等于设定值。
  • 整个主循环里没有一句 HAL_Delay，从根上遵守了 4.4 的第 1 条铁律。

4.8 上电验证清单

第一块板子焊好、第一次上电，是最容易「冒烟」的时刻。下面这张清单把顺序排好了：先量电，再量时钟，再看灯，最后才接负载。请按顺序做，不要跳步——跳过第一步直接插 12 V 再接风扇，是烧板子的标准剧本。

【第 0 步】上电之前（不插电，万用表电阻档）
  □ 12 V 输入与 GND 之间不短路（正向测应大于几百欧，反向无穷大）
  □ 3.3 V 与 GND 之间：用二极管档正向测应有几千欧以上，绝不能是 0 Ω
  □ 5 V 与 GND 之间同样检查
  □ 每个电源引脚旁都有 100 nF 去耦电容（越靠近引脚越好）
  □ MOS 管栅极有 10 kΩ 下拉到 GND（防止 MCU 复位期间引脚高阻导致风扇误导通）
  □ 续流二极管方向正确：阴极接 12 V 侧，阳极接 MOS 漏极
  □ SWD 的 SWDIO / SWCLK 没有被别的电路占用（做产品时尤其要确认）

【第 1 步】只插 USB（ST-Link 供电），不接 12 V、不接风扇
  □ 3.3 V 实测在 3.2~3.4 V 之间（万用表直流档）
  □ 5 V 实测在 4.9~5.1 V 之间
  □ NRST 引脚上电后为高（约 3.3 V）；按一下复位键应能拉到 0 V
  □ 空载整机电流在 20~60 mA 之间（F103 跑 72 MHz 的典型值）
     ——若超过 100 mA，立刻拔掉：八成是某处短路或芯片焊反
  □ 用手背轻触芯片表面：温热正常，烫手说明有引脚接错（尤其电源接反）

【第 2 步】量时钟（示波器，10× 探头）
  □ OSC_OUT（PD1）上有 8 MHz 波形，峰峰值 1 V 以上
     ——若没有波形：晶振没起振，检查负载电容（20 pF）与焊接
     ——★ 晶振不起振的典型后果：程序卡死在 SystemInit 里的等待循环，
        表现为「烧录成功但灯不亮、串口没输出」
  □ （可选）把某个空闲 GPIO 在 SysTick 中断里翻转，量到的方波周期应是 2 ms

【第 3 步】下载与调试
  □ ST-Link 能识别芯片，读到的 Device ID 与型号匹配
  □ 能在 main 的第一行停住断点（停不住说明卡在启动阶段，见 4.6）
  □ 全速运行后，读复位原因寄存器（RCC_CSR）：
     显示为上电复位 / 引脚复位 → 正常
     显示为看门狗复位 → 说明主循环没转起来或某个任务卡死，回头查
     显示为软件复位 → 说明有代码主动调用了 NVIC_SystemReset()

【第 4 步】接上 12 V（先不接风扇）
  □ 5 V 仍为 4.9~5.1 V，3.3 V 仍为 3.2~3.4 V（带载后不能掉下来）
  □ 整机电流增加不超过 20 mA（只是降压模块自身的损耗）
  □ 摸一下 MP1584 与 AMS1117：温热正常

【第 5 步】接上风扇，验证 PWM
  □ 风扇不转时，PA6 空载电压约为 0 V
  □ 让固件输出 50% 占空比，示波器量 PA6：应为 20 kHz 方波（周期 50 µs），
     高电平 25 µs、低电平 25 µs
  □ 改占空比到 100%，风扇应全速；回到 0% 应完全停转
  □ 长时间运行后 MOS 管温热正常，不烫手

【第 6 步】验证需求（对照 4.1 那张表逐条打勾）
  □ R1：3 个温度点（冰水 0 ℃、室温、40 ℃ 温水）与标准温度计误差 ≤ ±1 ℃
  □ R1：串口每秒输出的温度值在变化，且与 OLED 显示一致（验证 R3）
  □ R4：连按 20 次按键，一次都不许丢（这是检验「主循环有没有阻塞」的试金石）
  □ R5：温度稳定 10 分钟，观察 PWM 占空比不来回跳
  □ R6：带电拔掉 NTC，显示应进入故障状态而不是乱跳的数字
  □ R7：断电重新上电 5 次，目标温度都应恢复
  □ R9：连续运行 2 小时，用调试器看 g_tick_ms 是否稳定增长
     （若停住或归零：说明程序卡死或被看门狗复位了，去查 RCC_CSR）

  一句话记住顺序：先量电 → 再量时钟 → 再看灯 → 最后接负载。
这份清单为什么值钱

因为它把「调试」变成了一件有顺序、可复现的事。初学者最常见的失败模式是：板子不工作，于是开始乱改代码——改一行、烧一次、看一眼，两小时过去了什么都没定位到。而有经验的工程师会先问：「电对不对？时钟有没有？程序跑到 main 了吗？」这三个问题平均两分钟就能问完，却能把故障范围缩小到 20% 以内。这套思路就是第 33 篇《调试方法与工具》的主题——你现在看到的，是它的最小可用版本。

常见误解与坑

下面这八条，是初学者在这一层最容易踩的。它们的共同点是：都能让你在「自我感觉良好」的状态下走偏很久——不像接错线那样立刻冒烟，所以更危险。每一条都按「错误认知 → 为什么错 → 正确做法」写，你可以拿它当一份自查表。

误区 1 · 「C 语言好就够了」

错误认知

单片机开发就是写 C 代码。我 C 语言考了 90 分，指针、结构体、链表都会，学单片机应该很快。

为什么错 · C 语言只是工具，真正的难点是「这段代码跑在什么硬件上」。同一句 a = *p;，在 PC 上是读一块内存；在 MCU 上，p 可能指向一个传感器寄存器，读它会产生副作用（有些寄存器读一次就把标志位清掉）。同一句 while(!flag);，在 PC 上最多卡住一个线程，在 MCU 上会让主循环停转、看门狗把整块板子复位。C 语言课本里不会教你的东西有一长串：volatile、内存对齐、栈的深度上限、中断上下文里不能做什么、链接脚本与变量定位、编译器优化会怎样改写成你的代码。

正确做法 · 把 C 语言当及格线而不是门槛。从今天起，每写一句就多问三个问题：这条语句在硬件上做了什么动作？耗时多少？会被中断打断吗？这三个问题问上一个月，你看代码的方式就变了。第 31 篇《嵌入式 C 进阶》整篇讲的都是这些「课本上不教」的部分。

误区 2 · 「跑通例程就等于会了」

错误认知

把官方例程烧进去，灯亮了、串口也打印出东西了，这个外设就算掌握了。

为什么错 · 例程是一条「已知结果的路径」：正确的时钟配置、正确的引脚、正确的初始化顺序、正确的缓冲区大小，别人都已经替你试过了。你顺着走当然不摔。可真实项目里没人为你填坑，一旦遇到「官方例程能跑、我的代码不能跑」，你手里没有任何可比较的东西——因为你不知道例程里哪一行是关键的。而且例程只覆盖「功能」，不覆盖「边界」：它不会告诉你温度到 100 ℃ 会怎样、串口一次来 1000 字节会怎样、电源掉电 10 ms 会怎样。

正确做法 · 把例程当标本而不是答案。跑通之后做三件事：① 故意改坏一个参数（比如代码里波特率改成 9600、而串口终端还是 115200），观察现象并解释为什么；② 打开 map 文件，看这个例程占了 Flash / RAM 多少；③ 关掉代码，用自己的话把执行顺序写一遍。第 4 节那套「从需求到跑起来」的流程，就是用来替代「照着例程改参数」的。

误区 3 · 「RTOS 一定比裸机好」

错误认知

RTOS 是「专业」的标志。用了 RTOS 程序就更稳定、更规范、更像工业产品。

为什么错 · RTOS 是一个要消耗资源的软件，它带来三样成本：RAM（例题 3 算过，同样是温控风扇，从 3.3 KB 涨到 10.3 KB，多出 7 KB）、CPU（每次任务切换都要保存和恢复现场，几微秒到十几微秒，切换越频繁摊得越多）、以及复杂度（优先级反转、栈溢出、临界区、死锁——这些 bug 比裸机的 bug 难查得多，而且往往只在压力大时偶发）。对一个只有六个任务、每个任务 1 ms 内都跑得完的系统来说，RTOS 是纯粹的负担。

正确做法 · 先用时间片轮询。只有出现下面三种情况之一才升级：① 任务多到时间片排不下，或某个任务的执行时间随时长剧烈变化（比如要跑一遍 4 MB 数据的 CRC 校验）；② 需要复杂的同步与通信（多任务抢同一资源、要求严格的生产者—消费者队列）；③ 需要阻塞式编程模型来降低代码复杂度（任务里可以「等一个信号量」，而不是拆成状态机）。判断标准是「裸机写不出来了」，不是「RTOS 听起来更专业」。第 32 篇会把这条升级路径完整走一遍。

误区 4 · 「功能对了就算完成了」

错误认知

温度测准了、风扇转了、按键能用了，这个项目就做完了。

为什么错 · 功能正确只是最低要求。工业产品还有四类隐形要求，它们全都不体现在「演示效果」里：① 边界（传感器断线、温度超量程、按键被卡住、电源电压跌到 2.8 V 会怎样）；② 环境（−20 ℃ 冷启动、85 ℃ 高温、湿度、振动、EMC——打静电时会不会复位）；③ 长期（连续跑 72 小时、参数区被擦写 10 万次会不会坏、看门狗能不能把跑飞的程序救回来）；④ 可维护（别人接手能不能看懂、能不能远程升级、出了故障能不能查到复位原因）。这四类决定了产品能不能卖，而它们都不在「功能列表」上。

正确做法 · 在需求阶段就把它们写进验收标准（第 4 节的 R6 / R7 / R9 就是干这个的），到测试阶段逐条打勾。记住一句话：演示成功 ≠ 测试通过 ≠ 可以量产，每两个之间都隔着一段实打实的工作量。

误区 5 · 「费时的是写代码，不是调试和验证」

错误认知

排期就按「写代码要几天」来算。代码写完，剩下的只是点点鼠标、烧进去看看。

为什么错 · 真实的嵌入式项目里，写出第一版能跑的代码通常只占总工时的 20%~30%。剩下的时间花在：第一次配工具链与工程（能花掉一整天）、写驱动并对着示波器调时序、排查硬件问题（虚焊、飞线、电源纹波）、做边界与环境测试、写文档与生产测试工装。第 4 节那个温控风扇，第一版代码一个下午就能写完，但从第一次上电到 R1~R9 全部打勾，正常要两到三天。

正确做法 · 排期按「功能点耗时 × 3」估；每写完一个模块就立刻用串口或示波器验证它，而不是等全部写完再联调（联调时你分不清是哪一层的错）；把调试工具当成和编译器一样的必需品提前备好——SWD 调试器、USB 转串口、万用表、示波器。第 33 篇专门讲怎么把调试时间压下来。

误区 6 · 「能跑程序的芯片就是嵌入式系统」

错误认知

只要芯片里能装程序、能跑起来，做出来的东西就是嵌入式系统。

为什么错 · 回到 2.1 的三层含义。一块开发板放在桌上跑点灯例程，它没有嵌入到任何对象体系里——没有一个真实的被控对象需要它；一台装了 Windows 的迷你主机是通用平台，应用随便换；而一张音乐贺卡，虽然只有几百字节代码，却是标准的嵌入式系统——它专为这张贺卡存在，成本、体积、功耗都被压到极限。判据是「专用性」以及「它与被控对象的关系」，不是芯片的性能，也不是程序有多少行。

正确做法 · 判断时问三个问题：① 它是不是为某个特定对象或场景而存在？② 它的正确性判据是不是来自那个对象（而不是来自「用户觉得好用」）？③ 它的软硬件是不是为那个场景裁剪过？三个都「是」才算。用这个判据你会发现：同样的树莓派，「做一台小电脑」和「做一台固化的门禁机」性质完全不同——性质由用途决定，不由硬件决定。

误区 7 · 「选型只看性能」

错误认知

选芯片就是比主频、比 Flash / RAM、比单价，谁参数高、谁便宜就选谁。

为什么错 · 性能只是 2.8 那张表里的第二项。真实项目里最常翻车的是供货与生命周期：一颗参数完美、单价便宜 30% 的芯片，如果两年后停产，你要重新选型、重写驱动、重做认证、重新测试——省下的几毛钱，赔进去的是几个月。另外三项同样容易被忽略：封装（选了 QFN 或 BGA，手工焊不了，打样和维修成本翻倍）、温度等级（消费级芯片用在户外，冬天起不来）、生态（没有 HAL、没有社区、只有一份 20 页的英文数据手册，开发时间可能是别人的三倍）。

正确做法 · 把 2.8 那张表用起来：前四条（性能、存储、外设、封装）当一票否决，后五条逐项打分。并且强制自己为每一个被淘汰的候选写一句书面的否决理由——如果你写不出来，说明它不是被数据淘汰的，而是被你的偏好淘汰的。在答辩现场，能说出「为什么不用另外两个」的人，比能说出「我为什么用它」的人可信得多。

误区 8 · 「交叉编译只是换个编译器而已」

错误认知

交叉编译就是在命令前面加个 arm-none-eabi- 前缀，和平时编译没多大区别。

为什么错 · 交叉编译真正多出来的是两个 PC 上根本不存在的东西：链接脚本和启动文件。PC 上链接器只要把程序拼成一个可执行文件，操作系统负责装载它；而单片机没有装载器，程序必须被「排」到固定的物理地址上（Flash 从 0x08000000 起、RAM 从 0x20000000 起），谁住在哪、栈顶在哪、.data 段要从哪个地址搬到哪个地址，全部要在链接时定死。这就是为什么「代码一模一样、换一个链接脚本就跑不起来」，也是为什么「我改了一下工程配置就突然不能跑了」这类问题的答案通常不在 C 代码里。

正确做法 · 把链接脚本当成源码的一部分来读，至少搞清楚四件事：Flash 和 RAM 各多大、起始地址是多少、栈顶 _estack 定义在哪、.data 与 .bss 的边界符号叫什么。再学一个技巧：编译时加 -Wl,-Map=固件名.map 生成 map 文件，遇到「程序变大之后不跑了」先去翻 map，比盲改代码快十倍。

这八条误区的共同点

它们都来自同一个来源：把 PC 编程的直觉直接搬过来，并且把「能跑」当成了「正确」的标准。

区分嵌入式工程师水平的，从来不是「会不会写某个功能」，而是「有没有把不确定变成已验证」：Flash 够不够，算过没有？耗时多少，量过没有？断线了会怎样，试过没有？三年后还买得到吗，查过没有？这一层剩下的九篇，本质上都是在给你提供「算、量、试、查」这四件事的工具。

小结与自检

一张纸的要点回顾

概念上要立住的：

  • 嵌入式系统 = 以应用为中心、软硬件可裁剪、嵌入到对象体系中的专用计算机系统。三层含义缺一不可，其中「嵌入到对象体系」是它和「通用计算机上的一个程序」的分水岭。
  • 四层组成：硬件层 → 硬件抽象层（HAL / BSP / 寄存器驱动）→ 系统软件层（裸机框架 / RTOS / 嵌入式 Linux）→ 应用层。每一层都在替上一层屏蔽一类细节，而屏蔽是有代价的（体积、RAM、执行时间）。
  • 一颗 MCU 就是一台完整的计算机：CPU、Flash、SRAM、GPIO、定时器、串口、ADC、DMA、中断控制器、时钟树、看门狗——PC 上由主板芯片组和操作系统提供的东西，在这里全都在同一片硅上。

差别上要记住的八条：

  • ① 专用而非通用；② 资源受限（KB 级 RAM、MHz 级主频、无 MMU、无虚拟内存）；③ 交叉编译（宿主机编译、目标机运行，多出链接脚本与启动文件）；④ 没有操作系统（裸机前后台 / 时间片 / RTOS 三选一）；⑤ 实时性分硬 / 软 / 非实时，错过截止时间的后果不同；⑥ 调试手段不同（串口、SWD、示波器，而不是 printf 到屏幕）；⑦ 功耗与长期无人值守（电池容量要用 µA 去算，看门狗是最后一道防线）；⑧ 一旦出厂就难以召回（靠 IAP / OTA 和 A/B 双分区缓解）。

方法上要养成的习惯：

  • 选型：前四条表项一票否决，后五条打分，每个被淘汰的候选都写一句否决理由。
  • 写代码：主循环里不许有阻塞延时；每个任务的耗时必须算过、并且明显小于它的周期；中断里只搬数据、置标志，不做耗时运算。
  • 调试：先量电 → 再量时钟 → 再看灯 → 最后接负载。把「故障定位」变成有顺序、可复现的流程。
  • 验证：功能通过只是起点，边界、环境、长期、可维护四类要求要在需求阶段就写进验收标准。

自测题（先自己答，再点开对答案）

第 1 题 · 下面哪一个是嵌入式系统？为什么？

（A）一块出厂即固化、专门控制洗衣机水位与电机的板子；（B）一台装了 Linux、跑着你自己写的 Python 脚本的树莓派。

答案 · A 是。判据是三层含义：它嵌入在洗衣机这个对象体系里；它的正确性判据（水位准不准、电机控制对不对、会不会漏水）来自这个对象，而不是来自「用户觉得界面好看」；它的软硬件为这个场景裁剪过——成本、体积、功耗、可靠性都是围绕洗衣机定的。

B 不是：硬件是通用平台，软件可以随时替换、部署方式也没被固化。但要特别注意一个反转：如果你把这台树莓派装进门禁机里、固化成专用产品，它就成了嵌入式系统的硬件平台。所以性质由用途决定，不由硬件决定——这正是第 6 条误区要纠正的。

第 2 题 · 由编译输出估算所需 Flash 与 RAM

编译输出为 text 12480, data 208, bss 1840，链接脚本里的主栈是 2 KB。烧录需要的 Flash 至少多大？运行时 RAM 至少多大？按 30% 余量的原则，你会选什么规格的芯片？

答案 · Flash 占用 = text + data = 12480 + 208 = 12688 B ≈ 12.4 KB；RAM 占用 = data + bss + 栈 = 208 + 1840 + 2048 = 4096 B = 4 KB。

关键点是 data 段算了两次：这些变量的初值必须烧在 Flash 里（上电后由启动代码搬到 RAM），运行时又要在 RAM 里占一份，所以它同时出现在两个公式里。bss 段只占 RAM（初值全是 0，不需要在 Flash 里存一份）。

按 30% 余量：Flash 至少要 12.4 ÷ 0.7 ≈ 17.7 KB，实际会在 32 KB 或 64 KB 的型号里选；RAM 至少 4 ÷ 0.7 ≈ 5.7 KB，实际从 8 KB 或 20 KB 起选。注意这只是「当前版本」的账，功能还会长——第 4 节那个项目就是先算出 23.2 KB、再发现 A/B 双分区装不下。

第 3 题 · 为什么不能在 STM32 上编译它自己的程序？

答案 · 三个硬性障碍，一个比一个根本：

① 没有操作系统和文件系统。编译过程要读源文件、写一堆中间文件、再读回来，这需要文件系统支持，而裸机没有文件这个概念（你连「目录」都没有）。

② 资源差了三个数量级。编译器本身是一个几十 MB 的可执行文件，编译一个中等大小的源文件峰值内存要几十 MB；而 STM32F103C8T6 只有 64 KB Flash、20 KB RAM，连编译器这个程序本身都装不下，更不用说运行它。

③ 编译器要能跑在它自己的目标上（自举）。流行编译器是为宿主机的 64 位 CPU 和几 GB 内存写的，移植到 MCU 上不是「裁剪一下」的问题，而是重建整套工具链的问题。

所以分工是固定的：宿主机负责写和编译，目标机负责运行。这个分工就叫交叉编译——它不是「换个编译器」，而是承认两边是两个完全不同的计算环境。

第 4 题 · 这个控制环来得及吗？

某系统要求每 1 ms 执行一次控制环，环内代码约 800 条指令，平均每条指令 1.5 个时钟周期。芯片主频 24 MHz 时能否满足？换成 8 MHz 呢？

答案 · 800 × 1.5 = 1200 个时钟周期。

24 MHz：1200 ÷ 24,000,000 = 50 µs = 0.05 ms，占 1 ms 周期的 5%，满足，还剩 95% 给其他任务。

8 MHz：1200 ÷ 8,000,000 = 150 µs = 0.15 ms，占 15%，仍然满足。

但结论不能停在这里，还要补两句：① 这只是控制环自己，把显示、按键、采样、通信都加进来才是系统的真实占用（第 4 节那个项目合计约 38%）；② 要留最坏情况的余量——碰上 Flash 等待周期、中断嵌套、分支预测失败时，实际耗时可能是这个平均值的 2~3 倍，所以经验上要求「单个任务占用不超过其周期的 30%~50%」，而不是勉强压线。

第 5 题 · 需求里加一条「手机看温度」，选型结论会变吗？

答案 · 会，而且是直接推翻。4.2 选 STM32F103C8T6 的核心理由就是「没有无线需求」，这条需求一加，理由就没了。三条路：

① STM32 + 外挂 ESP8266 / ESP32 模块：多一个串口、多一份 AT 指令固件、多 3~5 元、多一层故障点（模块也会死机）。② 直接换 ESP32：Wi-Fi 与蓝牙内置，双核 240 MHz、520 KB SRAM，成本 15~25 元；代价是峰值电流 300 mA，电源和 PCB 布局要重新设计。③ 换带无线的 STM32 型号（STM32WB / WLE 系列）：保留原有 HAL 生态，但价格和供货要重新核。

更关键的第二次影响在软件架构：联网带来的重传、超时、协议解析都是「执行时间不固定」的任务，时间片轮询会开始吃力——这时才是第 32 篇里 RTOS 真正该上场的时机（对应误区 3 的升级条件 ①）。

一句话：需求变更必须回到选型表重走一遍，不能「在原方案上打个补丁」。

第 6 题 · 为什么喂狗必须放在主循环里？

答案 · 看门狗要解决的故障是「程序跑飞」或「某个任务卡死」，它的判据必须是「正常的程序流程还在推进」。主循环是所有任务依次执行的必经之路：只要主循环还在转，就说明没有任务把它卡住。

如果改成在定时器中断里喂狗，那么即使主循环已经死在某一行（比如卡在一个永远等不到的标志位上），中断照样按期为狗供食，看门狗永远不会复位——它从一个故障检测机制退化成了一只没有用处的定时器，而你还以为自己有保护。

判断标准很简单：喂狗的位置应该是「只有一切正常时才会被执行到」的地方。同理，如果某个任务卡死会让主循环转不动，那它就该被看门狗复位——这是它存在的意义，而不是把喂狗挪走让它「别复位」。

第 7 题 · 时间片轮询的两条硬约束是什么？

答案 ·

① 每个任务的最坏执行时间，必须明显小于它的调度周期（经验值：占用不超过周期的 30%~50%）。否则会出现「一次执行还没结束、下一次到点时间又到了」，任务开始互相挤压，表现为「某些功能偶尔失灵」——这是最难查的一类 bug，因为它在实验室里往往不复现。

② 主循环里不能有任何阻塞式延时（HAL_Delay、while(!flag);）。延时期间 CPU 在原地空转，这段时间里所有其他任务都被推迟。第 4 节那个项目如果把 OLED 整屏刷新（23 ms）直接放进主循环，按键响应会从 100 ms 以内掉到几百毫秒，直接违反需求 R4；正确做法是把它切成 64 片，每片 360 µs。

练习（动手才算学过）

  1. 给你手上跑通过的例程算一次资源账。在链接参数里加上 -Wl,-Map=输出名.map 重新编译，然后回答三个问题：这个工程占了多少 Flash、多少 RAM？占用最多的三个函数分别是谁？按「留 30% 余量」的标准，它还能加多少功能？
  2. 给开发板做一次最小验证。照着 4.8 的清单，用万用表和示波器把你手上板子的 3.3 V 电压、晶振波形、一个空闲 GPIO 在中断里翻转的方波周期各量一遍，把实测值记在本子上。这一步会让你对「板子是活的」这件事有实感。
  3. 写一个只有两个任务的时间片框架。要求：LED 每 500 ms 翻转一次、串口每 100 ms 打印一句话；主循环里不允许出现任何延时函数；用一张表写出这两个任务的周期、实测执行时间、以及占用的百分比。
  4. 做一次选型答辩。假设需求是「太阳能供电的土壤湿度记录仪，一节电池要撑一年」。用 2.8 的九项考量写半页纸的选型理由，并且必须写出至少两条否决其他方案的理由——写不出来就说明你还没想清楚。
  5. 收集反例。各举三个例子：三个「里面有程序、但不是嵌入式系统」的东西，三个「很便宜很简单、但确实是嵌入式系统」的东西，每个都写一句理由。做完这一题，你对「嵌入」两个字的理解会比读十遍定义都牢固。
