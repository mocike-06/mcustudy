原理介绍

前面三篇里，你要么连着 USB 线看串口，要么得先有路由器才能通信。 蓝牙解决的是第三种场景：设备完全独立， 人在几米之内，拿手机直接对话。 做智能小车调试、毕设演示、现场答辩，这一招特别有用—— 不用抱着笔记本，掏出手机就能改参数、开关设备。

ESP32 在这件事上有个先天优势：它同时支持经典蓝牙和 BLE， 而且芯片里只做了一套 2.4GHz 射频， 蓝牙和 Wi-Fi 是靠分时复用共用它的。 这一个硬件事实，决定了本页后面所有的使用限制和坑。

经典蓝牙与 BLE 怎么选

蓝牙这个名字下面其实住着两套几乎不相干的技术。它们只是都叫蓝牙、都用 2.4GHz， 协议栈、应用场景、能连的设备完全不同：

对比项 经典蓝牙（BR/EDR，用 SPP 协议） BLE（低功耗蓝牙，GATT 协议）
ESP32 库 BluetoothSerial BLEDevice / BLEServer / BLECharacteristic
核心概念 串口（SPP）——建立一条「虚拟串口线」 服务（Service）与特征值（Characteristic）
安卓手机 支持，任意蓝牙串口 App 直接用 支持，需要支持 BLE 的 App（nRF Connect 等）
iPhone / iPad 不支持（苹果不开放 SPP） 支持，这是 iOS 上唯一的办法
编程难度 极低，用法和 Serial 几乎一样 中等，要定义 UUID、服务、特征值、回调
功耗 高（几十 mA），不适合电池设备 低（广播时微安级），纽扣电池能撑几个月
传输速率 高，每秒几十 KB 很轻松 低，一次最多 20 字节左右（默认 MTU）
典型用途 调试终端、小车遥控、批量传数据 手环、传感器节点、手机配网、iOS 设备

选型其实只需要回答一个问题： 你要不要支持 iPhone？ 要，就只能用 BLE；只在安卓上做调试，经典蓝牙能让你十分钟就出成果。 本页的完整示例用经典蓝牙，因为它的代码最像串口、 最适合第一次接触蓝牙的人建立直觉； BLE 的入门门槛主要在于概念多，理解了 GATT 之后代码量并不大。

一个必须提前知道的坑

很多同学照着网上的教程写好了经典蓝牙，用自己的安卓手机跑通了， 答辩时老师的 iPhone 一搜——根本搜不到设备。 这不是程序错了，是 iPhone 系统层面就不支持经典蓝牙的 SPP 协议。 如果你的作品要适配所有人，直接上 BLE。

SerialBT 是什么

ESP32 的经典蓝牙库把 SPP 协议封装成了一个叫 BluetoothSerial 的类。 它的高明之处在于继承自 Arduino 的 Stream 类， 也就是和 Serial 完全同一套接口：

功能 USB 串口 蓝牙串口 说明
初始化Serial.begin(115200)SerialBT.begin("名字")蓝牙不需要波特率
有没有数据Serial.available()SerialBT.available()返回可读字节数
读一个字节Serial.read()SerialBT.read()读不到返回 -1
发一行Serial.println("Hi")SerialBT.println("Hi")自动补 \r\n
有没有人连着—SerialBT.hasClient()蓝牙独有，用来判断连接状态
断开连接—SerialBT.disconnect()主动踢掉手机

正因为接口一致，工程的常见做法是 同时开两个「终端」： 电脑上的串口用来看日志（调试用），手机上的蓝牙用来做交互（演示用）。 你写的业务逻辑只需要处理一次输入，把两个来源都喂给同一个解析函数就行—— 本页的代码正是这么组织的。

蓝牙串口没有「波特率」这个概念

已经习惯了 Serial.begin(115200) 的同学， 写 SerialBT.begin(115200) 是编译不过的—— begin() 的参数是设备名，不是波特率。 蓝牙链路的速率是协议自动协商的，双方不需要事先约定。 有些手机 App 里也有「波特率」选项，那是给连老式 HC-05 模块用的， 连 ESP32 时随便选一个都不影响通信。

蓝牙和 WiFi 为什么互相干扰

这是 ESP32 上一个非常反直觉、但必须理解的问题。 蓝牙和 Wi-Fi 都工作在 2.4GHz 的 ISM 频段—— Wi-Fi 的信道 1~13 覆盖 2401~2483MHz，蓝牙则在这个范围内 以每秒上千次的频率在 79 个 1MHz 宽的窄带上跳来跳去（跳频）。 两者在物理上是同一段频谱。

而 ESP32 里只有一套射频前端和一个天线。 所以当蓝牙和 Wi-Fi 都要用时，芯片内部的共存机制 （coexistence，靠时分复用 + 优先级仲裁）必须在两者之间来回切换： 这一刻收 Wi-Fi 的包，下一刻跳到蓝牙频点去收发。 

  理想情况（只开一个）              同时开两个（共存仲裁）

  ┌──────────────┐                 ┌──────────────┐
  │  2.4GHz 射频  │ 100% 时间归它  │  2.4GHz 射频  │ 时间被切成小片
  └──────┬───────┘                 └──┬────────┬──┘
         │                            │        │
     ┌───┴───┐                  ┌─────┴──┐  ┌──┴─────┐
     │ Wi-Fi │                  │ Wi-Fi  │  │ 蓝牙    │
     └───────┘                  └────────┘  └────────┘
     吞吐高、延迟稳               各自只能分到一部分时间片

  实际表现：
   · Wi-Fi 吞吐量下降（可能掉一半以上）
   · 蓝牙数据出现几十到几百毫秒的突发延迟
   · 极端情况下蓝牙直接断连，或者 Wi-Fi 频繁掉线重连
   · 经典蓝牙的干扰比 BLE 更严重（它占用的时间片更多）

  结论与对策：
   · 只做蓝牙调试 -> 不要在代码里调用任何 WiFi.begin()，
     甚至不要 #include <WiFi.h>，射频资源全给蓝牙，最稳
   · 必须两个都用 -> 优先用 BLE（占用时间片少得多）
   · 两个都要且数据量大 -> 错峰：连 Wi-Fi 传完数据后
     WiFi.disconnect(true) 关掉射频，再启用蓝牙

这份代价清单解释了一个很常见的现象： 同学把前一篇的 Wi-Fi 代码和这一篇的蓝牙代码合到一个工程里， 结果两边的表现都变差了—— 蓝牙发一条命令要等半秒才响应，Wi-Fi 也开始间歇性掉线。 代码本身没错，是射频在打架。

手机端要用什么 App

ESP32 这边负责「提供一条串口」，手机那边需要一个能打开这条串口的 App。 这类 App 的功能都很朴素：列出设备 → 点一下连接 → 一个输入框和一个接收区。

平台 推荐 App 适用协议 使用要点
安卓 Serial Bluetooth Terminal（中文常叫「蓝牙串口助手」） 经典蓝牙 SPP 连接后长按输入框可勾选「发送新行」，本页的 p128 这类命令需要它
安卓 SPP 串口助手 / 各类「蓝牙调试助手」 经典蓝牙 SPP 功能类似，注意在设置里把发送结尾设为 \r\n
安卓 / iOS nRF Connect for Mobile BLE BLE 调试的事实标准，能看服务与特征值的原始数据
iOS LightBlue BLE 界面友好，适合第一次理解 GATT 结构
iOS —（无经典蓝牙方案） — iOS 上不存在能连 ESP32 经典蓝牙串口的 App

还有两个概念要先分清，否则后面一定会卡住：

  • 配对 ≠ 连接。 在手机系统设置的蓝牙列表里点一下设备，只是完成了「配对」， 系统记住这个设备了。要真正收发数据， 还必须在串口 App 里再点一次「连接」。 很多人卡在这一步：明明系统显示「已配对」，但板子一直收不到数据。
  • 配对码通常不需要输。 ESP32 的 SPP 默认采用「Just Works」方式，大多数安卓手机不弹窗就直接配上了。 如果弹了配对码输入框，试 1234 或 0000。

硬件接线说明

这一篇和 Wi-Fi 那篇一样，核心功能零接线—— 天线和射频都在芯片里，用板载 LED 就能完成全部实验。 可选的外接 LED 只是为了让现象看得更清楚。

接线表与准备清单

对象 引脚 / 规格 连接到 说明
ESP32 开发板 USB 母座 电脑 USB 口 只用来供电和看日志，蓝牙通信本身不依赖电脑
板载天线 模组 PCB 天线 — 在金属屏蔽罩那一侧，天线附近别放金属物、别用手捏
板载 LED GPIO2 — 用来指示蓝牙连接状态和手机下发的命令，不需要接线
外接 LED（可选） GPIO16 LED 正极；负极经 220Ω 接 GND 把代码里的 PIN_LED 从 2 改成 16 即可
限流电阻 220Ω ~ 1kΩ 串在 LED 与 GND 之间 不接电阻会烧 LED，也可能拉坏 GPIO
供电 5V / ≥ 500mA USB 口 蓝牙发射虽然比 Wi-Fi 省，劣质线材一样会导致掉电复位

   └──────────────────────┘

  两个「终端」同时在线的好处：
   · 手机在几米外操作，像遥控器
   · 电脑上的串口监视器同时看到全部日志，方便定位问题
   · 电脑串口还能直接敲命令，手机没电时不影响调试

  上电顺序（建议）：
   1. 开发板插 USB，先看串口日志确认「已启动，等待手机连接」
   2. 再打开手机蓝牙，搜索设备名 ESP32-LED-Ctrl
   3. 先系统配对，再进 App 点连接
   4. 连上瞬间，串口会打印「手机已连接」，手机端收到一条欢迎语
上电前必查
  • 代码里没有 WiFi.begin()。蓝牙实验期间不要开 Wi-Fi，射频抢不过会互相拖累。
  • 开发板型号必须带蓝牙。ESP32-S2 没有蓝牙，ESP32-C3 只有 BLE 没有经典蓝牙。
  • 手机蓝牙和定位（位置信息）两个开关都打开，安卓扫描蓝牙设备依赖定位权限。
  • 设备名只用英文、数字和连字符，不要用中文和空格，部分手机搜不到或显示乱码。
  • 上传程序时手机先断开连接，否则串口可能被占用导致上传失败。

完整代码

一个文件就够。它实现了一套小型的命令协议： 单字符命令（1 0 t s） 不带换行也能立刻生效，多字符命令（p128）需要以换行结束。 这样无论手机 App 有没有开「发送新行」，你都能马上玩起来。 

/* =====================================================================
 *  esp32-bt-led.ino —— 用手机蓝牙串口控制板载 LED
 *
 *  功能：
 *    1. 以经典蓝牙 SPP 方式对外提供一个串口，设备名 ESP32-LED-Ctrl
 *    2. 手机 App 连接后可以开灯、关灯、翻转、调亮度、查状态
 *    3. 电脑 USB 串口和手机蓝牙共用同一套命令解析，两个终端都能操作
 *    4. 连接 / 断开都有日志和 LED 反馈
 *
 *  命令表：
 *    1 / on        点亮 LED（恢复到记忆的亮度）
 *    0 / off       熄灭 LED
 *    t / toggle    翻转开关状态
 *    p<0-255>      设置亮度，例如 p128、p255
 *    s / status    查询当前状态
 *    h / help      显示帮助
 *
 *  目标板：ESP32 Dev Module（ESP32-WROOM-32，必须带经典蓝牙）
 *  核心版本：arduino-esp32 2.x（2.0.17 及同系列版本自带 BluetoothSerial 库）
 *  波特率：115200
 *
 *  ⚠ 本程序刻意不包含 WiFi.h：蓝牙和 Wi-Fi 共用一套 2.4GHz 射频，
 *    只开一个才能获得最稳定的效果。
 * ===================================================================== */

#include <BluetoothSerial.h>      /* 经典蓝牙库，ESP32 核心自带，无需安装 */

/* 如果这块芯片根本没有经典蓝牙（例如 ESP32-S2 / ESP32-C3），
 * 让编译在早期就报出人话，而不是丢一堆看不懂的链接错误 */
#if !defined(CONFIG_BT_ENABLED) || !defined(CONFIG_BLUEDROID_ENABLED)
#error "经典蓝牙未启用：请把开发板选为 ESP32 Dev Module，并确认核心为 2.x"
#endif

/* ---------------- 可调参数 ---------------- */
#define DEVICE_NAME         "ESP32-LED-Ctrl"   /* 手机蓝牙列表里显示的名字 */
#define PIN_LED             2                  /* 板载 LED；外接 LED 可改成 16 */

#define LEDC_CHANNEL        0                  /* 用 LEDC 通道 0 做 PWM */
#define LEDC_FREQ           5000               /* 5kHz，远高于人眼闪烁感知 */
#define LEDC_RESOLUTION     8                  /* 8 位分辨率，占空比 0~255 */

#define STATUS_INTERVAL_MS  10000UL            /* 连上后每 10 秒回一条心跳 */
#define MAX_CMD_LEN         32                 /* 单条命令最长字符数，防止内存被撑爆 */

/* ---------------- 全局状态 ---------------- */
BluetoothSerial SerialBT;                      /* 蓝牙串口对象，用法和 Serial 一样 */

bool     g_btReady     = false;    /* 蓝牙是否初始化成功 */
bool     g_connected   = false;    /* 手机当前是否连着 */
bool     g_ledOn       = false;    /* LED 开关状态 */
uint8_t  g_brightness  = 128;      /* 记忆的亮度，开灯时用这个值 */
String   g_rxBuf       = "";       /* 命令接收缓冲 */
uint32_t g_lastStatusMs = 0;       /* 上次心跳时刻 */
uint32_t g_cmdCount    = 0;        /* 累计收到的命令条数 */
uint32_t g_connectCount = 0;       /* 手机连接过几次 */

/* ---------------------------------------------------------------------
 * 统一的回复函数：同一个消息同时发给手机和电脑
 * 为什么要两边都发？调试时电脑串口监视器能完整看到"手机发了什么、
 * 板子回了什么"，排查问题时不用来回切设备
 * ------------------------------------------------------------------- */
void reply(const String &msg) {
    Serial.print("[回复] ");
    Serial.println(msg);                 /* 给电脑看 */
    if (SerialBT.hasClient()) {
        SerialBT.println(msg);           /* 给手机看，没人连着就别白发 */
    }
}

/* ---------------------------------------------------------------------
 * 把当前状态应用到 LED
 * 注意引脚已经交给 LEDC 控制，之后只能用 ledcWrite，
 * 不能再用 digitalWrite，两者会互相打架
 * ------------------------------------------------------------------- */
void applyLed() {
    ledcWrite(LEDC_CHANNEL, g_ledOn ? g_brightness : 0);
}

/* ---------------------------------------------------------------------
 * 拼一行状态字符串
 * ------------------------------------------------------------------- */
String statusLine() {
    String s = "STATUS LED=";
    s += (g_ledOn ? "ON" : "OFF");
    s += " brightness=";
    s += g_brightness;
    s += " cmds=";
    s += g_cmdCount;
    s += " conns=";
    s += g_connectCount;
    s += " uptime=";
    s += (millis() / 1000);
    s += "s";
    return s;
}

/* ---------------------------------------------------------------------
 * 帮助信息
 * ------------------------------------------------------------------- */
void printHelp() {
    reply("---- ESP32 蓝牙 LED 控制 ----");
    reply("1 / on        点亮 LED");
    reply("0 / off       熄灭 LED");
    reply("t / toggle    翻转开关");
    reply("p<0-255>      设置亮度，例如 p128");
    reply("s / status    查询当前状态");
    reply("h / help      显示本帮助");
    reply("-----------------------------");
}

/* ---------------------------------------------------------------------
 * 命令解析：这是整个程序的核心
 * 把「协议解析」和「硬件动作」分开，是嵌入式代码保持可维护的关键：
 * 将来换成继电器、电机、舵机，只需要改这里的分支，接收逻辑完全不动
 * ------------------------------------------------------------------- */
void handleCommand(String cmd) {
    cmd.trim();              /* 去掉首尾的空格、回车、换行 */
    cmd.toLowerCase();       /* 统一转小写，"ON" 和 "on" 都认 */

    if (cmd.length() == 0) {
        return;              /* 空命令（比如只按了一下回车）直接忽略 */
    }

    g_cmdCount++;

    if (cmd == "1" || cmd == "on") {
        g_ledOn = true;
        applyLed();
        reply("OK LED=ON brightness=" + String(g_brightness));

    } else if (cmd == "0" || cmd == "off") {
        g_ledOn = false;
        applyLed();
        reply("OK LED=OFF");

    } else if (cmd == "t" || cmd == "toggle") {
        g_ledOn = !g_ledOn;
        applyLed();
        reply(String("OK LED=") + (g_ledOn ? "ON" : "OFF"));

    } else if (cmd == "s" || cmd == "status") {
        reply(statusLine());

    } else if (cmd == "h" || cmd == "help" || cmd == "?") {
        printHelp();

    } else if (cmd.startsWith("p")) {
        /* 亮度命令：p 后面跟 0~255 的数字 */
        int v = cmd.substring(1).toInt();
        if (v >= 0 && v <= 255) {
            g_brightness = (uint8_t)v;
            g_ledOn     = (v > 0);       /* 设成 0 就等于关灯 */
            applyLed();
            reply("OK brightness=" + String(g_brightness));
        } else {
            reply("ERR 亮度必须在 0~255 之间");
        }

    } else {
        reply("ERR 未知命令: " + cmd + "（发送 h 查看帮助）");
    }
}

/* ---------------------------------------------------------------------
 * 逐字符接收，负责把字节流切成一条条命令
 *
 * 设计要点：
 *   · 收到 \n 或 \r 时，把缓冲区里的内容当作一条命令交出去
 *   · 如果缓冲区是空的，且当前字符属于单字符命令，立刻执行
 *     —— 这样手机 App 即使没开"发送新行"，按下 1 也能马上开灯
 *   · 缓冲区有长度上限，手机端不停发不带换行的数据时不会耗尽内存
 * ------------------------------------------------------------------- */
void handleChar(char c) {
    if (c == '\n' || c == '\r') {
        if (g_rxBuf.length() > 0) {
            handleCommand(g_rxBuf);
            g_rxBuf = "";
        }
        return;
    }

    /* 缓冲为空 + 是单字符命令 -> 立即执行，不用等换行 */
    if (g_rxBuf.length() == 0) {
        if (c == '1' || c == '0' || c == 't' || c == 's' || c == 'h' || c == '?') {
            handleCommand(String(c));
            return;
        }
    }

    if (g_rxBuf.length() < MAX_CMD_LEN) {
        g_rxBuf += c;
    } else {
        /* 超长了：丢弃并报错。宁可丢一条命令，也不能让内存被撑爆 */
        g_rxBuf = "";
        reply("ERR 命令过长，已丢弃");
    }
}

void setup() {
    Serial.begin(115200);            /* USB 串口：看日志用 */
    delay(500);

    /* 先把 LED 引脚配成 PWM，再把亮度清零（上电默认熄灭） */
    ledcSetup(LEDC_CHANNEL, LEDC_FREQ, LEDC_RESOLUTION);
    ledcAttachPin(PIN_LED, LEDC_CHANNEL);
    ledcWrite(LEDC_CHANNEL, 0);

    Serial.println();
    Serial.println("=== ESP32 经典蓝牙串口（SPP）演示 ===");
    Serial.printf("设备名   : %s\n", DEVICE_NAME);
    Serial.printf("LED 引脚 : GPIO%d\n", PIN_LED);

    /* begin() 的参数是设备名，不是波特率。蓝牙链路速率由协议自己协商，
     * 不需要双方约定——这是和 Serial.begin() 最大的差别 */
    g_btReady = SerialBT.begin(DEVICE_NAME);

    if (!g_btReady) {
        Serial.println("[BT] 初始化失败！请确认开发板带经典蓝牙、核心版本为 2.x");
    } else {
        Serial.println("[BT] 已启动，等待手机连接...");
        Serial.printf("[BT] 请在手机蓝牙里搜索 \"%s\"\n", DEVICE_NAME);
    }
    printHelp();
}

void loop() {
    /* ---------- 1. 检测手机的连接状态变化 ---------- */
    bool nowConnected = SerialBT.hasClient();
    if (nowConnected != g_connected) {
        g_connected = nowConnected;
        if (g_connected) {
            g_connectCount++;
            Serial.println("[BT] 手机已连接");
            reply("ESP32 已就绪，发送 h 查看帮助");
            g_lastStatusMs = millis();
        } else {
            Serial.println("[BT] 手机已断开");
            /* 安全策略：断开时自动关灯。
             * 遥控类设备的通行做法——失去控制链路就应该回到安全状态，
             * 否则车还在跑、灯还亮着，人却已经连不上了 */
            g_ledOn = false;
            applyLed();
        }
    }

    /* ---------- 2. 处理来自手机蓝牙的数据 ---------- */
    while (SerialBT.available()) {
        handleChar((char)SerialBT.read());
    }

    /* ---------- 3. 处理来自电脑 USB 串口的数据 ----------
     * 和蓝牙共用同一个 handleChar，所以两个终端的行为完全一致。
     * 手机没电或者蓝牙抽风时，插着 USB 一样能调试 */
    while (Serial.available()) {
        handleChar((char)Serial.read());
    }

    /* ---------- 4. 连上之后周期性发心跳 ---------- */
    if (g_connected && millis() - g_lastStatusMs >= STATUS_INTERVAL_MS) {
        g_lastStatusMs = millis();
        reply(statusLine());
    }
}

关键代码解析

  • BluetoothSerial SerialBT; 这一行 写在所有函数外面。 它是全局对象，构造时会向系统申请蓝牙协议栈资源。 写进函数里会变成局部变量，函数一返回对象就析构了， 表现是「编译通过但完全搜不到设备」。
  • SerialBT.begin(DEVICE_NAME) —— 参数是设备名，绝对不是波特率。 它返回 bool，初始化失败会返回 false。很多教程忽略这个返回值， 结果蓝牙根本没起来，还在那儿反复重启手机找设备。 凡是返回 bool 的初始化函数，都要检查。
  • SerialBT.hasClient() 用来判断有没有手机连着。 它是轮询式的， 所以在 loop() 里比较前后两次的值， 就能捕捉到「刚连上」和「刚断开」这两个瞬间事件。 蓝牙库其实还提供了 SerialBT.register_callback() 回调机制，能在事件发生时被主动调用，代码更优雅； 但回调运行在蓝牙协议栈自己的任务里， 在里面做耗时操作或调用 Serial 打印都可能引发问题。 初学阶段先用轮询，行为可预测。
  • reply() 里那个 if (SerialBT.hasClient()) 判断不能省。往一个没人接收的蓝牙串口写数据不会报错， 但会一直往发送缓冲区里堆，堆满之后 println() 就会阻塞， 把整个主循环拖住。这是蓝牙项目里很隐蔽的一个卡顿来源。
  • handleChar() 里的 「缓冲为空 + 单字符命令立刻执行」 这一段，是应对手机 App 差异的实用设计。 有的 App 每按一次按钮就发一个字节，有的会自动补 \r\n，还有的要你手动勾选「发送新行」。 两种输入形态都兼容之后，你就不用为了 App 的设置去改代码。
  • MAX_CMD_LEN 的长度上限看着多余， 但它是防止内存被撑爆的必要保护。 如果手机端因为故障连续发送不带换行的字节， g_rxBuf 会无限增长， 最后耗尽堆内存导致芯片重启。凡是接收外部数据的地方， 都要有长度上限——这和网络编程里必须限制请求体大小是同一个道理。
  • applyLed() 里只用 ledcWrite 而没有混用 digitalWrite。 引脚一旦 ledcAttachPin 给了 LEDC 外设， 就不要再让 GPIO 矩阵直接驱动它，否则两个控制器会互相覆盖， 现象是亮度命令偶尔不生效、偶尔闪烁异常。 一个引脚同一时间只能有一个"主人"。
  • 断开连接时自动关灯，是安全状态设计。 遥控小车、加热台、电机这类执行器，只要控制链路断了， 就必须回到安全状态。这个思路来自工业控制里的「失能保护」， 建议从第一个带执行器的作品开始就养成习惯， 答辩时说出来也是加分项。

一个很实用的调试习惯

手机和电脑同时在线时，电脑上的日志才是完整的。 手机 App 的接收区常常只显示最近几十行，滚动就没了； 而电脑串口监视器能看到从开机到现在的全过程。 所以一旦出现「手机端看着不对劲」，第一反应应该是 看电脑上的日志，而不是反复重启 App。 代码里 reply() 同时往两边发， 就是为了这个目的。

常见报错排查方案

蓝牙问题的排查有个好用的二分法： 先看电脑串口日志，判断问题在 ESP32 这一侧还是手机那一侧。 日志里出现了「手机已连接」就说明蓝牙部分完全正常， 后面所有问题都在手机端或者命令格式上。

报错原文：fatal error: BluetoothSerial.h: No such file or directory

原因： 当前安装的 esp32 核心版本里没有这个经典蓝牙库。 最常见的情况是核心版本装得过新——esp32 核心 3.x 系列对经典蓝牙库做了调整， 部分版本不再默认提供 BluetoothSerial.h； 另一种情况是把开发板选成了 ESP32-S2（该型号物理上没有蓝牙）。

解决： 第一，确认开发板选的是 ESP32 Dev Module， 不是 ESP32-S2、ESP32-C3（S2 无蓝牙，C3 只有 BLE）。 第二，打开「工具 → 开发板 → 开发板管理器」，搜索 esp32， 把版本从 3.x 降到 2.0.x（如 2.0.17）， 这是经典蓝牙最稳定的版本线。第三，改完版本后 重启 Arduino IDE 再编译。如果课程要求必须用 3.x， 那就把方案改成 BLE——用 BLEDevice 系列库， 它在 3.x 里是完整支持的。

报错原文：（没有报错）手机蓝牙列表里根本搜不到 ESP32-LED-Ctrl

原因： 按概率排： ① Android 6.0 以后扫描蓝牙设备需要「位置信息」权限， 没给权限 App 和系统都列不出设备； ② SerialBT.begin() 没被调用， 或者调用了但没检查返回值，实际初始化失败了； ③ 设备名里有中文或空格，部分手机的蓝牙栈处理不了； ④ 手机之前连过同名设备，缓存里还留着旧记录； ⑤ 开发板型号不带经典蓝牙。

解决： 先看电脑串口有没有打印「[BT] 已启动，等待手机连接」—— 没有就是 ESP32 侧的问题，有就是手机侧的问题。 然后打开手机的「设置 → 应用 → 蓝牙串口助手 → 权限」， 把位置信息和附近的设备权限都打开。 设备名改成纯英文（本页用的 ESP32-LED-Ctrl 就是安全的）。 在系统蓝牙设置里把这个设备「忽略 / 取消配对」， 重启手机蓝牙开关，等 10 秒再搜。

报错原文：（没有报错）手机显示已连接，但发什么板子都没反应

原因： 分三层。 如果电脑串口连「手机已连接」都没打印， 说明系统配对成功但 App 里的 SPP 链路没建立—— 这是「配对 ≠ 连接」的经典误解。 如果打印了「手机已连接」，但发命令没有任何 [回复]， 说明数据没进来，多半是命令格式问题（多字符命令缺少结束换行）。 如果日志里有 ERR 未知命令， 那是你的命令拼错了或者用了中文标点。

解决： 第一，确认 App 里点过「连接」，而不只是在系统设置里配了对。 第二，先在手机里发单字符 1—— 它在代码里是不需要换行就立刻执行的， 如果 1 有反应，就说明链路正常， 问题一定在「发送新行」设置上。 第三，在 App 设置里把行结束符设为 \r\n（CR+LF）。 第四，检查输入法是不是中文状态， 中文全角字符 １ 和英文 1 在程序里是两个完全不同的字节。

报错原文：（没有报错）同时开 Wi-Fi 和蓝牙后，两边都变得不稳定

原因： ESP32 只有一套 2.4GHz 射频和一个天线， Wi-Fi 和蓝牙靠芯片内部的共存机制分时复用。 两者同时工作时，每次收发都要在频点之间切换， 结果是 Wi-Fi 吞吐下降、蓝牙延迟从几毫秒涨到几百毫秒， 严重时直接断连。经典蓝牙占用的时间片比 BLE 更多，冲突更明显。 如果此时还调用了 WiFi.setSleep(false)， Wi-Fi 会持续占用射频，蓝牙几乎抢不到时间片。

解决： 第一，也是最有效的：蓝牙调试期间干脆不要开 Wi-Fi， 连 #include <WiFi.h> 都不要写， 射频资源全给蓝牙，这是本页示例的做法。 第二，如果业务上必须两个都有， 把蓝牙那一侧从经典蓝牙换成 BLE， 它按需收发、占用时间片少得多。 第三，采用错峰策略：连 Wi-Fi 把数据传完， 调用 WiFi.disconnect(true) 关闭射频， 再启用蓝牙；需要用网时反过来。 第四，把蓝牙和手机的距离拉近到 2 米内， 信号强度足够时可以用更少的重传换到更长的有效时间片。

报错原文：（没有报错）手机收到的中文显示成乱码，比如「ES32 宸插氨缁」

原因： 编码不一致。ESP32 的 Arduino 环境里， 源代码和字符串常量默认按 UTF-8 编码存放和发送； 而不少蓝牙串口 App 为了兼容单片机的使用习惯， 默认按 GBK 解码接收到的字节。 同一串字节用两种规则去解释，就必然出现乱码。 另一种情况是你用手机发送中文命令， App 按 GBK 编码发出去，ESP32 收到的字节按 UTF-8 解释，同样是乱码。

解决： 第一，也是最省事的：凡是发给手机的内容一律用英文和数字。 蓝牙命令协议本来就该用 ASCII，用英文既不会有编码问题， 也方便将来换别的 App。 第二，中文只留在 Serial.println() 里给电脑看—— 电脑串口监视器是 UTF-8 的，中文显示完全正常。 第三，如果确实要给手机发中文， 在 App 设置里找「字符编码 / Encoding」选项，从 GBK 改成 UTF-8。 第四，实在找不到设置项时，用电脑串口当作参照： 同一条消息电脑显示正常、手机显示乱码，就能确定是手机端解码的问题。

小结与练习

蓝牙这一篇的核心其实只有三件事：

第一，先选协议再写代码。 要支持 iPhone 就必须用 BLE； 只在安卓上做调试、想要最简单最快出结果，就用经典蓝牙 BluetoothSerial。 选错了协议，后面的努力全是白费。 第二，SerialBT 就是第二个串口。 它和 Serial 是同一套接口， 用法完全一致，只是 begin() 的参数是设备名而不是波特率。 把两个终端的输入喂给同一个解析函数，是既省事又可靠的工程写法。 第三，蓝牙和 Wi-Fi 抢同一根天线。 只开一个最稳；必须同时开就优先用 BLE，或者错峰使用。 遇到「两个都变慢」时，先想想是不是射频在打架， 而不是急着去改代码。

动手练习
  1. 加一个「呼吸灯」命令 f，并观察它的副作用。 收到 f 时，用 for 循环在 1 秒内 把亮度从 0 拉到 255 再回到 0，重复 3 次。 写的过程中你会发现问题：这段循环里如果用 delay()，整个蓝牙接收都会停摆， 呼吸灯跑完之前发什么命令都没反应。 请把它改成用 millis() 推进的 非阻塞呼吸灯，让它在执行期间依然能响应新命令。 这个练习能让你真正体会到「不阻塞主循环」有多重要。
  2. 加一个「延时关灯」命令 d30。 含义是「30 秒后自动关灯」。 要点：不能用 delay(30000)—— 那会让板子在这 30 秒里彻底失去响应。 正确做法是记下「应该在什么时刻关灯」， 在 loop() 里用 millis() 比对。 做完之后再想一想：如果连续发两次 d30 和 d10，应该按哪个时间关？ 把「后发的命令覆盖先发的」这个逻辑实现出来。
  3. 把它改成 BLE 版本，并列一张对照表。 用 BLEDevice、 BLEServer、 BLECharacteristic 重新实现同样的功能， 用手机上的 nRF Connect 或 LightBlue 收发数据。 BLE 没有现成的「串口」， 需要自定义一个服务和一个特征值， 并给接收特征值写一个回调函数。 做完之后列一张表，对比两种方案在 代码行数、手机端操作步骤、iPhone 是否可用、 响应延迟这四个方面的差异。 这张表可以直接放进你的实验报告或毕设文档里。
