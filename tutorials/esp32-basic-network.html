原理介绍

网络里的每一个概念，其实都在回答一个很朴素的问题： 「我要把这段数据送到哪台设备的哪个程序手里，怎么保证它能送到、并且没送错？」 下面十个小节，就是这一句话拆出来的十个答案。 不需要背，看懂「为什么需要它」就够了。

局域网的构成

先把名词对上号。你家或学校里的网络，由这么几个角色组成：

名词是什么在 ESP32 语境里
路由器 / AP把大家的设备连在一起，并负责对外上网的设备你家 WiFi 那个盒子；手机热点也是一台 AP
STA「站点」，指接入别人热点的客户端设备ESP32 平时就是这个角色（WIFI_STA）
SSIDWiFi 的名字代码里 WiFi.begin("MyWiFi", ...) 的第一个参数
信道2.4GHz 上划分的 1~13 号频段ESP32 自动跟随 AP，不用你管
DHCP自动分配 IP 的协议连上后路由器「发」一个 IP 给你的板子

你写一句 WiFi.begin()，ESP32 内部实际做了四步： 

① 扫描（Scan）
   ESP32 在 1~13 信道逐个听广播帧，找出周围的 AP，
   读出每个 AP 的 SSID、加密方式、信号强度(RSSI)、信道。

② 认证（Authentication）
   用你给的密码做 WPA2 握手（四次握手），证明双方都知道密码。
   密码错 -> 卡在这一步，串口会一直显示 Connecting... 然后 status=6

③ 关联（Association）
   路由器同意你接入，给你一个「关联 ID」，此后你的帧会被转发。
   这一步失败常因为：连接数已满、MAC 被拉黑、信号太弱。

④ 取 IP（DHCP）
   ESP32 广播 DHCP Discover，路由器回 Offer，双方确认后
   你正式获得：本机 IP、子网掩码、网关、DNS 服务器这四样东西。
   拿到 IP 才叫「真的连上了」，WiFi.status() 才会返回 WL_CONNECTED

  对应串口中的：
    Connecting to WiFi....       <-- 步骤 ②③ 进行中
    Connected! IP: 192.168.1.42  <-- 步骤 ④ 完成
关键认知：IP 不是板子自带的，是「借」来的

ESP32 芯片里只有一个固定的 MAC 地址（出厂烧好的物理地址，像身份证号）， IP 是每次连上路由器时临时分配的（像酒店房间号）。 所以「上次能连、这次连不上」很常见——换个网络、路由器重启， 你的板子就会拿到另一个 IP。代码里不要写死自己的 IP。

IP 地址

IPv4 地址是四段 0~255 的数字，例如 192.168.1.42。 它在网络里的作用相当于门牌号：数据包上写着这个号， 路由器们才能把它送到正确的设备。

地址段类型说明
192.168.x.x私有（内网）家用路由器最常用，你的 ESP32 通常拿到这类地址
10.x.x.x私有（内网）公司、学校大网络常用
172.16.x.x ~ 172.31.x.x私有（内网）也是内网段，见到不必奇怪
127.0.0.1本机回环永远指「我自己」，用于本机测试
其它公有（公网）全球唯一，能在互联网上被直接访问

为什么家里所有设备（手机、电脑、ESP32）用的都是 192.168.x.x， 却不会和邻居家的设备冲突？因为私有地址只在局域网内有效， 出门前会被路由器做一次「换牌」—— 这就是 NAT（网络地址转换）： 路由器把你家的所有设备，统一换成它自己的那一个公网 IP 发出去。

这解释了一个高频困惑

「我在学校连上了实验室的 ESP32，回家用手机怎么访问不了？」 因为 192.168.1.42 这个地址只在你学校的局域网里存在， 互联网上根本没有这条路。要在外面访问，必须用云服务器中转 （MQTT Broker 就是干这个的），或者做端口映射 / 内网穿透。 这也是物联网设备为什么普遍使用 MQTT 而不是让手机直连—— 设备主动连出去，比让外面连进来容易得多。

子网掩码

你会在串口里看到板子报出这个值：255.255.255.0。 它的作用是告诉设备：IP 地址里哪部分是「网络号」，哪部分是「主机号」。 

IP 地址    192 . 168 . 1 . 42
子网掩码   255 . 255 . 255 . 0
           └─────网络号─────┘ └主机号┘

255 表示「这一段属于网络号」，0 表示「这一段属于主机号」。
所以：
  网络号 = 192.168.1.0    （同一个网络里的设备，网络号必须相同）
  主机号 = 42             （同一网络内用主机号区分设备，不能重复）

实践判断：
  192.168.1.42  与  192.168.1.88   -> 网络号都是 192.168.1.0，同一个局域网，可直接通信
  192.168.1.42  与  192.168.2.88   -> 网络号不同，必须经过网关才能通信

另一种写法：192.168.1.42/24   （/24 就等于 255.255.255.0）

这就是「同一局域网才能直连」这句话的真正含义。 很多「设备之间连不上」的问题，本质是两者根本不在同一个网络号里—— 比如电脑连着 WiFi，ESP32 却连着另一个路由器/手机热点。

网关

网关（Gateway）就是路由器的内网地址，通常是 192.168.1.1 或 192.168.0.1。 它的意义是：当目标不在我这个局域网里时，把数据交给它转发。

你要访问ESP32 怎么做
192.168.1.88（同网段）直接发 ARP 问「谁是 .88」，拿到 MAC 后直接通信，不经过网关
8.8.8.8（外网）不同网段 → 把包交给网关 → 网关做 NAT 后发到互联网
mqtt.example.com先 DNS 问出 IP，再按上面两条判断走哪条路

在代码里，WiFi.gatewayIP() 就能读到它。 排查网络问题时这个值非常有用：把网关地址填进浏览器， 一般就能打开路由器管理页面——能打开说明你的板子和网关在同一网段、链路通畅。

DNS

人记域名（broker.emqx.io），机器只认 IP。 中间的翻译工作由 DNS（域名系统） 完成。 ESP32 用的 DNS 服务器地址，也是连上路由器时 DHCP 一并下发的 （通常是网关本身，或者 114.114.114.114、 223.5.5.5 这类公共 DNS）。 

代码：mqttClient.setServer("broker.emqx.io", 1883);

实际过程：
  ① DNS 查询：broker.emqx.io 的 IP 是多少？
     ESP32 把查询发给 DNS 服务器，收到回答，例如 52.199.×.×

  ② 建立连接：向 52.199.×.× 的 1883 端口发起 TCP 连接

所以两个环节都可能失败，报错信息也不同：
  DNS 失败  -> 串口打印 DNS Failed / getaddrinfo() failed
              原因：域名拼错、DNS 服务器不可达、压根没连上 WiFi
  连接失败  -> 串口打印 connect failed / Connection refused
              原因：域名没问题，但端口不对、被防火墙拦、Broker 挂了

分不清这两者，就只能瞎猜 —— 这是本篇最想让你带走的一个判断能力。

想手动测一次域名解析，可以用： IPAddress ip; WiFi.hostByName("broker.emqx.io", ip); 然后打印 ip，能打出来就说明 DNS 正常。

端口

IP 把数据送到设备，端口把数据送到设备上的 某个程序。端口号范围 0~65535。 

一台服务器（一个 IP）上同时跑着：网页服务、MQTT 服务、数据库、SSH 管理……
它们共用同一个 IP，靠不同的端口区分：

   192.168.1.100:80     -> 网页服务器（HTTP）
   192.168.1.100:1883   -> MQTT Broker
   192.168.1.100:3306   -> 数据库
   192.168.1.100:22     -> SSH 远程登录

比喻：IP 是「小区门牌号」，端口是「房间号」。
      快递只写门牌号不够，还得写清楚送到哪个房间。
端口协议 / 用途你会用到的场景
80HTTP访问普通网站、局域网设备网页
443HTTPS（加密的 HTTP）访问 https 站点、云平台 API
1883MQTT（明文）连 Broker，学习阶段最常用
8883MQTT over TLS（加密）生产环境连云平台
8080 / 8081备用 HTTP有些管理页面用这个
53DNS不用你配，系统自动用
客户端的端口是随机的

服务器监听固定端口（比如 Broker 监听 1883）， 但 ESP32 作为客户端连出去时，系统会临时分配一个高位端口 （比如 49152 以上）作为自己的「房间号」，用完就还。 所以「客户端不需要指定端口」——只有服务器才需要固定端口。 这也解释了一个常见误解：不要给 ESP32 配一个「本地端口」。

TCP 与 UDP

端口之上还要选一种「送快递的方式」，最常用的是 TCP 和 UDP：

对比项TCPUDP
是否先建立连接是（三次握手后才发数据）否，直接发
可靠性有确认与重传，丢了会补不保证，丢了就丢了
顺序保证按顺序到达可能乱序
速度 / 开销慢一点、包头大快、开销小
典型用途HTTP、MQTT、文件传输、配置下发视频直播、DNS 查询、广播发现、游戏
物联网里绝大多数场景都用它少数低功耗、可容忍丢包的场景
 
ESP32（客户端）                       服务器
     │                                   │
     │──── ① SYN：我想连你:1883 ────────>│
     │                                   │
     │<─── ② SYN+ACK：同意，我也准备好了 ─│
     │                                   │
     │──── ③ ACK：收到，开始发数据 ──────>│
     │                                   │
     │======== 连接建立，双向传输 ========│

这就是为什么「连不上服务器」时表现为卡住：
连 1883 端口时对方不回 SYN+ACK，程序会一直等到超时。
反过来，这也给了你一个排查手段：
  如果 SYN 都发不出去(没人应答)，说明 IP/端口/防火墙有问题；
  能握手成功但收不到数据，说明是应用层的事（Topic、QoS、认证）。

为什么 MQTT 用 TCP？因为控制指令发丢了后果很严重—— 「开阀」这条指令丢了，设备就永远不开。宁可慢一点，也要保证到。

HTTP

HTTP 是「一问一答」的协议：客户端发一个请求，服务器回一个响应，然后连接可以关掉。 浏览器之所以能显示网页，是它替你做了「拼请求、解析响应、渲染」三件事； 用 ESP32 时，拼请求这件事要你自己做（或者用 HTTPClient 库帮你做）。 

请求（ESP32 发给服务器）：
  GET /api/device?id=esp32-01 HTTP/1.1      <-- 请求行：方法 路径 版本
  Host: 192.168.1.100                       <-- 头部：必须告诉对方访问哪台主机
  User-Agent: ESP32                         <-- 头部：我是谁（可省）
  Connection: close                         <-- 头部：拿完就关连接
                                            <-- 空行：表示头部结束
  （GET 请求一般没有正文）

响应（服务器回给 ESP32）：
  HTTP/1.1 200 OK                           <-- 状态行：状态码 + 说明
  Content-Type: text/plain                  <-- 头部：正文是什么格式
  Content-Length: 12                        <-- 头部：正文有多少字节
                                            <-- 空行
  temp=25.6 C                               <-- 正文
方法用途ESP32 场景
GET取数据，参数写在 URL 里上报一个传感器值、拉一次配置
POST提交数据，数据放在正文里上传一批记录、提交表单
状态码含义你该做什么
200成功读正文
301 / 302重定向到别处找 Location 头部，或直接改用 HTTPClient（它自动跟随）
400请求写错了检查 URL 与参数拼写
401 / 403没认证 / 没权限加 Token 或换账号
404路径不存在检查路径大小写（服务器区分大小写）
500服务器内部错误不是你这边的问题，看服务器日志

MQTT

HTTP 是「打电话」：要知道对方号码（IP/域名），接通，说完挂断。 设备一多、还要互相收发，这种模式就很别扭。MQTT 换了一种思路—— 像订报纸： 

                    ┌─────────────────────┐
                    │   Broker（邮局）     │
                    │  broker.emqx.io     │
                    │  :1883              │
                    └───┬─────────────┬───┘
      publish 温度      │             │  转发给所有订阅者
   ┌────────────────────┘             └────────────────────┐
   │                                                        │
┌──┴──────────┐                                    ┌────────┴─────┐
│ ESP32 传感器 │  发布 topic: house/room1/temp      │ 手机 MQTTX   │
│ (发布者)     │  payload: 25.6                     │ (订阅者)     │
└─────────────┘                                    └──────────────┘

关键点：
  ① 发布者和订阅者互相不认识，也不需要知道对方的 IP
  ② 两边都只跟 Broker 打交道 —— 所以设备在内网也能工作
  ③ 一个 topic 可以被多个订阅者同时收到（一对多天然支持）
  ④ Broker 可以部署在公网，于是「手机在外面也能收到家里的数据」

Topic（主题）是消息的「分类标签」，用斜杠分层，例如 house/room1/temp。 订阅时可以用通配符：

通配符含义例子
+匹配一层house/+/temp 能收到 house/room1/temp，收不到 house/room1/a/temp
#匹配后面所有层（只能放最后）house/# 收到 house 下的一切
QoS含义代价
0最多一次：发出去就不管，可能丢最快，适合高频传感器数据
1至少一次：没收到确认就重发，可能重复常用，接收端要能容忍重复
2恰好一次：四次握手保证不丢不重最慢、开销最大，用于计费类场景

还有三个必须知道的机制：

  • Retain（保留消息）：发布时带 retain 标志，Broker 会为这个 topic 保存最后一条；之后新订阅的人立刻收到它，不用等下一次发布。适合「当前状态」类数据。
  • 遗嘱消息（LWT, Last Will）：连接时预先告诉 Broker「如果我掉线了，请替我发这条消息」。设备被拔电时，手机端能立刻看到 offline。
  • Keep Alive（心跳）：约定一个时间（如 15 秒），设备每隔一段时间发个心跳包；Broker 超过 1.5 倍时间没收到就判定掉线。所以代码里必须周期性调用 mqttClient.loop()，否则会被踢。
ClientID 必须唯一

每个连上 Broker 的客户端都要有一个 ID。 如果两台设备用了同一个 ID，后连上的会把先连上的踢下线， 表现为「我的设备每隔几秒就断一次」。 公共测试 Broker 上人很多，尤其容易撞 ID—— 解决办法是在 ID 里加上芯片 MAC 的后几位，保证唯一。

JSON

传感器要上报的不止一个值，用「逗号分隔的裸数据」会让接收方很难解析、也无法扩展。 于是大家约定用一种自描述的文本格式： 

裸文本（能省字节，但对方必须知道顺序）：
  25.6,58,1013

键值对（清楚，但解析要自己写）：
  temp=25.6;humi=58;press=1013

JSON（通用，任何语言都有现成解析库）：
  {"device":"esp32-01","temp":25.6,"humi":58,"press":1013}

为什么要 JSON：
  ① 名字和值在一起，顺序变了也不影响
  ② 可以嵌套：{"device":"esp32-01","data":{"temp":25.6,"humi":58}}
  ③ 几乎所有云平台、手机 App、后端框架都直接支持
  ④ 缺点：文本比二进制啰嗦，解析要花内存（ESP32 上尤其要注意）

在 ESP32 上解析 JSON，标准做法是用 ArduinoJson 库 （库管理器里搜到就能装）。它的用法分两步：把文本解析成对象，然后按键取值： 

#include <ArduinoJson.h>

// 解析收到的 JSON
JsonDocument doc;                                  // v7 的写法：自动管理内存
DeserializationError err = deserializeJson(doc, payload);
if (!err) {
  const char *dev = doc["device"];                 // 取值，缺键时返回 0/null
  float temp      = doc["temp"] | 0.0f;            // 带默认值的写法，推荐
  int   humi      = doc["data"]["humi"] | 0;
  Serial.printf("设备 %s: %.1f 度 %d%%\n", dev, temp, humi);
} else {
  Serial.printf("JSON 解析失败: %s\n", err.c_str());
}

// 生成要发送的 JSON
JsonDocument out;
out["device"] = "esp32-01";
out["temp"]   = 25.6;
char buf[128];
serializeJson(out, buf, sizeof(buf));              // 一定要给缓冲区大小
mqttClient.publish("house/room1/data", buf);
ESP32 上用 JSON 的两条纪律

① 不要解析过大的报文：JSON 解析要在内存里建树， 几 KB 的报文可能吃掉几十 KB 堆；解析前先判断长度； ② 不要用 String 拼接 JSON：用 serializeJson() + 固定大小的 char[]， 原因见上一篇「C++ 与 Arduino API」里的堆碎片实验。

硬件须知：2.4GHz 与天线

只能连 2.4GHz

ESP32-WROOM-32 的射频支持 802.11 b/g/n，2.4GHz 频段， 硬件上不支持 5GHz。 这不是配置问题，也不是库的问题——芯片里就没有那个频段的射频通路。

现象原因处理
手机热点能连，家里 WiFi 连不上家里路由器开了 5GHz，或双频合一后优先给了 5GHz进路由器设置，把 2.4GHz 的 SSID 单独起个名字（例如 MyHome_2G），代码里连它
同一层楼别人能连、我不行2.4GHz 拥挤，信道干扰严重用手机 App 看信道占用，把路由器 2.4GHz 固定到 1/6/11 中较空的一个
热点开了却找不到部分手机热点默认 5GHz在热点设置里把「频段」改成 2.4GHz（有的机型叫「兼容模式」）
学校/公司 WiFi 连不上，密码明明对的那是 WPA2-Enterprise（要用户名+证书）ESP32 支持，但需要额外代码（esp_wifi_sta_wpa2_ent_*），入门阶段建议先用手机热点
隐藏 SSID 的 WiFi 连不上扫描不到，需要主动指定代码里把 WiFi.begin(ssid, pass) 的 SSID 写全，并多等一会儿

天线布局与信号强度

ESP32-WROOM-32 模组用的是板载 PCB 天线： 模组顶部那一段弯弯曲曲的铜箔走线。它有三个使用禁忌： 

┌──────────────────────────────┐
│  天线区（不要铺铜、不要走线）  │   <-- 模组顶端这段，周围必须「空」
│   ~~~~~~~~ 弯折的 PCB 天线     │
├──────────────────────────────┤
│                              │
│      ESP32 芯片 / Flash       │
│                              │
│  GPIO 排针 …                 │
└──────────────────────────────┘

三条纪律：
  ① 手不要一直按在天线上（人体对 2.4GHz 吸收很明显，RSSI 会掉 10dB 以上）
  ② 不要给板子套金属外壳，也不要把它贴在金属机箱/铝型材上
  ③ 自己画板时，模组天线下方和前方要保留净空区（keep-out），
     否则天线被「短路」，通信距离可能从 50 米掉到 5 米

信号强度参考（串口打印 WiFi.RSSI() 得到的 dBm 值，越接近 0 越好）：
  -30 ~ -50 dBm   极好，同房间、无遮挡
  -50 ~ -65 dBm   良好，隔一堵墙可用
  -65 ~ -75 dBm   一般，能连但速率下降、偶发丢包
  -75 ~ -85 dBm   勉强，容易掉线，MQTT 会频繁断开重连
  -90 dBm 以下     基本连不上

干扰源（都会让 2.4GHz 变差）：
  微波炉、无线摄像头、蓝牙耳机密集处、USB 3.0 硬盘盒、
  大功率电机/变频器、把板子塞在金属配电箱里

所以「板子放在配电箱里，WiFi 时好时坏」几乎必然发生。 工程做法是：把 ESP32 放在箱体外侧，或者改用外置天线版本 （ESP32-WROOM-32U + IPEX 天线），把天线引到箱外。

完整代码

三个程序从易到难：先连上 WiFi 并看清自己拿到了什么， 再主动去要一次数据（HTTP），最后做到双向通信（MQTT）。 每个程序开头都有要你填的两行——WiFi 名和密码。

程序一：最小 WiFi 连接并打印 IP

/*
 * ESP32 基础篇 / 网络基础
 * 程序一：最小 WiFi 连接
 *
 * 只需要 USB 线，不需要任何外接元件。
 * 目标：看清「连上之后我到底拿到了什么」——IP、掩码、网关、DNS、信号强度。
 */

#include <WiFi.h>

// ======== 改成你自己的 WiFi（注意：必须是 2.4GHz） ========
const char *WIFI_SSID = "MyHome_2G";
const char *WIFI_PASS = "12345678";
// ========================================================

void printNetworkInfo() {
  Serial.println("---------- 网络信息 ----------");
  Serial.printf("本机 IP   : %s\n", WiFi.localIP().toString().c_str());
  Serial.printf("子网掩码  : %s\n", WiFi.subnetMask().toString().c_str());
  Serial.printf("网关      : %s\n", WiFi.gatewayIP().toString().c_str());
  Serial.printf("DNS       : %s\n", WiFi.dnsIP().toString().c_str());
  Serial.printf("MAC       : %s\n", WiFi.macAddress().c_str());
  Serial.printf("信号强度  : %d dBm\n", WiFi.RSSI());
  Serial.printf("信道      : %d\n", WiFi.channel());
  Serial.println("------------------------------");

  // 自动判断信号质量，给出人话建议
  int rssi = WiFi.RSSI();
  if (rssi > -60) {
    Serial.println("信号评价：很好，放心用");
  } else if (rssi > -75) {
    Serial.println("信号评价：一般，长期运行建议靠近路由器或换外置天线");
  } else {
    Serial.println("信号评价：偏弱，MQTT 会频繁掉线，先解决信号问题");
  }
}

bool connectWiFi(unsigned long timeoutMs) {
  Serial.printf("正在连接 WiFi: %s\n", WIFI_SSID);
  WiFi.mode(WIFI_STA);              // 只做客户端，不发热点（更省电、更稳）
  WiFi.setSleep(false);             // 关闭省电模式：响应更快，代价是电流略大
  WiFi.begin(WIFI_SSID, WIFI_PASS);

  unsigned long start = millis();
  while (WiFi.status() != WL_CONNECTED) {
    if (millis() - start > timeoutMs) {       // 关键：一定要有超时，否则会永远卡死
      Serial.printf("\n连接超时，当前状态码 = %d\n", WiFi.status());
      Serial.println("状态码含义： 1=没找到SSID(名字错/5GHz)  4=密码错  6=已断开  0=空闲");
      return false;
    }
    delay(500);
    Serial.print(".");
  }
  Serial.println("\n已连接！");
  return true;
}

void setup() {
  Serial.begin(115200);
  delay(300);

  Serial.println("========================================");
  Serial.println("ESP32 网络基础 / 程序一：最小 WiFi 连接");
  Serial.println("========================================");

  if (!connectWiFi(20000)) {
    Serial.println("本次连接失败，5 秒后重启再试");
    delay(5000);
    ESP.restart();                  // 失败就重来，比停在那里更有用
  }

  printNetworkInfo();
  Serial.println("进入心跳循环：每 5 秒打印一次状态与信号强度");
}

void loop() {
  static unsigned long lastCheck = 0;

  // 掉线自动重连：WiFi 库自己会试，这里只负责报告和兜底
  if (WiFi.status() != WL_CONNECTED) {
    Serial.println("检测到掉线，尝试重连…");
    WiFi.reconnect();
    if (connectWiFi(10000)) {
      printNetworkInfo();
    }
  }

  if (millis() - lastCheck >= 5000) {
    lastCheck = millis();
    Serial.printf("[心跳] IP=%s  RSSI=%d dBm  在线时长=%lu 秒\n",
                  WiFi.localIP().toString().c_str(),
                  WiFi.RSSI(),
                  millis() / 1000);
  }
}

程序二：HTTP GET 并解析响应

这里刻意写成两段：第一段用最原始的 WiFiClient 手拼请求，让你看清楚 HTTP 请求长什么样； 第二段用 HTTPClient 库做同样的休息，体会封装带来的便利。 

/*
 * 程序二：HTTP GET 请求
 *
 * 目标地址用了 example.com（一个专门给教学用的稳定页面）。
 * 想改成局域网设备（比如自己电脑上跑的网页）也可以：
 *   换成本机 IP，例如 http://192.168.1.100/
 *   在电脑上用 python -m http.server 8000 起一个最简服务器即可。
 */

#include <WiFi.h>
#include <HTTPClient.h>

const char *WIFI_SSID = "MyHome_2G";
const char *WIFI_PASS = "12345678";

const char *HOST = "example.com";     // 不带 http://
const int   PORT = 80;
const char *PATH = "/";

// ---------- 方式 A：WiFiClient 手拼请求（看清 HTTP 的真面目） ----------
void doGetRaw() {
  WiFiClient client;

  Serial.printf("\n[手拼请求] 正在连接 %s:%d …\n", HOST, PORT);
  if (!client.connect(HOST, PORT)) {          // 这一步里包含 DNS 解析 + TCP 握手
    Serial.println("连接失败：域名解析不了，或端口被防火墙拦住");
    return;
  }

  // 请求必须严格按格式拼：请求行 + 头部 + 空行
  client.printf("GET %s HTTP/1.1\r\n", PATH);
  client.printf("Host: %s\r\n", HOST);
  client.print("User-Agent: ESP32\r\n");
  client.print("Connection: close\r\n");     // 拿完就关，省得自己管理连接
  client.print("\r\n");                      // 空行 = 请求头结束，绝对不能漏

  // 等服务器响应，最多等 5 秒
  unsigned long start = millis();
  while (!client.available() && millis() - start < 5000) {
    delay(10);
  }

  if (!client.available()) {
    Serial.println("没等到任何响应");
    client.stop();
    return;
  }

  // 逐行读响应：先读状态行和头部，遇到空行后才是正文
  Serial.println("[响应状态行与头部]");
  bool headerDone = false;
  int  bodyBytes  = 0;

  while (client.connected() || client.available()) {
    if (!client.available()) { delay(5); continue; }

    String line = client.readStringUntil('\n');   // 只在演示里用 String，实际项目请用 char[]
    line.trim();

    if (!headerDone) {
      Serial.println(line);
      if (line.length() == 0) {                   // 空行 = 头部结束
        headerDone = true;
        Serial.println("[正文（前 300 字节）]");
      }
    } else {
      if (bodyBytes < 300) {
        Serial.print(line);
        Serial.print(' ');
        bodyBytes += line.length() + 1;
      }
    }

    if (!client.connected() && !client.available()) break;
  }
  Serial.println("\n[手拼请求] 完成");
  client.stop();
}

// ---------- 方式 B：HTTPClient 库（实际项目推荐） ----------
void doGetWithLibrary() {
  HTTPClient http;

  String url = String("http://") + HOST + PATH;
  Serial.printf("\n[HTTPClient] GET %s\n", url.c_str());

  http.begin(url);                       // 开始一个请求（内部会做 DNS + 连接）
  http.setTimeout(5000);
  int code = http.GET();                 // 真正发出请求，返回状态码

  if (code > 0) {
    Serial.printf("状态码: %d\n", code);
    if (code == 200) {
      String body = http.getString();
      Serial.printf("正文长度: %u 字节\n", body.length());
      Serial.println("正文开头: ");
      Serial.println(body.substring(0, 200));
    } else if (code == 301 || code == 302) {
      Serial.println("被重定向了，可以读取 Location 头部或直接换用 https 地址");
    } else {
      Serial.println("服务器返回了非 200，检查路径与权限");
    }
  } else {
    // 负数是库定义的错误码，例如 -1 连接失败、-11 超时
    Serial.printf("请求失败，错误码 %d\n", code);
  }

  http.end();                            // 释放连接
}

void setup() {
  Serial.begin(115200);
  delay(300);

  Serial.println("========================================");
  Serial.println("ESP32 网络基础 / 程序二：HTTP GET");
  Serial.println("========================================");

  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }
  Serial.printf("\n已连接，本机 IP: %s\n", WiFi.localIP().toString().c_str());

  doGetRaw();              // 先用原始方式看一遍
  doGetWithLibrary();      // 再用库写一遍做对比

  Serial.println("\n进入循环：每 30 秒请求一次，观察稳定性");
}

void loop() {
  static unsigned long lastReq = 0;

  if (millis() - lastReq >= 30000) {
    lastReq = millis();

    if (WiFi.status() != WL_CONNECTED) {
      Serial.println("WiFi 掉线，重连中…");
      WiFi.reconnect();
      delay(3000);
      return;
    }

    HTTPClient http;
    http.begin(String("http://") + HOST + PATH);
    http.setTimeout(5000);
    int code = http.GET();
    Serial.printf("[%lu 秒] 状态码 %d，空闲堆 %u 字节\n",
                  millis() / 1000, code, ESP.getFreeHeap());
    http.end();
  }
}

程序三：MQTT 发布与订阅

这个程序用公共测试 Broker broker.emqx.io， 不需要注册。它做三件事：连上 Broker、每 5 秒发布一条 JSON、 同时订阅自己的主题把消息收回来（用来验证链路是通的）。 

/*
 * 程序三：MQTT 发布 + 订阅（最小可用版）
 *
 * 需要安装两个库（Arduino IDE -> 工具 -> 管理库 里搜索安装）：
 *   ① PubSubClient   作者 Nick O'Leary
 *   ② ArduinoJson    作者 Benoit Blanchon
 *
 * 用公共 Broker broker.emqx.io:1883 做演示，无需注册。
 * 生产环境请换成自己的 Broker（自建或云平台），并启用认证。
 */

#include <WiFi.h>
#include <PubSubClient.h>
#include <ArduinoJson.h>

const char *WIFI_SSID = "MyHome_2G";
const char *WIFI_PASS = "12345678";

const char *MQTT_HOST = "broker.emqx.io";   // 公共测试 Broker
const int   MQTT_PORT = 1883;

// 主题：用 + 通配符订阅「本设备的所有状态」，用固定主题发布数据
const char *TOPIC_PUB   = "mcustudy/esp32/demo/data";
const char *TOPIC_STATE = "mcustudy/esp32/demo/state";
const char *TOPIC_SUB   = "mcustudy/esp32/demo/#";     // 订阅 demo 下所有消息

WiFiClient   espClient;
PubSubClient mqtt(espClient);

// 客户端 ID：加 MAC 后 6 位保证唯一，避免和别人撞 ID 被踢
char clientId[32];

// ---------- 收到订阅消息时被调用 ----------
void onMqttMessage(char *topic, byte *payload, unsigned int length) {
  // 注意：payload 不是以 \0 结尾的，必须自己复制并补上结束符
  static char buf[256];
  unsigned int n = (length < sizeof(buf) - 1) ? length : sizeof(buf) - 1;
  memcpy(buf, payload, n);
  buf[n] = '\0';

  Serial.printf("\n[收到消息] topic=%s 长度=%u\n", topic, length);
  Serial.printf("原始内容: %s\n", buf);

  // 如果内容是 JSON，就解析出来给大家看
  if (buf[0] == '{') {
    JsonDocument doc;
    DeserializationError err = deserializeJson(doc, buf);
    if (!err) {
      const char *from = doc["device"] | "unknown";
      float temp       = doc["temp"] | 0.0f;
      Serial.printf("解析结果: 来自 %s, 温度 %.1f 度\n", from, temp);
    } else {
      Serial.printf("JSON 解析失败: %s\n", err.c_str());
    }
  }
}

// ---------- 连接 Broker，并在这里完成订阅 ----------
bool connectMqtt() {
  Serial.printf("正在连接 Broker %s:%d …\n", MQTT_HOST, MQTT_PORT);

  // 遗嘱消息：ESP32 掉线时由 Broker 代发，让手机端立刻知道设备离线
  const char *willMsg = "{\"device\":\"esp32-01\",\"status\":\"offline\"}";

  if (mqtt.connect(clientId, NULL, NULL, TOPIC_STATE, 1, true, willMsg)) {
    Serial.println("Broker 连接成功");

    // 先发一条在线状态（retain=true，新订阅的人立刻能看到）
    mqtt.publish(TOPIC_STATE, "{\"device\":\"esp32-01\",\"status\":\"online\"}", true);

    // 订阅必须在连接成功之后做；断线重连后要重新订阅
    if (mqtt.subscribe(TOPIC_SUB, 1)) {
      Serial.printf("已订阅: %s\n", TOPIC_SUB);
    } else {
      Serial.println("订阅失败");
    }
    return true;
  }

  Serial.printf("连接失败，状态码 = %d（-2=网络问题 -3=服务器不可达 -4=账号密码错 -5=未授权）\n",
                mqtt.state());
  return false;
}

void setup() {
  Serial.begin(115200);
  delay(300);

  Serial.println("========================================");
  Serial.println("ESP32 网络基础 / 程序三：MQTT 收发");
  Serial.println("========================================");

  // ---- 连 WiFi ----
  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }
  Serial.printf("\nWiFi 已连接，IP: %s\n", WiFi.localIP().toString().c_str());

  // ---- 组装唯一 ClientID ----
  uint8_t mac[6];
  WiFi.macAddress(mac);
  snprintf(clientId, sizeof(clientId), "esp32-%02X%02X%02X", mac[3], mac[4], mac[5]);
  Serial.printf("ClientID: %s\n", clientId);

  // ---- 配置 MQTT ----
  mqtt.setServer(MQTT_HOST, MQTT_PORT);
  mqtt.setCallback(onMqttMessage);
  mqtt.setKeepAlive(15);            // 15 秒心跳；必须配合下面 loop() 里的 mqtt.loop()
  mqtt.setBufferSize(512);          // 默认 256 字节，发 JSON 常常不够

  connectMqtt();
}

void loop() {
  // ① 维持 MQTT：这一句负责发心跳、收消息、处理重传。
  //    不调用它，15 秒后就会被 Broker 判定掉线！
  if (!mqtt.connected()) {
    static unsigned long lastTry = 0;
    if (millis() - lastTry >= 5000) {      // 失败后 5 秒重试，别狂刷
      lastTry = millis();
      connectMqtt();
    }
  } else {
    mqtt.loop();
  }

  // ② 每 5 秒发布一次传感器数据（这里用随机数模拟，可换成真实读数）
  static unsigned long lastPub = 0;
  if (millis() - lastPub >= 5000 && mqtt.connected()) {
    lastPub = millis();

    float temp = 20.0 + (random(0, 100) / 10.0);   // 20.0 ~ 29.9
    int   humi = 40 + random(0, 30);               // 40 ~ 69

    // 用 JSON 组织数据（char[] + serializeJson，绝不用 String 拼接）
    JsonDocument doc;
    doc["device"] = "esp32-01";
    doc["temp"]   = serialized(String(temp, 1));   // 保留 1 位小数
    doc["humi"]   = humi;
    doc["rssi"]   = WiFi.RSSI();
    doc["uptime"] = millis() / 1000;

    char payload[192];
    size_t len = serializeJson(doc, payload, sizeof(payload));

    Serial.printf("\n[发布] %s (%u 字节)\n%s\n", TOPIC_PUB, (unsigned)len, payload);

    bool ok = mqtt.publish(TOPIC_PUB, payload);
    Serial.printf("发布结果: %s\n", ok ? "成功" : "失败（缓冲区太小或连接已断）");
  }
}

关键代码解析

代码作用易错点
WiFi.mode(WIFI_STA)设为客户端模式不设也能连，但混用 AP 模式会多耗电、更容易掉线
WiFi.setSleep(false)关省电，响应更快电池供电的项目反而应保持开启省电
while (WiFi.status() != WL_CONNECTED)等待连接必须加超时，否则 WiFi 出问题时程序永远卡在这里
WiFi.localIP()读出本机 IP不能用 Serial.println(WiFi.localIP()) 直接打印，要 .toString().c_str()
WiFi.RSSI()信号强度（dBm）负值，越接近 0 越好；-75 以下要处理信号问题
client.connect(host, port)TCP 连接（含 DNS）返回 false 时分不清是 DNS 还是端口问题——先单独测 DNS
"Connection: close\r\n" + 空行手拼 HTTP 必需的收尾漏掉空行服务器会一直等你的头部，表现为「没响应」
http.GET()发请求并返回状态码负数是错误码，别都当成「HTTP 状态码」来打印
mqtt.setCallback()注册收消息的回调必须在 connect() 之前设置
mqtt.subscribe(topic)订阅主题断线重连后必须重新订阅（所以写在 connectMqtt 里）
mqtt.loop()维持连接、收发消息不调用 = 心跳发不出去 = 15 秒后被踢
mqtt.setBufferSize(512)加大收发缓冲区默认 256 字节，发稍长的 JSON 会静默失败
payload 不是字符串回调里的 payload 需要自己补 \0直接当 char* 打印会读到越界内存

为什么自己发的消息自己也能收到？

因为你正在同时扮演发布者和订阅者，而且订阅的通配符 mcustudy/esp32/demo/# 覆盖了自己发布的 …/data。 MQTT 默认会把消息回送给同一个客户端（除非协议版本特性另有约定）， 所以这恰好是验证链路通畅的最省事办法： 能收到自己的消息 = WiFi 通、Broker 通、Topic 通。

验证方法一：用手机热点

  1. 手机上打开「个人热点」，在设置里把频段改成 2.4GHz（有的机型叫「兼容模式」或「最大化兼容性」）。
  2. 把热点的名字和密码填进代码的 WIFI_SSID / WIFI_PASS。
  3. 上传后打开串口：看到 Connected! 说明成功；IP 一般是 192.168.43.x 之类。
  4. 此时电脑也连同一个热点（或用数据线看串口即可），就能做程序二的局域网 HTTP 测试。

验证方法二：用 MQTTX 看消息、发消息

  1. 电脑上装 MQTTX（免费的 MQTT 客户端工具，跨平台）。
  2. 新建连接：Host 填 broker.emqx.io，Port 填 1883，其它留默认，点连接。
  3. 订阅主题填 mcustudy/esp32/demo/#（和你代码里的 TOPIC_SUB 一致），QoS 选 1。
  4. 等最多 5 秒，就能看到 ESP32 发上来的 JSON，还能展开看每个字段。
  5. 反向验证：在 MQTTX 里向 mcustudy/esp32/demo/cmd 发布一条 {"led":1}，ESP32 的串口应立刻打印「收到消息」。
公共 Broker 的注意事项

broker.emqx.io 是公开测试服务器： 任何人只要猜到你的主题就能看到消息， 所以别发真实数据、别放密码。 做作业够用；做产品请换自建 Broker（如 EMQX、Mosquitto） 或云平台（阿里云 IoT、OneNET 等），并启用账号密码与 TLS（8883 端口）。

常见报错排查方案

网络问题的排查有一个通用套路： 先确认拿到了 IP → 再确认能到网关 → 再确认 DNS 能解析 → 最后才看应用层。 下面每条都按「现象 → 原因 → 解决」写。

现象：串口一直打印点，最后「连接超时，状态码 = 1」，连不上 WiFi

原因： 状态码 1（WL_NO_SSID_AVAIL）表示没找到这个 SSID。常见原因： ① SSID 拼错或大小写不符（MyWiFi 和 mywifi 是两个网络）； ② 目标路由器是 5GHz，ESP32 硬件不支持； ③ 双频合一的路由器把 2.4GHz 藏了；④ 距离太远/信号太弱。 （状态码 4 是密码错，6 是连上后断开，别混。）

解决： ① 用手机搜一遍，确认能看到这个 2.4GHz 网络，名字逐字符对着抄； ② 路由器里把 2.4GHz 的 SSID 单独命名（如 MyHome_2G），连它； ③ 用手机热点（改 2.4GHz 频段）做对照实验——能连热点说明板子没问题，是路由器的事； ④ 把 RSSI 打印出来，低于 -75 就先解决距离与遮挡。

现象：WiFi 连上了、IP 也拿到了，但连服务器/ Broker 一直失败

原因： 拿到 IP 只说明你进了局域网，不代表能到达目标。可能： ① 端口写错（MQTT 是 1883，不是 80 或 8883）； ② 目标服务器只监听本机（127.0.0.1），不接受外部连接； ③ 服务器所在电脑的防火墙没放行该端口； ④ 两者不在同一网段（比如板子连手机热点、服务器在另一个 WiFi）； ⑤ 公司/学校网络禁止对外连接非 80/443 端口。

解决： ① 用电脑先验证：命令行执行 telnet 服务器IP 1883（或 Test-NetConnection 服务器IP -Port 1883），能连上说明服务端没问题； ② 确认板子和服务器的前三段 IP 相同（在同一网段）； ③ 关掉电脑防火墙试一次，能通就是防火墙问题，再按需放行； ④ 服务器程序要监听 0.0.0.0 而不是 127.0.0.1； ⑤ 替换成公共 Broker 做对照：能连公共的 = 你的服务器/网络策略问题。

现象：MQTT 打印「连接失败，状态码 = -2」或 -3，连不上 Broker

原因： -2 是网络层失败（DNS 解析不了、根本没网）， -3 是服务器不可达（地址/端口错、被墙、Broker 不在线）， -4 是账号密码错，-5 是未授权。 公共 Broker 域名写错一个字母就会得到 -2（解析失败）。

解决： ① 先用 MQTTX 用完全相同的地址、端口、账号连一次—— 电脑能连、板子连不上，说明是板子的网络出口问题；两边都连不上，说明参数写错了； ② 确认端口：明文 1883，TLS 8883（用 8883 时必须配 WiFiClientSecure，否则必然失败）； ③ 只填域名不填 mqtt:// 前缀（setServer 只接受主机名）； ④ 有账号的平台要把用户名密码传给 mqtt.connect(clientId, user, pass)。

现象：发布返回成功，但手机/MQTTX 收不到消息

原因：按可能性从高到低—— ① Topic 不匹配：大小写不同、层级不同、多一个斜杠， 或订阅用了 +/# 却放错了位置（# 只能放末尾）； ② 订阅在连接之前做，或者断线重连后忘了重新订阅； ③ 发布者和订阅者连的是不同的 Broker（一个 emqx、一个 mosquitto）； ④ QoS 0 在网络不稳时确实可能丢； ⑤ 订阅方连上了但没点「订阅」。

解决： ① 拿串口打印的 topic 与 MQTTX 里订阅的字符串逐字符对比（最常见就是这里）； ② 把 subscribe() 写进 connectMqtt() 成功分支里，保证每次重连都订阅； ③ 先让 ESP32 订阅自己的发布主题（本页程序三就是这么做的）， 能收到自己的消息说明链路没问题，问题一定在另一端的订阅； ④ 关键数据把 QoS 提到 1，并检查 mqtt.setBufferSize() 是否够大； ⑤ 用 mqtt.publish() 的返回值判断是否真的发出（返回 false 通常是缓冲区太小）。

现象：串口打印 DNS Failed、getaddrinfo() failed，或域名解析出来是 0.0.0.0

原因： 域名到 IP 这一步失败了。可能是：① 域名拼错（broker.emqx.io 写成 broker.emqx.com）；② WiFi 其实没连上（先确认 WL_CONNECTED）； ③ 路由器没有下发 DNS，或指定的 DNS 服务器不可达；④ 该网络做了 DNS 拦截/需要认证（校园网常见）。

解决： ① 单独测解析：IPAddress ip; if (WiFi.hostByName("broker.emqx.io", ip)) Serial.println(ip);； ② 打印 WiFi.dnsIP() 看是不是 0.0.0.0，是的话手工指定： WiFi.config(WiFi.localIP(), WiFi.gatewayIP(), IPAddress(223,5,5,5));； ③ 临时用直连 IP 做实验（把域名换成解析好的 IP），能连上就锁定是 DNS 问题； ④ 校园网/酒店网络常需网页认证，换手机热点验证。

现象：MQTT 每隔十几秒就断开重连一次（或另一台设备一上线，我就掉线）

原因： ① ClientID 冲突：两台设备用了同一个 ID， Broker 认为「同一个人换了连接」，把先连的踢掉； ② 没有及时调用 mqtt.loop()： 你在 loop() 里写了 delay(30000) 之类的长延时， 心跳发不出去，超过 keepAlive 的 1.5 倍就被判定掉线； ③ 信号太弱导致 TCP 超时。

解决： ① ClientID 里加 MAC 后缀保证唯一（本页程序三的 snprintf(clientId, …) 就是干这个的）； ② 用 millis() 做定时，保证 loop 里不出现长时间阻塞； ③ 每次都调用 mqtt.loop()，把 keepAlive 设为 15~30 秒； ④ 打印 RSSI，弱信号先解决天线与位置问题； ⑤ 用 mqtt.state() 把断线原因打出来，别只看「重连中」。

现象：程序一启动就连不上，串口反复出现 brownout detector was triggered 并重启

原因： 供电不足。WiFi 射频在连接与发射瞬间电流峰值可达 500mA 以上， 如果用的是劣质 USB 线、电脑前置 USB 口、或 3.3V 稳压能力不足的模块， 电压会瞬间跌落，触发 ESP32 的欠压检测而复位。 典型特征是程序刚跑到 WiFi.begin 就重启。

解决： ① 换一根粗一点的数据线，插到电脑后面板 USB 口或 5V/2A 充电头； ② 外接电源时保证 5V 端能提供 1A 以上，并靠近板子的 VIN 加 470uF 以上电解电容； ③ 别从 ESP32 的 3.3V 引脚给舵机/继电器供电（那会把电压拉垮）； ④ 详细判据见基础篇「3.3V 供电与 GPIO 安全」。

现象：程序偶尔「假死」——串口不再输出，按 EN 才恢复；或一直卡在某个 while 里

原因： 典型的阻塞式等待没有超时。 例如 while (WiFi.status() != WL_CONNECTED) { delay(500); } 在路由器重启、密码改掉时永远出不来； client.connect() 在没有响应时也会等到超时。 现象就是程序「看着在跑，其实什么都没做」。

解决： ① 所有等待循环都加时间上限，超时后打印状态码并重启或重试 （本页程序一的 connectWiFi(20000) 就是这个思路）； ② 用状态机而不是阻塞等待：把「连接中」当成一个状态，在主循环里推进； ③ 加一个看门狗式的自检：连续 N 次心跳失败就 ESP.restart()； ④ 打印 millis() 让每次循环都有时间戳，卡住时一眼能看到最后停在哪一步。

现象：HTTP 请求返回乱码、内容不全，或者状态码是 301/302 却拿不到正文

原因： ① 服务器返回了 Content-Encoding: gzip，而你的程序把它当纯文本读； ② 用了 Transfer-Encoding: chunked（分块传输）， 正文里混着长度标记，手写解析很容易读错； ③ 301/302 重定向后正文其实是「请去另一个地址」的提示页； ④ 读到一半就 client.stop()，正文被截断。

解决： ① 请求时加一行 Accept-Encoding: identity，明确要求不要压缩； ② 优先使用 HTTPClient，它替你处理重定向与分块； ③ 按 Content-Length 决定读多少字节，别用「读到没有为止」的思路； ④ 需要 HTTPS 时用 WiFiClientSecure，并给它根证书或 setInsecure()（仅测试用，生产必须校验证书）； ⑤ 打印状态码 + 前几个头部的原文，先看清服务器到底回了什么。

现象：JSON 解析失败（InvalidInput / NoMemory），或解析出来全是默认值

原因： ① 收到的 payload 不是以 \0 结尾—— MQTT 回调里的 payload 是「指针 + 长度」， 直接丢给 deserializeJson 会读到缓冲区外的垃圾，必须自己复制并补结束符； ② 缓冲区太小：报文几 KB 时，JSON 文档需要更多堆内存； ③ 字段名大小写不一致（temp 与 Temp 是两个键）， 取值失败就落到默认值上； ④ 库里发的是「数字」而你按字符串取（或反之）—— 注意 doc["humi"] | 0 这种带默认值的写法能避免大部分坑。

解决： ① 先原样打印收到的字节（含长度），确认它是不是完整 JSON； ② 回调里 memcpy(buf, payload, len); buf[len] = '\0'; 之后再解析； ③ 发之前用 serializeJson(doc, buf, sizeof(buf)) 并检查返回值是否被截断； ④ 报文大就改用外层「主题分层」的小消息，别硬塞； ⑤ 打开发送端与接收端的字段名对照表，逐字符核对一遍。

小结与练习

这一页要你记住的七件事

  • IP 是借来的（DHCP 分配），MAC 才是出厂固定的身份；同网段直连，跨网段走网关。
  • 子网掩码决定「谁和我是一伙的」：255.255.255.0 意味着前三段相同的设备才能直接互通。
  • IP 找设备，端口找程序；服务器监听固定端口（MQTT 1883），客户端端口随机。
  • DNS 失败与连接失败要分清：前者是「不知道去哪」，后者是「知道去哪但到不了」。
  • TCP 可靠但慢，UDP 快但可能丢；物联网开关类指令一律走 TCP（MQTT）。
  • MQTT 是发布/订阅：设备只跟 Broker 打交道，所以内网设备也能把数据送到公网。
  • ESP32 只支持 2.4GHz，且天线怕遮挡与金属；RSSI 低于 -75 先修硬件再查代码。
