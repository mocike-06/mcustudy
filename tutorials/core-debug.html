调试方法与工具

前面三十二篇，讲的都是「系统怎么正常工作」：CPU 怎么执行指令、中断怎么打断主程序、定时器怎么数出 1 毫秒、DMA 怎么绕过 CPU 搬数据。这一篇反过来，讲「系统不正常的时候，你怎么知道是哪里不正常」。 这是第二层的最后一篇，也是十篇里唯一一篇「手艺」课。它不介绍任何一个新外设，而是给你一整套把故障从「一块板子不听话」收敛到「就是这一行」的工作方法：先分层再二分、每类工具只解决一类问题、偶发故障先量化频率再谈修复。

你会拿到的东西很具体：一张 SWD 接线图（以及不接 VREF 为什么检不到芯片）、四类断点的适用范围与数量上限、printf 的三条替代路径及其时间开销对比、一份能直接抄进工程的环形日志缓冲与断言宏、复位源与备份寄存器的完整实现、CPU 占用率与栈水位的测量代码，以及一张「什么现象该先动哪件工具」的对照表。 看完它，你应该不再靠「改一改再看看」来解决问题。

为什么需要它

先讲一个真实到有点残酷的场景，它几乎发生在每一个做完毕设的人身上。

你的板子已经能跑三天了：OLED 显示正常、按键响应正常、串口上报正常。第四天早上你来看，它死了——屏幕停在半路，串口一句不发，按复位又活过来，然后过几个小时再死一次。于是你开始「调试」：先怀疑 OLED 刷屏太慢，把刷新率砍一半；还是死。再怀疑栈不够，把几个大数组改成全局；还是死。又怀疑是中断优先级，把串口的优先级调高；还是死。三天过去，你把七八个地方都改了一遍，故障频率从「一天一次」变成「两天一次」——你甚至说不清到底是哪一处改动起了作用，因为你是同时怀疑一切、又同时改了一堆东西。

这不是能力问题，是方法问题。上面这段过程里，没有一个动作是「能得出确定结论的实验」：每次改动都同时动了多个变量，每次观察都靠肉眼等，结论只能靠感觉。真正会调试的人做的是完全不同的另一件事：他先问「这个故障大概在哪一层」，再设计一个能把一整类原因排除掉的实验，然后才动手。同样的三天，他能把故障钉到某一行。

三种最贵的「调试」方式
  • 凭感觉改代码。不知道原因，但觉得「这里可能有问题」，改完烧进去看看。改对了也不知道为什么对，改错了还多了一个变量。
  • 到处加 printf，然后肉眼找。日志本身会改变时序（后文 3.5 会算给你看：一条 32 字符的日志在 115200 波特率下要 2.78 ms），于是你既在看现象，又在制造现象。
  • 把「改完没再出现过」当成修好了。偶发故障的「没再出现」很可能只是概率没到。见 3.4：观测频率每小时 0.125 次时，蹲两小时能碰上的概率只有 22%。

这一篇在讲什么：不是某个工具，而是「用工具的顺序」

市面上的调试教程大多按工具分章：这一章讲 Keil 的断点怎么设，下一章讲串口怎么打印，再下一章讲示波器怎么用。你照着一路学下来，工具箱是满了，可面对一块死掉的板子时依然不知道先动哪个。这篇的组织方式是反过来的：先讲「缩小的顺序」，再讲每种工具只能回答哪一类问题。

因为调试器、串口打印、示波器、逻辑分析仪这四件东西，它们的视野完全不重叠：调试器只看得见 CPU 内部的数字世界（寄存器、内存、PC），它对你板子上的 3.3 V 到底是不是 3.3 V 一无所知；示波器看得见引脚上的电压，但不知道你的状态机走到了第几个状态；逻辑分析仪能告诉你 I²C 从机到底应没应答，但它看不见你的变量。用错工具的典型症状是：拿着一把只量电压的表笔，反复读代码。这一篇的核心内容之一，就是那条「什么时候该放下调试器去拿表笔」的分界线。

这一篇的定位：它是前面九篇的「使用说明书」

回头看这一层的前面几篇，你会发现它们各自都埋了一个「调试接口」：中断那一篇讲了怎么数中断次数、怎么看 NVIC 寄存器；定时器那一篇讲了怎么用输出比较在引脚上产生一个精确的脉冲（这就是最轻量的「打印」）；串口那一篇讲了怎么从错误标志位看出 ORE 溢出。温度计一样的寄存器窗口、__BKPT 内建函数、栈帧的读法——这些都是零件，这一篇把它们组装成一套工作流程。

需要说明的是：汇编层面「怎么看现场」不在这篇的范围里。怎么从 .lst 里读出出错的那条指令、HardFault 压栈的那 8 个字（xPSR / PC / LR / R12 / R3~R0）分别是什么、怎么用 naked 函数把栈帧取出来——那是第 25 篇《CPU 架构与指令执行》已经讲透的内容，本篇凡是涉及这一层的地方都会直接指过去，不重复。这一篇关心的是：怎么让「需要读现场」这件事本身变得尽量少发生，以及真发生时用什么手段把现场留住。

一句话概括本篇要建立的习惯

每次动手之前，先能说出这句话：「我这次要排除的是哪一类原因，如果结果是 A 就说明……，如果是 B 就说明……」。说不出来，就先别改代码——先想清楚这个实验能证明什么。

核心概念

这一节有八个子节，它们的关系是「一条主线 + 七件工具」：2.1 讲方法论（主线），2.2 到 2.8 讲每类工具各自能回答什么问题、以及它在哪里会骗你。如果你只有十分钟，读 2.1 和 2.3 就够了——那两节是本篇最值钱的部分。

调试的本质：把「哪里可能错」收敛到「就是这一行」

先给调试下一个能指导行动的定义：调试是一个不断缩小候选集的过程。故障刚出现时，可能出错的地方有几千处——每个函数、每个寄存器配置、每根线、每个电源轨都算一个候选。调试的每一步动作，都应该是一次能把候选集显著切小的实验，直到候选集里只剩一个元素，那就是原因。

这个定义能立刻判掉一大批「看起来在调试」的行为。把 while(1) 里的某个延时从 10 ms 改成 5 ms、再烧进去看看——这不是实验，因为如果故障消失了，你不知道是因为延时常数、还是因为重新编译、还是因为刚才拔插了一次电源线。它没有排除任何东西，只是引入了一个新变量。

判断一个动作是不是好实验，只有一条标准：做完之后，我能明确地说出「哪一大类原因被排除了」。比如「我在 ADC 中断入口翻转一个 GPIO，示波器上看到 1 kHz 的方波」——这个实验一次性排除了「定时器没配好」「中断没使能」「NVIC 优先级被屏蔽」三大类原因，候选集直接砍掉三分之一。

先分层，再二分：一张五层漏斗

候选集不能乱切，因为单片机系统是分层依赖的：电源不对，时钟必然不对；时钟不对，外设配置再正确也不工作；外设不工作，驱动层的所有逻辑都是空谈。下层坏了，上层一定表现异常；所以从上往下查，你永远在查「症状」；从下往上查，每确认一层就能永久排除一层。这就是「先分层」的含义。

漏斗的形状本身也在说明一件事：越靠下的层，候选越多、越难查。所以真正省时间的做法是「用最便宜的实验，砍掉最大的嫌疑块」——量一次电压只要三十秒，却能把第一层整个盖棺；而如果你跳过这一步直接在第五层下断点，可能要查两天才发现 3.3 V 在电机启动瞬间掉到 2.6 V。

「盖棺」这个词值得记住

每一层确认正常之后，要在心里（或本子上）明确地说一句「这一层盖棺了，后面不再怀疑它」。这样做的收益是：当故障第二次、第三次出现时，你不会又回到「会不会是电源问题」的循环里去。不做盖棺的人会在同一层反复挖。

二分法：把「一个点」变成「一半」

分层解决的是「切哪一块」，二分解决的是「切得多快」。最直接的二分是注释掉一半功能，看故障还在不在：在则凶手在剩下的那一半里，不在则凶手在被注释掉的那一半里。

有三种好用的二分变体，全都比「注释代码」更精细：

  • 边界打点。在两个模块的交界处（函数入口、DMA 完成回调、中断入口）翻转一个空闲 GPIO 或给一个全局计数器加一，看这个边界有没有被跨过。一个 GPIO 只有开和关两种状态，却能回答「这里到底执行了没有」这个最根本的问题。
  • 时间二分。用时间戳（第 4 节的环形日志就是为这个设计的）记录事件序列，把故障发生前最后几个事件按时间排出来。事件序列一旦排出来，凶手通常自己就跳出来了。
  • 版本二分。如果故障是「某天开始有的」，用版本控制每退一个提交跑一次（提交少就手工看 git log -p，提交多就让 git bisect 自动做二分）。这是唯一能保证「只改了一个变量」的二分方式。

最小可复现工程：剥离的过程本身就是排查

偶发故障最大的敌人是「工程太大，谁也说不清哪里有关」。这时候要做的不是接着查，而是先把问题从大工程里剥出来：新建一个只包含复现所需最小功能的工程，每次搬过来一块，看故障是否跟着过来。

为什么说「剥的过程本身就是排查」？因为剥离强迫你回答一连串平时从不问的问题：这段初始化到底是必要的吗？这个中断是谁使能的？这个全局变量究竟被谁写？很多人剥到一半就找到了原因——不是因为剥掉了什么，而是因为第一次真正看清了依赖关系。另外，最小工程还有一个附带价值：它能拿去论坛提问，也能作为回归测试留在仓库里。

版本回退、对照实验与统计证据

「昨天还好好的」这句话必须被拆成三个问题：代码变了吗、环境变了吗、硬件动过吗。凭记忆回答这三问的准确率很低，正确做法是拿证据：git diff 与 git status 看代码；看工具链版本与优化等级有没有被动过（有时候是 IDE 自动升级了编译器，或你不小心把构建配置从 Debug 切到 Release）；想一想板子是不是被换了供电方式、换了杜邦线、插拔过模块。经验上，「昨天还好好的」里相当一部分根本不是代码问题，而是供电、接线或编译配置变了。

对照实验的原则是一次只动一个变量。手上最好有两块板：如果 A 板和 B 板都能复现，说明是共性设计问题（软件或原理图）；只有 A 板能复现，就先怀疑焊接、器件个体、接线——把 A 板的问题件换到 B 板上，看故障会不会「跟着元件走」。这就是「换一块板/换一个电源」的价值：它能一刀切开「设计错」和「这一块坏」。

统计证据是偶发故障的前提。「跑了一晚上死了一次」和「每十分钟死一次」是两个完全不同量级的故障，排查策略也完全不同：前者需要的是「留住现场」（第 4 节的环形日志、复位源记录），后者需要的是「复现并观察」。所以在动手之前，先花半小时把频率量出来：让固件自己记录开机时长、复位次数、复位源，跑上十几个小时，算出「每小时多少次」。这个数字后面还有两个用途：设计复现实验的时长（3.4 会算），以及验证修复效果（同样的公式反过来用）。

「感觉变少了」不是证据

偶发故障的频率本来就带随机性：真实概率每小时 0.5 次，你观测三小时也可能一次都不出现。所以在没有量化频率之前，「改完以后一晚上没死」这个观察的信息量几乎为零。先量化，再修复，再量化——这三步缺一步，你都只是在赌。

把每一次实验写下来

最后给一个看起来最笨、实际收益最高的习惯：开一个调试日志本（纸本或纯文本文件都行），每次实验写四行：假设是什么、改了什么、观察到什么、结论是什么。原因是人的记忆会自动「修补」因果：三天后你会确信「当时是改了栈大小才好一点的」，而本子上写着那次改动其实没有任何效果。调试的敌人不是难题，是「你以为你已经排除过了」。

调试器与接口：SWD 为什么赢了 JTAG

先把一个概念摆正：调试器不是一段运行在单片机里的软件，而是另一台小计算机加一条旁路总线。ST-Link、J-Link、DAPLink 这些盒子里有自己的处理器和固件，它通过 SWD 接口接到芯片内部的 AHB-AP（总线访问端口）上，从而能绕过 CPU 直接读写内存和外设寄存器。这个事实能解释很多现象：

  • 为什么 CPU 都跑飞了、甚至停在 HardFault 里，调试器还能读出内存？因为它不需要 CPU 配合。
  • 为什么 CPU 停住（halt）时你还能看变量、改寄存器？因为访问是另一条通路。
  • 为什么芯片没供电、时钟没起来时，调试器什么也读不到、还报「检不到芯片」？因为这条通路本身也要靠目标供电与调试时钟。

明白了这一点，「检不到芯片」这类问题就有了明确的排查方向：先查这条旁路通道的物理条件（供电、参考电压、接线），再查软件（引脚被复用、低功耗把调试关了、复位循环）。

四根必接线的作用分别是：SWDIO 是双向数据线（空闲时上拉为高），SWCLK 是调试器提供的时钟（注意：SWD 的时钟完全由调试器产生，与芯片的主时钟无关，所以哪怕芯片的 HSE 没起振，只要供电正常、内核时钟有（HSI 也能顶），SWD 通信就能建立），GND 提供共地回路（长线或高噪声环境建议多接一根 GND，降低回流阻抗），VREF（也称 VTref）是目标板的参考电压。

VREF 这根线不传数据，但它是「检不到芯片」这个故障的头号原因。它在做两件事：

  • 当作「目标是否上电」的探测器。调试器固件会先量 VTref 上的电压，如果低于门限，它就直接判定「目标未供电」，连尝试都不尝试，于是报 No target connected 或 Cannot connect to target。你这边看到的现象是：板子明明亮着灯、程序跑得好好的，调试器却说找不到芯片。
  • 当作电平转换的参考。调试器内部对 SWDIO/SWCLK 有电平转换电路，它需要知道目标的高电平是 1.8 V、3.3 V 还是 5 V，才能把输出摆幅和输入判决阈值调对。参考电压接错（比如接的是 5 V 而目标是 3.3 V 芯片），可能长期灌电流；完全不接，则输出要么过高要么过低，通信时好时坏。

反过来也要注意一个常见误区：不要把 VREF 当成「调试器给目标板供电的电源」。它本质是检测/参考脚，能提供的电流通常只有几十毫安量级，带不动带屏幕、带无线模块的板子。用调试器给目标供电（供电不足）会导致一类特别隐蔽的故障：调试器一接上，板子就复位或行为异常，因为供电被拉低了。

还有两个工程细节：线长与上拉。SWD 不是差分总线，长杜邦线（超过 15~20 cm）配合高速率会出现「读内存偶尔校验失败」的现象——表现为 Watch 窗口里的值偶尔乱跳、断点命中有时候不灵。F103 内部对 PA13/PA14 有弱上拉，但线一长就不够，可以在板上各加一个 10 kΩ 上拉到 3.3 V。怀疑接线质量时，第一招是把 SWCLK 降下来（从 4 MHz 降到 1 MHz 再试），这招几乎零成本且立刻能验证。

Connect under reset：芯片一上电就跑飞时怎么抓住它

正常情况下，调试器是这样连接的：给目标供电 → 芯片从 Flash 跑起来 → 调试器通过 SWD 与内核握手（attach）。问题出在中间那一步——如果芯片跑起来的程序立刻把 PA13/PA14 配成了普通 GPIO，或者一上电就进了低功耗模式、或者陷入看门狗复位循环，那么调试器永远等不到一个「安静的、还保留着 SWD 功能的内核」。你看到的现象是：调试器报连接失败，或连上又立刻掉线。

解法是把时序倒过来：在复位还没释放的时候先连上内核，再让程序跑。这就叫 Connect under reset（复位期间连接）。它需要把调试器的 NRST 线接到板子的复位脚上，并在 IDE 里把连接方式改成 under Reset。

低功耗模式会顺手关掉调试口

断点的四个类别：它们根本不是同一种东西

大多数人以为「断点」就是「让程序停在我想要的地方」，四种断点随便用。事实上它们是四套完全不同的机制，有各自的数量上限、各自的代价、各自唯一适用的场景。搞混的直接后果是：下了八个断点只有五个生效、条件断点一开系统就瘫痪、想抓「谁改了这个变量」时怎么都抓不到。

硬件断点：为什么只有六个

硬件断点靠的是 Cortex-M 内核里的 FPB（Flash Patch and Breakpoint）单元。它内部有一组地址比较器，每个周期把 CPU 正在取指的地址与比较器里存的值并行比较，相等就产生一个调试事件、让内核停下。整个过程不修改任何指令字节，也不插入任何额外指令——所以它的命中开销接近于零，这也是它在中断和时序敏感代码里唯一可用的原因。

至于「为什么只有六个」：每个比较器都是一块独立的并行硬件（还得支持地址掩码、范围匹配、以及 Flash 补丁功能），要占硅片面积、要耗静态功耗，而调试功能对芯片厂来说是纯粹的「非功能性需求」——用户不会因为多两个断点而多买你的芯片。ARM 定义了上限（M3/M4 是 6 个指令比较器 + 4 个数据比较器，M0/M0+ 是 4 + 2），芯片厂可以少做、不能多做。所以确切数字要以你手上那颗芯片的参考手册为准；当你看到 IDE 提示 too many breakpoints，或者更糟——第八个断点静默地不生效——就是撞到这个上限了。

什么时候只能用硬件断点？① 目标代码在 Flash 里，而你不能接受调试器去擦写它（绝大多数生产调试场景）；② 断点要落在中断服务函数或时序敏感的通信代码里（软件断点的改写与更高开销都不可接受）；③ 你在做「带调试口但不改代码」的现场分析。第 3.1 节会算一个「六个别够不够用」的真实账。

软件断点：为什么在 Flash 里也能用，又为什么会破坏时序

软件断点的原理简单粗暴：把目标地址上的那条指令换成一条 BKPT 指令（Thumb 编码是 0xBE00），CPU 执行到它就会进入调试异常，于是停下来。恢复运行时，调试器再把原来的指令写回去。

在 RAM 里这只是一次普通的内存写，毫无难度。麻烦的是 Flash：Flash 不能像 RAM 那样按字节改写，要改就得擦一整页、再写回去。「Flash 里也能下软件断点」是调试器与内核协力做到的，常见两条路径：

  • 调试器在线擦写（J-Link 的 flash breakpoint 就是这么干的）。代价是一次页擦写要几十毫秒，断点越多越慢，而且反复擦写会消耗 Flash 寿命。你会发现「在 Flash 里下了十几个软件断点之后，程序运行速度明显变慢」——那不是错觉。
  • 用 FPB 的补丁能力重映射。Cortex-M3/M4 的 FPB 本来就是给 Flash 打补丁用的：它可以让某个 Flash 地址的取指被重定向到一块（通常位于 RAM 的）补丁区，而补丁区里放的正是我们想要的 BKPT。这条路径不需要写 Flash，但会占用硬件比较器名额——也就是说「看起来无限的软件断点」实际上还是借了硬件的额度。

「破坏时序」有两层含义，第二层经常被忽略：第一层是所有断点共有的——内核停住了，可你的外设、看门狗、通信对端都还在动，所以停下来本身就改变了系统的时间关系（2.7 与 4.6 讲的「断点导致看门狗复位」「加日志就好了」都是这个原因）。第二层是软件断点独有的——它真的修改了内存里的指令字节。如果这段代码同时还会被别的东西读取（DMA 从同一块 RAM 搬数据、CRC 自校验、双核共享代码区），那么它们看到的字节和你以为的不一样，可能出现校验失败、或执行到一半发现自己被改了。

条件断点：为什么它其实很慢

条件断点看起来很美好：「我只想在 i == 137 的时候停下来」。但它的实现决定了它的代价：调试器没有办法让芯片自己判断条件（除非你把它写进代码）。它只能：命中 → 停下内核 → 通过 SWD 读回变量 → 在主机上求值 → 不满足就恢复运行 → 等下一次命中。整个过程是一次完整的 halt + 后台读 + resume 往返，耗时从几十微秒到几毫秒不等（取决于调试器、SWCLK 速率、以及要读多少内存）。

把条件断点放在一个 10 kHz 的中断里，等于每秒要做一万次这样的往返：按每次 100 µs 保守估计，就是 10000 × 100 µs = 1 s 的调试开销，堆在 1 s 的墙钟时间里——CPU 的每一纳秒都在为调试服务，系统等于停摆。你会看到的现象是：程序慢得像死机、通信全部超时、看门狗复位。

把条件写进代码：最快的一招

正确做法是让 CPU 自己判断，只在真命中时才触发一次「廉价的硬件断点」。CMSIS 提供了内建函数 __BKPT(0)，你可以这样写：

if (cond) { __BKPT(0); }

条件满足才执行 BKPT，命中时停止；条件不满足时只是一次普通的比较与跳转，开销只有几个时钟周期。这比调试器的条件断点快上几个数量级，代价只是几字节代码空间。唯一要记住的是：没有调试器连接时，BKPT 会升级为 HardFault——所以在发布固件里要么删掉，要么用 #if 包起来。

那什么时候条件断点才值得用？事件频率低、条件复杂的时候：比如「每 5 分钟才进一次的校准流程里，只有温度偏差大于 3 度才停」、「指针链 p->next->state == 5 时才停」。这类条件用代码写会很啰嗦，而事件频率低到每小时几次，调试器往返的开销完全可以忽略。判断公式很简单：命中频率 × 单次往返时间 < 系统可接受的额外开销（经验上取 1% 以下）。

数据观察点：抓「谁改了这个变量」的唯一答案

有一类 bug 特别折磨人：某个全局变量明明只在两三个地方赋值，可实际运行中它变成了一个不该出现的值。传统的办法是在每个赋值点都下断点，然后一次次运行碰运气。数据观察点（watchpoint）把这个问题从「猜」变成「确定」：你把变量地址交给内核的 DWT 单元，让硬件替你盯着所有对该地址的写（或读）访问，谁写谁就被抓个正着。

它的工作方式与指令断点完全不同：硬件比较的不是「取指地址」而是总线上出现的数据地址，并且可以区分读、写、读写。所以它不需要知道你代码在哪里，也不需要改任何指令，甚至能抓到「DMA 写的」「另一个中断写的」「数组越界踩过来的」这类你根本没在代码里搜到的访问。命中后停下，看一眼调用栈，凶手就写在屏幕上。

用它的三个前提条件必须背下来：

  • 变量必须真的有一个内存地址。局部变量在 -O2 下很可能被放进寄存器甚至完全消失，那样你连地址都没有，观察点根本设不下去。要长期观察一个变量，把它提成全局或静态变量。
  • 最好加 volatile。这保证每次访问都真的产生一次内存访问（不被缓存到寄存器里、不被删除、顺序不被打乱），否则会出现「变量确实被改了，但观察点一次都没命中」的怪事。
  • 给它加 __attribute__((used))（GCC 系）或 __attribute__((used)) 的等价写法。这解决的是另一类问题：如果一个变量写了却从来没人读，或者根本没被任何代码引用，编译器和链接器（开了 -ffunction-sections -Wl,--gc-sections 时）会理直气壮地把它删掉——你精心准备用来「留现场」的变量，在最终的 .map 文件里根本不存在。used 属性就是在告诉工具链：「这个符号我另有用处，别动它。」

它也有明确的能力边界：观察点盯的是地址，不是表达式。所以你不能观察「结构体里的某个位域」（硬件没法区分同一个字里的不同位，只能盯整个字，于是其他位的访问也会命中）、不能观察「数组的越界写入」（它只知道地址，不知道这个地址越界了——但正因为如此，它恰好能抓到越界踩到邻居变量的场景）、也不能观察「某个函数被调用了」。数量上限同样只有 4 个（M3/M4），所以要留给最可疑的那一两个变量。

断点数量不是你说了算

教学里最常见的一幕：同学在代码里下了七八个断点，抱怨「有几个断点根本不停」。这不是 IDE 的 bug，而是硬件比较器用完了。习惯做法是：一次只保留一两个真正需要的硬件断点，其余位置改用「代码内判断 + __BKPT」或计数器/日志；同时把观察点留给「谁改了这个变量」这种非它不可的场合。

单步、调用栈与优化等级

断点回答「停在哪里」，单步回答「接下来它怎么走」。这三兄弟（step into / over / out）名字很直白，但每一个都有明确的实现机制，而机制决定了它们在什么地方会骗你。

操作它到底做了什么该用它的时候会骗你的地方
Step into
（单步进入）		 执行一条 C 语句；如果这条语句调用了函数，就进入函数内部再停 你想知道「这个函数内部是怎么算出这个结果的」 一不小心进了 HAL_Delay 或 printf，在里面迷路几百行，还得靠 Step out 爬出来
Step over
（单步跳过）		 把整条语句（含它调用的所有函数）执行完才停。
实现方式：在函数的返回地址处临时放一个断点，然后全速跑到那里		 你只关心「调用完它之后变量变成了什么」 跳过 while (flag); 等于全速死等（看起来像卡死）；跳过 HAL_Delay(1000) 会让你以为程序挂了；中间发生的故障你也看不见
Step out
（单步跳出）		 继续运行，直到当前函数返回为止。
实现方式：在函数返回地址（LR 指向的地方）放临时断点		 已经进来了，不想一步步爬出去 函数被内联（-O2）时不存在「返回」这件事；在中断服务函数里 Step out 会跑进被中断的主程序（因为 LR 里放的是 EXC_RETURN 特殊值，不是一个普通地址）

注意 Step over 与 Step out 都依赖「临时断点」——也就是说它们要消耗一个硬件断点名额。这解释了一个细节现象：当你已经把硬件断点用完时，单步跳过可能会失败或者变得很慢，因为调试器没有资源去放那个临时断点。

为什么在中断里单步会跑飞

这是新手最容易被吓到的一幕：在某个中断服务函数里单步，按了两下之后程序莫名其妙进了另一个中断，或者 PC 直接跳到了一个完全不相干的地方，再按几下就 HardFault 了。「跑飞」的原因有三条，全都不是 bug：

  1. 单步的时间窗里 CPU 是自由的。「单步」的本质是：释放内核执行一条指令，然后再停下来。在这个极其短暂但真实存在的窗口里，所有比当前中断优先级更高的中断随时可以闯入。于是你按下「下一步」，落点却在别人的 ISR 里——仔细看调用栈，其实栈是对的，只是你没意识到自己已经换了一个上下文。
  2. 单步跨过了「清中断标志」那一条。很多 ISR 的关键动作是清标志位。如果你单步时跳过了它（比如被 Step over 吞掉，或者在标志清除前就停住），中断会被反复重入，PC 看起来在乱跳、栈一层层变长。看到「同一个中断连续进很多次」，第一件事就是去查标志位清了没有。
  3. 单步一个「等中断喂数据」的循环。while (!rx_done); 这类代码依赖中断把标志置起来，而你在中断上下文里单步，等于把系统的时间推进权攥在自己手里：中断进不来、数据永远不来、循环永远不退出。表现就是「卡在这里不动了」。

正确的做法是：中断服务函数里只下断点、不单步。要看 ISR 内部的逻辑，用「只读信息」的手段替代单步——把关键状态记到全局计数器或环形日志里（第 4 节的代码就是为这个准备的），停下来之后一次性看个够。如果你的 ISR 复杂到需要单步才能理解，那它本身就该拆开：让 ISR 只做「取数据 + 置标志」，把处理逻辑放到主循环/任务里（这正是第 32 篇《嵌入式软件架构》讲的结构），单步那个部分就完全安全了。

真要在 ISR 里单步，唯一的办法是在调试器里把它「孤立」出来：进入断点后临时屏蔽其他中断（多数调试器提供「Mask interrupts on step」之类选项），再单步。但要清楚这已经改变了系统的时间关系——你验证的是「这段代码单独运行时的逻辑」，不是「它在真实时序下的行为」，不要把两种结论混用。

调用栈窗口：从下往上读，看到问号就是线索

调用栈（Call Stack）窗口把「我是怎么走到这里的」摊开给你看：最底下是 main，越往上越靠近当前停下的位置，每一行通常给出函数名、文件与行号、以及参数值。它的价值在于：当断点命中在某个底层函数（比如 memcpy 或某个驱动函数）里时，你不需要猜是谁调用的——栈上写得清清楚楚。双击任意一层，Watch 窗口会切换到那一层的上下文，你能看到当时的局部变量。

而当栈窗口显示出一串 ????、或者链条在某一层断掉时，这本身就是一条重要结论，而不是工具的故障。它通常意味着三件事之一：① 栈被破坏了（最常见的原因是栈溢出，或者野指针写坏了栈上的返回地址）；② 栈上没有可用的调试信息（汇编写的启动代码、没有 CFI 信息的库）；③ 优化太激进，栈帧被重排/省略。前两种都指向「你的程序已经出问题了」，所以看到问号时不要抱怨 IDE，先去量栈水位（4.5）。

优化等级：调试时它帮你，发布时它坑你

编译器优化对调试的破坏是「结构性」的，不是偶发的：它按语义等价的原则重排、合并、删除、内联，而调试信息里的行号与变量位置是按「源码结构」记录的。两者一对不上，单步就会看起来错乱。

优化等级单步与断点变量观察它会掩盖什么
-O0 -g3 行号与源码一一对应，单步非常听话 局部变量都在栈上有地址，Watch 基本都能用 会掩盖只在优化后才出现的 bug：缺少 volatile、非原子的读-改-写、编译器重排导致的竞态
-O2 语句被合并/重排、函数被内联，单步可能一次跨几行甚至回跳；断点可能落不到你以为的地址 局部变量常常显示 optimized out，或用的是过期值 它自己会「制造」一类现象：只在 Release 构建里出的错，让你误以为是编译器有 bug
-Os 与 -O2 类似，循环可能被展开/向量化 同上，且小变量更容易被塞进寄存器 同上；此外还会删掉「没被引用」的变量与函数（配合 --gc-sections），让你准备好的黑匣子变量消失

于是有一条实用的工作纪律：调试构建用 -O0 -g3，发布构建用 -O2 或 -Os，而且两类构建都要定期运行。只在 -O0 下测试，你测的是一个「比真实产品慢好几倍、而且不会暴露竞态」的变体；只在 -O2 下开发，你会被单步的错乱折磨到怀疑工具。合理的节奏是：日常开发用 -O0 快速定位逻辑问题；每次提交前用 -O2 跑一遍完整功能测试，专门盯「只在优化后出现」的故障。

这里要澄清两个新手最容易混用的关键字，它们与调试器的关系非常直接：

  • volatile 的作用范围。它保证「每一次访问都真的发生一次内存访问」：不缓存进寄存器、不删除、不越过它重排。它不保证原子性——g_cnt++ 在 -O2 下依然是「读、加、写」三步，如果中间被中断打断，计数就会丢。所以 volatile 让变量「对调试可见」，但共享计数仍必须进临界区。把 volatile 当成「线程安全」是嵌入式里最常见的一处误解。
  • static 的副作用。把局部变量改成 static（或全局）会让它有一个固定地址，于是 Watch、Live Watch、观察点都能长期盯着它，这是很实用的调试技巧；但要注意它同时改变了语义（不再是每次调用重新初始化）。另外，如果这个变量没有被任何代码引用，优化加 --gc-sections 会把它删掉，这时要用 __attribute__((used)) 把它钉住。

最后补一句衔接：如果你已经怀疑问题在汇编层面（比如奇怪的中断返回、HardFault 里的压栈现场），那属于第 25 篇的内容。那里讲了怎么从 .lst 反汇编文件里读出「编辑器显示的这一行到底编译成了什么」，以及怎么把 HardFault 的 8 字栈帧读出来。本篇的立场是：优先用能缩小可能性范围的手段，把「需要读汇编」当成最后一步而不是第一步。

变量的三种观察方式：从「停下来看」到「事后看」

断点解决「停在哪里」，但停下来之后你要看什么？观察变量有三种手段，它们的成本、能看到的东西、适用的场合完全不同。很多人只会用第一种，于是在「偶发」和「需要看趋势」这两类场景里束手无策。

第一种：Watch 窗口——精确，但必须停下来

Watch 窗口是我们最熟悉的：把变量拖进去，停下时看它的值。它的根本前提是「内核必须停住」，原因有两层：其一，局部变量可能根本不在内存里，而在某个寄存器（比如 R3）里，只有 halt 之后调试器才能安全地读到内核寄存器组；其二，调试信息里记录的是「在源码这个位置，这个变量位于哪个寄存器或栈偏移」，把这条信息还原成值需要一份静止的上下文。所以「普通 Watch 为什么要求程序停下来」不是工具的任性，而是它只能这么工作。

由此可以解释一个常见困惑：为什么局部变量离开作用域以后，Watch 窗口显示的东西就不对了？它通常表现为三种情况之一：显示 not in scope（找不到这个符号）、显示 cannot evaluate（无法求值）、或者更迷惑人的——显示一个看起来合理的、但完全错误的值。最后这种情况的原因是：那块栈空间已经被别的函数复用了，调试器按老偏移读出来的其实是别人的数据。要长期观察一个值，把它提升为静态变量或全局变量，这样它才有一个稳定的地址可供随时读取。

两个使用细节值得记下来：Watch 里可以写表达式（如 buf[i]、p->next->state），但不要在 Watch 里写带副作用的表达式（i++、cnt = cnt + 1）——表达式是在目标上求值的，某些调试器会真的把结果写回内存，于是你「看一眼」就改变了程序状态，这属于调试引入的新 bug。另外，展开大数组或长链表会让界面卡住：每展开一层都要通过 SWD 读一次内存，几千个元素读下来要好几秒，而这个过程中内核是停着的。

第二种：Live Watch——实时刷新是怎么做到的

普通 Watch 有一个致命局限：看一次就要停一次。可你真正关心的往往是趋势——计数器有没有在涨、标志位多久翻转一次、这个中断到底有没有进。这就需要「不停下 CPU 也能看变量」的能力，也就是 Live Watch（不同 IDE 里叫法不同：Keil 的 Periodic Window Update、STM32CubeIDE 的 Live Expressions、J-Link 的 Live Watch）。

它的原理其实在 2.2 已经埋好了：调试器有一条绕过 CPU 的旁路总线。既然能绕过 CPU 读内存，那么「每隔 200 ms 读一次 0x200000A4 这个地址」就不需要任何 halt。所以实时刷新的本质是调试器在后台周期性地做内存读，CPU 全程自由运行。

机制决定了它的三条限制：

  • 只能看「有固定地址的东西」。全局变量、静态变量、外设寄存器都没问题；局部变量、寄存器变量、复杂表达式（需要栈帧分析）看不了——那必须停下来才行。这也是为什么「调试时把可疑变量提成全局」是个好习惯。
  • 刷新率由调试器决定，典型是 100 ms 到 1 s。不同的 IDE 可调范围不同，但规律是一样的：间隔越短，后台读越频繁，占用的 SWD 带宽与总线时间越多。
  • 它不是零成本的。每一次后台读都要与 CPU 争一次总线（虽然每次只有几百纳秒），在高频采样或实时控制环路里会引入可测量的抖动。所以「打开实时刷新之后电机声音变了」这种事是真的会发生，而不是心理作用。

一个非常实用的组合技：让 Live Watch 盯「计数器 + 时间戳」。在中断里给一个全局计数器加一，再让它和 uwTick 一起实时显示：只要计数器在涨，就证明中断在进；观察它每秒涨多少，就知道中断频率对不对；观察它突然停住的那一刻，你就抓到了故障发生的时间点——整个过程一纳秒都没有打扰系统。

第三种：全局变量做黑匣子——为「跑一晚上才死一次」准备

前两种方式都有一个共同前提：你要在场，而且系统还活着。可最难缠的故障恰恰相反：它一晚上只发生一次，发生时调试器不在场（产品在现场、设备在电池供电、或者你根本不知道它什么时候死）。这时候唯一能救你的手段是让固件自己记录现场，事后你来读。

做法就是一块「环形日志缓冲」：在 RAM 里开一个固定长度的数组，每条记录包含时间戳、事件码、少量参数；写满之后覆盖最老的一条。它有几个设计要点，每一条都是踩过坑才总结出来的：

  • 放的事件码而不是字符串。一个事件码一个字节，字符串要几十字节；环形缓冲的空间很宝贵，而且事件码可以在事后用一张表翻译成人话。记录「值」而不是「描述」也能避免在中断里做格式化（格式化要几百微秒，事件码只要几纳秒）。
  • 把它放到不初始化的段里（__attribute__((section(".noinit")))）。这是整个方案最关键的一步：默认的启动代码会在进 main 之前把 .bss 段清零，你辛苦记录的现场会被抹掉。放到 .noinit 段，编译器不会给它初始值、启动代码也不会清零它，于是系统复位之后，RAM 里的历史记录还在——复位后的第一件事就是把它们读出来。注意：掉电重启（冷启动）时 SRAM 内容不保证保留，所以要用一个魔数来判断「这段数据是上一轮留下的，还是随机的」。
  • 写它要够快，且不能在多写者之间撕裂。一次记录就是三四条存储指令（几十纳秒），在中断里用完全安全。但如果有多个中断都往同一个环形缓冲写，就必须用一小段临界区保护「写数据 + 更新指针」这几条指令，否则会出现「指针更新了但数据只写了一半」的残缺记录。
  • 两条读出的路：调试器内存窗口，或者固件自己 dump。前者在 .map 文件里找到数组的地址，直接在 IDE 的 Memory 窗口里按 32 位查看（连格式都不用写），适合「现场就在手边」；后者是写一段 log_ring_dump()，把历史按时间顺序翻译成文本通过串口/ITM 打出来（第 4.1 节给完整实现）。

从 printf 到 ITM 再到 RTT：打印调试的三条路

printf 在嵌入式圈子里名声不太好，常被说成「业余手段」。但问题从来不在 printf 本身，而在它背后的那条输出通道：如果你把日志塞进一个 115200 波特率的阻塞串口里，它当然会毁掉实时性；可如果你换一条通道，同样的日志可以几乎不花时间。这一节讲的就是这三条通道的区别，以及各自在那张「能不能用在中断里」的表上占哪一格。

第一条：串口重定向——最慢，但最通用

做法你已经熟悉：实现 fputc（Keil / newlib）或 __io_putchar（HAL 风格），把字符交给 UART 发出去，然后 printf 就自动走串口了。它的机制决定了代价：如果用的是 HAL_UART_Transmit 这类轮询函数，CPU 会站在原地等每一个字节发完——发一个字节要 87 µs（115200、8N1），40 个字符要 3.47 ms，这段时间 CPU 什么也干不了。

于是「能不能在中断里用」的答案很明确：不能。一个几百微秒的中断服务函数已经算长了，几毫秒的阻塞会把整个系统的时间预算吃光（3.5 会算一个具体例子）。除了慢，还有两个更隐蔽的问题：① HAL_UART_Transmit 内部有超时与状态检查，如果主循环正在用同一个串口发送，你的中断里调用它会立刻返回 HAL_BUSY 或干脆丢掉数据；② 日志格式化用的那个共享缓冲区是不可重入的，主循环和中断同时用会打出一堆乱码。

那它为什么还是最重要的一条路？因为只有串口日志不依赖调试器：设备在现场、在客户手里、在你师兄的电脑上，插一根 USB-TTL 就能看到输出。它也能被完整地保存成文件、被脚本处理、被当作产品的一个功能（售后诊断口）。所以工程上的正确姿势是：串口日志必须有，但要用非阻塞的方式发（DMA 或中断 + 环形发送队列，把 printf 变成「往队列里放数据」），并且把它当成「给你自己看的历史记录」，而不是「实时调试的探针」。

第二条：SWO / ITM——一根线，几乎不花时间

Cortex-M 内核里除了 CPU 还有一堆「仪器」模块，ITM（Instrumentation Trace Macrocell）就是其中之一。它的用法简单到令人意外：你往一个特殊的地址写一个字节，这个字节就进入 ITM 的 FIFO，再由 TPIU 串行化后从 SWO 引脚移出去，PC 端的调试器把它收下来显示。CPU 侧的开销只是一次寄存器写（几个时钟周期），不占用任何外设、不占用 UART、不需要 while 等发送完成。

要用起来需要满足四个条件，缺一个都看不到输出：

  1. 芯片要把 SWO 引出来。STM32F103 的 TRACESWO 复用在 PB3 上，而 PB3 默认是 JTAG 的 JTDO——所以必须把 JTAG 关掉（保留 SWD）才能把它当追踪脚用。这也是 SWD 相对 JTAG 的一个实际好处：SWD 模式下 PB3/PB4/PA15 都能还给你。
  2. 固件里要打开追踪输出。在 DBGMCU_CR 里置 TRACE_IOEN，并把追踪模式设成异步（只有 SWO 一根线）。
  3. 调试器要支持并接上 SWO 线。J-Link、ST-Link/V2 及以上都有 SWO 引脚，但一些廉价的克隆调试器没有引出，或者引出了也没实现。
  4. 上位机要配对时钟。IDE 里要填对内核时钟（比如 72 MHz）和 SWO 分频（常见 1~4 MHz）；填错的表现是满屏乱码或什么都没有。这个「填时钟」的步骤是把 SWO 用起来最大的门槛。

速度上，SWO 与串口是同一种编码方式（每个字节 10 位：起始 + 8 数据 + 停止），所以线上时间可以直接类比：2 MHz 的 SWO 传 40 个字符只要 200 µs，而 115200 的串口要 3.47 ms——快约 17 倍。但真正的差别不在线上速度，而在 CPU 侧：串口是「CPU 陪着等 3.47 ms」，SWO 是「CPU 花几个周期把字节丢进 FIFO 就走」。这个差别决定了 SWO 可以用在中断里，而阻塞串口不行。第 3.3 节会把两者的时间账完整算一遍。

标准实现（CMSIS 已提供的 ITM_SendChar）有这么两个要点，第 4.3 节给出的自写版本 itm_putc 遵循同样两条（改名是为了不与 CMSIS 的同名函数撞车）：先判断 ITM->TCR 里的 ITMENA 位——没有调试器连接时这一位是 0，此时写入被硬件丢弃，程序什么也不会发生（这非常重要，否则一个忘记注释掉的日志会让产品在现场死等）；再判断 FIFO 有没有空位（ITM->PORT[0].u32 == 0 表示还有空间）。另外提醒一句：把 printf 重定向到 ITM 以后，格式化本身的开销一点都没变——打印一个 %f 要几百微秒的纯 CPU 运算，与输出通道无关。所以「SWO 很快」只意味着「输出很快」。

第三条：RTT 之类——内存环形缓冲，最快，且能双向

SEGGER 的 RTT（Real Time Transfer）换了一个思路：根本不用外设，也不走 SWO。目标端代码把日志写进 RAM 里一个环形缓冲（由一个控制块描述缓冲区地址、读写指针、状态），PC 端调试器则通过 SWD 的后台内存读，周期性地把数据拉走显示。目标侧的开销就是一次 memcpy 加指针更新——微秒级，三条路里最快，而且完全不占用任何引脚与串口资源（连 SWO 都不需要）。

它还有一个别人没有的能力：双向。PC 端可以往另一个缓冲区里写数据，目标端读出来——等于给你的固件开了一个「命令行」，可以在运行时改参数、触发自检、dump 内存，而不少平台（ESP-IDF、一些 RTOS 示例）把它做成了主要的调试通道。

限制也要说清楚：数据是被 PC 端主动拉走的，所以必须保持调试器连接。一旦拔掉调试器，数据只会把缓冲区填满然后被覆盖或丢弃（这反而比阻塞式串口安全）。另外它需要上位机/调试器支持 RTT（J-Link 原生支持，OpenOCD 与 pyOCD 也有实现）。最后，它和你在 4.1 节要写的「黑匣子环形日志」本质上是同一个思路，区别只在于谁来读：调试器来读，它就是 RTT；固件自己读出来打印，它就是黑匣子。

日志分级、断言与错误码：让「打印」变成工程语言

会打日志和会设计日志是两件事。前者是插一句 printf，后者是让日志在发布固件里自动消失、在现场能被临时打开、在事后能被脚本解析。这一节讲的是后面那种。

五级日志与两种裁剪强度

分级的意义是让接收方按重要性过滤，而不是让打印方自娱自乐。一套够用的分级是：E（错误：功能已经不正常了，必须处理）、W（警告：还能跑，但出现了不该出现的情况，比如重试成功、参数被限幅）、I（信息：正常的关键里程碑，开机参数、状态切换、连接建立）、D（调试：开发期才关心的细节）、V（冗长：逐帧、逐字节级别，通常只在解决某个具体问题时临时打开）。

裁剪有两种强度，区别很实际：用常量条件判断（if (LOG_LEVEL >= LOG_LEVEL_DEBUG) ...）在 -O2 下会把整段代码连同格式字符串一起删掉，但在 -O0 下格式字符串可能仍然留在 Flash 里；用预处理指令包起来（#if LOG_LEVEL >= LOG_LEVEL_DEBUG）则是彻底不进 Flash。发布固件里那些「永远不会执行」的日志字符串，也是要占 Flash 的——一个 64 KB Flash 的工程里塞进几百条调试字符串，几 KB 就没了。所以 D/V 两级建议用 #if 处理，E/W/I 用常量条件即可（它们本来就要保留）。

除了编译期开关，还值得留一个运行时开关：用一个全局的位掩码或一个「诊断模式」标志，让现场可以在不重新烧录的情况下打开某个模块的详细日志（比如通过串口收到一个特定命令）。这个能力在产品现场的价值极高：客户说「偶尔连不上」，你可以让他敲一条命令打开详细日志，等下次出问题再看——而不是把设备寄回来。

内容规范上，有三条经验：① 每条日志带时间戳与模块标签（[I][NET] ...），事后才能排出事件顺序；② 记录「值」而不是「描述」（rssi=-73 retry=2 比「信号有点弱，重试了」有用一万倍）；③ 不要在日志里做浮点运算。格式化一个 %f 要几百微秒，是普通整数格式化的几十倍——在中断或高频路径里，这个开销足以改变系统行为。要用浮点就先转成整数（把电压放大一千倍当毫伏打）。

断言：把「设计假设」写进代码

断言的定位需要说清楚：它不是错误处理，而是「如果这里不成立，说明我的设计假设已经错了」的自我检查。错误处理应对的是「可能发生的事」（通信可能失败、传感器可能不响应）；断言应对的是「按设计绝不该发生的事」（指针不会是空、状态机的状态一定是枚举里的某一个、缓冲区长度一定够）。把这两件事混起来，是嵌入式代码里最常见的设计错误之一。

HAL 库里的 assert_param 是一个具体的例子：它只在定义了 USE_FULL_ASSERT 时才展开成真正的检查，展开后做的事情是调用 assert_failed(file, line)；而 ST 给的默认实现是一个死循环——开发时很方便（停下来看现场），产品里是灾难（现场设备直接卡死，看门狗还得再过一会儿才复位它）。所以只要你打算在产品里保留断言，就必须自己实现那个失败处理函数，第 4.2 节给出一套三级策略。

断言里可以放什么：指针非空、数组下标在范围内、状态机状态合法、临界区进出配对、缓冲区长度足够、互斥量确实被持有、硬件初始化完成标志为真。断言里绝对不能放什么，有五类：

  • 带副作用的表达式。ASSERT(p++ != NULL) 是经典反面教材：开发构建里它自增了，发布构建里断言被裁掉、自增也没了，于是同一个程序在两种构建下行为不同。这条规则的本质是「断言必须可以随时被删掉而不改变任何行为」。
  • 可能瞬时违反的硬件状态。比如断言「UART 一定空闲」「ADC 转换一定完成」——硬件状态本来就是异步的，这类检查属于状态等待，不属于断言。
  • 阻塞操作。断言失败时去 printf、去写 Flash、去延时：断言函数本身必须是可重入、无阻塞、不用堆的，否则你会在中断里触发断言，然后在断言里再死一次。
  • 外部输入的合法性检查。按键值、串口收到的字节、传感器读数都属于「可能非法」的输入，它们应该被校验并返回错误码，而不是让断言炸掉——否则一个干扰脉冲就能让你的设备复位。
  • 可变的业务条件。「温度一定小于 50 度」「电池电压一定高于 3.0 V」这类是运行期监控，它们会正常地发生；把它们写成断言，等于把正常工况当成了设计错误。

还有一件事必须在设计阶段决定，而不是在写断言的那一刻随手决定：断言失败之后系统该怎么办？常见三种策略，选择取决于设备形态：① 保留现场并停机——适合实验室与开发阶段，也适合「停比乱跑安全」的设备；② 记录后复位——适合无人值守的设备（把失败的文件/行号/次数写进备份寄存器或非初始化 RAM，然后 NVIC_SystemReset()，复位后由日志报出来）；③ 降级运行——适合不能停的设备（关闭相关功能、上报错误、继续跑主业务）。三种都合理，但「什么都不做、让它带着错误的状态继续跑」几乎永远不合理。

错误码：一层层往上抛，还是就地处理

最后讲一个与调试直接相关的设计问题：错误怎么表达。两种极端都常见：一种是用 0/1 表示一切（于是你永远不知道到底哪里错了），另一种是每一层都写一堆 if (ret != 0) return ret; 却从来没有人真正处理过错误（等于没有错误处理，只是把代码变长）。

比较实用的规则是按「上层能不能做出不同的决定」来分流：

  • 上层能做出有用的决定 → 往上抛。例如「读传感器失败」这件事，上层可以选择重试、可以用上一次的值、可以切到备用传感器、也可以上报错误——这几种决定是真正不同的，所以底层应该只返回一个明确的错误码，不要自己决定策略。
  • 上层只能做同一件事 → 就地处理。例如「Flash 校验失败」「断言被违反」这类不可恢复的错误，从驱动层一路返回到 main，中间每一层都只能原样传递，那么层层返回只会污染所有函数签名。就地记录（备份寄存器 + 环形日志）并复位，是更诚实的做法。

具体形式上，用枚举而不是布尔值，并且配一张 err_str() 字符串表（这样日志里能打出人话，而不用去翻头文件）。表本身会占 Flash，所以可以只在调试构建里编译进去，或者把它放在一个单独的 .c 里、让链接器的段回收机制（-ffunction-sections -Wl,--gc-sections）把用不到的部分丢掉。一个具体的收益是：当串口里打出 ERR_TIMEOUT at sensor_read 时，你不需要再猜「读失败」是超时还是校验错。

放下调试器，去拿表笔：四条判据与四件工具

这一节回答本篇最实际的一个问题：什么时候该停止读代码，去动硬件工具？判据可以用两句话概括——当你的问题能被表述为下面任意一句时，调试器就帮不上忙了：

换工具的判据
  • 「这个引脚上到底有没有这个信号？」——调试器能告诉你寄存器里已经把发送位置 1 了，但它永远无法告诉你引脚上真的有波形。寄存器只是「意图」，引脚才是「事实」。
  • 「电源本身对不对？」——纹波、跌落、上电时序、共地。调试器看到的芯片内部世界是「电正常」的世界，它没有能力报告电压不够。

还有一条补充判据：当你发现代码逻辑怎么看都对、而现象依然存在时，就应该怀疑「代码之外的物理世界」。这时候读第一百遍代码的收益是零。

万用表：只回答静态问题

万用表是所有工具里最快、最便宜、也最常被跳过的一件。它的正确用法是回答三类静态问题：供电对不对（3.3 V 是不是 3.3 V，5 V 是不是 5 V）、静态电平对不对（复位脚是高还是低、某个配置引脚有没有被拉错、通信线空闲时是不是高）、通断对不对（虚焊、断线、短路——尤其是自己焊的板子）。

有一个陷阱必须提醒：用电流档测电流时，表本身是串在回路里的一个电阻。普通万用表 mA 档的分流电阻在 1~10 Ω 量级，100 mA 的电流经过它就会掉 0.1~1 V 的电压。对一个 3.3 V 系统来说，这可能直接把它拉到复位门限以下——于是你观察到的现象是「一接上电流表，板子就重启/行为异常」，而你会误以为是板子的问题。正确的做法是：量电流用尽量小的分流电阻（或专用 µCurrent 类方案）配合示波器/高位表看电压差，不要在 3.3 V 轨上串一只普通万用表去测几十毫安以上的电流。另外，测 µA 级睡眠电流时普通万用表的精度与内阻都力不从心，那属于专门的功耗分析工具。

示波器：看「好不好」，不只看「有没有」

示波器回答的是「信号的质量与时间关系」。四类最常用的观察：

  • 电源纹波。LDO 输出上几十毫伏的纹波是常见的，DC-DC 更大。关键是要用对方法：探头必须用最短的地线（弹簧地针），因为长地线本身就是一个天线，会把你自己的开关噪声引进来——很多「我量到 500 mV 的噪声」的报告，最后发现是探头地线太长造成的假象。
  • 上电时序。VDD 上升时间、复位脚释放的时刻、BOOT 引脚的电平、以及各个电源轨之间的先后关系（比如 3.3 V 与 5 V 谁先起来）。时序错误会造成一类非常隐蔽的故障：板子十次上电有两次起不来，但按复位键总能起来——因为手动复位时电源早就稳定了。
  • 晶振是否起振。用探头搭在晶振引脚上（注意探头电容会影响它），能看到几伏峰峰值的正弦波。起振慢、幅度小、或者干脆不起振，会让芯片退回内部 RC 时钟运行——此时程序还在跑，但所有定时与波特率都偏了，表现为「串口乱码」「定时不准」。
  • 用 GPIO 翻转测执行时间。这是本篇最推荐的技巧之一：在你怀疑耗时的代码段两头各翻转一个空闲 GPIO，用示波器量脉冲宽度，就能得到这段代码的真实执行时间——精度是纳秒级，而开销只有两条指令，比任何日志都轻。

逻辑分析仪：抓协议，比读代码快十倍

如果说示波器看的是「模拟质量」，逻辑分析仪看的就是「数字事实」：它把 I²C、SPI、UART 这类协议按通道录下来，再用解码器翻译成字节。为什么说它比读代码快十倍？因为通信类问题的一大半根本不在你的代码里：从机地址写错了、上拉电阻没焊、时钟极性配反、从机在忙没应答、时序参数不满足芯片手册——这些问题在波形上一目了然，在代码里却要盯着 HAL_I2C_Master_Transmit 的返回值猜半天。第 29 篇《串行通信原理》讲过每一个信号的含义，逻辑分析仪就是把那些知识变成「看得见的证据」的工具。

三个使用要点：① 采样率要够——经验值是被测信号最高频率的 4 倍以上（想看清边沿细节取 10 倍）；速率不够时抓到的波形会「缺齿」，让你误判。② 深度换时长——采样点是有限的，采样率越高、能录的时间越短（3.6 会算）。③ 用触发条件抓偶发：大部分逻辑分析仪支持「在某个字节/某个地址出现时才触发」，这是抓偶发通信错误的关键——否则你要盯着一屏屏正常的波形找那一帧错的。

动手算一遍

这一节的六道题，全部是调试时真实会遇到的「先算一算再决定」的问题。它们的共同价值是：把「感觉应该差不多」换成一个可以写下来的数字。你会发现，很多调试方案在算之前看起来完全可行，算完就再也不会去用了。

例 1：六个硬件断点到底够不够用

场景：一块 STM32F103（Cortex-M3，按数据手册是 6 个指令比较器 + 4 个数据比较器）跑电机控制加通信。你在排查一个「偶尔算错」的问题，于是在 IDE 里一口气下了八个断点：主循环入口、TIM1 更新中断、USART1 接收中断、PID 计算函数、I²C 读传感器失败分支、状态机非法状态分支，外加两个数据观察点——「谁改了 g_pid_out」和「谁改了 g_rx_cnt」。

【需求清单】                                        【硬件额度】M3/M4
  指令断点类需求                                        指令比较器  6 个
    ① main 循环入口            1                       数据比较器  4 个
    ② TIM1 更新中断入口        1
    ③ USART1 接收中断入口      1                     【开销规则】
    ④ PID 计算函数             1                       · Step over / Step out 各要临时借 1 个指令比较器
    ⑤ I²C 失败分支             1                       · 条件断点占用 1 个普通断点名额
    ⑥ 状态机非法分支           1                       · 观察点必须用数据比较器（不能用指令的）
  指令断点小计                 6  ← 正好等于上限

  数据观察点需求                                       【结论】
    ⑦ 谁写 g_pid_out           1                        表面看：6 用 6、2 用 2，一个不剩
    ⑧ 谁写 g_rx_cnt            1                      实际后果：
  观察点小计                   2                          · 单步「跳过/跳出」时会没有名额可用，
                                                          表现为卡顿或直接失败
【账怎么算】                                             · 条件断点只要再加一个就超额
  指令：6 需求 / 6 上限 = 100%（用光）                   · 一旦超额，某些 IDE 会静默忽略后面的断点，
  数据：2 需求 / 4 上限 = 50%（剩 2）                      于是你以为在观察，其实没在看

【改用「代码内断点」把需求压下来】
  ① main 循环入口   → 改成计数器 g_loop_cnt++（Live Watch 看，不用断点）
  ⑤ I²C 失败分支    → 改成 if (ret != ERR_OK) { __BKPT(0); }（只在失败时触发）
  ⑥ 状态机非法分支  → 改成 if (st >= ST_MAX) { __BKPT(0); } 或错误码 + 日志
  结果：指令断点需求 6 → 3，留出 3 个名额给临时断点，观察点 2 个照旧保留
        代价：几字节代码空间，开销从「硬件比较」变成「一次比较 + 跳转」

【如果换成 Cortex-M0+（4 指令 + 2 数据）】
  指令断点需求 6 > 上限 4    → 必须砍掉 2 个
  观察点需求   2 = 上限 2    → 刚好用光，一个都不能再加
  分配原则（按「不可替代性」排序）：
    第 1 优先：数据观察点（没有别的办法能回答「谁改了这个变量」）
    第 2 优先：时序敏感位置（中断入口、通信收发）——必须用零开销的硬件断点
    第 3 优先：需要单步的代码段（要留临时断点名额）
    第 4 优先：普通逻辑位置 → 一律改用计数器 / 日志 / 代码内 __BKPT

这道题的结论不是「六个够」或「六个不够」，而是「断点是稀缺资源，要按不可替代性分配」。数据观察点之所以排第一，是因为没有任何别的软件手段能替你回答「谁写了这个变量」——你可以到处加日志，但你永远不知道有没有漏掉一处写点；而硬件是逐次访问比较的，不会漏。反过来，最不值钱的就是「普通逻辑位置的断点」，因为它们几乎总能用一行 __BKPT 或一个计数器替代。

例 2：一条 40 字符的 printf 要多久，能不能放进 1 ms 中断

场景：你在 1 kHz 的定时器中断里加了一句日志，想把每拍的控制量打出来看看。日志长 40 个字符，串口配置是 115200、8 数据位、1 停止位、无校验（也就是常说的 8N1），发送方式是 HAL_UART_Transmit 轮询阻塞。这件事能不能干？

【第一步：一个字符在线上是多少位】
  8N1 的帧结构：1 起始位 + 8 数据位 + 1 停止位 = 10 位/字符
  （无校验位；如果有校验就是 11 位，下面的结果要再乘 1.1）

【第二步：40 个字符的总位数】
  40 字符 × 10 位/字符 = 400 位

【第三步：除以波特率】
  t = 400 位 ÷ 115200 位/s = 0.0034722 s = 3.472 ms

【第四步：它落在 1 ms 的中断里意味着什么】
  中断周期 T = 1 ms（1 kHz）
  占用率 = 3.472 ms ÷ 1 ms = 347%（!!）
  → 一次日志要花掉 3.47 个中断周期的时间。
     中断还没执行完，下一次中断早就该来了；
     结果是中断嵌套、SysTick 丢弃、控制环彻底失序。
  【判定：绝对不可行，不是「勉强能跑」】

【换更快的波特率有没有救】
  921600：400 ÷ 921600 = 434 µs  → 434 µs ÷ 1000 µs = 43.4%
    仍然不可接受：单条日志吃掉近一半 CPU，控制环的时序余量被压缩到几乎为零。
  2000000（2 M，部分 UART 可达）：400 ÷ 2e6 = 200 µs → 20%，还是太高。

【什么频率下才安全】
  每 1 秒打一条：3.472 ms ÷ 1000 ms = 0.347%  → 完全可以
  每 100 ms 打一条：3.472 ms ÷ 100 ms = 3.47%  → 偏高但可接受（视系统而定）
  经验判据：单条日志的耗时 ≤ 该系统时间预算的 1%

【如果非要打多条：1 KB 日志的代价】
  1024 字符 × 10 位 = 10240 位 ÷ 115200 = 88.9 ms
  → 一个 100 ms 的控制周期直接被吃掉 89%，
    而且这 89% 里 CPU 是「站着等字节发出去」，什么也做不了。

这道题的正确结局不是「那就不打日志了」，而是「换成不阻塞的方式」。三条替代路线的时间账在第 3.3 与 3.5 题里算。这里先记住一个数量级：在 115200 的串口上，一条 40 字符日志的 3.47 ms 是一个「以毫秒计」的开销；而任何以毫秒计的阻塞操作，都不可能放进微秒或毫秒级的实时回路。判断一个位置能不能加阻塞日志，只要问一句「这个位置的周期是多少」，然后比大小就够了。

例 3：SWO 与串口日志差多少

接着例 2 的场景，但换成 SWO/ITM 输出。这里要算两个不同的时间，很多人把它们混为一谈：① 数据在线上走完要多久（这决定日志会不会积压），② CPU 为了发这条日志要花多久（这决定实时性会不会被破坏）。

【账目 A：数据在线上走完要多久】（与串口同一种编码，10 位/字符）
  串口 115200：  400 位 ÷ 115200  = 3.472 ms
  SWO  2000000： 400 位 ÷ 2e6     = 0.0002 s = 200 µs
  倍率：3.472 ms ÷ 200 µs = 17.4 倍

【账目 B：CPU 为了「送出去」要花多久】（这才是实时性的关键）
  串口轮询：CPU 要一直等到最后一个停止位发完 → 3.472 ms 全程占用
            （245000 个时钟周期 @72 MHz）
  SWO/ITM ：CPU 只做一件事——把字节写进 ITM 的 FIFO：
              for (i = 0; i < 40; i++) itm_putc(buf[i]);
            每次写入约 3~10 个时钟周期（一次 APB 写 + FIFO 入队）
            40 × 3 ~ 40 × 10 = 120 ~ 400 个时钟周期
            @72 MHz：1 周期 = 1/72e6 = 13.9 ns
            120 × 13.9 ns = 1.67 µs；400 × 13.9 ns = 5.56 µs
  CPU 时间对比：3472 µs（串口） ÷ 1.67 µs（SWO） ≈ 2080 倍
  【也就是说：SWO 的 CPU 开销比串口小三个数量级】

【账目 C：别忘了格式化本身的开销】（与通道无关）
  printf 重定向到 ITM 时，真正花时间的往往不是输出，而是 vsnprintf：
    · 一个整数 + 固定文本的格式化：约 2 ~ 10 µs（@72 MHz，视库实现）
    · 一个 %f 浮点：约 200 ~ 600 µs（是整数格式化的几十倍）
  → 结论：SWO 让你省掉了 3.47 ms 的传输，但省不掉格式化。
     要打高频日志，就不要用 printf，直接压事件码或手写整数转字符串。

【什么时候 FIFO 会把你卡住】
  itm_putc 里有一句 while (ITM->PORT[0].u32 == 0);，它在等 FIFO 空位。
  如果 PC 端读得慢（上位机卡顿、SWCLK 太低、日志量太大），FIFO 会满，
  此时这个 while 就变成了阻塞等待——退化回「串口那种」行为。
  判据：SWO 位速率必须大于日志的平均产生速率。
    例：2 MHz 的 SWO ≈ 200 KB/s 的字符吞吐（10 位/字符）
        若你每秒打 100 条 × 40 字符 = 4000 字符/s = 40 kbit/s，
        只占 2 Mbit/s 的 2% —— 非常安全
        若你在中断里每拍打 40 字符（1 kHz × 40 = 40000 字符/s = 400 kbit/s），
        占 20%，仍然可行，但要注意上位机不能卡。

这道题最实用的收获是「把两笔账分开算」。很多人以为「SWO 快 17 倍」就是它的全部优点，于是照样在中断里用 printf 打浮点数，结果还是几百微秒的卡顿——因为瓶颈从来不在线上，而在格式化。反过来，一旦你改用「只压字节」的方式，SWO 的 CPU 开销会降到微秒级，这就是它能进中断的真正原因。

例 4：偶发故障，要跑多久才算有把握复现

场景：设备每跑一段时间就会死一次，你在实验室蹲了 24 小时，抓到 3 次。现在你想设计一个「能稳定复现」的测试，应该跑多久？修好之后又要跑多久才能说「确实好了」？这两个问题都可以用一个泊松模型回答（把随机到达的故障近似为泊松过程，这是工程上足够好的近似）。

【第一步：先量化频率（这是所有工作的前提）】
  观测：24 小时内发生 3 次
  平均间隔 = 24 h ÷ 3 = 8 h
  故障率 λ = 3 ÷ 24 = 0.125 次/小时

【第二步：t 小时内至少复现一次的概率】
  泊松过程：P(至少一次) = 1 - e^(-λt)

【第三步：解出「95% 把握」需要多久】
  要求 1 - e^(-λt) ≥ 0.95
       e^(-λt) ≤ 0.05
       λt ≥ ln(20) = 2.9957
       t ≥ 2.9957 ÷ 0.125 = 23.97 小时 ≈ 24 小时
  【结论：按这个故障率，要跑满约 24 小时才有 95% 的把握看到它一次】

【第四步：几个常用倍率（记这三个数就够）】
  63% 的把握：t = 1/λ    = 8 小时   （正好等于平均间隔，直觉上也说得通）
  95% 的把握：t = 3/λ    = 24 小时
  99% 的把握：t = 4.6/λ  = 36.8 小时

【第五步：蹲短了会怎样】（别用「跑了 2 小时没出现」当证据）
  蹲 2 小时：P = 1 - e^(-0.125 × 2) = 1 - e^(-0.25) = 22.1%
  蹲 4 小时：P = 1 - e^(-0.5)  = 39.3%
  蹲 8 小时：P = 1 - e^(-1)    = 63.2%
  → 蹲 2 小时看不到故障是「完全正常」的，它什么也没有证明。

【第六步：修复之后，跑多久才能宣称修好了】
  这是一个更容易犯错的问法。设修复后跑了 T 小时、一次都没复现。
  观测到 0 次时的 95% 置信上界（工程上常用的「3 倍法则」）：
      λ_new ≤ 3 / T
  跑 24 h：λ_new ≤ 3/24 = 0.125 次/h
     —— 和修复前的 0.125 次/h 一模一样！
        也就是说「跑了一天没死」在统计上等于什么都没说。
  想证明故障率下降了 10 倍（λ_new ≤ 0.0125）：
      T ≥ 3 / 0.0125 = 240 小时 ≈ 10 天
  【结论：宣称修复有效的时长要求，通常是「复现所需时长的 10 倍量级」】

【第七步：怎么把 10 天缩成 1 天】（工程上真正该做的事）
  · 加速应力：提高温度、加大负载、缩短通信周期、插入干扰 —— 把 λ 提上去
  · 让设备「自己记录」：复位源 + 环形日志（4.1 / 4.4 节），
    这样即使没人在场，故障发生时也有现场可查，不必守着它复现
  · 并行跑多台：N 台设备同时跑，等效于把观测时间乘以 N
    （10 台跑 1 天 = 单台跑 10 天）

这道题想纠正的是两种最常见的自欺：一种是「我蹲了一晚上没复现，说明这个 bug 很罕见」（其实只是样本不够）；另一种是「我改了一行，跑了一天没死，修好了」（统计上等于没证据）。正确的姿势是：先把 λ 量出来，用 3/λ 设计复现实验，用 3/T 描述修复后的上界，并且在跑不动的时候改用「让它自己留现场」的思路。

例 5：加一条日志，会不会把时序余量吃光

场景：一个 1 kHz 的控制环，周期预算 1000 µs，你用 GPIO 翻转量出最坏执行时间是 640 µs——余量 360 µs（36%）。现在你想在这个环里加一条 32 字符的状态日志。四种输出方式，各会吃掉多少余量？

【基准账】
  周期预算 T = 1000 µs（1 kHz）
  实测最坏执行时间 = 640 µs
  余量 = 1000 - 640 = 360 µs（36%）

【方案 a：阻塞串口 @115200】
  32 字符 × 10 位 = 320 位 ÷ 115200 = 2778 µs
  余量 360 - 2778 = -2418 µs  →  超预算 3.8 倍，环直接崩
  【判定：不可行。哪怕「一秒才打一条」也不行——
     因为对控制环来说，偶发的单拍超时比持续变慢更糟：
     它会造成拍与拍之间的抖动，而抖动正是控制环最怕的东西。】

【方案 b：阻塞串口 @921600】
  320 位 ÷ 921600 = 347 µs
  余量 360 - 347 = 13 µs（剩余 3.6%）
  【判定：数学上「塞得进去」，工程上不可接受。
     13 µs 只够几十条指令；任何一次稍微长一点的路径（缓存未命中、
     除零补偿、中断嵌套）都会立刻爆掉。这叫「余量被吃光」。】

【方案 c：SWO / ITM @2 MHz】
  线上时间：320 位 ÷ 2e6 = 160 µs
  但 CPU 侧只花「写 FIFO」的时间：32 × 3 ~ 32 × 10 周期
      = 96 ~ 320 周期 @72 MHz = 1.3 ~ 4.4 µs
  余量 360 - 4 = 356 µs（剩余 99%）
  【判定：可行。注意区分「线上 160 µs」与「CPU 占 4 µs」——
     前者是数据在 SWO 引脚上排队走完的时间，不影响 CPU 继续干活。】

【方案 d：RTT / RAM 环形缓冲】
  32 字节的拷贝：约 32 × 2 ~ 4 周期 = 64 ~ 128 周期 @72 MHz
      = 0.9 ~ 1.8 µs
  余量 360 - 2 = 358 µs（剩余 99.4%）
  【判定：可行，且是高频环境的首选。数据留在 RAM 里等调试器来取。】

【方案 e：只记一个事件码（最省）】
  ring_push(code, arg)：约 5 ~ 10 条指令 = 0.1 ~ 0.2 µs
  余量 ≈ 359.8 µs
  【判定：可行。这是「高频中断里唯一应该做的事」：
     中断里只压事件码，翻译成人话留给事后。】

【汇总表】
  方案                          单条 CPU 开销      剩余余量      能不能用
  a 串口 115200（阻塞）          2778 µs           -2418 µs     不能
  b 串口 921600（阻塞）           347 µs              13 µs      不推荐
  c SWO / ITM @2 MHz              1.3 ~ 4.4 µs       356 µs     可以
  d RTT / RAM 环形缓冲            0.9 ~ 1.8 µs       358 µs     可以（首选）
  e 只记事件码                    0.1 ~ 0.2 µs       359.8 µs   最佳

【还要考虑的事】
  · 上表算的是「一条日志」。如果一次要打 10 条，c/d/e 依然可以用，
    而 a/b 早已不能用。
  · 余量不是「还剩多少就行」，而是「最坏情况下够不够」。
    日志的开销是偶发的，但控制环看的是每一拍的最坏值。
  · 记得把日志本身也要算进「最坏执行时间」的测量里——
    用 GPIO 翻转重新量一次 640 µs 是不是还在。

这张表的用法很直接：先算「这条日志在你的时间预算里占多少」，再决定走哪条路。一个实用的经验线是：日志开销超过预算的 1%，就不该用阻塞方式；超过 10%，连「偶发」都不能接受——因为偶发超时在实时系统里的破坏力，往往比稳定的慢更大。

例 6：逻辑分析仪的采样率与深度换算出「能录多久」

场景：你要抓一个 I²C 偶发通信错误，手上是一台 8 通道、最大 1 M 采样点（1 M 点 = 1,000,000 个采样）、支持 24 MHz 采样率的廉价逻辑分析仪。问题是：该把采样率设成多少，才能录到足够长的时间，等到那个偶发的错误出现？

【基本关系】
  捕获时长 = 采样点数 ÷ 采样率
  （深度是固定的 1 M 点，所以采样率越低，能录的时间越长）

【第一步：采样率至少要多少】
  经验规则：采样率 ≥ 被测信号最高频率的 4 倍；
            想看清边沿细节、做可靠解码，取 10 倍。
  I²C 100 kHz（最窄的高/低电平 = 半周期 = 5 µs）
    · 4 倍  = 400 kHz（最低限度）
    · 10 倍 = 1 MHz（推荐，保证解码不出错）
  SPI 10 MHz（半周期 = 50 ns）
    · 4 倍  = 40 MHz（已超过这台 24 MHz 的最大值 → 需要换设备）

【第二步：I²C 场景下能录多久】
  采样率 24 MHz（最大值）：1e6 ÷ 24e6 = 0.0417 s = 41.7 ms
  采样率 1 MHz（10 倍，够用）：1e6 ÷ 1e6 = 1.0 s
  采样率 400 kHz（4 倍，勉强）：1e6 ÷ 0.4e6 = 2.5 s

【第三步：这点时间够抓多少通信量】
  一个 I²C 字节 = 8 数据位 + 1 应答位 = 9 个时钟
    在 100 kHz 下 = 9 × 10 µs = 90 µs
    加上起始/停止/间隔，一个「读一个寄存器」的事务约 100 ~ 200 µs
  24 MHz 采样（41.7 ms）→ 约 41.7 ms ÷ 100 µs ≈ 417 个字节
  1 MHz 采样（1.0 s）  → 约 10000 个字节
  【结论：用最大采样率只能看到约 400 字节的通信，
     对「几分钟才错一次」的故障来说，抓到的概率几乎为零；
     把采样率降到 1 MHz，能录的时间直接提升 24 倍。】

【第四步：如果换成 SPI 10 MHz 会怎样】
  按 4 倍规则需要 ≥ 40 MHz 采样 → 这台 24 MHz 的机器不够，
  必须上 100 MHz 级别的设备。
  若用 100 MHz 采样、1 M 点：1e6 ÷ 100e6 = 10 ms  → 只能看 10 毫秒
  【结论：信号越快，同样的深度能录的时间越短，这就是「深度换时长」】

【第五步：那怎么还能抓到偶发】
  ① 用触发：大多数分析仪支持「在特定字节/地址/错误条件出现时才触发」，
     让它安静地等几个小时，触发一次就录一次。
     —— 这是抓偶发最有效的功能，比加大深度有用得多。
  ② 用压缩（RLE）：空闲期不存采样点，等效深度提升几十倍。
  ③ 用流式采集：USB 边采边传，深度不再受限（受带宽限制）。
  ④ 如果协议本身能自诊断，也可以让固件记录错误计数器（更省事）。

这道题最容易被忽略的一点是「采样率不要开满」。新手拿到逻辑分析仪的第一反应是把采样率拉到最大，然后发现只能录几十毫秒，什么也抓不到。正确的做法是先算出「解码所需的最低采样率」（4~10 倍），再往下取整到设备支持的一档，把剩下的全部换成时间。深度是固定的，采样率是牺牲深度换精度的旋钮；抓偶发故障时，时间比精度值钱。

六道题的共同句式

回头看，这六道题其实都是同一句话的不同说法：「先算一个数，再决定要不要做。」断点够不够、日志能不能放、要跑多久、余量够不够、能录多长——每一个决定背后都有一个可以算出来的数。养成「先算再动手」的习惯，是这一篇最想留给你的东西：算一次只要三十秒，而算错一次的代价可能是三天。

4.1 黑匣子：环形日志缓冲与内存 dump

这是整篇最值得抄的一段代码。它解决的是「故障发生时你不在场」这个根本问题：把事件记录在 RAM 里，系统复位之后记录还在，你复位后第一件事就是把它们读出来。设计上有四个要点，代码里逐条标了出来。

#ifndef LOG_RING_H
#define LOG_RING_H

#include <stdint.h>

/* ① 长度必须是 2 的幂：这样可以用来代替取模，省掉除法 */
#define LOG_RING_SIZE   1024u
#define LOG_RING_MASK   (LOG_RING_SIZE - 1u)

/* 魔数：用来判断「RAM 里这段数据是上一轮留下的，还是随机的」 */
#define LOG_MAGIC       0x4C4F4731u   /* "LOG1" */

/* 事件码表：全部集中在一个枚举里，事后翻译成人话 */
typedef enum {
    EV_BOOT        = 1,   /* 上电/复位启动 */
    EV_ASSERT      = 2,   /* 断言失败 */
    EV_WDT_RESET   = 3,   /* 由看门狗复位（复位后补记） */
    EV_ADC_TIMEOUT = 4,   /* ADC 转换超时 */
    EV_I2C_ERR     = 5,   /* I2C 通信失败 */
    EV_COMM_LOST   = 6,   /* 通信中断 */
    EV_STATE_JUMP  = 7,   /* 状态机非法跳转 */
    EV_HEAP_LOW    = 8,   /* 堆余量不足 */
    EV_STACK_LOW   = 9,   /* 栈水位告警 */
    EV_MAX         = 10
} log_code_t;

/* ② 记录结构：8 字节对齐，一条记录正好 8 字节 */
typedef struct {
    uint32_t tick_ms;     /* 时间戳（HAL_GetTick，毫秒） */
    uint16_t code;        /* 事件码（见上面的枚举） */
    int16_t  arg;         /* 附带数值：错误码、计数、行号等 */
} log_rec_t;

void log_ring_init(void);
void log_ring_push(uint16_t code, int16_t arg);
void log_ring_dump(void (*put)(const char *line));
const char *log_code_str(uint16_t code);

#endif /* LOG_RING_H */

#include "log_ring.h"
#include "stm32f10x.h"
#include <stdio.h>

typedef struct {
    uint32_t  magic;
    uint32_t  head;              /* 下一条要写的下标 */
    uint32_t  seq;               /* 累计写入条数（用来判断是否发生过覆盖） */
    log_rec_t rec[LOG_RING_SIZE];
} log_ring_t;

/* ③ 关键一行：放进 .noinit 段。
 *    默认启动代码会把 .bss 清零，那样每次复位现场都没了；
 *    放进 .noinit 段后，启动代码不会碰它，复位后 RAM 内容保留。
 *    （Keil/ARMCC 下这个属性可能不生效，需改用 __attribute__((zero_init))
 *      或在分散加载文件里给该段加 UNINIT 标记。） */
static log_ring_t s_ring __attribute__((section(".noinit")));

void log_ring_init(void)
{
    if (s_ring.magic != LOG_MAGIC) {
        /* 魔数不对 → 冷启动（掉电重启，RAM 内容是随机的），从零开始 */
        s_ring.magic = LOG_MAGIC;
        s_ring.head  = 0u;
        s_ring.seq   = 0u;
    }
    /* 魔数正确 → 热复位（看门狗/软复位/复位键），保留旧记录继续追加 */
}

void log_ring_push(uint16_t code, int16_t arg)
{
    uint32_t idx;
    uint32_t primask = __get_PRIMASK();

    /* ④ 临界区只包住「写记录 + 更新指针」这几条指令（几十纳秒）。
     *    多个中断都可能记录事件，如果不保护，
     *    会出现「指针更新了但记录只写了一半」的残缺数据。 */
    __disable_irq();

    idx = s_ring.head & LOG_RING_MASK;
    s_ring.rec[idx].tick_ms = HAL_GetTick();
    s_ring.rec[idx].code    = code;
    s_ring.rec[idx].arg     = arg;
    s_ring.head = (s_ring.head + 1u) & LOG_RING_MASK;
    s_ring.seq++;

    if (primask == 0u) {
        __enable_irq();
    }
}

const char *log_code_str(uint16_t code)
{
    switch (code) {
    case EV_BOOT:        return "BOOT";
    case EV_ASSERT:      return "ASSERT";
    case EV_WDT_RESET:   return "WDT_RESET";
    case EV_ADC_TIMEOUT: return "ADC_TIMEOUT";
    case EV_I2C_ERR:     return "I2C_ERR";
    case EV_COMM_LOST:   return "COMM_LOST";
    case EV_STATE_JUMP:  return "STATE_JUMP";
    case EV_HEAP_LOW:    return "HEAP_LOW";
    case EV_STACK_LOW:   return "STACK_LOW";
    default:             return "?";
    }
}

/* 按时间顺序导出：从最老的一条开始，一直到最后写入的一条 */
void log_ring_dump(void (*put)(const char *line))
{
    char line[64];
    uint32_t n     = (s_ring.seq < LOG_RING_SIZE) ? s_ring.seq : LOG_RING_SIZE;
    uint32_t start = (s_ring.head + LOG_RING_SIZE - n) & LOG_RING_MASK;

    snprintf(line, sizeof(line), "-- log ring: %lu records --\r\n",
             (unsigned long)n);
    put(line);

    for (uint32_t i = 0u; i < n; i++) {
        const log_rec_t *r = &s_ring.rec[(start + i) & LOG_RING_MASK];
        snprintf(line, sizeof(line), "[%8lu ms] %-12s arg=%d\r\n",
                 (unsigned long)r->tick_ms, log_code_str(r->code), (int)r->arg);
        put(line);
    }
}

/* 在 .ld 文件里，放在 .bss 之后、堆栈之前 */
  .noinit (NOLOAD) :
  {
    . = ALIGN(4);
    __noinit_start = .;
    *(.noinit)
    *(.noinit.*)
    . = ALIGN(4);
    __noinit_end = .;
  } >RAM

/* 说明：
 *   NOLOAD 告诉链接器「这一段不放进 Flash 映像，也不要在启动时初始化」。
 *   于是启动代码不会清零它，复位之后里面的数据还在。
 *   注意：NOLOAD 段在 .map 文件里仍会有确定地址，这是后面读它的依据。 */

int main(void)
{
    /* 第一件事：初始化黑匣子（它会判断是冷启动还是热复位） */
    log_ring_init();

    /* 如果上一轮是被看门狗复位掉的，这一轮开机就补记一条，
     * 这样 dump 出来的时间线里能看到「死亡原因」 */
    if (reset_source_read() & RS_IWDG) {
        log_ring_push(EV_WDT_RESET, 0);
    }

    hal_init();

    /* 用串口把历史打出来（也可以走 ITM，见 4.3） */
    log_ring_dump(uart_puts);
    log_ring_push(EV_BOOT, (int16_t)reset_source_last());

    while (1) {
        /* ... */
    }
}

如果不想写 log_ring_dump，还有一条更省事的路：直接用调试器的内存窗口读。在 .map 文件里搜索 s_ring，拿到它的地址（比如 0x20000100），然后在 IDE 的 Memory 窗口里按 32 位查看：前三个字是 magic/head/seq，之后每两个字就是一条记录（第一个字是 tick_ms，第二个字的低 16 位是事件码、高 16 位是 arg）。这种读法的好处是完全不需要在固件里加导出代码，也不会因为打印而破坏现场；坏处是要自己心算时间戳的差值。跑通一次之后，你会把它当成标配。

.noinit 的三个前提

① 只有热复位能保留：按复位键、看门狗复位、软复位都不会丢 RAM 内容；但掉电重启（冷启动）时 SRAM 内容不保证保留，所以必须靠魔数判断，不要假设数据一定有效。② 低功耗模式下 SRAM 可能掉电：进入某些深度低功耗模式后（或某些系列的 SRAM 会被关闭），内容会丢，这时的记录等于没有。③ 别把重要数据全压在 .noinit 里：它的内容在冷启动时是随机的，任何直接使用它的代码都必须先做有效性校验。

4.2 断言与错误码：能直接抄的三级宏

这段代码解决两个问题：错误怎么表达（枚举而不是布尔值），以及断言失败之后到底怎么办（三级策略，由你在调用处显式选择）。注意三级策略是分开的三个宏，而不是一个宏加参数——因为「用什么策略」是调用点的决定，写清楚了以后读代码的人一眼就能看出严重程度。

#ifndef ERR_H
#define ERR_H

typedef enum {
    ERR_OK = 0,        /* 成功 */
    ERR_PARAM,         /* 参数非法（调用者用错了接口） */
    ERR_TIMEOUT,       /* 超时（外设/对端没有按时响应） */
    ERR_BUSY,          /* 忙（资源被占用，可以重试） */

    ERR_NOMEM,         /* 内存不足（堆/缓冲池耗尽） */

const char *err_str(err_t e);

#endif /* ERR_H */

#include "err.h"

const char *err_str(err_t e)

/* 发布固件如果嫌这张表占 Flash，可以整体用 #ifdef DEBUG_BUILD 包起来，
 * 或者把它单独放在一个 .c 里，让 -ffunction-sections + --gc-sections 回收。 */

#ifndef ASSERT_MCU_H
#define ASSERT_MCU_H

#include <stdint.h>
#include "err.h"

/* 备份寄存器里的魔数（16 位，因为 F103 的 BKP_DRx 只有低 16 位可用） */
#define ASSERT_MAGIC16   0x4153u    /* "AS" */

/* 三级策略，按「严重程度」排列，在调用处显式选择：
 *   ASSERT_RET   最轻：记录后返回错误码，交给上层决定
 *   ASSERT_BREAK 中等：记录后触发断点（开发期用；无调试器时会变成 HardFault）
 *   ASSERT_RESET 最重：记录后立刻复位（无人值守设备的产品级选择）
 * 共同点：失败时都会把「行号 + 次数」存进备份寄存器，复位后还能查。 */

#define ASSERT_RET(cond, e)                                          \
    do {                                                             \
        if (!(cond)) {                                               \
            assert_record((uint16_t)__LINE__);                       \
            return (e);                                              \
        }                                                            \
    } while (0)

#define ASSERT_BREAK(cond)                                           \
    do {                                                             \
        if (!(cond)) {                                               \
            assert_record((uint16_t)__LINE__);                       \
            __BKPT(0);                                               \
        }                                                            \
    } while (0)

#define ASSERT_RESET(cond)                                           \
    do {                                                             \
        if (!(cond)) {                                               \
            assert_record((uint16_t)__LINE__);                       \
            assert_reset_now();                                      \
        }                                                            \
    } while (0)

void assert_record(uint16_t line);
void assert_reset_now(void);
uint16_t assert_last_line(void);      /* 复位后取回上一次的断言行号 */
uint32_t assert_count(void);          /* 累计断言次数（存于备份寄存器） */

#endif /* ASSERT_MCU_H */

#include "assert_mcu.h"
#include "stm32f10x.h"

/* 备份寄存器 DR1~DR3 的使用约定：
 *   DR1 = 断言行号（16 位）
 *   DR2 = 断言累计次数（16 位，溢出后回绕）
 *   DR3 = 魔数（用于判断「这里面到底有没有有效内容」）
 * 注意：F103 的备份寄存器在 VBAT 域，主电源掉电后若有纽扣电池仍会保留；
 *       没有电池时，掉电后内容也会丢——所以魔数校验不能省。 */

static void bkp_enable(void)
{
    /* 备份域要两个条件：APB1 上的 PWR/BKP 时钟，以及解除写保护 DBP */
    RCC->APB1ENR |= RCC_APB1ENR_PWREN | RCC_APB1ENR_BKPEN;
    PWR->CR |= PWR_CR_DBP;
}

void assert_record(uint16_t line)
{
    uint16_t cnt;

    bkp_enable();

    cnt = (uint16_t)(BKP_ReadBackupRegister(BKP_DR2) + 1u);
    BKP_WriteBackupRegister(BKP_DR1, line);
    BKP_WriteBackupRegister(BKP_DR2, cnt);
    BKP_WriteBackupRegister(BKP_DR3, ASSERT_MAGIC16);
}

uint16_t assert_last_line(void)
{
    bkp_enable();
    if (BKP_ReadBackupRegister(BKP_DR3) != ASSERT_MAGIC16) {
        return 0u;                 /* 没有有效记录 */
    }
    return (uint16_t)BKP_ReadBackupRegister(BKP_DR1);
}

uint32_t assert_count(void)
{
    bkp_enable();
    if (BKP_ReadBackupRegister(BKP_DR3) != ASSERT_MAGIC16) {
        return 0u;
    }
    return (uint32_t)BKP_ReadBackupRegister(BKP_DR2);
}

void assert_reset_now(void)
{
    /* 复位前把现场固化：关中断 → 同步 → 内核级软复位。
     * 复位后 RCC_CSR 的 SFTRSTF 位会置起来，配合 4.4 的复位源记录，
     * 就能区分「是断言让我复位的」还是「是看门狗」还是「掉电」。 */
    __disable_irq();
    __DSB();
    NVIC_SystemReset();

    for (;;) {
        /* 兜底：正常情况下执行不到这里 */
    }
}

/* 【ASSERT_RET：可以恢复的、属于「调用者用错」的情况】
 *   典型场景：参数校验、状态前检查。
 *   为什么用 RET 而不是停机：调用者可能确实能做出不同的决定。
 *     ASSERT_RET(buf != NULL, ERR_PARAM);
 *     ASSERT_RET(len <= sizeof(s_tx_buf), ERR_PARAM);
 *     ASSERT_RET(st < ST_MAX, ERR_STATE);
 *   要点：断言条件必须是「按设计永远成立」的，不是「外部输入校验」。
 *         上面 len 的上限是内部约定，属于断言；
 *         而串口收到的字节数上限属于输入校验，应该返回错误码而不炸。 */

/* 【ASSERT_BREAK：开发期专用，最想让它「当场停下来让我看」的地方】
 *     ASSERT_BREAK(p != NULL);
 *     ASSERT_BREAK(irq_nesting >= 0);
 *   注意：没有调试器连接时 __BKPT(0) 会升级成 HardFault，
 *         所以发布构建里要么删掉、要么改成 ASSERT_RESET。 */

/* 【ASSERT_RESET：无人值守设备的产品级选择】
 *     ASSERT_RESET(spi_handle != NULL);
 *   为什么可以接受「复位」：对现场设备来说，
 *     带着错误状态继续跑（可能乱发指令、可能写坏 Flash）比复位危险得多。
 *     复位后靠备份寄存器里的行号 + 环形日志定位，代价只是一次重启。 */

/* 【绝对不要写成这样】
 *     ASSERT_BREAK(cnt++ < 10);        // 副作用！断言被裁掉后语义就变了
 *     ASSERT_BREAK(uart_is_idle());     // 瞬时硬件状态，会正常地不成立
 *     ASSERT_RESET(printf("bad"));      // 阻塞 + 副作用，断言函数必须无阻塞
 *     ASSERT_RET(temp < 50, ERR_HW);    // 可变业务条件，这是运行期监控不是断言
 */

4.3 串口分级日志与 SWO/ITM 重定向

这段代码把前面讲的「分级 + 编译期裁剪 + 非阻塞输出」三件事拼成一个能用的日志模块。核心设计只有一句：格式化在主循环里做（可以慢），发送变成「往队列里放数据」（几十纳秒），真正推字节交给中断或 DMA。这样主循环里的日志不会阻塞，而中断里则一律只用 4.1 的事件码——因为格式化用的缓冲区不可重入。

#define LOG_LEVEL_DEBUG  4

/* 默认等级：发布构建建议 INFO 或 WARN；

#else

#endif /* LOG_H */

#include "stm32f10x.h"
#include <stdio.h>
#include <stdarg.h>

volatile uint32_t g_log_mask = 0x1Fu;    /* 默认五级全开；发布前改成 0x03 */

/* ---------------- 非阻塞发送队列 ---------------- */
#define UART_TX_SIZE   512u                     /* 必须是 2 的幂 */
#define UART_TX_MASK   (UART_TX_SIZE - 1u)

static volatile uint8_t  s_tx[UART_TX_SIZE];
static volatile uint16_t s_tx_head;             /* 生产者（主循环/日志）写 */
static volatile uint16_t s_tx_tail;             /* 消费者（USART1 中断）读 */

static void uart_tx_kick(void)
{
    USART1->CR1 |= USART_CR1_TXEIE;             /* 打开 TXE 中断，开始推 */
}

int uart_tx_async(const uint8_t *p, uint16_t len)
{
    uint16_t i;
    uint32_t primask = __get_PRIMASK();

    for (i = 0u; i < len; i++) {
        uint16_t next = (uint16_t)((s_tx_head + 1u) & UART_TX_MASK);
        if (next == s_tx_tail) {
            /* 队列满：丢弃而不是阻塞。
             * 「少打几条日志」永远好过「主循环卡住」。 */
            if (primask == 0u) { __enable_irq(); }
            return -1;
        }
        s_tx[s_tx_head] = p[i];
        s_tx_head = next;
    }
    if (primask == 0u) { __enable_irq(); }
    uart_tx_kick();
    return (int)len;
}

/* 放在 USART1_IRQHandler 里调用：每发完一个字节取下一个 */
void uart_tx_isr(void)
{
    if ((USART1->SR & USART_SR_TXE) != 0u) {
        if (s_tx_tail != s_tx_head) {
            USART1->DR = s_tx[s_tx_tail];
            s_tx_tail = (uint16_t)((s_tx_tail + 1u) & UART_TX_MASK);
        } else {
            USART1->CR1 &= ~USART_CR1_TXEIE;    /* 队列空了，关中断 */
        }
    }
}

/* 给 log_ring_dump / 直接打印用的同步出口 */
void uart_puts(const char *s)
{
    uart_tx_async((const uint8_t *)s, (uint16_t)strlen(s));
}

/* ---------------- 日志本体 ---------------- */
static const char lv_char[6] = { '-', 'E', 'W', 'I', 'D', 'V' };

void log_write(int level, const char *tag, const char *fmt, ...)
{
    char buf[96];                                /* 栈上缓冲：不占堆，可重入性由调用者保证 */
    va_list ap;

    if (!LOG_ENABLED((uint32_t)level)) {
        return;
    }

    va_start(ap, fmt);
    /* 注意：vsnprintf 会取一部分栈与库的锁，
     * 所以本函数只能在主循环/任务上下文里用，不要在中断里用。
     * 另外：这里刻意不用 %f —— 浮点格式化是几百微秒级的开销。 */
    (void)vsnprintf(buf, sizeof(buf), fmt, ap);
    va_end(ap);

    uart_tx_async((const uint8_t *)buf, (uint16_t)strlen(buf));
    uart_tx_async((const uint8_t *)"\r\n", 2u);
}

#include "stm32f10x.h"

/* ---------- 1) 字符输出：先判断「有没有人在看」，再等 FIFO 空位 ---------- */
int itm_putc(int ch)
{
    /* ITMENA=0 表示没有调试器使能 ITM（比如脱机运行）：
     * 直接丢弃并返回，绝不能在这里死等 —— 否则产品现场会因为一句
     * 忘在代码里的日志而卡死。 */
    if ((ITM->TCR & ITM_TCR_ITMENA_Msk) == 0u) {
        return ch;
    }
    if ((ITM->TER & 1u) == 0u) {        /* 通道 0 未使能 */
        return ch;
    }
    while (ITM->PORT[0].u32 == 0u) {
        /* 等 FIFO 出现空位。正常情况下一两个周期就能写进去；
         * 如果这里长时间出不来，说明上位机读得比目标写得慢，见 3.3 的判据。 */
    }
    ITM->PORT[0].u8 = (uint8_t)ch;
    return ch;
}

/* ---------- 3) 使能 SWO 追踪输出（F103 专用细节） ---------- */
void trace_enable(uint32_t swo_hz)
{
    /* ① 释放 PB3：F103 的 TRACESWO 复用在 PB3 上，
     *    而 PB3 默认是 JTAG 的 JTDO。必须把 JTAG 关掉、只留 SWD，
     *    PB3 才能当追踪脚用（顺带把 PA15、PB4 也还给用户）。 */
    RCC->APB2ENR |= RCC_APB2ENR_AFIOEN;
    AFIO->MAPR = (AFIO->MAPR & ~AFIO_MAPR_SWJ_CFG)
               | AFIO_MAPR_SWJ_CFG_JTAGDISABLE;

    /* PB3 配成复用推挽输出 */
    RCC->APB2ENR |= RCC_APB2ENR_IOPBEN;
    GPIOB->CRL = (GPIOB->CRL & ~(0xFu << 12)) | (0xBu << 12);

    /* ② 打开调试模块的 TRACE 输出，并选异步模式（只有 SWO 一根线，
     *    不使用 TRACECLK，这是教学板上唯一可行的接法）。 */
    DBGMCU->CR |= DBGMCU_CR_TRACE_IOEN;
    DBGMCU->CR &= ~DBGMCU_CR_TRACE_MODE;      /* TRACE_MODE = 00：异步 */

    /* ③ 设 SWO 波特率：TPIU 的异步预分频。
     *    具体寄存器名随系列不同（F1 上是 TPIU->ACPR），
     *    关系式：SWO 速率 = TRACECLK / (ACPR + 1)，
     *    通常还要除以 2（因为内部按 2 倍采样）。 */
    TPIU->ACPR = (uint32_t)(SystemCoreClock / (2u * swo_hz)) - 1u;

    /* ④ ITM 侧：使能 ITM 本体与通道 0 */
    ITM->TER  |= 1u;                          /* 使能 Stimulus Port 0 */
    ITM->TCR  |= ITM_TCR_ITMENA_Msk;          /* 使能 ITM */
}

4.4 复位源与备份寄存器：复位前留下遗言

在 4.1 已经提到过一句：复位之后第一件事应该是搞清楚「上一次是谁把我弄死的」。STM32 的 RCC_CSR 寄存器把这件事做成了硬件功能——它会记住最近一次复位的原因，直到你手动清除。这段代码的价值在于：它把「死因」从一个靠回忆的问题，变成了一个开机就能打印出来的字段。

#ifndef RESET_INFO_H
#define RESET_INFO_H

#include <stdint.h>

/* 复位源位图（一个位对应一种原因，可能多个位同时置起来） */
#define RS_PIN      (1u << 0)   /* NRST 引脚复位：复位键、外部复位芯片、调试器 under reset */
#define RS_POR      (1u << 1)   /* 上电/掉电复位：真正的冷启动 */
#define RS_SOFT     (1u << 2)   /* 软件复位：NVIC_SystemReset()、断言策略、bootloader 跳转 */
#define RS_IWDG     (1u << 3)   /* 独立看门狗超时：程序卡死，或调试时被断点停太久 */
#define RS_WWDG     (1u << 4)   /* 窗口看门狗：喂狗太早或太晚 */
#define RS_LPWR     (1u << 5)   /* 低功耗模式异常 */

/* 跨复位保留的信息（放在 .noinit 段） */
typedef struct {
    uint32_t magic;          /* 有效性标记 */
    uint32_t boot_cnt;       /* 开机次数（热复位累加） */
    uint32_t assert_cnt;     /* 累计断言次数（来自备份寄存器） */
    uint16_t last_rs;        /* 上一次的复位源位图 */
    uint16_t last_line;      /* 上一次断言的行号 */
} reset_info_t;

#define RESET_MAGIC   0x52535431u    /* "RST1" */

uint16_t reset_source_read(void);        /* 读并清除 RCC_CSR 的标志 */
void     reset_info_capture(void);       /* 开机第一件事调用 */
const reset_info_t *reset_info_get(void);
void     reset_info_print(void (*put)(const char *));

#endif /* RESET_INFO_H */

#include "reset_info.h"
#include "assert_mcu.h"
#include "stm32f10x.h"
#include <stdio.h>

static reset_info_t s_ri __attribute__((section(".noinit")));

uint16_t reset_source_read(void)
{
    uint32_t csr = RCC->CSR;
    uint16_t flags = 0u;

    if (csr & RCC_CSR_PINRSTF)  { flags |= RS_PIN;  }
    if (csr & RCC_CSR_PORRSTF)  { flags |= RS_POR;  }
    if (csr & RCC_CSR_SFTRSTF)  { flags |= RS_SOFT; }
    if (csr & RCC_CSR_IWDGRSTF) { flags |= RS_IWDG; }
    if (csr & RCC_CSR_WWDGRSTF) { flags |= RS_WWDG; }
    if (csr & RCC_CSR_LPWRRSTF) { flags |= RS_LPWR; }

    /* 关键一步：清掉标志，否则下一次复位读到的还是这一批旧标志，
     * 于是你会永远以为「每次都是看门狗复位的」。 */
    RCC->CSR |= RCC_CSR_RMVF;

    return flags;
}

void reset_info_capture(void)
{
    uint16_t bkp_magic;

    /* 读复位源必须放在最前面：任何一次其它操作都不该影响它 */
    s_ri.last_rs = reset_source_read();

    if (s_ri.magic != RESET_MAGIC) {
        /* 冷启动：RAM 里是随机值，全部从零开始 */
        s_ri.magic     = RESET_MAGIC;
        s_ri.boot_cnt  = 0u;
        s_ri.last_line = 0u;
        s_ri.assert_cnt = 0u;
    }
    s_ri.boot_cnt++;

    /* 从备份寄存器取回「断言的遗言」：行号 + 累计次数。
     * 注意这与复位源是两条独立的信息：
     *   last_rs = RS_SOFT 说明「是主动复位的」，
     *   last_line 则告诉我「是哪一行断言触发的」。 */
    bkp_magic = (uint16_t)BKP_ReadBackupRegister(BKP_DR3);
    if (bkp_magic == ASSERT_MAGIC16) {
        s_ri.last_line  = assert_last_line();
        s_ri.assert_cnt = assert_count();
    }
}

const reset_info_t *reset_info_get(void)
{
    return &s_ri;
}

void reset_info_print(void (*put)(const char *))
{
    char line[128];

    snprintf(line, sizeof(line),
             "[RST] boot=%lu rs=0x%04X asserts=%lu last_line=%u\r\n",
             (unsigned long)s_ri.boot_cnt, (unsigned)s_ri.last_rs,
             (unsigned long)s_ri.assert_cnt, (unsigned)s_ri.last_line);
    put(line);
}

【单个标志的含义】

  标志                含义                              通常意味着
  ────────────────────────────────────────────────────────────────────────────────
  PORRSTF             上电/掉电复位                      真·冷启动。正常运行
  PINRSTF             NRST 引脚被拉低                    复位键 / 外部复位芯片 /
                                                         调试器 under reset 连接的副产物
  SFTRSTF             软件复位                            NVIC_SystemReset()，
                                                         断言策略、bootloader 跳转
  IWDGRSTF            独立看门狗超时                      程序卡死；或调试时断点停太久
  WWDRSTF             窗口看门狗超时                      喂狗太早（在窗口外）或太晚
  LPWRRSTF            低功耗模式异常                      进入了不该进的低功耗状态

【多个标志的组合怎么读】（这是最容易读错的地方）

  情形 A：PORRSTF + 其它位
     说明这次是上电，其它位是「上一次复位留下的陈迹」——
     因为 POR 会把所有标志一起置起来。
     → 结论：以 PORRSTF 为准，这是一次冷启动。

  情形 B：只有 IWDGRSTF
     → 结论：典型的看门狗复位（程序卡死，或者你正在被断点折磨，见 4.6）。

  情形 C：SFTRSTF + 备份寄存器里的行号非 0
     → 结论：断言主动复位，行号指给你看。

  情形 D：PINRSTF 反复出现，但没人按复位键
     → 结论：检查电源质量（掉电瞬间会有毛刺）、复位脚上的电容是否合适、
       或者调试器是不是一直挂在 under reset 模式上。

【配合 boot_cnt 使用】
  boot_cnt 每次热复位加一。如果一晚上从 1 涨到 300，
  说明设备在反复复位——这本身就是最重要的结论，
  比任何单次现场都有用。 */

4.5 CPU 占用率、栈水位与堆水位

这三个指标回答的是同一类问题：「系统的余量还剩多少」。它们全部是可以在运行时持续统计、并且几乎不花钱的——CPU 占用率告诉你时间的余量，栈水位与堆水位告诉你空间的余量。偶发故障中相当一部分（尤其是「跑一会儿就死」）就是这三样中的某一样被吃光了。

#include "stm32f10x.h"

static volatile uint32_t s_idle_cnt;     /* 空闲循环跑过的圈数 */
static volatile uint32_t s_idle_last;
static volatile uint32_t s_idle_max = 1u;/* 历史最大空闲圈数（= 空载时的值） */
static volatile uint32_t s_load_pct;     /* 0 ~ 100 */

/* 在 SysTick 的 1 ms 中断里调用 */
void load_tick_1ms(void)
{
    uint32_t now = s_idle_cnt;
    uint32_t d   = now - s_idle_last;
    s_idle_last  = now;

    /* 空闲圈数的最大值就是「CPU 完全没事干」时的值。
     * 第一次跑到最大值需要一个空载窗口；也可以用空载固件先标定一次。 */
    if (d > s_idle_max) {
        s_idle_max = d;
    }

    /* 空闲比例 = d / s_idle_max；占用率 = 1 - 空闲比例 */
    s_load_pct = 100u - (d * 100u) / s_idle_max;
}

/* 主循环的最后一行调用：什么也不做，只是把「我又闲了一圈」记下来 */
void load_idle_hook(void)
{
    s_idle_cnt++;
}

uint32_t load_get_pct(void)
{
    return s_load_pct;
}

/* 【用法与要点】
 *   while (1) {
 *       app_task();
 *       load_idle_hook();       // ← 主循环最后一行
 *   }
 *
 *   要点 1：分辨率 = 1 / s_idle_max。
 *           若主循环 1 ms 能跑 20000 圈，分辨率就是 0.005%，足够用；
 *           若只能跑 100 圈，分辨率 1%，那就该把统计窗口拉长到 10 ms。
 *   要点 2：s_idle_max 会被「曾经出现过的最空闲时刻」不断刷新，
 *           所以统计值会随时间越来越准（但也意味着上电初期偏高）。
 *   要点 3：占用率突然从 35% 跳到 90%，这本身就是一个重大线索——
 *           说明有任务变慢了、有中断变频繁了、或者有 while 在空转。 */

#include "stm32f10x.h"

/* 链接脚本里的栈底符号（栈向下增长，这是最低地址） */
extern uint32_t _stack_limit;

#define STACK_PAINT   0xA5A5A5A5u

/* 在 main 的最开始调用一次：把「当前还没用到的栈空间」全部涂上魔数。
 * 注意方向：栈从高地址往低地址增长，
 *   已被使用的区域在 [当前 SP, 栈顶)；
 *   我们要涂的是 [_stack_limit, 当前 SP) 这一段「未来会用到的空间」。 */
void stack_paint(void)
{
    uint32_t sp;
    uint32_t *lo = &_stack_limit;
    uint32_t *hi;

    __asm volatile ("mov %0, sp" : "=r"(sp));
    hi = (uint32_t *)(sp & ~3u);

    for (uint32_t *p = lo; p < hi; p++) {
        *p = STACK_PAINT;
    }
}

/* 任何时候都可以调用（比如每分钟一次、或复位前）：
 * 从栈底往上找第一个「不再是魔数」的字，它的位置就是历史最深水位。 */
uint32_t stack_used_max(void)
{
    uint32_t sp;
    uint32_t *lo = &_stack_limit;
    uint32_t *hi;
    uint32_t *p;

    __asm volatile ("mov %0, sp" : "=r"(sp));
    hi = (uint32_t *)(sp & ~3u);

    p = lo;
    while ((p < hi) && (*p == STACK_PAINT)) {
        p++;
    }
    /* 从 p 到 hi 就是曾经被用过的部分 */
    return (uint32_t)(hi - p) * 4u;
}

/* 【怎么用这些数字】
 *   总栈大小 = 初始 SP - _stack_limit（在 .map 里能看到）
 *   余量百分比 = (总栈 - stack_used_max) / 总栈
 *   经验线：余量小于 25% 就该加栈；小于 10% 属于随时会炸。
 *
 * 【三个必须知道的干扰】
 *   ① 如果某个变量恰好等于 0xA5A5A5A5，会把水位算浅（概率极低但存在）。
 *   ② -O2 会让局部变量消失（进寄存器），测出来的水位比 -O0 浅；
 *      要评估产品的最坏水位，就得在发布构建里测。
 *   ③ 中断嵌套会额外加深栈。跑到最深的那次很可能发生在中断里，
 *      所以测量时机要覆盖长时间运行，而不是开机测一次。
 *
 * 【用了 FreeRTOS 的话】
 *   每个任务用 uxTaskGetStackHighWaterMark(NULL) 直接拿余量（单位是字），
 *   它内部用的就是这个魔数填充原理（configCHECK_FOR_STACK_OVERFLOW）。 */

#include <errno.h>
#include <stddef.h>
#include <stdint.h>

extern uint32_t _end;            /* 堆起点：.bss 之后（链接脚本符号） */
extern uint32_t _stack_limit;    /* 栈底：堆绝不能长到这里 */

static uint32_t s_heap_peak;     /* 历史最高水位（字节） */

/* newlib 的 malloc 最终会调用 _sbrk 向系统要内存。
 * 自己实现它，就能在每一次分配时顺便记录水位 —— 零额外开销。 */
void *_sbrk(ptrdiff_t incr)
{
    static uint8_t *brk = NULL;
    uint8_t *prev;

    if (brk == NULL) {
        brk = (uint8_t *)&_end;
    }
    prev = brk;

    /* 越界检查：堆一旦长到栈底，接下来就是「堆踩栈」的经典死法 */
    if ((uint32_t)(brk + incr) >= (uint32_t)&_stack_limit) {
        errno = ENOMEM;
        return (void *)-1;
    }

    brk += incr;

    if ((uint32_t)(brk - (uint8_t *)&_end) > s_heap_peak) {
        s_heap_peak = (uint32_t)(brk - (uint8_t *)&_end);
    }
    return prev;
}

uint32_t heap_peak(void)
{
    return s_heap_peak;
}

/* 【怎么读】
 *   堆总大小 ≈ &_stack_limit - &_end
 *   水位长期在涨 → 有内存泄漏（每次分配都没释放），
 *                   或者在中断/异常路径里发生了分配但没回收。
 *   水位突然贴近上限 → 大概率马上要 HardFault，而且现场会很难看
 *                       （堆把栈盖了，返回地址变成垃圾）。
 *
 * 【用了 FreeRTOS 的话】
 *   xPortGetFreeHeapSize()         当前剩余
 *   xPortGetMinimumEverFreeHeapSize()  历史最小剩余（= 最高水位）
 *   后者才是判断余量的依据，前者只反映当下。 */

4.6 断点导致看门狗复位：复现与解决

这是「调试本身引入的问题」里最经典的一个，也是很多人第一次遇到时的心理阴影：程序跑得好好的，一下断点就重启；同学告诉你是「程序有病」，你也开始怀疑自己的代码。真相是：独立看门狗由自己的 LSI 时钟驱动，内核被调试器停住（halt）时它照样在数数。它超时了就复位，跟你的代码一点关系都没有。这段代码先把现象复现出来，再给三种解法。

#include "stm32f10x.h"
#include "reset_info.h"
#include "log_ring.h"

/* LSI ≈ 40 kHz（F103 典型值，实际 30~60 kHz 波动）
 * 超时 = RLR × 预分频 / f_LSI = 625 × 64 / 40000 = 1.0 s */
void iwdg_init(void)
{
    IWDG->KR = 0x5555u;              /* 解除写保护 */
    IWDG->PR = IWDG_PR_PR_2;         /* 预分频 64（PR=100b） */
    IWDG->RLR = 625u;                /* 重装值 → 约 1 s */
    IWDG->KR = 0xCCCCu;              /* 启动。注意：一旦启动，无法关闭 */
}

void iwdg_feed(void)
{
    IWDG->KR = 0xAAAAu;              /* 喂狗 */
}

int main(void)
{
    reset_info_capture();            /* 先记录上次的死因 */
    log_ring_init();

    iwdg_init();

    while (1) {
        GPIO_ToggleBits(GPIOC, GPIO_Pin_13);   /* ← 在这一行下断点，停 2 秒 */
        iwdg_feed();
    }
}

/* 【观察结果】
 *   断点停下 → 等 2 秒 → 调试器显示目标丢失/复位
 *   复位后读 log_ring 与 reset_info：
 *     [RST] boot=2 rs=0x0008 asserts=0 last_line=0
 *     rs 里的 0x0008 就是 RS_IWDG —— 独立看门狗复位。
 *   boot_cnt 从 1 变成 2，说明确实复位了一次。
 *
 * 【为什么这是「正常现象」】
 *   IWDG 的时钟来自独立的 LSI 振荡器（内部 RC），
 *   不依赖内核时钟、不依赖你停在哪条指令上。
 *   调试器 halt 只停 CPU，不会停外设 —— 看门狗、定时器、DMA、
 *   通信对端全都还在动。这就是「停下来本身改变了系统」的具体含义。 */

/* 在 main 的开头、iwdg_init() 之前调用 */
void debug_freeze_watchdog(void)
{
    /* STM32F1 系列：DBGMCU_CR 里有专门的控制位 ——
     * 内核在调试停止时，IWDG/WWDG 是否继续计数。 */
    DBGMCU->CR |= DBGMCU_CR_DBG_IWDG_STOP | DBGMCU_CR_DBG_WWDG_STOP;

    /* 【换系列要注意】
     *   STM32F4 把这两个位挪到了 DBGMCU_APB1_FZ 寄存器：
     *     · DBG_IWDG_STOP 在第 12 位
     *     · DBG_WWDG_STOP 在第 11 位
     *   F0/F3/F7/L4 等系列也在 DBGMCU_APB1_FZ（或 APB1FZR）里，
     *   位名与位置不完全相同 —— 请以工程里的 CMSIS 头文件为准，
     *   不要照抄这里的宏名。
     *
     *   还有一类产品根本不提供这个功能：看门狗一旦启动就绝不冻结
     *   （安全设计使然），这时只能用解法二或三。 */
}

/* 为什么推荐它：它是「只在调试时生效」的解法 ——
 * 调试器连着时看门狗冻结（你可以安心下断点、单步、蹲着看），
 * 调试器拔掉后看门狗照常工作（真实的产品行为被保留）。 */

/* ---------- 解法二：调试构建里不启动看门狗 ---------- */
void app_watchdog_start(void)
{
#ifndef DEBUG_BUILD
    iwdg_init();
#else
    /* 调试构建：什么都不做，让断点、单步、长时观察都不受干扰 */
#endif
}

/* 【代价与纪律】
 *   这个解法会把「喂狗太慢」这类真实缺陷一起掩盖掉：
 *   你在调试构建里跑得好好的，发布构建一上电就复位。
 *   所以它的使用纪律是：
 *     · 只在「专门追一个需要长时间断点/单步的问题」时临时用；
 *     · 追完之后立刻切回带看门狗的构建跑一遍完整测试；
 *     · 绝不把它当成长期配置留在工程里。 */

/* ---------- 解法三：改用不停 CPU 的手段观察 ---------- */
/*  把「停下来看」换成下面这些，看门狗就永远不会被踩到：

 *   ① Live Watch / 实时变量刷新（不 halt，后台读内存）
        —— 看计数器、标志位、状态机变量，见 2.5 节
 *   ② ITM / SWO 日志（CPU 只花几个周期把字节丢进 FIFO，见 4.3 节）
 *   ③ log_ring_push() 环形日志（几十纳秒，见 4.1 节）
        —— 事后 dump，跑一晚上也不影响系统
 *   ④ GPIO 翻转 + 示波器（两条指令，量时间最准）
 *   ⑤ 数据观察点（watchpoint）设为「命中即记录不停机」的场合很少，
        多数调试器一命中就停 —— 所以它仍然要配合解法一使用。

 * 【选择顺序建议】
    先试解法一（冻结看门狗）→ 不行再解法三（改成不停机观察）
    → 万不得已才用解法二（但必须记得切回来）。 */

/* 【现象】
 *   故障是偶发的：通信偶尔超时、偶尔丢一包、偶尔状态错。
 *   你为了查它加了几行日志 —— 故障消失了。
 *   把日志删掉 —— 故障又回来了。
 *   你会开始怀疑「编译器有 bug」或者「板子有灵性」。
 *
 * 【真相】
 *   加日志改变了「时间」：打印语句本身要花时间，
 *   于是两个事件之间的相对顺序、中断响应的时机、超时的边界全都变了。
 *   这是典型的**时序相关缺陷**（竞态、中断优先级、共享变量未保护），
 *   不是玄学。
 *
 * 【确认方法：只加时间，不加数据】
 *   把 printf 换成一段什么也不做的空循环，只消耗时间： */
for (volatile uint32_t i = 0; i < 200u; i++) {
    __NOP();
}
/*   · 如果故障也跟着消失了 → 100% 是时序问题，与日志内容无关。
 *   · 如果只有加「打印变量」才消失 → 也可能是时序（打印变量的开销更大）。
 *
 * 【接下来按这四步查】
 *   ① 看中断优先级：是不是有两个外设抢同一份数据，
 *      而优先级设置让「该先跑完的没跑完就被打断了」？（NVIC_SetPriority）
 *   ② 看共享变量：主循环与中断同时读写的那几个变量，
 *      有没有加 volatile？有没有进临界区？（volatile 不保证原子性，见 2.4）
 *   ③ 看通信超时：对端等你的时间是不是刚好卡在边界上？
 *      把超时放宽 20% 试试 —— 如果故障消失，就是余量不足，不是逻辑错。
 *   ④ 换成不停机的手段（ITM / 环形日志）复测：
 *      如果换成零开销的日志之后故障回归，就彻底证明了是「时间」在起作用。
 *
 * 【为什么第 ④ 步很重要】
 *   它把「加日志就好了」这个模糊现象，变成了一个可复现的实验：
 *   同一份逻辑，只改输出通道（阻塞 → 非阻塞），
 *   故障出现与否就成了一个干净的对照结论。
 */
这六段代码怎么落地

不要一次全抄进工程。建议的顺序是：先加 4.1（环形日志）+ 4.4（复位源）——这两段让你在任何时候都能回答「它上次是怎么死的」，收益最大、风险最小；再补 4.2（断言三级宏），把关键假设变成会主动报错的检查；最后按需要加上 4.3 / 4.5 / 4.6。整个过程加起来大约半天工作量，但它换来的是「下次出问题不用再靠猜」。这也正是第 33 篇想要的结果：调试能力的提升，往往不来自学会某个工具，而来自把「留现场」变成工程的默认配置。

常见误区：十个「听起来很对」的错误认知

这一节列的十条，全部是真实项目里能见到、而且会造成实际损失的误解——其中大半会让学生把自己的代码改坏、或者把已经修好的问题又改回去。每条都按「错误认知 → 为什么错 → 正确做法」三段写。

误区 1：遇到问题，先连上调试器下个断点

为什么错：断点只能回答「程序有没有走到这里」，而绝大多数问题的答案在走到这里之前就已经写好了——电源不稳、时钟没起来、引脚被复用成了别的功能。在一个「根本没跑起来」的系统上设断点，你会看到程序停在启动文件里，然后开始怀疑启动文件。这正是「先分层再二分」要避免的：你还不知道故障在哪一层，就已经把自己锁死在最里面那一层了。

正确做法：动手前先说一句「我认为问题在第几层」——电源硬件 / 时钟复位 / 外设配置 / 驱动中断 / 应用逻辑。分层之后选工具：下面两层用表笔，中间一层看寄存器，上面两层才用调试器。如果你说不出在哪一层，那就先做一件最便宜的判定：量一次供电、确认一次时钟、点一盏灯。

误区 2：一加断点就重启，说明程序有毛病

为什么错：独立看门狗（IWDG）的时钟来自独立的 LSI 振荡器，它不依赖内核时钟、也不受调试器 halt 的影响。你停住的是 CPU，不是整颗芯片——看门狗、定时器、DMA、通信对端全都还在跑。所以「下断点 → 停 2 秒 → 复位」是必然现象，和你的代码质量毫无关系。真正有毛病的是「把这个现象当成代码缺陷，然后开始乱改代码」。

正确做法：三条路，按顺序试。① 在 main 开头调用本页 4.6 的 debug_freeze_watchdog()，让调试器 halt 时冻结看门狗（F1 在 DBGMCU->CR，F4 在 DBGMCU_APB1_FZ）；② 把「停下来看」换成不停机的手段（Live Watch / ITM / 环形日志）；③ 万不得已才在调试构建里不启动看门狗，并且记得追完问题切回来。顺带一个收获：复位日志里出现 rs=0x0008（RS_IWDG）时，先想想自己刚才是不是在断点上停了很久，再去怀疑程序。

误区 3：条件断点就是「带条件的普通断点」，代价差不多

为什么错：条件断点不是硬件替你筛的。它的机制是：每次执行到这一行，都真的把 CPU 停下来，调试器读回条件里涉及的变量（走 SWD 传输）、判断、不满足再继续。也就是说，命中 100 万次的循环里放一个条件断点，等于让程序停下 100 万次、让调试器搬 100 万次数据。在 1 kHz 的中断里放条件断点，基本等于让系统停止工作。

正确做法：条件很挑（几乎不命中）→ 可以用，但优先改成代码里自带判断：if (cond) { __BKPT(0); }——条件由 CPU 自己用一条比较指令判断，只有真的满足时才触发硬件断点，速度快几个数量级。条件很常见（命中率高）→ 说明这不是「异常」，别用断点，用日志或计数器统计它出现的频率与上下文。另外记住：这两个方案各消耗一个硬件断点名额，而名额只有 6 个（见例 1）。

误区 4：数据观察点能盯着任何变量——包括局部变量和结构体成员

为什么错：数据观察点（watchpoint）靠硬件比较器工作，它只认「地址」，不认「名字」。所以它有三个硬前提：变量的地址必须固定（全局变量或 static 变量；局部变量在栈上、地址随调用层次变化，普通局部变量甚至可能只在寄存器里，根本没有地址）；变量必须是 volatile（否则编译器可能把它缓存在寄存器里，内存根本不会被写，观察点自然不触发）；编译器不能把这个变量优化掉（__attribute__((used)) 可以强制保留）。另外，观察点看的是「内存被改了」，看不到「谁改的」这个身份——它能给你精确的调用栈，但栈顶那行就是答案。

正确做法：要盯的变量满足三前提就直接用观察点——它是回答「谁改了这个变量」的唯一可靠手段，比在任何可疑代码上加断点都快。不满足三前提时：把变量提升为文件级全局变量并加 volatile 与 used，再观察；或者用「读-改-写」包装：static inline void set_state(uint8_t v){ g_state = v; }，在 set_state 里下断点，顺便还能看到全部调用者。

误区 5：printf 是最简单的调试手段，想加就加

为什么错：串口 printf 是阻塞的，而且是所有调试手段里最慢的一种。按 8N1 算，一个字符要 10 个位：115200 波特率下 40 个字符要 3.47 ms；放在 1 kHz 的控制中断里，占用率是 347%——不是「有点慢」，是根本不可能。更隐蔽的伤害是：它改变了时序，于是偶发的时序问题会被掩盖（就是那个著名的「一加日志就好了」）。

正确做法：按场合选通道。慢速、人在旁边看、不在中断里 → 串口日志没问题（用 4.3 的非阻塞环形队列版本，别用阻塞版）。中断里或实时回路里 → 用 ITM/SWO 或 RAM 环形缓冲：ITM 每次写只花几个周期，RTT 类方案几乎零开销。有一个简单的判据：日志开销超过时间预算的 1% 就要谨慎，超过 10% 就连「偶发」都不能接受（见例 5）。还有一条纪律：发布固件里不要把 DEBUG/VERBOSE 级日志和格式化字符串一起编进去——用 #if 裁掉，而不是把等级常量设成 none。

误区 6：-O0 下跑得好好的，说明代码没问题

为什么错：-O0 会保留所有变量在内存里、不做重排、不做内联、不删无用代码。于是两类真实缺陷被它藏起来了：① 该加 volatile 而没加的变量（-O0 每次都读内存，看起来正常；-O2 缓存进寄存器，主循环永远看不到中断里的修改）；② 竞态与重排（-O0 的执行顺序恰好不会踩雷）。现象就是那句经典的「Debug 版能跑，Release 版不行」。

正确做法：用 -O0 调试、用 -O2（或与发布一致的优化等级）做验证，两者都要跑。定位这类问题时，不要盯着源码猜，要去看反汇编——你会直接看到「这条读内存的指令消失了」。相关的一点：解除这类故障的关键词是「编译器不知道的事」——中断里改了主循环会读的变量、DMA 写了 CPU 会读的缓冲、寄存器读一次就清标志的硬件行为，这三类都必须 volatile。注意 volatile 不保证原子性，多位标志位仍要进临界区。

误区 7：改了几处之后没再出现过，就是修好了

为什么错：偶发故障的「没再出现」几乎没有证明力。如果它平均 8 小时出现一次，你蹲 2 小时没看到，只说明「有 22% 的概率本该看到」；蹲 8 小时也只有 63% 的概率能看到。更糟的是：如果你同时改了三处，那么即使真的修好了，你也不知道是哪一处起了作用——下次遇到同类问题你依然没有可复用的经验。

正确做法：先量化频率，再谈修复。① 用第 4 节的黑匣子/复位日志把故障次数自动记下来（别靠回忆「感觉变少了」）；② 记录基准频率 λ（次/小时），用 T = 3/λ 估算「需要观察多久才能说它有显著下降」——平均 8 小时一次的问题，至少要观察 24 小时（见例 4）；③ 一次只改一处，改完回到同一个场景跑够时间，对比次数；④ 说不清是根因时，就诚实地说「这是规避，不是根治」，并在代码里写下注释说明原因。

误区 8：HardFault 必须读汇编、看栈帧才能定位

为什么错：反过来说了。读栈帧是最后一步，不是第一步。在你还没弄清「是谁把程序弄到这个状态」之前就去读 xPSR 和 PC，很容易陷在一条无辜的指令上。而且现在绝大多数 HardFault 的真正入口是另外两条更便宜的信息：复位源（RCC->CSR：是看门狗、是断言软件复位、还是掉电）与故障状态寄存器（SCB->CFSR + BFAR：是访问了非法地址、除零、还是未对齐）。

正确做法：按这个顺序：① 读复位源与「上一次的死因」（本页 4.4，通常到这一步就结束了）；② 读 CFSR，如果 BFARVALID 置位再读 BFAR——它直接给出非法访问的地址（0x00000004 就是空指针 + 偏移 4，答案已经呼之欲出）；③ 用 addr2line 把 PC 翻成源码行号；④ 只有前面都问不出来时，才去读压栈帧与汇编现场。栈帧怎么读、naked 函数怎么写、xPSR/PC/LR 各自是什么，第 25 篇《CPU 架构与指令执行》已经完整讲过一遍，这里不重复——需要时回去看 core-cpu.html 的「打开反汇编，读一次 HardFault」。

误区 9：调试器插上了，就说明我正在调试

为什么错：「连上」和「能调试」之间还有好几道门：① VREF 没接——调试器不知道目标的电平，可能连芯片都检测不到；② 引脚被复用——PA13/PA14 被配成了普通 GPIO，或者 SWJ_CFG 关掉了 SWD；③ 芯片进了低功耗——Sleep/Stop 状态下调试口会被关闭，表现是「跑到一半就掉线」；④ 程序一上电就跑飞——常规连接抓不住它，必须用 connect under reset；⑤ 程序主动关了调试时钟（为了省电）。

正确做法：逐条排查，形成固定动作：先确认四线（SWDIO / SWCLK / GND / VREF）都在，再确认调试器设置里的「Connect under reset」打开、复位方式选对；如果怀疑程序关了调试口，就在 main 最开头、任何初始化之前先连（或者用 BOOT0 拉高从系统存储器启动，此时用户程序根本没运行）；确认低功耗场景时在 DBGMCU_CR 里把 DBG_SLEEP / DBG_STOP / DBG_STANDBY 打开。记住一个判据：如果「昨天还能连、今天就检不到」，先看代码里有没有新增 GPIO 初始化动到了 PA13/PA14/PA15/PB3/PB4。

误区 10：日志当然越多越好；断言里写什么表达式都行

为什么错：两件事都是「当下舒服、以后难受」。日志方面：全量日志会占满 RAM 环形缓冲（把真正重要的早期记录挤掉）、占满串口带宽（拖慢实时回路）、暴露内部信息，还会让编译产物变大。断言方面更危险：断言是定位工具，不是错误处理机制，写在里面的表达式如果带副作用（ASSERT_RET(buf[i++] != 0, ERR_PARAM)），在 NDEBUG 构建里被裁掉之后，程序行为就变了——这类 bug 极难查，因为它只在发布版出现。

正确做法：日志按等级与场合分级：故障与状态变化用事件码进环形缓冲（几十纳秒、始终开着），调试信息用 ITM（按需打开），串口只留人看的少量 INFO 及以上。断言里只放无副作用、可重复求值的检查（指针非空、范围、状态合法性、句柄有效），并且要能回答一个标准问题：「这个断言如果成立，我该去改哪一段代码？」答不出来就删掉它——那不是断言，是噪声。另外，断言失败后的动作要事先定好：停机（调试）/ 记录后复位（现场）/ 降级继续（不允许停机的场合），三者选一，不要每次现想。

小结与自测

回到开头那个场景：课设的程序不工作，你查了三天，同时改了十几个地方，最后也不知道是哪一处起了作用。现在你应该能说清楚它错在哪了——不是工具不够，是过程不对。调试的全部功夫，可以压缩成一句话：用最便宜的手段，把「哪里可能错」的集合，一次砍掉一半；并且在这个过程中，让系统始终替你留着证据。这一页的所有工具、所有算式、所有代码，都是为这句话服务的。

要点清单

一 · 思路：先分层，再二分
  • 五层漏斗：电源硬件 → 时钟复位 → 外设配置 → 驱动中断 → 应用逻辑。先说是哪一层，再选工具。
  • 下面两层用表笔，中间一层看寄存器，上面两层才用调试器。
  • 二分三种切法：边界打点（两头打点看谁先错）、时间二分（跑 1 分钟会不会错）、版本二分（昨天还好好的）。
  • 最小可复现工程是最强的一招——把问题剥出来的过程本身，常常就把原因剥出来了。
  • 对照实验：换一块板、换一个电源、换一个对端，一次只换一个变量。
  • 偶发故障先量化频率，别用「感觉变少了」当结论。
二 · 接口：为什么是 SWD
  • SWD 两线（SWDIO/SWCLK）vs JTAG 五线，引脚少、速率高、布线容易——所以它是默认选择。
  • 接线四件套必须全：SWDIO / SWCLK / GND / VREF。
  • VREF 的作用：① 让调试器知道目标电平（1.8V 还是 3.3V）；② 作为输入缓冲的参考，并据此判断目标是否上电。不接 VREF 的典型现象就是「检测不到芯片」。它只做参考，不要用它给目标板供电。
  • 建议同时接 NRST 与 SWO：前者用于 connect under reset（抓一上电就跑飞的程序），后者用于 ITM 日志。
  • 线长、上拉、降速：SWCLK 拉长到 20 cm 以上就该降到 1 MHz 试试。
三 · 四种断点，四种场合
  • 硬件断点：比较器实现，数量受限（M3/M4 一般 6 个指令 + 4 个数据），但能在 Flash 与 RAM 里随便用。
  • 软件断点：把指令换成 BKPT（编码 0xBE00），数量不限，但会改指令、可能破坏时序，不适合实时回路与自修改代码。
  • 条件断点：命中即停、由调试器判断，很慢；改写成 if (cond) __BKPT(0); 快得多。
  • 数据观察点：回答「谁改了这个变量」的唯一手段；前提是地址固定 + volatile + 没被优化掉。
  • 超了名额怎么办：改用计数器、事件码日志、代码内 __BKPT，并给断点排优先级（观察点 > 时序敏感 > 需单步 > 普通逻辑）。
四 · 停下来看，还是不停下看
  • Watch 窗口依赖 halt；局部变量出作用域后显示 <not in scope> 或地址错乱、值变成垃圾。
  • Live Watch 靠后台读内存，不停 CPU；只能看固定地址，刷新约 100 ms ~ 1 s，会与 CPU 争总线。
  • 环形黑匣子：把关键事件压成事件码存进 .noinit 段，复位后 dump——「跑一晚上才死一次」的正确答案。
  • printf 三条路：串口（慢、阻塞、唯一不依赖调试器）、SWO/ITM（不占串口、CPU 几个周期）、RTT（内存缓冲、最快、最适合中断里）。
  • 判据：这条日志会打断谁？如果它出现在中断或实时回路里，就不许用阻塞通道。
五 · 留证据：日志、断言、复位源
  • 日志五级 E/W/I/D/V；D/V 要用 #if 裁，常量条件裁不掉字符串。
  • 日志记值与事件码，不记大段描述；别用 %f（格式化比传输更贵）。
  • 断言是定位工具，不是错误处理；只放无副作用、可重复求值的检查。
  • 断言失败三策略：停机 / 记录后复位 / 降级继续，事先选定。
  • 复位源 RCC->CSR + 备份寄存器遗言：复位前把行号与次数写进 BKP->DRx，复位后第一件事读出来并清除标志。
  • 余量三指标：CPU 占用率、栈水位魔数 0xA5A5A5A5、堆水位。
六 · 调试本身会引入问题
  • 断点会让看门狗复位：IWDG 由 LSI 驱动，halt 不影响它 → 冻结看门狗或改用不停机手段。
  • 单步会让通信超时：对端不知道你在单步，它的超时照样在走。
  • 调试器占用引脚：PA13/PA14 被复用、SWO 要占 PB3（F1 需关 JTAG 才能释放）。
  • -O0 会掩盖 -O2 才出现的缺陷（缺 volatile、竞态、重排）。
  • 加日志改变时序：故障消失往往不是被修好，而是被掩盖——它是时序问题的证据，不是解法。

自测题（先自己答，再看答案）

  1. 板子上的程序完全不工作。请按顺序说出你的前三步，并说明每一步在排除哪一层。

    答案：关键在于从便宜到贵、从下往上。① 量供电与电平（万用表量 VDD 是否为 3.3V、复位脚是否为高、晶振是否起振）——排除「电源硬件层」。② 确认程序真的在跑（点一盏灯、翻转一个 GPIO，用示波器看）——排除「时钟复位层」：如果灯不亮，问题在系统启动而不是你的业务代码。③ 确认外设配置生效（读一眼寄存器，比如串口的 BRR、GPIO 的 MODER）——排除「外设配置层」。这三步都做完再去连调试器，因为此时你已经知道故障在哪一层，断点才有明确的目标。反例：一上来就下断点，停在启动文件里，然后开始怀疑启动文件。

  2. 调试器四根线都接了，但 IDE 里显示「No target connected」。列出至少三种可能原因和验证方法。

    答案：① VREF 接错或没接——调试器无法判定目标电平，也判不出目标是否上电；验证：量 VREF 引脚上是否有 3.3V，且与调试器的 VREF 脚导通。② 程序把 PA13/PA14 复用成了 GPIO 或关掉了 SWD（AFIO->MAPR 的 SWJ_CFG、或者 __HAL_AFIO_REMAP_SWJ_DISABLE）；验证：把 BOOT0 拉高、从系统存储器启动（用户程序不运行）再连——能连上就说明是程序关的。③ 芯片在低功耗或程序一上电就跑飞；验证：打开调试器的「Connect under reset」并接上 NRST，如果能连上就是这个问题。④（补充）复位方式选错（选了「硬件复位」但 NRST 没接）、SWCLK 速率过高或线太长、GND 没共地。⑤（补充）目标板由调试器供电但电流不足。

  3. 一个 6 个硬件断点名额的工程里，要同时盯 5 个可疑位置、2 个变量、并且还想单步。名额够吗？如果不够，给出两种不花钱的替代方案。

    答案：不够。计算是：5（指令）+ 2（数据）= 7 个名额，而 M3/M4 只有 6 + 4。虽然指令与数据是分开的两组、单看都不超，但单步本身也要占用一个硬件断点名额（step over 需要临时断点），而 IDE 还会为「断点列表」占位，所以实际上 5 个指令断点已经偏多。替代方案一：代码内 __BKPT(0)——把 5 个可疑位置改成「计数器 + 条件判断 + __BKPT」，只在真正异常时才触发，几乎不占名额，而且仍然能停在你想要的地方。替代方案二：观测点 + 事件码日志——2 个变量用数据观察点（真需要「谁改的」时才用），其余的可疑位置改成 log_ring_push(EV_STATE_JUMP, 值) 记录事件码，跑一段时间后 dump 出来看顺序。这两招合起来，可以把 7 个名额压到 1~2 个，剩下的留给单步。

  4. 1 kHz 的控制中断里想打一条 40 字符的日志。用 115200 串口、921600 串口、2 MHz SWO 各是什么代价？哪个能用？

    答案：8N1 下每个字符 10 位，40 字符 = 400 位。115200：400 ÷ 115200 = 3.47 ms，而中断周期只有 1 ms，占用率 347%——不可能，程序会完全失控。921600：400 ÷ 921600 = 434 µs，占 1 ms 的 43.4%——技术上能跑，但中断里干别的就没什么时间了，属于「能用但危险」，而且串口发送仍是阻塞的，会直接破坏控制环的时序。2 MHz SWO：线上 400 位 ÷ 2 MHz = 200 µs（占 20%），但 CPU 侧只花 几个周期把字节写进 ITM FIFO（约 1~5 µs），不阻塞——这个能用，前提是 FIFO 不满（满了就会退化阻塞）。结论：中断里用 SWO 或 RAM 环形缓冲（RTT 级别，约 1~2 µs），不要用串口；如果只是想记「发生过什么」，用事件码而不是字符串，代价可以降到 0.1 µs 量级。

  5. 某个偶发复位平均 8 小时出现一次。你改了代码，想证明「它真的好了」。至少需要观察多久？如果你只能连续跑 8 小时，能得出什么结论？

    答案：λ = 1/8 = 0.125 次/小时。用「三倍法则」T ≥ 3/λ：T ≥ 24 小时。所以至少要连续跑一整天没复现，才能说「有显著下降」。如果只跑了 8 小时（T = 1/λ），根据泊松分布，没复现的概率是 e^(-λT) = e^(-1) ≈ 36.8%——有多达 63% 的概率本该复现一次却没被你看到，所以「跑了 8 小时没事」几乎没有证明力。更严格的表述是：跑 T 小时无复现，只能给出上界 λ_new ≤ 3/T；跑 8 小时只能说 λ ≤ 0.375 次/h，比修复前的 0.125 次/h 还大——等于什么都没证明。想证明「下降 10 倍」，需要 T ≥ 3/(0.0125) = 240 小时，约 10 天，所以工程上会改用多台并行（10 台跑 1 天 = 单台 10 天）或加速应力（高温、电压边角、频繁上下电）。

  6. 「这个故障一加日志就好了，所以肯定是代码有 bug。」这句话哪里对、哪里不对？你会怎么确认？

    答案：对的一半是：它确实是真实缺陷，不是玄学，也不是编译器的问题。不对的一半是：它不代表「日志修好了它」——日志只是改变了时序，把原本会踩雷的窗口错开了。确认步骤：① 把 printf 换成一段什么都不做的空循环（只花时间、不改数据）：如果故障同样消失，就证明起作用的只是时间，不是日志内容。② 换成零开销的输出通道（ITM 或 RAM 环形缓冲）复测：如果故障回归，就彻底证明是时序问题。③ 然后按四条线索查根因：中断优先级配置是否让「该先跑完的」被打断（NVIC_SetPriority）、共享变量是否缺 volatile 或临界区保护、对端超时余量是否不足（把超时放宽 20% 试试）、以及有没有依赖「某段代码必须在一个时间窗内跑完」的隐含假设。④ 最后一点纪律：在没有找到根因之前，不要把「加了一条日志」当成修复提交上去——那是把 bug 藏起来。

  7. 为什么「跑一晚上才死一次」的问题，最适合用环形日志缓冲 + 内存 dump 来解决，而不是断点或实时日志？

    答案：因为这类故障有三个特征：偶发（无法靠蹲守等到）、可能发生在中断里（不能用阻塞输出）、一旦复位现场就没了（RAM 被清零、调试器早已掉线）。环形日志同时解决这三点：① 始终开着、开销极小（写一条记录几十纳秒，不影响时序，因此不会像 printf 那样掩盖问题）；② 放在 .noinit 段，复位不清零，配合复位源与 boot_cnt，复位后第一件事就能把「死之前的最后若干条事件」按时间顺序 dump 出来；③ 只记事件码与值，所以 RAM 占用固定且可控（1 KB 能存上百条记录），不会像字符串日志那样把缓冲挤爆。对比：断点需要人在场且怕看门狗；实时日志依赖连接且中断里不能用；Live Watch 只在连着调试器时有效，而故障往往发生在深夜无人值守时。一句话：它把「现场」从 RAM 里搬到了复位之后。

练习（建议动手做，每项 20~45 分钟）

1

给自己的工程装上「黑匣子 + 遗言」

把本页 4.1（环形日志）和 4.4（复位源与备份寄存器）移植进你正在做的工程：加 .noinit 段、在 main 第一行调用 reset_info_capture()、在几个关键位置（进入初始化、收到一帧数据、进入错误分支）调用 log_ring_push()。然后人为触发一次 ASSERT_RESET，复位后读串口打印出的 [RST] boot=… rs=… asserts=… last_line=…，确认行号正是你写的那一行；再把 s_ring 的地址从 map 文件里找出来，用调试器的内存窗口手工 dump 一遍，对照代码验证事件顺序。做完这一题，你就拥有了「事后复盘」的能力。

2

亲手复现一次「断点导致看门狗复位」，再修好它

按 4.6 的代码：使能 IWDG（约 1 s 超时）、主循环里翻转 LED + 喂狗，在翻转那一行下断点停 2 秒，观察复位与 rs=0x0008。然后加上 debug_freeze_watchdog()，同样停 2 秒，确认不再复位。再做一个对照实验：把断点移到 iwdg_feed() 之后、并且只在调试构建里关闭 IWDG，观察两次现象是否一致。思考并用一句话写下来：为什么「调试器 halt 不影响外设」这件事，既是一个坑，也是一个有用的特性？

3

量一次自己工程的「时间预算」，然后决定日志怎么写

选一个最紧的实时环节（定时中断、通信帧处理、控制环），用本页 2.8 节的 GPIO 翻转法 + 示波器测出最坏情况的执行时间，算出剩余余量；然后按例 5 的方法，分别计算「一条 32 字符串口日志 / 一条 ITM 日志 / 一条事件码记录」各占余量的百分之几。把结论写成工程里的一行注释（例如「本中断预算 1 ms，禁止串口日志；调试用 ITM，事件记录用 log_ring」），并且真的按它去改现有的日志语句。这一题的价值在于：把「日志会不会影响实时性」从争论变成一个数字。

4

用逻辑分析仪抓一次「代码看起来对、通信就是不通」

找一个通信不稳的场景（I²C 读传感器偶发失败、SPI 偶发错位、UART 偶发丢字节），把逻辑分析仪接到 SCL/SDA（或 SCK/MOSI/MISO）上，采样率按「信号频率的 10 倍」设置，用协议解码器解出报文。重点看四件事：从机的 ACK 位有没有按时拉低、有没有时钟拉伸（SCL 被从机拉低）、建立/保持时间是否满足、以及失败的帧里数据是否明显错位。写下你的发现，并说明这个问题「读代码」能不能看出来、为什么。

5

做一次「最小可复现工程」的剥离

从你手上（或网上找）的一个有偶发问题的工程出发，目标：把它剥成一个100 行以内、能独立编译运行、并且仍然会复现问题的工程。规则有两条：每删掉一部分代码之前先想「它为什么可能有关」；每删一次都跑一遍确认问题还在。过程中记录两样东西：① 剥离过程中发现的每一条「原来这里还依赖 X」（这类隐性依赖往往就是根因所在的线索）；② 最终的最小工程里，问题是被哪一行触发的。经验之谈：剥离的过程本身，十有八九就把原因剥出来了——因为剥离强迫你为每一行代码回答「它为什么必须在这儿」。
