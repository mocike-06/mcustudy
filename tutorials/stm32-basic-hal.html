写法一：直接写寄存器 —— 最贴近硬件，可读性最差

这种写法里，GPIOC 是一个指向结构体的指针，它的值是地址 0x40011000；GPIOC->ODR 就是「这个地址再往后偏移 0x0C」，也就是 0x4001100C。这些名字不是 C 语言的标准，而是 CMSIS 头文件里的 #define，本质上是给地址起的别名。

它的最大问题不是难写，而是「读代码的人必须同时读参考手册」。看到 GPIOC->CRH |= (0x3UL << 20); 这行，你得知道：CRH 管的是 8~15 号引脚、每个引脚占 4 位、引脚 13 对应第 5 组（20~23 位）、值 0x3 表示推挽输出 50MHz。这些知识一个都不在代码里。

写法二：标准外设库 —— 时代的眼泪

ST 在 2007 年前后推出了标准外设库（Standard Peripheral Library，常简称 SPL 或「标准库」）。它的思路是：为每个外设提供一组 外设名_动作() 风格的函数，比如 GPIO_Init()、GPIO_SetBits()、USART_SendData()。

它在 F1 时代是绝对主流，所以你在网上搜到的老教程、学校的旧实验指导书、很多考研复试资料，用的都是它。但从 2011 年之后 ST 基本停止了它的更新，新出的 F0、F4、F7、H7 系列都不再有标准库版本，官方全面转向 HAL 和后来的 LL 库。所以：能看懂，不必新学，不要用它开新项目。

它的一个显著特征是大量使用「位掩码宏」——GPIO_Pin_13 展开后是 0x2000（即 bit13），RCC_APB2Periph_GPIOC 展开后是 0x00000010（即 bit4）。这层名字比裸数字好读，但和 HAL 的命名风格不一样，两套混着看容易乱。

写法三：HAL 库 —— 官方主推，代价是「厚」

HAL（Hardware Abstraction Layer，硬件抽象层）是 ST 现在的主力库。它的核心设计目标是「让同一份代码能跑在不同系列的 STM32 上」：你写 HAL_GPIO_WritePin(GPIOC, GPIO_PIN_13, GPIO_PIN_RESET)，在 F103 上和在 F407 上都能编译、都能工作（当然引脚要对）。

为了做到这一点，HAL 付出了三个代价，这也是新手觉得它「绕」的原因：

  • 参数变多了。为了不写死任何具体芯片的细节，函数要收的参数更多：HAL_GPIO_WritePin 要收三个参数（哪个端口、哪个引脚、什么电平），而寄存器写法一个位操作就完了。
  • 引入了「句柄」这个新概念。每个外设的初始化、收发、状态都需要一个结构体来承载，也就是下一节的 UART_HandleTypeDef 之类。
  • 引入了「回调」这个新机制。中断里该干什么，不再由你直接写在中断服务函数里，而是交给一个约定好名字的函数，也就是后面讲的 HAL_UART_RxCpltCallback()。

此外 HAL 每次调用都会检查外设状态（Lock、gState），参数非法时返回 HAL_ERROR 而不是直接崩溃。这在工程上是好事，代价是每个操作多了几个判断，在超高频率翻转引脚这种场合会比寄存器慢——所以 HAL 另外提供了一套 LL 库（Low Layer，低层库），写法接近寄存器但保留了函数名，需要极致性能时可以混用。

句柄结构体：HAL 里最重要的一个概念（重点）

先解释「句柄」这个词。句柄（Handle）就是「一个代表某个资源的凭据」。生活里的例子是宾馆房卡：房卡本身不是房间，但你拿着它就能开对应的门、享受对应的服务。程序里的句柄也一样——它不是一个外设本身，而是一个装着这个外设全部信息的结构体，你把它传给 HAL 函数，HAL 就知道「你操作的是哪一个外设、它现在处在什么状态」。

为什么非要有个结构体？用具体场景说明：一个 STM32F103 上有 3 个串口。如果没有句柄，HAL_UART_Transmit() 就得写成「传 5 个参数告诉它用哪个串口、波特率多少、数据位几位……」；而且更麻烦的是状态——串口可能正在发送中、可能出过错、可能被某个任务独占。这些信息必须有人存着。句柄就是干这个的。

/* ============================================================================
 * UART_HandleTypeDef：串口句柄
 * 你每用一个串口，就要定义一个这样的全局变量，并把它传进所有 HAL 函数。
 * ============================================================================ */
typedef struct
{
  USART_TypeDef            *Instance;   /* ★ 指向哪个串口外设，如 USART1        */
  UART_InitTypeDef          Init;       /* ★ 通信参数：波特率、数据位、停止位…  */

  uint8_t                  *pTxBuffPtr; /* 正在发送的数据放在哪（指针）          */
  uint16_t                  TxXferSize; /* 这次一共要发多少字节                  */
  __IO uint16_t             TxXferCount;/* 还剩多少字节没发完                    */

  uint8_t                  *pRxBuffPtr; /* 正在接收的数据往哪放                  */
  uint16_t                  RxXferSize; /* 这次一共要收多少字节                  */
  __IO uint16_t             RxXferCount;/* 还剩多少字节没收完                    */

  DMA_HandleTypeDef        *hdmatx;     /* 关联的发送 DMA 句柄（没用 DMA 就是 NULL）*/
  DMA_HandleTypeDef        *hdmarx;     /* 关联的接收 DMA 句柄                    */

  HAL_LockTypeDef           Lock;       /* 占用锁：HAL_UNLOCKED / HAL_LOCKED     */
  __IO HAL_UART_StateTypeDef gState;    /* 发送状态：就绪 / 忙 / 出错            */
  __IO HAL_UART_StateTypeDef RxState;   /* 接收状态                              */
  __IO uint32_t             ErrorCode;  /* 出错代码：校验错、帧错、溢出…          */
} UART_HandleTypeDef;

 * 你在 CubeMX 生成的代码里看到的这一行，就是这个结构体的实例：
 *     UART_HandleTypeDef huart1;        ← 全局变量，名字通常叫 huart1
 *
 * 所有 HAL 串口函数都要收它的地址：

BSRR 和 BRR 是什么？为什么不用 ODR

前面几篇里点灯用的是 GPIOC->ODR（读改写：先读、改一位、再写回）。这个动作有个隐患：如果读和写之间来了个中断，中断里也改了 ODR，你写回去的值就会把中断的修改覆盖掉。STM32 为此专门提供了两个「只写」寄存器：BSRR（置位，低 16 位写 1 把对应引脚拉高）和 BRR（复位，写 1 把对应引脚拉低）。它们不需要读、直接写，天然是原子操作，也就不会踩掉别人的修改。HAL_GPIO_WritePin 内部用的正是它们——这是 HAL 比手写 ODR ^= 更严谨的一个具体例子。

回调机制：为什么 HAL 不让你在中断里写代码（重点）

这是新手最容易懵的地方：「我明明写了串口接收中断，可中断服务函数里怎么只有一行 HAL_UART_IRQHandler(&huart1)？我的处理代码该写在哪？」答案是你得写在一个名字固定的函数里，让 HAL 去调用你。

先讲清「回调（Callback）」这个词。回调就是「你把自己的函数地址交给别人，让别人在合适的时机替你调用它」。生活里的类比是留电话：你把号码给快递员，不是你自己一直站在门口等，而是他到了打给你。这里的「号码」在 C 语言里就是函数指针——函数在内存里也有地址，把地址存起来，以后就能通过它调用那个函数。

weak 是什么：为什么你不写它也能编译过

__weak 是编译器的一个属性（attribute），全称是「弱符号」。C 语言的链接器有个规则：如果同一个名字出现了两次，一次是强符号（普通定义）、一次是弱符号，就用强符号，把弱符号丢掉；如果两个都是强符号，才报「重复定义」错误。

HAL 把所有回调函数都定义成 __weak 的空函数，于是就有了这个效果：你不写，链接器用库里的空函数，编译通过、程序正常运行（只是什么也不做）；你写了同名同参数的函数，你的版本就是强符号，库里的被丢弃，程序就会调用你的。

/* ---------- 在 stm32f1xx_hal_def.h 里，HAL 是这样定义的 ---------- */
#define __weak   __attribute__((weak))

/* ---------- 库里的弱定义（空实现） ---------- */
__weak void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
{
  UNUSED(huart);        /* 宏，展开成 (void)huart;  用来消除「参数未使用」警告 */
}

/* ---------- 你写的强定义（覆盖上面那个） ---------- */
void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)   /* 注意：不要写 __weak */
{
  /* 你的处理逻辑 */
}

 *   → 用你的，库里的被丢弃。

 * ============================================================================ */
「函数写了但从来不执行」的排查顺序

遇到「我的回调没反应」，按这个顺序查，基本三分钟能定位：① 函数名是否与 HAL 头文件里的声明逐字一致（建议直接从 stm32f1xx_hal_uart.h 复制）；② 参数类型和个数是否一致（必须带 UART_HandleTypeDef *）；③ 是不是写成了 static；④ 中断到底有没有进——在 USART1_IRQHandler 里打个断点，如果不进，问题不在回调而在「中断没使能」；⑤ 接收是不是已经收满了——HAL_UART_Receive_IT(&huart1, buf, 1) 收满 1 个字节就自动关中断，需要你在回调里再调一次才能继续收。

HAL_xxx_MspInit()：为什么初始化要拆成两半

MSP 是 MCU Support Package（单片机支持包）的缩写。HAL 把一个外设的初始化工作明确分成了两类：

  • 第一类：外设自己内部的寄存器配置——波特率、数据位、停止位、中断使能等。这部分由 HAL_UART_Init() 完成，与芯片型号无关，写在 HAL 库里。
  • 第二类：这个外设「对外」需要的东西——用哪两个引脚、引脚配成什么模式、开哪条总线的时钟、用不用 DMA、中断优先级多少。这部分因板子而异（同一个 USART1，A 板子接 PA9/PA10，B 板子可能重映射到 PB6/PB7），所以不能写死在库里，必须由你提供。

于是 HAL 定了个约定：HAL_UART_Init() 在配完内部寄存器后，自己去调用一个叫 HAL_UART_MspInit() 的函数，把第二类工作交给你。这个函数在 HAL 库里同样是 __weak 的空实现，你在 stm32f1xx_hal_msp.c 里写一个同名的把它覆盖掉。

/* ============================================================================
 * stm32f1xx_hal_msp.c
 * MSP = MCU Support Package。这个文件专门放「外设对外的接线与时钟」。
 * CubeMX 会自动填好，你一般不需要改。
 * ============================================================================ */

#include "main.h"

/* ---------- 全局的 MSP 初始化：由 HAL_Init() 调用 ----------
 * 这里放「整个芯片级别」的底层配置。 */
void HAL_MspInit(void)
{
  __HAL_RCC_AFIO_CLK_ENABLE();              /* 打开 AFIO 时钟（用中断/重映射必需） */
  __HAL_RCC_PWR_CLK_ENABLE();               /* 打开电源管理时钟 */

  /* 关闭 JTAG、保留 SWD。
     原因：PA15/PB3/PB4 默认被 JTAG 占用，如果项目要用这三个引脚做普通 IO，
     就必须把 JTAG 关掉。这句是 CubeMX 在 System Core → SYS → Debug
     选了 "Serial Wire" 时自动加的。 */
  __HAL_AFIO_REMAP_SWJ_NOJTAG();
}

/* ---------- 串口 1 的 MSP 初始化：由 HAL_UART_Init() 内部调用 ----------
 * 注意调用时机：HAL_UART_Init() 先配好波特率等内部寄存器，
 * 再调这个函数配引脚和时钟。所以顺序是「先内部后外部」。 */
void HAL_UART_MspInit(UART_HandleTypeDef *huart)
{
  GPIO_InitTypeDef GPIO_InitStruct = {0};

  /* ★ 用 Instance 判断「这次初始化的是哪个串口」。
     因为同一个 MSP 函数服务所有串口实例 —— 这正是指针参数的用处。 */
  if (huart->Instance == USART1)
  {
    /* 1) 开时钟：串口本体在 APB2，引脚在 APB2 */
    __HAL_RCC_USART1_CLK_ENABLE();
    __HAL_RCC_GPIOA_CLK_ENABLE();

    /* 2) 配 PA9 = TX，复用推挽输出。
          注意 Mode 是 GPIO_MODE_AF_PP 而不是 GPIO_MODE_OUTPUT_PP：
          「复用」的意思是「这个引脚不归 GPIO 控制器管了，交给 USART 外设管」，
          配成普通输出的话，串口模块根本控制不到这个引脚。 */
    GPIO_InitStruct.Pin   = GPIO_PIN_9;
    GPIO_InitStruct.Mode  = GPIO_MODE_AF_PP;
    GPIO_InitStruct.Speed = GPIO_SPEED_FREQ_HIGH;
    HAL_GPIO_Init(GPIOA, &GPIO_InitStruct);

    /* 3) 配 PA10 = RX，输入浮空（或上拉，看外部电路） */
    GPIO_InitStruct.Pin  = GPIO_PIN_10;
    GPIO_InitStruct.Mode = GPIO_MODE_INPUT;
    GPIO_InitStruct.Pull = GPIO_NOPULL;
    HAL_GPIO_Init(GPIOA, &GPIO_InitStruct);

    /* 4) 配中断优先级并使能 NVIC。
          如果没有这句，即使你调了 HAL_UART_Receive_IT，
          中断也永远不会进 —— 这是「中断模式收不到数据」的最常见原因。 */
    HAL_NVIC_SetPriority(USART1_IRQn, 0, 0);
    HAL_NVIC_EnableIRQ(USART1_IRQn);
  }
}

/* ============================================================================
 * 为什么要拆成两半？看这个「照着别人代码抄串口」的经典翻车场景：
 *
 *   甲的板子：USART1 接 PA9/PA10  → 他的 MSP 里配的是 GPIOA
 *   乙的板子：USART1 重映射到 PB6/PB7 → 他的 MSP 里配的是 GPIOB + 重映射
 *
 *   乙抄了甲的 main.c，里面 HAL_UART_Init(&huart1) 一模一样，
 *   但乙没有抄甲的 stm32f1xx_hal_msp.c。
 *   结果：波特率等等全对，串口就是不出数据 —— 因为引脚根本没配对。
 *   这就是「初始化拆两半」这个设计的现实意义：
 *   让「跟板子有关的」和「跟芯片有关的」各自待在明确的地方。
 *
 * 反过来说：如果你发现「HAL_xxx_Init() 之后外设完全不工作」，
 * 第一件事就是去看对应的 HAL_xxx_MspInit() 有没有被正确实现。
 * ============================================================================ */

CubeMX 是什么，它生成什么，哪些地方你不能改

STM32CubeMX 是 ST 官方出的图形化配置工具（现在已并入 STM32CubeIDE，也有独立版本）。你在界面里点选「用哪个引脚、什么模式、时钟多少、开不开中断」，它据此生成一整套初始化代码：启动文件、CMSIS 头文件、HAL 库文件、main.c、stm32f1xx_hal_msp.c、stm32f1xx_it.c、Keil 工程文件，全部配好。

Core/Src/main.cmain()、SystemClock_Config()、各外设的 MX_xxx_Init()只写在 USER CODE 区域；while(1) 里那块也是

最重要的一条规矩：只写在 USER CODE 之间

CubeMX 生成的所有 .c 文件里都有成对的注释标记：

/* USER CODE BEGIN 2 */ …… 你的代码 …… /* USER CODE END 2 */

这两个标记之间的内容，CubeMX 在重新生成时会原样保留；标记之外的任何修改，重新生成时一律被覆盖掉，而且不会警告你。最常见的翻车场景：在 MX_GPIO_Init() 外面加了点初始化代码、或者改了 SystemClock_Config() 里的分频，几天后因为要加一个外设重新生成了一次代码，改动全部消失，然后花两小时找「代码怎么退回去了」。养成习惯：凡是自己要写的，一律塞进 USER CODE 区域。

LED 为什么要串 470Ω，为什么是低电平点亮

板载 LED 的接法是 3.3V → 470Ω 电阻 → LED → PC13。红色 LED 的正向压降约 1.8V，所以电阻上的电压是 3.3 − 1.8 = 1.5V，电流是 1.5V ÷ 470Ω ≈ 3.2mA。这个电流远小于普通 IO 的 20mA 上限，但 PC13 / PC14 / PC15 的额定上限只有 3mA（这三个引脚能力特别弱），3.2mA 已经压在红线上：板载这颗 470Ω 是厂家焊好的既成事实，你自己搭电路时请把限流电阻换成 1kΩ 以上（(3.3 − 1.8) ÷ 1kΩ = 1.5mA），或者把 LED 挪到 PA / PB 的普通 IO 上——那才是 20mA 级的引脚。而因为 LED 的阳极接在 3.3V、阴极接 PC13，所以PC13 输出低电平时才有电流流过（灯亮），输出高电平时两端都是 3.3V、没有压差（灯灭）。这就是「低电平点亮」的来历——和 51 上常见的「高电平点亮」接法正好相反，所以第一次写 STM32 点灯时很容易「逻辑写反了」。

完整代码

三份代码做同一件事：让 PC13 的 LED 每秒闪烁一次。它们都能单独编译运行（当然要各自配好对应的库工程）。建议你把三份都跑一遍，对比编译出来的代码大小——那是最直观的「抽象层的代价」。

三种写法并列

/* ============================================================================
 * 写法一：直接操作寄存器
 * 工程依赖：只需要 CMSIS 头文件（stm32f103xb.h）和启动文件，不需要任何库
 * 编译产物大小：约 1~2 KB
 * ============================================================================ */

#include "stm32f103xb.h"

int main(void)
{
  /* 1. 打开 GPIOC 的时钟（APB2 的 bit4）—— 没有这一句后面全白写 */
  RCC->APB2ENR |= (1UL << 4);

  /* 2. 把 PC13 配成通用推挽输出、50MHz
        引脚 13 属于 8~15，所以配 CRH；它在 CRH 里占第 (13-8)=5 组，即 bit23~20 */
  GPIOC->CRH &= ~(0xFUL << 20);   /* 先清 4 位 */
  GPIOC->CRH |=  (0x3UL << 20);   /* 0b0011 = 推挽输出 + 50MHz */

  /* 3. 主循环：翻转 PC13
        用 BSRR/BRR 而不是 ODR ^=，因为 BSRR/BRR 是只写寄存器，
        不需要「先读后写」，天然不会被中断打断出问题 */
  while (1)
  {
    GPIOC->BRR  = (1UL << 13);              /* PC13 = 0，灯亮 */

    /* 粗略延时：volatile 防止编译器把空循环优化掉 */
    for (volatile uint32_t i = 0; i < 800000UL; i++)
    {
      __NOP();
    }

    GPIOC->BSRR = (1UL << 13);              /* PC13 = 1，灯灭 */

    for (volatile uint32_t i = 0; i < 800000UL; i++)
    {
      __NOP();
    }
  }
}
/* ============================================================================
 * 写法二：标准外设库（Standard Peripheral Library）
 * 工程依赖：STM32F10x_StdPeriph_Driver + stm32f10x.h
 * 说明：这是 F1 时代的老写法，现在只用于维护旧工程和看懂老教程
 * 编译产物大小：约 3~6 KB
 * ============================================================================ */

#include "stm32f10x.h"

/* 老式的软件延时，SPL 工程里很常见 */
void Delay(__IO uint32_t nCount)
{
  for (; nCount != 0; nCount--)
  {
  }
}

int main(void)
{
  GPIO_InitTypeDef GPIO_InitStructure;      /* 注意：类型名是 GPIO_InitTypeDef */

  /* 1. 开时钟：SPL 用 RCC_APB2PeriphClockCmd() */
  RCC_APB2PeriphClockCmd(RCC_APB2Periph_GPIOC, ENABLE);

  /* 2. 填结构体。SPL 的成员只有三个：Pin / Speed / Mode */
  GPIO_InitStructure.GPIO_Pin   = GPIO_Pin_13;        /* 引脚掩码，展开是 0x2000 */
  GPIO_InitStructure.GPIO_Speed = GPIO_Speed_50MHz;   /* 输出速度 */
  GPIO_InitStructure.GPIO_Mode  = GPIO_Mode_Out_PP;   /* 推挽输出 */

  /* 3. 提交配置：这一步才真正写 CRH 寄存器 */
  GPIO_Init(GPIOC, &GPIO_InitStructure);

  /* 4. 主循环。SPL 提供了 SetBits / ResetBits 两个动作函数 */
  while (1)
  {
    GPIO_ResetBits(GPIOC, GPIO_Pin_13);   /* 拉低，灯亮 */
    Delay(800000);

    GPIO_SetBits(GPIOC, GPIO_Pin_13);     /* 拉高，灯灭 */
    Delay(800000);
  }
}
/* ============================================================================
 * 写法三：HAL 库
 * 工程依赖：STM32F1xx_HAL_Driver + stm32f1xx_hal.h
 * 编译产物大小：约 10~20 KB
 * 下面的 USER CODE 标记就是 CubeMX 的保护区，写在这里的内容重新生成时不会被覆盖
 * ============================================================================ */

#include "main.h"

UART_HandleTypeDef huart1;        /* CubeMX 自动生成的全局句柄（本例子没用到串口） */

void SystemClock_Config(void);
static void MX_GPIO_Init(void);

int main(void)
{
  /* ---- 第 1 步：初始化 HAL 库本身 ----
     它做三件事：设置中断优先级分组、使能 Flash 预取、把 SysTick 配成 1ms。
     少了这一句，HAL_Delay() 会失效。 */
  HAL_Init();

  /* ---- 第 2 步：把时钟配到 72MHz ---- */
  SystemClock_Config();

  /* ---- 第 3 步：初始化外设（这个函数里面就包含了开 GPIO 时钟） ---- */
  MX_GPIO_Init();

  /* USER CODE BEGIN 2 */
  /* 你自己的额外初始化写在这两块标记之间 */
  /* USER CODE END 2 */

  /* ---- 第 4 步：主循环 ---- */
  while (1)
  {
    /* USER CODE BEGIN 3 */
    HAL_GPIO_TogglePin(GPIOC, GPIO_PIN_13);   /* 翻转 PC13 */
    HAL_Delay(500);                            /* 等 500ms，靠 SysTick 实现 */
    /* USER CODE END 3 */
  }
}

 * CubeMX 生成的 GPIO 初始化函数（节选，里面的每一行都值得看）

{
  GPIO_InitTypeDef GPIO_InitStruct = {0};     /* ★ 必须清零，见下文报错排查 */

  /* 配置 PC13 */
  GPIO_InitStruct.Pin   = GPIO_PIN_13;            /* 引脚掩码 0x2000 */
  GPIO_InitStruct.Mode  = GPIO_MODE_OUTPUT_PP;    /* 推挽输出 */
  GPIO_InitStruct.Pull  = GPIO_NOPULL;            /* 不用内部上下拉 */
  GPIO_InitStruct.Speed = GPIO_SPEED_FREQ_LOW;    /* 低速即可（只是点灯） */

带回调的串口接收（HAL 的中断模式）

下面这段代码演示完整的「中断 + 回调」流程：收到一个字节就把它原样发回去（回显），并把收到的字符累加到一个计数里。请重点看 HAL_UART_Receive_IT() 被调用了两次——一次在初始化时，一次在回调函数里。这个「重新武装」的动作是新手最容易漏掉的。

/* ============================================================================
 * 中断方式串口回显 —— 演示 HAL 的回调机制
 * 硬件：USART1，PA9 = TX，PA10 = RX，波特率 115200
 * 现象：串口助手发什么字符，就收到什么字符
 * ============================================================================ */

#include "main.h"
#include <string.h>

UART_HandleTypeDef huart1;

/* ★ 接收缓冲区：必须是全局变量（或 static）！
   如果它是局部变量，函数一返回这块内存就失效了，
   而中断随时可能来写它 —— 这就是「句柄/缓冲区定义成局部变量」翻车的原理。 */
static uint8_t  rx_byte;                  /* 只存 1 个字节，够演示了 */
static uint32_t rx_count = 0;             /* 一共收到多少个字节 */

void SystemClock_Config(void);

/* ============================================================================
 * 回调函数：名字、返回类型、参数都必须与 HAL 头文件里的声明完全一致
 * ============================================================================ */
void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
{
  /* 第一步永远是判断「是哪个串口」——
     因为一个工程里可能有 huart1、huart2 都用同一个回调。 */
  if (huart->Instance == USART1)
  {
    rx_count++;

    /* 回显：把刚收到的这个字节发回去。
       用 HAL_MAX_DELAY 表示「一直等到发完」。
       注意：这里是在中断上下文里，HAL_UART_Transmit 是阻塞式的，
       发一个字节大约几十微秒，对这个演示够用；
       如果要发大量数据，应该用 HAL_UART_Transmit_IT 或 DMA。 */
    HAL_UART_Transmit(&huart1, &rx_byte, 1, HAL_MAX_DELAY);

    /* ★★ 最关键的一行：重新启动接收。
       HAL_UART_Receive_IT() 是「收满指定个数就停」的语义。
       上面这句配置的是收 1 个字节，收满后 HAL 会自动关闭 RXNE 中断，
       如果不在回调里重新调用一次，你就只能收到第一个字节 ——
       这是「串口只收到一个字符然后就没反应了」的标准原因。 */
    HAL_UART_Receive_IT(&huart1, &rx_byte, 1);
  }
}

/* ============================================================================
 * main
 * ============================================================================ */
int main(void)
{
  HAL_Init();
  SystemClock_Config();
  MX_GPIO_Init();
  MX_USART1_UART_Init();            /* CubeMX 生成的串口初始化（内部会调 MspInit） */

  /* USER CODE BEGIN 2 */
  /* 打印一句开机信息，确认串口通了 */
  const char *hello = "STM32 UART echo ready.\r\n";
  HAL_UART_Transmit(&huart1, (uint8_t *)hello, strlen(hello), 100);

  /* ★ 第一次「武装」接收：把缓冲区地址和长度告诉 HAL，
       并打开 RXNE 中断。从这一刻起，每收到 1 个字节就会进回调。 */
  HAL_UART_Receive_IT(&huart1, &rx_byte, 1);
  /* USER CODE END 2 */

  while (1)
  {
    /* USER CODE BEGIN 3 */
    /* 主循环里什么都不用做！接收完全由中断+回调处理。
       这就是中断相比「while 里不停查询有没有数据」的最大优势：
       主循环被彻底解放出来，可以去做别的事。 */
    /* USER CODE END 3 */
  }
}

/* ============================================================================
 * 【完整调用链回顾】上位机发一个字符 'A'，程序里依次发生：
 *
 *  1. USART1 硬件接收完成，SR 寄存器的 RXNE 位置 1
 *  2. NVIC 根据向量表跳到 USART1_IRQHandler（在 stm32f1xx_it.c 里）
 *  3. USART1_IRQHandler 调用 HAL_UART_IRQHandler(&huart1)
 *  4. HAL 读出 DR 里的 'A'，存进 rx_byte，RxXferCount 从 1 减到 0
 *  5. HAL 关闭 RXNE 中断，把 RxState 改回 READY
 *  6. HAL 调用 HAL_UART_RxCpltCallback(&huart1)
 *  7. 你的回调执行：rx_count 加一，把 'A' 发回去，再次调用 Receive_IT
 *  8. 中断返回，CPU 回到主循环里原来被打断的位置
 * ============================================================================ */
为什么 HAL_UART_Transmit 在中断里能用，HAL_Delay 却不能用

两个都是阻塞函数，但阻塞的对象不同。HAL_UART_Transmit 等的是外设寄存器的标志位（TXE / TC），这个标志由串口硬件自己置位，不依赖中断，所以在中断里等它没问题（只是会占用一点中断时间）。而 HAL_Delay 等的是 uwTick 的增长，而 uwTick 靠 SysTick 中断来加。SysTick 的优先级如果和当前中断相同或更低，它就无法打断当前中断，uwTick 永远不变，HAL_Delay 就会一直卡在中断里 —— 表现为「一进中断就死机」或「看门狗复位」。结论：中断里绝对不要用 HAL_Delay。

这一节的「现象」是一张速查表。HAL 的函数名大部分是可以猜的——它们遵循「HAL_外设_动作()」这个构词规律。记住规律，比死记硬背几百个函数名高效得多。

HAL 命名规律：看名字猜功能

函数名的结构是 HAL_ + 外设 + _ + 动作。动作部分的规律：带 _IT 后缀的是中断方式（Interrupt，不阻塞）；带 _DMA 后缀的是 DMA 方式；带 _Callback 后缀的是给你覆盖的回调；带 MspInit / MspDeInit 的是管引脚和时钟的那一半。返回值统一是 HAL_StatusTypeDef，取值有 HAL_OK、HAL_ERROR、HAL_BUSY、HAL_TIMEOUT 四种。看到函数返回 HAL_BUSY 就说明「这个外设正忙」，通常是上一次操作还没完成。

常见报错排查方案

这一节的问题分成两类：一类是「代码被覆盖」这种工程习惯问题，另一类是「函数写了却不执行」这种静默失败。后者的共同点是编译器不会帮你——它检查不出「你要覆盖 weak 函数但名字打错了」。

在 CubeMX 生成的代码里加的东西，重新生成后全没了

原因：代码写在了 USER CODE BEGIN/END 标记之外。CubeMX 重新生成时，只保留标记之间的内容，标记之外的文件内容会按当前配置整块重写，而且不会提示你「有内容被覆盖」。

解决：① 立刻停下别继续写，先养成习惯：凡是自己写的代码，一律放进 USER CODE 区域；② 如果已经丢了，去 Keil 的 Output 目录或版本控制里找备份；③ 从下一个工程开始用 Git——CubeMX 工程的 Core/、Drivers/ 目录每次生成都可能变，有版本控制才能 diff 出「这次生成了什么」。

回调函数写了，但从来不被执行（没有编译错误）

原因：三种可能，都指向「你的函数没有被链接器当成覆盖者」：① 函数名拼错——HAL_UART_RxCompleteCallback、HAL_UART_RxCpltCallBack（大写 B）、HAL_UART_RxCallback，这些都是常见错法，链接器看到的是两个不同的符号，库里的 __weak 空实现仍然生效；② 参数类型不匹配——你写成 void HAL_UART_RxCpltCallback(uint8_t ch)，C 语言不支持函数重载，于是你定义了一个谁也没引用的新函数；③ 加了 static——作用域被限制在本文件，链接器根本看不到，无法参与符号覆盖。

解决：从 stm32f1xx_hal_uart.h 里复制函数声明，粘贴到你的 .c 文件里再去掉末尾的分号，然后补上函数体。不要手打。另外确认函数不是 static。

程序卡在 HAL_Delay 里出不来 / 一上电就死机

原因：忘了调用 HAL_Init()。HAL_Delay() 依赖全局变量 uwTick，而 uwTick 由 SysTick 中断每秒加 1000。SysTick 是在 HAL_Init() → HAL_InitTick() 里配置的，没调它，SysTick 中断永远不来，uwTick 永远是 0，延时循环就永远等不到头。第二种情况：你把 HAL_Delay() 写进了某个中断服务函数里，SysTick 优先级不够高，打断不了当前中断，同样是死等。

解决：① 确认 main() 的第一行就是 HAL_Init();；② 检查中断优先级分组和 SysTick 的优先级（默认在 HAL_Init() 里设为最低优先级组）；③ 中断里绝对不要用 HAL_Delay，需要计时就用 HAL_GetTick() 做非阻塞判断，或者干脆置个标志位回主循环再延时。

串口用着用着突然没反应了（或者只收到第一个字符）

原因：HAL_UART_Receive_IT(&huart1, buf, n) 的语义是「收满 n 个字节就停」。收满之后 HAL 会自动关闭 RXNE 中断并把状态改回 READY，它不会自动开始下一轮。所以如果你在回调里没有再次调用 Receive_IT，就只能收到第一轮的数据。同理，如果 n 填得比实际会收到的字节数大，你会一直等不齐，回调永远不触发（看起来像「完全收不到」）。

解决：在 HAL_UART_RxCpltCallback() 的末尾重新调用一次 HAL_UART_Receive_IT()「重新武装」。要接收不定长数据，有三种正规做法：① 每次都只收 1 个字节，在回调里自己攒成帧；② 用空闲中断（IDLE）配合 DMA，一帧结束时触发；③ 用较新版本 HAL 的 HAL_UARTEx_ReceiveToIdle_IT()。注意不要在回调里用 printf 或大量阻塞操作，拖长中断时间会导致后面的字节丢失（ORE 溢出错误）。

句柄或缓冲区定义成了局部变量，程序行为随机错乱

原因：HAL 的工作方式是「你把地址给它，它记下来，以后在中断里往那块内存写」。如果你的句柄或接收缓冲区是函数内的局部变量，函数一返回，那块栈内存就被回收给别的函数用了，而中断随时可能按老地址往里写——于是你的数据被莫名其妙地改掉，或者你读到的东西像是「别人的变量」。这类 bug 的典型特征是时好时坏、加一行打印就正常、改优化等级就变样。

解决：凡是会被中断或 DMA 访问的变量，一律定义成全局变量或加 static，并且视情况加 volatile。UART_HandleTypeDef huart1; 这种句柄，CubeMX 生成时就放在 main.c 的文件开头，是全局的——不要自作聪明把它挪进函数里。

HAL 结构体没清零，配置出来的引脚行为古怪

原因：GPIO_InitTypeDef GPIO_InitStruct; 这样声明是没有初始化的——它是局部变量，在栈上，值是上一次别人用剩下的垃圾。如果你只赋了 Pin 和 Mode，忘了赋 Pull，那个字段就是随机值，可能恰好是「上拉」「下拉」或某个非法编码。HAL_GPIO_Init() 会把结构体里每个字段都读一遍并据此写寄存器，于是引脚行为就不可预测了。

解决：声明时一律写 GPIO_InitTypeDef GPIO_InitStruct = {0};——= {0} 会把所有成员清零，这是 C 语言里最省事也最可靠的初始化写法。HAL 的所有 Init 结构体都建议这么写，CubeMX 生成的代码本身也是这么做的，你手写时不要偷懒。

HAL_xxx_Init() 调用成功（返回 HAL_OK），但外设完全不工作

原因：MSP 那一半没做。HAL_UART_Init() 只负责配波特率、数据位这些「芯片内部」的参数，引脚模式、外设时钟、NVIC 使能全靠 HAL_UART_MspInit()，而它在 HAL 库里是 __weak 的空实现。如果你是从别人的工程里拷的 main.c，但没拷 stm32f1xx_hal_msp.c（或者你在 CubeMX 里没勾选对应引脚），那么 Init 一切正常、返回 HAL_OK、寄存器看着也对，就是引脚上没有任何信号。

解决：打开 stm32f1xx_hal_msp.c，找到对应外设的 HAL_xxx_MspInit()，确认里面有：① __HAL_RCC_xxx_CLK_ENABLE()；② 正确的引脚配置（注意串口 TX 要用 GPIO_MODE_AF_PP 复用推挽，配成普通输出是不通的）；③ 如果要用中断，是否有 HAL_NVIC_EnableIRQ()。最省事的做法是回 CubeMX 里把引脚重新点一遍再生成。

另一类：编译报错 "Undefined symbol HAL_UART_RxCpltCallback"

这和上面的「静默不执行」正好相反——是链接期找不到符号。原因是你在 main.c 里调用了这个函数（比如把它当普通函数传给别的函数），但 HAL 库里根本没有这个函数的定义（只有声明），而你自己也没写。这不是配置问题，是使用方式错了：回调函数是「等别人来调你」，不是「你去调它」。你在代码里唯一该出现它的地方，就是它自己的定义处。删掉那个调用即可。

小结与练习

这一篇的核心不是「学会 HAL 的函数」，而是建立一层心理模型：不管上面盖了多少层封装，最底下永远是那几个寄存器。把模型建起来，HAL 就从「黑盒」变成「我知道它在干什么的盒子」。

  • 三种写法操作同一组寄存器：HAL_GPIO_WritePin → GPIOx->BSRR / BRR；HAL_GPIO_Init → GPIOx->CRL / CRH。
  • 句柄 = 外设的身份证 + 状态记录本。Instance 说「我是谁」，Init 说「我怎么工作」，其余字段说「我现在忙不忙、还剩多少没发完」。
  • 回调 = 你把函数地址交给库，库在合适时机调你。库里的 __weak 空实现保证了「你不写也能编译过」，你写同名强符号就能覆盖它。
  • 初始化拆两半：HAL_xxx_Init() 管芯片内部寄存器，HAL_xxx_MspInit() 管引脚、时钟、NVIC、DMA——后者因板子而异，所以交给你。
  • 只写 USER CODE 区域。这是用 CubeMX 的唯一纪律。
自检题（先自己答，再对下面的判据）
  1. HAL_UART_Transmit(&huart1, ...) 里的 & 能不能去掉？

    判据：不能。函数原型收的是 UART_HandleTypeDef *（指针），去掉 & 传的是结构体本身，类型不匹配会编译报错。之所以传指针，一是避免把整个结构体复制一份（里面还有缓冲区指针、计数器等十几个成员），二是让 HAL 能就地修改句柄里的状态（比如把 gState 改成 BUSY）。

  2. 为什么你写的中断回调函数不需要在别处「注册」？

    判据：因为它靠的是链接期的符号覆盖，不是运行期的注册。HAL 库里已经写好了「调用 HAL_UART_RxCpltCallback(huart)」这句代码，只是那个函数体是空的（__weak）。你定义同名强符号后，链接器就把调用目标指向你的函数。

  3. 同样的 USART1 代码，A 板子能用 B 板子不能用，最可能的原因是什么？

    判据：MSP 层的差异——引脚接法不同（比如 B 板子做了引脚重映射到 PB6/PB7），或者外部上下拉电路不同。业务代码（main.c）是一样的，跟板子有关的都在 stm32f1xx_hal_msp.c 和 CubeMX 的引脚配置里。

  4. 为什么 HAL_GPIO_TogglePin() 内部要先读 ODR 再写 BSRR？

    判据：要知道「当前是什么状态」才能翻转，所以必须先读。但它不是简单地「读出来取反再写回 ODR」（那样有中断打断的风险），而是把「该置位的位」和「该复位的位」一次性写进 BSRR，用一次只写操作完成，避免了读改写的竞态。

  5. 「句柄定义了但没清零」和「结构体没加 = {0}」，哪个更危险？为什么？

    判据：句柄不清零更危险。因为 HAL 会持续读写句柄里的状态字段（gState、Lock、各种计数器），一个随机的初始状态可能让 HAL 认为「外设正忙」而直接返回 HAL_BUSY，或者让计数器从垃圾值开始倒计。而配置结构体只要每个字段你都显式赋值了，清不清零影响不大——问题在于人总会漏赋某个字段。

动手练习
  1. 三份代码都跑一遍：新建三个工程（或用同一个工程的三种 main.c），分别用寄存器、标准库、HAL 实现 PC13 闪烁。编译后对比 Keil 输出的 Program Size: Code=... RO-data=... RW-data=... ZI-data=... 那一行，记下三个 Code 值。
  2. 在调试器里看代码「展开」：用 HAL 版本，在 HAL_GPIO_WritePin(GPIOC, GPIO_PIN_13, GPIO_PIN_RESET); 这行打断点，单步步入（Step Into），一路看到 GPIOC->BRR = GPIO_PIN_13; 那一行。亲眼看到 HAL 最后落到的寄存器，这一篇就算真的学懂了。
  3. 故意制造「回调不执行」：把 HAL_UART_RxCpltCallback 改成 HAL_UART_RxCpltCallBack（大写 B），重新编译下载。观察现象：编译零错误零警告，串口回显完全没有了。然后再改回来。这个实验能让你以后一眼认出这类 bug。
