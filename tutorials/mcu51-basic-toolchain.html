原理介绍

前面两篇解决了两个问题：C 语言怎么写、 寄存器是什么。 但还有一个环节一直悬在半空：你屏幕上的 .c 文件， 是怎么跑到芯片的 Flash 里去的？

这个环节之所以值得单独讲一课，是因为它藏着很多"莫名其妙"的现象：

  • 编译明明显示 0 Error(s)，可 STC-ISP 里就是找不到 .hex 文件——因为它根本没被生成。
  • 同一个 Delay_ms(500)，昨天的流水灯速度正好， 今天换了台电脑、改了编译选项，快得只剩一道光——因为编译器把你的延时循环优化掉了。
  • 点了「下载」之后软件一直停在"正在检测单片机…"，直到你把电源拔了又插上才通—— 因为 STC 的下载必须在冷启动的那一刻才握手。
  • 用记事本打开 .hex，看到的是一堆 :100003007B00EB… 这样的"乱码"—— 其实那是格式极其规整的文本，每一段都有确定的含义。

这一页的目标就是让上面四件事全部变得理所当然。 读完你应该能：看懂 Keil 的 Build Output 每一行在说什么、 打开 Listings 目录读汇编清单、自己手算一节 HEX 的校验和、 并且知道按「下载」之后如果不冷启动，芯片内部在等什么。

阅读前提

本文默认你已经知道「寄存器」「SFR」「机器周期」「复位后 IO 是高电平」这些概念 （都在 上一篇 里）。 本文会出现一些机器码，比如 75 90 FE， 它们是"给人看的证据"，不是要你背下来的东西—— 真正要记住的是它们从哪来、怎么被放到芯片里。

四个阶段总览：从一行 C 到一节 HEX

先记住一句话：从 C 源码到能烧进芯片的文件， 中间要过四道工序，每一道都有明确的输入、输出和工具。 这四道工序不是 51 单片机特有的，任何 C 语言程序都要走，只是工具名字不同。

打个比方：假设你要把一篇中文稿变成一本能直接卖给外国读者的英文书。

现实里的工序 干的事 对应的编译阶段
把缩写、引用、脚注全部展开成完整句子 让正文里没有"待解释"的东西 预处理
中文翻译成英文 换一种语言表达同样的意思 编译（C → 汇编）
排版成印刷用的版面文件 变成印刷机能直接用的形式 汇编（汇编 → 机器码）
把各章装订成一本书、加上目录页 确定每一章在第几页 链接（定地址、拼成完整程序）

"确定每一章在第几页"这一条特别重要： 预处理、编译、汇编这三步都是按文件单独进行的， 编译器在编译 main.c 的时候并不知道 delay.c 里的函数最终会被放在哪个地址， 所以它只留下一个"待填"的记号。 真正决定"谁放在 0x0000、谁放在 0x0030"的，是最后一步的链接器。

更细一点，四个阶段的输入、输出、工具和"出问题时的典型表现"如下表：

阶段 输入 输出 Keil 里的工具 职责一句话

② 编译 展开后的 C .src（汇编） C51 编译器 C 语言换成 51 汇编
③ 汇编 .src（汇编） .obj（目标文件） A51 汇编器 汇编换成机器码，地址先留空

在 µVision 里，这四步是连着自动跑的， Build（F7）就等于"预处理 + 编译 + 汇编 + 链接"这四件事一次做完。 它跑完以后，窗口底部的 Build Output 会留下这样一段文字—— 现在你应该能逐行读懂它了： 

Build target 'Target 1'
compiling main.c...            <- ② ③：main.c 过了预处理，编译成汇编，又汇编成 main.obj
compiling delay.c...           <- ② ③：delay.c 同样走一遍（每个 .c 各走一遍）
linking...                     <- ④ 链接：把 main.obj + delay.obj + STARTUP.A51 + 库拼起来
Program Size: data=12.0 xdata=0 code=186
                               <- ④ 链接结果：占了多少 RAM（data）、多少 xdata、多少 Flash（code）
creating hex file from "Project"...
                               <- ④ 链接成功后，按你的设置额外导出 Project.hex
"Project" - 0 Error(s), 0 Warning(s).
                               <- 全部成功。注意：这一行不代表 hex 一定生成了（见错误①）

这里有一个新手极容易踩的坑，值得提前点出来： Program Size 里的 code=186 表示这段程序占了 186 字节的 Flash， 不是 186 KB，也不是 186 行。STC89C52RC 有 8 KB Flash， 相当于大约 8192 字节——所以 186 字节连零头都不到。 当你哪天编译出 code=8100 这样的数字，就要开始想办法瘦身了。

为什么记住"阶段"比记住"按钮"重要

报错信息里藏着阶段的名字：error C… 是 Compiler（编译）， error A… 是 Assembler， error L… 是 Linker（链接）。 看到 L 开头的编号，就知道问题不在语法， 而在"东西凑不齐"——比如某个函数只有声明没有定义。 这一条经验能省下大量瞎改代码的时间。

预处理器做了什么：贴入、替换、筛选

预处理器是四道工序里最"笨"的一道，它完全不懂 C 语言—— 不认识 int、不认识分号、不做语法检查。 它只认得以 # 开头的行，并且忠实地做三件事： 贴入、替换、筛选。

正因为"笨"，它的行为才特别好预测。下面三组例子， 每一组都给出"你写的"和"编译器实际看到的"，对照着看就能彻底明白。

第一件事：#include 就是把文件内容原样贴进来

你写的是这样（两行）： 

#include <reg52.h>

void main(void) { P1 = 0xFE; }

预处理器做的事，相当于把 reg52.h 这个文件 整个复制过来，粘在 #include 那一行的位置， 然后删掉 #include 这一行本身。它不检查里面写了什么， 也不管贴进来之后有没有重复。于是编译器真正看到的是： 

/* ↓↓↓ 以下是 reg52.h 被原样贴进来的内容 ↓↓↓ */
sfr P0  = 0x80;
sfr P1  = 0x90;
sfr P2  = 0xA0;
sfr P3  = 0xB0;
sfr TMOD = 0x89;
sbit EA = 0xAF;
/* …中间还有几十行，这里省略… */
/* ↑↑↑ reg52.h 的内容到此结束 ↑↑↑ */

void main(void) { P1 = 0xFE; }

现在回头看上一篇里的那句话就完全成立了： 「#include <reg52.h> 就是替你把 21 个 sfr 声明全写了一遍」。 它不是什么"引用一个模块"，就是最朴素的文本粘贴。

写法 去哪里找这个文件 什么时候用
#include <reg52.h> 只在编译器的系统包含目录里找（Keil 装在 C51\INC 下） 用编译器自带的头文件
#include "delay.h" 先在当前 .c 文件所在目录找，找不到再去系统目录 用自己写的头文件

第二件事：#define 是纯文本替换

#define 也不是"定义常量"，它只是给一段文字起了个名字。 编译器看到的永远是替换之后的文字。 

/* ---------- 展开前：你写的 ---------- */
#define CRYSTAL   11059200UL
#define DELAY_MS(x)  ((x) * 1000)

unsigned long f = CRYSTAL;
unsigned int  t = DELAY_MS(5);

/* ---------- 展开后：编译器看到的 ---------- */
unsigned long f = 11059200UL;
unsigned int  t = ((5) * 1000);

/* 注意：宏名字在展开后就彻底消失了，
   所以 Keil 的变量窗口里永远找不到 CRYSTAL 这个名字。 */

带参数的宏，参数一定要加括号，否则会得到一个 "看起来没错、算出来是错的"结果。这是宏最经典的坑： 

#define SQUARE_BAD(x)   x * x
#define SQUARE_OK(x)    ((x) * (x))

int a = SQUARE_BAD(1 + 2);   /* 展开成 1 + 2 * 1 + 2  = 1 + 2 + 2 = 5  ← 错！ */
int b = SQUARE_OK(1 + 2);    /* 展开成 ((1 + 2) * (1 + 2))       = 9  ← 对 */

还有一条几乎人人都踩过的坑：宏定义的行末不要加分号。 因为分号也是你写的文字，会被一起替换进去： 

#define MAX 100;              /* ← 行末这个分号是灾难 */

if (a < MAX)                  /* 展开后：if (a < 100;)      ← 语法错误 */
{
    a = 0;
}

/* 报错大致是：error C141: syntax error near ')' 之类
   （编译器被那个多出来的分号弄糊涂了） */

正确的写法是不加分号，让使用者自己决定在哪里结束语句： #define MAX 100。 这样 if (a < MAX) 展开成 if (a < 100)，完美。

第三件事：条件编译——决定留哪一段

#ifdef 的作用是"这段代码要不要"。 它最常见的两个用途：同一份代码适配不同板子、 防止头文件被重复贴入。 

/* ---------- 展开前 ---------- */
#define BOARD_A          /* 想给 B 板编译时，把这一行注释掉即可 */

#ifdef BOARD_A
    #define LED_PORT   P1
    #define LED_ACTIVE 0     /* A 板：低电平点亮 */
#else
    #define LED_PORT   P2
    #define LED_ACTIVE 1     /* B 板：高电平点亮 */
#endif

void LedOn(void) { LED_PORT &= 0xFE; }

/* ---------- 展开后（定义了 BOARD_A 的情况） ---------- */
void LedOn(void) { P1 &= 0xFE; }
/* 另一份代码整段消失了，连编译都不会编译它——
   这和 if 语句的区别是：if 是运行时判断，两段代码都会进 Flash；
   #ifdef 是编译前筛选，没被选中的那段根本不占 Flash。 */
/* ---------- delay.h ---------- */
#ifndef __DELAY_H__          /* 如果 __DELAY_H__ 还没被定义过 */
#define __DELAY_H__          /* 那就定义它，并往下走 */

void Delay_ms(unsigned int ms);

#endif                       /* 到底了 */

/* ---------- 作用 ----------
   如果 main.c 里既 #include "delay.h"，又 #include 了另一个
   也包含 delay.h 的头文件，那么第二次贴入时 __DELAY_H__ 已经定义过了，
   整个文件内容会被跳过，函数声明不会重复出现。 */
预处理指令 做什么 最容易踩的坑
#include 把文件内容原样贴到这个位置 头文件里放变量定义，被两个 .c 包含 → 链接期报重复定义
#define 名字 值 把名字替换成值（纯文本） 行末多写分号；带参宏的参数不加括号
#ifdef / #ifndef / #else / #endif 按条件保留或丢弃一整段代码 忘了写 #endif
#undef 取消一个宏定义 取消之后再用这个名字，就变成未定义标识符了

宏不是变量，也不是函数

三条结论，记住能少走很多弯路：
1. 不占内存。宏是编译前就被替换掉的文字，不会在 RAM 里占一个字节， 也不会出现在 Flash 里。这和 const、code 变量不同。
2. 不检查类型。DELAY_MS("abc") 也会被替换， 报错要等到编译器处理展开后的代码时才发现，错误信息指向的位置常常"看起来没错"。
3. 不能调试。单步调试时你看到的是展开后的值，宏名不存在了。 这也是为什么复杂逻辑要用函数而不是宏。

编译与优化等级：为什么你的延时突然不准了

编译这一步的核心任务是：把 C 语言翻译成 51 汇编， 再变成机器码。翻译的结果可以在 Keil 的 Listings 目录里直接看到—— 每一行 C 下面都列着它对应的汇编。

先建立"一句 C 到底对应几个字节"的直觉。下表是几个极常用的语句在 STC89C52RC（12T 模式）上的真实翻译结果：

C 语言 编译出来的汇编 机器码（十六进制） 占几个字节 几个机器周期
P1 = 0xFE; MOV P1,#0FEH 75 90 FE 3 2
P1 &= 0xFE; ANL P1,#0FEH 53 90 FE 3 2
LED = 0;（sbit） CLR P1.0 C2 90 2 1
x = P1; MOV A,P1 E5 90 2 1
while (1); SJMP $ 80 FE 2 2

这张表有两个用法。第一，它能解释"为什么 LED = 0; 比 P1 &= 0xFE; 更值得写"—— 前者 2 字节 1 周期，后者 3 字节 2 周期，而且后者会整字节重写 8 个锁存器（上一篇讲过）。 第二，它能帮你在反汇编窗口里认代码：看到 75 90 就知道是有人在写 P1。

在 Keil 里有两个地方能看到这些翻译：

想看什么 去哪里看 能回答的问题
C 与汇编的逐行对照 + 每行占的字节数 Listings/Project.lst（编译后自动生成） "这一行 C 到底编译成了什么？"

优化：编译器会"自作主张"改你的代码

编译器不只是逐句翻译，它还会优化： 在不改变程序"可观察行为"的前提下，把代码改得更小、更快。 大部分时候这是好事，但有一类代码会被它改得面目全非—— 靠空循环耗时间的软件延时。

新手最常写的延时函数长这样： 

void Delay_ms(unsigned int ms)
{
    unsigned int i, j;

    for (i = 0; i < ms; i++)
    {
        for (j = 0; j < 120; j++)   /* 内层空转，什么也不做 */
        {
            ;                        /* 这一行是空的 */
        }
    }
}

它的意图是"让 CPU 傻转 120 次算 1 毫秒"。可是在编译器眼里， 内层循环什么可观察的事情都没做： 变量 j 是局部的，循环结束后它的值没人用； 循环体里没有写寄存器、没有读写内存。 于是编译器有充分的理由认为："这个循环删掉，程序的行为没有区别。"

优化等级越高，它越倾向于这样处理。结果是：

优化等级 编译器大致会做什么 现象 适合什么时候用
0 级（不优化） 逐句翻译，变量都老老实实放在 RAM 里 延时基本准；代码最大；单步最"所见即所得" 调试、逐行观察变量
中间等级 合并常量、去掉无用赋值、循环展开一部分 延时会偏短，偏差不大 日常开发
最高等级（最省空间/最快） 删除"无副作用"的空循环、把循环变量放进寄存器、合并重复代码 延时可能快好几倍，流水灯变成一片糊影 发布、Flash 快满的时候

Keil C51 的优化等级在 Options for Target → C51 页里选， 用数字表示（不同版本界面写法略有差异，有的写 Level 0~9； 你在别的编译器上看到的 -O0、-O1、-O2 是同一件事的另一种写法，数字越大优化越激进）。

要让延时函数在优化面前站得住，有三种办法，从"能用"到"推荐"排列：

办法一：把循环变量声明成 volatile。 volatile 的含义是"这个变量的值可能在任何时刻被外部改变， 编译器不许假设它没变，也不许删掉对它的读写"。加上它，循环就"有副作用"了， 编译器不敢动： 

void Delay_ms(unsigned int ms)
{
    volatile unsigned int i, j;   /* volatile：禁止把它们优化掉 */

    for (i = 0; i < ms; i++)
    {
        for (j = 0; j < 120; j++)
        {
            ;
        }
    }
}

办法二：插入真正的空指令 _nop_()。 Keil 的 intrinsics.h 提供了一个"内建函数"， 它编译成一条 NOP 指令（机器码 00，1 个机器周期）。 因为 NOP 是真实的机器指令， 编译器不能删除它——删掉一条指令是"改变程序行为"。 做微秒级、几十微秒级的短延时时，它比空循环可靠得多： 

#include <intrinsics.h>

void Delay_10us(void)      /* 12MHz 晶振下大约 10 微秒 */
{
    unsigned char k;

    for (k = 0; k < 8; k++)
    {
        _nop_();           /* 一条 NOP，1 个机器周期 = 1 微秒 */
        _nop_();
    }
}

办法三（推荐）：用定时器。 定时器由硬件计数，和编译器的脾气完全无关，也不会浪费 CPU。 精确到毫秒以上的延时、需要长期稳定的节拍，都应该交给定时器 （见 定时器与计数器 那一篇）。 软件延时的唯一优势是"简单、不用配寄存器"，适合点亮 LED、做按键消抖这类 对精度要求不高的场合。

三条与优化有关的纪律

1. 调试和发布尽量用同一个优化等级。 调试时用 0 级、发布时开到最高，那些"只在发布版本里出现"的 诡异现象就是这么来的。
2. 单步时发现变量"不存在"或值不对，先怀疑优化。 被优化掉的局部变量在 Keil 的 Watch 窗口里会显示成 not in scope 或干脆消失，这不是你的代码写错了。
3. 凡是"靠耗时间"起作用的代码，都要有强制手段。 volatile、_nop_()、定时器， 三样至少用一样，否则换台电脑、换个版本，现象就可能完全不一样。

链接与启动代码：谁决定了程序放在哪

编译和汇编都是"一个文件一个人干活"：main.c 编成 main.obj，delay.c 编成 delay.obj。 这两个 .obj 各自都是"半成品"—— 里面的机器码已经生成好了，但所有"跳转到别的文件里的函数"、 "访问别的文件里的变量"的位置都还是空的。

链接器（Linker）就是把半成品拼成成品的那道工序，它做三件事：

  1. 合并：把所有 .obj、 启动代码 STARTUP.A51、以及用到的库函数，按段（代码段、数据段）归到一起。
  2. 分配地址：决定每个函数、每个变量最终落在哪个地址。 这就是为什么 main 有可能在 0x0003，也可能在 0x0030—— 取决于链接器怎么摆。
  3. 填空：把第一步里那些"待填"的位置换成真实地址， 最后按输出格式写出目标文件和 HEX 文件。

一个多文件工程长这样——注意头文件里只有声明，没有定义， 这是链接能成功的关键： 

/* ---------- delay.h：只告诉别人"有这么个函数" ---------- */
#ifndef __DELAY_H__
#define __DELAY_H__
void Delay_ms(unsigned int ms);      /* 这是【声明】：有名字、有参数、有返回值，没有函数体 */
#endif

/* ---------- delay.c：真正干活的实现 ---------- */
#include "delay.h"
void Delay_ms(unsigned int ms)       /* 这是【定义】：带函数体，会生成机器码 */
{
    unsigned int i, j;
    for (i = 0; i < ms; i++)
        for (j = 0; j < 120; j++);
}

/* ---------- main.c：只管调用 ---------- */
#include <reg52.h>
#include "delay.h"                   /* 让编译器知道 Delay_ms 的参数格式 */
void main(void)
{
    while (1)
    {
        P1 = 0xFE;
        Delay_ms(500);
        P1 = 0xFF;
        Delay_ms(500);
    }
}
声明（declaration） 定义（definition）
长什么样 void Delay_ms(unsigned int ms);（末尾分号） void Delay_ms(unsigned int ms) { … }（有花括号）
会不会生成机器码 不会，一行都不占 Flash 会，函数体全部编成指令
写在哪里 头文件里，谁用谁包含 某个 .c 里，全工程只能有一份
少了它会怎样 编译报 warning C206: missing function-prototype（还能过） 链接报"找不到符号"（过不去）

STARTUP.A51：芯片上电后跑的第一段代码

你的程序里没有 STARTUP.A51 这个文件，但它一定参与了链接—— 链接器会自动把它接进来（或者用你手动加进工程的那一份）。 它是复位之后最先执行的代码， 干完活才跳到你的 main： 

  上电 / 按复位键
        │
        ▼
  地址 0x0000：LJMP ?C_STARTUP     ← 复位向量，永远是第一条指令
        │
        ▼
  ?C_STARTUP（STARTUP.A51 里的启动代码）
        │
        ├─ 1. 设置堆栈指针 SP（默认 0x07，也可以用 STARTUP.A51 顶部改）
        │
        ├─ 2. 清零内部 RAM：把 data 区和 idata 区全部写成 0
        │     （所以 C 语言里"没赋初值的全局变量一定是 0"，靠的就是这一步）
        │
        ├─ 3. 如果有带初值的全局变量，把初值从 Flash 里的"初值表"复制到 RAM
        │     （初值表是链接器生成的，放在 code 区）
        │
        ├─ 4. 初始化 xdata 区（如果你的程序用了 xdata）
        │
        └─ 5. LJMP main               ← 终于进你的程序了
        │
        ▼
  void main(void) 开始执行

第 2 步正好解释了上一篇留下的一个疑问： 「复位不等于断电，可为什么每次复位后全局变量又都变成 0 了？」 因为启动代码主动把它们清零了， 不是硬件自己变的。你在 main 里看到的那个干净世界， 是启动代码替你打扫出来的。

如果把 STARTUP.A51 复制一份加入工程（很多人会这么做， 以便修改堆栈大小），它顶部有几个可以改的常量，含义如下：

常量名 默认值 控制什么
IDATALEN 0x80（128 字节） 启动时要清零多少个字节的 data/idata 空间
XDATALEN 0 启动时要清零多少个字节的 xdata 空间（没用 xdata 就是 0）
PDATALEN 0 pdata 区的清零长度
IBPSTACK / XBPSTACK 0 是否启用"大模式"下的模拟堆栈（新手用不到，保持 0）

还有一个更值得记住的事实：中断向量表也是链接器摆的。 上一篇看 HEX 时，第二行地址 0x0000 处的三个字节是 02 00 03，也就是 LJMP 0x0003； 而 0x000B、0x0013、0x001B、0x0023 这些位置要留给定时器、外部中断、串口。 这些"预留的格子"是谁安排的？是链接器—— 它知道每个中断函数被放在了哪里，于是在固定的向量地址上填一条跳转指令。 如果链接器不知道某个中断函数在哪，程序被打断时就跳不过去。

链接期的报错编号以 L 开头（L 就是 Linker）。 它们几乎都是在说同一件事："东西凑不齐"。

头文件里只放"承诺"，不放"实现"

这一条是链接期报错的最大来源。记住这个分工： 头文件（.h）＝ 菜单（告诉别人有哪些函数、长什么样）； 源文件（.c）＝ 厨房（真正做菜的只有一处）。 菜单可以复印很多份，厨房只能有一个。 所以头文件里写 extern unsigned char g_count;， 而 unsigned char g_count = 0; 要写在某一个 .c 里。

HEX 文件是什么：一行一条记录

链接成功后生成的 .hex 文件，是本文里最值得"拆开看"的东西。 它虽然叫"文件"，但不是二进制—— 用记事本打开它，你会看到一段纯文本，每行都以冒号开头： 

:03000000020003F8
:100003007B00EB232323242FF58275837A08E49363
:10001300F590120022A3DAF60BEBB410E580E17D34
:10002300057FC87EFADEFEDFFADDF622FEFDFBF772
:00000001FF

这就是 Intel HEX 格式： 一种用可打印字符表示二进制数据的文本格式，1960 年代就有了，今天的下载工具仍然在用。 它最大的好处是自带地址、自带校验—— 下载工具不需要你告诉它"这段数据该放在哪"，也不需要担心传输过程中出错没被发现。

一行 = 一条记录。每条记录的格式完全一样， 都是下面这七个部分按固定顺序排下来：

字段 含义 占几个字符 举例
: 记录起始符，每条记录都以它开头 1 :
LL 数据长度：本条记录里有几个数据字节 2（十六进制） 10 = 16 个字节
AAAA 这条数据的起始地址（高字节在前） 4 0003 = 地址 0x0003
TT 记录类型：00 数据 / 01 结束 / 02 扩展段地址 / 03 起始段地址 / 04 扩展线性地址 / 05 起始线性地址 2 00 = 这是数据
DD… 数据本身，字节数正好等于 LL 2 × LL 020003 三个字节
CC 校验和，用来检查整行有没有传错 2 F8

刻进脑子里的写法是：:LLAAAATT[DD…]CC， （严格来说 LL 是数据字节数，所以 LL 本身不算在这 6 个字段里，它只是校验和的一个加数。） 现在把上面第一行按这个格式切开，一个字符一个字符地看： 

      :  03  0000  00  020003  F8
      │   │    │    │    │      │
      │   │    │    │    │      └─ CC 校验和：F8
      │   │    │    │    │
      │   │    │    │    └──────── DD 数据：三个字节 02 00 03
      │   │    │    │
      │   │    │    └───────────── TT 记录类型：00 = 数据记录
      │   │    │
      │   │    └────────────────── AAAA 起始地址：0x0000
      │   │
      │   └─────────────────────── LL 数据长度：3 个字节
      │
      └─────────────────────────── 记录起始符

  三个数据字节 02 00 03 是什么？
  02 是 LJMP 指令的机器码，后面 00 03 是跳转目标地址：0x0003
  连起来读：LJMP 0x0003 —— 复位后从 0x0000 跳到 0x0003 去执行主程序。
  （这正是上一篇里那句"复位向量永远是第一条指令"的证据。）

  记录地址是 0x0000，长度 3 字节 → 这条记录覆盖 0x0000~0x0002。

校验和到底怎么算

校验和 CC 的算法只有两步，非常朴素：

  1. 把这一行里除了冒号和 CC 本身之外的所有字节相加 （也就是 LL、AAAA 的高字节和低字节、 TT、所有 DD 都算进去）；
  2. 只保留和的低 8 位（超过 0xFF 就丢掉进位），然后用 0x100 减去这个低字节，结果就是校验和。

用第一行 :03000000020003F8 验算一遍： 

参与相加的字节：
  03（LL） + 00（地址高） + 00（地址低） + 00（类型） + 02 + 00 + 03（三个数据）

求和：
  0x03 + 0x00 + 0x00 + 0x00 + 0x02 + 0x00 + 0x03 = 0x08

取低 8 位：
  0x08（没超过 0xFF，就是它）

0x100 - 0x08 = 0xF8   ← 与文件里的 CC 完全一致 ✓

（下载工具收到每一行都这么算一遍，算出来和自己带的 CC 不一样，
 就说明这一行在传输中坏了，会让上位机重发。）

再验算一个"有进位"的例子——文件最后一行 :0C00A3009966F00F7F3F1F0F070301005C， 这一行有 12 个数据字节，加出来会超过 0xFF，正好演示"丢掉进位"： 

LL = 0C（12 个字节）  地址 = 00A3   类型 = 00
数据 = 99 66 F0 0F 7F 3F 1F 0F 07 03 01 00

求和：
  0x0C + 0x00 + 0xA3 + 0x00
  + 0x99+0x66+0xF0+0x0F+0x7F+0x3F+0x1F+0x0F+0x07+0x03+0x01+0x00
  = 0x3A4

取低 8 位：
  0x3A4 → 0xA4（高位的 0x3 丢掉）

0x100 - 0xA4 = 0x5C   ← 与文件末尾的 CC 一致 ✓

这两次验算说明了一件事：HEX 文件的每一行都可以被人工核对。 当你怀疑"是不是下载文件坏了"的时候，随便挑一行算一遍， 就能把"文件问题"和"硬件问题"分开。

三种记录类型就够了

Intel HEX 定义了 6 种记录类型，但 51 单片机的程序通常只用得上两种：
00（数据记录）：99% 的行都是它，携带真正的程序数据。
01（结束记录）：永远是 :00000001FF 这一行，表示文件到此结束。
剩下的 02/04 用于超过 64 KB 的地址（51 用不到，STM32 常见）， 03/05 用于指定程序入口点（51 靠复位向量，也用不到）。 所以你打开一个 51 的 HEX，几乎只会看到 TT = 00 和最后一行 TT = 01。

既然有 HEX，为什么还有 BIN

.bin 是另一种输出格式：纯二进制镜像， 里面没有任何地址、长度、校验信息，就是从起始地址开始的一串字节，一个挨一个排下去。 它和 HEX 的关系是"同一批数据的两种包装"：

HEX（Intel HEX） BIN（二进制镜像）
文件本质 文本，能用记事本看（每行 ASCII 字符） 真正的二进制，记事本打开是乱码
体积 约为数据的 2.2 倍（每个字节写成两个字符，还有行开销） 等于数据本身的大小
带地址吗 带，每条记录自带起始地址 不带，默认从 0x0000 连续排列
带校验吗 带，每行一个校验和 不带，坏了只能靠外部手段发现
典型用途 串口 ISP 下载、仿真器下载、发给别人 批量烧录机、需要固定镜像的场合、某些 Bootloader

对新手来说结论很简单：优先用 HEX。 它有地址、有校验，下载工具能自己判断"这段数据该放哪、有没有传坏"； 用 BIN 你就得自己保证"从 0x0000 开始、大小正确"， 一旦芯片里存着旧程序，还可能留下没被覆盖的残余字节。 STC-ISP 两种都认，但默认让你选的就是 HEX。

Keil 工程目录：哪些文件重要，哪些是垃圾

第一次打开一个 Keil 工程文件夹，你会被吓一跳： 明明只写了两个 .c，文件夹里却有二十几个文件。 它们分成四类：工程配置、源文件、中间产物、最终产物。 分清这四类，你就能回答"我的 hex 在哪"和"哪些该提交到 Git"。

文件 / 目录 属于哪一类 作用 要不要提交 Git
Project.uvproj 工程配置 工程的"身份证"：包含哪些源文件、选了什么芯片、编译选项、输出路径。本质是 XML 文本 要（最该提交的就是它）
Project.uvopt 工程配置 个人偏好：断点、打开的窗口、上次的调试设置 不要（每个人都不一样，提交了会互相覆盖）

"找不到 hex"是新手第一大困惑， 所以这里先把答案给了：hex 默认生成在 Objects 目录下（和 .obj 放一起）， 名字默认与工程同名。如果你根本没勾选"生成 HEX"，那它压根不存在—— 见本文常见错误第①条。

路径三不要：不要中文、不要空格、不要放在同步盘里

这一条能省掉你至少两小时的抓狂：
1. 不要用中文路径。有些版本的编译器、以及一些下载工具， 遇到中文目录会报"找不到文件"或直接失败。D:\单片机\课程设计 这种路径请改成 D:\mcu\lesson1。
2. 不要在路径里留空格。D:\my project\led 中间那个空格会让某些命令行工具把路径断成两截。
3. 不要把工程放进 OneDrive、坚果云、百度网盘这类同步目录。 同步软件会在编译过程中锁文件、回滚文件，报"cannot open file"之类的错， 而且报错是随机的、时好时坏，极难排查。
一句话：工程放在 D:\mcu\ 这样的纯英文短路径下， 一个工程一个文件夹。

烧录原理与 ISP：为什么必须冷启动

先统一三个词：烧录 = 下载 = 编程， 说的都是"把电脑上的程序写进芯片的 Flash"。它们之间没有技术差别， 只是不同年代、不同厂家的叫法。

这里有一个很反直觉的事实：你的程序并不是"写进去"就一定在的， 芯片得先"愿意接收"才行。 因为 51 单片机（以 STC 系列为例）自己不会主动去串口取程序， 它内部固化了一段 ISP 引导程序 （In-System Programming，在系统编程）。 这段引导程序住在你擦不掉的区域里，上电后先由它接管： 

                     芯片上电 / 复位
                            │
                            ▼
                  芯片内部的 ISP 引导程序启动
                            │
              ┌─────────────┴─────────────┐
              │                           │
       检测到串口上有人在           串口上没有任何动静
       发"我要下载程序"的握手信号              │
              │                           │
              ▼                           ▼
     进入下载模式：                   直接跳到 Flash 里的
     · 回送芯片型号、固件版本           用户程序执行
     · 擦除用户程序区                        │
     · 逐帧接收 HEX 数据、逐帧校验             ▼
     · 提示"操作成功"                   你的 main() 开始跑
              │
              ▼
     自动跳到刚写入的用户程序，开始运行

这张图直接解释了那个"必须断电再上电"的规矩：

  • 下载模式只在"上电/复位的那一刻"检查。 芯片一旦跳去执行用户程序，就不会再回头看串口了—— 它甚至不知道串口上有人在喊它，因为用户程序里根本没有接收程序的代码。
  • 所以正确的操作顺序是：先在 STC-ISP 里点"下载"， 让电脑开始喊；再给单片机断电、重新上电，让芯片在刚启动的那一瞬间听到喊声。 顺序反了就永远握不上手——因为芯片早就跑进用户程序了。
  • 这也解释了为什么下载成功后不需要再断电： 芯片在写完之后自己就跳进新程序开始运行了。你想让它重新跑一遍， 按一下复位键（复位同样会回到引导程序，但那时电脑不在喊，它就直奔用户程序）。

完整的握手过程，用时间轴看是这样（STC-ISP 上显示的那几行状态文字就是它）：

顺序 谁在动 发生了什么 STC-ISP 上看到什么
1 你 选好型号、串口、HEX 文件，点"下载/编程" 状态栏开始刷"正在检测单片机…"
2 电脑 打开串口，反复发送握手的同步字符 同上，一直在等
3 你 把单片机断电（拔掉电源或按板子上的电源开关） 状态不变，仍在等
4 你 重新上电 仍显示检测中，但马上就要变了
5 芯片 引导程序启动，在串口上听到握手信号，回送自己的型号与固件版本 跳出"单片机型号：STC89C52RC / 固件版本：…"
6 芯片 + 电脑 擦除用户程序区 → 分批接收数据 → 每批校验 进度条走完，出现"操作成功"
7 芯片 跳转到刚写入的程序，开始运行 板子上的 LED 开始按程序闪

"下载波特率"和程序里的波特率是两回事

很多同学会问："我程序里串口波特率写的 9600，STC-ISP 里选的也是 9600， 是不是必须对上？"——不是。 STC-ISP 里的波特率是下载过程用的，是芯片里那段引导程序和你电脑之间的约定； 程序跑起来之后的波特率由你自己的代码决定（见 串口通信 那一篇）。两者互不干涉。
实践建议：下载不稳（老是握手失败、报校验错）时， 把下载波特率降下来（比如从 115200 降到 9600 甚至 4800）， 廉价 USB-TTL 模块在高速率下容易出错，降速往往立刻就好。

串口下载 vs 专用下载器

串口 ISP 下载（STC 系列） 专用编程器
需要什么 一个 USB-TTL 模块（几块钱）+ 芯片自带的引导程序 一台编程器（几十到几百元）
接哪些线 只用 P3.0、P3.1、GND 三根线 要插进编程器的锁紧座，或者接专用接口
能不能在板子上直接下载 能（这就是"在系统编程"的含义），芯片不用拔下来 多数要把芯片拔下来放进编程器
典型芯片 STC89 / STC12 / STC15 / STC8 全系列 AT89C51 这类没有内置 ISP 的老芯片（AT89S51 支持另一种 SPI 接口的 ISP，用 USBasp 之类的下载器）
对新手 首选：便宜、简单、够用 只有买到老式 AT89C51 时才需要

如果你的板子是学习板，通常已经板载了 USB 转串口芯片（CH340、CP2102 之类）， 插一根 USB 线就能下载，连 USB-TTL 模块都不用买。 如果是自己焊的最小系统，就需要一个 USB-TTL 模块， 接线方式在本文 接线那一节 有详细图和表。

最后提醒三个"下载成功但程序不跑"之外的前提条件—— 它们都属于电路层面，不是软件问题：

  • 晶振必须是好的、在起振。 STC89 系列在下载时要用外部晶振计时，晶振没起振就握不上手 （或下载成功但串口波特率全错）。
  • P3.0 / P3.1 不能已经被别的电路"占死"。 如果这两个脚上挂着上拉电阻到 3.3V、或者接了别的芯片的输出， 下载时通信就会被干扰。设计电路时要给下载口留出"干净"的通道。
  • 电源要够。 下载时芯片要擦写 Flash，电流比平时大；用电脑 USB 口直接供电一般没问题， 但如果板子上还挂着继电器、电机驱动之类的负载，就可能出现"下载到一半失败"。

软件仿真 vs 硬件仿真：不接板子能验证到什么

"程序写完就必须烧进板子才能看结果吗？"——不是。 Keil 自带一个软件仿真器， 它能在你的电脑里"假装"有一颗 51 单片机，按指令一条条执行你的程序， 而且不用晶振、不用电源、不用下载。

打开方式：Options for Target → Debug 页 → 选中左侧的 Use Simulator（使用仿真器）， 然后按 Ctrl + F5 开始调试。之后你会用到这几个窗口：

窗口 / 功能 在哪里 能看到什么
单步执行 / 全速运行 调试工具栏（Step、Step Over、Run） 一条指令一条指令地走，观察程序流向
变量观察 View → Watch Windows → Watch 1 把变量名加进去，实时看它的值怎么变
IO 口电平 Peripherals → I/O Ports → Port 1 P1 每一位的勾选框，能直接看到哪个引脚是高、哪个是低
中断开关状态 Peripherals → Interrupt IE、IP、TCON 每一位的值（查"忘了开 EA"最快的地方）
定时器计数器 Peripherals → Timer 0 / Timer 1 TH0/TL0 的实时值、是否溢出
执行时间 调试工具栏上的 sec 显示框 程序跑了多少秒（按指令周期累计，可用来验证延时时长）

仿真器能验证的和不能验证的，界限很清楚：

能验证（放心用仿真） 验证不了（必须上真板）
程序逻辑对不对：循环次数、判断分支、数组下标 LED 的实际亮度、颜色、有没有闪烁感
变量在每一步的值（比在真板上猜快得多） P0 口没接上拉电阻这类驱动能力问题（仿真里永远"看起来正常"）
寄存器配置对不对（IE、TMOD、SCON 的每一位） 按键抖动、接触不良、传感器真实时序
粗略的执行时间（用 sec 显示和机器周期估算） 晶振实际频率偏差、电源波动、电机/继电器的干扰
中断能不能进去（配好中断源后在仿真里跑） 串口和真实电脑/模块的通信是否稳定

仿真前先确认晶振频率设置

Keil 在 Options for Target → Target 页里有一个 Xtal（MHz）输入框， 仿真器就是按这个值把"机器周期"换算成时间的。 它默认值不一定等于你板子上的晶振—— 如果它写 24 MHz 而你的板子是 12 MHz， 仿真里看到的延时、串口波特率会全部差一倍。 养成习惯：建工程后第一件事就是把 Xtal 改成你板子上真实印着的那个数字。

硬件仿真与"最土的调试法"

硬件仿真（在线调试）是指芯片真的在板子上跑， 但你能像仿真器一样设断点、单步、看变量。STC 系列可以用 STC-ISP 把芯片 "设为仿真芯片"，再配合 Keil 通过串口在线调试。 它的代价是：要占用 P3.0/P3.1（串口）、占用一部分芯片资源、 有些型号不支持，而且断点数量有限。做课程设计时用得不多，了解即可。

实际项目里，工程师最常用的其实是第三种办法—— 让芯片把想说的话通过串口发到电脑上。 这就是所谓"串口打印调试"：把变量值发出来， 用串口助手看一眼，比单步调试快得多，也不占用任何调试资源。 代价是要多写几行串口初始化代码（见 串口通信 那一篇）。 没有串口条件时，把变量值显示到数码管上也是同一思路的土办法。

调试方式 需要硬件吗 能看真实电平/时序吗 最适合
软件仿真（Use Simulator） 不需要，有电脑就行 看不到（都是模拟的） 验证逻辑、查变量、查寄存器配置
硬件仿真（STC 仿真芯片） 需要板子和串口 能，但要占用串口资源 逻辑对但真板现象不对时的深入排查
串口打印 / 数码管显示 需要板子 间接反映，靠你判断 看变量的变化趋势、看程序跑到哪一步
万用表 / 示波器量引脚 需要板子和仪表 直接看到 区分"程序没跑"和"硬件接错"

推荐的调试顺序

① 先在软件仿真里把逻辑跑通（这一步不花钱、不接线、不烧片，能排掉 80% 的错误）； ② 再烧到真板上看现象； ③ 现象不对时，先用万用表量引脚电平，判断是"程序没跑对"还是"硬件接错了"； ④ 分不清时再上串口打印看变量。 按这个顺序走，最省时间。

逐根线说明，包括"接错了会怎样"：

USB-TTL 模块引脚 接到板子的哪个脚 作用 接错/不接的后果
TXD 芯片的 P3.0（也就是 RXD，第 10 脚） 模块发数据进芯片——下载时所有程序数据都从这根线进来 和 RXD 接反了就永远握不上手（最常见的错误）
RXD 芯片的 P3.1（也就是 TXD，第 11 脚） 芯片回话给模块——型号、固件版本、每一步的应答 不接的话 STC-ISP 可能能开始下载但中途失败，或者根本检测不到
GND 板子的 GND 给两边一个共同的"0V 参考点" 不接一定失败。没有共同的地，双方看到的"高电平"含义都不一样
5V（VCC） 一般不要接 给板子供电 如果板子已有独立电源（下载器供电 + 板子电源同时接），两路电源会互相"打架"， 轻则不稳定，重则芯片发热
3V3 不接 3.3V 输出 接到 5V 系统上可能烧掉模块或芯片
DTR / RTS 不接（新手用不到） 有些模块用它自动复位（Arduino 那样），51 的串口 ISP 用不到 接了可能造成意外复位

下载时的操作顺序（顺序错了必失败）

  1. USB-TTL 模块插到电脑上（板子电源先不打开也行）。
  2. 按上表接好 TXD→P3.0、RXD→P3.1、GND→GND 三根线。
  3. 打开 STC-ISP：选芯片型号、选串口号、选好 HEX 文件。
  4. 点「下载 / 编程」——此时电脑开始不停地喊。
  5. 等待状态栏出现「正在检测单片机…」。
  6. 给板子断电（拔电源、关电源开关，不是按复位键）。
  7. 重新上电——这一刻芯片会听到喊声并回应。
  8. 看到「操作成功」后程序已经在跑了，不需要再断电。

三个"接得很像但一定失败"的接线

① TXD 接 TXD、RXD 接 RXD。 这是最常见的错误。两个"喇叭"对着喊，谁也听不见谁。 判断方法：看模块上的丝印，TXD 那根线一定要落在芯片的 P3.0 上。
② 忘了共地。只接了 TXD、RXD 两根信号线就点下载， 症状是"时好时坏、偶尔能连上"。信号线再多，没有共同的地也白搭。
③ 板子有 USB 供电接口，又用 USB-TTL 给板子供电。 两路 5V 并联，轻则下载不稳定，重则 USB 口保护、芯片发热。 规矩很干脆：只让一方供电，其它设备一律只共地。

怎么快速判断"模块到底通没通"

把 USB-TTL 模块的 TXD 和 RXD 直接短接（只连模块自己的两个脚，不接板子）， 然后打开任意串口助手，随便发一串字符—— 如果能原样收回来，说明模块、驱动、串口都正常， 问题一定出在板子那一侧（接线、供电、晶振、冷启动）。 这个"自发自收"测试是排查串口问题的第一步，30 秒就能做完。

真实 HEX 逐行批注

从这张表能读出三个"意外的知识"：

  • 第一条记录只有 3 个字节。 为什么不是 16 个？因为复位向量只需要一条 LJMP （机器码 02 + 两字节地址 = 3 字节）， 而 Keil 的链接器习惯从 main 所在的代码段开始按 16 字节切块。 第一条记录的长度是"实际需要多少就写多少"，不是固定的。
  • 最后一条只有 12 个字节（LL = 0C）。 因为数据总量是 175 字节，前面按 16 字节切完剩下 12 字节， 记录长度自然就变成 0C。这也解释了为什么 LL 字段存在——每条记录的长度不一样。
  • 地址 0x0003~0x002A 本来是留给中断向量的，这里被主程序占了。 51 的 0x0003、0x000B、0x0013、0x001B、0x0023、0x002B 分别是 外部中断 0、定时器 0、外部中断 1、定时器 1、串口、定时器 2 的入口地址， 每个占 8 个字节。这个程序完全不用中断，所以主程序直接从 0x0003 一路写下去， 把这些格子"借用"了。
    反过来说：如果你后来给这个程序加了中断函数， 主程序就必须往后挪，把向量区让出来。——这正是链接器的工作， 它会自动处理，你只需要知道这 8 字节一格的规矩是怎么来的。

【第 2 条】:100003007B00EB232323242FF58275837A08E49363

为什么"记录边界"会把指令切成两半

你会发现第 3 条记录的最后多出一个孤零零的 7D， 而它的搭档在下一行的开头。 原因很简单：链接器是按固定长度（这里是 16 字节）切块的， 它不管指令的边界在哪。7D 34 是 MOV R5,#34H 这一条两字节的指令， 正好被切在中间。
这不影响程序运行—— 下载工具会按地址把数据重新拼成连续的内存，芯片看到的仍然是完整的一条指令。 这也顺便说明了 HEX 里"地址"字段的价值：有了它，记录怎么切都无所谓。

常见错误与排查

下面十条覆盖了从建工程到下载完成这条路上绝大多数会让新手卡住的地方。 格式还是老三样：报错原文（或现象）→ 原因 → 解决。 报错编号和原文来自 Keil C51，不同版本可能略有差异，但只要抓住关键字就能对上号。

① 编译通过了，可 Objects 里就是没有 .hex

现象：Build Output 显示 0 Error(s), 0 Warning(s).， 但打开 Objects 目录只有 .obj、 .lnp，没有 LedBlink.hex。 注意 Build Output 里也不会出现 creating hex file from … 这一行。
原因：「生成 HEX 文件」不是默认选项，必须手动勾选。 编译器默认只产出 .obj（给链接器和仿真器用）， 它并不知道你要拿去烧片。
解决：Options for Target → Output 页 → 勾选 Create HEX File → 重新按 F7 编译。之后 Build Output 最后会多出一行 creating hex file from ".\Objects\LedBlink"...， 看到这一行才算成功。

② *** FATAL ERROR L250: CODE SIZE LIMIT IN RESTRICTED VERSION EXCEEDED

报错原文：*** FATAL ERROR L250: CODE SIZE LIMIT IN RESTRICTED VERSION EXCEEDED
原因：你用的是没注册的 Keil 评估版，链接器对代码大小有硬性限制 （大约 2 KB 量级）。注意它报在链接阶段（L 开头）， 不是你的 C 语法有问题。程序一变大就必然撞上这堵墙。
解决：① 用学校/公司提供的正版授权； ② 换用免费版本或替代工具链； ③ 临时把 printf 之类的库函数去掉、把代码精简到限制以下。 不要去找来路不明的"破解补丁"——这是最常见的中毒途径。

③ *** ERROR L127: UNRESOLVED EXTERNAL SYMBOL

报错原文： *** ERROR L127: UNRESOLVED EXTERNAL SYMBOL
SYMBOL: DELAY_MS MODULE: main.obj
原因：你在 main.c 里调用了 Delay_ms()，头文件里也有声明， 但实现它的 delay.c 没有加进工程—— 编译器看得见"承诺"，链接器找不到"实现"。
解决：右键 Project 窗口里的 Source Group 1 → Add Existing Files to Group 'Source Group 1' → 选中 delay.c 加进来，重新编译。
同类现象：函数名大小写不一致（定义了 delay_ms 却调用 Delay_ms）也会报同一个错； C 语言区分大小写。

④ Target not created / 按了编译却几乎什么都没发生

现象：Build Output 最后一行是 Target not created， 或者按 F7 之后一闪而过、像是没编译。
原因：两种情况——① 编译有错误，自然没有目标文件； ② 工程里根本没有源文件（新建了 main.c 但没有 Add 到 Source Group 里，Keil 不知道要编译谁）。
解决：先看 Project 窗口里 Source Group 1 下面有没有你的 main.c；没有就 Add 进来。 有的话，往上翻 Build Output 找第一条 error。

⑤ STC-ISP 一直检测不到单片机

现象：点了「下载/编程」之后状态栏一直显示 正在检测单片机…，等多久都没反应。
原因（按出现频率排序）： ① 没有冷启动——按了复位键、或者根本没断电，芯片早就跑进用户程序了； ② TXD/RXD 没有交叉（模块的 TXD 没接到芯片的 P3.0）； ③ 没有共地； ④ 串口选错（电脑上可能有好几个 COM 口），或者串口被串口助手等软件占用着； ⑤ USB-TTL 驱动没装好；⑥ 芯片型号选错。
解决：按上面六条逐条排。 最快的定位手段是「TXD 与 RXD 短接的自发自收」测试： 能收回来就说明电脑侧全正常，问题在板子那一侧； 收不回来就是电脑侧的事（驱动、串口选择、线材）。

⑥ 下载显示「操作成功」，但板子毫无反应

现象：STC-ISP 明确写着操作成功，LED 却一动不动。
原因：程序确实写进去了，问题在别处。常见有三种： ① 程序逻辑本身的问题（延时算错、忘了写循环、把灯写成了常灭）； ② 电路问题（LED 极性接反、限流电阻过大、共阴共阳搞反、 P0 口没接上拉电阻）； ③ 芯片型号选错（内部时钟/复位相关的出厂配置不一样）。
解决：先拿万用表量对应引脚——引脚电平在变，就说明程序在跑，去查电路； 引脚不动，就说明程序有问题，回去查代码。 这一步能把"软件问题"和"硬件问题"彻底分开，是最高效的一刀。

⑦ error C129: missing ';' before …

报错原文：main.c(9): error C129: missing ';' before 'Delay_ms'
原因：上报的那一行并不是真正出错的行—— 编译器是在读到第 9 行时才"发现前面少了个分号"， 真正缺分号的通常是第 8 行（上一行）。 另一个高频原因是中文分号：它长得像分号， 但编码完全不同，编译器不认识。
解决：检查上一行的行尾；把输入法切成英文再补分号。 如果报的是 error C100: unprintable character 0xA3 skipped， 那就更明确是中文标点了。

⑧ 中文路径 / 带空格的路径导致编译失败

现象：代码一个字没改，换台电脑或者改了个文件夹名字就编译不过， 报类似"打不开某个文件"、cannot open file， 或者链接时报找不到 .obj。
原因：路径里出现了中文或空格。 Keil 会用命令行方式去调用编译器和链接器， 路径里的空格会把命令断成两截，中文在个别版本上会编码错误。
解决：把整个工程移到纯英文、无空格的路径下， 例如 D:\mcu\led，重新编译。 这也是本文反复强调"路径三不要"的原因—— 它不是洁癖，是省时间。

⑨ FATAL ERROR C318: CAN'T OPEN FILE 'REG52.H'

报错原文：FATAL ERROR C318: CAN'T OPEN FILE 'REG52.H'
原因：编译器找不到这个头文件。三种可能： ① Keil 安装不完整（C51\INC 目录下的头文件被删了或没装全）； ② 工程选了别的架构的器件，包含路径不对； ③ 你自己写的头文件放在了错误的目录里。
解决：① 用 Keil 自带的 reg52.h， 别自己另存一份改；② 检查 Options for Target → C51 页的 Include Paths； ③ 实在找不到，就照 上一篇 教的办法，自己在文件开头用 sfr 声明需要的寄存器， 一个头文件都不依赖。

⑩ 改了优化等级，软件延时突然不准了

现象：同一个 Delay_ms(500)， 优化等级为 0 时感觉是对的，把优化调到最高之后灯闪得像疯了一样， 或者干脆看不出闪。
原因：空循环里那两个计数变量没有被真正"使用"， 优化器认为它们没有副作用，就把整段循环删掉了（甚至删掉了整个函数调用）。 这不是编译器有 bug，是它在严格按 C 语言的规则做优化。
解决：① 把循环变量声明为 volatile （告诉编译器"这个变量会变，别动它"）； ② 在循环里插入 _nop_() 这类空操作； ③ 最正规的做法：用定时器做延时，不靠数指令。 做正经项目时第三条才是答案，前两条只是应急。

⑪ WARNING L15: MULTIPLE CALL TO SEGMENT（进阶预警）

报错原文：*** WARNING L15: MULTIPLE CALL TO SEGMENT
SEGMENT: ?PR?_DELAY_MS?DELAY CALLER1: ?C_C51STARTUP CALLER2: ?PR?T0_ISR?MAIN
原因：同一个函数既在主程序里调用、又在中断服务函数里调用。 51 的普通函数默认是"不可重入"的——它的局部变量放在固定的内存位置上， 如果主程序正调到一半被中断打断，中断里又调同一个函数， 两边的局部变量就会互相覆盖（这就是"重入"问题）。
解决：① 最简单的办法：不要在中断里调用那些耗时的、主程序也在调的函数， 中断里只做最少的动作（置个标志位，让主程序去干活）； ② 确实需要就在函数定义后加 reentrant 关键字 （会占用额外的栈空间，51 上要谨慎）； ③ 复制一份专用的小延时函数给中断用。 这条是警告不是错误，但它指出的是真实存在的隐患，别习惯性忽略。

排查纪律：四条能省下大量时间的习惯

① 从第一条错误开始改。 一个漏分号可能引发十几条报错，后面那些大多是"连带的"。 改完第一条重新编译，往往只剩一条。
② 报错行号不是出错行。 语法类报错（C129）要往上看一行甚至几行。
③ 分清阶段。 C 开头＝编译器（C 语言本身的问题）、 A 开头＝汇编器、 L 开头＝链接器（文件/符号/容量问题）。 知道是哪一段出的错，搜索方向完全不同。
④ 把 Build Output 全选复制到文本框里再搜。 搜错误编号比一行行读快得多，也方便贴出来问别人。

小结与自检

这一篇讲的是"代码从文本变成芯片里的电平"的完整路径。 把它压缩成十句话：

  • 一条 C 语句要经过预处理 → 编译 → 汇编 → 链接四道工序， 才变成能被芯片执行的机器码。
  • 预处理器只做三件事：贴入（#include）、替换（#define）、筛选（#ifdef）； 它不懂 C 语法，所以宏定义末尾多一个分号会引发莫名其妙的错误。
  • 编译产出的 .lst 文件里有"C 与汇编的逐行对照"， 这是理解"我的代码到底变成了什么"最快的窗口。
  • 优化等级会改变程序的机器码，也会改变软件延时的时长； 会被中断改的变量、或用来延时的变量，必须加 volatile。
  • 链接器做三件事：合并、分配地址、填空； 它还负责把启动代码和中断向量摆好。
  • STARTUP.A51 是复位后跑的第一段代码， 它设置堆栈、清零所有内部 RAM，然后才跳到 main—— 这就是"复位后全局变量又变成 0"的真正原因。
  • HEX 文件是文本格式，格式为 :LLAAAATT[DD…]CC， 每行自带地址和校验和；校验和 = 0x100 减去该行所有字节之和的低 8 位。
  • Keil 工程目录里，该提交 Git 的是源码 + .uvproj， Objects/、Listings/、 .uvopt 都可以丢弃。 工程路径要纯英文、无空格、不进同步盘。
  • 烧录 = 下载 = 编程。51（STC 系列）靠芯片内部的 ISP 引导程序接收程序，而它只在上电/复位的一瞬间检查串口—— 所以必须"先点下载、再断电上电"（冷启动）。
  • 调试的第一站是软件仿真（Use Simulator）， 但 P0 上拉、驱动能力、按键抖动这类问题只有真板能暴露； 分不清是软件还是硬件时，先用万用表量引脚。

五道自检题

别翻上面找答案，先自己写下来，再对照后面的参考答案：

  1. #define LED_ON P1 = 0xFE; 这样写为什么危险？把它用在 if (key == 0) LED_ON else … 里会被替换成什么样？
  2. 一个 HEX 记录是 :04001000A1B2C3D4??， 请算出 ?? 应该是多少。
  3. 为什么会出现"编译通过、但 Objects 里没有 hex"？ 怎么在 Build Output 里一眼看出到底有没有生成 hex？
  4. 链接报 L127: UNRESOLVED EXTERNAL SYMBOL， 列出两种可能的原因和对应的解决办法。
  5. 点完「下载」之后，为什么必须给板子断电再上电？ 按复位键行不行？为什么下载成功之后不需要再断一次电？

参考答案（先自己做完再看）

第 1 题：宏是纯文本替换，末尾那个分号会一起被替换进去， 于是变成 if (key == 0) P1 = 0xFE;; else …—— 多出一个空语句，else 就找不到它的 if 了， 编译器报 error C141: syntax error near 'else' 一类的语法错误。 正确写法是 #define LED_ON() (P1 = 0xFE) 这类不带末尾分号的形式。
第 2 题：参与相加的字节是 04 + 00 + 10 + 00 + A1 + B2 + C3 + D4。 逐段加：0x04+0x00+0x10+0x00 = 0x14； 0xA1+0xB2 = 0x153；0xC3+0xD4 = 0x197； 合计 0x14 + 0x153 + 0x197 = 0x2FE。 取低 8 位 = 0xFE； 0x100 − 0xFE = 0x02。 所以 ?? = 02， 整行是 :04001000A1B2C3D402。
第 3 题：因为「生成 HEX 文件」需要手动勾选 （Options for Target → Output → Create HEX File）， 默认只产出 .obj。 判定方法：看 Build Output 最后有没有 creating hex file from ".\Objects\…" 这一行—— 有就是生成了，没有就是没勾。
第 4 题：① 实现这个函数的 .c 文件 没有加入工程 → 右键 Source Group → Add Existing Files； ② 函数名大小写/拼写不一致（声明的是 Delay_ms，定义的是 delay_ms）→ 统一名字。 （补充：只写了声明没写函数体，也是同一个报错。）
第 5 题：因为芯片内部的 ISP 引导程序只在上电/复位那一瞬间 检查串口上有没有人在请求下载。程序一旦跑起来，就不会再回头看串口了。 按复位键同样能让芯片回到引导程序，但很多学习板/下载工具的 自动复位电路并不可靠，而且 STC-ISP 的握手机制要求"先喊再上电"这个顺序， 所以断电再上电（冷启动）是最稳、最通用的做法。 下载成功后不需要再断电，是因为芯片写完就自己跳到新程序开始运行了。
